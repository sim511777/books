지금까지는 주로 커밋을 "만드는" 쪽에 집중했다. 하지만 실무에서는 새 커밋을 만드는 시간 못지않게, 이미 쌓인 커밋들을 뒤져서 "이 버그가 언제 들어왔는지", "이 줄은 누가 왜 이렇게 고쳤는지", "지난주에 무슨 작업을 했는지"를 확인하는 시간도 많다. 저장소의 커밋 히스토리는 프로젝트가 걸어온 길을 그대로 기록한 로그이고, Git은 이 로그를 다양한 기준으로 잘라보고 검색할 수 있는 여러 명령을 제공한다.

이 책은 명령행 중심으로 진행한다. `gitk`나 GitHub Desktop, SourceTree, GitKraken, VS Code의 Git 통합 화면 같은 GUI 도구들도 히스토리를 그래프로 보여주는 데 유용하지만, 결국 그 화면들이 하는 일은 이 장에서 배울 `git log`, `git show`, `git blame`, `git diff` 같은 명령들이 만들어내는 정보를 그림으로 옮겨 그린 것에 지나지 않는다. 명령행에 먼저 익숙해지면 어떤 GUI 도구를 쓰더라도 그 도구가 지금 무엇을 보여주고 있는지 정확히 이해할 수 있다.

## 7.1 git log로 히스토리 훑어보기

`git log`는 현재 브랜치의 커밋을 최신 순서로 나열해 보여주는 가장 기본적인 히스토리 조회 명령이다.

```bash
git log
```

옵션 없이 실행하면 각 커밋마다 커밋 해시, 작성자, 날짜, 커밋 메시지가 다음과 같은 형식으로 출력된다.

```
commit 8f2a3c1e9d4b5f6a7c8d9e0f1a2b3c4d5e6f7a8b
Author: 홍길동 <hong@example.com>
Date:   Sun Aug 30 09:12:03 2026 +0900

    로그인 실패 메시지를 한국어로 변경
```

커밋 수가 많은 저장소에서는 이 기본 출력이 너무 장황할 수 있다. 자주 함께 쓰이는 몇 가지 옵션을 짚어보자.

```bash
# 커밋마다 한 줄로 축약해서 보여준다
git log --oneline

# 브랜치가 갈라지고 합쳐진 모양을 그래프로 함께 보여준다
git log --oneline --graph --all

# 최근 5개 커밋만 본다
git log -5
```

`--oneline`은 커밋 해시를 짧게 줄이고 메시지의 첫 줄만 보여주므로, 전체 흐름을 빠르게 훑어볼 때 가장 먼저 손이 가는 옵션이다. 이 장의 뒤에 나오는 예제들도 대부분 `--oneline`을 곁들여서 출력을 짧게 유지한다.

## 7.2 조건으로 커밋 걸러내기

프로젝트가 커지면 "누가", "언제", "어떤 내용으로" 커밋했는지를 기준으로 히스토리를 좁혀볼 일이 자주 생긴다. `git log`는 이런 조건을 옵션으로 지정할 수 있다.

### 7.2.1 작성자로 걸러내기: --author

```bash
git log --author="홍길동"
```

`--author`는 정규 표현식을 지원하므로, 이름의 일부만 적어도 그 문자열을 포함하는 작성자의 커밋을 모두 찾아준다. 이메일 주소로 찾고 싶다면 다음과 같이 적으면 된다.

```bash
git log --author="@example.com"
```

### 7.2.2 기간으로 걸러내기: --since, --until

```bash
# 최근 2주 동안의 커밋
git log --since="2 weeks ago"

# 특정 날짜 범위의 커밋
git log --since="2026-08-01" --until="2026-08-31"

# 오늘 아침 이후의 커밋
git log --since="9am"
```

`--since`와 `--until`은 `2026-08-01`처럼 명확한 날짜뿐 아니라 `"2 weeks ago"`, `"yesterday"`처럼 사람이 읽기 편한 상대 표현도 받아들인다. `--after`, `--before`는 각각 `--since`, `--until`의 다른 이름으로, 동작은 완전히 같다.

### 7.2.3 커밋 메시지로 걸러내기: --grep

```bash
git log --grep="로그인"
```

`--grep`은 커밋 메시지 안에서 주어진 패턴을 찾는다. 이 옵션도 정규 표현식을 지원하므로, 좀 더 정교한 검색도 가능하다.

```bash
# "버그" 또는 "수정"이 들어간 커밋 메시지
git log --grep="버그\|수정"

# 대소문자를 구분하지 않고 검색
git log --grep="fix" -i
```

### 7.2.4 조건 조합하기

`--author`, `--grep`처럼 서로 다른 종류의 조건을 함께 주면 기본적으로 **모든 조건을 동시에 만족**하는 커밋만 찾는다.

```bash
# 홍길동이 작성했으면서, 메시지에 "로그인"이 들어간 커밋
git log --author="홍길동" --grep="로그인"
```

반면 같은 종류의 조건(`--grep`)을 여러 번 주면 기본적으로 **그 중 하나라도 만족**하면 걸린다.

```bash
# 메시지에 "버그" 또는 "오류"가 포함된 커밋(OR 조건)
git log --grep="버그" --grep="오류"

# 위 두 패턴을 모두 포함해야 하는 커밋으로 바꾸고 싶다면 --all-match를 추가한다
git log --grep="버그" --grep="오류" --all-match
```

## 7.3 변경 내용까지 함께 보기: git log -p

`git log`는 기본적으로 커밋 메타데이터(해시, 작성자, 날짜, 메시지)만 보여주고 실제로 어떤 줄이 바뀌었는지는 보여주지 않는다. 각 커밋이 만들어낸 변경 내용, 즉 패치까지 함께 보고 싶다면 `-p`(또는 `--patch`) 옵션을 쓴다.

```bash
git log -p
```

커밋이 많은 저장소에서는 출력이 매우 길어지므로, 범위를 좁혀서 쓰는 경우가 많다.

```bash
# 최근 3개 커밋의 변경 내용까지 함께 본다
git log -p -3

# 특정 파일에 대한 커밋과 변경 내용만 본다
git log -p -- src/login.js
```

파일별로 몇 줄이 추가되고 삭제됐는지 요약만 보고 싶다면 `-p` 대신 `--stat`을 쓸 수도 있다.

```bash
git log --stat -3
```

## 7.4 파일 이름 변경 추적하기: git log --follow

Git은 파일 이동이나 이름 변경을 별도의 메타데이터로 기록하지 않고, 내용이 비슷한 삭제·추가 쌍을 나중에 비교해서 "이름이 바뀐 것 같다"고 추론한다. 그래서 파일 이름을 바꾼 뒤 그 파일의 히스토리를 그냥 조회하면, 이름이 바뀌기 이전의 커밋들은 보이지 않는다.

```bash
git log -- src/utils.js
```

파일 이름 변경 이전의 히스토리까지 이어서 보고 싶다면 `--follow`를 함께 준다.

```bash
git log --follow -- src/utils.js
```

`--follow`는 반드시 파일 경로 하나를 지정할 때만 의미가 있고, 여러 파일이나 디렉터리에는 적용되지 않는다. 이름이 바뀐 시점의 커밋에서 변경 내용을 함께 보고 싶다면 `-p`와 조합하면 된다.

```bash
git log --follow -p -- src/utils.js
```

## 7.5 커밋 해시와 상대 참조

### 7.5.1 커밋 해시와 축약 해시

Git의 모든 커밋은 그 내용(부모 커밋, 트리, 작성자, 메시지 등)을 바탕으로 계산한 40자리 SHA-1 해시로 식별된다.

```
8f2a3c1e9d4b5f6a7c8d9e0f1a2b3c4d5e6f7a8b
```

이 40자리를 매번 다 타이핑할 필요는 없다. 저장소 안에서 다른 커밋과 헷갈리지 않을 만큼만 앞자리를 잘라서 써도 Git이 알아서 찾아준다. 보통 7~8자 정도면 충분하다.

```bash
git show 8f2a3c1
```

`git log --oneline`이 커밋마다 이 축약 해시를 보여주는 것도 같은 이유다. 저장소가 아주 커져서 축약 해시가 겹칠 위험이 생기면 Git이 자동으로 더 긴 자릿수를 출력한다.

### 7.5.2 HEAD와 상대 참조

`HEAD`는 "지금 체크아웃되어 있는 커밋"을 가리키는 특별한 이름이다. 보통은 현재 브랜치의 가장 최근 커밋을 가리킨다. 매번 해시를 찾아 적는 대신 `HEAD`를 기준으로 상대적인 위치를 가리키는 문법을 쓰면 훨씬 편하다.

```bash
# 바로 이전 커밋
git show HEAD^
git show HEAD~1

# 두 커밋 이전
git show HEAD~2

# 세 커밋 이전
git show HEAD~3
```

`HEAD^`와 `HEAD~1`은 같은 커밋을 가리킨다. `^`를 연달아 붙이거나(`HEAD^^`), `~` 뒤에 숫자를 붙이는(`HEAD~2`) 두 표기 모두 부모를 거슬러 올라가는 문법인데, 일반 커밋처럼 부모가 하나뿐인 경우에는 결과가 같다.

차이는 **병합 커밋**을 만났을 때 드러난다. 병합 커밋은 부모가 둘 이상이다. `HEAD^1`(또는 `HEAD^`)은 첫 번째 부모, `HEAD^2`는 두 번째 부모를 가리키며, `HEAD~N`은 항상 첫 번째 부모만 따라가면서 N단계를 거슬러 올라간다.

```bash
# 병합 커밋의 두 번째 부모(병합되어 들어온 브랜치 쪽) 보기
git show HEAD^2

# 첫 번째 부모를 두 단계 거슬러 올라간 커밋
git show HEAD~2
```

브랜치 이름이나 태그도 `HEAD`처럼 상대 참조의 기준으로 쓸 수 있다.

```bash
git show main~1
git show v1.0^
```

## 7.6 특정 커밋 자세히 보기: git show

`git show`는 하나의 커밋을 지정해서 그 커밋의 메타데이터와 변경 내용(패치)을 함께 보여준다. 앞서 나온 `git log -p -1 <commit>`과 사실상 같은 정보를 보여주지만, 커밋 하나만 살펴볼 때는 `git show`가 더 짧고 직관적이다.

```bash
git show 8f2a3c1
git show HEAD
git show HEAD~2
```

`git show`는 커밋뿐 아니라 특정 시점의 파일 내용을 확인하는 데도 쓸 수 있다. `커밋:경로` 형식으로 지정하면 그 커밋 시점의 파일 전체 내용을 출력한다.

```bash
# HEAD 시점의 login.js 파일 전체 내용
git show HEAD:src/login.js

# 세 커밋 전 시점의 같은 파일
git show HEAD~3:src/login.js
```

## 7.7 각 줄의 마지막 수정자 찾기: git blame

"이 줄은 대체 왜 이렇게 되어 있지?"라는 의문이 들 때 `git blame`을 쓰면 파일의 각 줄이 마지막으로 어느 커밋에서 바뀌었는지 한눈에 볼 수 있다.

```bash
git blame src/login.js
```

출력은 줄마다 축약 해시, 작성자, 날짜, 그리고 원래 줄 내용을 붙여서 보여준다.

```
8f2a3c1e (홍길동 2026-08-12 10:03:21 +0900  1) function login(id, password) {
a4d7e2b9 (김철수 2026-08-20 15:41:07 +0900  2)   if (!id || !password) {
a4d7e2b9 (김철수 2026-08-20 15:41:07 +0900  3)     return false;
```

파일 전체가 아니라 특정 줄 구간만 보고 싶다면 `-L` 옵션에 시작줄,끝줄을 지정한다.

```bash
git blame -L 10,25 src/login.js
```

`git blame`은 이름 그대로 "누구 탓인지 찾는" 도구처럼 들리지만, 실제로는 "이 코드를 왜 이렇게 짰는지 알고 있는 사람이 누구인지, 그 배경이 담긴 커밋이 무엇인지" 찾는 도구에 가깝다. 몇 가지 유용한 옵션을 더 살펴보자.

```bash
# 공백만 바뀐 줄은 무시하고 그 이전 수정자를 찾는다
git blame -w src/login.js

# 이메일 주소를 함께 표시한다
git blame -e src/login.js

# 코드가 같은 커밋 안에서 다른 파일로 옮겨지거나 복사된 경우까지 추적한다
git blame -C src/login.js
```

`-w`는 들여쓰기를 정리하거나 줄 끝 공백을 지우기만 한 커밋 때문에 진짜 수정자를 놓치는 상황을 막아준다. `-C`는 코드를 다른 파일에서 그대로 옮기거나 복사해온 경우, 옮기기 전의 원래 작성자까지 찾아 올라간다.

## 7.8 커밋 사이의 차이 비교하기: git diff

`git diff`는 두 시점 사이에 무엇이 달라졌는지 보여주는 명령이다. 지금까지는 작업 디렉터리나 스테이징 영역과 비교하는 용도로 써봤겠지만(이전 장 참고), 커밋 두 개를 직접 지정해서 그 사이의 차이를 볼 수도 있다.

```bash
git diff <commit1> <commit2>
```

예를 들어 어제 커밋과 오늘 커밋 사이에 무엇이 바뀌었는지 확인하려면 다음과 같이 쓴다.

```bash
git diff HEAD~5 HEAD
```

이 명령은 `HEAD~5` 시점의 상태에서 `HEAD` 시점의 상태로 가는 동안 생긴 변경 내용을 보여준다. 두 인자의 순서를 바꾸면 diff의 +/- 방향도 뒤집힌다는 점에 유의한다.

특정 파일 하나에 대해서만 두 커밋 사이의 차이를 보고 싶다면 경로를 덧붙인다.

```bash
git diff HEAD~5 HEAD -- src/login.js
```

두 브랜치 사이의 차이를 볼 때도 문법은 똑같다.

```bash
git diff main feature/login
```

참고로 `git diff A B`와 `git diff A..B`는 완전히 같은 의미다. 반면 `git diff A...B`(점 세 개)는 "A와 B의 공통 조상부터 B까지의 변경"을 보여주는 다른 명령이라서, 두 브랜치가 각자 다른 커밋을 쌓아온 상황에서는 결과가 달라진다. 헷갈리기 쉬운 부분이므로, 특별한 이유가 없다면 이 장에서 소개한 두 커밋을 직접 나열하는 형태(`git diff A B`)에 먼저 익숙해지길 권한다.

## 요약

- `git log`는 히스토리를 조회하는 기본 명령이며, `--oneline`, `--graph`처럼 출력을 보기 좋게 다듬는 옵션과 함께 자주 쓴다.
- `--author`, `--since`/`--until`, `--grep`은 각각 작성자, 기간, 커밋 메시지를 기준으로 히스토리를 좁혀준다. 서로 다른 종류의 조건은 AND로, 같은 종류를 여러 번 주면 기본적으로 OR로 결합된다.
- `git log -p`는 각 커밋이 만들어낸 실제 변경 내용(패치)까지 함께 보여주며, `--follow`를 곁들이면 이름이 바뀐 파일의 이전 히스토리까지 이어서 볼 수 있다.
- 커밋은 40자리 SHA-1 해시로 식별되지만 앞자리 몇 글자(축약 해시)만으로도 대부분 충분하다. `HEAD`, `HEAD^`, `HEAD~N` 같은 상대 참조를 쓰면 해시를 몰라도 커밋을 가리킬 수 있다.
- `git show <commit>`은 커밋 하나의 메타데이터와 변경 내용을 보여주고, `git show <commit>:<경로>`는 그 시점의 파일 전체 내용을 보여준다.
- `git blame <file>`은 파일의 각 줄을 마지막으로 수정한 커밋을 찾아준다. `git diff <commit1> <commit2>`는 두 커밋 사이의 차이를 비교한다.

## 연습문제

1. 최근 1주일 동안 `"버그"`라는 단어가 포함된 커밋 메시지 중에서, 본인(자신의 이름 또는 이메일)이 작성한 커밋만 찾는 `git log` 명령을 작성하시오.
2. `git log --grep="A" --grep="B"`와 `git log --grep="A" --grep="B" --all-match`의 결과가 어떻게 다른지 설명하시오.
3. 어떤 파일을 `old.js`에서 `new.js`로 이름을 바꾼 뒤, `new.js`의 전체 히스토리(이름 변경 이전 커밋 포함)를 조회하려면 어떤 명령을 써야 하는지, 그리고 왜 `--follow` 없이는 이전 히스토리가 보이지 않는지 설명하시오.
4. 어떤 병합 커밋에서 `HEAD^1`과 `HEAD^2`가 각각 무엇을 가리키는지, 그리고 `HEAD~2`와 `HEAD^2`가 왜 서로 다른 커밋을 가리킬 수 있는지 설명하시오.
5. 프로젝트의 `config.js` 파일에서 특정 설정 값이 언제, 누구에 의해, 어떤 이유로 지금의 값으로 바뀌었는지 알아내고 싶다. 이 장에서 배운 명령들을 순서대로 사용해 조사하는 절차를 서술하시오.

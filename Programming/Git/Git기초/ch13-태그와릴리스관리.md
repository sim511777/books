지금까지 브랜치를 만들고, 커밋을 쌓고, 다른 브랜치와 병합하는 과정을 다루었습니다. 브랜치는 작업이 진행되는 동안 계속 앞으로 나아가는 흐름을 표현하는 도구였습니다. 그런데 개발을 하다 보면 "지금 이 시점의 코드가 정확히 어떤 상태였는지"를 흔들리지 않는 하나의 이름으로 고정해두고 싶은 순간이 옵니다. 예를 들어 "이 커밋이 바로 우리가 고객에게 배포한 1.0 버전이다"라거나 "이 커밋 시점에 QA 테스트를 통과했다" 같은 사실을, 나중에 언제 다시 찾아봐도 헷갈리지 않게 표시해두고 싶은 경우입니다.

이런 용도에 커밋 해시를 그대로 외워서 쓸 수도 있겠지만, `a3f9c21`처럼 사람이 기억하기 어려운 문자열보다는 `v1.0.0`처럼 의미가 담긴 이름을 붙이는 편이 훨씬 실용적입니다. 이번 장에서는 바로 이 역할을 하는 Git의 **태그(tag)** 기능을 다룹니다. 태그의 두 가지 종류, 태그를 원격 저장소에 공유하는 방법, 그리고 태그를 기반으로 한 버전 표기 관례와 GitHub의 릴리스 기능까지 살펴보겠습니다.

## 13.1 태그란 무엇인가

태그는 특정 커밋 하나를 가리키는 고정된 이름표입니다. 브랜치와 마찬가지로 태그도 "어떤 이름이 어떤 커밋을 가리키는가"라는 정보에 지나지 않지만, 둘 사이에는 결정적인 차이가 있습니다.

- **브랜치는 움직입니다.** 어떤 브랜치 위에서 새 커밋을 만들면, 그 브랜치 이름은 자동으로 새 커밋을 가리키도록 이동합니다. `main` 브랜치가 항상 "가장 최근에 main에 반영된 커밋"을 가리키는 것이 대표적인 예입니다.
- **태그는 고정됩니다.** 태그를 한 번 만들고 나면, 그 태그가 가리키는 커밋은 절대 바뀌지 않습니다. 태그 위에서 커밋을 만든다는 개념 자체가 없습니다. 새 커밋이 필요하다면 브랜치에서 작업해야 하고, 태그는 오직 "이 순간의 스냅샷을 기억하기 위한 이름표"로만 존재합니다.

이 성질 때문에 태그는 릴리스 시점, 즉 "이 커밋을 기준으로 v1.2.0을 배포했다"와 같은 사실을 기록하는 데 매우 적합합니다. 브랜치로도 비슷한 흉내를 낼 수는 있지만, 릴리스 브랜치는 이후에도 계속 커밋이 쌓이며 움직일 수 있는 반면 태그는 그 시점 그대로 영원히 고정되어 있다는 확실한 보장을 제공합니다.

태그가 가리키는 커밋으로 이동해서 코드를 살펴보고 싶다면 `git checkout` 명령에 태그 이름을 넘기면 됩니다.

```bash
git checkout v1.0.0
```

이때 Git은 "detached HEAD" 상태라는 경고 메시지를 보여줍니다. 태그는 브랜치가 아니므로 이 상태에서 커밋을 만들어도 어떤 브랜치에도 속하지 않는 커밋이 되어버립니다. 태그 시점의 코드를 잠깐 확인만 하고 다시 원래 작업으로 돌아가는 용도로 사용하고, 그 코드를 기반으로 실제 수정 작업을 이어가야 한다면 반드시 새 브랜치를 만들어서 작업해야 합니다.

```bash
git checkout -b hotfix-from-v1.0.0 v1.0.0
```

## 13.2 lightweight 태그와 annotated 태그

Git의 태그는 크게 두 종류로 나뉩니다.

**lightweight 태그**는 커밋을 가리키는 포인터 하나만 존재하는 가장 단순한 형태의 태그입니다. 별도의 메시지나 작성자 정보 없이, 그냥 이름과 커밋의 연결만 기록됩니다.

```bash
git tag v0.1-temp
```

**annotated 태그**는 태그 자체가 하나의 독립된 Git 객체로 저장되는 태그입니다. 태그를 만든 사람, 만든 날짜, 메시지가 함께 기록되며, GPG로 서명하는 것도 가능합니다. `-a` 옵션과 함께 `-m`으로 메시지를 지정해서 만듭니다.

```bash
git tag -a v1.0.0 -m "첫 정식 릴리스"
```

`-m`을 생략하면 커밋 메시지를 작성할 때처럼 에디터가 열려서 태그 메시지를 직접 입력할 수 있습니다.

```bash
git tag -a v1.1.0
```

두 방식의 차이가 실제로 크게 느껴지지 않을 수도 있지만, 릴리스처럼 "누가, 언제, 왜 이 지점을 태그했는지"가 중요한 상황에서는 annotated 태그를 쓰는 것이 관례입니다. 반대로 로컬에서 잠깐 위치를 표시해두고 곧 지울 임시 마커라면 lightweight 태그로 충분합니다.

### 태그 목록 확인하기

저장소에 있는 태그 목록은 `git tag` 또는 `git tag -l`로 확인할 수 있습니다.

```bash
git tag
git tag -l
```

패턴을 붙여서 특정 형식의 태그만 걸러볼 수도 있습니다.

```bash
git tag -l "v1.*"
```

### 태그의 상세 정보 확인하기

`git show` 명령에 태그 이름을 넘기면 태그의 상세 정보를 볼 수 있습니다.

```bash
git show v1.0.0
```

annotated 태그의 경우 태그 작성자, 작성 날짜, 태그 메시지가 먼저 출력되고 이어서 그 태그가 가리키는 커밋의 정보가 나옵니다. lightweight 태그는 별도의 태그 메타데이터가 없으므로 곧바로 커밋 정보만 출력됩니다.

## 13.3 지나간 시점에 태그 달기

태그는 반드시 현재 HEAD가 가리키는 커밋에만 달 수 있는 것이 아닙니다. `git log`로 과거 커밋의 해시를 확인한 다음, 그 해시를 태그 명령 뒤에 붙이면 그 커밋에 태그를 달 수 있습니다.

```bash
git log --oneline
# a3f9c21 릴리스 준비 커밋
# 7d21e88 결제 모듈 버그 수정
# ...

git tag -a v0.9.0 -m "베타 릴리스" a3f9c21
```

배포 자동화가 갖춰지기 전에 수동으로 배포하다가, 나중에서야 "그때 배포했던 커밋을 태그로 남겨둘 걸" 하고 아쉬워지는 경우가 흔합니다. 이럴 때도 `git log`로 배포 시점 근처의 커밋을 찾아 뒤늦게 태그를 붙여주면 됩니다.

## 13.4 태그 삭제하기

잘못 만든 태그는 `-d` 옵션으로 지울 수 있습니다.

```bash
git tag -d v0.1-temp
```

이 명령은 로컬 저장소의 태그만 지웁니다. 이미 원격 저장소에 푸시한 태그라면 원격에서도 별도로 삭제해야 합니다. 원격 태그 삭제는 13.5절에서 다룹니다.

## 13.5 태그를 원격 저장소로 푸시하기

여기서 반드시 기억해야 할 점이 있습니다. `git push`는 기본적으로 커밋만 원격으로 전송할 뿐, 태그는 함께 보내지 않습니다. 태그를 만든 뒤 팀원들과 공유하려면 명시적으로 푸시해야 합니다.

태그 하나만 푸시하려면 태그 이름을 지정합니다.

```bash
git push origin v1.0.0
```

로컬에 쌓인 태그를 한꺼번에 모두 푸시하려면 `--tags` 옵션을 사용합니다.

```bash
git push --tags
```

`--tags`는 원격에 아직 없는 태그를 전부 보내므로, 여러 태그를 순서대로 만든 뒤 한 번에 공유할 때 편리합니다. 다만 로컬에만 존재하고 아직 공유할 준비가 안 된 태그까지 함께 올라갈 수 있으므로, 상황에 따라 태그 이름을 하나씩 지정해서 푸시하는 편이 더 안전할 수 있습니다.

원격 저장소의 태그를 삭제하려면 `--delete` 옵션을 사용합니다.

```bash
git push origin --delete v0.1-temp
```

## 13.6 시맨틱 버저닝(semver) 개념

태그 이름을 지을 때 `v1.0.0`, `v2.3.1`처럼 점으로 구분된 세 개의 숫자를 쓰는 경우를 흔히 볼 수 있습니다. 이런 표기 관례를 **시맨틱 버저닝(Semantic Versioning, semver)** 이라고 부릅니다. 세 자리 숫자는 각각 다음을 의미합니다.

- **MAJOR**: 기존 사용 방식과 호환되지 않는 큰 변경이 있을 때 올립니다.
- **MINOR**: 기존 사용 방식과 호환되면서 새로운 기능이 추가되었을 때 올립니다.
- **PATCH**: 기존 동작을 유지한 채 버그만 수정했을 때 올립니다.

예를 들어 `v1.4.2`에서 사소한 버그 하나를 고쳤다면 `v1.4.3`이 되고, 새로운 기능을 추가했다면 `v1.5.0`이 되며, 기존 API를 크게 바꾸는 변경이라면 `v2.0.0`이 됩니다.

이 규칙은 Git 자체가 강제하는 규칙이 아닙니다. Git은 태그 이름에 어떤 문자열을 쓰든 전혀 관여하지 않습니다. 시맨틱 버저닝은 어디까지나 많은 오픈소스 프로젝트와 패키지 관리 생태계(npm, 각종 라이브러리 배포 시스템 등)에서 널리 채택하고 있는 하나의 관례일 뿐이며, 팀에 따라 날짜 기반 버전(`2026.08.30`)이나 순번 기반 버전(`build-142`)처럼 다른 방식을 쓰기도 합니다. 다만 협업하는 여러 사람이 버전 번호만 보고도 "이번 업데이트가 얼마나 위험한 변경인지" 짐작할 수 있다는 점에서, 시맨틱 버저닝은 여전히 참고할 만한 유용한 기준입니다.

## 13.7 GitHub Releases 개념

GitHub과 같은 원격 호스팅 서비스는 태그를 기반으로 한 **릴리스(Release)** 기능을 제공합니다. 태그가 "이 커밋이 v1.0.0이다"라는 순수한 지점 표시라면, 릴리스는 그 태그 위에 사람이 읽을 수 있는 릴리스 노트(이번 버전에서 무엇이 바뀌었는지에 대한 설명)를 덧붙이고, 필요하다면 실행 파일이나 압축된 배포 산출물 같은 첨부 파일을 함께 올려둘 수 있는 기능입니다.

즉 릴리스는 태그를 대체하는 것이 아니라, 태그를 기반으로 그 위에 부가 정보를 얹는 GitHub 자체의 기능입니다. 로컬에서 `git tag -a`로 태그를 만들고 푸시한 뒤, GitHub 저장소 화면에서 그 태그를 선택해 릴리스 노트를 작성하고 파일을 첨부하는 흐름으로 사용합니다. 이 책은 Git 자체를 다루는 책이므로 GitHub Releases의 구체적인 사용법까지는 다루지 않지만, 태그가 이런 상위 기능의 토대가 된다는 점은 기억해둘 필요가 있습니다.

## 요약

- 태그는 특정 커밋을 가리키는 고정된 이름표입니다. 브랜치와 달리 한 번 만들어지면 가리키는 커밋이 바뀌지 않습니다.
- lightweight 태그(`git tag <이름>`)는 단순한 포인터이고, annotated 태그(`git tag -a <이름> -m "메시지"`)는 작성자와 메시지 정보를 담은 별도의 Git 객체입니다. 릴리스처럼 기록이 중요한 태그는 annotated 태그를 권장합니다.
- `git tag -l`로 태그 목록을, `git show <태그>`로 태그의 상세 정보를 확인합니다.
- `git push`는 태그를 자동으로 보내지 않으므로, `git push origin <태그>`나 `git push --tags`로 명시적으로 푸시해야 합니다. 원격 태그 삭제는 `git push origin --delete <태그>`로 합니다.
- 시맨틱 버저닝(MAJOR.MINOR.PATCH)은 Git이 강제하는 규칙이 아니라 널리 쓰이는 버전 표기 관례이며, GitHub Releases는 태그를 기반으로 릴리스 노트와 배포 파일을 덧붙이는 호스팅 서비스의 부가 기능입니다.

## 연습문제

1. 브랜치와 태그가 "커밋을 가리킨다"는 점에서는 같지만 근본적으로 어떻게 다른지, 자신의 말로 설명해보세요.
2. lightweight 태그와 annotated 태그를 각각 만드는 명령어를 작성하고, `git show`로 확인했을 때 출력이 어떻게 다를지 설명해보세요.
3. 로컬에서 태그 `v2.0.0`을 만들고 원격 저장소 `origin`에 푸시하는 명령어를 작성해보세요. 만약 태그를 여러 개 한꺼번에 푸시하고 싶다면 어떤 옵션을 쓸 수 있나요?
4. 실수로 만든 태그 `v0.0.1-broken`을 로컬과 원격 저장소 양쪽에서 모두 삭제하는 명령어를 각각 작성해보세요.
5. 다음 상황에서 시맨틱 버저닝 규칙에 따라 버전이 각각 어떻게 바뀌어야 하는지 답해보세요. 현재 버전은 `v3.2.1`입니다.
   - 기존 함수의 이름을 변경해서 이전 코드와 호환되지 않게 되었다.
   - 기존 기능은 그대로 두고 새로운 옵션 기능을 하나 추가했다.
   - 로그인 시 발생하던 사소한 오타 버그를 수정했다.

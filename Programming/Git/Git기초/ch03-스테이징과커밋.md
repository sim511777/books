Git을 처음 접하면 가장 헷갈리는 부분이 "왜 파일을 수정했는데 바로 저장(커밋)되지 않고, `add`라는 중간 단계를 한 번 더 거쳐야 하는가"이다. 다른 버전 관리 도구나 일반적인 저장 개념에 익숙하다면 이 중간 단계가 번거로운 군더더기처럼 느껴질 수 있다. 하지만 이 중간 단계, 즉 스테이징 영역이야말로 Git을 다른 도구와 구별 짓는 핵심 설계이며, 한 번 이해하고 나면 커밋을 훨씬 정교하게 다룰 수 있게 해주는 도구가 된다. 이번 장에서는 Git이 변경 사항을 어떻게 세 단계로 나누어 관리하는지, 그리고 각 단계를 오가며 커밋을 만드는 실전 명령어를 살펴본다.

## 세 가지 영역: 작업 디렉터리, 스테이징 영역, 저장소

Git은 파일의 변경 사항을 하나의 단계가 아니라 세 개의 영역을 거치는 흐름으로 관리한다.

- **작업 디렉터리(working directory)**: 사용자가 실제로 파일을 열고, 수정하고, 눈으로 보는 공간이다. 탐색기나 에디터에서 보이는 그 파일들이 바로 작업 디렉터리에 있는 파일이다.
- **스테이징 영역(staging area, 인덱스index)**: 다음 커밋에 무엇을 포함시킬지 미리 골라 담아두는 임시 공간이다. 실체는 `.git/index`라는 하나의 파일이며, 작업 디렉터리의 특정 시점 스냅숏 정보를 담고 있다.
- **저장소(repository)**: 커밋이 실제로 기록되어 저장되는 곳이다. `.git` 디렉터리 안의 `objects` 폴더에 커밋, 트리, 파일 내용이 압축된 객체 형태로 영구히 저장된다.

파일을 수정하는 것만으로는 아무 기록도 남지 않는다. 변경 사항이 저장소에 커밋으로 기록되려면 반드시 스테이징 영역을 거쳐야 한다. 즉 데이터는 항상 "작업 디렉터리 → 스테이징 영역 → 저장소" 순서로 이동하며, 이 흐름을 담당하는 명령이 각각 `git add`와 `git commit`이다.

```bash
$ mkdir myproject
$ cd myproject
$ git init
Initialized empty Git repository in /home/user/myproject/.git/
```

`git init`을 실행하면 현재 디렉터리에 `.git`이라는 숨김 디렉터리가 생성된다. 이 디렉터리 하나가 곧 저장소 전체이며, 저장소를 통째로 삭제하고 싶다면 `.git` 디렉터리만 지우면 된다. 이제 파일을 하나 만들어보자.

```bash
$ echo "프로젝트 설명" > README.md
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
```

`README.md` 파일은 작업 디렉터리에는 존재하지만, Git이 아직 추적(track)하지 않는 파일이라는 뜻에서 "Untracked files"로 분류된다. 이 상태의 파일은 스테이징 영역에도, 저장소에도 아무런 흔적이 없다.

## git status로 상태 확인하기

`git status`는 세 영역 사이에서 파일이 지금 어떤 상태에 놓여 있는지 알려주는 가장 기본적이면서도 가장 자주 쓰는 명령이다. 앞으로 나올 모든 작업을 하기 전후로 습관처럼 실행해보는 것이 좋다.

```bash
$ git add README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md
```

`git add`를 실행한 뒤 다시 `git status`를 확인하면 `README.md`가 "Changes to be committed", 즉 스테이징 영역으로 옮겨진 것을 볼 수 있다. 이 시점에서 파일을 한 번 더 수정하면 어떻게 될까?

```bash
$ echo "추가 설명" >> README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
        modified:   README.md
```

같은 `README.md`가 두 번 등장한다. "Changes to be committed"에 있는 내용은 `git add`를 실행했던 시점까지의 스냅숏이고, "Changes not staged for commit"은 그 이후에 작업 디렉터리에서 추가로 바뀐 부분이다. 이는 스테이징 영역이 작업 디렉터리와 독립된 별도의 스냅숏이라는 사실을 잘 보여준다. 매번 실행할 때마다 상태 설명을 길게 읽기 번거롭다면 `-s`(또는 `--short`) 옵션으로 요약된 형태를 볼 수 있다.

```bash
$ git status -s
MM README.md
```

`MM`에서 앞 글자는 스테이징 영역의 상태를, 뒤 글자는 작업 디렉터리의 상태를 나타낸다. `M`은 수정(modified), `A`는 새 파일 추가, `??`는 추적하지 않는 파일을 뜻한다.

## git add로 스테이징하기

`git add`는 작업 디렉터리의 변경 사항을 스테이징 영역으로 옮기는 명령이다. 사용 범위에 따라 여러 방식으로 쓸 수 있다.

```bash
$ git add README.md              # 특정 파일 하나
$ git add README.md src/main.c   # 여러 파일 동시에
$ git add src/                   # 디렉터리 전체
$ git add *.txt                  # 셸 패턴 (셸이 확장한 뒤 Git에 전달)
```

여러 파일을 한꺼번에 스테이징할 때는 다음 세 가지 옵션의 차이를 정확히 알아두어야 실수를 줄일 수 있다.

| 명령 | 동작 |
|---|---|
| `git add .` | 현재 디렉터리 기준으로 그 아래의 새 파일, 수정된 파일, 삭제된 파일을 모두 스테이징한다. |
| `git add -A` (`--all`) | 저장소 전체를 기준으로 새 파일, 수정된 파일, 삭제된 파일을 모두 스테이징한다. |
| `git add -u` (`--update`) | 이미 추적 중인 파일의 수정·삭제만 스테이징한다. 새로 추가된 파일은 대상에서 제외된다. |

저장소 최상위 디렉터리에서 실행한다면 `git add .`와 `git add -A`는 사실상 같은 결과를 낸다. 차이가 드러나는 경우는 하위 디렉터리 안에서 실행할 때다. `git add .`는 현재 위치 아래만 대상으로 삼지만, `git add -A`는 현재 위치와 무관하게 저장소 전체를 대상으로 삼는다.

파일을 잘못 스테이징했다면 `git restore --staged`로 되돌릴 수 있다.

```bash
$ git add README.md
$ git restore --staged README.md
$ git status -s
?? README.md
```

스테이징만 취소될 뿐 작업 디렉터리의 파일 내용은 그대로 남는다는 점을 기억해두자.

## git diff로 변경 내용 비교하기

`git status`가 "어떤 파일이 바뀌었는가"를 보여준다면, `git diff`는 "정확히 어느 줄이 어떻게 바뀌었는가"를 보여준다. `git diff`는 비교 대상에 따라 동작이 달라진다.

```bash
$ git diff
```

옵션 없이 실행한 `git diff`는 **작업 디렉터리와 스테이징 영역**을 비교한다. 즉 아직 `git add`로 옮기지 않은, 앞으로 스테이징될 후보 변경 사항을 보여준다.

```bash
$ git diff --staged
```

(`git diff --cached`도 완전히 동일하게 동작하는 별칭이다.) 이 명령은 **스테이징 영역과 가장 최근 커밋**을 비교한다. 즉 지금 `git commit`을 실행하면 실제로 기록될 내용을 미리 보여준다.

두 비교 대상을 표로 정리하면 다음과 같다.

| 명령 | 비교 대상 |
|---|---|
| `git diff` | 작업 디렉터리 ↔ 스테이징 영역 |
| `git diff --staged` | 스테이징 영역 ↔ 마지막 커밋 |

실제 출력을 살펴보자.

```bash
$ echo "새로운 줄" >> README.md
$ git diff
diff --git a/README.md b/README.md
index e69de29..8f3d6c1 100644
--- a/README.md
+++ b/README.md
@@ -1,2 +1,3 @@
 프로젝트 설명
 추가 설명
+새로운 줄
```

각 줄의 의미는 다음과 같다.

- `diff --git a/README.md b/README.md`: 비교 대상 파일. `a/`는 이전 버전, `b/`는 이후 버전을 가리킨다.
- `--- a/README.md`, `+++ b/README.md`: 각각 이전 버전과 이후 버전의 파일 표시.
- `@@ -1,2 +1,3 @@`: "이전 버전은 1번째 줄부터 2줄, 이후 버전은 1번째 줄부터 3줄을 보여준다"는 위치 정보(hunk 헤더).
- 줄 앞의 공백은 변경되지 않은 문맥(context) 줄, `+`는 추가된 줄, `-`는 삭제된 줄을 뜻한다.

## git commit으로 커밋 만들기

스테이징 영역에 원하는 변경 사항을 모두 담았다면 `git commit`으로 저장소에 영구히 기록한다.

```bash
$ git add README.md
$ git commit -m "Add project README"
[main (root-commit) 3f2a1c9] Add project README
 1 file changed, 3 insertions(+)
 create mode 100644 README.md
```

`-m` 옵션 없이 `git commit`만 실행하면 `core.editor`에 설정된 텍스트 편집기(기본값은 대개 vi)가 열리고, 커밋 메시지를 작성한 뒤 저장하고 종료해야 커밋이 완료된다.

이미 추적 중인 파일을 수정한 경우에 한해, `git add`와 `git commit`을 한 번에 처리하는 단축 옵션도 있다.

```bash
$ git commit -am "Update README wording"
```

`-a`는 "추적 중인 파일 중 수정되거나 삭제된 것"을 자동으로 스테이징한 뒤 커밋한다. 다만 **새로 추가된(untracked) 파일에는 적용되지 않는다**는 점에 주의해야 한다. 새 파일은 반드시 `git add`로 먼저 등록해야 한다.

커밋이 만들어질 때 Git 내부에서는 다음과 같은 일이 일어난다.

1. 스테이징 영역(인덱스)의 내용을 바탕으로 트리(tree) 객체를 만든다. 트리는 그 시점의 디렉터리 구조와 파일 스냅숏이다.
2. 새 커밋 객체를 만든다. 이 객체는 방금 만든 트리를 가리키고, 직전 커밋을 부모(parent)로 기록하며, 작성자(author)·커밋 시각·커밋 메시지를 함께 담는다.
3. 현재 브랜치가 가리키는 참조(예: `main`)를 방금 만든 새 커밋으로 옮긴다.

커밋마다 이 내용을 바탕으로 SHA-1 해시 값이 계산되어 고유한 식별자로 사용된다. 커밋 메시지 한 글자만 달라져도 해시 값 전체가 완전히 달라진다.

## 좋은 커밋 메시지 작성법

커밋 메시지는 미래의 동료(그리고 미래의 자신)에게 남기는 기록이다. 실무에서 널리 통용되는 몇 가지 관례를 소개한다.

- **제목과 본문을 빈 줄로 구분한다.** 제목은 변경 사항을 한 줄로 요약하고, 본문에는 왜 이 변경이 필요했는지 배경과 이유를 적는다.
- **제목은 50자 안팎으로 짧게 쓴다.** `git log --oneline`처럼 제목만 나열되는 화면에서 잘리지 않고 한눈에 읽히도록 하기 위함이다.
- **명령형 어조를 사용한다.** "Fixed bug"나 "Fixes bug"보다 "Fix bug"처럼 명령형으로 쓰는 관례가 널리 퍼져 있다. "이 커밋을 적용하면 ___한다"라는 문장을 완성한다고 생각하면 자연스럽게 명령형이 된다.
- **본문은 "무엇을" 바꿨는지가 아니라 "왜" 바꿨는지를 설명한다.** 무엇이 바뀌었는지는 `git diff`로 언제든 볼 수 있지만, 왜 그런 선택을 했는지는 커밋 메시지에만 남는 경우가 많다.

`-m` 옵션을 여러 번 사용하면 각 값이 별도 문단으로 이어져 제목과 본문을 가진 메시지를 명령줄에서 바로 만들 수 있다.

```bash
$ git commit -m "Add input validation to login form" \
              -m "Empty username or password was previously accepted and
caused a null pointer exception downstream. Reject the
request early and show an inline error message instead."
```

메시지가 길어지면 파일에 미리 작성해두고 `-F`(`--file`) 옵션으로 불러오는 방법도 유용하다.

```bash
$ git commit -F commit-message.txt
```

## git log로 히스토리 살펴보기

`git log`는 저장소에 쌓인 커밋 이력을 확인하는 명령이다.

```bash
$ git log
commit 3f2a1c9d8e7b6a5c4d3e2f1a0b9c8d7e6f5a4b3c
Author: Hong Gildong <hong@example.com>
Date:   Sun Aug 30 10:00:00 2026 +0900

    Add project README
```

기본 출력은 각 커밋의 전체 해시, 작성자, 날짜, 메시지를 순서대로 보여준다. 커밋이 많아지면 다음 옵션들이 유용하다.

```bash
$ git log --oneline
3f2a1c9 Add project README
```

`--oneline`은 각 커밋을 짧은 해시(7자리)와 제목 한 줄로 압축해서 보여준다. 여러 브랜치가 얽힌 히스토리를 시각적으로 파악하고 싶을 때는 `--graph`를 함께 사용한다.

```bash
$ git log --oneline --graph
* 3f2a1c9 Add project README
```

브랜치가 여러 개로 나뉘고 병합된 이후에는 `*`, `|`, `\`, `/` 문자로 이루어진 그래프가 그려져 커밋들이 어떻게 갈라지고 합쳐졌는지 한눈에 볼 수 있다(자세한 예시는 4장에서 다룬다). 각 커밋에서 어떤 파일이 몇 줄 바뀌었는지 요약해서 보고 싶다면 `--stat`을 사용한다.

```bash
$ git log --stat
commit 3f2a1c9d8e7b6a5c4d3e2f1a0b9c8d7e6f5a4b3c
Author: Hong Gildong <hong@example.com>
Date:   Sun Aug 30 10:00:00 2026 +0900

    Add project README

 README.md | 3 +++
 1 file changed, 3 insertions(+)
```

이 옵션들은 서로 조합해서 쓸 수 있다.

```bash
$ git log --oneline --graph --stat -3
```

`-3`처럼 숫자만 붙이면 최근 3개의 커밋만 출력한다(`-n 3`과 동일하다).

## git show로 특정 커밋 들여다보기

`git log`가 여러 커밋을 훑어본다면, `git show`는 커밋 하나를 콕 짚어 그 내용을 자세히 보여준다.

```bash
$ git show 3f2a1c9
commit 3f2a1c9d8e7b6a5c4d3e2f1a0b9c8d7e6f5a4b3c
Author: Hong Gildong <hong@example.com>
Date:   Sun Aug 30 10:00:00 2026 +0900

    Add project README

diff --git a/README.md b/README.md
new file mode 100644
index 0000000..8f3d6c1
--- /dev/null
+++ b/README.md
@@ -0,0 +1,3 @@
+프로젝트 설명
+추가 설명
+새로운 줄
```

`git show`는 커밋 메타데이터와 함께, 그 커밋이 부모 커밋과 비교해 어떤 변경을 담고 있는지 `git diff`와 같은 형식으로 보여준다. 커밋 해시 대신 `HEAD`(가장 최근 커밋)나 `HEAD~1`(그 이전 커밋)처럼 상대 표기도 쓸 수 있다.

```bash
$ git show HEAD
$ git show HEAD~1
```

특정 커밋 시점의 파일 하나만 보고 싶다면 `커밋:경로` 형식을 사용한다.

```bash
$ git show 3f2a1c9:README.md
프로젝트 설명
추가 설명
새로운 줄
```

## 요약

- Git은 변경 사항을 작업 디렉터리, 스테이징 영역(인덱스), 저장소 세 단계로 나누어 관리한다. 데이터는 항상 이 순서로 이동한다.
- `git status`로 현재 각 영역의 상태를 확인하고, `git add`로 작업 디렉터리의 변경을 스테이징 영역으로 옮긴다. `git add .`, `-A`, `-u`는 대상 범위가 서로 다르다.
- `git diff`는 작업 디렉터리와 스테이징 영역을, `git diff --staged`는 스테이징 영역과 마지막 커밋을 비교한다.
- `git commit -m`으로 스테이징된 내용을 저장소에 기록한다. 좋은 커밋 메시지는 명령형으로 쓴 짧은 제목과, 왜 바꿨는지를 설명하는 본문으로 구성된다.
- `git log`(`--oneline`, `--graph`, `--stat`)로 히스토리를 훑어보고, `git show`로 특정 커밋 하나의 상세 내용을 확인한다.

## 연습문제

1. 빈 디렉터리에서 `git init`으로 저장소를 만들고, 파일 하나를 새로 만든 뒤 `git status`를 실행했을 때 나오는 "Untracked files" 메시지가 의미하는 바를 설명하라.
2. 파일을 수정한 뒤 `git add`로 스테이징하고, 같은 파일을 한 번 더 수정하라. 이 상태에서 `git diff`와 `git diff --staged`의 출력이 각각 무엇을 보여주는지 실행해서 비교하고 차이를 설명하라.
3. `git add .`과 `git add -A`가 결과적으로 다르게 동작하는 상황을 하나 만들어 재현하라. (힌트: 하위 디렉터리에서 명령을 실행해본다.)
4. 임의의 파일 변경을 두 개 이상의 커밋으로 나누어 기록하되, 각 커밋 메시지에 제목과 본문을 모두 작성하라. 이후 `git log --oneline`과 `git log --stat`으로 각각 확인하고 두 출력의 차이를 설명하라.
5. `git show HEAD`와 `git show HEAD~1`을 실행하여 두 출력이 어떻게 다른지 확인하고, `HEAD~1`이 가리키는 커밋이 무엇을 의미하는지 자신의 말로 설명하라.

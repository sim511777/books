작업을 하다 보면 실수는 늘 따라온다. 아직 커밋하지 않은 변경 내용을 통째로 버리고 싶을 때도 있고, 스테이징까지 해둔 파일을 다시 빼고 싶을 때도 있고, 이미 커밋해버린 내용을 없던 일로 하고 싶을 때도 있다. Git은 이 각각의 상황에 맞는 명령을 따로 제공한다. 이번 장에서는 "어디까지 되돌릴 것인가"를 기준으로, 작업 디렉터리 → 스테이징 영역 → 커밋 순서로 되돌리는 방법을 살펴보고, 마지막으로 이미 만든 커밋을 고치거나 지우는 여러 방법의 차이와 위험성을 짚어본다.

## 8.1 되돌리기의 세 층위

Git으로 작업할 때 변경 내용은 세 곳을 거쳐간다. 파일을 고치면 **작업 디렉터리**에 반영되고, `git add`로 담으면 **스테이징 영역**(인덱스)으로 올라가고, `git commit`으로 확정하면 **커밋**(히스토리)에 기록된다. 되돌리기도 이 세 층위에 맞춰서 생각하면 헷갈리지 않는다.

| 되돌리려는 대상 | 사용하는 명령 |
| --- | --- |
| 작업 디렉터리의 수정 내용을 버리고 싶다 | `git restore <file>` |
| 스테이징만 취소하고 수정 내용은 남기고 싶다 | `git restore --staged <file>` |
| 마지막 커밋 자체를 고치고 싶다 | `git commit --amend` |
| 이미 만든 커밋을 없애거나 되돌리고 싶다 | `git reset` 또는 `git revert` |

아래로 갈수록 되돌리는 범위가 넓어지고, 그만큼 신중하게 다뤄야 한다.

## 8.2 작업 디렉터리의 변경 취소하기: git restore

파일을 수정했지만 아직 `git add`하지 않은 상태에서, 그 수정 내용을 버리고 마지막으로 커밋된(또는 스테이징된) 상태로 되돌리고 싶다면 `git restore`를 쓴다. 이 명령은 Git 2.23부터 도입되었다.

```bash
git restore README.md
```

여러 파일을 한 번에 되돌리거나, 디렉터리 전체를 되돌릴 수도 있다.

```bash
git restore src/
git restore .
```

`git restore`는 기본적으로 스테이징 영역(인덱스)에 있는 내용을 기준으로 작업 디렉터리를 되돌린다. 만약 스테이징 영역이 아니라 특정 커밋 시점의 내용으로 되돌리고 싶다면 `--source` 옵션을 쓴다.

```bash
# HEAD 두 커밋 전 시점의 내용으로 되돌린다
git restore --source=HEAD~2 README.md
```

**주의**: `git restore`로 버려진 작업 디렉터리의 수정 내용은 어디에도 기록되지 않은 상태였으므로 복구할 방법이 없다. 실행하기 전에 `git diff`로 무엇이 사라지는지 반드시 확인하는 습관을 들이자.

```bash
git diff README.md
git restore README.md
```

### 8.2.1 구버전 문법: git checkout --

`git restore`가 나오기 전에는 같은 작업을 `git checkout -- <file>` 로 했다. `git checkout`은 원래 브랜치를 전환하는 명령인데, 파일 경로를 함께 지정하면 "그 파일만 되돌리기"라는 전혀 다른 동작을 겸했다. 이 두 가지 역할이 한 명령에 섞여 있다 보니 실수하기 쉬웠고, 그래서 Git 2.23에서 파일 복원 기능만 떼어내 `git restore`로 새로 만든 것이다.

```bash
# git restore README.md 와 동일하게 동작한다
git checkout -- README.md
```

`--`는 "여기부터는 파일 경로다"라는 뜻으로, 브랜치 이름과 파일 이름이 우연히 같은 경우의 혼동을 막아준다. 오래된 문서나 스크립트에서는 여전히 이 문법을 자주 볼 수 있으므로 읽을 줄은 알아두되, 새로 작성하는 코드에서는 `git restore`를 쓰는 편이 의도가 더 분명하다.

## 8.3 스테이징 취소하기: git restore --staged

`git add`로 스테이징까지 해둔 파일을, 커밋하지 않고 다시 작업 디렉터리 쪽(스테이징 안 된 상태)으로 내리고 싶을 때가 있다. 이때는 파일의 수정 내용 자체는 그대로 남기면서 스테이징만 취소해야 한다.

```bash
git add config.js
git restore --staged config.js
```

`git status`로 확인해보면, `config.js`는 여전히 수정된 상태지만 "커밋할 변경 사항(Changes to be committed)"이 아니라 "커밋하지 않은 변경 사항(Changes not staged for commit)" 쪽으로 옮겨간 것을 볼 수 있다. 즉 파일 내용은 하나도 사라지지 않고, 그저 스테이징 영역에서만 빠진다.

### 8.3.1 구버전 문법: git reset <file>

`git restore --staged`가 나오기 전에는 같은 작업을 `git reset` 뒤에 파일 경로를 붙여서 했다.

```bash
git reset config.js
# 또는 명시적으로
git reset HEAD config.js
```

이 형태의 `git reset`은 뒤에서 다룰 "커밋을 되돌리는" `git reset`과 이름은 같지만 동작이 다르다. 파일 경로를 지정하면 브랜치 포인터(`HEAD`)는 전혀 움직이지 않고, 그 파일만 스테이징 영역에서 HEAD 시점의 상태로 되돌려 언스테이징한다. 이 문법도 여전히 잘 동작하지만, `git restore --staged`가 "무엇을 되돌리는지" 이름만으로도 더 명확하므로 이 책에서는 앞으로 `git restore --staged`를 기본으로 쓴다.

작업 디렉터리와 스테이징 영역을 모두 HEAD 시점으로 한 번에 되돌리고 싶다면 두 옵션을 함께 쓸 수도 있다.

```bash
git restore --staged --worktree config.js
```

## 8.4 마지막 커밋 고치기: git commit --amend

커밋 메시지에 오타가 있거나, 커밋하고 나서야 파일 하나를 빠뜨린 걸 깨달았다면, 새 커밋을 또 만들 필요 없이 `git commit --amend`로 마지막 커밋 자체를 고칠 수 있다.

### 8.4.1 커밋 메시지만 고치기

```bash
git commit --amend
```

이 명령을 실행하면 편집기가 열리고 마지막 커밋 메시지가 채워져 있다. 내용을 고치고 저장한 뒤 편집기를 닫으면 새 메시지로 커밋이 다시 만들어진다. 메시지를 편집기 없이 바로 지정하고 싶다면 `-m`을 함께 쓴다.

```bash
git commit --amend -m "로그인 실패 메시지를 한국어로 변경"
```

### 8.4.2 빠뜨린 파일을 마지막 커밋에 포함시키기

```bash
git add forgotten-file.js
git commit --amend --no-edit
```

`--no-edit`는 커밋 메시지는 그대로 두고, 방금 스테이징한 내용만 마지막 커밋에 합쳐 넣으라는 뜻이다.

### 8.4.3 --amend가 실제로 하는 일

`git commit --amend`는 마지막 커밋의 내용을 "수정"하는 것처럼 보이지만, 실제로는 스테이징 영역의 내용과 지정한 메시지로 완전히 새로운 커밋을 만들고, 브랜치가 그 새 커밋을 가리키도록 바꾸는 동작이다. 이전 커밋은 히스토리에서 더는 보이지 않을 뿐, 당장 사라지지는 않는다(뒤에 나올 안전 수칙의 `git reflog`로 한동안 되찾을 수 있다). 다만 새 커밋은 해시가 다른 완전히 별개의 커밋이라는 점이 중요하다.

**주의**: 이미 원격 저장소에 푸시해서 다른 사람이 내려받았을 수도 있는 커밋을 `--amend`로 고치면, 나와 다른 사람의 히스토리가 서로 어긋난다. `--amend`는 아직 아무도 내려받지 않은, 나만 갖고 있는 마지막 커밋에 대해서만 쓰는 것이 안전하다.

## 8.5 커밋을 되돌리는 두 가지 철학: reset vs revert

이미 만든 커밋 자체를 없애거나 취소하고 싶을 때 Git은 성격이 전혀 다른 두 가지 방법을 제공한다. 하나는 히스토리를 다시 쓰는 `git reset`이고, 다른 하나는 새 커밋으로 취소하는 `git revert`다.

### 8.5.1 git reset: 브랜치 포인터를 되감기

`git reset <commit>`은 현재 브랜치(HEAD)가 가리키는 지점을 지정한 커밋으로 옮긴다. 즉 "이 커밋 이후로는 아무 일도 없었던 것"처럼 브랜치 포인터를 과거로 되감는다. 이때 스테이징 영역과 작업 디렉터리를 어떻게 처리할지에 따라 세 가지 모드가 있다.

```bash
# 3커밋 전으로 되감되, 그 사이의 변경 내용은 모두 스테이징된 상태로 남긴다
git reset --soft HEAD~3

# 3커밋 전으로 되감고, 변경 내용은 작업 디렉터리에 남기되 스테이징은 해제한다(기본값)
git reset --mixed HEAD~3
git reset HEAD~3

# 3커밋 전으로 되감고, 변경 내용을 작업 디렉터리에서도 완전히 지운다
git reset --hard HEAD~3
```

세 모드의 차이를 표로 정리하면 다음과 같다.

| 모드 | 브랜치(HEAD) | 스테이징 영역 | 작업 디렉터리 |
| --- | --- | --- | --- |
| `--soft` | 이동 | 그대로 유지(변경 내용이 스테이징된 채로 남음) | 그대로 유지 |
| `--mixed` (기본값) | 이동 | 되감은 커밋 시점으로 초기화 | 그대로 유지(수정 내용은 파일에 남음) |
| `--hard` | 이동 | 되감은 커밋 시점으로 초기화 | 되감은 커밋 시점으로 초기화(수정 내용 소실) |

`--soft`는 "커밋 단위를 다시 나누고 싶을 때" 유용하다. 예를 들어 커밋 3개를 하나로 합쳐서 다시 커밋하고 싶다면, `git reset --soft HEAD~3`로 되감은 뒤 `git commit`을 한 번만 실행하면 된다. `--mixed`는 커밋만 취소하고 무엇을 다시 스테이징할지는 직접 고르고 싶을 때 쓴다. `--hard`는 그 시점 이후의 모든 변경(커밋과 작업 중이던 수정 내용 모두)을 완전히 버리고 싶을 때만 쓴다.

`reset`은 파일 경로 없이 커밋을 지정하면 브랜치 자체를 움직이지만, 앞서 8.3절에서 본 것처럼 파일 경로를 지정하면 브랜치는 그대로 두고 그 파일의 스테이징만 되돌린다는 점도 함께 기억해두자.

### 8.5.2 git revert: 새 커밋으로 취소하기

`git revert <commit>`은 지정한 커밋이 만든 변경 내용을 정반대로 적용하는 **새 커밋**을 만든다. 기존 커밋은 히스토리에서 지워지지 않고 그대로 남아 있으며, 그 위에 "취소하는 커밋"이 하나 더 쌓인다.

```bash
git revert 8f2a3c1
```

이 명령을 실행하면 편집기가 열려 자동으로 채워진 커밋 메시지(예: `Revert "로그인 실패 메시지를 한국어로 변경"`)를 확인하고 저장할 수 있다. 메시지 편집 없이 바로 커밋하고 싶다면 `--no-edit`를 준다.

```bash
git revert --no-edit 8f2a3c1
```

되돌린 내용을 커밋까지 하지 않고 스테이징 영역에만 반영해두고, 다른 변경과 합쳐서 직접 커밋하고 싶다면 `-n`(`--no-commit`) 옵션을 쓴다.

```bash
git revert -n 8f2a3c1
```

여러 커밋을 연달아 되돌리고 싶다면 범위를 지정할 수도 있다.

```bash
# HEAD~3부터 HEAD까지(HEAD~3 제외)의 커밋들을 역순으로 되돌린다
git revert HEAD~3..HEAD
```

### 8.5.3 무엇을 선택해야 할까

핵심 기준은 하나다. **그 커밋을 이미 다른 사람과 공유했는가?**

- 아직 나만 갖고 있고 원격 저장소에 푸시하지 않은 커밋이라면, `git reset`으로 히스토리를 정리해도 아무 문제가 없다. 어차피 남들은 그 커밋을 본 적이 없다.
- 이미 `git push`해서 다른 사람이 내려받았을 수도 있는 커밋이라면, `git reset`으로 히스토리를 지우지 말고 `git revert`를 써야 한다. `reset`은 브랜치의 과거를 통째로 바꿔버리므로, 이미 그 커밋을 내려받은 사람들의 로컬 히스토리와 어긋나게 된다. 반면 `revert`는 기존 커밋을 그대로 둔 채 취소하는 커밋을 새로 쌓기만 하므로, 누구나 평소처럼 `git pull`만 받으면 자연스럽게 동기화된다.

요약하면, **아직 공개되지 않은 나만의 히스토리는 자유롭게 다시 써도 되지만(reset), 이미 공유된 히스토리는 새 커밋으로 덧붙여 고치는 편이 안전하다(revert)**.

## 8.6 위험한 명령과 안전 수칙

이 장에서 다룬 명령 중 몇 가지는 되돌릴 수 없는 손실로 이어질 수 있다. 특히 다음 두 가지는 실행하기 전에 반드시 한 번 더 확인하는 습관을 들이자.

### 8.6.1 git reset --hard

`git reset --hard`는 스테이징 영역과 작업 디렉터리를 지정한 커밋 시점으로 강제로 맞춘다. 이 과정에서 **아직 커밋하지 않은 작업 디렉터리의 수정 내용은 아무런 기록도 남기지 않은 채 사라진다.** 실행 전에 다음을 습관화하자.

```bash
# 무엇이 사라지는지 먼저 확인한다
git status
git diff

# 정말 필요하다면, 되돌리기 전에 지금 상태를 임시로 저장해둔다
git stash
```

만약 실수로 `git reset --hard`를 실행해서 커밋 자체를 잃어버렸다면(작업 디렉터리의 미완성 수정이 아니라, 이미 커밋했던 내용이라면), `git reflog`로 HEAD가 최근에 가리켰던 위치들의 기록을 확인해 복구할 수 있는 경우가 많다.

```bash
git reflog
git reset --hard HEAD@{1}
```

다만 이 방법은 커밋된 것에만 해당하며, 애초에 커밋한 적 없는 작업 디렉터리의 변경 내용에는 통하지 않는다. **커밋되지 않은 변경 내용을 지우는 명령 앞에서는 항상 한 번 더 멈춰서 확인하는 것이 최선의 안전장치**라는 점을 기억하자.

### 8.6.2 force push

로컬에서 `git reset`이나 `git commit --amend`로 이미 원격에 올라간 커밋의 히스토리를 바꾼 뒤 평범하게 `git push`를 하면, 원격의 히스토리와 어긋난다며 거부당한다. 이때 강제로 밀어붙이는 옵션이 `--force`다.

```bash
git push --force
```

이 명령은 원격 브랜치의 히스토리를 로컬 것으로 완전히 덮어써버린다. 그사이 다른 팀원이 같은 브랜치에 무언가를 푸시해뒀다면, **그 커밋들이 원격에서 통째로 사라질 수 있다.** 공유 브랜치(`main`, `develop` 등)에는 원칙적으로 강제 푸시를 쓰지 않는 것이 좋고, 꼭 필요하다면 `--force` 대신 좀 더 안전한 `--force-with-lease`를 쓰는 편이 좋다.

```bash
git push --force-with-lease
```

`--force-with-lease`는 "내가 마지막으로 받아본 원격 상태와 지금 원격 상태가 같을 때만" 강제 푸시를 허용한다. 즉 내가 모르는 사이 다른 사람이 같은 브랜치에 새 커밋을 올려뒀다면 푸시가 거부되어, 그 사람의 작업을 실수로 덮어쓰는 사고를 막아준다.

### 8.6.3 정리하면

- 아직 커밋하지 않은 변경 내용을 지우는 명령(`git restore`, `git reset --hard`)은 기록이 남지 않으므로 실행 전 `git status`/`git diff`로 반드시 확인한다.
- 이미 공유된 커밋의 히스토리는 되도록 고쳐 쓰지 말고(`reset`, `--amend`, force push), `git revert`처럼 히스토리를 보존하는 방법을 우선 고려한다.
- 부득이하게 공유된 히스토리를 강제로 바꿔야 한다면, 먼저 관련된 팀원들에게 알리고, `git push --force` 대신 `git push --force-with-lease`를 쓴다.
- 커밋까지는 됐던 내용을 실수로 잃어버렸다면 당황하지 말고 `git reflog`부터 확인한다.

## 요약

- 작업 디렉터리의 수정 내용은 `git restore <file>`로, 스테이징만 취소하려면 `git restore --staged <file>`로 되돌린다. 각각의 구버전 문법은 `git checkout -- <file>`과 `git reset <file>`이다.
- `git commit --amend`는 마지막 커밋의 메시지나 내용을 새 커밋으로 대체한다. 아직 공유하지 않은 커밋에만 사용하는 것이 안전하다.
- `git reset`은 브랜치 포인터를 과거로 되감아 히스토리 자체를 다시 쓴다. `--soft`(스테이징 유지), `--mixed`(작업 디렉터리만 유지, 기본값), `--hard`(모두 초기화) 세 모드로 스테이징 영역과 작업 디렉터리의 처리 방식이 달라진다.
- `git revert`는 기존 커밋을 지우지 않고, 그 변경을 취소하는 새 커밋을 추가한다. 이미 공유된 히스토리를 되돌릴 때 안전한 방법이다.
- `git reset --hard`와 `git push --force`는 각각 작업 내용과 원격 히스토리를 되돌릴 수 없이 손실시킬 수 있다. 실행 전 확인하는 습관을 들이고, 강제 푸시가 꼭 필요하다면 `--force-with-lease`를 우선 고려한다.

## 연습문제

1. `git restore <file>`과 `git restore --staged <file>`의 차이를 각각 어떤 상황에서 쓰는지와 함께 설명하시오.
2. `git reset --soft HEAD~2`, `git reset --mixed HEAD~2`, `git reset --hard HEAD~2`를 각각 실행했을 때 스테이징 영역과 작업 디렉터리가 어떻게 달라지는지 표로 정리하시오.
3. 이미 원격 저장소에 푸시되어 동료가 내려받은 커밋 하나를 취소하고 싶다. `git reset`이 아니라 `git revert`를 써야 하는 이유를 설명하시오.
4. 커밋 메시지에 오타를 낸 직후, 아직 아무에게도 푸시하지 않은 상태라고 가정한다. 이 오타를 고치는 명령을 작성하고, 만약 이미 푸시한 뒤였다면 왜 같은 방법을 쓰면 안 되는지 설명하시오.
5. 실수로 `git reset --hard HEAD~1`을 실행해서 방금 만든 커밋이 사라진 것을 발견했다. 이 커밋을 되찾기 위한 절차를 순서대로 서술하시오. 또한 이 방법이 통하지 않는 경우(애초에 커밋한 적 없는 변경 내용을 잃어버린 경우)에는 왜 복구가 불가능한지 설명하시오.

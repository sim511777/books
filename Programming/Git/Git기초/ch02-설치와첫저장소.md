# 2장. 설치와 첫 저장소

## 들어가며

이번 장에서는 실제로 손을 움직여 봅니다. Git을 설치하고, 설치가 잘 되었는지 확인하고, Git이 커밋마다 남기는 "누가 이 변경을 만들었는가"라는 정보를 위해 사용자 이름과 이메일을 설정합니다. 그리고 마지막으로 `git init` 명령으로 첫 저장소를 만들고, 파일 하나를 추가해서 Git이 그 상태를 어떻게 인식하는지 `git status`로 확인해 보겠습니다.

이 장에서 다루는 명령어들은 이후 모든 장에서 반복해서 사용하게 될 기초 중의 기초입니다. 조금 심심하게 느껴질 수 있지만, 여기서 다지는 기본기가 뒤에서 브랜치와 원격 저장소를 다룰 때 큰 도움이 됩니다.

## 운영체제별 설치 방법 개관

Git은 Windows, macOS, Linux를 포함한 대부분의 운영체제에서 무료로 사용할 수 있습니다. 설치 방법은 운영체제마다 조금씩 다르지만, 큰 흐름은 비슷합니다.

**Windows**. 공식 웹사이트(git-scm.com)에서 설치 프로그램을 내려받아 실행하는 방법이 가장 일반적입니다. 이 설치 프로그램에는 Git 명령어를 셸에서 사용할 수 있게 해 주는 "Git Bash"라는 터미널 환경이 함께 포함되어 있어서, Windows에서도 이 책에서 다루는 bash 스타일 명령어를 그대로 사용할 수 있습니다. 패키지 관리자를 사용한다면 `winget install --id Git.Git` 또는 Chocolatey의 `choco install git`, Scoop의 `scoop install git` 같은 방법으로도 설치할 수 있습니다.

**macOS**. Xcode Command Line Tools에 Git이 포함되어 있어서, 터미널에서 `git`을 처음 입력하면 설치 여부를 묻는 안내가 뜨는 경우가 많습니다. Homebrew를 사용한다면 `brew install git` 명령으로 최신 버전을 설치하거나 업데이트할 수 있습니다.

**Linux**. 대부분의 배포판은 패키지 관리자를 통해 Git을 설치할 수 있습니다. Debian/Ubuntu 계열은 `sudo apt install git`, Fedora 계열은 `sudo dnf install git`, Arch Linux 계열은 `sudo pacman -S git` 명령을 사용합니다.

어떤 운영체제를 쓰든, 설치가 끝나면 다음 절에서 확인하는 방법은 동일합니다. 이 책에서는 특정 운영체제의 설치 화면을 캡처해서 보여주지 않습니다. 대신 설치가 끝났다는 전제 아래, 터미널(또는 셸, 명령 프롬프트)에서 Git이 정상적으로 동작하는지 확인하는 것부터 시작하겠습니다.

## 설치 확인하기

터미널을 열고 다음 명령을 입력합니다.

```bash
git --version
```

정상적으로 설치되어 있다면 다음과 비슷한 형태의 출력이 나타납니다. 실제 버전 번호는 여러분이 설치한 시점에 따라 다를 수 있습니다.

```text
git version 2.43.0
```

만약 "command not found"나 "git은 내부 또는 외부 명령... 이 아닙니다" 같은 오류 메시지가 나타난다면, Git이 설치되지 않았거나 설치는 되었지만 시스템의 실행 경로(PATH)에 등록되지 않은 상태입니다. 이 경우 설치 프로그램을 다시 실행하거나, 설치 시 "PATH에 추가" 관련 옵션을 선택했는지 확인해 보아야 합니다.

이 책의 예제들은 Git 2.x 버전을 기준으로 작성되었습니다. Git은 대체로 하위 호환성을 잘 지키는 편이므로, 여러분이 설치한 버전이 이 책 집필 시점의 버전과 정확히 같지 않더라도 대부분의 명령어는 동일하게 동작합니다.

## 사용자 정보 설정하기

Git으로 커밋을 만들 때마다, Git은 "누가 이 변경을 만들었는가"라는 정보를 함께 기록합니다. 이 정보를 미리 설정해 두지 않으면 커밋할 때마다 경고가 나타나거나 커밋 자체가 거부될 수 있으므로, Git을 설치한 뒤 가장 먼저 해야 할 일 중 하나가 바로 사용자 이름과 이메일을 설정하는 것입니다.

```bash
git config --global user.name "Hong Gildong"
git config --global user.email "gildong@example.com"
```

`--global` 옵션은 이 설정을 특정 프로젝트가 아니라 현재 컴퓨터를 사용하는 이 사용자 계정 전체에 적용하겠다는 뜻입니다. 즉 한 번만 설정해 두면, 이후 어떤 저장소에서 커밋을 하든 별도로 다시 설정할 필요 없이 이 이름과 이메일이 사용됩니다.

이름에 공백이 포함되어 있으므로 반드시 따옴표로 감싸야 합니다. 이메일 주소는 실제로 이메일을 주고받는 용도가 아니라 커밋 작성자를 식별하는 값으로 쓰이지만, GitHub 같은 호스팅 서비스와 연동할 때는 그 서비스에 등록된 이메일과 일치시켜 두는 것이 여러 면에서 편리합니다.

기본적으로 사용하는 텍스트 편집기를 지정하고 싶다면 다음과 같이 설정할 수 있습니다. 이 설정은 나중에 커밋 메시지를 편집기에서 작성하는 상황(예: `git commit` 명령을 메시지 없이 실행했을 때)에서 사용됩니다.

```bash
git config --global core.editor "vim"
```

## 설정 확인하기

지금까지 설정한 내용이 실제로 잘 반영되었는지 확인하려면 `git config --list` 명령을 사용합니다.

```bash
git config --list
```

이 명령은 현재 적용되어 있는 모든 설정 항목을 `키=값` 형태로 나열해서 보여줍니다. 방금 설정한 `user.name`과 `user.email`이 목록에 포함되어 있는지 확인해 보세요.

```text
user.name=Hong Gildong
user.email=gildong@example.com
core.editor=vim
...
```

특정 항목 하나만 확인하고 싶다면 `git config` 뒤에 키 이름만 붙여서 조회할 수 있습니다.

```bash
git config user.name
git config user.email
```

각 설정 값이 어느 설정 파일에서 왔는지까지 함께 확인하고 싶다면 `--show-origin` 옵션을 추가로 사용할 수 있습니다.

```bash
git config --list --show-origin
```

### 설정 파일의 세 가지 계층

Git의 설정은 적용 범위에 따라 세 단계의 계층 구조로 나뉘며, 더 좁은 범위의 설정이 더 넓은 범위의 설정을 덮어씁니다.

| 범위 | 옵션 | 적용 대상 | 설정 파일 위치(예시) |
|---|---|---|---|
| system | `--system` | 이 컴퓨터를 사용하는 모든 사용자 | `/etc/gitconfig` |
| global | `--global` | 현재 로그인한 사용자 전체 | `~/.gitconfig` 또는 `~/.config/git/config` |
| local | `--local` (기본값) | 현재 작업 중인 저장소 하나 | 저장소 안의 `.git/config` |

예를 들어 평소에는 개인 이메일로 `--global` 설정을 해 두었더라도, 회사 프로젝트 저장소 안에서만 `--local`로 회사 이메일을 다시 설정하면 그 저장소에서의 커밋에는 회사 이메일이 사용됩니다. `--local` 옵션은 저장소 디렉터리 안에서 실행해야 하며, 별도로 범위를 지정하지 않고 `git config`를 실행하면 기본적으로 local 범위가 대상이 됩니다.

```bash
# 이 저장소에서만 다른 이메일을 쓰고 싶을 때
git config --local user.email "work@company.com"
```

세 계층의 우선순위를 정리하면 다음과 같습니다: local이 global을 덮어쓰고, global이 system을 덮어씁니다. 즉 가장 구체적인 범위의 설정이 항상 우선합니다.

## 첫 저장소 만들기: git init

이제 실제로 저장소를 하나 만들어 보겠습니다. 원하는 위치에 새 디렉터리를 만들고, 그 안으로 이동한 뒤 `git init` 명령을 실행합니다.

```bash
mkdir my-first-repo
cd my-first-repo
git init
```

명령을 실행하면 다음과 비슷한 메시지가 출력됩니다.

```text
Initialized empty Git repository in /path/to/my-first-repo/.git/
```

이 메시지가 뜨는 순간, 현재 디렉터리는 평범한 폴더에서 "Git 저장소"로 바뀝니다. 이 변화의 실체는 디렉터리 안에 `.git`이라는 숨김 디렉터리가 새로 생겼다는 것입니다.

```bash
ls -la
```

Windows의 명령 프롬프트를 사용한다면 다음과 같이 확인할 수 있습니다.

```bash
dir /a
```

`.git` 디렉터리 안에는 이 저장소의 모든 커밋 이력, 브랜치 정보, 설정 값 등 Git이 저장소를 관리하는 데 필요한 모든 데이터가 들어 있습니다. 지금 단계에서 이 디렉터리의 내부 구조를 자세히 들여다볼 필요는 없습니다. 다만 한 가지는 기억해 둘 만합니다. 바로 `.git` 디렉터리 자체가 저장소의 전부라는 점입니다. 이 디렉터리를 통째로 삭제하면 그 저장소의 이력은 모두 사라지고, 반대로 이 디렉터리만 다른 곳에 그대로 복사해도 이력을 포함한 저장소 전체가 복제됩니다. `.git` 디렉터리의 내부 구조와 Git이 데이터를 실제로 어떻게 저장하는지는 3장에서 자세히 다룹니다.

기존에 이미 파일들이 있는 디렉터리에서도 `git init`을 실행할 수 있습니다. 이 경우 기존 파일들이 삭제되거나 변경되지는 않으며, 단지 그 디렉터리가 Git의 추적 대상이 될 준비를 마칠 뿐입니다.

## 첫 파일 만들고 상태 확인하기

방금 만든 저장소 안에 파일을 하나 만들어 보겠습니다.

```bash
echo "# My First Repo" > README.md
```

이제 `git status` 명령으로 현재 저장소의 상태를 확인해 봅니다. 이 명령은 앞으로 작업하면서 가장 자주 입력하게 될 명령어라고 해도 과언이 아닙니다.

```bash
git status
```

다음과 비슷한 출력을 볼 수 있습니다.

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to commit)
```

이 출력을 하나씩 뜯어보겠습니다.

- `On branch main`: 현재 어떤 브랜치 위에 있는지를 알려줍니다. Git 2.28 이후 버전에서는 기본 브랜치 이름으로 `main`을 사용하는 경우가 많지만, 설정이나 Git 버전에 따라 `master`로 표시될 수도 있습니다.
- `No commits yet`: 아직 이 저장소에 한 번도 커밋을 한 적이 없다는 뜻입니다.
- `Untracked files`: Git이 아직 추적하고 있지 않은 파일 목록입니다. 방금 만든 `README.md`가 여기에 나타난 것은, Git이 이 파일의 존재는 알고 있지만 아직 이 파일을 버전 관리 대상으로 등록하지는 않았다는 뜻입니다.

즉 `git init`만으로는 디렉터리 안의 파일들이 자동으로 버전 관리 대상이 되지 않습니다. Git에게 "이 파일을 추적해 달라"고 명시적으로 알려주는 단계가 필요하며, 그 단계가 바로 `git add`와 `git commit`입니다. 이 두 명령과 스냅샷이 실제로 만들어지는 과정은 다음 장에서 자세히 다룹니다. 지금은 `git status`가 "지금 이 저장소 안에서 무슨 일이 벌어지고 있는지"를 알려주는 상태 확인 명령이라는 점만 기억해 두면 충분합니다.

한 가지 더 시도해 볼 수 있습니다. 파일을 하나 더 만들고 다시 `git status`를 실행해 보세요.

```bash
echo "print('hello')" > hello.py
git status
```

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	hello.py

nothing added to commit but untracked files present (use "git add" to commit)
```

새로 만든 `hello.py`도 마찬가지로 Untracked files 목록에 추가된 것을 볼 수 있습니다. `git status`는 이렇게 저장소 안의 파일들이 지금 어떤 상태에 놓여 있는지(추적되지 않음, 수정됨, 스테이징됨 등)를 한눈에 보여주는 역할을 합니다.

## 요약

- Windows, macOS, Linux 모두에서 Git을 설치할 수 있으며, 운영체제별로 공식 설치 프로그램이나 `winget`, `brew`, `apt`, `dnf`, `pacman` 같은 패키지 관리자를 사용할 수 있습니다.
- `git --version`으로 설치 여부와 버전을 확인할 수 있습니다.
- `git config --global user.name`과 `git config --global user.email`로 커밋에 기록될 사용자 정보를 설정합니다.
- `git config --list`로 현재 적용된 설정을 확인할 수 있으며, Git의 설정은 system, global, local 세 계층으로 나뉘고 더 좁은 범위(local)가 더 넓은 범위(global, system)를 덮어씁니다.
- `git init`을 실행하면 현재 디렉터리 안에 `.git` 디렉터리가 생성되면서 그 디렉터리가 Git 저장소가 됩니다. `.git` 디렉터리에는 저장소의 이력과 설정이 모두 담겨 있으며, 이 구조는 3장에서 더 자세히 다룹니다.
- 새로 만든 파일은 `git init` 직후에는 자동으로 추적되지 않으며, `git status`를 실행하면 Untracked files 목록에서 이를 확인할 수 있습니다.

## 연습문제

1. `git --version` 명령을 실행했을 때 "command not found"와 비슷한 오류가 발생했다면, 어떤 원인들을 의심해 볼 수 있는지 설명해 보세요.
2. `git config --global user.name`과 `git config --local user.name`의 차이는 무엇이며, 두 설정이 동시에 존재할 때 어느 쪽이 우선 적용되는지 설명해 보세요.
3. 새 디렉터리를 만들고 `git init`으로 저장소를 초기화한 뒤, `ls -la`(또는 `dir /a`)로 `.git` 디렉터리가 생성되었는지 직접 확인해 보세요.
4. 방금 만든 저장소 안에 파일을 하나 만든 뒤 `git status`를 실행해 보고, 출력에 나타나는 "Untracked files"라는 문구가 어떤 의미인지 자신의 말로 설명해 보세요.
5. system, global, local 세 가지 설정 계층이 왜 필요한지, 회사 컴퓨터에서 개인 프로젝트와 회사 프로젝트를 동시에 다루는 상황을 예로 들어 설명해 보세요.

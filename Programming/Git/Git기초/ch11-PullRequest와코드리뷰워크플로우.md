지금까지 살펴본 브랜치, 커밋, 병합은 모두 Git 자체가 제공하는 기능입니다. 하지만 실제 협업 현장에서 "이 브랜치의 변경 사항을 메인 브랜치에 반영해도 될까요?"라는 질문에 답하는 절차는 Git 명령어만으로는 완성되지 않습니다. 누군가 코드를 검토하고, 의견을 남기고, 필요하면 수정을 요청하고, 최종적으로 승인해서 병합하는 과정이 필요합니다.

이 절차를 지원하기 위해 GitHub, GitLab, Bitbucket 같은 Git 호스팅 서비스들은 **Pull Request(PR)**라는 기능을 제공합니다. Pull Request는 Git 자체의 기능이 아니라 호스팅 서비스가 Git 위에 얹어 놓은 협업 계층입니다. 이 장에서는 GitHub를 기준으로 Pull Request의 개념과 코드 리뷰 워크플로우를 설명합니다. GitLab에서는 같은 개념을 "Merge Request(MR)"라고 부르는데, 이름만 다를 뿐 역할은 동일합니다.

## 11.1 Fork와 Pull Request: 오픈소스 기여 시나리오

오픈소스 프로젝트에 기여하고 싶은데, 그 저장소에 직접 커밋할 권한이 없다면 어떻게 해야 할까요? 이때 사용하는 개념이 **Fork(포크)**입니다.

Fork는 다른 사람의 저장소를 자신의 계정 아래로 통째로 복사하는 것을 말합니다. 예를 들어 `octocat/hello-world`라는 저장소를 포크하면, GitHub 웹 인터페이스의 Fork 버튼을 통해 `내계정/hello-world`라는 새로운 저장소가 서버에 생성됩니다. 이 저장소는 원본과 커밋 히스토리를 공유하지만, 완전히 독립된 저장소이므로 자신의 포크에는 마음대로 푸시할 수 있습니다.

오픈소스 기여의 일반적인 흐름은 다음과 같습니다.

1. GitHub 웹에서 원본 저장소를 자신의 계정으로 Fork한다.
2. 포크한 저장소를 로컬로 clone한다.
3. 원본 저장소를 `upstream`이라는 이름의 원격 저장소로 추가한다.
4. 새 브랜치를 만들어 작업하고, 자신의 포크(`origin`)로 push한다.
5. 포크의 브랜치에서 원본 저장소의 브랜치로 Pull Request를 생성한다.

```bash
# 1. GitHub 웹에서 Fork 버튼을 눌러 내 계정에 저장소 복사본을 만든 뒤

# 2. 내 포크를 로컬로 clone
git clone https://github.com/내계정/hello-world.git
cd hello-world

# 3. 원본 저장소를 upstream이라는 이름으로 등록
git remote add upstream https://github.com/octocat/hello-world.git

# 원격 저장소 목록 확인 (origin은 내 포크, upstream은 원본)
git remote -v

# 4. 작업 전에 원본 저장소의 최신 내용을 받아온다
git fetch upstream
git checkout main
git merge upstream/main

# 새 브랜치를 만들어 작업
git checkout -b fix/typo-in-readme

# 수정 후 커밋
git add README.md
git commit -m "docs: README 오탈자 수정"

# 5. 내 포크(origin)로 push
git push -u origin fix/typo-in-readme
```

push가 끝나면 GitHub는 웹 화면에 "Compare & pull request" 버튼을 보여줍니다. 이 버튼을 누르면 내 포크의 `fix/typo-in-readme` 브랜치를 원본 저장소의 `main` 브랜치와 비교하는 Pull Request 작성 화면으로 이동합니다. 제목과 설명을 작성하고 제출하면, 원본 저장소의 관리자와 기여자들이 이 변경 사항을 검토할 수 있게 됩니다.

원본 저장소가 새로운 커밋으로 계속 업데이트되는 동안, `upstream`에서 다시 받아와 내 로컬 `main`을 최신 상태로 유지하는 습관을 들이면 다음 기여를 시작할 때 편리합니다.

## 11.2 조직 저장소에서의 브랜치 + PR 시나리오

회사나 팀 내부 프로젝트처럼 저장소에 대한 쓰기 권한이 이미 있는 경우에는 포크할 필요가 없습니다. 이 경우에는 저장소를 직접 clone하고, 브랜치를 만들어 같은 저장소에 push한 뒤, 그 브랜치에서 `main`(또는 팀에서 정한 기본 브랜치)으로 Pull Request를 생성합니다.

```bash
# 저장소를 직접 clone (원격은 origin 하나만 있으면 된다)
git clone https://github.com/우리팀/서비스.git
cd 서비스

# 작업용 브랜치 생성
git checkout -b feature/login-page

# 작업 후 커밋
git add .
git commit -m "feat: 로그인 페이지 UI 구현"

# 같은 저장소로 push
git push -u origin feature/login-page
```

두 시나리오의 차이를 정리하면 다음과 같습니다.

| 구분 | 오픈소스(Fork) 모델 | 조직 저장소(Shared Repo) 모델 |
|---|---|---|
| 쓰기 권한 | 원본 저장소에 없음 | 저장소에 이미 있음 |
| 브랜치 위치 | 자신의 포크 저장소 | 원본 저장소 그대로 |
| 원격 저장소 개수 | `origin`(내 포크) + `upstream`(원본) | `origin` 하나 |
| PR 방향 | 포크 브랜치 → 원본 저장소 브랜치 | 같은 저장소 내 브랜치 → 브랜치 |
| 주로 쓰는 곳 | 오픈소스 프로젝트, 외부 기여 | 회사/팀 내부 프로젝트 |

두 모델 모두 "브랜치에서 작업하고 Pull Request로 병합을 요청한다"는 핵심 흐름은 동일합니다. 차이는 그 브랜치가 어느 저장소에 있느냐뿐입니다.

## 11.3 일반적인 협업 흐름

저장소 형태와 관계없이, 실무에서 반복되는 협업 흐름은 대체로 다음 여덟 단계를 따릅니다.

1. **이슈 확인**: 작업할 이슈(버그 리포트, 기능 요청)를 이슈 트래커에서 확인하고 담당자로 지정받는다.
2. **브랜치 생성**: 이슈 내용을 반영한 이름으로 브랜치를 만든다.
3. **커밋**: 작업 단위를 의미 있게 나누어 커밋한다.
4. **푸시**: 원격 저장소로 브랜치를 올린다.
5. **PR 생성**: 무엇을, 왜 바꿨는지 설명을 담아 Pull Request를 연다.
6. **코드 리뷰**: 팀원이 변경 사항을 검토하고 의견을 남긴다.
7. **승인 또는 수정**: 리뷰어가 승인하거나, 수정을 요청하면 다시 커밋해 반영한다.
8. **병합**: 승인된 PR을 병합하고 브랜치를 정리한다.

```bash
# 1~2. 이슈 #42 "장바구니 수량 변경 버그 수정"을 담당하게 되어 브랜치 생성
git checkout main
git pull origin main
git checkout -b fix/cart-quantity-42

# 3. 작업하면서 의미 있는 단위로 커밋
git add src/cart.js
git commit -m "fix: 수량 0 이하로 내려갈 때 예외 처리 추가 (#42)"

git add tests/cart.test.js
git commit -m "test: 수량 경계값 테스트 케이스 추가 (#42)"

# 4. 원격 저장소로 push
git push -u origin fix/cart-quantity-42

# 5. PR 생성 (웹 UI를 사용하거나, GitHub CLI가 설치되어 있다면 아래처럼 생성 가능)
gh pr create \
  --title "fix: 장바구니 수량이 0 이하로 내려가는 버그 수정" \
  --body "이슈 #42 해결. 수량이 0 이하가 될 때 예외를 던지도록 수정하고 경계값 테스트를 추가함." \
  --base main \
  --head fix/cart-quantity-42
```

PR을 열고 나면 리뷰가 진행되는 동안에도 같은 브랜치에 계속 커밋하고 push할 수 있습니다. push할 때마다 PR 화면은 자동으로 최신 커밋을 반영합니다.

```bash
# 리뷰 코멘트를 반영해 수정한 뒤 같은 브랜치에 커밋 추가
git add src/cart.js
git commit -m "refactor: 리뷰 반영 - 예외 메시지를 상수로 분리"
git push
```

리뷰가 완료되고 승인을 받으면, PR을 병합하고 더 이상 필요 없는 로컬/원격 브랜치를 정리합니다.

```bash
# 병합 후 로컬 정리
git checkout main
git pull origin main
git branch -d fix/cart-quantity-42

# 원격 브랜치도 삭제 (GitHub는 PR 병합 시 자동 삭제 옵션을 제공하기도 한다)
git push origin --delete fix/cart-quantity-42
```

## 11.4 PR에서의 리뷰 코멘트, 변경 요청, 승인

GitHub의 Pull Request 화면은 코드 리뷰를 위한 세 가지 주요 액션을 제공합니다. 이 개념들은 Git 명령어가 아니라 GitHub가 제공하는 웹 기능이지만, 협업 흐름을 이해하려면 이름과 의미를 알아둘 필요가 있습니다.

- **코멘트(Comment)**: 승인이나 반려 의사 표시 없이, 특정 파일의 특정 줄이나 PR 전체에 의견을 남기는 것입니다. "이 부분은 왜 이렇게 처리했는지 궁금합니다" 같은 질문이나 제안에 주로 사용합니다.
- **변경 요청(Request changes)**: 리뷰어가 병합 전에 반드시 수정이 필요하다고 판단할 때 사용하는 리뷰 상태입니다. 변경 요청이 걸린 PR은 (저장소 설정에 따라) 그 리뷰어가 다시 승인하기 전까지 병합이 제한될 수 있습니다.
- **승인(Approve)**: 리뷰어가 현재 상태의 변경 사항에 동의하며 병합해도 좋다고 표시하는 것입니다. 저장소 설정에서 "최소 1명 이상의 승인 필요" 같은 브랜치 보호 규칙을 걸어두면, 승인 없이는 병합 버튼이 비활성화됩니다.

리뷰가 반복되는 경우 흐름은 대체로 "PR 생성 → 리뷰어가 변경 요청 → 작성자가 커밋 추가로 반영 → 리뷰어가 다시 확인 후 승인 → 병합" 형태를 띱니다. GitHub CLI를 사용하면 이 리뷰 액션도 명령줄에서 수행할 수 있습니다.

```bash
# PR 목록과 상태 확인
gh pr list
gh pr view 57

# 리뷰어 입장에서 PR을 승인
gh pr review 57 --approve --body "로직 확인했습니다. 문제 없어 보입니다."

# 수정이 필요하다고 판단될 때
gh pr review 57 --request-changes --body "cart.js 42번째 줄, null 체크가 빠진 것 같습니다."

# 승인/반려 없이 의견만 남길 때
gh pr review 57 --comment --body "테스트 케이스 하나만 더 추가해주시면 좋을 것 같아요."
```

## 11.5 PR 병합 방식 세 가지

리뷰가 끝나고 승인이 완료되면 PR을 병합합니다. GitHub는 병합 버튼을 누를 때 세 가지 방식 중 하나를 선택할 수 있게 해줍니다. 각 방식은 로컬 Git 명령어로도 똑같이 재현할 수 있습니다.

### Merge commit

PR 브랜치의 모든 커밋을 그대로 유지한 채, 두 브랜치를 합치는 새 병합 커밋 하나를 추가로 만듭니다. 로컬에서는 다음과 동작이 같습니다.

```bash
git checkout main
git merge --no-ff feature/login-page
```

- **장점**: 어떤 커밋이 어떤 PR을 통해 들어왔는지 히스토리에 그대로 남습니다. 브랜치가 실제로 존재했다는 기록과 병합 시점이 명확히 보존됩니다.
- **단점**: `main` 브랜치의 히스토리가 병합 커밋으로 계속 갈라지고 합쳐지는 형태가 되어, 커밋 그래프가 복잡해질 수 있습니다.
- **적합한 경우**: 릴리스 단위 통합처럼 "이 브랜치가 언제 통째로 들어왔는지"를 추적하는 것이 중요한 경우, 또는 팀이 커밋 단위 히스토리를 세밀하게 남기고 싶어 하는 경우.

### Squash and merge

PR에 포함된 모든 커밋을 하나의 커밋으로 합쳐서 대상 브랜치에 추가합니다. 로컬에서는 다음과 동작이 같습니다.

```bash
git checkout main
git merge --squash feature/login-page
git commit -m "feat: 로그인 페이지 구현 (#42)"
```

- **장점**: `main`의 히스토리가 PR 하나당 커밋 하나로 깔끔하게 정리됩니다. "WIP", "오타 수정", "다시 시도" 같은 작업 중 커밋들이 히스토리에서 사라지고, 의미 있는 단위만 남습니다.
- **단점**: PR 내부의 개별 커밋 히스토리(누가 어떤 순서로 작업했는지)는 사라집니다. 이미 병합된 브랜치를 다시 병합하려 하면 커밋이 겹쳐 보일 수 있어 주의가 필요합니다.
- **적합한 경우**: 기능 브랜치 안에 자잘한 커밋이 많이 쌓이는 팀, 또는 `main`의 히스토리를 최대한 단순하게 유지하고 싶은 팀.

### Rebase and merge

PR의 커밋들을 대상 브랜치의 최신 커밋 위로 재배치(rebase)한 뒤, 병합 커밋 없이 이어 붙입니다. 로컬에서는 다음과 동작이 같습니다.

```bash
git checkout feature/login-page
git rebase main
git checkout main
git merge --ff-only feature/login-page
```

- **장점**: 병합 커밋 없이 하나의 직선 히스토리가 유지되면서도, PR 내부의 개별 커밋들은 그대로 보존됩니다.
- **단점**: rebase 과정에서 커밋 해시가 바뀌므로, 이미 다른 사람이 그 브랜치를 기반으로 작업 중이었다면 충돌이나 혼란이 생길 수 있습니다. (9장에서 다룬 "공유된 히스토리는 rebase하지 않는다"는 원칙이 여기서도 적용됩니다.)
- **적합한 경우**: 커밋 단위를 세밀하게 남기고 싶으면서도 병합 커밋으로 히스토리가 복잡해지는 것은 피하고 싶은 팀. 다만 PR 브랜치 자체는 리뷰가 끝나면 삭제되므로 위 단점의 영향이 제한적입니다.

세 방식을 표로 정리하면 다음과 같습니다.

| 방식 | 커밋 히스토리 | 병합 커밋 | 적합한 상황 |
|---|---|---|---|
| Merge commit | 모든 커밋 보존 | 생성됨 | 브랜치 단위 이력 추적이 중요할 때 |
| Squash and merge | 커밋 하나로 압축 | 생성 안 됨(일반 커밋 하나) | 히스토리를 최대한 단순하게 유지하고 싶을 때 |
| Rebase and merge | 모든 커밋 보존, 위치만 이동 | 생성 안 됨 | 직선 히스토리를 유지하면서 커밋 단위도 남기고 싶을 때 |

많은 팀이 실무에서는 "Squash and merge"를 기본값으로 채택합니다. 작업 중 커밋 메시지 품질이 들쭉날쭉해도 `main`에는 정리된 커밋 하나만 남기 때문입니다. 저장소 설정(Settings → General → Pull Requests)에서 팀이 허용할 병합 방식을 아예 제한해 둘 수도 있습니다.

## 11.6 좋은 Pull Request를 만드는 실무 팁

### 작은 단위로 나누기

한 PR에 로그인 기능, 리팩터링, 스타일 변경이 뒤섞여 있으면 리뷰어는 무엇부터 봐야 할지 판단하기 어렵습니다. 하나의 PR은 하나의 목적을 갖도록 나누는 것이 좋습니다. 리뷰하는 데 몇 분이면 충분한 PR은 리뷰어의 부담을 줄이고, 문제가 생겼을 때 원인을 추적하기도 쉽습니다. "이 PR이 실패하면 되돌릴 수 있는 최소 단위인가?"를 기준으로 나눠보면 도움이 됩니다.

### 명확한 설명 작성하기

PR 설명에는 최소한 다음 세 가지가 담기는 것이 좋습니다.

- **무엇을(What)**: 이 PR이 어떤 변경을 담고 있는가.
- **왜(Why)**: 왜 이 변경이 필요한가. 관련 이슈 번호를 함께 적으면(`#42`) GitHub가 자동으로 링크를 연결해 줍니다.
- **어떻게(How)**: 특별한 구현 방식이나 대안을 검토했다면 그 이유를 남깁니다.

리뷰어 입장에서는 코드만 보고 의도를 추측하는 것보다, 작성자가 남긴 맥락을 먼저 읽고 코드를 보는 편이 훨씬 빠르게 이해할 수 있습니다.

### 셀프 리뷰 먼저 하기

PR을 열기 전에, 리뷰어가 볼 것과 똑같은 화면을 스스로 먼저 훑어보는 습관을 들이면 좋습니다.

```bash
# push 전에 main 대비 변경 사항을 직접 확인
git diff main...feature/login-page

# 커밋 목록과 메시지도 함께 점검
git log main..feature/login-page --oneline
```

자신이 직접 diff를 읽어보면 디버깅용으로 남겨둔 `console.log`, 실수로 포함된 임시 파일, 불필요한 공백 변경 등을 리뷰어보다 먼저 발견할 수 있습니다. GitHub에는 아직 리뷰를 요청할 준비가 안 된 PR을 표시하는 **Draft Pull Request** 기능도 있습니다. 작업 중인 상태를 팀에 공유하고 싶지만 아직 정식 리뷰를 받을 단계는 아닐 때 유용합니다.

## 요약

- Pull Request(PR)는 Git 자체의 기능이 아니라 GitHub 같은 호스팅 서비스가 제공하는 협업 계층으로, 브랜치의 변경 사항을 다른 브랜치에 병합하기 전에 리뷰와 논의를 거치도록 돕는다.
- 오픈소스 기여에서는 저장소를 Fork하고 `upstream` 원격을 등록해 원본과 동기화하며, 조직 내부 저장소에서는 포크 없이 같은 저장소에 브랜치를 만들어 PR을 연다.
- 협업 흐름은 이슈 확인 → 브랜치 생성 → 커밋 → 푸시 → PR 생성 → 코드 리뷰 → 승인/수정 → 병합 순서로 반복된다.
- GitHub는 리뷰 액션으로 코멘트, 변경 요청(Request changes), 승인(Approve) 세 가지를 제공한다.
- PR 병합 방식에는 Merge commit, Squash and merge, Rebase and merge가 있으며, 각각 히스토리를 남기는 방식과 적합한 상황이 다르다.
- 좋은 PR은 작은 단위로 나뉘어 있고, 명확한 설명을 담고 있으며, 작성자가 셀프 리뷰를 먼저 거친다.

## 연습문제

1. Fork 모델과 조직 저장소(Shared Repo) 모델의 차이를 원격 저장소 구성 관점에서 설명해 보세요.
2. `git merge --no-ff`, `git merge --squash`, rebase 후 fast-forward 병합의 결과로 남는 히스토리가 각각 어떻게 다른지 그림이나 글로 설명해 보세요.
3. 여러분이 리뷰어라면 어떤 상황에서 "코멘트"만 남기고, 어떤 상황에서 "변경 요청"을 걸겠습니까? 구체적인 예를 들어 설명해 보세요.
4. 큰 기능 하나를 구현하는 작업을 여러 개의 작은 PR로 나눈다면, 어떤 기준으로 나눌 수 있을지 가상의 기능(예: "회원가입 기능")을 예로 들어 3개 이상의 PR로 쪼개 보세요.
5. `git diff main...feature-branch`와 `git diff main..feature-branch`(점 2개와 3개)의 차이가 궁금하다면 Git 문서를 찾아보고, 셀프 리뷰 시 어느 쪽이 더 적합한지 생각해 보세요.

## 15.1 저장소 안에 다른 저장소가 필요할 때

프로젝트를 진행하다 보면 내 저장소 안에 다른 저장소의 코드를 그대로 포함시켜야 하는 상황을 만나게 된다. 예를 들어 여러 프로젝트에서 공통으로 쓰는 라이브러리를 별도 저장소로 관리하고 있는데, 그 라이브러리의 소스 코드를 애플리케이션 저장소 안에 하위 디렉터리 형태로 가져와야 한다고 해보자.

가장 단순한 방법은 라이브러리의 소스 코드를 복사해서 붙여넣는 것이다. 하지만 이렇게 하면 원본 저장소와의 연결 고리가 완전히 끊어진다. 라이브러리가 업데이트되어도 자동으로 반영되지 않고, 반대로 복사된 코드를 수정해도 원본에 기여할 방법이 없다. 두 저장소의 커밋 이력도 서로 완전히 분리되어, "이 애플리케이션은 라이브러리의 어느 시점 코드를 쓰고 있는가"라는 질문에 답하기 어려워진다.

Git은 이런 상황을 위해 서브모듈(submodule)이라는 기능을 제공한다. 서브모듈은 한 저장소(슈퍼프로젝트, superproject) 안에 다른 저장소(서브모듈)를 하위 디렉터리로 포함시키되, 두 저장소의 커밋 이력을 섞지 않고 독립적으로 유지하는 방법이다. 슈퍼프로젝트는 서브모듈의 전체 이력을 복사해오는 대신, "이 경로에는 어떤 저장소의 어떤 커밋이 들어가야 한다"는 포인터 정보만 기록한다.

## 15.2 git submodule add로 서브모듈 추가하기

기존 저장소에 다른 저장소를 서브모듈로 추가하려면 `git submodule add` 명령을 사용한다.

```bash
# my-app 저장소 안에서 작업한다고 가정
cd my-app

git submodule add https://github.com/example/awesome-lib.git libs/awesome-lib
```

이 명령을 실행하면 Git은 다음과 같은 일을 한다.

1. `https://github.com/example/awesome-lib.git` 저장소를 `libs/awesome-lib` 디렉터리에 클론한다.
2. 최상위 디렉터리에 `.gitmodules` 파일을 만들거나, 이미 있다면 새 항목을 추가한다.
3. `libs/awesome-lib` 경로를 슈퍼프로젝트에 커밋 대상으로 스테이징한다.

`git status`로 확인해보면 흥미로운 점을 발견할 수 있다.

```bash
git status
```

```text
Changes to be committed:
  new file:   .gitmodules
  new file:   libs/awesome-lib
```

`libs/awesome-lib` 디렉터리 안에 파일이 여러 개 있을 텐데도, `git status`는 그 안의 개별 파일을 나열하지 않고 `libs/awesome-lib` 자체를 하나의 항목으로만 보여준다. 이는 슈퍼프로젝트 입장에서 서브모듈 디렉터리가 특수한 항목(gitlink)으로 취급되기 때문이다. 슈퍼프로젝트는 그 디렉터리 안의 파일 내용이 아니라, 서브모듈이 현재 가리키고 있는 커밋 해시 하나만을 기록한다.

## 15.3 .gitmodules 파일 들여다보기

`git submodule add`가 만들어낸 `.gitmodules` 파일을 열어보자.

```bash
cat .gitmodules
```

```ini
[submodule "libs/awesome-lib"]
	path = libs/awesome-lib
	url = https://github.com/example/awesome-lib.git
```

`.gitmodules`는 평범한 텍스트 파일이며, 슈퍼프로젝트에 함께 커밋되어 다른 팀원에게도 그대로 공유된다. 여기에는 서브모듈의 경로(`path`)와 원격 URL(`url`)이 기록되어 있어서, 누군가 이 저장소를 새로 클론했을 때 "어떤 서브모듈을 어디서 가져와야 하는지"를 알 수 있게 해준다.

서브모듈을 여러 개 추가하면 `.gitmodules`에 `[submodule "..."]` 블록이 그만큼 늘어난다.

```bash
git submodule add https://github.com/example/ui-kit.git libs/ui-kit
```

```ini
[submodule "libs/awesome-lib"]
	path = libs/awesome-lib
	url = https://github.com/example/awesome-lib.git
[submodule "libs/ui-kit"]
	path = libs/ui-kit
	url = https://github.com/example/ui-kit.git
```

변경 사항을 커밋하면 슈퍼프로젝트의 이력에는 `.gitmodules`와 서브모듈 경로에 대한 포인터 정보만 남고, 서브모듈 내부의 커밋들은 슈퍼프로젝트의 `git log`에 나타나지 않는다.

```bash
git commit -m "Add awesome-lib and ui-kit as submodules"
```

## 15.4 서브모듈이 가리키는 커밋 확인하기

서브모듈 디렉터리로 들어가 보면 그 자체가 완전한 Git 저장소라는 사실을 알 수 있다.

```bash
cd libs/awesome-lib
git log -1
git branch -v
cd ../..
```

슈퍼프로젝트 쪽에서 각 서브모듈이 현재 어떤 커밋을 가리키고 있는지 한눈에 보려면 `git submodule status`를 사용한다.

```bash
git submodule status
```

```text
 3f2c1a9b4e8d7c6f5a4b3c2d1e0f9a8b7c6d5e4f libs/awesome-lib (v1.2.0)
 9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b libs/ui-kit (heads/main)
```

각 줄 맨 앞의 문자는 서브모듈의 상태를 나타낸다.

- 공백: 서브모듈이 슈퍼프로젝트에 기록된 커밋과 정확히 일치하는 상태로 체크아웃되어 있다.
- `+`: 서브모듈이 슈퍼프로젝트에 기록된 커밋과 다른 커밋으로 체크아웃되어 있다(로컬에서 변경되었음을 뜻한다).
- `-`: 서브모듈이 아직 초기화되지 않았다(클론만 되어 있고 내용은 비어 있는 상태).
- `U`: 서브모듈에 병합 충돌이 있다.

`git diff`를 슈퍼프로젝트 루트에서 실행하면, 서브모듈 항목이 변경되었을 때 파일 내용 대신 커밋 해시가 어떻게 바뀌었는지를 보여준다.

```bash
cd libs/awesome-lib
git checkout v1.3.0
cd ../..
git diff
```

```diff
diff --git a/libs/awesome-lib b/libs/awesome-lib
index 3f2c1a9..7d4e2f1 160000
--- a/libs/awesome-lib
+++ b/libs/awesome-lib
@@ -1 +1 @@
-Subproject commit 3f2c1a9b4e8d7c6f5a4b3c2d1e0f9a8b7c6d5e4f
+Subproject commit 7d4e2f1a9b8c7d6e5f4a3b2c1d0e9f8a7b6c5d4e
```

이 diff는 파일이 아니라 "포인터"가 바뀌었다는 것을 보여준다. 이 변경을 슈퍼프로젝트에 커밋해야 비로소 `libs/awesome-lib`가 새 버전(`v1.3.0`)을 가리킨다는 사실이 슈퍼프로젝트 이력에 남는다.

```bash
git add libs/awesome-lib
git commit -m "Bump awesome-lib to v1.3.0"
```

## 15.5 clone할 때 서브모듈까지 함께 받기

`.gitmodules`가 있는 저장소를 그냥 `git clone`으로 받으면, 서브모듈 디렉터리는 비어 있는 채로 남는다. Git이 슈퍼프로젝트의 파일만 가져오고, 서브모듈 자체는 클론하지 않기 때문이다.

```bash
git clone https://github.com/example/my-app.git
cd my-app
ls libs/awesome-lib
```

`libs/awesome-lib` 디렉터리는 존재하지만 그 안은 비어 있다. 이는 서브모듈을 처음 다루는 사람이 가장 자주 놀라는 지점이다.

처음부터 서브모듈까지 한 번에 받고 싶다면 클론할 때 `--recurse-submodules` 옵션을 붙인다.

```bash
git clone --recurse-submodules https://github.com/example/my-app.git
```

이렇게 하면 Git은 슈퍼프로젝트를 클론한 뒤, `.gitmodules`에 등록된 모든 서브모듈을 자동으로 초기화하고 슈퍼프로젝트가 기록해 둔 커밋으로 체크아웃한다. 서브모듈 안에 또 다른 서브모듈이 있는 경우(중첩 서브모듈)도 재귀적으로 처리된다.

## 15.6 이미 클론된 저장소에서 서브모듈 받아오기

`--recurse-submodules` 없이 이미 클론을 마쳤거나, 다른 팀원이 새 서브모듈을 추가한 뒤 pull만 받은 상태라면, 서브모듈 내용을 받아오기 위해 별도의 명령이 필요하다.

```bash
git submodule update --init --recursive
```

이 명령은 세 단계를 한 번에 수행한다.

- `--init`: `.gitmodules`에 등록되어 있지만 아직 로컬 `.git/config`에 등록되지 않은 서브모듈을 초기화한다.
- (초기화 후) 각 서브모듈을 슈퍼프로젝트가 기록해 둔 커밋 해시로 클론·체크아웃한다.
- `--recursive`: 서브모듈 안에 또 다른 서브모듈이 있다면 그것까지 재귀적으로 처리한다.

일상적인 워크플로에서는 슈퍼프로젝트를 `git pull`한 뒤 이 명령을 함께 실행하는 습관을 들이는 것이 안전하다.

```bash
git pull
git submodule update --init --recursive
```

## 15.7 서브모듈을 원격의 최신 커밋으로 갱신하기

`git submodule update`를 옵션 없이 실행하면 서브모듈을 슈퍼프로젝트에 "기록된" 커밋으로 되돌릴 뿐, 서브모듈 원격 저장소의 최신 변경 사항을 가져오지는 않는다. 서브모듈을 최신 상태로 갱신하고 싶다면 `--remote` 옵션을 사용한다.

```bash
git submodule update --remote libs/awesome-lib
```

이 명령은 `libs/awesome-lib` 서브모듈 안에서 원격의 최신 커밋(기본적으로 `.gitmodules`에 지정된 브랜치, 없으면 서브모듈의 기본 브랜치)을 가져와 체크아웃한다. 특정 브랜치를 추적하도록 지정하려면 `.gitmodules`에 `branch` 항목을 추가할 수 있다.

```bash
git config -f .gitmodules submodule.libs/awesome-lib.branch main
```

여러 서브모듈에 동일한 명령을 반복해서 실행하고 싶을 때는 `git submodule foreach`가 유용하다.

```bash
git submodule foreach 'git checkout main && git pull origin main'
```

물론 `--remote`로 서브모듈 내용을 갱신했다면, 그 결과 역시 슈퍼프로젝트 입장에서는 "포인터가 바뀐 것"이므로 반드시 슈퍼프로젝트에서 다시 커밋해야 한다.

```bash
git add libs/awesome-lib
git commit -m "Update awesome-lib to latest main"
```

## 15.8 서브모듈, 솔직히 말해서 번거롭다

서브모듈은 강력하지만, 실무에서 팀 단위로 사용해보면 다음과 같은 어려움을 자주 겪게 된다. 이 절은 서브모듈을 도입하기 전에 반드시 알아두어야 할 현실적인 비용을 정리한 것이다.

- **커밋 포인터를 계속 챙겨야 한다.** 서브모듈 안에서 변경하고 커밋한 뒤 슈퍼프로젝트에서 다시 `git add`/`git commit`을 하지 않으면, 슈퍼프로젝트는 여전히 예전 커밋을 가리킨 채로 남는다. 이 두 번째 커밋을 깜빡하는 실수가 매우 흔하다.
- **클론과 pull이 한 단계씩 늘어난다.** `--recurse-submodules`나 `submodule update --init --recursive`를 매번 기억해야 하며, 신규 팀원이 이 과정을 모른 채 빈 디렉터리를 보고 당황하는 일이 잦다.
- **detached HEAD 상태가 기본이다.** 서브모듈을 초기화하거나 업데이트하면 서브모듈은 특정 브랜치가 아니라 특정 커밋을 가리키는 detached HEAD 상태로 체크아웃된다. 서브모듈 안에서 바로 코드를 수정하려면 먼저 브랜치를 체크아웃해야 한다는 점을 잊기 쉽다.
- **팀원 간 동기화가 어긋나기 쉽다.** 한 팀원이 서브모듈 포인터를 새 커밋으로 갱신해서 푸시했는데, 다른 팀원이 슈퍼프로젝트만 pull하고 `submodule update`를 실행하지 않으면 두 사람의 작업 디렉터리가 눈에 보이지 않게 서로 다른 버전의 서브모듈을 담고 있게 된다.
- **URL이 바뀌면 별도로 동기화해야 한다.** 서브모듈 저장소의 URL이 바뀌었을 때 `.gitmodules`만 수정해서는 부족하고, `git submodule sync`를 실행해 로컬 `.git/config`에 반영된 URL까지 갱신해야 한다.
- **삭제 과정이 직관적이지 않다.** 서브모듈을 제거하려면 여러 단계를 거쳐야 한다.

```bash
git submodule deinit -f -- libs/awesome-lib
git rm -f libs/awesome-lib
rm -rf .git/modules/libs/awesome-lib
git commit -m "Remove awesome-lib submodule"
```

이런 이유로 서브모듈은 "정말로 독립적인 버전 관리가 필요한 외부 의존성"에는 적합하지만, 팀 내부에서 자주 함께 수정되는 코드에는 잘 맞지 않는 경우가 많다. 서브모듈을 도입하기 전에 "이 코드가 슈퍼프로젝트와 얼마나 자주 함께 바뀌는가"를 스스로 물어보는 것이 좋다.

## 15.9 대안으로서의 git subtree

서브모듈의 번거로움 때문에 등장한 대안 중 하나가 `git subtree`다. 서브모듈이 "다른 저장소를 가리키는 포인터"를 저장하는 방식이라면, subtree는 다른 저장소의 이력을 슈퍼프로젝트의 이력 안으로 실제로 병합해 넣는 방식이다.

```bash
git subtree add --prefix=libs/awesome-lib https://github.com/example/awesome-lib.git main --squash
```

이 명령을 실행하면 `awesome-lib` 저장소의 코드가 `libs/awesome-lib` 디렉터리에 그대로 복사되어 슈퍼프로젝트의 커밋 하나(또는 `--squash`를 생략하면 전체 이력)로 들어간다. 이렇게 만들어진 저장소는 클론 시점에 별도의 `.gitmodules`나 `submodule update` 같은 추가 단계가 전혀 필요 없다. 그냥 `git clone`만 해도 `libs/awesome-lib` 안의 파일이 처음부터 다 들어 있다.

물론 대가도 있다. subtree로 가져온 코드를 원본 저장소에 다시 반영하려면 `git subtree push`처럼 별도의 명령이 필요하고, 슈퍼프로젝트의 커밋 이력이 가져온 코드의 이력까지 포함하면서 더 커지고 복잡해질 수 있다. subtree의 세부 옵션과 워크플로는 이 책의 범위를 벗어나므로, 여기서는 "서브모듈과는 다른 접근 방식이 존재한다"는 사실과 대략적인 개념만 짚고 넘어간다. 실제 프로젝트에 subtree를 도입하려 한다면 별도의 문서를 참고해 세부 동작을 확인하기를 권한다.

## 15.10 모노레포라는 또 다른 선택지

여러 프로젝트나 컴포넌트를 다룰 때 서브모듈이나 subtree처럼 "저장소를 나누고 다시 연결하는" 방법 대신, 처음부터 모든 것을 하나의 저장소에 담아버리는 접근도 있다. 이를 모노레포(monorepo)라고 부른다. 반대로 컴포넌트마다 별도의 저장소를 두는 전통적인 방식은 멀티레포(multi-repo)라고 부르며, 서브모듈은 멀티레포 구조에서 저장소들을 연결하는 한 가지 수단이라고 볼 수 있다.

두 접근 방식은 각각 뚜렷한 장단점을 가지며, 어느 쪽이 절대적으로 우월하다고 말하기 어렵다.

**모노레포의 장점**

- 여러 컴포넌트에 걸친 변경을 하나의 커밋(또는 하나의 PR)으로 원자적으로 반영할 수 있다. 예를 들어 공통 라이브러리의 API를 바꾸면서 이를 사용하는 애플리케이션 코드도 같은 커밋에서 함께 수정할 수 있다.
- 코드 검색과 리팩토링이 저장소 하나 안에서 끝난다. IDE의 "전체 검색"이나 "이름 바꾸기" 기능이 컴포넌트 경계를 넘어 그대로 작동한다.
- 빌드 도구, 린트 설정, CI 파이프라인 같은 공통 인프라를 한 곳에서 관리하기 쉽다.
- 서브모듈처럼 포인터를 챙기고 동기화할 필요가 없다. `git clone` 한 번으로 전체 코드를 받을 수 있다.

**모노레포의 단점**

- 저장소 자체가 계속 커지므로, 이력이 쌓일수록 clone/fetch 속도가 느려질 수 있다.
- 모든 팀이 하나의 저장소에 커밋을 쌓으므로 커밋 그래프와 브랜치가 복잡해지기 쉽다.
- 저장소 단위로 접근 권한을 나누기 어렵다. 특정 팀에게 일부 디렉터리만 보여주고 싶어도 Git 자체는 저장소 전체 단위로만 접근 권한을 다룬다.

**멀티레포(서브모듈 포함)의 장점**

- 각 컴포넌트가 독립적인 저장소이므로 버전, 릴리스 주기, 접근 권한을 컴포넌트별로 완전히 분리할 수 있다.
- 저장소 하나하나의 크기가 작게 유지되어 clone과 fetch가 가볍다.
- 특정 컴포넌트만 필요한 사람은 그 저장소만 받으면 된다.

**멀티레포(서브모듈 포함)의 단점**

- 여러 저장소에 걸친 변경을 원자적으로 묶을 방법이 없다. 라이브러리와 애플리케이션을 동시에 바꾸는 작업이 서로 다른 저장소의 서로 다른 커밋/PR로 쪼개진다.
- 컴포넌트 간 의존 관계를 파악하려면 각 저장소를 따로 살펴봐야 한다.
- 15.8절에서 다룬 서브모듈의 동기화 문제가 그대로 따라온다.

참고로 모노레포가 커지면서 생기는 clone/fetch 성능 문제는, 특정 외부 도구를 도입하지 않고도 Git 자체가 제공하는 기능으로 어느 정도 완화할 수 있다. 필요한 디렉터리만 체크아웃하는 `git sparse-checkout`, 파일 내용을 필요한 시점까지 내려받지 않는 부분 클론(`git clone --filter=blob:none`), 이력을 얕게만 가져오는 얕은 클론(`git clone --depth`) 등이 그 예다. 이런 기능들은 뒤에서 다시 다룰 만한 주제이므로, 여기서는 "모노레포를 고려할 때 Git 자체에도 대응 수단이 있다"는 정도만 기억해두자.

결국 서브모듈/멀티레포와 모노레포 중 무엇을 선택할지는 팀의 조직 구조, 컴포넌트 간 결합도, 저장소 규모, 접근 권한 요구 사항에 따라 달라지는 트레이드오프의 문제다. 이 책에서는 어느 한쪽을 정답으로 제시하지 않으며, 각 방식이 어떤 상황에서 강점을 갖는지 이해하고 프로젝트의 상황에 맞게 판단하는 것을 목표로 한다.

## 요약

- 서브모듈은 슈퍼프로젝트 안에 다른 저장소를 하위 디렉터리로 포함시키되, 두 저장소의 이력을 분리해서 유지하는 기능이다. 슈퍼프로젝트는 서브모듈이 가리키는 커밋 해시(포인터)만 기록한다.
- `git submodule add <url> <path>`로 서브모듈을 추가하면 `.gitmodules` 파일이 생성·갱신되고, 슈퍼프로젝트에는 서브모듈 경로가 gitlink 항목으로 스테이징된다.
- `git clone --recurse-submodules`는 클론과 동시에 서브모듈까지 받아온다. 이미 클론된 저장소에서는 `git submodule update --init --recursive`로 서브모듈을 초기화하고 받아올 수 있다.
- 서브모듈 안에서 커밋을 만들거나 `git submodule update --remote`로 최신 커밋을 받아온 뒤에는, 슈퍼프로젝트에서 다시 `git add`/`git commit`을 해야 그 변경이 슈퍼프로젝트 이력에 반영된다.
- 서브모듈은 포인터 관리, detached HEAD, 팀원 간 동기화, 삭제 절차 등에서 실무적인 번거로움이 있다. `git subtree`는 다른 저장소의 이력을 아예 병합해 넣어 이런 번거로움 일부를 줄여주는 대안이다.
- 모노레포는 원자적 커밋과 통합된 코드 관리라는 장점을, 멀티레포(서브모듈 포함)는 독립적인 버전 관리와 가벼운 저장소 크기라는 장점을 갖는다. 어떤 구조가 적합한지는 팀과 프로젝트의 상황에 달려 있다.

## 연습문제

1. 서브모듈을 추가한 뒤 `git status`를 실행했을 때, 서브모듈 디렉터리 안의 개별 파일이 아니라 디렉터리 자체가 하나의 변경 항목으로 나타나는 이유를 설명하라.
2. 새 팀원이 `git clone`(옵션 없이)으로 서브모듈이 포함된 저장소를 받았다. 서브모듈 디렉터리가 비어 있는 이유와, 이를 해결하기 위해 실행해야 할 명령을 순서대로 설명하라.
3. 팀원 A가 서브모듈 안에서 새 커밋을 만들고 슈퍼프로젝트에서 포인터를 갱신해 푸시했다. 팀원 B가 슈퍼프로젝트만 `git pull`하고 아무 작업도 하지 않았을 때 어떤 문제가 발생할 수 있는지, 그리고 이를 막으려면 어떤 명령이 필요한지 설명하라.
4. 서브모듈과 `git subtree`가 다른 저장소의 코드를 가져오는 방식이 근본적으로 어떻게 다른지 비교하고, 각각의 장단점을 한 가지씩 제시하라.
5. 당신이 세 개의 서로 다른 마이크로서비스와 하나의 공통 라이브러리를 관리해야 한다고 가정하자. 이들을 모노레포로 관리할 때와 서브모듈을 사용한 멀티레포로 관리할 때 각각 어떤 상황에서 더 유리할지 논하라.

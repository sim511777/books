## 17.1 재귀 함수의 두 축: 기저 조건과 재귀 단계

**재귀(recursion)**란 함수가 자기 자신을 호출하는 방식으로 문제를 해결하는 기법입니다. 재귀 함수가 무한히 자신을 호출하며 폭주하지 않으려면 반드시 두 부분이 필요합니다.

1. **기저 조건(base case)**: 더 이상 재귀 호출을 하지 않고 즉시 답을 반환하는 조건. 재귀가 멈추는 지점입니다.
2. **재귀 단계(recursive case)**: 문제를 더 작은 버전의 같은 문제로 줄여서 자기 자신을 호출하고, 그 결과를 이용해 현재 문제의 답을 만드는 부분입니다.

가장 널리 쓰이는 예제인 팩토리얼로 시작해봅시다. n의 팩토리얼(n!)은 "1부터 n까지의 모든 정수를 곱한 값"으로 정의되며, 재귀적으로는 다음과 같이 정의할 수 있습니다.

- 기저 조건: `0! = 1`
- 재귀 단계: `n! = n * (n-1)!` (단, n ≥ 1)

이 정의를 그대로 코드로 옮기면 다음과 같습니다.

```csharp
public static long Factorial(int n)
{
    if (n < 0)
        throw new ArgumentOutOfRangeException(nameof(n), "음수는 팩토리얼을 정의할 수 없습니다.");

    // 기저 조건: 더 이상 쪼갤 수 없는 가장 단순한 경우
    if (n == 0)
        return 1;

    // 재귀 단계: n! 문제를 (n-1)! 이라는 더 작은 같은 문제로 줄인다
    return n * Factorial(n - 1);
}
```

`Factorial(5)`를 호출하면 내부적으로 다음과 같은 호출의 연쇄가 일어납니다.

```
Factorial(5)
= 5 * Factorial(4)
= 5 * (4 * Factorial(3))
= 5 * (4 * (3 * Factorial(2)))
= 5 * (4 * (3 * (2 * Factorial(1))))
= 5 * (4 * (3 * (2 * (1 * Factorial(0)))))
= 5 * (4 * (3 * (2 * (1 * 1))))
= 120
```

호출은 `Factorial(0)`에 도달할 때까지 계속 "더 작은 문제"를 향해 내려가고(하강 단계), 기저 조건에 도달한 순간부터는 각 호출이 자신을 호출한 곳으로 곱셈 결과를 돌려주면서 답을 조립합니다(상승 단계). 이 두 단계 — 문제를 쪼개며 내려가는 것과 결과를 조립하며 올라오는 것 — 은 이후 다룰 모든 재귀 알고리즘에서 반복해서 등장하는 패턴입니다.

기저 조건을 빠뜨리면 어떻게 될까요? 만약 `if (n == 0) return 1;` 줄을 지운다면 `Factorial`은 n이 음수 방향으로 한없이 줄어들며 영원히 자신을 호출하려 시도합니다. 이런 경우 프로그램은 조금 뒤에 살펴볼 `StackOverflowException`으로 강제 종료됩니다. **모든 재귀 함수는 반드시 도달 가능한 기저 조건을 가져야 하며, 재귀 단계는 매번 기저 조건에 한 걸음씩 가까워지는 방향으로 문제를 줄여야 합니다.**

## 17.2 두 번째 예제: 피보나치 수열

재귀에 익숙해지기 위해 하나만 더 살펴봅시다. 피보나치 수열은 "앞의 두 항을 더해 다음 항을 만드는" 수열로, 0, 1, 1, 2, 3, 5, 8, 13, ...로 이어집니다. 정의는 다음과 같습니다.

- 기저 조건: `F(0) = 0`, `F(1) = 1`
- 재귀 단계: `F(n) = F(n-1) + F(n-2)` (단, n ≥ 2)

팩토리얼과 다른 점은 재귀 단계에서 자기 자신을 **두 번** 호출한다는 것입니다.

```csharp
public static long Fibonacci(int n)
{
    if (n < 0)
        throw new ArgumentOutOfRangeException(nameof(n));

    // 기저 조건: n이 0 또는 1이면 그 값 자체가 답이다
    if (n == 0 || n == 1)
        return n;

    // 재귀 단계: 더 작은 두 개의 같은 문제로 나눠서 풀고 결과를 합친다
    return Fibonacci(n - 1) + Fibonacci(n - 2);
}
```

`Fibonacci(5)`를 호출하면 호출이 하나의 사슬이 아니라 나무(tree) 모양으로 뻗어나갑니다.

```
                    F(5)
                 /        \
             F(4)          F(3)
            /    \        /    \
         F(3)    F(2)   F(2)   F(1)
        /    \   /  \   /  \
     F(2)  F(1) F(1)F(0)F(1)F(0)
    /   \
  F(1) F(0)
```

당장은 결과만 확인하고 넘어가되, 이 그림에서 `F(3)`이 두 번, `F(2)`가 세 번 등장한다는 점을 눈여겨봐 주세요. 이 중복은 17.5절에서 다시 자세히 다룹니다.

## 17.3 재귀는 어떻게 실행되는가: 호출 스택

재귀가 "마법처럼" 동작하는 것처럼 보이지만, 사실 그 뒤에는 5장에서 다룬 **스택**이 그대로 자리 잡고 있습니다. 함수를 호출할 때마다 런타임은 그 함수 호출에 필요한 정보 — 매개변수 값, 지역 변수, 함수가 반환된 뒤 실행을 이어갈 위치 — 를 담은 **스택 프레임(stack frame)**을 **호출 스택(call stack)**에 쌓습니다(push). 함수가 반환되면 그 프레임은 스택에서 제거됩니다(pop). 이는 정확히 5장에서 배운 후입선출(LIFO) 구조입니다.

재귀 함수는 자기 자신을 호출할 때마다 새로운 스택 프레임을 쌓습니다. `Factorial(3)`을 호출하는 과정을 호출 스택의 관점에서 그려보면 다음과 같습니다.

```
호출이 진행되며 쌓이는 과정 (아래가 스택의 바닥)

Factorial(0) 호출         → [F(3)] [F(2)] [F(1)] [F(0)]   <- 맨 위(top)
Factorial(1) 호출         → [F(3)] [F(2)] [F(1)]
Factorial(2) 호출         → [F(3)] [F(2)]
Factorial(3) 호출         → [F(3)]
```

`Factorial(0)`이 `1`을 반환하면 스택 맨 위의 `F(0)` 프레임이 제거되고, 그 결과는 `F(1)` 프레임으로 전달되어 `1 * 1`을 계산합니다. `F(1)`이 반환되면 그 프레임도 제거되고 결과는 `F(2)`로 전달됩니다. 이렇게 스택이 하나씩 줄어들며(pop) 최종 결과가 조립되는 과정이, 앞서 17.1절에서 말한 "상승 단계"의 실체입니다.

이 사실은 중요한 결론으로 이어집니다. **재귀 호출이 너무 깊어지면 호출 스택 프레임이 계속 쌓여 메모리(호출 스택 공간)를 소진하고, `StackOverflowException`이 발생합니다.** 예를 들어 `Factorial(-1)`처럼 기저 조건에 도달하지 못하는 입력을 주거나, 재귀 깊이가 수십만에 이르는 문제를 무작정 재귀로 풀면 이 문제를 겪을 수 있습니다.

```csharp
// 위험한 예: 기저 조건이 없는 재귀는 스택을 무한정 소진한다
public static long BrokenCountDown(int n)
{
    Console.WriteLine(n);
    return BrokenCountDown(n - 1); // 절대 멈추지 않는다
}
```

반면 어떤 언어와 런타임은 **꼬리 재귀(tail recursion)** — 재귀 호출이 함수의 가장 마지막 동작이고 그 결과에 별다른 후처리를 하지 않는 형태 — 를 반복문처럼 최적화해서 스택을 소진하지 않게 만들기도 합니다. 다만 C#/.NET 런타임은 이런 꼬리 호출 최적화를 신뢰성 있게 보장하지 않으므로, 재귀 깊이가 매우 커질 수 있는 문제라면 반복문으로 바꾸거나 6장에서 다룬 큐, 혹은 스택 자료구조를 직접 사용해 반복적으로(iteratively) 흉내 내는 방법을 고려해야 합니다. 즉 재귀로 짠 코드는 "암묵적으로 스택을 사용하는 코드"이고, 반복문 + 직접 만든 스택으로 짠 코드는 "명시적으로 스택을 사용하는 코드"입니다. 둘은 근본적으로 같은 일을 하고 있는 셈입니다.

## 17.4 분할 정복 전략

재귀가 하나의 프로그래밍 기법이라면, **분할 정복(divide and conquer)**은 그 기법을 이용한 문제 해결 **전략**입니다. 분할 정복은 다음 세 단계로 요약됩니다.

1. **분할(Divide)**: 원래 문제를 더 작은 크기의 동일한 형태의 부분 문제들로 나눈다.
2. **정복(Conquer)**: 부분 문제가 충분히 작아 기저 조건에 해당하면 직접 풀고, 그렇지 않으면 재귀적으로 같은 전략을 적용해 푼다.
3. **결합(Combine)**: 부분 문제들의 답을 합쳐서 원래 문제의 답을 만든다.

이 세 단계는 17.1절에서 본 재귀의 구조와 정확히 대응됩니다. "분할"은 재귀 단계에서 문제를 줄이는 부분에, "정복"의 기저 조건 처리는 재귀의 기저 조건에, "결합"은 재귀 호출 결과들을 조립하는 상승 단계에 해당합니다. 다만 분할 정복이라는 이름을 따로 붙이는 이유는, 이 전략이 단순히 "함수가 자기 자신을 부른다"는 수준을 넘어서 **문제를 절반씩(또는 그에 준하는 비율로) 나눔으로써 전체 작업량을 극적으로 줄이는 알고리즘 설계 기법**이기 때문입니다.

이 전략을 가장 잘 보여주는 예는 이미 15장에서 다룬 **병합 정렬(merge sort)**입니다. 여기서 분할 정복의 틀로 다시 조명해보겠습니다.

- **분할**: 길이 n인 배열을 정확히 절반으로 나눠 길이 n/2인 두 개의 부분 배열을 만든다.
- **정복**: 각 부분 배열이 원소 1개 이하이면(기저 조건) 이미 정렬된 것으로 간주한다. 그렇지 않다면 각 부분 배열에 병합 정렬을 재귀적으로 적용해 정렬한다.
- **결합**: 정렬된 두 부분 배열을 하나로 병합(merge)해서 전체가 정렬된 배열을 만든다.

```csharp
public static int[] MergeSort(int[] array)
{
    // 기저 조건: 원소가 1개 이하면 이미 정렬된 상태
    if (array.Length <= 1)
        return array;

    // 분할: 배열을 절반으로 나눈다
    int mid = array.Length / 2;
    int[] left = array[0..mid];
    int[] right = array[mid..];

    // 정복: 각 절반을 재귀적으로 정렬한다
    int[] sortedLeft = MergeSort(left);
    int[] sortedRight = MergeSort(right);

    // 결합: 정렬된 두 부분을 하나로 병합한다
    return Merge(sortedLeft, sortedRight);
}

private static int[] Merge(int[] left, int[] right)
{
    int[] result = new int[left.Length + right.Length];
    int i = 0, j = 0, k = 0;

    while (i < left.Length && j < right.Length)
    {
        if (left[i] <= right[j])
            result[k++] = left[i++];
        else
            result[k++] = right[j++];
    }

    while (i < left.Length) result[k++] = left[i++];
    while (j < right.Length) result[k++] = right[j++];

    return result;
}
```

여기서 재귀 호출을 호출 스택 관점에서 다시 생각해봅시다. `MergeSort`가 배열을 절반씩 나누며 재귀 호출을 반복하면, 호출 스택에는 "왼쪽 절반을 정렬하라"는 프레임들이 배열 길이가 1이 될 때까지 계속 쌓입니다. 배열 길이가 n이면 절반씩 나누는 과정을 log₂(n)번 반복해야 1에 도달하므로, 호출 스택의 최대 깊이는 O(log n)입니다. 이는 앞서 말한 "재귀 깊이가 너무 크면 위험하다"는 우려와도 연결됩니다. 병합 정렬처럼 매번 절반으로 나누는 분할 정복은 깊이가 로그 스케일로 억제되기 때문에 실무에서 안전하게 재귀로 구현할 수 있지만, 만약 "절반"이 아니라 "1개씩만 줄어드는" 분할을 한다면(예: 17.1절의 `Factorial`처럼 n을 n-1로만 줄이는 경우) 깊이가 O(n)이 되어 훨씬 위험해질 수 있습니다.

분할 정복의 전체 수행 시간을 분석할 때는 보통 다음과 같은 **점화식(recurrence relation)**을 세웁니다. 병합 정렬의 경우:

```
T(n) = 2 * T(n/2) + O(n)
```

"크기 n인 문제 하나를 풀려면, 크기 n/2인 부분 문제 두 개를 풀고(2 * T(n/2)), 그 결과를 병합하는 데 O(n)이 든다"는 뜻입니다. 이 점화식을 풀면 T(n) = O(n log n)이라는, 2장에서 배운 복잡도 표기법으로 표현되는 결과가 나옵니다. 병합 정렬이 단순 정렬(버블, 선택, 삽입 정렬 — 모두 O(n²))보다 빠른 근본적인 이유가 바로 이 "절반씩 나눈다"는 분할 전략에 있습니다.

## 17.5 재귀의 함정: 피보나치의 중복 계산

분할 정복이 항상 병합 정렬처럼 효율적인 것은 아닙니다. 17.2절에서 본 재귀 피보나치로 돌아가 봅시다. 실제로 호출 횟수를 세어보면 문제가 드러납니다.

```csharp
public static int CallCount = 0;

public static long FibonacciCountingCalls(int n)
{
    CallCount++;

    if (n == 0 || n == 1)
        return n;

    return FibonacciCountingCalls(n - 1) + FibonacciCountingCalls(n - 2);
}
```

```csharp
CallCount = 0;
FibonacciCountingCalls(10);
Console.WriteLine(CallCount); // 177

CallCount = 0;
FibonacciCountingCalls(30);
Console.WriteLine(CallCount); // 2,692,537
```

n이 10에서 30으로 3배 커졌을 뿐인데 호출 횟수는 만 배 넘게 늘어납니다. 왜 이런 일이 벌어질까요? 17.2절의 호출 트리 그림을 다시 보면, `F(3)`이 두 번, `F(2)`가 세 번 계산되고 있었습니다. n이 커질수록 이런 중복은 기하급수적으로 불어납니다. `F(n)`을 계산하려면 `F(n-1)`과 `F(n-2)`를 계산해야 하는데, `F(n-1)`을 계산하는 과정에서 **다시** `F(n-2)`를 처음부터 계산합니다. 즉 같은 부분 문제가 서로 다른 호출 경로에서 반복적으로, 그것도 매번 처음부터 다시 계산되고 있는 것입니다.

이 재귀 피보나치의 전체 호출 횟수는 대략 O(2ⁿ)에 달합니다. 지수 시간 알고리즘은 n이 조금만 커져도 감당할 수 없을 만큼 느려집니다. 병합 정렬은 문제를 절반으로 나눈 뒤 "겹치지 않는" 두 부분 문제(왼쪽 절반과 오른쪽 절반은 서로 완전히 다른 데이터입니다)를 풀었기 때문에 O(n log n)에 그쳤지만, 피보나치는 나눈 두 부분 문제(`F(n-1)`과 `F(n-2)`)의 계산 과정이 서로 겹치기 때문에 이런 폭발이 일어납니다.

여기서 자연스러운 질문이 생깁니다. 같은 부분 문제를 반복해서 계산하고 있다면, **그 결과를 어딘가에 저장해두었다가 재사용하면 되지 않을까?** 이 아이디어가 바로 18장에서 다룰 **동적 프로그래밍(dynamic programming)**의 출발점입니다. 18장에서는 지금 만든 `Fibonacci` 함수를 거의 그대로 두되, 이미 계산한 결과를 저장하는 로직 하나만 추가해서 지수 시간을 선형 시간으로 끌어내리는 과정을 직접 확인합니다.

## 요약

- 재귀 함수는 **기저 조건**(더 이상 쪼개지 않고 즉시 답을 반환하는 조건)과 **재귀 단계**(문제를 더 작은 동일한 문제로 줄여 자기 자신을 호출하는 부분)로 이루어집니다. 기저 조건이 없거나 도달 불가능하면 무한 재귀에 빠집니다.
- 함수 호출은 실행 정보를 담은 스택 프레임을 **호출 스택**에 쌓는(push) 방식으로 관리되며, 함수가 반환되면 그 프레임이 제거(pop)됩니다. 재귀 호출은 이 호출 스택을 반복해서 사용하는 것이므로, 5장에서 다룬 스택 자료구조의 동작 원리와 본질적으로 같습니다.
- 재귀 깊이가 지나치게 깊어지면 호출 스택 공간이 소진되어 `StackOverflowException`이 발생할 수 있습니다.
- **분할 정복**은 문제를 (1) 더 작은 동일한 형태의 부분 문제로 나누고(분할), (2) 그 부분 문제를 재귀적으로 풀고(정복), (3) 부분 문제의 답을 합쳐 전체 답을 만드는(결합) 전략입니다. 15장에서 다룬 병합 정렬이 대표적인 예이며, 점화식 T(n) = 2T(n/2) + O(n)을 통해 O(n log n)이라는 결과를 얻을 수 있습니다.
- 분할 정복이 항상 효율적인 것은 아닙니다. 재귀 피보나치처럼 나누어진 부분 문제들이 서로 겹치는 경우, 같은 계산이 반복되어 시간 복잡도가 지수적으로(O(2ⁿ)) 폭발할 수 있습니다.
- 이 중복 계산 문제를 "이미 계산한 결과를 저장해서 재사용한다"는 아이디어로 해결하는 것이 18장의 주제인 동적 프로그래밍입니다.

## 연습문제

1. 배열의 모든 원소의 합을 구하는 재귀 함수 `SumRecursive(int[] array, int index)`를 작성해 보세요. 기저 조건과 재귀 단계를 명확히 구분해서 설계하세요.
2. `Factorial(5)`를 호출했을 때 호출 스택에 몇 개의 프레임이 동시에 쌓이는 최대 순간이 있는지 그려보고, 일반적으로 `Factorial(n)`의 최대 호출 스택 깊이가 얼마인지 답해 보세요.
3. 정수 배열에서 최댓값을 찾는 문제를 분할 정복으로 설계해 보세요. (힌트: 배열을 절반으로 나눠 각 절반의 최댓값을 구하고, 두 값 중 큰 쪽을 반환합니다.) 이 알고리즘의 점화식을 세우고 시간 복잡도를 구해 보세요.
4. `FibonacciCountingCalls(n)`의 호출 횟수를 n = 5, 10, 15, 20에 대해 실제로 실행해서 표로 정리해 보고, 호출 횟수가 대략 몇 배씩 증가하는지 관찰해 보세요.
5. 재귀로 작성된 `Factorial` 함수를 재귀 호출 없이 `while` 반복문만으로 다시 작성해 보고, 두 버전의 장단점(가독성, 스택 사용량, 성능)을 비교해 보세요.

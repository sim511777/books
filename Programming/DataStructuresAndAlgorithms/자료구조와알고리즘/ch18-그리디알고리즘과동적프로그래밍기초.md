17장에서는 재귀와 분할 정복을 다루면서, 재귀 피보나치가 겹치는 부분 문제를 매번 처음부터 다시 계산하느라 지수 시간이 걸린다는 문제를 확인했습니다. 이 장에서는 그 문제를 실제로 해결하는 **동적 프로그래밍(dynamic programming)**을 다룹니다. 다만 그 전에, 동적 프로그래밍과 자주 비교되는 또 다른 문제 해결 전략인 **그리디 알고리즘(greedy algorithm)**을 먼저 살펴봅니다. 두 전략 모두 "최적의 해를 찾는다"는 목표는 같지만, 접근 방식과 신뢰할 수 있는 상황이 서로 다릅니다. 이 책의 마지막 본문 장인 만큼, 지금까지 배운 자료구조와 알고리즘적 사고를 종합하는 자리이기도 합니다.

## 18.1 그리디 알고리즘: 당장 최선의 선택

**그리디 알고리즘**은 전체 문제를 한 번에 고민하는 대신, 각 단계마다 "지금 이 순간 가장 좋아 보이는 선택"을 하고 그 선택을 절대 번복하지 않는 전략입니다. 미래를 내다보지 않고 눈앞의 이득만 좇는다는 뜻에서 "탐욕적(greedy)"이라는 이름이 붙었습니다.

### 거스름돈 문제

그리디 알고리즘을 설명할 때 가장 자주 등장하는 예제는 거스름돈 문제입니다. 500원, 100원, 50원, 10원짜리 동전이 무한히 있다고 가정하고, 거스름돈 830원을 **최소 개수의 동전**으로 만들어야 한다고 합시다.

그리디 전략은 단순합니다. "매 순간 남은 금액을 넘지 않는 가장 큰 동전을 최대한 많이 사용한다."

```csharp
public static Dictionary<int, int> MakeChangeGreedy(int amount, int[] coinDenominations)
{
    // 큰 동전부터 시도하기 위해 내림차순으로 정렬
    var sortedCoins = coinDenominations.OrderByDescending(c => c).ToArray();
    var usedCoins = new Dictionary<int, int>();
    int remaining = amount;

    foreach (int coin in sortedCoins)
    {
        if (remaining <= 0)
            break;

        // 지금 볼 수 있는 동전 중 가장 큰 것을 최대한 많이 사용한다
        int count = remaining / coin;
        if (count > 0)
        {
            usedCoins[coin] = count;
            remaining -= coin * count;
        }
    }

    if (remaining != 0)
        throw new InvalidOperationException("주어진 동전으로는 정확히 거슬러줄 수 없습니다.");

    return usedCoins;
}
```

```csharp
int[] coins = { 500, 100, 50, 10 };
var result = MakeChangeGreedy(830, coins);

foreach (var (denomination, count) in result)
{
    Console.WriteLine($"{denomination}원 x {count}개");
}
// 500원 x 1개
// 100원 x 3개
// 10원 x 3개
// 총 7개 동전으로 830원 완성 — 이 동전 체계에서는 실제로 최소 개수
```

이 동전 체계(500, 100, 50, 10원)에서는 그리디 전략이 항상 최소 개수의 동전을 찾아줍니다. 각 단위가 그다음으로 작은 단위의 배수이거나, 그와 비슷하게 "큰 걸 먼저 쓰는 것이 절대 손해가 아닌" 구조를 갖고 있기 때문입니다.

### 그리디가 실패하는 경우

문제는 그리디 전략이 **모든 동전 체계에서 통하지는 않는다**는 것입니다. 동전 단위가 {1, 3, 4}이고 거스름돈이 6원이라고 해봅시다.

```csharp
int[] oddCoins = { 4, 3, 1 };
var result = MakeChangeGreedy(6, oddCoins);

foreach (var (denomination, count) in result)
{
    Console.WriteLine($"{denomination}원 x {count}개");
}
// 4원 x 1개
// 1원 x 2개
// 총 3개 동전 (4 + 1 + 1 = 6)
```

그리디 알고리즘은 가장 큰 동전인 4원을 먼저 최대한 사용해서 4 + 1 + 1 = 6원, 총 3개의 동전을 사용했습니다. 하지만 실제 최적해는 3원짜리 두 개, 즉 3 + 3 = 6원으로 **동전 2개**만 있으면 충분합니다. 그리디 알고리즘은 "지금 당장 4원을 쓰는 것이 유리해 보인다"는 근시안적 판단 때문에 진짜 최적해를 놓쳤습니다.

이 사례가 보여주는 교훈은 명확합니다. **그리디 알고리즘은 구현이 간단하고 빠르지만, 매 단계의 국소적(local) 최선 선택이 전역적(global) 최적해로 반드시 이어진다는 보장이 있는 문제에서만 사용해야 합니다.** 이런 보장이 있는 문제를 흔히 "탐욕적 선택 속성(greedy choice property)"을 만족한다고 표현합니다. 앞서 본 500/100/50/10원 체계는 이 속성을 만족하지만, {1, 3, 4} 체계는 만족하지 않습니다. 실무에서 그리디 알고리즘을 적용하기 전에는 "이 선택이 항상 안전한가?"를 증명하거나 최소한 반례가 없는지 충분히 검토해야 합니다. 만약 임의의 동전 체계에서도 항상 정확한 최적해를 보장하고 싶다면, 잠시 후 살펴볼 동적 프로그래밍으로 이 문제를 다시 풀어야 합니다.

## 18.2 동적 프로그래밍: 부분 문제를 저장해서 재사용하기

**동적 프로그래밍(dynamic programming, 줄여서 DP)**은 큰 문제를 부분 문제로 나눈다는 점에서 17장의 분할 정복과 비슷해 보이지만, 결정적인 차이가 하나 있습니다. **동적 프로그래밍은 부분 문제들이 서로 겹칠 때, 한 번 계산한 부분 문제의 결과를 저장해두었다가 다시 필요할 때 재사용합니다.** 이렇게 계산 결과를 저장해서 중복 계산을 없애는 기법을 **메모이제이션(memoization)**이라고 부릅니다.

동적 프로그래밍이 통하려면 문제가 다음 두 성질을 가져야 합니다.

1. **최적 부분 구조(optimal substructure)**: 문제의 최적해가 부분 문제의 최적해로부터 구성될 수 있어야 합니다.
2. **겹치는 부분 문제(overlapping subproblems)**: 재귀적으로 문제를 나눴을 때, 동일한 부분 문제가 여러 번 반복해서 등장해야 합니다. (반대로 부분 문제가 전혀 겹치지 않는다면 저장해둘 이유가 없으므로, 그런 경우는 그냥 분할 정복으로 충분합니다.)

## 18.3 피보나치 메모이제이션으로 개선하기

17.5절에서 확인했듯, 재귀 피보나치 `FibonacciCountingCalls`는 `F(2)`, `F(3)` 같은 값을 경로마다 매번 새로 계산하느라 호출 횟수가 O(2ⁿ)까지 폭증했습니다. 이 함수는 겹치는 부분 문제라는 조건을 정확히 만족하므로, 동적 프로그래밍으로 개선할 수 있는 완벽한 사례입니다.

핵심 아이디어는 간단합니다. `F(k)`를 한 번 계산했다면 그 값을 캐시(딕셔너리나 배열)에 저장해두고, 나중에 `F(k)`가 다시 필요해지면 재계산 대신 저장된 값을 즉시 꺼내 쓰는 것입니다. 이를 **하향식(top-down) 동적 프로그래밍**, 또는 "재귀 + 메모이제이션"이라고 부릅니다.

```csharp
public static class FibonacciMemo
{
    // 이미 계산한 F(n) 값을 저장해두는 캐시
    // 11장에서 다룬 해시 테이블 기반 딕셔너리를 그대로 활용한다
    private static readonly Dictionary<int, long> _cache = new();

    public static long Fibonacci(int n)
    {
        if (n < 0)
            throw new ArgumentOutOfRangeException(nameof(n));

        // 기저 조건은 재귀 버전과 동일하다
        if (n == 0 || n == 1)
            return n;

        // 이미 계산해둔 값이 있다면 즉시 반환 (재귀 호출 자체를 하지 않음)
        if (_cache.TryGetValue(n, out long cached))
            return cached;

        // 처음 계산하는 값이라면 재귀로 구하고, 반드시 캐시에 저장한다
        long result = Fibonacci(n - 1) + Fibonacci(n - 2);
        _cache[n] = result;
        return result;
    }
}
```

17장의 `FibonacciCountingCalls`와 코드 구조 자체는 거의 동일합니다. 달라진 부분은 딱 두 줄, "캐시에 값이 있으면 바로 반환한다"와 "계산한 값은 반드시 캐시에 저장한다"뿐입니다. 하지만 이 두 줄이 성능에 미치는 영향은 극적입니다. 호출 횟수를 다시 세어보면 차이가 분명하게 드러납니다.

```csharp
public static int CallCount = 0;
private static readonly Dictionary<int, long> _cache = new();

public static long FibonacciMemoCountingCalls(int n)
{
    CallCount++;

    if (n == 0 || n == 1)
        return n;

    if (_cache.TryGetValue(n, out long cached))
        return cached;

    long result = FibonacciMemoCountingCalls(n - 1) + FibonacciMemoCountingCalls(n - 2);
    _cache[n] = result;
    return result;
}
```

```csharp
CallCount = 0;
FibonacciMemoCountingCalls(30);
Console.WriteLine(CallCount); // 59 (메모이제이션 없이는 2,692,537번이었다)
```

`F(n)`은 0부터 n까지 각 값에 대해 **딱 한 번씩만** 실제로 계산되고, 두 번째부터는 캐시 조회 O(1)로 끝납니다(11장에서 다룬 해시 테이블 기반 딕셔너리 조회가 평균 O(1)이라는 점을 여기서 그대로 활용하고 있습니다). 그 결과 전체 시간 복잡도는 지수 시간 O(2ⁿ)에서 **선형 시간 O(n)**으로 떨어집니다. 대신 캐시를 유지하기 위한 공간이 O(n)만큼 추가로 필요합니다. 이것이 동적 프로그래밍의 전형적인 트레이드오프, 즉 **시간을 아끼기 위해 공간을 쓴다**는 원칙입니다.

### 상향식 접근: 반복문으로 재구성하기

같은 아이디어를 재귀 없이 반복문만으로 구현할 수도 있습니다. 작은 부분 문제(`F(0)`, `F(1)`)부터 시작해서 필요한 값을 순서대로 테이블에 채워나가는 방식이며, 이를 **상향식(bottom-up) 동적 프로그래밍**, 또는 **타뷸레이션(tabulation)**이라고 부릅니다.

```csharp
public static long FibonacciBottomUp(int n)
{
    if (n < 0)
        throw new ArgumentOutOfRangeException(nameof(n));

    if (n == 0 || n == 1)
        return n;

    // table[i]에는 F(i)의 값을 순서대로 채워 넣는다
    long[] table = new long[n + 1];
    table[0] = 0;
    table[1] = 1;

    for (int i = 2; i <= n; i++)
    {
        table[i] = table[i - 1] + table[i - 2]; // 이미 채워진 이전 값들을 재사용
    }

    return table[n];
}
```

이 버전은 재귀 호출이 전혀 없으므로 17.3절에서 걱정했던 호출 스택 문제로부터 자유롭습니다. 사실 바로 직전 두 값(`table[i-1]`, `table[i-2]`)만 있으면 그다음 값을 계산할 수 있으므로, 배열 전체를 유지할 필요 없이 변수 두 개만으로도 O(1) 공간에 O(n) 시간으로 풀 수 있습니다.

```csharp
public static long FibonacciConstantSpace(int n)
{
    if (n == 0 || n == 1)
        return n;

    long previous = 0, current = 1;
    for (int i = 2; i <= n; i++)
    {
        long next = previous + current;
        previous = current;
        current = next;
    }
    return current;
}
```

하향식(재귀 + 메모이제이션)과 상향식(반복문 + 테이블) 중 어느 쪽이 낫다는 정답은 없습니다. 하향식은 원래의 재귀적 문제 정의를 거의 그대로 유지하면서 필요한 부분 문제만 계산한다는 장점이 있고, 상향식은 재귀 호출 오버헤드와 스택 사용을 완전히 없앨 수 있다는 장점이 있습니다. 문제의 구조가 복잡할수록 하향식이 코드를 이해하기 쉬운 경우가 많고, 성능이 극도로 중요하거나 재귀 깊이가 우려되는 경우에는 상향식이 선호됩니다.

### 거스름돈 문제를 동적 프로그래밍으로 다시 풀기

18.1절에서 그리디 알고리즘이 {1, 3, 4} 동전 체계에서 실패했던 것을 기억해봅시다. 동적 프로그래밍은 어떤 동전 체계에서도 정확한 최적해를 보장합니다. 아이디어는 "금액 0원부터 목표 금액까지, 각 금액을 만드는 데 필요한 최소 동전 개수를 작은 금액부터 차례로 구해서 테이블에 저장한다"는 상향식 방식입니다.

```csharp
public static int MinCoinsDp(int amount, int[] coinDenominations)
{
    // minCoins[i] = i원을 만드는 데 필요한 최소 동전 개수
    int[] minCoins = new int[amount + 1];
    Array.Fill(minCoins, int.MaxValue - 1); // "아직 불가능"을 표현하는 큰 값
    minCoins[0] = 0; // 0원을 만드는 데는 동전이 0개 필요하다 (기저 조건)

    for (int target = 1; target <= amount; target++)
    {
        foreach (int coin in coinDenominations)
        {
            if (coin <= target)
            {
                // "target원 - coin원"을 이미 최소 개수로 만드는 방법을 알고 있으므로
                // 그 값에 동전 1개(coin)를 더 사용하는 경우를 고려한다
                minCoins[target] = Math.Min(minCoins[target], minCoins[target - coin] + 1);
            }
        }
    }

    return minCoins[amount] >= int.MaxValue - 1 ? -1 : minCoins[amount];
}
```

```csharp
int[] oddCoins = { 4, 3, 1 };
Console.WriteLine(MinCoinsDp(6, oddCoins)); // 2 (3 + 3) — 그리디는 3을 냈지만 DP는 정확히 2를 찾는다
```

`minCoins[target]`을 구하기 위해 `minCoins[target - coin]`이라는, 이미 계산해둔 더 작은 부분 문제의 답을 재사용하고 있다는 점에 주목해 주세요. 이것이 바로 최적 부분 구조입니다. 그리고 `minCoins[2]` 같은 값은 `minCoins[5]`를 구할 때도, `minCoins[6]`을 구할 때도 재사용될 수 있습니다. 이것이 겹치는 부분 문제입니다. 두 조건이 모두 성립하기 때문에 동적 프로그래밍이 이 문제에 정확히 들어맞고, 그리디와 달리 항상 옳은 답을 보장합니다.

## 18.4 동적 프로그래밍 vs 분할 정복: 부분 문제가 겹치는가

17장에서 분할 정복을, 이 장에서 동적 프로그래밍을 다뤘으니 이제 둘을 나란히 놓고 비교할 수 있습니다. 두 전략은 "문제를 부분 문제로 나누고 재귀적으로 해결한다"는 큰 틀에서는 동일합니다. 둘을 가르는 결정적인 기준은 단 하나, **나뉜 부분 문제들이 서로 겹치는가**입니다.

| 구분 | 분할 정복 | 동적 프로그래밍 |
|---|---|---|
| 부분 문제의 관계 | 서로 겹치지 않음 (독립적) | 서로 겹침 |
| 대표 예시 | 15장 병합 정렬 (왼쪽 절반과 오른쪽 절반은 완전히 다른 데이터) | 피보나치, 거스름돈 최소 개수 |
| 같은 부분 문제 재계산 | 애초에 발생하지 않음 | 저장해두지 않으면 반복 발생 |
| 결과 저장(메모이제이션) | 불필요 | 필수 |
| 전형적인 시간 복잡도 개선 | 이미 O(n log n) 등으로 효율적 | 지수 시간 → 다항 시간으로 개선 |

병합 정렬에서 왼쪽 절반을 정렬하는 과정과 오른쪽 절반을 정렬하는 과정은 서로 완전히 다른 데이터를 다루므로 결과를 캐싱해봐야 재사용할 일이 없습니다. 반면 피보나치에서 `F(n-1)`을 계산하는 과정과 `F(n-2)`를 계산하는 과정은 내부적으로 똑같은 `F(n-3)`, `F(n-4)`, ... 를 공유합니다. 이 공유되는 부분을 저장해서 재사용하느냐 마느냐가 지수 시간과 선형 시간의 차이를 만듭니다.

정리하면, 재귀적으로 문제를 나눴을 때 "이 부분 문제, 어디서 본 것 같은데?"라는 느낌이 든다면 동적 프로그래밍을 의심해봐야 하고, 나뉜 조각들이 매번 완전히 새로운 데이터라면 굳이 캐시를 쓸 필요 없이 순수한 분할 정복으로 충분합니다.

## 체크리스트

이 책 전체에서 배운 내용을 실전에 적용할 때 스스로 점검할 수 있는 체크리스트입니다.

- [ ] 문제를 더 작은 동일한 형태의 부분 문제로 나눌 수 있는가? (재귀적 정의가 가능한가)
- [ ] 재귀 함수를 설계했다면, 기저 조건이 명확하고 반드시 도달 가능한가?
- [ ] 재귀 깊이가 입력 크기에 비례해 커질 수 있는가? 그렇다면 `StackOverflowException` 위험을 검토했는가?
- [ ] 매 단계에서 "당장 최선"을 선택하는 그리디 전략을 고려하고 있다면, 그 선택이 전역 최적해로 항상 이어진다는 근거(혹은 반례가 없다는 확신)가 있는가?
- [ ] 그리디의 최적성이 의심된다면, {1, 3, 4} 동전 체계처럼 반례를 직접 만들어 검증해보았는가?

- [ ] 겹치는 부분 문제가 있다면, 결과를 캐시(딕셔너리 또는 배열)에 저장해 재사용하도록 메모이제이션을 적용했는가?
- [ ] 하향식(재귀+캐시)과 상향식(반복문+테이블) 중 문제 구조와 스택 안전성을 고려했을 때 어느 쪽이 더 적합한지 판단했는가?
- [ ] 시간을 절약하기 위해 추가로 사용하는 공간(캐시, 테이블)의 크기가 허용 가능한 수준인지 확인했는가?
- [ ] 지금 풀고 있는 문제와 유사한 구조가 이 책의 앞 장(정렬, 탐색, 그래프 등)에서 이미 다뤄지지 않았는지 되짚어보았는가?

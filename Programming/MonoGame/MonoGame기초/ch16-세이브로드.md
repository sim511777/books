# 16장. 세이브/로드

[◀ 이전: 15장. 파티클 시스템](ch15-파티클시스템.md) | [📖 목차](00-목차.md) | [다음: 17장. 크로스플랫폼 배포 ▶](ch17-크로스플랫폼배포.md)


아무리 재미있는 게임이라도 플레이할 때마다 처음부터 다시 시작해야 한다면 그 매력은 금세 반감될 것이다. 플레이어가 어디까지 진행했는지, 점수는 얼마였는지, 어떤 설정을 선택했는지를 기억해두었다가 다음에 게임을 실행했을 때 그대로 이어서 플레이할 수 있게 해주는 기능이 바로 세이브(save)와 로드(load)다. 이번 장에서는 게임의 진행 상태를 어떤 형태로 표현할지 정하는 것부터 시작해, .NET 표준 라이브러리에 포함된 `System.Text.Json`으로 이를 파일에 저장하고 다시 불러오는 방법, 그리고 저장 파일이 없거나 손상되었을 때 게임이 안전하게 동작하도록 만드는 방어적 코드 패턴까지 차례로 살펴본다.

## 저장할 데이터를 클래스로 구조화하기

세이브/로드 기능을 만들 때 가장 먼저 해야 할 일은 "무엇을 저장할 것인가"를 명확히 정하는 것이다. 무작정 게임 안의 모든 객체를 통째로 저장하려 하기보다는, 플레이어의 진행 상황을 나타내는 데 꼭 필요한 값들만 골라 하나의 단순한 클래스로 정리하는 것이 좋다.

```csharp
public class SaveData
{
    public int Score;
    public int Level;
    public string PlayerName = string.Empty;
    public float PlayTimeSeconds;
}
```

`SaveData`는 특별한 로직 없이 데이터만 담고 있는 순수한 데이터 컨테이너다. 이런 클래스를 흔히 DTO(Data Transfer Object) 또는 POCO(Plain Old CLR Object)라고 부른다. 게임 안에서 실제로 점수를 계산하거나 레벨을 관리하는 로직은 `ScoreManager`나 `GameState` 같은 다른 클래스가 담당하고, 저장이 필요한 순간에만 그 값들을 `SaveData` 인스턴스로 옮겨 담아 파일에 기록하는 식으로 역할을 나누는 것이 좋은 설계다. 14장에서 다룬 게임 상태 관리와 연결해서 생각해보면, 플레이 화면(`PlayScreen`)이 가지고 있는 점수와 레벨 값을 세이브 시점에 `SaveData` 객체로 변환하고, 로드 시점에는 반대로 `SaveData`에서 읽어온 값을 플레이 화면의 상태로 되돌려 놓는 흐름이 된다.

이렇게 저장용 클래스를 별도로 두면 몇 가지 이점이 있다. 첫째, 저장 파일의 형식이 게임 내부의 클래스 구조 변화에 덜 민감해진다. 둘째, 어떤 정보가 "저장되는 정보"인지 한눈에 파악할 수 있어 나중에 세이브 파일 포맷을 다룰 때 코드를 읽기 쉬워진다. 셋째, 뒤에서 다룰 JSON 직렬화 대상이 명확해져서 예상치 못한 필드가 저장 파일에 섞여 들어가는 것을 막을 수 있다.

## System.Text.Json으로 직렬화하고 파일에 저장하기

.NET에는 객체를 JSON 문자열로 변환(직렬화)하거나 JSON 문자열을 다시 객체로 되돌리는(역직렬화) 기능을 제공하는 `System.Text.Json` 네임스페이스가 표준으로 포함되어 있다. 별도의 NuGet 패키지를 추가로 설치할 필요 없이 바로 사용할 수 있다는 점이 큰 장점이다.

```csharp
using System.IO;
using System.Text.Json;

public static class SaveManager
{
    private const string SaveFileName = "savedata.json";

    public static void Save(SaveData data)
    {
        var options = new JsonSerializerOptions { WriteIndented = true };
        string json = JsonSerializer.Serialize(data, options);

        File.WriteAllText(SaveFileName, json);
    }
}
```

`JsonSerializer.Serialize(data, options)`는 `SaveData` 객체의 공개 필드와 속성을 읽어 JSON 형식의 문자열로 변환해준다. `JsonSerializerOptions`의 `WriteIndented`를 `true`로 설정하면 사람이 눈으로 읽기 좋게 줄바꿈과 들여쓰기가 적용된 JSON이 만들어진다. 예를 들어 `Score`가 1200, `Level`이 3인 `SaveData`를 직렬화하면 다음과 비슷한 문자열이 만들어진다.

```json
{
  "Score": 1200,
  "Level": 3,
  "PlayerName": "Player1",
  "PlayTimeSeconds": 542.3
}
```

이렇게 만들어진 문자열은 `System.IO.File.WriteAllText(경로, 내용)`으로 손쉽게 파일에 기록할 수 있다. `File.WriteAllText`는 지정한 경로에 파일이 없으면 새로 만들고, 이미 있으면 기존 내용을 덮어쓴다. 텍스트 인코딩이나 파일 스트림을 직접 다룰 필요 없이 문자열 하나만 넘겨주면 되므로, 세이브 기능처럼 파일 하나에 데이터를 통째로 기록하는 상황에 잘 맞는다.

## 파일에서 읽어와 역직렬화하기

저장한 데이터를 다시 불러오는 과정은 저장의 정반대 순서를 밟는다. `File.ReadAllText`로 파일의 전체 내용을 문자열로 읽어온 뒤, `JsonSerializer.Deserialize<T>`로 그 문자열을 다시 객체로 변환하면 된다.

```csharp
using System.IO;
using System.Text.Json;

public static class SaveManager
{
    private const string SaveFileName = "savedata.json";

    public static void Save(SaveData data)
    {
        var options = new JsonSerializerOptions { WriteIndented = true };
        string json = JsonSerializer.Serialize(data, options);
        File.WriteAllText(SaveFileName, json);
    }

    public static SaveData Load()
    {
        string json = File.ReadAllText(SaveFileName);
        SaveData data = JsonSerializer.Deserialize<SaveData>(json);
        return data;
    }
}
```

`JsonSerializer.Deserialize<SaveData>(json)`는 JSON 문자열의 각 키(`Score`, `Level`, `PlayerName`, `PlayTimeSeconds`)를 `SaveData` 클래스의 같은 이름의 필드와 매칭해 값을 채워 넣은 새 인스턴스를 만들어 돌려준다. 직렬화와 역직렬화 모두 리플렉션을 통해 필드 이름을 기준으로 자동으로 매칭이 이루어지기 때문에, 개발자가 JSON 파싱 코드를 한 줄도 직접 작성하지 않아도 된다는 점이 `System.Text.Json`을 사용하는 가장 큰 이유다.

게임 코드에서는 보통 다음과 같은 형태로 이 두 메서드를 사용하게 된다.

```csharp
// 저장할 때
var data = new SaveData
{
    Score = currentScore,
    Level = currentLevel,
    PlayerName = playerName,
    PlayTimeSeconds = totalPlayTime
};
SaveManager.Save(data);

// 불러올 때
SaveData loaded = SaveManager.Load();
currentScore = loaded.Score;
currentLevel = loaded.Level;
```

## 저장 파일은 어디에 두어야 할까

앞의 예제에서는 `SaveFileName`으로 `"savedata.json"`이라는 상대 경로를 그대로 사용했다. 이렇게 하면 파일이 게임 실행 파일이 위치한 작업 디렉터리에 저장되는데, 개발 중에 테스트하기에는 간편하지만 실제 배포 환경에서는 문제가 될 수 있다. Windows에서 `Program Files` 아래에 설치된 프로그램은 일반 사용자 권한으로 그 폴더에 파일을 쓸 수 없는 경우가 많고, macOS나 Linux에서도 애플리케이션 번들이나 시스템 디렉터리에 임의로 파일을 쓰는 것은 권장되지 않는다.

이런 이유로 대부분의 게임은 운영체제가 애플리케이션 데이터를 저장하라고 마련해준 사용자별 폴더에 세이브 파일을 둔다. .NET에서는 `Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData)`를 호출하면 현재 사용자의 애플리케이션 데이터 폴더 경로를 얻을 수 있다. 이 값과 게임 고유의 폴더 이름을 조합해 저장 경로를 구성하는 식이다.

```csharp
string appDataPath = Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData);
string saveFolder = Path.Combine(appDataPath, "MyMonoGameGame");
Directory.CreateDirectory(saveFolder);
string saveFilePath = Path.Combine(saveFolder, SaveFileName);
```

`Environment.SpecialFolder.ApplicationData`가 실제로 가리키는 경로는 플랫폼마다 다르다. Windows에서는 흔히 `C:\Users\사용자이름\AppData\Roaming` 아래, macOS나 Linux에서는 .NET이 이를 홈 디렉터리 하위의 애플리케이션 설정 폴더로 매핑해준다. 중요한 것은 개발자가 이 경로를 플랫폼별로 직접 분기해서 작성할 필요가 없다는 점이다. `Environment.GetFolderPath`가 현재 실행 중인 운영체제에 맞는 경로를 알아서 돌려주기 때문에, 같은 코드를 그대로 두어도 Windows/macOS/Linux 어디서 실행되든 각 플랫폼의 관례에 맞는 위치에 저장 파일이 만들어진다. `Directory.CreateDirectory`는 폴더가 이미 존재하면 아무 일도 하지 않고, 없으면 새로 만들어주므로 최초 실행 시 폴더가 없어 저장에 실패하는 상황도 함께 방지할 수 있다. 이 주제, 즉 플랫폼마다 달라지는 파일 시스템 규칙과 배포 시 고려해야 할 사항들은 17장 크로스플랫폼 배포에서 좀 더 자세히 다룬다.

## 저장 파일이 없거나 손상되었을 때 안전하게 대응하기

게임을 처음 실행하는 사용자에게는 애초에 저장 파일이 존재하지 않는다. 또한 파일이 저장되는 도중 프로그램이 강제 종료되거나, 사용자가 파일을 실수로 편집하는 등의 이유로 저장 파일의 내용이 유효한 JSON이 아니게 될 수도 있다. 이런 상황에서 `File.ReadAllText`나 `JsonSerializer.Deserialize`를 그대로 호출하면 각각 `FileNotFoundException`이나 `JsonException` 같은 예외가 발생하며 프로그램이 그대로 죽어버릴 수 있다. 세이브/로드 기능은 반드시 이런 예외 상황을 예상하고 방어적으로 작성해야 한다.

```csharp
using System;
using System.IO;
using System.Text.Json;

public static class SaveManager
{
    private const string SaveFileName = "savedata.json";

    public static SaveData Load()
    {
        try
        {
            string json = File.ReadAllText(SaveFileName);
            SaveData data = JsonSerializer.Deserialize<SaveData>(json);

            // 파일 내용이 "null"처럼 유효하지만 의미 없는 JSON이었을 경우도 대비한다.
            return data ?? CreateDefaultSaveData();
        }
        catch (FileNotFoundException)
        {
            // 저장 파일이 아직 없는, 최초 실행과 같은 정상적인 상황이다.
            return CreateDefaultSaveData();
        }
        catch (JsonException)
        {
            // 저장 파일이 손상되어 JSON으로 해석할 수 없는 경우다.
            Console.WriteLine("저장 파일이 손상되어 기본값으로 시작합니다.");
            return CreateDefaultSaveData();
        }
    }

    private static SaveData CreateDefaultSaveData()
    {
        return new SaveData
        {
            Score = 0,
            Level = 1,
            PlayerName = "Player",
            PlayTimeSeconds = 0f
        };
    }
}
```

이 패턴의 핵심은 두 가지다. 첫째, 예외가 발생할 수 있는 지점(파일 읽기, JSON 파싱)을 `try` 블록으로 감싸 프로그램이 그 자리에서 멈추지 않도록 한다. 둘째, 각 예외 상황에 대해 게임이 계속 진행될 수 있는 안전한 기본값(`CreateDefaultSaveData`)을 준비해둔다. `FileNotFoundException`은 사실 오류라기보다는 "이 사용자는 아직 저장한 적이 없다"는 지극히 정상적인 상황을 나타내므로, 별도의 로그 없이 조용히 기본값으로 넘어가도 무방하다. 반면 `JsonException`은 저장 파일이 실제로 손상되었다는 신호이므로, 개발 중이라면 콘솔에 메시지를 남기거나 나중에는 손상된 파일을 백업해두는 등 조금 더 신경 쓴 처리를 고려해볼 수 있다.

`catch (Exception)`처럼 모든 예외를 뭉뚱그려 잡기보다 이렇게 예상되는 예외 타입을 구체적으로 나눠 잡는 것이 좋다. 그래야 정말 예상하지 못한 다른 버그(예를 들어 `SaveManager` 코드 자체의 논리적 실수)까지 조용히 숨겨버리는 일을 방지할 수 있다. 저장(`Save`) 쪽에도 비슷한 방어 코드를 적용할 수 있는데, 예를 들어 디스크 용량 부족이나 접근 권한 문제로 `IOException`이 발생할 수 있는 상황이라면 저장 실패를 사용자에게 알리고 다음 자동 저장 시점에 다시 시도하도록 처리하는 것이 안전하다.

```csharp
public static bool TrySave(SaveData data)
{
    try
    {
        var options = new JsonSerializerOptions { WriteIndented = true };
        string json = JsonSerializer.Serialize(data, options);
        File.WriteAllText(SaveFileName, json);
        return true;
    }
    catch (IOException ex)
    {
        Console.WriteLine($"저장에 실패했습니다: {ex.Message}");
        return false;
    }
}
```

이렇게 `bool`을 반환해 성공 여부를 호출한 쪽에 알려주면, 14장에서 다룬 화면 전환 로직과 결합해 "저장에 실패했습니다" 같은 안내 메시지를 잠깐 화면에 띄워주는 식으로 사용자 경험을 개선할 수도 있다.

## 요약

- 게임의 진행 상태는 `class SaveData { public int Score; public int Level; ... }`처럼 저장에 필요한 값만 담은 단순한 클래스로 구조화해서 관리한다.
- `System.Text.Json`의 `JsonSerializer.Serialize`로 객체를 JSON 문자열로 변환하고 `System.IO.File.WriteAllText`로 파일에 기록하며, 반대로 `File.ReadAllText`와 `JsonSerializer.Deserialize<T>`로 파일을 다시 객체로 불러올 수 있다.
- 저장 파일은 실행 파일 옆이 아니라 `Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData)`처럼 운영체제가 제공하는 사용자별 데이터 폴더에 두는 것이 바람직하며, 이 주제는 17장 크로스플랫폼 배포에서 더 자세히 다룬다.
- 저장 파일이 없는 경우(`FileNotFoundException`)나 손상된 경우(`JsonException`)를 각각 `try`/`catch`로 구분해 처리하고, 두 경우 모두 게임이 멈추지 않도록 안전한 기본값을 반환하는 방어적 코드를 갖춰야 한다.

## 연습문제

1. `SaveData` 클래스를 게임 안의 실제 상태를 다루는 클래스(예: `GameState`)와 분리해서 설계하는 이유는 무엇인지 설명해보자.
2. `JsonSerializerOptions`의 `WriteIndented`를 `true`로 설정했을 때와 `false`(기본값)로 두었을 때 생성되는 JSON 문자열이 어떻게 다른지 실제로 두 가지 옵션으로 직렬화해보고 비교해보자.
3. 저장 파일 경로를 실행 파일 위치의 상대 경로 대신 `Environment.SpecialFolder.ApplicationData` 기반 경로로 바꾸는 코드를 직접 작성해보고, 그 경로가 실제로 어디를 가리키는지 `Console.WriteLine`으로 출력해서 확인해보자.
4. `SaveManager.Load()`에서 `catch (JsonException)` 블록을 아예 빼버리면 어떤 상황에서 게임이 예상치 못하게 종료될 수 있는지 시나리오를 만들어 설명해보자.
5. `SaveData`에 새로운 필드(예: `public List<string> UnlockedAchievements`)를 추가했다고 가정해보자. 예전 버전의 세이브 파일(새 필드가 없는 JSON)을 새 버전의 `SaveData`로 역직렬화하면 어떤 값이 채워지는지 직접 실험해보고, 이런 저장 파일 형식의 변화에 안전하게 대응하려면 어떤 점을 신경 써야 할지 생각해보자.

# 17장. 크로스플랫폼 배포

[◀ 이전: 16장. 세이브/로드](ch16-세이브로드.md) | [📖 목차](00-목차.md) | [다음: 18장. 실전 프로젝트: 미니 게임 만들기 ▶](ch18-실전프로젝트미니게임만들기.md)


1장에서 MonoGame을 소개하며 "하나의 코드베이스로 여러 플랫폼을 겨냥할 수 있다"는 특징을 강조했고, 2장에서는 `dotnet new list`로 확인해보면 `mgdesktopgl`, `mgandroid`, `mgios` 같은 여러 템플릿이 설치되어 있다는 것도 살펴봤습니다. 지금까지는 그중 `mgdesktopgl` 템플릿으로 만든 프로젝트를 `dotnet run`으로 실행하며 개발 컴퓨터에서만 게임을 구동해왔습니다. 이번 장에서는 한 걸음 더 나아가, 완성된 게임을 실제로 다른 사람의 컴퓨터에서도 실행할 수 있는 형태로 만드는 방법을 다룹니다.

데스크톱 배포는 이 책의 실습 환경만으로도 끝까지 따라 할 수 있으므로 자세히 다루고, Android/iOS 같은 모바일 배포는 별도의 SDK와 서명 절차가 필요한 훨씬 복잡한 과정이므로 이 책에서는 "이런 것이 존재하고, 대략 이런 흐름으로 진행된다"는 개념 수준까지만 소개합니다. 실제 스토어 출시까지 진행하고 싶다면 MonoGame 공식 문서와 각 플랫폼의 공식 가이드를 참고해야 합니다.

## 17.1 dotnet publish와 dotnet run의 차이

지금까지 사용해온 `dotnet run`은 프로젝트를 빌드한 뒤 곧바로 실행까지 이어서 해주는, 개발 중 빠른 확인을 위한 명령입니다. 반면 `dotnet publish`는 "다른 컴퓨터에 배포할 산출물"을 만들어내는 명령입니다. 두 명령은 목적이 다르므로 결과물도 다릅니다. `dotnet run`은 임시로 빌드된 결과를 즉시 실행하고 끝내는 데 초점이 맞춰져 있지만, `dotnet publish`는 실행에 필요한 모든 파일을 하나의 폴더(또는 하나의 실행 파일)로 정리해서 내보내는 데 초점이 맞춰져 있습니다.

```bash
dotnet publish -c Release -r win-x64 --self-contained true
```

이 명령을 프로젝트 폴더(`.csproj` 파일이 있는 위치)에서 실행하면, `bin/Release/<대상 프레임워크>/win-x64/publish` 폴더 아래에 배포용 파일들이 만들어집니다. `-c Release`는 최적화가 적용된 릴리스 구성으로 빌드하라는 뜻으로, 실제 배포 시에는 디버그 구성이 아니라 반드시 릴리스 구성을 사용해야 합니다.

## 17.2 런타임 식별자(RID)로 대상 플랫폼 지정하기

`-r`(또는 `--runtime`) 옵션에 넘기는 값을 **런타임 식별자(Runtime Identifier, RID)**라고 부릅니다. RID는 "어떤 운영체제, 어떤 CPU 아키텍처를 대상으로 빌드할 것인가"를 지정합니다. MonoGame의 `mgdesktopgl` 프로젝트가 주로 사용하는 RID는 다음과 같습니다.

| RID | 대상 플랫폼 |
|---|---|
| `win-x64` | 64비트 Windows |
| `linux-x64` | 64비트 Linux |
| `osx-x64` | Intel 기반 macOS |
| `osx-arm64` | Apple Silicon(M1/M2/M3 등) 기반 macOS |

```bash
# Windows용 산출물 만들기
dotnet publish -c Release -r win-x64 --self-contained true

# Linux용 산출물 만들기
dotnet publish -c Release -r linux-x64 --self-contained true

# macOS(Apple Silicon)용 산출물 만들기
dotnet publish -c Release -r osx-arm64 --self-contained true
```

RID만 바꾸면 같은 소스 코드에서 서로 다른 플랫폼용 산출물을 각각 만들어낼 수 있다는 점이 핵심입니다. 다만 크로스 컴파일(예: Windows 컴퓨터에서 `linux-x64`나 `osx-arm64`용 산출물을 만드는 것) 자체는 문제없이 동작하지만, 실제로 그 산출물이 의도대로 실행되는지는 결국 해당 운영체제(또는 가상 머신, CI 환경)에서 직접 확인해야 합니다. `mgdesktopgl`이 OpenGL 기반이라 소스 코드 수준에서는 플랫폼 차이가 거의 없더라도, 배포 전 실기기 테스트를 생략해서는 안 됩니다.

## 17.3 self-contained 배포로 자기 완결형 실행 파일 만들기

`dotnet publish`로 배포할 때 가장 중요한 선택 중 하나는 ".NET 런타임을 산출물 안에 포함시킬 것인가"입니다.

**framework-dependent 배포**는 실행 대상 컴퓨터에 호환되는 .NET 런타임이 이미 설치되어 있다고 가정하는 방식입니다.

```bash
dotnet publish -c Release -r win-x64 --self-contained false
```

산출물의 용량이 작다는 장점이 있지만, 사용자 컴퓨터에 맞는 .NET 런타임이 없으면 게임이 아예 실행되지 않습니다. 게임을 처음 접하는 일반 사용자에게 ".NET 런타임을 먼저 설치하세요"라고 요구하는 것은 배포 경험을 크게 해칩니다.

**self-contained 배포**는 게임 코드뿐 아니라 실행에 필요한 .NET 런타임 전체를 산출물에 포함시킵니다.

```bash
dotnet publish -c Release -r win-x64 --self-contained true
```

이렇게 만든 산출물은 대상 컴퓨터에 .NET이 설치되어 있는지와 무관하게 그대로 실행할 수 있는, 말 그대로 자기 완결형(self-contained) 배포본이 됩니다. 대신 .NET 런타임 자체가 포함되므로 산출물 용량은 눈에 띄게 커집니다. 일반 사용자에게 배포하는 게임이라면 대부분 self-contained 배포를 선택하는 것이 안전합니다.

| 구분 | framework-dependent | self-contained |
|---|---|---|
| .NET 런타임 포함 여부 | 미포함 | 포함 |
| 산출물 용량 | 작음 | 큼 |
| 실행 대상 컴퓨터 요구사항 | 호환 런타임 사전 설치 필요 | 없음(그대로 실행 가능) |
| 적합한 상황 | 개발자 간 공유, 사내 배포 | 일반 사용자 대상 게임 배포 |

### 단일 실행 파일로 묶기

self-contained 배포는 기본적으로 실행 파일 하나와 함께 여러 개의 DLL, 설정 파일을 같은 폴더에 만들어냅니다. 배포를 더 단순하게 만들고 싶다면 `PublishSingleFile` 옵션으로 이 파일들을 하나의 실행 파일로 묶을 수 있습니다.

```bash
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
```

이렇게 하면 사용자에게 실행 파일 하나(와 콘텐츠 폴더)만 전달하면 되므로 배포 경험이 한결 단순해집니다. 다만 단일 파일 안에는 여전히 실행 시 압축이 해제되는 임시 파일이 생기는 경우가 있으므로, 최초 실행 속도나 바이러스 백신 소프트웨어의 오탐 여부 등은 실제 배포 전에 한 번쯤 확인해보는 것이 좋습니다.

### DesktopGL의 네이티브 종속성

`mgdesktopgl` 템플릿이 참조하는 `MonoGame.Framework.DesktopGL` 패키지는 내부적으로 SDL2(창 생성과 입력 처리)와 OpenAL(오디오 재생) 같은 네이티브 라이브러리에 의존합니다. `dotnet publish`에 RID를 지정하면 이런 네이티브 라이브러리 중 해당 플랫폼에 맞는 버전(Windows라면 `SDL2.dll`, `soft_oal.dll` 같은 파일들)이 자동으로 산출물 폴더에 포함됩니다. 개발자가 이 파일들을 직접 챙길 필요는 없지만, 배포 폴더를 살펴보면 게임 실행 파일 옆에 이런 네이티브 라이브러리 파일들이 함께 놓여 있는 것을 확인할 수 있습니다. 이 파일들은 게임이 정상적으로 동작하는 데 반드시 필요하므로, 배포 시 임의로 삭제하거나 실행 파일만 따로 떼어 옮기면 안 됩니다.

## 17.4 콘텐츠 파이프라인 산출물이 함께 배포되는지 확인하기

4장에서 다룬 콘텐츠 파이프라인을 떠올려봅시다. `Content/Content.mgcb`에 등록해둔 텍스처, 폰트, 사운드 같은 원본 에셋은 빌드 시점에 MGCB가 `.xnb` 형식으로 변환해 `bin/<구성>/<대상 프레임워크>/Content` 폴더 아래에 만들어 둡니다. 게임 코드에서 `Content.Load<Texture2D>("player")`처럼 이름만으로 에셋을 불러올 수 있는 것도, 바로 이 `.xnb` 파일들이 실행 파일과 함께 배포되어 있기 때문입니다.

`dotnet publish`를 실행하면 이 `Content` 폴더도 자동으로 publish 결과물 폴더에 함께 복사됩니다. 프로젝트 파일(`.csproj`)에 등록된 `MonoGameContentReference` 항목이 빌드 과정에서 콘텐츠 빌드를 트리거하고, 그 결과물이 일반적인 콘텐츠 파일처럼 취급되어 게시 시에도 함께 옮겨지는 구조입니다. 배포 후 산출물 폴더는 대략 다음과 같은 모습이 됩니다.

```
publish/
├── MyGame.exe
├── MyGame.dll
├── SDL2.dll
├── soft_oal.dll
├── Content/
│   ├── player.xnb
│   ├── jump.xnb
│   └── GameFont.xnb
└── (기타 런타임 관련 파일들)
```

여기서 눈여겨볼 부분은 `Content` 폴더가 실행 파일과 같은 위치에 놓여 있어야 한다는 점입니다. `Game1`의 생성자에서 설정하는 `Content.RootDirectory = "Content";`(2장 참고)는 실행 파일 기준 상대 경로로 이 폴더를 찾기 때문에, 만약 배포 스크립트나 수동 복사 과정에서 `Content` 폴더를 빠뜨리거나 다른 위치로 옮기면 게임을 처음 실행하는 순간 `Content.Load<T>()`가 파일을 찾지 못해 예외를 던지게 됩니다.

따라서 배포 전에는 반드시 `dotnet publish`가 만들어낸 폴더를 통째로 다른 위치(가능하면 프로젝트 소스 코드가 전혀 없는 깨끗한 폴더나 다른 컴퓨터)로 복사한 뒤, 그 상태 그대로 실행해보는 검증 과정을 거치는 것이 좋습니다. 개발 중인 폴더에서는 정상 동작하다가도, 정작 배포용으로 파일을 옮기는 과정에서 `Content` 폴더가 누락되는 실수는 실무에서 의외로 자주 발생합니다.

## 17.5 모바일 배포: Android와 iOS는 존재만 소개합니다

2장에서 확인했듯, MonoGame 템플릿 목록에는 `mgandroid`와 `mgios`도 포함되어 있습니다.

```bash
dotnet new mgandroid -o MyGame.Android
dotnet new mgios -o MyGame.iOS
```

이 템플릿들은 지금까지 배운 `Game`, `SpriteBatch`, 콘텐츠 파이프라인 같은 핵심 개념을 그대로 재사용할 수 있게 해줍니다. 즉 `Game1.cs` 안에 들어가는 게임 로직 자체는 데스크톱용 프로젝트와 크게 다르지 않습니다. 하지만 이 프로젝트를 실제로 빌드하고 스토어에 출시하기까지의 과정은 데스크톱 배포보다 훨씬 복잡하며, 각 플랫폼 고유의 도구와 절차를 필요로 합니다.

**Android 배포**는 대략 다음과 같은 준비물을 필요로 합니다.

- .NET의 Android 워크로드(`dotnet workload install android`)와 Android SDK/NDK 설치
- 앱 서명에 사용할 키스토어(keystore) 파일 생성 및 관리
- Google Play Console 계정 등록과 APK 또는 AAB(Android App Bundle) 형식의 산출물 업로드, 스토어 등록 정보 작성

**iOS 배포**는 다음과 같은 준비물을 필요로 합니다.

- macOS 컴퓨터와 Xcode 설치(iOS 빌드는 원칙적으로 macOS에서만 가능합니다)
- 유료 Apple Developer Program 등록
- 서명 인증서와 프로비저닝 프로파일(provisioning profile) 발급 및 관리
- App Store Connect를 통한 빌드 업로드와 심사 제출

이런 절차는 SDK 설치부터 인증서 발급, 스토어 심사까지 이 책 한 장으로 다루기에는 지나치게 방대하고, MonoGame 고유의 내용이라기보다는 각 플랫폼(Google, Apple)의 개발자 프로그램 정책에 더 가깝습니다. 그래서 이 책에서는 "MonoGame으로 모바일 게임도 만들 수 있고, 그 진입점이 `mgandroid`/`mgios` 템플릿"이라는 사실만 소개하고, 상세한 서명·배포 절차는 다루지 않습니다. 실제로 모바일 출시를 준비하게 된다면 MonoGame 공식 문서의 플랫폼별 배포 가이드를 함께 참고하시기 바랍니다.

콘솔 플랫폼(Xbox, PlayStation, Nintendo Switch) 배포는 이보다 한 단계 더 나아가, 별도의 콘솔 제조사 개발자 프로그램 가입과 전용 SDK 라이선스가 필요합니다. 1장에서 이미 언급했듯 이 책의 범위를 완전히 벗어나므로, 이런 경로가 존재한다는 정도만 기억해두면 충분합니다.

## 17.6 배포 전 체크리스트

데스크톱용 self-contained 배포본을 만들었다면, 실제로 배포하기 전에 다음 사항들을 한 번씩 점검해보는 것을 권합니다.

- **깨끗한 환경에서 실행해보기**: 개발용 컴퓨터가 아닌 다른 컴퓨터(또는 가상 머신)에 publish 폴더를 통째로 복사해 실행되는지 확인합니다. 개발 컴퓨터에는 이미 .NET SDK와 각종 런타임이 설치되어 있어서, 실제로는 누락된 파일이 있어도 문제없이 실행되는 것처럼 착각하기 쉽습니다.
- **콘텐츠 폴더 확인**: publish 폴더 안에 `Content` 폴더와 그 안의 `.xnb` 파일들이 실제로 존재하는지 확인합니다.
- **실행 파일 이름과 아이콘**: 2장에서 살펴본 `Icon.ico`(Windows)가 실행 파일에 잘 반영되었는지, 창 제목(`Window.Title`)이 게임에 맞게 설정되어 있는지 확인합니다.
- **대상 플랫폼별 실행 테스트**: 크로스 컴파일로 만든 산출물이라면, 가능한 한 실제 대상 운영체제(또는 CI 환경)에서 한 번은 직접 실행해봅니다.

이 정도의 점검만으로도 "내 컴퓨터에서는 되는데 다른 컴퓨터에서는 안 된다"는 흔한 배포 사고를 상당 부분 예방할 수 있습니다.

## 요약

- `dotnet publish`는 배포용 산출물을 만드는 명령으로, `dotnet run`과 달리 실행이 아니라 배포 파일 생성이 목적이다.
- `-r` 옵션에 런타임 식별자(RID, 예: `win-x64`, `linux-x64`, `osx-x64`, `osx-arm64`)를 지정하면 같은 코드베이스에서 여러 데스크톱 플랫폼용 산출물을 각각 만들 수 있다.
- `--self-contained true`로 배포하면 .NET 런타임 전체가 포함되어 사용자가 별도 설치 없이 실행할 수 있는 자기 완결형 실행 파일이 되며, `-p:PublishSingleFile=true`를 함께 지정하면 이를 하나의 실행 파일로 묶을 수 있다.
- 콘텐츠 파이프라인(4장)으로 빌드된 `.xnb` 에셋은 `dotnet publish` 시 `Content` 폴더와 함께 자동으로 산출물에 포함되며, 배포 시 이 폴더가 실행 파일과 같은 위치에 있어야 한다.
- Android(`mgandroid`)와 iOS(`mgios`) 배포는 각각 별도의 SDK, 워크로드, 서명 인증서, 스토어 심사 절차가 필요한 훨씬 복잡한 과정이며, 이 책에서는 그 존재와 개략적인 흐름만 소개한다.
- 배포 전에는 개발 컴퓨터가 아닌 깨끗한 환경에서 publish 산출물이 실제로 정상 동작하는지 반드시 확인해야 한다.

## 연습문제

1. `dotnet run`과 `dotnet publish`의 목적 차이를 설명하고, 각각 어떤 상황에 사용하는 것이 적절한지 서술해보세요.
2. framework-dependent 배포와 self-contained 배포의 차이를 산출물 용량과 사용자 환경 요구사항 관점에서 비교하고, 일반 사용자에게 배포할 게임이라면 어느 쪽이 더 적합한지 설명해보세요.
3. `dotnet publish -c Release -r linux-x64 --self-contained true -p:PublishSingleFile=true` 명령이 수행하는 작업을 단계별로 설명해보세요.
4. 4장에서 배운 콘텐츠 파이프라인과 연결지어, 배포된 게임이 실행되자마자 텍스처를 불러오지 못해 예외가 발생했다면 어떤 부분을 먼저 점검해봐야 할지 설명해보세요.
5. Android나 iOS로 게임을 배포하려면 데스크톱 배포에는 없는 어떤 추가 준비물이 필요한지 각각 두 가지 이상 나열해보세요.

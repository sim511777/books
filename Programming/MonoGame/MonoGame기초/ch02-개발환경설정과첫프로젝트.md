# 2장. 개발 환경 설정과 첫 프로젝트

[◀ 이전: 1장. MonoGame이란 무엇인가](ch01-MonoGame이란무엇인가.md) | [📖 목차](00-목차.md) | [다음: 3장. 게임 루프와 Game 클래스 수명주기 ▶](ch03-게임루프와Game클래스수명주기.md)


1장에서 MonoGame이 어떤 프레임워크인지 큰 그림을 그려보았다면, 이번 장에서는 실제로 여러분의 컴퓨터에 MonoGame 개발 환경을 갖추고, 첫 번째 프로젝트를 만들어 화면에 창을 띄워본다. MonoGame은 .NET SDK와 `dotnet` CLI를 기반으로 프로젝트를 생성하기 때문에, 별도의 무거운 설치 프로그램 없이도 명령어 몇 줄로 시작할 수 있다.

## 사전 준비: .NET SDK

MonoGame 프로젝트를 만들기 전에 먼저 .NET SDK가 설치되어 있어야 한다. .NET SDK는 마이크로소프트 공식 사이트에서 무료로 내려받을 수 있으며, Windows, macOS, Linux 모두를 지원한다. 설치가 끝났다면 터미널(Windows에서는 PowerShell이나 명령 프롬프트, macOS/Linux에서는 터미널)을 열어 다음 명령으로 정상적으로 설치되었는지 확인해보자.

```
dotnet --version
```

버전 번호가 출력되면 준비가 끝난 것이다. 이 책의 예제는 특정 버전에 지나치게 의존하지 않지만, 너무 오래된 버전이라면 최신 LTS(Long-Term Support) 버전으로 업데이트해두는 편이 여러 모로 편하다.

에디터는 Visual Studio, Visual Studio Code, JetBrains Rider 등 C#을 지원하는 도구라면 무엇을 사용해도 무방하다. 이 책의 실습은 특정 에디터에 종속되지 않도록, 대부분의 과정을 `dotnet` CLI 명령어를 중심으로 진행한다. 원하는 에디터에서 생성된 프로젝트 폴더를 열어 코드를 작성하면 된다.

## MonoGame 프로젝트 템플릿 설치하기

.NET SDK에는 `dotnet new`라는 명령으로 다양한 프로젝트 템플릿을 생성하는 기능이 내장되어 있다. 하지만 MonoGame용 템플릿은 기본으로 들어 있지 않기 때문에, 먼저 아래 명령으로 MonoGame 템플릿 패키지를 설치해야 한다.

```
dotnet new install MonoGame.Templates.CSharp
```

이 명령은 NuGet을 통해 MonoGame 공식 프로젝트 템플릿 모음을 내려받아 `dotnet new` 명령에 등록한다. 한 번만 설치해두면 이후로는 컴퓨터의 어느 위치에서든 새로운 MonoGame 프로젝트를 즉시 생성할 수 있다. 설치가 끝난 뒤 `dotnet new list`를 실행해보면, 목록에 `mgdesktopgl`, `mgandroid`, `mgios` 같은 MonoGame 관련 템플릿들이 추가된 것을 확인할 수 있다.

## 첫 프로젝트 생성하기

템플릿 설치가 끝났다면, 이제 실제로 프로젝트를 만들어보자. 원하는 작업 폴더로 이동한 뒤 다음 명령을 실행한다.

```
dotnet new mgdesktopgl -o MyGame
```

`mgdesktopgl`은 Windows, macOS, Linux에서 공통으로 동작하는 데스크톱용 템플릿의 이름이다. 이름의 "GL"은 이 템플릿이 내부적으로 OpenGL 기반 렌더링을 사용한다는 것을 의미하며, 1장에서 살펴본 것처럼 하나의 코드베이스로 세 운영체제 모두를 겨냥할 수 있게 해주는 핵심적인 이유이기도 하다. `-o MyGame` 옵션은 `MyGame`이라는 이름의 새 폴더를 만들고 그 안에 프로젝트 파일들을 생성하라는 뜻이다. 명령이 끝나면 `MyGame` 폴더 안에 다음과 같은 파일들이 만들어져 있을 것이다.

```
MyGame/
├── Content/
│   └── Content.mgcb
├── Game1.cs
├── Icon.bmp
├── Icon.ico
├── MyGame.csproj
└── Program.cs
```

## 생성된 프로젝트 구조 살펴보기

각 파일이 어떤 역할을 하는지 하나씩 짚어보자.

**`MyGame.csproj`**. 이 파일은 일반적인 .NET 프로젝트 파일과 동일한 형식의 XML 파일로, 프로젝트가 어떤 SDK를 사용하는지, 어떤 NuGet 패키지(`MonoGame.Framework.DesktopGL` 등)를 참조하는지, 어떤 콘텐츠 파일을 빌드에 포함할지 등의 설정을 담고 있다. `dotnet` CLI의 다른 프로젝트와 마찬가지로 `dotnet build`, `dotnet run` 같은 명령이 이 파일을 기준으로 동작한다.

**`Program.cs`**. 프로그램의 진입점(entry point)이다. 내용을 열어보면 다음과 같이 매우 짧은 코드로 이루어져 있다.

```csharp
using var game = new Game1();
game.Run();
```

`Game1` 클래스의 인스턴스를 하나 만들고, `Run()` 메서드를 호출하는 것이 전부다. `Run()`을 호출하는 순간부터 MonoGame 내부의 게임 루프가 시작되며, 창이 닫히기 전까지 이 메서드는 반환되지 않는다. `using var`로 선언된 덕분에 게임이 종료될 때 `Game1`이 `IDisposable`을 구현하는 리소스들(그래픽 디바이스 등)을 자동으로 정리해준다.

**`Game1.cs`**. MonoGame 프로젝트의 심장에 해당하는 파일이다. 이 클래스가 실제 게임의 동작을 정의하는 곳으로, 다음 절에서 자세히 살펴본다.

**`Content/Content.mgcb`**. 콘텐츠 파이프라인(Content Pipeline)의 설정 파일이다. 게임에서 사용할 텍스처, 폰트, 오디오 파일 같은 원본 에셋들을 어떻게 빌드할지 정의해두는 곳으로, MGCB Editor라는 전용 도구로 열어 편집할 수 있다. 지금 당장은 텅 빈 상태에 가깝지만, 4장에서 이 파일을 중심으로 콘텐츠 파이프라인이 어떻게 동작하는지 깊이 있게 다룬다.

**`Icon.bmp`, `Icon.ico`**. 게임 실행 파일과 창에 표시될 기본 아이콘 이미지다. 나중에 자신만의 게임 아이콘으로 교체할 수 있다.

## Game1 클래스의 기본 골격

`Game1.cs` 파일을 열어보면 대략 다음과 같은 형태의 코드가 이미 작성되어 있다(주석 등 일부 내용은 생략했다).

```csharp
using Microsoft.Xna.Framework;
using Microsoft.Xna.Framework.Graphics;

namespace MyGame;

public class Game1 : Game
{
    private GraphicsDeviceManager _graphics;
    private SpriteBatch _spriteBatch;

    public Game1()
    {
        _graphics = new GraphicsDeviceManager(this);
        Content.RootDirectory = "Content";
        IsMouseVisible = true;
    }

    protected override void Initialize()
    {
        base.Initialize();
    }

    protected override void LoadContent()
    {
        _spriteBatch = new SpriteBatch(GraphicsDevice);
    }

    protected override void Update(GameTime gameTime)
    {
        base.Update(gameTime);
    }

    protected override void Draw(GameTime gameTime)
    {
        GraphicsDevice.Clear(Color.CornflowerBlue);

        base.Draw(gameTime);
    }
}
```

여기서 눈여겨볼 부분은 `Game1`이 `Microsoft.Xna.Framework` 네임스페이스의 `Game` 클래스를 상속받고 있다는 점이다. 이름에서도 알 수 있듯, MonoGame은 1장에서 살펴본 XNA의 API 네임스페이스를 그대로 유지하고 있다. `Game` 클래스는 창 생성, 게임 루프 실행, 타이밍 관리처럼 게임을 구동하는 데 필요한 복잡한 인프라를 내부에 감춰두고, 개발자는 몇 가지 정해진 메서드만 오버라이드하면 되도록 설계되어 있다.

생성자에서 만들어지는 `GraphicsDeviceManager` 필드는 화면 해상도, 전체화면 여부 같은 그래픽스 관련 설정을 관리하는 객체이고, `SpriteBatch` 필드는 이후 5장에서 자세히 배우게 될, 2D 이미지를 화면에 그리기 위한 도구다. 그리고 `Initialize`, `LoadContent`, `Update`, `Draw`라는 네 개의 메서드가 이미 오버라이드된 채로 생성되어 있는 것을 볼 수 있다. 이 메서드들은 각각 게임이 시작될 때, 에셋을 불러올 때, 매 프레임 로직을 갱신할 때, 매 프레임 화면을 그릴 때 MonoGame이 자동으로 호출해주는 콜백이다. 지금은 이름과 역할을 눈으로만 확인해두고, 각 메서드가 정확히 어떤 순서로, 어떤 조건에서 호출되는지는 3장 "게임 루프와 Game 클래스 수명주기"에서 상세히 다룬다.

## 빌드하고 실행하기

이제 프로젝트를 실제로 실행해보자. `MyGame` 폴더(즉 `.csproj` 파일이 있는 위치)에서 다음 명령을 입력한다.

```
dotnet run
```

이 명령은 프로젝트를 빌드한 뒤 곧바로 실행까지 이어서 해준다. 처음 실행할 때는 NuGet 패키지 복원과 컴파일 과정 때문에 다소 시간이 걸릴 수 있지만, 이후 재실행부터는 훨씬 빨라진다. 빌드가 성공하면 아무 내용도 없는 빈 창이 하나 뜨는데, 이 창의 배경색이 은은한 파란색 계열인 것을 확인할 수 있을 것이다.

이 색은 우연이 아니다. 방금 살펴본 `Draw` 메서드 안의 `GraphicsDevice.Clear(Color.CornflowerBlue)` 코드가 매 프레임 화면을 이 색으로 지워주고 있기 때문이다. `CornflowerBlue`(콘플라워블루)는 XNA 시절부터 신규 프로젝트의 기본 배경색으로 오랫동안 사용되어 온 색으로, MonoGame도 이 전통을 그대로 이어받았다. 그래서 MonoGame이나 XNA로 게임을 만들어본 개발자들 사이에서는 이 하늘색 화면이 "정상적으로 프로젝트가 생성되고 빌드되었다"는 일종의 신호처럼 여겨지기도 한다. 창을 닫으면 `Run()` 메서드가 반환되면서 프로그램이 종료된다.

## 실습: Hello, MonoGame!

이제 방금 실행해본 프로젝트에 아주 작은 변화를 직접 줘보자. 목표는 두 가지다. 배경색을 바꿔보는 것과, 창 제목을 바꿔보는 것이다.

먼저 배경색을 바꿔보자. `Game1.cs`의 `Draw` 메서드에서 `Color.CornflowerBlue` 부분을 다른 색으로 교체하면 된다. MonoGame의 `Color` 구조체는 `Color.Red`, `Color.Black`, `Color.DarkSlateGray`처럼 이름이 붙은 색상들을 정적 속성으로 미리 제공한다.

```csharp
protected override void Draw(GameTime gameTime)
{
    GraphicsDevice.Clear(Color.DarkSlateGray);

    base.Draw(gameTime);
}
```

이제 `dotnet run`으로 다시 실행하면, 코니플라워블루 대신 어두운 회청색 배경이 나타나는 것을 확인할 수 있다.

다음은 창 제목을 바꿔보자. 창 제목은 `Game` 클래스가 제공하는 `Window` 속성을 통해 접근할 수 있는 `Title` 속성으로 설정한다. 생성자나 `Initialize` 메서드에 다음과 같은 한 줄을 추가해보자.

```csharp
public Game1()
{
    _graphics = new GraphicsDeviceManager(this);
    Content.RootDirectory = "Content";
    IsMouseVisible = true;

    Window.Title = "Hello, MonoGame!";
}
```

다시 실행해보면 창의 제목 표시줄에 "Hello, MonoGame!"이라는 문구가 나타난다. 아주 사소한 변화처럼 보이지만, 이 두 줄의 코드는 여러분이 `Game1` 클래스의 내부 상태를 직접 건드려 화면에 보이는 결과를 바꿔낸 첫 경험이다. 지금은 배경색과 창 제목이라는 단순한 속성만 다뤘지만, 이 책을 따라가다 보면 같은 방식으로 텍스처를 그리고, 입력을 받고, 소리를 재생하는 훨씬 복잡한 코드를 이 `Game1` 클래스 안에 채워나가게 될 것이다.

## 요약

- MonoGame 프로젝트를 만들려면 먼저 `dotnet new install MonoGame.Templates.CSharp` 명령으로 프로젝트 템플릿을 설치해야 한다.
- `dotnet new mgdesktopgl -o MyGame` 명령으로 Windows/macOS/Linux를 아우르는 데스크톱(OpenGL 기반) 프로젝트를 생성할 수 있다.
- 생성된 프로젝트는 진입점인 `Program.cs`, 게임의 핵심 로직이 담기는 `Game1.cs`, 콘텐츠 파이프라인 설정 파일인 `Content/Content.mgcb`, 그리고 `.csproj` 프로젝트 파일로 구성된다.
- `Game1` 클래스는 `Game`을 상속하며, `GraphicsDeviceManager`와 `SpriteBatch` 필드, 그리고 `Initialize`/`LoadContent`/`Update`/`Draw` 메서드의 골격을 기본으로 갖추고 있다. 각 메서드의 자세한 역할은 3장에서 다룬다.
- `dotnet run`으로 프로젝트를 빌드하고 실행할 수 있으며, 기본 상태에서는 코니플라워블루(CornflowerBlue) 배경색의 빈 창이 뜬다.
- `GraphicsDevice.Clear()`에 전달하는 `Color` 값과 `Window.Title` 속성을 바꿔보는 것만으로도 게임의 겉모습을 바꿀 수 있다.

## 연습문제

1. `dotnet new install MonoGame.Templates.CSharp` 명령은 정확히 어떤 일을 하는가? 이 명령을 실행하지 않고 바로 `dotnet new mgdesktopgl`을 실행하면 어떤 일이 벌어질지 예상해보자.
2. `mgdesktopgl` 템플릿 이름에서 "GL"이 의미하는 바는 무엇이며, 이것이 왜 Windows/macOS/Linux를 하나의 코드베이스로 지원할 수 있게 해주는지 설명해보자.
3. `Program.cs`와 `Game1.cs`의 역할 차이를 각각 한두 문장으로 설명해보자.
4. 기본 생성된 `Game1` 클래스에서 배경색을 결정하는 코드는 어느 메서드 안에, 어떤 형태로 들어 있는가?
5. `Color.CornflowerBlue` 대신 자신이 좋아하는 색으로 배경을 바꾸고, 창 제목도 원하는 문구로 바꾼 뒤 `dotnet run`으로 결과를 확인해보자. `Color` 구조체가 제공하는 다른 색상 이름들도 몇 가지 찾아서 시도해보자.

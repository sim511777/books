## 타입마다 코드를 복제하는 문제

9장에서 클래스를 배우면서 우리는 데이터를 감싸는(wrapping) 클래스를 여러 번 만들어 보았다. 이번에는 정수 하나를 담아두는 아주 단순한 클래스를 생각해 보자.

```java
// 정수 하나를 저장하는 상자
public class IntBox {
    private int value;

    public void set(int value) {
        this.value = value;
    }

    public int get() {
        return value;
    }
}
```

이 클래스는 잘 동작한다. 그런데 문자열을 담고 싶다면 어떻게 할까? `int` 대신 `String`을 쓰는 새 클래스를 또 만들어야 한다.

```java
// 문자열 하나를 저장하는 상자
public class StringBox {
    private String value;

    public void set(String value) {
        this.value = value;
    }

    public String get() {
        return value;
    }
}
```

`IntBox`와 `StringBox`는 필드 타입만 다를 뿐, 나머지 구조는 완전히 똑같다. 만약 `Double`, `Person`, `LocalDate`를 담는 상자도 필요하다면 똑같은 클래스를 계속 복제해야 한다. 코드 중복은 유지보수를 어렵게 만든다. `set`과 `get` 메서드의 로직을 한 곳이라도 바꿔야 한다면, 복제된 클래스 개수만큼 똑같은 수정을 반복해야 하기 때문이다.

한 가지 대안은 필드 타입을 `Object`로 선언하는 것이다.

```java
// Object로 어떤 타입이든 담을 수 있게 만든 상자
public class ObjectBox {
    private Object value;

    public void set(Object value) {
        this.value = value;
    }

    public Object get() {
        return value;
    }
}
```

이 방법은 코드 중복은 없앴지만 새로운 문제를 만든다. `get()`이 돌려주는 값은 항상 `Object` 타입이므로, 실제로 사용하려면 원래 타입으로 강제 변환(casting)해야 한다.

```java
ObjectBox box = new ObjectBox();
box.set("hello");
String s = (String) box.get(); // 강제 변환 필요

box.set(123); // int도 자동으로 Integer로 박싱되어 들어감
String wrong = (String) box.get(); // 컴파일은 되지만 실행 중 ClassCastException 발생!
```

문제는 컴파일러가 `box`에 실제로 어떤 타입의 값이 들어있는지 전혀 알지 못한다는 점이다. 타입이 맞지 않는 변환은 컴파일 시점에는 걸러지지 않고, 프로그램을 실행하는 순간에야 `ClassCastException`으로 드러난다. 12장에서 다룬 것처럼 예외는 처리할 수 있지만, 애초에 컴파일 시점에 잡을 수 있는 실수를 실행 시점까지 미루는 것은 좋은 설계가 아니다.

우리에게 필요한 것은 "타입은 나중에 결정하되, 한 번 결정되면 컴파일러가 그 타입을 기억하고 검사해 주는" 방법이다. 이것이 바로 **제네릭(Generics)**이 해결하는 문제다.

## 제네릭 클래스: `class Box<T>`

제네릭은 클래스나 메서드를 정의할 때 구체적인 타입 대신 **타입 매개변수(type parameter)**를 사용하고, 실제로 그 클래스를 사용하는 시점에 구체적인 타입을 지정하는 방식이다. 타입 매개변수는 보통 대문자 한 글자로 쓰는데, `T`(Type), `E`(Element), `K`(Key), `V`(Value) 등이 관례적으로 쓰인다.

앞서 만든 `IntBox`, `StringBox`, `ObjectBox`를 하나의 제네릭 클래스로 통합해 보자.

```java
// T는 이 클래스를 사용할 때 결정되는 타입 매개변수
public class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

이제 `Box`를 사용할 때 어떤 타입을 담을지 `<>` 안에 명시한다.

```java
Box<String> stringBox = new Box<>();
stringBox.set("hello");
String s = stringBox.get(); // 강제 변환이 필요 없다

Box<Integer> intBox = new Box<>();
intBox.set(123);
Integer n = intBox.get();

// stringBox.set(123); // 컴파일 오류! String 상자에는 정수를 넣을 수 없다
```

핵심은 `stringBox.set(123)`처럼 타입이 맞지 않는 호출이 **컴파일 시점에 바로 오류로 잡힌다**는 것이다. `Object`를 쓰던 방식에서는 실행할 때까지 몰랐던 실수가, 제네릭에서는 코드를 작성하는 순간 드러난다. 또한 `get()`의 반환값도 이미 `String`이나 `Integer`로 확정되어 있으므로 강제 변환이 필요 없다.

`new Box<>()`에서 `<>`는 다이아몬드 연산자라고 부르는데, 좌변의 `Box<String>`에서 타입을 이미 알 수 있으므로 우변에서는 타입을 비워두어도 컴파일러가 추론해 준다.

참고로 제네릭의 타입 매개변수 자리에는 `int`, `double` 같은 기본 타입(primitive type)을 직접 쓸 수 없다. 반드시 `Integer`, `Double` 같은 래퍼 클래스를 사용해야 한다(`Box<int>`는 컴파일 오류다). 대신 자바의 오토박싱(autoboxing) 기능 덕분에 `intBox.set(123)`처럼 `int` 값을 넣으면 자동으로 `Integer`로 변환되어 저장된다.

## 제네릭 메서드

클래스 전체를 제네릭으로 만들지 않고, 메서드 하나만 제네릭으로 선언할 수도 있다. 예를 들어 배열의 첫 번째 원소를 돌려주는 메서드를 어떤 타입의 배열에도 쓸 수 있게 만들어 보자.

```java
public class ArrayUtil {
    // 메서드 이름 앞의 <T>가 이 메서드만의 타입 매개변수를 선언한다
    public static <T> T firstElement(T[] array) {
        return array[0];
    }
}
```

```java
String[] names = {"철수", "영희", "민수"};
String first = ArrayUtil.firstElement(names); // T가 String으로 결정됨

Integer[] numbers = {10, 20, 30};
Integer firstNum = ArrayUtil.firstElement(numbers); // T가 Integer로 결정됨
```

여기서 `T`는 `ArrayUtil` 클래스 전체의 타입 매개변수가 아니라, `firstElement` 메서드를 호출할 때마다 새로 결정되는 타입 매개변수다. 8장에서 배운 메서드 오버로딩과 비교하면, 오버로딩은 타입마다 메서드를 여러 개 작성해야 하지만 제네릭 메서드는 하나의 메서드 정의로 모든 타입을 처리한다.

## 제한된 타입 매개변수: `<T extends Comparable<T>>`

지금까지의 `T`는 아무 타입이나 올 수 있었다. 하지만 때로는 "아무 타입이나 되는 건 아니고, 특정 조건을 만족하는 타입만" 받고 싶을 때가 있다. 예를 들어 두 값 중 더 큰 값을 찾는 메서드를 만들려면, 그 타입은 최소한 "비교할 수 있는" 타입이어야 한다.

```java
// 컴파일 오류! T가 비교 가능한 타입인지 알 수 없으므로 compareTo를 호출할 수 없다
public static <T> T max(T a, T b) {
    return a.compareTo(b) > 0 ? a : b;
}
```

이 문제는 타입 매개변수에 **제한(bound)**을 걸어서 해결한다. `extends` 키워드를 사용해 `T`가 반드시 `Comparable<T>`를 구현한 타입이어야 한다고 명시하는 것이다. 11장에서 다룬 인터페이스를 떠올려 보면, `Comparable<T>`는 `compareTo` 메서드를 정의하는 표준 인터페이스다.

```java
// T는 반드시 Comparable<T>를 구현하는 타입이어야 한다
public static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) > 0 ? a : b;
}
```

```java
System.out.println(max(3, 7));           // 7 (Integer는 Comparable<Integer> 구현)
System.out.println(max("apple", "banana")); // banana (String도 Comparable<String> 구현)
```

이렇게 제한을 걸면 두 가지 이점이 생긴다. 첫째, `compareTo` 메서드를 안전하게 호출할 수 있다는 것을 컴파일러가 보장해 준다. 둘째, `Comparable`을 구현하지 않은 타입(예: 아무 필드도 없는 임의의 클래스)을 넘기면 컴파일 시점에 바로 오류가 발생해서 실수를 미리 막아 준다.

여기서 `extends`는 상속 문법에서 쓰는 `extends`와 문법상 같은 단어지만 의미는 조금 다르다. 제네릭의 제한에서는 클래스를 상속할 때든 인터페이스를 구현할 때든 항상 `extends`를 쓰고, "T는 이 타입이거나 그 하위 타입이어야 한다"는 뜻으로 읽으면 된다.

## 와일드카드: `? extends`와 `? super`

제네릭을 메서드의 매개변수로 받을 때, 정확히 어떤 타입인지보다 "어떤 타입 계열에 속하는지"만 알면 충분한 경우가 있다. 이럴 때 쓰는 것이 **와일드카드(wildcard)** `?`다.

예를 들어 상자 안의 값을 화면에 출력만 하는 메서드를 생각해 보자.

```java
// Box<Object>만 받을 수 있다 — Box<String>은 넘길 수 없어서 너무 제한적이다
public static void printBox(Box<Object> box) {
    System.out.println(box.get());
}
```

직관과 다르게, `Box<String>`은 `Box<Object>`의 하위 타입이 아니기 때문에 위 메서드에는 `Box<String>`을 넘길 수 없다. 이럴 때 `? extends Object`(또는 줄여서 `?`)를 사용하면 "어떤 타입이든 담긴 상자"를 받을 수 있다.

```java
// ? extends Object는 "Object이거나 그 하위 타입"을 담은 상자라면 무엇이든 받는다는 뜻
public static void printBox(Box<? extends Object> box) {
    System.out.println(box.get());
}
```

와일드카드는 크게 두 가지 형태로 쓰인다.

- `? extends T`: T이거나 T의 하위 타입만 허용한다. 주로 상자에서 값을 **읽어올 때(생산자, producer)** 사용한다.
- `? super T`: T이거나 T의 상위 타입만 허용한다. 주로 상자에 값을 **넣을 때(소비자, consumer)** 사용한다.

```java
// Number나 그 하위 타입(Integer, Double 등)이 담긴 상자에서 값을 읽는다
public static double sumOf(Box<? extends Number> box) {
    return box.get().doubleValue();
}

// Integer나 그 상위 타입(Number, Object)이 담긴 상자에 Integer 값을 넣는다
public static void putInteger(Box<? super Integer> box, int value) {
    box.set(value);
}
```

이 규칙은 실무에서 "읽기는 extends, 쓰기는 super(Get은 Extends, Put은 Super)"라는 문장으로 흔히 외운다. 지금 단계에서는 와일드카드가 있다는 것과 대략적인 용도만 기억해 두면 충분하다. 실제로 와일드카드를 자유자재로 쓰는 감각은 다음 장에서 컬렉션을 다루는 코드를 많이 작성해 보면서 자연스럽게 익히게 된다.

## 다음 장 예고: 이미 제네릭을 쓰고 있었다

사실 여러분은 이미 제네릭을 사용할 준비가 되어 있다. 14장에서 배울 `ArrayList<T>`, `HashMap<K, V>` 같은 컬렉션 클래스는 모두 이 장에서 배운 방식으로 만들어진 제네릭 클래스다. 예를 들어 `ArrayList<String>`은 우리가 만든 `Box<String>`과 원리가 같다. 다만 상자 하나가 아니라 여러 개의 값을 담을 수 있고, 추가·삭제·검색 같은 훨씬 풍부한 기능을 제공한다는 점이 다르다.

7장에서 배운 배열은 크기가 고정되어 있고 타입 검사가 실행 중에야 이루어지는 경우도 있었지만(예: `Object[]` 배열에 다른 타입을 넣는 경우), 제네릭 컬렉션은 컴파일 시점에 타입을 확실히 검사해 주면서도 크기를 자유롭게 늘리고 줄일 수 있다. 제네릭을 이해하고 나면, 컬렉션 프레임워크의 API가 왜 그런 형태로 설계되었는지 훨씬 쉽게 이해할 수 있다.

## 요약

- 타입마다 클래스를 복제하면(`IntBox`, `StringBox`) 코드 중복이 생기고, `Object`로 통합하면 강제 변환과 실행 시점 오류(`ClassCastException`) 위험이 생긴다.
- 제네릭 클래스(`class Box<T>`)는 타입 매개변수 `T`를 사용해 코드 중복 없이도 컴파일 시점에 타입 안전성을 보장한다.
- 제네릭 메서드는 클래스 전체가 아니라 메서드 하나에만 타입 매개변수를 선언하며, 호출할 때마다 타입이 결정된다.
- 제한된 타입 매개변수(`<T extends Comparable<T>>`)는 타입에 특정 조건(인터페이스 구현 등)을 강제해서 `compareTo` 같은 메서드를 안전하게 호출할 수 있게 한다.
- 와일드카드 `? extends T`(읽기 위주)와 `? super T`(쓰기 위주)는 타입 계열 전체를 매개변수로 받고자 할 때 사용한다.
- 14장에서 다룰 `ArrayList<T>`, `HashMap<K, V>` 등 컬렉션 프레임워크는 모두 제네릭으로 설계되어 있다.

## 연습문제

1. `Box<T>` 클래스를 참고해서, 두 개의 값을 담을 수 있는 `Pair<A, B>` 제네릭 클래스를 작성하라. `getFirst()`, `getSecond()` 메서드를 포함해야 한다.
2. 배열의 마지막 원소를 반환하는 제네릭 메서드 `lastElement`를 작성하라. `ArrayUtil.firstElement`를 참고하라.
3. `<T extends Comparable<T>>`를 사용해서, 배열에서 가장 큰 값을 찾는 제네릭 메서드 `maxOfArray(T[] array)`를 작성하라.
4. `Box<Object>`에 `Box<String>`을 대입할 수 없는 이유를 자신의 언어로 설명하고, 이 문제를 와일드카드로 어떻게 해결할 수 있는지 코드로 보여라.
5. 제네릭을 쓰지 않고 `Object`로만 구현한 스택(stack) 클래스와, 제네릭으로 구현한 스택 클래스를 각각 작성해 보고, 값을 꺼낼 때 코드가 어떻게 달라지는지 비교하라.

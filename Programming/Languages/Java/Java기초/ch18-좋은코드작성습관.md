## 들어가며

지금까지 17개 장을 거치면서 변수와 자료형부터 멀티스레딩까지, Java 문법의 거의 모든 영역을 살펴봤습니다. 문법을 안다는 것과 좋은 코드를 쓴다는 것은 다른 이야기입니다. 똑같은 기능을 하는 코드라도 어떻게 이름을 붙였는지, 예외를 어떻게 다뤘는지, 객체를 비교할 때 무엇을 오버라이드했는지에 따라 유지보수하기 쉬운 코드와 나중에 디버깅으로 밤을 새우게 되는 코드로 나뉩니다. 이 마지막 장에서는 문법이 아니라 "습관"에 대해 이야기합니다. 지금까지 배운 개념들을 실무에서 어떻게 다뤄야 하는지 정리하고, 이 책을 마친 뒤 어디로 나아가면 좋을지도 함께 살펴봅니다.

## 네이밍 컨벤션

Java 커뮤니티는 오랫동안 합의해온 이름 짓기 규칙을 가지고 있습니다. 이 규칙을 지키는 것만으로도 다른 사람(그리고 몇 달 뒤의 나 자신)이 코드를 훨씬 빠르게 이해할 수 있습니다.

| 대상 | 규칙 | 예시 |
|---|---|---|
| 클래스, 인터페이스 | PascalCase (단어마다 첫 글자 대문자) | `BankAccount`, `Runnable`, `OrderService` |
| 메서드, 변수 | camelCase (첫 글자 소문자, 이후 단어 첫 글자 대문자) | `getBalance()`, `totalPrice`, `isValid` |
| 상수 (`static final`) | 대문자와 밑줄 | `MAX_RETRY_COUNT`, `DEFAULT_TIMEOUT` |
| 패키지 | 모두 소문자, 보통 도메인 역순 | `com.example.shop.order` |

이 표는 이 책 전체에서 이미 자연스럽게 따르고 있던 규칙입니다. 3장에서 변수를 선언할 때, 8장에서 메서드를 만들 때, 9장에서 클래스를 정의할 때 사용한 이름들이 모두 이 규칙을 따르고 있었습니다. 몇 가지 추가로 기억해둘 만한 관례가 있습니다.

- **`boolean` 값을 반환하는 메서드**는 `is`, `has`, `can`으로 시작하는 것이 자연스럽습니다. `isEmpty()`, `hasNext()`, `canMove()`처럼요. 14장에서 다룬 컬렉션의 `isEmpty()` 메서드도 이 관례를 따르고 있습니다.
- **의미 있는 이름을 쓰세요.** `int d;`보다는 `int elapsedDays;`가 훨씬 낫습니다. 변수 이름을 줄여서 타이핑을 아끼는 것보다, 코드를 읽는 사람(대부분 나중의 자신)이 맥락을 다시 떠올리는 데 걸리는 시간이 훨씬 비쌉니다.
- **약어는 신중하게.** `usrNm`보다 `userName`이 낫습니다. 다만 `id`, `url`, `http`처럼 이미 업계 표준으로 굳어진 약어는 그대로 사용해도 됩니다.
- **단수/복수를 명확히.** 배열이나 컬렉션(7장, 14장)을 담는 변수는 복수형으로 짓습니다. `List<String> names`, `int[] scores`처럼요. 반면 하나의 값을 담는 변수는 단수형으로 짓습니다.

## equals, hashCode, toString을 오버라이드해야 하는 이유

9장에서 클래스와 객체를, 10장에서 상속과 오버라이드를 배웠습니다. 그런데 실제로 클래스를 설계할 때 놓치기 쉬운 부분이 `Object` 클래스로부터 물려받는 세 메서드 `equals()`, `hashCode()`, `toString()`을 언제, 왜 오버라이드해야 하는지입니다.

### equals() — "같다"의 기준을 정의한다

Java에서 `==` 연산자는 객체의 경우 "같은 메모리 주소를 가리키는가"를 검사합니다(4장의 연산자, 9장의 참조형을 떠올려보세요). 하지만 우리가 원하는 "같음"은 대부분 "필드 값이 같은가"입니다.

```java
public class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
    // getter는 생략
}
```

```java
Point p1 = new Point(3, 5);
Point p2 = new Point(3, 5);

System.out.println(p1 == p2);        // false - 서로 다른 객체이므로
System.out.println(p1.equals(p2));   // false - equals()를 오버라이드하지 않았다면 == 와 동일하게 동작
```

`equals()`를 오버라이드하지 않으면 `Object`의 기본 구현이 그대로 사용되는데, 이 기본 구현은 `==`와 똑같이 참조 비교만 합니다. `x`와 `y`가 같으면 같은 좌표로 취급하고 싶다면 직접 오버라이드해야 합니다.

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) return true;
    if (!(obj instanceof Point)) return false;
    Point other = (Point) obj;
    return this.x == other.x && this.y == other.y;
}
```

### hashCode() — equals()와 반드시 함께 오버라이드한다

14장에서 `HashMap`, `HashSet` 같은 해시 기반 컬렉션을 배웠습니다. 이 컬렉션들은 객체를 저장하고 찾을 때 `hashCode()`가 반환하는 값을 이용해 내부 저장 위치를 결정합니다. 규칙은 이렇습니다. **"같다고 판단되는 두 객체는(즉 `equals()`가 `true`를 반환하는 두 객체는) 반드시 같은 `hashCode()` 값을 반환해야 한다."**

`equals()`만 오버라이드하고 `hashCode()`를 그대로 두면, 논리적으로 같은 두 객체인데도 `HashSet`에 둘 다 들어가버리거나, `HashMap`에서 키로 찾을 수 없는 등 이해하기 어려운 버그가 생깁니다. 그래서 `equals()`를 오버라이드했다면 `hashCode()`도 같은 필드를 기준으로 함께 오버라이드하는 것이 원칙입니다.

```java
@Override
public int hashCode() {
    return Objects.hash(x, y);
}
```

`java.util.Objects`의 `hash()` 메서드를 사용하면 여러 필드를 조합한 해시코드를 간단하게 만들 수 있습니다.

### toString() — 디버깅과 로그를 위한 최소한의 예의

`toString()`을 오버라이드하지 않으면 `System.out.println(point)` 같은 코드는 `Point@1b6d3586`처럼 클래스 이름과 해시코드가 뒤섞인, 사람이 읽기 어려운 문자열을 출력합니다. 디버깅 중에 객체의 상태를 눈으로 확인하려 할 때마다 각 필드를 하나씩 꺼내 출력해야 한다면 매우 번거롭습니다.

```java
@Override
public String toString() {
    return "Point(x=" + x + ", y=" + y + ")";
}
```

이렇게 오버라이드해두면 `System.out.println(point)`, 로그 출력, 디버거의 변수 창 등 여러 곳에서 자동으로 읽기 좋은 형태로 표시됩니다. 세 메서드 모두 "오버라이드하지 않아도 컴파일은 되지만, 오버라이드하지 않으면 나중에 반드시 문제가 되는" 대표적인 예입니다. 클래스를 설계할 때는 이 필드들이 객체의 "정체성"에 해당하는지, 그렇다면 세 메서드를 함께 오버라이드해야 하는지 항상 점검하는 습관을 들이는 것이 좋습니다.

## 흔한 실수들 다시 보기

이 책을 진행하면서 이미 여러 번 마주쳤을 실수들을 한자리에 모아 다시 짚어봅니다.

**NullPointerException(NPE).** `null`인 참조를 통해 메서드를 호출하거나 필드에 접근하면 발생합니다(12장 예외 처리 참고). 특히 메서드가 컬렉션이나 문자열을 조회했는데 값이 없을 때 `null`을 반환하는 설계라면, 반환값을 바로 사용하기 전에 `null` 검사를 하는 습관이 필요합니다.

```java
String name = findUserName(id);
if (name != null && name.equals("관리자")) {   // name.equals()를 먼저 쓰면 NPE 위험
    // ...
}
```

참고로 비교할 값이 상수(리터럴)일 때는 `"관리자".equals(name)`처럼 상수를 앞에 두면 `name`이 `null`이어도 NPE가 나지 않습니다. `equals()`는 항상 호출하는 대상이 `null`이 아니어야 하기 때문입니다.

**배열/컬렉션 인덱스 초과.** 7장에서 배운 배열은 크기가 고정되어 있고, 유효한 인덱스는 `0`부터 `길이 - 1`까지입니다. `for` 반복문(6장)의 조건식을 `<=`로 잘못 쓰거나, 마지막 원소 다음 위치를 계산하면서 실수하면 `ArrayIndexOutOfBoundsException`이 발생합니다. `List`(14장)도 마찬가지로 `get(index)` 호출 시 유효 범위를 벗어나면 `IndexOutOfBoundsException`이 발생합니다.

```java
int[] scores = {90, 85, 77};
for (int i = 0; i <= scores.length; i++) {   // 오류: <= 대신 <를 써야 한다
    System.out.println(scores[i]);
}
```

**체크 예외를 무시하는 습관.** 12장에서 체크 예외(checked exception)는 반드시 `try-catch`로 처리하거나 `throws`로 선언해야 한다고 배웠습니다. 그런데 컴파일러가 요구한다는 이유만으로 `catch` 블록을 비워두고 넘어가는 경우가 흔합니다.

```java
try {
    riskyOperation();
} catch (IOException e) {
    // 아무것도 하지 않음 - 문제가 조용히 사라진 것처럼 보이지만 실제로는 숨겨진 것
}
```

이렇게 하면 컴파일은 통과하지만, 실제로 오류가 발생했을 때 아무 흔적도 남지 않아 원인을 찾기가 매우 어려워집니다. 최소한 `e.printStackTrace()`나 로그 기록을 남기거나, 정말로 무시해도 되는 상황인지 주석으로 근거를 남겨두는 것이 좋습니다.

**`==`로 문자열 비교하기.** 3장에서 배운 것처럼 `String`은 참조형입니다. `==`는 두 참조가 같은 객체를 가리키는지 비교하므로, 값이 같은 두 문자열이라도 `==`가 `false`를 반환할 수 있습니다. 문자열의 내용을 비교할 때는 항상 `equals()`를 사용해야 합니다.

**무한 루프와 종료 조건 누락.** 6장의 반복문에서 `while`의 조건이 절대 `false`가 되지 않거나, `for`문에서 증감식을 빠뜨리면 프로그램이 멈추지 않습니다. 반복문을 작성할 때마다 "이 조건이 언젠가 반드시 거짓이 되는가"를 스스로 점검하는 습관을 들이세요.

**자원을 닫지 않는 실수.** 파일이나 네트워크 연결처럼 외부 자원을 사용한 뒤 닫지 않으면 자원이 계속 누적되어 결국 프로그램이 자원 부족으로 실패할 수 있습니다. 12장에서 다룬 `try-with-resources` 구문을 사용하면 예외가 발생하더라도 자원이 자동으로 닫히므로, 자원을 다루는 코드에서는 이 구문을 기본으로 습관화하는 것이 좋습니다.

## 단위 테스트라는 습관

지금까지는 작성한 코드가 제대로 동작하는지 `main` 메서드에서 `System.out.println()`으로 값을 찍어보며 눈으로 확인했을 것입니다. 이 방법은 프로그램이 작을 때는 충분하지만, 클래스와 메서드가 많아질수록 "이 메서드를 고쳤는데 다른 곳이 망가지지 않았는지"를 매번 눈으로 확인하기 어려워집니다.

이런 문제를 해결하기 위해 실무에서는 **단위 테스트(unit test)**를 작성합니다. 단위 테스트란 메서드 하나(또는 작은 단위의 기능)가 특정 입력에 대해 기대한 출력을 내는지를 코드로 검증하는 것입니다. Java 생태계에서 가장 널리 쓰이는 단위 테스트 도구는 **JUnit**입니다. JUnit을 사용하면 다음과 같은 형태로 테스트를 작성합니다.

```java
// JUnit을 사용한 테스트 코드의 예시 (개념 설명용)
@Test
void addTwoPositiveNumbers() {
    Calculator calculator = new Calculator();
    assertEquals(5, calculator.add(2, 3));
}
```

이런 테스트를 미리 작성해두면, 나중에 `Calculator` 클래스를 리팩터링하거나 기능을 추가한 뒤에도 테스트를 다시 실행해서 기존 동작이 여전히 올바른지 몇 초 만에 확인할 수 있습니다. 이 책은 문법과 기본 개념에 집중하기 때문에 JUnit 사용법을 자세히 다루지는 않지만, "테스트 코드를 함께 작성하는 것이 좋은 개발 습관"이라는 사실만은 꼭 기억해두길 권합니다. 다음 단계로 Java 실무 개발을 학습할 때 JUnit은 거의 필수적으로 만나게 될 도구입니다.

## 코드 스타일에 대한 마지막 조언

- **메서드는 한 가지 일만 하게 작게 유지하세요.** 8장에서 배운 메서드 분리의 목적은 재사용뿐 아니라 "읽기 쉬움"입니다. 메서드 하나가 100줄을 넘어간다면 여러 개로 나눌 수 있는지 검토해보세요.
- **주석은 "왜"를 설명하는 데 쓰세요.** 코드가 "무엇"을 하는지는 코드 자체가 보여줍니다. 주석은 "왜 이렇게 처리했는지", "왜 이 예외 상황을 이렇게 다루는지"처럼 코드만 봐서는 알기 어려운 배경을 설명할 때 가장 값어치가 있습니다.
- **클래스는 하나의 책임만 지도록 설계하세요.** 9장, 10장, 11장에서 배운 클래스·상속·인터페이스는 결국 "역할을 잘 나누기 위한 도구"입니다. 하나의 클래스가 너무 많은 역할(데이터 검증, 저장, 화면 출력 등)을 동시에 맡고 있다면 나눌 수 있는지 고민해보세요.
- **예외 메시지를 구체적으로 쓰세요.** 12장에서 예외를 던질 때 `throw new IllegalArgumentException("잘못된 값")`처럼 모호하게 쓰기보다, `"age는 0 이상이어야 합니다. 입력값: " + age`처럼 원인을 특정할 수 있는 메시지를 남기면 나중에 문제를 훨씬 빠르게 추적할 수 있습니다.

## 다음 학습 단계

이 책은 Java 언어 자체의 문법과 기본 개념을 다루는 데 집중했습니다. 이제 여러분은 변수와 제어 흐름부터 객체지향, 컬렉션, 람다와 스트림, 멀티스레딩까지 실무 Java 코드를 읽고 쓰는 데 필요한 기초를 갖췄습니다. 여기서 어디로 나아갈지는 관심 분야에 따라 달라집니다.

- **웹 백엔드 개발.** Java 진영에서 웹 서버와 API를 만들 때 가장 널리 쓰이는 프레임워크 생태계는 **스프링(Spring)**입니다. 스프링은 이 책에서 배운 클래스, 인터페이스, 제네릭, 컬렉션 같은 개념을 그대로 활용하면서, 웹 요청 처리, 데이터베이스 연동, 의존성 관리 같은 실무 기능을 더해줍니다. 지금까지의 기초가 있다면 스프링 학습은 "새로운 문법을 배우는 것"이 아니라 "이미 아는 개념을 실무 도구에 적용하는 것"에 가깝게 느껴질 것입니다.
- **안드로이드 앱 개발.** 1장에서 언급했듯 안드로이드는 오랫동안 Java를 표준 언어로 사용해왔고, 지금도 Java 코드베이스가 많이 남아 있습니다. 최근에는 Kotlin이 권장 언어가 되었지만 Kotlin도 JVM 위에서 동작하며 Java와 상호 운용이 자유로우므로, Java 문법을 익힌 상태에서 안드로이드 개발로 넘어가는 길은 여전히 자연스럽습니다.
- **빌드 도구와 협업 환경.** 실무 프로젝트는 이 책의 예제처럼 파일 하나를 `javac`로 컴파일하지 않고, Maven이나 Gradle 같은 빌드 도구로 의존성과 빌드 과정을 관리합니다(2장에서 다룬 빌드 과정의 확장판이라고 생각하면 됩니다). 또한 Git을 이용한 버전 관리와 협업도 실무의 기본 소양입니다.
- **JVM 위의 다른 언어.** Kotlin, Scala처럼 JVM 위에서 동작하는 언어들은 Java와 상호 운용되면서도 더 간결한 문법이나 다른 패러다임(함수형 프로그래밍 등)을 제공합니다. 15장, 16장에서 배운 람다와 스트림에 익숙해졌다면 이런 언어들의 함수형 스타일에도 비교적 쉽게 적응할 수 있습니다.

어느 방향으로 가든 공통적으로 중요한 것은, 새로운 프레임워크나 언어를 배울 때도 "이것이 왜 필요한가"를 먼저 이해하려는 태도입니다. 이 책이 그런 태도로 Java의 각 기능을 설명하려 했던 것처럼, 앞으로도 새로운 도구를 마주할 때마다 스스로에게 "이 도구가 해결하려는 문제가 무엇인가"를 물어보길 권합니다.

## 체크리스트

다음 항목들을 스스로 점검하면서 이 책에서 배운 내용을 실제 코드 작성 습관으로 옮겨보세요.

- [ ] 클래스, 메서드, 변수, 상수의 이름이 Java의 네이밍 컨벤션을 따르고 있는가?
- [ ] 변수 이름만 보고도 그 역할을 짐작할 수 있는가? (`d`, `tmp`, `data2` 같은 이름을 피했는가?)
- [ ] 객체를 값으로 비교해야 하는 클래스라면 `equals()`와 `hashCode()`를 함께 오버라이드했는가?
- [ ] 디버깅과 로그 확인을 위해 `toString()`을 오버라이드했는가?
- [ ] 참조형 변수를 사용하기 전에 `null` 가능성을 점검했는가?
- [ ] 배열이나 리스트에 접근할 때 인덱스 범위를 벗어나지 않는지 확인했는가?
- [ ] `catch` 블록을 비워두지 않고, 최소한 로그를 남기거나 무시해도 되는 이유를 남겼는가?
- [ ] 문자열 내용을 비교할 때 `==` 대신 `equals()`를 사용했는가?
- [ ] 반복문의 종료 조건이 항상 언젠가는 만족되는지 확인했는가?
- [ ] 파일이나 네트워크 같은 외부 자원을 사용한 뒤 `try-with-resources`로 안전하게 닫았는가?
- [ ] 메서드와 클래스가 하나의 책임에 집중하도록 설계했는가?
- [ ] 핵심 로직에 대해 단위 테스트를 작성해볼 생각을 해보았는가?

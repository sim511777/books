## PEP 8 — Python 코드 스타일 가이드

**PEP**는 "Python Enhancement Proposal"의 줄임말로, Python 언어나 그 생태계를 개선하기 위한 공식 제안 문서를 가리킨다. 그중 PEP 8은 "Python 코드를 어떻게 작성하면 좋은가"에 대한 가이드라인으로, 이 책 전체에서 이미 자연스럽게 따르고 있던 규칙들의 근거이기도 하다. 핵심 원칙 몇 가지를 정리하면 다음과 같다.

### 들여쓰기와 공백

- 들여쓰기는 스페이스 4칸을 사용한다. 탭과 스페이스를 섞어 쓰지 않는다.
- 쉼표 뒤에는 공백을 하나 둔다. `[1, 2, 3]`처럼 쓰고 `[1,2,3]`처럼 붙여 쓰지 않는다.
- 연산자 앞뒤에는 공백을 둔다. `x = a + b`처럼 쓰고 `x=a+b`처럼 붙여 쓰지 않는다.

```python
# 좋은 예
총합 = 첫째_값 + 둘째_값
숫자_목록 = [1, 2, 3, 4]

# 피해야 할 예
총합=첫째_값+둘째_값
숫자_목록 = [1,2,3,4]
```

### 이름 짓기 규칙

이 책에서 지금까지 사용해 온 이름 짓기 방식이 바로 PEP 8의 권장 사항이다.

| 대상 | 스타일 | 예시 |
|---|---|---|
| 변수, 함수 | snake_case | `user_name`, `calculate_total()` |
| 클래스 | PascalCase | `BankAccount`, `UserProfile` |
| 상수 | 대문자 SNAKE_CASE | `MAX_RETRY_COUNT`, `PI` |
| 모듈 | 짧은 소문자 | `utils`, `data_loader` |

이름은 짧게 줄이기보다 의미가 분명하게 드러나도록 짓는 것이 좋다. `n`이나 `tmp` 같은 이름보다는 `사용자_수`, `임시_결과`처럼(혹은 영문이라면 `user_count`, `temp_result`처럼) 무엇을 담고 있는지 알 수 있는 이름이 협업과 유지보수에 유리하다.

### 한 줄의 길이와 빈 줄

- 한 줄은 보통 79자를 넘지 않도록 권장한다. 너무 긴 줄은 괄호를 이용해 여러 줄로 나눌 수 있다.
- 함수와 클래스 정의 사이에는 빈 줄을 두 줄씩 두어 구획을 명확히 한다.
- 클래스 안의 메서드 사이에는 빈 줄을 한 줄씩 둔다.

```python
class Rectangle:
    """직사각형을 표현하는 클래스."""

    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height


class Circle:
    """원을 표현하는 클래스."""

    def __init__(self, radius):
        self.radius = radius
```

### 도구로 자동화하기

PEP 8 규칙을 사람이 매번 눈으로 확인하며 지키기는 번거롭다. 실무에서는 코드가 스타일 규칙을 지키는지 자동으로 검사해 주는 도구(린터, linter)나, 아예 코드를 규칙에 맞게 자동으로 정리해 주는 도구(포매터, formatter)를 사용하는 경우가 많다. 지금 당장 이런 도구를 도입할 필요는 없지만, "스타일은 사람이 아니라 도구로 강제할 수도 있다"는 사실 정도는 기억해 두자.

## 타입 힌트로 의도 드러내기

3장에서 배웠듯이 Python은 변수를 선언할 때 자료형을 명시하지 않는 동적 타입 언어다. 이는 유연하다는 장점이 있지만, 함수를 작성한 사람이 아니면 "이 함수가 어떤 자료형을 받고 어떤 자료형을 돌려주는지" 코드만 보고 파악하기 어려울 때가 있다. **타입 힌트(type hint)** 는 이 문제를 완화하기 위해 등장한 문법으로, 변수나 함수의 매개변수·반환값에 "의도한 자료형"을 표시해 준다.

```python
def calculate_total(price: float, quantity: int) -> float:
    """단가와 수량을 받아 총액을 계산한다."""
    return price * quantity


이름: str = "홍길동"
나이: int = 25
점수_목록: list[int] = [90, 85, 100]
```

여기서 `price: float`은 "매개변수 `price`는 실수를 받을 것으로 예상한다"는 뜻이고, `-> float`은 "이 함수는 실수를 반환한다"는 뜻이다. 중요한 것은 타입 힌트가 **강제 사항이 아니라 정보 제공용 표시**라는 점이다. 실제로 `calculate_total("abc", 3)`처럼 호출해도 Python 인터프리터는 실행 시점에 이를 막지 않는다. 타입 힌트만으로는 타입 검사가 실행되지 않는다.

그렇다면 왜 사용할까?

- 코드를 읽는 사람(미래의 자신을 포함해서)이 함수의 사용법을 빠르게 파악할 수 있다.
- 편집기가 자동 완성이나 오타 경고 같은 도움을 더 정확하게 줄 수 있다.
- `mypy`와 같은 별도의 타입 검사 도구를 사용하면, 실행 전에 타입 불일치를 미리 잡아낼 수 있다.

9장에서 배운 함수의 기본값 매개변수와 함께 사용할 수도 있다.

```python
def greet(name: str, greeting: str = "안녕하세요") -> str:
    return f"{greeting}, {name}님!"
```

12장, 13장에서 배운 클래스에도 타입 힌트를 붙일 수 있다.

```python
class Product:
    def __init__(self, name: str, price: float) -> None:
        self.name = name
        self.price = price
```

처음부터 모든 코드에 타입 힌트를 붙일 필요는 없다. 다만 여러 사람이 함께 보는 코드나, 시간이 지난 뒤 다시 보게 될 코드에는 타입 힌트를 붙여 두면 큰 도움이 된다.

## 흔한 실수 정리

여기서는 Python을 배우는 사람들이 특히 자주 걸려 넘어지는 함정 세 가지를 짚어 본다. 모두 각 장에서 다룬 개념과 연결되어 있으니, 필요하면 해당 장을 다시 살펴보자.

### 가변 기본 인자의 함정

9장에서 함수의 기본값 매개변수를 배웠다. 이때 리스트나 딕셔너리처럼 가변(mutable) 객체를 기본값으로 사용하면 예상하지 못한 동작이 발생할 수 있다.

```python
# 문제가 있는 코드
def add_item(item, items=[]):
    items.append(item)
    return items


print(add_item("사과"))   # ['사과']
print(add_item("바나나"))  # ['사과', '바나나']  -- 예상과 다르다!
```

기본값 `[]`는 함수가 정의되는 시점에 **딱 한 번만** 만들어지고, 이후 호출마다 계속 같은 리스트 객체가 재사용된다. 따라서 앞선 호출에서 추가된 내용이 다음 호출에도 그대로 남아 있게 된다. 이는 6장에서 배운 리스트의 가변성과 직결된 문제다.

해결책은 기본값으로 불변(immutable) 객체인 `None`을 사용하고, 함수 본문에서 실제 가변 객체를 새로 만드는 것이다.

```python
# 올바른 코드
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items


print(add_item("사과"))   # ['사과']
print(add_item("바나나"))  # ['바나나']  -- 매번 새 리스트에서 시작
```

### 얕은 복사와 깊은 복사의 혼동

6장과 7장에서 리스트와 딕셔너리 같은 가변 객체를 다룰 때, 변수에 대입하는 것만으로는 복사가 일어나지 않고 같은 객체를 가리키는 또 다른 이름이 생길 뿐이라는 점을 배웠다. 이 특성 때문에 복사를 하려는 의도로 작성한 코드가 원본까지 함께 바꿔 버리는 실수가 자주 발생한다.

```python
원본 = [1, 2, [3, 4]]
복사본 = 원본            # 복사가 아니라 같은 리스트를 가리킴
복사본.append(5)
print(원본)              # [1, 2, [3, 4], 5]  -- 원본도 바뀌어 버렸다
```

리스트를 실제로 복사하려면 슬라이싱(`원본[:]`)이나 `list()`, `copy` 모듈의 `copy()` 함수를 사용할 수 있다. 다만 이런 **얕은 복사(shallow copy)** 는 리스트 자체는 새로 만들지만, 그 안에 들어 있는 가변 객체(위 예의 안쪽 리스트 `[3, 4]`)까지 복사하지는 않는다.

```python
import copy

원본 = [1, 2, [3, 4]]
얕은_복사본 = copy.copy(원본)
얕은_복사본[2].append(99)
print(원본)  # [1, 2, [3, 4, 99]]  -- 안쪽 리스트는 여전히 공유된다!
```

안쪽에 들어 있는 객체까지 완전히 독립적으로 복사하려면 **깊은 복사(deep copy)** 를 사용해야 한다.

```python
깊은_복사본 = copy.deepcopy(원본)
깊은_복사본[2].append(100)
print(원본)  # 영향을 받지 않는다
```

정리하면, 단순 대입(`=`)은 복사가 아니라 이름만 하나 더 생기는 것이고, 얕은 복사는 바깥 컨테이너만 새로 만들며, 깊은 복사는 내부의 모든 객체까지 재귀적으로 새로 만든다. 어느 방식이 필요한지는 다루는 데이터의 구조에 따라 달라지므로, "복사가 잘 안 되는 것 같다"는 버그를 만났을 때는 항상 이 세 가지를 구분해서 점검해 보자.

### 예외를 지나치게 넓게 잡는 습관

11장에서 배운 예외 처리는 프로그램이 예상치 못한 상황에서 갑자기 멈추지 않도록 도와주는 중요한 도구다. 하지만 다음과 같이 모든 예외를 무조건 잡아서 조용히 넘겨 버리는 코드는 오히려 문제를 숨기는 결과를 낳는다.

```python
# 피해야 할 코드
try:
    결과 = 10 / 사용자_입력
except:
    pass  # 무슨 예외가 발생했는지 전혀 알 수 없다
```

이렇게 작성하면 `ZeroDivisionError`뿐 아니라 오타로 인한 `NameError`나 프로그램을 강제로 멈추기 위한 `KeyboardInterrupt`까지도 조용히 삼켜 버려서, 정작 고쳐야 할 버그를 찾기가 몹시 어려워진다. 대신 예상되는 예외의 종류를 구체적으로 지정하고, 필요하다면 로그라도 남기는 것이 좋다.

```python
# 개선된 코드
try:
    결과 = 10 / 사용자_입력
except ZeroDivisionError:
    print("0으로 나눌 수 없습니다.")
    결과 = None
```

"예외 처리를 했다"는 것과 "문제를 안전하게 처리했다"는 것은 다르다는 점을 기억하자. `except` 뒤에 예외 종류를 명시하는 습관만으로도 코드의 신뢰도가 크게 올라간다.

## 디버깅의 기본기

아무리 조심해서 작성해도 버그는 생기기 마련이다. 정교한 도구 없이도 문제의 원인을 좁혀 나가는 방법 몇 가지를 소개한다.

### print로 상태 확인하기

가장 단순하면서도 효과적인 방법은 의심되는 지점에 `print`문을 넣어 변수의 값이 예상대로 바뀌고 있는지 눈으로 확인하는 것이다.

```python
def calculate_discount(price, rate):
    print(f"입력값 확인 - price: {price}, rate: {rate}")  # 디버깅용 출력
    discount = price * rate
    print(f"계산된 할인액: {discount}")                     # 디버깅용 출력
    return price - discount
```

이 방법은 즉시 적용할 수 있다는 장점이 있지만, 문제를 해결한 뒤에는 디버깅용 `print`문을 반드시 지우거나 주석 처리해야 한다는 점을 잊지 말자.

### 예외 메시지를 끝까지 읽기

11장에서 다룬 것처럼 예외가 발생하면 Python은 **트레이스백(traceback)** 이라는 정보를 출력한다. 트레이스백은 오류가 어느 파일의 몇 번째 줄에서, 어떤 함수를 거쳐 발생했는지를 순서대로 보여 주는 지도와 같다. 오류 메시지의 맨 아랫줄에 있는 예외 종류와 설명뿐 아니라, 그 위에 나열된 호출 경로도 함께 읽는 습관을 들이면 문제의 원인을 훨씬 빠르게 찾을 수 있다. 표준 라이브러리의 `traceback` 모듈을 사용하면 예외를 처리하는 코드 안에서도 이 정보를 원하는 형태로 출력하거나 파일에 기록할 수 있다.

### logging으로 기록 남기기

작은 스크립트에서는 `print` 디버깅으로 충분하지만, 프로그램이 커지고 오래 실행되는 서비스가 되면 "언제, 어디서, 무슨 일이 있었는지"를 체계적으로 기록해 둘 필요가 생긴다. 이럴 때 사용하는 것이 표준 라이브러리의 `logging` 모듈이다.

```python
import logging

logging.basicConfig(level=logging.INFO)

logging.info("프로그램을 시작합니다.")
logging.warning("설정 파일을 찾지 못해 기본값을 사용합니다.")
logging.error("데이터베이스 연결에 실패했습니다.")
```

`logging`은 `print`와 달리 메시지의 중요도(정보, 경고, 오류 등)를 구분할 수 있고, 필요에 따라 출력 위치를 화면이 아닌 파일로 바꿀 수도 있다. 지금 당장 모든 세부 기능을 익힐 필요는 없지만, "프로그램이 커지면 print 대신 logging을 쓴다"는 방향성 정도는 기억해 두면 좋다.

## 테스트의 필요성

지금까지는 작성한 코드가 제대로 동작하는지 직접 실행하고 눈으로 결과를 확인하는 방식에 의존해 왔다. 이 방식은 코드가 작을 때는 문제가 없지만, 프로그램이 커지고 함수 사이의 관계가 복잡해지면 "예전에는 잘 되던 기능이 새 코드를 추가한 뒤 조용히 망가지는" 상황이 자주 발생한다.

**테스트(test)** 는 이런 문제를 예방하기 위해, 함수나 클래스가 의도한 대로 동작하는지를 검증하는 코드를 별도로 작성해 두는 방법이다. 예를 들어 다음과 같은 함수가 있다고 하자.

```python
def add(a, b):
    return a + b
```

이 함수가 제대로 동작하는지 확인하는 테스트 코드는 대략 다음과 같은 모양이 된다.

```python
def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
    assert add(0, 0) == 0
```

`assert`문은 조건이 참이 아니면 예외를 발생시키는 문장으로, "이 조건은 반드시 참이어야 한다"는 것을 코드로 표현하는 방법이다. 이렇게 테스트를 미리 만들어 두면, 나중에 `add` 함수를 수정했을 때 테스트를 다시 실행해 보는 것만으로 "기존 기능이 여전히 잘 동작하는가"를 빠르게 확인할 수 있다.

직접 `assert`문을 나열하는 대신, Python은 테스트 작성과 실행을 체계적으로 도와주는 도구를 제공한다. 표준 라이브러리에는 `unittest` 모듈이 포함되어 있고, 외부 패키지로는 `pytest`가 널리 사용된다. 두 도구 모두 여러 개의 테스트를 자동으로 찾아 실행하고, 어떤 테스트가 통과했고 어떤 테스트가 실패했는지를 정리해서 보여 준다. 지금 단계에서는 이런 도구가 "존재한다"는 것과 "왜 필요한지"만 기억해 두어도 충분하며, 실제 사용법은 다음 학습 단계에서 자연스럽게 익히게 될 것이다.

## 다음 학습 단계

이 책에서는 Python 언어의 문법과 기본적인 코드 작성 습관을 다루었다. 이제 이 지식을 바탕으로 실제 문제를 해결하는 방향으로 학습을 넓혀 갈 차례다. 관심사에 따라 다음과 같은 방향을 고려해 볼 수 있다.

- **웹 개발**: 웹사이트나 API 서버를 만들고 싶다면 웹 프레임워크를 학습해서 요청을 처리하고 데이터베이스와 연동하는 방법을 익힐 수 있다.
- **데이터 분석과 시각화**: 표나 그래프 형태의 데이터를 다루고 싶다면 데이터 처리와 시각화를 위한 라이브러리들을 학습해서 대량의 데이터를 정리하고 통찰을 뽑아내는 방법을 익힐 수 있다.
- **자동화와 스크립팅**: 반복적인 작업(파일 정리, 웹 페이지 정보 수집, 문서 생성 등)을 자동화하는 스크립트를 작성하며 15장에서 배운 파일 입출력과 17장에서 배운 표준 라이브러리 활용 능력을 실전에서 발전시킬 수 있다.
- **비동기 프로그래밍**: 네트워크 요청이나 파일 입출력처럼 대기 시간이 긴 작업을 여러 개 동시에 처리해야 한다면, Python이 제공하는 비동기 프로그래밍 문법을 학습해서 프로그램의 응답성과 처리량을 높이는 방법을 익힐 수 있다.
- **테스트와 코드 품질**: 이 장에서 소개한 테스트 도구를 실제로 사용해 보면서, 코드를 안전하게 수정하고 확장하는 습관을 몸에 익힐 수 있다.

어떤 방향을 택하든 이 책에서 다진 변수, 자료형, 제어문, 함수, 클래스, 예외 처리, 모듈이라는 기본기는 그대로 이어져 사용된다. 새로운 분야를 학습할 때 낯선 용어나 도구를 만나더라도, 결국 그 밑바탕에는 지금까지 익힌 Python 문법이 자리 잡고 있다는 사실을 기억하면 큰 도움이 될 것이다.

## 요약

- PEP 8은 Python 코드의 스타일을 통일하기 위한 가이드라인으로, 들여쓰기, 공백, 이름 짓기 규칙 등을 규정한다.
- 타입 힌트는 변수와 함수의 예상 자료형을 코드에 표시하는 문법으로, 실행을 강제하지는 않지만 가독성과 도구 지원을 크게 향상시킨다.
- 가변 기본 인자, 얕은 복사와 깊은 복사의 혼동, 지나치게 넓은 예외 처리는 초보자가 자주 저지르는 대표적인 실수다.
- `print` 디버깅, 트레이스백 읽기, `logging` 모듈은 문제의 원인을 찾는 데 도움이 되는 기본적인 도구다.
- 테스트는 코드가 의도대로 동작하는지 검증하는 코드로, `unittest`나 `pytest` 같은 도구를 사용해 체계적으로 작성하고 실행할 수 있다.
- 이 책을 마친 뒤에는 웹 개발, 데이터 분석, 자동화, 비동기 프로그래밍 등 관심 있는 분야로 학습을 확장해 나갈 수 있다.

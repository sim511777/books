## 들어가며

12장 클래스와 객체지향 기초에서 우리는 `class` 키워드로 클래스를 정의하고, `__init__`으로 인스턴스를 초기화하며, 인스턴스 속성과 메서드를 다루고, 상속을 이용해 기존 클래스의 기능을 물려받는 방법까지 배웠습니다. 이번 장에서는 그 위에 네 가지 주제를 더 쌓아 올립니다.

- 클래스를 Python다운 방식으로 자연스럽게 동작하게 만드는 **매직 메서드**
- 속성에 대한 접근을 통제하는 **프로퍼티(@property)**
- 여러 클래스의 기능을 동시에 물려받는 **다중 상속과 MRO**
- Python이 인터페이스를 강제하지 않는 이유인 **덕 타이핑**

이 네 주제는 서로 독립적으로 보이지만, 결국 하나의 질문으로 수렴합니다. "어떻게 하면 내가 만든 클래스가 Python이 원래 제공하는 자료형들(문자열, 리스트, 숫자 등)처럼 자연스럽고 예측 가능하게 동작하도록 만들 수 있을까?"라는 질문입니다.

먼저 12장에서 만들었던 것과 같은 형태의 은행 계좌 클래스를 다시 가져와서 이야기를 시작하겠습니다. 아직 이 장의 기법들이 적용되지 않은, "기초적인" 형태입니다.

```python
class BankAccount:
    """은행 계좌 하나를 표현하는 클래스"""

    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        """계좌에 amount만큼 입금한다"""
        self.balance += amount

    def withdraw(self, amount):
        """계좌에서 amount만큼 출금한다"""
        if amount > self.balance:
            raise ValueError("잔액이 부족합니다.")
        self.balance -= amount
```

이 클래스는 잘 동작합니다. 그런데 인터프리터에서 인스턴스를 직접 출력해보면 다음과 같은 결과가 나옵니다.

```python
>>> account = BankAccount("김철수", 10000)
>>> account
<__main__.BankAccount object at 0x000001F2A3B4C5D0>
>>> print(account)
<__main__.BankAccount object at 0x000001F2A3B4C5D0>
```

객체가 잘 만들어지긴 했지만, 이 출력만 봐서는 이 계좌가 누구의 것인지, 잔액이 얼마인지 전혀 알 수 없습니다. 반면 리스트나 문자열은 다릅니다.

```python
>>> numbers = [1, 2, 3]
>>> numbers
[1, 2, 3]
>>> print(numbers)
[1, 2, 3]
```

리스트는 자기 자신을 사람이 알아볼 수 있는 형태로 표현할 줄 압니다. 우리가 만든 `BankAccount`도 이렇게 만들 수 없을까요? 바로 이 질문에 대한 답이 매직 메서드입니다.

## 매직 메서드란 무엇인가

Python에서 `__init__`처럼 앞뒤로 밑줄 두 개가 붙은 메서드를 **매직 메서드**(magic method)라고 부릅니다. "던더 메서드(dunder method, double underscore method)"라고도 부릅니다. 매직 메서드는 우리가 직접 호출하려고 만드는 것이 아닙니다. 대신 특정 상황(객체를 출력할 때, 두 객체를 `==`로 비교할 때, 객체에 `len()`을 호출할 때 등)에서 Python 인터프리터가 **자동으로** 찾아서 호출해주는 메서드입니다.

이 구조를 Python에서는 "데이터 모델(data model)"이라고 부릅니다. 즉 `print(account)`라는 코드는 사실 내부적으로 `account.__str__()`을 호출하고 그 결과를 화면에 찍는 것이고, `len(numbers)`라는 코드는 내부적으로 `numbers.__len__()`을 호출하는 것입니다. 우리가 클래스에 이런 메서드를 정의해두면, 우리가 만든 객체도 Python의 내장 함수와 연산자들이 자연스럽게 이해하는 대상이 됩니다.

### 객체를 문자열로 표현하기: `__str__`와 `__repr__`

가장 먼저 배울 매직 메서드는 `__str__`과 `__repr__`입니다. 둘 다 객체를 문자열로 표현하는 역할을 하지만, 용도가 다릅니다.

- `__str__`: `print()`나 `str()`로 객체를 사람이 보기 좋게 표현할 때 사용됩니다. **사용자를 위한** 표현입니다.
- `__repr__`: 인터프리터에서 값을 그대로 출력하거나 `repr()`을 호출할 때, 그리고 `__str__`이 정의되어 있지 않을 때 대신 사용됩니다. **개발자를 위한** 표현으로, 이상적으로는 이 문자열을 다시 코드로 실행했을 때 똑같은 객체를 만들 수 있을 정도로 명확해야 합니다.

`BankAccount`에 두 메서드를 추가해봅시다.

```python
class BankAccount:
    """은행 계좌 하나를 표현하는 클래스"""

    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("잔액이 부족합니다.")
        self.balance -= amount

    def __str__(self):
        # print(account)나 str(account)를 호출했을 때 보여줄 형태
        return f"{self.owner}님의 계좌 (잔액: {self.balance:,}원)"

    def __repr__(self):
        # 인터프리터 콘솔이나 디버깅 상황에서 보여줄 형태
        return f"BankAccount(owner={self.owner!r}, balance={self.balance!r})"
```

이제 결과가 완전히 달라집니다.

```python
>>> account = BankAccount("김철수", 10000)
>>> print(account)
김철수님의 계좌 (잔액: 10,000원)
>>> account
BankAccount(owner='김철수', balance=10000)
>>> str(account)
'김철수님의 계좌 (잔액: 10,000원)'
>>> repr(account)
"BankAccount(owner='김철수', balance=10000)"
```

여기서 `!r`은 f-string 안에서 `repr()`을 적용하라는 표시입니다. 문자열 값이었을 때 따옴표까지 포함해서 보여주므로, `__repr__`의 목적(코드로 재현 가능한 표현)에 잘 맞습니다.

두 메서드 중 하나만 정의해야 한다면 `__repr__`을 우선 정의하는 것이 일반적인 관례입니다. `__str__`이 없으면 Python은 자동으로 `__repr__`을 대신 사용하기 때문입니다. 반대의 경우는 성립하지 않습니다. `__str__`만 정의하면 `repr(account)`를 호출했을 때는 여전히 기본 형태(`<__main__.BankAccount object at ...>`)가 나옵니다.

### 값으로 비교하기: `__eq__`

기본적으로 클래스로 만든 객체 두 개를 `==`로 비교하면, 두 객체가 "같은 것을 의미하는지"가 아니라 "메모리상 완전히 동일한 객체인지"를 비교합니다.

```python
>>> a = BankAccount("김철수", 10000)
>>> b = BankAccount("김철수", 10000)
>>> a == b
False
>>> a == a
True
```

`a`와 `b`는 주인도 같고 잔액도 같지만, 서로 다른 객체이기 때문에 `False`가 나옵니다. 이런 기본 동작을 "정체성 비교(identity comparison)"라고 하며, 사실 `a is b`와 같은 결과를 냅니다. 만약 "주인과 잔액이 같으면 같은 계좌로 취급한다"는 규칙을 적용하고 싶다면 `__eq__` 메서드를 직접 정의해야 합니다.

```python
class BankAccount:
    # ... __init__, deposit, withdraw, __str__, __repr__ 생략 ...

    def __eq__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.owner == other.owner and self.balance == other.balance
```

```python
>>> a = BankAccount("김철수", 10000)
>>> b = BankAccount("김철수", 10000)
>>> c = BankAccount("이영희", 5000)
>>> a == b
True
>>> a == c
False
```

`isinstance(other, BankAccount)` 검사를 넣은 이유는, 비교 대상이 아예 다른 자료형(예: 정수나 문자열)일 때 `AttributeError`를 일으키지 않고 안전하게 "비교할 수 없다"는 뜻의 `NotImplemented`를 반환하기 위해서입니다. `NotImplemented`를 반환하면 Python은 상대방 자료형에게 비교를 다시 시도해보고, 그래도 안 되면 최종적으로 `False`로 처리합니다.

한 가지 기억해둘 점은, `__eq__`를 정의하면 그 클래스의 인스턴스는 더 이상 기본적으로 해시 가능(hashable)하지 않게 된다는 것입니다. 즉 `set`에 넣거나 딕셔너리의 키로 사용할 수 없게 됩니다(7장 딕셔너리와 셋 참고). 해시 가능하게 유지하고 싶다면 `__hash__`도 함께 정의해주어야 합니다.

### 길이를 갖는 객체처럼 만들기: `__len__`

`len()` 함수는 문자열, 리스트, 딕셔너리 등에 사용할 수 있습니다. 이 함수 역시 내부적으로는 `__len__` 메서드를 호출하는 것뿐이므로, 우리 클래스에도 "길이"라는 개념이 있다면 정의해볼 수 있습니다.

예를 들어 계좌에 거래 내역을 기록하는 기능을 추가하고, 거래 건수를 `len()`으로 확인할 수 있게 만들어보겠습니다.

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance
        self.history = []  # 거래 내역을 저장하는 리스트

    def deposit(self, amount):
        self.balance += amount
        self.history.append(f"입금 {amount:,}원")

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("잔액이 부족합니다.")
        self.balance -= amount
        self.history.append(f"출금 {amount:,}원")

    def __len__(self):
        # 지금까지 발생한 거래 건수를 길이로 취급한다
        return len(self.history)
```

```python
>>> account = BankAccount("김철수", 10000)
>>> account.deposit(5000)
>>> account.withdraw(2000)
>>> len(account)
2
```

`__len__`을 정의하면 부수적으로 얻는 이점이 하나 더 있습니다. `if account:`처럼 객체를 불리언 문맥에서 사용했을 때, `__bool__`이 따로 정의되어 있지 않으면 Python은 `__len__`의 결과가 0이면 `False`, 0이 아니면 `True`로 판단합니다. 거래 내역이 하나도 없는 계좌를 "비어 있다"고 취급하고 싶다면 이 동작이 자연스럽게 맞아떨어집니다.

### 크기를 비교하는 객체: `__lt__`와 정렬

계좌들을 잔액 순서로 정렬하고 싶다면 어떻게 해야 할까요? `<` 연산자에 대응하는 매직 메서드는 `__lt__`(less than)입니다.

```python
class BankAccount:
    # ... 생략 ...

    def __lt__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.balance < other.balance
```

```python
>>> accounts = [
...     BankAccount("김철수", 10000),
...     BankAccount("이영희", 5000),
...     BankAccount("박민수", 30000),
... ]
>>> for account in sorted(accounts):
...     print(account)
...
이영희님의 계좌 (잔액: 5,000원)
김철수님의 계좌 (잔액: 10,000원)
박민수님의 계좌 (잔액: 30,000원)
```

`sorted()` 내장 함수는 리스트 안의 원소들을 서로 비교해야 하는데, 이때 `__lt__`가 정의되어 있으면 그 기준으로 정렬합니다. `<=`, `>`, `>=`까지 모두 지원하고 싶다면 각각 `__le__`, `__gt__`, `__ge__`를 추가로 정의해야 하지만, 매번 이렇게 4개를 다 작성하는 것은 번거롭습니다. 표준 라이브러리의 `functools.total_ordering` 데코레이터를 사용하면 `__eq__`와 `__lt__` 두 개만 정의해도 나머지를 자동으로 채워줍니다. 데코레이터의 자세한 원리는 16장 데코레이터와 컨텍스트 매니저에서 다룹니다.

```python
from functools import total_ordering


@total_ordering
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def __eq__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.balance == other.balance

    def __lt__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.balance < other.balance
```

```python
>>> a = BankAccount("김철수", 10000)
>>> b = BankAccount("박민수", 30000)
>>> a < b
True
>>> a >= b
False
>>> a <= b
True
```

### 연산자 오버로딩: `__add__`

`+` 연산자에 대응하는 매직 메서드는 `__add__`입니다. 두 계좌를 합쳐서 새로운 계좌를 만드는 상황을 가정해보겠습니다.

```python
class BankAccount:
    # ... 생략 ...

    def __add__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        merged_owner = f"{self.owner}&{other.owner}"
        return BankAccount(merged_owner, self.balance + other.balance)
```

```python
>>> a = BankAccount("김철수", 10000)
>>> b = BankAccount("이영희", 5000)
>>> merged = a + b
>>> print(merged)
김철수&이영희님의 계좌 (잔액: 15,000원)
```

이처럼 `+`, `-`, `*` 같은 연산자를 직접 정의한 클래스에 맞게 재정의하는 것을 **연산자 오버로딩**(operator overloading)이라고 부릅니다. 사실 우리는 이미 이 개념을 알게 모르게 경험해왔습니다. `1 + 2`는 숫자를 더하지만 `"a" + "b"`는 문자열을 이어붙이고 `[1] + [2]`는 리스트를 합칩니다. 모두 각 자료형이 `__add__`를 자신의 목적에 맞게 정의해두었기 때문에 가능한 일입니다.

### 자주 쓰이는 매직 메서드 정리

지금까지 다룬 것 외에도 Python에는 다양한 매직 메서드가 있습니다. 자주 쓰이는 것들을 표로 정리합니다.

| 매직 메서드 | 호출되는 시점 | 예시 |
|---|---|---|
| `__init__` | 인스턴스를 생성할 때 | `BankAccount("김철수")` |
| `__str__` | `str()`, `print()`를 호출할 때 | `print(account)` |
| `__repr__` | `repr()`, 인터프리터 출력, `__str__`이 없을 때 | `account` |
| `__eq__` | `==` 연산자 | `a == b` |
| `__lt__` | `<` 연산자, `sorted()`, `min()` | `a < b` |
| `__len__` | `len()` 함수 | `len(account)` |
| `__add__` | `+` 연산자 | `a + b` |
| `__contains__` | `in` 연산자 | `x in account` |
| `__getitem__` | `account[key]` 형태의 인덱싱 | `account[0]` |
| `__iter__` | `for` 문, `iter()` 함수 | `for x in account:` |
| `__call__` | 객체를 함수처럼 호출할 때 | `account()` |

`__iter__`는 10장 컴프리헨션과 제너레이터에서 살펴본 이터레이터 프로토콜과 직접 연결되는 매직 메서드입니다. 클래스에 `__iter__`를 정의하면 그 클래스의 인스턴스를 `for` 문으로 순회할 수 있게 됩니다. 모든 매직 메서드를 외울 필요는 없습니다. "이런 연산을 내 클래스에도 자연스럽게 쓰고 싶다"는 필요가 생길 때, 그에 대응하는 매직 메서드를 찾아 정의하면 됩니다.

## 프로퍼티(@property)로 접근 제어하기

### 속성을 직접 노출하면 생기는 문제

지금까지 만든 `BankAccount`는 `balance` 속성에 누구나 직접 접근하고, 직접 값을 바꿀 수 있습니다.

```python
>>> account = BankAccount("김철수", 10000)
>>> account.balance = -999999
>>> account.balance
-999999
```

`deposit`과 `withdraw` 메서드는 잔액이 음수가 되지 않도록 검사하지만, `account.balance = -999999`처럼 속성에 직접 값을 대입하면 이런 검사를 완전히 우회할 수 있습니다. 클래스를 설계한 사람 입장에서는 매우 곤란한 상황입니다. 아무리 메서드를 잘 만들어도, 속성을 직접 조작하는 길이 열려 있으면 클래스가 스스로 지키려 했던 규칙(불변식, invariant)이 무너집니다.

다른 언어(Java, C++ 등)에서는 이런 문제를 속성을 `private`으로 감추고, `getBalance()`, `setBalance()` 같은 별도의 메서드로만 접근하게 만드는 방식으로 해결합니다. Python에서도 비슷한 결과를 얻을 수 있지만, 훨씬 Python다운 방법이 있습니다. 바로 `@property`입니다.

### `@property`로 getter 만들기

먼저 속성 이름 앞에 밑줄을 하나 붙여 "내부용"임을 표시하는 관례부터 짚고 넘어가겠습니다. 12장에서 살짝 언급했듯이, Python에는 진짜 `private` 키워드가 없습니다. 대신 다음과 같은 네이밍 관례로 의도를 표현합니다.

- `_balance`: 밑줄 한 개. "이 속성은 클래스 내부용이니 외부에서 직접 건드리지 말아 달라"는 **관례상의 신호**일 뿐, 실제로 접근을 막지는 않습니다.
- `__balance`: 밑줄 두 개. "이름 맹글링(name mangling)"이 적용되어 실제로는 `_BankAccount__balance`라는 이름으로 저장됩니다. 실수로 하위 클래스가 같은 이름의 속성을 덮어쓰는 사고를 방지하는 용도이며, 완전한 접근 차단은 아닙니다.

이제 `balance`를 내부적으로는 `_balance`라는 이름으로 저장하고, `@property`를 이용해 값을 읽는 통로를 만들어보겠습니다.

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance  # 내부 저장용 속성

    @property
    def balance(self):
        """현재 잔액을 반환한다"""
        return self._balance
```

```python
>>> account = BankAccount("김철수", 10000)
>>> account.balance
10000
```

여기서 중요한 점은, `account.balance`를 사용할 때 `account.balance()`처럼 괄호를 붙이지 않는다는 것입니다. `@property`가 붙은 메서드는 마치 일반 속성처럼 괄호 없이 접근합니다. 겉보기에는 평범한 속성이지만, 실제로는 메서드가 실행되어 값을 계산해서 돌려주는 것입니다.

### `@이름.setter`로 값 검증하기

지금 상태에서 `account.balance = -999999`를 시도하면 어떻게 될까요?

```python
>>> account.balance = -999999
Traceback (most recent call last):
  ...
AttributeError: property 'balance' of 'BankAccount' object has no setter
```

`@property`만 정의하면 그 속성은 기본적으로 **읽기 전용**이 됩니다. 값을 대입할 수 있게 하려면 같은 이름으로 `setter`를 별도로 정의해야 합니다. 이때 검증 로직을 끼워 넣을 수 있습니다.

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance

    @property
    def balance(self):
        """현재 잔액을 반환한다"""
        return self._balance

    @balance.setter
    def balance(self, value):
        """잔액을 설정한다. 음수는 허용하지 않는다"""
        if value < 0:
            raise ValueError("잔액은 음수가 될 수 없습니다.")
        self._balance = value
```

```python
>>> account = BankAccount("김철수", 10000)
>>> account.balance = 20000
>>> account.balance
20000
>>> account.balance = -500
Traceback (most recent call last):
  ...
ValueError: 잔액은 음수가 될 수 없습니다.
```

`@balance.setter`라는 문법이 낯설게 보일 수 있는데, 여기서 `balance`는 바로 위에서 `@property`로 정의한 그 메서드를 가리킵니다. `@property`가 반환하는 객체는 `.setter`라는 데코레이터를 추가로 제공하고, 그 데코레이터를 이용해 "같은 이름에 대한 대입 동작"을 등록하는 방식입니다. 데코레이터가 어떻게 동작하는지 원리 자체가 궁금하다면 16장 데코레이터와 컨텍스트 매니저에서 자세히 다룹니다. 지금은 "이 두 메서드가 짝을 이루어 `balance`라는 하나의 속성처럼 보이게 만든다" 정도로 이해하면 충분합니다.

이 구조의 가장 큰 장점은, 클래스를 사용하는 쪽 코드는 전혀 바뀌지 않는다는 것입니다. `account.balance`로 읽고 `account.balance = 값`으로 쓰는 코드는 `@property`를 도입하기 전이나 후나 똑같습니다. 즉 이미 공개 속성으로 설계했던 클래스도, 나중에 검증 로직이 필요해지면 기존 사용자 코드를 전혀 건드리지 않고 프로퍼티로 바꿔치기할 수 있습니다. 이것이 Java 같은 언어에서 애초부터 모든 속성을 `private`으로 감추고 getter/setter로 시작하는 것과 Python이 다른 지점입니다. Python에서는 "일단 평범한 속성으로 시작하고, 정말 필요해지면 그때 프로퍼티로 바꾼다"는 실용적인 접근이 자연스럽습니다.

### 읽기 전용 프로퍼티

setter를 정의하지 않으면 자동으로 읽기 전용 속성이 됩니다. 예를 들어 계좌 개설 후 경과 일수처럼, 외부에서 임의로 바꿀 수 없어야 하는 값에 적합합니다.

```python
import datetime


class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
        self._opened_at = datetime.date.today()

    @property
    def days_since_opened(self):
        """계좌 개설 후 경과 일수 (계산해서 보여주기만 하는 읽기 전용 프로퍼티)"""
        return (datetime.date.today() - self._opened_at).days
```

```python
>>> account = BankAccount("김철수", 10000)
>>> account.days_since_opened
0
>>> account.days_since_opened = 100
Traceback (most recent call last):
  ...
AttributeError: property 'days_since_opened' of 'BankAccount' object has no setter
```

`days_since_opened`는 저장된 값이 아니라 호출할 때마다 새로 계산되는 값입니다. 이렇게 "저장된 데이터처럼 보이지만 실제로는 계산 결과"인 속성을 만들 수 있다는 것도 프로퍼티의 중요한 활용법입니다. `datetime` 모듈은 15장 파일 입출력과 17장 표준 라이브러리와 패키지 관리에서 조금 더 자세히 다룰 날짜·시간 처리용 표준 라이브러리입니다.

## 다중 상속과 MRO

### 믹스인이라는 아이디어

12장에서 배운 상속은 클래스 하나가 부모 클래스 하나로부터 물려받는 형태(단일 상속)였습니다. Python은 여기서 한 걸음 더 나아가, 클래스 하나가 **여러 부모 클래스**로부터 동시에 상속받는 **다중 상속**을 허용합니다.

다중 상속이 유용한 대표적인 상황은 "서로 다른 역할을 하는 기능 조각을 조립하는" 경우입니다. 이런 기능 조각을 **믹스인(mixin) 클래스**라고 부릅니다. 믹스인은 그 자체로 완전한 개체를 나타내기 위한 것이 아니라, 다른 클래스에 특정 기능을 "섞어 넣기(mix in)" 위한 목적으로 설계된 작은 클래스입니다.

```python
class Swimmer:
    """헤엄칠 수 있는 능력을 제공하는 믹스인"""

    def swim(self):
        return f"{self.name}이(가) 헤엄칩니다."


class Flyer:
    """날 수 있는 능력을 제공하는 믹스인"""

    def fly(self):
        return f"{self.name}이(가) 날아갑니다."


class Duck(Swimmer, Flyer):
    """오리는 헤엄도 치고 날기도 한다"""

    def __init__(self, name):
        self.name = name
```

```python
>>> donald = Duck("도널드")
>>> donald.swim()
'도널드이(가) 헤엄칩니다.'
>>> donald.fly()
'도널드이(가) 날아갑니다.'
```

`Duck` 클래스는 `Swimmer`와 `Flyer` 두 클래스를 모두 부모로 두었기 때문에, 두 클래스가 제공하는 메서드를 모두 사용할 수 있습니다. 마치 레고 블록을 조립하듯, 필요한 능력을 가진 믹스인들을 조합해서 새로운 클래스를 만드는 방식입니다.

### 다이아몬드 문제와 MRO

다중 상속에는 한 가지 까다로운 상황이 있습니다. 아래 그림처럼 두 부모 클래스가 다시 하나의 공통 조상 클래스를 상속하고 있다면 어떻게 될까요?

```text
                        다중 상속의 다이아몬드 구조

                          +----------+
                          |  Animal  |
                          +----------+
                           ^        ^
                           |        |
              class Swimmer(Animal) |
                           |        |    class Flyer(Animal)
                           |        |
                     +----------+ +----------+
                     | Swimmer  | |  Flyer   |
                     +----------+ +----------+
                           ^        ^
                           |        |
                           +--------+
                           |        |
                     class Duck(Swimmer, Flyer)
                           |
                        +--------+
                        |  Duck  |
                        +--------+

     MRO 순서: Duck -> Swimmer -> Flyer -> Animal -> object
```

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"{self.name}은(는) 동물입니다."


class Swimmer(Animal):
    def describe(self):
        return f"{self.name}은(는) 헤엄치는 동물입니다."


class Flyer(Animal):
    def describe(self):
        return f"{self.name}은(는) 나는 동물입니다."


class Duck(Swimmer, Flyer):
    pass
```

`Duck` 인스턴스에서 `describe()`를 호출하면 어느 클래스의 `describe()`가 실행될까요? `Swimmer`의 것일까요, `Flyer`의 것일까요? 이런 상황을 흔히 **다이아몬드 문제**라고 부릅니다. `Animal`이라는 하나의 꼭짓점에서 시작해서 `Swimmer`와 `Flyer`로 갈라졌다가, 다시 `Duck`이라는 꼭짓점으로 합쳐지는 모양이 마름모(다이아몬드)를 닮았기 때문입니다.

Python은 이 상황을 **MRO**(Method Resolution Order, 메서드 결정 순서)라는 규칙으로 해결합니다. MRO는 "어떤 메서드를 찾을 때 부모 클래스들을 어떤 순서로 검색할 것인가"를 정해놓은 목록입니다. `__mro__` 속성이나 `mro()` 메서드로 직접 확인할 수 있습니다.

```python
>>> Duck.__mro__
(<class '__main__.Duck'>, <class '__main__.Swimmer'>, <class '__main__.Flyer'>, <class '__main__.Animal'>, <class 'object'>)
>>> donald = Duck("도널드")
>>> donald.describe()
'도널드은(는) 헤엄치는 동물입니다.'
```

MRO 결과를 보면 `Duck → Swimmer → Flyer → Animal → object` 순서입니다. `class Duck(Swimmer, Flyer):`라고 작성할 때 **괄호 안에 나열한 순서**(`Swimmer`를 먼저, `Flyer`를 나중에)가 그대로 검색 우선순위가 됩니다. 그래서 `Swimmer`에 정의된 `describe()`가 먼저 발견되어 실행된 것입니다.

Python은 이 순서를 정할 때 **C3 선형화(C3 linearization)**라는 알고리즘을 사용합니다. 핵심 규칙만 요약하면 다음과 같습니다.

- 자식 클래스는 항상 부모 클래스보다 먼저 검색된다.
- 여러 부모가 나열되어 있다면, `class Duck(Swimmer, Flyer):`에 작성한 순서를 그대로 존중한다.
- 모든 클래스의 최상위 조상인 `object`는 항상 맨 마지막에 온다.

이 알고리즘의 수학적 세부 사항까지 외울 필요는 없습니다. 실무에서 중요한 것은 "다중 상속을 사용할 때는 괄호 안에 나열하는 부모 클래스의 순서가 실제 동작에 영향을 준다"는 사실과, 헷갈릴 때는 언제든 `__mro__`로 실제 순서를 확인할 수 있다는 사실입니다.

### `super()`의 협력적 동작

다중 상속 환경에서 `super()`는 단순히 "바로 위 부모"를 가리키는 것이 아니라, **MRO 순서상 다음 클래스**를 가리킵니다. 각 클래스가 자기 몫의 처리를 하고 `super().메서드()`로 다음 순서에게 넘겨주면, 결과적으로 MRO에 나열된 모든 클래스가 한 번씩 협력적으로 실행될 수 있습니다.

```python
class Animal:
    def __init__(self, name):
        self.name = name
        print(f"Animal.__init__ 실행: {name}")


class Swimmer(Animal):
    def __init__(self, name):
        super().__init__(name)
        print("Swimmer.__init__ 실행")


class Flyer(Animal):
    def __init__(self, name):
        super().__init__(name)
        print("Flyer.__init__ 실행")


class Duck(Swimmer, Flyer):
    def __init__(self, name):
        super().__init__(name)
        print("Duck.__init__ 실행")
```

```python
>>> donald = Duck("도널드")
Animal.__init__ 실행: 도널드
Flyer.__init__ 실행
Swimmer.__init__ 실행
Duck.__init__ 실행
```

실행 순서를 보면 흥미로운 점이 있습니다. `Duck.__init__`이 `super().__init__(name)`을 호출하면 MRO 순서상 다음인 `Swimmer.__init__`으로 넘어가고, `Swimmer.__init__`이 다시 `super().__init__(name)`을 호출하면 그다음인 `Flyer.__init__`으로 넘어가며, `Flyer.__init__`이 마지막으로 `Animal.__init__`을 호출합니다. 각 클래스는 "내 바로 위 부모"가 아니라 "MRO상의 다음 차례"를 호출하는 셈입니다. 그 결과 `Animal.__init__`이 가장 먼저 실행되고, 이후 MRO의 역순으로 각 클래스의 나머지 코드(print문)가 실행됩니다.

다중 상속과 MRO는 알아두면 유용하지만, 남용하면 코드의 흐름을 파악하기 어렵게 만드는 대표적인 원인이기도 합니다. 실무에서는 "여러 기능을 조합하는 작고 명확한 믹스인" 용도로 제한적으로 사용하는 것이 안전합니다. 복잡한 클래스 계층을 다중 상속으로 얽어놓기보다는, 다음 절에서 다룰 덕 타이핑처럼 더 유연한 방식이 더 나은 선택일 때도 많습니다.

## 덕 타이핑

### "오리처럼 걷고 오리처럼 운다면"

Java나 C# 같은 언어에서는 어떤 객체가 특정 기능을 지원하는지 확인하려면, 그 객체가 명시적으로 특정 **인터페이스**를 구현했다고 선언해야 합니다. 예를 들어 "소리를 낼 수 있는 모든 것"을 다루는 함수를 만들려면, `Speakable`이라는 인터페이스를 정의하고 모든 대상 클래스가 `implements Speakable`이라고 명시해야 합니다.

Python에는 이런 형태의 강제 규칙이 없습니다. 대신 다음과 같은 격언으로 요약되는 철학을 따릅니다.

> "오리처럼 걷고, 오리처럼 소리를 낸다면, 그것은 오리다."

즉 어떤 객체가 정확히 어떤 클래스인지, 또는 어떤 인터페이스를 명시적으로 선언했는지는 중요하지 않습니다. 그 객체가 필요한 메서드나 속성을 실제로 가지고 있어서 원하는 동작을 해낼 수 있다면, 그것으로 충분하다는 사고방식입니다. 이를 **덕 타이핑**(duck typing)이라고 부릅니다.

```python
class Duck:
    def speak(self):
        return "꽥꽥!"


class Dog:
    def speak(self):
        return "멍멍!"


class RobotVacuum:
    def speak(self):
        return "삐빅- 청소를 시작합니다."


def make_it_speak(thing):
    """speak() 메서드를 가진 어떤 객체든 받아서 실행한다"""
    print(thing.speak())
```

```python
>>> make_it_speak(Duck())
꽥꽥!
>>> make_it_speak(Dog())
멍멍!
>>> make_it_speak(RobotVacuum())
삐빅- 청소를 시작합니다.
```

`make_it_speak` 함수는 매개변수 `thing`이 `Duck`인지 `Dog`인지 `RobotVacuum`인지 전혀 검사하지 않습니다. `Duck`, `Dog`, `RobotVacuum`은 서로 상속 관계도 없고 공통 부모도 없는 완전히 별개의 클래스이지만, 셋 다 `speak()`라는 메서드를 가지고 있다는 이유만으로 이 함수에 아무 문제 없이 전달될 수 있습니다. 심지어 로봇 청소기가 "말을 한다"는 개념적 어색함은 있지만, Python 인터프리터 입장에서는 `speak()`라는 이름의 메서드가 호출 가능하기만 하면 그만입니다.

### 왜 인터페이스를 명시하지 않는가

이런 설계는 11장 예외 처리에서 배운 **EAFP**(Easier to Ask Forgiveness than Permission, "허락보다 용서를 구하는 것이 쉽다") 철학과 정확히 같은 뿌리에서 나옵니다. Python은 코드를 실행하기 전에 "이 객체가 정말 이 인터페이스를 구현했는가?"를 미리 깐깐하게 검사(LBYP, Look Before You Leap)하기보다는, 일단 필요한 메서드를 호출해보고 문제가 생기면 그때 예외로 처리하는 방식을 선호합니다.

```python
def make_it_speak(thing):
    try:
        print(thing.speak())
    except AttributeError:
        print("이 객체는 말을 할 수 없습니다.")
```

이렇게 작성하면 `speak()` 메서드가 없는 객체가 들어와도 프로그램이 갑자기 멈추지 않고 우아하게 처리됩니다. 반면 함수 맨 앞에서 `if not isinstance(thing, (Duck, Dog, RobotVacuum)):`처럼 타입을 일일이 검사하는 방식은, 나중에 `speak()`를 가진 새로운 클래스(예: `Cat`)가 추가될 때마다 이 검사 목록에 계속 클래스를 끼워 넣어야 합니다. 덕 타이핑을 따르면 `Cat`에 `speak()` 메서드만 정의하면 별도의 수정 없이 `make_it_speak` 함수가 곧바로 `Cat`도 지원하게 됩니다. 이것이 Python이 유연하다고 평가받는 중요한 이유 중 하나입니다.

### 형식을 갖추고 싶을 때: 추상 베이스 클래스

덕 타이핑이 유연한 것은 사실이지만, 프로젝트 규모가 커지면 "이 계열의 클래스는 반드시 `speak()` 메서드를 구현해야 한다"는 규칙을 조금 더 명시적으로 강제하고 싶을 때가 있습니다. 이런 경우를 위해 Python은 표준 라이브러리에 `abc`(Abstract Base Class) 모듈을 제공합니다.

```python
from abc import ABC, abstractmethod


class Animal(ABC):
    """모든 동물은 반드시 speak()를 구현해야 한다"""

    @abstractmethod
    def speak(self):
        ...


class Cat(Animal):
    def speak(self):
        return "야옹!"
```

```python
>>> Animal()
Traceback (most recent call last):
  ...
TypeError: Can't instantiate abstract class Animal with abstract method speak
>>> Cat().speak()
'야옹!'
```

`Animal`처럼 `ABC`를 상속하고 `@abstractmethod`가 붙은 메서드를 하나라도 가진 클래스는 그 자체로는 인스턴스를 만들 수 없습니다. 오직 `speak()`를 실제로 구현한 하위 클래스만 인스턴스화할 수 있습니다. 이 방식은 덕 타이핑의 유연함과 인터페이스 강제의 안전함 사이에서 균형을 잡을 수 있는 선택지입니다. 다만 대부분의 Python 코드, 특히 작은 스크립트나 초기 단계의 프로젝트에서는 `abc` 없이 순수한 덕 타이핑만으로도 충분한 경우가 많습니다. "정말로 규칙을 강제해야 할 필요가 생겼을 때"에 도입하는 것이 좋습니다.

## 종합 예제: BankAccount 클래스 완성하기

이번 장에서 배운 내용을 모두 모아, `BankAccount` 클래스를 한 번에 정리해보겠습니다.

```python
from functools import total_ordering


@total_ordering
class BankAccount:
    """매직 메서드와 프로퍼티를 적용한 은행 계좌 클래스"""

    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance
        self.history = []

    @property
    def balance(self):
        """현재 잔액을 반환하는 읽기 전용 접근 통로"""
        return self._balance

    @balance.setter
    def balance(self, value):
        """잔액을 직접 설정할 때는 음수를 허용하지 않는다"""
        if value < 0:
            raise ValueError("잔액은 음수가 될 수 없습니다.")
        self._balance = value

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("입금액은 0보다 커야 합니다.")
        self._balance += amount
        self.history.append(f"입금 {amount:,}원")

    def withdraw(self, amount):
        if amount > self._balance:
            raise ValueError("잔액이 부족합니다.")
        self._balance -= amount
        self.history.append(f"출금 {amount:,}원")

    def __str__(self):
        return f"{self.owner}님의 계좌 (잔액: {self._balance:,}원)"

    def __repr__(self):
        return f"BankAccount(owner={self.owner!r}, balance={self._balance!r})"

    def __eq__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self._balance == other._balance

    def __lt__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self._balance < other._balance

    def __len__(self):
        return len(self.history)

    def __add__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        merged = BankAccount(f"{self.owner}&{other.owner}", self._balance + other._balance)
        return merged
```

이제 이 클래스는 다음과 같이 매우 자연스럽게 사용할 수 있습니다.

```python
>>> a = BankAccount("김철수", 10000)
>>> b = BankAccount("이영희", 30000)
>>> a.deposit(5000)
>>> a.withdraw(2000)
>>> print(a)
김철수님의 계좌 (잔액: 13,000원)
>>> len(a)
2
>>> a < b
True
>>> merged = a + b
>>> print(merged)
김철수&이영희님의 계좌 (잔액: 43,000원)
>>> for account in sorted([a, b]):
...     print(account)
...
김철수님의 계좌 (잔액: 13,000원)
이영희님의 계좌 (잔액: 30,000원)
```

처음 이 장을 시작할 때 `<__main__.BankAccount object at 0x...>`라는 낯선 출력만 내놓던 클래스가, 이제는 출력하고, 비교하고, 더하고, 정렬하고, 길이를 잴 수 있는 클래스로 성장했습니다. 이것이 매직 메서드가 만들어내는 "Python다움"입니다.

## 요약

- **매직 메서드**는 앞뒤로 밑줄 두 개가 붙은 특수 메서드로, `print()`, `==`, `len()`, `+` 같은 내장 함수와 연산자가 우리가 만든 클래스와 자연스럽게 상호작용하도록 연결해준다. `__str__`/`__repr__`은 문자열 표현, `__eq__`는 값 비교, `__len__`은 길이, `__lt__`는 크기 비교와 정렬, `__add__`는 연산자 오버로딩을 담당한다.
- **`@property`**는 메서드를 속성처럼 보이게 만들어, 값을 읽고 쓰는 과정에 검증 로직이나 계산 로직을 자연스럽게 끼워 넣을 수 있게 해준다. `@이름.setter`가 없으면 자동으로 읽기 전용 속성이 된다.
- **다중 상속**은 여러 부모 클래스의 기능을 하나의 클래스로 조합할 수 있게 해주며, 이때 어떤 부모의 메서드가 우선하는지는 **MRO**(메서드 결정 순서)로 결정된다. `class Duck(Swimmer, Flyer):`처럼 나열한 순서가 검색 우선순위이며, `__mro__`로 실제 순서를 확인할 수 있다.
- **덕 타이핑**은 객체의 클래스나 명시적 인터페이스 선언보다, 그 객체가 실제로 필요한 메서드를 가지고 있는지를 중시하는 Python의 설계 철학이다. 11장의 EAFP 철학과 같은 뿌리에서 나오며, 강제가 필요할 때는 `abc` 모듈의 추상 베이스 클래스로 보완할 수 있다.

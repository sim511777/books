문법을 아는 것과 좋은 코드를 쓰는 것은 다른 문제입니다. 지금까지 배운 문법만으로도 동작하는 프로그램을 만들 수 있지만, 시간이 지나도 읽기 쉽고 고치기 쉬운 코드를 쓰려면 몇 가지 관용구와 습관이 필요합니다. 이번 장에서는 이 책에서 배운 내용을 되짚으며, 실무에서 자주 마주치는 실수와 그것을 피하는 관용구를 정리합니다.

## null 안전성을 관용적으로 다루기

8장에서 배운 sound null safety는 "값이 없을 수 있다"는 사실을 타입 시스템에 드러내 컴파일 시점에 실수를 잡아주는 도구입니다. 하지만 도구를 잘못 쓰면 오히려 안전성을 스스로 무너뜨릴 수 있습니다.

가장 흔한 남용은 null 단정 연산자 `!`를 습관적으로 붙이는 것입니다.

```dart
// 좋지 않은 예: "어차피 null이 아니겠지"라는 가정에 의존
String? name = fetchName();
print(name!.toUpperCase()); // name이 null이면 런타임 예외로 즉시 앱이 죽음
```

`!`는 "나는 이 값이 null이 아님을 확신한다"고 컴파일러에게 선언하는 연산자입니다. 확신이 틀리면 컴파일 타임에는 아무 경고도 없다가 런타임에 예외가 발생합니다. 즉 `!`를 남발하는 코드는 8장에서 null 안전성이 없애준 위험을 코드 안에 다시 끌어들이는 것과 같습니다. 다음과 같은 대안을 먼저 고려하는 습관을 들이는 것이 좋습니다.

```dart
String? name = fetchName();

// 1. 기본값으로 대체: ?? 연산자
print((name ?? '이름 없음').toUpperCase());

// 2. null이면 그냥 건너뛰기: ?. 연산자
name?.toUpperCase();

// 3. 흐름 분석으로 타입을 좁혀서 안전하게 사용
if (name != null) {
  print(name.toUpperCase()); // 이 블록 안에서는 name이 String으로 좁혀짐
}

// 4. null일 때 예외를 던지고 싶다면, 의미를 드러내는 방식으로
final resolvedName = name ?? (throw StateError('이름이 반드시 필요합니다'));
```

`!`가 정말 필요한 순간은 있습니다. 예를 들어 위젯의 `initState`에서 초기화된 뒤 다시는 null이 될 수 없음을 타입 시스템이 알 방법이 없을 때, 혹은 방금 `containsKey`로 확인한 `Map`에서 값을 꺼낼 때처럼요. 다만 이런 경우에도 "왜 안전한지"를 주석으로 남기거나, `late`로 선언해 의도를 명확히 하는 쪽이 낫습니다. 반대로 `late` 변수를 초기화 이전에 접근하면 역시 런타임 예외가 발생하므로, `late`도 "확실히 나중에 초기화된다"는 근거가 있을 때만 쓰는 것이 원칙입니다.

## final과 const를 기본값으로

3장에서 `var`, `final`, `const`의 차이를 배웠습니다. 실무에서는 변수를 선언할 때 가변성이 정말 필요한지 먼저 따져보고, 필요하지 않다면 `final`을 기본으로 선택하는 습관이 버그를 크게 줄여줍니다.

```dart
// 좋지 않은 예: 재할당할 계획이 없는데도 var를 씀
var pi = 3.14159;
var greeting = '안녕하세요';

// 더 나은 예: 값이 바뀌지 않는다는 사실을 드러냄
final pi = 3.14159;
final greeting = '안녕하세요';
```

값이 한 번 정해지면 절대 바뀌지 않는다는 사실이 코드에 드러나면, 이 변수가 프로그램 어디에선가 몰래 바뀔까 봐 걱정하며 코드를 따라다닐 필요가 없어집니다. 특히 함수의 매개변수나 클래스의 필드는 대부분의 경우 `final`로 선언해도 충분합니다.

`const`는 한 걸음 더 나아가 "컴파일 시점에 이미 값이 정해진다"는 사실까지 보장합니다. 컴파일 타임 상수로 만들 수 있는 값이라면 `final`보다 `const`를 우선하세요. 특히 리스트나 맵, 객체 리터럴이 실행 중에 절대 바뀌지 않는다면 `const`로 선언해 불필요한 메모리 할당과 재생성을 피할 수 있습니다.

```dart
const maxRetryCount = 3;
const defaultTags = ['dart', 'flutter'];

class Circle {
  final double radius; // 인스턴스마다 다른 값이므로 final
  const Circle(this.radius); // 생성자 자체는 const 생성자로 만들 수 있음
}

const unitCircle = Circle(1.0); // 컴파일 타임에 완전히 고정된 인스턴스
```

가변 상태는 꼭 필요한 곳에만 최소한으로 남겨두고, 나머지는 불변으로 만드는 것이 코드를 예측 가능하게 만드는 가장 확실한 방법입니다.

## 확장 메서드와 믹스인, 필요한 곳에만

10장에서 배운 확장 메서드(`extension`)와 14장에서 배운 믹스인(`mixin`)은 강력하지만, 강력한 도구일수록 오용하기도 쉽습니다.

확장 메서드는 기존 타입을 수정하지 않고도 새로운 메서드를 "추가된 것처럼" 쓸 수 있게 해주는 기능입니다. 이 특징 때문에, 어떤 프로젝트 코드베이스 전반에서 반복되는 짧은 로직을 의미 있는 이름으로 캡슐화할 때는 좋은 선택이지만, 남발하면 "이 메서드가 원래 타입에 있던 것인지, 어디선가 확장으로 추가된 것인지" 헷갈리는 코드가 됩니다.

```dart
// 좋은 예: 여러 곳에서 반복되는 검사를 의미 있는 이름으로 캡슐화
extension EmailValidation on String {
  bool get isValidEmail => contains('@') && contains('.');
}

if (userInput.isValidEmail) {
  // ...
}
```

이런 확장은 파일 하나에 모아 어디서 정의됐는지 쉽게 찾을 수 있게 하고, `import` 시점에만 활성화된다는 점(10장 참고)을 활용해 정말 필요한 파일에서만 가져다 쓰는 것이 좋습니다.

믹스인은 "여러 클래스가 상속 관계 없이 같은 기능을 공유하고 싶을 때" 쓰는 도구입니다. 로깅, 직렬화, 비교 로직처럼 특정 클래스 계층에 얽매이지 않는 재사용 가능한 행동을 묶을 때 적합합니다.

```dart
mixin Loggable {
  void log(String message) => print('[${runtimeType}] $message');
}

class OrderService with Loggable {
  void placeOrder() {
    log('주문을 처리합니다'); // Loggable에서 가져온 메서드
  }
}
```

반대로, 믹스인을 상속 대신 쓰는 "만능 도구"로 남용하면 어떤 클래스가 어떤 기능을 갖는지 `with` 목록을 일일이 따라가야만 알 수 있는 코드가 됩니다. 클래스 사이에 진짜 "종류(is-a)" 관계가 있다면 9장과 11장에서 배운 상속이나 인터페이스가 더 적절하고, "행동(can-do)"만 공유한다면 믹스인이 더 적절하다는 기준을 기억해두세요.

## 비동기 코드에서 가장 흔한 실수: 기다리지 않은 Future

15장에서 배운 `async`/`await`는 비동기 코드를 동기 코드처럼 읽히게 해주지만, 그만큼 `await`를 빠뜨리기도 쉽습니다. 다음 코드는 컴파일도 되고 겉보기에는 문제가 없어 보이지만, 실제로는 버그를 안고 있습니다.

```dart
Future<void> saveUserData(String name) async {
  await Future.delayed(const Duration(seconds: 1)); // 저장 작업 흉내
  print('$name 저장 완료');
}

void handleSubmit() {
  saveUserData('철수'); // await를 빠뜨림!
  print('제출 처리 완료'); // 저장이 끝나기 전에 먼저 출력됨
}
```

`saveUserData`를 호출했지만 `await`도 `.then()`도 붙이지 않았기 때문에, 반환된 `Future`는 아무도 기다리지 않는 채로 백그라운드에서 실행됩니다. `handleSubmit`은 저장이 끝나길 기다리지 않고 곧바로 다음 줄로 넘어가 버립니다. 더 심각한 문제는, 이 `Future`가 실패했을 때 그 오류를 아무도 처리하지 않아 조용히 무시되거나 처리되지 않은 예외로 앱을 중단시킬 수 있다는 점입니다.

이런 실수를 피하는 원칙은 단순합니다.

```dart
// 1. 호출하는 함수도 async로 만들고 await로 기다린다
Future<void> handleSubmit() async {
  await saveUserData('철수');
  print('제출 처리 완료'); // 저장이 끝난 뒤에 출력됨
}

// 2. 정말로 결과를 기다릴 필요가 없다면, 의도를 명시적으로 드러낸다
void handleSubmitFireAndForget() {
  unawaited(saveUserData('철수')); // "일부러" 기다리지 않음을 코드로 표시
}
```

`unawaited`는 `dart:async`가 제공하는 함수로, 실제 동작은 아무것도 하지 않지만(`Future`를 그대로 무시) "이 `Future`를 기다리지 않는 것은 실수가 아니라 의도"라는 사실을 코드를 읽는 사람과 분석 도구에 알려줍니다. 16장에서 배운 `Stream`을 구독할 때도 비슷한 실수가 흔합니다. `listen`으로 등록한 구독을 더 이상 필요 없을 때 `cancel`하지 않으면, 스트림이 계속 살아 있는 동안 리스너가 자원을 붙잡고 있게 됩니다.

```dart
final subscription = someStream.listen((event) => print(event));
// 사용이 끝나면 반드시 해제
await subscription.cancel();
```

## dart format과 dart analyze로 스스로 코드 점검하기

좋은 코드 습관 중 상당수는 도구가 대신해줄 수 있습니다. Dart SDK에는 두 가지 명령이 기본으로 포함되어 있습니다.

```bash
dart format .
```

`dart format`은 코드의 들여쓰기, 줄바꿈, 공백을 Dart 공식 스타일에 맞춰 자동으로 정리합니다. 스타일을 두고 논쟁할 필요 없이, 프로젝트 전체가 항상 같은 형태를 유지하게 해줍니다. 대부분의 에디터는 저장할 때 자동으로 `dart format`을 실행하는 설정을 지원합니다.

```bash
dart analyze
```

`dart analyze`는 정적 분석기를 실행해 타입 오류, 사용하지 않는 import, 도달할 수 없는 코드, null 안전성 위반 가능성 등을 코드를 실행하지 않고도 찾아줍니다. 17장에서 소개한 `pubspec.yaml`의 `dev_dependencies`에 `lints`나 `flutter_lints` 패키지를 추가하고 프로젝트 루트에 `analysis_options.yaml`을 두면, 팀이 합의한 규칙(예: 항상 `final` 우선하기, 불필요한 `!` 지양하기 등)을 분석기가 자동으로 검사하게 만들 수 있습니다.

```yaml
# analysis_options.yaml
include: package:lints/recommended.yaml
```

`dart format`과 `dart analyze`를 커밋 전이나 CI(지속적 통합) 과정에 넣어두면, 사람이 매번 눈으로 스타일과 실수를 점검하지 않아도 최소한의 품질을 자동으로 지킬 수 있습니다.

## 다음 학습 단계

이 책은 Dart 언어 자체에 집중했습니다. 여기서 익힌 변수와 타입, 제어문과 반복문, 함수, 클래스와 인터페이스, 제네릭, null 안전성, 컬렉션, 비동기 프로그래밍, 그리고 이번 장에서 정리한 코드 습관은 Dart로 무엇을 만들든 계속 쓰이는 토대입니다. 이제 어느 방향으로 나아갈지는 여러분의 관심사에 따라 달라집니다.

- **모바일/웹 UI 개발**: 17장에서 언급했듯 Flutter는 Dart 위에 구축된 UI 프레임워크입니다. 위젯, 상태 관리, 레이아웃 같은 새로운 개념을 배우게 되지만, 그 개념을 표현하는 언어는 계속 Dart입니다.
- **서버 사이드 개발**: Dart는 HTTP 서버, API 백엔드를 만드는 데도 쓰일 수 있습니다. 15장과 16장에서 다진 비동기 프로그래밍과 스트림 지식이 특히 유용하게 쓰이는 영역입니다.
- **커맨드라인 도구와 스크립트**: 이 책의 예제 대부분처럼 `main` 함수 하나로 시작하는 간단한 도구부터, 17장에서 배운 패키지 구조를 갖춘 정교한 CLI 도구까지 Dart로 만들 수 있습니다.

어느 방향으로 가든, Dart 공식 문서와 pub.dev의 패키지 문서를 직접 읽고 실험해보는 습관을 들이는 것이 가장 효과적인 다음 단계입니다. 문법을 외우기보다, 작은 프로그램을 직접 만들어보면서 이 책에서 배운 개념이 실제로 어떻게 맞물리는지 몸으로 익히는 것을 추천합니다.

## 요약

- `!`는 null 안전성을 스스로 무너뜨릴 수 있는 연산자이므로, `??`, `?.`, 흐름 분석을 통한 타입 좁히기를 먼저 고려하고 `!`는 정말 안전하다는 근거가 있을 때만 씁니다.
- 재할당이 필요하지 않은 변수는 `final`을 기본으로 선택하고, 컴파일 타임에 값이 고정된다면 `const`를 우선합니다.
- 확장 메서드는 반복되는 로직을 의미 있는 이름으로 캡슐화할 때, 믹스인은 상속 관계 없이 행동을 공유할 때 적합합니다. "종류(is-a)"는 상속/인터페이스로, "행동(can-do)"은 믹스인으로 표현하는 기준을 기억해둡니다.
- `Future`를 반환하는 함수를 호출할 때 `await`를 빠뜨리면 실행 순서가 어긋나고 오류가 조용히 무시될 수 있습니다. 의도적으로 기다리지 않을 때는 `unawaited`로 그 의도를 명시합니다.
- `dart format`으로 코드 스타일을 통일하고, `dart analyze`(와 `lints`/`flutter_lints` 패키지)로 실행 전에 잠재적 오류를 잡아내는 습관을 들입니다.
- 이 책에서 익힌 Dart 언어 지식은 Flutter를 이용한 모바일/웹 개발, 서버 사이드 Dart, 커맨드라인 도구 개발 등 어떤 방향으로 나아가든 그대로 이어지는 토대입니다.

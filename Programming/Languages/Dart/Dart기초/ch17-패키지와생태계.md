지금까지는 파일 하나, 많아야 몇 개의 파일로 이루어진 프로그램을 다뤘습니다. 하지만 실제로 소프트웨어를 만들 때는 혼자서 모든 코드를 새로 작성하지 않습니다. 날짜를 다루는 기능, HTTP 요청을 보내는 기능, 상태 관리를 도와주는 기능처럼 이미 잘 만들어진 코드를 가져와 쓰고, 반대로 내가 만든 코드를 여러 파일로 나누거나 다른 프로젝트에서 재사용할 수 있는 형태로 정리하기도 합니다. 이번 장에서는 Dart 프로젝트가 의존성을 어떻게 관리하는지, 그리고 코드를 여러 파일과 라이브러리로 나누는 기본 방법을 살펴봅니다.

## 프로젝트의 설계도, pubspec.yaml

Dart 프로젝트(패키지)의 루트에는 `pubspec.yaml`이라는 파일이 있습니다. 이 파일은 프로젝트의 이름, 버전, 그리고 이 프로젝트가 어떤 외부 코드에 의존하는지를 기록하는 설계도 역할을 합니다. `dart create` 명령으로 새 프로젝트를 만들면 기본적인 `pubspec.yaml`이 자동으로 생성됩니다.

```yaml
name: my_awesome_app
description: 나만의 첫 Dart 프로젝트
version: 1.0.0
publish_to: 'none' # pub.dev에 공개하지 않을 패키지라면 명시

environment:
  sdk: ^3.0.0

dependencies:
  http: ^1.2.0
  intl: ^0.19.0

dev_dependencies:
  test: ^1.25.0
  lints: ^4.0.0
```

이 파일에서 눈여겨볼 부분은 세 가지입니다.

- `environment.sdk`: 이 프로젝트가 요구하는 Dart SDK 버전 범위입니다. 1장에서 설치한 Dart SDK가 이 범위를 만족해야 프로젝트를 실행할 수 있습니다.
- `dependencies`: 프로그램이 실제로 동작하는 데 필요한 패키지 목록입니다. 앱을 빌드하고 실행할 때 함께 포함됩니다.
- `dev_dependencies`: 개발 과정에서만 필요한 패키지 목록입니다. 테스트 프레임워크나 코드 검사 도구처럼, 완성된 앱을 사용자에게 배포할 때는 필요 없는 것들이 여기에 들어갑니다.

## 버전 제약을 읽는 법

`http: ^1.2.0`에서 `^`(캐럿) 기호는 "이 버전과 호환되는 범위"를 의미하는 시맨틱 버전(semantic versioning) 표기법입니다. `^1.2.0`은 `1.2.0` 이상이면서 `2.0.0`보다는 작은 버전을 허용한다는 뜻입니다. 즉 패치나 마이너 업데이트(버그 수정, 하위 호환되는 기능 추가)는 자동으로 받아들이지만, 호환성이 깨질 수 있는 메이저 업데이트는 명시적으로 버전을 올려주기 전까지 받지 않습니다. 이 규칙 덕분에 의존성을 최신 상태로 유지하면서도 예상치 못한 호환성 문제를 줄일 수 있습니다.

## 의존성 설치하고 관리하기

`pubspec.yaml`을 작성하거나 수정한 뒤에는 실제로 패키지를 내려받아야 합니다.

```bash
dart pub get
```

이 명령을 실행하면 pub 도구가 `pubspec.yaml`에 적힌 조건을 만족하는 패키지 버전을 계산하고, 그 결과를 `pubspec.lock` 파일에 정확한 버전으로 고정해 기록합니다. `pubspec.lock`은 "지금 이 순간 실제로 설치된 버전이 정확히 무엇인지"를 팀원 모두가, 그리고 배포 환경에서도 똑같이 재현할 수 있게 해주는 파일이므로 버전 관리 시스템에 함께 커밋하는 것이 좋습니다.

패키지를 하나씩 손으로 추가하는 대신 명령어로 추가할 수도 있습니다.

```bash
dart pub add http
dart pub add --dev test
dart pub remove intl
```

`dart pub add`는 `pubspec.yaml`에 알맞은 버전 제약을 자동으로 써주고 곧바로 `dart pub get`까지 실행해줍니다. `--dev` 옵션을 붙이면 `dev_dependencies`에 추가됩니다.

## pub.dev: Dart 패키지 저장소

`http`나 `intl` 같은 패키지는 어디서 오는 걸까요? 바로 [pub.dev](https://pub.dev)입니다. pub.dev는 Dart와 Flutter 커뮤니티가 만든 공개 패키지 저장소로, 누구나 자신이 만든 패키지를 올리고 다른 사람이 만든 패키지를 검색해 쓸 수 있습니다. 각 패키지 페이지에는 사용법 설명, API 문서, 좋아요와 다운로드 수, 그리고 pub.dev가 자동으로 채점하는 점수(신뢰도, 유지 관리 상태, 플랫폼 지원 범위 등)가 함께 표시되어 어떤 패키지를 선택할지 판단하는 데 도움을 줍니다.

패키지를 고를 때는 다음을 함께 살펴보는 습관을 들이는 것이 좋습니다.

- 최근에도 업데이트되고 있는가 (마지막 배포일)
- null 안전성을 지원하는가 (8장에서 배운 sound null safety 기준)
- 이슈 트래커나 저장소에 문제가 활발히 관리되고 있는가
- 내 프로젝트가 목표로 하는 플랫폼(웹, 모바일, 서버 등)을 지원하는가

## import로 코드 가져오기

11장 이전부터 계속 써온 `import` 문은 사실 세 가지 대상을 가리킬 수 있습니다.

```dart
import 'dart:math'; // Dart SDK에 내장된 코어 라이브러리
import 'package:http/http.dart' as http; // pub.dev에서 받은 외부 패키지
import 'utils/string_helper.dart'; // 같은 프로젝트 안의 다른 파일 (상대 경로)
```

- `dart:` 접두사는 `dart:core`, `dart:math`, `dart:async`(15장), `dart:convert`처럼 SDK에 내장된 라이브러리를 가져올 때 씁니다.
- `package:` 접두사는 `pubspec.yaml`에 등록된 외부 패키지, 혹은 같은 프로젝트 안에서 `lib/` 폴더 아래에 있는 내 코드를 패키지 이름으로 가져올 때 씁니다.
- 상대 경로는 같은 프로젝트의 다른 파일을 파일 시스템 경로로 직접 가져올 때 씁니다.

이름 충돌을 피하거나 어느 라이브러리에서 온 것인지 명확히 하고 싶을 때는 `as`로 별칭을 붙입니다. 반대로 특정 이름만 골라 가져오거나 제외하고 싶다면 `show`와 `hide`를 씁니다.

```dart
import 'package:collection/collection.dart' show ListEquality;
import 'my_math_utils.dart' hide oldHelper;
```

## 내 코드를 여러 파일로 나누기

프로젝트가 커지면 하나의 파일에 모든 클래스와 함수를 몰아넣기보다, 역할에 따라 파일을 나누는 것이 유지보수에 훨씬 유리합니다. Dart에서 파일을 나누는 가장 기본적인 방법은 각 파일을 독립된 라이브러리로 취급하고 `import`로 연결하는 것입니다.

```dart
// lib/models/user.dart
class User {
  final String name;
  final int age;

  User(this.name, this.age);
}
```

```dart
// lib/main.dart
import 'models/user.dart';

void main() {
  var user = User('철수', 20);
  print('${user.name}, ${user.age}살');
}
```

이렇게 파일을 나누면 각 파일이 각자 독립적인 라이브러리가 되며, 필요한 곳에서 `import`로 그 라이브러리를 가져와 씁니다. 9장에서 배운 클래스나 11장에서 배운 인터페이스, 14장에서 배운 믹스인 등을 이런 방식으로 파일 단위로 정리해두면 코드를 찾고 재사용하기 훨씬 쉬워집니다.

## part로 하나의 라이브러리를 여러 파일에 나눠 쓰기

`import`가 서로 다른 라이브러리를 연결하는 방법이라면, `part`는 반대로 "하나의 논리적인 라이브러리를 여러 파일로 물리적으로만 쪼개는" 방법입니다. 예를 들어 클래스 하나가 너무 커서 파일을 나누고 싶지만, 개념적으로는 여전히 같은 라이브러리로 취급하고 싶을 때 씁니다.

```dart
// shape.dart (라이브러리의 진입점)
part 'shape_circle.dart';
part 'shape_square.dart';

abstract class Shape {
  double get area;
}
```

```dart
// shape_circle.dart
part of 'shape.dart';

class Circle extends Shape {
  final double radius;
  Circle(this.radius);

  @override
  double get area => 3.14159 * radius * radius;
}
```

`part of` 파일은 독립된 라이브러리가 아니라 진입점 파일의 일부로 합쳐지므로, 별도로 `import`할 수 없고 진입점 파일을 통해서만 접근됩니다. 실무에서는 `json_serializable`처럼 코드 생성기가 자동으로 만들어주는 `.g.dart` 파일을 연결할 때 이 문법을 자주 보게 됩니다. 하지만 일반적인 상황에서는 앞서 본 것처럼 파일마다 독립된 라이브러리로 만들고 `import`로 연결하는 방식이 훨씬 흔하고 다루기도 쉬우니, `part`는 "이런 것도 있구나" 정도로 기억해두면 충분합니다.

## Flutter도 결국 Dart 패키지

이 책 곳곳에서 이미 언급했듯, Flutter는 별개의 언어가 아니라 Dart 위에 구축된 UI 프레임워크입니다. Flutter로 앱을 만들 때 작성하는 `pubspec.yaml`, `dependencies`에 추가하는 패키지, `import`로 위젯을 가져오는 방식은 이번 장에서 배운 것과 완전히 같은 메커니즘입니다. `flutter pub get`은 `dart pub get`과 같은 역할을 하는 Flutter SDK의 명령일 뿐이고, `flutter create`로 만든 프로젝트를 열어보면 `pubspec.yaml`에 `flutter` SDK 의존성이 하나 더 추가되어 있을 뿐 구조는 동일합니다.

즉 1장부터 지금까지 익힌 변수와 타입, 클래스와 인터페이스, 컬렉션과 고차 함수, null 안전성, 비동기 프로그래밍은 Flutter로 넘어가더라도 그대로 쓰이는 지식입니다. Flutter를 배우는 일은 새로운 언어를 배우는 것이 아니라, 이미 아는 Dart 위에 위젯이라는 UI 구성 방식을 얹어 배우는 것에 가깝습니다. 서버 사이드 Dart 프레임워크나 커맨드라인 도구를 만들 때도 마찬가지로, 이 책에서 다진 언어 기초는 그대로 이어집니다.

## 요약

- `pubspec.yaml`은 프로젝트의 이름, SDK 버전, 의존성을 기록하는 파일이며, `dependencies`는 실행에 필요한 패키지, `dev_dependencies`는 개발 중에만 필요한 패키지를 나열합니다.
- `^1.2.0` 같은 캐럿 버전 제약은 하위 호환되는 업데이트까지 자동으로 허용하고 호환성이 깨질 수 있는 메이저 업데이트는 막아줍니다.
- `dart pub get`으로 의존성을 설치하고, `dart pub add`/`dart pub remove`로 `pubspec.yaml`을 편집과 동시에 관리할 수 있습니다. `pubspec.lock`은 실제로 설치된 정확한 버전을 고정합니다.
- pub.dev는 Dart/Flutter 공식 패키지 저장소로, 패키지의 유지 관리 상태와 점수를 참고해 신중히 선택하는 것이 좋습니다.
- `import`는 `dart:`(코어 라이브러리), `package:`(외부 패키지 또는 내 프로젝트), 상대 경로(같은 프로젝트 파일) 세 가지 형태로 코드를 연결하며, `as`/`show`/`hide`로 세밀하게 조정할 수 있습니다.
- 여러 파일로 나눈 코드는 각각 독립된 라이브러리로 취급되어 `import`로 연결되는 것이 기본이며, `part`/`part of`는 하나의 라이브러리를 물리적으로만 여러 파일로 쪼개는 특수한 경우에 씁니다.
- Flutter는 Dart 위에 구축된 UI 프레임워크이므로, 이 책에서 배운 언어 지식은 Flutter나 서버 사이드 Dart로 넘어가서도 그대로 이어집니다.

## 연습문제

1. 새 Dart 프로젝트를 만들고 `pubspec.yaml`에 원하는 패키지 하나를 `dart pub add`로 추가한 뒤, `pubspec.yaml`과 `pubspec.lock`에 어떤 내용이 기록되는지 비교해보세요.
2. `^0.19.0`과 `^1.0.0`이라는 두 버전 제약이 각각 어떤 버전 범위를 허용하는지 설명해보세요.
3. `lib/models/`와 `lib/services/` 폴더를 만들고, 클래스 하나와 그 클래스를 사용하는 함수 하나를 각각 다른 파일에 작성한 뒤 `import`로 연결해보세요.
4. `import 'package:example/foo.dart' show Foo hide Bar;` 같은 문장은 문법적으로 허용되지 않습니다. `show`와 `hide`를 함께 쓸 수 없는 이유를 생각해보고, 원하는 이름만 가져오려면 어떻게 작성해야 할지 정리해보세요.
5. pub.dev에서 관심 있는 분야의 패키지를 하나 찾아, 마지막 업데이트 날짜와 pub.dev 점수, null 안전성 지원 여부를 확인해보세요.

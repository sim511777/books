# 18장. 좋은 Kotlin 코드 작성 습관

---

지금까지 17개의 장을 거치며 Kotlin의 문법과 기능을 하나씩 쌓아 왔습니다. 변수와 자료형, null 안전성, 클래스와 인터페이스, 컬렉션과 람다, 코루틴까지 배웠다면 이제 "동작하는 코드"는 충분히 작성할 수 있을 것입니다. 이 마지막 장에서는 한 걸음 더 나아가 "Kotlin다운(idiomatic) 코드", 즉 언어가 제공하는 안전성과 간결함을 제대로 활용하는 코드를 쓰는 습관을 정리합니다. 새로운 문법을 배우는 장이 아니라, 지금까지 배운 것들을 어떻게 조합해서 더 나은 코드로 만드는지 되짚어보는 장입니다.

## var보다 val을 먼저 떠올리기

3장에서 `val`은 재할당할 수 없는 읽기 전용 참조, `var`는 재할당 가능한 변수라고 배웠습니다. 습관적으로 `var`를 먼저 쓰고 나중에 필요 없으면 `val`로 바꾸는 방식보다는, 변수를 선언하는 순간 "이 값이 나중에 바뀔 필요가 있는가?"를 먼저 자문하고 기본값으로 `val`을 선택하는 편이 좋습니다.

```kotlin
// 지양: 재할당이 필요 없는데도 var를 습관적으로 사용
fun describe(age: Int): String {
    var category = "성인"
    if (age < 19) {
        category = "미성년자"
    }
    return category
}

// 선호: if를 표현식으로 사용해 val 하나로 끝내기
fun describe(age: Int): String {
    val category = if (age < 19) "미성년자" else "성인"
    return category
}
```

두 함수는 결과가 같지만, 아래쪽 코드는 `category`가 딱 한 번만 값을 가진다는 사실이 코드만 봐도 명확합니다. 5장에서 배운 `if` 표현식처럼 Kotlin은 값을 만들어내는 여러 문법(`if`, `when`, 나중에 볼 스코프 함수 등)을 표현식으로 제공하는데, 이런 표현식들을 적극적으로 활용하면 `var`로 중간 상태를 관리할 일이 자연스럽게 줄어듭니다. `var`가 아예 나쁜 것은 아닙니다. 반복문에서 누적값을 계산하거나(6장) 상태가 실제로 시간에 따라 바뀌어야 하는 경우에는 `var`가 정확히 맞는 선택입니다. 다만 "일단 var로 시작"하는 습관보다는 "정말 재할당이 필요한가"를 먼저 따져보는 순서를 권장합니다.

## null 안전성 관용구 정리

8장에서 배운 null 안전성 문법들은 개별로도 유용하지만, 서로 조합했을 때 더 큰 힘을 발휘합니다. 실무에서 자주 등장하는 조합 몇 가지를 정리합니다.

```kotlin
data class Member(val name: String, val nickname: String?)

fun main() {
    val member: Member? = findMember()

    // 1) 안전 호출 + 엘비스 연산자: 값이 없으면 기본값으로 대체
    val displayName = member?.nickname ?: member?.name ?: "손님"
    println(displayName)

    // 2) let과 결합해 null이 아닐 때만 블록 실행
    member?.let {
        println("${it.name}님이 로그인했습니다.")
    }

    // 3) 이른 반환과 엘비스 연산자 조합
    val nickname = member?.nickname ?: return
    println("닉네임: $nickname")
}

fun findMember(): Member? = Member("서연", null)
```

여기서 강조하고 싶은 습관은 `!!`(non-null assertion) 연산자를 최후의 수단으로 남겨두는 것입니다. `!!`는 "이 값은 절대 null이 아니라고 내가 보장한다"고 컴파일러에게 선언하는 연산자인데, 그 보장이 틀렸을 경우 다른 검사 없이 곧바로 `NullPointerException`이 발생합니다. 이는 Kotlin이 애초에 없애고자 했던 문제를 코드로 다시 불러들이는 것과 다름없습니다. `!!`를 쓰고 싶은 순간이 오면, 정말로 null일 수 없는 상황인지 먼저 점검하고, 안전 호출·엘비스 연산자·`let`·스마트 캐스트 중 하나로 대체할 수 없는지 한 번 더 고민하는 습관을 들이는 것이 좋습니다.

```kotlin
// 지양: nickname이 null이면 그 자리에서 예외로 죽는다
fun printNickname(member: Member) {
    println(member.nickname!!.uppercase())
}

// 선호: null인 경우를 코드에서 명시적으로 다룬다
fun printNickname(member: Member) {
    val nickname = member.nickname ?: "이름 없음"
    println(nickname.uppercase())
}
```

## 데이터 클래스와 확장 함수로 간결하게 쓰기

10장에서 배운 데이터 클래스와 14장에서 배운 확장 함수는 Kotlin다운 코드를 만드는 데 있어 가장 강력한 두 도구입니다. 데이터를 표현할 때는 로직이 없는 일반 클래스보다 데이터 클래스를 우선 고려하는 것이 좋습니다. `equals`, `hashCode`, `toString`, `copy`를 직접 구현하지 않아도 자동으로 얻을 수 있고, 그만큼 코드가 짧아지는 동시에 실수할 여지도 줄어듭니다.

```kotlin
// 데이터 클래스: 값 비교, 출력, 복사가 모두 공짜로 따라온다
data class Point(val x: Int, val y: Int)

fun main() {
    val p1 = Point(1, 2)
    val p2 = p1.copy(y = 5)   // x는 유지하고 y만 바꾼 새 인스턴스
    println(p1)               // Point(x=1, y=2)
    println(p1 == Point(1, 2)) // true, 값으로 비교된다
}
```

한편 기존 클래스에 새 기능을 추가하고 싶을 때, 상속으로 새 클래스를 만들기보다는 확장 함수를 먼저 고려해 보는 것도 좋은 습관입니다. 특히 데이터 클래스처럼 상태를 최소화한 클래스와 그 위에서 동작하는 순수한 로직을 확장 함수로 분리하면, "데이터"와 "그 데이터로 하는 일"이 코드에서 자연스럽게 구분됩니다.

```kotlin
data class Cart(val items: List<Int>)  // 각 항목의 가격(원)

// Cart의 정의는 그대로 두고, 필요한 계산만 확장 함수로 덧붙인다
fun Cart.totalPrice(): Int = items.sum()
fun Cart.isEmpty(): Boolean = items.isEmpty()

fun main() {
    val cart = Cart(listOf(1000, 2500, 3200))
    println("총액: ${cart.totalPrice()}원")
    println("비어있나요? ${cart.isEmpty()}")
}
```

## 가변 컬렉션을 함부로 밖으로 노출하지 않기

12장에서 배운 컬렉션 중 `MutableList`, `MutableMap` 같은 가변 컬렉션은 클래스 내부의 상태를 관리할 때는 편리하지만, 외부에 그대로 반환하면 호출한 쪽에서 내부 상태를 마음대로 바꿔버릴 수 있는 위험이 생깁니다.

```kotlin
// 지양: 내부의 가변 리스트를 그대로 반환
class Basket {
    private val _items = mutableListOf<String>()

    fun items(): MutableList<String> = _items

    fun add(item: String) {
        _items.add(item)
    }
}

fun main() {
    val basket = Basket()
    basket.add("사과")

    val leaked = basket.items()
    leaked.clear()   // Basket의 의도와 무관하게 내부 상태가 통째로 지워진다
}
```

위 코드에서는 `items()`가 반환한 리스트를 통해 외부에서 `Basket`이 전혀 모르는 사이에 내부 컬렉션을 비워버릴 수 있습니다. 이런 문제를 막으려면, 외부에 컬렉션을 노출할 때는 읽기 전용 타입(`List`, `Map` 등)으로 반환하는 것을 기본으로 삼는 것이 좋습니다.

```kotlin
// 선호: 외부에는 읽기 전용 타입으로만 노출한다
class Basket {
    private val _items = mutableListOf<String>()

    val items: List<String>
        get() = _items

    fun add(item: String) {
        _items.add(item)
    }
}

fun main() {
    val basket = Basket()
    basket.add("사과")

    val items = basket.items
    // items.add("바나나")   // 컴파일 오류: List에는 add가 없다
    println(items)
}
```

`List`로 바꾼다고 해서 실제 객체가 불변이 되는 것은 아니지만(내부적으로는 여전히 `MutableList`이므로 `Basket` 자신은 계속 변경할 수 있습니다), 외부에서 보이는 타입에는 변경 메서드가 없기 때문에 실수로 내부 상태를 건드리는 일을 컴파일 시점에 막을 수 있습니다. 클래스나 함수를 설계할 때 "이 값을 외부에서 바꿔도 되는가?"를 먼저 정하고, 안 된다면 읽기 전용 타입으로 노출하는 습관을 들이는 것이 좋습니다.

## 자주 보이는 실수들 다시 정리

지금까지 다룬 내용을 포함해, 초보자가 자주 저지르는 실수를 모아 정리합니다.

- **`!!` 남용**: null 가능성을 진지하게 다루지 않고 컴파일 오류를 임시로 없애기 위해 `!!`를 붙이는 경우가 많습니다. `!!`는 문제를 해결하는 것이 아니라 실행 시점으로 미루는 것일 뿐입니다.
- **가변 컬렉션을 그대로 반환**: 앞서 본 것처럼 클래스 내부의 `MutableList`, `MutableMap`을 그대로 외부에 노출하면 캡슐화가 무너집니다.
- **모든 것을 `var`로 선언**: 재할당이 필요 없는데도 `var`를 습관적으로 사용하면, 코드를 읽는 사람이 "이 값이 중간에 바뀔 수도 있겠구나"라고 오해하게 됩니다.
- **얕은 복사와 깊은 복사를 혼동**: 데이터 클래스의 `copy()`는 최상위 프로퍼티만 새로 복사하는 얕은 복사입니다. 프로퍼티가 다시 가변 컬렉션이나 다른 가변 객체를 참조하고 있다면, `copy()` 이후에도 그 내부 객체는 원본과 공유됩니다.
- **예외를 문자열 비교로 처리**: `try-catch`로 잡은 예외의 메시지를 문자열로 비교해 분기하는 방식은 5장, 11장에서 배운 타입 계층과 `when`을 활용하면 훨씬 안전하고 명확하게 표현할 수 있습니다.
- **sealed class를 쓸 자리에 문자열이나 정수 코드 사용**: 15장에서 배운 sealed class로 표현할 수 있는 상태를 문자열 상수(`"LOADING"`, `"ERROR"` 등)로 관리하면, 오타나 처리하지 않은 케이스를 컴파일러가 잡아주지 못합니다.
- **모든 코드를 동기적으로 작성한 뒤 나중에 코루틴을 끼워 맞추려 함**: 16장에서 본 것처럼, 오래 걸리는 작업이 예상되는 지점은 처음부터 `suspend` 함수와 코루틴 구조를 고려해 설계하는 편이 나중에 뜯어고치는 것보다 수월합니다.

## 다음 학습 단계

이 책은 Kotlin 언어 자체의 기초를 다지는 것을 목표로 삼았습니다. 언어 문법을 익힌 다음에는 실제로 무언가를 만들어보면서 배운 것을 몸에 익히는 과정이 필요합니다. 관심 분야에 따라 다음과 같은 방향을 고려해 볼 수 있습니다.

- **모바일 앱 개발**: Kotlin은 안드로이드의 공식 언어입니다. 화면을 그리는 방법, 생명주기, 비동기 처리(16장의 코루틴이 여기서 특히 중요하게 쓰입니다) 등을 다루는 안드로이드 개발 학습으로 이어갈 수 있습니다.
- **서버·백엔드 개발**: JVM 위에서 동작하는 다양한 백엔드 프레임워크가 Kotlin을 1급 언어로 지원합니다. 데이터베이스 연동, REST API 설계, 이 책에서 다루지 않은 예외 처리와 로깅 전략 등을 함께 배우게 됩니다.
- **멀티플랫폼 개발**: Kotlin은 JVM뿐 아니라 iOS, 웹, 데스크톱을 겨냥한 컴파일도 지원합니다. 하나의 비즈니스 로직을 여러 플랫폼에서 재사용하는 방식에 관심이 있다면 이 방향을 살펴볼 만합니다.
- **언어 자체를 더 깊이**: 이 책에서 다루지 않은 제네릭의 변성(variance), 위임(delegation), 애노테이션 처리, 코루틴의 심화 개념(Flow, 구조적 동시성의 세부 규칙) 등을 더 깊이 파고들 수 있습니다.

어떤 방향으로 가더라도, 공식 문서와 언어 레퍼런스를 직접 찾아 읽는 습관은 큰 도움이 됩니다. 구체적으로 무엇을 참고하면 좋은지는 부록에서 조금 더 정리합니다.

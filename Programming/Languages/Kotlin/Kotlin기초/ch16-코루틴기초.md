## 들어가며

지금까지 작성한 예제 프로그램은 대부분 한 줄씩 순서대로 실행되고, 각 줄이 끝나야 다음 줄로 넘어갔습니다. 그런데 실무에서 작성하는 프로그램은 종종 "시간이 걸리는 작업"을 다뤄야 합니다. 서버에 네트워크 요청을 보내고 응답을 기다리거나, 파일을 읽고 쓰거나, 데이터베이스에 쿼리를 보내는 작업이 대표적입니다. 이런 작업은 보통 몇 밀리초에서 몇 초까지 걸릴 수 있는데, 그 시간 동안 프로그램이 아무것도 못 하고 멈춰 있다면 사용자 경험이 크게 나빠집니다.

이 장에서는 이 문제를 Kotlin이 어떻게 해결하는지, 즉 코루틴(coroutine)이라는 개념을 배웁니다. 코루틴은 7장에서 배운 함수 호출의 개념을 확장한 것이라고 볼 수 있습니다. 함수가 어떻게 "중간에 멈췄다가 나중에 이어서 실행"할 수 있는지, 그리고 이 능력이 왜 프로그램의 응답성을 크게 개선하는지 하나씩 살펴보겠습니다.

## 문제 상황: 스레드를 블로킹한다는 것

먼저 코루틴 없이 시간이 걸리는 작업을 처리하면 어떤 일이 벌어지는지 살펴봅시다. 프로그램은 최소 하나의 스레드(thread) 위에서 실행됩니다. 스레드는 코드를 한 줄씩 순서대로 실행하는 실행 단위입니다. 만약 어떤 함수가 네트워크 응답을 기다리는 동안 스레드를 그 자리에 붙잡아 둔다면, 그 스레드는 응답이 올 때까지 다른 어떤 일도 할 수 없습니다. 이를 "스레드를 블로킹(blocking)한다"고 표현합니다.

```kotlin
// 블로킹 방식: 네트워크 응답을 기다리는 동안 스레드가 완전히 멈춥니다.
fun fetchUserBlocking(): String {
    Thread.sleep(2000) // 2초짜리 네트워크 요청을 흉내냄
    return "사용자 데이터"
}

fun main() {
    println("요청을 시작합니다.")
    val result = fetchUserBlocking() // 여기서 2초 동안 스레드가 멈춥니다.
    println(result)
    println("다른 작업을 계속합니다.")
}
```

이 코드는 `fetchUserBlocking()`이 끝날 때까지 `main` 함수의 스레드가 다른 어떤 일도 하지 못합니다. 예를 들어 이 코드가 안드로이드 앱의 메인 스레드(화면을 그리는 스레드)에서 실행되었다면, 그 2초 동안 화면이 멈춘 것처럼 보이고 사용자의 터치에도 반응하지 않게 됩니다. 서버 애플리케이션이라면 그 스레드가 다른 사용자의 요청을 처리하지 못하고 대기 줄에 세워두는 셈입니다.

이를 해결하려고 흔히 쓰는 방법이 별도의 스레드를 만들거나 콜백(callback)을 사용하는 것입니다.

```kotlin
// 콜백 방식: 작업이 끝나면 실행할 함수를 미리 넘겨 둡니다.
fun fetchUserWithCallback(onResult: (String) -> Unit) {
    // 실제로는 별도 스레드나 비동기 API에서 실행되어야 메인 스레드가 안 막힙니다.
    Thread {
        Thread.sleep(2000)
        onResult("사용자 데이터")
    }.start()
}

fun main() {
    println("요청을 시작합니다.")
    fetchUserWithCallback { result ->
        println(result)
        println("다른 작업을 계속합니다.")
    }
    println("콜백을 기다리는 동안 다른 코드를 계속 실행합니다.")
}
```

13장에서 배운 람다를 활용해 콜백을 넘기면 스레드를 블로킹하지 않으면서도 시간이 걸리는 작업을 처리할 수 있습니다. 하지만 이 방식은 작업이 여러 단계로 이어질수록 코드가 급격히 복잡해집니다. "사용자 정보를 가져온 다음, 그 정보로 게시물 목록을 가져오고, 다시 그 목록으로 댓글을 가져오는" 식으로 단계가 늘어나면 콜백 안에 콜백이, 그 안에 또 콜백이 중첩되는 구조가 됩니다. 이런 상태를 흔히 "콜백 지옥(callback hell)"이라고 부릅니다.

```kotlin
// 콜백 지옥의 예: 단계가 늘어날수록 코드가 오른쪽으로 계속 밀려납니다.
fun fetchUserWithCallback(onResult: (String) -> Unit) { /* ... */ }
fun fetchPostsWithCallback(user: String, onResult: (List<String>) -> Unit) { /* ... */ }
fun fetchCommentsWithCallback(post: String, onResult: (List<String>) -> Unit) { /* ... */ }

fun loadEverything() {
    fetchUserWithCallback { user ->
        fetchPostsWithCallback(user) { posts ->
            fetchCommentsWithCallback(posts.first()) { comments ->
                println(comments)
                // 단계가 늘어날수록 들여쓰기가 계속 깊어집니다.
            }
        }
    }
}
```

코틀린의 코루틴은 이 두 가지 문제, 즉 "스레드 블로킹"과 "콜백 지옥"을 동시에 해결하기 위해 설계되었습니다.

## 코루틴이란 무엇인가

코루틴(coroutine)은 실행 중간에 멈추고, 나중에 멈췄던 지점에서 다시 이어서 실행할 수 있는 가벼운 실행 단위입니다. "가볍다"는 것은 스레드보다 만드는 비용과 메모리 사용량이 훨씬 적다는 뜻입니다. 스레드는 보통 수백 개만 만들어도 시스템에 부담이 되지만, 코루틴은 수십만 개를 동시에 만들어도 큰 문제가 되지 않습니다. 그 이유는 코루틴이 스레드 자체를 새로 만드는 것이 아니라, 이미 존재하는 스레드(또는 스레드 풀) 위에서 "번갈아 실행되는 작업 단위"로 동작하기 때문입니다.

핵심 아이디어는 이렇습니다. 코루틴이 네트워크 응답처럼 시간이 걸리는 작업을 기다려야 할 때, 그 코루틴은 스레드를 붙잡고 있지 않고 자기 자신을 "중단(suspend)"시킵니다. 중단된 동안 그 스레드는 다른 코루틴의 작업을 이어서 실행할 수 있습니다. 기다리던 결과가 도착하면, 중단되었던 코루틴은 멈췄던 지점에서 "재개(resume)"되어 나머지 코드를 계속 실행합니다. 이 과정에서 스레드는 한 번도 놀지 않고 계속 일을 하지만, 어떤 코루틴도 응답을 기다리는 동안 스레드를 독점하지 않습니다.

다음 그림은 스레드를 블로킹하는 방식과 코루틴 방식의 차이를 보여줍니다.

```text
블로킹 방식과 코루틴 방식 비교

1) 스레드를 블로킹하는 방식
스레드 1개
  +----------+ +----------------------------+ +----------+ +----------+
  |작업 A 실행| |     네트워크 응답 대기      | |결과 처리 | |작업 B 실행|
  +----------+ |(스레드 블로킹, 다른 일 못 함)| +----------+ +----------+
  ------------------------------------------------------------------> (시간)
                                                          작업 A가 끝날 때까지 시작 못 함

------------------------------------------------------------------------

2) 코루틴을 사용하는 방식 (delay로 중단)
스레드 1개
  +----------+           +--------------+      +----------------+ +------------+
  |코루틴 A 실행|         |  코루틴 B 실행 |      |코루틴 A 결과 처리| |코루틴 B 계속|
  +----------+           +--------------+      +----------------+ +------------+
             ^                          ^
             |                          |
    delay 호출 -> 중단(suspend)   응답 도착 -> 재개(resume)
                          (스레드는 놀지 않고 다른 일을 함)
  ------------------------------------------------------------------> (시간)

핵심 차이: 블로킹 방식은 대기 시간 동안 스레드가 완전히 멈춰 있지만,
코루틴 방식은 대기 중인 코루틴을 "중단"시켜 두고 같은 스레드로 다른 코루틴을 실행합니다.
```

그림 위쪽은 블로킹 방식입니다. 스레드가 네트워크 응답을 기다리는 동안 완전히 멈춰 있고, 다른 작업(작업 B)은 그 스레드가 자유로워질 때까지 시작조차 하지 못합니다. 그림 아래쪽은 코루틴 방식입니다. 코루틴 A가 `delay`를 호출해 중단되는 순간, 같은 스레드가 곧바로 코루틴 B를 실행합니다. 나중에 코루틴 A가 기다리던 응답이 도착하면 A는 멈췄던 지점에서 재개되어 결과를 처리합니다. 스레드 하나로 여러 작업을 번갈아 처리하면서도, 어느 작업도 무한정 기다리게 하지 않는 것이 코루틴의 핵심입니다.

## suspend 함수: 중단할 수 있는 함수

코루틴 안에서 실행되며 중간에 중단될 수 있는 함수를 `suspend` 함수라고 부릅니다. 7장에서 배운 일반 함수 선언 앞에 `suspend` 키워드만 붙이면 됩니다.

```kotlin
// suspend 키워드가 붙은 함수는 중단될 수 있는 함수입니다.
suspend fun fetchUser(): String {
    delay(2000) // 2초 동안 "중단"됩니다. Thread.sleep과 달리 스레드를 블로킹하지 않습니다.
    return "사용자 데이터"
}
```

여기서 `delay()`는 코루틴 라이브러리가 제공하는 함수로, `Thread.sleep()`과 비슷하게 "일정 시간 기다린다"는 동작을 하지만 완전히 다른 방식으로 동작합니다. `Thread.sleep()`은 그 스레드를 강제로 멈춰서 아무 일도 못 하게 만드는 반면, `delay()`는 코루틴을 중단시켜서 그 스레드가 다른 코루틴의 작업을 할 수 있도록 비켜줍니다. 이 장의 예제에서 `delay()`는 실제 네트워크 호출을 흉내 내는 용도로 사용됩니다.

`suspend` 함수에는 중요한 규칙이 하나 있습니다. `suspend` 함수는 반드시 다른 `suspend` 함수 안에서, 또는 코루틴 안에서만 호출할 수 있습니다. 일반 함수(`main` 함수 포함) 안에서 `suspend` 함수를 직접 호출하려고 하면 컴파일 오류가 발생합니다. 이 규칙 덕분에 "이 함수는 중단될 수 있다"는 정보가 코드 전체에 명확하게 전파됩니다. 즉, `suspend` 키워드는 8장에서 배운 널러블 타입(`?`)과 비슷하게, 타입 시스템(정확히는 함수 시그니처) 차원에서 코드를 읽는 사람에게 중요한 정보를 알려주는 역할을 합니다.

## 코루틴 시작하기: launch와 runBlocking

`suspend` 함수는 코루틴 안에서만 호출할 수 있다고 했는데, 그렇다면 최초의 코루틴은 어떻게 시작할까요? 이때 사용하는 함수가 `launch`와 `runBlocking`입니다.

`runBlocking`은 새로운 코루틴을 만들고, 그 코루틴이 끝날 때까지 현재 스레드를 블로킹하며 기다립니다. 이름 그대로 "블로킹하며 실행한다"는 뜻입니다. 주로 `main` 함수나 테스트 코드처럼, 프로그램이 코루틴의 결과를 기다렸다가 끝나야 하는 최상위 진입점에서 사용합니다.

```kotlin
import kotlinx.coroutines.*

suspend fun fetchUser(): String {
    delay(2000)
    return "사용자 데이터"
}

fun main() = runBlocking {
    // 이 블록 안은 코루틴이므로 suspend 함수를 호출할 수 있습니다.
    println("요청을 시작합니다.")
    val result = fetchUser()
    println(result)
}
```

`launch`는 새로운 코루틴을 시작하되, 그 코루틴이 끝나기를 기다리지 않고 곧바로 다음 코드로 넘어갑니다. 여러 작업을 동시에 진행하고 싶을 때 사용합니다.

```kotlin
import kotlinx.coroutines.*

suspend fun fetchUser(): String {
    delay(2000)
    return "사용자 데이터"
}

suspend fun fetchNotifications(): String {
    delay(1000)
    return "알림 3개"
}

fun main() = runBlocking {
    println("요청을 시작합니다.")

    launch {
        val notifications = fetchNotifications()
        println(notifications) // 약 1초 후 출력
    }

    launch {
        val user = fetchUser()
        println(user) // 약 2초 후 출력
    }

    println("두 요청이 동시에 진행 중입니다.")
}
```

이 코드를 실행하면 "요청을 시작합니다.", "두 요청이 동시에 진행 중입니다."가 먼저 출력되고, 약 1초 후 알림 결과가, 약 2초 후 사용자 결과가 출력됩니다. 두 `suspend` 함수가 순서대로 4초를 기다리는 것이 아니라, 동시에 진행되어 총 2초 정도만 걸린다는 점에 주목해야 합니다. 이것이 바로 코루틴이 스레드를 블로킹하지 않고 여러 작업을 동시에 처리할 수 있다는 것을 보여주는 예시입니다.

## 콜백 지옥과 비교했을 때의 장점

앞서 콜백으로 작성했던 "사용자 → 게시물 → 댓글" 예제를 코루틴으로 다시 작성해 봅시다.

```kotlin
suspend fun fetchUser(): String {
    delay(500)
    return "사용자"
}

suspend fun fetchPosts(user: String): List<String> {
    delay(500)
    return listOf("게시물1", "게시물2")
}

suspend fun fetchComments(post: String): List<String> {
    delay(500)
    return listOf("댓글1", "댓글2")
}

fun main() = runBlocking {
    val user = fetchUser()
    val posts = fetchPosts(user)
    val comments = fetchComments(posts.first())
    println(comments)
}
```

콜백 버전과 비교하면 차이가 뚜렷합니다. 코루틴 버전은 마치 블로킹 코드를 그대로 순서대로 작성한 것처럼 보이지만, 실제로는 각 `suspend` 함수 호출 지점에서 필요하다면 스레드를 놓아주고 다른 작업에 양보합니다. 들여쓰기가 오른쪽으로 계속 밀려나는 콜백 지옥 없이, 마치 동기 코드를 읽듯이 자연스럽게 위에서 아래로 읽을 수 있습니다. 이는 6장에서 다룬 반복문이나 5장의 제어문처럼 익숙한 순차적 흐름을 그대로 유지하면서도, 내부적으로는 비동기적으로 동작한다는 뜻입니다.

## 정리: 코루틴을 쓰는 이유

지금까지 살펴본 내용을 정리하면, 코루틴을 사용하는 이유는 크게 두 가지입니다. 첫째, 시간이 걸리는 작업을 처리할 때 스레드를 블로킹하지 않아서 프로그램(또는 앱의 화면, 서버의 다른 요청 처리)이 계속 반응할 수 있습니다. 둘째, 콜백을 겹겹이 쌓지 않고도 비동기 코드를 순차적인 코드처럼 자연스럽게 작성할 수 있습니다.

이 장에서는 코루틴을 시작하는 가장 기본적인 도구인 `suspend`, `launch`, `runBlocking`, `delay`만 다뤘습니다. 실제 프로젝트에서는 `async`로 값을 반환하는 코루틴을 만들거나, `Job`으로 코루틴을 취소하거나, `Dispatcher`로 코루틴이 실행될 스레드(풀)를 지정하는 등 더 다양한 도구를 사용하게 됩니다. 하지만 그 모든 도구의 기반은 이 장에서 배운 "중단과 재개"라는 개념입니다. 코루틴은 안드로이드 앱에서 네트워크 요청과 화면 갱신을 함께 다룰 때, 또는 Ktor나 Spring 같은 서버 프레임워크에서 다수의 요청을 효율적으로 처리할 때 Kotlin 생태계 전반에서 표준처럼 쓰이고 있습니다. 17장에서는 이런 Kotlin만의 기능들이 기존 Java 코드와 어떻게 상호운용되는지 살펴보고, 18장에서는 코루틴을 포함해 지금까지 배운 내용을 좋은 코드 습관으로 정리합니다.

## 요약

- 시간이 걸리는 작업(네트워크 요청 등)을 처리할 때 스레드를 그대로 붙잡아 두면(블로킹), 그 스레드는 대기 시간 동안 다른 일을 하지 못합니다.
- 콜백으로 블로킹을 피할 수는 있지만, 작업 단계가 늘어날수록 콜백이 중첩되어 코드가 읽기 어려워지는 "콜백 지옥"이 발생합니다.
- 코루틴은 스레드보다 훨씬 가벼운 실행 단위로, 시간이 걸리는 작업을 만나면 스레드를 블로킹하는 대신 자신을 중단(suspend)시키고, 나중에 재개(resume)됩니다. 그 사이 스레드는 다른 코루틴의 작업을 처리할 수 있습니다.
- `suspend` 키워드가 붙은 함수는 중단될 수 있는 함수이며, 반드시 다른 `suspend` 함수나 코루틴 안에서만 호출할 수 있습니다.
- `runBlocking`은 코루틴이 끝날 때까지 현재 스레드를 기다리게 하고, `launch`는 코루틴을 시작한 뒤 기다리지 않고 다음 코드로 넘어갑니다.
- `delay()`는 `Thread.sleep()`과 달리 스레드를 블로킹하지 않고 코루틴만 중단시키므로, 같은 시간 동안 다른 코루틴이 그 스레드를 활용할 수 있습니다.
- 코루틴을 사용하면 비동기 코드를 콜백 중첩 없이 순차적인 코드처럼 자연스럽게 작성할 수 있습니다.

## 연습문제

1. "스레드를 블로킹한다"는 것이 무슨 의미인지, 그리고 그것이 왜 문제가 되는지 설명해 보세요.
2. `Thread.sleep()`과 `delay()`의 차이를 설명해 보세요.
3. `suspend` 함수는 왜 일반 함수 안에서 직접 호출할 수 없는지, 그리고 이 제약이 코드를 읽는 사람에게 어떤 정보를 주는지 설명해 보세요.
4. `launch`를 사용해 서로 다른 대기 시간을 가진 두 개의 `suspend` 함수를 동시에 실행하는 코드를 작성하고, 순차적으로 실행했을 때와 비교해 전체 실행 시간이 어떻게 달라지는지 설명해 보세요.
5. 이 장에서 다룬 "사용자 → 게시물 → 댓글" 예제를 콜백 방식과 코루틴 방식으로 각각 작성해 보고, 어떤 부분에서 가독성 차이가 나는지 자신의 말로 정리해 보세요.

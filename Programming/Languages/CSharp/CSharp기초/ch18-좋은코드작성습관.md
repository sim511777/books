지금까지 우리는 "문법적으로 동작하는 코드"를 작성하는 법을 배웠습니다. 변수를 선언하고, 조건문과 반복문으로 흐름을 제어하고, 클래스로 데이터와 동작을 묶고, 예외와 비동기까지 다뤄봤습니다. 이 마지막 장에서는 관점을 조금 바꿔서, "동작은 하지만 나중에 문제를 일으키기 쉬운 코드"와 "동작하면서도 안전하고 읽기 좋은 코드"의 차이를 만드는 습관들을 정리합니다. 여기서 다루는 내용 중 상당수는 앞 장에서 이미 조금씩 언급했던 것들을 한자리에 모아 완성하는 성격을 갖습니다.

## 네이밍 컨벤션 총정리

C# 커뮤니티는 오랫동안 굳어진 이름 짓기 규칙을 공유합니다. 지금까지 예제 코드 곳곳에서 자연스럽게 따라온 규칙이지만, 여기서 한 번에 정리해보겠습니다.

| 대상 | 표기법 | 예시 |
|---|---|---|
| 클래스, 구조체, 열거형, 인터페이스, 레코드 | PascalCase | `Customer`, `OrderStatus`, `IComparable` |
| 메서드 | PascalCase | `CalculateTotal()`, `SaveAsync()` |
| 속성(property), 이벤트 | PascalCase | `Name`, `IsValid`, `PriceChanged` |
| 지역 변수, 매개변수 | camelCase | `totalPrice`, `customerName` |
| private 필드 | `_camelCase` | `_orderCount`, `_logger` |
| 상수(`const`), `static readonly` 필드 | PascalCase | `MaxRetryCount`, `DefaultTimeout` |
| 제네릭 타입 매개변수 | `T` 또는 `T` + 의미 있는 이름 | `T`, `TKey`, `TValue`, `TResult` |
| 인터페이스 | 이름 앞에 `I` | `IDisposable`, `IEnumerable<T>` |

몇 가지는 특히 헷갈리기 쉬워서 짚어두겠습니다. C나 C++에서 상수를 `MAX_RETRY_COUNT`처럼 모두 대문자와 밑줄로 쓰던 습관이 있다면, C#에서는 `const`나 `static readonly`로 선언한 상수도 `MaxRetryCount`처럼 PascalCase를 쓴다는 점이 다릅니다. 인터페이스 이름에 `I`를 붙이는 규칙은 9장과 10장에서 다룬 클래스, 상속 문법과 함께 자주 등장하니 익혀두면 좋습니다. 제네릭은 13장에서 배운 대로, 타입 매개변수가 하나뿐이면 그냥 `T`를 쓰고, `Dictionary<TKey, TValue>`처럼 여러 개이거나 의미를 분명히 하고 싶을 때는 `T` 뒤에 설명을 붙입니다.

이런 규칙을 지키는 이유는 단순히 "관습이니까"가 아닙니다. `_orderCount`라는 이름만 보고도 이것이 클래스의 private 필드라는 것을 알 수 있고, `CalculateTotalAsync()`라는 이름만 보고도 이 메서드가 `Task`를 반환하며 `await`가 필요하다는 것을 짐작할 수 있습니다. 이름 짓는 규칙이 곧 코드에 대한 정보를 전달하는 통로가 되는 것입니다.

## Nullable Reference Types: null 참조를 미리 막는 최신 관행

3장에서 값 타입과 참조 타입을 배울 때, 참조 타입 변수는 아무 객체도 가리키지 않는 상태인 `null`이 될 수 있다는 것을 배웠습니다. 그리고 15장에서는 `null`인 참조의 멤버에 접근하려 할 때 `NullReferenceException`이 발생한다는 것도 확인했습니다. 문제는 코드만 봐서는 어떤 참조 타입 변수가 `null`이 될 수 있는지, 절대 `null`이 되지 않는지를 구분할 방법이 없었다는 점입니다.

C# 8.0부터 도입된 nullable reference types는 바로 이 구분을 컴파일러에게 알려주는 기능입니다. 파일 맨 위에 다음 지시문을 추가하거나, 프로젝트 파일(`.csproj`)에서 전체 프로젝트에 대해 활성화할 수 있습니다.

```csharp
#nullable enable
```

```xml
<!-- .csproj 파일에 추가하면 프로젝트 전체에 적용됨 -->
<PropertyGroup>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

이 기능을 켠 상태에서는 참조 타입의 의미가 둘로 나뉩니다. `string`처럼 물음표 없이 쓴 타입은 "`null`이 되어서는 안 되는 타입"이고, `string?`처럼 물음표를 붙인 타입은 "`null`이 될 수도 있는 타입"입니다.

```csharp
#nullable enable

string name = "지민";      // null이 아니어야 하는 문자열
string? nickname = null;   // null이 될 수 있는 문자열, 명시적으로 표시

Console.WriteLine(name.Length);      // 안전, name은 null이 아님이 보장됨
Console.WriteLine(nickname.Length);  // 컴파일러 경고: nickname은 null일 수 있음
```

`nickname.Length`처럼 `null`일 수 있는 값의 멤버에 별다른 확인 없이 접근하면 컴파일러가 경고를 띄웁니다. 이 경고는 프로그램을 실행하기도 전에 "여기서 `NullReferenceException`이 날 수도 있다"고 미리 알려주는 것입니다. 이런 경고를 마주했을 때는 값이 실제로 `null`인지 먼저 확인하는 습관을 들이면 됩니다.

```csharp
if (nickname is not null)
{
    Console.WriteLine(nickname.Length); // 이 블록 안에서는 경고가 사라짐
}

// 혹은 null이면 대체 값을 쓰는 null 병합 연산자
Console.WriteLine((nickname ?? "닉네임 없음").Length);
```

nullable reference types는 문법을 하나 더 배우는 것이 아니라, "이 값은 없을 수도 있다"는 사실을 타입 시스템에 드러내어 실수를 컴파일 시점으로 끌어오는 도구입니다. 새로 시작하는 프로젝트라면 처음부터 활성화해두는 것을 권장합니다.

## 앞 장에서 만났던 흔한 실수들, 다시 정리하기

여기서는 새로운 내용을 배우는 대신, 지금까지 각 장에서 흩어져 있던 "자주 발생하는 실수"들을 한자리에 모아 정리합니다.

**NullReferenceException.** 15장에서 다뤘던 대표적인 실행 시점 예외입니다. 객체를 생성하지 않고 선언만 한 변수(`Person person;`)를 그대로 사용하거나, 메서드가 조건에 따라 `null`을 반환할 수 있다는 것을 놓치고 결과를 바로 사용할 때 발생합니다. 위에서 본 nullable reference types를 활성화해두면 이런 지점의 상당수를 컴파일 시점에 미리 발견할 수 있습니다.

**값 타입과 참조 타입 혼동.** 3장과 9장에서 다룬 내용입니다. `struct`(12장의 구조체 포함)는 대입하거나 메서드에 전달할 때 값 전체가 복사되고, `class`는 참조(주소)만 복사되어 원본과 복사본이 같은 객체를 공유합니다. 구조체를 클래스처럼 "복사해도 원본이 같이 바뀌겠지"라고 착각하거나, 반대로 클래스를 구조체처럼 "복사했으니 독립적이겠지"라고 착각하는 실수가 흔합니다. 헷갈릴 때는 "이 타입이 `class`인지 `struct`인지"부터 확인하는 습관이 필요합니다.

**`==`와 `Equals`의 차이.** 기본 타입(`int`, `bool` 등)과 `string`은 `==`가 값을 비교하도록 미리 정의되어 있어서 `"abc" == "abc"`는 `true`입니다. 하지만 직접 만든 클래스는 `==`를 따로 재정의하지 않는 한 참조(주소)를 비교합니다. 즉 필드 값이 완전히 같은 두 객체라도 `==`로 비교하면 `false`가 나올 수 있습니다. 값을 기준으로 같음을 비교하려면 `Equals`를 오버라이드하거나 (10장의 오버라이드 개념), 값 비교가 기본으로 제공되는 레코드 타입(record)을 쓰는 것도 방법입니다.

**`for`문의 경계값 실수(off-by-one).** 6장과 7장에서 다룬 배열/컬렉션 순회에서 `<=`와 `<`를 헷갈려 `IndexOutOfRangeException`을 내거나, 마지막 요소를 하나 빼먹는 실수입니다. 배열과 `List<T>`의 유효한 인덱스는 항상 `0`부터 `Length - 1`(또는 `Count - 1`)까지라는 것을 조건식에서 다시 확인하는 습관이 도움이 됩니다.

**`foreach` 순회 중 컬렉션 수정.** 7장과 14장에서 다룬 `foreach`는 순회 중인 컬렉션의 구조(요소 추가/제거)가 바뀌면 `InvalidOperationException`을 던집니다. 순회하면서 값을 지워야 한다면 인덱스 기반 `for`문을 역순으로 사용하거나, LINQ의 `Where`로 새 목록을 만들어 교체하는 방식을 사용합니다.

이 목록에 담긴 실수들은 사실 처음 배울 때 한 번씩은 거의 누구나 겪는 것들입니다. 중요한 것은 이런 실수를 겪었을 때 "무엇이 문제였는지"를 정확히 짚어내고, 다음에는 같은 자리에서 멈춰 서서 한 번 더 확인하는 습관을 들이는 것입니다.

## 코드가 맞게 동작하는지 스스로 확인하기: 단위 테스트

지금까지는 코드가 잘 동작하는지 `Console.WriteLine`으로 값을 출력해 눈으로 확인하는 방식을 주로 사용했습니다. 이 방식은 간단한 예제에는 충분하지만, 코드가 많아질수록 "고친 부분이 다른 곳을 망가뜨리지 않았는지"를 매번 눈으로 확인하기는 어려워집니다. 이런 문제를 해결하기 위한 도구가 단위 테스트(unit test)입니다. 단위 테스트는 함수나 메서드 하나가 "특정 입력에 대해 기대한 결과를 내는지"를 코드로 작성해두고, 필요할 때마다 자동으로 실행해 검증하는 방법입니다.

.NET 생태계에는 xUnit, NUnit, MSTest 같은 테스트 프레임워크가 있으며, 이 중 xUnit과 NUnit이 특히 널리 쓰입니다. 사용하는 프레임워크에 따라 문법은 조금씩 다르지만, 기본 형태는 대체로 비슷합니다.

```csharp
// xUnit을 사용한 테스트 코드의 형태만 살짝 엿보기
public class CalculatorTests
{
    [Fact]
    public void Add_TwoPositiveNumbers_ReturnsSum()
    {
        int result = Calculator.Add(2, 3);

        Assert.Equal(5, result);
    }
}
```

이 책에서는 단위 테스트를 직접 다루지는 않지만, 앞으로 실무 코드를 작성하게 되면 반드시 마주치게 될 개념이므로 이름과 존재 목적만은 기억해두길 권합니다. "테스트를 작성해둔 코드는 나중에 마음 놓고 고칠 수 있다"는 감각은 코드가 커질수록 점점 더 소중해집니다.

## 다음 학습 단계

이 책은 C#이라는 언어 자체의 문법과 기본기를 다루는 데 초점을 맞췄습니다. 여기서 익힌 내용은 어느 분야로 나아가든 공통으로 쓰이는 토대입니다. 앞으로 관심사에 따라 다음과 같은 방향으로 학습을 넓혀갈 수 있습니다.

- **웹 개발**: ASP.NET Core로 웹 API 서버나 웹 애플리케이션을 만드는 방향입니다. 이 책에서 배운 클래스, 인터페이스, 비동기 프로그래밍(17장)이 그대로 활용되며, 여기에 HTTP 요청 처리, 라우팅, 데이터베이스 연동 같은 웹 고유의 개념이 추가됩니다.
- **게임 개발**: Unity 엔진에서 게임 로직을 작성하는 스크립팅 언어가 바로 C#입니다. 클래스와 객체(9장), 상속과 다형성(10장)을 기반으로 게임 오브젝트의 동작을 설계하는 방식을 자연스럽게 확장할 수 있습니다.
- **클라우드와 서버 인프라**: Azure를 비롯한 클라우드 플랫폼에서 C#/.NET으로 서버리스 함수, 마이크로서비스 등을 구축하는 방향입니다. 비동기 프로그래밍과 예외 처리(15장)에 대한 이해가 특히 중요해지는 영역입니다.
- **데스크톱과 모바일 앱**: MAUI나 WPF로 Windows 데스크톱 앱, 혹은 여러 플랫폼을 아우르는 앱을 만드는 방향입니다.

어느 방향을 택하든, 공식 문서를 검색하고 읽는 능력, 그리고 막히는 부분을 작은 예제로 쪼개서 직접 실험해보는 습관이 언어나 프레임워크가 바뀌어도 계속 쓰이는 가장 중요한 역량입니다. 부록에서 이런 공식 자료를 찾아보는 방법을 간단히 안내합니다.

## 체크리스트

이 책을 마무리하며, 코드를 작성하거나 리뷰할 때 스스로 점검해볼 수 있는 목록을 정리합니다.

- [ ] 클래스, 메서드, 속성은 PascalCase, 지역 변수와 매개변수는 camelCase, private 필드는 `_camelCase`로 일관되게 이름 지었는가?
- [ ] 새 프로젝트라면 nullable reference types(`#nullable enable` 또는 `.csproj`의 `<Nullable>enable</Nullable>`)를 활성화했는가?
- [ ] 참조 타입 변수를 사용하기 전에, 그 값이 `null`일 가능성을 고려했는가?
- [ ] 값 타입(`struct`)과 참조 타입(`class`)의 복사 방식 차이를 헷갈리지 않았는가?
- [ ] 객체를 비교할 때 `==`(참조 비교 혹은 재정의된 값 비교)와 `Equals`의 차이를 의도대로 사용했는가?
- [ ] 배열/컬렉션을 순회하는 반복문의 경계값(`<` vs `<=`)이 올바른가?
- [ ] `try-catch`로 예외를 잡을 때, 정말 처리할 수 있는 예외만 잡고 있는가(15장)?
- [ ] `async` 메서드를 `.Result`나 `.Wait()`로 강제로 기다리지 않고 `await`로 이어가고 있는가(17장)?
- [ ] 조건문이나 반복문의 중첩이 너무 깊어져 가독성이 떨어지지 않았는가(조기 반환 등을 고려했는가)?
- [ ] 같은 코드가 여러 곳에 반복되고 있지 않은가(메서드나 클래스로 추출할 여지가 있는가)?

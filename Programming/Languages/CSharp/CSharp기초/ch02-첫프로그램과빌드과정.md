# 2장. 첫 프로그램과 빌드 과정

[◀ 이전: 1장. C#이란 무엇인가](ch01-c샵이란.md) | [📖 목차](00-목차.md) | [다음: 3장. 변수와 자료형 ▶](ch03-변수와자료형.md)

---

1장에서 C#이 어떤 언어인지 살펴봤으니, 이제 실제로 손을 움직여 첫 프로그램을 만들어볼 차례입니다. 이 장에서는 화면에 문자열을 출력하는 아주 짧은 프로그램을 두 가지 방식으로 작성해보고, 그 코드가 `dotnet` 명령을 통해 어떻게 빌드되고 실행되는지, 그리고 그 과정에서 코드가 내부적으로 어떤 단계를 거치는지를 살펴봅니다.

## 프로젝트 만들기

C# 코드는 보통 "프로젝트" 단위로 관리됩니다. 터미널에서 다음 명령을 실행하면 콘솔 프로그램을 위한 프로젝트 하나가 새로 만들어집니다.

```csharp
// 터미널(PowerShell, cmd, bash 등)에 입력하는 명령입니다.
// dotnet new console -o HelloCSharp
```

이 명령을 실행하면 `HelloCSharp`이라는 폴더가 생기고, 그 안에 `HelloCSharp.csproj`(프로젝트 설정 파일)와 `Program.cs`(실제 C# 코드 파일)가 만들어집니다. `.csproj` 파일은 이 프로젝트가 어떤 .NET 버전을 사용하는지, 어떤 종류의 프로그램인지(콘솔 앱, 라이브러리 등) 등을 담고 있는 설정 파일이고, 지금 단계에서는 자세히 들여다볼 필요는 없습니다. 우리가 관심 있는 파일은 `Program.cs`입니다.

## Hello World, 두 가지 방식

### 최신 방식: top-level statements

.NET 6부터 도입된 최신 문법을 사용하면 `Program.cs`는 다음처럼 아주 짧게 작성할 수 있습니다.

```csharp
// Program.cs
// 클래스나 Main 메서드 선언 없이 곧바로 실행 코드를 적을 수 있습니다.
Console.WriteLine("Hello, C#!");
```

이 방식을 top-level statements(최상위 문)라고 부릅니다. 클래스 선언이나 `Main` 메서드 같은 상용구(boilerplate) 없이, 파일 맨 위에서부터 곧바로 실행할 코드를 적을 수 있습니다. `dotnet new console`로 새 프로젝트를 만들면 기본적으로 이 방식으로 파일이 생성됩니다. 처음 배우는 사람에게는 이 방식이 훨씬 부담이 적기 때문에, 이 책의 앞부분 예제 대부분은 이 방식을 기준으로 작성합니다.

### 전통적 방식: Main 메서드

하지만 실제로 C# 컴파일러는 위 코드를 내부적으로 아래와 같은 형태로 변환해서 처리합니다. 이 전통적인 방식은 지금도 많은 실무 코드와 예전에 작성된 코드에서 쓰이고 있으므로 반드시 읽는 법을 알아야 합니다.

```csharp
// 전통적인 Main 메서드 방식
using System;

namespace HelloCSharp
{
    // 모든 실행 가능한 C# 프로그램은 진입점(entry point) 역할을 하는
    // Main 메서드를 하나 가지고 있어야 합니다.
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello, C#!");
        }
    }
}
```

두 코드는 실행 결과가 완전히 동일합니다. `class Program`은 프로그램의 진입점을 담을 클래스이고, `static void Main(string[] args)`는 프로그램이 시작될 때 .NET 런타임이 가장 먼저 호출하는 메서드입니다. `args`는 프로그램을 실행할 때 함께 전달된 명령줄 인수를 담는 배열인데, 지금은 사용하지 않으므로 자세한 내용은 8장 함수(메서드)에서 다시 다룹니다. 클래스와 메서드가 정확히 무엇인지는 9장 클래스와 객체에서 본격적으로 배우게 되니, 지금은 "실행 가능한 C# 프로그램에는 시작점이 하나 필요하고, top-level statements는 그 시작점을 컴파일러가 자동으로 만들어주는 문법적 설탕(syntactic sugar)이다"라는 정도로 이해하면 충분합니다.

## dotnet run과 dotnet build

프로젝트 폴더 안에서 다음 명령을 실행하면 코드를 빌드하고 곧바로 실행까지 해줍니다.

```csharp
// 터미널 명령
// dotnet run
```

`dotnet run`은 내부적으로 두 단계를 순서대로 수행합니다. 먼저 소스 코드를 빌드하고, 빌드가 성공하면 그 결과물을 곧바로 실행합니다. 만약 빌드 결과물만 만들고 실행은 나중에 하고 싶다면 다음 명령을 사용합니다.

```csharp
// 터미널 명령
// dotnet build
```

`dotnet build`를 실행하면 프로젝트 폴더 아래 `bin` 폴더 안에 실행 파일과 함께 여러 파일이 생성됩니다. 이렇게 만들어진 결과물은 `dotnet bin/Debug/net8.0/HelloCSharp.dll`처럼 직접 실행할 수도 있습니다. 개발 중에는 `dotnet run`으로 빌드와 실행을 한 번에 처리하고, 배포용 결과물만 필요할 때는 `dotnet build`나 `dotnet publish`(배포용 결과물을 만드는 명령)를 사용하는 것이 일반적인 흐름입니다.

## 소스 코드가 실행되기까지: 빌드 파이프라인

`dotnet run` 한 번으로 코드가 바로 실행되니 간단해 보이지만, 그 뒤에서는 몇 단계의 변환이 일어납니다. 이 흐름을 이해하면 "왜 C# 프로그램이 여러 운영체제에서 동일하게 실행되는지", "왜 처음 실행할 때 살짝 느리다가 그 다음부터는 빨라지는지" 같은 질문에 답할 수 있습니다.

```text
                     C# 소스 코드가 실행되기까지

+-------------+  컴파일  +---------------+  생성  +----------------+  실행시점  +------------------+
|  소스 코드   | -------> |  C# 컴파일러   | -----> |    IL 코드      | --------> |   JIT 컴파일러    |
|Program.cs   |          |  (Roslyn)     |        |  (중간 언어)     |           |  (.NET 런타임)    |
|사람이 작성한 |          |문법 검사 후    |        |.dll / .exe     |           |IL을 CPU가 이해하는|
|C# 텍스트     |          |IL로 번역       |        |어셈블리 파일     |           |네이티브 코드로 변환|
+-------------+          +---------------+        +----------------+           +------------------+
                          <---- dotnet build ---------------->                          |
                                                                                         v
                                                                                +------------------+
                                                                                | 네이티브 코드 실행 |
                                                                                |      CPU          |
                                                                                | 실제 결과 출력      |
                                                                                +------------------+

- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
       dotnet run 명령 한 번이면 이 과정 전체가 자동으로 이어집니다
```

1. **소스 코드**: 우리가 작성한 `Program.cs` 같은 텍스트 파일입니다. 사람이 읽고 쓰기 위한 형태일 뿐, 이 상태로는 컴퓨터가 직접 실행할 수 없습니다.
2. **C# 컴파일러(Roslyn)**: `dotnet build`나 `dotnet run`을 실행하면 C# 컴파일러가 소스 코드의 문법을 검사합니다. 이 단계에서 오타나 문법 오류가 있으면 여기서 멈추고 오류 메시지를 보여줍니다. 문제가 없으면 컴파일러는 소스 코드를 IL(Intermediate Language, 중간 언어)이라는 형태로 번역합니다.
3. **IL 코드**: IL은 특정 CPU 종류(Intel, ARM 등)에 종속되지 않는 중간 형태의 명령어 집합입니다. 이 IL 코드는 `.dll`이나 `.exe` 확장자를 가진 어셈블리(assembly) 파일에 담깁니다. 같은 IL 파일이 Windows, macOS, Linux 어디서든 동일하게 실행될 수 있다는 점이 .NET의 크로스플랫폼 특성을 만드는 핵심입니다.
4. **JIT 컴파일러**: 프로그램을 실제로 실행하는 순간, .NET 런타임에 포함된 JIT(Just-In-Time) 컴파일러가 IL 코드를 그때그때 그 컴퓨터의 CPU가 이해할 수 있는 네이티브 코드로 변환합니다. "Just-In-Time"이라는 이름대로, 미리 전부 변환해두는 것이 아니라 실제로 필요한 순간에 필요한 부분만 변환하는 방식입니다.
5. **실행**: 변환된 네이티브 코드를 CPU가 실행하고, 그 결과로 우리가 원하던 출력(`Hello, C#!`이라는 문자열)이 화면에 나타납니다.

정리하면, C# 코드는 "소스 코드 → IL → 네이티브 코드"라는 두 번의 변환을 거쳐 실행됩니다. 이 구조는 Java의 "소스 코드 → 바이트코드 → JVM이 실행"이라는 구조와 매우 비슷합니다. 반면 C나 C++처럼 컴파일 시점에 곧바로 네이티브 코드를 만들어내는 언어와는 이 지점에서 차이가 생깁니다. C#은 그 대가로 플랫폼 독립성과, 실행 중에 코드를 최적화할 수 있는 유연성을 얻습니다.

## 흔한 컴파일 오류와 대처법

프로그래밍을 시작하면 컴파일 오류를 만나는 일이 훨씬 더 잦습니다. 오류 메시지를 두려워하지 말고, 무엇을 알려주는지 차분히 읽는 습관을 들이는 것이 중요합니다. 자주 마주치는 몇 가지를 살펴보겠습니다.

**세미콜론을 빠뜨린 경우**

```csharp
Console.WriteLine("Hello, C#!")
```

이 코드를 빌드하면 `; expected`라는 오류가 나타납니다. C#은 문장(statement)의 끝을 세미콜론으로 표시하므로, 문장마다 세미콜론을 붙이는 습관을 들여야 합니다. 처음에는 자주 빠뜨리지만 금방 익숙해집니다.

**괄호나 중괄호 짝이 맞지 않는 경우**

```csharp
static void Main(string[] args)
{
    Console.WriteLine("Hello, C#!");
// 닫는 중괄호가 없습니다.
```

이런 경우 `} expected` 오류가 나타납니다. 대부분의 에디터는 중괄호 짝을 자동으로 표시해주므로, 오류가 나면 에디터의 중괄호 강조 기능을 활용해 짝이 맞는지 확인하는 것이 빠릅니다.

**이름을 잘못 쓴 경우**

```csharp
consle.WriteLine("Hello, C#!");
```

`Console`을 `consle`로 잘못 입력하면 `The name 'consle' does not exist in the current context`라는 오류가 나타납니다. 이런 오류는 대소문자를 포함해 정확한 이름을 입력했는지 확인하면 해결됩니다. C#은 대소문자를 구분하는 언어이므로 `Console`과 `console`은 서로 다른 이름으로 취급됩니다.

**타입이 맞지 않는 경우**

```csharp
int number = "문자열";
```

`int` 자료형의 변수에 문자열을 대입하면 `Cannot implicitly convert type 'string' to 'int'`라는 오류가 나타납니다. 이런 오류는 1장에서 이야기한 정적 타입 언어의 특성이 그대로 드러나는 사례입니다. 자료형에 대해서는 3장 변수와 자료형에서 자세히 다룹니다.

이런 오류 메시지들은 처음에는 낯설게 느껴지지만, 대부분 "무엇이 어디에서 문제인지"를 상당히 구체적으로 알려줍니다. 오류 메시지에 나온 파일명과 줄 번호를 먼저 확인하고, 메시지에 등장하는 핵심 단어(`expected`, `does not exist`, `cannot convert` 등)를 중심으로 원인을 찾아가는 습관을 들이면 디버깅 속도가 눈에 띄게 빨라집니다.

## 요약

- 콘솔 프로젝트는 `dotnet new console`로 만들며, 실제 코드는 `Program.cs`에 작성합니다.
- 최신 C#은 top-level statements를 지원해 클래스와 `Main` 메서드 선언 없이 코드를 곧바로 작성할 수 있으며, 이는 전통적인 `Main` 메서드 방식을 컴파일러가 자동으로 생성해주는 것과 동일합니다.
- `dotnet run`은 빌드와 실행을 한 번에 처리하고, `dotnet build`는 빌드만 수행합니다.
- C# 소스 코드는 컴파일러(Roslyn)에 의해 IL(중간 언어)로 변환되고, 실행 시점에 JIT 컴파일러가 이를 그 컴퓨터의 네이티브 코드로 다시 변환한 뒤 CPU가 실행합니다.
- 흔한 컴파일 오류는 세미콜론 누락, 괄호/중괄호 짝 불일치, 이름 오타, 타입 불일치 등이며, 오류 메시지를 차분히 읽는 습관이 중요합니다.

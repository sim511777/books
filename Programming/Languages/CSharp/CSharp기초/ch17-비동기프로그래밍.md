지금까지 작성한 예제 코드는 모두 위에서 아래로, 한 문장이 끝나야 다음 문장이 시작되는 방식으로 흘러갔습니다. 대부분의 연산은 CPU가 순식간에 처리하기 때문에 이 방식에 별문제가 없었습니다. 그런데 실제 프로그램은 네트워크로 데이터를 요청하거나, 큰 파일을 디스크에서 읽거나, 데이터베이스의 응답을 기다리는 등 "시간이 오래 걸리는 대기"가 끊임없이 발생합니다. 이런 대기를 지금까지 배운 방식대로 처리하면 프로그램 전체가 그 시간만큼 멈춰버립니다. 이 장에서는 대기 시간 동안 프로그램이 멈추지 않도록 해주는 C#의 비동기 프로그래밍(asynchronous programming)을 다룹니다.

## 동기적으로 오래 걸리는 작업을 처리할 때 생기는 문제

네트워크에서 데이터를 받아오는 상황을 흉내 낸 코드를 보겠습니다. 실제 네트워크 호출 대신 `Thread.Sleep`으로 "3초가 걸리는 작업"을 만들어 보겠습니다.

```csharp
using System.Diagnostics;

string DownloadData()
{
    Console.WriteLine("다운로드를 시작합니다...");
    Thread.Sleep(3000); // 네트워크 응답을 기다리는 상황을 흉내냄
    Console.WriteLine("다운로드가 끝났습니다.");
    return "받아온 데이터";
}

Console.WriteLine("프로그램 시작");

string data = DownloadData();
Console.WriteLine($"결과: {data}");

Console.WriteLine("프로그램 종료");
```

이 코드를 실행하면 "다운로드를 시작합니다..."가 출력된 뒤 정확히 3초 동안 아무 일도 일어나지 않습니다. 이 3초 동안 프로그램을 실행하는 스레드는 `Thread.Sleep` 안에서 완전히 멈춰 있습니다. 콘솔 프로그램에서는 이 정도로 크게 불편하지 않을 수 있지만, 다음과 같은 상황이라면 이야기가 달라집니다.

- **화면이 있는 프로그램**이라면, 버튼을 클릭했을 때 이런 코드가 실행되는 순간 화면을 그리는 스레드까지 함께 멈춰버립니다. 사용자는 창을 옮기거나 다른 버튼을 눌러도 아무 반응이 없는 "응답 없음" 상태를 마주하게 됩니다.
- **여러 사용자의 요청을 처리하는 서버**라면, 한 요청을 처리하는 스레드가 3초 동안 아무 일도 못하고 대기만 합니다. 동시에 접속한 사용자가 많아질수록 이렇게 낭비되는 스레드가 쌓이고, 결국 새로운 요청을 처리할 스레드가 모자라게 됩니다.

두 경우 모두 핵심 문제는 같습니다. 스레드가 "대기"라는, 사실상 CPU를 전혀 쓰지 않는 시간 동안에도 다른 일을 하지 못하고 붙잡혀 있다는 것입니다. 비동기 프로그래밍은 바로 이 문제, 즉 대기하는 동안 스레드를 놓아주고 다른 작업을 할 수 있게 만드는 것을 목표로 합니다.

## Task와 Task&lt;T&gt;: 진행 중인 작업을 나타내는 객체

C#에서 비동기 작업의 중심에는 `Task`와 `Task<T>`가 있습니다. 이 둘은 "지금 당장은 끝나지 않았지만, 언젠가 끝날 작업"을 나타내는 객체입니다.

- `Task`는 결과값 없이 어떤 동작이 완료되는 것 자체를 나타냅니다. `void`를 반환하는 동기 메서드에 대응한다고 생각하면 됩니다.
- `Task<T>`는 작업이 끝나면 `T` 형의 결과값을 돌려준다는 뜻입니다. `T`를 반환하는 동기 메서드에 대응합니다. 13장에서 배운 제네릭이 바로 여기서 쓰이는데, `Task<string>`은 "언젠가 문자열을 돌려주는 작업", `Task<int>`는 "언젠가 정수를 돌려주는 작업"이라는 뜻이 됩니다.

`Task`와 `Task<T>`는 "작업을 시켜놓은 영수증" 같은 존재입니다. 영수증 자체로는 아직 물건을 받은 게 아니지만, 나중에 이 영수증을 들고 가면 완성된 결과를 받을 수 있습니다. 이 영수증을 손에 쥔 채로 다른 일을 계속하다가, 결과가 필요한 시점에 결과를 받아오는 것이 비동기 프로그래밍의 기본 그림입니다.

## async와 await로 비동기 메서드 작성하기

`Task`를 실제로 만들어내는 메서드는 `async` 키워드로 선언합니다. 그리고 그 메서드 안에서 다른 비동기 작업의 완료를 기다릴 때는 `await` 키워드를 사용합니다. 앞서 본 `Thread.Sleep` 예제를 비동기 버전으로 바꿔보겠습니다. 이번에는 `Task.Delay`를 사용합니다.

```csharp
async Task<string> DownloadDataAsync()
{
    Console.WriteLine("다운로드를 시작합니다...");
    await Task.Delay(3000); // 네트워크 응답을 기다리는 상황을 흉내냄 (스레드를 붙잡지 않음)
    Console.WriteLine("다운로드가 끝났습니다.");
    return "받아온 데이터";
}

Console.WriteLine("프로그램 시작");

string data = await DownloadDataAsync();
Console.WriteLine($"결과: {data}");

Console.WriteLine("프로그램 종료");
```

겉보기에는 `Thread.Sleep` 버전과 거의 비슷해 보이지만, 실행되는 방식은 근본적으로 다릅니다. `await Task.Delay(3000)`을 만나면 `DownloadDataAsync` 메서드의 실행은 그 자리에서 일시 중단되고, 스레드는 곧바로 호출한 곳으로 돌아가 다른 일을 할 수 있게 됩니다. 3초가 지나 `Task.Delay`가 완료되면, 중단되었던 지점부터 나머지 코드("다운로드가 끝났습니다." 출력과 `return`)가 이어서 실행됩니다. `Thread.Sleep`은 스레드를 붙잡고 강제로 재우는 것이고, `await Task.Delay`는 스레드를 놓아주고 "때가 되면 알려달라"고 예약해두는 것이라는 차이를 기억해두면 좋습니다.

몇 가지 규칙도 함께 짚어두겠습니다.

- `async` 메서드의 이름은 관례적으로 `Async` 접미사를 붙입니다. 위 예제의 `DownloadDataAsync`처럼요. 이는 문법적으로 강제되는 규칙은 아니지만, 이 메서드를 호출할 때 `await`가 필요하다는 것을 이름만 보고 알 수 있게 해주는 실무 관례입니다.
- `async` 메서드의 반환형은 보통 `Task`나 `Task<T>`입니다. `async void`도 문법적으로 가능하지만, 호출한 쪽에서 완료를 기다릴 방법이 없고 예외가 발생해도 정상적으로 잡아내기 어려워서 버튼 클릭 같은 이벤트 처리기(16장에서 다룬 이벤트) 안에서만 예외적으로 사용합니다.
- `await`는 오직 `async`로 선언된 메서드 안에서만 쓸 수 있습니다. 최상위 코드(top-level statements)로 작성한 `Program.cs`는 컴파일러가 자동으로 `async Task Main()`을 만들어주기 때문에 예제처럼 최상위 코드에서도 곧바로 `await`를 쓸 수 있습니다. 클래스 안에 명시적으로 `Main` 메서드를 작성하는 방식(2장 참고)이라면 `static async Task Main()`처럼 직접 `async`를 붙여야 합니다.

## 여러 작업을 동시에 기다리기: Task.WhenAll

`await`를 만날 때마다 하나씩 순서대로 기다리면, 결과적으로 걸리는 시간은 각 작업 시간을 모두 더한 것과 같습니다. 서로 관련이 없는 작업이라면 동시에 시작해서 한꺼번에 기다리는 것이 훨씬 효율적입니다. 이럴 때 쓰는 것이 `Task.WhenAll`입니다.

```csharp
async Task<string> DownloadDataAsync(string name, int delayMs)
{
    Console.WriteLine($"{name} 다운로드 시작");
    await Task.Delay(delayMs);
    Console.WriteLine($"{name} 다운로드 완료");
    return $"{name}의 결과";
}

Console.WriteLine("=== 동시에 시작하고 함께 기다리기 ===");

Task<string> taskA = DownloadDataAsync("A", 2000);
Task<string> taskB = DownloadDataAsync("B", 3000);
Task<string> taskC = DownloadDataAsync("C", 1000);

string[] results = await Task.WhenAll(taskA, taskB, taskC);

foreach (string result in results)
{
    Console.WriteLine(result);
}
```

여기서 중요한 점은 `DownloadDataAsync`를 호출하는 순간에는 `await`를 붙이지 않았다는 것입니다. `await` 없이 `async` 메서드를 호출하면 메서드가 곧바로 실행을 시작하고, 아직 끝나지 않은 `Task` 객체가 즉시 반환됩니다. 이렇게 세 작업을 모두 "시작"만 해둔 뒤, `Task.WhenAll`에 모아서 한 번에 `await`하면 세 작업이 동시에 진행됩니다. `Task.WhenAll`은 넘겨받은 모든 `Task`가 완료될 때까지 기다렸다가, `Task<string>[]`이었던 것들의 결과를 `string[]`으로 모아서 돌려줍니다. A(2초), B(3초), C(1초)를 순서대로 `await`했다면 총 6초가 걸리지만, 이렇게 동시에 시작하면 가장 오래 걸리는 작업인 B의 3초만 기다리면 됩니다.

## 동기 실행과 비동기 실행의 시간을 직접 비교해보기

말로 설명한 시간 차이를 코드로 직접 확인해보겠습니다. `Stopwatch`(`System.Diagnostics` 네임스페이스)로 실행 시간을 측정합니다.

```csharp
using System.Diagnostics;

async Task<string> DownloadDataAsync(string name, int delayMs)
{
    await Task.Delay(delayMs);
    return $"{name}의 결과";
}

// 방식 1: 순서대로 하나씩 기다리기
Stopwatch sw1 = Stopwatch.StartNew();

string r1 = await DownloadDataAsync("A", 2000);
string r2 = await DownloadDataAsync("B", 3000);
string r3 = await DownloadDataAsync("C", 1000);

sw1.Stop();
Console.WriteLine($"순차 실행 소요 시간: {sw1.ElapsedMilliseconds}ms"); // 약 6000ms

// 방식 2: 동시에 시작해서 함께 기다리기
Stopwatch sw2 = Stopwatch.StartNew();

Task<string> t1 = DownloadDataAsync("A", 2000);
Task<string> t2 = DownloadDataAsync("B", 3000);
Task<string> t3 = DownloadDataAsync("C", 1000);
await Task.WhenAll(t1, t2, t3);

sw2.Stop();
Console.WriteLine($"동시 실행 소요 시간: {sw2.ElapsedMilliseconds}ms"); // 약 3000ms
```

같은 세 작업인데도 어떻게 시작하고 기다리느냐에 따라 전체 소요 시간이 절반 이하로 줄어드는 것을 확인할 수 있습니다. 이 차이를 시간의 흐름으로 그려보면 다음과 같습니다.

```text
             동기 실행과 비동기 실행의 시간 흐름 비교

1. 동기 실행 - 하나씩 순서대로 await (또는 Thread.Sleep)

메인 스레드  |<---- A 다운로드 대기 ---->|<------ B 다운로드 대기 ------>|<-- C 대기 -->|
             (2초, 스레드 블로킹)         (3초, 스레드 블로킹)            (1초)

-> 한 작업이 끝나야 다음 작업을 시작할 수 있음

             |<--------------------------------------------------------------->|
                              총 6초 소요 (2 + 3 + 1)

- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

2. 비동기 실행 - 동시에 시작하고 Task.WhenAll로 함께 대기

메인 스레드  |....블로킹 없이 대기 (다른 작업 처리 가능)....|
             await Task.WhenAll(taskA, taskB, taskC)

Task A       |///// 2초 후 완료 /////|
Task B       |///// 3초 후 완료 (가장 오래 걸림) /////////|
Task C       |// 1초 후 완료 //|

-> 세 작업이 같은 시점에 시작되어 대기 시간이 겹쳐짐

             |<-------------------------------------------->|
                     총 3초 소요 (가장 긴 작업 시간만큼만 대기)

                                                : <- 3초 시점
시간축(초):  0        2        3        5        6

+--------------------------------------------------------------------+
| 같은 3초 시점에서 비교하면                                            |
| - 동기 실행: 아직 B 작업 대기 중 (전체 완료까지 3초 더 필요)              |
| - 비동기 실행: 세 작업 모두 이미 완료됨                                 |
+--------------------------------------------------------------------+
```

그림 위쪽은 세 작업을 순서대로 `await`한 경우입니다. 메인 스레드가 A의 2초, B의 3초, C의 1초를 차례로 블로킹 상태로 기다리기 때문에 전체 6초가 걸립니다. 그림 아래쪽은 `Task.WhenAll`로 세 작업을 동시에 시작한 경우입니다. 세 작업이 같은 시점에 시작되어 겹쳐서 진행되고, 메인 스레드는 대기하는 동안 실제로 블로킹되지 않으므로 가장 오래 걸리는 작업(3초)이 끝나는 순간 전체가 끝납니다. 그림에서 표시한 3초 시점을 비교해보면, 순차 실행은 아직 B 작업이 진행 중이지만 동시 실행은 이미 모든 작업이 끝나 있다는 것을 알 수 있습니다.

## 비동기 코드를 다룰 때 주의할 점

**`.Result`나 `.Wait()`로 강제로 기다리지 않기.** `Task`에는 `.Result`(값을 반환하는 경우)와 `.Wait()`라는 멤버가 있어서 `await` 없이도 결과를 강제로 기다릴 수 있습니다. 하지만 이렇게 하면 스레드를 다시 블로킹하게 되어 비동기로 얻은 이점이 사라지고, 특정 환경(예: 예전 방식의 UI 프레임워크)에서는 스레드끼리 서로를 기다리다 영원히 멈추는 데드락(deadlock)까지 발생할 수 있습니다. 한 번 `async`로 시작했다면 호출하는 쪽도 `async`로 만들고 `await`로 이어받는, 흔히 "async all the way"라고 부르는 원칙을 지키는 것이 안전합니다.

**예외 처리는 동기 코드와 동일하게.** `async` 메서드 안에서 예외가 발생하면 그 예외는 메서드가 반환하는 `Task`에 담겨 있다가, 그 `Task`를 `await`하는 순간 다시 던져집니다. 따라서 15장에서 배운 `try-catch`를 `await` 호출을 감싸는 형태로 그대로 사용할 수 있습니다.

```csharp
try
{
    string data = await DownloadDataAsync();
    Console.WriteLine(data);
}
catch (TaskCanceledException)
{
    Console.WriteLine("작업이 취소되었습니다.");
}
```

**비동기는 "빨라지는 것"이 아니라 "기다리는 동안 낭비되지 않는 것".** `Task.Delay(3000)`이 비동기로 바뀌어도 3초라는 물리적인 대기 시간 자체는 줄어들지 않습니다. 비동기 프로그래밍이 주는 이득은 그 3초 동안 스레드가 다른 작업을 처리할 수 있다는 데 있습니다. 여러 작업을 동시에 진행할 때 전체 소요 시간이 줄어드는 것은 대기 시간이 겹쳐지기 때문이며, 하나의 작업만 있다면 동기 코드든 비동기 코드든 그 작업 자체의 완료 시간은 동일합니다.

## 요약

- 시간이 오래 걸리는 작업(네트워크, 파일, 데이터베이스 등)을 동기적으로 처리하면 그 시간 동안 스레드가 완전히 멈춰 다른 일을 하지 못한다.
- `Task`와 `Task<T>`는 아직 끝나지 않은 작업을 나타내는 객체이며, `Task<T>`의 `T`는 작업이 끝난 뒤 돌려줄 결과의 형이다.
- `async` 키워드로 선언한 메서드 안에서 `await`를 사용하면, 대기하는 동안 스레드를 블로킹하지 않고 호출한 곳으로 제어를 돌려준다.
- `await` 없이 `async` 메서드를 호출하면 작업이 즉시 시작되며, 이렇게 시작해둔 여러 `Task`를 `Task.WhenAll`로 모아 한 번에 기다리면 작업들이 동시에 진행되어 전체 시간이 크게 줄어든다.
- `.Result`나 `.Wait()`로 강제로 기다리는 대신, 호출하는 쪽도 `async`/`await`로 이어가는 것이 데드락을 피하는 안전한 방법이다.
- 비동기 예외 처리는 동기 코드의 `try-catch`와 동일한 방식으로 `await` 호출을 감싸서 사용한다.

## 연습문제

1. `Thread.Sleep(2000)`으로 2초가 걸리는 동기 메서드와 `await Task.Delay(2000)`으로 동작하는 비동기 메서드를 각각 작성하고, `Stopwatch`로 두 방식이 프로그램 전체의 흐름에 어떤 영향을 주는지 관찰해보세요(비동기 메서드를 호출한 뒤 곧바로 다른 `Console.WriteLine`을 실행할 수 있는지 확인해보는 것도 좋습니다).
2. 서로 다른 지연 시간(예: 1초, 2초, 4초)을 갖는 비동기 메서드 세 개를 순서대로 `await`했을 때와 `Task.WhenAll`로 동시에 기다렸을 때의 총 소요 시간을 각각 측정하고 비교해보세요.
3. 사용자 세 명의 아이디를 입력받아, 각 아이디에 대해 "정보를 조회하는" 비동기 메서드(`Task.Delay`로 흉내)를 `Task.WhenAll`로 동시에 호출한 뒤 결과를 모두 출력하는 프로그램을 작성해보세요.
4. 비동기 메서드 안에서 임의로 예외를 던지도록 만든 뒤, 이를 호출하는 코드에서 `try-catch`로 예외를 잡아 처리하는 예제를 작성해보세요.
5. `async void`로 선언한 메서드와 `async Task`로 선언한 메서드의 차이를 코드로 확인해보고, 왜 이벤트 처리기가 아닌 일반 메서드에서는 `async Task`를 사용해야 하는지 자신의 말로 설명해보세요.

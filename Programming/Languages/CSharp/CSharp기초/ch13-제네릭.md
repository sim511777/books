프로그램을 만들다 보면 "타입만 다르고 로직은 완전히 똑같은 코드"를 반복해서 작성해야 하는 상황을 자주 만납니다. 이번 장에서는 이런 중복을 없애기 위해 C#이 제공하는 도구인 제네릭(Generic)을 다룹니다. 제네릭은 클래스나 메서드를 작성할 때 구체적인 자료형을 미리 정하지 않고, 사용하는 시점에 자료형을 끼워 넣을 수 있게 해주는 문법입니다.

## 타입마다 코드를 복제해야 하는 문제

정수만 담을 수 있는 스택(Stack) 자료구조를 만든다고 해봅시다. 스택은 마지막에 넣은 값이 가장 먼저 나오는 구조로, `Push`로 값을 넣고 `Pop`으로 값을 꺼냅니다.

```csharp
// 정수 전용 스택
class IntStack
{
    private int[] _items = new int[100];
    private int _count;

    public void Push(int item)
    {
        _items[_count] = item;
        _count++;
    }

    public int Pop()
    {
        _count--;
        return _items[_count];
    }
}
```

여기까지는 문제가 없습니다. 그런데 이번에는 문자열을 담는 스택도 필요해졌다고 해봅시다.

```csharp
// 문자열 전용 스택 - IntStack과 거의 똑같은 코드
class StringStack
{
    private string[] _items = new string[100];
    private int _count;

    public void Push(string item)
    {
        _items[_count] = item;
        _count++;
    }

    public string Pop()
    {
        _count--;
        return _items[_count];
    }
}
```

`IntStack`과 `StringStack`을 나란히 놓고 보면 `int`가 `string`으로 바뀐 것 말고는 완전히 동일한 코드입니다. 만약 `double` 스택, `Customer` 스택도 필요하다면 똑같은 클래스를 계속 복제해야 합니다. 이렇게 되면 스택의 동작 방식을 고치고 싶을 때(예: `Pop`에서 빈 스택을 확인하는 로직을 추가하고 싶을 때) 클래스 개수만큼 똑같은 수정을 반복해야 하는 유지보수 문제가 생깁니다.

`object` 타입을 사용해서 이 문제를 피해보려는 시도도 가능합니다. `object`는 모든 타입의 조상이므로 어떤 값이든 담을 수 있기 때문입니다.

```csharp
class ObjectStack
{
    private object[] _items = new object[100];
    private int _count;

    public void Push(object item)
    {
        _items[_count] = item;
        _count++;
    }

    public object Pop()
    {
        _count--;
        return _items[_count];
    }
}
```

하지만 이 방식에는 두 가지 심각한 단점이 있습니다. 첫째, `Pop()`이 항상 `object`를 반환하므로 실제로 정수를 꺼낼 때도 `(int)stack.Pop()`처럼 형변환을 해야 합니다. 형변환을 잊거나 잘못된 타입으로 변환하면 실행 중 오류가 발생합니다. 둘째, 값 타입(`int`, `double` 등)을 `object`에 담는 과정에서 박싱(boxing)이라는 추가 작업이 일어나 성능에도 손해를 봅니다. 즉 컴파일 시점에 타입을 검사받는 안전성을 포기하는 대신 얻는 것이 별로 없는 셈입니다.

## 제네릭 클래스로 타입을 매개변수화하기

제네릭은 이 문제를 정확히 해결합니다. 핵심 아이디어는 "타입 자체를 매개변수처럼 다루자"는 것입니다. 메서드가 `int x` 같은 매개변수를 받아서 실행 시점에 값을 채워 넣듯이, 제네릭 클래스는 `T` 같은 타입 매개변수를 받아서 사용 시점에 실제 타입을 채워 넣습니다.

```csharp
// T는 타입 매개변수(Type Parameter)입니다.
class Stack<T>
{
    private T[] _items = new T[100];
    private int _count;

    public void Push(T item)
    {
        _items[_count] = item;
        _count++;
    }

    public T Pop()
    {
        _count--;
        return _items[_count];
    }

    public int Count => _count;
}
```

`T`는 아직 정해지지 않은 타입을 나타내는 이름입니다. 관례상 타입 매개변수가 하나뿐일 때는 `T`(Type의 첫 글자)를 많이 쓰지만, 의미를 살려 `TKey`, `TValue`처럼 이름을 붙이기도 합니다. 이 클래스를 실제로 사용할 때는 `<>` 안에 구체적인 타입을 지정합니다.

```csharp
Stack<int> intStack = new Stack<int>();
intStack.Push(10);
intStack.Push(20);
int top = intStack.Pop(); // 20, 형변환이 필요 없습니다.

Stack<string> stringStack = new Stack<string>();
stringStack.Push("hello");
stringStack.Push("world");
string topWord = stringStack.Pop(); // "world"
```

`Stack<int>`를 사용하는 순간 컴파일러는 `T`를 `int`로 취급합니다. 그래서 `intStack.Push("문자열")`처럼 잘못된 타입을 넣으려 하면 컴파일 오류가 발생하고, `Pop()`의 반환값도 이미 `int`이므로 형변환이 필요 없습니다. 코드는 딱 한 번만 작성했지만, 컴파일러가 사용된 타입에 맞춰 필요한 만큼 특화된 버전을 만들어주는 셈입니다. `IntStack`, `StringStack`을 따로 만들던 중복이 완전히 사라졌습니다.

## 제네릭 메서드

클래스 전체가 아니라 메서드 하나만 제네릭으로 만들 수도 있습니다. 배열에서 두 원소의 위치를 바꾸는 함수를 만든다고 해봅시다.

```csharp
class ArrayHelper
{
    // Swap도 타입에 상관없이 동일하게 동작해야 하므로 제네릭 메서드로 작성합니다.
    public static void Swap<T>(T[] array, int i, int j)
    {
        T temp = array[i];
        array[i] = array[j];
        array[j] = temp;
    }
}
```

```csharp
int[] numbers = { 1, 2, 3 };
ArrayHelper.Swap(numbers, 0, 2);
// numbers는 { 3, 2, 1 }이 됩니다.

string[] words = { "가", "나", "다" };
ArrayHelper.Swap(words, 0, 1);
// words는 { "나", "가", "다" }가 됩니다.
```

`Swap<int>(numbers, 0, 2)`처럼 타입을 명시할 수도 있지만, 대부분은 컴파일러가 인자로 넘어온 배열의 타입을 보고 `T`가 무엇인지 스스로 추론(type inference)하기 때문에 위 예제처럼 타입을 생략해도 됩니다.

## 제약 조건(where)으로 T의 범위 좁히기

타입 매개변수 `T`는 기본적으로 "아무 타입이나 가능"하다는 뜻입니다. 그런데 때로는 `T`가 아무 타입이어서는 곤란한 경우가 있습니다. 예를 들어 두 값 중 더 큰 값을 반환하는 제네릭 메서드를 만들고 싶다고 해봅시다.

```csharp
static T Max<T>(T a, T b)
{
    // T가 아무 타입이나 될 수 있다면 a와 b를 비교할 방법이 없습니다.
    // if (a > b) return a;  // 컴파일 오류: T에는 > 연산자가 정의되어 있지 않습니다.
    return default(T);
}
```

`T`가 `Customer`처럼 비교 연산자가 없는 타입이라면 `>` 연산 자체가 성립하지 않습니다. 이럴 때 제약 조건(constraint)을 사용해 "`T`는 최소한 이런 조건을 만족하는 타입이어야 한다"라고 컴파일러에게 알려줄 수 있습니다. `IComparable<T>` 인터페이스를 구현한 타입만 받도록 제약을 걸면 비교가 가능해집니다.

```csharp
static T Max<T>(T a, T b) where T : IComparable<T>
{
    // IComparable<T>를 구현했다는 보장이 있으므로 CompareTo를 안전하게 쓸 수 있습니다.
    return a.CompareTo(b) > 0 ? a : b;
}
```

```csharp
int biggerNumber = Max(3, 7);           // 7
string biggerWord = Max("apple", "banana"); // "banana" (사전순 비교)
```

`int`, `string` 같은 기본 타입은 모두 `IComparable<T>`를 이미 구현하고 있으므로 별다른 준비 없이 `Max`를 호출할 수 있습니다. 자주 쓰이는 제약 조건 몇 가지를 정리하면 다음과 같습니다.

- `where T : class` — `T`는 참조 타입(클래스)이어야 합니다.
- `where T : struct` — `T`는 값 타입(구조체)이어야 합니다. 12장에서 다룬 구조체를 떠올리면 됩니다.
- `where T : new()` — `T`는 매개변수 없는 생성자를 가져야 하며, 이 제약이 있으면 메서드 안에서 `new T()`로 인스턴스를 만들 수 있습니다.
- `where T : SomeBaseClass` — `T`는 특정 클래스를 상속해야 합니다. 10장 상속과 다형성에서 배운 상속 관계를 제약으로 활용하는 경우입니다.
- `where T : ISomeInterface` — `T`는 특정 인터페이스를 구현해야 합니다.

여러 제약을 동시에 걸 수도 있습니다. 예를 들어 `where T : class, new()`는 "참조 타입이면서 매개변수 없는 생성자도 있어야 한다"는 뜻입니다. 제약 조건은 "이 코드가 T에 대해 무엇을 할 수 있어야 하는가"를 컴파일러에게 미리 알려주는 계약서와 같습니다.

## 이미 써봤던 제네릭: List&lt;T&gt;

사실 여러분은 이미 제네릭을 사용해봤습니다. 7장 배열과 컬렉션 기초에서 배운 `List<T>`가 바로 제네릭 클래스입니다.

```csharp
List<int> numbers = new List<int>();
numbers.Add(1);
numbers.Add(2);

List<string> names = new List<string>();
names.Add("철수");
names.Add("영희");
```

`List<int>`와 `List<string>`은 같은 `List<T>` 클래스에 서로 다른 타입 인자를 채워 넣은 결과입니다. 지금까지는 `List<T>`가 "그냥 그렇게 쓰는 문법"으로 느껴졌겠지만, 이제는 그 원리를 이해하셨을 것입니다. `List<T>` 내부는 이번 장에서 만든 `Stack<T>`와 비슷하게, `T` 배열을 두고 필요할 때마다 크기를 늘려가며 요소를 저장하는 방식으로 동작합니다. `.NET`이 제공하는 거의 모든 컬렉션 타입 — `Dictionary<TKey, TValue>`, `Queue<T>`, `HashSet<T>` 등 — 이 같은 원리로 만들어진 제네릭 클래스이며, 이 컬렉션들은 다음 14장 컬렉션과 LINQ에서 본격적으로 다룹니다.

제네릭이 없었다면 `List`도 `object`를 담는 컬렉션으로 만들어졌을 것이고, 우리는 값을 꺼낼 때마다 형변환을 해야 했을 것입니다. 제네릭 덕분에 C#의 컬렉션들은 타입 안전성을 유지하면서도 어떤 타입에든 재사용할 수 있는 유연함을 동시에 갖추게 되었습니다.

## 요약

- 타입만 다르고 로직이 같은 클래스를 반복해서 만드는 것은 유지보수 비용을 키우는 중복입니다. `object`로 일반화하면 형변환과 박싱 문제가 생깁니다.
- 제네릭은 `class Box<T>`처럼 타입 매개변수를 사용해 타입을 사용 시점에 결정하는 문법이며, 컴파일 시점의 타입 안전성을 그대로 유지합니다.
- 클래스뿐 아니라 `Swap<T>(...)`처럼 메서드 단위로도 제네릭을 적용할 수 있고, 대부분 타입 인자는 컴파일러가 추론합니다.
- `where T : IComparable<T>`처럼 제약 조건을 걸면 `T`에 대해 특정 연산이나 멤버를 사용할 수 있다는 것을 컴파일러에게 보장할 수 있습니다.
- `List<T>`, `Dictionary<TKey, TValue>` 등 .NET의 주요 컬렉션은 모두 제네릭으로 구현되어 있습니다.

## 연습문제

1. `int` 값만 저장할 수 있는 `IntQueue` 클래스와 `string` 값만 저장할 수 있는 `StringQueue` 클래스를 각각 작성한 뒤, 두 코드가 얼마나 중복되는지 확인해보세요.
2. 위에서 작성한 두 클래스를 `Queue<T>`라는 제네릭 클래스 하나로 통합해보세요. `Enqueue(T item)`으로 값을 넣고 `Dequeue()`로 값을 꺼내도록 구현합니다.
3. `where T : IComparable<T>` 제약을 사용해, 배열에서 가장 작은 값을 찾아 반환하는 `Min<T>(T[] array)` 제네릭 메서드를 작성해보세요.
4. `where T : new()` 제약을 사용하는 제네릭 메서드 `Create<T>()`를 작성해, `new T()`로 인스턴스를 만들어 반환하도록 해보세요. 이 메서드를 매개변수 없는 생성자가 있는 클래스와 없는 클래스에 각각 호출해보고 컴파일러가 어떻게 반응하는지 관찰해보세요.
5. `Stack<T>` 클래스에 `Peek()` 메서드(꺼내지 않고 맨 위 값만 확인)와, 스택이 비어 있을 때 `Pop()`을 호출하면 적절한 예외를 던지는 로직을 추가해보세요. 예외 처리는 15장에서 자세히 다루지만, 우선 `throw new InvalidOperationException("...")` 형태로 시도해보세요.

# 16장. 패키지와 모듈

지금까지 작성한 예제는 대부분 파일 하나, `package main` 하나로 끝나는 짧은 프로그램이었습니다. 하지만 프로그램이 커지면 코드를 여러 파일과 폴더로 나누고, 다른 사람이 만든 코드를 가져다 쓰고, 내가 만든 코드를 다른 프로젝트에서 재사용해야 할 때가 옵니다. 이번 장에서는 Go가 코드를 조직하는 기본 단위인 패키지(package)와, 여러 패키지를 하나로 묶어 관리하는 모듈(module) 시스템을 살펴봅니다.

## package 선언과 폴더 구조

Go 소스 파일은 예외 없이 첫 줄(주석 제외)에 `package` 선언으로 시작합니다.

```go
package main
```

패키지는 Go에서 코드를 묶는 가장 기본적인 단위입니다. 규칙은 단순합니다.

- **한 폴더 = 한 패키지.** 같은 폴더 안에 있는 모든 `.go` 파일은 반드시 같은 `package` 이름을 선언해야 합니다(테스트 파일에 한해 `_test`가 붙은 패키지 이름을 예외로 허용하지만, 이는 18장에서 다룹니다).
- 폴더 이름과 패키지 이름이 반드시 같아야 하는 것은 아니지만, 관례적으로 일치시킵니다. 예를 들어 `stringutil`이라는 폴더 안의 파일들은 보통 `package stringutil`을 선언합니다.
- `package main`은 특별한 의미를 가집니다. `func main()`을 포함한 `main` 패키지만이 실행 가능한 프로그램(바이너리)으로 빌드됩니다. 그 외의 패키지는 다른 패키지에서 가져다 쓰는 라이브러리 역할을 합니다.

폴더 구조로 보면 다음과 같은 모양이 됩니다.

```
myapp/
├── go.mod
├── main.go          // package main
├── stringutil/
│   ├── reverse.go    // package stringutil
│   └── trim.go        // package stringutil
└── mathutil/
    └── sum.go          // package mathutil
```

`stringutil` 폴더 안의 `reverse.go`와 `trim.go`는 서로 다른 파일이지만 같은 `package stringutil`을 선언하므로, 컴파일러 입장에서는 사실상 하나로 이어붙인 코드처럼 취급됩니다. 반대로 `main.go`와 `stringutil` 폴더의 파일들은 서로 다른 패키지이므로, `main.go`에서 `stringutil`의 기능을 쓰려면 명시적으로 import해야 합니다.

## Go 모듈 시스템과 go.mod

패키지가 "코드를 묶는 단위"라면, 모듈(module)은 "패키지들을 묶고 버전을 관리하는 단위"입니다. 하나의 모듈은 보통 하나의 프로젝트나 하나의 배포 단위에 대응하며, 그 안에 여러 개의 패키지(폴더)를 포함할 수 있습니다.

모듈을 시작하는 첫 단계는 `go mod init`입니다. 프로젝트의 최상위 폴더에서 다음처럼 실행합니다.

```bash
mkdir myapp
cd myapp
go mod init example.com/myapp
```

이 명령은 `go.mod`라는 파일을 만듭니다.

```
module example.com/myapp

go 1.22
```

`go.mod`의 각 줄이 의미하는 바는 다음과 같습니다.

- `module example.com/myapp`: 이 모듈의 이름(모듈 경로)을 선언합니다. 이 경로는 모듈 안의 모든 패키지를 가리키는 import 경로의 기준(prefix)이 됩니다. 실제로 깃허브 등에 공개할 계획이라면 `github.com/사용자이름/저장소이름` 형태로 짓는 것이 관례입니다. 사내에서만 쓰는 프로젝트라면 회사 도메인이나 임의의 문자열도 상관없습니다.
- `go 1.22`: 이 모듈이 요구하는 Go 언어 버전의 하한선입니다. Go 툴체인은 이 버전에 맞춰 문법과 표준 라이브러리 동작을 해석합니다.

외부 패키지를 추가하면(뒤에서 설명할 `go get`) `go.mod`에 `require` 절이 추가되고, 각 의존성의 정확한 버전과 체크섬을 기록하는 `go.sum` 파일이 함께 생성됩니다. `go.sum`은 사람이 직접 편집하는 파일이 아니라 도구가 자동으로 관리하는 파일이므로, 버전 관리 시스템에는 커밋하되 손으로 고치지 않는 것이 원칙입니다.

> 참고: 예전 Go(모듈 시스템이 도입되기 전, 1.11 이전)에서는 모든 코드를 `GOPATH`라는 정해진 위치 아래에 두어야 했습니다. 지금은 `go.mod`가 있는 폴더가 곧 프로젝트의 루트가 되므로, 디스크의 어느 위치에서든 자유롭게 프로젝트를 만들 수 있습니다. 이 책의 예제들도 모두 모듈 시스템을 기준으로 설명합니다.

## import 경로 규칙

다른 패키지의 기능을 쓰려면 `import` 문으로 그 패키지를 가져와야 합니다. 지금까지 자주 써온 다음 코드를 다시 보겠습니다.

```go
import "fmt"
```

`import` 경로는 크게 두 종류로 나뉩니다.

**표준 라이브러리 경로**: `fmt`, `strings`, `net/http`처럼 Go에 기본 내장된 패키지는 짧은 경로 하나만 쓰면 됩니다. 별도의 설치가 필요 없습니다.

**모듈 내부 패키지 경로**: 내가 만든 패키지나 외부에서 내려받은 패키지는 `go.mod`에 선언한 모듈 경로를 기준으로 한 전체 경로를 씁니다. 앞서 만든 `example.com/myapp` 모듈 안의 `stringutil` 패키지를 `main.go`에서 사용한다면 다음처럼 import합니다.

```go
import "example.com/myapp/stringutil"
```

즉 import 경로는 "모듈 경로 + 모듈 루트로부터의 폴더 경로"로 결정되며, 실제 파일 시스템 경로와 정확히 대응합니다. 여러 개를 import할 때는 괄호로 묶습니다.

```go
import (
	"fmt"
	"strings"

	"example.com/myapp/mathutil"
	"example.com/myapp/stringutil"
)
```

관례적으로 표준 라이브러리 패키지와 외부/내부 패키지 사이에 빈 줄을 두어 그룹을 구분합니다. `gofmt`와 `goimports` 도구는 이 순서를 자동으로 정렬해 주므로, 순서 자체를 손으로 맞추려고 애쓸 필요는 없습니다.

패키지를 import했는데 코드에서 실제로 그 이름을 한 번도 쓰지 않으면 컴파일 에러가 납니다. Go는 쓰지 않는 import를 엄격하게 금지해서 코드가 불필요하게 무거워지는 것을 막습니다. 반대로 패키지 이름이 겹치거나 더 짧은 이름으로 쓰고 싶다면 별칭(alias)을 붙일 수 있습니다.

```go
import (
	mrand "math/rand"
	crand "crypto/rand"
)
```

## 여러 파일로 나뉜 패키지 구성

패키지 하나가 반드시 파일 하나일 필요는 없습니다. 관련 있는 기능을 파일별로 나눠 정리하면 코드를 찾고 관리하기 쉬워집니다. 같은 패키지 안의 파일들은 서로 다른 파일에 있어도 마치 한 파일에 있는 것처럼 서로의 함수와 타입을 바로 사용할 수 있습니다. import가 필요 없다는 뜻입니다.

`mathutil` 패키지를 두 파일로 나눈 예를 보겠습니다.

```go
// mathutil/add.go
package mathutil

// Add는 두 정수의 합을 반환한다.
func Add(a, b int) int {
	return a + b
}
```

```go
// mathutil/subtract.go
package mathutil

// Subtract는 두 정수의 차를 반환한다.
func Subtract(a, b int) int {
	return a - b
}

// AddThenSubtract는 같은 패키지의 Add를 import 없이 바로 호출한다.
func AddThenSubtract(a, b, c int) int {
	return Add(a, b) - c
}
```

`subtract.go`에서 `add.go`에 정의된 `Add`를 아무런 import 없이 바로 호출할 수 있다는 점에 주목하세요. 두 파일이 같은 `package mathutil`을 선언했기 때문에, 컴파일러는 이 둘을 사실상 하나의 코드 단위로 취급합니다.

이름 규칙도 다시 짚어보겠습니다. 함수, 타입, 변수 이름의 첫 글자가 대문자면(`Add`, `Subtract`) 그 식별자는 패키지 바깥에서도 접근할 수 있는 공개(exported) 식별자입니다. 첫 글자가 소문자면(`helper`, `internalCount`) 같은 패키지 안에서만 쓸 수 있는 비공개 식별자입니다. 이 규칙 덕분에 별도의 `public`/`private` 키워드 없이도 패키지의 공개 API와 내부 구현을 명확히 구분할 수 있습니다.

## 자체 패키지 만들기 예제

지금까지 배운 내용을 모아 처음부터 끝까지 하나의 예제로 만들어 보겠습니다. 목표는 문자열을 뒤집는 기능을 담은 나만의 패키지를 만들고, `main` 패키지에서 그 기능을 가져다 쓰는 것입니다.

**1단계. 프로젝트 폴더와 모듈 만들기**

```bash
mkdir greeting
cd greeting
go mod init example.com/greeting
```

**2단계. 하위 패키지 폴더 만들기**

`greeting` 폴더 아래에 `stringutil`이라는 폴더를 만들고, 그 안에 파일을 작성합니다.

```go
// stringutil/reverse.go
package stringutil

// Reverse는 문자열을 룬(rune) 단위로 뒤집어 반환한다.
// 한글, 이모지 등 여러 바이트로 이루어진 문자도 깨지지 않도록
// byte가 아닌 rune 슬라이스로 변환해서 처리한다.
func Reverse(s string) string {
	runes := []rune(s)
	for i, j := 0, len(runes)-1; i < j; i, j = i+1, j-1 {
		runes[i], runes[j] = runes[j], runes[i]
	}
	return string(runes)
}
```

**3단계. main 패키지에서 사용하기**

```go
// main.go
package main

import (
	"fmt"

	"example.com/greeting/stringutil"
)

func main() {
	msg := "Go 기초부터 응용까지"
	fmt.Println(stringutil.Reverse(msg))
}
```

**4단계. 실행하기**

```bash
go run .
```

최종 폴더 구조는 다음과 같습니다.

```
greeting/
├── go.mod
├── main.go
└── stringutil/
    └── reverse.go
```

이 예제에서 `stringutil` 패키지는 `greeting` 모듈 안에 속한 하위 패키지입니다. `main.go`는 `example.com/greeting/stringutil`이라는 전체 경로로 이 패키지를 import했고, 그 경로는 정확히 "모듈 경로(`example.com/greeting`) + 폴더 경로(`/stringutil`)"와 일치합니다. 함수 이름을 `Reverse`로, 첫 글자를 대문자로 지었기 때문에 `main` 패키지에서 접근할 수 있었다는 점도 함께 기억해 두세요.

## go get으로 외부 의존성 추가하기

지금까지는 내가 만든 패키지만 다뤘지만, 실무에서는 다른 사람이 만들어 공개한 패키지를 가져다 쓰는 일이 훨씬 많습니다. `go get` 명령이 이 과정을 담당합니다.

```bash
go get github.com/사용자이름/저장소이름
```

`go get`을 실행하면 다음과 같은 일이 일어납니다.

1. 지정한 경로의 소스 코드를 내려받아 로컬 모듈 캐시에 저장합니다.
2. `go.mod`의 `require` 절에 해당 패키지와 사용할 버전을 추가합니다.
3. 내려받은 코드의 체크섬을 `go.sum`에 기록해서, 나중에 같은 코드를 받았을 때 변조 여부를 검증할 수 있게 합니다.

버전을 명시하고 싶다면 경로 뒤에 `@버전`을 붙입니다.

```bash
go get github.com/사용자이름/저장소이름@v1.4.0
go get github.com/사용자이름/저장소이름@latest
```

의존성을 추가한 뒤에는 일반적인 패키지와 똑같은 방식으로 import해서 사용합니다.

```go
import "github.com/사용자이름/저장소이름"
```

버전을 따로 지정하지 않고 `go build`나 `go run`을 실행해도, 소스 코드에서 아직 `go.mod`에 없는 외부 패키지를 import하고 있다면 Go 툴체인이 알아서 필요한 버전을 찾아 `go.mod`와 `go.sum`을 갱신해 주기도 합니다. 다만 의존성을 명시적으로 추가하거나 갱신할 때는 `go get`을 직접 실행하는 습관을 들이는 것이 버전 관리 이력을 깔끔하게 유지하는 데 도움이 됩니다. 외부 패키지를 더 이상 쓰지 않게 되었다면 `go mod tidy` 명령으로 `go.mod`와 `go.sum`에서 불필요해진 항목을 정리할 수 있습니다.

외부 의존성을 다루는 더 자세한 내용(버전 선택 규칙, 프록시, private 모듈 설정 등)은 실무에서 점차 필요할 때 공식 문서를 참고하는 것으로 충분합니다. 이 책에서는 표준 라이브러리와 직접 만든 패키지만으로도 대부분의 예제를 다룰 수 있도록 구성했습니다.

## 요약

- 패키지는 Go 코드를 묶는 기본 단위이며, 한 폴더 안의 모든 `.go` 파일은 같은 `package` 이름을 선언해야 합니다. `package main`과 `func main()`이 있는 패키지만 실행 파일로 빌드됩니다.
- 모듈은 패키지들을 묶고 버전을 관리하는 단위입니다. `go mod init 모듈경로`로 `go.mod` 파일을 만들며, 이 파일은 모듈 이름과 요구 Go 버전, 외부 의존성 목록을 담습니다.
- import 경로는 표준 라이브러리는 짧은 이름 그대로, 모듈 내부 패키지는 "모듈 경로 + 폴더 경로"의 전체 경로로 지정합니다. 실제 사용하지 않는 import는 컴파일 에러가 됩니다.
- 같은 패키지에 속한 여러 파일은 import 없이 서로의 exported/비공개 식별자를 자유롭게 공유합니다. 이름의 첫 글자 대소문자로 공개 범위가 결정됩니다.
- `go get 경로@버전`으로 외부 의존성을 추가하면 `go.mod`와 `go.sum`이 갱신되고, 더 이상 쓰지 않는 의존성은 `go mod tidy`로 정리할 수 있습니다.

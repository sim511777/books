1장에서 Go의 설계 철학으로 단순함과 명시성을 이야기하면서, 에러를 값으로 다루는 관용구를 잠깐 언급했습니다. 이번 장에서는 그 관용구의 속을 제대로 들여다봅니다. Go에는 `try`/`catch` 같은 예외(exception) 문법이 없습니다. 대신 실패할 수 있는 함수는 결과값과 함께 에러 값을 반환하고, 호출하는 쪽이 그 에러를 직접 검사해서 처리합니다. 처음에는 이 방식이 번거롭게 느껴질 수 있지만, 왜 Go가 이런 선택을 했는지 이해하고 나면 오히려 코드를 더 안전하고 예측 가능하게 만들어준다는 것을 알게 될 것입니다.

## 왜 Go에는 예외가 없는가

자바, 파이썬, 자바스크립트 같은 언어는 실패를 표현할 때 예외를 던지고(throw) 잡는(catch) 방식을 씁니다. 이 방식은 정상적인 로직과 실패 처리 로직을 분리할 수 있다는 장점이 있지만, 동시에 몇 가지 문제를 안고 있습니다.

- **함수 시그니처만 봐서는 실패 가능성을 알 수 없습니다.** `readFile(path)`라는 함수가 있을 때, 이 함수가 어떤 예외를 던질 수 있는지는 문서를 찾아보거나 구현을 직접 읽어보기 전까지는 알기 어렵습니다.
- **예외는 호출 스택을 거슬러 조용히 전파됩니다.** 중간에 있는 함수들이 예외 처리를 깜빡해도 컴파일 시점에는 아무 문제가 없어 보이다가, 실행 중에야 처리되지 않은 예외로 프로그램이 죽는 경우가 흔합니다.
- **정상 흐름과 실패 흐름이 코드상 분리되어, 어디서 무엇이 실패할 수 있는지 한눈에 파악하기 어렵습니다.**

Go의 설계자들은 이런 문제를 피하기 위해 정반대의 선택을 했습니다. 에러를 예외적인 사건이 아니라 **평범한 반환값**으로 취급하는 것입니다. 함수가 실패할 수 있다면 시그니처에 그 사실이 그대로 드러나고, 호출자는 그 값을 받아서 즉시 확인해야 합니다.

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	n, err := strconv.Atoi("123")
	if err != nil {
		fmt.Println("변환 실패:", err)
		return
	}
	fmt.Println("변환 성공:", n)
}
```

`strconv.Atoi`는 문자열을 정수로 바꾸는 함수인데, 실패할 수도 있는 작업이라는 것이 반환 타입 `(int, error)`에 그대로 드러나 있습니다. 문서를 뒤지지 않아도 함수 시그니처만으로 "이 함수는 실패할 수 있으니 에러를 확인해야 한다"는 사실을 알 수 있습니다.

Go에도 `panic`과 `recover`라는 도구가 있어서 예외와 비슷한 흐름을 만들 수는 있습니다. 하지만 이는 프로그래머의 버그나 정말로 복구 불가능한 상황을 위한 최후의 수단이며, 일상적인 실패 처리에는 쓰지 않는 것이 Go의 관용입니다. 이 부분은 12장 defer, panic, recover에서 자세히 다룹니다. 이번 장은 "예상 가능한 실패는 error 값으로 다룬다"는 원칙에 집중합니다.

## error 인터페이스의 정체

Go에서 에러는 마법 같은 특별한 타입이 아니라, 그냥 하나의 인터페이스입니다. 10장 인터페이스에서 배운 구조적 타이핑이 여기서도 그대로 적용됩니다. 표준 라이브러리에 있는 `error` 인터페이스의 정의는 다음과 같이 놀랍도록 단순합니다.

```go
type error interface {
	Error() string
}
```

즉, `Error() string`이라는 메서드 하나만 가지고 있으면 어떤 타입이든 `error` 인터페이스를 만족합니다. 별도로 "이 타입은 error를 구현합니다"라고 선언할 필요도 없습니다.

```go
package main

import "fmt"

// myError는 Error() string 메서드를 가지므로 error 인터페이스를 만족한다
type myError struct {
	msg string
}

func (e *myError) Error() string {
	return e.msg
}

func doSomething() error {
	return &myError{msg: "뭔가 잘못됐다"}
}

func main() {
	err := doSomething()
	if err != nil {
		fmt.Println(err) // fmt.Println은 Error() 메서드를 호출해 출력한다
	}
}
```

`fmt.Println`이나 `fmt.Printf`의 `%v`, `%s`는 인자가 `error` 인터페이스를 만족하면 자동으로 `Error()`를 호출해서 문자열로 바꿔줍니다. 에러가 없다는 것은 `error` 값이 `nil`이라는 뜻이며, 그래서 `if err != nil`이 "에러가 발생했는가?"를 확인하는 표준적인 방법이 됩니다.

## 다중 반환값과 if err != nil 패턴

Go 함수는 값을 여러 개 반환할 수 있고, 실패할 가능성이 있는 함수는 관례적으로 **마지막 반환값으로 error를 돌려줍니다.** 표준 라이브러리 전체가 이 관례를 따릅니다.

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	f, err := os.Open("존재하지않는파일.txt")
	if err != nil {
		fmt.Println("파일을 열 수 없습니다:", err)
		return
	}
	defer f.Close() // 정상적으로 열렸을 때만 이 줄에 도달한다
	fmt.Println("파일 열기 성공")
}
```

이 패턴에서 중요한 점은 **에러를 확인하기 전에는 다른 반환값을 신뢰해서는 안 된다**는 것입니다. 위 예제에서 `os.Open`이 실패하면 `f`는 `nil`이 되므로, `err`를 확인하지 않고 바로 `f`를 사용하면 nil 포인터 역참조로 프로그램이 패닉에 빠집니다. 그래서 Go 코드에는 다음과 같은 형태가 끊임없이 반복됩니다.

```go
result, err := doSomething()
if err != nil {
	return err // 혹은 여기서 에러를 처리
}
// 이 지점부터는 err가 nil이라는 것이 보장되므로 result를 안심하고 쓸 수 있다
```

`defer`는 12장에서 자세히 다루지만, 위 예제처럼 "성공적으로 얻은 자원을 함수가 끝날 때 정리한다"는 용도로 에러 처리 패턴과 짝을 이루어 아주 자주 쓰입니다.

반복적으로 느껴질 수 있는 이 패턴은 사실 의도된 설계입니다. 에러가 발생할 수 있는 모든 지점이 코드에 그대로 노출되기 때문에, 코드를 읽는 사람은 "이 함수 호출이 실패하면 무슨 일이 일어나는지"를 굳이 다른 곳을 찾아보지 않아도 바로 옆 줄에서 확인할 수 있습니다. 에러를 확인하지 않고 무시하는 것(`result, _ := doSomething()`)도 문법적으로는 가능하지만, `go vet`이나 `errcheck` 같은 도구, 그리고 코드 리뷰 관례를 통해 지양됩니다.

## errors.New와 fmt.Errorf로 에러 만들기

직접 에러를 만들어야 할 때 가장 간단한 방법은 표준 라이브러리 `errors` 패키지의 `errors.New`입니다.

```go
package main

import (
	"errors"
	"fmt"
)

func divide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, errors.New("0으로 나눌 수 없다")
	}
	return a / b, nil
}

func main() {
	result, err := divide(10, 0)
	if err != nil {
		fmt.Println("에러:", err)
		return
	}
	fmt.Println("결과:", result)
}
```

에러 메시지에 다른 값을 함께 담고 싶다면 `fmt.Errorf`를 사용합니다. `fmt.Printf`와 동일한 서식 지정자를 쓸 수 있어서 훨씬 유연합니다.

```go
func divide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, fmt.Errorf("%.2f를 0으로 나눌 수 없다", a)
	}
	return a / b, nil
}
```

Go의 관례상 에러 메시지는 대문자로 시작하지 않고, 문장 끝에 마침표도 찍지 않습니다. 에러 메시지가 다른 에러 메시지 뒤에 이어 붙여지는 경우가 많기 때문입니다(예: `"user 조회 실패: 0으로 나눌 수 없다"`처럼 연결됨). 이 관례는 `go vet`이 검사해주기도 합니다.

## 에러 래핑: %w로 문맥 추가하기

실무 코드는 여러 계층의 함수를 거치며 호출됩니다. 아래쪽 계층에서 발생한 에러가 위쪽으로 전달될 때, 원래 에러 정보를 잃지 않으면서 "어디서 실패했는지" 문맥을 덧붙이고 싶을 때가 많습니다. 이럴 때 `fmt.Errorf`의 `%w` 서식 지정자를 사용합니다.

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("데이터를 찾을 수 없다")

func fetchUser(id int) error {
	// 실제로는 DB나 파일을 조회하겠지만, 여기서는 항상 실패한다고 가정
	return ErrNotFound
}

func getUserProfile(id int) error {
	if err := fetchUser(id); err != nil {
		// %w로 원본 에러를 감싸면서 어느 단계에서 실패했는지 문맥을 추가한다
		return fmt.Errorf("사용자 프로필 조회 실패 (id=%d): %w", id, err)
	}
	return nil
}

func main() {
	err := getUserProfile(42)
	fmt.Println(err)
	// 출력: 사용자 프로필 조회 실패 (id=42): 데이터를 찾을 수 없다
}
```

`%v`나 `%s`로 에러를 문자열에 끼워 넣으면 그냥 텍스트가 합쳐질 뿐, 원본 에러(`ErrNotFound`)와의 연결 고리는 사라집니다. 반면 `%w`로 감싸면 새로 만들어진 에러 내부에 원본 에러에 대한 참조가 남아서, 나중에 `errors.Is`나 `errors.As`로 "이 에러 체인 안에 그 원본 에러가 들어있는가?"를 확인할 수 있습니다. 이렇게 에러가 여러 겹으로 감싸진 것을 **에러 체인(error chain)**이라고 부릅니다.

## errors.Is: 특정 에러인지 판별하기

에러 체인 어딘가에 특정 에러(주로 **센티널 에러**, sentinel error라고 부르는 미리 정의된 에러 값)가 포함되어 있는지 확인할 때는 `errors.Is`를 사용합니다.

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("데이터를 찾을 수 없다")

func fetchUser(id int) error {
	return fmt.Errorf("사용자 조회 중 실패: %w", ErrNotFound)
}

func main() {
	err := fetchUser(42)

	if errors.Is(err, ErrNotFound) {
		fmt.Println("사용자가 존재하지 않는다") // 이 분기로 들어온다
	} else {
		fmt.Println("알 수 없는 에러:", err)
	}
}
```

`err == ErrNotFound`처럼 직접 비교하면 `false`가 나옵니다. `fetchUser`가 반환한 값은 `ErrNotFound` 그 자체가 아니라 그것을 감싼 새로운 에러이기 때문입니다. `errors.Is`는 `%w`로 연결된 에러 체인을 하나씩 풀어보면서(unwrap) 그 안에 찾는 대상이 있는지 확인해주므로, 에러가 몇 겹으로 감싸져 있든 안전하게 판별할 수 있습니다.

표준 라이브러리에도 이런 식으로 비교해야 하는 센티널 에러가 많습니다. 대표적으로 `io.EOF`(더 읽을 데이터가 없음을 나타내는 에러)나 `os.ErrNotExist`(파일이 존재하지 않음)가 있습니다.

```go
if errors.Is(err, io.EOF) {
	// 파일 끝에 도달한 정상적인 상황으로 처리
}
```

## errors.As: 특정 타입의 에러 꺼내기

센티널 에러처럼 값 하나로 판별하는 것이 아니라, 에러가 담고 있는 **추가 정보**(예: 어떤 필드가 잘못됐는지, 어떤 값이 실패를 유발했는지)를 꺼내 쓰고 싶다면 `errors.As`를 사용합니다. 이를 위해서는 먼저 커스텀 에러 타입을 정의해야 합니다.

```go
package main

import (
	"errors"
	"fmt"
)

// ValidationError는 어떤 필드가 어떤 이유로 유효하지 않은지 담는 커스텀 에러 타입이다
type ValidationError struct {
	Field  string
	Reason string
}

// Error() string 메서드를 가지므로 ValidationError는 error 인터페이스를 만족한다
func (e *ValidationError) Error() string {
	return fmt.Sprintf("필드 %q 검증 실패: %s", e.Field, e.Reason)
}

func validateAge(age int) error {
	if age < 0 {
		return &ValidationError{Field: "age", Reason: "음수일 수 없다"}
	}
	return nil
}

func createUser(age int) error {
	if err := validateAge(age); err != nil {
		return fmt.Errorf("사용자 생성 실패: %w", err)
	}
	return nil
}

func main() {
	err := createUser(-5)

	var validationErr *ValidationError
	if errors.As(err, &validationErr) {
		// 에러 체인 안에서 *ValidationError 타입을 찾아 validationErr에 대입해준다
		fmt.Println("검증 실패 필드:", validationErr.Field)
		fmt.Println("이유:", validationErr.Reason)
	} else {
		fmt.Println("알 수 없는 에러:", err)
	}
}
```

`errors.As(err, &validationErr)`는 `err`의 체인을 따라가면서 `*ValidationError` 타입에 해당하는 에러를 찾고, 찾으면 `validationErr` 변수에 대입한 뒤 `true`를 반환합니다. 두 번째 인자가 반드시 포인터여야 한다는 점에 주의해야 합니다. 이렇게 하면 단순히 "에러가 발생했다"는 사실을 넘어, 그 에러가 어떤 종류인지에 따라 서로 다른 처리를 할 수 있습니다.

`errors.Is`와 `errors.As`를 구분하는 기준은 간단합니다.

- **값 자체가 같은지** 확인하고 싶다면 `errors.Is` (예: "이 에러가 바로 그 `sql.ErrNoRows`인가?")
- **특정 타입인지** 확인하고 그 타입이 가진 부가 정보를 꺼내고 싶다면 `errors.As` (예: "이 에러가 `*ValidationError` 타입이라면 그 Field 값이 뭔가?")

## 커스텀 에러 타입 설계하기

에러에 부가 정보를 담고 싶을 때는 앞서 본 `ValidationError`처럼 구조체로 커스텀 에러 타입을 만드는 것이 좋습니다. 이렇게 하면 문자열 메시지를 파싱하는 방식이 아니라 구조화된 데이터로 실패 원인을 다룰 수 있습니다.

```go
package main

import (
	"errors"
	"fmt"
)

// NotFoundError는 어떤 리소스가 없는지를 구조화된 정보로 담는다
type NotFoundError struct {
	Resource string
	ID       int
}

func (e *NotFoundError) Error() string {
	return fmt.Sprintf("%s(id=%d)를 찾을 수 없다", e.Resource, e.ID)
}

func findUser(id int) (string, error) {
	if id != 1 {
		return "", &NotFoundError{Resource: "user", ID: id}
	}
	return "홍길동", nil
}

func main() {
	_, err := findUser(99)

	var notFound *NotFoundError
	switch {
	case errors.As(err, &notFound):
		fmt.Printf("%s를 찾을 수 없어서 기본값을 사용한다 (id=%d)\n", notFound.Resource, notFound.ID)
	case err != nil:
		fmt.Println("알 수 없는 에러:", err)
	default:
		fmt.Println("정상 처리")
	}
}
```

커스텀 에러 타입을 만들 때 고려할 점을 정리하면 다음과 같습니다.

- 여러 곳에서 재사용되는 단순한 실패 신호라면 패키지 수준의 센티널 에러(`var ErrX = errors.New(...)`)만으로 충분합니다.
- 호출자가 실패 원인에 따라 다르게 동작해야 하고, 그 원인을 판단하는 데 추가 데이터(필드 이름, 잘못된 값, 재시도 가능 여부 등)가 필요하다면 커스텀 에러 타입을 정의하고 `errors.As`로 꺼내 쓰게 합니다.
- 커스텀 에러 타입도 결국 `Error() string` 메서드만 있으면 되므로, 포인터 리시버(`*NotFoundError`)로 구현하는 것이 일반적입니다. 값 리시버로 구현하면 `errors.As`에서 포인터/값 타입을 혼동하기 쉬우므로 포인터로 통일하는 편이 안전합니다.

## 에러 처리 모범 사례

지금까지 배운 내용을 실전에서 적용할 때 도움이 되는 원칙 몇 가지를 정리합니다.

- **에러는 발생 즉시 확인합니다.** `_`로 무시하지 말고, `if err != nil` 뒤에 그 함수가 실패했을 때 무엇을 할지 명확히 작성합니다.
- **문맥을 추가할 때는 `%w`로 감쌉니다.** 단순히 `%v`나 문자열 연결로 새 에러를 만들면 원본 에러의 정체성이 사라져서 나중에 `errors.Is`/`errors.As`로 판별할 수 없게 됩니다.
- **같은 에러를 두 번 로그로 남기지 않습니다.** 에러를 로그에 기록하면서 동시에 호출자에게 반환하면, 상위 계층에서 또 로그를 남길 때 같은 실패가 여러 번 기록됩니다. 에러는 최상위에서 한 번만 로그로 남기고, 중간 계층은 문맥만 추가해서 전달하는 것이 좋습니다.
- **에러 메시지는 소문자로 시작하고 마침표로 끝내지 않습니다.** 다른 메시지 뒤에 이어 붙는 경우가 많기 때문입니다.
- **정말 예외적이고 복구 불가능한 상황이 아니라면 `panic`을 쓰지 않습니다.** "파일이 없다", "입력값이 잘못됐다", "네트워크 요청이 실패했다"처럼 충분히 예상 가능한 실패는 항상 `error`로 표현합니다. `panic`을 언제, 왜 써야 하는지는 12장에서 자세히 다룹니다.

## 요약

- Go에는 예외 대신 `error`를 반환값으로 명시적으로 다루는 관용구가 있습니다. 함수 시그니처만으로 실패 가능성이 드러나고, 호출자가 그 자리에서 바로 처리를 결정할 수 있다는 것이 장점입니다.
- `error`는 `Error() string` 메서드 하나만 가지면 만족되는 평범한 인터페이스입니다. 10장에서 배운 구조적 타이핑이 그대로 적용됩니다.
- 실패할 수 있는 함수는 마지막 반환값으로 `error`를 반환하는 것이 관례이며, 호출자는 `if err != nil` 패턴으로 즉시 확인합니다. 에러를 확인하기 전에는 다른 반환값을 신뢰해서는 안 됩니다.
- `errors.New`로 간단한 에러를, `fmt.Errorf`로 서식이 있는 에러를 만듭니다. `%w`로 감싸면 원본 에러 정보를 유지한 채 문맥을 추가하는 에러 체인을 만들 수 있습니다.
- `errors.Is`는 에러 체인 안에 특정 센티널 에러가 있는지 확인하고, `errors.As`는 체인 안에서 특정 타입의 에러를 찾아 그 안의 부가 정보를 꺼낼 때 사용합니다.
- 부가 정보가 필요한 실패는 `Error() string`을 구현한 커스텀 구조체 타입으로 표현하는 것이 좋습니다.

## 연습문제

1. 문자열 슬라이스에서 특정 값의 인덱스를 찾는 함수 `indexOf(items []string, target string) (int, error)`를 작성해 보세요. 값을 찾지 못하면 `errors.New`로 만든 에러를 반환합니다.
2. 센티널 에러 `var ErrEmptyInput = errors.New("입력이 비어 있다")`를 정의하고, 이를 사용하는 함수를 여러 단계로 감싸서(`fmt.Errorf`의 `%w` 사용) 호출한 뒤, 최상위에서 `errors.Is`로 `ErrEmptyInput`인지 판별해 보세요.
3. `Field`와 `Value`(interface{} 타입) 필드를 가진 `RangeError`라는 커스텀 에러 타입을 만들고, `Error() string`을 구현해 보세요. 그리고 이 에러를 반환하는 함수를 작성한 뒤 `errors.As`로 꺼내서 `Field`와 `Value`를 출력해 보세요.
4. `fmt.Errorf("...: %v", err)`와 `fmt.Errorf("...: %w", err)`로 각각 에러를 감싼 뒤, 두 경우 모두에 대해 `errors.Is`로 원본 에러를 판별해 보고 결과가 왜 다른지 설명해 보세요.
5. 나눗셈을 수행하는 함수에서 0으로 나누는 경우와 음수를 나누는 경우를 서로 다른 커스텀 에러 타입으로 표현하고, `switch`문과 `errors.As`를 조합해 두 경우를 구분해서 처리하는 프로그램을 작성해 보세요.

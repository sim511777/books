지금까지 배운 구조체와 메서드는 "구체적인 타입이 무엇을 할 수 있는가"를 표현했습니다. `Circle`은 `Area()`를 계산할 수 있고, `User`는 `Greet()`를 할 수 있는 식입니다. 하지만 프로그램이 커지면 "구체적으로 무엇인지는 몰라도, 이런 동작만 할 수 있으면 된다"는 식으로 코드를 작성하고 싶을 때가 많습니다. 예를 들어 도형이 원이든 사각형이든 상관없이 "넓이를 구할 수 있는 것들"을 한데 모아 다루고 싶은 경우입니다.

이런 요구를 만족시키는 Go의 도구가 인터페이스(interface)입니다. 인터페이스는 "어떤 메서드를 가지고 있어야 하는가"만 정의하고, 그 메서드를 실제로 어떻게 구현하는지는 신경 쓰지 않습니다. 이번 장에서는 인터페이스를 정의하는 문법부터, Go 인터페이스의 가장 독특한 특징인 암묵적 구현, 그리고 빈 인터페이스와 타입 단언까지 살펴보겠습니다.

## 인터페이스 정의 문법

인터페이스는 `type` 키워드와 `interface` 키워드로 정의합니다. 인터페이스 안에는 메서드의 이름과 시그니처(매개변수 타입과 반환 타입)만 나열합니다.

```go
package main

import "fmt"

// Shape 인터페이스: Area 메서드를 가진 모든 타입을 나타낸다
type Shape interface {
	Area() float64
}
```

`Shape`는 "`Area() float64`라는 메서드를 가진 모든 타입"을 나타내는 타입입니다. 이 정의 자체는 어떤 필드도, 어떤 구체적인 구현도 담고 있지 않습니다. 오직 "이런 메서드가 있어야 한다"는 계약(contract)만 표현합니다.

인터페이스는 메서드를 여러 개 가질 수도 있습니다.

```go
type Shape interface {
	Area() float64
	Perimeter() float64
}
```

이제 `Shape` 인터페이스를 만족시키려면 `Area() float64`와 `Perimeter() float64` 두 메서드를 모두 갖추어야 합니다.

## Go의 암묵적 구현: implements가 없다

자바나 C#같은 언어에서는 어떤 클래스가 인터페이스를 구현한다는 것을 `implements` 키워드로 명시적으로 선언합니다. Go에는 그런 키워드가 아예 없습니다. Go에서는 어떤 타입이 인터페이스가 요구하는 메서드를 모두 가지고 있기만 하면, 별도의 선언 없이 자동으로 그 인터페이스를 만족한 것으로 취급됩니다. 이를 암묵적 구현(implicit implementation)이라고 부릅니다.

```go
package main

import (
	"fmt"
	"math"
)

type Shape interface {
	Area() float64
	Perimeter() float64
}

// Circle은 Shape를 구현한다고 어디에도 선언하지 않았다
type Circle struct {
	Radius float64
}

func (c Circle) Area() float64 {
	return math.Pi * c.Radius * c.Radius
}

func (c Circle) Perimeter() float64 {
	return 2 * math.Pi * c.Radius
}

func main() {
	var s Shape = Circle{Radius: 5} // Circle이 Shape의 메서드를 모두 가지고 있으므로 대입 가능
	fmt.Printf("넓이: %.2f\n", s.Area())
	fmt.Printf("둘레: %.2f\n", s.Perimeter())
}
```

`Circle`을 정의하는 곳 어디에도 "`Circle`은 `Shape`를 구현한다"는 문장이 없습니다. 그런데도 `Circle` 값을 `Shape` 타입 변수에 대입할 수 있습니다. Go 컴파일러가 `Circle`의 메서드 집합을 살펴보고, `Shape`가 요구하는 `Area()`와 `Perimeter()`를 모두 가지고 있음을 확인한 뒤 자동으로 통과시켜 주기 때문입니다.

이런 방식을 구조적 타이핑(structural typing)이라고 부릅니다. "이름이 무엇인지"가 아니라 "어떤 구조(메서드 집합)를 가지고 있는지"로 타입 호환성을 판단하는 방식입니다. 덕분에 다음과 같은 실전 이점이 생깁니다.

- 이미 존재하는 타입에 대해, 그 타입의 코드를 전혀 건드리지 않고도 새로운 인터페이스를 나중에 정의해서 끼워 맞출 수 있습니다.
- 인터페이스를 사용하는 쪽과 구현하는 쪽이 서로의 존재를 몰라도 됩니다. 표준 라이브러리가 정의한 인터페이스를 내가 만든 타입이 자연스럽게 만족시키는 일도 흔합니다(표준 라이브러리는 17장 "표준 라이브러리 둘러보기"에서 더 살펴봅니다).
- 테스트를 작성할 때 실제 구현 대신 가짜(mock) 구현을 쉽게 끼워 넣을 수 있습니다.

## 여러 구조체가 하나의 인터페이스를 구현하기

암묵적 구현의 힘은 여러 타입이 같은 인터페이스를 만족시킬 때 잘 드러납니다. 서로 다른 도형 구조체 세 개가 같은 `Shape` 인터페이스를 만족시키는 예제를 살펴보겠습니다.

```go
package main

import (
	"fmt"
	"math"
)

type Shape interface {
	Area() float64
	Perimeter() float64
}

type Circle struct {
	Radius float64
}

func (c Circle) Area() float64 {
	return math.Pi * c.Radius * c.Radius
}

func (c Circle) Perimeter() float64 {
	return 2 * math.Pi * c.Radius
}

type Rectangle struct {
	Width, Height float64
}

func (r Rectangle) Area() float64 {
	return r.Width * r.Height
}

func (r Rectangle) Perimeter() float64 {
	return 2 * (r.Width + r.Height)
}

type Triangle struct {
	Base, Height float64 // 넓이 계산용
	A, B, C      float64 // 세 변의 길이, 둘레 계산용
}

func (t Triangle) Area() float64 {
	return 0.5 * t.Base * t.Height
}

func (t Triangle) Perimeter() float64 {
	return t.A + t.B + t.C
}

func main() {
	shapes := []Shape{
		Circle{Radius: 3},
		Rectangle{Width: 4, Height: 5},
		Triangle{Base: 6, Height: 4, A: 5, B: 5, C: 6},
	}

	for _, s := range shapes {
		fmt.Printf("넓이: %.2f, 둘레: %.2f\n", s.Area(), s.Perimeter())
	}
}
```

`Circle`, `Rectangle`, `Triangle`은 서로 아무런 관계가 없는 독립된 구조체입니다. 상속 관계도 없고, 공통 부모 타입도 없습니다. 그런데도 셋 다 `Area()`와 `Perimeter()`라는 메서드를 가지고 있다는 이유만으로 `[]Shape` 슬라이스 하나에 담길 수 있습니다. `for range`로 순회하면서 `s.Area()`를 호출할 때, 실제로 어떤 메서드가 실행될지는 그 슬라이스 원소가 어떤 구체적인 타입인지에 따라 런타임에 결정됩니다. 이를 동적 디스패치(dynamic dispatch)라고 합니다.

다음 그림은 세 구조체가 하나의 `Shape` 인터페이스를 암묵적으로 만족시키는 관계를 보여줍니다.

```text
여러 구조체의 암묵적 인터페이스 구현

                    +---------------------------+
                    |     Shape 인터페이스        |
                    |  Area() float64           |
                    |  Perimeter() float64      |
                    +---------------------------+
                       ^          ^          ^
                       :          :          :  (메서드 집합이 일치, implements 선언 없음)
                       :          :          :
      +--------------+   +--------------+   +--------------+
      |    Circle    |   |  Rectangle   |   |   Triangle   |
      +--------------+   +--------------+   +--------------+
      | Radius       |   | Width,Height |   | Base,Height, |
      |              |   |              |   | A,B,C        |
      | Area()       |   | Area()       |   | Area()       |
      | Perimeter()  |   | Perimeter()  |   | Perimeter()  |
      +--------------+   +--------------+   +--------------+

  var shapes []Shape = []Shape{Circle{...}, Rectangle{...}, Triangle{...}}

  세 구조체 모두 Area()와 Perimeter()를 가지고 있으므로,
  "implements Shape" 같은 선언 없이도 Shape 타입 변수에 그대로 담을 수 있다
  -> 이것이 구조적 타이핑(structural typing)이다
```

화살표가 점선으로 그려진 이유는 실제 코드에 이런 연결을 명시하는 선언이 존재하지 않기 때문입니다. 이 연결은 오직 "메서드 집합이 일치하는가"라는 컴파일 타임 검사로만 성립합니다.

## 인터페이스는 값이 아니라 계약이다

한 가지 기억할 점은, 인터페이스 타입의 변수 자체는 아무 데이터도 담고 있지 않다는 것입니다. 인터페이스 변수는 내부적으로 두 가지 정보, 즉 "실제 값의 구체적인 타입이 무엇인지"와 "그 값이 무엇인지"를 함께 담고 있습니다. 앞의 예제에서 `s`는 `Shape` 타입이지만, 실제로는 `Circle{Radius: 3}`이라는 구체적인 값과 타입 정보를 함께 들고 있는 상자라고 생각하면 됩니다.

```go
var s Shape = Circle{Radius: 3}
fmt.Printf("%T\n", s) // main.Circle — 실제 저장된 구체 타입이 출력된다
```

## 빈 인터페이스(interface{})와 any

메서드를 하나도 요구하지 않는 인터페이스, 즉 `interface{}`는 특별한 의미를 가집니다. 모든 타입은 메서드를 0개 이상 가지고 있으므로, 어떤 타입이든 예외 없이 `interface{}`를 만족시킵니다. 즉 `interface{}` 타입의 변수에는 어떤 값이든 담을 수 있습니다.

```go
package main

import "fmt"

func describe(v interface{}) {
	fmt.Printf("값: %v, 타입: %T\n", v, v)
}

func main() {
	describe(42)
	describe("hello")
	describe(3.14)
	describe([]int{1, 2, 3})
}
```

Go 1.18부터는 `interface{}`와 완전히 같은 의미를 가지는 `any`라는 별칭(alias)이 추가되었습니다. 요즘 작성되는 Go 코드는 대부분 `interface{}` 대신 `any`를 사용합니다.

```go
func describe(v any) { // interface{}와 동일하지만 훨씬 읽기 좋다
	fmt.Printf("값: %v, 타입: %T\n", v, v)
}
```

### 빈 인터페이스를 사용할 때 주의할 점

`any`는 편리하지만 남용하면 Go의 가장 큰 장점인 컴파일 타임 타입 검사를 포기하게 됩니다.

```go
func sum(a, b any) any {
	// a와 b가 실제로 숫자인지 컴파일 타임에는 전혀 보장되지 않는다
	return nil // 실제 덧셈을 어떻게 구현할지도 애매하다
}
```

`any`를 매개변수나 반환값으로 사용하면 함수를 호출하는 쪽도, 구현하는 쪽도 "실제로 어떤 타입이 들어올지"를 코드만 보고 알 수 없습니다. 결국 함수 내부에서 타입을 검사하고 분기하는 코드가 필요해지며, 실수로 기대하지 않은 타입을 넘기면 컴파일 타임이 아니라 런타임에야 문제가 발견됩니다.

```go
func printLength(v any) {
	s := v.(string) // v가 string이 아니면 여기서 패닉!
	fmt.Println(len(s))
}

printLength(42) // panic: interface conversion: interface {} is int, not string
```

가능하다면 `any` 대신 구체적인 타입이나, 필요한 메서드만 요구하는 좁은 인터페이스를 사용하는 것이 안전합니다. `any`는 정말로 "어떤 타입이든 상관없이 담아두기만 하면 되는" 상황(로그 기록, JSON 직렬화, 범용 컨테이너 등)에 한정해서 사용하는 것이 좋습니다. Go 1.18 이후에는 이런 상황 중 상당수를 제네릭으로 더 안전하게 표현할 수 있게 되었지만, 제네릭은 이 책의 범위를 벗어나므로 다루지 않습니다.

## 타입 단언: 인터페이스 값의 실제 타입 꺼내기

인터페이스 변수 안에 담긴 값의 구체적인 타입을 알고 있다면, 타입 단언(type assertion) 문법으로 그 값을 원래 타입으로 꺼낼 수 있습니다.

```go
var v any = "hello"

s := v.(string) // v의 실제 타입이 string이라고 "단언"한다
fmt.Println(s)  // hello
```

만약 단언한 타입이 실제 타입과 다르면 패닉이 발생합니다.

```go
var v any = "hello"
n := v.(int) // panic: interface conversion: interface {} is string, not int
```

패닉을 피하고 싶다면 두 번째 반환값을 받는 형태를 사용합니다. 이 형태는 단언이 성공했는지를 나타내는 `bool` 값을 함께 반환하며, 실패해도 패닉을 일으키지 않습니다.

```go
var v any = "hello"

s, ok := v.(string)
fmt.Println(s, ok) // hello true

n, ok := v.(int)
fmt.Println(n, ok) // 0 false — 실패해도 패닉이 아니라 제로 값과 false를 반환
```

이 `ok` 형태는 `if`와 함께 자주 사용됩니다.

```go
func printIfString(v any) {
	if s, ok := v.(string); ok {
		fmt.Println("문자열입니다:", s)
	} else {
		fmt.Println("문자열이 아닙니다")
	}
}
```

## 타입 스위치: 여러 타입을 한 번에 분기하기

확인해야 할 타입이 여러 개라면 `v.(type)` 문법을 사용하는 타입 스위치(type switch)가 훨씬 깔끔합니다.

```go
package main

import "fmt"

func describe(v any) {
	switch x := v.(type) {
	case int:
		fmt.Printf("int입니다: %d\n", x)
	case string:
		fmt.Printf("string입니다: %q\n", x)
	case bool:
		fmt.Printf("bool입니다: %t\n", x)
	case []int:
		fmt.Printf("int 슬라이스입니다: %v (길이 %d)\n", x, len(x))
	case nil:
		fmt.Println("nil입니다")
	default:
		fmt.Printf("알 수 없는 타입입니다: %T\n", x)
	}
}

func main() {
	describe(42)
	describe("hello")
	describe(true)
	describe([]int{1, 2, 3})
	describe(nil)
	describe(3.14)
}
```

각 `case` 블록 안에서 `x`는 그 `case`에 해당하는 구체적인 타입으로 자동 변환됩니다. 예를 들어 `case string:` 블록 안에서는 `x`가 `string` 타입이므로, 타입 단언 없이 곧바로 문자열 메서드나 연산을 사용할 수 있습니다. 이 문법은 4장에서 다룬 일반 `switch`문과 형태는 비슷하지만, 비교 대상이 값이 아니라 타입이라는 점이 다릅니다.

타입 스위치는 인터페이스 값을 받아 그 실제 타입에 따라 처리를 분기해야 할 때, 예를 들어 서로 다른 종류의 이벤트나 메시지를 처리하는 코드에서 특히 유용합니다.

```go
type Event interface {
	Name() string
}

type ClickEvent struct{ X, Y int }

func (ClickEvent) Name() string { return "click" }

type KeyEvent struct{ Key string }

func (KeyEvent) Name() string { return "key" }

func handle(e Event) {
	switch ev := e.(type) {
	case ClickEvent:
		fmt.Printf("클릭 위치: (%d, %d)\n", ev.X, ev.Y)
	case KeyEvent:
		fmt.Printf("눌린 키: %s\n", ev.Key)
	default:
		fmt.Println("알 수 없는 이벤트:", ev.Name())
	}
}
```

## 인터페이스를 작게 유지하기

Go 표준 라이브러리와 커뮤니티에는 "인터페이스는 작을수록 좋다"는 관례가 널리 퍼져 있습니다. 메서드 하나만 요구하는 인터페이스가 이상적이라는 뜻에서 나온 말도 있을 정도입니다. 예를 들어 표준 라이브러리의 `io.Writer`는 다음과 같이 단 하나의 메서드만 요구합니다.

```go
type Writer interface {
	Write(p []byte) (n int, err error)
}
```

메서드 하나만 요구하기 때문에, `Write` 메서드를 가진 어떤 타입이든(파일, 네트워크 연결, 메모리 버퍼, 심지어 직접 만든 로그 타입까지) 별도의 선언 없이 자동으로 `io.Writer`가 됩니다. 인터페이스가 커질수록 그 인터페이스를 만족시켜야 하는 타입의 부담도 커지므로, 꼭 필요한 메서드만 담은 작은 인터페이스를 여러 개 만들고 필요하면 조합해서 쓰는 방식이 Go다운 설계로 여겨집니다. 이런 설계 습관은 18장 "좋은 Go 코드 작성 습관"에서 다시 다룹니다.

## 요약

- 인터페이스는 메서드의 이름과 시그니처만 정의하는 계약이며, `type 이름 interface { ... }` 형태로 선언합니다.
- Go에는 `implements` 키워드가 없습니다. 어떤 타입이 인터페이스가 요구하는 메서드를 모두 가지고 있으면 별도 선언 없이 자동으로 그 인터페이스를 만족합니다. 이를 암묵적 구현, 또는 구조적 타이핑이라고 부릅니다.
- 서로 관계없는 여러 구조체가 같은 메서드 집합을 가지고 있다면 하나의 인터페이스 슬라이스에 함께 담아 다룰 수 있으며, 실제 실행될 메서드는 런타임에 구체 타입에 따라 결정됩니다(동적 디스패치).
- `interface{}`(또는 `any`)는 메서드를 요구하지 않아 모든 타입을 담을 수 있지만, 컴파일 타임 타입 검사를 포기하는 대가가 따르므로 꼭 필요한 곳에만 사용해야 합니다.
- `v.(T)` 형태의 타입 단언으로 인터페이스 값의 구체 타입을 꺼낼 수 있고, `v, ok := v.(T)` 형태를 사용하면 실패해도 패닉 없이 `ok`로 성공 여부를 확인할 수 있습니다.
- 여러 타입을 한 번에 분기해야 한다면 `switch v := x.(type) { case T1: ... }` 형태의 타입 스위치를 사용합니다.
- 인터페이스는 작게 유지하는 것이 Go다운 설계입니다. 꼭 필요한 메서드만 요구하는 인터페이스일수록 더 많은 타입이 자연스럽게 만족시킬 수 있습니다.

## 연습문제

1. `Speaker`라는 인터페이스를 정의해 `Speak() string` 메서드를 요구하도록 만들고, `Dog`와 `Cat` 구조체가 각각 다른 문자열을 반환하는 `Speak()` 메서드를 구현하게 하세요. `[]Speaker` 슬라이스에 두 타입의 값을 담아 `for range`로 순회하며 출력해 보세요.
2. 본문의 `Circle`, `Rectangle`, `Triangle` 예제를 참고해 `Square` 구조체를 추가로 정의하고, `Shape` 인터페이스를 만족시키도록 `Area()`와 `Perimeter()`를 구현해 `shapes` 슬라이스에 포함시켜 보세요.
3. `any` 타입 매개변수를 받아 타입 스위치로 `int`, `float64`, `string`, 그 외 타입을 구분해 서로 다른 메시지를 출력하는 함수를 작성해 보세요.
4. 타입 단언의 두 가지 형태(`v.(T)`와 `v, ok := v.(T)`)를 각각 사용하는 코드를 작성하고, 실제 타입과 다른 타입으로 단언했을 때 두 형태의 동작이 어떻게 다른지(패닉 발생 여부) 확인해 보세요.
5. 메서드를 하나만 요구하는 `Closer` 인터페이스(`Close() error`)를 정의하고, 서로 다른 두 구조체(`FileHandle`, `NetworkConn` 등 임의로 정의)가 이를 만족시키도록 구현한 뒤, 왜 인터페이스를 작게 유지하는 것이 여러 타입이 재사용하기 쉬운지 설명해 보세요.

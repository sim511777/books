지금까지 이 책은 Go 언어의 문법과 기능을 순서대로 소개해 왔습니다. 문법을 안다고 해서 곧바로 좋은 코드를 쓸 수 있는 것은 아닙니다. 같은 문법으로도 읽기 쉬운 코드와 그렇지 않은 코드, 유지보수하기 쉬운 코드와 그렇지 않은 코드를 얼마든지 만들 수 있습니다. 이번 장에서는 Go 커뮤니티가 오랜 시간에 걸쳐 다져온 관용적인(idiomatic) 스타일과, 지금까지 배운 개념들을 실무에서 어떻게 조합해 쓰는지 정리합니다. 이 책의 마지막 장이기도 하니, 앞으로 무엇을 더 공부하면 좋을지도 함께 이야기해 보겠습니다.

## 관용적인 Go 스타일

### 도구가 스타일을 대신 잡아준다

Go는 언어 설계 단계부터 "코드 스타일 논쟁을 없앤다"는 목표를 가지고 있었습니다. 그 결과로 나온 도구가 `gofmt`입니다.

```bash
gofmt -l .    # 포맷이 맞지 않는 파일 목록 출력
gofmt -w .    # 포맷을 자동으로 맞춰서 덮어쓰기
```

`gofmt`는 들여쓰기에 탭을 쓸지 스페이스를 쓸지, 중괄호를 어느 줄에 놓을지 같은 논쟁을 원천적으로 없애줍니다. 이 책의 모든 코드 예제도 `gofmt` 규칙(탭 들여쓰기 등)을 따르고 있습니다. 대부분의 편집기는 저장할 때 자동으로 `gofmt`를 실행하도록 설정할 수 있으니, 처음부터 습관을 들여두는 것이 좋습니다.

포맷을 넘어서 코드의 잠재적인 문제까지 짚어주는 도구도 있습니다.

- `go vet`: 표준 도구 체인에 포함되어 있으며, `Printf` 서식 지정자 불일치나 도달할 수 없는 코드처럼 컴파일은 되지만 버그일 가능성이 높은 패턴을 찾아줍니다.
- `golint`(또는 그 후속 도구들): 명명 규칙이나 문서 주석 누락처럼 스타일에 가까운 문제를 지적해 줍니다.

이런 도구를 CI(지속적 통합) 파이프라인에 넣어두면, 사람이 코드 리뷰에서 "여기 포맷 틀렸어요" 같은 지적을 할 필요가 없어져서 리뷰가 정말 중요한 로직에 집중할 수 있게 됩니다.

### 짧은 변수명 관례

다른 언어에서 넘어온 개발자는 Go 코드의 변수명이 유난히 짧다는 인상을 받곤 합니다. 이는 게으름이 아니라 관례입니다. Go에서는 변수의 **스코프가 짧을수록 이름도 짧게** 짓는 경향이 있습니다.

```go
// 관용적인 Go 스타일: 스코프가 짧으면 이름도 짧다
for i, v := range items {
	fmt.Println(i, v)
}

if err := doSomething(); err != nil {
	return err
}
```

몇 가지 널리 쓰이는 관례를 정리하면 다음과 같습니다.

| 이름 | 관례적 의미 |
|---|---|
| `i`, `j`, `k` | 반복문의 인덱스 |
| `err` | 에러 값 (거의 예외 없이 이 이름을 씀) |
| `ok` | 콤마-ok 관용구의 두 번째 반환값 |
| `s` | 문자열 |
| `r`, `w` | 각각 Reader, Writer |
| `ctx` | `context.Context` |

반대로 함수나 패키지 수준처럼 스코프가 넓은 곳에서 정의되는 이름, 그리고 exported 식별자(패키지 밖에서도 쓰이는 이름)는 의미가 분명하게 드러나도록 충분히 설명적으로 짓습니다. `for i := 0; i < 10; i++`의 `i`는 괜찮지만, 패키지 최상위에 있는 함수를 `f`라고 짓는 것은 좋은 습관이 아닙니다.

## 에러 처리 패턴 정리

11장과 12장에서 Go의 에러 처리와 `panic`/`recover`를 자세히 다뤘습니다. 여기서는 실무에서 자주 쓰이는 패턴을 한데 모아 정리합니다.

### 원칙: 에러는 값이고, 그 자리에서 처리한다

```go
data, err := os.ReadFile("config.json")
if err != nil {
	return fmt.Errorf("설정 파일을 읽는 중 오류: %w", err)
}
```

- 에러가 발생할 수 있는 함수를 호출한 직후에는 항상 `if err != nil`로 확인합니다.
- 에러를 그대로 무시하거나(`_`로 버리거나) 나중으로 미루지 않습니다. 에러를 처리할 수 없는 상황이라도 최소한 호출자에게 전달해야 합니다.
- `%w` 서식 지정자로 에러를 감싸면(wrap) 원본 에러 정보를 유지한 채로 맥락을 덧붙일 수 있고, 호출자는 `errors.Is`나 `errors.As`로 감싸진 원본 에러를 확인할 수 있습니다.

### panic은 정말 예외적인 상황에만

12장에서 배웠듯, `panic`은 프로그램이 계속 진행할 수 없는 진짜 예외 상황(초기화 실패, 프로그래머의 명백한 실수로 인한 불변조건 위반 등)을 위한 것입니다. "파일을 찾을 수 없다", "네트워크 요청이 실패했다"처럼 충분히 예상 가능한 실패는 `panic`이 아니라 `error` 반환값으로 표현하는 것이 Go의 관용입니다. 라이브러리를 만든다면 특히 이 원칙이 중요합니다. 라이브러리가 예상 가능한 실패로 `panic`을 일으키면, 그 라이브러리를 사용하는 모든 코드가 `recover`로 방어해야 하는 부담을 지게 됩니다.

```go
// 좋지 않은 예: 예상 가능한 실패에 panic을 사용
func mustParseAge(s string) int {
	n, err := strconv.Atoi(s)
	if err != nil {
		panic(err) // 호출자가 recover 없이는 프로그램이 그대로 종료된다
	}
	return n
}

// 관용적인 예: error를 반환해서 호출자가 선택하게 한다
func parseAge(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("나이 파싱 실패: %w", err)
	}
	return n, nil
}
```

## 인터페이스는 사용하는 쪽에서 작게 정의하기

10장에서 인터페이스를 배울 때 언급했듯, Go의 인터페이스는 구조적 타이핑을 따르기 때문에 "이 타입이 이 인터페이스를 구현합니다"라고 선언할 필요가 없습니다. 이 특성 덕분에 Go 커뮤니티에는 다음과 같은 격언이 자리 잡았습니다.

> "인터페이스는 사용하는 쪽에서 정의하라(accept interfaces, return structs)."

즉, 함수를 만드는 쪽에서는 필요한 동작만 담은 작은 인터페이스를 매개변수로 받고, 반환값은 구체적인 구조체 타입으로 돌려주는 것이 좋습니다.

```go
// 관용적이지 않은 예: 굳이 필요하지 않은 넓은 인터페이스를 요구
func saveToFile(f *os.File, data []byte) error {
	_, err := f.Write(data)
	return err
}

// 관용적인 예: 정말 필요한 동작(Write)만 요구하는 작은 인터페이스
func saveTo(w io.Writer, data []byte) error {
	_, err := w.Write(data)
	return err
}
```

`saveTo` 함수는 `*os.File`뿐 아니라 `io.Writer` 인터페이스를 만족하는 어떤 타입(네트워크 연결, 메모리 버퍼, 테스트용 가짜 객체 등)이라도 받을 수 있어 재사용성과 테스트 용이성이 크게 좋아집니다. 인터페이스는 크게 만들수록 구현하기 어려워지고, 작게 만들수록 누구나 쉽게 구현할 수 있습니다. 표준 라이브러리의 `io.Reader`, `io.Writer`처럼 메서드 하나짜리 인터페이스가 Go에서 특히 많이 보이는 이유도 여기에 있습니다.

## 동시성 코드의 흔한 실수

13장부터 15장까지 고루틴, 채널, `sync` 패키지를 다뤘습니다. 동시성 코드는 강력한 만큼 실수하기도 쉬운 영역입니다. 실무에서 특히 자주 나오는 세 가지 실수를 정리합니다.

### 1. 고루틴 누수

고루틴을 실행시켜 놓고 그 고루틴이 끝날 방법을 마련해 두지 않으면, 그 고루틴은 프로그램이 끝날 때까지 메모리에 남아있는 "누수" 상태가 됩니다.

```go
// 문제: 아무도 이 채널을 읽지 않으면 고루틴은 영원히 블록된 채로 남는다
func leak() {
	ch := make(chan int)
	go func() {
		val := compute()
		ch <- val // 읽는 쪽이 없다면 여기서 영원히 멈춘다
	}()
	// ch를 읽지 않고 함수가 끝나버림
}
```

고루틴을 만들 때는 항상 "이 고루틴이 언제, 어떻게 끝나는가?"를 스스로 물어봐야 합니다. `context.Context`로 취소 신호를 전달하거나, 버퍼가 있는 채널을 사용하거나, `sync.WaitGroup`으로 종료를 기다리는 방법으로 고루틴의 생명주기를 명확히 관리하는 것이 좋습니다.

### 2. 경쟁 상태(race condition)

여러 고루틴이 동기화 없이 같은 변수를 동시에 읽고 쓰면 결과를 예측할 수 없습니다.

```go
// 문제: counter++는 원자적 연산이 아니어서 값이 유실될 수 있다
var counter int
var wg sync.WaitGroup

for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		counter++ // 여러 고루틴이 동시에 읽고 쓴다
	}()
}
wg.Wait()
fmt.Println(counter) // 1000이 아닐 수 있다
```

이런 문제는 `go run -race` 또는 `go test -race`로 실행하면 Go의 레이스 디텍터가 상당수 잡아줍니다. 실제 프로젝트에서는 습관적으로 `-race` 플래그를 켜고 테스트하는 것이 좋습니다. 해결 방법은 14~15장에서 다룬 대로 `sync.Mutex`로 공유 변수 접근을 보호하거나, 애초에 공유 변수 대신 채널로 값을 주고받는 방식으로 설계를 바꾸는 것입니다.

```go
// 해결: Mutex로 공유 변수 접근을 보호
var mu sync.Mutex
var counter int

for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		mu.Lock()
		counter++
		mu.Unlock()
	}()
}
```

### 3. 데드락(deadlock)

서로가 서로를 기다리기만 하면서 아무도 진행하지 못하는 상태입니다.

```go
// 문제: 버퍼 없는 채널에 아무도 받는 사람이 없는 상태에서 보내기만 함
func deadlock() {
	ch := make(chan int)
	ch <- 1 // 받는 고루틴이 없으므로 여기서 영원히 멈춘다
	fmt.Println(<-ch)
}
```

데드락은 대부분 "채널에 보내는 쪽과 받는 쪽의 짝이 맞지 않는다"거나 "이미 잠근 `Mutex`를 다시 잠그려 한다"에서 비롯됩니다. 채널을 사용할 때는 항상 받는 고루틴이 준비되어 있는지, `Mutex`를 사용할 때는 `Lock`과 `Unlock`이 반드시 짝을 이루는지(가급적 `defer mu.Unlock()`으로 짝을 강제하는지) 확인하는 습관이 중요합니다.

## 테스트의 필요성

이 책에서는 다루지 않았지만, Go에는 표준 라이브러리에 `testing` 패키지가 기본으로 포함되어 있어서 별도의 도구 설치 없이 바로 테스트 코드를 작성할 수 있습니다. `go test` 명령 하나로 프로젝트 전체의 테스트를 실행할 수 있다는 점은 Go의 큰 장점 중 하나입니다. 지금까지 배운 함수와 에러 처리, 인터페이스에 대한 이해가 쌓였다면 `testing` 패키지는 자연스럽게 다음으로 배울 만한 주제이니, 여유가 될 때 꼭 살펴보시기 바랍니다.

여기까지 오셨다면 Go 언어의 핵심 문법과 표준 라이브러리, 그리고 관용적인 코드 작성 습관까지 한 바퀴 돌아본 셈입니다. 이제부터는 실제로 무언가를 만들어보며 배운 것을 몸에 익히는 단계입니다. 몇 가지 방향을 제안하면 다음과 같습니다.

- **동시성을 활용하는 프로그램**: 13~15장에서 배운 고루틴과 채널을 실제로 활용해, 여러 파일을 동시에 처리하거나 여러 네트워크 요청을 병렬로 보내는 프로그램을 만들어 보며 감각을 키워보세요.
- **클라우드 네이티브 환경으로 확장**: Go는 컨테이너, 오케스트레이션, 인프라 도구 생태계에서 널리 쓰이는 언어입니다. 직접 작성한 프로그램을 컨테이너 이미지로 만들어 배포해보는 경험은 실무 감각을 키우는 데 큰 도움이 됩니다.

어떤 방향으로 나아가든, 작은 프로그램을 직접 완성해보는 경험이 가장 좋은 스승입니다. 이 책이 그 여정의 튼튼한 출발점이 되었기를 바랍니다.

## 요약

- `gofmt`로 포맷을, `go vet`이나 린트 도구로 잠재적 문제를 자동으로 점검하는 습관을 들이면 코드 리뷰가 로직에 집중할 수 있습니다.
- 변수 이름은 스코프가 짧을수록 짧게, exported 식별자처럼 넓은 스코프에서 쓰일수록 설명적으로 짓습니다.
- 에러는 발생한 자리에서 `if err != nil`로 확인하고 필요하면 `%w`로 감싸 전달하며, `panic`은 프로그램이 계속될 수 없는 진짜 예외 상황에만 사용합니다.
- 인터페이스는 사용하는 쪽에서 필요한 동작만 담아 작게 정의하고("accept interfaces, return structs"), 구현체는 구체적인 구조체 타입으로 반환합니다.
- 동시성 코드에서는 고루틴 누수, 경쟁 상태, 데드락이라는 세 가지 흔한 함정을 항상 염두에 두고, `-race` 플래그로 검증하는 습관을 들입니다.
- 표준 라이브러리의 `testing` 패키지로 테스트를 작성하는 방법은 이 책 이후의 자연스러운 다음 학습 주제입니다.

## 체크리스트

Go 코드를 작성하거나 리뷰할 때 다음 항목을 스스로 점검해 보세요.

- [ ] 코드를 커밋하기 전에 `gofmt`(또는 편집기의 저장 시 자동 포맷)를 거쳤는가?
- [ ] `go vet`(혹은 린트 도구)을 실행해서 나온 경고를 확인했는가?
- [ ] 변수 이름의 길이가 그 변수의 스코프 크기와 어울리는가?
- [ ] 에러를 반환하는 함수를 호출한 직후 `if err != nil`로 확인하고 있는가? 에러를 조용히 버리고 있지는 않은가?
- [ ] `panic`을 예상 가능한 실패(파일 없음, 잘못된 입력 등)에 사용하고 있지는 않은가?
- [ ] 함수가 받는 인터페이스가 정말 필요한 동작만 담고 있는가, 아니면 불필요하게 넓은 인터페이스를 요구하고 있는가?
- [ ] 새로 만든 고루틴이 언제 어떻게 끝나는지 설명할 수 있는가?
- [ ] 여러 고루틴이 공유하는 변수에 동기화 없이 접근하고 있지는 않은가? `-race` 플래그로 확인해 보았는가?
- [ ] 채널을 주고받을 때 보내는 쪽과 받는 쪽의 짝이 맞는지 확인했는가?
- [ ] 핵심 로직에 대해 `testing` 패키지를 이용한 테스트를 작성할 계획이 있는가?

## 함수가 변수를 "기억"한다는 것

9장 마지막에서 `make-adder`라는 함수를 만들어봤습니다. 이 함수는 `n`을 인자로 받아서, "x에 n을 더하는" 새로운 함수를 반환했습니다.

```lisp
(defun make-adder (n)
  (lambda (x) (+ x n)))

* (defparameter *add5* (make-adder 5))
*ADD5*

* (funcall *add5* 10)
15
```

곰곰이 생각해보면 이상한 일입니다. `make-adder`가 호출을 마치고 값을 반환한 순간, 그 함수의 지역 변수 `n`은 이미 "사라졌어야" 할 것 같습니다. 함수 호출이 끝나면 그 안에서 만들어진 지역 변수들은 보통 함께 정리되기 때문입니다. 그런데 `*add5*`를 나중에 호출해보면, `n`이 5였다는 사실을 여전히 정확하게 기억하고 있습니다.

이렇게 자신을 만들어낸 환경(주변의 지역 변수들)을 함께 붙들고 다니는 함수를 **클로저(closure)**라고 부릅니다. "클로저"라는 이름은 함수가 자유 변수(자신의 매개변수가 아닌, 바깥에서 가져온 변수)를 그 정의 시점의 값으로 "닫아서(close over)" 가둔다는 뜻에서 왔습니다.

## 렉시컬 스코프: 정의된 위치가 기준이다

클로저가 가능한 이유는 Common Lisp이 기본적으로 **렉시컬 스코프(lexical scope)**를 따르기 때문입니다. 렉시컬 스코프란, 변수가 어떤 값을 가리키는지가 코드가 **작성된 위치**를 기준으로 결정된다는 뜻입니다. "렉시컬(lexical)"이라는 말 자체가 "글자로 쓰인 대로"라는 뜻을 담고 있습니다.

6장에서 배운 `let`을 다시 떠올려봅시다.

```lisp
* (let ((n 5))
    (lambda (x) (+ x n)))
#<FUNCTION (LAMBDA (X)) {1004ABCDEF}>
```

`(lambda (x) (+ x n))`은 `let`이 만든 `n` 바인딩 **안에** 텍스트로 위치해 있습니다. 그래서 이 람다 안에서 `n`을 참조하면, 항상 이 `let`이 만든 그 `n`을 가리킵니다. `make-adder`의 몸체도 정확히 이 구조입니다. `n`은 `make-adder`의 매개변수로 만들어진 지역 바인딩이고, 그 안에 위치한 `lambda`가 `n`을 참조하고 있는 것이지요.

렉시컬 스코프 아래에서는, 함수가 호출되는 시점이나 위치와 무관하게, 오직 **함수가 정의된 텍스트상의 위치**만으로 어떤 변수를 가리키는지가 결정됩니다. `make-adder`가 반환한 람다는 어디서 호출되든 상관없이, 자신이 태어난 자리에서 보였던 `n`을 계속 참조합니다.

## 클로저는 매번 독립된 환경을 만든다

중요한 점은, `make-adder`를 호출할 때마다 **새로운** `n` 바인딩이 만들어진다는 것입니다. 즉 클로저들은 서로 다른 환경을 각자 독립적으로 붙들고 있습니다.

```lisp
* (defparameter *add5* (make-adder 5))
*ADD5*

* (defparameter *add100* (make-adder 100))
*ADD100*

* (funcall *add5* 1)
6

* (funcall *add100* 1)
101
```

`*add5*`와 `*add100*`은 같은 `lambda` 코드로 만들어졌지만, 서로 다른 `n` 값을 각자 기억하고 있습니다. 마치 붕어빵 틀은 하나인데, 그 틀로 찍어낸 붕어빵마다 속에 든 팥소가 다른 것과 비슷합니다.

## 카운터 생성기: 클로저의 대표적인 활용

클로저가 정말 유용해지는 지점은, 그 안에 담긴 값이 **변할 수 있을 때**입니다. 카운터를 만드는 함수를 작성해봅시다.

```lisp
(defun make-counter ()
  "호출할 때마다 1씩 증가하는 카운터 함수를 반환한다."
  (let ((count 0))
    (lambda ()
      (setf count (+ count 1))
      count)))

* (defparameter *counter1* (make-counter))
*COUNTER1*

* (funcall *counter1*)
1

* (funcall *counter1*)
2

* (funcall *counter1*)
3
```

`setf`는 기존 값을 새 값으로 바꾸는 연산입니다. 여기서 `count`는 `make-counter`가 호출될 때 `let`으로 만들어진 지역 변수인데, 그 함수 호출이 끝난 뒤에도 `lambda`가 계속 붙들고 있다가, 호출될 때마다 값을 갱신합니다.

독립된 카운터가 여러 개 필요하다면, `make-counter`를 여러 번 호출하면 됩니다. 각 호출은 서로 다른 `count` 바인딩을 만들어냅니다.

```lisp
* (defparameter *counter2* (make-counter))
*COUNTER2*

* (funcall *counter1*)
4

* (funcall *counter2*)
1
```

`*counter1*`이 이미 3까지 증가한 상태여도 `*counter2*`는 자기만의 `count`를 0부터 새로 시작합니다. 두 카운터는 서로의 상태에 전혀 영향을 주지 않습니다. 이것이 바로 클로저를 이용해서 "상태를 가진 함수"를 만드는 전형적인 방법입니다.

두 개 이상의 함수가 같은 클로저 환경을 공유하게 만들 수도 있습니다.

```lisp
(defun make-counter-pair ()
  "같은 count를 공유하는 증가 함수와 조회 함수를 리스트로 반환한다."
  (let ((count 0))
    (list (lambda () (setf count (+ count 1)))
          (lambda () count))))

* (defparameter *pair* (make-counter-pair))
*PAIR*

* (funcall (first *pair*))
1

* (funcall (first *pair*))
2

* (funcall (second *pair*))
2
```

두 람다 모두 같은 `let`이 만든 `count`를 텍스트상으로 감싸고 있으므로, 동일한 바인딩을 공유합니다. 하나가 값을 바꾸면 다른 하나가 그 변화를 즉시 볼 수 있습니다.

## 다이나믹 스코프: 특수 변수는 다르게 동작한다

지금까지 본 것은 모두 렉시컬 스코프입니다. 그런데 Common Lisp에는 이와 반대로 동작하는 변수도 있습니다. 바로 `defvar`나 `defparameter`로 선언한 **특수 변수(special variable)**입니다.

```lisp
(defvar *unit* "cm")

(defun describe-length (n)
  (format nil "~a~a" n *unit*))

* (describe-length 10)
"10cm"
```

`*unit*`처럼 별표(`*`)로 감싸는 이름 관례는 관용적으로 특수 변수임을 표시하는 것입니다. 특수 변수는 `let`으로 다시 바인딩하면 렉시컬 변수와는 다르게 동작합니다.

```lisp
* (let ((*unit* "inch"))
    (describe-length 10))
"10inch"
```

여기서 흥미로운 점은, `describe-length` 함수는 `*unit*`을 재바인딩한 `let` 바깥에서 **정의**되었다는 사실입니다. 렉시컬 스코프 규칙대로라면 `describe-length`는 자신이 정의된 위치를 기준으로 `*unit*`을 찾아야 하므로, `let`의 영향을 받지 않아야 할 것 같습니다. 그런데 실제로는 `let` 안에서 `describe-length`를 호출하는 동안만 `*unit*`이 `"inch"`로 바뀌어 보입니다.

이것이 **다이나믹 스코프(dynamic scope)**입니다. 다이나믹 스코프에서는 변수가 코드가 작성된 위치가 아니라, 호출이 진행되는 동안의 **실행 흐름(call stack)** 을 기준으로 값을 찾습니다. `let`으로 특수 변수를 재바인딩하면, 그 `let`의 몸체가 실행되는 동안에는 그 함수가 어디서 호출되든, 심지어 다른 함수 안에서 호출되더라도 새 값이 적용됩니다. `let`의 몸체 실행이 끝나면 원래 값으로 자동 복원됩니다.

```lisp
* *unit*
"cm"

* (let ((*unit* "inch"))
    (describe-length 10))
"10inch"

* *unit*
"cm"
```

`describe-length`가 별도의 인자 없이도 "현재 문맥의 단위"를 자연스럽게 참조할 수 있다는 점이 다이나믹 스코프의 장점입니다. 반대로 어디서 값이 바뀌었는지 코드만 보고 추적하기 어렵다는 단점도 있습니다. 그래서 Common Lisp에서는 이런 성질을 가진 변수를 일반 지역 변수와 시각적으로 구분하기 위해 `*이름*`처럼 별표로 감싸는 관례를 지킵니다.

## 렉시컬 스코프와 다이나믹 스코프 비교

| | 렉시컬 스코프 | 다이나믹 스코프 |
|---|---|---|
| 값을 찾는 기준 | 코드가 **작성된** 위치 | 코드가 **실행되는** 흐름 |
| 만드는 방법 | `let`으로 만든 일반 변수, 함수의 매개변수 | `defvar`/`defparameter`로 선언한 특수 변수를 `let`으로 재바인딩 |
| 클로저 가능 여부 | 가능 (함수가 환경을 기억) | 해당 없음 (재바인딩은 일시적) |
| 대표 용도 | 지역 상태 은닉, 카운터, 콜백 | 현재 문맥 설정값(단위, 언어, 디버그 모드 등) |

일반적인 지역 변수(예: `let`으로 만든 변수나 함수 매개변수)는 모두 렉시컬 스코프를 따릅니다. 오직 `defvar`/`defparameter`로 선언한 특수 변수만 다이나믹 스코프로 동작합니다. 대부분의 코드에서는 렉시컬 스코프만으로 충분하며, 다이나믹 스코프는 "현재 실행 중인 코드 전체에 걸쳐 잠시 설정을 바꾸고 싶을 때" 같은 특별한 상황에 쓰입니다. 13장에서 다룰 조건 시스템도 내부적으로 다이나믹 스코프의 성질을 활용합니다.

## 정리하며

클로저는 "함수 + 그 함수가 정의될 당시의 환경"이 한 몸으로 묶인 것입니다. 6장에서 `let`으로 만든 지역 바인딩이 함수 몸체 안에 텍스트로 감싸여 있으면, 그 함수는 나중에 어디서 호출되든 그 바인딩을 계속 참조할 수 있습니다. 이 성질 덕분에 `make-counter` 같은 "상태를 가진 함수 생성기"를 만들 수 있고, 9장에서 살펴본 "함수를 반환하는 함수" 패턴이 실제로 쓸모 있어집니다.

## 요약

- 클로저는 함수가 자신이 정의된 환경의 지역 변수를 계속 참조하고 기억하는 현상입니다.
- 렉시컬 스코프는 변수가 코드의 작성 위치를 기준으로 결정되는 방식이며, Common Lisp의 일반 지역 변수(`let`, 함수 매개변수)는 모두 이 규칙을 따릅니다.
- `make-adder`나 `make-counter`를 호출할 때마다 서로 독립된 클로저 환경이 새로 만들어집니다.
- 여러 클로저가 같은 `let` 바인딩을 감싸고 있으면, 그 바인딩을 공유하며 서로의 변화를 볼 수 있습니다.
- 다이나믹 스코프는 `defvar`/`defparameter`로 선언한 특수 변수에 적용되며, 코드 작성 위치가 아니라 실행 흐름을 기준으로 값을 찾습니다. `let`으로 재바인딩하면 그 몸체가 실행되는 동안만 값이 바뀌고, 끝나면 원래 값으로 복원됩니다.

## 연습문제

1. `make-adder`를 호출해서 `*add3*`과 `*add7*`을 각각 만들고, 두 클로저가 서로 다른 값을 기억하는지 확인해보세요.
2. `make-counter`를 응용해서, 호출할 때마다 1씩 **감소**하는 카운터를 반환하는 `make-down-counter` 함수를 작성하세요.
3. `make-counter-pair`처럼, "증가 함수"와 "0으로 초기화하는 함수"를 함께 담은 리스트를 반환하는 `make-resettable-counter`를 작성해보세요.
4. `defvar`로 `*greeting*`이라는 특수 변수를 `"안녕하세요"`로 선언하고, 이를 사용하는 `greet` 함수를 작성한 뒤, `let`으로 `*greeting*`을 일시적으로 `"Hello"`로 바꿔서 `greet`을 호출해보세요. `let` 밖에서 다시 호출했을 때 원래 값으로 돌아오는지 확인하세요.
5. 렉시컬 스코프와 다이나믹 스코프의 차이를, "함수가 어디서 정의되었는지"와 "함수가 어디서 호출되었는지"라는 두 표현을 사용해서 자신의 말로 설명해보세요.

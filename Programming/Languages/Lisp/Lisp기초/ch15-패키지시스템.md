# 15장. 패키지 시스템

## 시작하며

지금까지는 하나의 REPL 세션이나 짧은 파일 안에서 함수와 변수 이름을 자유롭게 지어 왔습니다. 하지만 프로그램이 커지고 여러 사람이 코드를 나누어 작성하거나, 다른 사람이 만든 라이브러리를 가져다 쓰기 시작하면 곧바로 문제가 생깁니다. 바로 **이름 충돌(name collision)**입니다. 이번 장에서는 Lisp가 이름 충돌을 해결하기 위해 마련한 **패키지(package)** 시스템을 살펴보고, `defpackage`와 `in-package`를 이용해 나만의 이름 공간을 만드는 방법을 배웁니다.

## 이름 충돌이라는 문제

간단한 상황을 상상해 봅시다. 여러분은 도형을 다루는 라이브러리를 만들고 있고, 넓이를 계산하는 함수를 이렇게 정의했습니다.

```lisp
(defun area (width height)
  (* width height))
```

그런데 동료가 만든 통계 라이브러리에도 `area`라는 이름의 함수가 있다고 해봅시다. 두 파일을 같은 REPL 세션에 순서대로 로드하면 어떻게 될까요?

```lisp
* (defun area (width height)
    (* width height))
AREA

* (defun area (radius)
    (* pi radius radius))
AREA
```

두 번째 `defun`이 첫 번째 정의를 완전히 덮어써 버립니다. Common Lisp는 경고를 띄우기는 하지만 실행을 막지는 않습니다. 결과적으로 먼저 정의된 사각형 넓이 함수는 사라지고, 이를 사용하던 코드는 엉뚱한 계산을 하게 됩니다. 함수 하나라면 금방 눈치채겠지만, 수십 개의 이름이 얽힌 대형 프로젝트에서는 이런 충돌을 알아차리기가 매우 어렵습니다.

이 문제의 근본 원인은 모든 심볼(symbol)이 하나의 공용 공간에 등록된다는 데 있습니다. Lisp는 이 "심볼이 등록되는 공간"을 **패키지**라는 단위로 나누어, 서로 다른 패키지에 속한 동명의 심볼은 별개의 것으로 취급할 수 있게 해 줍니다.

## 패키지란 무엇인가

패키지는 심볼의 이름 공간(namespace)입니다. 우리가 지금까지 REPL에서 사용해 온 `defun`, `+`, `car` 같은 심볼들은 사실 `COMMON-LISP`라는 패키지에 속해 있으며, REPL이 기본으로 사용하는 `CL-USER` 패키지가 이를 가져다 쓰고 있습니다. 지금 사용 중인 패키지를 확인해 봅시다.

```lisp
* *package*
=> #<PACKAGE "COMMON-LISP-USER">

* (package-name *package*)
=> "COMMON-LISP-USER"
```

`*package*`는 현재 활성화된 패키지를 담고 있는 특수 변수입니다. REPL을 처음 켜면 `COMMON-LISP-USER`(줄여서 `CL-USER`) 패키지가 기본으로 활성화되어 있습니다. 지금까지 작성한 모든 함수와 변수는 이 패키지 안에 등록되어 온 셈입니다.

## defpackage로 나만의 이름 공간 만들기

`defpackage`는 새 패키지를 정의하는 매크로입니다. 도형 넓이를 계산하는 라이브러리를 위한 패키지를 하나 만들어 보겠습니다.

```lisp
(defpackage :shapes
  (:use :cl)
  (:export :area :perimeter))
```

각 부분의 의미는 다음과 같습니다.

- `:shapes`: 새로 만들 패키지의 이름입니다. 관례적으로 키워드(`:이름`)로 표기합니다.
- `(:use :cl)`: `:cl`은 `:common-lisp`의 줄임 표기로, 표준 함수인 `defun`, `+`, `if` 등을 아무 접두어 없이 쓸 수 있도록 이 패키지를 가져다(use) 씁니다. `:use`를 빼먹으면 `defun`조차 직접 쓸 수 없게 되므로 거의 모든 패키지에서 `(:use :cl)`을 지정합니다.
- `(:export :area :perimeter)`: 이 패키지 바깥에서도 접두어 없이 사용할 수 있도록 공개(export)할 심볼 목록입니다. 여기 나열되지 않은 심볼은 패키지 내부에서만 쓰이는 "비공개" 심볼로 취급됩니다.

## in-package로 패키지 전환하기

`defpackage`는 패키지의 "설계도"를 등록할 뿐, 이후 코드를 어느 패키지에 넣을지는 `in-package`로 지정해야 합니다.

```lisp
(defpackage :shapes
  (:use :cl)
  (:export :area :perimeter))

(in-package :shapes)

(defun area (width height)
  (* width height))

(defun perimeter (width height)
  (* 2 (+ width height)))
```

`in-package` 이후에 등장하는 `defun`들은 모두 `shapes` 패키지에 등록됩니다. 이 코드를 파일로 저장하고 로드한 뒤 확인해 보겠습니다.

```lisp
* (load "shapes.lisp")
T

* (shapes:area 3 4)
=> 12

* *package*
=> #<PACKAGE "SHAPES">
```

`load`를 실행하면 파일 안의 `in-package`가 그대로 적용되어 현재 패키지가 `shapes`로 바뀐 채 남는다는 점에 주의하세요. 다시 `cl-user`로 돌아가려면 명시적으로 전환해야 합니다.

```lisp
* (in-package :cl-user)
#<PACKAGE "COMMON-LISP-USER">

* (shapes:area 3 4)
=> 12
```

`cl-user`로 돌아온 뒤에도 `shapes:area`처럼 **패키지 접두어**를 붙이면 다른 패키지의 공개 심볼을 가져다 쓸 수 있습니다. 콜론(`:`) 하나는 "패키지 이름에 이어 공개된(export된) 심볼"을 가리키는 문법입니다.

## export로 공개 범위 정하기

이제 통계 라이브러리 쪽에도 `area`라는 이름의 함수를 정의해 봅시다. 이번에는 원의 넓이를 계산합니다.

```lisp
(defpackage :geo-stats
  (:use :cl)
  (:export :area))

(in-package :geo-stats)

(defparameter *pi-approx* 3.14159)

(defun area (radius)
  (* *pi-approx* radius radius))
```

두 패키지가 각자 `area`라는 심볼을 가지고 있지만, 이제는 전혀 충돌하지 않습니다.

```lisp
* (shapes:area 3 4)
=> 12

* (geo-stats:area 2)
=> 12.56636
```

`shapes:area`와 `geo-stats:area`는 이름은 같아 보여도 서로 다른 패키지에 속한 완전히 다른 심볼입니다. 반면 `*pi-approx*`처럼 `:export`에 나열하지 않은 심볼은 `geo-stats::*pi-approx*`처럼 콜론 두 개(`::`)를 붙여야만 외부에서 접근할 수 있고, 이는 "내부 구현이니 함부로 쓰지 말라"는 신호이기도 합니다.

```lisp
* geo-stats:*pi-approx*

debugger invoked...
;; *PI-APPROX* 심볼이 GEO-STATS 패키지에서 외부로 공개(export)되지 않았습니다.

* geo-stats::*pi-approx*
=> 3.14159
```

이처럼 `export` 여부는 단순한 편의 기능이 아니라, 패키지 작성자가 "이것은 공개 API이고, 이것은 내부 구현이다"라는 의도를 코드로 명시하는 수단입니다.

## use-package와 이름 충돌의 재발

패키지를 `:use`하면 그 패키지의 공개 심볼을 접두어 없이 쓸 수 있어 편리하지만, 두 패키지를 동시에 `:use`했을 때 같은 이름이 공개되어 있다면 다시 충돌이 발생할 수 있습니다.

```lisp
(defpackage :my-app
  (:use :cl :shapes :geo-stats))
```

`shapes`와 `geo-stats` 둘 다 `area`를 공개하고 있으므로, 이 `defpackage`를 실행하면 "AREA가 여러 패키지에서 상속되어 모호합니다"라는 경고 혹은 에러가 발생합니다. 이런 경우 둘 중 하나만 `:use`하고 나머지는 패키지 접두어로 명시하거나, `:shadowing-import-from` 옵션으로 어느 쪽을 우선할지 명시적으로 지정해야 합니다. 실무에서는 애매한 이름(`area`, `data`, `process`처럼 흔한 단어)을 무분별하게 `export`하지 않는 것이 이런 충돌을 예방하는 가장 좋은 방법입니다.

## 여러 파일로 프로젝트 구성하기

실제 프로젝트는 보통 여러 파일로 나뉩니다. 예를 들어 `package.lisp`, `shapes.lisp`, `main.lisp` 세 파일로 구성한다고 해봅시다.

```lisp
;; package.lisp — 패키지 정의만 모아두는 파일
(defpackage :shapes
  (:use :cl)
  (:export :area :perimeter :make-rectangle))
```

```lisp
;; shapes.lisp — 실제 구현
(in-package :shapes)

(defstruct rectangle width height)

(defun area (rect)
  (* (rectangle-width rect) (rectangle-height rect)))

(defun perimeter (rect)
  (* 2 (+ (rectangle-width rect) (rectangle-height rect))))
```

```lisp
;; main.lisp — 패키지를 사용하는 쪽
(in-package :cl-user)

(let ((r (shapes:make-rectangle :width 3 :height 4)))
  (format t "넓이: ~a, 둘레: ~a~%"
          (shapes:area r)
          (shapes:perimeter r)))
```

이 세 파일은 반드시 `package.lisp`, `shapes.lisp`, `main.lisp` 순서로 로드해야 합니다. 패키지가 정의되기 전에 `in-package`가 실행되면 존재하지 않는 패키지를 찾다가 에러가 나기 때문입니다.

```lisp
* (load "package.lisp")
T
* (load "shapes.lisp")
T
* (load "main.lisp")
넓이: 12, 둘레: 14
```

패키지 정의를 별도 파일로 분리해 두면, 다른 파일들이 로드 순서에 상관없이 "패키지가 어떤 이름을 공개하는지"를 한눈에 확인할 수 있어 프로젝트가 커질수록 유리합니다. 파일이 늘어나면 매번 `load` 순서를 손으로 관리하기보다 `asdf`와 같은 시스템 정의 도구를 쓰는 것이 일반적이지만, 그 내용은 이 책의 범위를 넘어가므로 지금은 패키지와 파일의 관계를 이해하는 데 집중합니다. 파일을 직접 열고 닫으며 내용을 다루는 방법은 16장에서 이어서 다룹니다.

## 요약

- 프로젝트가 커지면 여러 곳에서 같은 이름의 함수나 변수를 정의하다가 **이름 충돌**이 발생할 수 있습니다.
- **패키지**는 심볼이 등록되는 이름 공간이며, 현재 패키지는 특수 변수 `*package*`에 저장됩니다.
- `defpackage`로 새 패키지를 정의하고, `(:use :cl)`로 표준 함수를 가져오며, `(:export ...)`로 외부에 공개할 심볼을 지정합니다.
- `in-package`는 이후 코드가 등록될 패키지를 전환하며, 다른 패키지의 공개 심볼은 `패키지이름:심볼이름` 형태로 접근합니다.
- 여러 패키지를 동시에 `:use`할 때 같은 이름이 공개되어 있으면 다시 충돌이 생길 수 있으므로, 흔한 이름을 함부로 `export`하지 않는 것이 좋습니다.
- 규모가 있는 프로젝트는 패키지 정의 파일과 구현 파일을 분리하고, 정해진 순서로 로드하는 방식으로 구성합니다.

## 연습문제

1. `defpackage`에서 `:use`를 빠뜨리면 어떤 문제가 생기는지, 직접 코드를 작성해서 확인해 보세요.
2. `:calc`라는 패키지를 만들어 `add`와 `subtract` 두 함수를 `export`하고, `cl-user`에서 접두어를 붙여 호출해 보세요.
3. 같은 이름의 심볼을 공개하는 두 패키지를 만들고, 이 둘을 동시에 `:use`하는 세 번째 패키지를 정의했을 때 어떤 에러 메시지가 나오는지 관찰해 보세요.
4. `export`하지 않은 심볼에 콜론 두 개(`::`)를 붙여 접근하는 것이 왜 "권장되지 않는" 방식인지 자신의 말로 설명해 보세요.
5. 패키지 정의 파일(`package.lisp`)과 구현 파일을 분리해서 작성한 뒤, 로드 순서를 일부러 바꿔 실행하면 어떤 에러가 나는지 확인해 보세요.

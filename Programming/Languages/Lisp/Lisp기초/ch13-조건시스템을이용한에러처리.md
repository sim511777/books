# 13장. 조건 시스템을 이용한 에러 처리

[◀ 이전: 12장. 구조체와 CLOS 객체 시스템 기초](ch12-구조체와CLOS.md) | [📖 목차](00-목차.md) | [다음: 14장. 문자열과 포맷팅 ▶](ch14-문자열과포맷팅.md)

---

프로그램은 언젠가 실패한다. 파일이 없을 수도 있고, 0으로 나누려 할 수도 있고, 사용자가 이상한 값을 입력할 수도 있다. 다른 언어를 써봤다면 `try`/`catch`나 `try`/`except` 같은 예외 처리 구문에 익숙할 것이다. Common Lisp도 비슷한 일을 할 수 있지만, 그 밑바탕에는 훨씬 더 유연한 **조건 시스템(condition system)**이 자리하고 있다. 이번 장에서는 이 조건 시스템을 이용해 에러를 발생시키고 처리하는 실용적인 방법을 익힌다.

## 다른 언어의 예외 처리와 무엇이 다른가

자바나 파이썬의 예외 처리는 기본적으로 "스택을 풀고(unwind) 상위 호출자에게 처리를 맡긴다"는 한 가지 흐름만 지원한다. 에러가 발생한 지점의 실행 상태는 예외가 던져지는 순간 사라진다. `catch` 블록에서 할 수 있는 일은 "복구를 포기하고 다른 값을 리턴하거나 다시 예외를 던지는 것"뿐이다.

Common Lisp의 조건 시스템은 이보다 한 단계 더 유연하다. 에러가 발생한 지점에서 스택을 풀지 않은 채로 "이 상황을 어떻게 처리할지" 상위 코드에 물어볼 수 있고, 상위 코드는 실행을 재개(restart)하도록 지시할 수도 있다. 이 장에서는 이런 고급 기능(`restart-case`, `invoke-restart` 등)까지 깊이 들어가지는 않지만, 그 토대가 되는 `error`, `handler-case`, `ignore-errors`를 확실히 익혀두면 나중에 더 깊은 내용을 배울 때 자연스럽게 이해할 수 있다.

핵심은 이것이다. Common Lisp에서 "조건(condition)"은 예외보다 더 넓은 개념이다. 에러뿐 아니라 경고(warning), 단순한 알림까지도 조건으로 표현할 수 있다. 에러는 그중에서 "복구하지 않으면 프로그램 흐름을 멈춰야 하는" 조건의 한 종류일 뿐이다.

## error로 에러 발생시키기

가장 간단하게 에러를 일으키는 방법은 `error` 함수를 호출하는 것이다.

```lisp
(defun divide (a b)
  (if (zerop b)
      (error "0으로 나눌 수 없습니다: ~a / ~a" a b)
      (/ a b)))
```

`error`는 첫 번째 인자를 포맷 문자열처럼 사용하고, 나머지 인자를 그 안에 끼워 넣는다(`~a` 지시자는 14장에서 자세히 다룬다). REPL에서 이 함수를 호출하면 어떤 일이 벌어지는지 보자.

```lisp
* (divide 10 2)
5

* (divide 10 0)
; 디버거로 진입
; 0으로 나눌 수 없습니다: 10 / 0
;    [Condition of type SIMPLE-ERROR]
```

처리되지 않은 에러가 발생하면 Common Lisp 구현체는 보통 **디버거**로 진입한다. 이것은 버그가 아니라 의도된 동작이다. 디버거 안에서는 스택을 살펴보고, 변수 값을 확인하고, 심지어 코드를 고쳐서 실행을 재개할 수도 있다. 하지만 실제 프로그램에서는 에러가 났을 때 디버거로 빠지는 대신 코드 안에서 처리하고 싶을 때가 많다. 이때 `handler-case`가 등장한다.

## handler-case로 에러 잡아 처리하기

`handler-case`는 다른 언어의 `try`/`catch`와 가장 비슷한 매크로다.

```lisp
(defun safe-divide (a b)
  (handler-case (/ a b)
    (division-by-zero (c)
      (format t "에러 발생: ~a~%" c)
      nil)))
```

```lisp
* (safe-divide 10 2)
5

* (safe-divide 10 0)
에러 발생: 0으로 0을 나누려 했습니다.
NIL
```

`handler-case`의 구조를 뜯어보면 다음과 같다.

```lisp
(handler-case 본문-폼
  (조건-타입 (변수) 처리-폼...)
  (조건-타입2 (변수) 처리-폼...)
  ...)
```

- 첫 번째 자리(본문-폼)는 실제로 실행할 코드다.
- 그 뒤에 오는 각 절은 "이런 타입의 조건이 발생하면 이렇게 처리하라"는 규칙이다.
- 변수는 발생한 조건 객체를 받는 이름이다. 필요 없으면 생략할 수 있다.

`division-by-zero`는 Common Lisp이 이미 정의해둔 조건 타입으로, `/` 함수가 정수 0으로 나누기를 시도하면 자동으로 발생한다. 우리가 직접 `error`로 만든 조건은 기본적으로 `simple-error` 타입을 갖는다.

```lisp
(defun safe-parse (str)
  (handler-case (parse-integer str)
    (error (c)
      (format t "파싱 실패: ~a~%" c)
      nil)))
```

```lisp
* (safe-parse "42")
42

* (safe-parse "abc")
파싱 실패: 문자열에서 정수를 파싱할 수 없습니다: "abc"
NIL
```

여기서 `error`를 조건 타입으로 지정하면 `error`의 모든 하위 타입(`division-by-zero`, `simple-error`, `parse-error` 등)을 포괄해서 잡는다. 자바의 `catch (Exception e)`처럼 넓게 잡는 것과 비슷하다고 생각하면 된다. 여러 절을 위에서부터 순서대로 시도하므로, 구체적인 타입을 먼저 쓰고 넓은 타입을 나중에 쓰는 것이 일반적인 관례다.

```lisp
(defun robust-divide (a b)
  (handler-case (/ a b)
    (division-by-zero (c)
      (declare (ignore c))
      (format t "0으로 나눌 수 없습니다.~%")
      0)
    (error (c)
      (format t "알 수 없는 에러: ~a~%" c)
      nil)))
```

`handler-case`의 중요한 특징 하나는, 처리 절이 실행되는 시점에는 이미 에러가 발생한 지점의 스택이 풀려 있다는 것이다. 즉 처리 절 안에서 원래 실행 위치로 돌아가 계속 진행할 수는 없다. 이런 "그 자리에서 재개하기" 기능은 `restart-case`라는 더 고급 도구가 담당하는데, 이는 다음에 배울 기회가 있을 것이다.

## ignore-errors로 간단히 넘기기

에러 종류를 구분할 필요 없이 그냥 "실패하면 nil로 취급하고 넘어가자"고 할 때는 `ignore-errors`가 더 간결하다.

```lisp
* (ignore-errors (/ 10 0))
NIL
NIL

* (ignore-errors (/ 10 2))
5
```

`ignore-errors`는 두 개의 값을 리턴한다. 에러가 없었다면 첫 번째 값은 본문의 결과이고 두 번째 값은 `nil`이다. 에러가 발생했다면 첫 번째 값은 `nil`이고 두 번째 값은 발생한 조건 객체다. 두 번째 값을 이용하면 에러가 실제로 있었는지, 아니면 원래 계산 결과가 `nil`이었는지 구분할 수 있다.

```lisp
(defun try-divide (a b)
  (multiple-value-bind (result condition) (ignore-errors (/ a b))
    (if condition
        (format t "실패: ~a~%" condition)
        (format t "결과: ~a~%" result))))
```

`ignore-errors`는 사실 `handler-case`를 이용해 정의된 매크로에 가깝다. 간단한 스크립트에서 "이 부분에서 에러가 나든 말든 넘어가고 싶다"는 상황에 편리하게 쓴다. 하지만 어떤 에러인지 구분해서 다르게 대응해야 한다면 `handler-case`를 쓰는 것이 코드 의도를 더 명확히 드러낸다.

## 12장의 구조체/클래스와 연결하기 — 커스텀 컨디션

12장에서 `defstruct`와 `defclass`로 우리만의 데이터 타입을 정의하는 법을 배웠다. 조건도 마찬가지로 우리가 직접 정의할 수 있다. `define-condition`은 `defclass`와 매우 비슷한 문법을 쓴다.

```lisp
(define-condition insufficient-funds (error)
  ((balance :initarg :balance :reader ifund-balance)
   (amount :initarg :amount :reader ifund-amount))
  (:report
   (lambda (condition stream)
     (format stream "잔액 부족: 잔액 ~a원, 요청 금액 ~a원"
             (ifund-balance condition)
             (ifund-amount condition)))))
```

`define-condition`의 구조는 `defclass`와 거의 같다. 조건 이름, 부모 조건 목록(여기서는 `error`), 슬롯 목록, 그리고 `:report` 옵션으로 사람이 읽을 메시지를 어떻게 만들지 정의한다. 슬롯에 `:initarg`와 `:reader`를 쓰는 방식도 12장에서 본 CLOS 슬롯 옵션과 동일하다.

이제 이 조건을 실제로 사용해보자.

```lisp
(defun withdraw (balance amount)
  (if (> amount balance)
      (error 'insufficient-funds :balance balance :amount amount)
      (- balance amount)))
```

```lisp
* (withdraw 1000 500)
500

* (handler-case (withdraw 1000 1500)
    (insufficient-funds (c)
      (format t "출금 실패 - ~a~%" c)
      (format t "부족한 금액: ~a원~%" (- (ifund-amount c) (ifund-balance c)))))
출금 실패 - 잔액 부족: 잔액 1000원, 요청 금액 1500원
부족한 금액: 500원
```

`error`에 조건 타입 이름과 슬롯 값을 넘기면 그 타입의 조건 객체를 만들어 신호를 보낸다. `handler-case`의 절에서는 조건 객체를 받아 `ifund-balance`, `ifund-amount` 같은 리더 함수로 세부 정보를 꺼내 쓸 수 있다. 이렇게 하면 단순한 문자열 에러 메시지보다 훨씬 더 프로그래밍적으로 다루기 쉬운 에러 정보를 전달할 수 있다.

구조체로도 비슷한 접근이 가능할까? 조건은 반드시 `define-condition`으로 정의해야 하며, 조건 타입 계층은 클래스 계층과 마찬가지로 상속을 지원한다. 즉 조건을 설계할 때는 12장에서 클래스 계층을 설계하던 감각을 그대로 가져오면 된다. "환불 관련 에러"라는 상위 조건 아래 "잔액 부족", "존재하지 않는 계좌" 같은 하위 조건을 두는 식으로 계층을 구성할 수 있다.

```lisp
(define-condition account-error (error)
  ((account-id :initarg :account-id :reader account-error-id)))

(define-condition insufficient-funds (account-error)
  ((balance :initarg :balance :reader ifund-balance)
   (amount :initarg :amount :reader ifund-amount)))

(define-condition account-not-found (account-error) ())
```

이렇게 만들어두면 `handler-case`에서 `account-error`를 잡아 모든 계좌 관련 에러를 한 곳에서 처리하거나, `insufficient-funds`만 콕 집어 세밀하게 처리하는 것을 모두 선택할 수 있다. 이는 표준 예외처럼 자기만의 에러 클래스 계층을 만들어 쓰는 것과 똑같은 사고방식이며, 12장에서 배운 CLOS 지식이 그대로 이어지는 지점이다.

## 요약

- Common Lisp의 조건 시스템은 단순한 예외 처리보다 넓은 개념으로, 에러 발생 지점의 실행 상태를 유지한 채 처리 방식을 결정할 수 있는 유연한 구조를 제공한다.
- `error` 함수는 조건을 발생시킨다. 문자열과 포맷 인자를 넘기면 즉석에서 `simple-error`가 만들어지고, 조건 타입 이름과 슬롯 값을 넘기면 해당 타입의 조건 객체가 만들어진다.
- `handler-case`는 지정한 조건 타입별로 처리 절을 등록하며, 처리 절이 실행되는 순간에는 이미 스택이 풀려 원래 위치로 돌아갈 수 없다.
- `ignore-errors`는 `handler-case`를 간단히 감싼 매크로로, 에러 발생 시 `nil`과 조건 객체를 리턴해 조용히 넘어가고 싶을 때 편리하다.
- `define-condition`은 `defclass`와 비슷한 문법으로 커스텀 조건 타입을 정의하며, 조건 계층을 만들어 에러를 세밀하게 또는 폭넓게 처리할 수 있다.

## 연습문제

1. 리스트를 인자로 받아 첫 번째 원소를 리턴하되, 리스트가 비어 있으면 `"빈 리스트입니다"`라는 메시지로 `error`를 발생시키는 `safe-first` 함수를 작성하라.
2. 위 `safe-first`를 호출하는 코드에서 `handler-case`로 에러를 잡아 `nil`을 리턴하도록 감싼 `safe-first-or-nil` 함수를 작성하라.
3. `empty-list-error`라는 조건 타입을 `define-condition`으로 정의하라. 슬롯으로 원래 어떤 함수에서 발생했는지 나타내는 `operation`을 두고, `:report`로 "빈 리스트에 ~a 연산을 시도했습니다" 형태의 메시지를 출력하도록 하라. `safe-first`를 이 조건을 사용하도록 수정하라.
4. `ignore-errors`를 이용해 문자열 리스트를 정수 리스트로 변환하되, 파싱할 수 없는 문자열은 건너뛰는 `parse-all-integers` 함수를 작성하라. (힌트: `mapcar`와 `ignore-errors`를 조합하되, 실패한 항목을 걸러내려면 결과에서 `nil`을 제거해야 한다.)
5. `account-error`를 부모로 하는 `insufficient-funds`와 `account-not-found` 두 조건을 정의하고, 각각을 발생시키는 테스트 함수를 작성한 뒤 `handler-case`에서 `account-error` 하나로 둘 다 잡아 처리해보라. 그다음 두 조건을 구분해서 처리하도록 절을 나누어 다시 작성해보라.

지금까지 17개 장을 거치며 Common Lisp의 문법과 도구를 하나씩 쌓아 왔습니다. 이번 마지막 장은 새로운 문법을 배우는 장이 아닙니다. 대신 지금까지 배운 도구들을 **어떻게 써야 좋은 코드가 되는지**, 초보자가 흔히 빠지는 함정은 무엇인지, 그리고 이 책 이후에는 무엇을 더 공부하면 좋을지를 정리합니다.

## 함수로 될 일이면 매크로를 쓰지 않는다

11장에서 매크로를 배우고 나면, 매크로의 힘에 매료되어 모든 것을 매크로로 풀고 싶어지는 시기가 옵니다. 하지만 이는 대부분의 경우 좋은 선택이 아닙니다. Common Lisp 커뮤니티에는 오래된 원칙이 하나 있습니다. "함수로 해결할 수 있다면 함수를 써라. 매크로는 함수로는 할 수 없는 일에만 써라."

함수와 매크로의 근본적인 차이를 다시 떠올려 봅시다. 함수는 인자를 **평가한 값**을 받지만, 매크로는 인자로 주어진 **코드 자체**를 받아서 다른 코드로 변환합니다. 즉 매크로가 필요한 경우는 다음과 같이 "코드의 모양 자체를 바꿔야 하는" 상황으로 좁혀집니다.

- 인자를 평가하지 않고 그대로(또는 조건부로) 다뤄야 할 때 — 5장의 `when`, `unless`처럼 조건에 따라 본문 실행 여부 자체를 결정해야 하는 경우
- 새로운 바인딩이나 제어 흐름 구문을 도입해야 할 때 — 17장에서 살펴본 `loop`처럼 `for`, `collect` 같은 새로운 키워드를 도입하는 경우
- 반복되는 상용구(boilerplate) 코드 패턴을 문법 수준에서 지워버리고 싶을 때

반대로 다음과 같은 경우라면 매크로가 아니라 함수로 충분합니다.

```lisp
;; 나쁜 예: 굳이 매크로일 필요가 없다
* (defmacro 제곱-매크로 (x)
    `(* ,x ,x))
제곱-매크로

;; 좋은 예: 평범한 함수로 충분하다
* (defun 제곱 (x)
    (* x x))
제곱
```

`제곱-매크로`는 인자를 평가하지 않고 다룰 이유가 전혀 없습니다. 단순히 값을 받아 계산해서 돌려주는 일이라면 함수가 훨씬 자연스럽습니다. 함수로 만들면 9장에서 배운 것처럼 `mapcar`나 `funcall`에 값처럼 넘길 수도 있고, 디버거에서 호출 스택을 그대로 확인할 수도 있습니다. 매크로는 컴파일 시점에 코드로 펼쳐져 버리기 때문에 이런 유연함을 갖기 어렵습니다.

판단이 애매할 때 스스로에게 던질 질문은 하나입니다. "이 인자를 평가한 **값**만 있으면 충분한가, 아니면 평가되기 전의 **코드 형태**가 꼭 필요한가?" 값만 있으면 충분하다면 함수를, 코드 형태 자체가 필요하다면 그때 비로소 매크로를 고려하세요.

## REPL 기반 개발: 작은 단위로 평가하며 만들어가기

2장에서 REPL을 처음 소개하며 "한 줄씩 입력하고 결과를 바로 확인하는" 경험을 강조했습니다. 이 습관은 입문 단계를 넘어서도 Lisp 개발의 핵심으로 남습니다. 다른 많은 언어에서는 "코드를 전부 작성 → 컴파일 또는 실행 → 결과 확인"이라는 큰 단위의 주기로 개발하지만, Lisp에서는 함수 하나, 심지어 식 하나 단위로 이 주기를 훨씬 짧게 가져갈 수 있습니다.

큰 함수를 한 번에 작성하고 나서 실행해 보는 대신, 다음과 같은 흐름을 습관으로 들이는 것을 권합니다.

1. 함수의 뼈대만 작성하고 바로 정의해 본다.
2. 함수 본문에서 사용할 작은 식들을 REPL에서 개별적으로 실행해 값을 확인한다.
3. 확인된 조각들을 함수 본문에 조립해 넣고, 함수 전체를 다시 정의한다.
4. 몇 가지 입력값으로 함수를 호출해 보며 예상과 다른 결과가 없는지 확인한다.

```lisp
* (defun 평균 (숫자들)
    (/ (apply #'+ 숫자들) (length 숫자들)))
평균

* (평균 '(1 2 3 4 5))
3
```

만약 이 함수가 예상과 다르게 동작한다면, 함수 전체를 다시 들여다보기 전에 `(apply #'+ '(1 2 3 4 5))`와 `(length '(1 2 3 4 5))`를 각각 REPL에서 따로 실행해 봅니다. 어느 조각이 잘못됐는지 좁혀나가는 것이 전체를 다시 읽는 것보다 훨씬 빠릅니다.

이 방식이 특히 힘을 발휘하는 곳은 6장에서 배운 지역 바인딩이나 10장의 클로저처럼, 상태나 스코프가 얽혀 있는 코드를 다룰 때입니다. 함수 전체를 코드만 보고 머릿속으로 시뮬레이션하는 대신, `let`으로 만든 중간 값을 REPL에서 직접 찍어 보고 클로저가 기억하고 있는 값을 직접 호출해서 확인하세요. 이렇게 작은 단위로 검증하며 쌓아 올린 코드는 나중에 문제가 생겼을 때도 "어디서부터 잘못됐는지" 되짚기가 훨씬 쉽습니다.

## 괄호 균형을 편집기에 맡긴다

Lisp 코드를 손으로 짤 때 괄호 개수를 눈으로 세는 것은 오래 지속 가능한 방법이 아닙니다. 코드가 조금만 길어져도 괄호가 몇 겹으로 중첩되는데, 사람이 이를 실수 없이 세는 것은 비효율적일 뿐 아니라 실수의 원인이 됩니다. 다행히 Lisp 계열 언어를 위한 편집기 지원은 오랫동안 발전해 왔고, 다음과 같은 기능들이 널리 쓰입니다.

- **괄호 자동 짝맞춤(auto-closing)**: 여는 괄호를 입력하면 편집기가 자동으로 닫는 괄호를 채워 줍니다.
- **짝 괄호 강조(match highlighting)**: 커서가 괄호 위에 있을 때 짝이 되는 괄호를 시각적으로 표시해 줍니다.
- **구조 기반 편집(structural editing)**: 괄호를 문자 단위가 아니라 "식(expression)" 단위로 다루어, 식을 통째로 이동하거나 감싸거나 풀어낼 수 있게 해 줍니다. Emacs의 Paredit, 여러 에디터의 "구조 편집" 확장 기능이 이런 역할을 합니다.
- **자동 들여쓰기**: 괄호 깊이에 맞춰 코드를 자동으로 정렬해 주므로, 들여쓰기만 봐도 괄호가 어디서 닫혀야 하는지 가늠할 수 있습니다.

이런 도구들에 의존하는 것은 부끄러운 일이 아니라 오히려 권장되는 습관입니다. 괄호를 세는 데 쓸 주의력을 아껴서 "이 코드가 무엇을 하는가"에 집중하는 것이 훨씬 생산적입니다. 어떤 편집기를 쓰든, 지금 사용 중인 도구에 Lisp 계열 언어를 위한 괄호 관련 기능이 있는지 한 번쯤 찾아보길 권합니다.

## 흔한 실수 정리

### 실수 1: 꼬리 재귀가 아닌 깊은 재귀로 인한 스택 오버플로우

8장에서 재귀를, 17장에서 `dotimes`·`dolist`·`loop`를 배운 이유 중 하나가 바로 이 문제 때문입니다. 재귀 호출의 결과에 다른 연산을 추가로 적용해야 하는 형태(`(+ (car 리스트) (재귀호출 ...))`처럼)는 호출이 끝나기 전까지 "나중에 할 일"을 계속 스택에 쌓아 둡니다. 리스트나 반복 횟수가 커지면 이 스택이 감당할 수 없는 크기로 자라 스택 오버플로우가 발생합니다.

```lisp
;; 위험할 수 있는 형태: 재귀 호출 뒤에 추가 연산이 남아있다
* (defun 합계-위험 (리스트)
    (if (null 리스트)
        0
        (+ (car 리스트) (합계-위험 (cdr 리스트)))))
```

이런 코드를 큰 입력에도 안전하게 만드는 방법은 크게 두 가지입니다. 하나는 8장에서 다룬 것처럼 누적값을 인자로 넘겨 꼬리 재귀 형태로 바꾸는 것이고(처리기가 꼬리 호출 최적화를 지원해야 효과가 있습니다), 다른 하나는 아예 17장의 `dolist`나 `loop` 같은 반복 도구로 바꿔 쓰는 것입니다. 처리 대상의 크기가 작을 것이 확실하다면 재귀의 간결함을 그대로 누려도 되지만, 크기를 예측하기 어려운 데이터를 다룬다면 처음부터 반복 도구를 쓰는 편이 안전합니다.

### 실수 2: 동적 스코프와 렉시컬 스코프의 혼동

10장에서 클로저와 렉시컬 스코프를 배우면서, `let`으로 만든 지역 변수는 그 변수가 **문법적으로 둘러싸인 범위** 안에서만 보인다고 배웠습니다. 반면 `defvar`나 `defparameter`로 선언한 특수 변수(special variable)는 동적 스코프를 따르며, 실행 시점에 그 변수를 호출한 함수들의 전체 호출 체인 안에서 값을 공유합니다.

```lisp
* (defparameter *환율* 1300)

* (defun 원화-환산 (달러)
    (* 달러 *환율*))
원화-환산

* (defun 환율-변경-후-계산 (달러 새환율)
    (let ((*환율* 새환율))   ; 동적 바인딩: 이 let 블록 동안만 *환율*이 바뀐다
      (원화-환산 달러)))
환율-변경-후-계산

* (환율-변경-후-계산 100 1350)
135000
* (원화-환산 100)
130000
```

여기서 `*환율*`처럼 별표(`*`)로 감싸는 이름 규칙(earmuffs)은 우연이 아닙니다. 특수 변수임을 코드만 보고도 알아챌 수 있도록 하는 관례입니다. 이 규칙을 지키지 않고 평범한 이름으로 특수 변수를 선언하면, 나중에 그 변수가 렉시컬 변수인지 동적 변수인지 코드만 보고는 구분할 수 없게 됩니다.

흔한 실수는 다음 두 가지입니다.

- **렉시컬 변수라고 착각하고 동적 변수를 다루는 경우**: `let`으로 특수 변수를 다시 바인딩했다고 생각했지만, 실은 그 안에서 호출한 다른 함수들의 동작까지 영향을 받는다는 것을 잊는 경우입니다. 위 예제의 `원화-환산`이 `환율-변경-후-계산` 안에서 호출되면서 바뀐 `*환율*` 값을 그대로 사용한 것이 그 예입니다. 클로저가 필요한 자리에 특수 변수를 쓰면 "누가 언제 이 값을 바꿨는지" 추적하기 어려워집니다.
- **동적 변수가 필요한데 렉시컬 변수로 설계하는 경우**: 여러 함수가 전역적으로 같은 설정값을 공유하며 임시로 바꿔 써야 하는 상황(예: 로그 레벨, 현재 통화 단위)에서 클로저로 값을 감춰버리면, 다른 함수에서 그 값을 임시로 바꿔 쓰기가 오히려 번거로워집니다.

일반적인 지침은 이렇습니다. 특별한 이유가 없다면 함수의 지역 상태는 `let`과 클로저를 이용한 렉시컬 스코프로 관리하고, 여러 함수가 실행 중에 잠시 공유해야 하는 전역 설정값에 한해서만 이름에 별표를 붙인 특수 변수를 사용하세요.

### 그 밖에 자주 만나는 실수들

- **`eq`, `eql`, `equal`을 구분 없이 사용하기**: 숫자나 문자열을 비교할 때 `eq`를 썼다가 예상과 다른 결과를 얻는 경우가 흔합니다. 3장, 7장에서 다룬 것처럼 값의 종류에 맞는 비교 함수를 고르는 습관이 필요합니다.
- **`format`의 지시자를 헷갈리기**: `~A`와 `~S`, `~%`와 `~&`의 차이는 14장에서 다시 확인해 보세요.
- **매크로 안에서 인자를 여러 번 평가하기**: 11장에서 다룬 것처럼, 매크로 본문에서 같은 파라미터를 여러 번 사용하면 부작용이 여러 번 일어날 수 있습니다. 이런 문제가 걱정된다면 `gensym`과 함께 값을 한 번만 평가하도록 매크로를 설계해야 합니다.

## 다음 학습 단계

이 책은 Common Lisp의 기초를 다지는 데 집중했습니다. 여기서 다진 기초 위에 쌓을 수 있는 방향은 다양합니다.

- **웹 개발**: HTTP 서버, 라우팅, HTML 생성 등을 Lisp로 다루는 라이브러리들을 찾아보면, 15장에서 배운 패키지 시스템이 실전에서 어떻게 여러 라이브러리를 조합하는 데 쓰이는지 체감할 수 있습니다.
- **DSL(도메인 특화 언어) 설계**: 17장에서 살펴본 `loop`처럼, 매크로를 이용해 특정 문제 영역에 맞는 자신만의 작은 언어를 설계해 보는 것은 Lisp의 매력을 가장 깊이 경험할 수 있는 방향입니다. 11장의 매크로 기초를 더 깊이 파고들어 보세요.
- **다른 Lisp 방언 탐구**: 1장에서 언급했던 Scheme이나 Clojure를 접해 보면, Common Lisp에서 당연하게 여겼던 선택들(동적 변수, 패키지 시스템, 조건 시스템 등)이 방언마다 얼마나 다르게 설계될 수 있는지 알게 됩니다. 이는 역으로 Common Lisp 자체를 더 잘 이해하는 데도 도움이 됩니다.
- **처리기 내부와 최적화**: SBCL 같은 처리기가 코드를 어떻게 컴파일하고 최적화하는지, 타입 선언이나 컴파일러 매크로 같은 고급 주제를 공부하면 성능이 중요한 상황에서도 Lisp를 자신 있게 쓸 수 있습니다.
- **실전 프로젝트로 몸에 익히기**: 무엇을 배우든 가장 확실한 방법은 스스로 정한 작은 프로젝트를 끝까지 완성해 보는 것입니다. 지금까지 배운 조건문, 재귀, 고차 함수, 매크로, 조건 시스템, 파일 입출력을 모두 동원해야 하는 정도 크기의 프로젝트(예: 간단한 텍스트 기반 도구, 데이터 처리 스크립트)를 하나 골라 완주해 보세요.

어느 방향으로 나아가든, 이 책에서 강조한 두 가지 태도, 즉 "REPL에서 작은 단위로 확인하며 개발하기"와 "문제에 맞는 도구를 신중하게 고르기"는 계속 유효할 것입니다.

## 체크리스트

새 코드를 작성하거나 기존 코드를 리뷰할 때 다음 항목을 점검해 보세요.

- [ ] 매크로로 작성한 부분이 있다면, 정말 코드 형태 자체가 필요한 경우인지 확인했는가? 함수로 바꿀 수 있다면 바꾸었는가?
- [ ] 함수를 큰 덩어리로 한 번에 작성하지 않고, REPL에서 작은 조각 단위로 값을 확인해 가며 만들었는가?
- [ ] 편집기의 괄호 관련 기능(자동 짝맞춤, 짝 강조, 자동 들여쓰기)을 활용하고 있는가?
- [ ] 재귀 함수가 다룰 데이터 크기가 커질 가능성이 있다면, 꼬리 재귀나 `loop`/`dolist` 같은 반복 도구로 스택 오버플로우 위험을 없앴는가?
- [ ] 전역으로 선언한 변수가 정말 동적 스코프(특수 변수)가 필요한 것인지, 아니면 `let`과 클로저로 충분한 것인지 검토했는가? 특수 변수라면 이름에 별표(`*`)를 붙였는가?
- [ ] `eq`/`eql`/`equal`, `format`의 지시자 등 헷갈리기 쉬운 세부 사항을 값의 종류에 맞게 골랐는가?

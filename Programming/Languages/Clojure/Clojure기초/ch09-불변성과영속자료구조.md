지금까지 우리는 벡터, 맵, 셋 같은 컬렉션을 다루면서 `assoc`, `conj`, `update` 같은 함수들이 "원본을 바꾸는 것 같은" 결과를 돌려준다는 사실을 여러 번 마주쳤습니다. 그런데 조금만 자세히 들여다보면 이상한 점이 있습니다. 원본 컬렉션은 여전히 그대로 남아 있고, 함수는 매번 새 값을 반환합니다. 이번 장에서는 그 이유와 원리를 정면으로 다룹니다. Clojure가 왜 불변(immutable) 자료구조를 기본값으로 삼았는지, 그리고 "매번 새 값을 만든다"는 원칙이 어떻게 성능 문제 없이 실현되는지를 영속적 자료구조(persistent data structure)라는 개념으로 설명합니다.

## 불변 자료구조란 무엇인가

불변 자료구조란 한 번 만들어지면 그 내용이 절대로 바뀌지 않는 자료구조를 말합니다. Java나 Python, JavaScript 같은 언어에 익숙하다면 리스트나 배열에 원소를 추가하거나 값을 바꾸는 연산에 익숙할 것입니다.

```java
// Java 예시 (Clojure 코드가 아닙니다)
List<Integer> numbers = new ArrayList<>();
numbers.add(1);
numbers.add(2);
numbers.add(3); // numbers 자체가 변경됨
```

Clojure에서는 이런 식의 "제자리 변경(in-place mutation)"이 기본 컬렉션에서 아예 불가능합니다. 벡터에 값을 추가하는 `conj`를 예로 들어보겠습니다.

```clojure
(def numbers [1 2 3])

(conj numbers 4)
;; => [1 2 3 4]

numbers
;; => [1 2 3]
```

`conj`를 호출했지만 `numbers`가 가리키는 벡터는 전혀 바뀌지 않았습니다. `conj`는 원본을 건드리지 않고 4가 추가된 완전히 새로운 벡터를 만들어서 반환할 뿐입니다. `numbers`라는 이름(심볼)은 여전히 `[1 2 3]`이라는 값을 가리키고 있습니다.

이 점은 3장에서 다룬 심볼과 값의 관계, 그리고 4장에서 살펴본 컬렉션의 기본 성질과도 이어집니다. Clojure의 핵심 컬렉션 — 리스트, 벡터, 맵, 셋 — 은 모두 불변입니다. 값을 "바꾸는" 것처럼 보이는 모든 함수는 사실 새 값을 만들어서 돌려주는 함수입니다.

### 왜 하필 불변성인가

처음 Clojure를 접하면 "그럼 매번 새 컬렉션을 복사해야 하니 느리지 않을까?"라는 의문이 자연스럽게 듭니다. 이 의문에 답하기 전에, 먼저 Clojure가 불변성을 기본으로 선택한 이유부터 짚어봅시다. 크게 세 가지 이유가 있습니다.

**첫째, 예측 가능성입니다.** 어떤 함수에 컬렉션을 넘겼을 때, 그 함수가 컬렉션의 내용을 몰래 바꿔버릴 걱정을 할 필요가 없습니다.

```clojure
(defn print-and-mystery [coll]
  (println "받은 값:" coll)
  ;; 이 함수 안에서 coll에 어떤 일이 일어나도
  ;; 호출자가 가진 coll은 절대 바뀌지 않는다
  (conj coll :new-item))

(def my-data [:a :b :c])
(print-and-mystery my-data)
;; 받은 값: [:a :b :c]
;; => [:a :b :c :new-item]

my-data
;; => [:a :b :c]
```

함수가 인자로 받은 값을 변경할 수 없다는 보장은 코드를 읽고 추론하는 부담을 크게 줄여줍니다. 함수의 반환값만 보면 그 함수가 무엇을 했는지 완전히 알 수 있습니다.

**둘째, 동시성(concurrency)입니다.** 13장 "상태와 동시성 모델"에서 본격적으로 다루겠지만, 여러 스레드가 같은 데이터에 동시에 접근할 때 가장 골치 아픈 문제는 한 스레드가 데이터를 바꾸는 도중 다른 스레드가 그 데이터를 읽어서 생기는 경쟁 상태(race condition)입니다. 데이터가 애초에 바뀌지 않는다면 여러 스레드가 그 데이터를 동시에 읽어도 아무 문제가 없습니다. 잠금(lock)이나 복잡한 동기화 장치 없이도 데이터를 안전하게 공유할 수 있는 것입니다.

```clojure
(def shared-config {:timeout 3000 :retries 5})

;; 100개의 스레드가 동시에 shared-config를 읽어도
;; 서로 방해하거나 값이 훼손될 일이 없다.
;; shared-config는 절대로 바뀌지 않기 때문이다.
```

**셋째, 시간에 따른 값의 동일성이 보장됩니다.** 어떤 벡터를 변수에 담아 여러 곳에 전달했다면, 나중에 그 변수를 다시 확인해도 처음 담았던 그 값 그대로입니다. 이는 디버깅과 테스트를 훨씬 쉽게 만들어줍니다. "이 데이터가 언제, 어디서 바뀌었는지" 추적할 필요 자체가 없어지기 때문입니다.

## "바꾸는 것"이 아니라 "새로 만드는 것"

불변성을 이해하는 가장 좋은 방법은 관점을 바꾸는 것입니다. Clojure에서 `assoc`, `conj`, `dissoc`, `update` 같은 함수는 "컬렉션을 수정하는 함수"가 아니라 "기존 컬렉션과 조금 다른 새 컬렉션을 만드는 함수"입니다.

```clojure
(def original {:name "지수" :age 28})

(def updated (assoc original :age 29))

original
;; => {:name "지수", :age 28}

updated
;; => {:name "지수", :age 29}
```

`original`과 `updated`는 서로 다른 두 개의 독립된 맵입니다. `assoc`을 호출하는 순간 `:age` 값이 29로 바뀐 새로운 맵 하나가 탄생했고, 원래 있던 맵은 조금도 손상되지 않은 채 그대로 존재합니다.

이 그림을 머릿속에 새겨두면 좋습니다. Clojure의 값은 시간이 흘러도 변하지 않는 "스냅샷"과 같습니다. 어떤 시점의 데이터 상태를 나타내는 값이 있고, 그 값에 변경을 가하고 싶다면 항상 그 결과로 새로운 스냅샷(새 값)을 얻습니다. 원래 스냅샷은 사라지지 않고 그 자리에 그대로 남아 있습니다.

## 영속적 자료구조: 매번 복사하지 않는 비결

여기서 자연스러운 의문이 생깁니다. "매번 새 컬렉션을 만든다면서, 어떻게 원소가 수백만 개인 벡터에 값 하나를 추가하는 연산이 여전히 빠를 수 있을까?" 만약 `conj`가 호출될 때마다 벡터 전체를 처음부터 끝까지 복사해야 한다면, 큰 컬렉션을 다루는 프로그램은 감당할 수 없이 느려질 것입니다.

이 문제를 해결하는 것이 바로 영속적 자료구조(persistent data structure)입니다. 여기서 "영속적"이라는 단어는 파일을 디스크에 저장한다는 뜻이 아닙니다. 자료구조 이론에서 "영속적"이란 "이전 버전이 새 버전을 만든 뒤에도 계속 존재하고 사용 가능하다"는 뜻입니다. Clojure의 벡터, 맵, 셋은 모두 이런 의미에서 영속적입니다.

영속적 자료구조가 매번 전체를 복사하지 않고도 이전 버전을 유지할 수 있는 비결은 구조 공유(structural sharing)에 있습니다. 핵심 아이디어는 이렇습니다.

> 새 값을 만들 때, 바뀌지 않은 부분은 기존 값과 그대로 공유하고, 바뀐 부분만 새로 만든다.

### 연결 리스트로 먼저 감을 잡기

구조 공유를 이해하는 가장 쉬운 예는 연결 리스트에 원소를 앞에 추가하는 경우입니다. Clojure의 리스트는 연결 리스트로 구현되어 있고, `cons`로 맨 앞에 원소를 붙일 수 있습니다.

```clojure
(def base-list '(2 3 4))

(def new-list (cons 1 base-list))

base-list
;; => (2 3 4)

new-list
;; => (1 2 3 4)
```

`new-list`는 새로운 원소 1을 담은 노드 하나만 새로 만들고, 그 노드가 `base-list`의 첫 번째 노드를 그대로 가리키게 만들어 완성됩니다. `base-list`를 이루던 노드들(2, 3, 4)은 단 하나도 복사되지 않았습니다. `new-list`와 `base-list`는 꼬리 부분(2 3 4)을 메모리상에서 그대로 공유합니다. 새로 생긴 것은 딱 1을 담은 노드 하나뿐입니다.

이것이 구조 공유의 가장 단순한 형태입니다. 리스트 앞에 추가하는 연산은 항상 이렇게 O(1)로 끝납니다. 이미 있던 데이터는 절대 손대지 않고, 새 데이터가 옛 데이터를 "가리키기만" 하면 되기 때문입니다.

### 벡터는 어떻게 구조를 공유하는가

벡터는 리스트보다 조금 더 복잡한 구조를 가집니다. 벡터는 인덱스로 임의의 위치에 빠르게 접근할 수 있어야 하기 때문에(6장, 4장에서 다룬 것처럼 `(nth v 100000)`도 빠르게 동작해야 합니다), 단순 연결 리스트로는 구현할 수 없습니다.

Clojure의 벡터는 내부적으로 폭이 32인 트리(정확히는 32-way branching trie) 구조로 구현되어 있습니다. 자세한 구현을 몰라도 원리는 다음과 같이 이해하면 충분합니다.

- 벡터의 원소들은 트리의 잎(leaf) 노드에 최대 32개씩 묶여서 저장됩니다.
- 원소가 많아지면 트리의 깊이가 한 단계씩 늘어나면서, 각 단계마다 최대 32개의 자식을 가지는 나뭇가지가 생깁니다.
- 원소 32개 정도까지는 트리 깊이가 1이고, 수만 개 수준이 되어도 트리 깊이는 겨우 서너 단계에 불과합니다. 32의 거듭제곱이 매우 빠르게 커지기 때문입니다.

벡터 끝에 `conj`로 원소를 추가할 때는 다음과 같은 일이 일어납니다.

1. 마지막 잎 노드에 아직 자리가 남아 있다면(32개를 채우지 못했다면), 그 잎 노드만 새로 복사해서 원소 하나를 더 넣은 새 잎 노드를 만듭니다.
2. 새 잎 노드를 가리키도록, 그 잎 노드의 부모 노드도 새로 복사해서 만듭니다. 이때 다른 형제 노드들은 복사하지 않고 원래 있던 것을 그대로 가리키게 합니다.
3. 이 과정을 뿌리(root)까지 반복합니다.

즉, 트리의 뿌리에서 새 원소가 들어갈 잎까지 이어지는 "경로" 위에 있는 노드들만 새로 만들어지고, 그 경로에서 벗어난 나머지 모든 가지는 원본 벡터와 그대로 공유됩니다. 트리 깊이가 서너 단계에 불과하므로, 아무리 벡터가 커도 새로 복사해야 하는 노드의 수는 몇 개뿐입니다. 이 덕분에 `conj`, `assoc` 같은 연산이 원소 개수와 거의 무관하게 빠르게(실질적으로 상수 시간에 가깝게) 동작합니다. 이를 흔히 "O(log₃₂ n)"이라고 표현하는데, 32의 거듭제곱으로 자라는 트리이다 보니 실제 체감 성능은 상수 시간과 거의 다르지 않습니다.

다음 그림은 원소 3개를 가진 벡터에 `conj`로 원소 하나를 추가했을 때, 새 벡터가 기존 벡터의 잎 노드를 그대로 공유하면서 경로에 있는 노드만 새로 만드는 모습을 단순화해서 보여줍니다.

```text
                영속적 벡터의 구조 공유 (conj 예시)
   (설명을 위해 리프 노드 용량을 3개로 단순화함 -- 실제 Clojure
    벡터는 32개씩 묶임)

     v1 = [1 2 3 4 5 6]                v2 = (conj v1 7) = [1 2 3 4 5 6 7]

      +--------+                          +---------------------+
      |  루트   |                          | 루트 (v2, 새로 생성)  |
      |  (v1)  |                          +----------+-----------+
      +---+----+                                    /  \
          |    \                                   /    \
          |     \                                 /      \
     +----v---+  \                          +----v----+   +----v---------+
     | 리프 B  |   \                         | 리프 A  |   | 리프 B' (새로  |
     |[4 5 6] |    \                        |(공유됨)  |   |  생성)        |
     +--------+     \                       |[1 2 3]  |   |[4 5 6 7]     |
                     \                       +---------+   +--------------+
                      \                          ^
                       +------------------------>+
                       (v1의 화살표도 같은 리프 A를 가리킴)

   범례: [ ] 기본 테두리 = 기존 노드 (변경 없이 그대로 재사용)
         '새로 생성' 표시가 붙은 노드 = 새로 생성된 노드
```

그림에서 보듯, `conj` 이후에도 원래 벡터(`v1`)가 가리키던 잎 노드는 그대로 남아 있습니다. 새 벡터(`v2`)는 새로운 값 하나가 담긴 새 잎 노드를 만들고, 그 잎을 가리키는 새 뿌리 노드를 만들되, 나머지 원소는 원래 잎 노드를 "가리키기만" 합니다. 두 벡터는 메모리상에서 상당 부분을 공유하면서도 서로 완전히 독립된, 각자 완결된 값입니다.

```clojure
(def v1 [10 20 30])
(def v2 (conj v1 40))

v1
;; => [10 20 30]

v2
;; => [10 20 30 40]

(= v1 [10 20 30])
;; => true

;; v1과 v2는 내부적으로 30까지의 원소를 나타내는 구조를 공유하지만
;; 이는 구현 세부사항일 뿐, 프로그래머는 두 값을 완전히 독립된
;; 값으로 다루면 된다.
```

맵과 셋도 내부적으로 비슷한 트리 기반 구조(해시 배열 매핑 트라이, HAMT)를 사용하여 같은 원리로 구조 공유를 실현합니다. `assoc`으로 맵에 키를 하나 추가하거나 값을 바꿀 때도, 벡터와 마찬가지로 바뀐 경로의 노드들만 새로 만들고 나머지는 공유합니다.

```clojure
(def m1 {:a 1 :b 2 :c 3})
(def m2 (assoc m1 :d 4))

m1
;; => {:a 1, :b 2, :c 3}

m2
;; => {:a 1, :b 2, :c 3, :d 4}
```

프로그래머 입장에서는 구현 세부사항을 몰라도 됩니다. 중요한 것은 "값을 바꾸는 것 같은 연산도 사실은 새 값을 만드는 것이며, 그 과정이 놀랍도록 효율적으로 이루어진다"는 사실입니다.

### 얼마나 효율적인가: 직접 확인해보기

구조 공유의 효과를 REPL에서 간접적으로 느껴볼 수 있습니다. 아주 큰 벡터를 만들어도 `conj` 연산 자체는 여전히 빠르게 끝납니다.

```clojure
(def big-vector (vec (range 1000000)))

(count big-vector)
;; => 1000000

;; 백만 개짜리 벡터에 원소 하나를 추가해도 즉시 끝난다.
;; 전체를 복사한다면 이렇게 빠를 수 없다.
(def big-vector-2 (conj big-vector :extra))

(count big-vector-2)
;; => 1000001

(= (count big-vector) 1000000)
;; => true
```

만약 `conj`가 매번 백만 개의 원소를 전부 복사해야 했다면, 이런 연산을 반복문 안에서 수만 번 수행하는 프로그램은 실용적이지 않았을 것입니다. 8장에서 다룬 `reduce`나 시퀀스 처리 함수들이 컬렉션을 계속 새로 만들어가며 연산을 이어갈 수 있는 것도, 바로 이 영속적 자료구조 덕분입니다.

## 불변성의 장점과 대가

불변성은 공짜로 얻어지는 것이 아닙니다. 장점과 함께 감수해야 할 특성도 있습니다. 균형 잡힌 시각을 갖기 위해 정리해봅시다.

### 장점

- **동시성 안전성.** 여러 스레드가 같은 데이터를 동시에 읽어도 안전합니다. 잠금이 필요 없습니다.
- **참조 투명성과 예측 가능성.** 함수가 인자를 몰래 바꿀 수 없으므로, 함수의 동작을 그 입력과 출력만으로 온전히 이해할 수 있습니다. 5장에서 다룬 순수 함수의 개념과 자연스럽게 맞물립니다.
- **안전한 공유.** 같은 값을 여러 곳에서 참조해도 누군가 실수로 그 값을 훼손할 위험이 없습니다. 방어적 복사(defensive copy)를 할 필요가 아예 사라집니다.
- **이력 관리의 용이함.** 이전 버전의 데이터가 자연스럽게 보존되므로, "이전 상태로 되돌리기"나 "변경 이력 추적" 같은 기능을 구현하기 쉬워집니다. 13장에서 다룰 아톰(atom)이나 레퍼런스(ref)를 이용한 상태 관리도 이 특성을 적극 활용합니다.
- **캐싱과 동등성 비교의 효율.** 불변 값은 한 번 계산한 해시값을 재사용할 수 있어, 맵이나 셋에서의 동등성 비교(`=`)가 특정 상황에서 더 빨라질 수 있습니다.

### 감수해야 할 특성

- **약간의 오버헤드.** 원소 하나를 바꾸기 위해 트리의 일부 노드를 새로 만드는 과정은, 배열 인덱스 하나를 직접 덮어쓰는 연산보다는 느립니다. 대부분의 경우 이 차이는 무시할 만한 수준이지만, 극도로 성능에 민감한 저수준 연산에서는 고려 대상이 됩니다.
- **다량의 변경을 순차적으로 할 때의 비용.** 반복문 안에서 벡터에 원소를 하나씩 수백만 번 추가한다면, 매번 새 버전을 만드는 대신 "일시적으로 변경 가능한 임시 버전"을 사용하는 편이 유리할 수 있습니다. Clojure는 이를 위해 `transient`라는 메커니즘을 제공합니다.

```clojure
;; 대량의 원소를 연속으로 추가할 때는 transient!를 활용할 수 있다.
(defn build-large-vector [n]
  (persistent!
   (reduce conj! (transient []) (range n))))

(count (build-large-vector 100000))
;; => 100000
```

`transient`는 영속적 자료구조를 잠시 "변경 가능한" 형태로 바꾸어 일련의 연산을 빠르게 수행한 뒤, `persistent!`로 다시 안전한 불변 값으로 되돌리는 도구입니다. 이는 어디까지나 성능 최적화를 위한 예외적인 도구이며, 일반적인 코드에서는 잘 쓰지 않습니다. 지금 단계에서는 "이런 것이 존재하고, 필요하면 나중에 찾아볼 수 있다" 정도로만 기억해두면 충분합니다.

전체적으로 보면, 대부분의 Clojure 프로그램에서 불변성이 주는 이점(안전성, 예측 가능성, 동시성 지원)이 약간의 성능 오버헤드보다 훨씬 크다는 것이 실전에서 널리 검증된 결론입니다. 성능이 정말 중요한 극히 일부 구간에서만 `transient`나 다른 저수준 기법을 선택적으로 사용하면 됩니다.

## 불변성과 "제자리에서 바뀐 것처럼 보이는" 코드

한 가지 흔히 헷갈리는 부분을 짚고 넘어갑시다. 다음 코드를 봅시다.

```clojure
(def counter [0])

(def counter (conj counter 1))
(def counter (conj counter 2))

counter
;; => [0 1 2]
```

`def`를 반복해서 `counter`라는 이름이 가리키는 값을 계속 바꾸고 있으니, 얼핏 보면 "counter를 제자리에서 변경하고 있다"는 착각이 들 수 있습니다. 하지만 실제로 일어나는 일은 다음과 같습니다.

1. 처음의 `[0]`이라는 벡터가 만들어진다.
2. `(conj counter 1)`이 `[0]`을 바탕으로 `[0 1]`이라는 완전히 새로운 벡터를 만든다.
3. `def`가 `counter`라는 이름이 이제 `[0 1]`을 가리키도록 다시 연결한다. 이전 값 `[0]`은 변경되지 않은 채로 존재하지만, 더 이상 `counter`라는 이름으로는 접근할 수 없을 뿐이다.
4. 같은 과정이 `[0 1 2]`에 대해서도 반복된다.

즉, **바뀌는 것은 값이 아니라 이름이 가리키는 대상**입니다. 심볼 `counter`는 시간에 따라 다른 값을 가리킬 수 있지만, 각각의 값(`[0]`, `[0 1]`, `[0 1 2]`)은 한 번 만들어지면 절대로 변하지 않습니다. 이 구분은 매우 중요합니다. "변경 가능한 상태"를 다루는 진짜 도구는 `def`가 아니라 13장에서 배울 아톰이며, `def`는 최상위 이름과 값을 연결하는 정적인 선언에 가깝습니다.

## 요약

- Clojure의 기본 컬렉션(리스트, 벡터, 맵, 셋)은 모두 불변(immutable) 자료구조입니다. 한 번 만들어진 값은 절대로 바뀌지 않습니다.
- `conj`, `assoc`, `dissoc`, `update` 같은 함수는 원본을 변경하는 것이 아니라, 변경 사항이 반영된 새로운 값을 만들어 반환합니다.
- 불변성은 예측 가능성을 높이고, 동시성 문제(여러 스레드의 동시 접근)를 근본적으로 단순화하며, 데이터를 안전하게 공유할 수 있게 해줍니다.
- 영속적 자료구조(persistent data structure)는 구조 공유(structural sharing)를 이용해, 매번 전체를 복사하지 않고도 이전 버전과 새 버전을 모두 효율적으로 유지합니다.
- 벡터는 32-way 트리 구조로 구현되어 있어, 값 하나를 추가하거나 바꿀 때 변경 경로에 있는 노드만 새로 만들고 나머지는 기존 구조와 공유합니다. 그 결과 `conj`, `assoc` 같은 연산이 원소 개수와 거의 무관하게 빠르게 동작합니다.
- 불변성에는 약간의 성능 오버헤드가 따르지만, 대부분의 경우 이는 무시할 만한 수준이며 그 대가로 얻는 안전성이 훨씬 큽니다. 극단적인 성능 최적화가 필요할 때는 `transient`라는 예외적 도구를 선택적으로 사용할 수 있습니다.
- `def`로 이름을 다시 연결하는 것과, 값 자체가 변경되는 것은 전혀 다른 이야기입니다. 값은 항상 불변이며, 바뀌는 것은 이름이 가리키는 대상뿐입니다.

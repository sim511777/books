프로그램은 언제나 예상대로만 흘러가지 않습니다. 파일이 없을 수도 있고, 사용자가 숫자 대신 문자를 입력할 수도 있고, 네트워크 너머의 서버가 응답하지 않을 수도 있습니다. 지금까지 이 책에서 다룬 예제들은 "정상적인 경로"에 집중해왔지만, 실무 코드의 상당 부분은 사실 "일이 잘못되었을 때 무엇을 할 것인가"를 다룹니다. Clojure는 JVM 위에서 동작하는 언어인 만큼 자바의 예외 처리 메커니즘을 그대로 물려받으면서도, `ex-info`라는 도구와 "예외 대신 값으로 실패를 표현하는" 함수형 스타일을 통해 Clojure다운 접근을 함께 제공합니다. 이번 장에서는 이 두 갈래를 모두 살펴봅니다.

## try, catch, finally의 기본 형태

### 예외를 잡아내기

Clojure에서 예외를 처리하는 기본 형식은 `try`, `catch`, `finally`입니다. 문법 자체는 자바나 다른 주류 언어의 try-catch와 거의 같은 역할을 합니다.

```clojure
(defn safe-divide [a b]
  (try
    (/ a b)
    (catch ArithmeticException e
      (println "0으로 나눌 수 없습니다:" (.getMessage e))
      nil)))

(safe-divide 10 2)
;; => 5

(safe-divide 10 0)
;; 0으로 나눌 수 없습니다: Divide by zero
;; => nil
```

`try` 블록 안의 코드를 실행하다가 예외가 발생하면, Clojure는 그 예외의 클래스와 일치하는 `catch` 절을 찾아 실행합니다. `catch` 절은 `(catch 예외클래스 바인딩이름 실행할코드...)` 형태를 가지며, 여러 개의 `catch` 절을 나란히 두어 예외 종류에 따라 다르게 처리할 수 있습니다.

```clojure
(defn parse-and-divide [numerator-str denominator-str]
  (try
    (let [a (Integer/parseInt numerator-str)
          b (Integer/parseInt denominator-str)]
      (/ a b))
    (catch NumberFormatException e
      (println "숫자로 변환할 수 없는 입력입니다")
      nil)
    (catch ArithmeticException e
      (println "0으로 나눌 수 없습니다")
      nil)))

(parse-and-divide "10" "abc")
;; 숫자로 변환할 수 없는 입력입니다
;; => nil

(parse-and-divide "10" "0")
;; 0으로 나눌 수 없습니다
;; => nil

(parse-and-divide "10" "5")
;; => 2
```

`catch` 절은 위에서부터 순서대로 검사되므로, 더 구체적인 예외 클래스를 먼저 두고 일반적인 예외 클래스(`Exception`)를 나중에 두는 것이 일반적입니다. 모든 예외를 하나로 묶어 처리하고 싶다면 `Exception`을 사용합니다.

```clojure
(defn attempt [f]
  (try
    (f)
    (catch Exception e
      (println "예상치 못한 오류:" (.getMessage e))
      nil)))
```

다만 `Exception`으로 모든 예외를 뭉뚱그려 잡으면 정말로 예상치 못한 버그까지 조용히 삼켜버릴 위험이 있습니다. 어떤 예외를 구체적으로 예상하고 있는지 명시하는 습관은 18장 좋은 Clojure 코드 작성 습관에서 다시 강조할 코드 품질의 중요한 부분입니다.

### finally로 뒷정리하기

`finally` 절은 예외 발생 여부와 관계없이 항상 실행되는 블록입니다. 파일 핸들을 닫거나 자원을 반납하는 등 "무슨 일이 있어도 반드시 해야 하는" 정리 작업에 사용합니다.

```clojure
(defn process-with-cleanup [risky?]
  (try
    (println "작업을 시작합니다")
    (when risky?
      (throw (Exception. "작업 도중 문제가 발생했습니다")))
    (println "작업이 성공적으로 끝났습니다")
    :done
    (finally
      (println "자원을 정리합니다"))))

(process-with-cleanup false)
;; 작업을 시작합니다
;; 작업이 성공적으로 끝났습니다
;; 자원을 정리합니다
;; => :done

(process-with-cleanup true)
;; 작업을 시작합니다
;; 자원을 정리합니다
;; Execution error at ... (Exception)
;; 작업 도중 문제가 발생했습니다
```

두 번째 호출에서 `finally` 블록이 실행된 뒤에도 예외는 계속 위로 전파된다는 점에 주목하세요. `finally`는 예외를 잡아서 없애주지 않습니다. 예외를 실제로 멈추고 처리하려면 반드시 `catch` 절이 있어야 합니다. 16장 파일 입출력에서 다루는 파일 자원 해제 대부분은 `with-open`이라는 매크로가 내부적으로 이런 `try`/`finally` 패턴을 대신 처리해줍니다.

### throw로 예외 던지기

직접 예외를 발생시키려면 `throw`에 예외 객체를 넘깁니다. 자바 예외 클래스를 그대로 사용할 수도 있습니다.

```clojure
(defn withdraw [balance amount]
  (when (> amount balance)
    (throw (IllegalArgumentException. "잔액보다 큰 금액은 출금할 수 없습니다")))
  (- balance amount))

(withdraw 10000 3000)
;; => 7000

(withdraw 10000 50000)
;; Execution error at ... (IllegalArgumentException)
;; 잔액보다 큰 금액은 출금할 수 없습니다
```

`IllegalArgumentException.`처럼 클래스 이름 뒤에 점을 붙이는 문법은 3장 기본 문법과 데이터 타입에서 살펴본 자바 클래스 생성자 호출 문법입니다. Clojure에서 예외를 던지는 일은 사실 "자바 예외 객체를 하나 만들어서 JVM에게 넘기는 것"과 다르지 않습니다.

## Clojure가 JVM 예외 메커니즘을 그대로 쓴다는 것의 의미

Clojure는 예외 처리를 위한 독자적인 메커니즘을 새로 만들지 않고, JVM이 원래 가지고 있는 예외 처리 체계를 그대로 사용합니다. 이는 몇 가지 실질적인 결과를 낳습니다.

첫째, Clojure에서 발생하는 모든 예외는 결국 `java.lang.Throwable`의 하위 클래스입니다. `ArithmeticException`, `NullPointerException`, `IllegalArgumentException`처럼 자바 표준 라이브러리에 있는 예외 클래스를 Clojure 코드에서도 그대로 `catch`할 수 있고, 반대로 Clojure에서 던진 예외를 자바 코드가 잡을 수도 있습니다. 이 상호운용성은 15장 Java 상호운용에서 다루는 주제와 자연스럽게 이어집니다.

둘째, 예외가 발생하면 그 호출 스택(call stack)이 함께 기록됩니다. REPL에서 예외가 출력될 때 나오는 긴 스택 추적(stack trace)은 "어떤 함수가 어떤 함수를 호출하다가 문제가 생겼는지"를 추적하는 정보입니다.

```clojure
(defn level-three [] (throw (Exception. "가장 안쪽에서 발생한 문제")))
(defn level-two [] (level-three))
(defn level-one [] (level-two))

(level-one)
;; Execution error at user/level-three (REPL:1).
;; 가장 안쪽에서 발생한 문제
```

REPL 환경에 따라 `(pst)` 함수나 `*e`(가장 최근 예외를 가리키는 var)를 이용해 더 자세한 스택 추적을 확인할 수 있습니다.

셋째, Clojure의 예외 처리는 자바와 달리 "확인된 예외(checked exception)" 개념이 없습니다. 자바에서는 메서드 시그니처에 어떤 예외를 던질 수 있는지 명시하고 호출하는 쪽에서 반드시 처리하거나 다시 선언해야 하지만, Clojure 함수는 어떤 예외를 던질 수 있는지 타입 시스템 차원에서 강제하지 않습니다. 이는 코드를 간결하게 만들어주는 대신, 어떤 예외가 발생할 수 있는지를 문서화하고 소통하는 책임이 온전히 개발자에게 넘어온다는 뜻이기도 합니다. 이 책임을 잘 감당하기 위한 도구가 바로 다음 절에서 살펴볼 `ex-info`입니다.

## ex-info와 ex-data: Clojure다운 예외 정보 전달

### 왜 ex-info가 필요한가

`(Exception. "메시지")`처럼 평범한 예외를 던지면 사람이 읽을 수 있는 문자열 메시지 하나만 전달할 수 있습니다. 하지만 실제 오류 상황에서는 "어떤 값이 잘못되었는지", "어떤 필드가 문제인지"처럼 프로그램이 다룰 수 있는 구조화된 정보가 필요할 때가 많습니다. 이럴 때 메시지 문자열에 정보를 욱여넣는 대신, Clojure는 `ex-info`라는 함수를 제공합니다.

```clojure
(defn validate-age [age]
  (when (neg? age)
    (throw (ex-info "나이는 음수가 될 수 없습니다"
                     {:field :age
                      :value age
                      :error-type :invalid-input}))))

(validate-age -5)
;; Execution error (ExceptionInfo) at user/validate-age (REPL:2).
;; 나이는 음수가 될 수 없습니다
```

`ex-info`는 첫 번째 인자로 사람이 읽을 메시지 문자열을, 두 번째 인자로 임의의 맵을 받아 `ExceptionInfo`라는 예외 객체를 만들어줍니다. 이 맵에는 예외 상황을 프로그램이 이해할 수 있는 형태로 담을 수 있습니다.

### ex-data로 정보 꺼내기

`ex-info`로 만든 예외를 `catch`로 잡은 뒤에는 `ex-data` 함수로 두 번째 인자에 넘겼던 맵을 그대로 꺼낼 수 있습니다.

```clojure
(defn validate-age [age]
  (if (neg? age)
    (throw (ex-info "나이는 음수가 될 수 없습니다"
                     {:field :age
                      :value age
                      :error-type :invalid-input}))
    age))

(defn describe-validation-error [f value]
  (try
    (f value)
    (catch clojure.lang.ExceptionInfo e
      (let [data (ex-data e)]
        (println "필드:" (:field data))
        (println "잘못된 값:" (:value data))
        (println "오류 종류:" (:error-type data))))))

(describe-validation-error validate-age -5)
;; 필드: :age
;; 잘못된 값: -5
;; 오류 종류: :invalid-input
```

이 방식의 장점은 예외 메시지를 문자열 파싱으로 분석할 필요 없이, 맵의 키를 통해 오류 정보에 접근할 수 있다는 점입니다. 4장 컬렉션에서 배운 `get`, 키워드 함수 호출(`(:field data)`) 등 평범한 맵 다루기 기술을 예외 처리에도 그대로 재사용할 수 있는 셈입니다.

### 오류 종류에 따라 분기하기

`ex-data`가 반환하는 맵에 오류를 구분할 수 있는 키(흔히 `:type`이나 `:error-type`처럼 이름 짓습니다)를 넣어두면, 잡은 예외의 정보를 바탕으로 분기 처리를 할 수 있습니다.

```clojure
(defn withdraw! [balance amount]
  (cond
    (neg? amount)
    (throw (ex-info "출금액은 0보다 커야 합니다"
                     {:type :invalid-amount :amount amount}))

    (> amount balance)
    (throw (ex-info "잔액이 부족합니다"
                     {:type :insufficient-funds :balance balance :amount amount}))

    :else
    (- balance amount)))

(defn try-withdraw [balance amount]
  (try
    (withdraw! balance amount)
    (catch clojure.lang.ExceptionInfo e
      (case (:type (ex-data e))
        :invalid-amount (println "출금액이 올바르지 않습니다.")
        :insufficient-funds (println "잔액이 부족해서 출금할 수 없습니다.")
        (println "알 수 없는 오류입니다.")))))

(try-withdraw 10000 -100)
;; 출금액이 올바르지 않습니다.

(try-withdraw 10000 50000)
;; 잔액이 부족해서 출금할 수 없습니다.
```

`case`는 6장 제어 흐름에서 살펴본 것처럼 값을 기준으로 빠르게 분기하는 특수형입니다. `ex-data`가 돌려주는 맵의 특정 키 값으로 `case` 분기를 태우는 패턴은 여러 종류의 예외를 하나의 예외 클래스(`ExceptionInfo`)만으로 표현하면서도 세밀하게 대응할 수 있게 해줍니다.

### 원래 예외를 원인으로 감싸기

때로는 저수준에서 발생한 예외를 잡아서, 더 상위 수준의 의미를 가진 예외로 다시 던지고 싶을 때가 있습니다. `ex-info`의 세 번째 인자로 원래 예외를 넘기면 원인(cause) 체인을 유지할 수 있습니다.

```clojure
(defn load-config [path]
  (try
    (slurp path)
    (catch java.io.FileNotFoundException e
      (throw (ex-info "설정 파일을 불러오는 데 실패했습니다"
                       {:path path}
                       e)))))

(load-config "없는-파일.edn")
;; Execution error (ExceptionInfo) at user/load-config (REPL:3).
;; 설정 파일을 불러오는 데 실패했습니다
```

이렇게 감싸두면 `(.getCause e)`로 원래의 `FileNotFoundException`까지 추적할 수 있어서, "무슨 일이 있었는지"에 대한 정보를 한 겹도 잃어버리지 않습니다. 파일을 다루는 구체적인 방법은 16장 파일 입출력에서 이어서 다룹니다.

## 예외 대신 값으로 실패를 표현하기

### 예외의 대가

`try`/`catch`는 강력하지만 한 가지 단점이 있습니다. 예외를 던지는 함수는 함수 시그니처만 보고는 "이 함수가 실패할 수도 있다"는 사실을 알기 어렵습니다. 호출하는 쪽에서 `try`로 감싸는 것을 잊으면, 프로그램이 예상치 못한 지점에서 멈춰버립니다. 또한 예외를 던지고 잡는 과정 자체가 정상적인 함수 반환보다 계산 비용이 더 크다는 특징도 있습니다.

이런 이유로 Clojure 커뮤니티에서는 "정말로 예외적인 상황(프로그램이 계속 진행할 수 없는 버그, 시스템 오류)"에는 예외를 사용하되, "충분히 예상 가능한 실패(입력 값 검증 실패, 찾는 값이 없음)"에는 예외 대신 평범한 값을 돌려주는 스타일을 함께 사용하는 경우가 많습니다.

### nil로 실패를 표현하기

가장 단순한 방법은 실패했을 때 `nil`을 돌려주는 것입니다. 이미 4장 컬렉션과 6장 제어 흐름에서 만난 `get`, `some`, 맵 조회 같은 함수들이 이 스타일을 따릅니다.

```clojure
(defn find-user [users id]
  (some #(when (= (:id %) id) %) users))

(def users [{:id 1 :name "박지훈"} {:id 2 :name "이서윤"}])

(find-user users 1)
;; => {:id 1, :name "박지훈"}

(find-user users 999)
;; => nil
```

`find-user`는 예외를 던지는 대신 사용자를 찾지 못하면 조용히 `nil`을 돌려줍니다. 호출하는 쪽에서는 `if-let`이나 `when-let`(11장 구조 분해에서도 함께 등장하는 패턴입니다)으로 실패 여부를 자연스럽게 다룰 수 있습니다.

```clojure
(defn greet-user [users id]
  (if-let [user (find-user users id)]
    (str "안녕하세요, " (:name user) "님")
    "사용자를 찾을 수 없습니다"))

(greet-user users 1)
;; => "안녕하세요, 박지훈님"

(greet-user users 999)
;; => "사용자를 찾을 수 없습니다"
```

다만 `nil`을 실패의 신호로 쓰는 방식은 "왜 실패했는지"에 대한 정보를 전혀 담지 못한다는 한계가 있습니다. 또한 함수가 원래도 정상적으로 `nil`을 돌려줄 수 있는 상황이라면(예: 컬렉션 안에 실제로 `nil` 값이 들어 있는 경우), "실패해서 nil인지 정상적으로 nil인지" 구분할 수 없는 모호함이 생길 수 있습니다.

### 결과 맵으로 성공과 실패를 함께 표현하기

좀 더 풍부한 정보를 전달하고 싶다면, 성공 여부와 관련 데이터를 함께 담은 맵을 돌려주는 방식을 사용할 수 있습니다.

```clojure
(defn parse-age [input]
  (try
    (let [age (Integer/parseInt input)]
      (if (neg? age)
        {:success? false :error "나이는 음수가 될 수 없습니다"}
        {:success? true :value age}))
    (catch NumberFormatException _
      {:success? false :error "숫자로 변환할 수 없습니다"})))

(parse-age "29")
;; => {:success? true, :value 29}

(parse-age "-3")
;; => {:success? false, :error "나이는 음수가 될 수 없습니다"}

(parse-age "스물아홉")
;; => {:success? false, :error "숫자로 변환할 수 없습니다"}
```

이 함수를 호출하는 쪽은 `:success?` 키를 확인해 분기하면 됩니다.

```clojure
(defn handle-age-input [input]
  (let [result (parse-age input)]
    (if (:success? result)
      (println "입력받은 나이:" (:value result))
      (println "오류:" (:error result)))))

(handle-age-input "29")
;; 입력받은 나이: 29

(handle-age-input "스물아홉")
;; 오류: 숫자로 변환할 수 없습니다
```

여기서 흥미로운 점은 `parse-age` 내부에서 실제로 `try`/`catch`를 사용하고 있다는 사실입니다. `Integer/parseInt`처럼 우리가 직접 제어할 수 없는 자바 라이브러리 함수는 예외를 던지는 방식으로만 실패를 알려주므로, 그 경계에서 예외를 잡아 값으로 변환해주는 어댑터 역할을 `parse-age`가 수행하고 있는 것입니다. 실무에서는 이렇게 "외부 세계와 맞닿는 경계에서는 예외를 잡아 값으로 바꾸고, 내 코드의 로직 안에서는 값으로 실패를 주고받는" 패턴이 자주 쓰입니다.

### 두 스타일을 언제 섞어 쓸 것인가

예외와 값, 두 가지 방식을 다음과 같은 기준으로 구분해 사용하면 코드의 의도가 분명해집니다.

- **예외가 어울리는 경우**: 프로그램이 정상적으로 계속 진행될 수 없는 상황(설정 파일이 아예 없어 애플리케이션을 시작할 수 없는 경우), 호출하는 쪽 대부분이 실패를 신경 쓸 필요가 없어서 실패 시 즉시 중단되는 편이 자연스러운 상황, 그리고 자바 라이브러리와의 경계처럼 이미 예외 기반으로 동작하는 영역.
- **값이 어울리는 경우**: 실패가 흔히 일어날 수 있고 호출하는 쪽이 매번 그 실패를 적절히 처리해야 하는 상황(사용자 입력 검증, 외부 API 결과 처리), 실패의 원인을 세분화해서 호출자가 각기 다르게 대응해야 하는 상황.

두 스타일은 서로 배타적이지 않습니다. 앞의 `parse-age` 예제처럼 "함수 내부에서는 예외를 다루되 바깥으로는 값을 돌려준다"는 조합이 실무에서 아주 흔하게 나타나는 패턴입니다.

## 요약

- Clojure는 `try`, `catch`, `finally`, `throw`라는 익숙한 형태로 예외를 다루며, 이는 JVM의 예외 처리 메커니즘을 그대로 사용하는 것입니다.
- `catch`는 예외 클래스를 기준으로 여러 절을 나란히 둘 수 있고, 위에서부터 순서대로 일치하는 절이 실행됩니다. `finally`는 예외 발생 여부와 관계없이 항상 실행되지만 예외 자체를 없애주지는 않습니다.
- Clojure에서 발생하는 모든 예외는 `Throwable`의 하위 클래스이므로 자바 예외 클래스와 자유롭게 상호운용되며, 자바와 달리 확인된 예외 개념이 없습니다.
- `ex-info`는 메시지 문자열과 함께 임의의 맵을 담아 예외를 만들 수 있게 해주고, `ex-data`로 그 맵을 다시 꺼낼 수 있어 오류 정보를 프로그램이 다룰 수 있는 구조화된 형태로 전달할 수 있습니다.
- 예외를 던지는 대신 `nil`이나 `{:success? ... }` 같은 결과 맵으로 실패를 표현하는 함수형 스타일은 실패가 흔하고 호출자가 매번 분기해야 하는 상황에 적합하며, 외부 라이브러리 경계에서 예외를 값으로 변환하는 어댑터 패턴과 자주 결합됩니다.
- "프로그램이 계속 진행할 수 없는 상황"에는 예외를, "흔히 일어나고 호출자가 처리해야 하는 실패"에는 값을 사용하는 것이 실무적인 구분 기준입니다.

지금까지 다룬 코드는 대부분 "입력을 받아 새로운 값을 돌려주는" 함수였습니다. 벡터에 원소를 추가해도 원본은 그대로였고, 맵의 키를 바꿔도 새로운 맵이 만들어질 뿐이었습니다. 그런데 실제 프로그램은 결국 어딘가의 "상태"를 다뤄야 합니다. 은행 계좌의 잔액, 접속 중인 사용자 목록, 게임 캐릭터의 체력처럼 시간이 흐르면서 값이 바뀌어야 하는 대상이 분명히 존재합니다. 이번 장에서는 Clojure가 불변 값이라는 원칙을 깨뜨리지 않으면서도 이런 "변하는 무언가"를 어떻게 다루는지, 그리고 여러 스레드가 동시에 상태를 건드릴 때 어떤 도구를 골라야 하는지 살펴봅니다.

## 값과 상태를 구분하기

Clojure를 이해하는 데 가장 중요한 개념 중 하나는 "값(value)"과 "상태(state)"를 서로 다른 것으로 취급한다는 점입니다. 9장 불변성과 영속적 자료구조에서 살펴본 것처럼, `[1 2 3]`이라는 벡터는 그 자체로 하나의 불변한 값입니다. 이 값은 절대로 변하지 않습니다. 어제 만든 `[1 2 3]`과 오늘 만든 `[1 2 3]`은 완전히 동일한 값입니다.

반면 "상태"는 시간에 따라 다른 값을 가리킬 수 있는 무언가입니다. 예를 들어 "현재 장바구니에 담긴 상품 목록"이라는 개념을 생각해보면, 이 개념 자체는 시간이 지나면서 `[]`였다가 `["사과"]`가 되었다가 `["사과" "우유"]`가 될 수 있습니다. 장바구니에 담긴 상품 목록이라는 "상태"는 특정 시점마다 서로 다른 불변 "값"을 가리키는 것입니다.

Java나 Python처럼 변수가 곧 상자이고 그 상자 안의 내용물을 직접 덮어쓰는 언어에 익숙하다면, Clojure의 이런 구분이 다소 낯설게 느껴질 수 있습니다. Clojure는 "상자 안의 내용물을 지우고 다시 쓴다"는 비유 대신 "상태란 시간의 흐름에 따라 서로 다른 불변 값을 순서대로 가리키는 것"이라는 비유를 사용합니다. 이 관점을 코드로 표현하기 위해 Clojure는 아톰(atom), 레퍼런스(ref), 에이전트(agent), 그리고 var라는 네 가지 참조 타입(reference type)을 제공합니다. 이들은 모두 "지금 이 순간 어떤 불변 값을 가리키고 있는지"를 관리하는 상자 역할을 하지만, 그 상자의 내용물을 바꾸는 방식과 안전성 보장이 서로 다릅니다.

이 장에서 다루는 네 가지 도구를 미리 한 문장씩 요약하면 다음과 같습니다.

- **아톰**: 하나의 독립적인 상태를 동기적으로, 원자적으로 바꿉니다. 가장 많이 쓰이는 도구입니다.
- **레퍼런스**: 여러 개의 상태를 하나의 트랜잭션 안에서 함께, 일관되게 바꿉니다.
- **에이전트**: 상태 변경 작업을 백그라운드 스레드에 맡기고 결과를 기다리지 않습니다.
- **var**: 네임스페이스에 속한 이름에 값을 연결하고, 필요하면 스레드마다 다른 값을 갖게 합니다.

## 아톰: 독립적인 상태를 다루는 기본 도구

### 아톰 만들고 값 읽기

아톰은 `atom` 함수로 만듭니다. 인자로 준 값이 아톰의 초기 상태가 됩니다.

```clojure
(def counter (atom 0))

counter
;; => #object[clojure.lang.Atom 0x... {:status :ready, :val 0}]
```

아톰 안에 들어 있는 현재 값을 꺼내려면 `deref` 함수를 쓰거나, 더 널리 쓰이는 축약 문법인 `@` 기호를 붙입니다.

```clojure
(deref counter)
;; => 0

@counter
;; => 0
```

`counter`라는 이름 자체는 "아톰이라는 상자"를 가리키고, `@counter`는 "그 상자 안에 지금 들어 있는 값"을 가리킨다는 점을 분명히 구분해야 합니다. `def`로 만든 `counter`는 한 번 정의되면 항상 같은 아톰 객체를 가리키지만, 그 아톰 안의 내용물은 시간에 따라 바뀔 수 있습니다.

### swap!으로 값 변경하기

아톰의 값을 바꾸는 가장 일반적인 방법은 `swap!` 함수입니다. `swap!`은 "아톰"과 "현재 값을 받아 새로운 값을 돌려주는 함수"를 인자로 받습니다.

```clojure
(swap! counter inc)
;; => 1

@counter
;; => 1

(swap! counter + 10)
;; => 11

@counter
;; => 11
```

`swap!`이 하는 일을 풀어서 설명하면 다음과 같습니다.

1. 아톰의 현재 값을 읽는다.
2. 그 값에 주어진 함수를 적용해 새로운 값을 계산한다.
3. 아톰의 값을 새로운 값으로 원자적으로 교체한다.

여기서 "원자적으로(atomically)"라는 표현이 핵심입니다. 여러 스레드가 동시에 같은 아톰에 `swap!`을 호출해도, Clojure는 내부적으로 CAS(Compare-And-Set)라는 하드웨어 수준의 연산을 이용해 "누군가 먼저 값을 바꿔버렸다면 다시 계산해서 재시도"하는 과정을 자동으로 반복합니다. 즉 `swap!`에 넘기는 함수는 언제든 여러 번 재시도될 수 있으므로 부작용(side effect)이 없는 순수 함수여야 합니다. 데이터베이스에 기록하거나 화면에 출력하는 코드를 `swap!`에 넘기는 함수 안에 넣으면, 경쟁 상황에서 그 부작용이 여러 번 실행될 위험이 있습니다.

여러 스레드가 동시에 하나의 카운터를 증가시키는 상황을 시뮬레이션해보면 아톰의 원자성을 확인할 수 있습니다.

```clojure
(def shared-counter (atom 0))

(defn bump-many-times! [n]
  (dotimes [_ n]
    (swap! shared-counter inc)))

;; 4개의 스레드가 각각 10000번씩 증가시킨다
(let [threads (repeatedly 4 #(Thread. (fn [] (bump-many-times! 10000))))]
  (doseq [t threads] (.start t))
  (doseq [t threads] (.join t)))

@shared-counter
;; => 40000
```

만약 `shared-counter`가 평범한 가변 변수였고 `swap!` 없이 "읽고 더하고 다시 쓰는" 세 단계를 따로 수행했다면, 두 스레드가 동시에 값을 읽어버려서 일부 증가 연산이 누락되는 경쟁 조건(race condition)이 발생할 수 있습니다. `swap!`은 이런 문제를 별도의 락(lock) 없이도 해결해줍니다.

### reset!으로 값을 통째로 교체하기

현재 값과 무관하게 새로운 값으로 완전히 덮어쓰고 싶다면 `reset!`을 씁니다.

```clojure
(reset! counter 0)
;; => 0

@counter
;; => 0
```

`swap!`은 "현재 값을 바탕으로 다음 값을 계산"하는 반면, `reset!`은 "현재 값이 무엇이든 상관없이 이 값으로 바꿔라"라는 명령입니다. 초기화 로직이나, 이전 값과 무관하게 정해진 값을 넣어야 하는 상황(예: 설정 값을 다시 불러오는 경우)에 적합합니다.

### 복합 자료구조를 담은 아톰

아톰은 숫자뿐 아니라 맵, 벡터, 셋 등 어떤 값이든 담을 수 있습니다. 실무에서는 애플리케이션의 상태 전체를 하나의 맵으로 표현하고 그 맵을 아톰에 담아 관리하는 패턴이 흔합니다.

```clojure
(def app-state (atom {:users [] :logged-in? false}))

(swap! app-state update :users conj {:name "김서연" :age 29})
;; => {:users [{:name "김서연", :age 29}], :logged-in? false}

(swap! app-state assoc :logged-in? true)
;; => {:users [{:name "김서연", :age 29}], :logged-in? true}

@app-state
;; => {:users [{:name "김서연", :age 29}], :logged-in? true}
```

여기서 `update`와 `assoc`처럼 4장 컬렉션에서 배운 순수 함수들이 그대로 `swap!`의 두 번째 인자로 재사용되는 모습을 볼 수 있습니다. "불변 자료구조를 다루는 순수 함수"와 "그 값을 담고 있는 상태를 바꾸는 도구"가 명확히 분리되어 있다는 점이 Clojure 상태 관리의 핵심 설계입니다.

### watch: 값이 바뀔 때 알아채기

아톰(그리고 레퍼런스, 에이전트, var)에는 값이 바뀔 때마다 호출되는 감시 함수를 등록할 수 있습니다. `add-watch`를 사용합니다.

```clojure
(def temperature (atom 20))

(add-watch temperature :alert
  (fn [key ref old-val new-val]
    (when (> new-val 30)
      (println "경고: 온도가" new-val "도까지 올라갔습니다 (이전:" old-val ")"))))

(reset! temperature 25)
;; => 25

(reset! temperature 32)
;; 경고: 온도가 32 도까지 올라갔습니다 (이전: 25)
;; => 32
```

감시 함수는 `[key ref old-val new-val]` 네 개의 인자를 받습니다. 로깅, 알림, 캐시 무효화처럼 "상태 변경에 반응해야 하는" 부수적인 작업을 본체 로직과 분리할 때 유용합니다.

## 레퍼런스와 STM: 여러 상태를 함께 바꾸기

### 아톰만으로는 부족한 상황

아톰은 하나의 독립적인 상태를 다룰 때는 완벽하지만, "여러 개의 상태를 동시에, 일관되게 바꿔야 하는" 상황에는 적합하지 않습니다. 대표적인 예가 계좌 이체입니다. 계좌 A에서 만 원을 빼서 계좌 B에 만 원을 더하는 작업은 두 아톰을 각각 `swap!`하는 것만으로는 안전하지 않습니다.

```clojure
;; 이렇게 하면 위험합니다 (설명용 예시)
(def account-a (atom 10000))
(def account-b (atom 5000))

(swap! account-a - 3000)
(swap! account-b + 3000)
```

두 `swap!` 사이에는 아무런 연결 고리가 없습니다. 첫 번째 `swap!`이 끝나고 두 번째 `swap!`이 실행되기 전에 다른 스레드가 끼어들어 `account-a`나 `account-b`를 읽는다면, "A에서는 이미 돈이 빠졌는데 B에는 아직 들어오지 않은" 순간을 목격하게 됩니다. 두 상태를 마치 하나의 원자적인 단위처럼 묶어서 바꿀 방법이 필요합니다.

### ref와 dosync, alter

Clojure는 이런 상황을 위해 레퍼런스(ref)와 STM(Software Transactional Memory, 소프트웨어 트랜잭션 메모리)을 제공합니다. 레퍼런스는 `ref` 함수로 만들고, 그 값을 바꾸는 연산은 반드시 `dosync` 블록 안에서 이뤄져야 합니다.

```clojure
(def account-a (ref 10000))
(def account-b (ref 5000))

(defn transfer! [from to amount]
  (dosync
    (alter from - amount)
    (alter to + amount)))

(transfer! account-a account-b 3000)

@account-a
;; => 7000

@account-b
;; => 8000
```

`dosync`는 "이 블록 안의 모든 레퍼런스 변경을 하나의 트랜잭션으로 묶어라"는 뜻입니다. 트랜잭션 안에서는 관계형 데이터베이스의 트랜잭션과 비슷하게 다음 성질이 보장됩니다.

- **원자성**: `dosync` 블록 안의 모든 `alter` 호출은 전부 성공하거나 전부 실패합니다. 중간에 예외가 발생하면 지금까지의 변경은 전부 취소됩니다.
- **일관성**: 트랜잭션이 끝난 시점에는 관련된 모든 레퍼런스가 항상 서로 앞뒤가 맞는 상태로 관찰됩니다. 다른 스레드는 "이체 도중의 어중간한 상태"를 절대로 볼 수 없습니다.
- **격리성**: 여러 트랜잭션이 동시에 실행되어도 서로의 중간 과정을 보지 못합니다. 충돌이 감지되면 STM이 자동으로 트랜잭션을 재시도합니다.

`alter`는 아톰의 `swap!`과 비슷하게 "현재 값에 함수를 적용해 새 값을 계산"하는 방식으로 동작합니다. 마찬가지로 충돌 시 재시도될 수 있으므로 `alter`에 넘기는 함수도 부작용이 없어야 합니다.

### commute: 순서가 중요하지 않을 때의 최적화

`alter`는 트랜잭션이 충돌하면 재시도하면서 실행 순서를 엄격하게 지킵니다. 그런데 덧셈처럼 "어떤 순서로 적용해도 결과가 같은" 연산이라면, `commute`를 사용해 STM이 좀 더 유연하게 재시도하도록 최적화할 수 있습니다.

```clojure
(def total-points (ref 0))

(defn add-points! [n]
  (dosync
    (commute total-points + n)))
```

`commute`는 커밋 시점에 실제 연산을 다시 적용하기 때문에 `alter`보다 충돌이 적고 성능이 좋을 수 있지만, 연산이 교환법칙과 결합법칙을 만족하지 않는 경우(예: 나눗셈, 리스트에 원소를 순서대로 추가하는 연산)에 사용하면 예상과 다른 결과가 나올 수 있습니다. 확신이 서지 않는다면 안전한 `alter`를 기본으로 사용하고, 성능이 실제로 문제가 될 때만 `commute`로 바꾸는 것을 권합니다.

### 여러 계좌를 함께 검증하는 예제

`dosync`의 진짜 힘은 여러 레퍼런스를 함께 검증하고 바꿔야 할 때 드러납니다. 잔액이 부족하면 이체를 취소하는 로직을 추가해봅시다.

```clojure
(defn safe-transfer! [from to amount]
  (dosync
    (when (< @from amount)
      (throw (ex-info "잔액이 부족합니다"
                       {:balance @from :requested amount})))
    (alter from - amount)
    (alter to + amount)))

(safe-transfer! account-a account-b 100000)
;; Execution error (ExceptionInfo) at ...
;; 잔액이 부족합니다
```

트랜잭션 안에서 예외가 발생하면 `alter`로 이미 만들어둔 변경 사항까지 포함해 트랜잭션 전체가 취소됩니다. 덕분에 "일부만 반영된 상태"가 절대로 외부에 노출되지 않습니다. 예외 처리 자체는 14장 예외 처리와 에러 다루기에서 자세히 다룹니다.

## 에이전트: 비동기적으로 상태 바꾸기

### send와 send-off

아톰과 레퍼런스는 모두 동기적입니다. `swap!`이나 `alter`를 호출한 스레드는 그 결과가 반영될 때까지 (트랜잭션 재시도를 포함해) 기다립니다. 반면 에이전트(agent)는 상태 변경 작업 자체를 별도의 스레드 풀에 맡기고, 호출한 스레드는 결과를 기다리지 않고 즉시 다음 코드로 넘어갑니다.

에이전트는 `agent` 함수로 만들고, `send` 또는 `send-off`로 상태를 변경하는 함수를 보냅니다.

```clojure
(def log-agent (agent []))

(defn log! [entry]
  (send log-agent conj entry))

(log! "서버 시작")
(log! "사용자 로그인")
(log! "데이터 저장 완료")

;; send 호출은 즉시 반환됩니다
@log-agent
;; => [] 혹은 이미 일부/전부 반영된 값 (타이밍에 따라 다름)

;; 잠시 후
@log-agent
;; => ["서버 시작" "사용자 로그인" "데이터 저장 완료"]
```

`send`로 넘긴 작업들은 해당 에이전트에 대해 보낸 순서대로 하나씩 순차적으로 실행됩니다. 여러 스레드가 같은 에이전트에 `send`를 호출해도 에이전트 내부의 상태 변경은 항상 한 번에 하나씩만 일어나므로, 아톰처럼 재시도할 필요 없이 안전합니다.

`send`와 `send-off`는 비슷하지만 사용하는 스레드 풀이 다릅니다. `send`는 CPU 연산 위주의 짧고 논블로킹(non-blocking)인 작업을 위한 고정 크기 스레드 풀을 사용하고, `send-off`는 파일 읽기나 네트워크 호출처럼 오래 걸리거나 블로킹될 수 있는 작업을 위한 확장 가능한 스레드 풀을 사용합니다. 파일 입출력(16장 파일 입출력에서 다룹니다)처럼 시간이 걸리는 작업을 에이전트에 맡길 때는 `send-off`를 사용해야 `send`용 스레드 풀이 고갈되는 것을 막을 수 있습니다.

```clojure
(def file-writer-agent (agent nil))

(send-off file-writer-agent
  (fn [_]
    (spit "log.txt" "새로운 로그 항목\n" :append true)
    nil))
```

### await로 완료 기다리기

`send`나 `send-off`는 결과를 기다리지 않지만, 필요하다면 `await`로 지금까지 보낸 작업이 모두 끝날 때까지 현재 스레드를 멈춰 기다릴 수 있습니다.

```clojure
(log! "마지막 로그")
(await log-agent)

@log-agent
;; => ["서버 시작" "사용자 로그인" "데이터 저장 완료" "마지막 로그"]
```

### 에이전트의 오류 처리

에이전트에 보낸 함수 안에서 예외가 발생하면 기본적으로 그 에이전트는 "실패 상태"가 되고, 이후에 보내는 작업은 실행되지 않습니다. `agent-error`로 오류를 확인하고 `restart-agent`로 복구할 수 있습니다.

```clojure
(def risky-agent (agent 0))

(send risky-agent (fn [_] (/ 1 0)))
(await risky-agent)

(agent-error risky-agent)
;; => #error { :cause "Divide by zero" ... }

(restart-agent risky-agent 0)
;; => 0
```

이런 동작 방식 덕분에 에이전트는 "오류가 나도 조용히 무시하고 다음 작업을 계속 처리하는" 대신 "오류를 명확히 드러내고 복구를 요구하는" 안전한 기본값을 갖습니다.

## var와 동적 바인딩 간단히 살펴보기

`def`로 만드는 것은 사실 var라는 참조 타입입니다.

```clojure
(def app-name "나의 애플리케이션")

app-name
;; => "나의 애플리케이션"
```

일반적인 var는 네임스페이스 안에서 이름과 값을 연결해주는 역할만 하며, 10장 네임스페이스와 코드 구성에서 살펴본 것처럼 대부분 한 번 정의하면 값을 바꾸지 않습니다. 그런데 var는 `^:dynamic` 메타데이터를 붙이면 스레드마다 서로 다른 값을 가질 수 있는 동적 var가 됩니다.

```clojure
(def ^:dynamic *log-level* :info)

(defn log-message [msg]
  (println (str "[" (name *log-level*) "] " msg)))

(log-message "기본 레벨로 출력")
;; [info] 기본 레벨로 출력

(binding [*log-level* :debug]
  (log-message "디버그 레벨로 출력"))
;; [debug] 디버그 레벨로 출력

(log-message "다시 기본 레벨")
;; [info] 다시 기본 레벨로 출력
```

관례적으로 동적 var의 이름은 별표(`*`)로 감싸서 `*log-level*`처럼 씁니다. `binding`은 해당 블록이 실행되는 동안에만, 그리고 그 블록에서 호출된 함수들 안에서만 var의 값을 임시로 바꿔줍니다. 블록을 벗어나면 원래 값으로 돌아옵니다.

동적 바인딩은 "함수의 인자로 매번 넘기기는 번거롭지만, 특정 구간 동안만 전역적으로 동작을 바꾸고 싶은" 상황에 씁니다. 실제로 Clojure 표준 라이브러리의 `*out*`(표준 출력 스트림)이나 `*print-length*`(컬렉션 출력 시 최대 길이) 같은 var들이 이런 방식으로 쓰입니다.

```clojure
(binding [*print-length* 3]
  (println (range 100)))
;; (0 1 2 ...)
```

다만 동적 바인딩은 "코드를 읽는 사람이 눈에 보이지 않는 전역 상태에 의존하게 만든다"는 단점이 있으므로, 로깅 설정이나 테스트 환경에서 임시로 의존성을 바꿔치기하는 등 제한된 용도로 사용하는 것이 바람직합니다.

## 언제 무엇을 쓸 것인가

지금까지 살펴본 도구를 정리하면 다음과 같습니다.

| 도구 | 동기/비동기 | 다루는 상태 개수 | 값 변경 방법 | 대표 상황 |
|---|---|---|---|---|
| 아톰(atom) | 동기 | 하나 | `swap!`, `reset!` | 독립적인 카운터, 캐시, 애플리케이션 전체 상태 맵 |
| 레퍼런스(ref) | 동기 | 여러 개(트랜잭션) | `dosync` 안에서 `alter`, `commute` | 계좌 이체처럼 여러 상태를 일관되게 함께 바꿔야 할 때 |
| 에이전트(agent) | 비동기 | 하나 | `send`, `send-off` | 로그 적재, 백그라운드 집계처럼 결과를 즉시 기다릴 필요가 없는 작업 |
| var(동적 바인딩) | 동기(스레드 국소적) | 하나(이름에 연결) | `binding` | 로깅 레벨, 출력 대상처럼 특정 구간 동안만 바꾸고 싶은 설정 값 |

실무에서 마주치는 대부분의 상태는 아톰 하나로 충분히 해결됩니다. "여러 개의 서로 다른 상태를 원자적으로 함께 바꿔야 하는가?"라는 질문에 그렇다고 답할 수 있을 때만 레퍼런스를 고려하고, "이 상태 변경 작업의 결과를 지금 당장 알아야 하는가?"라는 질문에 아니오라고 답할 수 있을 때 에이전트를 고려하는 순서로 판단하면 선택이 한결 쉬워집니다.

아래 다이어그램은 세 가지 동시성 도구가 동기/비동기, 단일/복수 상태라는 두 축에서 어떻게 자리 잡는지를 정리한 것입니다.

```text
                     아톰 . 레퍼런스 . 에이전트 비교
        가로축: 다루는 상태의 개수 / 세로축: 실행 방식(동기.비동기)

              단일 상태(독립된 값 하나)   |   복수 상태(여러 값을 함께)
            -----------------------------+-----------------------------
            +-------------------------+  |  +-------------------------+
   동기      |     아톰 (atom)          |  |  |    레퍼런스 (ref)        |
  (호출자가  |   swap! / reset!        |  |  |  dosync 안에서            |
   결과를    |  CAS 기반, 재시도로      |  |  |  alter / commute         |
   기다림)   |  원자성 보장             |  |  |  STM 트랜잭션으로          |
            |  예: 카운터, 캐시        |  |  |  원자성.일관성.격리성 보장 |
            |                         |  |  |  예: 계좌 간 이체          |
            +-------------------------+  |  +-------------------------+
            -----------------------------+-----------------------------
            +-------------------------+  |  +-------------------------+
   비동기    |   에이전트 (agent)       |  |  |  해당하는 표준 도구 없음   |
  (백그라운드|   send / send-off       |  |  |  (필요하면 에이전트 여러  |
   스레드에  |  작업을 스레드 풀에 맡기고 |  |  |   개를 직접 조합해서      |
   위임)     |  즉시 반환, await로 대기 |  |  |   구성)                  |
            |  가능                    |  |  |                         |
            |  예: 로그 적재, 백그라운드|  |  |                         |
            |      집계               |  |  |                         |
            +-------------------------+  |  +-------------------------+

  공통점: 세 도구 모두 내부 값은 불변(immutable) 값이며,
  참조 타입만 "지금 어떤 값을 가리키는지"를 바꿀 뿐입니다.
```

## 상태 도구를 고를 때 흔히 하는 실수

몇 가지 실수를 미리 짚어두면 나중에 디버깅 시간을 아낄 수 있습니다.

**`swap!`이나 `alter`에 부작용이 있는 함수를 넘기는 실수**. 두 함수 모두 충돌 시 재시도될 수 있으므로, 넘기는 함수 안에서 `println`을 호출하거나 외부 시스템에 네트워크 요청을 보내면 그 부작용이 여러 번 실행될 수 있습니다.

```clojure
;; 이렇게 하면 재시도 시 콘솔에 여러 번 출력될 수 있습니다
(swap! counter (fn [n] (println "증가 중...") (inc n)))
```

**모든 상태를 레퍼런스로 만들어버리는 실수**. STM은 강력하지만 트랜잭션 관리에는 비용이 따릅니다. 독립적인 상태 하나를 다룰 때는 아톰만으로 충분하며, 레퍼런스는 "여러 상태를 함께" 바꿔야 하는 경우로 한정하는 것이 좋습니다.

**에이전트의 결과를 기다리지 않고 바로 사용하는 실수**. `send`나 `send-off`는 즉시 반환되므로, 직후에 `deref`로 값을 읽으면 아직 작업이 반영되지 않았을 수 있습니다. 결과를 확실히 확인해야 한다면 `await`를 쓰거나, 애초에 결과를 동기적으로 알아야 하는 작업이라면 에이전트 대신 아톰이나 일반 함수 호출을 고려해야 합니다.

## 요약

- Clojure는 "불변 값"과 "그 값을 시간에 따라 가리키는 상태"를 명확히 구분합니다. 값 자체는 절대 바뀌지 않고, 상태는 어느 순간 어떤 값을 가리키는지가 바뀔 뿐입니다.
- 아톰은 `swap!`(현재 값 기반 갱신)과 `reset!`(무조건 교체)으로 다루는, 하나의 독립적인 상태를 위한 동기적 도구입니다.
- 레퍼런스와 `dosync`, `alter`, `commute`로 대표되는 STM은 여러 상태를 하나의 트랜잭션으로 묶어 원자성, 일관성, 격리성을 보장하며 함께 바꿔야 할 때 사용합니다.
- 에이전트는 `send`(짧은 작업)와 `send-off`(오래 걸리거나 블로킹되는 작업)로 상태 변경을 백그라운드에 맡기는 비동기 도구이며, `await`로 완료를 기다리거나 `agent-error`로 오류를 확인할 수 있습니다.
- var는 기본적으로 네임스페이스에 이름과 값을 연결하며, `^:dynamic`과 `binding`을 사용하면 특정 구간에서만 스레드 국소적으로 값을 바꿀 수 있습니다.
- 상태 하나만 독립적으로 다룬다면 아톰, 여러 상태를 함께 일관되게 바꿔야 한다면 레퍼런스, 결과를 즉시 기다릴 필요가 없다면 에이전트를 선택하는 것이 실무적인 기준입니다.

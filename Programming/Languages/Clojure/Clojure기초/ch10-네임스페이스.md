지금까지의 예제들은 대부분 REPL 안에서, 혹은 파일 하나짜리 짧은 프로그램 안에서 함수를 정의하고 바로 사용해왔습니다. 하지만 실제 프로젝트는 파일 하나로 끝나지 않습니다. 코드가 늘어나면 관련된 함수와 데이터를 의미 있는 단위로 묶고, 이름 충돌을 피하고, 다른 사람이 만든 코드(라이브러리)를 가져다 쓸 방법이 필요해집니다. 이 모든 것을 담당하는 Clojure의 도구가 바로 네임스페이스(namespace)입니다. 이번 장에서는 네임스페이스가 무엇이고, `require`·`import` 같은 도구로 어떻게 다른 네임스페이스의 코드를 가져다 쓰는지, 그리고 여러 파일로 프로젝트를 구성하는 방법을 살펴봅니다.

## 네임스페이스란 무엇인가

네임스페이스는 심볼(symbol)들의 이름공간, 즉 이름들을 담아두는 독립된 상자라고 생각하면 됩니다. 지금까지 REPL에서 `def`나 `defn`으로 무언가를 정의할 때마다, 사실 우리는 매번 "현재 네임스페이스"라는 상자 안에 이름을 채워 넣고 있었던 것입니다.

```clojure
user=> (def greeting "안녕하세요")
#'user/greeting
```

REPL이 출력한 `#'user/greeting`을 눈여겨보세요. `user`는 네임스페이스 이름이고, `greeting`은 그 네임스페이스 안에 정의된 심볼 이름입니다. `user/greeting`이라는 표기는 "user라는 네임스페이스에 속한 greeting"이라는 뜻이며, 이를 정규 한정 이름(fully-qualified name)이라고 부릅니다.

REPL을 처음 띄우면 기본적으로 `user`라는 네임스페이스에 들어와 있습니다. 지금까지 별다른 선언 없이 함수를 정의해온 것은, 사실 암묵적으로 `user` 네임스페이스 안에서 작업해온 것입니다.

### 왜 네임스페이스가 필요한가

작은 프로젝트 두 개가 있다고 상상해봅시다. 하나는 온라인 서점, 하나는 도서관 대출 시스템입니다. 두 프로젝트 모두 `book`이라는 개념을 다루기 때문에, 각각 다음과 같은 함수를 만들고 싶어 할 수 있습니다.

```clojure
(defn available? [book]
  ;; 서점: 재고가 있는지 확인
  (> (:stock book) 0))
```

```clojure
(defn available? [book]
  ;; 도서관: 대출 가능한지 확인
  (not (:borrowed? book)))
```

두 `available?` 함수는 이름은 같지만 의미가 완전히 다릅니다. 만약 Clojure에 네임스페이스라는 개념이 없다면, 이 두 함수는 같은 이름 공간 안에서 서로를 덮어써버릴 것입니다. 네임스페이스는 이런 충돌을 막아줍니다. 서점 관련 코드는 `bookstore.inventory` 네임스페이스에, 도서관 관련 코드는 `library.catalog` 네임스페이스에 넣어두면, 두 `available?` 함수는 각각 `bookstore.inventory/available?`과 `library.catalog/available?`라는 서로 다른 정규 이름을 가지게 되어 절대 충돌하지 않습니다.

즉 네임스페이스는 다음 두 가지 역할을 합니다.

1. **이름 충돌 방지.** 서로 다른 네임스페이스에 속한 같은 이름의 심볼은 완전히 별개로 취급됩니다.
2. **논리적 코드 구성.** 관련 있는 함수와 데이터를 하나의 네임스페이스로 묶어서, 코드의 역할과 경계를 명확히 드러냅니다.

## ns 선언: 네임스페이스 정의하기

실제 프로젝트에서는 파일 하나가 보통 네임스페이스 하나에 대응합니다. 파일의 맨 위에 `ns` 매크로로 그 파일이 어떤 네임스페이스에 속하는지 선언합니다.

```clojure
(ns bookstore.inventory)

(defn available? [book]
  (> (:stock book) 0))

(defn low-stock? [book]
  (< (:stock book) 5))
```

이 파일을 로드하면, `available?`과 `low-stock?`은 `bookstore.inventory` 네임스페이스에 속하게 됩니다. 다른 코드에서 이 함수들을 쓰려면 `bookstore.inventory/available?`처럼 정규 이름으로 접근하거나, 뒤에서 설명할 `require`를 사용해야 합니다.

### 네임스페이스 이름과 파일 경로의 관계

Clojure에서는 네임스페이스 이름과 파일이 저장되는 경로가 정해진 규칙으로 대응됩니다. 점(`.`)은 디렉터리 구분자로, 하이픈(`-`)은 밑줄(`_`)로 바꾸어 파일 경로를 만듭니다.

| 네임스페이스 이름 | 대응하는 파일 경로 |
|---|---|
| `bookstore.inventory` | `bookstore/inventory.clj` |
| `bookstore.core` | `bookstore/core.clj` |
| `my-app.util-belt` | `my_app/util_belt.clj` |

이 규칙은 Clojure가 `require`로 어떤 네임스페이스를 불러오라는 요청을 받았을 때, 클래스패스(classpath)에서 해당 파일을 자동으로 찾아낼 수 있게 해주는 약속입니다. 규칙을 어기면(예: 네임스페이스는 `my-app.core`인데 파일명이 `myapp/core.clj`라면) Clojure는 파일을 찾지 못해 오류를 냅니다.

2장에서 다룬 프로젝트 구조를 다시 떠올려보면, 보통 `src/` 디렉터리 아래에 이런 규칙에 따라 파일들이 정리됩니다.

```
my-app/
├── deps.edn
└── src/
    └── my_app/
        ├── core.clj
        ├── util.clj
        └── db/
            └── connection.clj
```

`src/my_app/core.clj` 파일은 `(ns my-app.core)`로 시작하고, `src/my_app/db/connection.clj` 파일은 `(ns my-app.db.connection)`으로 시작하는 식입니다.

## require: 다른 네임스페이스 불러오기

한 네임스페이스에서 다른 네임스페이스에 정의된 함수를 쓰고 싶다면 `require`를 사용합니다. 보통은 `ns` 선언 안에 `:require` 절로 함께 적습니다.

먼저 두 개의 네임스페이스를 정의해봅시다.

```clojure
;; src/bookstore/inventory.clj
(ns bookstore.inventory)

(defn available? [book]
  (> (:stock book) 0))

(defn restock [book amount]
  (update book :stock + amount))
```

```clojure
;; src/bookstore/core.clj
(ns bookstore.core
  (:require [bookstore.inventory :as inv]))

(def sample-book {:title "클로저 입문" :stock 0})

(defn describe [book]
  (if (inv/available? book)
    (str (:title book) "은(는) 구매 가능합니다.")
    (str (:title book) "은(는) 품절입니다.")))
```

`bookstore.core`에서는 `(:require [bookstore.inventory :as inv])`라고 선언했습니다. 이 선언은 두 가지 일을 합니다.

1. `bookstore.inventory` 네임스페이스를 로드합니다(아직 로드되지 않았다면).
2. `inv`라는 짧은 별칭(alias)을 통해 그 네임스페이스의 함수들에 접근할 수 있게 해줍니다.

이제 `bookstore.core` 안에서는 `bookstore.inventory/available?`이라는 긴 이름 대신 `inv/available?`이라고 짧게 쓸 수 있습니다.

```clojure
(describe sample-book)
;; => "클로저 입문은(는) 품절입니다."

(describe (inv/restock sample-book 3))
;; => "클로저 입문은(는) 구매 가능합니다."
```

### :as로 별칭 붙이기

`:as`는 불러온 네임스페이스에 짧은 별칭을 붙여주는 옵션입니다. 실전 코드에서는 네임스페이스 이름이 `company.project.module.submodule`처럼 길어지는 경우가 흔하기 때문에, 관용적으로 짧고 뜻이 통하는 별칭을 붙여서 사용합니다.

```clojure
(ns bookstore.core
  (:require [bookstore.inventory :as inv]
            [bookstore.pricing :as pricing]
            [clojure.string :as str]))

(defn summary [book]
  (str/upper-case (:title book)))
```

`clojure.string`은 Clojure 표준 라이브러리에서 문자열 처리 함수들을 모아둔 네임스페이스입니다. 관용적으로 `str`이라는 별칭을 붙여 사용합니다. 여러 네임스페이스를 불러올 때는 이렇게 `:require` 벡터 안에 각 네임스페이스를 한 줄씩 나열하는 것이 일반적인 스타일입니다.

### REPL에서 즉석으로 require하기

파일이 아니라 REPL에서 실험할 때는 `ns` 선언 없이 바로 `require`를 호출할 수도 있습니다.

```clojure
(require '[clojure.string :as str])

(str/join ", " ["사과" "바나나" "체리"])
;; => "사과, 바나나, 체리"
```

REPL에서 이미 불러온 네임스페이스의 코드를 수정한 뒤 다시 반영하고 싶다면 `:reload` 옵션을 사용합니다.

```clojure
(require '[bookstore.inventory :as inv] :reload)
```

### :refer로 심볼을 직접 노출하기

`:refer`를 사용하면 별칭 없이, 마치 현재 네임스페이스에 정의된 것처럼 특정 함수 이름을 직접 쓸 수 있습니다.

```clojure
(ns bookstore.core
  (:require [bookstore.inventory :refer [available? restock]]))

(defn describe [book]
  (if (available? book)          ;; inv/available? 대신 그냥 available?
    "구매 가능"
    "품절"))
```

`:refer [available? restock]`은 딱 지정한 두 심볼만 현재 네임스페이스로 끌어옵니다. 편리해 보이지만, 프로젝트가 커질수록 `:refer`를 남용하면 이 함수가 정확히 어느 네임스페이스에서 왔는지 코드만 보고는 알기 어려워지는 문제가 생깁니다. 예를 들어 `available?`이라는 이름이 여러 네임스페이스에 흩어져 있다면, 지금 쓰고 있는 `available?`이 어느 것인지 파일을 오가며 찾아야 할 수도 있습니다.

이런 이유로 실전에서는 다음과 같은 관례를 따르는 경우가 많습니다.

- 자주 쓰고 이름이 명확한 소수의 핵심 함수만 `:refer`로 가져온다.
- 그 외에는 `:as`로 별칭을 붙여서, `inv/available?`처럼 출처가 드러나게 쓴다.
- 테스트 코드에서는 `clojure.test`의 `deftest`, `is`, `testing` 같은 함수를 `:refer :all`로 통째로 가져오는 것이 관례적으로 널리 허용됩니다(17장 "테스트 작성"에서 다시 다룹니다).

```clojure
;; 테스트 파일에서 흔히 보는 패턴 (17장에서 자세히)
(ns bookstore.core-test
  (:require [clojure.test :refer :all]
            [bookstore.core :as core]))
```

일반 애플리케이션 코드에서 `:refer :all`로 네임스페이스 전체를 무분별하게 끌어오는 것은 좋은 습관이 아닙니다. 어떤 심볼이 어디서 왔는지 추적하기 어려워지고, 두 네임스페이스에 같은 이름의 함수가 있을 경우 미묘한 충돌이 생길 수 있기 때문입니다.

## use는 왜 권장되지 않는가

Clojure 초기 버전이나 오래된 예제 코드에서는 `require` 대신 `use`라는 함수를 종종 볼 수 있습니다.

```clojure
;; 오래된 스타일 — 권장하지 않음
(ns bookstore.core
  (:use bookstore.inventory))

(describe sample-book) ;; available?, restock 등이 전부 별칭 없이 노출됨
```

`use`는 사실상 `:refer :all`을 기본값으로 하는 `require`와 비슷하게 동작합니다. 즉 불러온 네임스페이스의 모든 공개 심볼을 별칭 없이 현재 네임스페이스에 쏟아붓습니다. 문제는 이렇게 되면 다음과 같은 상황이 생기기 쉽다는 점입니다.

- 여러 네임스페이스를 `use`로 가져왔는데, 그중 두 곳에 같은 이름의 함수가 있다면 어느 쪽이 실제로 쓰이는지 코드만 봐서는 알 수 없습니다.
- 새로운 버전의 라이브러리가 새 함수를 추가했는데, 그 이름이 하필 내가 이미 쓰고 있던 이름과 겹치면 코드가 예고 없이 깨질 수 있습니다.
- 코드를 읽는 사람 입장에서 `available?`이라는 함수가 어디서 정의되었는지 파악하기 위해 여러 파일을 뒤져야 합니다.

이런 이유로 현재 Clojure 커뮤니티에서는 `use` 사용을 권장하지 않으며, 대신 `require`에 `:as`(별칭)나 필요한 경우에 한해 제한적으로 `:refer`를 사용하는 것이 표준 관례로 자리 잡았습니다. 새 코드를 작성할 때는 `use`를 사용할 이유가 거의 없다고 생각해도 좋습니다.

## import: Java 클래스 가져오기

`require`가 다른 Clojure 네임스페이스를 불러오는 도구라면, `import`는 Java 클래스를 가져오는 도구입니다. Clojure는 JVM 위에서 동작하는 언어이기 때문에(1장에서 다룬 것처럼), Java의 방대한 클래스 라이브러리를 직접 활용할 수 있습니다. 이 주제는 15장 "Java 상호운용"에서 본격적으로 다루지만, 네임스페이스 선언과 밀접하게 관련되어 있으므로 기본 형태를 여기서 짚고 넘어갑니다.

```clojure
(ns bookstore.core
  (:import [java.time LocalDate]
           [java.util UUID]))

(defn today []
  (LocalDate/now))

(defn new-id []
  (str (UUID/randomUUID)))

(today)
;; => #object[java.time.LocalDate 0x... "2026-08-07"]

(new-id)
;; => "3fa2c1e0-9b7d-4a2e-9c1a-1234567890ab"
```

`:import`는 `:require`와 비슷한 자리에서 쓰이지만, 대상이 Clojure 네임스페이스가 아니라 Java 클래스라는 점이 다릅니다. `java.lang` 패키지에 속한 클래스(`String`, `Math` 등)는 별도의 `import` 없이 바로 사용할 수 있습니다.

```clojure
(Math/sqrt 16)
;; => 4.0

(.toUpperCase "hello")
;; => "HELLO"
```

`require`와 `import`를 함께 쓰는 것도 흔합니다.

```clojure
(ns bookstore.reports
  (:require [clojure.string :as str])
  (:import [java.time LocalDate]))
```

정리하면 다음과 같습니다.

| 도구 | 대상 | 용도 |
|---|---|---|
| `require` | Clojure 네임스페이스 | 다른 `.clj` 파일에 정의된 코드 불러오기 |
| `import` | Java 클래스 | JVM 클래스 라이브러리 활용하기 |
| `use` | Clojure 네임스페이스 | (권장하지 않음) `require` + 전체 `:refer` |

## 여러 네임스페이스로 프로젝트 구성하기

이제 배운 내용을 종합해서, 작은 규모지만 여러 네임스페이스로 나뉜 프로젝트 예제를 만들어보겠습니다. "할 일 목록" 애플리케이션을 다음과 같이 세 개의 네임스페이스로 나눈다고 가정합시다.

```
todo-app/
├── deps.edn
└── src/
    └── todo_app/
        ├── core.clj      ;; 진입점, 조합 역할
        ├── task.clj      ;; 할 일 하나에 대한 로직
        └── report.clj    ;; 통계와 요약 출력
```

**`src/todo_app/task.clj`** — 할 일 하나를 다루는 순수한 로직을 담당합니다.

```clojure
(ns todo-app.task)

(defn make-task [title]
  {:title title :done? false})

(defn complete [task]
  (assoc task :done? true))

(defn done? [task]
  (:done? task))
```

**`src/todo_app/report.clj`** — 여러 할 일에 대한 통계를 계산합니다. `task` 네임스페이스에 정의된 `done?`을 가져다 씁니다.

```clojure
(ns todo-app.report
  (:require [todo-app.task :as task]))

(defn count-done [tasks]
  (count (filter task/done? tasks)))

(defn summary [tasks]
  (str (count-done tasks) " / " (count tasks) " 완료"))
```

**`src/todo_app/core.clj`** — 두 네임스페이스를 조합해서 전체 흐름을 구성하는 진입점입니다.

```clojure
(ns todo-app.core
  (:require [todo-app.task :as task]
            [todo-app.report :as report]))

(defn -main [& args]
  (let [tasks [(task/make-task "장보기")
               (task/complete (task/make-task "청소하기"))
               (task/make-task "책 읽기")]]
    (println (report/summary tasks))))
```

이 구조에서 각 네임스페이스는 명확한 책임을 하나씩 맡고 있습니다.

- `todo-app.task`는 할 일 하나의 개념과 동작을 정의합니다. 다른 어떤 네임스페이스에도 의존하지 않는 가장 기초적인 계층입니다.
- `todo-app.report`는 `todo-app.task`에 의존하여, 여러 할 일을 모아 통계를 냅니다.
- `todo-app.core`는 `todo-app.task`와 `todo-app.report`를 모두 가져와 실제 프로그램의 흐름을 조립합니다.

이렇게 의존 방향이 한쪽으로만 흐르도록(`core` → `report` → `task`) 설계하면, 코드를 이해하고 테스트하기가 훨씬 쉬워집니다. `todo-app.task`만 따로 테스트하고 싶다면 다른 네임스페이스를 전혀 신경 쓰지 않고 독립적으로 검증할 수 있습니다. 이 원칙은 18장 "좋은 Clojure 코드 작성 습관"에서 다시 강조할 내용이기도 합니다.

REPL에서 이 프로젝트를 확인하려면 다음과 같이 진입점 네임스페이스를 불러와서 함수를 직접 호출해볼 수 있습니다.

```clojure
(require '[todo-app.core :as core])

(core/-main)
;; 1 / 3 완료
```

### 순환 의존을 피하기

네임스페이스를 나눌 때 반드시 주의해야 할 규칙이 하나 있습니다. **네임스페이스 A가 B를 require하는데, B가 다시 A를 require하는 순환 구조는 만들 수 없습니다.** Clojure는 네임스페이스를 로드할 때 이런 순환을 감지하면 오류를 냅니다.

```clojure
;; a.clj
(ns a
  (:require [b :as b]))

;; b.clj
(ns b
  (:require [a :as a])) ;; 오류: 순환 의존
```

순환 의존이 생겼다는 것은 대개 두 네임스페이스의 책임 구분이 명확하지 않다는 신호입니다. 이런 경우 두 네임스페이스가 공통으로 필요로 하는 부분을 제3의 네임스페이스로 뽑아내는 방식으로 해결하는 것이 일반적입니다. 위에서 본 할 일 목록 예제처럼 의존 방향이 한 방향으로만 흐르도록(`core` → `report` → `task`) 설계하면 이런 문제 자체를 피할 수 있습니다.

## in-ns와 현재 네임스페이스 확인하기

REPL을 사용하다 보면 지금 내가 어느 네임스페이스에 들어와 있는지 확인하거나, 다른 네임스페이스로 옮겨가고 싶을 때가 있습니다. `*ns*`는 현재 네임스페이스를 가리키는 특수 변수이고, `in-ns`는 네임스페이스를 전환하는 함수입니다.

```clojure
user=> *ns*
#object[clojure.lang.Namespace 0x... "user"]

user=> (in-ns 'bookstore.core)
#object[clojure.lang.Namespace 0x... "bookstore.core"]

bookstore.core=> *ns*
#object[clojure.lang.Namespace 0x... "bookstore.core"]
```

REPL 프롬프트 자체가 `user=>`에서 `bookstore.core=>`로 바뀐 것을 볼 수 있습니다. 실전 개발에서는 `in-ns`를 직접 호출하기보다, 대부분의 에디터/REPL 통합 도구(2장에서 소개한 개발 환경)가 지금 열려 있는 파일의 네임스페이스로 자동으로 전환해주는 기능을 제공합니다.

## 요약

- 네임스페이스(namespace)는 심볼들을 담는 독립된 이름 공간으로, 이름 충돌을 막고 관련 코드를 논리적으로 묶어주는 역할을 합니다.
- 파일 맨 위의 `(ns 이름)` 선언으로 그 파일이 속할 네임스페이스를 정하며, 네임스페이스 이름은 정해진 규칙에 따라 파일 경로와 대응됩니다(점은 디렉터리, 하이픈은 밑줄).
- `require`는 다른 Clojure 네임스페이스를 불러올 때 사용하며, `:as`로 짧은 별칭을 붙이거나 `:refer`로 특정 심볼을 직접 노출할 수 있습니다.
- `:refer`는 편리하지만 남용하면 심볼의 출처를 추적하기 어려워지므로, 일반적으로는 `:as` 별칭 사용을 우선하고 `:refer`는 제한적으로 사용합니다.
- `use`는 사실상 전체를 `:refer`하는 옛 방식으로, 이름 충돌과 추적 어려움 때문에 현재는 권장되지 않습니다.
- `import`는 Java 클래스를 가져올 때 사용하며, `require`와는 대상(네임스페이스 vs 클래스)이 다릅니다.
- 여러 네임스페이스로 프로젝트를 구성할 때는 의존 방향이 한쪽으로만 흐르도록 설계하는 것이 좋으며, 순환 의존은 Clojure에서 허용되지 않습니다.

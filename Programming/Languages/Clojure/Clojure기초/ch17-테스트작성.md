지금까지 우리는 REPL에서 함수를 하나씩 평가해 보며 "이 함수가 잘 동작하는가"를 눈으로 확인해왔습니다. 하지만 프로젝트가 커지고 함수 개수가 늘어나면, 사람이 매번 눈으로 확인하는 방식은 한계에 부딪힙니다. 어제는 잘 동작하던 함수가 오늘 다른 코드를 고치다가 조용히 깨질 수도 있습니다. 이런 문제를 막아주는 것이 바로 **테스트**입니다.

이 장에서는 Clojure에 기본으로 포함된 테스트 도구인 `clojure.test` 네임스페이스를 사용해 테스트를 작성하는 방법을 배웁니다. 그리고 왜 함수형 스타일로 작성된 코드가 테스트하기에 특히 유리한지도 함께 살펴봅니다.

## 함수형 코드가 테스트하기 쉬운 이유

테스트를 작성하는 방법을 배우기 전에, 먼저 "테스트하기 쉬운 코드"란 무엇인지 생각해봅시다.

가장 테스트하기 쉬운 함수는 다음과 같은 성질을 가집니다.

- 같은 입력을 넣으면 항상 같은 출력이 나온다 (참조 투명성)
- 함수 바깥의 상태를 읽거나 바꾸지 않는다 (부작용이 없다)
- 데이터베이스, 파일, 네트워크 같은 외부 자원에 의존하지 않는다

이런 함수를 **순수 함수**라고 부릅니다. 순수 함수를 테스트하는 것은 매우 단순합니다. 입력값을 넣고, 결과값이 기대한 값과 같은지 비교하면 끝이기 때문입니다. 별도의 준비 작업(데이터베이스 초기화, 파일 생성, 네트워크 모킹 등)이 필요 없습니다.

```clojure
(defn 할인가 [원가 할인율]
  (- 원가 (* 원가 할인율)))

;; 테스트하기 아주 쉽다: 입력을 넣고 출력만 확인하면 된다
(할인가 10000 0.1) ;; => 9000.0
```

반대로 이런 함수를 생각해봅시다.

```clojure
(def 장바구니 (atom []))

(defn 담기! [상품]
  (swap! 장바구니 conj 상품)
  (println "담았습니다:" 상품))
```

이 함수는 전역 상태(`장바구니` 아톰)를 바꾸고, 콘솔에 출력까지 합니다. 이 함수를 테스트하려면 아톰의 상태를 미리 초기화하고, 호출 후에 아톰 내부를 들여다봐야 하고, 부수적으로 콘솔 출력까지 신경 써야 합니다. 게다가 테스트를 여러 번 실행하면 아톰에 값이 계속 쌓여서 테스트끼리 서로 영향을 주는 문제도 생깁니다.

9장에서 이야기한 불변성과 5장, 8장에서 다룬 순수 함수·고차 함수 스타일은 단순히 "이해하기 쉬운 코드"를 위한 것만이 아니라, 애초에 "검증하기 쉬운 코드"를 만들기 위한 설계이기도 합니다. Clojure로 프로그램을 작성할 때 흔히 권장되는 방식은, 계산 로직은 순수 함수로 최대한 많이 작성하고, 부작용(파일 읽기, 네트워크 호출, 상태 변경 등)은 프로그램의 가장자리(경계)에 얇게 모아두는 것입니다. 이렇게 하면 프로그램 로직의 대부분을 부작용 없이 테스트할 수 있습니다. 이 설계 원칙은 18장에서 다시 자세히 다룹니다.

## clojure.test 소개

Clojure는 별도의 라이브러리를 설치하지 않아도 기본으로 `clojure.test`라는 테스트 네임스페이스를 제공합니다. 10장에서 배운 네임스페이스 사용법 그대로, `require`로 불러와서 사용합니다.

```clojure
(ns 계산기.core-test
  (:require [clojure.test :refer [deftest is testing run-tests]]
            [계산기.core :refer [할인가]]))
```

`clojure.test`가 제공하는 핵심 요소는 세 가지입니다.

- `deftest`: 하나의 테스트 케이스(테스트 함수)를 정의
- `is`: 어떤 조건이 참인지 검사하는 단언(assertion)
- `testing`: 관련된 `is` 검사들을 묶어서 설명을 붙이는 그룹

### is: 가장 기본적인 단언

`is`는 뒤에 오는 식을 평가해서 그 값이 참이면 통과, 거짓이면 실패로 기록합니다.

```clojure
(is (= 4 (+ 2 2)))       ;; 통과
(is (= 5 (+ 2 2)))       ;; 실패: 기대값 5, 실제값 4
(is (true? (odd? 3)))    ;; 통과
```

`is`가 좋은 점은 실패했을 때 단순히 "실패"라고만 말하지 않는다는 것입니다. `(= 5 (+ 2 2))`처럼 `=` 비교식을 그대로 넣으면, 실패 메시지에 기대값과 실제값이 모두 출력되어서 무엇이 잘못되었는지 바로 알 수 있습니다.

`is`는 예외가 던져지는지 검사하는 용도로도 쓸 수 있습니다. 14장에서 다룬 예외 처리와 연결되는 부분입니다.

```clojure
(defn 나누기 [a b]
  (if (zero? b)
    (throw (ex-info "0으로 나눌 수 없습니다" {:a a :b b}))
    (/ a b)))

(is (thrown? Exception (나누기 10 0)))
```

`thrown-with-msg?`를 쓰면 예외 메시지가 특정 패턴과 일치하는지까지 확인할 수 있습니다.

```clojure
(is (thrown-with-msg? Exception #"0으로 나눌 수 없습니다" (나누기 10 0)))
```

### deftest: 테스트 케이스 묶기

여러 개의 `is`를 하나의 논리적 단위로 묶으려면 `deftest`를 사용합니다. `deftest`는 이름과 본문을 받아 테스트 함수를 정의합니다. 형태는 5장에서 배운 `defn`과 비슷하지만, 인자 목록이 없다는 점이 다릅니다.

```clojure
(deftest 할인가-테스트
  (is (= 9000.0 (할인가 10000 0.1)))
  (is (= 10000.0 (할인가 10000 0)))
  (is (= 0.0 (할인가 10000 1))))
```

### testing: 의미 있는 이름으로 그룹 짓기

테스트가 많아지면, 어떤 `is`가 무엇을 검증하는지 이름을 붙여서 정리하고 싶어집니다. `testing`은 문자열 설명과 함께 `is` 여러 개를 묶어줍니다. 실패했을 때 이 설명이 함께 출력되므로, 실패 지점을 훨씬 빨리 찾을 수 있습니다.

```clojure
(deftest 할인가-테스트
  (testing "정상적인 할인율"
    (is (= 9000.0 (할인가 10000 0.1)))
    (is (= 5000.0 (할인가 10000 0.5))))

  (testing "경계값"
    (is (= 10000.0 (할인가 10000 0)))
    (is (= 0.0 (할인가 10000 1)))))
```

`testing`은 중첩해서 사용할 수도 있어서, 큰 시나리오 안에 작은 상황들을 계층적으로 표현할 수 있습니다.

## REPL에서 테스트 실행하기

Clojure 테스트의 큰 장점 중 하나는 별도의 도구 없이 REPL에서 바로 실행해볼 수 있다는 점입니다. 2장에서 익힌 "코드를 작성하고 바로 평가해보는" 흐름을 테스트에도 그대로 적용할 수 있습니다.

가장 간단한 방법은 `deftest`로 정의한 테스트 함수를 그냥 직접 호출하는 것입니다.

```clojure
(할인가-테스트)
```

하지만 이렇게 호출하면 출력이 자세하지 않습니다. 제대로 된 결과 보고(몇 개를 검사했고 몇 개가 실패했는지 등)를 보려면 `run-tests`를 사용합니다.

```clojure
(require '[clojure.test :refer [run-tests]])

(run-tests)
```

`run-tests`는 인자 없이 호출하면 현재 네임스페이스에 있는 모든 `deftest`를 찾아 실행합니다. 특정 네임스페이스를 지정할 수도 있습니다.

```clojure
(run-tests '계산기.core-test)
```

여러 네임스페이스에 흩어진 테스트를 한 번에 실행하고 싶다면 `run-all-tests`를 사용합니다.

```clojure
(require '[clojure.test :refer [run-all-tests]])

(run-all-tests)
```

`run-all-tests`는 정규식을 인자로 받아 이름이 일치하는 네임스페이스만 골라서 실행할 수도 있습니다. 예를 들어 `(run-all-tests #"계산기\..*-test")`처럼 사용하면 `계산기` 아래에 있는 테스트 네임스페이스만 실행됩니다.

실행 결과는 다음과 같은 형태로 출력됩니다.

```
Testing 계산기.core-test

Ran 1 tests containing 4 assertions.
0 failures, 0 errors.
```

만약 테스트가 실패하면, 어느 `testing` 블록의 몇 번째 `is`에서 무엇을 기대했고 실제로 무엇이 나왔는지가 함께 출력됩니다.

```
FAIL in (할인가-테스트) (core_test.clj:8)
정상적인 할인율
expected: (= 5000.0 (할인가 10000 0.5))
  actual: (not (= 5000.0 4999.9))
```

이 흐름을 습관화하면, 함수를 하나 고칠 때마다 관련 테스트 네임스페이스에서 `run-tests`를 눌러보는 것만으로 "방금 수정이 다른 부분을 망가뜨리지 않았는지"를 즉시 확인할 수 있습니다. 이것이 REPL 중심 개발과 테스트가 자연스럽게 맞물리는 지점입니다.

## 예제: 문자열 유틸리티 함수 테스트하기

실제 예제로 연습해봅시다. 문자열을 다루는 간단한 유틸리티 함수 몇 개를 작성하고, 각각에 대한 테스트를 붙여보겠습니다.

```clojure
(ns 문자열유틸.core)

(defn 팰린드롬? [s]
  (let [정리된 (clojure.string/lower-case (clojure.string/replace s #"[^a-zA-Z0-9가-힣]" ""))]
    (= 정리된 (clojure.string/reverse 정리된))))

(defn 단어수 [s]
  (count (clojure.string/split (clojure.string/trim s) #"\s+")))

(defn 이니셜 [이름]
  (->> (clojure.string/split (clojure.string/trim 이름) #"\s+")
       (map first)
       (apply str)
       clojure.string/upper-case))
```

`이니셜` 함수에서 사용한 `->>`는 6장과 8장에서 다룬 스레딩 매크로입니다. 단어들을 나눈 뒤, 각 단어의 첫 글자를 뽑고, 이를 이어붙여 대문자로 바꾸는 흐름을 중첩 없이 표현하고 있습니다.

이제 이 함수들에 대한 테스트를 작성합니다. 관례상 테스트 네임스페이스 이름은 원본 네임스페이스 이름 뒤에 `-test`를 붙입니다. `문자열유틸.core`를 테스트한다면 `문자열유틸.core-test`가 됩니다.

```clojure
(ns 문자열유틸.core-test
  (:require [clojure.test :refer [deftest is testing]]
            [문자열유틸.core :refer [팰린드롬? 단어수 이니셜]]))

(deftest 팰린드롬-테스트
  (testing "참인 경우"
    (is (true? (팰린드롬? "level")))
    (is (true? (팰린드롬? "A man a plan a canal Panama"))))

  (testing "거짓인 경우"
    (is (false? (팰린드롬? "clojure")))))

(deftest 단어수-테스트
  (testing "기본적인 문장"
    (is (= 3 (단어수 "나는 밥을 먹는다"))))

  (testing "앞뒤 공백이 있는 경우"
    (is (= 2 (단어수 "  hello world  ")))))

(deftest 이니셜-테스트
  (testing "영문 이름"
    (is (= "JD" (이니셜 "John Doe"))))

  (testing "세 단어 이름"
    (is (= "AKL" (이니셜 "Amy Kate Lee")))))
```

이 테스트들을 REPL에서 로드한 뒤 `(run-tests)`를 호출하면 세 함수가 모두 올바르게 동작하는지 한 번에 확인할 수 있습니다. 만약 `이니셜` 함수를 리팩터링하다가 실수로 `upper-case`를 빼먹었다면, 테스트가 즉시 실패를 알려줄 것입니다.

```
FAIL in (이니셜-테스트) (core_test.clj:15)
영문 이름
expected: (= "JD" (이니셜 "John Doe"))
  actual: (not (= "JD" "jd"))
```

이처럼 테스트는 "내가 방금 고친 코드가 예전에 세워둔 약속을 여전히 지키고 있는가"를 자동으로 확인해주는 안전망 역할을 합니다.

## 예외적인 입력과 경계값도 함께 테스트하기

좋은 테스트는 정상적인 입력뿐 아니라 경계값과 예외적인 입력도 함께 검증합니다. 앞서 만든 `단어수` 함수를 예로 들면, 빈 문자열이 들어왔을 때 어떤 결과가 나오는지도 확인해볼 가치가 있습니다.

```clojure
(deftest 단어수-경계값-테스트
  (testing "빈 문자열"
    (is (= 1 (단어수 "")))))
```

이 테스트를 실행해보면 뜻밖에도 실패할 수 있습니다. `clojure.string/split`은 빈 문자열을 나누면 `[""]`라는, 빈 문자열 하나를 담은 벡터를 돌려주기 때문에 `단어수 ""`의 결과가 1이 됩니다. 이런 경계 사례는 코드를 눈으로만 볼 때는 놓치기 쉽지만, 테스트를 작성하는 과정에서 자연스럽게 드러납니다. 이렇게 테스트 작성 자체가 코드의 숨은 동작을 검토하는 좋은 계기가 되기도 합니다. 만약 실제 요구사항이 "빈 문자열의 단어 수는 0이어야 한다"는 것이라면, 이 실패는 버그를 미리 잡아낸 것이고, 함수를 다음과 같이 고쳐야 합니다.

```clojure
(defn 단어수 [s]
  (let [정리 (clojure.string/trim s)]
    (if (clojure.string/blank? 정리)
      0
      (count (clojure.string/split 정리 #"\s+")))))
```

## 테스트 조직과 관례

프로젝트가 커지면 테스트를 어디에, 어떻게 배치할지에 대한 관례를 따르는 것이 좋습니다.

- 소스 코드는 보통 `src/` 디렉터리 아래, 테스트 코드는 `test/` 디렉터리 아래에 둡니다. 두 디렉터리는 네임스페이스 경로 구조를 그대로 반영합니다. 예를 들어 `src/계산기/core.clj`에 대응하는 테스트는 `test/계산기/core_test.clj`에 둡니다.
- 테스트 네임스페이스 이름은 대상 네임스페이스 이름 뒤에 `-test`를 붙입니다.
- 하나의 `deftest`는 하나의 함수, 혹은 하나의 명확한 시나리오를 검증하는 정도의 크기로 유지하는 것이 좋습니다. 너무 많은 것을 한 테스트에 몰아넣으면 실패했을 때 원인을 찾기 어려워집니다.

## 준비와 정리가 필요할 때: use-fixtures

대부분의 순수 함수 테스트는 별도의 준비 작업이 필요 없지만, 16장에서 다룬 파일 입출력처럼 부작용이 있는 코드를 테스트할 때는 테스트 전후에 임시 파일을 만들고 지우는 등의 준비/정리 작업이 필요할 수 있습니다. 이럴 때 `use-fixtures`를 사용합니다.

```clojure
(ns 파일유틸.core-test
  (:require [clojure.test :refer [deftest is use-fixtures]]
            [clojure.java.io :as io]))

(def 임시파일 "test-temp.txt")

(defn 파일-준비 [테스트함수]
  (spit 임시파일 "테스트 내용")   ;; 테스트 실행 전 준비
  (테스트함수)                    ;; 실제 테스트 실행
  (io/delete-file 임시파일 true)) ;; 테스트 실행 후 정리

(use-fixtures :each 파일-준비)

(deftest 파일읽기-테스트
  (is (= "테스트 내용" (slurp 임시파일))))
```

`use-fixtures`의 `:each`는 각 `deftest`마다 픽스처 함수를 실행하라는 뜻이고, `:once`를 쓰면 해당 네임스페이스의 모든 테스트를 통틀어 한 번만 실행합니다. 다만 이런 픽스처가 자주 필요해진다면, 애초에 부작용이 있는 부분과 순수한 로직을 분리해서 순수한 부분만 더 많이 테스트할 수 있도록 설계를 다시 살펴보는 것도 좋은 방법입니다.

## 요약

- 함수형 스타일로 작성된 순수 함수는 입력과 출력의 관계가 명확하고 외부 상태에 의존하지 않기 때문에 테스트하기 쉽습니다. 부작용은 프로그램의 경계로 몰아두는 설계가 테스트 용이성과도 직결됩니다.
- `clojure.test`는 Clojure에 기본 포함된 테스트 도구로, `deftest`로 테스트 케이스를 정의하고, `is`로 개별 조건을 검사하고, `testing`으로 관련 검사들을 묶어 설명을 붙입니다.
- `is`는 `=` 비교뿐 아니라 `thrown?`, `thrown-with-msg?`를 통해 예외 발생 여부까지 검사할 수 있습니다.
- `run-tests`는 현재 네임스페이스(또는 지정한 네임스페이스)의 테스트를 실행하고, `run-all-tests`는 여러 네임스페이스의 테스트를 한 번에 실행합니다. REPL에서 코드를 수정할 때마다 관련 테스트를 다시 실행하는 습관을 들이면 회귀 오류를 빠르게 잡을 수 있습니다.
- 테스트 네임스페이스는 관례적으로 대상 네임스페이스 이름 뒤에 `-test`를 붙이고, 소스와 같은 디렉터리 구조를 `test/` 아래에 반영합니다.
- 부작용이 있는 코드를 테스트할 때는 `use-fixtures`로 준비와 정리 작업을 자동화할 수 있지만, 가능하다면 순수 로직과 부작용을 분리해 순수한 부분을 더 많이 테스트하는 편이 유지보수에 유리합니다.

## 연습문제

1. 5장에서 만들어본 함수(또는 아무 함수나) 하나를 골라, 정상적인 입력에 대한 테스트와 경계값(빈 컬렉션, 0, 음수 등)에 대한 테스트를 각각 `testing` 블록으로 나누어 작성해보세요.

2. 다음 함수에 대한 테스트를 작성하세요. 이 함수는 정수 리스트를 받아 짝수만 걸러서 제곱한 값의 합을 반환합니다.

   ```clojure
   (defn 짝수제곱합 [숫자들]
     (->> 숫자들
          (filter even?)
          (map #(* % %))
          (reduce + 0)))
   ```

   최소한 다음 상황을 포함해 테스트하세요: 짝수와 홀수가 섞인 경우, 짝수가 하나도 없는 경우, 빈 리스트인 경우.

3. 14장에서 다룬 `ex-info`와 `thrown-with-msg?`를 활용해서, 유효하지 않은 나이(음수)를 입력하면 예외를 던지는 `나이검증` 함수를 작성하고, 정상적인 나이와 잘못된 나이 각각에 대한 테스트를 작성해보세요.

4. 문자열유틸 예제의 `팰린드롬?` 함수에 숫자와 특수문자가 섞인 문자열("12321", "A1B1a!!") 테스트를 추가해보고, 함수가 기대대로 동작하는지 확인해보세요. 만약 실패한다면 함수를 어떻게 고쳐야 할지 생각해보세요.

5. `use-fixtures`를 사용해, 테스트 시작 전에 아톰을 초기값으로 리셋하고 테스트가 끝난 뒤에도 같은 초기값으로 되돌리는 픽스처를 작성해보세요. 그리고 왜 이런 방식보다 애초에 상태를 사용하지 않는 순수 함수로 로직을 작성하는 편이 나은지 스스로 설명해보세요.

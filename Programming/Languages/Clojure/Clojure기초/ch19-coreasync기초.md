# 19장. core.async 기초

---

13장에서 아톰, 레퍼런스, 에이전트로 "여러 흐름이 상태를 공유하는" 방법을 배웠습니다. 그런데 실전에서는
상태를 공유하는 것만으로는 부족하고, 서로 다른 실행 흐름이 값을 주고받으며 협력해야 하는 경우가
자주 있습니다. 예를 들어 한쪽에서는 데이터를 계속 생산하고, 다른 쪽에서는 그 데이터를 순서대로
소비해야 하는 상황이 그렇습니다. `core.async`는 채널(channel)이라는 개념을 중심으로 이런 협력을
표현하는 라이브러리입니다.

`core.async`는 Clojure의 핵심 문법이 아니라 별도로 추가해야 하는 라이브러리라는 점을 먼저 짚고
넘어가겠습니다. `deps.edn`을 사용한다면 다음과 같이 의존성을 추가합니다.

```clojure
;; deps.edn
{:deps {org.clojure/core.async {:mvn/version "1.6.681"}}}
```

그리고 코드에서는 보통 다음과 같이 불러옵니다.

```clojure
(require '[clojure.core.async :as async :refer [chan go >! <! >!! <!! close! go-loop timeout alts! alts!!]])
```

## 채널: 값을 주고받는 통로

채널은 값을 넣고 뺄 수 있는 통로입니다. `chan`으로 채널을 만듭니다.

```clojure
;; => user=>
(def 신호채널 (chan))
```

채널에 값을 넣고 꺼내는 함수는 두 종류가 있습니다.

- `>!!`, `<!!` — 느낌표가 두 개인 버전은 일반 스레드에서 사용하며, 값을 넣거나 받을 수 있을
  때까지 그 스레드를 그대로 블록(block)합니다.
- `>!`, `<!` — 느낌표가 하나인 버전은 반드시 `go` 블록 안에서만 사용하며, 스레드를 블록하는 대신
  "파킹(park)"합니다. 이 차이는 바로 다음 절에서 설명합니다.

먼저 블로킹 버전으로 기본 동작을 확인해 보겠습니다.

```clojure
(def ch (chan))

;; 별도 스레드에서 값을 채널에 넣는다
(future (>!! ch "안녕하세요"))

;; 메인 스레드에서 값을 받는다 (값이 들어올 때까지 대기한다)
(println (<!! ch))
;; => 안녕하세요
```

`chan`으로 만든 채널은 기본적으로 버퍼가 없습니다. 즉 보내는 쪽은 받는 쪽이 준비될 때까지, 받는
쪽은 보내는 쪽이 값을 넣을 때까지 서로 기다립니다. 이는 마치 두 사람이 물건을 직접 손에서 손으로
건네주는 것과 비슷합니다.

## go 블록: 경량 프로세스

`go` 블록은 스레드를 새로 만드는 대신, 내부적으로 관리되는 스레드 풀 위에서 실행되는 가벼운 실행
단위입니다. `go` 블록 안에서 `<!`나 `>!`를 만나 값을 기다려야 하는 상황이 오면, 그 스레드를 붙잡고
있는 대신 "파킹"해서 다른 `go` 블록이 그 스레드를 쓸 수 있게 양보합니다. 그러다 값이 준비되면 다시
이어서 실행됩니다.

```clojure
(def ch (chan))

(go
  (println "생산자: 값을 준비합니다")
  (>! ch 42)
  (println "생산자: 값을 보냈습니다"))

(go
  (let [값 (<! ch)]
    (println "소비자: 받은 값은" 값)))
```

겉모습은 순차적인 코드처럼 보이지만, 실제로는 두 `go` 블록이 채널을 통해 값이 오갈 때까지 서로
기다리면서 협력하고 있습니다. 8장에서 배운 지연 시퀀스가 "값을 필요할 때 계산한다"는 개념이었다면,
`go` 블록과 채널은 "여러 실행 흐름이 값을 주고받는 시점을 조율한다"는 개념이라고 볼 수 있습니다.

아래 다이어그램은 생산자 `go` 블록이 채널에 값을 넣고, 소비자 `go` 블록이 그 값을 꺼내가는 흐름을
보여줍니다.

```text
   +-----------+           +------------------+           +-----------+
   |  생산자    |  >! ch 값  |    채널 (chan)     |  <! ch    |  소비자    |
   |  (go ...) | --------> | >! 로 넣고         | --------> |  (go ...) |
   +-----------+           | <! 로 꺼냄          |           +-----------+
                           +------------------+

   생산자가 값이 준비될 때까지, 소비자가 값을 받을 때까지
   서로 파킹(park)하며 기다린다
```

## 버퍼가 있는 채널과 채널 닫기

`chan`에 숫자를 넘기면 그만큼의 버퍼를 가진 채널을 만들 수 있습니다. 버퍼가 있으면, 버퍼가 가득
차기 전까지는 받는 쪽이 없어도 보내는 쪽이 곧바로 진행할 수 있습니다.

```clojure
(def 버퍼채널 (chan 3))  ;; 최대 3개까지 대기 가능

(go
  (dotimes [n 5]
    (>! 버퍼채널 n)
    (println "보냄:" n)))
```

채널을 다 쓰고 나면 `close!`로 닫을 수 있습니다. 닫힌 채널에서 값을 받으면, 남아 있던 값을 모두
받은 뒤에는 `nil`이 돌아옵니다. 이 성질을 이용하면 `go-loop`로 채널의 값을 끝까지 소비하는 관용구를
만들 수 있습니다.

```clojure
(def ch (chan))

(go
  (dotimes [n 3]
    (>! ch n))
  (close! ch))

(go-loop []
  (when-let [값 (<! ch)]
    (println "받은 값:" 값)
    (recur)))
;; => 받은 값: 0
;;    받은 값: 1
;;    받은 값: 2
```

`go-loop`는 7장에서 배운 `loop`/`recur`를 `go` 블록 안에서 쓸 수 있게 해주는 매크로입니다. 채널이
닫혀서 `<!`가 `nil`을 반환하면 `when-let` 조건이 거짓이 되어 반복이 자연스럽게 끝납니다.

## alts!로 여러 채널 동시에 기다리기

`alts!!`(또는 `go` 블록 안에서는 `alts!`)를 사용하면 여러 채널 중 먼저 값이 준비되는 채널을 골라
처리할 수 있습니다.

```clojure
(def 채널-a (chan))
(def 채널-b (chan))

(future (Thread/sleep 100) (>!! 채널-a "A에서 옴"))
(future (Thread/sleep 50) (>!! 채널-b "B에서 옴"))

(let [[값 채널] (alts!! [채널-a 채널-b])]
  (println "먼저 도착한 값:" 값 "(채널:" 채널 ")"))
;; => 먼저 도착한 값: B에서 옴 (채널: ...)
```

`timeout` 함수는 지정한 시간이 지나면 자동으로 닫히는 채널을 만들어 주는데, 이를 `alts!!`와
조합하면 "특정 시간 안에 응답이 없으면 포기한다"는 타임아웃 패턴을 표현할 수 있습니다.

```clojure
(let [[값 채널] (alts!! [응답채널 (timeout 1000)])]
  (if (= 채널 응답채널)
    (println "응답 도착:" 값)
    (println "1초 안에 응답이 없어 포기합니다")))
```

## 아톰/레퍼런스/에이전트와 core.async의 차이

13장에서 배운 도구들과 이 장에서 배운 채널은 서로 다른 문제를 풉니다.

| 도구 | 무엇을 위한 것인가 |
|---|---|
| 아톰 | 여러 흐름이 하나의 값을 공유하고, 각자 원자적으로 갱신해야 할 때 |
| 레퍼런스(ref)와 STM | 여러 상태를 동시에, 일관되게 갱신해야 할 때 |
| 에이전트 | 상태 갱신을 비동기로 처리하되 결과를 굳이 즉시 알 필요가 없을 때 |
| 채널(core.async) | 서로 다른 실행 흐름이 값을 "주고받으며" 순서를 조율해야 할 때 |

즉 아톰과 레퍼런스는 "공유된 상태"에 초점을 맞추고, 채널은 "흐름 사이의 통신"에 초점을 맞춥니다.
데이터를 생산하는 쪽과 소비하는 쪽이 명확히 구분되는 파이프라인 형태의 문제라면 채널이 더 자연스러운
경우가 많습니다.

## 언제 core.async를 쓰는가

`core.async`는 강력하지만, 모든 동시성 문제에 필요한 것은 아닙니다.

- 단순히 "오래 걸리는 작업을 백그라운드에서 실행하고 결과만 나중에 받으면 되는" 경우라면
  `future`나 `promise`만으로 충분합니다.
- 여러 단계를 거치는 데이터 파이프라인을 구성하거나, 콜백을 겹겹이 쌓아야 하는 이벤트 기반 로직을
  순차적인 코드처럼 표현하고 싶을 때 `core.async`가 진가를 발휘합니다.
- 채널과 `go` 블록을 남용하면 오히려 어떤 값이 언제 어디서 오가는지 추적하기 어려운 코드가 될 수
  있습니다. 먼저 "이 문제가 정말 여러 흐름 간의 통신 문제인가"를 자문해 보고 도입하는 것이 좋습니다.

## 요약

- `core.async`는 채널(channel)을 통해 서로 다른 실행 흐름이 값을 주고받게 해주는 별도의 라이브러리다.
- `>!!`/`<!!`는 일반 스레드에서 채널을 블로킹 방식으로 사용하고, `>!`/`<!`는 `go` 블록 안에서
  스레드를 파킹하는 방식으로 사용한다.
- `go` 블록은 실제 스레드를 점유하지 않는 경량 실행 단위로, 순차적인 코드처럼 보이는 형태로
  비동기 로직을 표현할 수 있게 해준다.
- 채널은 버퍼를 가질 수 있고, `close!`로 닫을 수 있으며, 닫힌 채널에서 값을 받으면 결국 `nil`이
  돌아온다. `go-loop`와 `when-let`을 조합하면 채널을 끝까지 소비하는 관용구를 만들 수 있다.
- `alts!`/`alts!!`로 여러 채널 중 먼저 준비되는 값을 처리할 수 있고, `timeout` 채널과 조합하면
  타임아웃 패턴을 만들 수 있다.
- 아톰/레퍼런스/에이전트는 "상태 공유", 채널은 "흐름 간 통신"에 초점을 맞춘 서로 다른 도구다.

## 연습문제

1. 버퍼가 없는 채널 하나를 만들고, `future`와 `>!!`로 값을 보내는 쪽과 `<!!`로 받는 쪽을 각각
   작성해 동작을 확인해 보세요.
2. `go`와 `go-loop`를 이용해, 1부터 5까지의 숫자를 채널에 순서대로 넣고 모두 소비한 뒤 채널을
   닫는 프로그램을 작성해 보세요.
3. 두 개의 채널을 만들고, 각각 다른 지연 시간 뒤에 값을 보내도록 한 다음 `alts!!`로 먼저 도착하는
   값을 받아 출력해 보세요.
4. `timeout` 채널과 `alts!!`를 조합해, 특정 채널에서 1초 안에 값이 오지 않으면 "시간 초과"를
   출력하는 코드를 작성해 보세요.
5. 아톰으로 해결하는 것이 자연스러운 문제와 채널로 해결하는 것이 자연스러운 문제를 각각 한 가지씩
   떠올려 보고, 왜 그렇게 생각하는지 설명해 보세요.

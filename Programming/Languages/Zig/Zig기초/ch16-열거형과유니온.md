# 16장. 열거형과 유니온

[◀ 이전: 15장. 메모리 할당자(Allocator)](ch15-메모리할당자.md) | [📖 목차](00-목차.md) | [다음: 17장. 빌드 시스템과 패키지 ▶](ch17-빌드시스템과패키지.md)


9장에서 구조체를 이용해 여러 개의 값을 하나로 묶는 방법을 배웠습니다. 구조체는 "이 값은 항상 이런 필드들을 동시에 가진다"는 상황에 알맞습니다. 하지만 현실의 데이터는 종종 "이 값은 여러 종류 중 정확히 하나에 해당한다"는 형태를 띱니다. 요일은 월요일부터 일요일 중 하나이고, 네트워크 응답은 성공 아니면 몇 가지 실패 유형 중 하나이며, 도형은 원이거나 사각형이거나 삼각형입니다. 이런 "여러 경우 중 하나"를 표현하기 위한 도구가 이 장에서 다룰 열거형(enum)과 유니온(union)입니다.

## 이 장에서 다루는 내용

- `enum`으로 정해진 값들의 집합을 표현하고, 특정 정수값을 지정하는 방법
- 9장에서 배운 구조체 메서드 문법을 열거형에도 그대로 적용하는 방법
- 순수 유니온(`union`)과 그 안전성 문제
- 태그된 유니온(`union(enum)`)으로 "여러 종류의 값을 하나의 타입으로" 안전하게 표현하는 방법
- 5장에서 배운 `switch` 문법으로 태그된 유니온을 분기 처리하는 관용적인 패턴

## 열거형(enum) 정의하기

열거형은 이름 붙인 값들의 유한한 집합을 정의합니다.

```zig
const Direction = enum {
    north,
    south,
    east,
    west,
};
```

`Direction` 타입의 값은 `.north`, `.south`, `.east`, `.west` 네 가지 중 하나뿐입니다. 값을 만들 때는 타입 이름을 생략하고 점(`.`)으로 시작하는 축약형을 쓸 수 있는데, 이는 9장에서 구조체 리터럴을 다룰 때 보았던 것과 같은 종류의 문맥 추론입니다.

```zig
const std = @import("std");

fn opposite(dir: Direction) Direction {
    return switch (dir) {
        .north => .south,
        .south => .north,
        .east => .west,
        .west => .east,
    };
}

pub fn main() void {
    const d: Direction = .north;
    std.debug.print("{}의 반대 방향은 {}\n", .{ d, opposite(d) });
}
```

`switch` 문으로 열거형 값을 분기하는 방식은 5장에서 배운 문법과 정확히 같습니다. 다만 열거형과 함께 쓸 때 특히 중요한 점이 하나 있습니다. Zig 컴파일러는 `switch`의 대상이 열거형일 때, 그 열거형이 가진 **모든** 값을 처리하는지 검사합니다. 위 예제에서 `.west` 분기를 빼먹으면 컴파일 오류가 발생합니다. 새로운 방향을 열거형에 추가했는데 이 `switch`를 고치지 않으면, 컴파일이 즉시 실패하며 놓친 부분을 알려줍니다. 열거형에 값을 추가할 때마다 관련된 모든 분기 처리를 컴파일러가 대신 점검해 준다는 뜻이며, 이는 열거형을 쓰는 가장 큰 이유 중 하나입니다.

모든 분기를 나열하고 싶지 않다면 `else` 분기를 추가해 나머지를 한꺼번에 처리할 수도 있지만, 그렇게 하면 나중에 값을 추가했을 때 컴파일러가 그 사실을 알려주지 못한다는 점을 기억해 두어야 합니다.

## 특정 정수값 지정하기

기본적으로 열거형의 각 값에는 0부터 시작하는 정수가 내부적으로 자동 부여됩니다. 하지만 파일 형식이나 네트워크 프로토콜처럼 특정 정수값이 이미 정해져 있는 경우도 많습니다. 이때는 열거형이 사용할 정수 타입과 각 값에 대응하는 정수를 직접 지정할 수 있습니다.

```zig
const HttpStatus = enum(u16) {
    ok = 200,
    not_found = 404,
    internal_error = 500,
};
```

`enum(u16)`은 "이 열거형은 내부적으로 `u16` 정수로 표현된다"는 뜻이고, `= 200`, `= 404`, `= 500`은 각 값에 대응하는 실제 정수를 지정합니다. 더 단순한 예로, 값 몇 개만 순서대로 매기고 싶을 때도 같은 문법을 씁니다.

```zig
const Level = enum(u8) {
    low = 1,
    medium = 2,
    high = 3,
};
```

열거형 값과 정수 사이를 오갈 때는 `@intFromEnum`과 `@enumFromInt`라는 빌트인 함수를 사용합니다.

```zig
const std = @import("std");

pub fn main() void {
    const status: HttpStatus = .not_found;
    const code = @intFromEnum(status);
    std.debug.print("상태 코드: {}\n", .{code}); // 404

    const back: HttpStatus = @enumFromInt(200);
    std.debug.print("{}\n", .{back}); // ok
}
```

`@intFromEnum(status)`는 열거형 값을 그에 대응하는 정수로 변환하고, `@enumFromInt(200)`은 반대로 정수를 열거형 값으로 변환합니다. 다만 `@enumFromInt`에 그 열거형이 갖고 있지 않은 정수값(예: `HttpStatus`에 없는 `999`)을 넘기면, 안전 검사가 활성화된 빌드에서는 런타임 패닉이 발생합니다. 정수값이 실제로 그 열거형에 속하는지 확신할 수 없다면, 값을 검증하는 로직을 별도로 두어야 합니다.

## 열거형에 메서드 추가하기

열거형도 구조체와 마찬가지로 자신만의 메서드를 가질 수 있습니다. 문법은 9장에서 본 구조체 메서드와 완전히 동일합니다. 첫 매개변수로 그 타입의 값을 받는 함수를 열거형 본문 안에 선언하면, `값.메서드이름()` 형태로 호출할 수 있습니다.

```zig
const std = @import("std");

const Direction = enum {
    north,
    south,
    east,
    west,

    fn opposite(self: Direction) Direction {
        return switch (self) {
            .north => .south,
            .south => .north,
            .east => .west,
            .west => .east,
        };
    }

    fn label(self: Direction) []const u8 {
        return switch (self) {
            .north => "북쪽",
            .south => "남쪽",
            .east => "동쪽",
            .west => "서쪽",
        };
    }
};

pub fn main() void {
    const d: Direction = .east;
    std.debug.print("{s}의 반대는 {s}입니다\n", .{ d.label(), d.opposite().label() });
}
```

앞서 만들었던 `opposite` 함수를 열거형 안으로 옮겨 `Direction.opposite`로 만들었습니다. 호출하는 쪽에서는 `d.opposite()`처럼 마치 다른 언어의 인스턴스 메서드를 부르듯 사용할 수 있지만, 실제로는 9장에서 설명한 것과 동일하게 `d.opposite()`가 `Direction.opposite(d)`로 풀어써지는 문법적 편의일 뿐입니다. 이 원리를 알고 있으면 열거형의 메서드도 구조체의 메서드와 다르지 않다는 사실이 자연스럽게 이해됩니다.

## 순수 유니온(union): 한 번에 한 필드만 유효하다

이제 "여러 종류 중 하나"를 표현하는 두 번째 도구인 유니온을 살펴봅니다. 유니온은 여러 필드를 선언하지만, 그 필드들이 메모리 공간을 공유합니다. 즉 어느 순간이든 그 값들 중 **하나의 필드만** 유효합니다.

```zig
const Number = union {
    int: i32,
    float: f32,
};
```

`Number` 타입의 값은 `int` 필드로 정수를 담을 수도 있고, `float` 필드로 실수를 담을 수도 있습니다. 하지만 구조체처럼 두 필드를 동시에 갖는 것이 아니라, 마지막으로 대입한 필드 하나만 유효합니다.

```zig
const std = @import("std");

pub fn main() void {
    var n = Number{ .int = 42 };
    std.debug.print("{}\n", .{n.int});

    n = Number{ .float = 3.14 };
    std.debug.print("{}\n", .{n.float});
}
```

이 코드는 정상적으로 동작합니다. `n.int`로 값을 읽을 때는 마지막으로 대입된 필드가 실제로 `int`였고, `n.float`로 읽을 때는 마지막으로 대입된 필드가 `float`였기 때문입니다.

문제는 순수 유니온에는 **지금 어떤 필드가 유효한지 스스로 기억하는 장치가 없다**는 점입니다. 아래처럼 마지막으로 대입한 필드와 다른 필드를 읽으면 어떻게 될까요?

```zig
var n = Number{ .int = 42 };
std.debug.print("{}\n", .{n.float}); // 위험: int로 대입했는데 float로 읽는다
```

이런 접근은 "안전 검사가 적용된 정의되지 않은 동작(safety-checked undefined behavior)"으로 분류됩니다. 즉 안전 검사가 켜진 빌드(디버그 빌드 등)에서는 런타임 패닉으로 이 실수를 잡아낼 수도 있지만, 안전 검사가 꺼진 최적화 빌드에서는 아무 경고 없이 `int`로 저장된 42라는 비트 패턴을 그대로 `f32`로 잘못 해석해 버립니다. 어느 필드가 유효한지는 프로그래머가 다른 수단(예: 별도의 `bool`이나 `enum` 변수)으로 스스로 기억하고 있어야 하며, 언어가 이를 대신 검증해주지 않습니다.

이런 위험 때문에 순수 유니온은 일반적인 애플리케이션 코드에서 자주 쓰이지 않습니다. 주로 C의 `union`과 메모리 구조를 그대로 맞춰야 하는 상호운용 코드(`extern union`)나, 성능이 극도로 중요해서 태그를 저장하는 비용조차 줄이고 싶은 아주 특수한 저수준 상황에서만 신중하게 사용합니다. 일반적인 "여러 종류 중 하나" 문제는 다음 절에서 다룰 태그된 유니온으로 푸는 것이 훨씬 안전합니다.

## 태그된 유니온(union(enum)): 안전하게 종류를 구분하기

순수 유니온의 문제는 결국 "지금 어떤 필드가 활성 상태인지 런타임에 알 방법이 없다"는 것이었습니다. `union(enum)`으로 선언하면 Zig가 이 정보를 자동으로 함께 저장해 줍니다. 이를 **태그된 유니온(tagged union)**이라고 부릅니다.

```zig
const Shape = union(enum) {
    circle: f32, // 반지름
    rectangle: struct { w: f32, h: f32 },
};
```

`Shape`는 원이거나 사각형입니다. 원일 때는 반지름 하나(`f32`)를 담고, 사각형일 때는 너비와 높이를 담은 구조체를 담습니다. `union(enum)`으로 선언했으므로, 이 값은 내부적으로 "지금 이 값은 `circle`인가 `rectangle`인가"를 나타내는 태그를 함께 들고 다닙니다. 값을 만들 때는 열거형과 똑같은 문법을 씁니다.

```zig
const std = @import("std");

pub fn main() void {
    const c = Shape{ .circle = 2.0 };
    const r = Shape{ .rectangle = .{ .w = 3.0, .h = 4.0 } };

    std.debug.print("{}\n", .{@as(std.meta.Tag(Shape), c)});
    std.debug.print("{}\n", .{@as(std.meta.Tag(Shape), r)});
}
```

`std.meta.Tag(Shape)`는 `Shape`가 내부적으로 사용하는 태그 열거형 타입을 얻어냅니다. 매번 이렇게 태그 타입을 직접 다룰 일은 많지 않지만, 이 예제는 태그된 유니온이 정말로 "지금 어떤 종류인지"를 값 안에 함께 가지고 다닌다는 사실을 보여줍니다.

## switch로 태그된 유니온 분기 처리하기

태그된 유니온을 다루는 가장 흔하고 관용적인 방법은 `switch`입니다. 5장에서 배운 `switch` 문법에, 각 분기에서 그 종류에 담긴 실제 데이터(payload)까지 함께 꺼내 쓰는 캡처 문법이 추가됩니다.

```zig
const std = @import("std");

const Shape = union(enum) {
    circle: f32,
    rectangle: struct { w: f32, h: f32 },
};

fn area(shape: Shape) f32 {
    return switch (shape) {
        .circle => |radius| std.math.pi * radius * radius,
        .rectangle => |rect| rect.w * rect.h,
    };
}

pub fn main() void {
    const shapes = [_]Shape{
        Shape{ .circle = 2.0 },
        Shape{ .rectangle = .{ .w = 3.0, .h = 4.0 } },
    };

    for (shapes) |s| {
        std.debug.print("넓이: {d}\n", .{area(s)});
    }
}
```

`.circle => |radius| ...`에서 `|radius|`는 이 분기가 실행될 때 `circle` 필드에 들어 있던 실제 값을 `radius`라는 이름으로 꺼내 쓰겠다는 뜻입니다. `.rectangle => |rect| ...`도 마찬가지로, 이 분기 안에서만 유효한 `rect`라는 이름으로 사각형의 너비와 높이를 담은 구조체에 접근합니다. 이 캡처 문법 덕분에 "지금 이 값이 원인지 사각형인지"와 "원이라면 반지름이 얼마인지, 사각형이라면 너비와 높이가 얼마인지"를 한 번의 `switch`로 동시에 알아낼 수 있습니다.

열거형과 마찬가지로, 태그된 유니온에 대한 `switch`도 컴파일러가 모든 종류를 다 처리했는지 검사합니다. 나중에 `Shape`에 `triangle` 종류를 추가하고 이 `switch`를 고치지 않으면, `area` 함수는 즉시 컴파일 오류를 냅니다. 여러 종류의 값을 하나의 타입으로 표현하면서도, 새로운 종류가 추가될 때 관련된 모든 처리 코드를 컴파일러가 빠짐없이 점검해 주는 이 조합이야말로 태그된 유니온이 자주 쓰이는 이유입니다.

## 유니온에도 메서드를 붙일 수 있다

열거형과 마찬가지로 태그된 유니온도 자신만의 메서드를 가질 수 있습니다. 앞서 별도 함수로 작성했던 `area`를 `Shape` 안으로 옮겨 보겠습니다.

```zig
const std = @import("std");

const Shape = union(enum) {
    circle: f32,
    rectangle: struct { w: f32, h: f32 },

    fn area(self: Shape) f32 {
        return switch (self) {
            .circle => |radius| std.math.pi * radius * radius,
            .rectangle => |rect| rect.w * rect.h,
        };
    }

    fn describe(self: Shape) []const u8 {
        return switch (self) {
            .circle => "원",
            .rectangle => "사각형",
        };
    }
};

pub fn main() void {
    const s = Shape{ .circle = 5.0 };
    std.debug.print("{s}의 넓이: {d}\n", .{ s.describe(), s.area() });
}
```

`describe` 메서드처럼 분기에서 payload가 필요 없다면 캡처 문법(`|radius|` 등)을 생략해도 됩니다. 이렇게 도형의 종류를 판단하는 로직과 각 종류가 어떤 데이터를 갖는지에 대한 정의를 `Shape` 타입 하나에 모아 두면, 도형을 다루는 코드 전체가 한곳에 정리되어 가독성이 높아집니다. 이는 9장에서 구조체에 메서드를 붙였던 이유와 정확히 같은 이유입니다.

## 요약

- `enum`은 이름 붙인 값들의 유한한 집합을 정의하며, `enum(u8) { a = 1, b = 2 }`처럼 내부 정수 타입과 각 값의 정수를 직접 지정할 수 있습니다.
- 열거형과 태그된 유니온에 대한 `switch`는 컴파일러가 모든 경우를 처리했는지 검사해 주므로, 새로운 값을 추가했을 때 놓친 분기를 즉시 알 수 있습니다.
- 열거형은 9장에서 배운 구조체 메서드와 똑같은 문법으로 메서드를 가질 수 있습니다(`값.메서드()` 형태로 호출).
- `union`(순수 유니온)은 한 번에 한 필드만 유효하며, 어떤 필드가 활성 상태인지 스스로 기억하지 않으므로 잘못된 필드를 읽으면 안전 검사가 적용된 정의되지 않은 동작으로 이어질 수 있습니다.
- `union(enum)`(태그된 유니온)은 활성 필드를 나타내는 태그를 함께 저장해서, 어떤 종류가 지금 담겨 있는지 런타임에 안전하게 알 수 있습니다.
- 태그된 유니온은 `switch (value) { .변형 => |payload| ... }` 형태로 분기하며, 각 종류가 서로 다른 데이터를 가질 수 있는 "여러 종류의 값을 하나의 타입으로" 표현하는 대표적인 패턴입니다.

## 연습문제

1. 요일을 나타내는 `Weekday` 열거형을 만들고, 그 요일이 주말인지 아닌지 판단하는 `is_weekend` 메서드를 추가해 보세요.
2. `enum(u8) { red = 1, green = 2, blue = 4 }`처럼 정수값을 지정한 열거형을 만들고, `@intFromEnum`과 `@enumFromInt`로 값과 정수를 오가며 출력해 보세요.
3. 순수 유니온에서 마지막으로 대입한 필드와 다른 필드를 읽었을 때 어떤 문제가 생길 수 있는지, 이 장의 내용을 바탕으로 설명해 보세요. 그리고 태그된 유니온을 쓰면 이 문제가 어떻게 해결되는지도 함께 적어 보세요.
4. `union(enum)`으로 `Command` 타입을 정의해 보세요. `move: struct { dx: i32, dy: i32 }`, `say: []const u8`, `quit` 세 가지 변형을 갖도록 하고, `switch`로 각 명령을 처리해 출력하는 함수 `execute(cmd: Command) void`를 작성해 보세요.
5. 3번 문제의 `Shape` 예제에 `triangle: struct { base: f32, height: f32 }` 변형을 추가하고, `area`와 `describe` 메서드가 컴파일되도록 각각의 `switch`에 새 분기를 채워 넣어 보세요.

# 1장. Zig란 무엇인가

[◀ 이전: 목차](00-목차.md) | [📖 목차](00-목차.md) | [다음: 2장. 첫 프로그램과 빌드 과정 ▶](ch02-첫프로그램과빌드과정.md)


프로그래밍 언어를 새로 배운다는 것은 단순히 문법을 외우는 일이 아닙니다. 그 언어가 어떤 문제를 풀기 위해 태어났는지, 어떤 가치를 우선시하는지를 이해하면 이후에 만나는 모든 문법과 규칙이 훨씬 자연스럽게 다가옵니다. Zig도 마찬가지입니다. 이 장에서는 Zig가 어떤 배경에서 만들어졌고, 어떤 철학을 가지고 설계되었는지 살펴본 다음, 이후 장에서 자세히 다룰 핵심 개념들을 짧게 미리 맛보겠습니다.

## Zig의 탄생 배경

Zig는 2016년 Andrew Kelley가 개인 프로젝트로 시작한 프로그래밍 언어입니다. 당시 그는 게임 개발과 오디오 소프트웨어 작업을 하면서 C 언어의 손에 익은 단순함은 좋아했지만, C가 가진 여러 약점들 때문에 불편을 겪고 있었습니다. 헤더 파일과 매크로로 얽힌 전처리기, 정의되지 않은 동작(undefined behavior)이 조용히 버그를 만들어내는 상황, 그리고 빌드 시스템을 구성할 때마다 반복되는 수고 같은 것들이었죠.

Andrew Kelley는 "C보다 나은 언어를 새로 만들면 어떨까"라는 질문에서 출발해 Zig를 설계하기 시작했습니다. Zig라는 이름 자체는 특별한 의미를 담은 약어가 아니라, 아직 다른 프로젝트에서 쓰이지 않은 짧고 발음하기 쉬운 이름을 고른 결과라고 알려져 있습니다.

Zig 프로젝트가 내세우는 목표는 명확합니다. C가 지금까지 시스템 프로그래밍 언어로서 차지해온 자리, 즉 운영체제 커널, 임베디드 소프트웨어, 게임 엔진, 각종 라이브러리처럼 하드웨어에 가깝고 성능이 중요한 영역을 대체할 수 있는 언어가 되는 것입니다. 다만 Zig는 C의 손자 세대 언어처럼 완전히 새로운 패러다임을 강요하지 않습니다. 오히려 "C가 잘하던 것은 그대로 두고, C가 못하던 것을 고친다"는 태도를 취합니다. 가비지 컬렉터도 없고, 거대한 런타임도 없으며, 컴파일된 결과물은 여전히 C와 크게 다르지 않은 저수준 실행 파일입니다. 그러면서도 컴파일 시점에 훨씬 많은 것을 검증하고, 실수를 줄여주는 장치를 곳곳에 마련해 두었습니다.

## 핵심 설계 철학

Zig를 이해하는 가장 좋은 방법은 이 언어가 반복해서 강조하는 몇 가지 원칙을 먼저 아는 것입니다. 이 원칙들은 이후 장에서 배우는 거의 모든 문법 뒤에 숨어 있는 이유이기도 합니다.

### 숨겨진 제어 흐름이 없다

"숨겨진 제어 흐름이 없다(no hidden control flow)"는 Zig의 코드를 눈으로 읽었을 때, 실제로 실행되는 순서와 분기를 그대로 예측할 수 있어야 한다는 원칙입니다.

예를 들어 C++이나 Java 같은 언어에는 예외(exception)라는 기능이 있습니다. 함수를 호출하는 코드만 보면 그 함수가 예외를 던질 수 있는지, 던진다면 어디서 잡히는지 한눈에 알기 어렵습니다. 호출 스택을 여러 단계 거슬러 올라가야 실제 제어 흐름을 파악할 수 있는 경우도 많습니다. 연산자 오버로딩도 비슷한 문제를 일으킵니다. `a + b`라는 코드가 단순한 정수 덧셈일 수도 있지만, 어떤 클래스에서는 숨겨진 함수 호출, 심지어 예외를 던지는 복잡한 로직으로 이어질 수도 있습니다.

Zig는 이런 종류의 "보이지 않는 분기"를 언어 차원에서 허용하지 않습니다. 예외가 없고, 연산자 오버로딩도 없습니다. 대신 실패할 수 있는 함수는 반환 타입에 그 사실을 명시적으로 드러냅니다.

```zig
const std = @import("std");

fn divide(a: i32, b: i32) !i32 {
    if (b == 0) return error.DivisionByZero;
    return @divTrunc(a, b);
}

pub fn main() void {
    const result = divide(10, 2) catch |err| {
        std.debug.print("오류 발생: {}\n", .{err});
        return;
    };
    std.debug.print("결과: {}\n", .{result});
}
```

위 코드에서 `divide` 함수의 반환 타입 `!i32`는 "이 함수는 실패할 수도 있고, 성공하면 `i32` 값을 돌려준다"는 뜻을 코드 자체로 표현합니다. 호출하는 쪽에서는 `catch`나 `try` 같은 키워드로 그 실패 가능성을 반드시 마주해야 합니다. 조용히 예외가 위로 튀어 올라가서 엉뚱한 곳에서 프로그램이 멈추는 일이 없습니다. 이 에러 처리 방식은 11장에서 훨씬 자세히 다룹니다.

### 숨겨진 메모리 할당이 없다

"숨겨진 메모리 할당이 없다(no hidden memory allocations)"는 Zig의 두 번째 핵심 원칙입니다. C++의 `std::vector`나 `std::string`, 혹은 다른 여러 언어의 표준 컬렉션들은 필요할 때 내부적으로 알아서 힙 메모리를 할당합니다. 편리하지만, 정확히 언제 어디서 할당이 일어나는지 코드만 보고는 알기 어렵고, 임베디드 환경처럼 메모리 할당 자체를 세심하게 통제해야 하는 상황에서는 오히려 걸림돌이 됩니다.

Zig의 표준 라이브러리는 메모리를 필요로 하는 모든 자료구조와 함수에 할당자(allocator)를 매개변수로 직접 전달하도록 설계되어 있습니다. 즉, 코드에 할당자가 등장하지 않으면 그 코드는 힙 메모리를 할당하지 않는다고 확신할 수 있습니다.

```zig
const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const allocator = gpa.allocator();

    var list = std.ArrayList(i32).init(allocator);
    defer list.deinit();

    try list.append(1);
    try list.append(2);
    try list.append(3);

    std.debug.print("합계: {}\n", .{list.items[0] + list.items[1] + list.items[2]});
}
```

`std.ArrayList(i32).init(allocator)` 코드를 보면 이 리스트가 메모리를 어디서 얻어오는지가 명확히 드러납니다. 함수를 호출하는 사람이 원한다면 스택 기반 할당자, 고정된 크기의 버퍼를 쓰는 할당자, 혹은 테스트용으로 할당 실패를 흉내내는 할당자 등 원하는 전략을 자유롭게 끼워넣을 수 있습니다. 할당자를 명시적으로 전달하는 이 패턴은 15장에서 다양한 할당자 종류와 함께 본격적으로 다룹니다.

### 전처리기와 매크로 대신 comptime

C에는 `#define`과 매크로로 대표되는 전처리기가 있습니다. 전처리기는 강력하지만, 텍스트를 그대로 치환하는 방식이라 디버깅이 어렵고 타입 검사도 제대로 이루어지지 않습니다. 매크로 하나가 잘못되면 에러 메시지가 원래 코드와 전혀 다른 곳을 가리키는 경험을 해본 사람이라면 이 불편함을 잘 알 것입니다.

Zig는 전처리기를 아예 두지 않는 대신, `comptime`이라는 기능으로 "컴파일 시점에 실행되는 코드"를 언어 자체에 통합했습니다. `comptime`으로 표시된 코드는 매크로처럼 텍스트를 치환하는 것이 아니라, 실제 Zig 코드가 컴파일하는 동안 그대로 실행되어 값을 계산하거나 타입을 만들어냅니다. 그 결과 매크로와 달리 완전한 타입 검사를 받고, 일반 함수와 똑같은 문법을 사용합니다.

## comptime 맛보기

`comptime`이 정확히 어떻게 동작하는지는 14장에서 하나의 장을 통째로 할애해 다룰 만큼 중요한 주제입니다. 여기서는 감을 잡을 수 있도록 짧은 예제 하나만 살펴보겠습니다.

```zig
const std = @import("std");

fn square(x: i32) i32 {
    return x * x;
}

pub fn main() void {
    // comptime 블록 안의 계산은 프로그램이 실행되기 전, 컴파일 도중에 끝납니다.
    const nine: i32 = comptime square(3);
    std.debug.print("9 = {}\n", .{nine});
}
```

`comptime square(3)` 부분은 프로그램이 실행될 때 계산되는 것이 아니라, 컴파일러가 소스 코드를 기계어로 바꾸는 그 순간에 미리 계산되어 버립니다. 실행 파일에는 이미 계산이 끝난 값 `9`만 남습니다.

`comptime`의 진짜 힘은 이렇게 값을 미리 계산하는 데서 끝나지 않습니다. Zig에서는 타입도 하나의 값처럼 다룰 수 있기 때문에, `comptime`을 이용해 여러 타입에 대해 똑같이 동작하는 함수를 매크로 없이도 작성할 수 있습니다.

```zig
fn maxOf(comptime T: type, a: T, b: T) T {
    return if (a > b) a else b;
}

pub fn main() void {
    const bigger_int = maxOf(i32, 3, 7);
    const bigger_float = maxOf(f64, 1.5, 0.9);
    _ = bigger_int;
    _ = bigger_float;
}
```

`maxOf` 함수는 `comptime T: type`이라는 매개변수를 받아서, 호출할 때 넘긴 타입에 맞춰 컴파일 시점에 전용 버전의 함수를 만들어냅니다. C++의 템플릿이나 다른 언어의 제네릭이 하는 일과 목적은 비슷하지만, Zig에서는 이 모든 과정이 별도의 문법 없이 우리가 이미 알고 있는 평범한 함수 문법으로 이루어진다는 점이 다릅니다. 이 기법은 14장에서 훨씬 다양한 예제와 함께 다시 등장합니다.

## C와의 상호운용성

시스템 프로그래밍 세계에는 이미 C로 작성된 수십 년 치의 라이브러리와 운영체제 API가 쌓여 있습니다. 새로운 언어가 이 생태계와 얼마나 잘 어울리는지는 실용성 면에서 아주 중요한 문제입니다. Zig는 이 부분을 처음부터 핵심 설계 목표로 삼았습니다.

Zig 컴파일러는 `@cImport`와 `@cInclude`라는 내장 함수를 통해 C 헤더 파일을 직접 읽어들여, 그 안에 선언된 함수와 타입을 Zig 코드에서 그대로 사용할 수 있게 해줍니다. 별도의 바인딩 코드를 손으로 작성하거나 코드 생성 도구를 돌릴 필요가 없습니다.

```zig
const c = @cImport({
    @cInclude("stdio.h");
});

pub fn main() void {
    _ = c.printf("Zig에서 C 함수를 직접 호출합니다: %d\n", @as(c_int, 42));
}
```

또한 Zig 컴파일러는 그 자체로 C/C++ 컴파일러 역할도 겸합니다. `zig cc`, `zig c++` 명령으로 기존 C 프로젝트를 컴파일할 수 있고, 이 덕분에 Zig 하나만 설치해도 크로스 컴파일 환경을 손쉽게 구성할 수 있습니다. 이러한 특징 때문에 Zig는 완전히 새로운 프로젝트를 처음부터 짤 때뿐만 아니라, 기존 C 코드베이스에 부분적으로 섞어 쓰는 방식으로도 많이 채택되고 있습니다.

## 다른 시스템 언어와 비교한 Zig의 포지셔닝

Zig가 어떤 위치에 있는지는 이미 널리 쓰이는 다른 시스템 프로그래밍 언어들과 비교해보면 더 뚜렷해집니다.

**C와 비교하면**, Zig는 C가 가진 단순함과 낮은 추상화 수준을 그대로 이어받으면서도, C가 오랫동안 안고 있던 문제들을 정면으로 고칩니다. 정수 오버플로우나 배열 경계를 벗어난 접근처럼 정의되지 않은 동작으로 이어지던 실수들을 디버그 빌드에서 즉시 잡아내고, 전처리기 없이도 조건부 컴파일과 코드 재사용을 `comptime`으로 해결합니다. 그러면서도 C처럼 런타임이 거의 없고, 결과물의 동작을 예측하기 쉽습니다.

**C++와 비교하면**, Zig는 훨씬 작고 단순한 언어를 지향합니다. C++는 수십 년에 걸쳐 클래스, 상속, 템플릿, 예외, 연산자 오버로딩, 여러 초기화 문법 등 기능이 계속 추가되어 왔고, 그만큼 학습 곡선도 가파르고 "이 코드가 실제로 무엇을 하는지" 파악하기 어려운 경우가 많습니다. Zig는 상속이나 예외, 연산자 오버로딩 같은 기능을 아예 두지 않는 대신, 구조체와 명시적인 에러 처리, `comptime`이라는 비교적 적은 수의 개념만으로 비슷한 문제들을 풀어냅니다. 이 내용은 9장(구조체)과 11장(에러 처리)에서 자세히 다룹니다.

**Rust와 비교하면**, 둘 다 "C보다 안전하면서도 빠른 시스템 언어"를 지향한다는 점에서 자주 함께 언급됩니다. 다만 접근 방식은 상당히 다릅니다. Rust는 소유권(ownership)과 빌림 검사기(borrow checker)라는 정교한 컴파일 시점 규칙을 통해 메모리 안전성을 컴파일러가 강하게 보장합니다. 그 대가로 문법과 타입 시스템이 비교적 복잡해지고, 컴파일러와 씨름하는 학습 기간이 필요합니다. Zig는 이런 강제적인 소유권 시스템을 두지 않습니다. 대신 할당자를 명시적으로 전달하는 관례, 디버그 빌드의 다양한 런타임 검사, 그리고 개발자가 직접 자원 해제를 챙기도록 돕는 `defer`/`errdefer` 같은 도구(12장에서 다룹니다)로 메모리 문제를 줄여나갑니다. 즉 Rust는 "컴파일러가 강제로 안전을 보장한다"는 쪽에, Zig는 "언어가 안전을 향한 도구는 제공하지만 최종 판단은 개발자에게 맡기고, 그 대신 코드를 최대한 단순하고 투명하게 유지한다"는 쪽에 더 가깝습니다.

정리하면, Zig는 C의 단순함과 실행 모델을 계승하면서, C++의 복잡함이나 Rust의 가파른 학습 곡선 없이도 더 안전하고 예측 가능한 코드를 작성할 수 있게 해주는 것을 목표로 하는 언어입니다. 이후 장들에서 이 목표가 실제 문법 하나하나에 어떻게 반영되어 있는지 차근차근 확인하게 될 것입니다.

## 요약

- Zig는 2016년 Andrew Kelley가 시작한 언어로, C를 대체할 수 있는 더 안전하고 명료한 시스템 프로그래밍 언어를 목표로 합니다.
- "숨겨진 제어 흐름이 없다"는 원칙에 따라 예외나 연산자 오버로딩 없이, 실패 가능성을 반환 타입으로 명시적으로 드러냅니다.
- "숨겨진 메모리 할당이 없다"는 원칙에 따라 메모리가 필요한 코드는 항상 할당자를 매개변수로 명시적으로 전달받습니다.
- 전처리기와 매크로 대신 `comptime`을 이용해 컴파일 시점 계산과 제네릭 코드를 일반 함수 문법으로 작성합니다.
- `@cImport`, `@cInclude`, `zig cc` 등을 통해 기존 C 코드와 매끄럽게 상호운용할 수 있습니다.
- Zig는 C의 단순함, C++의 강력함, Rust의 안전 지향이라는 스펙트럼 사이에서 "단순하고 투명한 코드"라는 자신만의 위치를 차지하고 있습니다.

## 연습문제

1. "숨겨진 제어 흐름이 없다"는 원칙이 실제로 어떤 문법적 선택으로 이어졌는지, 이 장에서 등장한 예시를 들어 설명해 보세요.
2. C++의 `std::vector`와 Zig의 `std.ArrayList`가 메모리를 다루는 방식에는 어떤 차이가 있는지 설명해 보세요.
3. `comptime`이 C의 매크로와 근본적으로 다른 점은 무엇인가요? 최소 두 가지를 들어보세요.
4. Zig, C++, Rust 세 언어가 메모리 안전성 문제를 각각 어떤 전략으로 다루는지 한두 문장씩 비교해 보세요.
5. 여러분이 시스템 프로그래밍 프로젝트를 새로 시작한다고 가정할 때, Zig를 선택할 만한 상황과 다른 언어를 선택할 만한 상황을 각각 하나씩 생각해 보세요.

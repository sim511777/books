## 이 장에서 다루는 내용

3장에서는 값을 담는 그릇인 변수와, 그 그릇의 종류를 정하는 자료형을 살펴보았습니다. 이제 그 값들을 조합해서 새로운 값을 만들어내는 도구인 연산자를 다룹니다. 연산자 자체는 다른 언어와 크게 다르지 않지만, Zig는 정수 오버플로를 다루는 태도에서 뚜렷한 개성을 보여줍니다. 이 장에서는 다음을 다룹니다.

- 산술, 비교, 논리 연산자
- 정수 오버플로에 대한 Zig의 태도와 디버그 빌드에서의 패닉
- 오버플로를 명시적으로 허용하는 wrapping 연산자
- 비트 연산자
- Zig에 연산자 오버로딩이 없는 이유와 그 철학적 배경

## 산술 연산자

기본적인 산술 연산자는 더하기(`+`), 빼기(`-`), 곱하기(`*`), 나누기(`/`), 나머지(`%`)입니다.

```zig
const std = @import("std");

pub fn main() void {
    const a: i32 = 17;
    const b: i32 = 5;

    const sum = a + b;
    const diff = a - b;
    const product = a * b;
    const quotient = @divTrunc(a, b);
    const remainder = @rem(a, b);

    std.debug.print("sum={d}, diff={d}, product={d}, quotient={d}, remainder={d}\n", .{
        sum, diff, product, quotient, remainder,
    });
}
```

정수 나누기와 나머지 연산에서 한 가지 눈여겨볼 점이 있습니다. 위 예제에서는 `/`와 `%` 대신 `@divTrunc`와 `@rem`이라는 빌트인 함수를 사용했습니다. 사실 정수에도 `/`와 `%`를 그대로 쓸 수 있지만, Zig는 나눗셈에 여러 가지 방식이 있다는 사실을 코드에 드러내는 것을 선호합니다. 예를 들어 피연산자에 음수가 섞여 있을 때 결과를 0을 향해 자를지(trunc), 음의 무한대를 향해 자를지(floor)에 따라 몫과 나머지가 달라질 수 있습니다. `@divTrunc`, `@divFloor`, `@divExact`, `@rem`, `@mod` 같은 빌트인 함수는 이 선택을 코드에서 명시적으로 표현하게 해 줍니다. 두 피연산자가 모두 양수인 일반적인 경우에는 `/`와 `%`를 그대로 사용해도 무방하며, 아래 예제처럼 자연스럽게 쓸 수 있습니다.

```zig
const std = @import("std");

pub fn main() void {
    const total_minutes: i32 = 135;
    const hours = @divTrunc(total_minutes, 60);
    const minutes = @rem(total_minutes, 60);

    std.debug.print("{d}시간 {d}분\n", .{ hours, minutes });
}
```

부동소수점 값에는 `/`가 일반적인 실수 나누기로 동작하며, 나눗셈의 방식을 고민할 필요가 없습니다.

```zig
const std = @import("std");

pub fn main() void {
    const distance: f64 = 42.195;
    const time: f64 = 3.5;
    const pace = distance / time;

    std.debug.print("페이스: {d}\n", .{pace});
}
```

## 비교 연산자

두 값을 비교하는 연산자는 같음(`==`), 다름(`!=`), 초과(`>`), 미만(`<`), 이상(`>=`), 이하(`<=`)이며, 결과는 항상 `bool` 타입입니다.

```zig
const std = @import("std");

pub fn main() void {
    const score: i32 = 85;
    const passing_line: i32 = 60;

    const is_passed = score >= passing_line;
    const is_perfect = score == 100;

    std.debug.print("passed={}, perfect={}\n", .{ is_passed, is_perfect });
}
```

비교 연산자는 서로 같은 타입의 값 사이에서만 사용할 수 있습니다. 예를 들어 `u8` 값과 `i32` 값을 직접 `==`로 비교하려고 하면 컴파일 오류가 발생합니다. 이는 3장에서 본 것처럼 Zig가 타입 간의 암묵적 변환을 최소화하기 때문입니다. 서로 다른 정수 타입을 비교하고 싶다면 `@as`나 `@intCast` 같은 빌트인 함수로 타입을 명시적으로 맞춰 주어야 하며, 이 내용은 8장에서 좀 더 자세히 다룹니다.

## 논리 연산자

논리 연산자는 `bool` 값을 다루며, C 계열 언어의 `&&`, `||`와 달리 `and`, `or` 키워드를 사용합니다. 논리 부정은 `!`입니다.

```zig
const std = @import("std");

pub fn main() void {
    const age: i32 = 25;
    const has_ticket = true;

    const can_enter = (age >= 18) and has_ticket;
    const should_alert = (age < 0) or (age > 150);

    std.debug.print("can_enter={}, should_alert={}\n", .{ can_enter, should_alert });
}
```

`and`와 `or`는 단축 평가(short-circuit evaluation)를 수행합니다. `a and b`에서 `a`가 `false`이면 `b`는 평가되지 않고 즉시 `false`가 반환되며, `a or b`에서 `a`가 `true`이면 `b`는 평가되지 않고 즉시 `true`가 반환됩니다. 이 특성은 다음처럼 앞의 조건이 뒤의 조건을 안전하게 지켜주는 패턴에서 유용합니다.

```zig
const std = @import("std");

pub fn main() void {
    const list_length: usize = 0;

    // list_length가 0이면 뒤의 조건은 평가되지 않으므로 안전하다
    const has_first_item = (list_length > 0) and (list_length >= 1);

    std.debug.print("has_first_item={}\n", .{has_first_item});
}
```

## 정수 오버플로에 대한 Zig의 태도

여기서부터가 이 장에서 가장 중요한 부분입니다. 정수 타입은 표현할 수 있는 값의 범위가 정해져 있습니다. 예를 들어 `u8`은 0부터 255까지만 표현할 수 있는데, 여기에 1을 더 더하면 어떤 일이 벌어질까요?

```zig
const std = @import("std");

pub fn main() void {
    var counter: u8 = 255;
    counter += 1; // 디버그 빌드에서는 여기서 패닉이 발생한다

    std.debug.print("counter={d}\n", .{counter});
}
```

C 언어에서는 부호 없는 정수의 오버플로는 정의된 동작(0으로 순환)이고, 부호 있는 정수의 오버플로는 정의되지 않은 동작입니다. 어느 쪽이든 프로그램은 조용히 실행을 계속하고, 잘못된 값은 한참 뒤 예상치 못한 곳에서 문제를 일으킵니다.

Zig는 이 상황을 다르게 다룹니다. 디버그 빌드(`zig build-exe`의 기본 모드, 즉 `Debug` 최적화 모드)와 `ReleaseSafe` 모드에서는 정수 오버플로가 발생하는 순간 프로그램이 즉시 패닉을 일으키며 실행을 멈춥니다. 위 코드를 실행하면 다음과 비슷한 메시지를 보게 됩니다.

```
thread panic: integer overflow
```

이것은 버그가 아니라 의도된 안전장치입니다. Zig의 설계 철학은 "잘못된 상태가 조용히 퍼져 나가는 것보다, 잘못된 순간에 즉시 멈추는 것이 훨씬 낫다"는 것입니다. `u8` 변수에 256이라는 값을 담으려는 시도는 프로그래머의 실수이거나 예상치 못한 입력값이 들어왔다는 신호이며, Zig는 이 신호를 조용히 감추지 않고 바로 그 지점에서 드러냅니다. 오버플로가 발생한 지점에서 즉시 패닉이 일어나기 때문에, 잘못된 값이 함수를 몇 단계씩 거쳐 전달된 뒤 전혀 관계없어 보이는 곳에서 이상 동작을 일으키는 상황을 막을 수 있습니다. 버그를 최대한 발생 지점 가까이에서 찾아내는 것, 이것이 디버그 빌드에서 오버플로를 패닉으로 처리하는 핵심 이유입니다.

참고로 `ReleaseFast`나 `ReleaseSmall`처럼 안전 검사를 생략하는 최적화 모드에서는 오버플로 검사 코드 자체가 빠지므로 오버플로가 나더라도 패닉이 일어나지 않고 정의되지 않은 동작으로 이어질 수 있습니다. 따라서 오버플로가 일어날 수 있는 코드를 그대로 릴리스 빌드에 내보내는 것은 위험하며, 이런 상황을 다루는 올바른 방법은 아래에서 소개하는 wrapping 연산자나 11장에서 다룰 오버플로 검사 빌트인 함수(`@addWithOverflow` 등)를 사용하는 것입니다.

## 오버플로를 허용하는 wrapping 연산자

오버플로가 항상 실수인 것은 아닙니다. 예를 들어 체크섬을 계산하거나, 해시 함수를 구현하거나, 순환 버퍼의 인덱스를 다루는 코드에서는 값이 범위를 넘어가면 자연스럽게 0으로 돌아가는(순환하는) 동작을 의도적으로 원할 때가 있습니다. 이런 경우를 위해 Zig는 오버플로를 패닉 없이 조용히 순환시키는 별도의 연산자를 제공합니다: `+%`, `-%`, `*%`.

```zig
const std = @import("std");

pub fn main() void {
    var counter: u8 = 255;
    counter = counter +% 1; // 순환하여 0이 된다. 패닉이 발생하지 않는다

    var small: i8 = 127;
    small = small +% 1; // 순환하여 -128이 된다

    std.debug.print("counter={d}, small={d}\n", .{ counter, small });
}
```

`+%`, `-%`, `*%`는 이름 그대로 더하기, 빼기, 곱하기의 wrapping 버전입니다. 일반 산술 연산자 `+`, `-`, `*`는 "오버플로가 나면 그건 버그니까 멈춰라"라는 뜻이고, `+%`, `-%`, `*%`는 "이 연산은 순환할 수 있다는 것을 내가 이미 알고 있고, 의도한 동작이다"라는 뜻입니다.

이 두 종류의 연산자가 나뉘어 있다는 사실 자체가 중요합니다. 코드에 `+%`가 보인다면, 그 자리는 오버플로가 일어날 수 있고 그것이 정상적인 흐름이라는 사실을 작성자가 이미 고려했다는 뜻입니다. 반면 평범한 `+`가 보인다면, 오버플로가 나서는 안 되는 자리라는 뜻이고, 실제로 오버플로가 나면 패닉으로 즉시 알려줍니다. 다음은 8비트 순환 카운터를 이용한 간단한 예입니다.

```zig
const std = @import("std");

pub fn main() void {
    var tick: u8 = 250;
    var i: usize = 0;

    while (i < 10) {
        std.debug.print("tick={d}\n", .{tick});
        tick = tick +% 1;
        i += 1;
    }
}
```

이 반복문은 `tick`이 255를 넘어가는 순간에도 패닉 없이 0, 1, 2, 3으로 자연스럽게 순환합니다. `while` 반복문의 자세한 문법은 6장에서 다룹니다.

## 비트 연산자

비트 연산자는 정수를 이루는 각 비트를 직접 다룹니다. AND(`&`), OR(`|`), XOR(`^`), 좌측 시프트(`<<`), 우측 시프트(`>>`)를 제공합니다.

```zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 0b1100_1010;
    const b: u8 = 0b1010_1100;

    const and_result = a & b;
    const or_result = a | b;
    const xor_result = a ^ b;
    const shifted_left = a << 2;
    const shifted_right = a >> 2;

    std.debug.print("and={b:08b}, or={b:08b}, xor={b:08b}\n", .{
        and_result, or_result, xor_result,
    });
    std.debug.print("left={b:08b}, right={b:08b}\n", .{ shifted_left, shifted_right });
}
```

`0b`로 시작하는 리터럴은 2진수 표기이며, 숫자 사이의 밑줄은 3장에서 본 것처럼 읽기 편하게 자릿수를 나누는 역할만 합니다. 비트 연산자는 플래그를 조합하거나, 특정 비트만 추출하거나, 색상값의 채널을 분리하는 등의 상황에서 유용합니다.

```zig
const std = @import("std");

const FLAG_READ: u8 = 0b0001;
const FLAG_WRITE: u8 = 0b0010;
const FLAG_EXEC: u8 = 0b0100;

pub fn main() void {
    const permission = FLAG_READ | FLAG_WRITE;

    const can_read = (permission & FLAG_READ) != 0;
    const can_exec = (permission & FLAG_EXEC) != 0;

    std.debug.print("can_read={}, can_exec={}\n", .{ can_read, can_exec });
}
```

좌측 시프트(`<<`)도 오버플로 검사를 받는다는 점을 기억해 둘 필요가 있습니다. `u8` 값을 왼쪽으로 시프트했을 때 1인 비트가 8비트 범위를 벗어나면, 이 역시 디버그 빌드에서 패닉을 일으킵니다. 이 값을 넘어가는 비트를 그대로 버리고 싶다면 wrapping 시프트 연산자인 `<<%`을 대신 사용할 수 있습니다.

## 연산자 오버로딩이 없는 이유

C++이나 Rust 같은 언어에서는 사용자가 정의한 구조체에 대해 `+`나 `==` 같은 연산자의 동작을 직접 정의할 수 있습니다. 이를 연산자 오버로딩이라고 부릅니다. Zig에는 이 기능이 존재하지 않습니다. 어떤 구조체 타입에 대해 `a + b`를 쓰고 싶다면, Zig는 그런 문법 자체를 허용하지 않으며, 대신 `add(a, b)`처럼 이름이 있는 함수를 명시적으로 호출해야 합니다.

이 결정은 1장에서 이야기한 Zig의 핵심 철학, 즉 "숨겨진 제어 흐름이 없어야 한다(no hidden control flow)"는 원칙과 정확히 맞물려 있습니다. 코드에 `+` 기호가 보이면, 그것을 읽는 사람은 이 연산이 두 숫자를 더하는 단순한 산술 명령어 하나로 이어진다고 믿을 수 있어야 합니다. 만약 연산자 오버로딩이 허용된다면, `a + b`라는 겉보기에 단순한 표현식 뒤에 실제로는 임의의 길이를 가진 함수 호출, 심지어 메모리 할당이나 예외 처리까지 숨어 있을 수 있습니다. 코드를 읽는 사람은 `+` 기호만 보고는 그 안에 무엇이 들어 있는지 전혀 알 수 없게 됩니다.

Zig는 이런 놀라움을 근본적으로 없애기로 결정했습니다. 두 구조체 값을 "더하는" 로직이 필요하다면, `Vector.add(v1, v2)`처럼 이름이 붙은 평범한 함수로 작성합니다. 함수 이름과 호출 형태만 보고도 이것이 함수 호출이라는 사실이 명확하며, 함수 본문을 열어 보면 그 안에서 무슨 일이 일어나는지 정확히 알 수 있습니다. 다음 예제는 이런 방식이 실제로 어떻게 보이는지 보여줍니다. 구조체 문법 자체는 9장에서 본격적으로 다루므로, 지금은 함수 호출의 형태에만 주목하면 됩니다.

```zig
const std = @import("std");

const Point = struct {
    x: i32,
    y: i32,

    fn add(a: Point, b: Point) Point {
        return Point{ .x = a.x + b.x, .y = a.y + b.y };
    }
};

pub fn main() void {
    const p1 = Point{ .x = 1, .y = 2 };
    const p2 = Point{ .x = 3, .y = 4 };
    const p3 = Point.add(p1, p2);

    std.debug.print("p3=({d}, {d})\n", .{ p3.x, p3.y });
}
```

`p1 + p2`처럼 쓸 수는 없지만, `Point.add(p1, p2)`라는 호출은 그 자체로 "이것은 함수 호출이며, 그 정의를 보면 정확히 무슨 일이 일어나는지 알 수 있다"는 사실을 숨기지 않습니다. 이는 산술 연산자, 비교 연산자, 논리 연산자, 비트 연산자를 포함한 이 장의 모든 연산자에도 똑같이 적용되는 원칙입니다. Zig에서 `+`나 `==` 같은 기호를 볼 때마다, 그 뒤에는 사용자가 정의한 임의의 코드가 아니라 언어가 정의한 정해진 동작만 있다는 확신을 가질 수 있습니다.

## 요약

- 산술 연산자는 `+ - * / %`이며, 정수 나눗셈에서 방식을 명확히 하고 싶을 때는 `@divTrunc`, `@divFloor`, `@rem`, `@mod` 같은 빌트인 함수를 사용합니다.
- 비교 연산자(`== != < > <= >=`)는 같은 타입의 값 사이에서만 사용할 수 있고 결과는 `bool`입니다.
- 논리 연산자는 `and`, `or`, `!`이며, `and`/`or`는 단축 평가를 수행합니다.
- 디버그 빌드와 `ReleaseSafe` 모드에서 정수 오버플로가 발생하면 프로그램은 즉시 패닉을 일으킵니다. 이는 버그를 발생 지점 가까이에서 조기에 발견하기 위한 Zig의 의도적인 안전장치입니다.
- 오버플로가 순환하는 동작이 의도된 상황(체크섬, 해시, 순환 버퍼 등)에서는 wrapping 연산자 `+%`, `-%`, `*%`를 사용해 패닉 없이 값을 순환시킬 수 있습니다.
- 비트 연산자 `& | ^ << >>`는 정수의 각 비트를 직접 다루며, 플래그 조합이나 비트 필드 추출에 유용합니다.
- Zig에는 연산자 오버로딩이 없습니다. 이는 `+`나 `==` 같은 기호가 항상 언어가 정의한 단순한 동작만을 의미하도록 보장하는, 1장에서 소개한 "숨겨진 제어 흐름이 없다"는 철학의 직접적인 결과입니다.

## 연습문제

1. `u16` 타입의 변수에 65535를 대입한 뒤 `+ 1`과 `+% 1`을 각각 시도해 보세요. 두 결과가 어떻게 다른지, 그리고 왜 그런 차이가 나는지 설명해 보세요.
2. 초 단위로 주어진 정수를 시/분/초로 변환하는 함수를 `@divTrunc`와 `@rem`을 이용해 작성해 보세요.
3. `u8` 타입의 색상 채널 값 두 개를 XOR 연산으로 결합하는 간단한 프로그램을 작성하고, 결과를 2진수(`{b:08b}`)로 출력해 보세요.
4. 8비트 순환 카운터를 wrapping 연산자로 구현하고, 0부터 시작해 300번 증가시켰을 때 최종 값이 무엇인지 예측한 뒤 실제로 실행해서 확인해 보세요.
5. Zig에 연산자 오버로딩이 없는 이유를 1장에서 다룬 "숨겨진 제어 흐름이 없다"는 철학과 연결해서 자신의 말로 서술해 보세요. 만약 `+` 연산자를 구조체에 오버로딩할 수 있다면 어떤 문제가 생길 수 있을지 구체적인 예를 들어 설명해 보세요.

이 장에서는 다음을 다룹니다.

- 타입 추론과 명시적 타입 표기

## const와 var

Zig에서 이름에 값을 묶어 두는 방법은 두 가지입니다.

```zig
const pi = 3.14159;
var counter = 0;
```

`const`로 선언한 이름은 이후 다시 대입할 수 없습니다. 반면 `var`로 선언한 이름은 프로그램 실행 중에 값을 바꿀 수 있습니다.

```zig
const std = @import("std");

pub fn main() void {
    const greeting = "안녕하세요";
    var count: i32 = 0;

    count += 1;
    count += 1;

    // greeting = "다른 문자열"; // 컴파일 오류: const 값은 재대입할 수 없음

    std.debug.print("{s}, count = {d}\n", .{ greeting, count });
}
```

`greeting`에 새 값을 대입하려는 줄의 주석을 풀면 컴파일 오류가 발생합니다. Zig 컴파일러는 `const`로 선언된 이름에 대한 재대입을 컴파일 시점에 차단합니다.

### 왜 불변이 기본값인가

많은 언어에서는 `var`나 `let` 같은 가변 선언이 기본이고, 불변 선언은 선택 사항으로 취급됩니다. Zig는 이 순서를 뒤집습니다. 코드를 작성할 때 먼저 `const`를 쓰고, 정말로 값을 바꿔야 할 이유가 생겼을 때만 `var`로 바꾸는 것이 권장되는 습관입니다.

이렇게 하는 이유는 단순합니다. 어떤 이름이 `const`로 선언되어 있다면, 코드를 읽는 사람은 그 값이 선언된 이후로 절대 바뀌지 않는다는 사실을 보장받습니다. 함수가 길어지고 코드베이스가 커질수록 "이 변수가 지금 무슨 값을 가지고 있을까"를 추적하는 일은 점점 어려워지는데, `const`로 선언된 이름은 그 추적 대상에서 완전히 제외할 수 있습니다. 반대로 `var`가 눈에 보이면, 그 이름은 어딘가에서 값이 바뀔 수 있다는 신호로 읽을 수 있습니다.

실제로 Zig 컴파일러는 이 습관을 강제하는 역할도 합니다. `var`로 선언했지만 실제로 값을 한 번도 바꾸지 않는 지역 변수가 있으면, 컴파일러가 이를 지적합니다.

```zig
pub fn main() void {
    var x: i32 = 10; // 컴파일 오류: 이 var는 한 번도 재대입되지 않음
    _ = x;
}
```

이 경우 `var x`를 `const x`로 고쳐야 합니다. 컴파일러가 이런 것까지 확인해 주는 이유는, 불필요한 `var`가 코드를 읽는 사람에게 "이 값이 바뀔 수 있다"는 잘못된 신호를 주기 때문입니다. Zig는 코드가 실제로 하는 일과 코드를 읽었을 때 받는 인상이 항상 일치하도록 만드는 데 신경을 씁니다.

## 정수 타입

Zig의 정수 타입은 이름에 부호 여부와 비트 수를 직접 담고 있습니다. 부호가 있는 정수는 `i`로, 부호가 없는 정수는 `u`로 시작하고, 뒤에 비트 수가 붙습니다.

| 타입 | 의미 | 표현 범위 |
|---|---|---|
| `i8` | 부호 있는 8비트 정수 | -128 ~ 127 |
| `u8` | 부호 없는 8비트 정수 | 0 ~ 255 |
| `i16` / `u16` | 16비트 정수 | 약 -3.2만 ~ 3.2만 / 0 ~ 6.5만 |
| `i32` / `u32` | 32비트 정수 | 약 -21억 ~ 21억 / 0 ~ 42억 |
| `i64` / `u64` | 64비트 정수 | 매우 큰 범위 |

```zig
const std = @import("std");

pub fn main() void {
    const age: u8 = 30;
    const temperature: i16 = -15;
    const population: u32 = 51_780_000;
    const nano_seconds: i64 = 1_000_000_000;

    std.debug.print("age={d}, temp={d}, pop={d}, ns={d}\n", .{
        age, temperature, population, nano_seconds,
    });
}
```

숫자 리터럴 안에 있는 밑줄(`_`)은 자릿수를 구분하기 위한 표기일 뿐, 값에는 아무 영향을 주지 않습니다. `51_780_000`은 `51780000`과 완전히 같은 값입니다.

### 타입을 명시해야 하는 이유

다른 언어에서 흔히 쓰는 `int`처럼 크기를 특정하지 않는 정수 타입은 Zig에 없습니다. 대신 프로그래머가 "이 값은 몇 비트면 충분한가"를 직접 결정하도록 강제합니다. 예를 들어 사람의 나이를 저장한다면 음수가 될 수 없고 200을 넘길 일도 없으니 `u8`이면 충분합니다. 반면 인구수처럼 40억을 넘는 값을 저장하려면 `u32`로는 부족할 수 있으니 `u64`를 고려해야 합니다.

이런 선택을 강제하는 것이 번거로워 보일 수 있지만, 실제로는 자료구조의 메모리 사용량을 줄이고, 값의 범위에 대한 가정을 코드에 명시적으로 남기는 효과가 있습니다. `u8`로 선언된 필드를 보면 "이 값은 0에서 255 사이"라는 사실을 타입 이름만으로 알 수 있습니다.

### 임의 비트폭 정수

Zig의 정수 타입 체계에서 특히 독특한 부분은, 8·16·32·64비트 같은 흔한 크기 외에도 원하는 비트 수를 자유롭게 지정할 수 있다는 점입니다. `u1`부터 `u65535`까지, `i1`부터 `i65535`까지 어떤 비트폭이든 타입으로 사용할 수 있습니다.

```zig
const std = @import("std");

pub fn main() void {
    const flag: u1 = 1; // 0 또는 1만 가질 수 있는 1비트 정수
    const small_signed: i7 = -64; // -64 ~ 63 범위의 7비트 정수
    const three_bits: u3 = 5; // 0 ~ 7 범위의 3비트 정수

    std.debug.print("flag={d}, small_signed={d}, three_bits={d}\n", .{
        flag, small_signed, three_bits,
    });
}
```

`u1`은 불리언과 비슷해 보이지만 엄연히 다른 타입입니다. `u1`은 정수 연산의 대상이 되고, `bool`은 논리 연산과 조건문의 대상이 됩니다. 이런 임의 비트폭 정수는 일상적인 코드에서 자주 쓰이지는 않지만, 하드웨어 레지스터의 특정 비트 필드를 표현하거나 네트워크 프로토콜의 압축된 헤더를 다룰 때, 또는 비트 단위로 정밀하게 메모리를 절약해야 하는 상황에서 유용합니다. 구조체 안에서 임의 비트폭 정수를 여러 개 이어 붙이면 패킹된 비트 필드를 자연스럽게 표현할 수 있는데, 이 내용은 9장에서 구조체를 다룰 때 다시 살펴봅니다.

## 부동소수점 타입

실수를 표현할 때는 `f32`와 `f64`를 사용합니다. 각각 IEEE 754 표준의 단정밀도와 배정밀도 부동소수점 형식을 따릅니다.

```zig
const std = @import("std");

pub fn main() void {
    const pi: f32 = 3.14159;
    const e: f64 = 2.718281828459045;
    const half: f64 = 0.5;

    std.debug.print("pi={d}, e={d}, half={d}\n", .{ pi, e, half });
}
```

`f32`는 소수점 아래 정밀도가 낮지만 메모리를 절반만 사용하고, `f64`는 정밀도가 높은 대신 메모리를 두 배 사용합니다. 특별한 이유가 없다면 `f64`를 기본으로 사용하고, 대량의 데이터를 다루면서 메모리나 연산 속도가 중요한 경우(예: 그래픽 프로그래밍의 정점 좌표)에 `f32`를 고려하는 것이 일반적인 선택입니다.

## 불리언 타입

참과 거짓을 표현하는 타입은 `bool`이며, 값은 `true`와 `false` 두 가지뿐입니다.

```zig
const std = @import("std");

pub fn main() void {
    const is_ready: bool = true;
    var has_error = false;

    has_error = !is_ready;

    std.debug.print("is_ready={}, has_error={}\n", .{ is_ready, has_error });
}
```

Zig에서 `bool`은 정수와 자동으로 섞이지 않습니다. C 계열 언어처럼 `if (1)`이나 `if (some_int)`처럼 정수를 곧바로 조건식에 쓰는 것은 허용되지 않습니다. 조건문에는 반드시 `bool` 타입의 값이 들어가야 하며, 이 규칙은 5장에서 제어문을 다룰 때 다시 확인합니다.

## 타입 추론과 명시적 타입 표기

지금까지 예제에서 일부 변수는 타입을 적었고, 일부는 적지 않았습니다. Zig는 초기값이 있으면 그 값으로부터 타입을 추론할 수 있습니다.

```zig
const std = @import("std");

pub fn main() void {
    var x = 10; // 정수 리터럴이므로 i32로 추론됨
    var y: u8 = 10; // 타입을 u8로 명시

    x += 1;
    y += 1;

    std.debug.print("x={d} ({s}), y={d} ({s})\n", .{
        x, @typeName(@TypeOf(x)), y, @typeName(@TypeOf(y)),
    });
}
```

이 프로그램을 실행하면 `x`의 타입은 `i32`로, `y`의 타입은 `u8`로 출력됩니다. `10`처럼 크기가 정해지지 않은 정수 리터럴은 문맥에 따라 타입이 결정되는데, 타입을 강제하는 문맥이 전혀 없을 때는 `i32`가 기본값으로 선택됩니다. 부동소수점 리터럴의 경우도 마찬가지로, 문맥이 없으면 `f64`로 추론됩니다.

```zig
var ratio = 0.5; // f64로 추론됨
```

`var y: u8 = 10;`처럼 타입을 콜론 뒤에 명시하면, 리터럴 `10`은 추론 대신 그 타입으로 강제됩니다. 이렇게 타입을 명시하는 방식은 함수의 매개변수나 반환값처럼 타입을 반드시 밝혀야 하는 곳, 혹은 기본 추론 결과가 아닌 다른 타입을 의도적으로 쓰고 싶을 때 사용합니다.

타입 추론이 있다고 해서 Zig의 타입 시스템이 느슨해지는 것은 아닙니다. 추론은 컴파일 시점에 정확히 하나의 타입으로 확정되며, 이후 그 이름의 타입은 절대 바뀌지 않습니다. 동적 타입 언어에서 변수가 실행 중에 다른 타입의 값을 담을 수 있는 것과는 근본적으로 다릅니다.

## undefined: 초기화하지 않은 상태를 명시하기

변수를 선언하면서 아직 어떤 값을 넣을지 정하지 못했을 때, Zig는 이를 어물쩍 넘기지 않고 `undefined`라는 특별한 값으로 명시하도록 요구합니다.

```zig
const std = @import("std");

pub fn main() void {
    var result: i32 = undefined;

    // 이후 실제 로직을 통해 값을 계산해서 채운다
    result = 3 * 14;

    std.debug.print("result={d}\n", .{result});
}
```

`undefined`는 "이 메모리 공간은 마련해 두었지만, 그 안에 어떤 값이 들어 있는지는 아직 정해지지 않았다"는 뜻입니다. 이 값을 읽으면 실제로 어떤 값이 나올지 알 수 없고, 디버그 빌드에서는 이런 실수를 잡아내기 위해 해당 메모리를 특정 패턴으로 채워 두기도 합니다.

여기서 중요한 점은, Zig가 `undefined`라는 문법을 통해 "초기화되지 않았다"는 상태 자체를 명시적으로 코드에 드러낸다는 것입니다. 많은 언어는 변수를 선언만 하고 초기화를 생략할 수 있게 해 주는데, 그 경우 변수 안에 어떤 값이 들어 있는지는 코드만 봐서는 알 수 없습니다. Zig에서는 초기화를 생략한다는 선택 자체를 `undefined`라는 눈에 보이는 키워드로 표현하게 만들어, "이 변수는 아직 값이 정해지지 않은 상태"라는 사실을 코드를 읽는 사람과 컴파일러 모두에게 알립니다.

`undefined`는 다음과 같은 상황에서 특히 유용합니다.

```zig
const std = @import("std");

pub fn main() void {
    var buffer: [10]u8 = undefined;

    for (&buffer, 0..) |*slot, i| {
        slot.* = @intCast(i);
    }

    std.debug.print("buffer[3]={d}\n", .{buffer[3]});
}
```

크기가 10인 바이트 배열을 선언했지만, 이 배열은 어차피 곧바로 반복문으로 채워질 예정입니다. 모든 원소를 0으로 초기화하는 비용을 들일 필요가 없으므로 `undefined`로 선언한 뒤 즉시 값을 채우는 방식이 자연스럽습니다. 배열과 반복문에 대해서는 6장과 8장에서 더 자세히 다룹니다.

`undefined`를 다루는 자유가 주어지는 만큼 책임도 함께 따릅니다. 값을 채우기 전에 실수로 읽어버리면 정의되지 않은 동작으로 이어질 수 있으므로, `undefined`는 반드시 "이후 코드에서 값을 확정적으로 채운다"는 확신이 있을 때만 사용해야 합니다.

## 표준 라이브러리 다시 보기

2장에서 이미 `const std = @import("std");`라는 줄을 사용해 보았습니다. `@import`는 Zig의 빌트인 함수 중 하나로, 다른 소스 파일이나 표준 라이브러리 모듈을 현재 파일로 가져옵니다. `"std"`라는 이름은 Zig 컴파일러에 내장된 표준 라이브러리를 가리키는 특별한 경로이며, 이 안에는 지금까지 사용한 `std.debug.print`를 비롯해 이 책에서 앞으로 다룰 메모리 할당자, 자료구조, 파일 입출력 등 다양한 기능이 들어 있습니다. `@import`가 반환하는 값은 하나의 구조체이며, `std.debug`나 `std.mem`처럼 점(`.`)으로 그 안의 하위 구조에 접근합니다. 표준 라이브러리의 구체적인 구성은 이후 장에서 필요할 때마다 조금씩 소개합니다.

## 요약

- `const`는 재대입이 불가능한 불변 바인딩이고, `var`는 재대입이 가능한 가변 바인딩입니다. Zig는 `const`를 기본값으로 삼고, 정말 필요할 때만 `var`를 쓰는 습관을 권장합니다. 값이 바뀌지 않는 `var`는 컴파일 오류로 잡힙니다.
- 정수 타입은 부호(`i`/`u`)와 비트 수를 조합해 이름이 정해지며(`i32`, `u64` 등), `u1`이나 `i7`처럼 임의의 비트폭도 타입으로 쓸 수 있습니다.
- 실수는 `f32`와 `f64`, 참/거짓은 `bool`로 표현합니다.
- 초기값이 있으면 타입을 추론할 수 있고(`var x = 10;`은 `i32`), 콜론 뒤에 타입을 적어 명시적으로 지정할 수도 있습니다(`var x: u8 = 10;`).
- `undefined`는 "아직 초기화되지 않은 상태"를 코드에 명시적으로 드러내는 값으로, 이후 반드시 값을 채울 것이 확실할 때만 사용합니다.
- `@import("std")`는 표준 라이브러리 모듈을 가져오는 빌트인 함수이며, 결과는 점 표기법으로 하위 기능에 접근할 수 있는 구조체입니다.

## 연습문제

1. `const`로 선언한 변수에 다시 값을 대입하면 어떤 일이 벌어지는지, 그리고 값을 한 번도 바꾸지 않는 `var`를 선언하면 어떤 일이 벌어지는지 각각 짧은 코드로 확인해 보세요.
2. 다음 값들을 저장하기에 적절한 정수 타입을 각각 고르고 그 이유를 설명해 보세요: (a) 요일을 나타내는 1~7 사이의 값, (b) 대한민국의 총 인구수, (c) 온도계가 표시하는 영하 40도에서 영상 50도 사이의 값.
3. `u4` 타입의 변수를 선언하고 0부터 15까지의 값을 대입해 보세요. 만약 16을 대입하면 어떤 일이 일어나는지 실제로 컴파일해서 확인해 보세요.
4. `var x = 5;`와 `var y: f32 = 5;`를 각각 선언한 뒤 `@TypeOf`와 `@typeName`을 이용해 두 변수의 타입을 출력해 보고, 왜 서로 다른 타입으로 추론되었는지 설명해 보세요.
5. 크기가 5인 `i32` 배열을 `undefined`로 선언한 뒤, 반복문으로 각 원소에 자신의 인덱스를 제곱한 값을 채우고 출력하는 프로그램을 작성해 보세요.

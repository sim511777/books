## 이 장에서 다루는 내용

2장에서 우리는 `zig build-exe`로 소스 파일 하나를 곧바로 실행 파일로 만들어 보았고, `zig build` 명령이 존재한다는 사실도 잠깐 언급했습니다. 파일이 하나뿐인 작은 예제에서는 `zig build-exe`만으로도 충분합니다. 하지만 소스 파일이 여러 개로 늘어나고, 실행 파일과 테스트를 함께 빌드해야 하고, 다른 사람이 만든 패키지를 가져와 써야 하는 순간이 오면 이야기가 달라집니다. Zig는 이런 상황을 다루기 위해 셸 스크립트나 별도의 빌드 도구 대신, Zig 코드로 직접 빌드 절차를 기술하는 방식을 택했습니다. 이 장에서는 그 핵심인 `build.zig` 파일을 자세히 들여다봅니다.

이 장에서는 다음을 다룹니다.

- `build.zig` 파일의 기본 구조와 `build` 함수의 역할
- `zig build`가 내부적으로 `build.zig`를 실행해서 빌드 그래프를 구성하는 과정
- `build.zig.zon`을 이용한 패키지 의존성 선언 방식의 개요
- Debug, ReleaseSafe, ReleaseFast, ReleaseSmall 네 가지 빌드 모드의 차이와 선택 기준

## build.zig 파일의 기본 구조

`zig init`을 실행하거나 새 프로젝트를 시작하면 프로젝트 최상위 폴더에 `build.zig`라는 파일이 생깁니다. 이 파일은 다른 언어의 `Makefile`이나 `CMakeLists.txt`와 비슷한 역할을 하지만, 문법은 평범한 Zig 코드입니다. 즉, 빌드 스크립트를 작성하기 위해 새로운 언어를 배울 필요가 없습니다.

가장 단순한 형태의 `build.zig`는 다음과 같습니다.

```zig
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const exe = b.addExecutable(.{
        .name = "hello",
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
    });

    b.installArtifact(exe);
}
```

이 파일의 핵심은 `build`라는 이름의 함수입니다. Zig 컴파일러는 `zig build`를 실행할 때 이 함수를 찾아서 호출하며, 이 함수 안에서 무엇을 만들지, 어떤 순서로 만들지를 선언합니다. 함수의 시그니처를 하나씩 살펴보겠습니다.

- `pub fn build(...) void`: 반드시 `pub`으로 공개되어야 하고, 이름은 정확히 `build`여야 하며, 반환 타입은 `void`입니다. Zig 컴파일러가 이 이름을 규칙으로 찾아서 호출하기 때문입니다.
- `b: *std.Build`: 매개변수 `b`는 `std.Build` 타입 값을 가리키는 포인터입니다. `std.Build`는 표준 라이브러리가 제공하는 "빌더" 객체로, 실행 파일을 정의하거나 빌드 단계를 추가하는 등 빌드와 관련된 거의 모든 작업이 이 객체를 통해 이루어집니다. 관례적으로 매개변수 이름을 `b`로 짧게 씁니다.

### 타겟과 최적화 옵션

`b.standardTargetOptions(.{})`와 `b.standardOptimizeOption(.{})`는 커맨드라인에서 `-Dtarget=...`, `-Doptimize=...` 같은 옵션을 사용자가 지정할 수 있게 열어 주는 표준적인 방법입니다.

- `target`은 "어떤 CPU 아키텍처와 운영체제를 위해 컴파일할 것인가"를 나타냅니다. 아무 옵션도 주지 않으면 지금 빌드를 실행하는 컴퓨터, 즉 네이티브 환경이 기본값이 됩니다.
- `optimize`는 뒤에서 다룰 네 가지 빌드 모드 중 하나를 나타냅니다.

이 두 값을 직접 필드에 하드코딩하지 않고 `standardTargetOptions`와 `standardOptimizeOption`을 거치는 이유는, 이렇게 해야 프로젝트를 사용하는 사람이 `build.zig`를 고치지 않고도 커맨드라인 옵션만으로 타겟이나 최적화 수준을 바꿀 수 있기 때문입니다.

### 실행 파일 타겟 정의하기

`b.addExecutable(...)`은 "이런 이름과 이런 소스로 실행 파일 하나를 만들겠다"는 선언입니다. 반환값은 `*std.Build.Step.Compile`이라는 타입인데, 이는 "컴파일이라는 작업 하나"를 나타내는 객체로 이해하면 됩니다.

```zig
const exe = b.addExecutable(.{
    .name = "hello",
    .root_source_file = b.path("src/main.zig"),
    .target = target,
    .optimize = optimize,
});
```

- `.name`: 생성될 실행 파일의 이름입니다. 플랫폼에 따라 `hello` 또는 `hello.exe`가 됩니다.
- `.root_source_file`: 이 실행 파일의 진입점이 되는 소스 파일입니다. `b.path(...)`는 프로젝트 루트를 기준으로 한 상대 경로를 빌드 시스템이 이해하는 경로 값으로 바꿔 줍니다.
- `.target`, `.optimize`: 앞에서 만든 옵션 값을 그대로 전달합니다.

이렇게 정의한 `exe` 자체는 아직 "만들어라"는 지시가 아니라 "이런 것을 만들 수 있다"는 선언에 가깝습니다. 실제로 결과물을 설치 폴더(기본적으로 `zig-out`)에 내놓으려면 다음 줄이 필요합니다.

```zig
b.installArtifact(exe);
```

이 호출은 "기본 설치 단계가 실행될 때 `exe`도 함께 설치 대상에 포함하라"는 뜻입니다. `zig build`를 인자 없이 실행하면 이 기본 설치 단계가 동작하고, 그 결과 `zig-out/bin/hello` 같은 경로에 실행 파일이 생깁니다.

## 빌드 스텝이라는 개념

`std.Build`가 다루는 모든 작업은 "스텝(step)"이라는 단위로 표현됩니다. 컴파일 하나, 실행 파일 하나 실행하기, 파일 복사하기, 테스트 실행하기 등이 각각 하나의 스텝입니다. 스텝들은 서로 "이 스텝이 끝나야 저 스텝을 시작할 수 있다"는 의존 관계로 연결되며, 이 의존 관계 전체가 하나의 그래프를 이룹니다.

`zig build`를 커맨드라인에서 실행할 때 뒤에 붙이는 이름, 예를 들어 `zig build run`이나 `zig build test`의 `run`, `test`는 바로 이 스텝의 이름입니다. 직접 실행 파일을 실행하는 스텝을 만들어 보겠습니다.

```zig
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const exe = b.addExecutable(.{
        .name = "hello",
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
    });
    b.installArtifact(exe);

    // exe를 실행하는 스텝을 만든다
    const run_cmd = b.addRunArtifact(exe);
    run_cmd.step.dependOn(b.getInstallStep());

    // "run"이라는 이름으로 커맨드라인에서 부를 수 있는 스텝을 등록한다
    const run_step = b.step("run", "빌드한 실행 파일을 실행합니다");
    run_step.dependOn(&run_cmd.step);
}
```

이 코드가 만드는 의존 관계를 순서대로 읽으면 다음과 같습니다.

1. `b.addRunArtifact(exe)`는 "`exe`를 실행하는 작업" 자체를 하나의 스텝(`run_cmd`)으로 만듭니다.
2. `run_cmd.step.dependOn(b.getInstallStep())`는 "실행하기 전에 먼저 설치 단계가 끝나 있어야 한다"는 의존 관계를 추가합니다. 설치가 안 되어 있으면 실행할 파일이 없기 때문입니다.
3. `b.step("run", "...")`은 커맨드라인에 노출할 새로운 스텝을 하나 만듭니다. 이름이 `"run"`이므로 `zig build run`으로 부를 수 있습니다.
4. `run_step.dependOn(&run_cmd.step)`은 "`run` 스텝이 실제로 하는 일은 `run_cmd`를 실행하는 것"이라는 연결을 만듭니다.

이제 터미널에서 다음처럼 실행할 수 있습니다.

```bash
zig build run
```

`zig build test`처럼 테스트를 실행하는 스텝도 원리는 같습니다. `b.addTest(...)`로 테스트용 컴파일 스텝을 만들고, `b.addRunArtifact(...)`로 그 테스트 바이너리를 실행하는 스텝을 만든 뒤, `b.step("test", ...)`로 이름을 붙여 연결합니다. 테스트 자체의 문법(`test "..." { ... }` 블록)은 18장에서 자세히 다룹니다.

## zig build는 어떻게 동작하는가: 빌드 그래프

`zig build`라는 명령을 실행했을 때 벌어지는 일을 조금 더 근본적으로 살펴보겠습니다. 흔히 오해하기 쉬운 점은 "`build.zig`가 빌드 설정을 적어 놓은 정적인 파일"이라고 생각하는 것입니다. 실제로는 그렇지 않습니다.

`zig build`를 실행하면 Zig 컴파일러는 다음 순서로 동작합니다.

1. `build.zig` 파일 자체를 하나의 독립적인 Zig 프로그램으로 컴파일합니다.
2. 컴파일된 이 프로그램을 즉시 실행합니다. 이 프로그램의 진입점이 바로 우리가 작성한 `build` 함수입니다.
3. `build` 함수가 실행되는 동안 `b.addExecutable`, `b.step`, `dependOn` 같은 호출들이 차례로 일어나면서, 메모리 안에 스텝들의 의존 관계 그래프가 만들어집니다. 이 시점까지는 아직 실제 컴파일이나 파일 복사 같은 무거운 작업은 일어나지 않습니다. "무엇을, 어떤 순서로 할 것인가"라는 계획만 세워지는 단계입니다.
4. `build` 함수가 반환되면, Zig 빌드 시스템은 완성된 그래프를 보고 커맨드라인에서 요청한 스텝(기본값은 설치 스텝)과 그것이 의존하는 스텝들을 역순으로 실제로 수행합니다. 이 단계에서 비로소 소스 파일이 컴파일되고, 실행 파일이 만들어지고, 필요하면 그 파일이 실행됩니다.

즉 `build.zig`는 "설정 파일"이 아니라 "빌드 그래프를 만들어 내는 프로그램"입니다. 이 관점을 받아들이면 `build.zig` 안에서 `if`문으로 조건을 나누거나, 반복문으로 여러 실행 파일을 한꺼번에 정의하는 것이 왜 자연스럽게 가능한지 이해할 수 있습니다. 이것은 그냥 Zig 코드이기 때문입니다.

```zig
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    // 여러 개의 예제 프로그램을 반복문으로 한꺼번에 등록한다
    const example_names = [_][]const u8{ "basics", "sorting", "networking" };

    for (example_names) |name| {
        const path = std.fmt.allocPrint(b.allocator, "examples/{s}.zig", .{name}) catch @panic("OOM");
        const exe = b.addExecutable(.{
            .name = name,
            .root_source_file = b.path(path),
            .target = target,
            .optimize = optimize,
        });
        b.installArtifact(exe);
    }
}
```

이렇게 하면 `examples` 폴더 안의 세 파일이 각각 독립된 실행 파일로 빌드되도록 하는 코드를, 파일 이름이 늘어나도 목록에 한 줄만 추가하면 되도록 작성할 수 있습니다.

### 어떤 스텝이 있는지 확인하기

프로젝트에 어떤 스텝이 정의되어 있는지 잘 모를 때는 다음 명령으로 확인할 수 있습니다.

```bash
zig build --help
```

이 명령은 `build.zig`를 (그래프를 만드는 단계까지) 실행한 뒤, `b.step`으로 등록된 이름과 설명을 나열해 보여 줍니다. 앞서 만든 예제라면 `install`, `run` 같은 스텝 이름과 함께 "빌드한 실행 파일을 실행합니다"라는 설명이 나타납니다.

## 패키지와 의존성: build.zig.zon

혼자 작성한 프로그램이 점점 커지면, 이미 누군가 만들어 둔 기능을 가져와 쓰고 싶은 순간이 옵니다. Zig는 이런 외부 패키지(다른 사람이 만든 Zig 코드 묶음)를 프로젝트에 선언하기 위한 파일로 `build.zig.zon`을 사용합니다. `build.zig`와 이름이 비슷하지만 역할은 다릅니다. `build.zig`는 "무엇을 어떻게 빌드할지"를 기술하는 코드이고, `build.zig.zon`은 "이 프로젝트가 무엇이고, 어떤 외부 패키지에 의존하는지"를 기술하는 데이터입니다. 확장자 `.zon`은 "Zig Object Notation"의 줄임말로, Zig의 컴파일 타임 리터럴 문법으로 데이터를 표현하는 형식입니다.

`build.zig.zon`은 대략 다음과 같은 모양을 가집니다.

```zig
.{
    .name = "my_project",
    .version = "0.1.0",
    .dependencies = .{
        .cool_library = .{
            .url = "https://example.com/cool_library/archive/refs/tags/v1.2.0.tar.gz",
            .hash = "1220abcdef...",
        },
    },
    .paths = .{
        "build.zig",
        "build.zig.zon",
        "src",
    },
}
```

이 파일이 하는 역할을 이름과 목적 위주로만 짚어 보면 다음과 같습니다.

- `.name`, `.version`: 이 프로젝트 자체를 하나의 패키지로 식별하는 이름과 버전입니다. 다른 프로젝트가 이 프로젝트를 의존성으로 가져다 쓸 때 이 정보가 쓰입니다.
- `.dependencies`: 이 프로젝트가 필요로 하는 외부 패키지들의 목록입니다. 각 의존성은 어디서 가져올지(URL이나 로컬 경로)와, 내용이 변조되지 않았음을 확인하기 위한 해시 값을 함께 적습니다.
- `.paths`: 이 패키지를 배포할 때 포함해야 할 파일과 폴더 목록입니다.

의존성을 선언해 두면 `build.zig` 안에서 `b.dependency("cool_library", .{})`처럼 그 이름으로 접근해서, 해당 패키지가 제공하는 모듈을 자신의 실행 파일에 연결할 수 있습니다. 새 의존성을 추가할 때 해시 값을 손으로 계산하는 대신 `zig fetch` 명령을 사용하면, 지정한 URL의 패키지를 내려받아 캐시에 저장하고 `build.zig.zon`에 알맞은 항목을 자동으로 채워 줍니다.

이 책은 입문서이므로 `build.zig.zon`을 이용한 실제 의존성 추가와 모듈 연결 과정을 자세히 다루지는 않습니다. 여기서 기억해야 할 것은 "패키지 선언은 `build.zig.zon`이라는 별도의 데이터 파일이 담당하고, 그 정보를 실제 빌드 그래프에 연결하는 것은 `build.zig` 코드가 담당한다"는 역할 분리입니다. 프로젝트가 커져서 외부 패키지가 필요해지면, 이 개념을 출발점으로 삼아 공식 문서를 참고하면 됩니다.

## 빌드 모드 네 가지

`b.standardOptimizeOption(.{})`로 열어 둔 최적화 옵션에는 네 가지 값이 있습니다. `zig build -Doptimize=<모드>`처럼 커맨드라인에서 지정할 수 있고, 아무 값도 지정하지 않으면 `Debug`가 기본값입니다.

| 모드 | 안전 검사 | 실행 속도 | 바이너리 크기 | 컴파일 속도 |
|---|---|---|---|---|
| `Debug` | 모두 켜짐 | 느림 | 큼 | 빠름 |
| `ReleaseSafe` | 모두 켜짐 | 빠름 | 큼 | 느림 |
| `ReleaseFast` | 꺼짐 | 가장 빠름 | 큼 | 느림 |
| `ReleaseSmall` | 꺼짐 | 보통 | 가장 작음 | 느림 |

여기서 "안전 검사"란 정수 오버플로우, 배열 경계를 벗어난 접근, 널 포인터 역참조 같은 실수를 실행 중에 탐지해서 곧바로 프로그램을 중단시키는 기능을 말합니다. 이 검사들은 10장과 11장에서 살펴본 옵셔널 처리, 에러 처리와도 맞물려 있는 Zig의 안전성 철학의 일부입니다.

- **Debug**: 개발 중 기본으로 사용하는 모드입니다. 모든 안전 검사가 켜져 있어서 버그를 최대한 빨리, 최대한 명확한 오류 메시지로 발견할 수 있습니다. 컴파일 자체도 빠르게 끝나도록 최적화되어 있어서, 코드를 조금 고치고 곧바로 다시 빌드해 확인하는 반복 작업에 적합합니다. 실행 속도는 네 모드 중 가장 느립니다.
- **ReleaseSafe**: 실제 배포용 빌드이지만, 안전 검사는 그대로 유지하고 싶을 때 선택합니다. 컴파일러가 최적화를 적용해 실행 속도를 크게 끌어올리면서도, 정수 오버플로우나 배열 범위 초과 같은 문제가 발생하면 여전히 그 자리에서 프로그램을 중단시키고 알려 줍니다. 안전성이 중요한 서버 소프트웨어나, 아직 충분히 검증되지 않은 신규 기능을 배포할 때 적합합니다.
- **ReleaseFast**: 안전 검사를 모두 끄고 실행 속도를 최우선으로 최적화합니다. 이미 충분히 테스트를 거쳐 안전 검사에 의존할 필요가 없다고 판단되는 코드, 예를 들어 성능이 극도로 중요한 수치 계산이나 게임 엔진의 핵심 루프에 적합합니다. 안전 검사가 꺼져 있으므로, 만약 실제로 정수 오버플로우나 배열 범위 초과가 일어난다면 이 모드에서는 프로그램이 오류 없이 조용히 잘못된 값을 계산하거나 예측할 수 없는 동작을 할 수 있습니다.
- **ReleaseSmall**: 안전 검사를 끄고, 실행 속도보다 결과물의 크기를 줄이는 것을 우선합니다. 임베디드 기기나 저장 공간이 제한된 환경, 혹은 다운로드 크기가 중요한 배포 상황에 적합합니다.

간단한 기준을 세워 보면 다음과 같습니다. 코드를 작성하고 고치는 동안에는 `Debug`를 씁니다. 기능이 완성되어 실제로 배포하되 여전히 안전 검사의 도움을 받고 싶다면 `ReleaseSafe`를 씁니다. 속도가 최우선이고 코드를 충분히 신뢰할 수 있다면 `ReleaseFast`를, 결과물 크기가 최우선이라면 `ReleaseSmall`을 씁니다. 프로젝트 하나 안에서도 상황에 따라 다른 모드로 빌드해 비교해 보는 것이 좋은 습관입니다.

```bash
zig build -Doptimize=ReleaseFast
zig build -Doptimize=ReleaseSmall run
```

## 요약

- `build.zig`는 `pub fn build(b: *std.Build) void` 함수를 중심으로 작성하는 평범한 Zig 코드이며, 이 함수 안에서 `b.addExecutable`로 실행 파일 타겟을 정의하고 `b.installArtifact`로 설치 대상에 포함시킵니다.
- 빌드에서 이루어지는 각 작업은 "스텝"으로 표현되고, `dependOn`으로 스텝 사이의 순서를 정하며, `b.step(이름, 설명)`으로 커맨드라인에서 부를 수 있는 이름을 붙입니다(`zig build run`, `zig build test` 등).
- `zig build`는 `build.zig`를 먼저 컴파일하고 실행해서 빌드 그래프를 메모리에 구성한 뒤, 그 그래프를 바탕으로 실제 컴파일과 설치 작업을 수행합니다. `build.zig`는 설정 파일이 아니라 그래프를 만들어 내는 프로그램입니다.
- `build.zig.zon`은 프로젝트의 이름·버전과 외부 패키지 의존성을 선언하는 데이터 파일입니다. `zig fetch`로 의존성을 추가하고, `b.dependency(...)`로 `build.zig` 안에서 그 패키지를 연결합니다.
- 빌드 모드는 `Debug`(개발용, 안전 검사 켜짐, 느림), `ReleaseSafe`(배포용, 안전 검사 켜짐, 빠름), `ReleaseFast`(배포용, 안전 검사 꺼짐, 가장 빠름), `ReleaseSmall`(배포용, 안전 검사 꺼짐, 크기 최소화) 네 가지가 있으며 `-Doptimize=` 옵션으로 선택합니다.

## 연습문제

1. `src/main.zig`를 진입점으로 삼는 실행 파일 하나를 정의하고, `zig build run`으로 실행할 수 있도록 `run` 스텝까지 갖춘 `build.zig`를 처음부터 작성해 보세요.
2. `zig build --help`를 실행해서 어떤 스텝들이 나열되는지 확인하고, 각 스텝이 어디서 어떻게 정의되었는지 `build.zig` 코드와 연결해서 설명해 보세요.
3. `build.zig`의 `build` 함수 안에 반복문을 사용해서, `examples` 폴더 아래의 서로 다른 이름을 가진 소스 파일 세 개를 각각 독립된 실행 파일로 등록하는 코드를 작성해 보세요.
4. 같은 프로그램을 `Debug`와 `ReleaseFast` 두 모드로 각각 빌드한 뒤, 정수 오버플로우가 발생하는 코드(예: `u8` 값에 300을 더하는 연산)를 넣어 두 모드에서 실행 결과가 어떻게 달라지는지 비교해 보세요.
5. `build.zig.zon`과 `build.zig`가 각각 어떤 정보를 담당하는지, 그리고 왜 이 둘이 하나의 파일로 합쳐져 있지 않고 분리되어 있는지 자신의 말로 설명해 보세요.

# 10장. 옵셔널 타입(Optional)

[◀ 이전: 9장. 구조체(struct)](ch09-구조체.md) | [📖 목차](00-목차.md) | [다음: 11장. 에러 처리 ▶](ch11-에러처리.md)


프로그램을 작성하다 보면 "값이 있을 수도 있고 없을 수도 있는" 상황을 자주 만납니다. 예를 들어 리스트에서 특정 조건을 만족하는 첫 번째 원소를 찾는 함수는, 조건을 만족하는 원소가 있으면 그 원소를 돌려주고, 없으면 "결과 없음"을 돌려줘야 합니다. 이런 "없음"을 표현하는 값이 바로 `null`입니다.

많은 언어에서 null은 버그의 큰 원인이 되어 왔습니다. 어떤 값이 null일 수 있는지 없는지가 타입에 드러나지 않기 때문에, 프로그래머가 null을 확인하지 않고 그 값을 사용하다가 프로그램이 죽어버리는 사고가 흔히 일어납니다. Zig는 이 문제를 타입 시스템 차원에서 막습니다. 이번 장에서는 "값이 있거나 없을 수 있음"을 타입으로 표현하는 옵셔널(optional) 타입 `?T`를 배우고, 그 값을 안전하게 꺼내는 여러 방법을 살펴봅니다.

## null이 될 수 없는 일반 타입

Zig에서는 일반 타입의 변수에 `null`을 넣을 수 없습니다. 예를 들어 다음 코드는 컴파일되지 않습니다.

```zig
var x: i32 = null; // 컴파일 오류: i32는 null이 될 수 없다
```

8장에서 살펴본 것처럼, 이 규칙은 포인터에도 그대로 적용됩니다. `*T`라는 일반 포인터 타입은 항상 유효한 대상을 가리키고 있다고 보장되며, `null`을 담을 수 없습니다.

```zig
var value: i32 = 10;
var ptr: *i32 = &value;
ptr = null; // 컴파일 오류: *i32는 null이 될 수 없다
```

이것이 바로 Zig가 다른 많은 언어와 다른 지점입니다. C나 Java 같은 언어에서는 포인터나 참조 변수가 기본적으로 null일 수 있어서, 코드를 읽는 것만으로는 어떤 포인터가 null을 가질 수 있는지 알 수 없습니다. 그 결과 "이 값이 null일까?"라는 질문에 답하려면 함수의 구현부를 직접 읽거나 문서를 찾아봐야 하고, 확인을 빠뜨리면 null 포인터 역참조로 프로그램이 그대로 죽어버립니다. Zig는 애초에 일반 포인터와 일반 타입이 null을 담을 수 없도록 막아서, 이런 종류의 버그를 컴파일 시점에 원천적으로 차단합니다.

## `?T`로 "T이거나 null" 표현하기

그렇다면 값이 없을 수도 있는 상황은 어떻게 표현할까요? 타입 앞에 물음표를 붙여 옵셔널 타입을 만들면 됩니다. `?T`는 "`T` 타입의 값이거나, 혹은 `null`"이라는 뜻입니다.

```zig
var maybe_number: ?i32 = null;
maybe_number = 42;
```

`?i32`는 `i32` 값을 담을 수도 있고 `null`을 담을 수도 있는 타입입니다. 처음에는 `null`로 초기화했다가, 나중에 실제 값(`42`)을 대입하는 것도 자유롭게 할 수 있습니다.

8장에서 예고한 대로, 포인터도 마찬가지입니다. null이 될 수 있는 포인터가 필요하다면 `*T`가 아니라 `?*T`로 감싸야 합니다.

```zig
var value: i32 = 10;
var ptr: ?*i32 = &value; // *i32를 ?*i32에 담을 수 있다
ptr = null; // 옵셔널이므로 null도 허용된다
```

`?*i32`라는 타입 자체가 "이 포인터는 null일 수도 있다"는 사실을 코드에 명시적으로 드러냅니다. 이 포인터를 넘겨받은 다른 함수는 타입만 보고도 null 확인이 필요하다는 것을 바로 알 수 있습니다. 반대로 매개변수 타입이 그냥 `*i32`라면, 그 함수를 호출하는 쪽이나 구현하는 쪽 모두 "이 포인터는 항상 유효하다"고 믿고 별도의 null 확인 없이 안전하게 사용할 수 있습니다.

## 옵셔널 값을 그냥 사용할 수 없는 이유

옵셔널 타입의 값은 바로 산술 연산이나 필드 접근에 쓸 수 없습니다.

```zig
var maybe_number: ?i32 = 42;
const result = maybe_number + 1; // 컴파일 오류
```

`maybe_number`의 타입은 `?i32`이고 `1`의 타입은 `i32`이므로, 두 타입이 다르기 때문에 이 코드는 컴파일되지 않습니다. Zig는 `maybe_number`가 지금 이 순간 실제로 값을 담고 있는지 아니면 null인지 컴파일러가 알 수 없다는 사실을 이렇게 강제로 코드 작성자에게 확인시킵니다. 즉 옵셔널 값을 사용하기 전에는 반드시 "이 값이 null인지 아닌지"를 먼저 분명하게 짚고 넘어가야 합니다. 이제부터 그 방법들을 하나씩 살펴봅니다.

## `if` 언랩 문법

옵셔널 값에서 null 여부를 확인하고 안에 든 값을 꺼내는 가장 기본적인 방법은 `if` 문의 캡처(capture) 문법입니다.

```zig
const maybe_number: ?i32 = 42;

if (maybe_number) |value| {
    std.debug.print("값이 있습니다: {d}\n", .{value});
} else {
    std.debug.print("값이 없습니다\n", .{});
}
```

`if (maybe_number) |value| { ... }`는 `maybe_number`가 `null`이 아니면 그 안에 든 값을 `value`라는 이름으로 꺼내서 블록 안에서 쓸 수 있게 해줍니다. 이때 `value`의 타입은 `?i32`가 아니라 `i32`입니다. 즉 이 블록 안에서는 옵셔널을 벗겨낸 순수한 값을 다루게 됩니다. `maybe_number`가 `null`이면 `if` 블록은 실행되지 않고 `else` 블록이 실행됩니다.

`else` 블록이 필요 없다면 생략할 수도 있습니다.

```zig
if (maybe_number) |value| {
    std.debug.print("값: {d}\n", .{value});
}
// maybe_number가 null이면 아무 일도 하지 않고 지나간다
```

값을 바꿔야 하는 경우에는 옵셔널 변수의 포인터를 캡처할 수도 있습니다.

```zig
var maybe_number: ?i32 = 42;

if (maybe_number) |*value| {
    value.* += 1; // 원본 maybe_number 안의 값을 직접 수정
}
```

`|*value|`처럼 캡처 변수 앞에 `*`를 붙이면, `value`는 옵셔널 안에 들어 있는 값을 가리키는 포인터가 됩니다. 9장에서 살펴본 포인터를 통한 대입과 마찬가지로, `value.* += 1;`은 `maybe_number` 안의 실제 값을 바꿉니다.

## `orelse`로 기본값 지정하기

옵셔널 값이 null일 때 사용할 기본값이 이미 정해져 있다면, `if`로 블록을 여는 것보다 `orelse`가 훨씬 간결합니다.

```zig
const maybe_number: ?i32 = null;
const x = maybe_number orelse 0;
std.debug.print("x = {d}\n", .{x}); // x = 0
```

`maybe_number orelse 0`은 "`maybe_number`가 값을 가지고 있으면 그 값을, `null`이면 `0`을 사용하라"는 뜻입니다. 결과인 `x`의 타입은 `?i32`가 아니라 `i32`입니다. 즉 `orelse`는 옵셔널을 확실한 값으로 바꿔주는 역할을 합니다.

`orelse` 뒤에는 값 하나만 올 수 있는 게 아니라, 블록을 사용해서 더 복잡한 대체 동작을 표현할 수도 있습니다.

```zig
const config_value: ?i32 = null;
const timeout = config_value orelse blk: {
    std.debug.print("설정값이 없어 기본 타임아웃을 사용합니다\n", .{});
    break :blk 30;
};
```

또한 옵셔널이 null일 때 함수를 즉시 종료하고 싶다면 `orelse return`이나 `orelse continue` 같은 형태도 자주 쓰입니다.

```zig
fn print_positive(maybe_number: ?i32) void {
    const value = maybe_number orelse return;
    std.debug.print("{d}\n", .{value});
}
```

`maybe_number`가 `null`이면 `return`이 즉시 실행되어 함수가 끝나고, `print`는 실행되지 않습니다. `null`이 아니면 `value`에는 안에 든 값이 담깁니다.

## `.?`로 강제 언랩하기

옵셔널 값이 반드시 null이 아니라고 확신할 수 있는 상황에서는, `.?`를 붙여서 값을 즉시 꺼낼 수 있습니다.

```zig
const maybe_number: ?i32 = 42;
const value = maybe_number.?;
std.debug.print("{d}\n", .{value});
```

`maybe_number.?`는 `maybe_number`가 `null`이 아니라고 가정하고 안에 든 값을 곧바로 꺼냅니다. 문제는 이 가정이 틀렸을 때입니다. `maybe_number`가 실제로 `null`인 상태에서 `.?`를 사용하면, 프로그램은 그 자리에서 즉시 패닉(panic)을 일으키며 종료됩니다.

```zig
const maybe_number: ?i32 = null;
const value = maybe_number.?; // 런타임 패닉: 여기서 프로그램이 죽는다
```

`.?`는 `if` 언랩이나 `orelse`처럼 null인 경우를 처리할 방법을 프로그래머에게 요구하지 않습니다. 대신 "여기서는 절대로 null이 아니다"라는 확신을 그대로 컴파일러에게 전달하는 것입니다. 이 확신이 맞다면 코드가 짧고 명확해지지만, 확신이 틀리면 프로그램이 그 자리에서 죽어버립니다. 즉 `.?`는 앞서 이 장 초반에서 설명한 "다른 언어의 null 포인터 예외"와 본질적으로 같은 위험을 다시 불러들이는 셈입니다. 차이가 있다면 Zig에서는 이 위험을 감수하겠다는 선택을 `.?`라는 눈에 보이는 문법으로 명시적으로 표시해야 한다는 점입니다.

그래서 `.?`는 다음과 같은 경우로 한정해서 사용하는 것이 좋습니다.

- 방금 직접 null이 아닌 값을 대입했거나 확인해서, null일 가능성이 논리적으로 없는 경우
- 프로그램의 다른 곳에서 이미 조건을 검사해서 이 지점에 도달했다면 반드시 값이 있다는 것이 보장되는 경우
- 값이 없는 상황 자체가 프로그램의 심각한 버그를 의미해서, 조용히 넘어가기보다 즉시 패닉으로 알리는 것이 오히려 바람직한 경우

반대로 "값이 없을 수도 있지만 일단 있다고 치고 넘어가자"는 식으로 `.?`를 습관적으로 사용하는 것은 위험합니다. 이런 코드는 평소에는 잘 동작하다가, 예상하지 못한 입력이 들어오는 순간 프로그램을 통째로 멈춰버립니다. 확신이 없다면 `if` 언랩이나 `orelse`로 null인 경우를 명시적으로 처리하는 쪽을 선택하세요.

## 세 가지 방법 비교

지금까지 살펴본 세 가지 방법을 정리하면 다음과 같습니다.

```zig
const maybe_number: ?i32 = get_number(); // null일 수도, 아닐 수도 있다고 가정

// 1. if 언랩: null인 경우와 아닌 경우를 모두 명시적으로 처리
if (maybe_number) |value| {
    std.debug.print("값: {d}\n", .{value});
} else {
    std.debug.print("값 없음\n", .{});
}

// 2. orelse: null이면 기본값을 대신 사용
const value_with_default = maybe_number orelse 0;

// 3. .?: null이 아니라고 확신할 때만 사용. 틀리면 패닉
const value_forced = maybe_number.?;
```

셋 중 어느 것을 골라야 할지는 "null인 경우에 무엇을 해야 하는가"에 따라 결정하면 됩니다. null인 경우를 별도의 로직으로 다뤄야 한다면 `if` 언랩을, 그 자리에서 바로 쓸 수 있는 대체값이 있다면 `orelse`를, null일 가능성이 논리적으로 없다고 확신한다면 `.?`를 사용하세요. 확신이 없을 때는 항상 `if` 언랩이나 `orelse`를 우선적으로 고려하는 것이 안전합니다.

## 옵셔널 포인터와 구조체

8장과 9장에서 배운 포인터, 구조체 지식을 옵셔널과 함께 사용하는 예를 살펴보겠습니다. 연결 리스트의 노드처럼, "다음 노드가 있을 수도 있고 없을 수도 있는" 상황은 옵셔널 포인터로 자연스럽게 표현됩니다.

```zig
const std = @import("std");

const Node = struct {
    value: i32,
    next: ?*Node = null,

    const Self = @This();

    fn print_all(self: *const Self) void {
        var current: ?*const Self = self;
        while (current) |node| {
            std.debug.print("{d} ", .{node.value});
            current = node.next;
        }
        std.debug.print("\n", .{});
    }
};

pub fn main() void {
    var third = Node{ .value = 3 };
    var second = Node{ .value = 2, .next = &third };
    var first = Node{ .value = 1, .next = &second };

    first.print_all(); // 1 2 3
}
```

`Node`의 `next` 필드는 `?*Node`, 즉 "다음 `Node`를 가리키는 포인터이거나 없음(null)"을 의미합니다. 마지막 노드인 `third`는 `next`를 지정하지 않아서 기본값인 `null`을 그대로 가집니다. `print_all`에서는 `while (current) |node| { ... }`로 `current`가 null이 아닌 동안 계속 다음 노드로 넘어갑니다. `current`가 결국 `null`이 되면 `while` 문이 자연스럽게 종료됩니다. 이처럼 옵셔널은 "리스트의 끝"이나 "아직 정해지지 않은 값"처럼 데이터 구조 안에서 값이 있을 수도 없을 수도 있는 지점을 표현하는 데 아주 자연스럽게 쓰입니다.

## null 안전성이 중요한 이유

이번 장을 마무리하면서, 왜 Zig가 이렇게까지 null을 엄격하게 다루는지 다시 짚어보겠습니다. C처럼 포인터가 기본적으로 null일 수 있는 언어에서는, 함수의 매개변수 타입만 보고는 그 포인터가 null일 수 있는지 알 방법이 없습니다. 그래서 프로그래머는 습관적으로 모든 포인터를 의심하며 방어적으로 null 검사를 넣거나, 혹은 반대로 "여기는 절대 null이 아닐 거야"라고 낙관하고 검사를 생략합니다. 두 경우 모두 문제가 있습니다. 앞의 경우는 정말로 null일 수 없는 곳에도 불필요한 검사 코드가 여기저기 흩어지고, 뒤의 경우는 예상이 틀렸을 때 프로그램이 알 수 없는 시점에 충돌합니다. Java나 다른 참조 기반 언어에서 널리 알려진 "널 포인터 예외(NullPointerException)"도 근본적으로 같은 문제에서 나옵니다. 참조 타입이라면 어디서든 null이 들어올 수 있으므로, 프로그래머가 모든 참조 사용 지점에서 이를 놓치지 않고 검사해야 하는데, 실제로는 놓치는 경우가 계속 생기는 것입니다.

Zig의 해법은 이 판단을 타입 시스템으로 옮기는 것입니다. 일반 타입과 일반 포인터는 절대로 null이 될 수 없다는 규칙을 컴파일러가 강제하기 때문에, 그런 값을 다루는 코드는 null 검사를 걱정할 필요가 없습니다. 반대로 값이 없을 수 있는 자리는 `?T`로 명시적으로 표시되므로, 그 값을 실제로 사용하려는 순간 컴파일러가 "이건 null일 수도 있는데, 그 경우를 처리했는지 확인해라"라고 강제로 요구합니다. `if` 언랩과 `orelse`는 이 요구를 안전하게 만족시키는 방법이고, `.?`는 그 요구를 프로그래머의 책임으로 넘기고 넘어가는 예외적인 탈출구입니다. 결과적으로 Zig 코드에서 "null 검사를 깜빡해서 생기는 버그"는 컴파일 시점에 대부분 걸러지며, 남은 위험은 `.?`처럼 코드에 뚜렷하게 표시된 지점으로 좁혀집니다.

## 요약

- `?T`는 "`T` 타입의 값이거나 `null`"을 의미하는 옵셔널 타입이다. Zig의 일반 타입과 일반 포인터(`*T`)는 null이 될 수 없으며, null이 필요한 자리는 반드시 `?T`나 `?*T`로 감싸야 한다.
- 옵셔널 값은 바로 연산이나 접근에 쓸 수 없다. 먼저 null 여부를 처리해야 한다.
- `if (opt) |value| { ... } else { ... }`는 null이 아닐 때와 null일 때를 모두 명시적으로 처리하는 가장 안전한 방법이다. `|*value|`로 캡처하면 옵셔널 안의 값을 포인터로 받아 직접 수정할 수 있다.
- `opt orelse default_value`는 옵셔널이 null이면 지정한 기본값을 사용하는 간결한 표현이다. `orelse return`, `orelse continue`처럼 흐름 제어와 함께 쓸 수도 있다.
- `opt.?`는 null이 아니라고 확신할 때 값을 강제로 꺼낸다. 실제로 null이면 그 자리에서 런타임 패닉이 발생하므로, 확신이 없을 때는 사용하지 않는다.
- Zig는 null이 될 수 있는 값을 타입 시스템(`?T`)으로 명시하도록 강제해서, 다른 언어에서 흔한 null 포인터 예외 같은 버그를 컴파일 시점에 예방한다.

3. 정수 슬라이스에서 특정 값과 같은 첫 번째 원소의 인덱스를 찾아 `?usize`를 반환하는 함수 `find_index(items: []const i32, target: i32) ?usize`를 작성하세요. 찾으면 인덱스를, 못 찾으면 `null`을 반환해야 합니다. (슬라이스는 13장에서 더 자세히 다루지만, 8장에서 배운 배열과 반복문 지식으로도 작성할 수 있습니다.)

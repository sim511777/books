## Zig다운 코드 스타일

### 이름 짓기 규칙

Zig 커뮤니티에는 공식적으로 정리된 이름 짓기 관례가 있고, 표준 라이브러리 전체가 이 관례를 일관되게 따르고 있습니다. 이 책에서 지금까지 작성한 모든 예제 코드도 같은 규칙을 따르고 있었습니다.

- **타입**은 `PascalCase`를 사용합니다. 구조체, 열거형, 유니온처럼 새로운 타입을 정의할 때는 첫 글자를 대문자로 시작하고 단어 경계마다 대문자를 씁니다. `Point`, `HttpRequest`, `TokenKind` 같은 이름이 여기에 해당합니다.
- **함수와 변수**는 `snake_case`를 사용합니다. 모든 글자를 소문자로 쓰고 단어 사이를 밑줄로 구분합니다. `calculate_area`, `user_count`, `is_valid` 같은 이름이 여기에 해당합니다.

```zig
const std = @import("std");

// 타입 이름: PascalCase
const Point = struct {
    x: f64,
    y: f64,
};

// 함수 이름, 매개변수 이름: snake_case
fn distance_from_origin(point: Point) f64 {
    return std.math.sqrt(point.x * point.x + point.y * point.y);
}

pub fn main() void {
    // 변수 이름: snake_case
    const origin_point = Point{ .x = 3.0, .y = 4.0 };
    const result_distance = distance_from_origin(origin_point);

    std.debug.print("distance = {d}\n", .{result_distance});
}
```

이 규칙이 왜 중요한지는 규칙 자체보다 규칙의 "일관성"에 있습니다. 코드를 읽을 때 이름의 대소문자 형태만 보고도 그것이 타입인지, 함수나 변수인지를 즉시 구별할 수 있다면, 코드를 이해하는 데 필요한 정신적 노력이 그만큼 줄어듭니다. 예를 들어 `Reader`라는 이름을 보면 별다른 설명 없이도 이것이 어떤 값의 타입이라는 것을 짐작할 수 있고, `read_line`이라는 이름을 보면 이것이 어떤 동작을 수행하는 함수라는 것을 짐작할 수 있습니다. 표준 라이브러리를 포함한 Zig 생태계 전체가 이 규칙을 따르기 때문에, 이 관례를 지키는 것만으로도 다른 사람이 짠 코드와 자신의 코드가 자연스럽게 섞여 들어갑니다.

### zig fmt로 포맷팅을 자동화하기

이름 짓기는 사람이 판단해야 하는 영역이지만, 들여쓰기나 줄바꿈, 중괄호 위치, 공백의 개수처럼 기계적으로 정해질 수 있는 부분까지 사람이 신경 쓸 필요는 없습니다. Zig는 이런 부분을 처리하는 공식 포맷터를 컴파일러에 내장하고 있습니다.

```bash
zig fmt src/main.zig
```

파일 하나를 지정하는 대신 폴더를 지정하면 그 안의 모든 `.zig` 파일을 한 번에 정리할 수 있습니다.

```bash
zig fmt .
```

`zig fmt`는 코드의 의미를 바꾸지 않으면서 형태만 표준적인 모습으로 다시 씁니다. 예를 들어 들여쓰기가 뒤섞여 있거나 한 줄에 억지로 여러 문장을 눌러 쓴 코드도, `zig fmt`를 한 번 돌리면 일관된 스타일로 정리됩니다.

```zig
// 정리하기 전
const std=@import("std");
pub fn main() void {
  const x=1; const y  =2;
    std.debug.print("{d}\n" , .{x+y});
}
```

```zig
// zig fmt를 적용한 뒤
const std = @import("std");
pub fn main() void {
    const x = 1;
    const y = 2;
    std.debug.print("{d}\n", .{x + y});
}
```

이 도구가 주는 실질적인 이점은 "스타일에 대한 논쟁을 없앤다"는 것입니다. 여러 사람이 함께 작업하는 프로젝트에서 중괄호를 어디에 둘지, 들여쓰기를 몇 칸으로 할지를 두고 논쟁하는 대신, 그냥 `zig fmt`가 정한 방식을 따르면 됩니다. 에디터가 파일을 저장할 때마다 자동으로 `zig fmt`를 실행하도록 설정해 두면, 포맷팅에 신경 쓸 일 자체가 사라지고 코드의 논리에만 집중할 수 있습니다. 좋은 Zig 코드를 쓰는 첫 번째 습관은 사실 "코드를 손으로 예쁘게 정리하려 하지 않는 것"이라고도 말할 수 있습니다.

## 에러를 무시하지 않는 습관

11장에서 우리는 Zig의 에러 처리가 `!T`라는 에러 유니온 타입을 중심으로 이루어진다는 것을 배웠습니다. 에러가 날 수 있는 함수를 호출할 때 Zig 컴파일러는 그 결과를 그냥 흘려버리는 것을 허용하지 않고, `try`나 `catch`로 반드시 처리하도록 강제합니다. 이 규칙 덕분에 Zig 코드에서는 "에러가 났는데 아무도 확인하지 않아서 조용히 잘못된 상태로 계속 진행되는" 상황이 문법적으로 봉쇄됩니다.

그런데 이 규칙을 지키면서도 실질적으로는 에러를 무시하는 것과 다름없는 코드를 짤 수 있습니다. 좋은 습관과 나쁜 습관을 나란히 놓고 비교해 보겠습니다.

```zig
const std = @import("std");

fn parse_port(text: []const u8) u16 {
    // 나쁜 습관: 에러가 나면 무조건 프로그램을 강제 종료한다.
    // 사용자가 잘못된 입력을 주는 것은 프로그램의 정상적인 실행 경로인데,
    // 이를 unreachable로 처리하면 실제로 그 경로에 도달했을 때 크래시로 이어진다.
    return std.fmt.parseInt(u16, text, 10) catch unreachable;
}
```

```zig
const std = @import("std");

fn parse_port(text: []const u8) !u16 {
    // 좋은 습관: 에러를 호출한 쪽으로 전파해서, 실제로 사용자 입력을 다루는
    // 위치에서 적절한 안내 메시지와 함께 처리할 수 있게 한다.
    return std.fmt.parseInt(u16, text, 10);
}

pub fn main() void {
    const port = parse_port("abc") catch |err| {
        std.debug.print("포트 번호를 해석할 수 없습니다: {}\n", .{err});
        return;
    };
    std.debug.print("port = {d}\n", .{port});
}
```

`catch unreachable`은 "이 실패는 절대로 일어날 수 없다"는 프로그래머의 확신을 코드로 표현하는 도구입니다. 문제는 사용자 입력, 파일 내용, 네트워크 응답처럼 프로그램 바깥에서 오는 값을 다룰 때는 이 확신이 거의 항상 근거가 없다는 점입니다. `catch unreachable`을 코드 곳곳에 습관적으로 붙이는 것은, 겉보기에는 에러를 처리한 것처럼 보이지만 실제로는 "에러가 나면 프로그램이 즉시 죽어도 된다"고 선언하는 것과 같습니다. 좋은 습관은 에러가 실제로 일어날 수 있는 경계(사용자 입력, 파일 입출력, 외부 시스템과의 통신)를 인식하고, 그 경계에서는 `try`로 에러를 상위로 전파하거나 `catch |err|`로 받아서 사용자에게 의미 있는 메시지를 보여 주는 것입니다. `catch unreachable`은 정말로 실패가 불가능하다는 것을 스스로 증명할 수 있는 상황(예: 이미 검증을 마친 상수 문자열을 파싱하는 경우)에서만 써야 합니다.

## 자원 해제는 defer로 바로 옆에

12장에서 살펴본 `defer`의 핵심 아이디어는 "자원을 획득하는 코드와 그것을 해제하는 코드를 최대한 가까이 붙여 놓는다"는 것입니다. 이 습관은 실수를 줄이는 데 직접적인 효과가 있습니다.

```zig
const std = @import("std");

fn read_and_process(allocator: std.mem.Allocator, path: []const u8) !void {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close(); // 열자마자 바로 defer로 닫는다

    const contents = try file.readToEndAlloc(allocator, 1024 * 1024);
    defer allocator.free(contents); // 할당하자마자 바로 defer로 해제한다

    std.debug.print("파일 크기: {d} 바이트\n", .{contents.len});
}
```

만약 `file.close()`와 `allocator.free(contents)`를 함수 맨 아래에 몰아서 적어 두었다면, 그 사이에 `return`이나 `try`로 함수를 일찍 빠져나가는 경로가 새로 생길 때마다 자원 해제 코드도 그 경로에 맞춰 새로 추가해야 합니다. 코드가 복잡해질수록 이런 경로를 빠뜨리기 쉽습니다. 반면 자원을 얻는 줄 바로 다음에 `defer`로 해제를 적어 두면, 함수 안에 새로운 탈출 경로가 몇 개나 생기더라도 해제 코드는 딱 한 번만 적으면 되고 절대 빠지지 않습니다.

이 습관은 초기화 도중 실패가 나는 경우까지 고려하면 `errdefer`로 확장됩니다.

```zig
const std = @import("std");

const Connection = struct {
    buffer: []u8,
    socket_id: i32,
};

fn open_connection(allocator: std.mem.Allocator) !Connection {
    const buffer = try allocator.alloc(u8, 4096);
    errdefer allocator.free(buffer); // 이후 단계에서 실패하면 buffer를 해제한다

    const socket_id = try create_socket(); // 실패할 수 있는 작업

    return Connection{ .buffer = buffer, .socket_id = socket_id };
}

fn create_socket() !i32 {
    return 42; // 예시를 위한 더미 구현
}
```

`buffer`를 할당한 직후에 `errdefer`를 붙여 두면, 그 뒤에 이어지는 `create_socket()`이 실패했을 때 이미 할당해 둔 `buffer`가 자동으로 해제됩니다. 함수가 성공적으로 끝나서 `Connection` 값을 반환할 때는 `errdefer`가 실행되지 않으므로, 반환된 `buffer`는 안전하게 살아 있습니다. "자원을 얻는 곳 바로 옆에 해제 계획을 적어 둔다"는 원칙은 정상 종료(`defer`)와 실패 종료(`errdefer`) 모두에 동일하게 적용됩니다.

## 내장 테스트: test 블록

Zig는 별도의 테스트 프레임워크를 설치하지 않아도 코드를 검증할 수 있는 기능을 언어 자체에 내장하고 있습니다. 바로 `test` 블록입니다.

```zig
const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a + b;
}

test "add는 두 정수를 더한다" {
    try std.testing.expect(add(2, 3) == 5);
}

test "add는 음수도 올바르게 처리한다" {
    try std.testing.expectEqual(@as(i32, -1), add(2, -3));
}
```

`test` 뒤에 문자열로 그 테스트가 무엇을 확인하는지 설명을 적고, 중괄호 안에 실제로 검증할 내용을 작성합니다. `std.testing.expect`는 전달받은 불리언 값이 `true`가 아니면 테스트를 실패로 표시하고, `std.testing.expectEqual`은 두 값이 같은지를 비교하면서 실패 시 두 값을 나란히 출력해 줍니다. `test` 블록 안의 검증 함수들은 실패할 경우 에러를 반환하도록 만들어져 있으므로, `test` 블록 자체도 하나의 "에러를 반환할 수 있는 함수"처럼 다루어지고 `try`로 그 에러를 그대로 위로 흘려보냅니다.

이렇게 작성한 테스트는 다음 명령으로 실행합니다.

```bash
zig test src/main.zig
```

이 명령은 파일 안에 있는 일반 코드(예: `pub fn main`)는 실행하지 않고, `test` 블록들만 찾아서 하나씩 실행한 뒤 몇 개가 통과하고 몇 개가 실패했는지 알려 줍니다. 17장에서 다룬 `build.zig`를 이용하면 `zig build test`처럼 프로젝트 전체의 테스트를 빌드 시스템의 일부로 편입시킬 수도 있습니다.

`test` 블록이 언어에 내장되어 있다는 점은 단순히 편리하다는 것 이상의 의미가 있습니다. 테스트를 검증하려는 함수와 같은 파일, 심지어 바로 아래에 적을 수 있기 때문에, 테스트는 "나중에 시간이 남으면 작성하는 것"이 아니라 "함수를 작성하는 행위의 일부"가 됩니다.

```zig
const std = @import("std");

fn clamp(value: i32, min: i32, max: i32) i32 {
    if (value < min) return min;
    if (value > max) return max;
    return value;
}

test "clamp는 범위를 벗어난 값을 경계값으로 자른다" {
    try std.testing.expectEqual(@as(i32, 0), clamp(-5, 0, 10));
    try std.testing.expectEqual(@as(i32, 10), clamp(15, 0, 10));
    try std.testing.expectEqual(@as(i32, 5), clamp(5, 0, 10));
}
```

함수를 작성한 바로 다음 줄에 그 함수가 지켜야 할 약속을 테스트로 남겨 두는 습관은, 코드를 나중에 고칠 때도 그 약속이 깨지지 않았는지 즉시 확인할 수 있는 안전망이 되어 줍니다.

## 되짚어보기: 이 책에서 배운 것들

여기까지 오는 동안 다룬 내용을 몇 개의 큰 줄기로 정리해 보겠습니다.

**기초 문법 (1장~6장)**: Zig가 무엇을 지향하는 언어인지에서 시작해, `const`와 `var`, 크기가 정해진 정수와 부동소수점 타입, 연산자, 제어문, 반복문까지 다른 언어에서도 익숙하게 볼 수 있는 개념들을 Zig의 문법으로 익혔습니다. 이 단계에서부터 이미 Zig의 성격이 드러났습니다. 암묵적인 타입 변환이 없고, 정수 오버플로우를 조용히 넘기지 않으며, 초기화되지 않은 값은 `undefined`로 명시해야 했습니다.

**함수와 데이터 구조 (7장~9장)**: 함수를 정의하는 방법, 포인터와 배열로 메모리를 직접 다루는 방법, 그리고 구조체로 데이터를 묶는 방법을 배웠습니다. Zig의 포인터는 C의 포인터만큼 직접적이지만, `*`(단일 항목)와 `[*]`(크기를 모르는 배열) 같은 구분을 통해 "이 포인터가 정확히 무엇을 가리키는가"를 타입 시스템 안에서 표현하려 한다는 점이 특징적이었습니다.

**부재와 실패를 다루는 방법 (10장~12장)**: 옵셔널 타입(`?T`)으로 "값이 없을 수 있음"을, 에러 유니온(`!T`)으로 "실패할 수 있음"을 각각 타입으로 표현하는 방법을 배웠습니다. 그리고 `defer`와 `errdefer`로 자원 해제를 실행 흐름과 무관하게 보장하는 방법을 배웠습니다. 이 세 장은 서로 강하게 얽혀 있습니다. 실패할 수 있는 자원 획득은 에러 유니온을 반환하고, 그 자원의 해제는 `defer`나 `errdefer`로 보장됩니다.

**메모리와 컴파일 타임 (13장~15장)**: 슬라이스로 배열의 일부 구간을 안전하게 참조하는 방법, `comptime`으로 컴파일 시점에 코드를 생성하거나 값을 계산하는 방법, 그리고 할당자(`Allocator`)를 명시적으로 전달해서 메모리 할당 방식을 함수 호출자가 결정할 수 있게 하는 방법을 배웠습니다.

**데이터 모델링과 실전 도구 (16장~18장)**: 열거형과 유니온으로 "여러 경우 중 하나"를 표현하는 방법, `build.zig`로 빌드 과정 자체를 코드로 기술하는 방법, 그리고 이번 장에서 다룬 코드 스타일과 테스트 습관을 배웠습니다.

이 모든 내용을 관통하는 세 가지 개념이 있다면, 그것은 **comptime**, **명시적 allocator**, **에러 유니온**입니다.

- **comptime**은 "코드가 실행되기 전에 컴파일러가 무엇을 할 수 있는가"에 대한 Zig의 답입니다. 제네릭 함수를 별도의 문법 없이 평범한 함수로 작성할 수 있게 해 주고, 타입 자체를 값처럼 다룰 수 있게 해 줍니다. 다른 언어의 매크로나 템플릿이 하는 일을, Zig에서는 "그냥 Zig 코드를 컴파일 시점에 실행한다"는 하나의 원리로 처리합니다.
- **명시적 allocator**는 "메모리를 어디서, 어떻게 가져올 것인가"라는 결정을 언어나 런타임이 대신 내려 주지 않겠다는 선언입니다. 함수가 메모리를 할당해야 한다면 그 함수의 시그니처에 `allocator: std.mem.Allocator`가 드러나야 하고, 호출하는 쪽은 그 함수가 정확히 어떤 메모리 전략(범용 힙, 고정 버퍼, 아레나 등)을 쓰게 될지를 스스로 선택할 수 있습니다.
- **에러 유니온**은 "실패할 수 있는 연산"과 "실패할 수 없는 연산"을 타입 수준에서 구분합니다. `!T`라는 반환 타입을 보는 순간, 코드를 읽는 사람은 이 함수를 호출할 때 실패 가능성을 반드시 고려해야 한다는 것을 압니다. 그리고 컴파일러는 그 고려를 실제로 강제합니다.

이 세 가지는 서로 독립적인 기능이 아니라, "숨기지 않는다"는 Zig의 하나의 태도가 서로 다른 상황에 적용된 결과라고 볼 수 있습니다. comptime은 컴파일러가 무엇을 하고 있는지를 숨기지 않고, allocator는 메모리가 어디서 오는지를 숨기지 않으며, 에러 유니온은 무엇이 실패할 수 있는지를 숨기지 않습니다.

## 앞으로 더 공부할 방향

이 책은 Zig 언어의 문법과 핵심 개념을 다루는 입문서로 기획되었기 때문에, 다루지 않은 것도 많습니다. 이 책을 마친 뒤 다음 방향들을 살펴보면 좋습니다.

- **표준 라이브러리를 더 깊이 탐구하기**: 이 책에서는 `std.debug.print`, `std.mem`, `std.fs`, `std.testing` 같은 일부만 다루었습니다. 표준 라이브러리에는 자료구조(`std.ArrayList`, `std.HashMap` 등), 문자열 처리, 네트워킹, 시간 처리 등 훨씬 많은 모듈이 있습니다.
- **C 라이브러리와의 FFI 연동**: Zig는 C 코드를 아주 자연스럽게 가져와 쓸 수 있도록 설계되어 있습니다. `@cImport`로 C 헤더 파일을 직접 가져오는 방법, 기존에 C나 C++로 작성된 라이브러리를 Zig 프로젝트에 연결하는 방법을 익히면 활용 범위가 크게 넓어집니다.
- **임베디드 타겟과 WebAssembly(WASM) 빌드**: 17장에서 살짝 언급한 타겟 지정 기능을 확장하면, 운영체제가 없는 마이크로컨트롤러를 위한 프리스탠딩(freestanding) 바이너리나, 브라우저에서 실행되는 WebAssembly 모듈을 같은 언어로 작성할 수 있습니다.

Zig는 아직 활발히 발전하고 있는 언어입니다. 버전이 올라가면서 문법 세부사항이 조금씩 바뀌기도 하므로, 공식 문서와 변경 로그를 꾸준히 확인하는 습관을 들이는 것도 중요합니다. 이 책에서 다진 기초 위에서, 이제는 직접 작은 프로젝트를 만들어 보면서 배운 개념들을 실전에서 부딪혀 보는 것을 권합니다.

## 요약

- 타입은 `PascalCase`, 함수와 변수는 `snake_case`로 이름 짓는 것이 Zig의 관례이며, `zig fmt`로 코드 형태를 자동으로 통일하는 습관을 들이는 것이 좋습니다.
- 에러가 날 수 있는 경계(사용자 입력, 파일, 네트워크 등)에서는 `catch unreachable`로 얼렁뚱땅 넘기지 말고, `try`나 `catch |err|`로 실제로 처리해야 합니다.
- 자원을 획득하는 코드 바로 옆에 `defer`(정상 종료 시 해제)나 `errdefer`(실패 시 해제)를 적어 두면, 함수의 탈출 경로가 늘어나도 자원 누수를 걱정하지 않을 수 있습니다.
- `test "설명" { ... }` 블록은 언어에 내장된 테스트 문법이며, `zig test` 명령이나 `build.zig`의 테스트 스텝으로 실행할 수 있습니다. 함수를 작성한 자리 바로 옆에 테스트를 남기는 습관을 권장합니다.
- 이 책 18개 장을 관통하는 세 가지 핵심 개념은 comptime, 명시적 allocator, 에러 유니온이며, 이들은 모두 "무엇이 일어나는지 숨기지 않는다"는 Zig의 태도를 서로 다른 영역에서 구현한 것입니다.
- 이후에는 표준 라이브러리 심화, C 라이브러리와의 FFI, 임베디드/WASM 타겟 빌드 등을 살펴보며 배운 지식을 실전 프로젝트로 확장해 나가기를 권합니다.

## 연습문제

1. 아래 코드에서 이름 짓기 관례를 위반한 부분을 모두 찾아 Zig의 관례에 맞게 고쳐 보세요.

   ```zig
   const point_struct = struct {
       X: f64,
       Y: f64,
   };

   fn CalculateDistance(P1: point_struct, P2: point_struct) f64 {
       return 0; // 계산 로직은 생략
   }
   ```

2. `catch unreachable`을 사용하는 것이 적절한 상황과 부적절한 상황을 각각 하나씩 예로 들고, 왜 그렇게 판단했는지 설명해 보세요.
3. 파일을 열고, 내용을 읽어 온 뒤 처리하는 함수를 작성하되, 자원 획득과 해제(`defer`/`errdefer`)를 각각 바로 옆에 짝지어 배치해 보세요. 그리고 만약 해제 코드를 함수 맨 끝에 몰아서 배치했다면 어떤 문제가 생길 수 있는지 설명해 보세요.
4. 정수를 인자로 받아 그 수가 소수인지 판별하는 함수를 작성하고, 최소 세 가지 경우(소수인 경우, 소수가 아닌 경우, 경계값인 경우)를 확인하는 `test` 블록을 작성해 `zig test`로 통과시켜 보세요.
5. 이 책에서 다룬 comptime, 명시적 allocator, 에러 유니온 중 하나를 골라, 만약 그 기능이 Zig에 없었다면 어떤 종류의 버그나 불편함이 생길 수 있을지 구체적인 예를 들어 설명해 보세요.

# 15장. 개방 클래스와 몽키패칭

[◀ 이전: 14장. 예외 처리](ch14-예외처리.md) | [📖 목차](00-목차.md) | [다음: 16장. 메타프로그래밍 기초 ▶](ch16-메타프로그래밍기초.md)


9장 클래스와 객체에서 우리는 `class` 키워드로 새로운 클래스를 정의하는 방법을 배웠습니다. 그런데 Ruby에서는 이미 정의된 클래스라고 해서 거기서 끝이 아닙니다. `String`이나 `Integer`처럼 Ruby 언어 자체에 내장된 클래스조차, 여러분이 원하면 언제든 다시 열어서 메서드를 추가하거나 기존 동작을 바꿀 수 있습니다. 이런 특징을 개방 클래스(open class)라고 부르며, 이를 이용해 다른 사람이 만든(혹은 언어가 기본으로 제공하는) 클래스의 동작을 몰래 바꿔치기하는 기법을 흔히 몽키패칭(monkey patching)이라고 부릅니다.

이번 장에서는 개방 클래스가 어떻게 동작하는지 살펴보고, 몽키패칭을 실제로 해 보면서 그 강력함과 동시에 위험성을 이해합니다. 그리고 위험성을 줄이면서 필요한 순간에만 안전하게 클래스를 확장하는 방법인 리파인먼트(refinement)와, 16장에서 본격적으로 다룰 메타프로그래밍의 기초 도구인 `class_eval`/`instance_eval`을 간단히 소개합니다.

## 클래스는 왜 "열려" 있는가

다른 언어에서는 클래스를 한 번 정의하면 그 정의가 고정되는 경우가 많습니다. 하지만 Ruby의 `class` 키워드는 사실 "새 클래스를 만든다"는 뜻이 아니라 "이 이름의 클래스를 연다. 없으면 새로 만든다"는 뜻에 가깝습니다. 그래서 같은 이름으로 `class` 블록을 또 작성하면, 새 클래스가 만들어지는 것이 아니라 기존 클래스가 다시 열리고 그 안에 작성한 내용이 추가됩니다.

```ruby
class Greeter
  def hello
    "안녕하세요"
  end
end

# 같은 클래스를 다시 연다.
class Greeter
  def bye
    "안녕히 가세요"
  end
end

g = Greeter.new
puts g.hello # => "안녕하세요"
puts g.bye   # => "안녕히 가세요"
```

`Greeter` 클래스는 두 번에 걸쳐 정의되었지만, 최종적으로는 `hello`와 `bye` 메서드를 모두 가진 하나의 클래스가 됩니다. 클래스 정의는 한 파일 안에서 끝날 필요도 없습니다. 큰 프로젝트에서는 하나의 클래스를 여러 파일에 나누어 열어 두고, 각 파일이 관련된 메서드 몇 개씩만 추가하는 방식으로 코드를 구성하기도 합니다.

이 특징은 여러분이 직접 만든 클래스에만 적용되는 것이 아닙니다. Ruby가 기본으로 제공하는 `String`, `Integer`, `Array`, `Hash` 같은 내장 클래스들도 똑같이 "열려 있는" 클래스입니다. Ruby 인터프리터 입장에서는 여러분이 만든 클래스나 표준 라이브러리의 클래스나 아무런 차이가 없기 때문입니다.

## 내장 클래스에 메서드 추가하기

개방 클래스의 성질을 이용하면 `String`이나 `Integer` 같은 내장 클래스에도 새 메서드를 추가할 수 있습니다. 예를 들어 문자열을 큰따옴표로 감싸서 강조하는 메서드를 `String`에 추가해 보겠습니다.

```ruby
class String
  def shout
    upcase + "!!!"
  end
end

puts "ruby is fun".shout  # => "RUBY IS FUN!!!"
puts "hello".shout        # => "HELLO!!!"
```

`shout`은 원래 `String` 클래스에 없던 메서드지만, 클래스를 다시 열어 정의하는 순간부터 모든 문자열 객체에서 마치 처음부터 있었던 메서드처럼 호출할 수 있게 됩니다. 3장 변수와 자료형에서 다룬 것처럼 `"ruby is fun"`은 `String` 클래스의 인스턴스이므로, `String`에 메서드를 추가하면 이미 만들어져 있던 문자열이든 앞으로 새로 만들 문자열이든 모두 그 메서드를 사용할 수 있습니다.

숫자를 다루는 `Integer` 클래스에도 같은 방식으로 메서드를 추가할 수 있습니다.

```ruby
class Integer
  def prime?
    return false if self < 2

    (2..Math.sqrt(self)).none? { |n| (self % n).zero? }
  end
end

puts 7.prime?   # => true
puts 10.prime?  # => false
puts 2.prime?   # => true
```

이제 모든 정수 리터럴이 `prime?`라는 메서드를 가지게 되었습니다. 12장 이터레이터와 Enumerable에서 배울 `none?`과 범위(`Range`) 객체를 활용하면, 이렇게 몇 줄만으로도 내장 타입에 새로운 기능을 자연스럽게 녹여 넣을 수 있습니다.

이처럼 내장 클래스를 확장하는 코드는 언뜻 매우 매력적으로 보입니다. 마치 언어 자체에 새로운 기능이 추가된 것처럼 자연스러운 문법으로 사용할 수 있기 때문입니다. 그러나 이 매력 뒤에는 분명한 대가가 따릅니다.

## 몽키패칭의 위험성

이렇게 이미 존재하는 클래스(특히 내가 만들지 않은 클래스)의 동작을 바꾸는 것을 몽키패칭이라고 부릅니다. 몽키패칭이 위험한 이유는 크게 두 가지입니다.

### 전역적으로 영향을 미친다

클래스에 메서드를 추가하면, 그 프로그램 안에서 해당 클래스를 사용하는 **모든 곳**에 영향을 미칩니다. 예를 들어 다음처럼 `String`에 `empty?`와 비슷한 이름의 메서드를 실수로 다시 정의했다고 가정해 보겠습니다.

```ruby
class String
  # 원래 있던 empty? 메서드를 실수로 덮어썼다.
  def empty?
    length <= 1  # 의도와 다르게 동작하는 정의
  end
end

puts "a".empty?  # => true (원래는 false여야 하는데!)
puts "".empty?   # => true
```

이 코드는 `String` 클래스에 이미 존재하던 `empty?` 메서드를 완전히 덮어씁니다. 문제는 이 변경이 지금 작성 중인 파일에만 적용되는 것이 아니라, 같은 프로세스 안에서 실행되는 **프로그램 전체**에 적용된다는 점입니다. 내가 작성하지 않은 다른 파일, 심지어 내가 사용하는 gem 내부 코드에서 `"foo".empty?`를 호출하는 부분이 있다면, 그 코드도 함께 영향을 받아 예상치 못한 결과를 만들어 냅니다.

### 라이브러리 충돌 가능성

더 골치 아픈 문제는 여러 라이브러리(gem)가 같은 클래스를 각자의 방식으로 몽키패칭할 때 벌어집니다. 예를 들어 라이브러리 A가 `Array#summarize`라는 메서드를 추가하고, 라이브러리 B도 우연히 같은 이름의 `Array#summarize`를 다른 의미로 추가했다고 해 보겠습니다. 두 라이브러리를 함께 사용하면 나중에 로드된 쪽의 정의가 먼저 정의된 쪽을 덮어써 버립니다. 어느 gem이 먼저 로드되느냐에 따라 동작이 달라지고, 이런 버그는 재현하기도 어렵고 원인을 찾기도 매우 힘듭니다.

이런 이유로, 몽키패칭은 강력하지만 "코드베이스 전체가 공유하는 이름 공간을 조용히 오염시키는" 위험한 도구로 여겨집니다. 특히 이름이 흔한 메서드(`empty?`, `to_s`, `each` 등)를 재정의할수록 충돌 가능성은 커집니다.

## 몽키패칭을 안전하게 쓰는 방법

몽키패칭 자체를 완전히 금지할 필요는 없습니다. 다만 다음과 같은 원칙을 지키면 위험을 크게 줄일 수 있습니다.

- **꼭 필요한 경우로 한정한다.** 새 클래스를 만들거나, 메서드 이름을 다르게 지어 충돌을 피할 수 있다면 그쪽을 먼저 고려합니다.
- **이름을 구체적으로 짓는다.** `empty?`처럼 이미 존재할 법한 흔한 이름 대신, `blank_for_report?`처럼 프로젝트 맥락이 드러나는 구체적인 이름을 사용하면 충돌 확률이 줄어듭니다.
- **기존 메서드가 있는지 확인한다.** `method_defined?`로 미리 확인하거나, `alias_method`로 원래 메서드를 보존해 두면 실수로 덮어쓰는 사고를 막을 수 있습니다.

```ruby
class String
  unless method_defined?(:shout)
    def shout
      upcase + "!!!"
    end
  end
end
```

- **꼭 전역으로 바꿔야 하는지 다시 생각한다.** 특정 파일이나 특정 상황에서만 새 동작이 필요하다면, 전역 몽키패칭 대신 아래에서 소개할 리파인먼트를 사용하는 것이 훨씬 안전합니다.

## 리파인먼트(refine)로 범위를 제한하기

Ruby는 몽키패칭의 "전역으로 퍼지는" 문제를 완화하기 위해 리파인먼트라는 기능을 제공합니다. 리파인먼트를 사용하면 클래스의 변경 사항을 프로그램 전체가 아니라, 그 변경을 명시적으로 "사용하겠다"고 선언한 범위 안에서만 적용할 수 있습니다.

```ruby
module ShoutRefinement
  refine String do
    def shout
      upcase + "!!!"
    end
  end
end
```

`refine String do ... end`는 `String` 클래스를 직접 수정하는 것이 아니라, `ShoutRefinement`라는 모듈 안에 "이런 변경을 담고 있다"는 정보를 저장해 둡니다. 이 변경을 실제로 활성화하려면 `using` 키워드로 해당 모듈을 명시적으로 불러와야 합니다.

```ruby
puts "ruby".respond_to?(:shout)  # => false (아직 활성화되지 않음)

using ShoutRefinement

puts "ruby".shout  # => "RUBY!!!" (using 이후부터 활성화됨)
```

`using`을 호출하지 않은 다른 파일이나 다른 스코프에서는 `shout` 메서드가 전혀 보이지 않습니다. 즉, 리파인먼트로 만든 변경은 기본적으로 "전역"이 아니라 "이 파일에서, 이 지점 이후부터"라는 국소적인 범위에만 영향을 미칩니다. 이 덕분에 다른 라이브러리나 다른 파일의 코드는 전혀 영향을 받지 않습니다.

리파인먼트는 몽키패칭이 꼭 필요하지만 그 영향 범위를 최소화하고 싶을 때, 예를 들어 특정 파일 안에서만 임시로 편의 메서드를 쓰고 싶을 때 유용한 선택지입니다. 다만 리파인먼트는 적용 범위 규칙이 다소 까다롭고(파일, 모듈, `using` 호출 위치에 따라 동작이 미묘하게 달라집니다) 완전한 기능을 다루려면 별도의 학습이 필요하므로, 이 책에서는 "이런 도구가 존재하며, 전역 몽키패칭보다 안전한 대안이 될 수 있다"는 정도로만 소개합니다.

## class_eval과 instance_eval 살짝 엿보기

지금까지는 `class Foo ... end` 문법으로 클래스를 직접 열었습니다. 그런데 Ruby에는 이미 존재하는 클래스나 객체를 문자열이나 블록을 이용해 동적으로 조작하는 방법도 있습니다. 그 대표적인 도구가 `class_eval`과 `instance_eval`입니다.

`class_eval`은 클래스 객체에게 "이 블록을 마치 네 본문인 것처럼 실행해 줘"라고 요청하는 메서드입니다.

```ruby
String.class_eval do
  def whisper
    downcase + "..."
  end
end

puts "RUBY".whisper  # => "ruby..."
```

이 코드는 앞서 본 `class String ... end` 방식과 거의 같은 효과를 냅니다. 차이가 있다면 `class_eval`은 블록을 받기 때문에, 클래스 이름을 변수에 담아 동적으로 넘기거나 블록 안에서 바깥 스코프의 변수를 그대로 참조할 수 있다는 점입니다.

```ruby
suffix = "..."

String.class_eval do
  define_method(:whisper) { downcase + suffix }
end
```

`instance_eval`은 이름이 비슷하지만 대상이 다릅니다. `class_eval`이 클래스에 메서드를 추가하는 데 쓰인다면, `instance_eval`은 특정 객체 하나만을 대상으로 그 안에서 코드를 실행합니다.

```ruby
name = "Ruby"

name.instance_eval do
  puts self       # => "Ruby" (self가 name 객체 자신이 됨)
  puts upcase     # => "RUBY"
end
```

`class_eval`과 `instance_eval`은 클래스나 객체를 "문자열이나 블록으로 동적으로 조작한다"는 점에서 메타프로그래밍의 출발점이라고 할 수 있습니다. 이 두 메서드가 왜 유용한지, 그리고 `define_method`나 `method_missing` 같은 더 강력한 도구와 어떻게 연결되는지는 16장 메타프로그래밍 기초에서 자세히 다룹니다.

## 요약

- Ruby의 클래스는 언제든 다시 열어서 메서드를 추가하거나 재정의할 수 있는 개방 클래스다. `class` 키워드는 새 클래스를 정의하기도 하지만, 이미 있는 클래스를 다시 여는 역할도 한다.
- `String`, `Integer` 같은 내장 클래스도 예외 없이 열려 있으므로, 이미 존재하는 클래스에 메서드를 추가하는 몽키패칭이 가능하다.
- 몽키패칭은 변경 사항이 프로그램 전체에 전역적으로 영향을 미치고, 여러 라이브러리가 같은 클래스를 각자 수정하면 충돌이 발생할 수 있다는 위험이 있다.
- 몽키패칭이 꼭 필요하다면 이름을 구체적으로 짓고, `method_defined?`로 기존 메서드 존재 여부를 확인하는 등 신중하게 사용해야 한다.
- `refine`과 `using`을 사용하는 리파인먼트는 클래스 변경의 영향 범위를 특정 파일이나 스코프로 제한할 수 있는 더 안전한 대안이다.
- `class_eval`은 클래스에, `instance_eval`은 개별 객체에 블록을 실행해 동적으로 메서드를 추가하거나 코드를 실행할 수 있게 해 주며, 이는 16장 메타프로그래밍의 기초가 된다.

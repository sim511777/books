## 18.1 Julia다운(idiomatic) 코드란

같은 결과를 내는 코드라도 그 언어의 관용적인 방식을 따르는 코드와 그렇지 않은 코드는 차이가 있습니다. 다른 언어의 습관을 그대로 옮겨 온 코드는 동작은 하지만 Julia 커뮤니티가 작성하는 코드와는 결이 다르고, 때로는 성능 면에서도 불리합니다. 여기서는 Julia다운 코드를 만드는 몇 가지 핵심 습관을 정리합니다.

### 이름 짓기 규칙

이 책 전체에서 일관되게 지켜 온 명명 규칙을 다시 한번 정리하면 다음과 같습니다.

- **함수와 변수**: `snake_case`를 사용합니다. `student_count`, `calculate_average`처럼 소문자와 밑줄로 단어를 구분합니다.
- **타입(구조체, 추상 타입)**: `PascalCase`를 사용합니다. `Point`, `AbstractShape`처럼 각 단어의 첫 글자를 대문자로 씁니다.
- **모듈**: 타입과 마찬가지로 `PascalCase`를 사용합니다. `LinearAlgebra`, `DataStructures`처럼 씁니다.
- **상수**: 관례적으로 대문자를 사용하는 경우가 많지만, Julia 표준 라이브러리에서도 `pi`, `Inf`처럼 소문자 상수가 섞여 있어 절대적인 규칙은 아닙니다.

```julia
# Julia다운 이름 짓기
struct Point
    x::Float64
    y::Float64
end

function distance_from_origin(point::Point)
    return sqrt(point.x^2 + point.y^2)
end

MAX_RETRY_COUNT = 3
```

### 원본을 변경하는 함수에는 !를 붙인다

8장에서 배열을 다룰 때 잠깐 언급했듯이, Julia 커뮤니티는 인자로 받은 값을 직접 수정하는 함수의 이름 끝에 느낌표(`!`)를 붙이는 관례를 철저히 지킵니다. 이 관례 덕분에 함수 이름만 보고도 "이 함수를 호출하면 내가 넘긴 값이 바뀔 수 있다"는 것을 짐작할 수 있습니다.

```julia
function double_values!(arr::Vector{<:Number})
    for i in eachindex(arr)
        arr[i] *= 2
    end
    return arr
end

numbers = [1, 2, 3]
double_values!(numbers)
println(numbers)   # [2, 4, 6] — 원본이 바뀜
```

반대로 원본은 그대로 두고 새로운 값을 반환하는 함수라면 `!` 없이 이름을 짓습니다. 표준 라이브러리의 `sort`와 `sort!`, `push!`와 (존재하지 않지만 개념적으로 대응되는) 순수 버전의 관계를 떠올리면 이 관례가 얼마나 널리 지켜지는지 알 수 있습니다.

```julia
original = [3, 1, 2]
sorted_copy = sort(original)     # original은 그대로
println(original)                # [3, 1, 2]
println(sorted_copy)             # [1, 2, 3]

sort!(original)                  # original 자체가 정렬됨
println(original)                # [1, 2, 3]
```

새로운 함수를 설계할 때 "이 함수가 인자를 변경하는가?"를 자문해 보고, 변경한다면 반드시 `!`를 붙이는 습관을 들이세요. 이는 사소해 보이지만 Julia 코드를 읽는 사람과의 중요한 약속입니다.

### 타입 안정성을 해치지 않는 습관

16장에서 성능 최적화의 핵심으로 **타입 안정성(type stability)**을 다뤘습니다. 타입 안정성이란 함수의 반환 타입이 입력값의 타입만 보고 미리 결정될 수 있는 성질을 말합니다. 좋은 코드 습관 중 상당수는 결국 타입 안정성을 자연스럽게 지키는 방향으로 이어집니다. 대표적인 몇 가지를 다시 짚어 보겠습니다.

```julia
# 타입이 바뀔 수 있는 코드
function unstable_value(flag)
    if flag
        return 1        # Int64
    else
        return 1.0       # Float64
    end
end

# 타입이 고정된 코드
function stable_value(flag)
    if flag
        return 1.0
    else
        return 2.0
    end
end
```

`unstable_value`는 `flag` 값에 따라 `Int64`를 반환할 수도, `Float64`를 반환할 수도 있습니다. 이런 함수를 호출하는 쪽에서는 반환 타입을 예측할 수 없으므로 Julia 컴파일러가 효율적인 코드를 만들기 어렵습니다. 함수를 작성할 때 "이 함수는 항상 같은 타입을 반환하는가?"를 습관적으로 점검하는 것이 좋습니다.

컨테이너를 초기화할 때 구체적인 타입을 명시하는 습관도 비슷한 맥락입니다.

```julia
# 타입이 Any로 추론되어 느려질 수 있음
container = []

# 타입이 명확해 성능에 유리함
container = Float64[]
```

빈 배열 `[]`은 원소 타입을 `Any`로 추론합니다. 이후에 어떤 타입의 값이든 넣을 수 있지만, 그만큼 컴파일러가 최적화할 정보가 줄어듭니다. 들어갈 값의 타입을 이미 알고 있다면 `Float64[]`, `String[]`처럼 구체적으로 선언하는 편이 좋습니다.

### 다중 디스패치를 활용한 확장

10장에서 배운 다중 디스패치는 Julia다운 코드의 뼈대를 이룹니다. 조건문으로 타입을 분기하는 대신, 타입별로 별도의 메서드를 정의하는 것이 Julia의 방식입니다.

```julia
# Julia답지 않은 방식: 함수 내부에서 타입을 검사
function area_v1(shape)
    if shape isa Circle
        return pi * shape.radius^2
    elseif shape isa Rectangle
        return shape.width * shape.height
    end
end

# Julia다운 방식: 타입별 메서드 정의
area(shape::Circle) = pi * shape.radius^2
area(shape::Rectangle) = shape.width * shape.height
```

두 번째 방식은 새로운 도형 타입이 추가될 때 기존 함수를 건드리지 않고 새 메서드만 추가하면 됩니다. 이는 11장에서 살펴본 구조체 설계와도 자연스럽게 이어집니다.

## 18.2 공식 스타일 가이드에서 배우는 몇 가지 관례

Julia 공식 문서는 코드 스타일에 대한 권장 사항을 제공합니다. 이 책에서 이미 자연스럽게 따라온 관례도 있지만, 몇 가지를 짚고 넘어갈 만합니다.

- **함수는 되도록 하나의 명확한 일만 하도록 작게 나눕니다.** 짧고 이름이 명확한 함수 여러 개가, 길고 여러 일을 하는 함수 하나보다 읽기 쉽고 재사용하기도 좋습니다.
- **불필요한 타입 어노테이션을 남발하지 않습니다.** 3장과 9장에서 보았듯 Julia는 타입 추론이 뛰어난 언어입니다. 함수 인자에 타입을 명시하는 것은 디스패치를 위한 것이지, 모든 변수에 타입을 강제로 못 박기 위한 것이 아닙니다. 지나치게 좁은 타입으로 인자를 제한하면 오히려 함수의 재사용성을 떨어뜨릴 수 있습니다.
- **들여쓰기는 공백 4칸을 사용합니다.** 탭 문자 대신 공백을 쓰는 것이 Julia 커뮤니티의 일반적인 관례입니다.
- **한 줄이 너무 길어지지 않게 적절히 줄바꿈합니다.** 특히 함수 인자가 많거나 파이프라인이 길게 이어질 때는 가독성을 위해 줄을 나눕니다.
- **`export`하는 이름은 신중하게 고릅니다.** 13장에서 다룬 모듈 작성 시, 외부에 공개하는 이름이 많아질수록 그 모듈을 사용하는 쪽의 이름 충돌 위험도 커집니다. 정말 공개가 필요한 이름만 `export`하는 것이 좋습니다.

이 관례들은 강제 규칙이 아니라 권장 사항입니다. 다만 여러 사람이 함께 작업하는 코드베이스에서는 이런 관례를 따르는 것이 협업의 마찰을 크게 줄여 줍니다.

## 18.3 테스트의 중요성과 Test 표준 라이브러리

아무리 스타일이 좋은 코드라도 의도한 대로 동작하지 않으면 소용이 없습니다. 함수를 작성할 때마다 REPL에 몇 가지 값을 넣어 눈으로 결과를 확인하는 것도 나쁘지 않지만, 코드가 변경될 때마다 매번 손으로 다시 확인하는 것은 비효율적이고 실수하기도 쉽습니다. **자동화된 테스트**는 이 문제를 해결합니다. 한 번 작성해 둔 테스트 코드는 몇 번이고 다시 실행해 "이 변경이 기존 동작을 망가뜨리지 않았는가"를 즉시 확인해 줍니다.

Julia는 `Test`라는 표준 라이브러리를 기본으로 제공합니다. 별도의 패키지를 설치할 필요 없이 `using Test`만으로 바로 사용할 수 있습니다.

### @test로 단일 조건 검사하기

`@test` 매크로는 뒤에 오는 표현식이 `true`인지 확인합니다. 참이면 조용히 통과하고, 거짓이면 실패를 알려 줍니다.

```julia
using Test

function add(a, b)
    return a + b
end

@test add(2, 3) == 5
@test add(-1, 1) == 0
```

```
Test Passed
Test Passed
```

만약 결과가 기대와 다르면 다음처럼 실패 내용을 자세히 알려 줍니다.

```julia
@test add(2, 2) == 5
```

```
Test Failed at REPL[3]:1
  Expression: add(2, 2) == 5
   Evaluated: 4 == 5
ERROR: There was an error during testing
```

기대값과 실제값을 함께 보여 주기 때문에, 단순히 `println`으로 값을 찍어 눈으로 비교하는 것보다 훨씬 빠르게 문제를 파악할 수 있습니다.

### @testset으로 테스트 묶기

관련된 테스트를 여러 개 작성하다 보면 이들을 하나의 단위로 묶어서 관리하고 싶어집니다. `@testset`은 이름을 붙인 테스트 그룹을 만들고, 그 안의 모든 `@test` 결과를 요약해서 보여 줍니다.

```julia
using Test

function is_even(n)
    return n % 2 == 0
end

@testset "is_even 함수 테스트" begin
    @test is_even(2) == true
    @test is_even(3) == false
    @test is_even(0) == true
    @test is_even(-4) == true
end
```

```
Test Summary:          | Pass  Total  Time
is_even 함수 테스트     |    4      4  0.0s
```

`@testset` 안에서 일부 테스트가 실패하더라도, 나머지 테스트는 계속 실행되고 마지막에 전체 통과/실패 개수가 요약되어 출력됩니다. 이 덕분에 한 번의 실행으로 여러 케이스의 성공 여부를 한눈에 파악할 수 있습니다.

테스트를 작성할 때는 정상적인 입력뿐 아니라 경계값(0, 음수, 빈 배열 등)과 예외 상황도 함께 검사하는 것이 좋습니다. 14장에서 배운 예외 처리와 연결지어, 특정 상황에서 예외가 발생하는지를 확인하고 싶다면 `@test_throws`를 사용할 수 있습니다.

```julia
function safe_divide(a, b)
    if b == 0
        throw(DivideError())
    end
    return a / b
end

@testset "safe_divide 예외 테스트" begin
    @test safe_divide(10, 2) == 5.0
    @test_throws DivideError safe_divide(10, 0)
end
```

작은 함수를 만들 때마다 짧은 `@testset`을 함께 작성하는 습관을 들이면, 나중에 코드를 리팩터링하거나 기능을 추가할 때 훨씬 안심하고 변경할 수 있습니다. 테스트는 "귀찮은 추가 작업"이 아니라 "미래의 나 자신을 돕는 안전망"이라고 생각하는 것이 좋습니다.

## 18.4 회고: 우리가 배운 것들

이 책의 18개 장을 관통하는 흐름을 되짚어 보겠습니다.

1장에서는 Julia가 왜 만들어졌는지, "빠르면서도 쓰기 쉬운 언어"라는 목표를 어떻게 달성하려 했는지 살펴보았습니다. 2장에서는 REPL이라는 Julia 특유의 대화형 환경에 익숙해졌고, 3장과 4장에서는 변수, 자료형, 연산자라는 기본 재료를 다뤘습니다. 5장과 6장의 제어문과 반복문은 프로그램의 흐름을 만드는 방법을, 7장의 함수는 코드를 재사용 가능한 단위로 묶는 방법을 알려 주었습니다. 8장에서는 배열과 브로드캐스팅을 통해 데이터를 다루는 Julia 특유의 벡터화된 사고방식을 익혔습니다.

그리고 9장과 10장, 여기서 우리는 이 책 전체에서 가장 중요한 전환점을 지났습니다. **9장의 타입 시스템**은 Julia가 단순히 "타입을 검사하는 언어"가 아니라, 타입 자체가 계층 구조를 이루며 프로그램 설계의 중심이 되는 언어라는 것을 보여 주었습니다. 추상 타입과 구체 타입의 구분, 타입 계층을 따라 내려가는 상속 구조는 이후 모든 장에서 반복해서 등장하는 개념이었습니다. **10장의 다중 디스패치**는 한 걸음 더 나아가, "어떤 코드를 실행할지"를 하나의 인자가 아니라 함수에 전달되는 모든 인자의 타입 조합으로 결정한다는, 다른 널리 쓰이는 언어에서는 좀처럼 볼 수 없는 방식을 소개했습니다. 이 두 장은 단순한 문법 설명이 아니라, **Julia라는 언어의 정체성 그 자체**입니다. 객체지향 언어의 메서드 오버라이딩과도 다르고, 단순한 함수 오버로딩과도 다른, 타입 계층 전체를 아우르는 디스패치 방식이야말로 Julia가 "과학 계산에는 느린 언어(Python, R)와 빠르지만 쓰기 어려운 언어(C, Fortran) 사이의 간극을 메운다"는 목표를 실현하는 핵심 장치입니다.

11장의 구조체는 이 타입 시스템 위에서 우리만의 데이터 모델을 만드는 방법이었고, 12장의 컬렉션(튜플, 딕셔너리, 세트)은 데이터를 조직하는 다양한 방식을 넓혀 주었습니다. 13장의 모듈과 패키지 관리는 코드를 재사용 가능한 단위로 배포하고 공유하는 Julia 생태계의 관문이었으며, 14장의 예외 처리는 예상치 못한 상황에서도 프로그램이 우아하게 대응하도록 만드는 방법을 다뤘습니다.

15장의 매크로는 코드를 데이터처럼 다루어 코드 자체를 생성하는, Julia의 메타프로그래밍 능력을 살짝 엿보는 시간이었습니다. 16장의 성능 최적화 기초는 타입 안정성이라는 개념을 중심으로 "왜 Julia가 빠를 수 있는지"와 "그 속도를 실제로 끌어내려면 어떻게 코드를 써야 하는지"를 연결 지었습니다. 그리고 17장에서는 멀티코어와 대기 시간을 다루는 병렬 및 동시성 프로그래밍의 기초를 살펴보았습니다.

이 모든 장을 하나로 꿰는 실은 결국 **타입**입니다. 변수의 타입(3장), 함수 인자의 타입에 따른 디스패치(7장, 10장), 타입 계층을 이용한 추상화(9장, 11장), 타입 안정성을 통한 성능(16장)까지, Julia에서 타입은 단순한 분류표가 아니라 프로그램을 설계하고 실행 속도를 결정짓는 핵심 축이었습니다. 이 관점을 몸에 익혔다면, 이 책의 목표는 이미 상당 부분 달성된 것입니다.

## 18.5 앞으로 더 공부할 방향

이 책은 Julia 언어 자체의 기초를 다지는 데 집중했습니다. 이제 여러분이 실제로 하고 싶은 작업에 따라 다음과 같은 방향으로 학습을 이어 갈 수 있습니다.

- **데이터 분석**: `DataFrames.jl`은 표 형태의 데이터를 다루는 핵심 패키지로, R의 데이터프레임이나 Python의 pandas와 비슷한 역할을 합니다. 데이터를 불러오고, 정제하고, 집계하는 작업에 필수적입니다.
- **시각화**: `Plots.jl`은 다양한 백엔드를 지원하는 범용 시각화 패키지입니다. 이 밖에도 `Makie.jl`처럼 인터랙티브하고 고성능인 시각화에 특화된 패키지도 있습니다.
- **머신러닝**: `Flux.jl`은 Julia로 작성된 딥러닝 프레임워크로, Julia의 다중 디스패치와 자동 미분 기능을 적극 활용합니다. 미분 가능 프로그래밍(differentiable programming)이라는 Julia 생태계의 독특한 강점을 경험할 수 있습니다.
- **성능 튜닝 심화**: 16장과 17장에서 다룬 내용은 시작에 불과합니다. `BenchmarkTools.jl`을 이용한 정밀 벤치마킹, 메모리 할당 추적, `@code_warntype`과 `@code_llvm`을 이용한 저수준 분석 등으로 더 깊이 들어갈 수 있습니다.
- **과학 계산과 수치 해석**: 미분방정식을 다루는 `DifferentialEquations.jl`, 최적화 문제를 다루는 `JuMP.jl` 등, Julia가 태생적으로 강점을 가진 과학 계산 분야의 패키지들도 살펴볼 만합니다.

어떤 방향으로 나아가든, 이 책에서 다진 타입 시스템과 다중 디스패치에 대한 이해는 흔들리지 않는 토대가 되어 줄 것입니다. Julia 생태계의 많은 패키지가 바로 이 두 가지 개념 위에서 서로 자연스럽게 맞물리도록 설계되어 있기 때문입니다.

## 요약

- 함수와 변수는 `snake_case`, 타입과 모듈은 `PascalCase`로 이름 짓는 것이 Julia의 명명 관례입니다.
- 인자를 직접 변경하는 함수의 이름 끝에는 `!`를 붙입니다. 이는 Julia 커뮤니티가 엄격하게 지키는 약속입니다.
- 함수의 반환 타입이 입력 타입만으로 결정되도록(타입 안정성) 코드를 작성하는 습관은 가독성뿐 아니라 성능에도 직결됩니다.
- 타입별로 조건문을 쓰는 대신 다중 디스패치로 메서드를 나누는 것이 Julia다운 확장 방식입니다.
- `Test` 표준 라이브러리의 `@test`와 `@testset`을 이용하면 코드의 정확성을 자동화된 방식으로 반복 확인할 수 있습니다. `@test_throws`로 예외 발생 여부도 검사할 수 있습니다.
- 이 책 전체를 관통하는 핵심은 **타입 시스템(9장)**과 **다중 디스패치(10장)**이며, 이 둘이야말로 Julia라는 언어의 정체성을 규정하는 개념입니다.
- 앞으로는 목적에 따라 `DataFrames.jl`(데이터 분석), `Plots.jl`(시각화), `Flux.jl`(머신러닝) 등 생태계의 패키지로 학습을 확장해 나갈 수 있습니다.

   function classify(x)

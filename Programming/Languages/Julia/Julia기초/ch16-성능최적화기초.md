# 16장. 성능 최적화 기초

[◀ 이전: 15장. 매크로 기초](ch15-매크로기초.md) | [📖 목차](00-목차.md) | [다음: 17장. 병렬 및 동시성 프로그래밍 기초 ▶](ch17-병렬및동시성프로그래밍기초.md)


1장에서 Julia가 탄생한 배경을 이야기하면서 **two-language problem**을 언급했습니다. Python이나 R처럼 배우기 쉽고 표현력이 좋은 언어로 프로토타입을 작성한 뒤, 정작 속도가 필요한 부분은 C나 Fortran으로 다시 작성해야 하는 딜레마 말입니다. Julia는 "쉽게 쓰면서도 빠르게 실행되는 언어"를 목표로 설계되었다고 했는데, 이번 장에서는 그 약속이 실제로 어떻게 지켜지는지, 그리고 그 약속을 지키기 위해 우리가 코드를 어떻게 작성해야 하는지를 살펴봅니다.

지금까지는 주로 "어떻게 하면 원하는 결과를 얻을 수 있는가"에 집중했다면, 이번 장은 "어떻게 하면 그 결과를 더 빠르고 효율적으로 얻을 수 있는가"에 관한 내용입니다. 성능 최적화는 그 자체로 깊이 있는 주제이지만, 이 장에서는 Julia를 사용하는 사람이라면 누구나 알아야 할 가장 기본적인 원칙만 다룹니다.

## 16.1 Julia는 two-language problem을 어떻게 해결하는가

1장에서 다룬 것처럼, two-language problem이 생기는 근본적인 이유는 대부분의 동적 언어(Python, R 등)가 코드를 한 줄씩 해석하며 실행하는 인터프리터 방식이거나, 설령 컴파일을 하더라도 변수의 타입이 실행 중에 계속 바뀔 수 있다는 전제 아래 매우 범용적이고 느린 코드를 생성하기 때문입니다.

Julia는 다른 전략을 택합니다. Julia는 **JIT(Just-In-Time) 컴파일** 방식을 사용하는데, 어떤 함수가 특정 타입의 인자들과 함께 처음 호출되는 순간, Julia는 그 구체적인 타입 조합에 맞춰 LLVM을 통해 최적화된 기계어 코드를 그 자리에서 생성합니다. 이후 같은 타입 조합으로 그 함수가 다시 호출되면, 이미 만들어둔 기계어 코드를 재사용하므로 매우 빠르게 실행됩니다.

이 과정에서 핵심적인 조건이 하나 있습니다. 함수 안에서 사용되는 변수들의 타입을 컴파일 시점에 컴파일러가 확실하게 알아낼 수 있어야 한다는 것입니다. 타입을 확실히 알 수 있다면 컴파일러는 마치 C 컴파일러가 하듯이 타입에 딱 맞는 효율적인 기계어를 생성할 수 있습니다. 반대로 타입을 확신할 수 없다면, 컴파일러는 "어떤 타입이 오더라도 대응할 수 있는" 안전하지만 느린 범용 코드를 생성할 수밖에 없습니다.

즉, Julia에서는 언어를 바꿀 필요 없이 **같은 Julia 코드 안에서 "타입을 컴파일러가 예측할 수 있게 작성하는 것"만으로 C에 준하는 속도**를 얻을 수 있습니다. 이것이 바로 Julia가 two-language problem을 해결하는 방식입니다. 그리고 이 조건, 즉 "타입을 예측 가능하게 유지하는 것"을 가리키는 말이 바로 다음 절에서 다룰 **타입 안정성**입니다.

## 16.2 타입 안정성이란

**타입 안정성(type stability)**이란, 함수에 특정 타입의 인자가 주어졌을 때 그 함수가 실행 경로와 무관하게 **항상 하나의 예측 가능한 구체 타입(concrete type)**을 반환하는 성질을 말합니다. 함수 본문을 실제로 실행해보지 않고, 인자의 타입만 보고도 반환값의 타입을 미리 알 수 있어야 타입 안정적이라고 할 수 있습니다.

타입이 불안정한 함수를 하나 만들어보겠습니다.

```julia
function unstable_pick(x)
    if x > 0
        return 1
    else
        return 1.0
    end
end
```

`unstable_pick`은 `x`가 양수이면 `Int64`인 `1`을, 그렇지 않으면 `Float64`인 `1.0`을 반환합니다. `x`의 타입을 알더라도(예를 들어 `x::Int64`), `x`의 **값**이 양수인지 아닌지는 실행해보기 전까지 알 수 없기 때문에, 컴파일러는 이 함수가 `Int64`를 반환할지 `Float64`를 반환할지 컴파일 시점에 확정할 수 없습니다. 이런 경우 컴파일러는 두 타입을 모두 담을 수 있는 `Union{Int64, Float64}`라는 애매한 타입을 다루는 코드를 생성해야 하고, 이는 하나의 구체 타입만 다루는 코드보다 훨씬 비효율적입니다.

같은 함수를 타입 안정적으로 고쳐보겠습니다.

```julia
function stable_pick(x)
    if x > 0
        return 1.0
    else
        return 1.0
    end
end
```

이제 두 갈래 모두 `Float64`를 반환하므로, 컴파일러는 `x`의 값과 무관하게 이 함수가 항상 `Float64`를 반환한다는 사실을 컴파일 시점에 확신할 수 있습니다. 실무에서는 이런 극단적인 예보다, 함수가 정상적인 경우에는 계산된 값을 반환하고 특정 조건에서는 `nothing`을 반환하는 경우처럼 자연스러워 보이지만 실제로는 타입이 불안정한 코드가 훨씬 흔하게 나타납니다.

```julia
function find_first_negative(arr)
    for (i, v) in enumerate(arr)
        if v < 0
            return i          # Int64를 반환
        end
    end
    return nothing             # Nothing을 반환 -> Union{Int64, Nothing}
end
```

이런 함수는 반환 타입이 `Union{Int64, Nothing}`이 되어 완전한 타입 안정성을 잃습니다. 다만 이 정도의 작은 `Union`은 Julia 컴파일러가 상당히 효율적으로 처리해주는 경우가 많아서, 무조건 나쁘다고 단정할 수는 없습니다. 중요한 것은 "타입 안정성이 성능에 영향을 준다"는 원리를 이해하고, 뒤에서 소개할 도구로 직접 확인하는 습관을 들이는 것입니다.

## 16.3 흔한 성능 함정

타입 안정성이 저절로 깨지는 대표적인 두 가지 상황을 살펴보겠습니다.

### 타입 표기 없는 전역 변수

REPL이나 스크립트 최상위 스코프에서 선언한 전역 변수는 프로그램 어디에서든 값(과 타입)이 바뀔 수 있습니다. 문제는 이런 전역 변수를 함수 안에서 그대로 사용할 때 발생합니다.

```julia
count = 10

function increment()
    global count
    count += 1
    return count
end
```

`count`는 `Int64` 값을 담고 있지만, 컴파일러 입장에서는 "이 전역 변수의 타입이 앞으로도 계속 `Int64`일 것"이라고 보장할 방법이 없습니다. 언제든 `count = "문자열"`처럼 다른 타입의 값이 대입될 수 있기 때문입니다. 그 결과 `increment` 함수는 `count`의 타입을 매번 실행 시점에 확인해야 하는 타입 불안정한 함수가 되어 버립니다.

가장 간단한 해결책은 이런 전역 변수를 `const`로 선언해서 타입이 바뀌지 않는다는 것을 컴파일러에게 알려주는 것입니다.

```julia
const MAX_RETRY = 3

function should_retry(attempt)
    return attempt < MAX_RETRY
end
```

`const`를 붙이면 해당 이름에는 처음 정의된 타입의 값만 계속 대입되도록 보장되므로, 컴파일러가 안심하고 최적화된 코드를 생성할 수 있습니다. 더 근본적인 해결책은 애초에 전역 변수에 의존하지 않고 필요한 값을 함수의 인자로 전달하는 것입니다. 7장에서 다룬 것처럼 함수는 입력을 인자로 받는 것이 기본 원칙이며, 성능 측면에서도 이 원칙을 지키는 것이 유리합니다.

### 서로 다른 타입을 섞은 컨테이너: Vector{Any}

8장과 12장에서 배열과 컬렉션을 다루면서, 배열은 원소들이 같은 타입일 때 `Vector{Int64}`, `Vector{Float64}`처럼 구체적인 타입 파라미터를 갖는다고 이야기했습니다. 그런데 서로 다른 타입의 값을 한 배열에 섞어 담으면 어떻게 될까요?

```julia
julia> mixed = [1, "둘", 3.0, :넷]
4-element Vector{Any}:
 1
  "둘"
 3.0
  :넷

julia> typeof(mixed)
Vector{Any}
```

원소 타입이 통일되지 않으니 Julia는 이 배열의 원소 타입을 가장 포괄적인 `Any`로 처리합니다. `Vector{Any}`는 각 원소가 실제로 어떤 타입인지 배열 자체의 타입 정보만으로는 알 수 없기 때문에, 원소에 접근할 때마다 그 원소가 정확히 어떤 타입인지 실행 시점에 확인하는 과정(박싱, 동적 디스패치)이 필요합니다. 이는 원소 타입이 고정된 `Vector{Int64}` 같은 배열을 순회하는 것보다 훨씬 느립니다.

```julia
using Random

typed_vec = rand(1_000_000)          # Vector{Float64}
any_vec = Vector{Any}(typed_vec)     # 같은 값을 담았지만 Vector{Any}

@time sum(typed_vec)
@time sum(any_vec)
```

두 벡터는 담고 있는 값 자체는 같지만, `any_vec`을 합산하는 쪽이 눈에 띄게 느리고 메모리도 훨씬 많이 사용하는 것을 `@time`으로 확인할 수 있습니다. 성능이 중요한 코드에서는 배열에 항상 하나의 구체적인 타입만 담도록 신경 쓰는 것이 좋습니다. 만약 정말로 서로 다른 종류의 데이터를 함께 다뤄야 한다면, `Vector{Any}`보다는 11장에서 다룬 구조체로 데이터를 묶거나 10장의 다중 디스패치를 활용하는 방향을 먼저 고려해 보는 것이 좋습니다.

## 16.4 @code_warntype으로 타입 안정성 점검하기

타입이 안정적인지 눈으로만 판단하기 어려울 때는 `@code_warntype` 매크로를 사용합니다. 이 매크로는 함수 호출을 실제로 실행하는 대신, 주어진 인자 타입에 대해 컴파일러가 각 변수와 표현식의 타입을 어떻게 추론했는지 보여줍니다.

```julia
julia> function unstable_pick(x)
           if x > 0
               return 1
           else
               return 1.0
           end
       end
unstable_pick (generic function with 1 method)

julia> @code_warntype unstable_pick(3)
```

이 명령을 REPL에서 실행하면 함수 내부의 변수들과 최종 반환 타입(`Body::`로 표시되는 부분)이 나열된 긴 출력이 나타납니다. `unstable_pick`처럼 타입이 불안정한 함수라면 반환 타입 자리에 `Union{Float64, Int64}`처럼 여러 타입을 아우르는 표시가 나타나고, 대부분의 터미널 환경에서는 이런 부분이 노란색이나 빨간색으로 강조되어 한눈에 문제를 알아볼 수 있게 해줍니다. 반면 `stable_pick`처럼 타입이 안정적인 함수는 반환 타입 자리에 `Float64`처럼 구체적인 타입 하나만 깔끔하게 표시됩니다.

`@code_warntype`이 출력하는 내용을 세세히 해석하는 방법은 이 책의 범위를 넘어서지만, "내가 작성한 함수가 타입 안정적인지 궁금할 때 확인할 수 있는 도구가 있다"는 사실과 기본적인 사용법(`@code_warntype 함수호출(...)`)만 기억해 두어도 충분합니다. 실제로 성능이 중요한 코드를 작성할 때는 함수를 작성한 뒤 `@code_warntype`을 한 번씩 돌려보는 습관을 들이는 것이 좋습니다.

## 16.5 @time으로 실행 시간과 메모리 할당량 확인하기

15장에서 소개한 `@time` 매크로는 성능을 점검하는 가장 기본적이면서도 강력한 도구입니다. 다시 한번 사용법을 확인해 보겠습니다.

```julia
julia> @time sum(rand(1_000_000))
  0.011234 seconds (2 allocations: 7.629 MiB)
500071.3220...
```

출력에서 눈여겨봐야 할 것은 시간뿐만이 아닙니다. 괄호 안의 `allocations`(할당 횟수)와 그 옆의 메모리 크기도 중요한 정보입니다. 같은 계산을 하더라도 불필요하게 많은 메모리를 할당하는 코드는 그렇지 않은 코드보다 대체로 느리며, 할당 횟수가 비정상적으로 많다면 십중팔구 타입 불안정성이나 불필요한 임시 배열 생성이 원인일 가능성이 큽니다.

`@time`을 사용할 때 반드시 기억해야 할 점이 하나 있습니다. Julia 함수는 특정 타입 조합으로 **처음** 호출될 때 컴파일이 함께 일어나기 때문에, 첫 호출의 `@time` 결과에는 실제 실행 시간뿐 아니라 컴파일에 걸린 시간까지 섞여 들어갑니다.

```julia
julia> f(x) = x^2 + 2x + 1;

julia> @time f(3.0)          # 첫 호출: 컴파일 시간이 포함되어 느리게 보임
  0.003812 seconds (1 allocation: 16 bytes)
16.0

julia> @time f(3.0)          # 두 번째 호출: 이미 컴파일된 코드를 재사용
  0.000000 seconds
16.0
```

그래서 실제 실행 성능을 측정하고 싶을 때는 같은 코드를 최소 한 번 먼저 실행해서 컴파일을 끝낸 뒤, 그 다음 호출을 `@time`으로 측정하는 것이 정확한 습관입니다. 또한 한 번의 측정 결과는 시스템 상황에 따라 오차가 있을 수 있으므로, 중요한 비교라면 여러 번 반복해서 실행해 보는 것이 안전합니다. 더 정밀하고 반복적인 벤치마크가 필요하다면 `BenchmarkTools`처럼 별도로 설치하는 패키지를 활용할 수 있는데, 패키지를 설치하고 관리하는 방법은 13장에서 다뤘습니다.

성능 최적화는 결국 "느리다고 느껴지는 코드를 막연히 고치는 것"이 아니라, `@time`으로 현재 상태를 측정하고, `@code_warntype`으로 원인을 살펴보고, 이 장에서 다룬 원칙(타입 안정성 유지, 전역 변수 주의, 컨테이너 타입 통일)에 따라 코드를 개선한 뒤, 다시 `@time`으로 개선 여부를 확인하는 반복적인 과정입니다. 이런 습관을 들이는 것만으로도 Julia 코드의 성능을 크게 끌어올릴 수 있습니다.

## 요약

- Julia는 함수가 특정 타입 조합으로 처음 호출될 때 그 타입에 맞는 기계어 코드를 즉석에서 생성하는 JIT 컴파일 방식을 사용합니다. 타입을 컴파일 시점에 예측할 수 있는 코드일수록 C에 준하는 속도를 낼 수 있으며, 이것이 Julia가 1장에서 언급한 two-language problem을 해결하는 방식입니다.
- **타입 안정성(type stability)**이란 함수가 주어진 입력 타입에 대해 실행 경로와 무관하게 항상 예측 가능한 하나의 구체 타입을 반환하는 성질입니다. 타입이 불안정하면 컴파일러는 `Union` 타입을 다루는 비효율적인 코드를 생성할 수밖에 없습니다.
- 타입 표기 없이 사용하는 전역 변수와, 서로 다른 타입을 섞어 담은 `Vector{Any}` 컨테이너는 대표적인 성능 함정입니다. 전역 변수는 `const`로 선언하거나 함수 인자로 전달하고, 컨테이너는 가능한 한 하나의 구체적인 타입으로 통일하는 것이 좋습니다.
- `@code_warntype`을 사용하면 함수가 타입 안정적인지, 반환 타입에 `Union`이나 `Any`가 섞여 있는지를 점검할 수 있습니다.
- `@time`으로 실행 시간과 메모리 할당량을 확인하는 습관을 들이면 성능 문제를 조기에 발견할 수 있습니다. 단, 첫 호출에는 컴파일 시간이 포함되므로 정확한 측정을 위해서는 같은 코드를 한 번 실행해 컴파일을 마친 뒤 다시 측정해야 합니다.

## 연습문제

1. 1장에서 다룬 two-language problem이 무엇인지 한 문단으로 요약하고, Julia의 JIT 컴파일 방식이 이 문제를 어떻게 완화하는지 설명해 보세요.
2. 다음 함수가 타입 안정적이지 않은 이유를 설명하고, 타입 안정적인 함수로 고쳐 보세요.
   ```julia
   function classify(n)
       if n % 2 == 0
           return "짝수"
       else
           return n
       end
   end
   ```
3. 전역 변수를 함수 안에서 그대로 사용하는 것이 왜 성능에 해로운지 설명하고, 이를 피하는 두 가지 방법을 제시해 보세요.
4. `[1, 2, 3]`과 `Any[1, 2, 3]`을 각각 만들어 `typeof()`로 타입을 비교해 보고, 두 배열에 대해 `sum()`을 `@time`으로 측정했을 때 어떤 차이가 나타나는지 관찰해 보세요.
5. 자신이 작성한 함수 하나를 골라 `@code_warntype`으로 점검해 보고, 반환 타입이 구체적인 타입 하나로 표시되는지 확인해 보세요. 만약 `Union`이 나타난다면 그 원인을 추측해 보세요.

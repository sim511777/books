# 13장. 모듈과 패키지 관리

[◀ 이전: 12장. 컬렉션(튜플, 딕셔너리, 세트)](ch12-컬렉션.md) | [📖 목차](00-목차.md) | [다음: 14장. 예외 처리 ▶](ch14-예외처리.md)


지금까지는 하나의 파일이나 REPL 세션 안에서 함수와 변수를 자유롭게 정의하고 사용해 왔습니다. 하지만 프로그램의 규모가 커지면 이름 충돌을 막고 코드를 논리적인 단위로 묶어야 할 필요가 생깁니다. Julia는 이를 위해 **모듈(module)**이라는 네임스페이스 도구를 제공합니다. 또한 다른 사람이 만든 코드를 가져와 쓰거나 자신의 코드를 재사용 가능한 형태로 배포하려면 **패키지(package)** 관리 체계를 이해해야 합니다. 이번 장에서는 모듈을 정의하는 방법, `using`과 `import`의 차이, 그리고 Julia의 패키지 관리자 Pkg를 다룹니다.

## 13.1 모듈이 필요한 이유

작은 스크립트를 작성할 때는 모든 함수와 변수 이름이 하나의 전역 공간에 존재해도 큰 문제가 없습니다. 하지만 여러 사람이 함께 작업하거나 여러 파일로 나뉜 큰 프로젝트에서는 서로 다른 곳에서 정의한 이름이 우연히 겹칠 수 있습니다.

```julia
julia> area(radius) = 3.14 * radius^2
area (generic function with 1 method)
```

만약 다른 파일에서도 `area`라는 이름으로 사각형의 넓이를 구하는 함수를 정의한다면, 나중에 정의한 함수가 앞의 정의를 덮어써 버립니다. 모듈은 이런 이름들을 독립된 공간에 담아, 서로 다른 모듈에 속한 같은 이름의 함수나 변수가 충돌 없이 공존할 수 있게 해 줍니다.

## 13.2 module로 네임스페이스 만들기

모듈은 `module`과 `end` 키워드로 정의합니다.

```julia
module Geometry

pi_value = 3.14159

function circle_area(radius)
    return pi_value * radius^2
end

function rectangle_area(width, height)
    return width * height
end

end
```

이 코드를 실행하면 `Geometry`라는 이름의 모듈이 만들어집니다. 모듈 안에서 정의한 함수나 변수는 기본적으로 모듈 바깥에서 바로 보이지 않고, `모듈이름.이름` 형태로 접근해야 합니다.

```julia
julia> Geometry.circle_area(2)
12.56596

julia> Geometry.rectangle_area(3, 4)
12
```

모듈 이름은 관례적으로 PascalCase(단어의 첫 글자를 대문자로 쓰는 방식)를 사용합니다. `Geometry`, `DataTools`처럼 씁니다.

모듈은 REPL에서 직접 정의할 수도 있지만, 실제로는 대부분 `.jl` 파일 하나에 모듈 하나를 정의하고 `include()`로 그 파일을 불러오는 방식을 사용합니다.

```julia
# geometry.jl 파일의 내용
module Geometry

function circle_area(radius)
    return pi * radius^2
end

end
```

```julia
julia> include("geometry.jl")

julia> Geometry.circle_area(2)
12.566370614359172
```

여기서 사용한 `pi`는 Julia에 기본으로 내장된 원주율 상수입니다.

## 13.3 export로 공개 심볼 지정하기

매번 `모듈이름.함수이름`처럼 길게 쓰는 것이 번거로울 수 있습니다. 모듈 안에서 `export` 키워드를 사용하면 특정 이름을 "외부에 공개하는 이름"으로 지정할 수 있고, 이렇게 지정된 이름은 `using`으로 모듈을 가져왔을 때 접두사 없이 바로 사용할 수 있습니다.

```julia
module Geometry

export circle_area, rectangle_area

function circle_area(radius)
    return pi * radius^2
end

function rectangle_area(width, height)
    return width * height
end

function internal_helper()
    return "이 함수는 export되지 않았습니다"
end

end
```

`export`는 모듈 정의 맨 위쪽에 쓰는 것이 일반적인 관례입니다. 위 예제에서 `circle_area`와 `rectangle_area`는 공개되었지만 `internal_helper`는 공개되지 않았습니다. `internal_helper`는 모듈 내부 구현에서만 사용하도록 의도한 함수라는 뜻입니다.

## 13.4 using과 import의 차이

모듈에 정의된 이름을 가져오는 방법에는 `using`과 `import` 두 가지가 있으며, 둘의 동작 방식에는 중요한 차이가 있습니다.

### using: export된 이름을 바로 사용

`using 모듈이름`을 쓰면 그 모듈이 `export`한 모든 이름을 접두사 없이 바로 쓸 수 있게 됩니다.

```julia
julia> using .Geometry

julia> circle_area(2)
12.566370614359172

julia> rectangle_area(3, 4)
12
```

(여기서 모듈 이름 앞의 점 `.`은 현재 코드에 이미 정의되어 있는 로컬 모듈을 가리킨다는 뜻입니다. Pkg로 설치한 외부 패키지를 쓸 때는 점 없이 `using DataFrames`처럼 씁니다.)

`export`되지 않은 이름은 `using`으로 가져와도 접두사 없이는 쓸 수 없고, 여전히 `Geometry.internal_helper()`처럼 전체 경로로 접근해야 합니다.

```julia
julia> internal_helper()
ERROR: UndefVarError: `internal_helper` not defined

julia> Geometry.internal_helper()
"이 함수는 export되지 않았습니다"
```

### import: 명시적으로 이름을 가져오기

`import`는 지정한 이름만 정확히 가져옵니다. `import 모듈이름`만 쓰면 `using`과 달리 export된 이름조차 접두사 없이는 쓸 수 없고, 항상 `모듈이름.이름` 형태로 접근해야 합니다.

```julia
julia> import .Geometry

julia> Geometry.circle_area(2)
12.566370614359172

julia> circle_area(2)
ERROR: UndefVarError: `circle_area` not defined
```

특정 이름만 콕 집어서 가져오고 싶다면 다음과 같이 씁니다.

```julia
julia> import .Geometry: circle_area

julia> circle_area(2)
12.566370614359172
```

이렇게 하면 `export` 여부와 관계없이 지정한 이름만 정확히 가져올 수 있습니다. `internal_helper`처럼 export되지 않은 이름도 `import`로 이름을 명시하면 가져올 수 있습니다.

```julia
julia> import .Geometry: internal_helper

julia> internal_helper()
"이 함수는 export되지 않았습니다"
```

### 언제 무엇을 쓸까

두 방식의 차이를 정리하면 다음과 같습니다.

| 방식 | 접두사 없이 사용 가능 | 가져오는 대상 |
|---|---|---|
| `using 모듈이름` | export된 이름만 | 모듈 전체 |
| `import 모듈이름` | 불가능 (항상 `모듈이름.이름`) | 모듈 전체 |
| `import 모듈이름: 이름1, 이름2` | 지정한 이름만 | 지정한 이름만 |

일반적으로 패키지를 가져다 쓸 때는 `using`이 훨씬 흔하게 사용됩니다. 반면 여러 모듈에서 같은 이름의 함수가 있어서 어디서 온 함수인지 명확히 구분하고 싶을 때, 혹은 아주 소수의 함수만 필요할 때는 `import`가 더 적합합니다.

또한 `import`로 가져온 함수에는 새로운 메서드를 추가(확장)할 수 있다는 실용적인 차이도 있습니다. 이는 10장에서 다룬 다중 디스패치와 관련된 내용으로, 기존 함수에 새로운 타입 조합에 대한 메서드를 정의하고 싶을 때는 `import Base: 함수이름` 형태로 해당 함수를 명시적으로 가져오는 관례가 널리 쓰입니다.

## 13.5 Pkg: Julia의 패키지 관리자

지금까지는 직접 만든 모듈을 다뤘지만, Julia의 진짜 강점은 전 세계 개발자들이 만들어 놓은 방대한 패키지 생태계에 있습니다. 이 패키지들을 설치하고 관리하는 도구가 바로 **Pkg**입니다.

### REPL의 Pkg 모드

Julia REPL에서 `]` 키를 누르면 프롬프트가 `julia>`에서 `pkg>`로 바뀌면서 Pkg 전용 모드로 들어갑니다. (REPL의 여러 모드에 대해서는 2장에서 살펴본 적이 있습니다.)

```julia
julia> ]
pkg> add JSON
```

`add` 명령은 지정한 패키지를 설치합니다. 설치가 끝나면 `Backspace` 키를 눌러 다시 일반 `julia>` 모드로 돌아올 수 있습니다.

패키지를 제거하려면 `remove`(또는 줄여서 `rm`) 명령을 사용합니다.

```julia
pkg> remove JSON
```

현재 환경에 설치된 패키지 목록은 `status`(줄여서 `st`) 명령으로 확인합니다.

```julia
pkg> status
```

### Pkg.add()로 코드에서 설치하기

`]` 모드 대신 일반 Julia 코드 안에서 `Pkg` 모듈의 함수를 호출해 같은 작업을 할 수도 있습니다. 스크립트나 설치 자동화 코드에서는 이 방식이 유용합니다.

```julia
julia> using Pkg

julia> Pkg.add("JSON")

julia> Pkg.remove("JSON")

julia> Pkg.status()
```

`]` 모드의 `add`, `remove`, `status` 명령은 각각 `Pkg.add()`, `Pkg.remove()`, `Pkg.status()` 함수와 동일한 작업을 수행합니다. 대화식으로 작업할 때는 `]` 모드가 간편하고, 스크립트에 포함시켜야 할 때는 `Pkg` 함수 호출 방식이 적합합니다.

## 13.6 Project.toml과 Manifest.toml

패키지를 설치하면 현재 작업 중인 프로젝트 폴더에 두 개의 파일이 만들어지거나 갱신됩니다.

- **Project.toml**: 이 프로젝트가 직접 의존하는 패키지 이름과 버전 범위를 기록합니다. 사람이 읽고 관리하기 쉬운 상위 수준의 목록입니다.
- **Manifest.toml**: Project.toml에 적힌 패키지들이 실제로 의존하는 다른 패키지들까지 포함해, 정확히 어떤 버전이 설치되었는지를 낱낱이 기록합니다. 이 파일은 Pkg가 자동으로 관리하며 사람이 직접 편집하지 않는 것이 원칙입니다.

간단히 비유하면 Project.toml은 "이 프로젝트에는 A와 B 패키지가 필요하다"는 장보기 목록이고, Manifest.toml은 그 장보기 목록을 실제로 채우기 위해 구매한 모든 물건(A, B는 물론 A와 B가 내부적으로 사용하는 C, D까지)의 영수증이라고 할 수 있습니다.

두 파일이 함께 있으면 다른 컴퓨터에서도 정확히 동일한 패키지 버전 조합을 재현할 수 있습니다. 프로젝트 폴더를 그대로 옮기거나 깃(Git) 저장소에 두 파일을 함께 커밋해 두면, 다음 명령 하나로 동일한 환경을 복원할 수 있습니다.

```julia
pkg> instantiate
```

`instantiate`는 현재 폴더의 Project.toml과 Manifest.toml을 읽어, 거기에 기록된 패키지들을 정확히 그 버전으로 설치합니다.

## 13.7 프로젝트별 독립 환경

Julia의 패키지 환경은 프로젝트 단위로 독립적으로 관리하는 것을 권장합니다. 이런 방식을 흔히 **가상환경(virtual environment)**이라고 부르는데, Python 등 다른 언어를 접해 본 독자라면 익숙한 개념일 것입니다.

기본적으로 Pkg는 전역 환경(홈 디렉터리 아래의 공용 환경)에 패키지를 설치합니다. 하지만 프로젝트마다 필요한 패키지 버전이 다를 수 있으므로, 프로젝트별로 별도의 환경을 만들어 사용하는 것이 안전합니다.

새 프로젝트 폴더에서 다음과 같이 하면 그 폴더 전용 환경을 활성화할 수 있습니다.

```julia
pkg> activate .
```

이 명령을 실행하면 현재 폴더에 새로운 Project.toml이 만들어지고(또는 이미 있다면 그것을 사용하고), 이후 `add`로 설치하는 패키지는 전역 환경이 아니라 이 프로젝트의 Project.toml/Manifest.toml에 기록됩니다.

프로젝트별로 독립된 환경을 사용하면 다음과 같은 장점이 있습니다.

- 프로젝트 A는 어떤 패키지의 1.0 버전을, 프로젝트 B는 같은 패키지의 2.0 버전을 사용해도 서로 충돌하지 않습니다.
- 프로젝트를 다른 사람과 공유하거나 다른 컴퓨터로 옮길 때, Project.toml/Manifest.toml만 함께 전달하면 `instantiate` 한 번으로 동일한 실행 환경을 만들 수 있습니다.
- 실험적으로 이런저런 패키지를 설치해 보다가 문제가 생겨도, 그 프로젝트 환경만 삭제하고 새로 시작하면 되므로 전역 환경이 지저분해지지 않습니다.

현재 어떤 환경이 활성화되어 있는지는 `pkg>` 프롬프트 옆에 괄호로 표시되는 환경 이름으로 확인할 수 있고, `status` 명령으로도 확인할 수 있습니다.

## 13.8 자주 쓰이는 패키지 소개

Julia 생태계에는 수천 개의 등록된 패키지가 있습니다. 이 책은 입문서이므로 각 패키지의 자세한 사용법을 다루지는 않지만, 앞으로 실제 프로젝트를 진행하며 마주칠 가능성이 높은 대표적인 패키지 몇 가지의 이름과 용도만 간단히 소개합니다.

- **DataFrames.jl**: 표 형태(행과 열)의 데이터를 다루기 위한 패키지입니다. 스프레드시트나 데이터베이스 테이블과 비슷한 형태의 데이터를 불러오고, 가공하고, 집계하는 데 사용됩니다.
- **Plots.jl**: 그래프와 차트를 그리기 위한 시각화 패키지입니다. 선 그래프, 막대 그래프, 산점도 등 다양한 그림을 몇 줄의 코드로 그릴 수 있습니다.
- **CSV.jl**: CSV(쉼표로 구분된 값) 형식의 파일을 읽고 쓰는 데 특화된 패키지로, 주로 DataFrames.jl과 함께 사용됩니다.
- **Flux.jl**: 딥러닝 모델을 만들고 학습시키기 위한 머신러닝 패키지입니다.
- **JuMP.jl**: 수리 최적화 문제(선형 계획, 정수 계획 등)를 정의하고 푸는 데 사용되는 패키지입니다.
- **Test**(표준 라이브러리): Julia에 기본 포함된 패키지로, 코드가 의도한 대로 동작하는지 검증하는 테스트 코드를 작성할 때 사용합니다.

이 패키지들은 각각 `Pkg.add("패키지이름")`으로 설치한 뒤 `using 패키지이름`으로 불러와 사용합니다. 구체적인 사용법은 각 패키지의 공식 문서에서 확인할 수 있으며, 데이터 분석이나 머신러닝처럼 특정 분야에 집중한 책이나 자료를 통해 더 깊이 배울 수 있습니다.

## 요약

- `module`~`end`로 모듈을 정의하면 함수와 변수를 독립된 네임스페이스에 담아 이름 충돌을 방지할 수 있습니다.
- 모듈 안에서 `export`로 지정한 이름은 `using`으로 가져왔을 때 접두사 없이 바로 사용할 수 있습니다.
- `using 모듈이름`은 export된 이름을 그대로 노출시키고, `import 모듈이름`은 항상 `모듈이름.이름` 형태로 명시적으로 접근해야 합니다. `import 모듈이름: 이름`으로 특정 이름만 콕 집어 가져올 수도 있습니다.
- Julia의 패키지 관리자 Pkg는 REPL의 `]` 모드(`add`, `remove`, `status` 등)와 `Pkg.add()` 같은 함수 호출 양쪽으로 사용할 수 있습니다.
- Project.toml은 프로젝트가 직접 필요로 하는 패키지 목록을, Manifest.toml은 실제로 설치된 모든 패키지의 정확한 버전을 기록합니다. `instantiate` 명령으로 이 두 파일을 바탕으로 동일한 환경을 재현할 수 있습니다.
- `pkg> activate .`로 프로젝트별 독립 환경(가상환경)을 만들면, 프로젝트마다 서로 다른 패키지 버전을 충돌 없이 사용할 수 있습니다.
- DataFrames.jl, Plots.jl, CSV.jl, Flux.jl, JuMP.jl 등은 각각 데이터 처리, 시각화, 파일 입출력, 머신러닝, 최적화 분야에서 널리 쓰이는 대표적인 패키지입니다.

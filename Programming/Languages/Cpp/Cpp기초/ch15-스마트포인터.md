## 15.1 다시 떠올려보는 `new`/`delete`의 위험

9장에서는 `new`로 힙에 메모리를 할당하고, 사용이 끝나면 반드시 `delete`로 해제해야 한다고 배웠다. 이 규칙은 간단해 보이지만, 실제 프로그램에서는 지키기가 생각보다 어렵다. 다음 코드를 보자.

```cpp
void process_data() {
    int* buffer = new int[1000];

    if (some_condition()) {
        return;  // buffer를 delete하지 않고 함수가 끝나버린다
    }

    delete[] buffer;
}
```

`some_condition()`이 참이면 함수는 `delete[]`를 실행하지 못한 채 반환된다. 이렇게 할당한 메모리를 해제하지 못하고 잃어버리는 현상을 메모리 누수(memory leak)라고 부른다. 문제는 이런 실수가 코드를 처음 작성할 때는 잘 드러나지 않고, 조건 분기가 늘어나거나 예외가 발생하는 경로가 생기면서 조용히 누적된다는 점이다. 16장에서 다룰 예외 처리와 결합되면 상황은 더 나빠진다. `new`와 `delete` 사이에서 예외가 던져지면, 그 사이의 `delete` 호출은 아예 실행되지 않고 함수를 빠져나가 버린다.

```cpp
void risky_function() {
    Resource* res = new Resource();
    do_something_that_might_throw();  // 여기서 예외가 발생하면
    delete res;                       // 이 줄은 절대 실행되지 않는다
}
```

즉, 원시 포인터(raw pointer)를 직접 `new`/`delete`로 관리하는 방식은 코드가 복잡해질수록 실수할 여지가 늘어난다. C++은 이 문제를 언어 차원에서 해결하기 위해 스마트 포인터(smart pointer)라는 도구를 표준 라이브러리에 포함시켰다.

## 15.2 RAII 원칙과 스마트 포인터

9장에서 잠깐 언급했던 RAII(Resource Acquisition Is Initialization)는 "자원의 획득과 해제를 객체의 생명주기에 묶는다"는 원칙이다. 객체가 생성될 때 자원을 확보하고, 객체가 소멸될 때(스코프를 벗어날 때) 소멸자에서 자원을 자동으로 해제하면, 프로그래머가 직접 `delete`를 호출할 필요가 없어진다. 스코프를 벗어나는 경로가 `return`이든, `break`든, 심지어 예외 때문이든 상관없이 소멸자는 반드시 호출되기 때문이다.

스마트 포인터는 바로 이 RAII 원칙을 포인터에 적용한 클래스다. 스마트 포인터 객체는 내부에 원시 포인터를 하나 가지고 있으면서, 자신의 소멸자에서 그 포인터가 가리키는 메모리를 `delete`한다. 즉 스마트 포인터 변수가 스코프를 벗어나는 순간 자동으로 메모리가 해제된다.

```cpp
#include <memory>

void safe_process_data() {
    std::unique_ptr<int[]> buffer(new int[1000]);

    if (some_condition()) {
        return;  // buffer의 소멸자가 자동으로 호출되어 메모리가 해제된다
    }
}  // 여기서도 buffer가 소멸하면서 메모리가 해제된다
```

C++ 표준 라이브러리는 `<memory>` 헤더에 두 가지 대표적인 스마트 포인터를 제공한다. 소유권을 오직 하나의 객체만 갖는 `std::unique_ptr`와, 여러 객체가 소유권을 공유할 수 있는 `std::shared_ptr`이다.

## 15.3 `std::unique_ptr` : 단독 소유권

`std::unique_ptr`는 가리키는 자원을 단 하나의 소유자만 가질 수 있도록 강제하는 스마트 포인터다. 복사(copy)를 하려고 하면 컴파일 에러가 발생하며, 소유권을 넘기고 싶으면 `std::move`를 사용해 이동(move)해야 한다. 이동 시맨틱스의 자세한 원리는 17장에서 다시 다룬다.

```cpp
#include <memory>
#include <iostream>

class Widget {
public:
    Widget(int id) : id_(id) {
        std::cout << "Widget " << id_ << " 생성\n";
    }
    ~Widget() {
        std::cout << "Widget " << id_ << " 소멸\n";
    }
    void greet() const {
        std::cout << "Widget " << id_ << " 입니다\n";
    }
private:
    int id_;
};

int main() {
    std::unique_ptr<Widget> ptr1 = std::make_unique<Widget>(1);
    ptr1->greet();

    // std::unique_ptr<Widget> ptr2 = ptr1;  // 컴파일 에러: 복사 불가
    std::unique_ptr<Widget> ptr2 = std::move(ptr1);  // 소유권 이동은 가능

    if (ptr1 == nullptr) {
        std::cout << "ptr1은 더 이상 아무것도 소유하지 않는다\n";
    }
    ptr2->greet();

    return 0;
}  // ptr2가 소멸하면서 Widget이 자동으로 소멸된다
```

객체를 생성할 때는 `new`를 직접 쓰지 않고 `std::make_unique<T>(생성자 인자...)`를 사용하는 것이 권장된다. `make_unique`는 예외 안전성 측면에서도 더 안전하고, 코드에서 `new`라는 키워드가 사라지므로 소유권 관리가 스마트 포인터에 완전히 위임되었다는 점이 명확해진다.

`unique_ptr`는 함수의 반환값으로도 자연스럽게 쓸 수 있다. 반환되는 순간 이동이 일어나므로 성능 손실도 없다.

```cpp
std::unique_ptr<Widget> create_widget(int id) {
    return std::make_unique<Widget>(id);
}
```

배열을 관리할 때는 `std::unique_ptr<int[]>`처럼 배열 형태로 선언할 수 있으며, 이 경우 소멸자에서 `delete[]`가 호출된다. 다만 14장에서 배운 `std::vector`를 쓸 수 있는 상황이라면 `vector`가 더 안전하고 편리하므로, 배열용 `unique_ptr`는 크기가 고정된 저수준 버퍼를 다룰 때 정도로 제한적으로 사용하는 것이 좋다.

## 15.4 `std::shared_ptr` : 공유 소유권과 참조 카운트

여러 객체가 하나의 자원을 함께 소유해야 하는 경우도 있다. 예를 들어 여러 개의 데이터 구조가 같은 캐시 객체를 참조하는 경우다. 이럴 때는 `std::shared_ptr`를 사용한다. `shared_ptr`는 내부적으로 참조 카운트(reference count)를 유지하며, `shared_ptr`가 복사될 때마다 카운트가 1 증가하고, 소멸될 때마다 1 감소한다. 카운트가 0이 되는 순간, 즉 마지막 소유자가 사라지는 순간에만 실제로 `delete`가 호출된다.

```cpp
#include <memory>
#include <iostream>

int main() {
    std::shared_ptr<Widget> ptr1 = std::make_shared<Widget>(10);
    std::cout << "참조 카운트: " << ptr1.use_count() << "\n";  // 1

    {
        std::shared_ptr<Widget> ptr2 = ptr1;  // 복사 가능, 카운트 증가
        std::cout << "참조 카운트: " << ptr1.use_count() << "\n";  // 2
        ptr2->greet();
    }  // ptr2가 소멸하면서 카운트가 다시 1로 감소

    std::cout << "참조 카운트: " << ptr1.use_count() << "\n";  // 1

    return 0;
}  // ptr1도 소멸하면서 카운트가 0이 되고, 이때 Widget이 실제로 소멸된다
```

`unique_ptr`와 마찬가지로 `shared_ptr`도 직접 `new`를 쓰기보다 `std::make_shared<T>(...)`로 생성하는 것이 권장된다. `make_shared`는 객체와 참조 카운트를 담는 제어 블록을 한 번의 메모리 할당으로 처리하므로 `shared_ptr<T>(new T(...))`보다 효율적이다.

`shared_ptr`를 사용할 때 주의할 점 하나는 순환 참조(circular reference)다. 객체 A가 B를 `shared_ptr`로 가리키고, B도 A를 `shared_ptr`로 가리키면 두 객체의 참조 카운트는 서로를 붙잡고 있어 영원히 0이 되지 않는다. 이런 경우를 대비해 표준 라이브러리는 소유권 없이 대상을 참조만 하는 `std::weak_ptr`를 제공하는데, 이 챕터에서는 개념만 짧게 언급하고 넘어간다. 실무에서 순환 참조가 의심되면 관계 중 한쪽을 `weak_ptr`로 바꾸는 것을 검토하면 된다.

## 15.5 `unique_ptr`와 `shared_ptr`, 언제 어떤 것을 쓸까

두 스마트 포인터의 소유권 모델은 근본적으로 다르다. 아래 그림은 이 차이를 보여준다.

```text
                    unique_ptr vs shared_ptr 소유권 모델

   unique_ptr : 단독 소유권          |    shared_ptr : 공유 소유권 (참조 카운트)
                                     |
   +------------------------+       |    +------------------+
   | unique_ptr<Widget> ptr |       |    | shared_ptr ptr1  |----+
   +-----------+------------+       |    +------------------+    \
               |                    |                              \
               v                    |    +------------------+       v
   +------------------------+       |    | shared_ptr ptr2  |----+  +--------------+
   |      Widget 객체         |       |    +------------------+     \-| Widget 객체   |
   |         (heap)          |       |                            /  |   (heap)     |
   +------------------------+       |    +------------------+   /   +------+-------+
                                     |    | shared_ptr ptr3  |--+           |
   소유자는 오직 하나뿐               |    +------------------+              v
   복사(copy) 불가, 이동(move)만 가능  |                            +----------------------+
                                     |                            | 참조 카운트 : 3         |
   +------------------------+       |                            +----------------------+
   | ptr가 범위를 벗어나면       |       |
   | 소멸자가 자동으로            |       |    shared_ptr를 복사하면 카운트 +1
   | delete 호출                |       |    shared_ptr가 소멸하면 카운트 -1
   +------------------------+       |
                                     |    +--------------------------+
                                     |    | 참조 카운트가 0이 되는 순간    |
                                     |    | 마지막 소유자가 delete 호출    |
                                     |    +--------------------------+
   ------------------------------------------------------------------------
   두 경우 모두 소멸자가 자동으로 호출되어 메모리 해제를 보장한다 (RAII 원칙)
```

일반적인 원칙은 이렇다.

- **기본값은 `unique_ptr`다.** 자원을 소유하는 곳이 코드 상에서 명확히 한 곳뿐이라면 `unique_ptr`를 쓴다. 소유권이 명확하면 코드를 읽는 사람이 "이 자원은 언제 해제되는가"를 즉시 파악할 수 있고, 참조 카운트를 관리하는 추가 비용도 없다.
- **소유권을 여러 곳에서 공유해야 할 때만 `shared_ptr`를 쓴다.** 예를 들어 10장에서 다룬 객체를 여러 컨테이너나 여러 다른 객체가 동시에 참조해야 하고, 그중 누가 마지막까지 살아있을지 코드 작성 시점에 확정할 수 없는 경우다.
- **소유권이 필요 없다면 스마트 포인터 자체가 필요 없을 수도 있다.** 단순히 어떤 객체를 "빌려서" 잠깐 참조하는 함수 매개변수라면 원시 포인터나 참조(9장 참고)로 충분하다. 스마트 포인터는 소유권을 표현하는 도구이지, 모든 포인터를 대체해야 하는 것은 아니다.

## 15.6 원시 포인터로 직접 `new`/`delete`를 피해야 하는 이유

정리하면, 원시 포인터에 직접 `new`로 메모리를 할당하고 `delete`로 해제하는 코드는 다음과 같은 위험을 늘 안고 있다.

1. 여러 반환 경로나 예외 경로 중 하나라도 `delete`를 빼먹으면 메모리 누수가 발생한다.
2. 같은 메모리를 두 번 `delete`하면 정의되지 않은 동작(undefined behavior)이 발생한다.
3. 소유권이 누구에게 있는지 코드만 봐서는 알기 어려운 경우가 많다.

스마트 포인터는 이 세 가지 문제를 소멸자 호출이라는 언어의 기본 메커니즘으로 해결한다. 그래서 현대 C++ 코드에서는 "직접 `new`를 호출하는 코드가 보이면 의심하라"는 말이 있을 정도로, `new`/`delete`를 직접 쓰는 대신 `make_unique`/`make_shared`를 쓰는 것이 관례가 되었다. 18장에서 다룰 좋은 C++ 코드 작성 습관에서도 이 원칙은 핵심 항목 중 하나로 다시 등장한다.

## 요약

- 원시 포인터를 직접 `new`/`delete`로 관리하면 반환 경로나 예외 경로에서 해제를 빼먹어 메모리 누수가 발생하기 쉽다.
- RAII 원칙은 자원의 획득과 해제를 객체의 생명주기(생성자/소멸자)에 묶어 이 문제를 해결하며, 스마트 포인터는 이 원칙을 포인터에 적용한 클래스다.
- `std::unique_ptr`는 단독 소유권을 표현하며 복사할 수 없고 이동만 가능하다. 생성은 `std::make_unique`를 사용한다.
- `std::shared_ptr`는 참조 카운트를 통해 공유 소유권을 표현하며, 카운트가 0이 될 때 자원이 해제된다. 생성은 `std::make_shared`를 사용한다.
- 소유권이 하나뿐이면 `unique_ptr`를 기본으로 쓰고, 여러 곳에서 소유권을 공유해야 할 때만 `shared_ptr`를 쓴다.
- 순환 참조 문제를 피하려면 소유권이 없는 관찰용 포인터인 `std::weak_ptr`를 고려할 수 있다.

## 연습문제

1. 원시 포인터로 `new`/`delete`를 직접 관리하는 코드에서 메모리 누수가 발생하는 상황을 하나 만들고, 이를 `std::unique_ptr`로 바꿔 해결해 보라.
2. `std::unique_ptr<Widget> a = std::make_unique<Widget>(1);` 다음에 `std::unique_ptr<Widget> b = a;`를 작성하면 어떤 컴파일 에러가 발생하는지 확인하고, 그 이유를 설명해 보라.
3. `std::shared_ptr<Widget>`를 세 개의 변수에 복사한 뒤, 각 변수가 스코프를 벗어날 때마다 `use_count()`가 어떻게 변하는지 출력해 보라.
4. 클래스 `Node`가 `std::shared_ptr<Node>` 타입의 `next` 멤버를 가지도록 연결 리스트를 만들고, 두 노드가 서로를 가리키게 했을 때 소멸자가 호출되지 않는 현상을 관찰해 보라. 이 문제를 `std::weak_ptr`로 어떻게 해결할 수 있을지 생각해 보라.
5. 함수가 특정 자원의 소유권을 다른 함수로 넘겨야 하는 상황과, 단지 잠깐 빌려주기만 하면 되는 상황을 각각 하나씩 예로 들고, 어떤 방식(값 반환, `unique_ptr`, 참조, 원시 포인터)이 적합한지 설명해 보라.

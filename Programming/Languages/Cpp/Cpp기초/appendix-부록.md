## A. STL 컨테이너·알고리즘 치트시트

14장에서 다룬 표준 템플릿 라이브러리(STL)의 핵심 컨테이너와 자주 쓰는 알고리즘을 정리합니다.

### A.1 주요 컨테이너

| 컨테이너 | 헤더 | 특징 | 대표 상황 |
|---|---|---|---|
| `std::vector` | `<vector>` | 동적 배열, 끝에 추가/삭제가 빠름, 임의 접근(`[]`)이 O(1) | 순서가 있는 데이터를 담는 기본 선택 |
| `std::array` | `<array>` | 크기가 컴파일 시점에 고정된 배열, 스택에 저장됨 | 크기가 절대 바뀌지 않는 고정 길이 데이터 |
| `std::deque` | `<deque>` | 양쪽 끝에서 추가/삭제가 모두 빠름 | 앞뒤로 데이터를 자주 넣고 빼는 큐 |
| `std::list` | `<list>` | 이중 연결 리스트, 임의 위치 삽입/삭제가 빠름, 임의 접근은 느림(O(n)) | 중간 삽입/삭제가 빈번하고 순차 접근만 필요할 때 |
| `std::set` | `<set>` | 정렬된 상태를 유지하는 중복 없는 집합 | 중복 없이, 항상 정렬된 상태로 값을 관리 |
| `std::map` | `<map>` | 키로 정렬된 키-값 쌍 저장 | 키를 통해 값을 조회하되 정렬 순서도 필요할 때 |
| `std::unordered_set` | `<unordered_set>` | 해시 기반 집합, 평균 O(1) 조회 | 정렬이 필요 없고 조회 속도가 중요할 때 |
| `std::unordered_map` | `<unordered_map>` | 해시 기반 키-값 저장, 평균 O(1) 조회 | 정렬이 필요 없는 빠른 키-값 조회 |
| `std::stack` | `<stack>` | LIFO(후입선출) 어댑터, 보통 `deque` 위에 구현 | 되돌리기, 괄호 짝 검사 등 |
| `std::queue` | `<queue>` | FIFO(선입선출) 어댑터 | 작업 대기열, BFS 탐색 등 |
| `std::priority_queue` | `<queue>` | 항상 최댓값(또는 최솟값)을 먼저 꺼낼 수 있는 어댑터 | 우선순위가 있는 작업 처리 |

가장 먼저 익혀야 할 컨테이너는 `std::vector`입니다. 대부분의 경우 "일단 벡터로 시작해서, 실제로 성능 문제가 확인되면 다른 컨테이너로 바꾼다"는 접근이 실용적입니다.

### A.2 컨테이너 공용 멤버 함수

| 멤버 함수 | 의미 |
|---|---|
| `size()` | 현재 원소 개수 반환 |
| `empty()` | 원소가 하나도 없으면 `true` |
| `clear()` | 모든 원소 제거 |
| `begin()`, `end()` | 첫 원소를 가리키는 반복자, 마지막 다음 위치를 가리키는 반복자 |
| `push_back(value)` | (순서 컨테이너) 끝에 원소 추가 |
| `pop_back()` | (순서 컨테이너) 마지막 원소 제거 |
| `insert(pos, value)` | 지정한 위치(또는 키)에 원소 삽입 |
| `erase(pos)` | 지정한 위치(또는 키)의 원소 제거 |
| `find(key)` | (연관 컨테이너) 키를 찾아 반복자 반환, 없으면 `end()` |
| `at(index)` | 범위를 검사하며 원소 접근, 범위를 벗어나면 `std::out_of_range` 예외(16장) |

### A.3 자주 쓰는 알고리즘 (`<algorithm>`)

| 알고리즘 | 의미 | 간단한 사용 예 |
|---|---|---|
| `std::sort(first, last)` | 범위를 오름차순으로 정렬 | `std::sort(v.begin(), v.end());` |
| `std::sort(first, last, comp)` | 사용자 정의 비교자로 정렬 | `std::sort(v.begin(), v.end(), std::greater<int>());` |
| `std::find(first, last, value)` | 값을 찾아 반복자 반환, 없으면 `last` | `auto it = std::find(v.begin(), v.end(), 42);` |
| `std::count(first, last, value)` | 값과 일치하는 원소 개수 | `int n = std::count(v.begin(), v.end(), 0);` |
| `std::max_element` / `std::min_element` | 최댓값 / 최솟값을 가리키는 반복자 | `*std::max_element(v.begin(), v.end());` |
| `std::accumulate(first, last, init)` | 합계 계산 (`<numeric>` 헤더 필요) | `std::accumulate(v.begin(), v.end(), 0);` |
| `std::reverse(first, last)` | 범위를 뒤집음 | `std::reverse(v.begin(), v.end());` |
| `std::unique(first, last)` | 인접한 중복 원소를 제거(정렬 후 사용 권장) | `v.erase(std::unique(v.begin(), v.end()), v.end());` |
| `std::for_each(first, last, fn)` | 각 원소에 함수(람다) 적용 | `std::for_each(v.begin(), v.end(), [](int x){ ... });` |
| `std::transform(first, last, out, fn)` | 각 원소를 변환해 다른 곳에 저장 | `std::transform(v.begin(), v.end(), out.begin(), fn);` |
| `std::all_of` / `std::any_of` / `std::none_of` | 조건을 모두/하나라도/아무도 만족하는지 검사 | `std::all_of(v.begin(), v.end(), pred);` |

거의 모든 알고리즘은 "시작 반복자, 끝 반복자(그리고 필요하면 조건/비교 함수)"라는 동일한 패턴을 따릅니다. 이 패턴에 익숙해지면 새로운 알고리즘을 만나도 사용법을 금방 짐작할 수 있습니다.

## B. 연산자 우선순위표

4장에서 배운 연산자들의 우선순위를 정리합니다. 표에서 위쪽에 있을수록 먼저 계산됩니다. 같은 칸에 있는 연산자는 우선순위가 같으며, 결합 방향(좌에서 우로 묶이는지, 우에서 좌로 묶이는지)에 따라 계산 순서가 정해집니다.

| 우선순위 | 연산자 | 설명 | 결합 방향 |
|---|---|---|---|
| 1 (가장 높음) | `::` | 범위 지정 | 좌→우 |
| 2 | `()` `[]` `.` `->` `++`(후위) `--`(후위) | 함수 호출, 배열 첨자, 멤버 접근, 후위 증감 | 좌→우 |
| 3 | `++`(전위) `--`(전위) `+`(단항) `-`(단항) `!` `~` `(type)` `sizeof` `&`(주소) `*`(역참조) | 전위 증감, 단항 부호, 논리/비트 NOT, 형변환, 주소/역참조 | 우→좌 |
| 4 | `*` `/` `%` | 곱셈, 나눗셈, 나머지 | 좌→우 |
| 5 | `+` `-` | 덧셈, 뺄셈 | 좌→우 |
| 6 | `<<` `>>` | 비트 시프트 | 좌→우 |
| 7 | `<` `<=` `>` `>=` | 관계 비교 | 좌→우 |
| 8 | `==` `!=` | 동등 비교 | 좌→우 |
| 9 | `&` | 비트 AND | 좌→우 |
| 10 | `^` | 비트 XOR | 좌→우 |
| 11 | `\|` | 비트 OR | 좌→우 |
| 12 | `&&` | 논리 AND | 좌→우 |
| 13 | `\|\|` | 논리 OR | 좌→우 |
| 14 | `?:` | 삼항 조건 연산자 | 우→좌 |
| 15 | `=` `+=` `-=` `*=` `/=` `%=` `<<=` `>>=` `&=` `^=` `\|=` | 대입 및 복합 대입 | 우→좌 |
| 16 (가장 낮음) | `,` | 쉼표 연산자 | 좌→우 |

실무에서 특히 자주 헷갈리는 순서는 다음과 같습니다.

- `*`, `/`, `%`(4번)이 `+`, `-`(5번)보다 먼저 계산됩니다. `a + b * c`는 `a + (b * c)`와 같습니다.
- 비트 연산자(`&`, `^`, `\|`)는 관계/동등 비교(7, 8번)보다 우선순위가 낮습니다. 그래서 `if (flags & MASK == 0)`처럼 괄호 없이 쓰면 `==`가 먼저 계산되어 의도한 결과가 나오지 않습니다. `if ((flags & MASK) == 0)`처럼 괄호로 의도를 명시해야 합니다.
- `&&`가 `||`보다 우선순위가 높습니다. `a || b && c`는 `a || (b && c)`로 계산됩니다.
- 대입 연산자는 우선순위가 매우 낮고 우에서 좌로 묶이므로 `a = b = c`는 `a = (b = c)`로 계산됩니다.

우선순위를 정확히 외우기보다는, 조금이라도 헷갈리는 조합이라면 괄호를 명시적으로 쓰는 것이 훨씬 안전하고, 코드를 읽는 사람에게도 의도를 분명히 전달합니다.

## C. 기본 자료형 크기표

3장에서 다룬 것처럼 기본 자료형의 정확한 크기는 플랫폼과 컴파일러에 따라 달라질 수 있습니다. 아래 표는 오늘날 널리 쓰이는 64비트 플랫폼(예: 64비트 Windows/Linux, `g++`나 `clang++` 기본 설정)에서 흔히 관찰되는 크기입니다. 실제 크기는 항상 `sizeof`로 직접 확인하는 것이 정확합니다.

| 자료형 | 흔히 관찰되는 크기 | 비고 |
|---|---|---|
| `bool` | 1바이트 | |
| `char` | 1바이트 | 표준이 보장하는 유일한 정확한 크기(1바이트) |
| `short` | 2바이트 | |
| `int` | 4바이트 | |
| `long` | 4바이트(Windows) / 8바이트(Linux, macOS) | 플랫폼별로 가장 크게 갈리는 타입 |
| `long long` | 8바이트 | C++11부터 표준에 포함 |
| `float` | 4바이트 | IEEE 754 단정도 |
| `double` | 8바이트 | IEEE 754 배정도 |
| `long double` | 8, 12, 16바이트 등 | 플랫폼/컴파일러마다 차이가 큼 |
| 포인터(`T*`) | 8바이트 (64비트 플랫폼) | 32비트 플랫폼에서는 4바이트 |

### C.1 크기가 고정된 정수 타입 (`<cstdint>`)

파일 포맷이나 네트워크 프로토콜처럼 플랫폼에 관계없이 정확한 크기가 필요한 경우, 다음과 같은 고정 크기 타입을 사용합니다.

| 타입 | 크기 | 표현 범위(부호 있음 기준) |
|---|---|---|
| `int8_t` / `uint8_t` | 1바이트 | -128 ~ 127 / 0 ~ 255 |
| `int16_t` / `uint16_t` | 2바이트 | -32,768 ~ 32,767 / 0 ~ 65,535 |
| `int32_t` / `uint32_t` | 4바이트 | 약 -21억 ~ 21억 / 0 ~ 약 42억 |
| `int64_t` / `uint64_t` | 8바이트 | 약 -922경 ~ 922경 / 0 ~ 약 1844경 |

```cpp
#include <cstdint>
#include <iostream>

int main() {
    std::cout << "int32_t 크기: " << sizeof(int32_t) << " bytes\n";
    std::cout << "int64_t 크기: " << sizeof(int64_t) << " bytes\n";
}
```

## D. 더 공부하고 싶다면: 참고 자료를 찾는 방법

이 책 한 권으로 C++의 모든 세부 사항을 다룰 수는 없습니다. 앞으로 더 깊이 있는 내용이 필요할 때는 다음과 같은 유형의 자료를 활용하는 것을 권장합니다. (특정 책이나 사이트를 나열하는 대신, 어떤 종류의 자료를 어떤 상황에 찾아야 하는지를 기준으로 정리합니다.)

- **언어/표준 라이브러리 레퍼런스 사이트**: 특정 함수나 클래스의 정확한 매개변수, 반환값, 예외 발생 조건을 확인하고 싶을 때는 표준 라이브러리 레퍼런스를 검색합니다. `std::vector::insert`가 정확히 어떤 반복자를 반환하는지, `std::string::substr`의 두 번째 인자가 시작 위치인지 길이인지처럼 세부 사항을 확인하는 용도로 특히 유용합니다.
- **컴파일러 공식 문서**: 사용 중인 컴파일러(`g++`, `clang++`, MSVC)가 어떤 명령줄 옵션을 지원하는지, 어떤 C++ 표준까지 지원하는지는 각 컴파일러의 공식 문서에서 확인할 수 있습니다. 18장에서 다룬 `-Wall`, `-Wextra` 외에도 프로젝트 상황에 맞는 유용한 옵션들이 많습니다.
- **C++ 표준 위원회의 제안서와 변경 로그**: 새로운 표준(C++20, C++23 등)에서 무엇이 바뀌었는지 정확히 알고 싶다면, 표준화 과정에서 논의된 제안서 문서나 각 표준의 변경 사항 요약을 찾아보는 것이 가장 신뢰할 수 있는 방법입니다.
- **정적 분석 도구와 컴파일러 경고**: 18장에서 다룬 경고 옵션 외에도, 정적 분석 도구를 프로젝트에 도입하면 사람이 눈으로 놓치기 쉬운 문제(자원 누수 가능성, 정의되지 않은 동작의 위험 등)를 기계적으로 찾아낼 수 있습니다. 이런 도구들의 사용법은 각 도구의 공식 문서를 참고합니다.
- **오픈소스 프로젝트의 실제 코드**: 문서만으로는 "실제로 어떻게 쓰이는가"를 파악하기 어려울 때가 많습니다. 관심 있는 분야(게임 엔진, 데이터베이스, 네트워크 라이브러리 등)의 오픈소스 저장소에서 실제 코드를 읽어보는 것은 이 책에서 배운 개념들이 실전에서 어떻게 조합되는지 확인하는 좋은 방법입니다.
- **커뮤니티 질의응답과 코드 리뷰**: 특정 에러 메시지의 의미나, 두 가지 설계 중 어느 것이 더 나은지에 대한 논의는 개발자 커뮤니티의 질의응답 자료를 검색해 참고할 수 있습니다. 다만 답변의 작성 시점과 대상 표준 버전을 항상 확인하는 습관이 필요합니다. 오래된 답변은 이후 표준에서 더 나은 방법이 추가되었을 수 있습니다.

어떤 자료를 보든, 예제 코드를 직접 컴파일해서 실행해보고 `-Wall -Wextra` 경고가 뜨는지 확인해보는 습관이 가장 확실한 학습 방법입니다. 이 책의 각 장에서 강조했던 것처럼, C++는 읽는 것만으로는 감을 잡기 어려운 언어입니다. 직접 작성하고, 컴파일러의 오류와 경고를 마주하고, 그것을 하나씩 해결해 나가는 과정 자체가 가장 좋은 학습 자료입니다.

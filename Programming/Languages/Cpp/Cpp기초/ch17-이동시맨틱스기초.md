지금까지 우리는 객체를 함수에 넘기거나 다른 변수에 대입할 때, 그 값이 "복사"된다는 것을 자연스럽게 받아들였습니다. 기본 자료형(3장)처럼 작은 값이라면 복사는 거의 비용이 들지 않습니다. 하지만 10장에서 배운 클래스가 내부에 큰 배열이나 동적으로 할당한 자원을 들고 있다면 어떨까요? 이 장에서는 그런 상황에서 발생하는 "불필요한 복사" 문제를 짚어보고, C++11부터 도입된 이동 시맨틱스(move semantics)가 이 문제를 어떻게 해결하는지 개념 위주로 살펴봅니다. 문법의 세세한 규칙보다는 "왜 필요한가"와 "언제 도움이 되는가"에 초점을 맞춥니다.

## 복사가 비싼 경우

큰 데이터를 담은 클래스를 예로 들어 보겠습니다. 9장에서 배운 RAII 원칙에 따라, 이 클래스는 생성자에서 자원을 확보하고 소멸자에서 해제합니다.

```cpp
#include <iostream>
#include <cstring>

class Buffer {
public:
    // 생성자: 지정한 크기만큼 힙 메모리를 할당한다
    explicit Buffer(std::size_t size)
        : size_(size), data_(new int[size]) {
        std::cout << "Buffer(" << size_ << ") 생성, 메모리 할당\n";
        for (std::size_t i = 0; i < size_; ++i) {
            data_[i] = 0;
        }
    }

    // 복사 생성자: 다른 Buffer의 내용을 통째로 복사한다
    Buffer(const Buffer& other)
        : size_(other.size_), data_(new int[other.size_]) {
        std::cout << "Buffer 복사 생성 (원소 " << size_ << "개 복사)\n";
        std::memcpy(data_, other.data_, size_ * sizeof(int));
    }

    // 소멸자: 할당했던 메모리를 해제한다 (9장 RAII)
    ~Buffer() {
        delete[] data_;
    }

    std::size_t size() const { return size_; }

private:
    std::size_t size_;
    int* data_;
};

// 인자로 받은 Buffer를 그대로 반환만 하는 함수
Buffer make_and_return(std::size_t size) {
    Buffer temp(size);
    return temp;   // temp가 함수 밖으로 나가면서 복사가 일어날 수 있는 지점
}

int main() {
    Buffer original(1'000'000);      // 원소 100만 개짜리 버퍼
    Buffer copy_of_original = original;  // 복사 생성자 호출 -> 100만 개를 통째로 복사
    return 0;
}
```

`copy_of_original`을 만드는 순간, 복사 생성자가 호출되어 100만 개의 `int`를 새로 할당한 메모리에 하나씩 복사합니다. 그런데 잘 생각해보면, 많은 경우 우리는 `original`을 이후에도 계속 쓰려는 게 아니라, 그 값을 다른 곳으로 "넘겨주고" 원래 것은 더 이상 쓰지 않는 상황일 때가 많습니다. 함수가 지역 변수를 반환하거나, 컨테이너(14장)에 임시 객체를 넣거나, `std::unique_ptr`(15장)을 다른 소유자에게 넘기는 경우가 그렇습니다. 이런 상황에서 굳이 원본 데이터를 통째로 복사할 필요가 있을까요? 원본이 어차피 곧 사라질 값이라면, 그 내부의 자원(포인터가 가리키는 메모리)을 그대로 "가져오고" 원본은 빈 상태로 남겨두는 편이 훨씬 효율적입니다. 이것이 바로 이동(move)의 개념입니다.

## 값의 두 얼굴: lvalue와 rvalue

이동 시맨틱스를 이해하려면 먼저 C++가 값을 두 가지로 구분한다는 것을 알아야 합니다. 엄밀한 표준 용어로는 더 세분화되지만, 이 장에서는 직관적인 수준으로만 구분해 보겠습니다.

- **lvalue(좌측값)**: 이름이 있고, 메모리 주소를 취할 수 있으며, 대입식의 왼쪽에 올 수 있는 값입니다. 변수 `original`처럼 "계속 살아있는 대상"을 가리킵니다.
- **rvalue(우측값)**: 이름이 없는 임시 값입니다. `make_and_return(10)`의 반환값처럼, 한 문장이 끝나면 사라질 값을 가리킵니다.

```cpp
Buffer a(10);          // a는 lvalue
Buffer b = make_and_return(20);  // make_and_return(20)의 결과는 rvalue (이름 없는 임시 객체)
```

핵심 아이디어는 이렇습니다. rvalue는 "곧 사라질 값"이므로, 그 내부 자원을 안전하게 가져와도 아무 문제가 없습니다. 어차피 아무도 그 임시 객체를 다시 참조하지 않기 때문입니다. 반면 `a`처럼 이름이 있는 lvalue는 이후에도 계속 쓰일 수 있으므로, 함부로 내부 자원을 빼앗아 오면 위험합니다. C++는 이 구분을 이용해서 "복사해야 하는 상황"과 "이동해도 안전한 상황"을 컴파일 시점에 구별합니다.

## 우측값 참조 `&&`

C++11은 rvalue를 가리킬 수 있는 새로운 참조 타입인 **우측값 참조(rvalue reference)** `T&&`를 도입했습니다. 9장에서 배운 일반 참조 `T&`(정확히는 lvalue 참조)와 짝을 이루는 개념입니다.

```cpp
void describe(const std::string& s) {
    std::cout << "lvalue 참조로 받음: " << s << '\n';
}

void describe(std::string&& s) {
    std::cout << "rvalue 참조로 받음: " << s << '\n';
}

int main() {
    std::string name = "Alice";
    describe(name);              // name은 lvalue -> 첫 번째 오버로드
    describe(std::string("Bob")); // 임시 객체는 rvalue -> 두 번째 오버로드
}
```

두 함수는 같은 이름으로 오버로딩되어 있지만, 인자가 lvalue인지 rvalue인지에 따라 컴파일러가 자동으로 알맞은 버전을 골라 호출합니다. 이 구분 덕분에 클래스는 "값이 복사되어도 되는 상황"과 "값을 그대로 훔쳐와도 되는 상황"에 각각 다른 코드를 작성할 수 있게 됩니다.

## `std::move`: "이 값은 더 이상 안 쓸게요"라는 선언

그런데 앞의 `original` 같은 lvalue를 일부러 이동시키고 싶을 때는 어떻게 해야 할까요? lvalue를 그대로 넘기면 컴파일러는 여전히 lvalue 참조 버전을 고르므로 복사가 일어납니다. 여기서 `<utility>` 헤더의 `std::move`가 등장합니다.

```cpp
#include <utility>

std::string a = "Hello";
std::string b = std::move(a);   // a의 내부 자원을 b로 이동시킴

// 이 시점 이후 a는 "빈 문자열"과 비슷한, 유효하지만 값이 정해지지 않은 상태
// a를 다시 읽으려고 하면 안 되고, 재대입한 뒤에는 다시 사용할 수 있다
```

`std::move`는 사실 아무것도 "이동"시키지 않습니다. 이름과 달리, 실제로는 `a`를 rvalue 참조로 타입만 바꿔주는 캐스팅에 불과합니다. 진짜 이동 작업은 이어서 호출되는 이동 생성자나 이동 대입 연산자가 수행합니다. 즉 `std::move(a)`는 "이 값을 rvalue처럼 취급해 주세요. 저는 `a`를 더 이상 이전 상태로 쓰지 않을 겁니다"라고 컴파일러와 코드를 읽는 사람 모두에게 알리는 선언입니다.

이 선언을 한 이후에, 이동의 대상이 된 원본 객체(`a`)는 "유효하지만 특정되지 않은 상태(valid but unspecified state)"에 놓입니다. 프로그램이 깨지지는 않지만, 그 값이 무엇인지 더 이상 가정할 수 없다는 뜻입니다. 그래서 `std::move`를 호출한 뒤에는 원본 변수를 다시 읽지 않는 것이 원칙입니다.

## 이동 생성자와 이동 대입 연산자

클래스가 "이동"이라는 개념을 실제로 지원하려면, 복사 생성자·복사 대입 연산자와 짝을 이루는 **이동 생성자**와 **이동 대입 연산자**를 정의해야 합니다. 앞서 본 `Buffer` 클래스에 이동 연산을 추가해 보겠습니다.

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : size_(size), data_(new int[size]) {}

    // 복사 생성자: 자원을 새로 할당하고 값을 복사
    Buffer(const Buffer& other)
        : size_(other.size_), data_(new int[other.size_]) {
        std::memcpy(data_, other.data_, size_ * sizeof(int));
    }

    // 이동 생성자: other가 들고 있던 포인터를 그대로 가져오고, other는 비운다
    Buffer(Buffer&& other) noexcept
        : size_(other.size_), data_(other.data_) {
        other.size_ = 0;
        other.data_ = nullptr;   // 원본이 소멸자에서 같은 메모리를 다시 해제하지 않도록 함
    }

    // 이동 대입 연산자: 기존 자원을 정리하고 other의 자원을 가져옴
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data_;
            size_ = other.size_;
            data_ = other.data_;
            other.size_ = 0;
            other.data_ = nullptr;
        }
        return *this;
    }

    ~Buffer() {
        delete[] data_;   // data_가 nullptr이면 delete[]는 안전하게 아무 일도 하지 않음
    }

    std::size_t size() const { return size_; }

private:
    std::size_t size_;
    int* data_;
};
```

이동 생성자는 매개변수로 `Buffer&&`(우측값 참조)를 받습니다. 몸체를 보면 새 메모리를 할당하지 않고, `other`가 이미 가지고 있던 포인터(`data_`)를 그대로 넘겨받은 뒤, `other`의 포인터는 `nullptr`로 만들어 둡니다. 이렇게 하면 두 가지가 보장됩니다.

1. 실제 데이터 복사(`memcpy`)가 전혀 일어나지 않으므로 원소 개수와 무관하게 항상 빠릅니다.
2. `other`가 스코프를 벗어나 소멸자가 호출되어도, `data_`가 `nullptr`이라 이미 다른 객체(새로 만들어진 객체)가 소유하게 된 메모리를 실수로 두 번 해제하지 않습니다.

이동 연산에는 보통 `noexcept`를 붙입니다. `std::vector`(14장) 같은 표준 컨테이너는 원소를 재배치할 때, 이동 연산이 예외를 던지지 않는다는 것이 보장되어야 복사 대신 이동을 안전하게 선택할 수 있기 때문입니다. `noexcept`가 없으면 컨테이너가 안전을 위해 이동 대신 복사로 되돌아가는 경우가 있습니다.

## 이동은 언제 자동으로 일어나는가

`std::move`를 직접 호출하지 않아도, 컴파일러가 스스로 rvalue라고 판단할 수 있는 상황에서는 이동 생성자/대입 연산자가 자동으로 선택됩니다.

```cpp
Buffer make_buffer() {
    Buffer temp(100);
    return temp;   // temp는 함수를 벗어나며 사라질 지역 변수 -> 컴파일러가 이동으로 처리
}

Buffer b1 = make_buffer();          // 반환값(rvalue)으로부터 이동 생성
Buffer b2(Buffer(200));              // 임시 객체로부터 이동 생성
Buffer b3 = std::move(b1);            // 명시적으로 이동을 요청
```

`return temp;`처럼 함수의 지역 변수를 그대로 반환하는 경우, 그 지역 변수는 함수가 끝나면 어차피 소멸될 값이므로 컴파일러가 자동으로 이동(또는 아예 복사·이동조차 생략하는 최적화)을 적용합니다. 프로그래머가 매번 `std::move`를 써야만 이동이 일어나는 것은 아니라는 점을 기억해두면 좋습니다. `std::move`는 "원래는 lvalue라서 복사가 될 상황을, 강제로 이동으로 바꾸고 싶을 때"에만 필요합니다.

## 이동이 이미 여러 곳에서 쓰이고 있다

사실 이 책의 앞부분에서 다룬 도구들은 이미 이동 시맨틱스를 전제로 설계되어 있습니다.

- **9장의 RAII 클래스**: 자원을 소유하는 클래스를 설계할 때, 복사를 금지하고 이동만 허용하는 패턴이 흔합니다. 자원이 파일 핸들이나 네트워크 연결처럼 "복사한다는 개념 자체가 의미 없는" 것일 때, 복사 생성자를 `= delete`로 막고 이동 생성자만 제공하면 "소유권은 이전할 수 있지만 두 곳에서 동시에 소유할 수는 없다"는 규칙을 코드로 강제할 수 있습니다.
- **15장의 스마트 포인터**: `std::unique_ptr`는 정확히 이 원칙을 따르는 대표적인 예입니다. `std::unique_ptr`는 복사 생성자와 복사 대입 연산자가 삭제되어 있고, 이동 생성자와 이동 대입 연산자만 존재합니다. 그래서 `std::unique_ptr`를 함수에 값으로 넘기거나 컨테이너에 담을 때는 반드시 `std::move`를 사용해 소유권을 이전해야 합니다. 이것이 바로 "복사할 수 없지만 이동할 수는 있는" 자원 관리의 핵심 아이디어이며, 지금 배운 이동 생성자/대입 연산자가 그 밑바탕이 됩니다.
- **14장의 STL 컨테이너**: `std::vector`가 원소를 추가하며 내부 배열을 더 큰 메모리로 재할당할 때, 원소들의 이동 생성자가 `noexcept`이면 복사 대신 이동으로 재배치하여 성능을 크게 높입니다. `std::vector<std::string>`에 문자열을 `push_back`할 때도, 임시 문자열을 넘기면 복사 대신 이동이 일어나 불필요한 메모리 할당을 피할 수 있습니다.

즉 이동 시맨틱스는 단독으로 존재하는 문법 기능이 아니라, 자원을 안전하고 효율적으로 다루기 위한 C++ 전체 설계 철학과 맞물려 있는 개념입니다.

## 지금 단계에서 기억해야 할 것

이 장의 목표는 이동 생성자와 이동 대입 연산자를 직접 손으로 작성하는 숙련도를 갖추는 것이 아닙니다. 실무에서도 직접 작성해야 하는 경우는 자원을 직접 관리하는 저수준 클래스를 만들 때뿐이고, 대부분은 `std::vector`, `std::string`, `std::unique_ptr` 같은 표준 라이브러리 타입을 멤버로 사용하면 컴파일러가 이동 연산을 자동으로 생성해 줍니다. 지금 단계에서 꼭 기억해야 할 것은 다음 세 가지입니다.

1. 큰 자원을 담은 객체를 값으로 넘기거나 반환할 때, 반드시 매번 통째로 복사되는 것은 아니다. "곧 사라질 값"이라면 이동이 대신 일어날 수 있고, 이동은 복사보다 훨씬 저렴하다.
2. 어떤 변수를 더 이상 원래 형태로 쓰지 않을 것이 확실할 때, `std::move`로 그 사실을 명시적으로 알려주면 불필요한 복사를 피할 수 있다. 단, `std::move`를 호출한 뒤에는 그 변수를 다시 사용하지 않아야 한다.
3. 표준 라이브러리(특히 15장의 스마트 포인터, 14장의 컨테이너)는 이미 이동 시맨틱스를 적극적으로 활용하도록 설계되어 있으므로, 이 개념을 이해하면 왜 어떤 타입은 복사가 안 되고 이동만 되는지, 왜 컨테이너에 원소를 채울 때 `std::move`를 권장하는지를 자연스럽게 이해할 수 있다.

## 요약

- 클래스가 큰 자원(동적 메모리 등)을 소유하고 있으면, 값을 복사할 때마다 그 자원을 통째로 복사하는 비용이 발생한다.
- C++는 값을 이름 있는 lvalue와 이름 없는 임시 값인 rvalue로 구분하며, rvalue는 "곧 사라질 값"이므로 내부 자원을 안전하게 가져와도 문제가 없다.
- 우측값 참조 `T&&`는 rvalue를 받는 참조 타입으로, 클래스가 "복사"와 "이동"에 서로 다른 코드를 작성할 수 있게 해준다.
- `std::move`는 실제로 값을 옮기지 않고, lvalue를 rvalue로 취급하도록 타입만 바꿔주는 캐스팅이며, "이 값은 더 이상 이전 형태로 쓰지 않겠다"는 선언에 해당한다.
- 이동 생성자와 이동 대입 연산자는 새로 자원을 할당하지 않고 원본의 자원을 그대로 넘겨받은 뒤 원본을 빈 상태로 만들어, 복사보다 훨씬 빠르게 값을 옮긴다.
- 함수가 지역 변수를 반환하는 경우처럼 컴파일러가 rvalue임을 스스로 판단할 수 있는 상황에서는 `std::move` 없이도 자동으로 이동이 일어난다.
- 9장의 RAII 원칙과 15장의 `std::unique_ptr`는 "복사는 금지하고 이동만 허용"하는 방식으로 자원의 유일한 소유권을 보장하는데, 이 설계는 이동 시맨틱스 위에서 성립한다.

## 연습문제

1. 복사와 이동의 차이를 자신의 말로 설명하고, 어떤 상황에서 이동이 복사보다 유리한지 예를 들어 보라.
2. 본문의 `Buffer` 클래스에서 이동 생성자가 `other.data_`를 `nullptr`로 만들어 두지 않으면 어떤 문제가 발생할지 설명해 보라. (힌트: 소멸자가 두 번 호출되는 상황을 생각해 보라.)
3. 다음 코드에서 각 대입/전달이 복사로 처리되는지 이동으로 처리되는지 판단하고 이유를 설명해 보라.
   ```cpp
   std::string make_greeting() {
       std::string s = "hello";
       return s;
   }

   std::string a = "world";
   std::string b = a;                 // (1)
   std::string c = std::move(a);        // (2)
   std::string d = make_greeting();     // (3)
   ```
4. `std::unique_ptr`가 복사 생성자를 제공하지 않고 이동 생성자만 제공하는 이유를, 이 장에서 배운 개념을 이용해 설명해 보라.
5. `std::move(a)`를 호출한 뒤 `a`를 다시 읽는 것이 왜 위험할 수 있는지, "유효하지만 특정되지 않은 상태"라는 표현을 사용해 설명해 보라.

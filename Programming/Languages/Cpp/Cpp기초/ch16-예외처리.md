## 16.1 오류를 어떻게 알릴 것인가

지금까지 작성한 함수들은 대부분 오류가 없다고 가정하고 동작했다. 하지만 실제 프로그램에서는 파일이 존재하지 않거나, 배열 인덱스가 범위를 벗어나거나, 메모리 할당이 실패하는 등 예상치 못한 상황이 늘 발생한다. 이런 상황을 처리하는 전통적인 방법은 함수의 반환값으로 오류 코드를 돌려주는 것이다.

```cpp
// 오류 코드 방식: 반환값 0은 성공, -1은 실패를 의미한다고 가정
int divide(int a, int b, int* result) {
    if (b == 0) {
        return -1;  // 실패
    }
    *result = a / b;
    return 0;  // 성공
}
```

이 방식은 함수를 호출할 때마다 반환값을 확인해야 하고, 확인을 빼먹어도 컴파일러가 경고해주지 않는다는 단점이 있다. 게다가 생성자처럼 반환값이 없는 함수에서는 이런 방식을 아예 쓸 수 없다. C++은 이런 문제를 해결하기 위해 예외(exception)라는 별도의 오류 전달 경로를 언어 차원에서 제공한다.

## 16.2 `try`-`catch`-`throw` 기본 구조

예외는 세 가지 키워드로 이루어진다. `throw`는 예외를 던지는 지점, `try`는 예외가 발생할 수 있는 코드를 감싸는 블록, `catch`는 던져진 예외를 받아 처리하는 블록이다.

```cpp
#include <iostream>

int divide(int a, int b) {
    if (b == 0) {
        throw std::runtime_error("0으로 나눌 수 없습니다");
    }
    return a / b;
}

int main() {
    try {
        int result = divide(10, 0);
        std::cout << "결과: " << result << "\n";  // 여기까지 도달하지 않는다
    } catch (const std::runtime_error& e) {
        std::cout << "예외 발생: " << e.what() << "\n";
    }

    std::cout << "프로그램은 계속 실행된다\n";
    return 0;
}
```

`divide` 함수 안에서 `throw`가 실행되면, 함수는 즉시 실행을 멈추고 예외 객체를 던진다. 프로그램은 호출 스택을 따라 올라가며 해당 예외 타입을 처리할 수 있는 `catch` 블록을 찾는다. `main`의 `try` 블록이 `std::runtime_error`를 받는 `catch`를 가지고 있으므로 여기서 처리되고, 프로그램은 정상적으로 계속 실행된다. 만약 어떤 `catch`도 예외를 받지 못하면 프로그램은 종료된다.

## 16.3 표준 예외 클래스

C++ 표준 라이브러리는 `<exception>`과 `<stdexcept>` 헤더에 예외 클래스들의 계층 구조를 미리 정의해 두었다. 모든 표준 예외의 최상위 클래스는 `std::exception`이며, 이 클래스는 오류 메시지를 문자열로 반환하는 `what()`이라는 가상 함수를 가지고 있다(가상 함수의 원리는 11장에서 배운 다형성을 그대로 활용한다).

대표적인 파생 클래스는 다음과 같다.

- `std::logic_error` 계열: 프로그램 논리상 발생해서는 안 되는 오류. `std::invalid_argument`(잘못된 인자), `std::out_of_range`(범위를 벗어난 접근) 등이 여기 속한다.
- `std::runtime_error` 계열: 실행 중에만 판단할 수 있는 오류. `std::overflow_error`, `std::underflow_error` 등이 있다.
- `std::bad_alloc`: `new`로 메모리 할당에 실패했을 때 던져진다.

```cpp
#include <vector>
#include <iostream>
#include <stdexcept>

int main() {
    std::vector<int> numbers = {1, 2, 3};

    try {
        std::cout << numbers.at(10) << "\n";  // 범위 밖 접근
    } catch (const std::out_of_range& e) {
        std::cout << "범위 오류: " << e.what() << "\n";
    }

    return 0;
}
```

14장에서 배운 `std::vector`의 `at()` 멤버 함수는 인덱스가 범위를 벗어나면 `operator[]`와 달리 `std::out_of_range` 예외를 던진다. 이렇게 표준 라이브러리 자체도 예외를 적극적으로 활용한다.

`catch` 블록은 여러 개를 나열할 수 있으며, 다형성 덕분에 파생 클래스의 참조를 부모 클래스인 `std::exception&`으로 받아 한 번에 처리할 수도 있다.

```cpp
try {
    risky_operation();
} catch (const std::out_of_range& e) {
    std::cout << "범위 오류: " << e.what() << "\n";
} catch (const std::exception& e) {
    // out_of_range 이외의 모든 표준 예외를 여기서 처리
    std::cout << "일반 오류: " << e.what() << "\n";
} catch (...) {
    // 표준 예외가 아닌 모든 예외를 처리(타입을 알 수 없을 때의 최후 수단)
    std::cout << "알 수 없는 예외 발생\n";
}
```

`catch` 블록은 위에서부터 순서대로 검사되므로, 더 구체적인 타입을 먼저 배치하고 `std::exception&`처럼 넓은 타입, 마지막으로 `catch(...)`를 배치하는 것이 일반적인 순서다.

## 16.4 커스텀 예외 클래스 만들기

라이브러리가 제공하는 예외로 표현하기 어려운, 우리 프로그램만의 오류 상황이 있다면 `std::exception`을 상속받아 직접 예외 클래스를 만들 수 있다. `what()`을 오버라이드하여 의미 있는 메시지를 돌려주면 된다.

```cpp
#include <exception>
#include <string>

class InsufficientBalanceError : public std::exception {
public:
    InsufficientBalanceError(double balance, double amount)
        : balance_(balance), amount_(amount) {
        message_ = "잔액 부족: 잔액 " + std::to_string(balance_) +
                   ", 요청 금액 " + std::to_string(amount_);
    }

    const char* what() const noexcept override {
        return message_.c_str();
    }

private:
    double balance_;
    double amount_;
    std::string message_;
};

class BankAccount {
public:
    BankAccount(double balance) : balance_(balance) {}

    void withdraw(double amount) {
        if (amount > balance_) {
            throw InsufficientBalanceError(balance_, amount);
        }
        balance_ -= amount;
    }

private:
    double balance_;
};
```

`what()`을 오버라이드할 때는 반환형이 `const char*`이고 `noexcept`가 붙어 있어야 한다는 점에 주의해야 한다. `noexcept`는 이 함수가 예외를 던지지 않는다는 약속으로, 예외 처리 도중 또 다른 예외가 던져지는 상황을 막기 위한 규칙이다. 커스텀 예외 클래스는 10장에서 배운 클래스 설계와 11장에서 배운 상속을 그대로 응용한 것일 뿐이며, 특별한 문법이 추가되는 것은 아니다.

```cpp
int main() {
    BankAccount account(1000.0);
    try {
        account.withdraw(5000.0);
    } catch (const InsufficientBalanceError& e) {
        std::cout << e.what() << "\n";
    }
    return 0;
}
```

## 16.5 예외와 RAII : 소멸자는 반드시 호출된다

15장에서 소개한 스마트 포인터와 RAII 원칙은 예외 처리와 밀접하게 연결된다. `throw`가 실행되면 프로그램은 호출 스택을 거슬러 올라가며 이를 스택 풀기(stack unwinding)라고 부르는데, 이 과정에서 스택에 있던 지역 객체들의 소멸자가 순서대로 호출된다. 즉, 함수 중간에서 예외가 발생해도 그 시점까지 생성된 지역 객체들은 정상적으로 소멸자를 호출받는다.

```cpp
#include <memory>
#include <iostream>

class Resource {
public:
    Resource() { std::cout << "자원 획득\n"; }
    ~Resource() { std::cout << "자원 해제\n"; }
};

void might_throw() {
    auto res = std::make_unique<Resource>();
    std::cout << "작업 시작\n";
    throw std::runtime_error("문제 발생");
    // 이 아래 코드는 실행되지 않는다
}

int main() {
    try {
        might_throw();
    } catch (const std::exception& e) {
        std::cout << "예외 잡음: " << e.what() << "\n";
    }
    return 0;
}
```

이 코드를 실행하면 "자원 획득", "작업 시작", "자원 해제", "예외 잡음: 문제 발생" 순서로 출력된다. `throw`가 실행되는 순간 `might_throw` 함수는 즉시 빠져나가지만, 그 전에 스택에 있던 `res`(`std::unique_ptr<Resource>`)의 소멸자가 먼저 호출되어 `Resource`가 안전하게 해제된다. 만약 `res`가 스마트 포인터가 아니라 원시 포인터였고 `delete`를 직접 호출해야 했다면, `throw` 때문에 그 `delete` 문장은 절대 실행되지 못해 메모리 누수가 발생했을 것이다. 이것이 바로 RAII와 스마트 포인터가 예외 안전한 코드를 작성하는 데 핵심적인 이유다.

## 16.6 예외 안전성의 세 단계

예외가 발생해도 프로그램이 일관된 상태를 유지하도록 코드를 작성하는 것을 예외 안전성(exception safety)이라고 부른다. 보통 세 단계로 구분해서 이야기한다.

- **기본 보장(basic guarantee)**: 예외가 발생해도 메모리 누수 등 자원 누수가 없고, 객체는 유효한(파괴되지 않은) 상태를 유지한다. 최소한의 요구사항이다.
- **강한 보장(strong guarantee)**: 예외가 발생하면 연산이 마치 전혀 실행되지 않았던 것처럼 프로그램 상태가 원래대로 되돌아간다. 예를 들어 `std::vector::push_back`은 내부 재할당 중 예외가 발생해도 원래 벡터를 그대로 유지한다.
- **예외 없음 보장(no-throw guarantee)**: 해당 연산은 절대 예외를 던지지 않는다. 소멸자와 이동 연산(17장 참고)은 보통 이 수준을 지키도록 작성하는 것이 관례이며, 그래서 `noexcept`를 붙인다.

실무에서 모든 함수가 강한 보장을 지킬 필요는 없지만, 최소한 기본 보장은 지키는 것이 바람직하다. 그리고 기본 보장을 지키는 가장 쉬운 방법이 바로 자원 관리를 스마트 포인터와 RAII에 맡기는 것이다. 직접 자원을 관리하는 코드가 늘어날수록 예외 발생 경로를 일일이 손으로 챙겨야 하고, 그만큼 실수할 여지도 커진다.

## 16.7 예외를 언제 쓸 것인가

예외는 강력하지만 모든 오류 상황에 적합한 도구는 아니다. 일반적으로는 다음과 같이 구분한다.

- 함수가 "정상적으로는 발생하지 않아야 하는" 예외적 상황(파일을 열 수 없음, 잘못된 인자, 메모리 부족 등)을 만났을 때 예외를 던진다.
- 흔히 발생하고 호출자가 당연히 확인해야 하는 상황(예: 사용자가 빈 문자열을 입력했는지)은 반환값이나 `std::optional` 같은 방식으로 처리하는 것이 더 자연스러울 때가 많다.
- 생성자는 반환값으로 실패를 알릴 수 없으므로, 생성자에서 실패를 알려야 한다면 예외가 거의 유일한 표준적인 방법이다.

이 판단 기준은 프로젝트나 팀의 관례에 따라 달라질 수 있지만, 중요한 것은 오류 처리 방식을 코드 전체에서 일관되게 유지하는 것이다. 18장에서는 이런 관례를 포함해 좋은 C++ 코드를 작성하는 습관을 종합적으로 정리한다.

## 요약

- 예외는 반환값 대신 `throw`/`try`/`catch`로 오류를 전달하는 C++의 표준적인 방법으로, 오류 확인을 빼먹는 문제와 생성자의 실패 전달 문제를 해결한다.
- 모든 표준 예외는 `std::exception`을 상속하며, `what()`으로 오류 메시지를 얻을 수 있다. `std::logic_error`, `std::runtime_error`, `std::out_of_range` 등 다양한 파생 클래스가 표준 라이브러리 전반에서 쓰인다.
- `std::exception`을 상속해 커스텀 예외 클래스를 만들 수 있으며, `what()`은 `const char*`를 반환하고 `noexcept`가 붙어야 한다.
- 예외가 발생하면 스택 풀기가 일어나며, 그 과정에서 지역 객체의 소멸자가 반드시 호출된다. 이 덕분에 스마트 포인터와 RAII로 관리되는 자원은 예외가 발생해도 안전하게 해제된다.
- 예외 안전성은 기본 보장, 강한 보장, 예외 없음 보장으로 나뉘며, RAII를 일관되게 적용하는 것이 기본 보장을 지키는 가장 확실한 방법이다.

## 연습문제

1. 정수를 인자로 받아 음수이면 `std::invalid_argument`를 던지는 함수 `check_positive`를 작성하고, `main`에서 이를 `try`-`catch`로 처리해 보라.
2. `std::exception`을 상속한 커스텀 예외 클래스 `FileNotFoundError`를 만들고, 파일 이름을 생성자 인자로 받아 `what()`에서 "파일을 찾을 수 없습니다: 파일이름" 형식의 메시지를 반환하도록 구현해 보라.
3. 함수 안에서 `std::unique_ptr`로 자원을 관리하다가 중간에 예외를 던지는 코드를 작성하고, 소멸자가 예외 전파 과정에서도 호출되는지 출력문으로 확인해 보라.
4. `catch (const std::out_of_range&)`, `catch (const std::exception&)`, `catch (...)`를 모두 가진 코드를 작성하고, 각기 다른 종류의 예외를 던져보며 어떤 블록이 실행되는지 관찰해 보라.
5. 반환값으로 오류를 알리는 것이 더 적합한 상황과 예외를 던지는 것이 더 적합한 상황을 각각 하나씩 예로 들고, 그 이유를 설명해 보라.

지금까지 우리는 변수와 자료형(3장)부터 클래스와 상속(10장, 11장), 템플릿(13장), STL(14장), 스마트 포인터(15장), 예외 처리(16장), 이동 시맨틱스(17장)까지 C++의 주요 문법과 도구를 순서대로 살펴보았습니다. 이 마지막 장에서는 새로운 문법을 배우는 대신, 지금까지 배운 도구들을 "어떻게 쓰는 것이 좋은가"를 정리합니다. ## RAII를 기본값으로 삼기

9장에서 배운 RAII(Resource Acquisition Is Initialization) 원칙은 이 책 전체를 관통하는 가장 중요한 습관입니다. 핵심은 단순합니다. **자원의 획득과 해제를 객체의 생성자와 소멸자에 맡기면, 그 자원을 손으로 관리할 필요가 없어진다**는 것입니다.

```cpp
// 좋지 않은 예: 자원 해제를 사람이 기억해야 함
void process_bad() {
    int* buffer = new int[1000];

    // ... 작업 중 예외가 발생하거나 return으로 일찍 빠져나가면?
    if (/* 어떤 오류 조건 */ false) {
        return;   // delete[] buffer를 빠뜨림 -> 메모리 누수
    }

    delete[] buffer;   // 정상 경로에서만 해제됨
}

// 좋은 예: 소멸자가 자동으로 해제를 책임짐
#include <vector>

void process_good() {
    std::vector<int> buffer(1000);   // 자원 관리를 벡터에게 위임

    if (/* 어떤 오류 조건 */ false) {
        return;   // buffer의 소멸자가 자동으로 호출되어 메모리가 해제됨
    }

    // 함수가 정상적으로 끝나도 마찬가지로 자동 해제
}
```

`process_bad`는 함수 중간에 `return`이 추가되거나 예외가 던져지는 순간 `delete[]`를 놓치기 쉬운 구조입니다. 반면 `process_good`은 `std::vector`가 스코프를 벗어나는 시점에 소멸자가 자동으로 호출되어, 정상 종료든 예외로 인한 종료든 자원이 항상 해제됩니다. 16장에서 배운 예외 처리와 RAII를 함께 쓰면, `catch` 블록에서 자원을 일일이 정리하는 코드를 쓰지 않아도 스택이 풀리는(unwinding) 과정에서 소멸자들이 순서대로 호출되어 자원이 안전하게 회수됩니다. RAII는 파일 핸들, 뮤텍스 락, 네트워크 연결, 메모리 등 "획득했으면 반드시 해제해야 하는" 모든 자원에 적용할 수 있는 범용적인 습관입니다.

## 원시 포인터보다 스마트 포인터와 참조를 먼저 떠올리기

8장에서 포인터를 배우고 9장에서 참조를 배운 뒤, 15장에서는 `std::unique_ptr`와 `std::shared_ptr` 같은 스마트 포인터를 다뤘습니다. 이제 실제로 코드를 작성할 때는 다음과 같은 순서로 도구를 고르는 습관을 들이는 것이 좋습니다.

1. **참조(`&`)**: 함수에 객체를 전달하되 소유권 이전이나 `nullptr` 가능성이 필요 없다면 참조가 가장 단순하고 안전합니다.
2. **`std::unique_ptr`**: 동적으로 할당한 자원을 정확히 한 곳에서 소유해야 한다면 `std::unique_ptr`를 사용합니다. 17장에서 배운 이동 시맨틱스를 통해 소유권을 다른 곳으로 넘길 수 있습니다.
3. **`std::shared_ptr`**: 여러 곳에서 같은 자원의 소유권을 공유해야 하는, 정말로 필요한 경우에만 사용합니다.
4. **원시 포인터(`T*`)**: 소유권이 없는 "그냥 어떤 객체를 가리키기만 하는" 용도, 또는 위 스마트 포인터들이 이미 관리하는 자원을 잠깐 참조할 때만 씁니다. `new`와 `delete`를 직접 짝지어 호출하는 코드는 되도록 새로 작성하지 않는 것이 좋습니다.

```cpp
#include <memory>
#include <vector>

// 좋지 않은 예: 소유권이 불분명하고, delete를 누가 언제 호출해야 하는지 코드만 봐서는 알기 어려움
Widget* create_widget_raw() {
    return new Widget();   // 호출한 쪽이 반드시 delete 해야 하는데, 코드에 그 책임이 드러나지 않음
}

// 좋은 예: 소유권이 명확하게 드러남
std::unique_ptr<Widget> create_widget() {
    return std::make_unique<Widget>();   // 반환받은 쪽이 소유자가 됨을 타입으로 표현
}

void use_widget(const Widget& w) {
    // 참조로 받으므로 소유권을 요구하지 않고, w가 nullptr일 걱정도 없음
}
```

`std::unique_ptr<Widget>`을 반환 타입으로 쓰면, 함수를 호출하는 사람은 코드를 자세히 읽지 않아도 "이 반환값의 소유권은 나에게 있고, 스코프를 벗어나면 자동으로 해제된다"는 것을 타입만으로 알 수 있습니다. 원시 포인터를 반환하면 그 정보가 문서나 주석에만 의존하게 되고, 시간이 지나 코드가 바뀌면 문서와 실제 동작이 어긋나는 일이 흔히 벌어집니다.

## `const`를 기본값으로, 필요할 때만 제거하기

3장에서 배운 `const`는 단순히 상수를 선언하는 도구가 아니라, "이 값(또는 이 함수)은 대상을 바꾸지 않는다"는 약속을 컴파일러와 코드를 읽는 사람 모두에게 전달하는 문서화 수단입니다. 좋은 습관은 변수나 매개변수를 선언할 때 기본적으로 `const`를 붙이고, 정말로 값을 바꿔야 하는 경우에만 `const`를 빼는 것입니다.

```cpp
// 매개변수에 const를 붙이지 않으면, 함수 내부에서 원본이 바뀔 수 있는지
// 호출하는 쪽에서 함수 본문을 읽어보지 않고는 확신할 수 없다
void print_report(std::vector<int>& data) {
    // data를 실수로 수정해도 컴파일러는 아무 말도 하지 않는다
}

// const 참조를 쓰면 "읽기만 하고 바꾸지 않는다"는 것이 타입에 드러난다
void print_report(const std::vector<int>& data) {
    for (int value : data) {
        std::cout << value << ' ';
    }
    std::cout << '\n';
}
```

클래스의 멤버 함수도 마찬가지입니다. 객체의 상태를 바꾸지 않는 함수(예: 값을 조회만 하는 함수)에는 항상 `const`를 붙이는 습관을 들이면, 나중에 `const` 객체나 `const` 참조를 통해서도 그 함수를 호출할 수 있게 되어 코드의 재사용성이 높아집니다. `const`를 붙였다가 컴파일 오류가 난다면, 그 함수가 실제로 객체를 변경하고 있다는 뜻이므로 오히려 설계를 다시 점검할 좋은 신호로 받아들일 수 있습니다.

## 흔한 실수와 그 뿌리

지금까지 배운 여러 장의 내용을 되짚어 보면, C++에서 반복적으로 등장하는 버그들은 대부분 몇 가지 패턴으로 압축됩니다.

### 메모리 누수(memory leak)

`new`로 할당한 메모리를 `delete`하지 않고 그 메모리를 가리키던 포인터가 사라지면, 그 메모리는 프로그램이 끝날 때까지 회수되지 않습니다(8장, 9장). 앞서 본 RAII와 스마트 포인터(15장)를 기본값으로 쓰면 이 문제는 대부분 저절로 사라집니다.

```cpp
void leak_example() {
    int* data = new int[100];
    // return이나 예외로 함수가 일찍 끝나면 delete[]를 못 만나고 메모리가 누수됨
}
```

### 댕글링 포인터(dangling pointer)와 댕글링 참조

이미 해제되었거나 스코프를 벗어난 대상을 가리키는 포인터·참조를 계속 사용하는 문제입니다(8장, 9장).

```cpp
int* dangling_pointer() {
    int local = 42;
    return &local;   // local은 함수가 끝나면 사라지는 지역 변수
    // 반환된 포인터는 이미 사라진 메모리를 가리키는 댕글링 포인터가 됨
}
```

지역 변수의 주소나 참조를 함수 밖으로 반환하지 않는 것, 그리고 `std::unique_ptr`나 `std::shared_ptr`가 관리하는 객체가 아직 살아있는지 확실하지 않은 상태에서 원시 포인터로 접근하지 않는 것이 기본 대책입니다.

### 배열 경계 초과(out-of-bounds access)

8장에서 배운 배열이나 14장의 STL 컨테이너에서, 유효한 인덱스 범위를 벗어난 위치에 접근하는 실수입니다.

```cpp
#include <vector>

std::vector<int> numbers = {1, 2, 3};
int value = numbers[3];   // 유효한 인덱스는 0, 1, 2뿐인데 3에 접근 -> 정의되지 않은 동작
```

`operator[]`는 속도를 위해 범위를 검사하지 않습니다. 인덱스가 프로그램 로직상 확실히 안전한 경우가 아니라면, 범위를 검사하고 예외를 던지는 `at()`을 대신 사용하거나(16장에서 배운 예외 처리와 연결됩니다), 반복문에서는 인덱스보다 반복자나 범위 기반 `for`(6장)를 사용하는 편이 이런 실수를 원천적으로 줄여줍니다.

### 얕은 복사(shallow copy) 문제

클래스가 포인터 멤버를 가지고 있는데 복사 생성자나 복사 대입 연산자를 직접 정의하지 않으면, 컴파일러가 자동으로 만들어주는 기본 복사는 포인터 "값"(주소)만 복사합니다. 그 결과 두 객체가 같은 메모리를 가리키게 되고, 한 객체가 소멸되며 그 메모리를 해제하면 다른 객체는 이미 해제된 메모리를 가리키는 댕글링 포인터를 갖게 됩니다.

```cpp
class ShallowBox {
public:
    ShallowBox(int value) : data_(new int(value)) {}
    ~ShallowBox() { delete data_; }
    // 복사 생성자를 직접 정의하지 않으면 컴파일러가 data_ 포인터 값만 복사한다

private:
    int* data_;
};

void shallow_copy_problem() {
    ShallowBox a(10);
    ShallowBox b = a;   // b.data_와 a.data_가 같은 메모리를 가리키게 됨
}   // a와 b의 소멸자가 각각 delete data_를 호출 -> 같은 메모리를 두 번 해제 (undefined behavior)
```

이 문제를 해결하는 방법은 세 가지입니다. 자원을 직접 관리하는 클래스라면 복사 생성자·복사 대입 연산자를 제대로 정의해서 깊은 복사(deep copy)를 하거나(12장의 연산자 오버로딩과 연결), 17장에서 배운 것처럼 복사를 막고 이동만 허용하거나, 가장 흔하게는 포인터 멤버 자체를 `std::vector`나 `std::unique_ptr`(15장) 같은 자원 관리 클래스로 바꾸어 컴파일러가 만들어주는 기본 복사·이동이 이미 올바르게 동작하도록 만드는 것입니다. 실무에서는 세 번째 방법, 즉 직접 자원을 들고 있는 클래스를 최소화하는 방식이 가장 널리 권장됩니다.

## 컴파일러의 경고를 무시하지 않기

컴파일러는 코드에서 의심스러운 부분을 발견하면 오류로 처리하지 않더라도 경고를 낼 수 있습니다. 기본 옵션만으로 컴파일하면 이런 경고들이 상당수 숨겨져 있으므로, 2장에서 다룬 `g++` 컴파일 명령에 경고 옵션을 추가하는 습관을 들이는 것이 좋습니다.

```bash
g++ -Wall -Wextra -Wpedantic -std=c++17 -o program main.cpp
```

- `-Wall`: 초기화되지 않은 변수 사용, 사용하지 않는 변수, 비교 연산자를 대입 연산자로 잘못 쓴 경우 등 흔한 실수 대부분을 잡아줍니다.
- `-Wextra`: `-Wall`보다 더 넓은 범위의 경고를 추가로 활성화합니다.
- `-Wpedantic`: 표준에서 엄격히 벗어나는 비표준 확장 문법 사용을 경고합니다.

예를 들어 다음과 같은 코드는 `-Wall`을 켜면 바로 경고가 나옵니다.

```cpp
int compute(int x) {
    int result;          // 초기화되지 않음
    if (x > 0) {
        result = x * 2;
    }
    return result;        // x <= 0이면 초기화되지 않은 값을 반환 -> 경고
}
```

경고를 그냥 무시하고 넘기는 습관은 위험합니다. 프로젝트가 커질수록 경고가 수백 개씩 쌓이면 정말 중요한 경고가 그 사이에 묻혀 버립니다. 가능하다면 프로젝트 초기부터 경고를 모두 해결하는 것을 목표로 삼거나, 심지어 `-Werror`(경고를 오류로 취급하여 빌드를 실패시키는 옵션)를 적용해 경고가 새로 생기는 즉시 알아차리도록 강제하는 것도 좋은 전략입니다.

## 좋은 습관을 코드 리뷰 체크리스트로 압축하기

이 책에서 다룬 내용을 하나의 체크리스트로 압축하면 다음과 같습니다. 코드를 작성하거나 다른 사람의 코드를 리뷰할 때 참고할 수 있습니다.

- [ ] `new`/`delete`를 직접 짝지어 쓰는 대신, RAII를 지키는 표준 클래스(`std::vector`, `std::string`, 스마트 포인터)로 자원을 감쌌는가?
- [ ] 소유권이 필요 없는 곳에는 참조나 원시 포인터를, 소유권이 필요한 곳에는 `std::unique_ptr`나 `std::shared_ptr`를 사용했는가?
- [ ] 값을 바꾸지 않는 매개변수와 멤버 함수에 `const`를 붙였는가?
- [ ] 포인터 멤버를 가진 클래스가 있다면, 복사·이동 동작(깊은 복사, 복사 금지, 또는 이동만 허용)을 의도적으로 정했는가? 컴파일러의 기본 동작에 우연히 맡겨두지 않았는가?
- [ ] 배열이나 컨테이너 인덱스가 항상 유효한 범위 안에 있다고 확신할 수 있는가? 확신할 수 없다면 `at()`이나 반복자, 범위 기반 `for`를 사용했는가?
- [ ] 함수가 지역 변수의 주소나 참조를 반환하고 있지 않은가?
- [ ] 예외가 발생할 수 있는 코드 경로에서도 자원이 안전하게 해제되는가(즉, 자원 정리를 RAII에 맡겼는가)?
- [ ] `-Wall -Wextra` 경고를 켜고 빌드했을 때 경고가 없는가?

## 다음 학습 단계

이 책은 C++의 기본 문법부터 클래스, 템플릿, STL, 스마트 포인터, 예외 처리, 이동 시맨틱스, 그리고 좋은 코드 습관까지 한 바퀴를 돌았습니다. 이제부터는 각자의 관심 분야에 따라 다음과 같은 방향으로 학습을 넓혀갈 수 있습니다.

- **모던 C++ 표준 더 깊이 파고들기**: 이 책은 C++11에서 도입된 개념(이동 시맨틱스, `auto`, 스마트 포인터 등)을 중심으로 다뤘지만, C++14, 17, 20, 그리고 그 이후 표준에서는 개념(concepts), 범위(ranges), 코루틴(coroutine), 모듈(module) 같은 더 강력한 도구들이 계속 추가되고 있습니다. 표준이 바뀔 때마다 언어에 어떤 기능이 새로 들어왔는지 살펴보는 습관은 C++ 실력을 꾸준히 넓혀줍니다.
- **동시성과 멀티스레딩**: `<thread>`, `<mutex>`, `<atomic>`, `<future>` 등 표준 라이브러리가 제공하는 동시성 도구를 배우면, 여러 작업을 병렬로 처리하는 프로그램을 안전하게 작성할 수 있습니다. 이 영역에서는 특히 9장의 RAII 원칙(락을 자동으로 해제하는 `std::lock_guard` 등)이 그대로 적용됩니다.
- **성능 분석과 최적화**: 프로파일러로 프로그램의 병목을 실제로 측정하고, 캐시 친화적인 자료구조 배치나 메모리 할당 패턴을 고민하는 영역입니다. 1장에서 언급한 "C++가 성능이 중요한 분야에서 선택되는 이유"를 실전에서 체감할 수 있는 단계입니다.
- **특정 응용 분야로의 확장**: 게임/그래픽스 엔진, 임베디드 시스템, 고빈도 거래 시스템, 대규모 서버 인프라 등 C++가 널리 쓰이는 분야마다 그 분야에 특화된 라이브러리와 관행이 있습니다. 관심 있는 분야를 하나 정해 그 분야의 오픈소스 프로젝트 코드를 읽어보는 것도 좋은 학습 방법입니다.
- **빌드 시스템과 협업 도구**: 프로젝트가 커지면 `CMake` 같은 빌드 시스템, 패키지 관리자(vcpkg, Conan 등), 정적 분석 도구, 단위 테스트 프레임워크를 다루는 능력이 실무에서 점점 더 중요해집니다.

C++는 배우는 데 시간이 오래 걸리는 언어로 알려져 있지만, 동시에 한번 익힌 개념들이 다른 언어를 배울 때도 계속 도움이 되는 언어입니다. 메모리가 실제로 어떻게 쓰이는지, 자원의 소유권을 누가 책임지는지에 대한 감각은 C++를 깊이 공부한 사람만이 자연스럽게 갖추게 되는 능력입니다. 이 책에서 다룬 18개의 장은 그 여정의 출발점일 뿐이며, 앞으로는 실제 프로젝트에서 코드를 작성하고, 다른 사람의 코드를 읽고, 버그를 직접 고쳐보는 경험을 통해 이 지식을 단단하게 다져가시기 바랍니다.

## 요약

- RAII 원칙을 기본값으로 삼으면 메모리 누수, 자원 미해제 문제가 대부분 저절로 사라진다(9장, 15장, 16장 참고).
- 원시 포인터 대신 참조와 스마트 포인터(`std::unique_ptr`, `std::shared_ptr`)를 우선적으로 고려하면 소유권이 코드에 명확히 드러난다.
- 값을 바꾸지 않는 변수·매개변수·멤버 함수에는 `const`를 기본으로 붙이는 습관이 안전성과 가독성을 함께 높인다.
- 메모리 누수, 댕글링 포인터, 배열 경계 초과, 얕은 복사는 C++에서 가장 흔한 버그 패턴이며, 각각의 원인과 대책을 이해해두면 대부분 예방할 수 있다.
- `-Wall -Wextra` 같은 컴파일러 경고 옵션을 항상 켜두고, 경고를 무시하지 않는 습관이 버그를 초기에 잡아낸다.
- 이 책을 마친 뒤에는 모던 C++ 표준, 멀티스레딩, 성능 분석, 관심 있는 응용 분야의 실전 코드 읽기 등으로 학습을 이어갈 수 있다.

## 체크리스트

작성한 C++ 코드를 제출하거나 리뷰받기 전에 아래 항목을 스스로 점검해 보십시오.

- [ ] 이 코드에서 `new`와 `delete`를 직접 짝지어 호출하는 곳이 있는가? 있다면 스마트 포인터나 표준 컨테이너로 대체할 수 있는가?
- [ ] 함수의 매개변수 중 값을 바꾸지 않아야 하는데 `const`가 빠진 것이 있는가?
- [ ] 클래스가 포인터나 동적 자원을 멤버로 가지고 있다면, 복사·이동 동작을 의도적으로 설계했는가?
- [ ] 배열/컨테이너 접근이 항상 유효한 범위 안에서 이루어지는지 확인했는가?
- [ ] 함수가 지역 변수의 주소나 참조를 반환하지 않는가?
- [ ] 예외가 발생해도 자원이 안전하게 해제되는 구조인가?
- [ ] `-Wall -Wextra`로 빌드했을 때 경고가 없는가?
- [ ] 다른 사람이 6개월 뒤에 이 코드를 처음 봤을 때, 변수 이름과 구조만으로 의도를 이해할 수 있는가?

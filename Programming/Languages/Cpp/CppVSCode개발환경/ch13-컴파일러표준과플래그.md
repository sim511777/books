# 13장. 컴파일러 표준과 플래그

[◀ 이전: 12장. vcpkg manifest 모드](ch12-vcpkgmanifest모드.md) | [📖 목차](00-목차.md) | [다음: 14장. 디버깅 심화(GDB) ▶](ch14-디버깅심화GDB.md)


2장에서는 `g++ main.cpp -o main`처럼 가장 단순한 형태로 컴파일러를 호출해 보았습니다. 그리고 6장과 7장에서는 `CMakeLists.txt`를 작성해 이 컴파일 과정을 프로젝트 단위로 체계화했습니다. 그런데 지금까지는 컴파일러에게 "어떤 언어 표준을 쓸 것인지", "코드에 잠재적인 문제가 있으면 알려 달라고 할 것인지", "결과물을 얼마나 최적화할 것인지"를 거의 지정하지 않은 채로 작업해 왔습니다.

이 장에서는 실무에서 거의 예외 없이 사용하는 네 가지 컴파일러 플래그 범주, 즉 언어 표준 지정, 경고, 최적화, 디버그 정보를 다룹니다. 그리고 이 플래그들을 커맨드라인에서 직접 지정하는 방법과, CMake 프로젝트에서 지정하는 방법을 함께 살펴봅니다. 이 장에서 다루는 `-g`와 `-O0`의 관계는 14장에서 GDB로 디버깅할 때 그대로 이어집니다.

## C++ 표준 버전 지정하기

### -std 플래그

C++은 표준이 여러 차례 개정되어 왔습니다. C++11, C++14, C++17, C++20, C++23처럼 버전이 올라갈 때마다 새로운 문법과 라이브러리가 추가됩니다. 예를 들어 구조적 바인딩(structured binding)은 C++17부터, 개념(concepts)은 C++20부터 사용할 수 있습니다.

컴파일러는 기본적으로 특정 표준 버전을 가정하고 코드를 해석합니다. 그런데 이 기본값은 GCC 버전마다 다르고, 여러분이 사용하려는 최신 문법을 지원하지 못할 수도 있습니다. 그래서 어떤 표준을 기준으로 컴파일할지 명시적으로 지정하는 것이 안전합니다. 이때 사용하는 것이 `-std` 플래그입니다.

```bash
g++ -std=c++17 main.cpp -o main
g++ -std=c++20 main.cpp -o main
```

GCC가 지원하는 대표적인 값은 다음과 같습니다.

- `-std=c++11`, `-std=c++14`, `-std=c++17`, `-std=c++20`, `-std=c++23`: 각 표준의 ISO 규격을 엄격하게 따릅니다.
- `-std=gnu++17`, `-std=gnu++20`처럼 `gnu`로 시작하는 값도 있습니다. 이는 해당 표준에 GNU 확장 문법을 추가로 허용하는 모드입니다. GCC의 기본값은 보통 이 `gnu++` 계열입니다.

`c++17`과 `gnu++17`의 차이는 실무에서 은근히 중요합니다. `gnu++17`로 컴파일되던 코드가 다른 컴파일러(예: MSVC나 Clang의 엄격 모드)에서는 컴파일되지 않는 경우가 있는데, 그 원인이 GNU 확장 문법을 무심코 사용했기 때문인 경우가 많습니다. 이식성을 중요하게 여긴다면 `gnu++` 대신 순수한 `c++` 계열 값을 사용하는 편이 안전합니다.

`-std`를 지정하지 않으면 어떤 표준이 적용될지는 GCC 버전에 따라 달라지므로, 프로젝트를 시작할 때는 항상 원하는 표준을 명시적으로 지정하는 습관을 들이는 것이 좋습니다.

### CMake에서 표준 지정하기

6장에서 다룬 것처럼 CMake 프로젝트에서는 `g++`을 직접 호출하지 않고 `CMakeLists.txt`를 통해 빌드 설정을 기술합니다. 표준 버전도 마찬가지로 CMake 변수나 명령으로 지정합니다. 두 가지 방법이 있습니다.

**첫 번째: 프로젝트 전역 변수로 지정**

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

- `CMAKE_CXX_STANDARD`: 사용할 C++ 표준의 숫자만 지정합니다(`17`, `20`처럼). CMake가 이 값을 보고 컴파일러에 맞는 `-std` 플래그를 자동으로 만들어 붙여 줍니다.
- `CMAKE_CXX_STANDARD_REQUIRED`: `ON`으로 설정하면, 지정한 표준을 컴파일러가 지원하지 못할 경우 빌드를 조용히 낮은 표준으로 진행하는 대신 에러를 내고 멈춥니다. 끄면 컴파일러가 지원하는 한도 내에서 표준을 낮춰 시도할 수 있습니다.
- `CMAKE_CXX_EXTENSIONS`: `ON`이면 `gnu++17`처럼 GNU 확장이 포함된 플래그를 사용하고, `OFF`이면 순수한 `c++17` 플래그를 사용합니다. 앞서 설명한 이식성 문제를 피하려면 `OFF`으로 두는 것이 일반적으로 권장됩니다.

이 세 줄은 프로젝트 최상단, 즉 `add_executable`이나 `add_library`보다 앞쪽에 두는 것이 관례입니다. 이렇게 설정하면 이 `CMakeLists.txt` 안에서 정의되는 모든 타깃에 동일한 표준이 적용됩니다.

**두 번째: 타깃 단위로 지정 — target_compile_features**

프로젝트 전체가 아니라 특정 타깃에만 표준을 지정하고 싶다면 `target_compile_features`를 사용합니다.

```cmake
add_executable(myapp main.cpp)
target_compile_features(myapp PRIVATE cxx_std_17)
```

`target_compile_features`는 단순히 `-std` 플래그를 붙이는 것을 넘어, "이 타깃은 C++17의 어떤 기능을 요구한다"는 의도를 CMake에게 전달하는 방식입니다. 만약 여러 라이브러리를 조합하는 프로젝트에서 타깃마다 요구하는 표준이 다르다면(예: 라이브러리 A는 C++14로 충분하지만, 이를 사용하는 실행 파일은 C++20 기능이 필요한 경우), `CMAKE_CXX_STANDARD`로 프로젝트 전역을 한 번에 지정하는 것보다 `target_compile_features`로 타깃별로 세밀하게 지정하는 편이 7장에서 다룬 것과 같은 다중 타깃 프로젝트 구조에 더 잘 맞습니다.

`PRIVATE` 키워드는 이 요구 사항이 `myapp` 자신을 컴파일할 때만 적용된다는 뜻입니다. 만약 `myapp`이 라이브러리이고 이를 사용하는 다른 타깃에도 동일한 표준을 강제하고 싶다면 `PUBLIC`을 사용합니다. 이 `PRIVATE`/`PUBLIC`/`INTERFACE`의 의미는 7장에서 다룬 `target_link_libraries`의 가시성 규칙과 동일합니다.

## 경고 플래그: -Wall -Wextra

### 왜 항상 켜두어야 하는가

컴파일러는 기본적으로 문법적으로 명백히 틀린 코드만 에러로 처리합니다. 그런데 문법적으로는 완전히 유효하지만 의도와 다르게 동작할 가능성이 높은 코드도 많습니다. 예를 들면 다음과 같은 코드입니다.

```cpp
int add(int a, int b) {
    int result;
    if (a > 0) {
        result = a + b;
    }
    return result;  // a가 0 이하이면 result는 초기화되지 않은 값
}
```

이 코드는 문법 오류가 없기 때문에 별도의 옵션 없이 컴파일하면 아무 경고 없이 실행 파일이 만들어집니다. 하지만 `a`가 0 이하인 경우 `result`는 초기화되지 않은 채로 반환되며, 이는 정의되지 않은 동작(undefined behavior)입니다. 이런 문제를 컴파일 시점에 잡아내는 것이 경고 플래그의 역할입니다.

```bash
g++ -std=c++17 -Wall -Wextra main.cpp -o main
```

- `-Wall`: "all"이라는 이름과 달리 모든 경고를 켜는 것은 아니지만, 사용되지 않는 변수, 초기화되지 않은 변수 사용 가능성, 비교 연산자의 흔한 실수(`if (x = 5)`처럼 대입과 비교를 혼동한 경우) 등 실무에서 자주 문제가 되는 경고들을 폭넓게 활성화합니다.
- `-Wextra`: `-Wall`에는 포함되지 않는 추가적인 경고들을 켭니다. 예를 들어 부호 있는 정수와 부호 없는 정수를 비교하는 코드, 사용하지 않는 함수 매개변수 등을 잡아냅니다.

이 두 옵션은 사실상 한 쌍으로 취급되어 `-Wall -Wextra`로 항상 함께 켜두는 것이 관례입니다.

경고를 항상 켜두어야 하는 이유는 명확합니다. 경고가 알려주는 문제들 대부분은 당장 프로그램이 멈추지는 않지만, 특정 입력값이나 특정 실행 환경에서만 드러나는 버그의 원인이 됩니다. 이런 버그는 개발 단계에서는 우연히 발견되지 않다가 배포 이후에야 재현되는 경우가 많고, 그때는 원인을 추적하는 비용이 훨씬 커집니다. 반면 컴파일 시점에 경고로 나타나면 코드를 작성하는 그 순간 바로 고칠 수 있습니다. 즉 경고 플래그는 컴파일러가 공짜로 제공하는 가장 저렴한 정적 분석 도구이며, 이를 꺼두는 것은 이 도구가 잡아줄 수 있는 버그를 스스로 포기하는 것과 같습니다.

### -Werror: 경고를 에러로 취급하기

경고를 켜두어도 실제로 그 경고를 읽고 고치지 않으면 의미가 없습니다. 프로젝트가 커지면 경고 메시지가 수십, 수백 개씩 쌓여도 빌드 자체는 성공하기 때문에 경고를 무시하고 넘어가기 쉽습니다. 이를 방지하는 방법이 `-Werror`입니다.

```bash
g++ -std=c++17 -Wall -Wextra -Werror main.cpp -o main
```

`-Werror`는 경고가 하나라도 발생하면 컴파일 자체를 실패시킵니다. 즉 경고를 실질적으로 에러와 동일하게 취급하도록 강제하는 것입니다. 이렇게 하면 개발자가 경고를 못 본 척 넘어갈 수 없게 되고, 코드베이스에 경고가 쌓이는 것을 원천적으로 막을 수 있습니다.

다만 `-Werror`를 프로젝트 전체에 무조건 적용하면 부작용도 있습니다. 새로운 GCC 버전으로 업그레이드했을 때 이전에는 없던 경고가 새로 추가되어 기존에 잘 컴파일되던 코드가 갑자기 빌드에 실패하는 경우가 그렇습니다. 또한 아직 리팩터링하지 못한 레거시 코드가 있다면 그 코드의 경고 때문에 프로젝트 전체의 빌드가 막혀버릴 수도 있습니다. 이런 상황을 대비해 특정 경고만 선택적으로 에러로 승격시키는 것도 가능합니다.

```bash
g++ -std=c++17 -Wall -Wextra -Werror=return-type main.cpp -o main
```

이렇게 하면 `-Wall -Wextra`가 켜는 다른 경고들은 여전히 경고로만 표시되고, `return-type`(함수가 값을 반환해야 하는데 반환하지 않는 경로가 있는 경우)에 해당하는 경고만 에러로 취급됩니다. 처음 `-Werror`를 도입하는 프로젝트라면 전체를 한꺼번에 적용하기보다, 이렇게 특정 경고부터 단계적으로 에러로 승격시켜 나가는 방식이 현실적인 경우가 많습니다.

## 최적화 플래그: -O0 vs -O2/-O3

`-O` 플래그는 컴파일러가 생성하는 기계어 코드를 얼마나 최적화할지를 지정합니다.

- `-O0`: 최적화를 수행하지 않습니다. 소스 코드의 각 문장이 거의 그대로, 순서 그대로 기계어로 옮겨집니다. 컴파일 속도가 가장 빠르고, 생성된 코드는 소스 코드와 일대일로 대응됩니다.
- `-O1`: 기본적인 수준의 최적화를 수행합니다. 컴파일 시간을 크게 늘리지 않으면서 어느 정도 성능을 개선합니다.
- `-O2`: 실무에서 릴리스 빌드에 가장 널리 쓰이는 수준입니다. 함수 인라이닝, 루프 최적화, 불필요한 계산 제거 등 다양한 최적화 기법을 적용하지만, 코드 크기를 과도하게 늘리는 최적화는 제외합니다.
- `-O3`: `-O2`의 모든 최적화에 더해 벡터화(vectorization)나 더 공격적인 함수 인라이닝 등을 추가로 적용합니다. 실행 속도는 `-O2`보다 빨라질 수 있지만, 코드 크기가 커지고 경우에 따라서는 캐시 효율이 떨어져 오히려 느려지는 경우도 있어, 반드시 실측을 통해 확인하는 것이 좋습니다.
- `-Os`: 실행 속도보다 코드 크기를 우선적으로 최적화합니다. 임베디드 환경처럼 저장 공간이 제한적인 경우에 사용합니다.

```bash
# 디버그 빌드: 최적화 없이, 디버그 정보 포함
g++ -std=c++17 -Wall -Wextra -g -O0 main.cpp -o main_debug

# 릴리스 빌드: 최적화 적용
g++ -std=c++17 -Wall -Wextra -O2 main.cpp -o main_release
```

### 디버깅할 때는 왜 -O0을 써야 하는가

`-O2`나 `-O3`가 수행하는 최적화는 프로그램의 최종 실행 결과는 그대로 유지하면서, 그 결과에 이르는 내부 과정을 완전히 다른 방식으로 재구성합니다. 컴파일러는 다음과 같은 일들을 서슴없이 수행합니다.

- 여러 줄에 걸친 코드를 재배열하거나 하나로 합칩니다.
- 값이 바뀌지 않는 변수를 아예 메모리에 두지 않고 레지스터에만 유지하거나, 계산 결과를 상수로 미리 확정해 변수 자체를 코드에서 지워버립니다.
- 함수 호출을 호출부에 그대로 풀어 넣는 인라이닝을 수행해, 원래는 별도의 함수였던 코드가 호출한 쪽 코드와 뒤섞입니다.
- 반복문을 풀어헤치거나(loop unrolling) 실행 순서를 바꿉니다.

이 모든 변형은 프로그램이 내는 최종 출력이 같다는 것을 전제로 하기 때문에 문제가 되지 않습니다. 하지만 14장에서 다룰 GDB로 소스 코드 한 줄 한 줄을 따라가며 디버깅하려는 입장에서는 이야기가 다릅니다. 최적화된 코드에서는 소스 코드의 특정 줄과 실제로 실행되는 기계어 명령이 더 이상 일대일로 대응하지 않습니다. 그 결과 다음과 같은 현상들이 나타납니다.

- 디버거로 한 줄씩 실행(step)해도 소스 코드 순서와 다르게 건너뛰거나 되돌아가는 것처럼 보입니다.
- 특정 변수를 출력(print)하려고 하면 `<optimized out>`이라는 메시지가 뜨면서 값을 확인할 수 없습니다. 컴파일러가 그 변수를 아예 메모리에 두지 않았기 때문입니다.
- 중단점을 특정 줄에 걸었는데 그 줄에서 멈추지 않거나, 함수 이름으로 중단점을 걸었는데 인라이닝되어 그 함수가 실행 파일 안에 독립적으로 존재하지 않는 경우도 있습니다.

이런 이유로 디버깅이 목적인 빌드에서는 `-O0`을 사용해 소스 코드와 실행되는 기계어 사이의 대응 관계를 최대한 그대로 유지하는 것이 원칙입니다. 반대로 실제 배포할 릴리스 빌드에서는 `-O2`나 `-O3`으로 성능을 확보하되, 그 빌드로는 세밀한 디버깅을 시도하지 않는 것이 일반적인 관행입니다.

## 디버그 정보: -g 플래그

`-O0`으로 최적화를 꺼두는 것만으로는 충분하지 않습니다. GDB가 "지금 실행 중인 기계어 명령이 소스 코드의 몇 번째 줄에 해당하는지", "이 메모리 주소에 있는 값이 소스 코드의 어떤 변수 이름에 대응하는지"를 알려면 별도의 정보가 필요합니다. 이 정보를 실행 파일에 포함시키는 플래그가 `-g`입니다.

```bash
g++ -std=c++17 -g -O0 main.cpp -o main
```

`-g`를 붙이면 컴파일러는 실행 파일 안에 DWARF라는 형식의 디버그 정보를 함께 저장합니다. 여기에는 다음과 같은 내용이 들어갑니다.

- 각 기계어 명령이 소스 코드의 어느 파일, 몇 번째 줄에 대응하는지에 대한 매핑 정보
- 함수와 변수의 이름, 타입 정보
- 스택 프레임의 구조 정보(함수 호출 시 지역 변수와 매개변수가 스택의 어디에 위치하는지)

`-g`는 최적화 플래그와 독립적으로 붙일 수 있는 옵션입니다. 즉 `-O2 -g`처럼 최적화된 빌드에도 디버그 정보를 포함시킬 수 있습니다. 이 조합은 릴리스 빌드에서 발생한 문제를 사후에 분석해야 할 때 유용합니다. 다만 앞서 설명한 것처럼 최적화된 코드는 소스 코드와의 대응 관계가 흐트러지기 때문에, `-O2 -g`로 디버깅하는 것은 `-O0 -g`만큼 매끄럽지 않습니다. 그래서 실제로 한 줄씩 코드를 추적하며 디버깅할 때는 `-g -O0` 조합이, 배포된 릴리스 빌드에서 발생한 크래시를 사후 분석할 때는 `-O2 -g`(또는 이에 준하는 조합)가 각각 쓰이는 경우가 많습니다.

`-g`를 붙이지 않고 빌드한 실행 파일로 GDB를 실행하면, 중단점을 소스 코드 줄 번호로 걸 수 없고 변수 이름으로 값을 조회할 수도 없습니다. 남아있는 것은 메모리 주소와 레지스터 값 같은 저수준 정보뿐입니다. 14장에서 다룰 GDB 명령들은 모두 `-g`로 빌드된 실행 파일을 전제로 합니다.

## CMake의 빌드 타입이 이 플래그들을 자동으로 설정한다

지금까지 다룬 `-std`, `-Wall -Wextra`, `-O0`/`-O2`, `-g`를 매번 커맨드라인에 직접 나열하는 것은 번거롭습니다. CMake는 `CMAKE_BUILD_TYPE`이라는 변수를 통해 이 조합을 미리 정의된 프로파일로 묶어서 제공합니다.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
```

GCC를 사용하는 경우, CMake가 각 빌드 타입에 대해 기본적으로 적용하는 플래그는 대략 다음과 같습니다.

| CMAKE_BUILD_TYPE | 적용되는 플래그 | 용도 |
|---|---|---|
| `Debug` | `-g` | 최적화 없이(`-O0`이 GCC의 기본값이므로 별도 지정 없이도 사실상 `-O0`) 디버그 정보를 포함 |
| `Release` | `-O3 -DNDEBUG` | 최적화를 최대로 적용하고, `assert` 매크로를 비활성화 |
| `RelWithDebInfo` | `-O2 -g -DNDEBUG` | 최적화를 적용하면서 디버그 정보도 함께 포함 |
| `MinSizeRel` | `-Os -DNDEBUG` | 실행 파일 크기를 최소화 |

즉 `CMAKE_BUILD_TYPE=Debug`로 설정하는 것은 여러분이 매번 `-g`를 손으로 붙이는 것과 사실상 같은 효과이고, `CMAKE_BUILD_TYPE=Release`로 설정하는 것은 `-O3 -DNDEBUG`를 손으로 붙이는 것과 같은 효과입니다. `DNDEBUG`는 `NDEBUG`라는 매크로를 정의하는 `-D` 옵션으로, 이 매크로가 정의되면 `<cassert>`의 `assert()` 매크로가 아무 동작도 하지 않게 됩니다. 즉 디버그 빌드에서는 `assert`로 잡아내던 논리적 오류 검사가, 릴리스 빌드에서는 성능을 위해 제거된다는 뜻입니다.

이 표에서 알 수 있듯이, `CMAKE_BUILD_TYPE`이 자동으로 설정해 주는 것은 이 장에서 다룬 `-O`와 `-g`, 그리고 `NDEBUG` 매크로뿐입니다. `-std`나 `-Wall -Wextra`는 빌드 타입과 무관하게 별도로 지정해야 합니다. 따라서 실무에서 `CMakeLists.txt`를 작성할 때는 보통 다음과 같은 형태를 갖추게 됩니다.

```cmake
cmake_minimum_required(VERSION 3.20)
project(myapp)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(myapp main.cpp)
target_compile_options(myapp PRIVATE -Wall -Wextra)
```

여기에 `-DCMAKE_BUILD_TYPE=Debug` 또는 `Release`를 커맨드라인에서 지정해 주면, 표준 지정과 경고 플래그는 `CMakeLists.txt`가, 최적화와 디버그 정보는 빌드 타입이 각각 담당하는 구조가 완성됩니다. 만약 빌드 타입을 아예 지정하지 않으면 `CMAKE_BUILD_TYPE`은 빈 문자열이 되고, 이 경우 위 표의 어떤 플래그도 자동으로 추가되지 않으므로 `-O0`에 가깝지만 `-g`도 없는 애매한 상태로 빌드된다는 점에 주의해야 합니다. 그래서 프로젝트를 구성할 때는 빌드 타입을 명시적으로 지정하는 습관을 들이는 것이 좋습니다.

## 요약

- `-std=c++17`, `-std=c++20`처럼 언어 표준 버전을 명시적으로 지정해야 하며, `gnu++` 계열 대신 순수한 `c++` 계열을 쓰면 이식성이 높아집니다.
- CMake에서는 `CMAKE_CXX_STANDARD`/`CMAKE_CXX_STANDARD_REQUIRED`/`CMAKE_CXX_EXTENSIONS`로 프로젝트 전체의 표준을 지정하거나, `target_compile_features`로 타깃별로 지정할 수 있습니다.
- `-Wall -Wextra`는 잠재적인 버그를 컴파일 시점에 잡아내는 가장 저렴한 정적 분석 도구이므로 항상 켜두는 것이 좋으며, `-Werror`는 경고를 에러로 승격시켜 무시하고 넘어가는 것을 막습니다.
- `-O0`은 최적화를 하지 않아 소스 코드와 기계어의 대응 관계를 그대로 유지하므로 디버깅에 적합하고, `-O2`/`-O3`는 실행 속도를 높이지만 디버깅을 어렵게 만듭니다.
- `-g`는 GDB가 소스 코드 줄 번호와 변수 이름을 추적할 수 있도록 디버그 정보(DWARF)를 실행 파일에 포함시키는 플래그입니다.
- `CMAKE_BUILD_TYPE=Debug`는 `-g`(및 사실상의 `-O0`)를, `Release`는 `-O3 -DNDEBUG`를 자동으로 적용해 주지만, `-std`나 `-Wall -Wextra`는 별도로 지정해야 합니다.

## 연습문제

1. `-std=c++17`과 `-std=gnu++17`의 차이를 설명하고, 이식성을 중요하게 여기는 프로젝트에서 어느 쪽을 선택해야 하는지 근거를 들어 서술하세요.
2. `CMAKE_CXX_STANDARD`로 프로젝트 전체의 표준을 지정하는 방식과 `target_compile_features`로 타깃별로 지정하는 방식은 각각 어떤 상황에 더 적합한지 설명하세요.
3. `-Wall -Wextra`를 켜두어야 하는 이유를 초기화되지 않은 변수 사용의 예를 들어 설명하고, `-Werror`를 프로젝트 전체에 무조건 적용했을 때 발생할 수 있는 부작용을 하나 이상 제시하세요.
4. `-O2`로 최적화된 실행 파일을 GDB로 디버깅할 때 `<optimized out>` 메시지가 뜨는 이유를 설명하고, 이를 피하려면 어떤 플래그 조합으로 다시 빌드해야 하는지 답하세요.
5. `CMAKE_BUILD_TYPE=Release`로 빌드했을 때 자동으로 적용되는 플래그를 나열하고, `NDEBUG` 매크로가 정의되었을 때 `assert()`가 어떻게 동작이 바뀌는지 설명하세요.

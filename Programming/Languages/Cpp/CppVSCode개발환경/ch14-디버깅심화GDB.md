# 14장. 디버깅 심화(GDB)

[◀ 이전: 13장. 컴파일러 표준과 플래그](ch13-컴파일러표준과플래그.md) | [📖 목차](00-목차.md) | [다음: 15장. 정적 분석과 코드 포맷팅 ▶](ch15-정적분석과코드포맷팅.md)


4장에서는 VS Code의 UI를 통해 디버깅을 경험해 보았습니다. 코드 왼쪽 여백을 클릭해 빨간 점(중단점)을 찍고, F5를 눌러 디버깅을 시작하고, 상단의 재생/건너뛰기 버튼을 눌러 코드를 한 줄씩 따라가고, 왼쪽 패널에서 변수 값을 확인했습니다. 이 모든 과정은 사실 VS Code가 여러분 대신 GDB(GNU Debugger)라는 프로그램을 실행하고, 그 결과를 그래픽 화면으로 보기 좋게 그려준 것에 지나지 않습니다.

이 장에서는 그 GDB 자체를 커맨드라인에서 직접 다뤄봅니다. UI 뒤에 숨어 있던 명령어를 직접 입력해 보면, VS Code의 버튼 하나하나가 실제로 어떤 동작을 수행하는지 더 명확하게 이해할 수 있고, VS Code 없이 서버 환경 등에서 디버깅해야 하는 상황에도 대응할 수 있습니다. 이 장의 모든 예제는 13장에서 설명한 `-g -O0` 플래그로 빌드한 실행 파일을 전제로 합니다. 이 플래그 없이는 GDB가 소스 코드 줄 번호나 변수 이름을 전혀 알아볼 수 없다는 점을 다시 한번 기억해 두기 바랍니다.

## 실습용 코드 준비하기

이 장에서 계속 사용할 간단한 예제를 준비합니다.

```cpp
// debug_demo.cpp
#include <iostream>
#include <vector>

int sumUpTo(int n) {
    int total = 0;
    for (int i = 1; i <= n; ++i) {
        total += i;
    }
    return total;
}

int main() {
    std::vector<int> numbers = {3, 5, 7, 9};
    int target = 0;

    for (size_t i = 0; i <= numbers.size(); ++i) {  // 의도적인 버그: <=
        int value = numbers[i];
        target += sumUpTo(value);
        std::cout << "i=" << i << " value=" << value << " target=" << target << "\n";
    }

    return 0;
}
```

이 코드는 `numbers.size()`가 4인데도 반복 조건을 `i <= numbers.size()`로 잘못 작성해서, `i`가 4일 때 `numbers[4]`라는 존재하지 않는 원소에 접근하게 됩니다. `std::vector`의 `operator[]`는 범위를 검사하지 않으므로 이 접근은 정의되지 않은 동작이며, 운이 나쁘면 세그멘테이션 폴트로 이어집니다. 이 장의 뒷부분에서 이 버그를 GDB로 실제로 추적해 봅니다. 먼저 디버그 정보를 포함해 컴파일합니다.

```bash
g++ -std=c++17 -Wall -Wextra -g -O0 debug_demo.cpp -o debug_demo
```

## GDB를 커맨드라인에서 시작하기

빌드가 끝나면 GDB에 이 실행 파일을 넘겨 실행합니다.

```bash
gdb ./debug_demo
```

명령줄 인자를 받는 프로그램이라면 `--args`로 인자를 함께 전달할 수 있습니다.

```bash
gdb --args ./debug_demo arg1 arg2
```

GDB를 실행하면 `(gdb)`라는 프롬프트가 나타납니다. 이후의 모든 명령은 이 프롬프트에 입력합니다.

## 기본 명령어

### break: 중단점 설정

`break`(축약형 `b`)는 VS Code에서 코드 줄 왼쪽을 클릭하던 것과 같은 역할을 합니다. 파일명과 줄 번호, 또는 함수 이름으로 중단점을 걸 수 있습니다.

```bash
(gdb) break debug_demo.cpp:19
(gdb) break sumUpTo
```

첫 번째 명령은 19번째 줄(`int value = numbers[i];`)에, 두 번째 명령은 `sumUpTo` 함수의 시작 지점에 중단점을 겁니다. 중단점을 걸면 GDB는 `Breakpoint 1 at 0x...: file debug_demo.cpp, line 19.`처럼 몇 번 중단점으로 등록되었는지 알려줍니다. 이 번호는 이후 중단점을 지우거나(`delete 1`) 비활성화할 때(`disable 1`) 사용합니다.

### run: 프로그램 실행

`run`(축약형 `r`)은 프로그램을 처음부터 실행합니다. 걸어둔 중단점을 만나면 그 지점에서 실행이 멈춥니다.

```bash
(gdb) run
```

### next와 step: 한 줄씩 실행하기

중단점에서 멈춘 다음 코드를 한 줄씩 따라가려면 `next`(`n`)와 `step`(`s`)을 사용합니다. 이 둘의 차이는 함수 호출을 만났을 때 드러납니다.

- `next`: 현재 줄이 함수 호출을 포함하고 있어도, 그 함수 내부로 들어가지 않고 함수 호출 전체를 한 번에 실행한 뒤 다음 줄로 넘어갑니다. VS Code의 "Step Over" 버튼과 같습니다.
- `step`: 현재 줄이 함수 호출을 포함하고 있으면, 그 함수 내부의 첫 줄로 들어갑니다. VS Code의 "Step Into" 버튼과 같습니다.

예를 들어 `target += sumUpTo(value);` 줄에서 `next`를 실행하면 `sumUpTo` 함수 전체가 실행되고 그 결과만 반영된 채 바로 다음 줄로 넘어갑니다. 반면 같은 줄에서 `step`을 실행하면 `sumUpTo` 함수의 첫 줄인 `int total = 0;`으로 들어가게 됩니다. 이미 정확성이 검증된 함수(예: 표준 라이브러리 함수)라면 `next`로 건너뛰고, 버그가 있을 것으로 의심되는 함수라면 `step`으로 들어가는 식으로 상황에 맞게 구분해서 사용합니다.

### continue: 다음 중단점까지 계속 실행

`continue`(`c`)는 현재 멈춘 지점부터 다음 중단점을 만나거나 프로그램이 끝날 때까지 실행을 계속합니다.

```bash
(gdb) continue
```

### print: 변수와 표현식 확인

`print`(`p`)는 현재 멈춘 지점에서 변수나 표현식의 값을 출력합니다.

```bash
(gdb) print i
$1 = 2
(gdb) print numbers[i]
$2 = 7
(gdb) print numbers.size()
$3 = 4
(gdb) print total + 10
$4 = 25
```

`print`는 단순히 변수 하나만 출력하는 것이 아니라, C++ 표현식을 그 자리에서 평가할 수 있습니다. 배열 인덱싱, 산술 연산, 심지어 `numbers.size()`처럼 멤버 함수 호출까지 가능합니다. `$1`, `$2`처럼 붙는 번호는 GDB가 각 출력 결과에 자동으로 부여하는 값 히스토리 번호로, `print $1 + $2`처럼 이전 결과를 다시 참조할 때 사용할 수 있습니다.

구조체나 클래스 객체를 출력하면 멤버 전체가 함께 출력됩니다.

```bash
(gdb) print numbers
$5 = std::vector of length 4, capacity 4 = {3, 5, 7, 9}
```

### backtrace: 호출 스택 확인

`backtrace`(`bt`, 또는 `where`)는 현재 멈춘 지점에 이르기까지 어떤 함수들이 어떤 순서로 호출되었는지 스택 전체를 보여줍니다.

```bash
(gdb) backtrace
#0  sumUpTo (n=7) at debug_demo.cpp:6
#1  0x0000000000401234 in main () at debug_demo.cpp:20
```

`#0`이 현재 실행 중인 가장 안쪽 함수이고, 번호가 커질수록 그 함수를 호출한 바깥쪽 함수입니다. 위 예시는 `main`의 20번째 줄에서 `sumUpTo(7)`을 호출했고, 지금 그 `sumUpTo` 안에 멈춰 있다는 뜻입니다. `frame 1`처럼 번호를 지정하면 해당 스택 프레임으로 이동해 그 시점의 지역 변수를 `print`로 확인할 수 있습니다.

## 조건부 중단점

지금까지의 예제처럼 반복문 안에서 특정 조건일 때만 멈추고 싶은 경우가 많습니다. 매번 `continue`를 여러 번 눌러가며 원하는 반복 횟수까지 수동으로 넘어가는 것은 비효율적입니다. 이때 조건부 중단점을 사용합니다.

```bash
(gdb) break debug_demo.cpp:19 if i == 3
```

이 명령은 19번째 줄에 중단점을 걸되, `i`가 3일 때만 실제로 멈추도록 합니다. `i`가 0, 1, 2일 때는 이 중단점을 그냥 지나칩니다. 함수 이름으로 건 중단점에도 동일하게 조건을 붙일 수 있습니다.

```bash
(gdb) break sumUpTo if n > 5
```

이미 걸어둔 중단점에 나중에 조건을 추가하거나 바꾸고 싶다면 `condition` 명령을 사용합니다.

```bash
(gdb) condition 1 i == 3
```

이 명령은 1번 중단점에 `i == 3`이라는 조건을 새로 설정(또는 기존 조건을 교체)합니다. 조건을 완전히 제거하려면 조건식 없이 `condition 1`만 입력합니다.

조건부 중단점은 특히 반복문이 수천, 수만 번 도는 상황에서 특정 반복 횟수나 특정 값에서만 문제가 발생할 때 유용합니다. 예를 들어 "1000번째 반복에서만 값이 이상해진다"는 것을 알고 있다면 `break loop.cpp:42 if count == 1000`처럼 걸어두고 `run` 한 번으로 바로 그 지점까지 도달할 수 있습니다.

## 세그멘테이션 폴트 디버깅 흐름

이제 앞서 준비한 `debug_demo.cpp`의 버그를 실제로 추적해 봅니다. 중단점 없이 그냥 실행해 봅니다.

```bash
(gdb) run
i=0 value=3 target=6
i=1 value=5 target=21
i=2 value=7 target=49
i=3 value=9 target=94

Program received signal SIGSEGV, Segmentation fault.
0x0000000000401556 in main () at debug_demo.cpp:19
19          int value = numbers[i];
```

GDB는 프로그램이 세그멘테이션 폴트(SIGSEGV)로 죽는 순간 자동으로 실행을 멈추고, 그 시점의 소스 코드 위치를 그대로 보여줍니다. 이것이 GDB로 크래시를 분석할 때 가장 먼저 확인해야 할 정보입니다. 프로그램이 그냥 죽어버리면 어느 줄에서 문제가 생겼는지 알 방법이 없지만, GDB 아래에서 실행하면 크래시가 발생한 정확한 줄이 즉시 드러납니다.

다음으로 할 일은 `backtrace`로 그 지점에 이르기까지의 호출 경로를 확인하는 것입니다.

```bash
(gdb) backtrace
#0  0x0000000000401556 in main () at debug_demo.cpp:19
```

이 경우는 `main` 함수 안에서 바로 크래시가 났으므로 스택이 한 줄뿐입니다. 만약 크래시가 여러 겹의 함수 호출 안쪽에서 발생했다면 `backtrace`에는 그만큼 여러 줄의 프레임이 나타나고, 각 프레임을 따라가며 어떤 호출 경로로 여기까지 왔는지 파악할 수 있습니다.

이제 크래시가 발생한 줄의 변수들을 `print`로 확인합니다.

```bash
(gdb) print i
$1 = 4
(gdb) print numbers.size()
$2 = 4
```

`i`가 4인데 `numbers.size()`도 4입니다. `std::vector`의 유효한 인덱스는 0부터 `size() - 1`, 즉 0부터 3까지이므로 `numbers[4]`는 이미 범위를 벗어난 접근입니다. 이 시점에서 원인이 명확해집니다. `main` 함수의 반복문 조건이 `i <= numbers.size()`로 되어 있어 `i`가 4일 때도 반복이 한 번 더 실행된 것입니다. 조건을 `i < numbers.size()`로 고치면 이 버그는 해결됩니다.

정리하면 세그멘테이션 폴트를 GDB로 추적하는 흐름은 다음과 같습니다.

1. `-g`로 빌드한 실행 파일을 GDB로 실행하고 `run`으로 프로그램을 돌립니다.
2. 크래시가 발생하면 GDB가 자동으로 멈추고 신호(SIGSEGV 등)와 크래시 위치를 보여줍니다.
3. `backtrace`로 크래시 지점까지의 호출 스택을 확인합니다.
4. 각 프레임에서 `print`로 관련 변수 값을 확인해, 어떤 값이 잘못되어 있었는지(범위를 벗어난 인덱스, 널 포인터 등) 원인을 좁혀 나갑니다.

## 그 밖에 알아두면 유용한 명령

- `list`(`l`): 현재 멈춘 지점 주변의 소스 코드를 보여줍니다. `list 10,20`처럼 범위를 지정할 수도 있습니다.
- `info locals`: 현재 스택 프레임의 지역 변수를 모두 출력합니다. 어떤 변수 이름이 있는지 잘 기억나지 않을 때 유용합니다.
- `info args`: 현재 함수에 전달된 인자 값을 모두 출력합니다.
- `watch`: 특정 변수의 값이 바뀌는 순간마다 자동으로 멈추는 감시점(watchpoint)을 설정합니다. 예를 들어 `watch total`이라고 하면 `total`의 값이 바뀔 때마다 실행이 멈추고 이전 값과 이후 값을 함께 보여줍니다. 어디선가 예상치 못하게 값이 바뀌는 변수를 추적할 때 `break`보다 편리합니다.
- `up` / `down`: `backtrace`로 확인한 스택 프레임 사이를 한 단계씩 위(호출한 쪽)나 아래(호출된 쪽)로 이동합니다.
- `finish`: 현재 함수의 실행이 끝나고 호출한 쪽으로 돌아갈 때까지 실행한 뒤 멈추고, 그 함수가 반환한 값을 보여줍니다. `step`으로 함수 안에 들어갔다가 더 볼 것이 없어 바로 빠져나오고 싶을 때 유용합니다.
- `delete`: 중단점을 지웁니다. 번호 없이 `delete`만 입력하면 모든 중단점을 지웁니다.

## VS Code 디버그 콘솔에서 GDB 표현식 사용하기

4장에서 F5로 디버깅을 시작하면 하단에 "디버그 콘솔(Debug Console)" 패널이 함께 열리는 것을 보았을 것입니다. 이 패널은 사실 지금까지 다룬 GDB와 직접 대화할 수 있는 창구입니다.

디버그 콘솔에 변수 이름이나 표현식을 그냥 입력하면, VS Code의 C/C++ 확장이 이를 평가해서 결과를 보여줍니다.

```
numbers[2]
```

이렇게 입력하면 `print numbers[2]`를 실행한 것과 비슷한 결과가 나타납니다. 대부분의 경우 이 정도로 충분하지만, `watch`나 `info locals`처럼 GDB 고유의 명령을 그대로 실행하고 싶을 때는 앞에 `-exec`를 붙여야 합니다.

```
-exec info locals
-exec backtrace
-exec print numbers.size()
-exec watch total
```

`-exec` 접두사는 "이 뒤의 문자열을 표현식으로 평가하지 말고, GDB에게 그대로 명령어로 전달하라"는 뜻입니다. VS Code가 사용하는 디버그 어댑터(cpptools 확장의 경우 GDB를 감싼 MI 인터페이스)는 단순한 값 조회는 자동으로 알아서 처리하지만, `backtrace`나 `watch`처럼 GDB 세션 자체의 동작을 바꾸는 명령은 `-exec`로 명시적으로 요청해야 합니다.

이 사실을 알아두면 4장에서 그래픽 UI로만 다뤘던 디버깅 세션을, 필요할 때는 커맨드라인 GDB와 똑같은 방식으로 다룰 수 있습니다. 예를 들어 UI의 "조건부 중단점" 입력창이 다소 제한적으로 느껴진다면, 디버그 콘솔에 직접 `-exec condition 1 i == 3`을 입력해 이 장에서 다룬 `condition` 명령을 그대로 사용할 수도 있습니다. 결국 VS Code의 디버깅 UI는 이 장에서 배운 GDB 명령어들을 버튼과 패널로 감싸놓은 것이고, 디버그 콘솔은 그 포장을 벗기고 GDB 본연의 인터페이스에 직접 접근할 수 있는 통로인 셈입니다.

## 요약

- GDB는 `break`(중단점), `run`(실행), `next`/`step`(한 줄 실행, 함수 내부 진입 여부가 다름), `continue`(다음 중단점까지 실행), `print`(변수/표현식 출력), `backtrace`(호출 스택 확인)라는 기본 명령으로 대부분의 디버깅 작업을 수행할 수 있습니다.
- 조건부 중단점(`break 파일:줄번호 if 조건식`)을 사용하면 반복문 등에서 특정 조건이 성립할 때만 멈추도록 할 수 있으며, `condition` 명령으로 이미 걸어둔 중단점의 조건을 나중에 추가하거나 바꿀 수 있습니다.
- 세그멘테이션 폴트가 발생하면 GDB는 자동으로 실행을 멈추고 크래시 위치를 보여주며, 이후 `backtrace`로 호출 경로를, `print`로 관련 변수 값을 확인해 원인을 좁혀 나가는 것이 기본적인 분석 흐름입니다.
- `list`, `info locals`, `info args`, `watch`, `finish` 같은 보조 명령들은 상황에 따라 `break`/`print`만으로는 부족한 부분을 보완해 줍니다.
- VS Code의 디버그 콘솔은 단순 표현식을 자동으로 평가해 주지만, `backtrace`나 `watch` 같은 GDB 고유 명령을 실행하려면 앞에 `-exec`를 붙여야 합니다. 이를 통해 4장에서 다룬 그래픽 디버깅 UI와 이 장에서 다룬 커맨드라인 GDB가 결국 같은 도구를 다른 방식으로 노출한 것임을 확인할 수 있습니다.

## 연습문제

1. GDB의 `next`와 `step` 명령의 차이를 설명하고, 각각을 사용하는 것이 더 적합한 상황을 하나씩 제시하세요.
2. `break debug_demo.cpp:19 if i == 3`이라는 명령이 하는 일을 설명하고, 이미 걸어둔 중단점에 조건을 나중에 추가하려면 어떤 명령을 사용해야 하는지 답하세요.
3. 세그멘테이션 폴트가 발생했을 때 GDB로 원인을 파악하는 절차를 순서대로 서술하세요.
4. VS Code 디버그 콘솔에서 `-exec`를 붙이는 경우와 붙이지 않는 경우의 차이를 설명하세요.
5. 13장에서 다룬 `-O2` 플래그로 빌드한 실행 파일을 GDB로 디버깅하면 어떤 문제가 발생할 수 있는지 설명하고, 이를 피하기 위한 컴파일 옵션 조합을 제시하세요.

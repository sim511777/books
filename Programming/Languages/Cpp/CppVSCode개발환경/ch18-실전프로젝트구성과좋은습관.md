## 배운 것을 하나의 프로젝트로 모으기

1장부터 17장까지 우리는 GCC, VS Code, CMake, Ninja, vcpkg, 그리고 clang-format·clang-tidy·CTest까지 한 켜씩 도구를 쌓아 올렸습니다. 각 도구를 따로 배울 때는 그 도구 하나에 집중했지만, 실전에서 새 프로젝트를 시작할 때는 이 모든 도구가 처음부터 함께 자리를 잡고 있어야 합니다. 이번 장에서는 지금까지 배운 요소를 모두 담은 "표준" 프로젝트 폴더 구조를 제안하고, 새 프로젝트를 시작할 때 따라갈 수 있는 체크리스트를 정리한 뒤, 18개 장 전체를 돌아보는 회고로 이 책을 마무리하겠습니다.

## 표준 프로젝트 폴더 구조

아래 구조는 이 책에서 다룬 도구를 모두 사용하는 중소규모 C++ 프로젝트의 전형적인 모습입니다. 실제 프로젝트마다 세부 사항은 달라지겠지만, 뼈대가 되는 원칙은 대부분의 프로젝트에 그대로 적용할 수 있습니다.

```
my-project/
├── .vscode/
│   ├── settings.json
│   ├── launch.json
│   └── extensions.json
├── include/
│   └── my-project/
│       └── calc.h
├── src/
│   ├── calc.cpp
│   └── main.cpp
├── tests/
│   ├── CMakeLists.txt
│   └── test_calc.cpp
├── CMakeLists.txt
├── CMakePresets.json
├── vcpkg.json
├── .clang-format
├── .clang-tidy
└── .gitignore
```

각 항목이 이 책의 어느 장과 연결되는지, 그리고 왜 그 자리에 있는지를 하나씩 짚어보겠습니다.

### `src/`와 `include/` — 소스와 공개 헤더의 분리

`include/`에는 다른 파일에서 가져다 쓸 헤더만 두고, 실제 구현이 담긴 `.cpp` 파일은 `src/`에 둡니다. 헤더를 `include/my-project/`처럼 프로젝트 이름으로 한 번 더 감싸 두면, 나중에 이 프로젝트가 라이브러리로 다른 프로젝트에 설치되었을 때 `#include <my-project/calc.h>`처럼 다른 라이브러리의 헤더와 이름이 겹치지 않는 형태로 include할 수 있습니다. 7장에서 다룬 프로젝트 구조화의 연장선입니다.

### `tests/` — 17장에서 다룬 테스트 코드

테스트 코드는 `src/`와 섞어두지 않고 별도 디렉터리로 분리합니다. 자체 `CMakeLists.txt`를 두고 최상위 `CMakeLists.txt`에서 `add_subdirectory(tests)`로 포함시키면, 테스트가 필요 없는 배포용 빌드에서는 이 디렉터리 전체를 옵션 하나로 빌드 대상에서 제외할 수도 있습니다.

```cmake
option(MYPROJECT_BUILD_TESTS "테스트를 빌드할지 여부" ON)

if(MYPROJECT_BUILD_TESTS)
    enable_testing()
    add_subdirectory(tests)
endif()
```

### `CMakeLists.txt`와 `CMakePresets.json` — 6, 7, 16장

`CMakeLists.txt`는 프로젝트의 빌드 설계도이고, `CMakePresets.json`은 16장에서 다룬 것처럼 "이 프로젝트를 어떤 컴파일러, 어떤 빌드 디렉터리, 어떤 옵션으로 구성할지"를 이름 붙여 저장해 둔 파일입니다. 팀원이나 CI 서버가 `cmake --preset linux-debug` 한 줄만으로 동일한 환경을 재현할 수 있게 해주므로, 개인 프로젝트라도 처음부터 만들어 두는 습관을 들이는 것이 좋습니다.

### `vcpkg.json` — 10~12장

프로젝트가 의존하는 외부 라이브러리 목록을 manifest 모드로 관리하는 파일입니다. 이 파일 하나만 있으면 새 컴퓨터에서 프로젝트를 클론했을 때 vcpkg가 필요한 라이브러리를 자동으로 맞춰 설치해 주므로, "내 컴퓨터에서는 되는데 다른 사람 컴퓨터에서는 안 된다"는 문제를 크게 줄여줍니다.

### `.clang-format`과 `.clang-tidy` — 15장

코드 스타일을 자동으로 통일해 주는 clang-format 설정과, 잠재적인 버그 패턴을 잡아주는 clang-tidy 설정입니다. 이 파일들을 프로젝트 루트에 커밋해 두면, 팀원이 각자 다른 에디터 설정을 쓰더라도 저장할 때마다 동일한 스타일로 코드가 정리됩니다.

### `.vscode/` — 3, 4, 5, 9장

`settings.json`, `launch.json` 같은 VS Code 프로젝트별 설정을 담습니다. 이 디렉터리를 저장소에 커밋해서 팀 전체가 공유할지, 아니면 각자의 로컬 설정으로만 둘지는 팀마다 선택이 갈리는 지점입니다. 공유하기로 했다면 `extensions.json`에 이 프로젝트에 필요한 확장 목록(C/C++ 확장, CMake Tools 등)을 `recommendations`로 적어두면, 새로 합류한 팀원이 프로젝트를 열었을 때 VS Code가 필요한 확장을 자동으로 추천해 줍니다.

```json
{
  "recommendations": [
    "ms-vscode.cpptools",
    "ms-vscode.cmake-tools",
    "llvm-vs-code-extensions.vscode-clangd"
  ]
}
```

## `.gitignore`에 빌드 산출물을 넣어야 하는 이유

프로젝트를 Git 저장소로 관리한다면 `.gitignore`에 최소한 다음 두 항목은 반드시 포함해야 합니다.

```
build/
vcpkg_installed/
```

`build/` 디렉터리에는 CMake가 생성한 캐시 파일, Ninja가 만든 중간 산출물, 컴파일된 오브젝트 파일과 실행 파일이 들어 있습니다. 이 파일들을 저장소에 커밋하면 몇 가지 문제가 생깁니다.

첫째, 빌드 산출물은 컴퓨터마다, 운영체제마다, 심지어 같은 컴퓨터라도 컴파일러 버전이 바뀔 때마다 달라지는 파일입니다. 커밋해 둔 산출물이 다른 사람의 환경에서는 아무 의미가 없을뿐더러, 사람이 작성한 코드가 아니라 기계가 매번 새로 생성하는 파일이기 때문에 버전 관리 시스템이 추적할 가치가 없습니다. 둘째, 이런 산출물은 소스 코드에 비해 용량이 훨씬 크고 자주 바뀌기 때문에, 저장소 크기를 빠르게 불리고 `git diff`나 `git log`를 사실상 못 쓰게 만듭니다. 셋째, 팀원이 각자 다른 시점에 커밋한 빌드 산출물이 저장소에 섞이면, 소스 코드는 최신인데 실행 파일은 옛날 버전이 함께 들어있는 것처럼 보이는 혼란을 유발할 수 있습니다.

`vcpkg_installed/` 역시 마찬가지입니다. 이 디렉터리는 `vcpkg.json`에 적힌 목록을 바탕으로 vcpkg가 자동으로 내려받아 만들어내는 결과물입니다. 원본이 되는 `vcpkg.json`만 저장소에 있으면 언제든 다시 만들어낼 수 있는 파생 산출물이므로, 굳이 저장소에 포함시킬 이유가 없습니다. 오히려 라이브러리마다 수십 메가바이트가 넘는 컴파일된 결과물이 통째로 커밋되면 저장소 용량 문제가 훨씬 심각해집니다.

정리하면 `.gitignore`에 넣어야 할 대상을 가르는 기준은 "이 파일이 다른 파일(소스 코드, 설정 파일)로부터 기계적으로 다시 만들어질 수 있는가"입니다. 다시 만들어질 수 있다면 커밋하지 않고, 다시 만들어낼 수 없는 원본(소스 코드, `CMakeLists.txt`, `vcpkg.json`, 설정 파일)만 커밋 대상으로 남깁니다.

## 새 프로젝트를 시작할 때의 체크리스트

새 C++ 프로젝트를 시작할 때마다 아래 순서를 그대로 따라가면, 이 책에서 다룬 도구들이 처음부터 빠짐없이 자리를 잡습니다.

1. **`vcpkg.json` 작성** — 프로젝트 이름과 버전을 적고, 처음에는 의존성 없이 빈 배열로 시작해도 괜찮습니다. 필요한 라이브러리가 생길 때마다 이 파일에 하나씩 추가합니다.
2. **`CMakeLists.txt` 뼈대 작성** — `cmake_minimum_required`, `project`, C++ 표준(13장 참고) 지정부터 시작해서, 라이브러리 타깃과 실행 파일 타깃을 분리해 둡니다.
3. **`CMakePresets.json` 작성** — 최소한 디버그 프리셋 하나는 만들어 둡니다. vcpkg의 toolchain file 경로를 여기에 지정해 두면 매번 커맨드라인에 옵션을 반복해서 입력할 필요가 없어집니다.
4. **VS Code 확장 설치 확인** — C/C++ 확장, CMake Tools 확장이 설치되어 있는지 확인하고, 팀 프로젝트라면 `.vscode/extensions.json`에 추천 목록을 적어둡니다.
5. **`.clang-format`, `.clang-tidy` 작성** — 아예 새로 규칙을 고민하기보다는, 이전 프로젝트에서 검증된 설정을 복사해 오는 것이 현실적입니다.
6. **`tests/` 디렉터리와 테스트 프레임워크 연결** — `vcpkg.json`에 `catch2`를 추가하고, 최소한 하나의 `TEST_CASE`가 통과하는 것까지 확인한 뒤 본격적인 기능 개발을 시작합니다. 프로젝트 초반에 테스트 인프라를 갖춰 두면 이후로는 새 기능마다 테스트를 추가하는 일이 훨씬 자연스러워집니다.
7. **`.gitignore` 작성** — `build/`, `vcpkg_installed/`를 포함해 도구들이 생성하는 산출물 경로를 등록합니다.
8. **첫 빌드와 첫 커밋** — `cmake --preset`, `cmake --build --preset`으로 빈 프로젝트가 정상적으로 빌드되는 것을 확인한 뒤, 지금까지 만든 뼈대 파일들을 첫 커밋으로 남깁니다.

이 순서를 지키는 이유는 "코드를 작성하기 전에 코드를 검증하고 관리할 인프라부터 갖춘다"는 원칙 때문입니다. 기능을 절반쯤 만들고 나서 뒤늦게 테스트 프레임워크나 CMakePresets를 끼워 넣으려 하면, 이미 쌓인 코드를 구조에 맞게 다시 정리하는 비용이 추가로 들게 됩니다.

## 18개 장을 돌아보며

이 책은 하나의 질문에서 시작했습니다. "C++ 코드 한 줄을 실행 가능한 프로그램으로 만들기까지 왜 이렇게 많은 도구가 필요한가?" 그 답을 찾아가는 과정에서 우리는 다섯 가지 도구를 한 켜씩 쌓아 올렸습니다.

**GCC**(2장)는 소스 코드를 기계어로 바꾸는 가장 근본적인 도구였습니다. 커맨드라인에서 `g++`를 직접 호출해 보는 것으로 시작한 이유는, 이후에 배울 모든 도구가 결국 이 GCC 호출을 "대신 해주는" 역할일 뿐이라는 점을 먼저 체감하기 위해서였습니다.

**VS Code**(3~5장)는 GCC를 비롯한 나머지 도구들을 터미널 명령 대신 버튼과 단축키로 다룰 수 있게 해주는 조종석이었습니다. C/C++ 확장을 설치하고, 빌드와 디버깅을 설정하고, IntelliSense가 프로젝트의 include 경로와 컴파일 옵션을 정확히 인식하도록 맞추는 과정을 다뤘습니다.

**CMake**(6, 7장)는 여러 소스 파일로 이루어진 프로젝트의 빌드 규칙을 선언적으로 관리하는 방법을 알려주었습니다. 프로젝트가 커지면서 소스를 여러 타깃으로 나누고, 라이브러리와 실행 파일의 의존 관계를 명확히 하는 구조화 방법도 함께 다뤘습니다.

**Ninja**(8, 9장)는 CMake가 만든 설계도를 받아 실제로 컴파일러를 호출하는 실행기였고, VS Code의 CMake Tools 확장을 통해 이 둘을 에디터 안에서 자동으로 다루는 방법도 배웠습니다.

**vcpkg**(10~12장)는 C++에 공식 패키지 관리자가 없다는 오랜 약점을 보완해 주는 도구였습니다. 개별 라이브러리 설치부터 manifest 모드를 통한 프로젝트별 의존성 관리까지, 외부 코드를 가져다 쓰는 표준적인 방법을 정리했습니다.

이후의 장들은 이 다섯 도구를 뼈대로 실전에 필요한 디테일을 채워 넣는 과정이었습니다. **13장**에서는 컴파일러 표준과 플래그를 통해 어떤 언어 버전과 경고 수준으로 코드를 컴파일할지 결정하는 법을, **14장**에서는 GDB를 통한 심화 디버깅을, **15장**에서는 clang-format과 clang-tidy로 코드 스타일과 잠재적 버그를 자동으로 관리하는 법을, **16장**에서는 CMake Presets로 여러 플랫폼에서 동일한 빌드를 재현하는 법을, **17장**에서는 Catch2와 CTest로 테스트를 자동화하는 법을 다뤘습니다. 그리고 이번 18장에서는 이 모든 요소를 하나의 프로젝트 구조로 모으는 것으로 마무리했습니다.

돌이켜 보면 이 책 전체를 관통하는 하나의 태도가 있습니다. 바로 **"각 도구가 정확히 어떤 문제를 해결하기 위해 존재하는지"를 먼저 이해하고, 그다음에 그 도구를 자동화하는 상위 도구를 얹는 순서**입니다. GCC를 직접 호출해 본 뒤에 CMake를 배웠고, CMake와 Ninja를 손으로 조합해 본 뒤에 CMake Tools 확장을 배웠습니다. 이 순서를 따랐기 때문에, 앞으로 VS Code나 CMake Tools 확장이 어떤 이유로든 기대와 다르게 동작할 때도 "결국 이 확장이 어떤 명령을 대신 실행해 주고 있는가"를 스스로 추론해서 문제를 좁혀나갈 수 있는 감각을 갖추게 되었을 것입니다.

## 더 공부할 방향

이 책은 개인 개발 환경을 완결성 있게 구축하는 데 초점을 맞췄지만, 실무에서 C++ 프로젝트를 운영하다 보면 자연스럽게 마주치게 될 몇 가지 다음 단계를 짧게 소개하며 마무리하겠습니다.

**GitHub Actions를 통한 CI 자동화**는 이 책에서 손으로 실행했던 빌드와 테스트 과정을, 코드를 저장소에 push할 때마다 서버에서 자동으로 실행하도록 만드는 방법입니다. 16장에서 다룬 CMake Presets는 CI 환경에서도 동일한 이름의 프리셋을 그대로 재사용할 수 있어서, 로컬에서 검증한 빌드 설정을 CI 파이프라인으로 옮기는 작업이 한결 수월해집니다.

**Conan**은 vcpkg와 마찬가지로 C++ 패키지 관리 문제를 해결하는 또 다른 도구입니다. vcpkg가 CMake와 특히 밀접하게 통합되어 있다면, Conan은 여러 빌드 시스템을 유연하게 지원하는 것을 강점으로 내세우는 등 접근 방식에 차이가 있습니다. 두 도구 모두 활발히 유지되고 있으므로, 회사나 프로젝트에 따라 어느 쪽이 채택되어 있는지 확인하고 필요에 맞게 익혀두면 좋습니다.

**크로스 컴파일**은 지금 작업 중인 컴퓨터와는 다른 아키텍처(예를 들어 x86 컴퓨터에서 ARM 기반 임베디드 기기용 실행 파일을 만드는 것)를 대상으로 빌드하는 기법입니다. CMake의 toolchain file 메커니즘은 이 책에서 vcpkg 연동에 사용했던 것과 같은 개념이지만, 크로스 컴파일에서는 대상 아키텍처용 컴파일러와 라이브러리 경로를 지정하는 데 활용됩니다.

이 세 가지는 이름과 개략적인 역할만 소개했을 뿐, 본격적으로 다루려면 각각 별도의 학습이 필요한 주제입니다. 지금까지 이 책에서 쌓아 올린 GCC, VS Code, CMake, Ninja, vcpkg에 대한 이해가 있다면, 이런 다음 단계로 넘어갈 때도 "이 새 도구가 기존의 어느 도구와 어떻게 맞물리는가"를 스스로 파악하며 학습 속도를 크게 낼 수 있을 것입니다.

## 요약

- 실전 C++ 프로젝트는 `src/`, `include/`, `tests/`로 코드를 분리하고, `CMakeLists.txt`, `CMakePresets.json`, `vcpkg.json`, `.clang-format`, `.clang-tidy`, `.vscode/`를 프로젝트 루트에 갖춘 구조로 시작하는 것이 이 책에서 다룬 도구들을 모두 활용하는 표준적인 방식입니다.
- `.gitignore`에는 `build/`, `vcpkg_installed/`처럼 다른 파일로부터 기계적으로 다시 만들어질 수 있는 산출물을 등록해서, 버전 관리 대상은 원본 소스와 설정 파일로 한정합니다.
- 새 프로젝트는 `vcpkg.json` 작성부터 `CMakeLists.txt` 뼈대, `CMakePresets.json`, VS Code 확장 확인, 코드 스타일 도구, 테스트 인프라, `.gitignore` 순으로 준비한 뒤 코드를 작성하는 것이 이후 비용을 줄이는 순서입니다.
- 이 책은 GCC, VS Code, CMake, Ninja, vcpkg 다섯 도구를 한 켜씩 쌓아 올리고, 그 위에 컴파일러 플래그, 디버깅, 정적 분석과 포맷팅, 멀티플랫폼 빌드, 테스트 자동화를 더해 하나의 완결된 개발 파이프라인을 구성했습니다.
- 앞으로 더 공부할 만한 방향으로 GitHub Actions를 통한 CI 자동화, vcpkg의 대안인 Conan, 그리고 크로스 컴파일이 있습니다.

## 연습문제

1. 이 장에서 제안한 표준 프로젝트 구조를 실제로 빈 디렉터리에 만들어 보고, 각 파일이 비어 있는 상태에서도 `cmake --preset`이 에러 없이 구성 단계를 통과하는지 확인해 보세요.
2. `.gitignore`에 `build/`를 넣지 않은 상태로 한 번 커밋해 보고, 이후 `.gitignore`에 추가해도 이미 추적 중인 파일은 계속 추적된다는 점을 `git status`로 확인해 보세요. (이미 추적 중인 파일을 제외하려면 `git rm -r --cached build`가 필요하다는 점도 함께 조사해 보세요.)
3. 이 책의 체크리스트 순서 중 하나를 의도적으로 건너뛰고(예를 들어 `.clang-format` 없이) 프로젝트를 진행하면 실제로 어떤 불편함이 생기는지 스스로 경험해 보세요.
4. 1장에서 소개한 다섯 가지 도구 각각에 대해, 그 도구가 없다면 지금 여러분이 만든 프로젝트를 빌드하고 테스트하기 위해 무엇을 손으로 해야 할지 한 문단씩 정리해 보세요.
5. GitHub Actions, Conan, 크로스 컴파일 중 하나를 골라 관련 공식 문서를 검색해 보고, 이 책에서 배운 어떤 개념(toolchain file, CMake Presets, manifest 모드 등)이 그 주제에서도 그대로 등장하는지 찾아보세요.

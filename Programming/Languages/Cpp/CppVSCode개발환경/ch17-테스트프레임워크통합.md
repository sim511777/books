## 왜 "직접 실행해서 눈으로 확인하기"로는 부족한가

지금까지 이 책에서는 프로그램이 제대로 동작하는지 확인하는 방법이 사실상 하나뿐이었습니다. 빌드하고, 실행하고, 콘솔에 찍힌 결과를 눈으로 보고 "맞는 것 같다"고 판단하는 방식입니다. 함수가 하나둘일 때는 이 방식으로도 충분합니다. 하지만 프로젝트가 커지고 함수와 클래스가 수십, 수백 개로 늘어나면 이 방식은 두 가지 지점에서 무너집니다.

첫째, 새 기능을 추가하다가 기존에 잘 동작하던 다른 함수를 실수로 망가뜨렸는지를 매번 손으로 다시 확인할 수 없습니다. 어제까지 잘 되던 계산 함수가 오늘 수정한 다른 코드 때문에 틀린 값을 돌려주기 시작해도, 화면에 그 함수의 결과를 다시 찍어보지 않는 이상 알아챌 방법이 없습니다. 둘째, "눈으로 보고 맞는지 판단"하는 방식은 사람이 매번 반복해야 하는 수작업이라 프로젝트가 커질수록 점점 하지 않게 됩니다. 확인 자체가 귀찮아지면 결국 확인을 건너뛰고 넘어가는 습관이 생깁니다.

**단위 테스트(unit test)**는 이 문제를 코드로 해결합니다. "이 함수에 이 값을 넣으면 이 결과가 나와야 한다"는 기대를 프로그램으로 작성해 두고, 코드를 수정할 때마다 그 기대가 여전히 맞는지를 사람이 아니라 컴퓨터가 몇 초 안에 검사하게 만드는 것입니다. 한 번 작성해 둔 테스트는 그 이후로 몇 번이고 공짜로 재사용됩니다. 이번 장에서는 C++ 생태계에서 널리 쓰이는 두 가지 테스트 프레임워크인 Catch2와 GoogleTest를 소개하고, vcpkg로 설치한 뒤 CMake와 CTest로 통합해서 VS Code 안에서 직접 실행하고 결과를 확인하는 방법을 실습합니다.

## Catch2와 GoogleTest, 무엇이 다른가

C++ 테스트 프레임워크는 여러 종류가 있지만 실무에서 가장 널리 쓰이는 것은 Catch2와 GoogleTest 두 가지입니다. 둘 다 좋은 도구이며 우열을 가리기보다는 성격이 다르다고 보는 편이 정확합니다.

**Catch2**는 문법이 매우 간결한 것이 특징입니다. `TEST_CASE`라는 매크로 하나로 테스트를 정의하고, `REQUIRE`라는 매크로로 조건을 검사합니다. 별도의 `main` 함수를 직접 작성할 필요도 없이(Catch2가 제공하는 라이브러리가 대신 처리해 줍니다) 몇 줄만으로 테스트를 시작할 수 있어서, 개인 프로젝트나 중소규모 프로젝트에서 빠르게 테스트를 도입하고 싶을 때 특히 적합합니다.

**GoogleTest**는 구글이 만들고 유지하는 프레임워크로, `TEST`와 `TEST_F`(픽스처를 사용하는 테스트) 매크로, `EXPECT_EQ`나 `ASSERT_EQ` 같은 비교 매크로로 구성됩니다. Catch2보다 설정이 조금 더 필요하지만, 목(mock) 객체를 만들어주는 GoogleMock이 함께 제공되고, 대규모 팀에서 오랫동안 검증된 관례가 많이 쌓여 있어 큰 프로젝트에서 특히 널리 채택됩니다.

이번 장의 실습은 문법이 더 간결하고 도입 장벽이 낮은 **Catch2**를 기준으로 진행하되, GoogleTest로 같은 예제를 작성하면 어떤 모습이 되는지도 함께 비교해 보겠습니다. 둘 중 하나만 골라 쓰는 것이 일반적이며, 한 프로젝트에 두 프레임워크를 동시에 섞어 쓰는 경우는 거의 없습니다.

## vcpkg로 Catch2 설치하기

10~12장에서 다룬 vcpkg를 그대로 사용합니다. manifest 모드로 관리 중인 프로젝트라면 `vcpkg.json`에 의존성을 추가하는 방식이 가장 자연스럽습니다.

```json
{
  "name": "calc-demo",
  "version": "0.1.0",
  "dependencies": [
    "catch2"
  ]
}
```

`vcpkg.json`에 추가한 뒤 CMake를 구성하면 vcpkg가 자동으로 Catch2를 내려받아 설치합니다. classic 모드를 쓰고 있다면 다음처럼 직접 설치 명령을 실행해도 됩니다.

```bash
vcpkg install catch2
```

GoogleTest를 쓰고 싶다면 패키지 이름만 `gtest`로 바꾸면 됩니다.

```bash
vcpkg install gtest
```

## 프로젝트 구조 준비하기

테스트 대상이 될 아주 단순한 함수 하나로 시작하겠습니다. 두 정수를 더하는 함수입니다. 실전에서는 물론 훨씬 복잡한 로직을 테스트하게 되지만, 프레임워크를 처음 통합할 때는 결과를 눈으로 바로 검증할 수 있는 단순한 예제로 시작하는 편이 CMake 설정 문제와 로직 문제를 구분하기 쉽습니다.

```
calc-demo/
├── CMakeLists.txt
├── vcpkg.json
├── include/
│   └── calc.h
├── src/
│   ├── calc.cpp
│   └── main.cpp
└── tests/
    ├── CMakeLists.txt
    └── test_calc.cpp
```

`include/calc.h`에는 함수 선언만 둡니다.

```cpp
#pragma once

int add(int a, int b);
```

`src/calc.cpp`에 실제 구현을 작성합니다.

```cpp
#include "calc.h"

int add(int a, int b) {
    return a + b;
}
```

`src/main.cpp`는 이 함수를 사용하는 실제 프로그램입니다.

```cpp
#include <iostream>
#include "calc.h"

int main() {
    std::cout << "3 + 4 = " << add(3, 4) << '\n';
    return 0;
}
```

## CMake와 Catch2 통합하기

최상위 `CMakeLists.txt`에서는 라이브러리 형태로 계산 로직을 분리하고, 실행 파일과 테스트가 이 라이브러리를 공유하도록 구성합니다. 이렇게 로직을 별도 타깃으로 분리해 두면 테스트 코드가 `main` 함수와 충돌할 일이 없어집니다.

```cmake
cmake_minimum_required(VERSION 3.21)
project(calc_demo CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(calc_lib src/calc.cpp)
target_include_directories(calc_lib PUBLIC include)

add_executable(calc_demo src/main.cpp)
target_link_libraries(calc_demo PRIVATE calc_lib)

enable_testing()
add_subdirectory(tests)
```

`enable_testing()`은 이 프로젝트에서 CTest를 사용하겠다고 CMake에 선언하는 명령입니다. 이 줄이 없으면 아래에서 등록할 `add_test()`가 무시됩니다. 반드시 최상위 `CMakeLists.txt`에서 호출해야 하며, 하위 디렉터리의 `CMakeLists.txt`에서 호출하면 제대로 인식되지 않을 수 있습니다.

`tests/CMakeLists.txt`에서 Catch2를 찾고, 테스트 실행 파일을 만들고, 그 실행 파일을 CTest에 등록합니다.

```cmake
find_package(Catch2 3 CONFIG REQUIRED)

add_executable(unit_tests test_calc.cpp)
target_link_libraries(unit_tests PRIVATE calc_lib Catch2::Catch2WithMain)

include(CTest)
include(Catch)
catch_discover_tests(unit_tests)
```

몇 가지 짚어볼 부분이 있습니다. `find_package(Catch2 3 CONFIG REQUIRED)`는 vcpkg가 설치해 둔 Catch2 3.x 버전의 CMake 설정 파일을 찾으라는 뜻입니다. `CONFIG` 키워드는 시스템 표준 경로가 아니라 패키지가 제공하는 `.cmake` 설정 파일을 사용하라는 지시이고, `REQUIRED`는 찾지 못하면 CMake 구성 단계에서 바로 에러를 내라는 뜻입니다. vcpkg를 toolchain file로 지정해 두었다면(9장, 10장 참고) 이 `find_package` 호출은 별다른 경로 지정 없이도 성공합니다.

`Catch2::Catch2WithMain`을 링크하면 Catch2가 제공하는 기본 `main` 함수가 자동으로 포함되므로, 테스트 파일에 별도의 `main` 함수를 작성할 필요가 없습니다. 마지막으로 `catch_discover_tests(unit_tests)`는 Catch2가 제공하는 CMake 헬퍼 함수로, `unit_tests` 실행 파일 안에 정의된 `TEST_CASE` 각각을 CTest가 개별 테스트로 인식하도록 자동 등록해 줍니다. 이 헬퍼를 쓰지 않고 `add_test(NAME unit_tests COMMAND unit_tests)`처럼 직접 등록할 수도 있지만, 그 경우 CTest는 테스트 파일 전체를 하나의 테스트로만 인식하기 때문에 어떤 `TEST_CASE`가 실패했는지 CTest 결과만으로는 구분하기 어렵습니다. 여러 개의 개별 테스트로 세밀하게 확인하고 싶다면 `catch_discover_tests`를 쓰는 편이 유리합니다.

## 테스트 코드 작성하기

`tests/test_calc.cpp`에서 실제 테스트를 작성합니다.

```cpp
#include <catch2/catch_test_macros.hpp>
#include "calc.h"

TEST_CASE("두 양수를 더하면 합이 반환된다", "[calc]") {
    REQUIRE(add(2, 3) == 5);
}

TEST_CASE("음수를 더해도 정상적으로 계산된다", "[calc]") {
    REQUIRE(add(-1, -1) == -2);
    REQUIRE(add(-5, 5) == 0);
}

TEST_CASE("0을 더하면 값이 변하지 않는다", "[calc]") {
    REQUIRE(add(7, 0) == 7);
}
```

`TEST_CASE`의 첫 번째 인자는 사람이 읽을 테스트 설명이고, 두 번째 인자인 대괄호 문자열은 태그입니다. 태그를 붙여 두면 나중에 `--tag [calc]`처럼 태그 단위로 원하는 테스트만 골라 실행할 수 있습니다. `REQUIRE`는 조건이 거짓이면 그 자리에서 테스트를 실패시키고 무엇이 왜 틀렸는지(실제 값과 기대 값)를 자동으로 출력해 줍니다. 같은 `TEST_CASE` 안에 `REQUIRE`를 여러 번 써서 하나의 시나리오 안에서 여러 조건을 검사할 수도 있습니다.

같은 테스트를 GoogleTest로 작성하면 다음과 같은 모습이 됩니다. 참고로만 살펴보고, 이 책의 실습은 계속 Catch2를 기준으로 진행합니다.

```cpp
#include <gtest/gtest.h>
#include "calc.h"

TEST(CalcTest, AddsTwoPositiveNumbers) {
    EXPECT_EQ(add(2, 3), 5);
}

TEST(CalcTest, HandlesNegativeNumbers) {
    EXPECT_EQ(add(-1, -1), -2);
    EXPECT_EQ(add(-5, 5), 0);
}
```

GoogleTest는 `TEST(그룹이름, 테스트이름)` 형태로 테스트를 묶고, `EXPECT_EQ`는 실패해도 같은 테스트 안의 나머지 검사를 계속 진행하는 반면 `ASSERT_EQ`는 실패 즉시 그 테스트를 중단시킨다는 차이가 있습니다. CMake 쪽에서는 `find_package(GTest CONFIG REQUIRED)`로 찾고 `GTest::gtest_main`을 링크하면 되며, 테스트 등록에는 GoogleTest가 제공하는 `gtest_discover_tests()` 헬퍼를 사용합니다.

## 빌드하고 CTest로 실행하기

이제 8장과 9장에서 익힌 방식대로 구성하고 빌드합니다.

```bash
cmake --preset default
cmake --build --preset default
```

빌드가 끝나면 빌드 디렉터리 안에서 `ctest` 명령으로 등록된 모든 테스트를 실행할 수 있습니다.

```bash
ctest --test-dir build
```

정상적으로 통과하면 다음과 비슷한 출력을 볼 수 있습니다.

```bash
Test project D:/calc-demo/build
    Start 1: 두 양수를 더하면 합이 반환된다
1/3 Test #1: 두 양수를 더하면 합이 반환된다 ......   Passed    0.01 sec
    Start 2: 음수를 더해도 정상적으로 계산된다
2/3 Test #2: 음수를 더해도 정상적으로 계산된다 ....   Passed    0.01 sec
    Start 3: 0을 더하면 값이 변하지 않는다 ..........   Passed    0.01 sec

100% tests passed, 0 tests failed out of 3
```

`ctest` 명령에는 자주 쓰는 유용한 옵션이 몇 가지 있습니다. `-V`(또는 `--verbose`)는 각 테스트의 상세 출력을 함께 보여주고, `--output-on-failure`는 평소에는 조용히 진행하다가 실패한 테스트가 있을 때만 그 상세 출력을 보여줍니다. 테스트가 많아질수록 `--output-on-failure`를 습관적으로 붙이는 것이 유용합니다.

```bash
ctest --test-dir build --output-on-failure
```

일부러 테스트를 실패시켜 보는 것도 좋은 연습입니다. `REQUIRE(add(2, 3) == 6)`처럼 기대값을 틀리게 바꿔서 다시 실행하면, CTest가 어떤 테스트가 실패했는지와 함께 Catch2가 출력하는 "기대한 값"과 "실제 값"을 나란히 보여주는 것을 확인할 수 있습니다.

## VS Code 테스트 탐색기로 실행하기

9장에서 설치한 CMake Tools 확장은 CTest와 자동으로 연동되는 **테스트 탐색기(Test Explorer)** 기능을 제공합니다. 커맨드라인에서 `ctest`를 매번 입력하는 대신, VS Code 왼쪽 액티비티 바의 테스트 아이콘(플라스크 모양)을 클릭하면 프로젝트에 등록된 모든 테스트가 트리 형태로 나타납니다.

CMake Tools가 프로젝트를 구성(configure)할 때 CTest에 등록된 테스트 목록을 함께 읽어 오기 때문에, 앞서 `catch_discover_tests`로 등록한 세 개의 테스트가 각각 개별 항목으로 표시됩니다. 테스트 탐색기에서는 다음과 같은 조작이 가능합니다.

- 트리 상단의 재생 버튼을 누르면 전체 테스트를 한 번에 실행합니다.
- 개별 테스트 항목 옆의 재생 버튼을 누르면 그 테스트 하나만 실행합니다.
- 실패한 테스트는 빨간색 아이콘으로 표시되며, 클릭하면 실패 메시지(기대값과 실제값)를 바로 확인할 수 있습니다.
- 통과한 테스트는 초록색 체크 표시로 바뀝니다.

이 UI의 가장 큰 장점은 커맨드라인 출력을 눈으로 스캔하며 어떤 테스트가 실패했는지 찾을 필요 없이, 실패한 항목이 트리에서 바로 시각적으로 구분된다는 점입니다. 코드를 수정한 뒤 저장하고 재빌드한 다음 테스트 탐색기의 재생 버튼만 누르는 흐름에 익숙해지면, 4장에서 다룬 디버깅 워크플로처럼 테스트 실행도 VS Code를 벗어나지 않고 처리할 수 있게 됩니다. 참고로 실패한 테스트를 디버거로 바로 실행해서 중단점을 걸고 원인을 추적하는 기능도 테스트 탐색기에서 함께 제공되므로, 4장과 14장에서 익힌 디버깅 지식을 테스트 실패 원인 분석에도 그대로 활용할 수 있습니다.

## 테스트를 어디에, 언제 추가할 것인가

실전에서 테스트를 도입할 때 자주 나오는 질문은 "모든 함수를 다 테스트해야 하는가"입니다. 정답은 없지만, 실용적인 기준으로는 다음과 같은 코드에 우선순위를 두는 것이 좋습니다.

- 입력에 따라 분기가 여러 갈래로 나뉘는 로직(경계값, 예외 상황을 놓치기 쉬운 코드)
- 한 번 버그가 발생했다가 고친 코드(재발을 막기 위한 회귀 테스트)
- 여러 곳에서 재사용되어 잘못되면 파급 효과가 큰 공용 함수나 클래스

반대로 단순히 입력을 그대로 화면에 출력하는 코드나, 외부 라이브러리를 얇게 감싸기만 하는 코드까지 전부 테스트로 덮으려 하면 테스트를 작성하는 데 드는 노력이 얻는 이득보다 커질 수 있습니다. 이 책의 예제처럼 계산 로직을 `main` 함수와 분리된 라이브러리 타깃으로 구성해 두면, 어떤 부분을 테스트 대상으로 삼을지 자연스럽게 구분되는 효과도 있습니다.

## 요약

- 단위 테스트는 코드 변경이 기존 동작을 깨뜨리지 않았는지를 사람이 아니라 컴퓨터가 반복적으로 검사하게 해주는 도구입니다.
- Catch2는 `TEST_CASE`/`REQUIRE` 매크로로 간결하게 테스트를 작성할 수 있는 프레임워크이고, GoogleTest는 `TEST`/`EXPECT_EQ` 매크로를 사용하며 대규모 프로젝트에서 널리 쓰입니다.
- vcpkg의 `vcpkg.json`에 `catch2`(또는 `gtest`)를 의존성으로 추가하면 CMake가 곧바로 사용할 수 있는 형태로 라이브러리가 준비됩니다.
- `enable_testing()`으로 CTest 사용을 선언하고, `find_package(Catch2 3 CONFIG REQUIRED)`로 라이브러리를 찾은 뒤, `catch_discover_tests()`로 개별 `TEST_CASE`를 CTest 테스트로 자동 등록합니다.
- `ctest --output-on-failure` 명령으로 커맨드라인에서 전체 테스트를 실행할 수 있고, VS Code의 CMake Tools 테스트 탐색기를 사용하면 트리 UI에서 개별 테스트를 실행하고 실패 원인을 바로 확인할 수 있습니다.

## 연습문제

1. `calc.h`에 두 수를 곱하는 `multiply` 함수를 추가하고, 양수·음수·0을 곱하는 경우를 각각 검사하는 `TEST_CASE`를 세 개 작성해 보세요.
2. `add` 함수의 구현을 일부러 틀리게 바꾼 뒤(`return a - b;`처럼) `ctest --output-on-failure`를 실행해서 CTest와 Catch2가 실패 원인을 어떻게 보여주는지 관찰해 보세요.
3. `catch_discover_tests(unit_tests)` 대신 `add_test(NAME unit_tests COMMAND unit_tests)`로 등록을 바꾼 뒤 `ctest`를 실행하고, 개별 `TEST_CASE` 단위로 결과가 보이는지 아니면 실행 파일 전체가 하나의 테스트로 보이는지 비교해 보세요.
4. VS Code 테스트 탐색기에서 테스트 하나만 골라 실행하는 방법과, 실패한 테스트를 디버거로 실행해 중단점까지 도달시키는 방법을 직접 시도해 보세요.
5. 같은 `add` 함수에 대한 테스트를 GoogleTest 문법(`TEST`, `EXPECT_EQ`)으로 다시 작성해 보고, Catch2 버전과 비교했을 때 CMake 설정에서 어떤 부분이 달라지는지 정리해 보세요.

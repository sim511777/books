# 15장. 정적 분석과 코드 포맷팅

[◀ 이전: 14장. 디버깅 심화(GDB)](ch14-디버깅심화GDB.md) | [📖 목차](00-목차.md) | [다음: 16장. 멀티플랫폼 빌드와 CMake Presets ▶](ch16-멀티플랫폼빌드와CMakePresets.md)


13장에서는 컴파일러가 코드를 어떤 표준으로 해석하고 어떤 경고를 띄우는지 다뤘고, 14장에서는 GDB로 이미 발생한 버그를 추적하는 방법을 살펴봤습니다. 이번 장에서는 시선을 조금 앞당겨, 버그가 실제로 터지기 전에 잠재적인 문제를 미리 찾아내는 **정적 분석**과, 여러 사람이 함께 작성한 코드를 하나의 스타일로 맞춰주는 **코드 포맷팅**을 다룹니다. 두 도구 모두 LLVM 프로젝트에서 나온 `clang-tidy`와 `clang-format`이며, 실제로 컴파일을 하지 않고도(혹은 컴파일 정보를 참고해서) 소스 코드 자체를 분석하고 다듬어 준다는 공통점이 있습니다.

## 정적 분석이 하는 일: 컴파일러 경고와는 무엇이 다른가

GCC도 `-Wall -Wextra` 같은 옵션을 주면 상당히 많은 문제를 경고로 잡아줍니다. 그런데 컴파일러의 경고는 근본적으로 "이 코드를 기계어로 번역할 수 있는가"라는 질문에서 파생된 부산물입니다. 컴파일러 입장에서 코드가 문법적으로 유효하고 타입도 맞는다면, 설령 그 코드가 나쁜 습관이나 잠재적 버그를 담고 있어도 굳이 알려줄 의무는 없습니다.

정적 분석 도구는 이와 다른 목적으로 만들어졌습니다. 코드를 실행하거나 완전히 컴파일하지 않고도 소스 코드의 구조(추상 구문 트리)를 분석해서, 문법적으로는 완벽히 유효하지만 실제로는 버그이거나 나쁜 패턴일 가능성이 높은 코드를 찾아냅니다. 예를 들면 다음과 같은 것들입니다.

- 지역 변수를 초기화하지 않고 사용하는 경우
- `new`로 할당한 메모리를 `delete`하지 않아 누수가 발생할 가능성이 있는 경우
- 값을 복사해도 되는데 불필요하게 큰 객체를 복사하는 비효율적인 코드
- C 스타일 캐스트를 사용해 타입 안전성을 우회하는 경우
- C++11 이후에 나온 더 안전하고 간결한 문법으로 바꿀 수 있는 오래된 코드

이런 문제들은 컴파일 자체에는 아무 지장이 없기 때문에 GCC나 Clang의 기본 경고만으로는 잡히지 않는 경우가 많습니다. 정적 분석 도구는 바로 이 빈틈을 메워 줍니다.

## clang-tidy 소개

`clang-tidy`는 LLVM/Clang 프로젝트에서 제공하는 정적 분석 도구입니다. Clang 컴파일러와 같은 프런트엔드 파서를 사용하기 때문에 C++ 문법을 실제 컴파일러 수준으로 정확하게 이해하면서도, 컴파일 자체는 수행하지 않고 소스 코드를 분석하는 데 집중합니다.

### 설치 확인하기

MSYS2 환경이라면 `clang-tools` 패키지를, 우분투 계열이라면 `clang-tidy` 패키지를 설치하면 됩니다.

```bash
# MSYS2 (MinGW64 셸)
pacman -S mingw-w64-x86_64-clang-tools-extra

# Ubuntu/Debian
sudo apt install clang-tidy
```

설치 후 버전을 확인해 봅니다.

```bash
clang-tidy --version
```

### 단일 파일 분석해 보기

가장 단순한 사용법은 소스 파일 하나를 직접 넘기는 것입니다.

```bash
clang-tidy main.cpp -- -std=c++20
```

`--` 뒤에 오는 옵션들은 실제 컴파일러에 전달되는 옵션과 동일한 형식입니다. 표준 버전이나 include 경로처럼 코드를 올바르게 파싱하기 위해 필요한 정보를 여기에 넘겨줍니다. 프로젝트가 여러 파일과 include 경로로 이루어져 있다면 이렇게 매번 옵션을 손으로 나열하기가 번거로운데, 이 문제는 뒤에서 `compile_commands.json`으로 해결합니다.

### 검사 항목(check)의 구조

clang-tidy가 수행하는 검사들은 접두사가 붙은 이름으로 그룹화되어 있습니다. 대표적인 그룹은 다음과 같습니다.

- `bugprone-*`: 실제 버그로 이어지기 쉬운 패턴(예: 문자열 비교에 `==` 대신 실수로 대입 연산자를 쓴 경우)
- `modernize-*`: 오래된 C++ 문법을 최신 표준의 기능으로 바꾸도록 제안(예: `typedef`를 `using`으로, 원시 반복문을 범위 기반 `for`로)
- `performance-*`: 불필요한 복사나 비효율적인 연산을 지적
- `readability-*`: 가독성을 해치는 코드 스타일 지적
- `cppcoreguidelines-*`: C++ Core Guidelines 문서가 권장하는 규칙을 기준으로 한 검사

기본적으로 clang-tidy는 이 중 일부만 활성화한 채로 실행됩니다. 어떤 그룹을 켜고 끌지는 `-checks` 커맨드라인 옵션으로 지정할 수도 있지만, 프로젝트 차원에서 규칙을 고정하려면 설정 파일을 쓰는 편이 훨씬 관리하기 쉽습니다.

### .clang-tidy 설정 파일

프로젝트 루트에 `.clang-tidy`라는 이름의 YAML 파일을 두면, clang-tidy가 그 디렉터리 이하에서 실행될 때 자동으로 이 설정을 읽어 들입니다.

```yaml
Checks: >
  -*,
  bugprone-*,
  modernize-*,
  performance-*,
  readability-*,
  -modernize-use-trailing-return-type

WarningsAsErrors: 'bugprone-*'
HeaderFilterRegex: '^(include|src)/'

CheckOptions:
  - key: readability-identifier-naming.VariableCase
    value: camelBack
  - key: readability-identifier-naming.ClassCase
    value: CamelCase
```

각 항목의 의미는 다음과 같습니다.

- `Checks`: 활성화할 검사 목록입니다. 맨 앞의 `-*`는 "일단 모든 검사를 끈다"는 뜻이고, 그 뒤에 나열된 그룹들을 다시 켭니다. 이름 앞에 `-`가 붙으면 그 항목만 제외한다는 뜻이므로, 예시의 마지막 줄은 `modernize-*` 그룹 중 `modernize-use-trailing-return-type` 하나만 빼겠다는 의미입니다.
- `WarningsAsErrors`: 여기 나열된 검사에서 문제가 발견되면 경고가 아니라 오류로 취급합니다. CI 파이프라인에서 특정 규칙 위반 시 빌드를 실패시키고 싶을 때 유용합니다.
- `HeaderFilterRegex`: 프로젝트 자체의 헤더 파일만 검사 대상에 포함하고, 외부 라이브러리나 표준 라이브러리 헤더는 검사에서 제외하기 위한 정규식입니다.
- `CheckOptions`: 개별 검사의 세부 동작을 조정하는 옵션입니다. 예시는 변수 이름은 `camelBack`(예: `myVariable`), 클래스 이름은 `CamelCase`(예: `MyClass`)를 따르도록 강제하는 설정입니다.

이 파일 하나를 저장소에 커밋해 두면, 팀원 누가 clang-tidy를 실행하든 동일한 기준으로 검사가 이루어집니다.

### 실전 프로젝트에서는 compile_commands.json이 필요하다

앞서 `-- -std=c++20`처럼 옵션을 직접 나열하는 방법을 보여드렸지만, 여러 소스 파일에 서로 다른 include 경로와 매크로가 얽혀 있는 실제 프로젝트에서는 이 방식이 금방 한계에 부딪힙니다. 6장에서 다룬 CMake는 이 문제를 위해 `compile_commands.json`이라는 파일을 생성해 줄 수 있습니다. CMake 설정 시 다음 캐시 변수를 켜면 됩니다.

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

이 옵션을 켜고 빌드 디렉터리를 구성하면, 빌드 디렉터리 안에 `compile_commands.json`이 생성됩니다. 이 파일에는 프로젝트의 각 소스 파일이 실제로 어떤 컴파일러 옵션과 include 경로로 컴파일되는지가 기록되어 있습니다. clang-tidy는 이 파일이 있는 디렉터리를 `-p` 옵션으로 지정하면, 파일마다 옵션을 따로 넘길 필요 없이 정확한 컴파일 정보를 자동으로 읽어 분석합니다.

```bash
clang-tidy -p build src/main.cpp
```

## clang-format 소개

`clang-format`은 같은 LLVM 프로젝트에서 나온 코드 포맷터입니다. clang-tidy가 코드의 "의미"에 관여하는 문제를 찾는다면, clang-format은 오직 들여쓰기, 중괄호 위치, 줄바꿈, 공백처럼 코드의 "생김새"만을 일관되게 정리합니다.

여러 사람이 함께 작업하는 프로젝트에서 각자 선호하는 들여쓰기 방식이나 중괄호 위치가 다르면, 코드 리뷰에서 실제 로직과 무관한 스타일 차이 때문에 diff가 지저분해지고 리뷰에 불필요한 시간이 소모됩니다. clang-format을 도입하면 이런 스타일 차이를 도구가 자동으로 없애 주기 때문에, 코드 리뷰는 오직 로직에만 집중할 수 있게 됩니다.

### .clang-format 설정 파일

`.clang-format` 파일도 프로젝트 루트에 두는 YAML 형식의 설정 파일입니다. 처음부터 모든 항목을 하나하나 정의할 필요는 없고, 잘 알려진 스타일을 기반으로 삼아 필요한 부분만 덮어쓰는 방식이 일반적입니다.

```yaml
BasedOnStyle: Google
IndentWidth: 4
ColumnLimit: 100
BreakBeforeBraces: Attach
AllowShortIfStatementsOnASingleLine: false
PointerAlignment: Left
```

- `BasedOnStyle`: 기준으로 삼을 스타일입니다. `LLVM`, `Google`, `Chromium`, `Mozilla`, `WebKit`, `Microsoft` 등 잘 알려진 스타일 이름을 지정할 수 있습니다. 이 예시는 구글 스타일 가이드를 기반으로 삼았습니다.
- `IndentWidth`: 들여쓰기 폭을 스페이스 몇 칸으로 할지 지정합니다.
- `ColumnLimit`: 한 줄의 최대 길이입니다. 이 길이를 넘는 줄은 자동으로 개행됩니다.
- `BreakBeforeBraces`: 중괄호를 어느 위치에서 줄바꿈할지 지정합니다. `Attach`는 여는 중괄호를 이전 줄 끝에 붙이는 방식(K&R 스타일에 가까움)입니다.
- `PointerAlignment`: 포인터 기호 `*`를 타입 쪽에 붙일지(`Left`, 예: `int* p`) 변수 쪽에 붙일지(`Right`, 예: `int *p`) 지정합니다.

지정하지 않은 나머지 항목은 모두 `BasedOnStyle`에서 지정한 스타일의 기본값을 그대로 따릅니다.

### 커맨드라인에서 실행하기

```bash
# 결과를 화면에 출력만 하고 파일은 바꾸지 않음
clang-format main.cpp

# -i 옵션을 주면 파일을 직접 수정(in-place)
clang-format -i main.cpp

# 여러 파일을 한 번에
clang-format -i src/*.cpp include/*.h
```

`-i` 옵션 없이 실행하면 포맷팅된 결과가 표준 출력으로만 나가고 원본 파일은 그대로 유지됩니다. 실제로 파일을 정리하려면 `-i`를 반드시 붙여야 합니다.

## VS Code에서 두 도구 통합하기

3장에서 설치한 VS Code C/C++ 확장은 clang-tidy와 clang-format을 편집기 안에서 바로 사용할 수 있도록 통합 기능을 제공합니다.

### clang-tidy 통합 설정

`.vscode/settings.json`에 다음 설정을 추가하면, 편집기에서 코드를 작성하는 즉시 clang-tidy 검사 결과가 물결선으로 표시됩니다.

```json
{
    "C_Cpp.codeAnalysis.clangTidy.enabled": true,
    "C_Cpp.codeAnalysis.clangTidy.path": "C:/msys64/mingw64/bin/clang-tidy.exe"
}
```

- `C_Cpp.codeAnalysis.clangTidy.enabled`: clang-tidy 통합 기능을 켤지 여부입니다.
- `C_Cpp.codeAnalysis.clangTidy.path`: 사용할 clang-tidy 실행 파일의 경로입니다. 시스템 PATH에 이미 등록되어 있다면 실행 파일 이름만 적어도 됩니다.

이 설정을 켜면 확장은 프로젝트 루트(혹은 상위 디렉터리)에 있는 `.clang-tidy` 파일을 자동으로 찾아 그 규칙을 적용합니다. 9장에서 CMake Tools 확장을 함께 사용하고 있다면, CMake Tools가 이미 생성해 둔 `compile_commands.json`을 C/C++ 확장이 함께 참고하기 때문에 정확한 include 경로 기반으로 분석이 이루어집니다.

### 저장 시 자동 포맷 설정

포맷팅은 매번 커맨드라인에서 수동으로 실행하는 대신, 파일을 저장하는 순간 자동으로 적용하는 것이 실무에서 훨씬 편리합니다. `settings.json`에 다음을 추가합니다.

```json
{
    "editor.formatOnSave": true,
    "[cpp]": {
        "editor.defaultFormatter": "ms-vscode.cpptools"
    },
    "C_Cpp.clang_format_path": "C:/msys64/mingw64/bin/clang-format.exe",
    "C_Cpp.clang_format_style": "file"
}
```

- `editor.formatOnSave`: 파일을 저장할 때 등록된 포맷터를 자동으로 실행합니다.
- `"[cpp]"` 블록: C++ 파일에 한정해서 기본 포맷터를 C/C++ 확장(`ms-vscode.cpptools`)으로 지정합니다.
- `C_Cpp.clang_format_path`: 확장이 내부적으로 사용할 clang-format 실행 파일 경로입니다.
- `C_Cpp.clang_format_style`: `"file"`로 지정하면 프로젝트 루트의 `.clang-format` 파일을 읽어 그 규칙을 따릅니다. 이 값을 생략하면 확장에 내장된 기본 스타일이 적용되므로, 팀에서 합의한 스타일을 쓰려면 반드시 `"file"`로 지정해야 합니다.

이제 코드를 작성하고 `Ctrl+S`로 저장하기만 하면, 들여쓰기와 중괄호 위치 같은 스타일이 `.clang-format` 규칙에 맞춰 즉시 정리됩니다.

## 왜 팀 전체가 같은 규칙을 써야 하는가

정적 분석 규칙과 포맷 스타일은 개인의 취향에 따라 얼마든지 달라질 수 있는 영역입니다. 하지만 여러 사람이 함께 만드는 프로젝트에서 이 부분이 사람마다 제각각이라면, 코드 리뷰 때마다 스타일 차이로 인한 diff 잡음이 실제 로직 검토를 방해하고, "이 프로젝트에서는 어떤 방식이 맞는가"를 둘러싼 소모적인 논쟁이 반복됩니다.

`.clang-tidy`와 `.clang-format` 파일을 프로젝트 저장소에 커밋해 두면, 이 판단을 사람이 매번 내릴 필요 없이 도구가 대신 내려줍니다. 새로 합류한 팀원도 별도의 스타일 문서를 정독할 필요 없이, 저장소를 내려받고 VS Code에서 저장 버튼만 누르면 자연스럽게 팀의 규칙을 따르게 됩니다. 이것이 두 설정 파일을 프로젝트 루트에 두고 형상 관리에 포함시켜야 하는 이유입니다.

## 요약

- 정적 분석은 코드를 실행하거나 완전히 컴파일하지 않고도 잠재적인 버그나 나쁜 패턴을 찾아내는 기법으로, 컴파일러 경고가 다루지 않는 영역을 보완합니다.
- `clang-tidy`는 Clang 프런트엔드를 기반으로 한 정적 분석 도구이며, `bugprone-*`, `modernize-*`, `performance-*`, `readability-*` 같은 그룹으로 검사 항목이 나뉩니다.
- `.clang-tidy` 파일로 활성화할 검사 항목과 세부 옵션을 프로젝트 단위로 고정할 수 있습니다.
- 실제 프로젝트에서 clang-tidy를 정확하게 실행하려면 CMake의 `CMAKE_EXPORT_COMPILE_COMMANDS` 옵션으로 생성한 `compile_commands.json`을 함께 활용해야 합니다.
- `clang-format`은 코드의 스타일(들여쓰기, 중괄호 위치, 줄 길이 등)만을 자동으로 정리하는 도구이며, `.clang-format` 파일에서 `BasedOnStyle`을 기준으로 세부 항목을 조정합니다.
- VS Code C/C++ 확장의 `C_Cpp.codeAnalysis.clangTidy.enabled` 설정으로 편집기 안에서 실시간 정적 분석을, `editor.formatOnSave`와 `C_Cpp.clang_format_style: "file"` 설정으로 저장 시 자동 포맷을 구성할 수 있습니다.
- 정적 분석 규칙과 포맷 스타일을 프로젝트 저장소에 설정 파일로 커밋해 두면 팀 전체가 동일한 기준을 자동으로 따르게 되어, 코드 리뷰가 스타일이 아닌 로직에 집중할 수 있게 됩니다.

## 연습문제

1. 컴파일러 경고와 정적 분석 도구가 찾아내는 문제의 성격이 어떻게 다른지 예를 들어 설명하세요.
2. `.clang-tidy` 파일에서 `Checks: -*, bugprone-*`처럼 작성했을 때 최종적으로 활성화되는 검사 그룹은 무엇인지 설명하세요.
3. clang-tidy를 실제 CMake 프로젝트에서 정확하게 실행하기 위해 필요한 CMake 캐시 변수의 이름과 그 역할을 서술하세요.
4. `.clang-format`에서 `BasedOnStyle: Google`을 지정한 뒤 `IndentWidth: 2`를 추가로 지정하면 최종 스타일은 어떻게 결정되는지 설명하세요.
5. VS Code에서 저장할 때마다 `.clang-format` 규칙대로 자동 포맷이 적용되도록 하려면 `settings.json`에 어떤 항목들을 추가해야 하는지 나열하세요.

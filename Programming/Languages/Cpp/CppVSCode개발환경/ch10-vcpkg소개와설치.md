# 10장. vcpkg 소개와 설치

[◀ 이전: 9장. VS Code CMake Tools 확장](ch09-VSCodeCMakeTools확장.md) | [📖 목차](00-목차.md) | [다음: 11장. vcpkg로 라이브러리 사용하기 ▶](ch11-vcpkg로라이브러리사용하기.md)


## 이 장에서 할 일

지금까지 만든 프로젝트들은 표준 라이브러리만으로 충분했기 때문에 외부 라이브러리를 가져다 쓰는 문제는 다루지 않았습니다. 하지만 실제 프로젝트에서는 JSON 파싱, 로깅, 네트워킹, 테스트 프레임워크처럼 이미 잘 만들어진 라이브러리를 가져다 쓰는 경우가 훨씬 많습니다. 이 장에서는 C++ 진영에서 이런 외부 라이브러리를 손쉽게 설치하고 관리할 수 있게 해주는 vcpkg를 소개하고, 설치와 기본 설정 과정을 실습합니다. vcpkg로 실제 라이브러리를 받아 CMake 프로젝트에 연결하는 실습은 11장에서, `vcpkg.json`을 이용한 매니페스트 모드는 12장에서 이어서 다룹니다.

## vcpkg란 무엇인가

vcpkg는 마이크로소프트가 만들어 공개한 오픈소스 C/C++ 패키지 관리자입니다. GitHub의 `microsoft/vcpkg` 저장소로 배포되며, 특정 운영체제나 컴파일러에 종속되지 않고 Windows, Linux, macOS에서 모두 동작합니다.

vcpkg의 가장 큰 특징은 라이브러리를 미리 컴파일된 바이너리 형태로 배포하는 것이 아니라, 대부분의 경우 사용자의 환경에서 소스 코드를 직접 빌드해서 제공한다는 점입니다. 사용자가 `vcpkg install` 같은 명령으로 라이브러리를 요청하면, vcpkg는 해당 라이브러리의 소스를 내려받고, 그 라이브러리가 필요로 하는 CMake나 Makefile 같은 빌드 스크립트를 실행해서 현재 사용 중인 컴파일러와 아키텍처에 맞는 결과물을 만들어 냅니다. 이렇게 소스 기반으로 빌드하기 때문에, 2장에서 설치한 GCC나 이후 다른 장에서 다룰 MSVC 등 어떤 컴파일러를 쓰든 그 컴파일러와 실제로 호환되는 라이브러리를 얻을 수 있습니다.

## C++ 패키지 관리가 오랫동안 어려웠던 이유

Python의 pip이나 Node.js의 npm에 익숙한 개발자라면 "라이브러리 하나 설치하는 게 왜 이렇게 복잡한가"라는 의문이 들 수 있습니다. 이는 C++ 생태계가 가진 몇 가지 근본적인 특성 때문입니다.

첫째, C++에는 오랫동안 표준화된 빌드 방식이 없었습니다. 어떤 라이브러리는 Makefile로, 어떤 라이브러리는 자체 셸 스크립트로, 또 어떤 라이브러리는 각 컴파일러 벤더가 제공하는 IDE 프로젝트 파일로 빌드되었습니다. 6장과 7장에서 다룬 CMake가 사실상의 표준으로 자리 잡으면서 이 문제는 많이 개선되었지만, 여전히 CMake를 쓰지 않는 라이브러리도 존재합니다. pip이나 npm이 다루는 패키지들은 애초에 해당 언어의 표준 빌드/배포 형식(휠, 패키지 매니페스트)을 전제로 하기 때문에 이런 파편화 문제를 겪지 않습니다.

둘째, ABI(Application Binary Interface, 애플리케이션 바이너리 인터페이스) 호환성 문제가 있습니다. C++는 컴파일러나 컴파일 옵션이 다르면 함수 이름 맹글링, 구조체 메모리 레이아웃, 예외 처리 방식 등이 달라질 수 있고, 그 결과 한 컴파일러로 만든 바이너리 라이브러리를 다른 컴파일러(또는 같은 컴파일러의 다른 버전이나 옵션)로 컴파일한 프로그램에 그대로 링크하면 동작이 깨지거나 링크 자체가 실패하는 일이 흔합니다. 예를 들어 Debug/Release 빌드 모드가 다르거나, 표준 라이브러리 구현체가 다르거나(리눅스의 libstdc++와 Windows의 MSVC 런타임), 심지어 같은 컴파일러라도 C++ 표준 버전 설정이 다르면 문제가 생길 수 있습니다. Python이나 JavaScript처럼 인터프리터나 VM이 실행 환경을 통일해 주는 언어에서는 이런 문제가 원천적으로 발생하지 않기 때문에, 미리 컴파일된 패키지 하나를 모두가 내려받아 쓰는 방식이 잘 통합니다.

vcpkg는 이 두 번째 문제, 즉 ABI 호환성 문제를 "미리 컴파일된 바이너리를 배포하는" 대신 "사용자 환경에서 직접 소스를 빌드하는" 전략으로 우회합니다. 사용자가 어떤 컴파일러와 어떤 빌드 옵션을 쓰든, vcpkg는 바로 그 조합으로 라이브러리를 새로 빌드하기 때문에 최종적으로 만들어지는 라이브러리와 여러분의 애플리케이션 코드는 ABI가 어긋날 일이 없습니다. 다만 이 전략에는 대가가 따르는데, 라이브러리를 처음 설치할 때 컴파일 시간이 걸린다는 점입니다. pip이나 npm으로 패키지를 설치할 때보다 vcpkg의 첫 설치가 눈에 띄게 오래 걸리는 이유가 바로 여기에 있습니다.

## vcpkg 설치하기

vcpkg는 별도의 설치 프로그램을 배포하지 않고, 깃 저장소를 그대로 클론해서 사용하는 방식을 기본으로 합니다. 원하는 위치(예를 들어 사용자 홈 디렉터리나 별도의 도구 모음 디렉터리)에서 다음 명령을 실행합니다.

```bash
git clone https://github.com/microsoft/vcpkg
```

클론이 끝나면 `vcpkg` 디렉터리가 생성됩니다. 이 디렉터리는 이후 여러 프로젝트에서 공용으로 사용할 수 있으므로, 프로젝트마다 반복해서 클론할 필요는 없습니다.

클론한 디렉터리로 이동한 뒤, 부트스트랩 스크립트를 실행해서 vcpkg 실행 파일 자체를 빌드합니다. vcpkg는 C++로 작성되어 있어서, 처음 사용하기 전에 이 실행 파일부터 컴파일해야 합니다.

Windows(PowerShell 또는 명령 프롬프트)에서는 다음과 같이 실행합니다.

```bash
cd vcpkg
./bootstrap-vcpkg.bat
```

Linux나 macOS에서는 다음과 같이 실행합니다.

```bash
cd vcpkg
./bootstrap-vcpkg.sh
```

스크립트가 끝나면 `vcpkg` 디렉터리 안에 `vcpkg`(Linux/macOS) 또는 `vcpkg.exe`(Windows) 실행 파일이 생성됩니다. 이 실행 파일이 바로 우리가 앞으로 라이브러리를 설치할 때 사용할 명령어입니다. 실행이 잘 되는지 다음 명령으로 확인해 봅니다.

```bash
./vcpkg version
```

버전 정보가 출력되면 설치가 정상적으로 끝난 것입니다. 이후 명령어를 더 간편하게 쓰고 싶다면 이 디렉터리를 시스템 PATH에 추가해도 되지만, 필수는 아닙니다.

## vcpkg integrate install로 전역 통합하기

vcpkg로 라이브러리를 설치하는 것과, CMake 프로젝트가 그 라이브러리를 실제로 찾아서 링크하는 것은 별개의 문제입니다. `vcpkg integrate install` 명령은 이 둘을 연결해 주는 설정을 시스템에 등록합니다.

```bash
./vcpkg integrate install
```

이 명령을 실행하면 vcpkg가 툴체인 파일(`scripts/buildsystems/vcpkg.cmake`)의 위치를 시스템에 등록합니다. Windows에서는 MSBuild 프로젝트에도 자동으로 통합되고, CMake 프로젝트의 경우 다음처럼 `CMAKE_TOOLCHAIN_FILE`을 명시적으로 지정하지 않아도, 또는 이미 이 옵션이 전역 설정으로 인식되어 있어서 vcpkg로 설치한 라이브러리를 `find_package`가 별다른 추가 설정 없이 찾아낼 수 있게 됩니다.

명령을 실행하면 다음과 비슷한 안내 메시지가 출력됩니다.

```text
Applied user-wide integration for this vcpkg root.
CMake projects should use: "-DCMAKE_TOOLCHAIN_FILE=<vcpkg 경로>/scripts/buildsystems/vcpkg.cmake"
```

메시지에 안내된 것처럼, 엄밀히 말하면 `integrate install`을 실행한 뒤에도 CMake 프로젝트를 구성할 때 이 툴체인 파일 경로를 넘겨주는 것이 가장 확실한 방법입니다. 다만 `integrate install`을 한 번 실행해 두면 Visual Studio나 VS Code CMake Tools(9장 참고)처럼 이 설정을 자동으로 인식하는 도구들이 많아서, 별도로 경로를 신경 쓰지 않아도 되는 경우가 대부분입니다. 실제로 vcpkg 라이브러리를 CMake 프로젝트에 연결해서 빌드해 보는 실습은 11장에서 툴체인 파일 지정 방법까지 포함해 자세히 다룹니다.

통합을 해제하고 싶다면 다음 명령을 사용합니다.

```bash
./vcpkg integrate remove
```

## vcpkg search로 사용 가능한 패키지 찾아보기

vcpkg가 어떤 라이브러리를 제공하는지 알아보려면 `search` 명령을 사용합니다.

```bash
./vcpkg search fmt
```

이 명령을 실행하면 이름에 `fmt`가 포함된 패키지 목록과 각 패키지에 대한 짧은 설명이 출력됩니다. 예를 들어 문자열 포매팅 라이브러리인 `fmt` 패키지가 검색 결과에 나타나고, 그 옆에 버전 정보와 한 줄 설명이 함께 표시됩니다.

다른 라이브러리 이름으로도 검색해 볼 수 있습니다.

```bash
./vcpkg search json
./vcpkg search boost
./vcpkg search catch2
```

`json`으로 검색하면 `nlohmann-json`처럼 널리 쓰이는 JSON 라이브러리가 나타나고, `catch2`로 검색하면 17장에서 다룰 테스트 프레임워크인 Catch2가 검색됩니다. `boost`처럼 여러 하위 모듈로 나뉜 큰 라이브러리는 `boost-asio`, `boost-filesystem`처럼 세분화된 여러 패키지가 함께 나타나는 것을 볼 수 있습니다.

검색 결과에 나타나는 이름이 바로 `vcpkg install` 명령에 그대로 넘겨줄 패키지 이름입니다. 예를 들어 검색 결과에서 `fmt`를 확인했다면 다음 명령으로 실제 설치를 진행할 수 있습니다.

```bash
./vcpkg install fmt
```

다만 이 장에서는 vcpkg를 설치하고 검색해 보는 것까지만 다루고, 실제로 라이브러리를 설치해서 프로젝트에 연결하고 `#include`로 사용하는 과정은 11장 "vcpkg로 라이브러리 사용하기"에서 이어집니다. 매번 라이브러리를 `install` 명령으로 하나씩 설치하는 대신, 프로젝트 폴더에 `vcpkg.json` 매니페스트 파일을 두고 필요한 라이브러리 목록을 선언적으로 관리하는 방법은 12장 "vcpkg manifest 모드"에서 다룹니다.

## 요약

- vcpkg는 마이크로소프트가 만든 오픈소스 C/C++ 패키지 관리자로, 대부분의 라이브러리를 미리 컴파일된 바이너리가 아니라 사용자 환경에서 직접 소스를 빌드해서 제공합니다.
- C++는 표준화된 빌드 방식이 오랫동안 없었고 ABI 호환성 문제가 있어서, pip이나 npm처럼 미리 컴파일된 패키지를 그대로 공유하는 방식이 통하기 어려웠습니다. vcpkg는 사용자 환경에서 직접 빌드하는 방식으로 이 문제를 우회합니다.
- 설치는 `git clone https://github.com/microsoft/vcpkg` 후 Windows에서는 `bootstrap-vcpkg.bat`, Linux/macOS에서는 `bootstrap-vcpkg.sh`를 실행해서 진행합니다.
- `vcpkg integrate install`로 시스템 전역 통합을 설정해 두면, CMake를 비롯한 여러 빌드 도구가 vcpkg로 설치한 라이브러리를 더 쉽게 찾을 수 있습니다.
- `vcpkg search 라이브러리이름`으로 설치 가능한 패키지를 검색해 볼 수 있으며, 검색 결과의 이름이 곧 `vcpkg install`에 넘길 패키지 이름입니다.
- 실제 라이브러리 설치와 CMake 프로젝트 연동은 11장, `vcpkg.json` 매니페스트 모드는 12장에서 다룹니다.

## 연습문제

1. 본인의 운영체제에 맞는 부트스트랩 스크립트를 실행해서 vcpkg를 설치하고, `vcpkg version` 명령으로 정상 설치를 확인해 보세요.
2. vcpkg가 소스 기반으로 라이브러리를 빌드하는 방식이 ABI 호환성 문제를 어떻게 해결하는지 본인의 말로 설명해 보세요.
3. `vcpkg search`로 `spdlog`, `curl`, `sqlite3` 세 가지 라이브러리를 각각 검색해 보고, 검색 결과에 표시되는 정보(버전, 설명)를 비교해 보세요.
4. `vcpkg integrate install`을 실행했을 때 출력되는 안내 메시지에서 툴체인 파일의 전체 경로를 확인하고, 그 파일이 실제로 어떤 역할을 하는지 다음 장을 예습하는 마음으로 추측해 보세요.
5. pip이나 npm과 비교했을 때 vcpkg의 설치 속도가 왜 더 느리게 느껴질 수 있는지, 본문에서 설명한 이유를 근거로 정리해 보세요.

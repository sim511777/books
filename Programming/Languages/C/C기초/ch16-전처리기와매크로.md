# 16장. 전처리기와 매크로

[◀ 이전: 15장. 파일 입출력](ch15-파일입출력.md) | [📖 목차](00-목차.md) | [다음: 17장. 표준 라이브러리 둘러보기 ▶](ch17-표준라이브러리.md)

C 컴파일러가 소스 코드를 실제로 번역하기 전에, 전처리기(preprocessor)라는 프로그램이 먼저 소스 코드를 한 차례 가공합니다. 지금까지 아무 설명 없이 사용해 온 `#include <stdio.h>`도 사실 전처리기가 처리하는 지시문(directive)입니다. 이번 장에서는 전처리기가 정확히 무슨 일을 하는지, `#define`으로 상수와 매크로 함수를 어떻게 만드는지, 그리고 조건부 컴파일로 코드의 일부를 켜고 끄는 방법을 배웁니다.

## 전처리기는 언제, 무엇을 하는가

컴파일 과정은 보통 다음과 같은 단계를 거칩니다.

1. **전처리(preprocessing)**: `#`으로 시작하는 지시문을 처리하여 소스 코드를 변형한다.
2. **컴파일(compilation)**: 전처리가 끝난 순수한 C 코드를 어셈블리어나 목적 코드로 변환한다.
3. **링킹(linking)**: 여러 목적 파일과 라이브러리를 하나의 실행 파일로 합친다.

전처리기는 C 언어의 문법이나 의미를 전혀 이해하지 못합니다. 오직 텍스트를 그대로 복사하거나 치환하는 단순한 작업만 수행합니다. 이 점이 전처리기를 이해하는 데 가장 중요한 열쇠입니다. `#define`으로 만든 매크로는 "함수처럼 보이지만 실제로는 컴파일 전에 텍스트가 그대로 바뀌는 것"이라는 사실을 항상 염두에 두어야 합니다.

전처리기가 실제로 소스 코드를 어떻게 바꾸는지 직접 확인하고 싶다면, gcc를 사용하는 경우 `-E` 옵션으로 전처리 결과만 출력해 볼 수 있습니다.

```
gcc -E hello.c
```

이 명령을 실행하면 `#include`로 가져온 헤더 파일의 내용이 통째로 삽입되고, `#define`으로 정의한 매크로가 모두 치환된 결과를 볼 수 있습니다.

## #include의 동작 원리: 따옴표 vs 꺾쇠괄호

`#include` 지시문은 지정한 파일의 내용을 그 위치에 그대로 복사해 넣습니다. 2장 첫 프로그램과 빌드 과정에서 사용했던 `#include <stdio.h>`를 떠올려 보면, 이 문장이 실행되는 순간 `stdio.h` 파일 안에 들어 있는 함수 선언들이 우리 소스 코드 맨 위에 통째로 삽입되는 것입니다.

`#include`에는 두 가지 표기법이 있습니다.

```c
#include <stdio.h>   // 꺾쇠괄호
#include "myheader.h" // 큰따옴표
```

- **꺾쇠괄호(`< >`)**: 컴파일러가 미리 정해 둔 시스템 헤더 디렉터리(표준 라이브러리가 설치된 경로)에서 먼저 파일을 찾는다. 주로 표준 라이브러리나 외부 라이브러리의 헤더 파일을 포함시킬 때 사용한다.
- **큰따옴표(`" "`)**: 현재 소스 파일이 있는 디렉터리에서 먼저 파일을 찾고, 없으면 시스템 헤더 디렉터리를 뒤진다. 주로 자신이 직접 작성한 헤더 파일을 포함시킬 때 사용한다.

예를 들어 프로젝트에 `math_utils.h`라는 직접 작성한 헤더 파일이 있다면 다음과 같이 포함시킵니다.

```c
#include <stdio.h>      // 표준 라이브러리 헤더
#include "math_utils.h" // 내가 작성한 헤더 파일
```

이 규칙은 강제 사항이 아니라 컴파일러가 파일을 찾는 순서에 대한 관례이지만, 대부분의 컴파일러가 이 규칙을 따르므로 관례대로 사용하는 것이 좋습니다.

## #define으로 상수 정의하기

`#define`의 가장 단순한 용도는 이름 붙은 상수를 만드는 것입니다.

```c
#define PI 3.14159
#define MAX_STUDENTS 100
#define PROGRAM_NAME "성적 관리 시스템"
```

이렇게 정의하면 전처리기는 소스 코드에서 `PI`, `MAX_STUDENTS`, `PROGRAM_NAME`이라는 단어가 등장할 때마다 (문자열이나 다른 식별자의 일부가 아닌 온전한 단어일 때) 이를 오른쪽에 적힌 텍스트로 그대로 바꿔치기합니다.

```c
#include <stdio.h>

#define PI 3.14159
#define MAX_STUDENTS 100

int main(void)
{
    double radius = 5.0;
    double area = PI * radius * radius;

    printf("반지름 %.1f인 원의 넓이: %.2f\n", radius, area);
    printf("최대 학생 수: %d명\n", MAX_STUDENTS);

    return 0;
}
```

전처리기는 이 코드를 컴파일러에게 넘기기 전에 실제로는 다음과 같은 코드로 바꿔 놓습니다.

```c
int main(void)
{
    double radius = 5.0;
    double area = 3.14159 * radius * radius;

    printf("반지름 %.1f인 원의 넓이: %.2f\n", radius, area);
    printf("최대 학생 수: %d명\n", 100);

    return 0;
}
```

`#define`으로 만든 이름은 관례적으로 모두 대문자와 밑줄로 작성합니다(`MAX_STUDENTS`처럼). 이렇게 하면 코드를 읽을 때 "이것은 매크로로 정의된 상수구나"라고 한눈에 알아볼 수 있어, 일반 변수와 혼동하지 않게 됩니다.

## 매크로 함수 만들기

`#define`은 상수뿐 아니라 함수처럼 인자를 받는 매크로도 만들 수 있습니다.

```c
#define SQUARE(x) ((x) * (x))
#define MAX(a, b) ((a) > (b) ? (a) : (b))
```

```c
#include <stdio.h>

#define SQUARE(x) ((x) * (x))
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int main(void)
{
    int n = 5;

    printf("%d의 제곱은 %d입니다.\n", n, SQUARE(n));
    printf("10과 20 중 큰 값은 %d입니다.\n", MAX(10, 20));

    return 0;
}
```

여기서 `SQUARE(n)`은 8장 함수에서 배운 함수 호출처럼 보이지만, 실제로는 전처리 단계에서 `((n) * (n))`이라는 텍스트로 그대로 치환될 뿐입니다. 함수 호출에 따르는 오버헤드(스택 프레임 생성, 인자 복사 등)가 전혀 없다는 점이 매크로 함수의 장점입니다.

### 왜 괄호를 겹겹이 둘러싸는가

매크로 함수를 정의할 때는 인자 하나하나와 전체 표현식 모두를 괄호로 감싸는 것이 필수적인 습관입니다. 왜 그런지 다음 예를 통해 확인해 보겠습니다.

```c
// 잘못된 정의: 괄호가 부족하다.
#define BAD_SQUARE(x) x * x

int result = BAD_SQUARE(2 + 3);
```

이 코드에서 `BAD_SQUARE(2 + 3)`은 텍스트 치환 규칙에 따라 그대로 `2 + 3 * 2 + 3`으로 바뀝니다. 곱셈이 덧셈보다 우선순위가 높으므로 이 식은 `2 + 6 + 3 = 11`이 되어 버립니다. 우리가 기대했던 `(2 + 3)의 제곱인 25`와는 전혀 다른 결과입니다.

이 문제는 인자를 괄호로 감싸면 해결됩니다.

```c
#define SQUARE(x) ((x) * (x))

int result = SQUARE(2 + 3); // ((2 + 3) * (2 + 3)) 으로 치환되어 25가 된다.
```

인자 `x`뿐 아니라 전체 표현식도 괄호로 감싸야 하는 이유는, 매크로가 다른 연산과 함께 쓰일 때도 문제가 생기지 않도록 하기 위해서입니다. 예를 들어 매크로 정의를 `#define SQUARE(x) (x) * (x)`처럼 바깥쪽 괄호 없이 만들면, `10 / SQUARE(2)`가 `10 / (2) * (2)`로 치환되어 나눗셈과 곱셈이 왼쪽부터 순서대로 계산되므로 `10`이 되어 버립니다(`10 / 4`가 아니라). 이런 실수를 원천적으로 막으려면 매크로 함수를 정의할 때 다음 원칙을 지켜야 합니다.

- 매크로에 전달되는 각 인자는 개별적으로 괄호로 감싼다.
- 매크로 전체 결과도 괄호로 감싼다.

### 부작용(side effect)이 있는 인자를 조심하라

매크로 함수의 또 다른 함정은, 같은 인자가 매크로 정의 안에서 여러 번 나타난다는 점입니다. 만약 인자로 전달하는 표현식에 부작용(변수 값을 바꾸는 연산)이 있다면, 그 부작용이 여러 번 일어나는 예상치 못한 결과를 낳습니다.

```c
#include <stdio.h>

#define SQUARE(x) ((x) * (x))

int main(void)
{
    int a = 5;
    int result = SQUARE(a++); // ((a++) * (a++)) 로 치환된다.

    printf("result = %d, a = %d\n", result, a);

    return 0;
}
```

이 코드는 `a++`가 두 번 치환되어 `((a++) * (a++))`가 되므로, `a`가 한 번이 아니라 두 번 증가합니다. 게다가 곱셈의 두 피연산자를 계산하는 순서는 C 표준에서 명확히 정해져 있지 않으므로(정의되지 않은 동작에 가깝습니다), 결과값도 컴파일러에 따라 달라질 수 있습니다. 우리가 `SQUARE`를 함수로 만들었다면 `a`는 인자로 전달되기 전에 딱 한 번만 증가했을 것입니다.

```c
// 함수로 만들면 인자가 딱 한 번만 평가된다.
int square(int x)
{
    return x * x;
}
```

이 예는 매크로 함수와 일반 함수의 근본적인 차이를 보여 줍니다. **매크로는 인자를 값으로 넘겨받는 것이 아니라, 텍스트 그대로 여러 번 복사해 붙여 넣는다는 것**입니다. 따라서 매크로 함수에는 증감 연산자(`++`, `--`)나 대입 연산자처럼 부작용이 있는 표현식을 인자로 넘기지 않는 것이 안전합니다.

### 여러 문장으로 이루어진 매크로: do-while(0) 관용구

매크로 안에 여러 문장을 넣어야 할 때도 있습니다. 이때 중괄호만 사용하면 `if`문과 함께 쓰일 때 문제가 생길 수 있습니다.

```c
#define PRINT_PAIR(a, b) { printf("%d\n", a); printf("%d\n", b); }
```

```c
if (condition)
    PRINT_PAIR(1, 2); // 세미콜론 때문에 의도치 않게 블록이 끊어진다.
else
    printf("아무것도 안 함\n");
```

위 코드가 치환되면 `if (condition) { ... };`처럼 되어, 중괄호 뒤에 세미콜론이 하나 더 붙습니다. 이 세미콜론이 빈 문장으로 취급되면서 `if`문이 그 자리에서 끝나 버리고, 뒤따르는 `else`는 문법 오류를 일으킵니다. 이 문제를 피하기 위한 관용적인 해법이 `do { ... } while (0)`으로 감싸는 방법입니다.

```c
#define PRINT_PAIR(a, b) \
    do { \
        printf("%d\n", (a)); \
        printf("%d\n", (b)); \
    } while (0)
```

이렇게 정의하면 `PRINT_PAIR(1, 2);`는 하나의 완전한 문장처럼 동작하여, `if`-`else` 구조 안에서도 안전하게 사용할 수 있습니다. `\`(역슬래시)는 매크로 정의를 다음 줄로 이어 쓸 때 사용하는 줄 연결 문자입니다.

## 조건부 컴파일: #ifdef, #ifndef, #if, #endif

전처리기는 특정 조건에 따라 소스 코드의 일부를 컴파일 대상에서 아예 빼 버릴 수도 있습니다. 이를 조건부 컴파일이라고 부르며, 운영체제별로 다른 코드를 작성하거나, 디버깅용 코드를 켜고 끄거나, 헤더 파일이 중복 포함되는 것을 막을 때 널리 사용됩니다.

### #ifdef와 #ifndef

`#ifdef 이름`은 해당 이름이 `#define`으로 정의되어 있으면 그 블록을 포함시키고, 그렇지 않으면 제외합니다. `#ifndef`는 정반대로, 정의되어 있지 않을 때 블록을 포함시킵니다.

```c
#include <stdio.h>

#define DEBUG_MODE

int main(void)
{
    int total = 0;

    for (int i = 1; i <= 5; i++) {
        total += i;

#ifdef DEBUG_MODE
        printf("[디버그] i = %d, total = %d\n", i, total);
#endif
    }

    printf("합계: %d\n", total);

    return 0;
}
```

`DEBUG_MODE`가 정의되어 있으므로 위 프로그램은 반복문이 실행될 때마다 디버그 메시지를 함께 출력합니다. 만약 `#define DEBUG_MODE` 줄을 지우거나 주석 처리하면, `#ifdef DEBUG_MODE`와 `#endif` 사이의 코드는 컴파일 자체가 되지 않아 실행 파일에 전혀 포함되지 않습니다. 컴파일러가 명령줄 옵션으로 매크로를 정의할 수 있게 해 주는 기능(`gcc -DDEBUG_MODE ...`)과 함께 사용하면, 소스 코드를 고치지 않고도 디버그용 출력을 켜고 끌 수 있습니다.

### #if와 #elif

`#if`는 정수 상수 표현식의 참/거짓을 평가하여 조건부 컴파일을 수행합니다. `#elif`, `#else`와 함께 쓸 수 있으며, `if`-`else if`-`else` 문과 비슷한 구조를 가집니다.

```c
#include <stdio.h>

#define VERSION 2

int main(void)
{
#if VERSION == 1
    printf("버전 1: 기본 기능만 제공합니다.\n");
#elif VERSION == 2
    printf("버전 2: 확장 기능을 제공합니다.\n");
#else
    printf("알 수 없는 버전입니다.\n");
#endif

    return 0;
}
```

`defined` 연산자를 `#if`와 함께 사용하면 `#ifdef`와 같은 효과를 내면서도 더 복잡한 조건을 표현할 수 있습니다.

```c
#if defined(DEBUG_MODE) && !defined(RELEASE_MODE)
    printf("디버그 전용 코드입니다.\n");
#endif
```

### 헤더 가드: 헤더 파일 중복 포함 막기

여러 개의 소스 파일이 같은 헤더 파일을 `#include` 하다 보면, 하나의 번역 단위 안에서 같은 헤더 파일이 두 번 이상 포함되는 경우가 흔히 생깁니다. 예를 들어 `a.h`가 `common.h`를 포함하고, `b.h`도 `common.h`를 포함하는데, 어떤 `.c` 파일이 `a.h`와 `b.h`를 모두 포함한다면 `common.h`의 내용이 두 번 삽입됩니다. 만약 `common.h` 안에 구조체나 함수 정의가 들어 있다면, "재정의(redefinition)" 오류가 발생합니다.

이 문제를 막기 위한 표준적인 방법이 헤더 가드(header guard)입니다.

```c
// point.h
#ifndef POINT_H
#define POINT_H

struct point {
    int x;
    int y;
};

struct point make_point(int x, int y);
double distance(struct point a, struct point b);

#endif // POINT_H
```

동작 원리는 다음과 같습니다.

1. 헤더 파일이 처음 포함될 때는 `POINT_H`가 아직 정의되어 있지 않으므로 `#ifndef POINT_H`가 참이 되어, 그 아래 코드가 포함되고 `POINT_H`가 정의된다.
2. 같은 헤더 파일이 다시 포함되려고 하면, 이번에는 `POINT_H`가 이미 정의되어 있으므로 `#ifndef POINT_H`가 거짓이 되어, `#endif`까지의 내용 전체가 건너뛰어진다.

헤더 가드에 사용하는 매크로 이름은 관례적으로 헤더 파일 이름을 대문자로 바꾸고 점을 밑줄로 바꾼 형태를 사용합니다(`point.h` -> `POINT_H`). 프로젝트 규모가 커지면 이름이 겹칠 수 있으므로, `MYPROJECT_POINT_H`처럼 프로젝트 이름까지 포함시키는 경우도 많습니다.

일부 컴파일러는 `#pragma once`라는 비표준 지시문으로 같은 효과를 더 간단히 낼 수 있게 해 줍니다.

```c
#pragma once

struct point {
    int x;
    int y;
};
```

`#pragma once`는 대부분의 현대적인 컴파일러(GCC, Clang, MSVC 등)에서 지원되지만 C 표준에 정식으로 포함된 기능은 아니므로, 이식성을 중시한다면 전통적인 `#ifndef` 방식의 헤더 가드를 사용하는 것이 안전합니다.

## const와 #define, 다시 비교하기

3장 변수와 자료형에서 `const` 키워드를 잠깐 언급했습니다. 이제 전처리기의 동작 원리를 이해했으니, `const`로 상수를 만드는 방법과 `#define`으로 상수를 만드는 방법의 차이를 제대로 비교할 수 있습니다.

```c
const double PI_CONST = 3.14159;
#define PI_MACRO 3.14159
```

겉보기에는 둘 다 "PI라는 이름의 상수"를 만드는 것처럼 보이지만, 실제로는 완전히 다른 층위에서 동작합니다.

| 구분 | `const` | `#define` |
|------|---------|-----------|
| 처리 시점 | 컴파일 단계 (타입 검사 포함) | 전처리 단계 (단순 텍스트 치환) |
| 타입 | 명확한 타입을 가진다 (`double`, `int` 등) | 타입이 없다. 치환된 텍스트의 타입을 따를 뿐이다 |
| 디버거에서 확인 | 변수처럼 이름과 값이 디버거에 나타난다 | 이미 치환되어 사라졌으므로 디버거가 원래 이름을 알지 못한다 |
| 스코프 | 변수처럼 스코프(범위) 규칙을 따른다 | 스코프가 없다. `#undef`로 정의를 취소하기 전까지 파일 전체에서 유효하다 |
| 메모리 | 실제로 메모리 공간을 차지할 수 있다 | 메모리를 차지하지 않는다. 치환된 텍스트일 뿐이다 |
| 함수 흉내 | 낼 수 없다 | 매크로 함수로 함수처럼 흉내 낼 수 있다 (부작용 주의) |
| 오류 메시지 | 변수 이름 그대로 오류 메시지에 나타나 디버깅이 쉽다 | 치환된 결과가 오류 메시지에 나타나 원인 파악이 어려울 수 있다 |

구체적인 예로 타입 관련 차이를 살펴보겠습니다.

```c
const int MAX = 100;
int arr1[MAX]; // 컴파일러가 MAX의 타입(int)과 값을 알고 있다.

#define MAX_MACRO 100
int arr2[MAX_MACRO]; // 전처리 후 int arr2[100]; 으로 치환되어 동작은 같다.
```

두 방식 모두 배열 크기를 지정하는 데는 문제없이 쓸 수 있지만, `const int MAX`는 실제 타입을 가진 변수이므로 함수에 포인터로 넘기거나, 타입 검사를 거치거나, 디버거에서 값을 확인하는 등 일반 변수가 할 수 있는 일을 대부분 할 수 있습니다. 반면 `MAX_MACRO`는 컴파일 시점에는 이미 `100`이라는 순수한 숫자로 바뀌어 있어서, "원래 이름이 무엇이었는지"에 대한 정보가 전혀 남지 않습니다.

또한 `#define`은 부주의하게 사용하면 예상치 못한 곳까지 영향을 미칠 수 있습니다.

```c
#define MAX 100

void foo(void)
{
    int MAX = 5; // 오류! 전처리 결과 "int 100 = 5;" 가 되어 문법 오류가 발생한다.
}
```

`#define`으로 정의한 이름은 스코프 개념이 없으므로, 매크로와 같은 이름의 변수를 함수 안에서 새로 선언하면 심각한 문제가 생깁니다. 이런 이유로, 매크로 이름을 관례적으로 모두 대문자로 쓰는 규칙이 단순한 스타일을 넘어 실질적인 사고를 예방하는 안전장치 역할을 합니다.

정리하면, 다음과 같은 기준으로 선택하는 것이 좋습니다.

- **값에 타입이 있고, 디버깅 편의성이 중요하며, 일반적인 상수를 정의하고 싶다면** `const`를 사용한다.
- **컴파일 시점에 코드 자체를 켜고 끄거나(조건부 컴파일), 헤더 가드처럼 전처리기의 텍스트 치환 기능이 꼭 필요하거나, 배열 크기처럼 컴파일 타임 상수가 반드시 필요한 문맥(예: 오래된 컴파일러의 배열 선언)에서는** `#define`을 사용한다.
- **매크로 함수는 인라인 함수 대용으로 쓰이던 시절이 있었지만, 현대 C에서는 `inline` 키워드를 지원하는 함수가 있다면 그쪽이 타입 안전성 면에서 더 낫다.** 매크로 함수는 부작용이 없는 단순한 값에 대해서만 신중하게 사용하는 것이 좋다.

## 종합 예제: 매크로와 조건부 컴파일 활용

다음은 이번 장에서 배운 내용을 종합한 예제입니다. 로깅 매크로를 만들고, 디버그 모드 여부에 따라 동작을 다르게 하며, 헤더 가드 스타일의 중복 정의 방지도 함께 보여 줍니다.

```c
#include <stdio.h>

// 이 파일 안에서만 유효한 디버그 스위치. 필요 없을 때는 이 줄을 지우면 된다.
#define DEBUG_MODE

// 여러 문장을 안전하게 감싸는 매크로: do-while(0) 관용구 사용
#ifdef DEBUG_MODE
    #define LOG(fmt, value) \
        do { \
            printf("[LOG] " fmt "\n", (value)); \
        } while (0)
#else
    #define LOG(fmt, value) do { } while (0)
#endif

// 괄호로 인자를 안전하게 감싼 매크로 함수
#define MAX(a, b) ((a) > (b) ? (a) : (b))

// 매크로 상수
#define ARRAY_SIZE 5

int main(void)
{
    int scores[ARRAY_SIZE] = { 88, 95, 72, 100, 63 };
    int best = scores[0];

    for (int i = 1; i < ARRAY_SIZE; i++) {
        LOG("검사 중인 점수: %d", scores[i]);
        best = MAX(best, scores[i]);
    }

    printf("최고 점수: %d\n", best);

    return 0;
}
```

`DEBUG_MODE`가 정의되어 있을 때는 `LOG` 매크로가 실제로 메시지를 출력하고, 정의를 지우면 `LOG(...)`는 아무 일도 하지 않는 빈 `do { } while (0)` 문으로 치환되어 실행 파일에서 로그 출력 코드 자체가 사라집니다. 이런 패턴은 실무에서 디버그 빌드와 배포(릴리스) 빌드를 구분할 때 자주 사용됩니다.

## 요약

- 전처리기는 컴파일에 앞서 소스 코드를 텍스트 차원에서 가공하는 단계이며, C 언어의 문법이나 타입을 이해하지 못한 채 단순 치환만 수행한다.
- `#include <...>`는 시스템 헤더 디렉터리에서, `#include "..."`는 현재 디렉터리를 먼저 뒤져 파일을 찾는다.
- `#define 이름 값`으로 상수를 정의하고, `#define 이름(인자) 표현식`으로 매크로 함수를 정의할 수 있다.
- 매크로 함수를 정의할 때는 인자 각각과 전체 표현식을 모두 괄호로 감싸야 연산자 우선순위 문제를 피할 수 있으며, 부작용이 있는 인자(`x++` 등)는 여러 번 평가될 수 있으므로 전달하지 않아야 한다.
- 여러 문장을 포함하는 매크로는 `do { ... } while (0)` 관용구로 감싸야 `if`-`else` 구문에서 안전하게 동작한다.
- `#ifdef`, `#ifndef`, `#if`, `#elif`, `#else`, `#endif`로 조건부 컴파일을 수행하며, 헤더 파일 중복 포함을 막기 위한 헤더 가드(`#ifndef ... #define ... #endif`)는 거의 모든 헤더 파일에 적용해야 하는 표준적인 관례이다.
- `const`는 타입과 스코프가 있는 진짜 변수를 만드는 컴파일 단계의 기능이고, `#define`은 타입도 스코프도 없는 전처리 단계의 텍스트 치환이다. 일반적인 상수에는 `const`를, 조건부 컴파일이나 헤더 가드처럼 전처리기 고유의 기능이 필요할 때는 `#define`을 사용한다.

지금까지 17개의 장을 거치며 변수와 자료형부터 표준 라이브러리까지, C 언어로 프로그램을 작성하는 데 필요한 문법적 도구를 모두 갖추었습니다. 하지만 "컴파일이 되고 실행이 되는 코드"와 "좋은 코드"는 다릅니다. 좋은 코드란 오늘의 나뿐 아니라 내일의 나, 그리고 이 코드를 함께 보게 될 동료가 읽어도 무엇을 하는지 쉽게 이해할 수 있고, 예상치 못한 입력이 들어와도 안전하게 동작하는 코드입니다.

이번 장에서는 문법을 넘어서, C로 코드를 작성할 때 몸에 배어 있으면 좋은 습관들을 정리합니다. 지금까지 배운 내용을 실무 수준의 감각으로 연결하는 마무리 장이라고 생각하시면 됩니다.

## 18.1 일관된 코드 스타일과 네이밍 컨벤션

### 스타일이 통일되어야 하는 이유

다음 두 코드를 비교해 보겠습니다. 둘 다 정상적으로 컴파일되고 동일하게 동작합니다.

```c
#include <stdio.h>
int Calc(int A,int B){
  int result=A+B;
    return result;}
```

```c
#include <stdio.h>

int calc_sum(int a, int b)
{
    int result = a + b;
    return result;
}
```

문법적으로는 둘 다 문제가 없지만, 두 번째 코드가 훨씬 읽기 편합니다. 들여쓰기가 일관되고, 중괄호 위치가 예측 가능하며, 함수와 변수의 이름만 봐도 무엇을 하는지 짐작할 수 있습니다. 코드는 컴퓨터가 실행하기 위해서만이 아니라 사람이 읽고 유지보수하기 위해서도 작성됩니다. 특히 여러 사람이 함께 작업하는 프로젝트에서는 스타일이 제각각이면 코드를 읽을 때마다 형식을 해석하는 데 불필요한 에너지를 쓰게 됩니다.

이 책의 모든 예제 코드는 다음 규칙을 따랐습니다. 이 규칙 자체가 유일한 정답은 아니지만, 스스로 프로젝트를 시작할 때는 이런 규칙 중 하나를 정해 끝까지 일관되게 지키는 것이 중요합니다.

- 들여쓰기는 4칸 공백을 사용한다(탭과 공백을 섞어 쓰지 않는다).
- 여는 중괄호 `{`는 함수, 조건문, 반복문 모두 줄 끝에 둔다.
- 변수와 함수 이름은 `snake_case`(소문자와 밑줄)를 사용한다.
- 매크로 상수와 열거형 상수는 대문자와 밑줄(`MAX_SIZE`, `COLOR_RED`)로 구분해 변수와 한눈에 구별되게 한다.

### 이름을 짓는 원칙

이름 짓기는 사소해 보이지만 코드의 가독성을 좌우하는 가장 중요한 습관 중 하나입니다.

```c
/* 좋지 않은 예 */
int a, b, c;
int f(int x, int y) { return x * y; }

/* 개선한 예 */
int width, height, area;
int calculate_rectangle_area(int width, int height)
{
    return width * height;
}
```

- **이름만 보고 역할을 짐작할 수 있게 짓습니다.** `n`, `tmp`, `data` 같은 이름은 반복문의 짧은 카운터 변수 정도가 아니라면 피하는 것이 좋습니다.
- **불리언 성격의 변수는 `is_`, `has_` 등의 접두사를 붙입니다.** `is_valid`, `has_error`처럼 이름만 보고 참/거짓 값이라는 것을 알 수 있게 합니다. (C는 별도의 불리언 자료형이 표준에 명시적으로 없어 흔히 `int`로 표현하지만, C99부터는 `stdbool.h`의 `bool`, `true`, `false`를 사용할 수 있습니다.)
- **함수 이름은 동사로 시작합니다.** `calculate_area`, `print_report`, `is_prime`처럼 함수가 "무엇을 하는지" 동사로 드러나면 호출하는 쪽에서 함수의 부수 효과(side effect)를 예측하기 쉬워집니다.
- **약어는 신중하게 사용합니다.** `num`, `idx`, `cnt`처럼 널리 통용되는 축약은 무방하지만, 자신만 알아볼 수 있는 줄임말은 다른 사람(그리고 몇 달 뒤의 자신)을 혼란스럽게 만듭니다.

## 18.2 컴파일러 경고와 assert 활용하기

### 컴파일러 경고를 무시하지 않기

C 컴파일러는 기본 설정으로는 많은 잠재적 문제를 조용히 넘어갑니다. 하지만 경고 옵션을 켜면 컴파일러가 훨씬 더 꼼꼼하게 코드를 검사해 줍니다.

```
gcc -Wall -Wextra -o program program.c
```

- `-Wall`: "all"이라는 이름과 달리 모든 경고를 켜는 것은 아니지만, 초기화되지 않은 변수 사용, 사용하지 않는 변수, 잘못된 서식 지정자 등 실전에서 자주 문제가 되는 항목들을 폭넓게 잡아 줍니다.
- `-Wextra`: `-Wall`보다 더 엄격한 추가 검사를 활성화합니다.

다음 코드를 `-Wall` 옵션으로 컴파일하면 어떤 경고가 나오는지 살펴보겠습니다.

```c
#include <stdio.h>

int main(void)
{
    int count;
    printf("count = %d\n", count);   // count를 초기화하지 않고 사용

    return 0;
}
```

이 코드는 옵션 없이 컴파일하면 경고 없이 통과할 수도 있지만, `-Wall`을 켜면 "`count`가 초기화되지 않은 채로 사용되었을 수 있다"는 경고가 출력됩니다. 이런 경고는 프로그램이 우연히 잘못된 값을 출력하거나 예측할 수 없는 동작을 하기 전에 문제를 미리 알려 주는 훌륭한 안전장치입니다. 경고가 떴다고 해서 프로그램이 실행되지 않는 것은 아니지만, "경고가 0개인 상태"를 항상 목표로 삼는 습관을 들이는 것이 좋습니다.

더 엄격하게 관리하고 싶다면 `-Werror` 옵션으로 경고를 아예 오류로 취급하게 만들 수도 있습니다. 이렇게 하면 경고가 하나라도 남아 있는 코드는 컴파일 자체가 실패하므로, 경고를 무시하고 넘어가는 습관을 원천적으로 차단할 수 있습니다.

```
gcc -Wall -Wextra -Werror -o program program.c
```

### assert로 전제 조건 검증하기

`assert`는 `assert.h` 헤더에 정의된 매크로로, 프로그램이 실행되는 도중 특정 조건이 반드시 참이어야 한다는 것을 코드로 명시하는 도구입니다. 조건이 거짓이면 프로그램은 오류 메시지와 함께 즉시 중단됩니다.

```c
#include <assert.h>
#include <stdio.h>

double calculate_average(int *scores, int count)
{
    assert(count > 0);   // count가 0 이하이면 여기서 프로그램이 중단된다

    int sum = 0;
    for (int i = 0; i < count; i++) {
        sum += scores[i];
    }

    return (double)sum / count;
}

int main(void)
{
    int scores[] = { 90, 80, 70 };

    printf("평균: %.2f\n", calculate_average(scores, 3));

    return 0;
}
```

`calculate_average`는 `count`가 0이면 0으로 나누는 문제가 발생합니다. `assert(count > 0)`은 "이 함수는 count가 반드시 양수라는 전제 하에 동작한다"는 사실을 코드 자체에 문서처럼 남기는 동시에, 그 전제가 깨지는 순간 바로 문제의 위치를 알려 줍니다. 만약 이 검증이 없었다면, 0으로 나눈 결과가 프로그램 훨씬 뒤쪽에서야 이상한 값으로 발견되어 원인을 추적하기 훨씬 어려웠을 것입니다.

`assert`는 "사용자의 실수로 발생할 수 있는 입력 오류"가 아니라 "프로그래머의 실수로만 발생해야 하는, 있어서는 안 되는 상황"을 검증하는 데 사용합니다. 사용자가 잘못된 값을 입력하는 것처럼 정상적으로 일어날 수 있는 상황은 `if`문으로 처리하고 사용자에게 안내 메시지를 보여주는 것이 옳고, `assert`는 "절대 일어나서는 안 되는 내부 논리 오류"를 잡아내는 안전망으로 사용해야 합니다. 참고로 `NDEBUG`라는 매크로가 정의된 상태로 컴파일하면 `assert` 검사 자체가 코드에서 통째로 제거되므로, 배포용 빌드에서는 assert에 의존한 필수 로직(예: 값을 변경하는 대입문)을 넣어서는 안 됩니다.

## 18.3 흔한 실수 총정리

지금까지 각 장에서 개별적으로 다뤘던 실수들을 한자리에 모아 정리합니다. 이 목록은 코드를 작성한 뒤 스스로 점검할 때 체크리스트로 활용할 수 있습니다.

### 배열 경계를 벗어난 접근

```c
int scores[5];

for (int i = 0; i <= 5; i++) {   // 잘못된 조건: i가 5일 때도 실행된다
    scores[i] = 0;               // scores[5]는 배열 범위를 벗어난 접근
}
```

9장 배열에서 다뤘듯, C는 배열의 경계를 자동으로 검사해 주지 않습니다. `scores[5]`처럼 범위를 벗어난 접근은 컴파일 오류 없이 다른 변수의 메모리를 덮어쓸 수 있고, 문제가 한참 뒤에야 이상한 증상으로 나타나는 경우가 많습니다. 반복문 조건은 `<`를 사용하는지, 배열 크기와 반복 횟수가 정확히 일치하는지 항상 재확인하는 습관이 필요합니다.

### 초기화하지 않은 변수 사용

```c
int total;
printf("%d\n", total);   // total에 어떤 값이 들어있는지 알 수 없다
```

3장 변수와 자료형에서 설명했듯, 지역 변수는 선언만 하면 이전에 그 메모리 위치에 남아 있던 쓰레기 값(garbage value)을 그대로 가지고 있습니다. 사용하기 전에 항상 명시적으로 초기화하는 습관을 들여야 하며, `-Wall` 옵션으로 이런 실수를 상당 부분 잡아낼 수 있습니다.

### 정수 오버플로우

```c
int a = 2000000000;
int b = 2000000000;
int sum = a + b;   // int의 표현 범위를 넘어서는 값 (오버플로우 발생)
```

4장 연산자와 표현식에서 다뤘듯, `int`가 표현할 수 있는 범위를 넘어서는 계산은 예상하지 못한 값(대개 음수로 순환)을 만들어 냅니다. 큰 값을 다뤄야 한다면 `long long`이나 `unsigned` 자료형을 사용하는 것을 고려하고, 각 자료형이 표현할 수 있는 범위는 부록의 표를 참고해 미리 확인하는 것이 좋습니다.

### 포인터 오용

```c
int *make_pointer(void)
{
    int local_value = 42;
    return &local_value;   // 함수가 끝나면 local_value의 메모리는 더 이상 유효하지 않다
}
```

11장 포인터 기초와 12장 포인터 응용에서 다룬 대로, 함수의 지역 변수는 함수가 끝나는 순간 스코프(범위)를 벗어나 소멸합니다. 그 지역 변수의 주소를 반환해 밖에서 계속 사용하려고 하면, 이미 무효화된 메모리를 가리키는 댕글링 포인터(dangling pointer)가 만들어집니다. 또한 `NULL` 포인터를 역참조하는 실수, 초기화하지 않은 채로 사용하는 야생 포인터(wild pointer)도 자주 발생하는 문제이므로, 포인터를 선언할 때는 가능한 한 바로 유효한 값이나 `NULL`로 초기화하는 습관이 중요합니다.

### 동적 메모리 관련 실수

```c
int *buffer = malloc(sizeof(int) * 10);
// ... buffer를 사용하는 코드 ...
// free(buffer)를 호출하지 않고 함수가 끝남 -> 메모리 누수(memory leak)

free(buffer);
buffer[0] = 1;   // 이미 해제된 메모리에 접근 (댕글링 포인터 문제)
```

14장 동적 메모리 할당에서 다룬 대로, `malloc`으로 할당한 메모리는 `free`로 명시적으로 반납해야 합니다. 반납을 잊으면 메모리 누수가 쌓이고, 반납한 뒤에도 그 포인터를 계속 사용하면 이미 해제된 메모리에 접근하는 문제가 생깁니다. `free(buffer)` 직후에 `buffer = NULL;`로 만들어 두면, 실수로 다시 사용하려고 할 때 최소한 프로그램이 명확하게 충돌해서 문제를 바로 알아차릴 수 있습니다.

### 문자열 버퍼 오버플로우

```c
char name[10];
strcpy(name, "이것은매우긴이름입니다");   // name의 크기를 넘어서는 복사
```

10장 문자열에서 강조했듯, `strcpy`는 대상 배열의 크기를 확인하지 않습니다. 사용자 입력처럼 길이를 예측할 수 없는 데이터를 다룰 때는 `strncpy`나 17장 표준 라이브러리 둘러보기에서 소개한 `snprintf`처럼 크기 제한이 있는 함수를 사용하는 것이 안전합니다.

### 파일과 자원 해제 누락

```c
FILE *fp = fopen("data.txt", "r");
// ... 파일을 읽는 도중 오류가 발생해 중간에 return ...
// fclose(fp)가 호출되지 않음
```

15장 파일 입출력에서 다룬 대로, 열었던 파일은 반드시 닫아야 합니다. 함수 중간에 여러 경로로 반환하는 코드에서는 특정 경로에서만 `fclose`를 빠뜨리는 실수가 흔히 발생합니다. 함수 안에서 자원을 여는 지점과 닫는 지점을 가능한 한 가까이 두거나, 오류 처리를 위한 공통 종료 지점을 만들어 자원 해제 코드가 누락되지 않도록 구조를 짜는 것이 좋습니다.

### 매크로의 부수 효과

```c
#define SQUARE(x) x * x

int result = SQUARE(2 + 3);   // (2 + 3) * (2 + 3)이 아니라 2 + 3 * 2 + 3 = 11 로 계산됨
```

16장 전처리기와 매크로에서 설명했듯, 함수처럼 보이는 매크로는 단순 텍스트 치환이기 때문에 괄호를 충분히 두르지 않으면 의도와 다르게 전개됩니다. 매크로를 정의할 때는 전체 표현식과 각 매개변수를 모두 괄호로 감싸는 습관(`#define SQUARE(x) ((x) * (x))`)이 반드시 필요합니다.

## 18.4 가독성을 높이는 함수 분리와 주석 작성

### 함수는 한 가지 일만 하도록 쪼개기

```c
/* 좋지 않은 예: 입력, 계산, 출력이 뒤섞인 하나의 거대한 함수 */
int main(void)
{
    int scores[100];
    int count = 0;
    int sum = 0;
    double average;

    printf("점수를 입력하세요(0 이하 입력 시 종료): ");
    while (1) {
        int value;
        scanf("%d", &value);
        if (value <= 0) break;
        scores[count++] = value;
        sum += value;
    }

    average = (double)sum / count;

    if (average >= 90) {
        printf("등급: A (평균 %.1f)\n", average);
    } else if (average >= 80) {
        printf("등급: B (평균 %.1f)\n", average);
    } else {
        printf("등급: C (평균 %.1f)\n", average);
    }

    return 0;
}
```

이 코드는 짧지만, "입력받기", "평균 계산하기", "등급 판정하고 출력하기"라는 서로 다른 역할이 하나의 함수 안에 뒤섯여 있습니다. 이렇게 되면 등급 판정 기준만 바꾸고 싶어도 전체 코드를 다시 읽어야 하고, 나중에 이 로직을 재사용하기도 어렵습니다. 다음처럼 역할별로 함수를 나누면 각 함수가 하는 일이 이름만 보고도 명확해지고, 필요할 때 그 함수만 따로 테스트하거나 재사용할 수 있습니다.

```c
#include <stdio.h>

int read_scores(int scores[], int max_count)
{
    int count = 0;

    printf("점수를 입력하세요(0 이하 입력 시 종료): ");
    while (count < max_count) {
        int value;
        scanf("%d", &value);
        if (value <= 0) {
            break;
        }
        scores[count++] = value;
    }

    return count;
}

double calculate_average(const int scores[], int count)
{
    int sum = 0;

    for (int i = 0; i < count; i++) {
        sum += scores[i];
    }

    return (double)sum / count;
}

char determine_grade(double average)
{
    if (average >= 90) {
        return 'A';
    } else if (average >= 80) {
        return 'B';
    } else {
        return 'C';
    }
}

int main(void)
{
    int scores[100];
    int count = read_scores(scores, 100);
    double average = calculate_average(scores, count);
    char grade = determine_grade(average);

    printf("등급: %c (평균 %.1f)\n", grade, average);

    return 0;
}
```

8장 함수에서 배운 것처럼, 함수를 나누는 기준은 "코드의 길이"가 아니라 "역할의 단일성"입니다. 함수 하나가 여러 가지 일을 한다면, 그 함수의 이름을 지으려고 할 때 `and`가 들어가는 이름(`read_and_calculate_and_print`)이 되기 쉽습니다. 함수 이름에 `and`가 필요하다고 느껴진다면 함수를 쪼갤 신호로 받아들이면 됩니다.

### 주석은 "무엇을"이 아니라 "왜"를 설명한다

```c
/* 좋지 않은 주석: 코드를 그대로 읽어 주는 주석 */
i = i + 1;   // i에 1을 더한다

/* 좋은 주석: 코드만으로는 알 수 없는 의도를 설명 */
i = i + 1;   // 배열 인덱스가 아니라 화면에 표시할 번호이므로 1부터 시작하도록 보정
```

코드 자체가 "무엇을 하는지"는 웬만하면 코드를 읽으면 알 수 있습니다. 주석이 진짜 가치를 발휘하는 곳은 "왜 이렇게 작성했는지"를 설명할 때입니다. 예를 들어 특정 알고리즘을 선택한 이유, 얼핏 이상해 보이는 코드가 실제로는 어떤 버그를 피하기 위한 것인지, 매직 넘버가 어디서 나온 값인지 등을 남겨 두면 나중에 코드를 수정하려는 사람(자신을 포함해서)이 실수로 그 이유를 무시하고 코드를 망가뜨리는 것을 막을 수 있습니다.

또한 이름을 잘 지으면 주석이 필요 없는 경우가 많다는 점도 기억해 둘 만합니다. `int d; // 지난 며칠`보다는 `int days_since_last_login;`처럼 이름 자체가 설명이 되도록 짓는 것이 더 신뢰할 수 있는 문서화 방법입니다. 코드는 수정되어도 주석은 갱신되지 않아 실제 동작과 어긋나는 경우가 흔하지만, 이름은 코드와 분리될 수 없기 때문입니다.

## 18.5 다음 학습 단계 제안

이 책을 완주했다면 C 언어의 문법과 표준 라이브러리, 그리고 좋은 코드를 작성하기 위한 기본적인 습관까지 갖춘 것입니다. 이제부터는 C라는 도구를 사용해 무엇을 만들 것인지, 어떤 방향으로 지식을 넓혀 갈 것인지 선택할 차례입니다. 몇 가지 방향을 제안합니다.

- **자료구조**: 이 책에서 다룬 배열, 포인터, 구조체는 연결 리스트(linked list), 스택, 큐, 트리, 해시 테이블 같은 자료구조를 구현하기 위한 재료입니다. 특히 14장 동적 메모리 할당에서 배운 내용은 크기가 고정되지 않은 자료구조를 다루는 데 필수적입니다.
- **알고리즘**: 정렬, 탐색, 재귀(recursion)를 활용하는 분할 정복 기법 등은 17장에서 잠깐 언급한 `qsort`가 내부적으로 어떤 원리로 동작하는지를 이해하는 데도 도움이 됩니다. 알고리즘의 효율성을 시간/공간 복잡도로 분석하는 방법을 함께 공부하면 좋습니다.
- **네트워크 프로그래밍**: 소켓(socket) 프로그래밍을 통해 C로 클라이언트와 서버가 통신하는 프로그램을 작성해 볼 수 있습니다. 15장 파일 입출력에서 배운 스트림 개념이 네트워크 통신에서도 비슷하게 활용됩니다.
- **운영체제와 시스템 프로그래밍**: 프로세스, 스레드, 파일 시스템, 시그널(signal) 처리 등 운영체제가 제공하는 기능을 직접 다루는 시스템 프로그래밍으로 나아갈 수 있습니다. 1장에서 언급했듯 실제 운영체제 커널 상당 부분이 C로 작성되어 있습니다.
- **더 발전된 언어로의 확장**: C++는 C 문법을 기반으로 객체지향, 템플릿 등의 기능을 더한 언어이고, Rust는 C의 성능을 유지하면서도 메모리 안전성을 컴파일 시점에 강제하려는 현대적인 시스템 언어입니다. C를 제대로 이해했다면 이런 언어로의 확장도 한결 수월합니다.
- **오픈소스 프로젝트 읽어보기**: 실제로 널리 쓰이는 오픈소스 C 프로젝트의 소스 코드를 읽어 보는 것도 훌륭한 학습 방법입니다. 이 책에서 배운 습관들(네이밍, 함수 분리, 오류 처리 방식)이 실전 코드에서 어떻게 적용되는지 확인할 수 있습니다.

어느 방향으로 나아가든, 직접 손으로 코드를 작성하고 실패하고 디버깅하는 경험이 가장 확실한 성장의 밑거름이 된다는 사실은 변하지 않습니다. 이 책의 모든 장에서 강조했던 것처럼, 읽는 것에서 그치지 말고 반드시 직접 실행해 보시기 바랍니다.

## 요약

- 일관된 코드 스타일과 의미가 명확한 네이밍 컨벤션은 협업과 유지보수의 기본이다.
- `-Wall`, `-Wextra` 같은 컴파일러 경고 옵션을 항상 켜고, 경고가 없는 상태를 목표로 삼는다.
- `assert`는 "절대 일어나서는 안 되는" 프로그래머의 논리 오류를 검증하는 안전망으로 사용한다.
- 배열 경계 초과, 초기화되지 않은 변수, 정수 오버플로우, 포인터 오용, 메모리 누수, 버퍼 오버플로우, 자원 해제 누락, 매크로 부수 효과는 C 프로그래밍에서 반복적으로 발생하는 대표적인 실수들이다.
- 함수는 한 가지 역할만 하도록 쪼개고, 주석은 코드가 "무엇을" 하는지보다 "왜" 그렇게 작성되었는지를 설명하는 데 사용한다.
- C를 익힌 뒤에는 자료구조, 알고리즘, 네트워크/시스템 프로그래밍, 더 발전된 언어로의 확장 등 다양한 방향으로 학습을 이어갈 수 있다.

## 체크리스트

코드를 작성하고 나서, 혹은 다른 사람의 코드를 리뷰하기 전에 다음 항목을 점검해 보시기 바랍니다.

- [ ] 들여쓰기, 중괄호 위치, 이름 짓는 방식이 프로젝트 전체에서 일관되는가?
- [ ] 변수와 함수의 이름만으로 역할을 짐작할 수 있는가?
- [ ] `-Wall -Wextra` 옵션으로 컴파일했을 때 경고가 하나도 없는가?
- [ ] 모든 지역 변수가 사용되기 전에 초기화되었는가?
- [ ] 배열에 접근하는 모든 인덱스가 배열의 크기 범위 안에 있는지 확인했는가?
- [ ] `malloc`으로 할당한 메모리가 모든 실행 경로에서 정확히 한 번씩 `free`되는가?
- [ ] 해제한 포인터를 다시 사용하고 있지는 않은가? (해제 후 `NULL`로 초기화했는가?)
- [ ] 사용자 입력이나 외부 데이터를 다루는 문자열 처리에 크기 제한이 있는 함수(`snprintf`, `strncpy` 등)를 사용했는가?
- [ ] 연 파일이나 확보한 자원이 모든 실행 경로(오류 처리 경로 포함)에서 해제되는가?
- [ ] 함수 하나가 여러 가지 역할을 떠맡고 있지는 않은가?
- [ ] 주석이 코드를 그대로 반복하지 않고, 코드만으로 알 수 없는 "왜"를 설명하고 있는가?

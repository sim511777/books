## 작은 순수 함수를 우선하라

3장에서부터 계속 강조해 온 것처럼, Haskell 함수는 기본적으로 **순수(pure)**하다. 같은 입력에는 항상 같은 출력을 내고, 함수 밖의 어떤 것도 몰래 바꾸지 않는다. 좋은 Haskell 코드를 쓰는 습관의 출발점은 이 순수성을 최대한 넓게 지키는 것이다.

```haskell
-- 좋은 예: 순수 함수. 입력만 보고 결과를 예측할 수 있다
applyDiscount :: Double -> Double -> Double
applyDiscount rate price = price * (1 - rate)

ghci> applyDiscount 0.1 10000
9000.0
```

이 함수는 테스트하기 쉽고, 어디서 호출하든 결과가 똑같으며, 다른 함수와 조합하기도 쉽다. 반면 15장에서 배운 `IO`가 섞여 들어간 함수는 사정이 다르다.

```haskell
-- 덜 좋은 예: 할인 계산과 화면 출력이 뒤섞여 있다
applyDiscountAndPrint :: Double -> Double -> IO ()
applyDiscountAndPrint rate price =
  putStrLn ("할인 후 가격: " ++ show (price * (1 - rate)))
```

두 번째 함수는 계산 로직과 "화면에 출력한다"는 부작용이 한 함수 안에 뭉쳐 있다. 이 함수는 GHCi 밖에서 값만 검증하고 싶어도 반드시 `IO` 안에서 실행해야 하고, 결과를 다른 계산에 재사용하기도 번거롭다. 좋은 습관은 순수한 계산과 `IO` 동작을 분리하는 것이다.

```haskell
-- 계산은 순수 함수로
applyDiscount :: Double -> Double -> Double
applyDiscount rate price = price * (1 - rate)

-- IO는 계산 결과를 받아 출력만 담당
printDiscounted :: Double -> Double -> IO ()
printDiscounted rate price =
  putStrLn ("할인 후 가격: " ++ show (applyDiscount rate price))
```

이렇게 나누면 `applyDiscount`는 GHCi에서 `IO` 없이 즉시 검증할 수 있고, 나중에 "할인율을 화면 대신 로그 파일에 기록하자"처럼 요구사항이 바뀌어도 계산 로직은 그대로 두고 `IO` 부분만 바꾸면 된다. 실무에서 이 원칙은 흔히 "**순수한 핵심, 얇은 IO 껍질(functional core, imperative shell)**"이라 불린다. 프로그램의 핵심 로직은 최대한 순수 함수로 작성하고, 파일을 읽거나 네트워크를 호출하거나 화면에 출력하는 `IO` 동작은 프로그램의 가장 바깥쪽 얇은 층에만 몰아넣으라는 뜻이다.

물론 프로그램은 결국 무언가를 입력받고 출력해야 하므로 `IO`를 완전히 없앨 수는 없다. 목표는 `IO`를 없애는 게 아니라, `IO`가 필요한 부분과 필요 없는 부분의 경계를 명확히 긋는 것이다. 함수의 타입 시그니처에 `IO`가 등장하는지 여부가 바로 그 경계선이다. 시그니처에 `IO`가 없다면 그 함수는 부작용이 없다는 것을 컴파일러가 보장해 준다는 사실을, 14장의 펑터·애플리커티브와 15장의 모나드를 배우며 이미 확인했다.

## 타입이 곧 설계다: 시그니처를 먼저 쓴다

Haskell에서 함수를 작성하는 좋은 순서는 구현이 아니라 **타입 시그니처**에서 시작하는 것이다.

```haskell
-- 구현 전에 시그니처만 먼저 적어 본다
wordFrequency :: [String] -> [(String, Int)]
wordFrequency = undefined  -- 아직 구현 없음, 일단 타입만 확정
```

`undefined`는 "아직 구현하지 않았다"는 뜻의 특별한 값으로, 어떤 타입으로도 취급될 수 있어 컴파일은 통과하지만 실제로 평가되는 순간 프로그램이 멈춘다. 시그니처만 먼저 적어 두고 `undefined`로 자리를 채워 두면, 전체 프로그램이 이 함수를 어떻게 사용할지부터 컴파일이 되는지 확인해 볼 수 있다.

이 습관이 강력한 이유는 Haskell의 타입 시스템이 유난히 표현력이 높기 때문이다. 시그니처 하나만 봐도 함수가 무엇을 할 수 있고 무엇을 할 수 없는지 상당 부분 짐작할 수 있다.

```haskell
-- 이 시그니처만 보고 무엇을 추론할 수 있을까?
process :: [Int] -> Maybe Int
```

`Maybe Int`가 반환 타입이라는 것만으로도, 12장에서 배운 대로 "실패할 수 있는 계산"이라는 사실이 드러난다. 반대로 아래 시그니처를 보자.

```haskell
process2 :: [Int] -> Int
```

이 함수는 실패하지 않는다고 타입이 약속하고 있다. 만약 내부에서 빈 리스트를 만나 실패할 수 있는 로직이라면, 이 시그니처는 거짓말을 하고 있는 셈이다. 이런 거짓 시그니처를 피하려면 결국 `head []`처럼 부분 함수를 억지로 쓰게 되는데, 이는 뒤에서 다시 다룰 흔한 실수의 근원이다.

타입 시그니처를 먼저 쓰는 습관은 "타입이 곧 설계"라는 말로 요약된다. 함수를 구현하기 전에 시그니처만으로 다음 질문에 답해 보자.

- 이 함수는 실패할 수 있는가? (`Maybe`, `Either`로 표현되어야 하는가, 12장)
- 이 함수는 부작용이 있는가? (`IO`가 필요한가, 15장)
- 이 함수는 여러 타입에 대해 동작해야 하는가? (타입 변수와 타입 클래스 제약이 필요한가, 11장과 16장)
- 입력이 하나의 값인가, 여러 값의 컬렉션인가? (리스트인가 튜플인가, 6장과 7장)

이 질문들에 먼저 답하고 나면, 실제 구현은 놀라울 만큼 자연스럽게 따라오는 경우가 많다. 반대로 시그니처를 정하지 않고 구현부터 시작하면, 중간에 "이 함수가 실패할 수도 있었네"라는 사실을 뒤늦게 깨닫고 함수 전체를 뒤엎는 일이 자주 생긴다.

## 패턴 매칭은 전부 다루어라

4장에서 패턴 매칭을 배울 때 이미 강조했지만, 좋은 코드 습관으로 다시 짚을 만큼 중요하다. `data`로 정의한 타입의 생성자가 여러 개라면, 함수는 **그 생성자 전부**에 대응하는 패턴을 갖추어야 한다.

```haskell
data TrafficLight = Red | Yellow | Green

-- 나쁜 예: Green을 처리하는 패턴이 없다
next :: TrafficLight -> TrafficLight
next Red    = Green
next Yellow = Red
-- Green 패턴이 빠져 있다!
```

GHC는 이런 실수를 컴파일 시점에 경고로 알려 줄 수 있다. `-Wincomplete-patterns` 옵션(또는 `-Wall`)을 켜고 컴파일하면 다음과 같은 경고가 뜬다.

```
warning: [-Wincomplete-patterns]
    Pattern match(es) are non-exhaustive
    In an equation for `next':
        Patterns not matched: Green
```

이 경고를 무시하고 `next Green`을 실제로 호출하면, 컴파일은 통과했더라도 실행 중에 다음과 같은 오류로 멈춘다.

```
*** Exception: NonExhaustivePatterns
```

즉 **비완전 패턴은 컴파일러가 경고해 주는데도 실행 시점 오류로 이어지는 대표적인 실수**다. 고칠 방법은 두 가지다. 첫째, 빠진 패턴을 채운다.

```haskell
next :: TrafficLight -> TrafficLight
next Red    = Green
next Yellow = Red
next Green  = Yellow
```

둘째, 5장에서 배운 가드나 `case`의 `_` 패턴으로 "나머지 모두"를 명시적으로 처리한다. 다만 `_`로 뭉개 버리면 나중에 새 생성자를 추가했을 때 컴파일러가 "이 경우도 처리해야 한다"고 알려 주지 못한다는 단점이 있다. 그래서 가능하면 각 생성자를 하나씩 명시적으로 나열하는 쪽을 권장한다. 이렇게 하면 10장에서 만든 데이터 타입에 나중에 생성자를 하나 추가할 때, 그 타입을 다루는 모든 함수에서 GHC가 "이 생성자를 빠뜨렸다"고 정확히 짚어 준다. 이는 코드를 고칠 때 실수를 막아 주는 가장 강력한 안전망 중 하나다.

항상 `-Wall`을 켜고 개발하는 습관을 들이면, 비완전 패턴뿐 아니라 사용하지 않는 이름, 타입 시그니처 누락 등도 함께 잡아낼 수 있다.

```powershell
ghc -Wall Main.hs
```

## 흔한 실수 정리

지금까지 여러 장에 걸쳐 마주쳤던 실수들을 한자리에 모아 다시 짚어 본다.

### 무한 재귀

8장에서 재귀를 배울 때 강조했듯, 재귀 함수는 반드시 **종료 조건(base case)**에 도달해야 한다.

```haskell
-- 나쁜 예: n이 절대 0에 도달하지 않는다
countDown :: Int -> [Int]
countDown n = n : countDown (n + 1)  -- n - 1이 아니라 n + 1!
```

이 함수를 실제로 호출하면 리스트를 다 소비하기 전까지는(13장의 지연 평가 덕분에) 당장 멈추지는 않지만, `length (countDown 5)`처럼 리스트 전체 길이를 요구하는 순간 메모리를 소진할 때까지 영원히 계산을 이어간다. 재귀 함수를 작성할 때는 항상 "이 재귀 호출은 종료 조건에 더 가까워지고 있는가?"를 스스로 확인하는 습관이 필요하다.

### `head`, `tail`, `!!` 같은 부분 함수의 오용

6장에서 리스트를 배울 때 다뤘던 `head`, `tail`, `!!`, `fromJust`(12장) 같은 함수는 모든 입력에 대해 결과를 내놓지 못하는 **부분 함수(partial function)**다.

```haskell
ghci> head ([] :: [Int])
*** Exception: Prelude.head: empty list
```

`head []`가 예외를 던진다는 사실 자체는 문서화되어 있지만, 문제는 이 위험이 타입 시그니처에 전혀 드러나지 않는다는 점이다. `head :: [a] -> a`라는 시그니처만 보면 이 함수가 항상 성공할 것처럼 보인다. 좋은 습관은 가능하면 부분 함수 대신 12장에서 배운 안전한 대안을 쓰는 것이다.

```haskell
-- 부분 함수 대신 전체 함수로
safeHead :: [a] -> Maybe a
safeHead []    = Nothing
safeHead (x:_) = Just x
```

`safeHead`의 시그니처는 "실패할 수 있다"는 사실을 `Maybe`로 정직하게 드러낸다. 리스트가 빈 경우를 호출하는 쪽에서 반드시 처리하도록 컴파일러가 강제하는 셈이다. `Data.Maybe`의 `listToMaybe`도 같은 역할을 한다.

부분 함수를 완전히 피할 수 없는 상황도 있다. 예를 들어 "이 리스트는 절대 비어 있지 않다"는 사실을 호출하는 쪽에서 이미 보장하고 있는 경우다. 그런 경우라도 `error`에 상황을 설명하는 메시지를 넣어 두면, 실제로 그 가정이 깨졌을 때 원인을 훨씬 빠르게 찾을 수 있다.

```haskell
firstOrError :: [a] -> a
firstOrError [] = error "firstOrError: 리스트가 비어 있을 수 없다는 가정이 깨졌습니다"
firstOrError (x:_) = x
```

### 지나치게 큰 `where`와 깊은 중첩

함수 하나에 `where` 절이 지나치게 많은 보조 함수를 품고 있거나, `case`와 `let`이 여러 겹으로 중첩되면 읽기가 어려워진다. 보조 함수가 다른 함수에서도 쓸 만하다면, 17장에서 배운 대로 별도의 최상위 함수로 뽑아내거나 별도 모듈로 옮기는 것이 좋다. "한 함수가 한 가지 일만 하도록" 나누는 습관은 명령형 언어에서도 익숙하지만, 순수 함수 위에서는 그 작은 조각들을 마음껏 조합할 수 있다는 점이 Haskell의 큰 장점이다.

### `Int` 오버플로를 잊는 것

3장에서 다뤘던 내용이지만 실수로 자주 반복된다. 아주 큰 수를 다루는 계산에 `Int`를 썼다가 조용히 오버플로가 나는 경우다. 정확한 값이 중요하다면 `Integer`를 쓰는 편이 안전하다.

## GHCi를 이용한 탐색적 개발

2장에서 처음 GHCi를 켜 본 뒤로, 이 책의 거의 모든 예제는 GHCi 세션으로 결과를 확인했다. 좋은 Haskell 개발 습관에서 GHCi는 단순한 "계산기"가 아니라 **탐색 도구**로 쓰인다.

파일을 고치는 중이라면 `:load`(줄여서 `:l`)로 그 파일을 불러오고, 함수를 하나 바꿀 때마다 `:reload`(`:r`)로 다시 불러와 즉시 확인하는 흐름이 실무에서 가장 흔한 개발 루프다.

```haskell
ghci> :load Shapes.hs
[1 of 1] Compiling Shapes
ghci> circleArea 3.0
28.274333882308138
-- Shapes.hs를 고친 뒤
ghci> :reload
[1 of 1] Compiling Shapes
ghci> circleArea 3.0
28.3
```

함수의 타입이 헷갈릴 때는 `:type`(`:t`)으로 즉시 확인하고, 어떤 이름이 정확히 어떤 모듈에서 왔는지, 어떤 타입 클래스에 속하는지 궁금할 때는 `:info`(`:i`)를 쓴다.

```haskell
ghci> :info Maybe
type Maybe :: * -> *
data Maybe a = Nothing | Just a
  ...
instance Applicative Maybe
instance Functor Maybe
instance Monad Maybe
  ...
```

`:info`는 11장, 14장, 15장에서 다룬 타입 클래스 인스턴스 관계를 한눈에 확인하는 데 특히 유용하다. "이 타입이 `Functor`인가, `Monad`인가?"를 문서를 뒤지지 않고 바로 GHCi에서 확인할 수 있다.

작은 함수를 하나 만들고 나면, 파일을 저장하고 컴파일까지 하기 전에 먼저 GHCi에서 몇 가지 입력으로 즉시 실험해 보는 습관을 들이자. 경계값(빈 리스트, 0, 음수, `Nothing`)을 GHCi에서 먼저 던져 보는 것만으로도 앞서 이야기한 비완전 패턴이나 부분 함수 문제를 구현 초기에 잡아낼 수 있다.

## 코드 리뷰 체크리스트

지금까지의 내용을 실전에서 쓸 수 있는 체크리스트로 정리한다. 함수를 다 작성한 뒤, 또는 다른 사람의 코드를 읽을 때 아래 항목을 훑어보자.

- [ ] 모든 최상위 함수에 타입 시그니처가 있는가? (3장)
- [ ] 이 함수가 부작용이 있다면 시그니처에 `IO`가 명시되어 있고, 없다면 실제로 순수한가?
- [ ] `data`로 만든 타입을 다루는 함수에서 모든 생성자를 패턴으로 다루고 있는가? `-Wall`로 경고가 없는가? (4장, 10장)
- [ ] `head`, `tail`, `!!`, `fromJust` 같은 부분 함수를 꼭 필요한 곳에만 최소한으로 쓰고 있는가? (6장, 12장)
- [ ] 재귀 함수에 명확한 종료 조건이 있고, 재귀 호출마다 그 조건에 가까워지는가? (8장)
- [ ] 실패할 수 있는 계산은 `Maybe`나 `Either`로, 여러 개일 수 있는 부작용은 `IO`나 적절한 모나드로 표현되어 있는가? (12장, 15장)
- [ ] 반복되는 로직은 직접 재귀를 쓰기보다 `map`, `filter`, `fold` 같은 고차 함수로 표현할 수 있는가? (9장)
- [ ] 모듈의 내보내기 목록이 실제로 외부에서 필요한 이름만 담고 있는가? (17장)
- [ ] 이 함수를 GHCi에서 몇 가지 입력(특히 경계값)으로 직접 실행해 확인해 보았는가?

이 체크리스트를 매번 처음부터 끝까지 완벽하게 지키기는 어렵다. 하지만 코드를 쓰다가 막히거나 버그가 자꾸 나는 순간, 이 목록으로 돌아와 어떤 항목을 놓쳤는지 점검해 보면 원인을 훨씬 빠르게 찾을 수 있다.

## 다음 학습 단계

이 책은 Haskell의 문법과 핵심 개념을 순서대로 훑어보는 입문서였다. 여기서 익힌 타입, 패턴 매칭, 고차 함수, 타입 클래스, 펑터·애플리커티브·모나드는 이후 어떤 방향으로 나아가든 공통적으로 쓰이는 토대다. 앞으로 더 나아가고 싶다면 다음과 같은 방향을 살펴볼 만하다.

- **웹 서버와 API 개발**: HTTP 요청을 처리하는 서버를 만들어 보면, 이 책에서 배운 `IO`와 모나드가 실제 애플리케이션에서 어떻게 조립되는지 체감할 수 있다. 라우팅, 요청 파싱, 응답 생성 같은 실전 문제를 겪으며 타입 클래스와 모듈 설계 감각이 훨씬 단단해진다.
- **파서 조합기(parser combinator)**: 작은 파싱 함수들을 애플리커티브와 모나드 인터페이스로 조합해 복잡한 문법을 처리하는 기법이다. 14장과 15장에서 배운 개념이 실전에서 가장 극적으로 활용되는 분야 중 하나이며, 직접 작은 파서 라이브러리를 만들어 보는 것도 좋은 연습이다.
- **동시성과 병렬성**: Haskell은 순수성과 불변성 덕분에 동시성 프로그래밍에서 특히 강점을 갖는다. 여러 계산을 안전하게 병렬로 실행하는 방법을 다루는 자료를 찾아보면, 이 책에서 다진 불변성의 실질적 이점을 새로운 각도에서 확인할 수 있다.
- **테스트와 속성 기반 테스트(property-based testing)**: 순수 함수는 테스트하기 쉽다는 이점이 있는데, 이를 극대화한 것이 속성 기반 테스트다. "이 함수는 입력이 무엇이든 항상 이 성질을 만족해야 한다"를 선언하고 무작위 입력으로 검증하는 방식으로, 타입 시그니처를 먼저 쓰는 습관과 자연스럽게 이어진다.
- **실전 프로젝트를 직접 완성해 보기**: 간단한 CLI 도구, 개인용 가계부, 텍스트 기반 게임처럼 작더라도 처음부터 끝까지 완성해 보는 경험이 무엇보다 중요하다. 이 책의 예제들과 달리, 실전 프로젝트에서는 요구사항이 바뀌고 예상 못 한 입력이 들어온다. 그 과정에서 이 장에서 정리한 습관들이 왜 중요한지 몸으로 이해하게 될 것이다.

어떤 방향을 택하든, 공식 문서와 표준 라이브러리 레퍼런스를 직접 찾아 읽는 습관이 가장 오래가는 학습 방법이다. 부록에서 그런 자료를 어디서, 어떻게 찾아야 하는지 안내한다.

11장에서는 `Eq`, `Show`, `Ord` 같이 GHC가 미리 마련해 둔 타입클래스를 사용했고, 대부분의 경우 `deriving` 키워드만 붙이면 충분했다. 이번 장에서는 방향을 바꿔, 우리가 직접 새로운 "행동의 규약"을 설계하는 법을 배운다. `class`로 규약을 정의하고, `instance`로 특정 타입에 그 규약을 채워 넣는 과정을 통해, 서로 다른 타입들이 같은 이름의 함수로 각자 다르게 동작하도록 만들 수 있다.

## `class`: 나만의 타입클래스 정의하기

커피숍 메뉴를 예로 들어 보자. 메뉴에 있는 것이라면 무엇이든 "가격을 물어볼 수 있어야 한다"는 규약을 만들고 싶다. 이를 타입클래스로 표현하면 다음과 같다.

```haskell
class Priced a where
  price :: a -> Double
```

`class Priced a where`는 "`a`라는 타입이 `Priced`에 속하려면, `price :: a -> Double` 함수를 반드시 구현해야 한다"는 선언이다. 아직 어떤 타입도 이 규약을 만족하지 않는다. 규약을 만족시키려면 `instance`를 써서 구체적인 구현을 채워야 한다.

타입클래스에는 **기본 구현(default implementation)**도 넣을 수 있다. 다음처럼 `describePrice`라는 두 번째 메서드를 추가하되, 미리 합리적인 기본 동작을 정의해 두자.

```haskell
class Priced a where
  price :: a -> Double           -- 반드시 구현해야 하는 메서드
  describePrice :: a -> String   -- 기본 구현이 있는 메서드
  describePrice item = "가격: " ++ show (price item) ++ "원"
```

`price`는 구현부가 없으므로 `instance`를 만들 때 반드시 채워야 하는 **최소 구현(minimal complete definition)**이다. `describePrice`는 기본 구현이 이미 있으므로, `instance`에서 굳이 다시 정의하지 않아도 자동으로 이 동작을 물려받는다. 물론 원한다면 특정 타입에서만 `describePrice`를 오버라이드할 수도 있다.

## `instance`: 구체적인 타입에 규약 채우기

10장에서 다룬 방식대로 커스텀 데이터 타입 두 개를 만들고, 각각 `Priced`의 `instance`로 등록해 보자.

```haskell
data Coffee = Americano | Latte | ColdBrew deriving (Show, Eq)

data Book = Book { bookTitle :: String, bookPrice :: Double } deriving (Show)

instance Priced Coffee where
  price Americano = 4500
  price Latte      = 5000
  price ColdBrew   = 5500

instance Priced Book where
  price b = bookPrice b
  describePrice b = bookTitle b ++ "의 가격: " ++ show (price b) ++ "원"
```

`Coffee`는 `describePrice`를 따로 정의하지 않았으므로 `Priced`의 기본 구현을 그대로 쓴다. `Book`은 제목을 포함한 더 친절한 문구를 원해서 `describePrice`를 직접 오버라이드했다. GHCi에서 확인해 보자.

```haskell
ghci> price Latte
5000.0
ghci> describePrice Latte
"가격: 5000.0원"
ghci> let novel = Book { bookTitle = "이상한 나라의 앨리스", bookPrice = 12000 }
ghci> describePrice novel
"이상한 나라의 앨리스의 가격: 12000.0원"
```

같은 이름의 함수 `price`와 `describePrice`가 `Coffee`와 `Book`이라는 서로 다른 타입에 대해 서로 다르게 동작한다. 이것이 타입클래스가 제공하는 **애드혹 다형성(ad-hoc polymorphism)**이다. "이 타입이 무엇인가"에 따라 실제로 실행되는 코드가 달라진다는 점에서, 9장에서 본 `map :: (a -> b) -> [a] -> [b]`처럼 "타입이 무엇이든 완전히 동일하게 동작하는" **매개변수 다형성(parametric polymorphism)**과는 성격이 다르다.

## 다형적 함수: 타입클래스 제약으로 "이 조건만 만족하면 다 됩니다" 표현하기

`Priced`의 진짜 힘은, `Priced` 인스턴스이기만 하면 어떤 타입에도 통하는 함수를 짤 수 있다는 데 있다.

```haskell
totalPrice :: Priced a => [a] -> Double
totalPrice items = sum (map price items)
```

`Priced a =>` 부분이 바로 **타입클래스 제약(constraint)**이다. "`a`가 무슨 타입인지는 몰라도, 최소한 `Priced`의 인스턴스여야 한다"는 조건을 걸어 둔 것이다. 3장에서 `Num a => a -> a` 같은 시그니처를 본 적이 있는데, 원리는 똑같다. `Priced` 제약이 있으면 함수 본문에서 `price`를 마음껏 쓸 수 있고, 그 대신 `totalPrice`를 호출하는 쪽에서는 반드시 `Priced` 인스턴스인 타입의 리스트를 넘겨야 한다.

```haskell
ghci> totalPrice [Americano, Latte, ColdBrew]
15000.0
ghci> totalPrice [novel, Book "함수형 사고" 25000]
37000.0
```

같은 `totalPrice` 함수가 `[Coffee]`에도, `[Book]`에도 그대로 통한다. 단, `[Coffee]`와 `[Book]`을 한 리스트에 섞어 넣을 수는 없다. Haskell의 리스트는 원소가 모두 같은 타입이어야 하기 때문이다(6장 참고). 서로 다른 `Priced` 타입을 한 리스트에 담으려면 이 책의 범위를 넘어서는 존재 타입(existential type) 같은 고급 기법이 필요하다.

## 여러 제약을 동시에 걸기

제약은 하나만 걸 수 있는 게 아니다. 괄호와 쉼표로 여러 조건을 동시에 요구할 수 있다.

```haskell
cheapest :: Priced a => [a] -> a
cheapest = foldr1 (\x y -> if price x <= price y then x else y)

describeCheapest :: (Priced a, Show a) => [a] -> String
describeCheapest items = "가장 저렴한 항목: " ++ show (cheapest items)
```

`cheapest`는 `Priced` 제약만으로 충분하다. 두 값 중 가격이 더 낮은 쪽을 고르기만 하면 되기 때문이다. 하지만 `describeCheapest`는 결과를 문자열로 보여줘야 하므로 `show`도 필요하고, 그러려면 `a`가 `Show`의 인스턴스여야 한다. `(Priced a, Show a) => ...`처럼 쉼표로 나열하면 "`a`는 `Priced`이면서 동시에 `Show`여야 한다"는 두 조건을 모두 강제한다.

```haskell
ghci> describeCheapest [Americano, Latte, ColdBrew]
"가장 저렴한 항목: Americano"
```

## 타입클래스 계층: 슈퍼클래스 제약

타입클래스 자체도 다른 타입클래스를 전제로 정의할 수 있다. 예를 들어 "할인 가능한 항목"이라는 개념은 애초에 가격이 있어야만 의미가 있다.

```haskell
class Priced a => Discountable a where
  discountedPrice :: a -> Double
  discountedPrice item = price item * 0.9   -- 기본값: 10% 할인
```

`class Priced a => Discountable a where`에서 `Priced a =>` 부분이 **슈퍼클래스 제약**이다. 이는 "어떤 타입이 `Discountable`의 인스턴스가 되려면, 먼저 `Priced`의 인스턴스여야 한다"는 뜻이다. 이미 11장에서 `Ord`가 내부적으로 `Eq`를 슈퍼클래스로 요구한다는 사실(크기 비교를 하려면 같음 비교가 먼저 정의되어 있어야 한다는 논리)을 살짝 언급했는데, 우리가 직접 만드는 타입클래스에도 같은 원리를 적용할 수 있다.

```haskell
instance Discountable Coffee   -- price가 이미 있으므로 기본 구현만으로 충분

instance Discountable Book where
  discountedPrice b = price b * 0.8   -- 책은 20% 할인으로 오버라이드
```

`Coffee`는 `discountedPrice`를 따로 정의하지 않아도 `Priced Coffee` 인스턴스가 이미 있으므로 기본 구현(10% 할인)을 그대로 쓸 수 있다. `Book`은 다른 할인율을 원해서 직접 오버라이드했다.

```haskell
ghci> discountedPrice Latte
4500.0
ghci> discountedPrice novel
9600.0
```

## 다른 언어의 인터페이스·제네릭과 비교

Java나 C# 같은 언어의 인터페이스와 비교하면 타입클래스의 성격이 더 분명해진다.

```java
interface Priced {
    double price();
}

class Coffee implements Priced {
    public double price() { return 5000; }
}
```

겉모습은 비슷해 보이지만 중요한 차이가 있다. Java의 `implements`는 클래스를 **선언할 때** 미리 인터페이스를 붙여야 한다. 이미 만들어진 클래스, 특히 내가 소유하지 않은 라이브러리의 클래스에는 나중에 인터페이스를 끼워 넣을 수 없다. Haskell의 `instance`는 이와 달리 **비침습적(retroactive)**이다. 이미 존재하는 타입(심지어 `Int`나 `String`처럼 표준 라이브러리의 타입도)에 대해, 그 타입을 정의한 코드를 건드리지 않고도 나중에 원하는 곳에서 새로운 타입클래스의 인스턴스를 추가할 수 있다.

제네릭과의 비교도 흥미롭다. TypeScript나 Java의 `<T extends Comparable<T>>` 같은 제약 있는 제네릭은 Haskell의 `Ord a => ...` 제약과 목적이 비슷하다. 둘 다 "이 타입 매개변수는 특정 조건을 만족해야 한다"는 제약을 표현한다. 다만 Haskell의 타입클래스는 그 자체로 "같은 이름의 함수가 타입마다 다르게 구현될 수 있다"는 애드혹 다형성의 기반이 되는 반면, 제네릭은 보통 하나의 구현이 여러 타입에 그대로 재사용되는 매개변수 다형성 쪽에 더 가깝다. 이 두 다형성을 한 문장으로 구분하면: **매개변수 다형성**은 타입을 몰라도 되는 동작(리스트 길이 구하기처럼)에, **애드혹 다형성**은 타입마다 다르게 동작해야 하는 것(가격 계산이나 같음 비교처럼)에 쓰인다. Haskell의 타입클래스는 이 두 가지를 같은 함수 시그니처 문법(`Priced a => a -> ...`) 안에서 자연스럽게 표현할 수 있게 해 준다는 점이 특징이다. Rust를 안다면, Rust의 `trait`이 Haskell의 타입클래스와 가장 가까운 개념이라는 점도 참고할 만하다.

## 요약

- `class`는 새로운 타입클래스, 즉 "이 타입클래스에 속하려면 어떤 함수를 구현해야 하는가"를 정의하는 규약이다. 구현이 없는 메서드는 반드시 채워야 하고, 기본 구현이 있는 메서드는 선택적으로 오버라이드할 수 있다.
- `instance`는 특정 타입에 대해 그 규약을 실제로 채우는 선언이며, 이미 정의된 타입에도 나중에 비침습적으로 인스턴스를 추가할 수 있다.
- `Priced a => [a] -> Double`처럼 타입클래스 제약을 함수 시그니처에 붙이면, "이 조건을 만족하는 타입이라면 무엇이든 동작하는" 다형적 함수를 만들 수 있다. 여러 제약은 `(Eq a, Show a) => ...`처럼 쉼표로 동시에 걸 수 있다.
- 타입클래스는 다른 타입클래스를 슈퍼클래스 제약으로 요구할 수 있다(`class Priced a => Discountable a where`). 이는 `Ord`가 `Eq`를 요구하는 것과 같은 원리다.
- Java/C# 인터페이스는 클래스 선언 시 침습적으로 붙여야 하지만, Haskell의 타입클래스 인스턴스는 기존 타입에도 나중에 추가할 수 있다. 매개변수 다형성(타입 무관 동일 동작)과 애드혹 다형성(타입별 다른 동작)을 구분해 이해하면, 타입클래스가 후자를 구현하는 메커니즘이라는 점이 명확해진다.

## 연습문제

1. 도형의 "부피"를 구하는 `class Volume a where volume :: a -> Double`을 정의하고, `Cube`(정육면체)와 `Sphere`(구) 데이터 타입에 대한 `instance`를 작성하라.
2. `Priced` 클래스에 `isExpensive :: a -> Bool`이라는 기본 구현(예: 10000원 이상이면 `True`)을 추가하고, 특정 타입(예: `Book`)에서는 기준을 다르게 오버라이드해 보라.
3. `(Priced a, Ord a) => [a] -> [a]`처럼 여러 제약을 가진 함수를 하나 설계해, 가격 순으로 정렬된 리스트를 반환하도록 작성하라. (힌트: `Ord`를 만족시키려면 해당 타입에 `Ord` 인스턴스도 필요하다.)
4. `class Discountable a => VipDiscountable a where` 형태로, `Discountable`을 슈퍼클래스로 요구하는 새로운 타입클래스를 설계하고 기본 구현을 하나 이상 포함시켜 보라.
5. 자신이 아는 다른 언어(Java, TypeScript, Python 등)에서 "여러 타입에 공통 동작을 강제하는" 기능을 하나 골라, Haskell의 `class`/`instance`와 어떤 점이 비슷하고 어떤 점이 다른지 세 문장 이상으로 비교해 보라.

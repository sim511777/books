지금까지 이 책에서 다룬 함수는 모두 "순수"했다. 같은 입력을 넣으면 항상 같은 출력이 나왔고, 화면에 무언가를 찍거나 파일을 읽는 일은 전혀 없었다. 하지만 실제로 쓸모 있는 프로그램은 결국 사용자의 입력을 받고, 화면에 결과를 보여주고, 파일이나 네트워크에 접근해야 한다. 이 장에서는 순수 함수형 언어인 Haskell이 이런 "부작용"을 어떻게 타입 시스템 안으로 끌어들이는지, 그리고 그 중심에 있는 `IO`와 **모나드(Monad)**라는 개념을 살펴본다.

## 문제 제기: 순수한 언어에서 화면에 글자를 찍으려면

3장에서 배운 대로 Haskell의 함수는 참조 투명해야 한다. 그런데 "화면에 문자열을 출력하라"는 동작은 참조 투명성과 정면으로 충돌한다. 같은 코드를 두 번 실행하면 화면에 글자가 두 번 나타나야 하고, 이건 순수한 계산이 아니라 세상에 영향을 주는 **행위**다. 만약 `putStrLn`이 그냥 평범한 함수라면, 다음과 같은 코드에서 컴파일러가 마음대로 계산 순서를 바꾸거나 결과를 캐싱해 버려도 이상하지 않을 것이다.

```haskell
greet :: String
greet = "안녕, " ++ "Haskell"
```

이 `greet`은 언제 평가하든 항상 같은 문자열이다. 하지만 "화면에 출력하는 일"은 순서가 중요하고, 두 번 하면 두 번 일어나야 하며, 컴파일러가 마음대로 생략하거나 순서를 바꾸면 안 된다. Haskell은 이 문제를 아예 없애는 대신, **부작용이 필요한 계산을 별도의 타입으로 명확히 표시**하는 방법을 택했다. 그 타입이 바로 `IO`다.

## `IO`: 부작용을 수행하는 "계획"을 값으로 표현하기

`putStrLn`의 타입을 GHCi에서 확인해 보자.

```haskell
ghci> :type putStrLn
putStrLn :: String -> IO ()
ghci> :type putStrLn "hello"
putStrLn "hello" :: IO ()
```

`putStrLn "hello"`는 `IO ()` 타입의 **값**이다. 여기서 핵심은, 이 값 자체가 "hello를 출력하는 행위"가 아니라 **"hello를 출력하겠다는 계획을 담은 값"**이라는 점이다. `IO ()`라는 상자 안에는 "실행하면 화면에 무언가를 찍고, 결과로 `()`(아무 의미 없는 값, 4장에서 다룬 유닛 타입)를 돌려주는 계획"이 들어 있다. 이 값을 만드는 것 자체는 순수한 일이다. 값을 만든다고 해서 당장 화면에 뭔가 찍히지는 않는다.

이 계획이 실제로 "실행"되는 시점은 딱 하나, 프로그램의 진입점인 `main`으로 연결되었을 때뿐이다.

```haskell
main :: IO ()
main = putStrLn "Hello, Haskell!"
```

GHC 런타임은 `main`이라는 이름에 묶인 `IO ()` 값을 꺼내서 "실제로 실행"한다. GHCi에서는 편의상 최상위 프롬프트에 IO 액션을 입력하면 즉시 실행해 주기 때문에, 마치 `putStrLn`이 평범한 함수처럼 느껴질 수 있지만 내부적으로는 항상 "값을 만들고, 그 값을 실행한다"는 두 단계로 나뉘어 있다는 점을 기억해 두자.

```haskell
ghci> :type getLine
getLine :: IO String
```

`getLine`도 마찬가지다. `IO String`은 "실행하면 사용자로부터 한 줄을 입력받아 `String`을 돌려주는 계획"이다. 이렇게 `IO a`라는 타입은 "실행하면 부작용을 일으키고, 그 결과로 `a` 타입의 값을 내놓는 계획"이라고 일반화할 수 있다.

## `do` 표기법: IO 액션을 순서대로 엮기

계획이 하나뿐이면 편하지만, 실제 프로그램은 "입력받고 → 처리하고 → 출력하는" 여러 단계를 순서대로 이어 붙여야 한다. Haskell은 이를 위해 `do` 표기법을 제공한다.

```haskell
main :: IO ()
main = do
  putStrLn "이름을 입력하세요:"
  name <- getLine
  putStrLn ("안녕하세요, " ++ name ++ "!")
```

이 코드를 한 줄씩 읽어 보자.

1. `putStrLn "이름을 입력하세요:"` — 안내 문구를 출력하는 `IO ()` 액션을 실행한다.
2. `name <- getLine` — `getLine`이라는 `IO String` 액션을 실행하고, 그 결과로 나온 `String` 값을 `name`이라는 이름에 묶는다.
3. `putStrLn (...)` — `name`을 이용해 인사말을 만들고 출력한다.

여기서 `<-`가 하는 일이 중요하다. `<-`는 `let`처럼 이름을 값에 묶지만, 오른쪽이 `IO a` 타입의 액션일 때만 쓸 수 있고, "이 액션을 실행한 결과로 나온 `a` 타입 값을 이름에 묶는다"는 뜻이다. `name`에 묶이는 값은 `IO String`이 아니라 그 안에서 꺼낸 순수한 `String`이다. `do` 블록은 이렇게 여러 개의 `IO` 액션을 위에서 아래로 순서대로 실행하면서, 앞선 액션의 결과를 뒤따르는 액션에서 쓸 수 있게 이어 준다.

## `>>=`: `do` 표기법 뒤에 숨은 진짜 연산자

`do` 표기법은 사실 문법적 설탕(syntactic sugar)이다. 그 뒤에는 `>>=`(바인드, bind)라는 연산자가 숨어 있다. 타입을 먼저 보자.

```haskell
ghci> :type (>>=)
(>>=) :: Monad m => m a -> (a -> m b) -> m b
```

`>>=`는 "`m a` 타입의 액션과, `a` 값을 받아 `m b` 타입의 액션을 만들어내는 함수"를 받아서, 최종적으로 `m b` 타입의 액션 하나를 만들어낸다. 말로 풀면 "이 액션을 먼저 실행하고, 그 결과값으로 다음에 할 액션을 결정한다"는 뜻이다. 앞서 본 `do` 블록은 사실 이렇게 풀어 쓸 수 있다.

```haskell
main :: IO ()
main =
  putStrLn "이름을 입력하세요:" >>
  getLine >>= \name ->
    putStrLn ("안녕하세요, " ++ name ++ "!")
```

여기 등장하는 `>>`는 `>>=`의 사촌으로, "앞의 결과값은 필요 없고 그냥 순서만 이어 달라"는 뜻이다(`a >> b = a >>= \_ -> b`). 결과값이 필요할 때는 `>>=`와 람다(`\name -> ...`)를, 필요 없을 때는 `>>`를 쓴다. `do` 표기법은 이 `>>=`와 `>>`의 연쇄를 사람이 읽기 좋게 줄을 나눠 쓴 것일 뿐이다. 즉 다음 두 코드는 완전히 같은 프로그램이다.

```haskell
ghci> :type ( getLine >>= \name -> putStrLn ("안녕, " ++ name) )
getLine >>= \name -> putStrLn ("안녕, " ++ name) :: IO ()
```

## 14장과의 연결: 펑터 · 애플리커티브를 넘어서는 것

14장에서 펑터와 애플리커티브를 배웠다면, `>>=`의 타입이 낯설지 않을 것이다. 세 가지를 나란히 놓고 비교해 보자.

```haskell
fmap  ::            (a ->   b) -> f a -> f b
(<*>) ::          f (a ->   b) -> f a -> f b
(>>=) :: Monad m => m a -> (a -> m b) -> m b
```

`fmap`은 상자 밖의 평범한 함수를 상자 속 값에 적용한다. `<*>`는 함수까지 상자 속에 들어 있을 때, 상자 두 개를 나란히 결합한다. 그런데 이 둘은 공통적인 한계가 있다. 어떤 상자들을 어떤 순서로 결합할지가 **프로그램을 작성하는 시점에 이미 고정**되어 있다. 예를 들어 `f <$> action1 <*> action2`라고 쓰면, `action1`과 `action2`는 항상 둘 다 실행되고, `action2`가 어떤 값을 만들어낼지는 `action1`의 결과에 따라 달라질 수 없다.

`>>=`는 이 한계를 넘어선다. `a -> m b`라는 함수는 **이전 액션이 실제로 내놓은 값 `a`를 들여다보고**, 그 값에 따라 완전히 다른 다음 액션을 만들어낼 수 있다. 즉 모나드는 "다음에 무엇을 할지가 이전 결과에 동적으로 의존하는" 계산을 표현할 수 있다는 점에서 펑터·애플리커티브보다 한 단계 더 강력하다.

```haskell
main :: IO ()
main = do
  putStrLn "숫자를 입력하세요:"
  input <- getLine
  let n = read input :: Int
  if n > 0
    then putStrLn "양수를 입력했습니다."
    else putStrLn "0 또는 음수를 입력했습니다."
```

`getLine`으로 얻은 실제 문자열 값을 보기 전까지는, 다음에 어떤 `putStrLn`이 실행될지 아무도 알 수 없다. 이런 "실행 중에 결정되는 분기"는 `<*>`만으로는 표현할 수 없고, `>>=`(그리고 그 설탕인 `do`)가 있어야 가능하다. 실제로 GHC의 `Monad` 클래스는 `Applicative`를 상위 클래스로 두고 있어서, 모든 모나드는 자동으로 펑터이자 애플리커티브이기도 하다.

```haskell
class Applicative m => Monad m where
  (>>=) :: m a -> (a -> m b) -> m b
  return :: a -> m a
  return = pure
```

`return`은 `pure`의 다른 이름일 뿐이다(14장에서 본 `pure`를 떠올려 보자). "평범한 값을 상자 속에 그대로 넣기만 하는" 동작은 펑터·애플리커티브·모나드 모두에서 똑같이 필요하기 때문에, `Monad`는 `Applicative`의 `pure`를 그대로 물려받아 `return`이라는 이름으로도 쓸 수 있게 해 둔 것이다.

## `IO`만의 것이 아니다: `Maybe`도 모나드다

`>>=`는 `IO`만을 위한 특수 문법이 아니라, `Monad` 타입클래스를 구현한 모든 타입에서 똑같이 쓸 수 있는 범용 인터페이스다. 12장에서 다룬 `Maybe`도 모나드다.

```haskell
safeDivide :: Double -> Double -> Maybe Double
safeDivide _ 0 = Nothing
safeDivide x y = Just (x / y)

calc :: Double -> Double -> Double -> Maybe Double
calc a b c = do
  r1 <- safeDivide a b
  r2 <- safeDivide r1 c
  return r2
```

```haskell
ghci> calc 100 5 2
Just 10.0
ghci> calc 100 0 2
Nothing
```

`IO`의 `do` 블록에서는 "실행 순서"가, `Maybe`의 `do` 블록에서는 "실패 시 즉시 중단"이 자동으로 처리된다. `safeDivide a b`가 `Nothing`이면 `r1 <- ...`에서 바인딩이 실패하고, 뒤따르는 모든 계산이 건너뛰어지며 전체 결과가 `Nothing`이 된다. 겉모습은 `IO`와 똑같은 `do`와 `<-`이지만, 상자 종류(`IO` 대 `Maybe`)에 따라 "다음 줄로 넘어가는" 규칙이 다르게 정의되어 있을 뿐이다. 이 규칙을 정의하는 것이 바로 각 타입의 `Monad` 인스턴스다.

## 모나드는 결국 무엇인가: 실용적인 결론

지금까지의 내용을 한 문장으로 정리하면 이렇다. **모나드는 "상자 안에 든 값을 안전하게 꺼내 쓰면서, 그 값에 따라 다음에 할 일을 정할 수 있게 해 주는 방법"**이다. `IO`라는 상자는 "부작용이 아직 실행되지 않은 계획"을, `Maybe`라는 상자는 "값이 있을 수도, 없을 수도 있는 상태"를 담는다. 상자의 정체는 서로 다르지만, `>>=`와 `do` 표기법은 두 경우 모두에서 "상자를 열고, 값을 보고, 다음 상자를 결정한다"는 동일한 패턴을 제공한다.

여기서 안심해도 되는 점 하나. `IO` 액션은 오직 `do` 블록(또는 `>>=` 연쇄)으로 다른 `IO` 액션과 이어질 때만 실행될 기회를 얻고, 그 계획을 "몰래 풀어서" 순수한 값으로 빼낼 방법은 이 책의 범위 안에서는 없다. 한 번 `IO`에 발을 들이면, `main`까지 이어지는 `IO` 액션의 연쇄 안에 계속 머물러야 한다. 이 제약이 불편해 보일 수 있지만, 바로 이 제약 덕분에 함수의 타입 시그니처만 보고도 "이 함수가 부작용을 일으키는지 아닌지"를 항상 확신할 수 있다. `Int -> Int` 타입의 함수는 순수하다는 보장이 있고, `Int -> IO Int` 타입의 함수는 부작용이 있을 수 있다는 경고가 타입에 이미 적혀 있는 셈이다.

```text
do 표기법으로 연결된 IO 액션

+========================================================+
: 전체는 하나의 IO () 값 (main)                          :
:                                                         :
:  +---------------------------------------------+       :
:  | putStrLn "이름을 입력하세요:"                 |       :
:  | :: IO ()                                     |       :
:  +---------------------------------------------+       :
:                       |                                 :
:                       v  >> (결과 무시하고 순서만 이음)  :
:  +---------------------------------------------+        +----------------------+
:  | getLine                                      | ---->  | name :: String       |
:  | :: IO String                                 | name<- | (상자에서 꺼낸 값)   |
:  +---------------------------------------------+        +----------------------+
:                       |                                 :
:                       v  >>= (name 값을 다음 액션에 전달):
:  +---------------------------------------------+       :
:  | putStrLn ("안녕하세요, " ++ name ++ "!")     |       :
:  | :: IO ()                                     |       :
:  +---------------------------------------------+       :
:                       |                                 :
+========================================================+
                        v
        +-----------------------------------------+
        | runtime이 main을 실행 -> 실제 부작용 발생 |
        +-----------------------------------------+

각 상자는 "부작용을 수행하는 계획"이며, >>=/>>는 계획들을 순서대로 이어 붙인다.
```

## 요약

- Haskell 함수는 참조 투명해야 하지만, 실제 프로그램은 화면 출력 같은 부작용이 필요하다. `IO a` 타입은 "실행하면 부작용을 일으키고 `a` 타입 값을 내놓는 계획"을 순수한 값으로 표현한다.
- `do` 표기법은 `<-`를 이용해 여러 `IO` 액션을 순서대로 실행하고, 각 액션의 결과를 다음 줄에서 쓸 수 있게 이어 준다.
- `do` 표기법은 문법적 설탕이며, 실제로는 `>>=`(바인드)와 `>>` 연산자의 연쇄로 풀어 쓸 수 있다. `(>>=) :: Monad m => m a -> (a -> m b) -> m b`.
- 14장의 펑터(`fmap`)와 애플리커티브(`<*>`)는 상자 결합 구조가 미리 고정되어 있지만, 모나드의 `>>=`는 이전 액션의 실제 결과값을 보고 다음 액션을 동적으로 결정할 수 있다. `Monad`는 `Applicative`를 상위 클래스로 두며, `return`은 `pure`와 같다.
- `IO`뿐 아니라 `Maybe` 등 `Monad` 인스턴스를 가진 모든 타입에서 같은 `do`/`>>=` 패턴을 쓸 수 있다. 결국 모나드는 "상자 속 값을 안전하게 연결해서 다음 계산으로 넘기는 공통 방법"이라고 실용적으로 이해하면 충분하다.

2. 위에서 작성한 프로그램을 `do` 표기법 없이 `>>=`와 `>>`만으로 다시 작성하라.
3. `safeDivide`를 이용해 세 번 연속으로 나눗셈을 수행하는 함수를 `Maybe` 모나드의 `do` 표기법으로 작성하고, 중간에 0으로 나누는 경우와 그렇지 않은 경우를 각각 GHCi에서 실행해 결과를 확인하라.
4. 애플리커티브(`<*>`)로는 표현할 수 없고 모나드(`>>=`)가 있어야만 가능한 계산의 예를 하나 더 생각해 보고, 왜 `<*>`로는 안 되는지 설명해 보라.
5. `return`과 14장의 `pure`가 실제로 같은 동작을 하는지, GHCi에서 `:type return`과 `:type pure`를 비교해 확인해 보라.

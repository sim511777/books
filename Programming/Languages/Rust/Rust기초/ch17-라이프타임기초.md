9장에서 참조(reference)를 다루면서 빌림 검사기(borrow checker)가 두 가지 규칙, 즉 "같은 시점에 가변 참조는 하나만 존재할 수 있다"와 "가변 참조와 불변 참조는 동시에 존재할 수 없다"를 강제한다고 배웠다. 사실 빌림 검사기는 이 두 규칙 외에도 훨씬 근본적인 규칙 하나를 항상 지키고 있다. 바로 "참조는 그것이 가리키는 값보다 오래 살아있을 수 없다"는 규칙이다. 이번 장에서는 이 규칙이 왜 필요한지, 그리고 컴파일러가 이 규칙을 검증하기 위해 요구하는 라이프타임(lifetime) 표기가 무엇인지 살펴본다.

## 참조는 원본보다 오래 살 수 없다

참조란 결국 어떤 값이 메모리의 어디에 있는지를 가리키는 정보다. 그 값이 사라진 뒤에도 참조가 남아있다면, 그 참조는 이미 유효하지 않은 메모리를 가리키는 셈이 된다. 이런 참조를 댕글링 참조(dangling reference)라고 부른다. C나 C++에서는 댕글링 포인터를 통해 이미 해제된 메모리를 읽거나 쓰는 사고가 흔히 일어나지만, Rust는 이런 코드 자체를 컴파일 단계에서 거부한다.

다음 코드로 문제를 구체적으로 살펴보자.

```rust
fn main() {
    let reference_to_nothing = dangle();
    println!("{reference_to_nothing}");
}

fn dangle() -> &String {
    let s = String::from("hello");
    &s
}
```

`dangle` 함수는 함수 안에서 `String`을 만들고 그 참조를 반환하려 한다. 하지만 `s`는 `dangle` 함수의 지역 변수이므로, 함수가 끝나는 순간 8장에서 배운 소유권 규칙에 따라 드롭(drop)된다. 함수가 반환한 참조는 이미 사라진 값을 가리키는 댕글링 참조가 되어버린다. 이 코드는 컴파일되지 않으며, Rust 컴파일러는 다음과 같은 취지의 오류를 낸다.

```text
error[E0106]: missing lifetime specifier
 --> src/main.rs:6:17
  |
6 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value,
    but there is no value for it to be borrowed from
```

오류 메시지는 "빌려올 대상이 없다"는 점을 정확히 짚어준다. 이런 상황을 막으려면 애초에 참조가 아니라 값 자체(`String`)를 반환해서 소유권을 넘겨야 한다. 이 예제는 극단적으로 단순하지만, 실제로는 구조체나 함수가 복잡하게 얽혀 있어서 "이 참조가 원본보다 오래 살아있는지"를 사람이 눈으로 판단하기 어려운 경우가 많다. 라이프타임은 바로 이런 상황에서 컴파일러가 판단할 수 있도록 돕는 장치다.

## 라이프타임 표기는 새로운 규칙이 아니라 이미 있던 규칙의 이름표다

여기서 오해하기 쉬운 부분이 있다. `'a`처럼 생긴 라이프타임 표기를 처음 보면 "참조에 유효 기간을 부여하는 새로운 기능"처럼 느껴지기 쉽다. 하지만 그렇지 않다. 모든 참조에는 원래부터 유효한 범위, 즉 라이프타임이 존재한다. 변수가 스코프에 들어가는 순간부터 스코프를 벗어나는 순간까지가 그 변수의 라이프타임이고, 그 변수를 가리키는 참조는 최대한 그 범위 안에서만 유효할 수 있다. 이는 라이프타임이라는 이름을 붙이기 전부터 이미 참이었던 사실이다.

라이프타임 표기(`'a`, `'b`처럼 작은따옴표로 시작하는 이름)가 하는 일은 이 이미 존재하는 사실을 컴파일러에게 명시적으로 알려주는 것뿐이다. 대부분의 경우 컴파일러는 코드를 보고 참조들의 라이프타임 관계를 스스로 추론할 수 있다(이는 이 장의 뒷부분에서 다룬다). 하지만 함수의 매개변수와 반환값처럼, 함수 본문을 보지 않고 시그니처만으로는 참조들 사이의 관계를 판단할 수 없는 상황이 있다. 이럴 때 라이프타임 표기로 "이 참조들이 서로 얼마나 오래 유효해야 하는지"에 대한 관계를 명시적으로 적어줘야 한다. 3장에서 타입 표기(`: i32`)가 "이미 존재하는 값의 타입"을 명시적으로 적어주는 것과 비슷한 역할을 한다고 생각하면 이해하기 쉽다. 타입 표기가 새로운 타입을 만들어내지 않듯, 라이프타임 표기도 새로운 규칙을 만들어내지 않는다.

## 라이프타임이 필요한 예: 더 긴 문자열 슬라이스 반환하기

라이프타임 표기가 실제로 필요해지는 대표적인 예로, 두 문자열 슬라이스(10장 참고) 중 더 긴 쪽을 반환하는 함수를 만들어보자.

```rust
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

이 코드는 그대로 컴파일되지 않는다. 컴파일러는 다음과 같이 항의한다.

```text
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:33
  |
1 | fn longest(x: &str, y: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value,
    but the signature does not say whether it is borrowed from `x` or `y`
```

`longest` 함수 본문을 보면 `x`를 반환할 때도 있고 `y`를 반환할 때도 있다. 즉 반환되는 참조가 `x`의 라이프타임을 따라야 할지, `y`의 라이프타임을 따라야 할지가 실행 시점의 조건에 따라 달라진다. 함수 시그니처만 보는 컴파일러는 이 사실을 알 수 없다. 함수를 호출하는 쪽에서 `x`와 `y`가 서로 다른 스코프에 속해 있다면, 반환된 참조가 둘 중 먼저 사라지는 값을 가리키게 될 위험이 있다. 컴파일러는 이 위험을 확인할 방법이 없으니 아예 컴파일을 거부하는 것이다.

해결책은 라이프타임 매개변수를 도입해 두 매개변수와 반환값이 라이프타임을 공유한다고 명시하는 것이다.

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

`<'a>`는 제네릭 타입 매개변수(14장 참고)를 선언하는 `<T>`와 문법적으로 같은 자리에 라이프타임 매개변수를 선언한다. `x: &'a str`, `y: &'a str`, `-> &'a str`은 모두 같은 라이프타임 `'a`를 사용하는데, 이는 "반환되는 참조는 `x`와 `y`가 모두 유효한 기간 동안만 유효하다고 보장한다"는 뜻이다. 더 정확히 말하면, `'a`는 `x`와 `y`의 라이프타임 중 더 짧은 쪽으로 맞춰진다. 함수가 `x`를 반환하든 `y`를 반환하든, 반환된 참조는 두 입력이 모두 유효한 구간 안에서만 사용해도 안전하다는 것을 컴파일러가 보장할 수 있게 된다.

이제 라이프타임 규칙이 실제로 문제를 잡아내는 상황을 보자.

```rust
fn main() {
    let string1 = String::from("매우 긴 문자열입니다");
    let result;
    {
        let string2 = String::from("짧은 문자열");
        result = longest(string1.as_str(), string2.as_str());
    } // string2가 여기서 드롭된다

    println!("더 긴 문자열: {result}");
}
```

`string2`는 안쪽 블록이 끝나는 순간 드롭된다. `result`가 `string2`를 빌린 참조일 가능성이 있는데, `println!`은 그 이후 바깥 스코프에서 `result`를 사용한다. `longest`의 시그니처가 "반환값은 `x`와 `y`의 라이프타임 중 더 짧은 쪽을 따른다"고 약속했기 때문에, 컴파일러는 `result`의 라이프타임이 `string2`의 라이프타임을 넘어설 수 없다는 것을 알고 이 코드를 컴파일 오류로 처리한다. 만약 `longest`에 라이프타임 표기가 없었다면(즉 애초에 컴파일이 통과했다면), 이 오류는 런타임까지 발견되지 않았을 수도 있는 종류의 버그다. 라이프타임 표기 덕분에 이런 위험한 코드가 실행되기 전에, 심지어 함수를 정의하는 시점에 이미 걸러진다.

## 라이프타임 표기의 의미를 다시 짚기

라이프타임 매개변수 `'a`가 함수의 실행 속도나 동작을 바꾸는 것은 아니라는 점을 다시 강조할 필요가 있다. `longest` 함수는 라이프타임 표기가 있든 없든 정확히 같은 일을 한다(길이를 비교해서 더 긴 슬라이스를 반환한다). 라이프타임 표기가 하는 일은 오직 하나, 컴파일러에게 "이 참조들의 유효 기간이 서로 어떤 관계에 있는지"를 알려주는 것뿐이다. 컴파일러는 이 정보를 바탕으로 호출하는 쪽의 코드가 안전한지를 검증한다.

구조체가 참조를 필드로 가질 때도 같은 이유로 라이프타임 표기가 필요하다.

```rust
struct Excerpt<'a> {
    part: &'a str,
}
```

`Excerpt` 구조체는 `String`을 직접 소유하지 않고 어딘가의 문자열 슬라이스를 빌려서 `part` 필드에 저장한다(11장에서 다룬 구조체 문법의 연장이다). `'a`는 "`Excerpt` 인스턴스는 `part`가 빌려온 원본 문자열이 살아있는 동안만 유효하다"는 관계를 표현한다. 구조체와 메서드에 라이프타임을 본격적으로 활용하는 방법은 이 책의 범위를 벗어나므로 여기서는 "참조를 담는 구조체에도 같은 원리가 적용된다"는 정도만 기억해 두자.

## 라이프타임 생략 규칙: 대부분은 표기하지 않아도 된다

지금까지 본 예제 때문에 "참조를 매개변수나 반환값으로 쓸 때마다 라이프타임을 적어야 하나"라고 걱정할 수 있지만, 실제로는 그렇지 않다. Rust 컴파일러는 자주 나타나는 몇 가지 패턴에 대해 라이프타임을 자동으로 추론하는 규칙을 가지고 있다. 이를 라이프타임 생략(lifetime elision)이라 부른다. 대표적인 규칙은 다음과 같다.

- 참조 매개변수가 하나뿐이라면, 반환되는 참조의 라이프타임은 그 매개변수의 라이프타임을 따른다고 추론한다.
- 매개변수 중 `&self`나 `&mut self`가 있다면(13장에서 다룰 메서드), 반환되는 참조의 라이프타임은 `self`의 라이프타임을 따른다고 추론한다.

예를 들어 10장에서 다뤘던 것과 비슷한 함수를 보자.

```rust
fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(index) => &s[..index],
        None => &s[..],
    }
}
```

이 함수는 참조를 매개변수로 받고 참조를 반환하지만 라이프타임 표기가 전혀 없는데도 컴파일된다. 매개변수가 `s` 하나뿐이므로, 컴파일러는 "반환값은 `s`와 같은 라이프타임을 가진다"고 자동으로 판단하기 때문이다. `longest` 함수가 라이프타임 표기를 필요로 했던 이유는 매개변수가 둘이었고, 그중 어느 쪽의 라이프타임을 반환값이 따르는지 컴파일러가 스스로 결정할 수 없었기 때문이다. 즉 라이프타임 표기는 "컴파일러가 애매함 없이 추론할 수 있는 상황"에서는 생략되고, "여러 참조 중 무엇을 기준으로 삼아야 하는지 애매한 상황"에서만 명시적으로 요구된다.

## 참고: 'static 라이프타임

가끔 오류 메시지나 다른 사람의 코드에서 `'static`이라는 특별한 라이프타임을 보게 될 수도 있다. `'static`은 프로그램이 실행되는 전체 기간 동안 유효한 참조를 뜻한다. 문자열 리터럴(`"hello"`처럼 코드에 직접 쓴 문자열)은 프로그램의 바이너리에 새겨져 있으므로 항상 `'static` 라이프타임을 가진다.

```rust
let s: &'static str = "이 문자열은 프로그램이 끝날 때까지 유효하다";
```

컴파일러가 라이프타임 오류를 낼 때 "`'static`을 붙이면 해결되지 않을까"라는 유혹을 느끼기 쉽지만, 대부분의 경우 이는 근본적인 해결책이 아니라 문제를 가리는 임시방편이다. 참조의 실제 라이프타임이 함수 전체나 프로그램 전체만큼 길지 않은데도 억지로 `'static`을 강제하면, 오히려 코드의 구조가 왜곡되는 경우가 많다. 라이프타임 오류를 만났을 때는 먼저 "이 참조가 실제로 어디까지 유효해야 하는가"를 다시 생각해보는 것이 바람직하다.

## 요약

- 참조는 그것이 가리키는 값보다 오래 살아있을 수 없으며, Rust 컴파일러는 이 규칙을 컴파일 시점에 검증해 댕글링 참조를 원천적으로 막는다.
- 라이프타임 표기(`'a`)는 새로운 규칙을 만드는 것이 아니라, 참조들 사이에 이미 존재하는 유효 기간 관계를 컴파일러에게 명시적으로 알려주는 주석이다.
- 함수가 여러 참조를 받아 그중 하나를 반환할 수 있는 경우처럼, 반환값의 라이프타임이 어느 매개변수를 따르는지 컴파일러가 스스로 판단할 수 없을 때 라이프타임 표기가 필요하다.
- `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`처럼 매개변수와 반환값에 같은 라이프타임을 부여하면, 반환된 참조가 두 입력 중 더 짧게 사는 쪽보다 오래 사용되지 않도록 컴파일러가 보장한다.
- 라이프타임 생략 규칙 덕분에 대부분의 함수는 라이프타임을 표기하지 않아도 컴파일러가 자동으로 추론한다. 표기가 필요한 경우는 컴파일러가 여러 참조 중 무엇을 기준으로 삼아야 하는지 애매할 때뿐이다.
- `'static`은 프로그램 전체 기간 동안 유효한 특별한 라이프타임이지만, 라이프타임 오류를 해결하는 만능 도구로 남용해서는 안 된다.

## 연습문제

1. 다음 함수가 컴파일되지 않는 이유를 설명하고, 라이프타임 표기를 추가해 컴파일되도록 수정하라.

   ```rust
   fn first_or(s: &str, default: &str) -> &str {
       if s.is_empty() {
           default
       } else {
           s
       }
   }
   ```

2. 이 장의 `dangle` 함수 예제를 컴파일 오류가 나지 않도록 직접 고쳐 보라. 참조 대신 무엇을 반환해야 하는지, 그리고 그 이유를 8장의 소유권 개념과 연결해 설명하라.
3. 매개변수가 하나뿐인데도 라이프타임 표기 없이 참조를 반환할 수 있는 함수를 하나 작성하고, 어떤 라이프타임 생략 규칙이 적용되는지 설명하라.
4. `longest` 함수를 호출하는 코드에서, 두 인자 중 하나가 먼저 스코프를 벗어나 컴파일 오류가 발생하는 예제를 직접 작성해 보고, 오류 메시지를 읽어 어떤 참조의 라이프타임이 문제가 되었는지 확인하라.
5. `&'static str`과 일반적인 `&str`의 차이를 자신의 말로 설명하고, `'static`을 남용했을 때 어떤 문제가 생길 수 있는지 예를 들어보라.

## 들어가며

목록에서 가장 큰 값을 찾는 함수를 작성해 보자. 정수 목록이라면 다음과 같이 쓸 수 있다.

```rust
fn largest_i32(list: &[i32]) -> &i32 {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

그런데 실수(`f64`) 목록에서도 가장 큰 값을 찾아야 한다면 어떻게 할까? 함수를 그대로 복사해서 타입만 `f64`로 바꾼 `largest_f64`를 또 만들어야 한다. 문자(`char`) 목록, 문자열(`String`) 목록에도 같은 로직이 필요하다면 똑같은 코드를 계속 복제해야 한다. 로직은 완전히 동일한데 타입만 다르다는 이유로 함수를 몇 번이나 다시 쓰는 것은 명백한 낭비이고, 나중에 로직을 수정해야 할 때 모든 복사본을 일일이 찾아 고쳐야 하는 유지보수 문제로 이어진다.

Rust는 이 문제를 제네릭(generic)으로 해결한다. 제네릭은 "타입을 나중에 결정할 변수처럼 다루는" 기능이다. 함수나 구조체를 작성할 때 구체적인 타입 대신 타입 매개변수(type parameter)를 써 두면, 컴파일러가 실제로 그 함수나 구조체가 쓰이는 시점에 알맞은 타입을 채워 넣는다.

## 제네릭 함수

타입 매개변수는 관례적으로 대문자 한 글자, 흔히 `T`(Type의 첫 글자)를 사용한다. 함수 이름 뒤에 `<T>`를 붙여 선언하고, 매개변수나 반환값의 타입 자리에 `T`를 그대로 쓴다.

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn main() {
    let numbers = vec![34, 50, 25, 100, 65];
    println!("가장 큰 정수: {}", largest(&numbers));

    let chars = vec!['y', 'm', 'a', 'q'];
    println!("가장 큰 문자: {}", largest(&chars));
}
```

이제 `largest` 함수는 단 하나만 존재하지만, `i32` 목록에도 `char` 목록에도 그대로 쓸 수 있다. 여기서 `<T: PartialOrd>` 부분을 눈여겨보자. `T`라는 타입이 있다고만 선언하면, 함수 본문에서 `item > largest`처럼 `>` 연산자로 비교하는 코드가 컴파일되지 않는다. 컴파일러는 "`T`가 어떤 타입인지 모르는데, 그 타입에 `>` 연산이 정의되어 있는지 어떻게 아느냐"고 반문한다. `PartialOrd`는 13장에서 배운 트레이트로, `<`, `>` 같은 비교 연산을 지원한다는 것을 보장하는 표준 라이브러리 트레이트다. `T: PartialOrd`라고 트레이트 바운드(trait bound)를 걸어 주면, "이 함수는 비교 가능한 타입만 받는다"는 제약이 생기고, 그 대신 함수 본문에서 비교 연산자를 마음 놓고 쓸 수 있게 된다.

트레이트 바운드는 제네릭의 자유로움과 안전성을 동시에 지켜 주는 핵심 장치다. 제약이 없다면 컴파일러는 `T` 자리에 어떤 타입이 들어올지 전혀 예측할 수 없어 본문의 연산을 검증할 수 없고, 제약이 있으면 "이 트레이트가 보장하는 동작만 쓰겠다"는 약속이 성립되어 컴파일러가 안전하게 코드를 검증할 수 있다.

## 제네릭 구조체

구조체도 필드의 타입을 제네릭으로 선언할 수 있다. 좌표를 표현하는 `Point` 구조체를 만들어 보자.

```rust
struct Point<T> {
    x: T,
    y: T,
}

fn main() {
    let integer_point = Point { x: 5, y: 10 };
    let float_point = Point { x: 1.5, y: 4.2 };
}
```

`Point<T>`는 `x`와 `y`가 항상 같은 타입이어야 한다는 제약이 있다. `Point { x: 5, y: 4.2 }`처럼 정수와 실수를 섞으면 컴파일 오류가 발생한다. 만약 두 필드가 서로 다른 타입을 가져도 되게 하려면, 타입 매개변수를 두 개 선언하면 된다.

```rust
struct Point<T, U> {
    x: T,
    y: U,
}

fn main() {
    let mixed = Point { x: 5, y: 4.2 };
}
```

제네릭 구조체에 메서드를 붙일 때는 `impl` 뒤에도 타입 매개변수를 선언해야 한다.

```rust
impl<T> Point<T, T> {
    fn x(&self) -> &T {
        &self.x
    }
}
```

11장에서 구조체에 메서드를 붙이던 문법(`impl Point { ... }`)과 거의 같지만, `impl<T>`처럼 타입 매개변수를 먼저 선언해 준다는 점만 다르다.

## 트레이트 바운드로 조건에 따라 다르게 구현하기

제네릭 구조체에 특정 트레이트 바운드를 만족할 때만 사용할 수 있는 메서드를 추가할 수도 있다. 예를 들어 `Point<T>`의 값을 화면에 보기 좋게 출력하는 메서드는, `T`가 13장에서 다룬 `std::fmt::Display` 트레이트를 구현했을 때만 의미가 있다.

```rust
use std::fmt::Display;

struct Point<T> {
    x: T,
    y: T,
}

// T가 Display를 구현한 경우에만 이 메서드를 사용할 수 있다
impl<T: Display> Point<T> {
    fn show(&self) {
        println!("({}, {})", self.x, self.y);
    }
}
```

이렇게 하면 `Point<i32>`나 `Point<f64>`처럼 `Display`를 구현한 타입으로 만든 `Point`는 `show()`를 호출할 수 있지만, `Display`를 구현하지 않은 타입으로 만든 `Point`는 `show()` 메서드 자체가 존재하지 않는 것처럼 취급되어 호출 시 컴파일 오류가 난다. 이런 식으로 트레이트 바운드는 함수뿐 아니라 구조체의 메서드 구현 범위도 정밀하게 제어할 수 있다.

## 여러 트레이트 바운드와 where절

트레이트 바운드가 여러 개 필요하면 13장에서 본 것처럼 `+`로 이어 쓴다.

```rust
fn largest_clone<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

여기서는 값을 복사해서 반환하기 위해 `Copy` 트레이트도 함께 요구했다. 바운드가 늘어나 함수 시그니처가 길어지면, `where`절로 옮겨 적을 수도 있다.

```rust
fn largest_clone<T>(list: &[T]) -> T
where
    T: PartialOrd + Copy,
{
    let mut largest = list[0];
    for &item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}
```

두 표기법은 동작이 완전히 같고, 바운드가 짧으면 `<T: ...>` 형태가, 여러 타입 매개변수에 여러 바운드가 얽히면 `where`절이 가독성 면에서 더 낫다.

## 성능에 대한 오해

"타입이 나중에 결정된다"는 설명을 들으면 실행 속도가 느려지지 않을까 걱정할 수 있다. 하지만 Rust의 제네릭은 런타임에 타입을 검사하는 방식이 아니다. 컴파일러는 `largest::<i32>`, `largest::<char>`처럼 실제로 쓰인 각 타입에 맞춰 전용 코드를 컴파일 시점에 생성한다. 이 과정을 단일화(monomorphization)라 부른다. 그 결과 제네릭으로 작성한 코드는 애초에 각 타입별로 함수를 직접 복제해서 작성했을 때와 실행 속도가 동일하다. 코드는 한 번만 작성하고, 성능은 손해 보지 않는 것이다.

## Option과 Result, 이미 만나 본 제네릭 열거형

여기까지 왔다면, 사실 이 책은 처음부터 제네릭을 계속 사용하고 있었다는 것을 눈치챘을 수도 있다. 12장에서 배운 `Option<T>`는 이름에 이미 `<T>`가 들어 있는 제네릭 열거형이다.

```rust
enum Option<T> {
    Some(T),
    None,
}
```

`Option<i32>`는 `T`가 `i32`로 채워진 것이고, `Option<String>`은 `T`가 `String`으로 채워진 것뿐이다. 값이 있을 수도 없을 수도 있는 상황을 표현하는 이 하나의 열거형이, 어떤 타입에도 적용될 수 있는 이유가 바로 제네릭이다.

`Result<T, E>` 역시 마찬가지다. 이 타입은 15장에서 본격적으로 다룰 에러 처리의 핵심인데, 타입 매개변수를 두 개 받는 제네릭 열거형이다.

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

성공했을 때 돌려줄 값의 타입 `T`와 실패했을 때 돌려줄 에러의 타입 `E`를 각각 독립적으로 지정할 수 있다. 예를 들어 파일을 읽는 함수는 `Result<String, std::io::Error>`를, 문자열을 숫자로 변환하는 함수는 `Result<i32, std::num::ParseIntError>`를 반환하는 식이다. 만약 제네릭이 없었다면 표준 라이브러리는 상황마다 `IntResult`, `StringResult`, `FileResult` 같은 열거형을 무한히 만들어야 했을 것이다. 제네릭 덕분에 단 하나의 `Result<T, E>` 정의로 이 모든 경우를 표현할 수 있다.

## 요약

- 제네릭은 타입을 매개변수(`T`)로 다뤄, 동일한 로직을 여러 타입에 대해 중복 작성하지 않게 해 준다.
- 제네릭 함수는 `fn 함수명<T>(...)` 형태로 선언하며, 본문에서 특정 연산(비교, 복사 등)을 쓰려면 `T: 트레이트명` 형태의 트레이트 바운드로 제약을 걸어야 한다.
- 제네릭 구조체는 `struct 이름<T> { ... }`로 선언하고, 메서드를 붙일 때는 `impl<T> 이름<T> { ... }` 형태를 쓴다.
- 트레이트 바운드를 만족할 때만 특정 메서드를 제공하도록 조건부로 구현할 수 있으며, 바운드가 여러 개면 `+`나 `where`절로 표현한다.
- 제네릭은 컴파일 시점에 단일화(monomorphization)를 거치므로 런타임 성능 손실이 없고, `Option<T>`와 `Result<T, E>`가 바로 제네릭 열거형의 대표적인 예다.

## 연습문제

1. `largest` 함수를 참고해, 목록에서 가장 작은 값을 반환하는 제네릭 함수 `smallest<T: PartialOrd>(list: &[T]) -> &T`를 작성해 보라.
2. `Point<T, U>` 구조체에 `mixup<V, W>(self, other: Point<V, W>) -> Point<T, W>` 메서드를 추가해, 두 `Point`의 `x`, `y`를 섞은 새로운 `Point`를 만들어 보라.
3. 13장에서 만든 `Shape` 트레이트를 다시 가져와, `fn largest_area<T: Shape>(shapes: &[T]) -> &T`처럼 트레이트 바운드를 이용해 넓이가 가장 큰 도형을 찾는 제네릭 함수를 작성해 보라.
4. `impl<T: Display> Point<T>`에 `show` 메서드를 추가한 예제를 그대로 컴파일해 보고, `Display`를 구현하지 않은 타입(예: 아무 트레이트도 구현하지 않은 사용자 정의 구조체)으로 `Point`를 만들어 `show()`를 호출했을 때 어떤 오류 메시지가 나오는지 확인해 보라.
5. `Option<T>`와 `Result<T, E>`가 왜 각각 타입 매개변수를 하나, 두 개 받는지 본문의 설명을 바탕으로 자신의 언어로 설명해 보라.

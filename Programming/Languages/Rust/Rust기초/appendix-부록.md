이 부록은 본문에서 이미 설명한 내용을 다시 찾아보기 쉽도록 정리한 참고 자료다. 새로운 개념을 설명하지는 않으며, 자주 쓰는 `cargo` 명령어와 표준 라이브러리 타입/메서드를 한곳에 모아두는 것이 목적이다.

## cargo 명령어 치트시트

2장에서 `cargo`로 프로젝트를 만들고 빌드하는 기본적인 흐름을 다뤘다. 여기서는 그때 다룬 명령어와, 이후 장에서 자연스럽게 등장했던 명령어들을 함께 정리한다.

| 명령어 | 설명 |
| --- | --- |
| `cargo new 프로젝트명` | 새 프로젝트를 생성한다. `Cargo.toml`과 `src/main.rs`가 만들어진다. |
| `cargo new 프로젝트명 --lib` | 실행 파일이 아니라 라이브러리 크레이트로 프로젝트를 생성한다. |
| `cargo build` | 프로젝트를 빌드한다. 결과물은 `target/debug`에 생성된다. |
| `cargo build --release` | 최적화를 적용해 빌드한다. 결과물은 `target/release`에 생성되며, 실행 속도는 빠르지만 빌드 시간이 더 길다. |
| `cargo run` | 빌드하고 곧바로 실행한다. 개발 중에는 이 명령어를 가장 자주 쓴다. |
| `cargo check` | 실제로 실행 파일을 만들지 않고 컴파일 오류만 빠르게 확인한다. `cargo build`보다 훨씬 빠르다. |
| `cargo test` | `#[test]`가 붙은 테스트 함수들을 모두 실행한다. |
| `cargo add 크레이트명` | `Cargo.toml`의 `[dependencies]`에 의존성을 추가한다(아래 "크레이트 생태계" 절 참고). |
| `cargo remove 크레이트명` | 의존성을 제거한다. |
| `cargo fmt` | 코드를 표준 스타일로 자동 정렬한다(18장 참고). |
| `cargo clippy` | 관용적이지 않은 코드 패턴을 찾아 경고해준다(18장 참고). |
| `cargo doc --open` | 프로젝트와 의존 크레이트의 문서를 생성해 브라우저로 연다. |

개발 중에는 `cargo check`로 자주 오류를 확인하고, 실제로 실행해봐야 할 때만 `cargo run`을 쓰는 것이 빠른 반복 작업에 도움이 된다. 배포하거나 성능을 측정할 때는 반드시 `cargo build --release`나 `cargo run --release`로 최적화된 결과물을 사용해야 한다. 디버그 빌드는 최적화가 거의 없어 실행 속도가 눈에 띄게 느리다.

## 크레이트 생태계와 Cargo.toml

Rust 표준 라이브러리는 의도적으로 작게 유지되어 있다. HTTP 요청을 보내거나, JSON을 파싱하거나, 무작위 수를 생성하는 기능은 표준 라이브러리에 포함되어 있지 않다. 대신 이런 기능들은 크레이트(crate)라는 단위의 외부 라이브러리로 제공되며, [crates.io](https://crates.io)라는 공개 저장소에 누구나 자신이 만든 크레이트를 올릴 수 있다. 2장에서 만든 프로젝트 자체도 하나의 크레이트이고, 프로젝트가 의존하는 외부 라이브러리들도 각각 크레이트다.

프로젝트에 크레이트를 추가하는 가장 쉬운 방법은 `cargo add` 명령어를 쓰는 것이다.

```bash
cargo add rand
```

이 명령어는 `Cargo.toml`의 `[dependencies]` 항목에 다음과 같은 줄을 자동으로 추가한다.

```toml
[dependencies]
rand = "0.8"
```

버전 번호 `"0.8"`은 시맨틱 버저닝(semantic versioning, semver) 규칙을 따른다. `"0.8"`이라고 적으면 `0.8.0` 이상, `0.9.0` 미만의 호환 가능한 버전 중 가장 최신 버전을 사용한다는 뜻이다. 즉 버그 수정이나 사소한 기능 추가는 자동으로 받아들이지만, 호환성을 깨뜨릴 수 있는 큰 변경(`0.9`나 `1.0`으로의 이동)은 자동으로 받아들이지 않는다.

`cargo build`나 `cargo run`을 실행하면 `Cargo.toml`에 적힌 의존성을 실제로 어떤 정확한 버전으로 사용할지 계산해 `Cargo.lock` 파일에 기록한다. `Cargo.lock`은 "이번에 빌드했을 때 정확히 이 버전들을 썼다"는 기록이므로, 이 파일을 함께 커밋해두면 다른 컴퓨터에서 같은 프로젝트를 빌드할 때도 동일한 버전의 의존성을 사용하게 되어 "내 컴퓨터에서는 되는데" 하는 문제를 줄일 수 있다.

의존성을 추가한 뒤에는 `use` 문으로 크레이트의 기능을 가져와 쓴다.

```rust
use rand::Rng;

fn main() {
    let mut rng = rand::thread_rng();
    let n: u32 = rng.gen_range(1..=100);
    println!("난수: {n}");
}
```

크레이트를 고를 때는 다운로드 수, 최근 업데이트 시점, 문서화 수준을 함께 살펴보는 것이 좋다. crates.io의 각 크레이트 페이지는 문서 링크와 함께 이런 정보를 보여준다.

## 표준 라이브러리 타입/메서드 치트시트

10장(슬라이스와 문자열), 15장(에러 처리), 16장(컬렉션)에서 다룬 핵심 타입들의 자주 쓰는 메서드를 모아 정리한다. 정확한 동작이나 전체 메서드 목록은 표준 라이브러리 문서에서 확인하는 것이 가장 정확하다.

### String

| 메서드/문법 | 설명 |
| --- | --- |
| `String::new()` | 빈 문자열을 만든다. |
| `String::from("텍스트")` | 문자열 리터럴로부터 `String`을 만든다. |
| `s.push_str("추가")` | 뒤에 문자열 슬라이스를 이어붙인다. |
| `s.push('c')` | 뒤에 문자 하나를 이어붙인다. |
| `s.len()` | 바이트 단위 길이를 반환한다(문자 개수가 아니다). |
| `s.is_empty()` | 길이가 0인지 확인한다. |
| `s.trim()` | 앞뒤 공백을 제거한 슬라이스를 반환한다. |
| `s.split(",")` | 구분자로 나눈 슬라이스들의 이터레이터를 반환한다. |
| `s.contains("부분")` | 부분 문자열을 포함하는지 확인한다. |
| `s.replace("old", "new")` | 부분 문자열을 치환한 새 `String`을 반환한다. |
| `s.to_string()` | `&str`이나 다른 `Display` 타입을 `String`으로 변환한다. |
| `format!("{a}와 {b}")` | 여러 값을 조합해 새 `String`을 만든다. |
| `s.chars()` | 문자(char) 단위로 순회하는 이터레이터를 반환한다. |

### Vec\<T\>

| 메서드/문법 | 설명 |
| --- | --- |
| `Vec::new()` | 빈 벡터를 만든다. |
| `vec![1, 2, 3]` | 초기값을 가진 벡터를 만드는 매크로. |
| `v.push(값)` | 끝에 요소를 추가한다. |
| `v.pop()` | 마지막 요소를 꺼낸다. `Option<T>`를 반환한다. |
| `v.len()` | 요소 개수를 반환한다. |
| `v.is_empty()` | 비어 있는지 확인한다. |
| `v.get(인덱스)` | 인덱스에 해당하는 요소를 `Option<&T>`로 반환한다(범위를 벗어나도 패닉하지 않는다). |
| `v[인덱스]` | 인덱스로 직접 접근한다(범위를 벗어나면 패닉한다). |
| `v.iter()` | 요소를 빌려서 순회하는 이터레이터를 반환한다. |
| `v.sort()` | 요소를 정렬한다(요소 타입이 `Ord`를 구현해야 한다). |
| `v.contains(&값)` | 특정 값을 포함하는지 확인한다. |
| `Vec::with_capacity(n)` | 미리 용량을 확보한 빈 벡터를 만든다(반복적인 재할당을 줄여 성능에 도움이 된다). |

### Option\<T\>

| 메서드/문법 | 설명 |
| --- | --- |
| `Some(값)` / `None` | 값이 있음/없음을 나타내는 두 가지 값. |
| `opt.is_some()` / `opt.is_none()` | 값이 있는지/없는지 확인한다. |
| `opt.unwrap()` | 값을 꺼낸다. `None`이면 패닉한다(18장에서 남용을 피하라고 다룬 메서드). |
| `opt.unwrap_or(기본값)` | 값이 있으면 그 값을, 없으면 기본값을 반환한다. |
| `opt.unwrap_or_else(\|\| 계산())` | 값이 없을 때 대신 실행할 클로저를 지정한다. |
| `opt.map(\|v\| 변환)` | 값이 있으면 변환을 적용한 새 `Option`을 반환하고, 없으면 `None`을 그대로 유지한다. |
| `opt.and_then(\|v\| 다른_Option)` | 값이 있으면 다른 `Option`을 반환하는 함수를 연쇄적으로 적용한다. |
| `opt?` | 함수가 `Option`을 반환할 때, `None`이면 즉시 `None`을 반환하고 아니면 값을 꺼낸다. |

### Result\<T, E\>

| 메서드/문법 | 설명 |
| --- | --- |
| `Ok(값)` / `Err(에러)` | 성공/실패를 나타내는 두 가지 값. |
| `res.is_ok()` / `res.is_err()` | 성공했는지/실패했는지 확인한다. |
| `res.unwrap()` | 성공값을 꺼낸다. `Err`이면 패닉한다. |
| `res.expect("메시지")` | `unwrap`과 같지만 패닉 메시지를 직접 지정한다. |
| `res.unwrap_or(기본값)` | 성공하면 값을, 실패하면 기본값을 반환한다. |
| `res.map(\|v\| 변환)` | 성공값에 변환을 적용한다. 실패값은 그대로 둔다. |
| `res.map_err(\|e\| 변환)` | 실패값에 변환을 적용한다. 성공값은 그대로 둔다. |
| `res?` | 함수가 `Result`를 반환할 때, `Err`이면 즉시 그 에러를 반환하고 아니면 값을 꺼낸다(18장에서 권장한 에러 전파 방식). |

## 참고할 만한 자료 유형

이 책은 Rust의 기초 문법과 소유권 모델을 다루는 데 집중했다. 더 깊이 파고들고 싶을 때는 다음과 같은 유형의 자료를 참고하면 도움이 된다.

- **Rust 공식 문서**: 언어 자체의 표준 문서와 표준 라이브러리 레퍼런스는 각 타입과 메서드의 정확한 동작을 확인할 수 있는 가장 신뢰도 높은 출처다. 이 부록의 표준 라이브러리 치트시트에서 확실하지 않은 부분이 있다면 공식 문서에서 함수 시그니처와 예제를 직접 확인하는 습관을 들이자.
- **Cargo 공식 가이드**: 크레이트 의존성 관리, 워크스페이스(workspace) 구성, 빌드 설정(profile) 등 이 부록에서 다루지 못한 `cargo`의 고급 기능을 다룬다.
- **크레이트 문서(docs.rs)**: crates.io에 등록된 크레이트는 대부분 자동으로 API 문서 사이트에 등록된다. 새로운 크레이트를 쓰기 전에 이 문서에서 예제와 타입 시그니처를 확인하는 것이 좋은 습관이다.
- **컴파일러 오류 메시지 자체**: Rust 컴파일러는 오류의 원인과 종종 수정 방법까지 함께 제시한다. `rustc --explain 오류코드` 명령어로 특정 오류 코드(예: `E0106`)에 대한 더 자세한 설명을 터미널에서 바로 확인할 수도 있다.
- **커뮤니티 포럼과 채팅**: Rust 사용자 커뮤니티는 질문에 답을 얻기 좋을 만큼 활발하다. 막힌 문제를 검색하거나 질문을 올릴 때는, 문제를 재현할 수 있는 최소한의 코드와 함께 정확한 오류 메시지를 첨부하면 더 빠르고 정확한 도움을 받을 수 있다.

이 책에서 다룬 소유권(8장), 빌림(9장), 트레이트(13장), 제네릭(14장), 에러 처리(15장), 라이프타임(17장)의 개념을 확실히 이해하고 나면, 위 자료들을 읽을 때 등장하는 용어와 코드가 훨씬 익숙하게 느껴질 것이다.

# 9장. 빌림(Borrowing)과 참조

8장에서 우리는 Rust의 소유권 규칙을 배웠습니다. 값은 항상 하나의 변수가 소유하며, 그 변수를 다른 변수에 대입하거나 함수에 넘기면 소유권이 이동(move)한다는 것이었습니다. 이 규칙은 메모리 안전성을 보장해주지만, 실제로 코드를 작성해보면 조금 불편한 상황을 자주 만나게 됩니다. 어떤 값의 내용을 잠깐 살펴보거나 수정만 하고 싶을 뿐인데, 매번 소유권을 넘기고 다시 돌려받아야 한다면 코드가 번거로워집니다. 이번 장에서는 이 문제를 해결해주는 개념인 **빌림(borrowing)**과 **참조(reference)**를 다룹니다.

## 소유권 이동 없이 값을 사용하고 싶을 때

다음 코드를 봅시다. 문자열의 길이를 계산하는 함수에 문자열을 넘긴 뒤, 그 문자열을 다시 사용하려고 합니다.

```rust
fn calculate_length(s: String) -> (String, usize) {
    let length = s.len();
    (s, length) // 사용이 끝난 소유권을 다시 돌려줘야 한다
}

fn main() {
    let s1 = String::from("hello");
    let (s1, len) = calculate_length(s1);
    println!("'{}'의 길이는 {}입니다.", s1, len);
}
```

`calculate_length` 함수는 문자열의 길이만 알아내면 되는데, 소유권까지 넘겨받는 바람에 다 쓴 값을 다시 튜플로 돌려줘야 합니다. 함수를 호출할 때마다 이렇게 값을 되돌려받는 방식은 코드를 지저분하게 만듭니다. Rust는 이 문제를 위해 값의 소유권은 그대로 두고, 잠시 "빌려서" 사용할 수 있는 방법을 제공합니다. 그것이 바로 참조입니다.

## 참조란 무엇인가

참조는 값의 소유권을 가져오지 않고 그 값을 가리키는 방법입니다. 앰퍼샌드(`&`)를 사용해서 만듭니다. 위 예제를 참조를 사용해 다시 작성하면 다음과 같습니다.

```rust
fn calculate_length(s: &String) -> usize {
    s.len() // 참조를 통해 값을 읽기만 한다
}

fn main() {
    let s1 = String::from("hello");
    let len = calculate_length(&s1); // s1의 소유권은 그대로 main에 남는다
    println!("'{}'의 길이는 {}입니다.", s1, len);
}
```

`&s1`은 "`s1`을 빌려온다"는 뜻입니다. `calculate_length` 함수는 `s1`이 가리키는 문자열 데이터에 접근할 수 있지만, 그 데이터를 소유하지는 않습니다. 함수가 끝나도 `s1`은 여전히 `main`의 것이며, 아무것도 drop되지 않습니다. 이렇게 참조를 만드는 행위를 **빌림(borrowing)**이라고 부릅니다. 도서관에서 책을 빌리는 것과 비슷합니다. 잠시 빌려서 읽어보고, 소유권은 원래 주인에게 그대로 남겨둔 채 돌려주는 것입니다.

## 불변 참조: 읽기만 가능한 빌림

앞서 만든 `&s1`은 **불변 참조(immutable reference)**입니다. 참조를 통해서는 값을 읽을 수만 있고 수정할 수는 없습니다. 불변 참조의 중요한 특징은 **동시에 여러 개를 만들 수 있다**는 점입니다.

```rust
fn main() {
    let s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    let r3 = &s;

    // 세 참조 모두 동시에 s를 읽을 수 있다
    println!("{}, {}, {}", r1, r2, r3);
}
```

여러 사람이 도서관에서 같은 책의 복사본을 동시에 읽는다고 생각하면 됩니다. 아무도 내용을 바꾸지 않는다면 여러 명이 동시에 읽어도 문제가 없습니다.

## 가변 참조: 값을 바꿀 수 있는 빌림

값을 읽는 것뿐만 아니라 수정까지 하고 싶다면 **가변 참조(mutable reference)**를 사용합니다. `&mut` 키워드로 만듭니다.

```rust
fn append_world(s: &mut String) {
    s.push_str(", world"); // 빌려온 값을 실제로 수정한다
}

fn main() {
    let mut s = String::from("hello");
    append_world(&mut s);
    println!("{}", s); // "hello, world"
}
```

가변 참조를 만들려면 원본 변수 역시 `mut`으로 선언되어 있어야 합니다. `s`가 불변이었다면 `&mut s`는 컴파일 오류가 됩니다. 이는 자연스러운 규칙입니다. 원래 변경할 수 없는 값을 참조를 통해서 몰래 변경할 수 있다면 불변성의 의미가 없어지기 때문입니다.

## 빌림 규칙: 데이터 경쟁을 막는 장치

여기까지는 자연스러워 보이지만, Rust는 가변 참조에 대해 훨씨 엄격한 규칙을 하나 더 둡니다.

> 어떤 값에 대해 가변 참조가 존재하는 동안에는, 그 값에 대한 다른 참조(가변이든 불변이든)를 동시에 만들 수 없다.

정리하면 다음 두 가지로 요약할 수 있습니다.

- 같은 값에 대해 **가변 참조는 동시에 최대 하나만** 존재할 수 있다.
- **가변 참조와 불변 참조는 동시에 존재할 수 없다.** (불변 참조는 여러 개 존재해도 괜찮다.)

이 규칙을 위반하는 코드를 직접 작성해서 컴파일러가 어떻게 반응하는지 살펴봅시다.

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &mut s;
    let r2 = &mut s; // 오류: s를 두 번 이상 가변으로 빌릴 수 없다

    println!("{}, {}", r1, r2);
}
```

이 코드를 컴파일하면 다음과 비슷한 오류가 발생합니다.

```text
error[E0499]: cannot borrow `s` as mutable more than once at a time
```

가변 참조와 불변 참조를 섞어도 마찬가지로 오류가 납니다.

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;     // 불변 참조 - 문제 없음
    let r2 = &s;     // 불변 참조 - 여러 개라도 문제 없음
    let r3 = &mut s; // 오류: r1, r2가 살아있는 동안 가변 참조를 만들 수 없다

    println!("{}, {}, {}", r1, r2, r3);
}
```

```text
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
```

왜 이렇게까지 엄격할까요? 답은 **데이터 경쟁(data race)** 방지입니다. 데이터 경쟁이란 둘 이상의 코드가 동시에 같은 데이터에 접근하는데, 그중 하나가 데이터를 쓰고 있어서 결과를 예측할 수 없게 되는 상황을 말합니다. 만약 어떤 값을 누군가는 읽고 있는데 동시에 다른 누군가가 그 값을 바꿔버린다면, 읽는 쪽은 일관성 없는 데이터를 보게 됩니다. Rust는 이런 상황이 발생할 가능성을 컴파일 시점에 원천적으로 차단합니다. 프로그램을 실제로 실행해보지 않아도, 컴파일이 성공한 순간부터 이런 종류의 버그가 없다는 것이 보장되는 것입니다. 이것이 Rust가 "안전한 시스템 프로그래밍 언어"라고 불리는 핵심 이유 중 하나입니다.

아래 그림은 이 규칙을 단순화해서 보여줍니다. 불변 참조는 동시에 여러 개가 허용되지만, 가변 참조는 단 하나만 허용되며 다른 참조와 공존할 수 없습니다.

```text
   불변 참조는 여러 개 허용                    가변 참조는 하나만 허용

        +-----------+                        +-----------+
        | s: String |                        | s: String |
        +-----------+                        +-----------+
          /    |    \                          /    |    \
         /     |     \                        /      :      \
        v      v      v                      v       :       :
   +-------+ +-------+ +-------+        +----------+ :       :
   |r1 = &s| |r2 = &s| |r3 = &s|        |r1=&mut s | :       :
   +-------+ +-------+ +-------+        | (허용)    | :       :
                                        +----------+ v       v
                                                 +----------+ +-------+
                                                 |r2=&mut s | |r3 = &s|
                                                 |  X    X  | | X   X |
                                                 +----------+ +-------+
                                                 (컴파일 오류)  (컴파일 오류)

   +----------------------------+          +-------------------------------+
   |   동시에 읽기 가능 (O)        |          |   r1만 존재 가능 (O)             |
   +----------------------------+          |   r2, r3은 컴파일 오류 (X)        |
                                            +-------------------------------+

   읽기만 하는 참조는 서로 방해하지          쓰기 가능한 참조가 있는 동안
   않는다 -> 개수 제한 없이 동시에           다른 참조가 끼어들면
   존재 가능                                데이터 경쟁 위험

  +--------------------------------------------------------------------+
  | 빌림 규칙: 가변 참조는 동시에 최대 1개,                                  |
  | 가변 참조와 불변 참조는 함께 존재할 수 없다                              |
  | -> 컴파일 시점에 데이터 경쟁을 방지한다                                  |
  +--------------------------------------------------------------------+
```

## 참조의 유효 범위와 참조 검사기

참조가 언제부터 언제까지 "살아있는지"는 그 참조가 마지막으로 사용되는 지점까지입니다. 다음 코드는 규칙을 위반하지 않습니다.

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("{}, {}", r1, r2); // r1, r2는 여기서 마지막으로 사용된다

    let r3 = &mut s; // r1, r2의 생명이 끝난 뒤이므로 문제 없다
    println!("{}", r3);
}
```

Rust 컴파일러는 각 참조가 실제로 사용되는 마지막 지점까지만 그 참조를 "살아있다"고 판단합니다. 이런 분석을 하는 컴파일러의 구성 요소를 **빌림 검사기(borrow checker)**라고 부릅니다. 빌림 검사기는 코드를 실행하지 않고도 모든 참조의 생명 주기를 추적해서 규칙 위반을 찾아냅니다. 참조의 생명 주기를 더 명시적으로 다루는 방법은 17장 라이프타임 기초에서 자세히 설명합니다.

## 댕글링 참조는 아예 만들어지지 않는다

C나 C++에서는 이미 해제된 메모리를 가리키는 포인터, 즉 **댕글링 포인터(dangling pointer)** 때문에 발생하는 버그가 흔합니다. Rust는 컴파일러가 이런 상황을 막아줍니다.

```rust
fn dangle() -> &String { // 오류: 참조가 가리킬 값이 사라진다
    let s = String::from("hello");
    &s
} // s가 스코프를 벗어나며 drop된다
```

`dangle` 함수 안에서 만든 `s`는 함수가 끝나는 순간 소유권 규칙에 따라 drop됩니다(8장 참고). 그런데 함수는 `s`를 가리키는 참조를 반환하려고 합니다. 이 참조는 함수가 끝난 뒤에는 존재하지 않는 값을 가리키게 되므로, 컴파일러는 이 코드를 거부합니다.

```text
error[E0106]: missing lifetime specifier
```

이 오류는 처음에는 당황스럽지만, 사실 매우 유용한 안전장치입니다. 값이 있는 동안에만 참조를 사용할 수 있다는 것을 컴파일 시점에 강제하기 때문에, "이미 사라진 값을 가리키는 참조"라는 클래스의 버그 자체가 Rust에서는 발생할 수 없습니다.

## 요약

- 참조(`&`)는 값의 소유권을 가져오지 않고 그 값을 잠시 빌려서 사용하는 방법입니다.
- 불변 참조(`&T`)는 값을 읽기만 할 수 있으며, 동시에 여러 개를 만들 수 있습니다.
- 가변 참조(`&mut T`)는 값을 읽고 수정할 수 있지만, 동시에 하나만 존재할 수 있습니다.
- 가변 참조가 존재하는 동안에는 다른 어떤 참조(가변이든 불변이든)도 동시에 존재할 수 없습니다.
- 이 빌림 규칙 덕분에 Rust는 컴파일 시점에 데이터 경쟁을 원천적으로 방지합니다.
- 빌림 검사기는 각 참조가 실제로 사용되는 마지막 지점까지의 생명 주기를 추적해서 규칙 위반을 찾아냅니다.
- 값보다 오래 살아남는 참조, 즉 댕글링 참조는 Rust 컴파일러가 만들어지지 못하게 막습니다.
- 참조가 컬렉션의 일부만 가리키도록 범위를 지정하는 방법은 10장 슬라이스와 문자열에서 이어서 다룹니다.

## 연습문제

1. 소유권을 이동시키는 함수와, 참조를 받는 함수를 각각 작성해서 문자열의 단어 개수를 세어보세요. 두 방식의 차이를 `main` 함수에서 어떻게 체감할 수 있는지 설명해보세요.
2. 벡터에 대한 가변 참조를 두 개 동시에 만들어서 컴파일 오류를 직접 발생시켜보고, 오류 메시지를 읽고 어떤 규칙을 위반했는지 적어보세요.
3. `&mut Vec<i32>`를 받아서 벡터의 모든 원소를 두 배로 만드는 함수 `double_all`을 작성하세요.
4. 불변 참조 두 개와 가변 참조 하나를 동시에 살아있게 만들어 오류를 발생시킨 뒤, 코드 순서를 바꾸어 오류 없이 컴파일되도록 고쳐보세요.
5. 함수 안에서 지역 변수를 만들고 그 참조를 반환하려는 코드를 작성해서 어떤 오류가 나는지 확인하고, 참조 대신 값을 직접 반환하도록 고쳐보세요.

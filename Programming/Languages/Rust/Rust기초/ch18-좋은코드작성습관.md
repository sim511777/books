지금까지 이 책은 Rust의 문법과 개념을 하나씩 쌓아왔다. 변수와 자료형(3장)부터 소유권(8장), 빌림(9장), 트레이트(13장), 제네릭(14장), 에러 처리(15장), 라이프타임(17장)까지 다루고 나면 문법적으로 컴파일되는 코드는 충분히 작성할 수 있다. 하지만 "컴파일되는 코드"와 "좋은 Rust 코드"는 다르다. 이번 장에서는 문법을 넘어, 관용적이고 유지보수하기 좋은 Rust 코드를 쓰기 위한 습관들을 정리한다. 이후 새로운 개념은 다루지 않으므로, 지금까지 배운 내용을 되짚어보는 마무리 장이라고 생각하면 된다.

## unwrap과 expect 대신 ?로 에러를 전파하기

15장에서 `Result<T, E>`와 `?` 연산자를 다뤘다. 여기서는 왜 `unwrap`이나 `expect`를 습관적으로 쓰지 않아야 하는지를 다시 강조한다.

```rust
use std::fs::File;

fn read_config() {
    let file = File::open("config.txt").unwrap(); // Err이면 그 자리에서 패닉
    // ...
}
```

`unwrap()`은 `Result`가 `Ok`이면 값을 꺼내주지만, `Err`이면 프로그램 전체를 즉시 패닉(panic)시킨다. 프로토타입을 빠르게 작성하거나, 절대 실패할 수 없다는 것이 논리적으로 보장된 상황("이 문자열은 방금 내가 직접 만들었으니 파싱이 실패할 리 없다" 같은 경우)이라면 `unwrap`이나 `expect`가 나쁜 선택은 아니다. `expect`는 `unwrap`과 동작이 같지만 패닉 메시지를 직접 지정할 수 있어, 최소한 실패했을 때 무엇이 문제였는지 힌트를 남긴다는 점에서 `unwrap`보다는 낫다.

```rust
let file = File::open("config.txt").expect("설정 파일을 열 수 없습니다");
```

하지만 실제 애플리케이션 코드, 특히 파일 입출력이나 네트워크 요청처럼 실패가 일상적으로 일어날 수 있는 상황에서는 `unwrap`/`expect`가 호출자에게 실패를 처리할 기회를 주지 않고 프로그램을 끝내버린다는 점이 문제다. 좋은 습관은 함수가 실패할 수 있다면 `Result`를 반환하고, `?` 연산자로 에러를 호출자에게 전파하는 것이다.

```rust
use std::fs::File;
use std::io::Read;

fn read_config() -> Result<String, std::io::Error> {
    let mut file = File::open("config.txt")?; // 실패하면 즉시 Err을 반환
    let mut contents = String::new();
    file.read_to_string(&mut contents)?;
    Ok(contents)
}
```

이렇게 작성하면 `read_config`를 호출하는 쪽에서 파일이 없는 경우를 어떻게 처리할지(기본값을 쓸지, 사용자에게 안내할지, 프로그램을 종료할지) 스스로 결정할 수 있다. 실패를 처리하는 책임을 함수 내부에서 최종 결정하지 않고, 호출 체인을 따라 적절한 위치까지 전달하는 것이 관용적인 Rust 스타일이다. 실무에서 흔히 쓰는 기준은 다음과 같다.

- 라이브러리 코드나 재사용될 함수: 거의 항상 `Result`를 반환하고 `?`로 전파한다.
- 프로그램의 최상위(`main` 함수 등)에서 더 이상 전파할 곳이 없을 때: 이때는 로그를 남기거나 사용자에게 메시지를 보여주고 종료하는 등 최종 처리를 한다.
- 테스트 코드나 예제, 실패가 논리적으로 불가능함을 확신하는 상황: `unwrap`/`expect`도 무방하다.

## 불필요한 clone() 남용 피하기

8장과 9장에서 소유권과 빌림 규칙을 배우다 보면, 컴파일러가 "값이 이동되었다"거나 "참조 규칙을 어겼다"고 항의할 때 가장 손쉬운 탈출구로 `.clone()`을 붙이는 습관이 생기기 쉽다.

```rust
fn print_length(s: String) {
    println!("길이: {}", s.len());
}

fn main() {
    let name = String::from("러스트");
    print_length(name.clone()); // name을 계속 쓰고 싶어서 clone
    println!("{name}");
}
```

이 코드는 동작하지만, 애초에 `print_length`가 `String`을 소유할 필요가 없었다는 점을 놓치고 있다. `s`를 읽기만 하고 소유권이 필요 없다면, 매개변수를 참조로 받는 것이 훨씬 자연스럽다.

```rust
fn print_length(s: &str) {
    println!("길이: {}", s.len());
}

fn main() {
    let name = String::from("러스트");
    print_length(&name); // 빌려주기만 하면 충분하다
    println!("{name}");
}
```

이렇게 고치면 `clone()`으로 데이터를 복제하는 비용도 없고, 코드를 읽는 사람에게도 "이 함수는 문자열을 읽기만 하고 소유권을 가져가지 않는다"는 의도가 더 명확하게 드러난다. `clone()` 자체가 나쁜 것은 아니다. 정말로 독립적인 복사본이 필요한 경우(예: 두 스레드에 각각 데이터를 넘겨야 하거나, 원본과 별개로 수정해야 할 때)에는 `clone()`이 올바른 선택이다. 문제는 소유권 이동이나 빌림 규칙을 이해하지 못한 채, 컴파일 오류를 없애기 위한 반사적인 습관으로 `clone()`을 붙이는 경우다. `clone()`을 쓰기 전에 스스로 던져볼 만한 질문은 다음과 같다.

- 이 함수는 값을 읽기만 하는가, 아니면 값을 소유하거나 수정해야 하는가? 읽기만 한다면 참조(`&T`)로 충분하다.
- 반복문에서 컬렉션(16장)을 순회할 때 `for item in vec` 대신 `for item in &vec`를 쓰면 소유권을 옮기지 않고도 순회할 수 있지 않은가?
- 정말 두 개의 독립된 복사본이 필요한 상황인가, 아니면 빌림 규칙을 아직 잘 모를 뿐인가?

`String`처럼 힙에 데이터를 저장하는 타입은 `clone()` 한 번에 데이터 전체를 복제하는 비용이 든다. 작은 프로그램에서는 눈에 띄지 않지만, 반복문 안에서 습관적으로 `clone()`을 부르면 데이터 크기와 반복 횟수에 비례해 비용이 누적된다.

## cargo fmt와 cargo clippy를 습관적으로 사용하기

2장에서 `cargo`로 프로젝트를 빌드하고 실행하는 법을 다뤘다. `cargo`는 코드 품질을 관리하는 도구도 함께 제공한다.

`cargo fmt`는 코드를 Rust 커뮤니티가 합의한 표준 스타일로 자동 정렬해준다. 들여쓰기, 줄바꿈, 공백 규칙을 사람이 신경 쓸 필요가 없어지고, 여러 사람이 함께 작업하는 프로젝트에서도 스타일 논쟁 없이 일관된 코드를 유지할 수 있다.

```bash
cargo fmt
```

`cargo clippy`는 한 걸음 더 나아가, 문법적으로는 문제없지만 더 나은 방식이 있는 코드를 찾아 알려주는 린터(linter)다. 예를 들어 clippy는 다음과 같은 패턴을 지적한다.

- 불필요한 `.clone()`을 호출하는 코드(이 장에서 다룬 문제를 자동으로 잡아주기도 한다)
- `if x == true`처럼 굳이 비교할 필요 없는 불(bool) 비교
- 함수 끝에서 값을 반환할 때 불필요하게 `return`을 명시한 경우
- `match`로 작성했지만 `if let`이나 다른 메서드로 더 간결하게 표현할 수 있는 패턴

```bash
cargo clippy
```

`clippy`가 내는 경고는 대부분 "컴파일은 되지만 더 관용적인 방법이 있다"는 제안이다. 처음에는 경고가 여러 개 쏟아져 당황할 수 있지만, 하나씩 읽어보면 그 자체로 관용적인 Rust 코드가 어떤 모습인지 배우는 좋은 자료가 된다. 코드를 커밋하기 전에 `cargo fmt`와 `cargo clippy`를 실행하는 습관을 들이면, 스타일과 관용구 두 측면에서 코드 품질을 꾸준히 유지할 수 있다.

## 자주 저지르는 실수 정리

지금까지 여러 장에서 다룬 오류 상황을 모아 다시 정리해본다. 이 실수들은 Rust를 배우는 과정에서 누구나 한 번쯤은 마주치는 것들이므로, 오류 메시지를 겁내지 말고 원인을 파악하는 연습으로 삼자.

**소유권 이동 후 값 사용하기** (8장)

```rust
let s1 = String::from("hello");
let s2 = s1; // s1의 소유권이 s2로 이동
println!("{s1}"); // 오류: s1은 더 이상 유효하지 않다
```

`String`처럼 힙 데이터를 가진 타입을 다른 변수에 대입하면 값이 복사되는 것이 아니라 소유권이 이동한다. 이후 원래 변수를 사용하려 하면 컴파일 오류가 난다. 해결책은 상황에 따라 다르다. 원본을 계속 써야 한다면 `.clone()`으로 복제하거나(앞서 다뤘듯 정말 필요한 경우에만), 처음부터 참조를 넘겨 소유권 이동 자체를 피하는 방법도 있다.

**빌림 규칙 위반: 가변 참조와 불변 참조의 동시 존재** (9장)

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];       // 불변 참조 시작
v.push(4);                // 오류: 불변 참조가 살아있는 동안 가변 빌림 시도
println!("{first}");
```

`first`가 `v`의 요소를 불변 참조로 빌리고 있는 동안, `v.push(4)`는 `v` 전체에 대한 가변 참조를 필요로 한다. 벡터에 새 요소를 추가하면 내부적으로 메모리 재할당이 일어날 수 있어 기존 참조가 무효화될 위험이 있으므로, 컴파일러는 이 코드를 거부한다. 해결책은 불변 참조의 사용이 끝난 뒤에 가변 작업을 하도록 순서를 바꾸는 것이다.

```rust
let mut v = vec![1, 2, 3];
let first = v[0]; // 참조가 아니라 값을 복사(i32는 Copy 타입)
v.push(4);
println!("{first}");
```

**빌림 규칙 위반: 두 개의 가변 참조** (9장)

```rust
let mut x = 5;
let r1 = &mut x;
let r2 = &mut x; // 오류: 가변 참조는 동시에 하나만
println!("{r1}, {r2}");
```

같은 값에 대한 가변 참조는 한 번에 하나만 존재할 수 있다. 이 규칙 덕분에 컴파일러는 데이터 경쟁(data race)이 발생할 수 있는 코드를 컴파일 시점에 차단한다. 두 참조의 사용 시점이 겹치지 않도록 스코프를 나누면 해결된다.

**라이프타임이 원본보다 길어지는 경우** (17장)

17장에서 다룬 것처럼, 함수가 반환하는 참조가 매개변수 중 하나보다 더 오래 살려고 하면 컴파일러가 이를 막는다. 이런 오류를 만났을 때는 "정말 참조가 필요한가, 아니면 값을 직접 반환하거나 소유권을 넘겨야 하는가"를 먼저 점검해보는 것이 좋다.

이 오류들의 공통점은, 모두 실행 중에 발생했다면 다른 언어에서는 찾기 어려운 버그(댕글링 포인터, 데이터 경쟁, use-after-free)로 이어졌을 상황이라는 점이다. Rust는 이런 버그를 실행 전에, 컴파일러의 오류 메시지라는 형태로 먼저 보여준다. 오류 메시지를 마주쳤을 때 "왜 컴파일러가 이걸 막는지"를 이해하려는 태도가 Rust에 익숙해지는 가장 빠른 길이다.

## 다음 학습 단계

이 책은 Rust 언어의 기초 문법과 소유권 모델을 중심으로 구성되었다. 여기서 익힌 개념들은 이후 어떤 방향으로 나아가든 공통으로 필요한 토대다. 다음으로 관심을 가져볼 만한 주제를 몇 가지 소개한다.

- **비동기 프로그래밍(async programming)**: 네트워크 요청이나 파일 입출력처럼 기다리는 시간이 긴 작업을 효율적으로 처리하는 방법이다. `async`/`await` 문법과, 그 뒤에서 작업을 스케줄링하는 런타임의 개념을 함께 이해해야 한다.
- **안전한 동시성(concurrency)**: 여러 스레드가 데이터를 안전하게 공유하고 통신하는 방법을 다룬다. 이 책에서 배운 소유권과 빌림 규칙이 스레드 사이의 데이터 공유에도 그대로 확장되어, 데이터 경쟁을 컴파일 시점에 막아주는 과정을 경험할 수 있다.
- **웹어셈블리(WebAssembly)**: Rust 코드를 브라우저에서 네이티브에 가까운 속도로 실행할 수 있도록 컴파일하는 분야다. 1장에서 언급했던 Rust의 활용 영역 중 하나를 실제로 다뤄보는 경험이 된다.
- **CLI 도구와 크레이트 생태계**: 부록에서 소개할 크레이트(crate) 생태계를 활용해, 명령줄 인자를 파싱하거나 다양한 출력 형식을 다루는 실용적인 도구를 만들어보는 것도 좋은 다음 단계다.

이 중 무엇을 먼저 공부하든, 이 책에서 다진 소유권·빌림·라이프타임에 대한 감각이 계속 밑바탕이 된다는 점은 변하지 않는다.

## 요약

- 실패할 수 있는 함수는 `unwrap`/`expect`로 즉시 패닉시키기보다 `Result`를 반환하고 `?`로 에러를 호출자에게 전파하는 것이 일반적으로 더 나은 습관이다.
- `.clone()`은 정말 독립된 복사본이 필요할 때 쓰는 도구이며, 소유권/빌림 오류를 피하려는 반사적인 습관으로 남용하면 불필요한 비용과 흐릿한 의도를 남긴다.
- `cargo fmt`로 스타일을 통일하고 `cargo clippy`로 관용적이지 않은 패턴을 찾아내는 습관을 들이면 코드 품질이 꾸준히 개선된다.
- 소유권 이동 후 사용, 가변/불변 참조 동시 존재, 두 개의 가변 참조, 라이프타임 초과 같은 오류는 모두 실행 중 버그가 될 수 있었던 문제를 컴파일 시점에 미리 알려주는 것이다.
- 이 책에서 다진 소유권·빌림·라이프타임 감각은 비동기 프로그래밍, 동시성, 웹어셈블리, CLI 도구 개발 등 어떤 다음 단계로 나아가든 공통의 토대가 된다.

## 체크리스트

코드를 커밋하거나 다른 사람에게 리뷰를 요청하기 전에, 다음 항목들을 스스로 점검해보자.

- [ ] 실패할 수 있는 함수에서 `unwrap`/`expect`를 습관적으로 쓰고 있지는 않은가? `Result`와 `?`로 바꿀 수 있는 부분이 있는가?
- [ ] `.clone()`을 호출한 자리마다, 정말 독립된 복사본이 필요한지 다시 확인했는가? 참조로 바꿔서 없앨 수 있는 `.clone()`은 없는가?
- [ ] 커밋 전에 `cargo fmt`를 실행했는가?
- [ ] `cargo clippy`가 내는 경고를 모두 읽어보고, 그중 받아들일 것과 의도적으로 무시할 것을 판단했는가?
- [ ] 컴파일 오류가 났을 때 오류 메시지만 보고 임시방편으로 고치지 않고, 소유권·빌림·라이프타임 중 어떤 규칙이 문제였는지 이해했는가?
- [ ] 함수의 매개변수 타입을 고를 때, 소유권이 꼭 필요한지 아니면 참조로 충분한지 검토했는가?

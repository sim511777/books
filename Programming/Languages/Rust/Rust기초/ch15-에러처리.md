## 들어가며

Java나 Python, C++에는 `try`/`catch`(또는 `try`/`except`)로 처리하는 예외(exception)가 있다. 함수 실행 중 문제가 생기면 예외를 던지고, 호출한 쪽에서 잡지 않으면 그 예외는 호출 스택을 타고 계속 위로 전파된다. 문제는 함수의 시그니처만 봐서는 그 함수가 예외를 던질 수 있는지, 던진다면 어떤 종류인지 알 수 없다는 점이다. 문서를 읽거나 소스 코드를 직접 확인하지 않으면 놓치기 쉽다.

Rust에는 이런 의미의 예외가 없다. 대신 "실패할 수 있는 연산"과 "값이 없을 수 있는 상황"을 함수의 반환 타입 자체로 표현한다. 함수 시그니처만 보고도 이 함수가 실패할 수 있는지, 실패하면 어떤 정보를 돌려주는지 컴파일러가 강제로 알려준다. 이번 장에서는 이 방식의 핵심인 `Option<T>`와 `Result<T, E>`, 그리고 이들을 다루는 관용적인 방법을 살펴본다.

## Option<T>: 값이 없을 수도 있다는 사실을 타입으로 표현하기

많은 언어에는 "값이 없음"을 나타내는 `null`이 있다. 그런데 `null`의 근본적인 문제는 어떤 타입의 변수든 `null`이 될 수 있다는 것이다. 컴파일러는 "이 변수가 지금 `null`인지 아닌지"를 추적하지 않으므로, 실제로 값이 없는데 있다고 가정하고 접근하면 런타임에 프로그램이 죽는다. 이 문제를 처음 설계한 토니 호어(Tony Hoare)는 이를 "10억 달러짜리 실수"라고 부르기도 했다.

Rust에는 `null`이 없다. 대신 12장에서 배운 열거형(enum) 문법을 이용해 표준 라이브러리가 다음과 같은 타입을 정의해 둔다.

```rust
enum Option<T> {
    Some(T),
    None,
}
```

`Option<T>`는 값이 있으면 `Some(T)`, 없으면 `None`이라는 두 경우만 가지는 열거형이다. 값이 없을 수 있는 함수는 반환 타입에 `Option<T>`를 명시해야 하므로, 함수를 호출하는 쪽은 반환값이 항상 있다고 가정할 수 없다는 사실을 타입만 보고 알 수 있다.

```rust
fn find_first_even(numbers: &[i32]) -> Option<i32> {
    for &n in numbers {
        if n % 2 == 0 {
            return Some(n);
        }
    }
    None
}

fn main() {
    let numbers = vec![1, 3, 7, 8, 9];
    match find_first_even(&numbers) {
        Some(n) => println!("첫 짝수: {n}"),
        None => println!("짝수를 찾지 못했습니다"),
    }
}
```

`Option<i32>`를 그냥 `i32`처럼 사용할 수는 없다. `Some(n)`과 `None`을 구분해서 처리하도록 컴파일러가 강제하기 때문이다. 이 강제성이 바로 `null` 관련 버그를 컴파일 시점에 없애는 장치다. 5장에서 살짝 다룬 `if let`도 여기서 유용하다. `None`일 때 할 일이 없다면 `match` 대신 더 간결하게 쓸 수 있다.

```rust
let numbers = vec![1, 3, 7, 8, 9];
if let Some(n) = find_first_even(&numbers) {
    println!("첫 짝수: {n}");
}
```

## Result<T, E>: 실패 원인까지 함께 담기

`Option<T>`는 "값이 있는지 없는지"만 표현할 뿐, 없다면 왜 없는지는 말해주지 않는다. 파일을 열거나 문자열을 숫자로 변환하는 것처럼 실패할 수 있고, 그 실패의 원인이 다양한 연산에는 `Result<T, E>`를 쓴다.

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

성공하면 `Ok(T)`에 결과값을 담고, 실패하면 `Err(E)`에 에러 정보를 담는다. 표준 라이브러리의 여러 함수가 이 패턴을 따른다. 예를 들어 문자열을 정수로 파싱하는 `str::parse`는 실패할 수 있으므로 `Result`를 반환한다.

```rust
fn main() {
    let input = "42";
    let parsed: Result<i32, _> = input.parse();

    match parsed {
        Ok(n) => println!("파싱 성공: {n}"),
        Err(e) => println!("파싱 실패: {e}"),
    }
}
```

`"42abc"`처럼 숫자로 변환할 수 없는 문자열을 넣으면 `Err` 분기가 실행되고, 그 안에는 `ParseIntError`라는 구체적인 에러 값이 들어 있다. 예외를 던지는 언어라면 이 상황에서 프로그램이 그대로 죽거나 `catch` 블록으로 흐름이 튀어버리지만, Rust에서는 `Ok`와 `Err`가 똑같이 취급되는 하나의 값일 뿐이다. 실패는 예외적인 사건이 아니라, 함수의 반환값에 포함된 정상적인 경우의 하나로 다뤄진다.

직접 만드는 함수도 같은 방식으로 작성할 수 있다.

```rust
fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err(String::from("0으로 나눌 수 없습니다"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    match divide(10.0, 2.0) {
        Ok(result) => println!("결과: {result}"),
        Err(message) => println!("오류: {message}"),
    }
}
```

여기서는 에러 타입으로 간단히 `String`을 썼지만, 실전에서는 에러의 종류를 구분할 수 있는 전용 열거형을 만드는 경우가 많다. 이는 12장에서 배운 열거형 문법을 그대로 활용하는 예다.

```rust
enum DivideError {
    DivideByZero,
    NegativeResult,
}

fn divide_checked(a: f64, b: f64) -> Result<f64, DivideError> {
    if b == 0.0 {
        return Err(DivideError::DivideByZero);
    }
    let result = a / b;
    if result < 0.0 {
        return Err(DivideError::NegativeResult);
    }
    Ok(result)
}
```

이렇게 하면 호출하는 쪽에서 `match`로 각 에러 종류마다 다른 대응을 할 수 있고, 컴파일러가 새로운 에러 종류를 추가했을 때 처리를 빠뜨린 곳을 찾아준다.

## ? 연산자로 에러 전파하기

`Result`를 반환하는 함수를 여러 개 연달아 호출하다 보면, 매번 `match`로 성공/실패를 나누는 코드가 반복되기 쉽다.

```rust
fn get_doubled(input: &str) -> Result<i32, std::num::ParseIntError> {
    let parsed = match input.parse::<i32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    Ok(parsed * 2)
}
```

이 패턴, 즉 "성공하면 값을 꺼내서 계속 진행하고, 실패하면 그 에러를 그대로 함수 밖으로 반환한다"는 매우 흔해서 Rust는 `?` 연산자라는 전용 문법을 제공한다.

```rust
fn get_doubled(input: &str) -> Result<i32, std::num::ParseIntError> {
    let parsed = input.parse::<i32>()?;
    Ok(parsed * 2)
}
```

`expr?`는 `expr`이 `Ok(value)`이면 `value`로 평가되고, `Err(e)`이면 즉시 `Err(e)`를 현재 함수의 반환값으로 만들어 함수를 종료시킨다. 두 함수는 동작이 완전히 같지만, `?`를 쓴 쪽이 훨씬 짧고 "성공 경로"에 집중해서 읽힌다. 여러 단계를 거치는 코드에서 차이가 더 두드러진다.

```rust
fn calculate_average(a: &str, b: &str, c: &str) -> Result<f64, std::num::ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    let z = c.parse::<i32>()?;
    Ok((x + y + z) as f64 / 3.0)
}
```

세 번의 파싱 중 어디서든 실패하면 그 즉시 `calculate_average`도 같은 에러를 반환하며 종료된다. `?`는 `Option<T>`에도 똑같이 쓸 수 있다. `None`이면 즉시 함수가 `None`을 반환하고, `Some(value)`이면 `value`로 평가된다.

```rust
fn first_char_uppercase(text: &str) -> Option<char> {
    let first = text.chars().next()?;
    Some(first.to_ascii_uppercase())
}
```

한 가지 주의할 점은 `?`를 쓸 수 있는 위치가 제한적이라는 것이다. `?`가 등장한 함수의 반환 타입은 `?`를 적용한 값과 호환되는 `Result`나 `Option`이어야 한다. `main` 함수의 기본 반환 타입은 `()`이므로, `main` 안에서 `?`를 쓰려면 `main`의 반환 타입을 `Result<(), E>`로 바꿔야 한다.

```rust
fn main() -> Result<(), std::num::ParseIntError> {
    let n: i32 = "42".parse()?;
    println!("{n}");
    Ok(())
}
```

## unwrap과 expect, 그리고 그것을 함부로 쓰면 안 되는 이유

`Option`이나 `Result`를 다루다 보면 "지금 이 상황에서는 절대 실패할 리 없다"고 확신하게 되는 경우가 있다. 이럴 때 값을 빠르게 꺼내는 메서드가 `unwrap`과 `expect`다.

```rust
let some_number: Option<i32> = Some(5);
let value = some_number.unwrap(); // 5

let parsed: Result<i32, _> = "42".parse();
let value2 = parsed.unwrap(); // 42
```

문제는 `Some`이나 `Ok`가 아닌 경우, 즉 `None`이거나 `Err`인 경우 `unwrap`은 그 자리에서 프로그램을 즉시 패닉(panic)시켜 종료해 버린다는 점이다.

```rust
let empty: Option<i32> = None;
let value = empty.unwrap(); // 여기서 패닉! "called `Option::unwrap()` on a `None` value"
```

이는 예외를 잡지 않고 방치한 것과 비슷한 결과를 낳는다. 다른 점은 Rust가 이 위험을 `unwrap`이라는 이름으로 명시적으로 드러낸다는 것이다. 코드에 `unwrap()`이 보인다면 "여기서 실패하면 프로그램이 죽는다"는 뜻이므로, 리뷰어나 미래의 자신이 그 위험성을 눈으로 바로 확인할 수 있다. `expect`는 `unwrap`과 동작이 같지만 패닉 메시지를 직접 지정할 수 있어, 왜 실패했는지 디버깅하기 더 쉽다.

```rust
let config_value = std::env::var("MY_CONFIG")
    .expect("MY_CONFIG 환경 변수가 설정되어 있어야 합니다");
```

`unwrap`/`expect`가 무조건 나쁜 것은 아니다. 다음과 같은 상황에서는 합리적인 선택이다.

- 프로토타입이나 예제 코드처럼 에러 처리의 완성도보다 핵심 로직을 빠르게 보여주는 것이 목적일 때
- 테스트 코드에서 실패 자체가 테스트의 실패를 의미해야 할 때
- 프로그램의 불변 조건(invariant)에 의해 절대 실패할 수 없다고 논리적으로 보장되는 경우(예: 방금 `Vec`에 넣은 값을 바로 꺼내는 경우)

하지만 사용자 입력, 파일 시스템, 네트워크처럼 실제로 실패할 수 있는 외부 요인이 관련된 코드에서 `unwrap`을 남발하면, 예상 가능한 실패 상황(파일이 없다, 입력이 잘못됐다)만으로도 프로그램 전체가 죽어버린다. 실전 코드에서는 다음과 같이 `?`로 에러를 호출자에게 넘기거나, `match`/`unwrap_or`/`unwrap_or_else` 같은 메서드로 기본값을 정해 복구하는 방식을 우선 고려해야 한다.

```rust
// 실패해도 프로그램을 죽이지 않고 기본값으로 대체
let count: i32 = "abc".parse().unwrap_or(0);
println!("count = {count}");
```

"컴파일이 되면 대체로 동작한다"는 Rust의 평판은 에러 상황을 타입 시스템으로 드러내고 강제로 처리하게 만들기 때문에 가능한 것이다. `unwrap`을 습관적으로 남발하는 것은 이 안전장치를 스스로 걷어내는 것과 같다는 점을 기억해 두자. 이런 실패 처리 습관은 18장에서 다루는 "좋은 Rust 코드 작성 습관"과도 직결된다.

## 요약

- Rust에는 예외가 없다. 실패 가능성은 함수의 반환 타입인 `Option<T>`, `Result<T, E>`로 명시적으로 표현된다.
- `Option<T>`는 `Some(T)`/`None`으로 값의 있음/없음을 표현하며, `null`이 야기하는 문제를 컴파일 시점에 차단한다.
- `Result<T, E>`는 `Ok(T)`/`Err(E)`로 성공/실패와 그 원인을 함께 표현한다.
- `?` 연산자는 `Err`나 `None`을 만나면 즉시 함수 밖으로 전파하는 관용구로, 에러 처리 코드를 크게 줄여준다.
- `unwrap`/`expect`는 실패 시 프로그램을 패닉으로 종료시키므로, 절대 실패하지 않는다고 확신할 수 있는 경우나 프로토타입 코드 외에는 신중하게 사용해야 한다.

## 연습문제

1. 문자열 슬라이스의 벡터를 받아 그 안에서 가장 긴 문자열을 `Option<&str>`으로 반환하는 함수를 작성하라. 벡터가 비어 있으면 `None`을 반환해야 한다.
2. 나이를 나타내는 문자열을 받아 `u8`로 파싱하되, 150을 넘는 값이면 `Err("나이가 너무 큽니다")`를, 파싱 자체가 실패하면 그 파싱 에러를 반환하는 함수를 작성하라. (힌트: 에러 타입을 통일하려면 열거형이나 `String`을 활용한다.)
3. 두 개의 문자열을 각각 `i32`로 파싱한 뒤 곱한 값을 반환하는 함수를 `?` 연산자를 사용해 작성하고, `?`를 쓰지 않은 버전과 코드 길이를 비교해 보라.
4. `Option<i32>` 값을 `unwrap_or(0)`, `unwrap_or_else(|| compute_default())`, `match`로 각각 처리하는 코드를 작성해 보고 세 방식의 차이를 설명하라.
5. `main` 함수의 반환 타입을 `Result<(), Box<dyn std::error::Error>>`로 바꾸고, 그 안에서 `?`를 사용해 여러 개의 실패 가능한 연산을 연쇄적으로 호출하는 예제를 작성하라.

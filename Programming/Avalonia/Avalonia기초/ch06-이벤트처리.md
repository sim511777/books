# 6장. 이벤트 처리

[◀ 이전: 5장. 기본 컨트롤](ch05-기본컨트롤.md) | [📖 목차](00-목차.md) | [다음: 7장. 데이터 바인딩 기초 ▶](ch07-데이터바인딩기초.md)


5장에서 만든 로그인 폼은 아직 보기만 하는 화면입니다. 버튼을 눌러도, 체크박스를 클릭해도 아무 반응이 없습니다. 이번 장에서는 사용자의 조작에 실제로 반응하는 코드를 작성하는 방법, 즉 이벤트 처리를 배웁니다.

Avalonia에서 이벤트를 다루는 가장 기본적인 방법은 XAML에 이벤트 핸들러 이름을 적어두고, 같은 뷰의 코드비하인드 파일에 그 이름의 메서드를 작성하는 것입니다. 이 장에서는 이 방식을 중심으로, 이벤트가 컨트롤 트리를 따라 전파되는 라우티드 이벤트의 개념과, XAML 없이 코드에서 직접 이벤트를 구독하는 방법까지 함께 살펴봅니다. 그리고 장의 마지막에서는 이런 코드비하인드 중심의 이벤트 처리 방식이 언제까지 유효한지, 규모가 커졌을 때는 어떤 방식으로 옮겨가는지 미리 짚어봅니다.

## 6.1 이벤트란 무엇인가

이벤트는 "무언가 일어났다"는 사실을 알리는 신호입니다. 사용자가 버튼을 클릭하거나, 텍스트를 입력하거나, 마우스 포인터가 컨트롤 위로 지나가는 순간마다 Avalonia는 해당 컨트롤에서 이벤트를 발생시킵니다. 개발자는 이 이벤트에 자신의 코드를 연결해서, "버튼이 클릭되면 이런 동작을 해라"와 같은 반응을 정의합니다.

2장에서 처음 만든 프로젝트를 떠올려 보면, `.axaml` 파일과 `.axaml.cs` 파일이 한 쌍으로 존재했습니다. `.axaml`은 화면의 모양을 선언하고, `.axaml.cs`는 그 화면에 대응하는 클래스(코드비하인드)를 정의합니다. 이벤트 처리 코드는 바로 이 `.axaml.cs` 파일에 작성합니다.

## 6.2 코드비하인드에서 이벤트 핸들러 연결하기

가장 흔히 쓰는 방식은 XAML에서 이벤트 이름과 핸들러 이름을 직접 지정하는 것입니다. `Button`의 `Click` 이벤트를 예로 들어보겠습니다.

```xml
<Button Content="로그인"
        Click="LoginButton_Click" />
```

`Click="LoginButton_Click"`은 "이 버튼이 클릭되면 코드비하인드에 있는 `LoginButton_Click`이라는 메서드를 호출하라"는 뜻입니다. 이제 같은 뷰의 `.axaml.cs` 파일에 그 이름과 정확히 일치하는 메서드를 작성합니다.

```csharp
using Avalonia.Controls;
using Avalonia.Interactivity;

namespace LoginApp;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }

    private void LoginButton_Click(object? sender, RoutedEventArgs e)
    {
        StatusText.Text = "로그인 버튼이 클릭되었습니다.";
    }
}
```

몇 가지 눈여겨볼 점이 있습니다.

- 이벤트 핸들러의 시그니처는 `void 메서드이름(object? sender, RoutedEventArgs e)` 형태를 따릅니다. `Click`뿐 아니라 대부분의 UI 이벤트가 이 패턴을 따르며, 이벤트 종류에 따라 두 번째 매개변수의 타입만 `PointerPressedEventArgs`, `KeyEventArgs`처럼 더 구체적인 타입으로 바뀝니다.
- 첫 번째 매개변수 `sender`는 이벤트를 발생시킨 컨트롤 자신입니다. 여러 버튼이 같은 핸들러를 공유할 때 `sender`를 `Button`으로 캐스팅해서 "어떤 버튼이 클릭됐는지" 구분하는 데 씁니다.
- 두 번째 매개변수 `e`는 이벤트에 대한 추가 정보를 담고 있습니다. 뒤에서 다룰 `e.Handled`도 이 안에 있습니다.
- `StatusText`처럼 XAML에서 `x:Name`을 지정한 컨트롤은 코드비하인드에서 별도의 선언 없이 필드처럼 바로 사용할 수 있습니다. 이는 Avalonia의 XAML 컴파일러가 `InitializeComponent()` 호출 시점에 이름이 붙은 컨트롤들을 찾아 자동으로 필드를 채워주기 때문입니다.

5장의 로그인 폼에 이 방식을 적용해 실제로 값을 검사하는 코드를 작성해 보겠습니다.

```xml
<Button x:Name="LoginButton"
        Content="로그인"
        Click="LoginButton_Click"
        HorizontalAlignment="Stretch"
        HorizontalContentAlignment="Center" />
```

```csharp
private void LoginButton_Click(object? sender, RoutedEventArgs e)
{
    var username = UsernameBox.Text;
    var password = PasswordBox.Text;

    if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(password))
    {
        StatusText.Text = "아이디와 비밀번호를 모두 입력하세요.";
        return;
    }

    StatusText.Text = $"{username} 님, 환영합니다.";
}
```

버튼 외에도 `CheckBox`, `RadioButton`, `ToggleButton`은 상태가 바뀔 때 `Checked`, `Unchecked`, `Indeterminate` 이벤트를 발생시킵니다. 5장 연습문제에서 언급했던 "비밀번호 표시 토글 버튼"을 이 방식으로 구현할 수 있습니다.

```xml
<ToggleButton x:Name="ShowPasswordToggle"
              Content="비밀번호 표시"
              Checked="ShowPasswordToggle_Checked"
              Unchecked="ShowPasswordToggle_Unchecked" />
```

```csharp
private void ShowPasswordToggle_Checked(object? sender, RoutedEventArgs e)
{
    PasswordBox.PasswordChar = default;
}

private void ShowPasswordToggle_Unchecked(object? sender, RoutedEventArgs e)
{
    PasswordBox.PasswordChar = '●';
}
```

`PasswordChar`를 기본값(`default`, 즉 `'\0'`)으로 되돌리면 `TextBox`는 문자를 가리지 않고 그대로 표시합니다.

## 6.3 라우티드 이벤트 이해하기

Avalonia의 UI 이벤트는 대부분 평범한 .NET 이벤트가 아니라 **라우티드 이벤트(Routed Event)** 입니다. 라우티드 이벤트의 특징은 이벤트가 발생한 컨트롤 하나에서 끝나지 않고, 컨트롤 트리를 따라 다른 컨트롤에도 전달된다는 점입니다.

가장 흔한 전파 방식은 **버블링(Bubble)** 입니다. 이벤트가 발생한 컨트롤에서 시작해서, 그 컨트롤을 감싸고 있는 부모, 부모의 부모, 이렇게 트리를 따라 위로 거슬러 올라가며 같은 이벤트가 계속 발생합니다.

![라우티드 이벤트가 자식에서 부모로 버블링되는 모습](images/ch06-routed-event-bubbling.svg)

예를 들어 `StackPanel` 안에 `Button`이 있고, `Button`을 클릭하면 `Click` 이벤트는 먼저 `Button` 자신에서 발생한 뒤, 이벤트를 가로채 처리하지 않는 한 부모인 `StackPanel`, 그 부모인 `Grid`, 최상위 `Window`까지 순서대로 전달됩니다. 이 덕분에 자식 컨트롤 하나하나에 핸들러를 달지 않고도, 부모 컨트롤 하나에서 여러 자식의 이벤트를 한꺼번에 받아 처리하는 것이 가능합니다.

```xml
<StackPanel Name="ButtonPanel" PointerPressed="ButtonPanel_PointerPressed">
    <Button Content="확인" />
    <Button Content="취소" />
</StackPanel>
```

```csharp
private void ButtonPanel_PointerPressed(object? sender, PointerPressedEventArgs e)
{
    // StackPanel 안의 어느 버튼을 눌러도 이 핸들러가 호출됩니다.
    var clicked = e.Source as Control;
    StatusText.Text = $"{clicked?.GetType().Name} 위에서 포인터가 눌렸습니다.";
}
```

반대 방향으로 전파되는 **터널링(Tunnel)** 방식도 있습니다. 터널링 이벤트는 최상위 컨트롤에서 시작해서 실제로 이벤트가 발생한 자식 컨트롤 방향으로 내려갑니다. Avalonia에서는 관례적으로 터널링 이벤트 이름 앞에 `Preview`를 붙입니다. 예를 들어 키보드 입력은 `Tunnel` 방식의 `KeyDown`(내부적으로 미리 전달)과 `Bubble` 방식의 `KeyDown`이 짝을 이루는 식으로 동작해서, 부모가 자식보다 먼저 입력을 살펴보고 필요하면 가로챌 기회를 가질 수 있습니다.

이벤트가 트리를 계속 타고 올라가는 것을 막고 싶다면 이벤트 인자의 `Handled` 속성을 `true`로 설정합니다.

```csharp
private void InnerButton_Click(object? sender, RoutedEventArgs e)
{
    StatusText.Text = "안쪽 버튼에서 처리했습니다.";
    e.Handled = true; // 이 지점 이후로는 부모에게 이벤트가 전달되지 않습니다.
}
```

`e.Handled = true`로 표시된 이벤트는 기본적으로 더 이상 상위 컨트롤의 핸들러를 호출하지 않습니다. 다만 상위 컨트롤에서 `AddHandler`를 사용해 핸들러를 등록할 때 `handledEventsToo: true` 옵션을 주면, 이미 처리된 것으로 표시된 이벤트도 계속 받아볼 수 있습니다. 이는 다이얼로그나 특수한 입력 처리처럼 하위에서 이미 처리한 이벤트라도 상위에서 반드시 알아야 하는 상황에 사용하는 고급 기법입니다.

```csharp
this.AddHandler(Button.ClickEvent, OuterHandler, handledEventsToo: true);
```

지금 단계에서는 "이벤트는 자식에서 부모로 전파되며, `e.Handled = true`로 그 전파를 멈출 수 있다"는 정도만 기억해도 충분합니다.

## 6.4 코드에서 직접 이벤트 구독하기

XAML에 `Click="..."`을 적는 대신, 코드비하인드에서 `+=` 연산자로 이벤트를 직접 구독할 수도 있습니다. 이 방식은 다음과 같은 상황에서 유용합니다.

- 코드에서 동적으로 생성한 컨트롤에 이벤트를 연결할 때(애초에 XAML이 없으므로 `Click` 속성을 적을 수 없습니다)
- 조건에 따라 특정 시점에만 이벤트를 구독하거나 해제하고 싶을 때
- 하나의 이벤트에 여러 핸들러를 등록하고 싶을 때

```csharp
public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();

        LoginButton.Click += LoginButton_Click;
    }

    private void LoginButton_Click(object? sender, RoutedEventArgs e)
    {
        StatusText.Text = "코드에서 직접 연결한 핸들러가 호출되었습니다.";
    }
}
```

`InitializeComponent()`가 호출된 뒤에 구독해야 한다는 점에 주의합니다. `InitializeComponent()`는 XAML을 읽어 `LoginButton`과 같은 필드를 실제로 채워 넣는 역할을 하므로, 그 전에는 아직 컨트롤 인스턴스가 존재하지 않습니다.

동적으로 컨트롤을 만드는 경우를 예로 들어보겠습니다.

```csharp
private void AddLanguageButton(string language)
{
    var button = new Button { Content = language };
    button.Click += (sender, e) =>
    {
        StatusText.Text = $"{language} 버튼이 클릭되었습니다.";
    };

    LanguagePanel.Children.Add(button);
}
```

이렇게 코드로 생성한 `button`은 애초에 XAML 파일에 존재하지 않으므로 `Click` 속성을 적을 방법이 없습니다. 이런 경우 `+=`로 이벤트를 구독하는 것이 유일한 방법입니다.

이벤트 구독을 더 이상 유지할 필요가 없어지면 `-=` 연산자로 해제합니다.

```csharp
LoginButton.Click -= LoginButton_Click;
```

특히 컨트롤이 화면에서 사라진 뒤에도 이벤트 핸들러가 살아남아 다른 객체를 계속 참조하고 있으면 메모리에서 해제되지 못하는 문제(메모리 누수)로 이어질 수 있습니다. `Window`나 `UserControl` 자신에 붙인 이벤트는 컨트롤과 생명 주기가 같이 끝나므로 크게 문제되지 않지만, 오래 살아있는 객체가 짧게 사는 객체의 이벤트를 구독할 때는 반드시 구독 해제를 고려해야 합니다.

## 6.5 종합 예제: 로그인 폼에 동작 연결하기

지금까지 배운 내용을 모두 활용해서, 5장에서 만든 로그인 폼을 실제로 동작하는 화면으로 완성해 보겠습니다.

```xml
<Window xmlns="https://github.com/avaloniaui"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        x:Class="LoginApp.MainWindow"
        Title="로그인"
        Width="360" Height="440">
    <Border Padding="24">
        <StackPanel Spacing="12">

            <TextBlock Text="계정 로그인"
                       FontSize="20"
                       FontWeight="Bold"
                       HorizontalAlignment="Center" />

            <TextBox x:Name="UsernameBox"
                     Watermark="아이디 또는 이메일" />

            <TextBox x:Name="PasswordBox"
                     Watermark="비밀번호"
                     PasswordChar="●" />

            <ToggleButton x:Name="ShowPasswordToggle"
                          Content="비밀번호 표시"
                          Checked="ShowPasswordToggle_Checked"
                          Unchecked="ShowPasswordToggle_Unchecked" />

            <CheckBox x:Name="RememberMeBox"
                      Content="로그인 상태 유지" />

            <Button x:Name="LoginButton"
                    Content="로그인"
                    Click="LoginButton_Click"
                    HorizontalAlignment="Stretch"
                    HorizontalContentAlignment="Center" />

            <TextBlock x:Name="StatusText"
                       Foreground="Red"
                       TextWrapping="Wrap"
                       HorizontalAlignment="Center" />

        </StackPanel>
    </Border>
</Window>
```

```csharp
using Avalonia.Controls;
using Avalonia.Interactivity;

namespace LoginApp;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }

    private void LoginButton_Click(object? sender, RoutedEventArgs e)
    {
        var username = UsernameBox.Text;
        var password = PasswordBox.Text;

        if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(password))
        {
            StatusText.Text = "아이디와 비밀번호를 모두 입력하세요.";
            return;
        }

        var remember = RememberMeBox.IsChecked == true;
        StatusText.Foreground = Avalonia.Media.Brushes.Green;
        StatusText.Text = remember
            ? $"{username} 님, 환영합니다. 로그인 상태가 유지됩니다."
            : $"{username} 님, 환영합니다.";
    }

    private void ShowPasswordToggle_Checked(object? sender, RoutedEventArgs e)
    {
        PasswordBox.PasswordChar = default;
    }

    private void ShowPasswordToggle_Unchecked(object? sender, RoutedEventArgs e)
    {
        PasswordBox.PasswordChar = '●';
    }
}
```

이제 이 화면은 아이디나 비밀번호가 비어 있으면 경고 문구를 보여주고, 정상적으로 입력했다면 환영 메시지를 보여주며, 토글 버튼으로 비밀번호를 보이거나 가릴 수 있습니다. `Click`, `Checked`, `Unchecked` 세 가지 이벤트를 각각 코드비하인드 메서드에 연결한 것이 이 동작의 전부입니다.

## 6.6 코드비하인드의 한계와 다음 단계

여기까지 배운 방식, 즉 XAML에 `Click="..."`을 적고 `.axaml.cs`에 메서드를 작성하는 방식은 간단하고 직관적입니다. 버튼 하나, 체크박스 하나 정도의 작은 화면에서는 이 정도로도 충분히 실용적입니다.

하지만 화면이 복잡해질수록 이 방식에는 몇 가지 불편함이 드러납니다.

- 화면에 있는 모든 로직이 코드비하인드 클래스 하나에 쌓이면서 파일이 점점 비대해집니다.
- 코드비하인드는 `UsernameBox.Text`, `PasswordBox.Text`처럼 컨트롤 자체를 직접 참조하기 때문에, 화면(뷰)과 로직이 강하게 결합됩니다. UI를 건드리지 않고 로직만 따로 테스트하기가 어렵습니다.
- 같은 로직을 다른 화면에서도 재사용하려면 코드를 복사하거나 억지로 끌어와야 합니다.

이런 문제를 해결하기 위해 Avalonia를 포함한 대부분의 XAML 기반 프레임워크는 **MVVM(Model-View-ViewModel)** 이라는 설계 패턴을 널리 사용합니다. MVVM에서는 화면(View)이 어떤 데이터를 보여줄지는 뷰모델(ViewModel)이라는 별도의 클래스가 책임지고, 뷰는 데이터 바인딩을 통해 뷰모델의 값을 그대로 보여주기만 합니다. 버튼 클릭 같은 사용자 동작도 `Click` 이벤트 대신 `ICommand`라는 추상화를 통해 뷰모델에 전달됩니다.

7장에서는 먼저 데이터 바인딩의 기초를 배우면서 `UsernameBox.Text`를 직접 읽고 쓰는 대신 값이 자동으로 연결되는 방법을 익히고, 8장에서 MVVM 패턴 전체를, 9장에서 `ICommand`를 이용해 `Click` 이벤트 없이 버튼 동작을 연결하는 방법을 배웁니다. 이번 장에서 익힌 이벤트와 라우티드 이벤트의 개념은 MVVM을 사용하더라도 여전히 유효합니다. 커맨드로 표현하기 애매한 저수준 UI 상호작용(예: 드래그, 커스텀 제스처)은 MVVM 환경에서도 결국 이벤트 처리로 귀결되기 때문입니다.

## 요약

- 이벤트 핸들러는 XAML에서 `Click="핸들러이름"`처럼 지정하고, 같은 뷰의 코드비하인드에 `void 핸들러이름(object? sender, RoutedEventArgs e)` 형태의 메서드로 작성합니다.
- Avalonia의 대부분의 UI 이벤트는 라우티드 이벤트이며, 기본적으로 자식에서 부모로 전파되는 버블링 방식을 따릅니다. `e.Handled = true`로 전파를 멈출 수 있습니다.
- `x:Name`이 붙은 컨트롤은 `InitializeComponent()` 호출 이후 코드비하인드에서 필드처럼 바로 사용할 수 있습니다.
- XAML 없이도 `button.Click += 핸들러;` 형태로 코드에서 직접 이벤트를 구독할 수 있으며, 동적으로 생성한 컨트롤에는 이 방식이 유일한 선택지입니다. 더 이상 필요 없는 구독은 `-=`로 해제합니다.
- 코드비하인드 이벤트 처리는 간단한 화면에는 적합하지만, 화면과 로직이 강하게 결합되어 규모가 커지면 유지보수가 어려워집니다. 8장의 MVVM 패턴과 9장의 커맨드는 이 문제를 해결하는 표준적인 방법입니다.

## 연습문제

1. `Button`의 `Click` 이벤트를 XAML에서 연결하는 방법과 코드비하인드에서 `+=`로 직접 구독하는 방법을 각각 코드로 작성하고, 두 방식이 언제 더 유리한지 비교해 보세요.
2. `StackPanel` 안에 `Button` 세 개를 두고, 각 버튼이 아닌 `StackPanel`의 `PointerPressed` 이벤트 하나로 어떤 버튼이 눌렸는지 구분해서 처리하는 코드를 작성해 보세요.
3. 라우티드 이벤트의 버블링과 터널링의 차이를 자신의 말로 설명하고, `e.Handled = true`가 무엇을 멈추는지 예제 코드와 함께 설명해 보세요.
4. 이번 장의 로그인 폼 예제에서 `RememberMeBox`의 `Checked`/`Unchecked` 이벤트를 구독해서, 체크될 때마다 `StatusText`에 현재 체크 상태를 표시하도록 수정해 보세요.
5. 코드비하인드 이벤트 처리 방식의 한계로 이 장에서 언급한 것들을 정리하고, MVVM이 그중 어떤 문제를 어떻게 완화하는지 자신이 이해한 대로 설명해 보세요.

## 문제 상황

한 회사에서 여러 클라우드 서비스 제공사(AWS, Azure, GCP)를 동시에 지원하는 배포 도구를 만든다고 가정해 봅시다. 이 도구는 사용자가 선택한 클라우드에 맞춰 가상 머신, 스토리지, 로드밸런서를 만들어 하나의 애플리케이션 환경을 구성합니다.

문제는 이 세 가지 리소스가 서로 독립적으로 만들어지면 안 된다는 점입니다. AWS용 가상 머신을 만들었다면 스토리지도 AWS용이어야 하고, 로드밸런서도 AWS용이어야 합니다. AWS 가상 머신과 Azure 스토리지를 섞어서 만드는 것은 애초에 말이 되지 않습니다. 즉 "서로 어울려야 하는 제품들의 묶음(제품군, product family)"을 다뤄야 하는 상황입니다.

4장에서 다룬 팩토리 메서드 패턴으로 이 문제를 풀어보려 하면 금방 한계에 부딕힙니다. 가상 머신을 만드는 팩토리 메서드, 스토리지를 만드는 팩토리 메서드, 로드밸런서를 만드는 팩토리 메서드를 각각 따로 호출한다면, 호출하는 쪽에서 실수로 AWS 가상 머신 팩토리와 Azure 스토리지 팩토리를 같이 써버릴 위험이 항상 존재합니다. 코드는 다음과 같은 모습이 될 것입니다.

```csharp
// 문제가 되는 코드: 팩토리들이 서로 아무 관계없이 흩어져 있음
IVirtualMachine vm = new AwsVirtualMachineFactory().Create();
IStorage storage = new AzureStorageFactory().Create(); // 실수! AWS와 Azure가 섞였다
ILoadBalancer lb = new AwsLoadBalancerFactory().Create();
```

컴파일러는 이 실수를 잡아주지 못합니다. 클라우드 제공사가 늘어날수록, 그리고 리소스 종류가 늘어날수록 이런 조합 실수가 발생할 확률도 커집니다. 필요한 것은 "이 제공사 하나를 선택하면, 그 제공사에 속한 리소스들이 항상 통째로 짝을 이루어 만들어진다"는 보장입니다.

## 패턴 설명

추상 팩토리 패턴은 여러 개의 관련된 팩토리 메서드를 하나의 인터페이스로 묶어서, "제품 하나"가 아니라 "서로 어울리는 제품군 전체"를 만들어내는 패턴입니다.

핵심 구성 요소는 다음과 같습니다.

- **추상 제품(Abstract Product)**: `IVirtualMachine`, `IStorage`, `ILoadBalancer`처럼 제품군에 속하는 각 제품의 인터페이스
- **구체 제품(Concrete Product)**: `AwsVirtualMachine`, `AzureStorage`처럼 각 제공사별로 구현된 실제 제품
- **추상 팩토리(Abstract Factory)**: `ICloudResourceFactory`처럼 제품군에 속한 모든 제품을 만드는 메서드를 한데 모은 인터페이스
- **구체 팩토리(Concrete Factory)**: `AwsResourceFactory`, `AzureResourceFactory`처럼 하나의 제공사에 대해 인터페이스의 모든 메서드를 구현한 클래스

클라이언트 코드는 처음에 구체 팩토리 하나만 선택하고, 그 이후로는 오직 추상 팩토리 인터페이스와 추상 제품 인터페이스만 사용합니다. 그러면 한 번 선택된 팩토리에서 나온 제품들은 절대 서로 섞이지 않습니다. 같은 공장에서 나온 부품들만 사용하게 되는 것이죠.

아래 다이어그램은 이 구조를 요약합니다.

```
ICloudResourceFactory (추상 팩토리)
    ├─ CreateVirtualMachine() : IVirtualMachine
    ├─ CreateStorage()        : IStorage
    └─ CreateLoadBalancer()   : ILoadBalancer

AwsResourceFactory   : ICloudResourceFactory  →  AwsVirtualMachine, AwsStorage, AwsLoadBalancer
AzureResourceFactory : ICloudResourceFactory  →  AzureVirtualMachine, AzureStorage, AzureLoadBalancer
```

## C# 예제 코드

먼저 제품군에 속하는 세 가지 제품의 인터페이스를 정의합니다.

```csharp
// 제품군에 속하는 인터페이스들
public interface IVirtualMachine
{
    void Start();
}

public interface IStorage
{
    void Mount();
}

public interface ILoadBalancer
{
    void Route();
}
```

AWS와 Azure 각각에 대한 구체 제품을 만듭니다. 여기서는 콘솔 출력으로 동작을 단순화해서 보여줍니다.

```csharp
// AWS 제품군
public class AwsVirtualMachine : IVirtualMachine
{
    public void Start() => Console.WriteLine("AWS EC2 인스턴스를 시작합니다.");
}

public class AwsStorage : IStorage
{
    public void Mount() => Console.WriteLine("AWS S3 버킷을 마운트합니다.");
}

public class AwsLoadBalancer : ILoadBalancer
{
    public void Route() => Console.WriteLine("AWS ELB로 트래픽을 분산합니다.");
}

// Azure 제품군
public class AzureVirtualMachine : IVirtualMachine
{
    public void Start() => Console.WriteLine("Azure VM을 시작합니다.");
}

public class AzureStorage : IStorage
{
    public void Mount() => Console.WriteLine("Azure Blob Storage를 마운트합니다.");
}

public class AzureLoadBalancer : ILoadBalancer
{
    public void Route() => Console.WriteLine("Azure Load Balancer로 트래픽을 분산합니다.");
}
```

이제 이 세 제품을 한 번에 묶어서 만드는 추상 팩토리와, 제공사별 구체 팩토리를 정의합니다.

```csharp
// 추상 팩토리: 제품군 전체를 만드는 메서드를 한 곳에 모은다
public interface ICloudResourceFactory
{
    IVirtualMachine CreateVirtualMachine();
    IStorage CreateStorage();
    ILoadBalancer CreateLoadBalancer();
}

public class AwsResourceFactory : ICloudResourceFactory
{
    public IVirtualMachine CreateVirtualMachine() => new AwsVirtualMachine();
    public IStorage CreateStorage() => new AwsStorage();
    public ILoadBalancer CreateLoadBalancer() => new AwsLoadBalancer();
}

public class AzureResourceFactory : ICloudResourceFactory
{
    public IVirtualMachine CreateVirtualMachine() => new AzureVirtualMachine();
    public IStorage CreateStorage() => new AzureStorage();
    public ILoadBalancer CreateLoadBalancer() => new AzureLoadBalancer();
}
```

마지막으로 배포 환경을 구성하는 클라이언트 코드는 구체 팩토리 하나만 주입받고, 그 뒤로는 추상 팩토리와 추상 제품만 알면 됩니다.

```csharp
// 클라이언트 코드: 어떤 팩토리를 쓰는지만 결정하면 나머지는 자동으로 통일된다
public class DeploymentEnvironment
{
    private readonly ICloudResourceFactory _factory;

    public DeploymentEnvironment(ICloudResourceFactory factory)
    {
        _factory = factory;
    }

    public void Provision()
    {
        IVirtualMachine vm = _factory.CreateVirtualMachine();
        IStorage storage = _factory.CreateStorage();
        ILoadBalancer lb = _factory.CreateLoadBalancer();

        vm.Start();
        storage.Mount();
        lb.Route();
    }
}

// 사용 예
var env = new DeploymentEnvironment(new AwsResourceFactory());
env.Provision();
// AWS EC2 인스턴스를 시작합니다.
// AWS S3 버킷을 마운트합니다.
// AWS ELB로 트래픽을 분산합니다.
```

`DeploymentEnvironment`는 `AwsResourceFactory`인지 `AzureResourceFactory`인지 몰라도 되고, 두 제공사의 제품이 섞일 가능성 자체가 코드 구조상 차단되어 있습니다. 새로운 제공사(예: GCP)를 추가하려면 `GcpResourceFactory` 하나만 새로 만들면 되고, `DeploymentEnvironment`는 전혀 수정할 필요가 없습니다. 이는 2장에서 다룬 개방-폐쇄 원칙을 그대로 만족하는 결과입니다.

## 팩토리 메서드와 추상 팩토리의 차이

4장의 팩토리 메서드 패턴과 이번 장의 추상 팩토리 패턴은 자주 혼동됩니다. 둘 다 "생성 로직을 캡슐화한다"는 목적은 같지만, 다루는 범위가 다릅니다.

| 구분 | 팩토리 메서드 (4장) | 추상 팩토리 (5장) |
|---|---|---|
| 목적 | 제품 **하나**를 만드는 방법을 서브클래스에 위임 | 서로 관련된 제품 **여러 개(제품군)**를 한 번에 만듦 |
| 구성 | 메서드 하나(또는 소수)를 오버라이드 | 인터페이스 안에 여러 생성 메서드를 모아둠 |
| 관계 보장 | 제품 간 호환성은 신경 쓰지 않음 | 같은 팩토리에서 나온 제품끼리는 항상 호환됨을 보장 |
| 확장 방향 | 제품의 종류를 늘릴 때 서브클래스 추가 | 제품군(제공사, 테마 등) 전체를 늘릴 때 팩토리 클래스 추가 |
| 구현 관계 | 추상 팩토리는 내부적으로 팩토리 메서드를 여러 개 모아놓은 형태로 구현되는 경우가 많음 | 각 생성 메서드 하나하나가 사실상 팩토리 메서드 |

즉 추상 팩토리는 팩토리 메서드를 여러 개 묶어서 "이 묶음은 항상 세트로 움직인다"는 규칙을 추가한 구조라고 볼 수 있습니다. 가상 머신 하나만 만들면 되는 상황이라면 팩토리 메서드로 충분하지만, 가상 머신·스토리지·로드밸런서가 항상 같은 제공사에서 나와야 하는 이번 장의 상황에서는 추상 팩토리가 필요합니다.

## 언제 사용하는가

- 시스템이 여러 개의 제품을 함께 다루는데, 그 제품들이 반드시 같은 "계열(family)"에서 나와야 할 때
- 제품 계열 전체(예: 클라우드 제공사, UI 테마)를 런타임에 교체할 수 있어야 할 때
- 제품 간 잘못된 조합이 코드 상에서 원천적으로 불가능하도록 만들고 싶을 때
- 새로운 계열을 추가하는 일이 기존 계열을 수정하는 일보다 훨씬 자주 일어날 것으로 예상될 때

반대로, 제품이 하나뿐이거나 제품 간에 지켜야 할 조합 규칙이 없다면 추상 팩토리는 과한 설계입니다. 그런 경우에는 4장의 팩토리 메서드나, 더 단순하게는 간단한 정적 생성 메서드로 충분한 경우가 많습니다.

## .NET BCL에서 이 패턴 찾아보기

.NET BCL에서 추상 팩토리 패턴을 가장 잘 보여주는 예는 `System.Data.Common.DbProviderFactory`다. 이 클래스는 이번 장에서 정의한 추상 팩토리의 성격을 정확히 그대로 갖고 있다. `DbProviderFactory` 하나가 `DbConnection`, `DbCommand`, `DbParameter`, `DbDataAdapter`처럼 서로 관련된 "제품군"을 함께 만들어내고, 실제로 어떤 구현체(`SqlClientFactory`, `NpgsqlFactory` 등)를 선택하느냐에 따라 이 제품군 전체가 한꺼번에 바뀐다.

```csharp
// 클라이언트 코드는 DbProviderFactory(추상 팩토리)와
// DbConnection/DbCommand/DbParameter(추상 제품)에만 의존한다.
public class GenericRepository
{
    private readonly DbProviderFactory _factory;
    private readonly string _connectionString;

    public GenericRepository(DbProviderFactory factory, string connectionString)
    {
        _factory = factory;
        _connectionString = connectionString;
    }

    public void QueryUsers()
    {
        // 어떤 데이터베이스 공급자인지 몰라도 항상 같은 제품군끼리 짝을 이룬다.
        using DbConnection connection = _factory.CreateConnection();
        connection.ConnectionString = _connectionString;
        connection.Open();

        using DbCommand command = _factory.CreateCommand();
        command.Connection = connection;
        command.CommandText = "SELECT Name FROM Users";

        DbParameter parameter = _factory.CreateParameter();
        parameter.ParameterName = "@minId";
        parameter.Value = 1;
        command.Parameters.Add(parameter);

        using DbDataReader reader = command.ExecuteReader();
        while (reader.Read())
        {
            Console.WriteLine(reader.GetString(0));
        }
    }
}

// 사용 예: 팩토리 인스턴스 하나만 바꾸면 전체 제품군이 함께 교체된다.
// var repository = new GenericRepository(SqlClientFactory.Instance, connectionString);
```

`GenericRepository`는 `SqlClientFactory`를 쓰는지 `NpgsqlFactory`를 쓰는지 전혀 몰라도 되고, `CreateConnection()`이 만든 커넥션과 `CreateCommand()`가 만든 커맨드가 서로 다른 데이터베이스 공급자용으로 섞일 가능성도 코드 구조상 차단된다. 이는 이 장 앞부분에서 살펴본 클라우드 리소스 예제에서 `ICloudResourceFactory` 하나를 선택하면 가상 머신·스토리지·로드밸런서가 항상 같은 제공사로 통일되는 것과 동일한 원리다. 4장에서 잠깐 언급했던 `DbProviderFactory.CreateConnection()`, `CreateCommand()` 같은 개별 `CreateXxx()` 메서드들은, 이렇게 하나의 팩토리 인터페이스로 묶여야 비로소 추상 팩토리 패턴의 진짜 가치가 드러난다는 점을 확인할 수 있다.

## 요약

추상 팩토리 패턴은 서로 관련된 여러 제품을 하나의 팩토리 인터페이스로 묶어서, 제품 계열 전체를 안전하게 교체할 수 있게 해주는 패턴입니다. 클라이언트는 구체 팩토리 하나만 선택하면 되고, 그 이후로는 어떤 제품이 나오든 같은 계열 안에서 항상 호환이 보장됩니다. 팩토리 메서드가 제품 하나의 생성을 캡슐화하는 데 초점을 둔다면, 추상 팩토리는 여러 팩토리 메서드를 묶어 "이 제품들은 항상 세트로 취급되어야 한다"는 제약을 코드로 강제합니다. 클라우드 제공사, UI 테마, 지역별 정책처럼 "함께 가야 하는 것들의 집합"이 여러 벌 존재하는 상황에서 특히 유용합니다.

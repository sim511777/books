## 문제 상황

건설 회사의 설계 도면 관리 시스템을 개발한다고 해보자. 이 시스템은 프로젝트를 열면 그 프로젝트에 속한 모든 설계 도면 목록을 보여주고, 사용자가 목록에서 도면 하나를 클릭하면 해당 도면을 화면에 그린다.

문제는 도면 하나의 데이터가 매우 크다는 점이다. 하나의 CAD 도면 파일을 읽어서 화면에 그릴 수 있는 형태로 변환하는 작업은 디스크에서 수백 메가바이트를 읽고, 벡터 좌표를 파싱하고, 레이어별로 렌더링 정보를 구성하는 과정을 거친다. 이 작업에는 수 초가 걸린다.

처음에는 프로젝트를 열 때 도면 목록에 있는 도면들을 전부 미리 로딩하도록 만들었다.

```csharp
public class RealDocumentLoader : IDocumentLoader
{
    private readonly string _filePath;
    private readonly byte[] _vectorData;

    public RealDocumentLoader(string filePath)
    {
        _filePath = filePath;
        _vectorData = LoadAndParse(filePath); // 수 초가 걸리는 무거운 작업
    }

    public void Render()
    {
        // _vectorData를 화면에 그린다
    }

    private byte[] LoadAndParse(string filePath) => File.ReadAllBytes(filePath); // 예시 단순화
}
```

프로젝트 하나에 도면이 40개 있다면, 프로젝트를 여는 순간 40개의 `RealDocumentLoader`가 한꺼번에 생성되면서 파일을 전부 읽고 파싱한다. 사용자는 실제로는 그중 두세 개만 열어볼 뿐인데, 화면이 뜨기까지 1분 가까이 걸리는 문제가 생겼다.

원하는 동작은 이렇다. 도면 목록에는 가벼운 항목만 표시하고, 사용자가 실제로 특정 도면을 클릭해서 열어볼 때만 그 도면에 대해 무거운 로딩 작업을 수행해야 한다. 그리고 한 번 로딩한 도면은 다시 클릭했을 때 또 로딩하지 않고 재사용해야 한다. 게다가 일부 도면은 보안 등급이 있어서, 열람 권한이 없는 사용자는 애초에 로딩을 시도조차 못하게 막아야 한다.

## 패턴 설명

프록시 패턴은 실제 객체(**RealSubject**)와 똑같은 인터페이스를 구현하는 대리자 객체(**Proxy**)를 만들고, 클라이언트가 실제 객체 대신 이 대리자를 사용하게 하는 패턴이다. 클라이언트는 자신이 다루는 것이 진짜 객체인지 대리자인지 구분할 필요가 없다. 둘 다 같은 인터페이스를 구현하기 때문이다.

프록시는 실제 객체로 향하는 요청을 그대로 전달하기 전에 무언가를 끼워 넣을 수 있는 지점이다. 대표적으로 다음과 같은 종류가 있다.

- **가상 프록시(virtual proxy)**: 생성 비용이 큰 객체를 실제로 필요한 시점까지 미루고, 그 전까지는 가벼운 대리자로 버틴다. 위 도면 뷰어 예제가 여기에 해당한다.
- **보호 프록시(protection proxy)**: 요청을 실제 객체에 전달하기 전에 호출자가 그 작업을 수행할 권한이 있는지 검사한다.
- **원격 프록시(remote proxy)**: 실제 객체가 다른 프로세스나 다른 서버에 있을 때, 로컬에 있는 것처럼 보이게 통신을 대신 처리한다.

이번 장에서는 가상 프록시를 중심으로 다루되, 보호 프록시의 권한 검사 로직도 같은 프록시 안에 함께 넣어서 두 가지가 자연스럽게 섞일 수 있음을 보여준다.

구조는 세 요소로 이루어진다.

- `IDocumentLoader`: 실제 객체와 프록시가 공통으로 구현하는 인터페이스.
- `RealDocumentLoader`: 실제로 무거운 작업을 수행하는 객체.
- `DocumentProxy`: `IDocumentLoader`를 구현하지만 내부적으로는 `RealDocumentLoader`를 필요한 시점에만 생성해서 위임하는 대리자.

이 관계를 그림으로 나타내면 다음과 같다.

```text
                          +--------------------------+
                          |     <<interface>>        |
                          |     IDocumentLoader       |
                          |   + Render()              |
                          +--------------------------+
                              ^                  ^
                              : (구현)            : (구현)
                              :                  :
  +----------+  참조/호출   +----------------+     +------------------------+
  |  Client  | ---------> |  DocumentProxy  | --> |  RealDocumentLoader      |
  | (클라이언트|            | - _realLoader   |위임 |  + Render()             |
  |   코드)   |            | + Render()      |     |  (실제 대용량 로딩 수행)   |
  +----------+            | (접근 제어 ·      |     |  생성 비용이 큼          |
                           |  지연 생성)       |     +------------------------+
                           +----------------+

  둘 다 같은 인터페이스를 구현

  그림 설명
  Client는 IDocumentLoader 타입으로 변수를 선언하지만, 실제로 담기는 것은
  RealDocumentLoader가 아니라 DocumentProxy다.
  Render() 호출을 받은 프록시는 접근 권한을 검사하거나, 필요한 시점에 비로소
  RealDocumentLoader를 생성한 뒤 그 인스턴스에 실제 작업을 위임(delegation)한다.
  Client는 프록시를 거치고 있다는 사실을 전혀 알 필요가 없다.
```

## C# 예제 코드

```csharp
// 실제 객체와 프록시가 함께 구현할 인터페이스
public interface IDocumentLoader
{
    void Render();
}

// 실제로 무거운 파일 로딩과 파싱을 수행하는 클래스
// 생성자를 호출하는 순간 비용이 큰 작업이 일어난다
public class RealDocumentLoader : IDocumentLoader
{
    private readonly string _filePath;

    public RealDocumentLoader(string filePath)
    {
        _filePath = filePath;
        Console.WriteLine($"[로딩 시작] '{_filePath}' 파일을 읽고 파싱하는 중... (수 초 소요)");
        System.Threading.Thread.Sleep(500); // 무거운 작업을 흉내 낸 지연
        Console.WriteLine($"[로딩 완료] '{_filePath}'");
    }

    public void Render()
    {
        Console.WriteLine($"'{_filePath}' 도면을 화면에 그립니다.");
    }
}

// 접근을 대리하는 프록시. 인터페이스는 RealDocumentLoader와 동일하다.
public class DocumentProxy : IDocumentLoader
{
    private readonly string _filePath;
    private readonly string _requiredRole;
    private readonly string _currentUserRole;
    private RealDocumentLoader _realLoader; // 실제로 필요할 때까지 null로 남아있다

    public DocumentProxy(string filePath, string requiredRole, string currentUserRole)
    {
        _filePath = filePath;
        _requiredRole = requiredRole;
        _currentUserRole = currentUserRole;
    }

    public void Render()
    {
        // 1) 보호 프록시 역할: 권한 검사를 실제 로딩보다 먼저 수행한다
        if (_currentUserRole != _requiredRole && _currentUserRole != "관리자")
        {
            Console.WriteLine($"[접근 거부] '{_filePath}'는 '{_requiredRole}' 권한이 필요합니다.");
            return;
        }

        // 2) 가상 프록시 역할: 실제로 필요한 시점에만 RealDocumentLoader를 생성한다
        if (_realLoader == null)
        {
            _realLoader = new RealDocumentLoader(_filePath);
        }
        else
        {
            Console.WriteLine($"[재사용] '{_filePath}'는 이미 로딩되어 있어 다시 읽지 않습니다.");
        }

        // 3) 실제 작업은 실제 객체에 위임한다
        _realLoader.Render();
    }
}

public class DocumentViewer
{
    public static void Main()
    {
        // 프로젝트를 열 때는 가벼운 프록시만 40개 만든다. 실제 파일 로딩은 일어나지 않는다.
        var drawings = new List<IDocumentLoader>
        {
            new DocumentProxy("1층_평면도.dwg", requiredRole: "일반", currentUserRole: "일반"),
            new DocumentProxy("배관_설계도.dwg", requiredRole: "설계팀", currentUserRole: "일반"),
            new DocumentProxy("전기_배선도.dwg", requiredRole: "설계팀", currentUserRole: "설계팀"),
        };

        Console.WriteLine("=== 프로젝트 화면 진입 (아직 아무 도면도 로딩되지 않음) ===\n");

        Console.WriteLine("--- 사용자가 '1층_평면도'를 클릭 ---");
        drawings[0].Render();

        Console.WriteLine("\n--- 사용자가 '배관_설계도'를 클릭 (권한 없음) ---");
        drawings[1].Render();

        Console.WriteLine("\n--- 사용자가 '1층_평면도'를 다시 클릭 (캐시된 결과 재사용) ---");
        drawings[0].Render();

        Console.WriteLine("\n--- 사용자가 '전기_배선도'를 클릭 (권한 있음) ---");
        drawings[2].Render();
    }
}
```

이 코드에서 `DocumentViewer`는 `IDocumentLoader` 타입만 알고 있을 뿐, 각 항목이 실제로는 `DocumentProxy`라는 사실을 신경 쓰지 않는다. 프록시는 클릭이 일어나기 전까지 실제 로딩을 미루고, 권한이 없으면 로딩 자체를 시도하지 않으며, 이미 로딩된 도면은 다시 읽지 않고 캐시된 `_realLoader`를 재사용한다.

## 데코레이터와 무엇이 다른가

11장 데코레이터도 프록시처럼 실제 객체와 같은 인터페이스를 구현하고 그 객체를 감싸는 구조를 쓴다. 코드 모양만 보면 둘은 거의 똑같아 보일 수 있어서 혼동하기 쉽지만, 목적이 근본적으로 다르다.

| 구분 | 프록시(Proxy) | 데코레이터(Decorator) |
|---|---|---|
| 목적 | 실제 객체에 대한 **접근을 제어**한다 | 실제 객체에 **새로운 기능을 추가**한다 |
| 실제 객체 존재 여부 | 실제 객체가 아예 생성되지 않을 수도 있다(가상 프록시) | 감싸는 대상 객체는 이미 존재하는 것이 보통이다 |
| 중첩 | 보통 단일 계층 — 프록시 하나가 실제 객체 하나를 대리한다 | 여러 데코레이터를 겹겹이 쌓아 기능을 조합하는 것이 흔하다 |
| 클라이언트의 인식 | 클라이언트는 프록시를 거치고 있다는 사실 자체를 몰라야 한다 | 클라이언트는 보통 "장식된 객체"를 의도적으로 조립한다 |
| 대표 사례 | 지연 로딩, 권한 검사, 원격 호출 대리 | 로깅 추가, 압축 추가, 입력 검증 추가처럼 책임을 덧붙이는 경우 |

한 문장으로 요약하면, 프록시는 "이 객체에 접근해도 되는가, 언제 접근할 것인가"를 다루고, 데코레이터는 "이 객체가 무엇을 더 할 수 있는가"를 다룬다.

## 언제 사용하는가

프록시는 다음과 같은 상황에서 특히 유용하다.

- 객체를 생성하는 비용이 커서, 실제로 쓰일 때까지 생성을 미루고 싶을 때(가상 프록시). 이번 장의 도면 예제가 대표적이다.
- 객체에 대한 접근을 역할이나 권한에 따라 제한해야 할 때(보호 프록시). 관리자만 열 수 있는 설정 화면, 등급이 높은 사용자만 볼 수 있는 리포트 등이 해당한다.
- 실제 객체가 다른 서버나 프로세스에 있어서, 네트워크 호출을 로컬 호출처럼 감싸야 할 때(원격 프록시). 흔히 쓰는 gRPC나 WCF의 클라이언트 스텁도 이 개념에 가깝다.
- 객체에 대한 접근 자체를 로깅하거나 캐싱해야 할 때도 프록시로 처리할 수 있다.

다만 접근을 제어할 필요가 전혀 없는 단순한 객체에 프록시를 씌우면 계층만 하나 더 늘어나 코드를 읽기 어렵게 만든다. 정말로 "생성을 미뤄야 한다" 혹은 "접근을 검사해야 한다"는 요구가 있을 때만 프록시를 도입하는 것이 좋다.

## .NET BCL에서 이 패턴 찾아보기

가상 프록시는 이론으로만 존재하는 개념이 아니다. Entity Framework(EF Core 및 EF6)의 지연 로딩(lazy loading) 프록시가 산업 현장에서 널리 쓰이는 실제 사례다.

엔터티 클래스의 탐색 속성(navigation property)을 `virtual`로 선언해두면, EF는 런타임에 그 엔터티 클래스를 상속하는 동적 프록시 클래스를 생성한다.

```csharp
public class Order
{
    public int Id { get; set; }
    public DateTime OrderDate { get; set; }

    // virtual로 선언하면 EF가 이 속성 접근을 가로채는 동적 프록시를 만들 수 있다
    public virtual Customer Customer { get; set; }
}

// 사용하는 쪽 코드
var order = dbContext.Orders.Find(orderId);
// 이 시점까지는 Customer에 대한 쿼리가 실행되지 않는다

Console.WriteLine(order.Customer.Name);
// Customer 속성에 처음 접근하는 순간, 프록시가 가로채서
// 그제야 실제 데이터베이스 쿼리를 실행하고 결과를 채워 넣는다
```

여기서 `dbContext`가 실제로 반환하는 `order` 객체는 우리가 정의한 `Order` 클래스 그대로가 아니라, EF가 런타임에 만들어낸 `Order`의 하위 클래스(프록시)다. 이 프록시는 `Order`와 동일한 인터페이스(정확히는 동일한 공개 API)를 가지므로 클라이언트 코드는 자신이 프록시를 다루고 있다는 사실을 전혀 몰라도 된다. `Customer` 속성에 처음 접근하는 순간에만 실제 SQL 쿼리를 실행해 데이터를 채우고, 그 전까지는 무거운 로딩을 미룬다.

이는 이번 장의 `DocumentProxy`가 `Render`를 호출하기 전까지 `RealDocumentLoader` 생성을 미루는 것과 정확히 같은 발상이다. 차이는 `DocumentProxy`는 우리가 직접 작성한 클래스인 반면, EF의 프록시는 프레임워크가 런타임에 동적으로 생성해 준다는 점뿐이다. 비슷한 개념의 또 다른 예로 WCF의 `ChannelFactory<T>`가 만들어내는 클라이언트 프록시도 있는데, 이쪽은 원격 프록시에 가깝다. 로컬 인터페이스를 호출하는 것처럼 보이지만 실제로는 그 뒤에서 네트워크 통신을 대신 처리해 준다.

## 요약

- 프록시 패턴은 실제 객체와 동일한 인터페이스를 구현하는 대리자를 두어, 클라이언트가 실제 객체에 접근하는 방식을 제어한다.
- 가상 프록시는 생성 비용이 큰 객체의 생성을 실제로 필요한 시점까지 미루고, 보호 프록시는 접근 전에 권한을 검사한다. 하나의 프록시 안에서 두 역할을 함께 수행할 수도 있다.
- 클라이언트는 프록시와 실제 객체를 구분하지 않고 동일한 인터페이스로 다루므로, 프록시를 끼워 넣어도 클라이언트 코드는 바뀌지 않는다.
- 데코레이터와 구조가 비슷해 보이지만, 프록시는 접근 제어가 목적이고 데코레이터는 기능 추가가 목적이라는 점에서 근본적으로 다르다.

## 연습문제

1. 온라인 쇼핑몰의 상품 상세 페이지에서, 상품에 달린 수백 개의 리뷰 이미지를 스크롤해서 실제로 보게 되는 순간에만 원본 이미지를 불러오고 싶다. 이 상황에 맞는 가상 프록시 클래스를 설계해 보라. 어떤 인터페이스를 공유해야 하는가?
2. 이번 장의 `DocumentProxy`는 권한 검사를 먼저 하고 나서 로딩을 수행한다. 만약 반대로 "권한이 있는 사용자에 대해서만 캐싱을 적용하고, 권한이 없는 사용자의 요청은 매번 거부 로그를 남겨야 한다"는 요구가 추가된다면 코드를 어떻게 수정해야 하는가?
3. 원격 프록시를 C#으로 흉내 내보라. `IWeatherService`라는 인터페이스가 있고, `RemoteWeatherServiceProxy`가 실제로는 HTTP 호출을 통해 원격 서버의 날씨 정보를 가져온다고 가정하고 클래스 뼈대를 작성하라.
4. 프록시 패턴과 12장 퍼사드는 둘 다 다른 객체 앞에 위치하는 구조를 가진다. 두 패턴의 목적이 어떻게 다른지 설명해 보라.
5. 이번 장의 `DocumentProxy`에서 `_realLoader`를 캐싱하는 대신, 사용자가 명시적으로 "새로고침"을 요청하면 다시 로딩하도록 기능을 추가하려면 어떤 메서드를 더 추가해야 하는가?

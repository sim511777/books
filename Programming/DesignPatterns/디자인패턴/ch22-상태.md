## 문제 상황

온라인 서점의 주문 처리 시스템을 만든다고 해보자. 주문은 다음과 같은 상태를 거친다.

- **대기(Waiting)**: 주문이 생성되었지만 아직 결제되지 않았다.
- **결제완료(Paid)**: 결제가 끝나서 배송 준비가 가능하다.
- **배송중(Shipping)**: 택배가 출고되어 이동 중이다.
- **배송완료(Delivered)**: 고객에게 전달이 끝났다.
- **취소(Cancelled)**: 주문이 취소되었다.

그리고 상태마다 허용되는 동작이 다르다. 대기 상태에서는 결제나 취소가 가능하지만 배송을 시작할 수는 없다. 배송중 상태에서는 취소가 불가능하다. 배송완료 상태에서는 어떤 동작도 다시 일어날 수 없다. 처음에는 `Order` 클래스에 상태를 `enum`으로 두고, 각 동작 메서드마다 `switch`문으로 분기하는 방식으로 구현했다.

```csharp
public enum OrderStatus { Waiting, Paid, Shipping, Delivered, Cancelled }

public class Order
{
    public OrderStatus Status { get; private set; } = OrderStatus.Waiting;

    public void Pay()
    {
        switch (Status)
        {
            case OrderStatus.Waiting:
                Status = OrderStatus.Paid;
                Console.WriteLine("결제가 완료되었습니다.");
                break;
            case OrderStatus.Paid:
                Console.WriteLine("이미 결제된 주문입니다.");
                break;
            default:
                Console.WriteLine($"{Status} 상태에서는 결제할 수 없습니다.");
                break;
        }
    }

    public void Ship()
    {
        switch (Status)
        {
            case OrderStatus.Paid:
                Status = OrderStatus.Shipping;
                Console.WriteLine("배송을 시작합니다.");
                break;
            default:
                Console.WriteLine($"{Status} 상태에서는 배송을 시작할 수 없습니다.");
                break;
        }
    }

    public void Deliver()
    {
        switch (Status)
        {
            case OrderStatus.Shipping:
                Status = OrderStatus.Delivered;
                Console.WriteLine("배송이 완료되었습니다.");
                break;
            default:
                Console.WriteLine($"{Status} 상태에서는 배송완료 처리를 할 수 없습니다.");
                break;
        }
    }

    public void Cancel()
    {
        switch (Status)
        {
            case OrderStatus.Waiting:
            case OrderStatus.Paid:
                Status = OrderStatus.Cancelled;
                Console.WriteLine("주문이 취소되었습니다.");
                break;
            default:
                Console.WriteLine($"{Status} 상태에서는 취소할 수 없습니다.");
                break;
        }
    }
}
```

메서드 네 개가 전부 비슷한 모양의 `switch`문을 하나씩 가지고 있다. 여기에 "환불(Refunded)"이라는 상태가 추가된다고 해보자. `Cancel`뿐 아니라 배송완료 이후에만 환불이 가능하다는 새 규칙까지 생기면, `Pay`, `Ship`, `Deliver`, `Cancel` 네 메서드의 `switch`문을 전부 열어서 새 케이스를 끼워 넣어야 하고, `Refund`라는 다섯 번째 메서드에도 똑같은 모양의 `switch`문을 새로 작성해야 한다. 상태가 늘어날수록 이런 `switch`문이 메서드 수만큼 늘어나 계속 반복되고, 어느 한 곳에서 분기 처리를 빠뜨리면 "취소된 주문인데 배송이 시작되는" 것 같은 버그가 조용히 발생한다. 상태에 따른 규칙이 한 곳에 모여 있지 않고 메서드마다 흩어져 있다는 것이 근본적인 문제다.

## 패턴 설명

상태 패턴은 객체가 가질 수 있는 각각의 상태를 별도의 클래스로 만들고, 원래 객체(**Context**)는 그 상태 객체에게 행동을 위임하는 방식으로 이 문제를 해결한다. `Order`는 더 이상 `enum`과 `switch`문으로 상태를 다루지 않고, 현재 상태를 나타내는 객체 하나(`IOrderState`)를 들고 있다가 모든 요청을 그 객체에게 그대로 넘긴다.

핵심은 상태 전환의 책임도 Context가 아니라 상태 객체 자신에게 있다는 점이다. `WaitingState`는 `Pay()`가 호출되면 "다음 상태는 `PaidState`다"라는 것을 스스로 알고 있고, Context의 현재 상태를 그 `PaidState` 인스턴스로 바꿔 버린다. Context는 "지금 상태 객체에게 위임한다"는 사실만 알 뿐, 상태들이 서로 어떻게 이어지는지는 알 필요가 없다.

구성 요소는 다음과 같다.

- **IOrderState**: 상태마다 달라지는 행동(`Pay`, `Ship`, `Deliver`, `Cancel`)을 정의하는 인터페이스.
- **ConcreteState** (`WaitingState`, `PaidState`, `ShippingState`, `DeliveredState`, `CancelledState`): 각 상태에서 허용되는 동작과, 허용될 때 다음에 어떤 상태로 넘어갈지를 구현한다.
- **Order (Context)**: 현재 상태 객체에 대한 참조를 들고 있고, 모든 공개 메서드를 그 상태 객체에 위임한다.

## C# 예제 코드

```csharp
// 상태마다 달라지는 행동을 정의하는 인터페이스
// Order 자신을 인자로 받아, 상태 전환이 필요하면 order.State를 직접 바꾼다
public interface IOrderState
{
    void Pay(Order order);
    void Ship(Order order);
    void Deliver(Order order);
    void Cancel(Order order);
    string Name { get; }
}

public class WaitingState : IOrderState
{
    public string Name => "대기";

    public void Pay(Order order)
    {
        Console.WriteLine("결제가 완료되었습니다.");
        order.State = new PaidState(); // 다음 상태를 스스로 결정한다
    }

    public void Ship(Order order) => Console.WriteLine("결제 전에는 배송을 시작할 수 없습니다.");

    public void Deliver(Order order) => Console.WriteLine("결제 전에는 배송완료 처리를 할 수 없습니다.");

    public void Cancel(Order order)
    {
        Console.WriteLine("주문이 취소되었습니다.");
        order.State = new CancelledState();
    }
}

public class PaidState : IOrderState
{
    public string Name => "결제완료";

    public void Pay(Order order) => Console.WriteLine("이미 결제된 주문입니다.");

    public void Ship(Order order)
    {
        Console.WriteLine("배송을 시작합니다.");
        order.State = new ShippingState();
    }

    public void Deliver(Order order) => Console.WriteLine("아직 배송이 시작되지 않았습니다.");

    public void Cancel(Order order)
    {
        Console.WriteLine("결제완료 상태에서 주문이 취소되었습니다. 환불이 진행됩니다.");
        order.State = new CancelledState();
    }
}

public class ShippingState : IOrderState
{
    public string Name => "배송중";

    public void Pay(Order order) => Console.WriteLine("이미 결제된 주문입니다.");

    public void Ship(Order order) => Console.WriteLine("이미 배송이 진행 중입니다.");

    public void Deliver(Order order)
    {
        Console.WriteLine("배송이 완료되었습니다.");
        order.State = new DeliveredState();
    }

    public void Cancel(Order order) => Console.WriteLine("배송이 시작된 주문은 취소할 수 없습니다.");
}

public class DeliveredState : IOrderState
{
    public string Name => "배송완료";

    public void Pay(Order order) => Console.WriteLine("이미 완료된 주문입니다.");
    public void Ship(Order order) => Console.WriteLine("이미 배송이 완료되었습니다.");
    public void Deliver(Order order) => Console.WriteLine("이미 배송이 완료되었습니다.");
    public void Cancel(Order order) => Console.WriteLine("배송완료 후에는 취소할 수 없습니다. 환불 절차를 이용하세요.");
}

public class CancelledState : IOrderState
{
    public string Name => "취소";

    public void Pay(Order order) => Console.WriteLine("취소된 주문입니다.");
    public void Ship(Order order) => Console.WriteLine("취소된 주문입니다.");
    public void Deliver(Order order) => Console.WriteLine("취소된 주문입니다.");
    public void Cancel(Order order) => Console.WriteLine("이미 취소된 주문입니다.");
}

// Context: 현재 상태 객체에게 모든 동작을 위임한다
public class Order
{
    public IOrderState State { get; set; } = new WaitingState();

    public void Pay() => State.Pay(this);
    public void Ship() => State.Ship(this);
    public void Deliver() => State.Deliver(this);
    public void Cancel() => State.Cancel(this);

    public void PrintStatus() => Console.WriteLine($"현재 상태: {State.Name}");
}
```

사용하는 코드는 이렇다.

```csharp
var order = new Order();
order.PrintStatus();   // 현재 상태: 대기

order.Ship();          // 결제 전에는 배송을 시작할 수 없습니다.
order.Pay();           // 결제가 완료되었습니다.
order.PrintStatus();   // 현재 상태: 결제완료

order.Ship();          // 배송을 시작합니다.
order.Cancel();        // 배송이 시작된 주문은 취소할 수 없습니다.
order.Deliver();       // 배송이 완료되었습니다.
order.PrintStatus();   // 현재 상태: 배송완료
```

`Order` 클래스에는 더 이상 `switch`문이 하나도 없다. 각 상태에서 허용되는 동작과 다음 상태로의 전환 규칙은 그 상태를 나타내는 클래스 안에 모여 있다. "환불" 상태가 추가되어야 한다면 `RefundedState` 클래스를 새로 만들고, `DeliveredState.Cancel`이 `order.State = new RefundedState()`로 전환하도록 한 줄만 바꾸면 된다. 다른 상태 클래스들은 전혀 건드릴 필요가 없다. 이는 2장에서 다룬 개방-폐쇄 원칙(OCP)을 그대로 만족하는 구조다.

상태 사이의 전환 관계를 그림으로 나타내면 다음과 같다.

```text
   ( 대기 )  --결제(Pay)--> ( 결제완료 ) --배송시작(Ship)--> ( 배송중 ) --배송완료(Deliver)--> ( 배송완료 )
  WaitingState              PaidState                 ShippingState                 DeliveredState
      |                        |                            |                             |
      | 취소(Cancel)            | 취소(Cancel)                | 취소(Cancel) -> 거부           | 모든 동작 -> 거부
      v                        v
   ( 취소 )  <------------------
  CancelledState

  그림 설명
  각 원은 상태 클래스 하나를 나타내며, 화살표는 해당 동작이 호출되었을 때
  상태 객체 스스로가 결정하는 다음 상태를 가리킨다.
  배송중과 배송완료 상태에서는 취소가 허용되지 않으며, 이 규칙은 각 상태
  클래스의 Cancel() 메서드 안에 있다.
```

## 전략 패턴과 무엇이 다른가

23장에서 다루는 전략 패턴도 Context가 인터페이스 타입의 필드를 들고 그 객체에게 행동을 위임하는 구조를 쓴다. 코드 구조만 놓고 보면 상태 패턴과 전략 패턴은 거의 구분이 안 될 정도로 닮아 있다. 둘 다 "인터페이스를 구현하는 객체를 필드로 들고 있다가 메서드 호출을 그 객체에 위임한다"는 형태를 취하기 때문이다. 하지만 의도는 분명히 다르다.

| 구분 | 상태(State) | 전략(Strategy) |
|---|---|---|
| 핵심 목적 | 시간에 따른 **상태 전환**을 표현한다 | 서로 대체 가능한 **알고리즘을 교체**한다 |
| 전환의 주체 | 상태 객체 자신이 다음 상태를 결정하고 전환시킨다 | 전략 객체는 다른 전략으로 스스로 바뀌지 않는다 |
| 교체 시점과 주도자 | Context 내부에서, 동작의 결과로 자연스럽게 일어난다 | 클라이언트가 명시적으로 전략을 선택하거나 바꾼다 |
| 객체 사이의 인지 | 상태 객체들은 서로의 존재를 알고 있는 경우가 많다(다음 상태를 생성하므로) | 전략 객체들은 서로의 존재를 전혀 모른다 |
| 대표 사례 | 주문 상태, TCP 연결 상태, 신호등 | 정렬 알고리즘 선택, 할인 정책 선택, 압축 방식 선택 |

한 문장으로 요약하면, 상태 패턴은 "이 객체가 지금 어떤 국면에 있고, 그 국면이 어떻게 바뀌어 가는가"를 다루고, 전략 패턴은 "이 작업을 수행하는 여러 방법 중 무엇을 쓸 것인가"를 다룬다. 이번 장의 `WaitingState`가 `Pay` 호출의 결과로 `PaidState`라는 다른 구현체를 생성해서 스스로를 대체하는 부분이, 전략 패턴에서는 결코 일어나지 않는 지점이다.

## 언제 사용하는가

- 객체의 행동이 몇 가지 뚜렷이 구분되는 국면(상태)에 따라 크게 달라지고, 상태마다 허용되는 동작의 집합이 다를 때.
- 상태 전환 규칙이 복잡해서 하나의 `switch`문이나 `if`문 체인으로 표현하면 여러 메서드에 걸쳐 같은 조건 분기가 반복될 때. 이번 장의 주문 예제가 그런 경우다.
- 새로운 상태가 추가될 가능성이 높고, 기존 상태 클래스는 건드리지 않으면서 확장하고 싶을 때.
- 반대로 상태가 두세 가지뿐이고 앞으로도 늘어날 가능성이 거의 없다면, 상태 패턴을 도입하는 것이 오히려 클래스 개수만 늘리는 과잉 설계가 될 수 있다. 이런 경우는 `enum`과 짧은 `switch`문으로 충분하다.

## .NET BCL에서 이 패턴 찾아보기

.NET BCL 안에서 상태 패턴을 그대로 구현한 뚜렷한 공개 클래스를 찾기는 어렵다. 하지만 C# 컴파일러 자체가 `async`/`await`를 컴파일할 때 상태 패턴과 매우 비슷한 방식을 쓴다는 사실은 눈여겨볼 만하다.

`async` 메서드를 작성하면, 컴파일러는 그 메서드를 우리가 직접 보는 코드가 아니라 `IAsyncStateMachine`이라는 인터페이스를 구현하는 클래스(또는 구조체)로 변환한다. 이 인터페이스는 `MoveNext()`라는 메서드 하나를 정의하는데, `await` 지점을 만날 때마다 컴파일러가 생성한 내부 필드(정수 값의 상태 번호)가 바뀌고, 다음번에 `MoveNext()`가 호출되면 그 상태 값에 따라 실행이 이어질 지점이 달라진다.

```csharp
// 우리가 작성하는 코드
public async Task<string> FetchOrderStatusAsync(int orderId)
{
    var order = await _repository.GetOrderAsync(orderId);   // await 지점 1
    var status = await _shippingApi.GetStatusAsync(order);  // await 지점 2
    return status;
}

// 컴파일러가 실제로 생성하는 것은 대략 이런 모양이다 (간략화)
private struct FetchOrderStatusAsyncStateMachine : IAsyncStateMachine
{
    public int State; // 지금 어느 await 지점까지 진행했는지 나타내는 상태 값
    // ... 그 밖에 지역 변수, awaiter 필드 등이 들어간다

    public void MoveNext()
    {
        switch (State) // 현재 상태에 따라 다른 동작을 수행한다
        {
            case 0:
                // GetOrderAsync 호출 후 대기, 완료되면 State = 1로 전환
                break;
            case 1:
                // GetStatusAsync 호출 후 대기, 완료되면 State = 2로 전환
                break;
            case 2:
                // 결과를 반환하고 완료 처리
                break;
        }
    }
}
```

이 구조는 이번 장에서 만든 `WaitingState`, `PaidState` 같은 상태 클래스들이 "현재 상태에 따라 동작이 달라지고, 동작의 결과로 다음 상태로 전환된다"는 것과 본질적으로 같다. 차이는 우리가 상태마다 별도의 클래스(`ConcreteState`)를 만든 반면, 컴파일러는 하나의 상태 기계 안에 정수 값과 `switch`문으로 상태를 표현한다는 점뿐이다. 흥미롭게도 이는 이번 장 서두에서 우리가 버렸던 "enum과 switch문" 방식과 오히려 닮아 있다. 컴파일러가 자동으로 생성하는 코드이므로 사람이 유지보수할 필요가 없고, 상태 전이가 순차적이며 상태 개수도 코드 흐름에 따라 정해지는 이런 경우에는 이런 방식도 충분히 합리적인 선택이 될 수 있다.

## 요약

- 상태 패턴은 객체가 가질 수 있는 각 상태를 별도의 클래스로 만들고, Context가 현재 상태 객체에게 행동을 위임하는 구조다.
- 여러 메서드에 반복되는 `switch`문 대신, 상태별 규칙과 전환 로직을 해당 상태 클래스 안에 모아둘 수 있다.
- 상태 전환의 책임은 Context가 아니라 상태 객체 자신에게 있다. 상태 객체는 자신이 처리한 요청의 결과로 다음 상태를 결정하고 Context의 상태를 바꾼다.
- 23장의 전략 패턴과 구조는 비슷하지만, 상태 패턴은 전환이 핵심이고 전략 패턴은 알고리즘 교체가 핵심이라는 점에서 의도가 다르다.

## 연습문제

1. 이번 장의 `DeliveredState.Cancel`은 단순히 안내 메시지만 출력한다. "배송완료 후 7일 이내에는 환불 요청이 가능하다"는 규칙을 추가하려면 `RefundedState` 클래스를 어떻게 설계해야 하는가? 이 변경이 다른 상태 클래스에 영향을 주지 않는지 확인해 보라.
2. 이번 장의 상태 클래스들은 `new PaidState()`처럼 매번 새 인스턴스를 생성한다. 만약 상태 객체가 아무런 필드도 갖지 않는다면(무상태, stateless), 상태마다 인스턴스를 하나씩만 만들어 재사용하도록 바꿀 수 있다. 이렇게 바꾸려면 코드를 어떻게 수정해야 하며, 어떤 상황에서는 이 최적화를 적용하면 안 되는가?
3. 신호등 시스템(빨강 → 초록 → 노랑 → 빨강)을 상태 패턴으로 설계해 보라. `ITrafficLightState` 인터페이스에는 어떤 메서드가 필요한가?
4. 상태 패턴과 23장 전략 패턴의 코드 구조가 비슷해서 혼동하기 쉽다고 했다. 어떤 코드를 보고 "이것이 상태 패턴인지 전략 패턴인지" 구분하려면 구조가 아니라 무엇을 살펴봐야 하는지 설명해 보라.
5. 이번 장에서는 `Order.State`를 `public` setter로 열어두었다. 클라이언트 코드가 `order.State = new DeliveredState()`처럼 상태를 임의로 바꿔버릴 수 있다는 것은 문제가 될 수 있다. 이 위험을 줄이면서도 상태 클래스들이 전환을 수행할 수 있게 하려면 어떻게 설계를 바꿀 수 있을지 제안해 보라.

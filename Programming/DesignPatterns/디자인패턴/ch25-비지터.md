## 문제 상황

간단한 그림 편집기를 만들고 있다고 하자. 도형은 원(Circle), 사각형(Rectangle), 삼각형(Triangle) 세 종류가 있고, 처음 요구사항은 "전체 도형의 넓이 합을 구하라"는 것뿐이었다. 그래서 각 도형 클래스에 `GetArea()` 메서드를 하나씩 넣는 것으로 충분했다.

```csharp
public class Circle
{
    public double Radius { get; }
    public Circle(double radius) => Radius = radius;
    public double GetArea() => Math.PI * Radius * Radius;
}

public class Rectangle
{
    public double Width { get; }
    public double Height { get; }
    public Rectangle(double width, double height)
    {
        Width = width;
        Height = height;
    }
    public double GetArea() => Width * Height;
}
```

문제는 여기서 끝나지 않았다. 얼마 뒤 "도형 목록을 콘솔에 표 형태로 출력하라"는 요구사항이 들어왔다. `Print()` 메서드를 세 클래스에 하나씩 추가했다. 그다음에는 "도형 정보를 XML로 내보내라"는 요구사항이 들어왔다. 또 `ToXml()` 메서드를 세 클래스에 하나씩 추가했다. 그다음에는 "도형의 경계 상자(bounding box)를 계산하라"는 요구사항이 들어왔다.

패턴이 보이는가? 새로운 연산이 하나 생길 때마다, 그 연산과 아무 관계도 없어 보이는 `Circle`, `Rectangle`, `Triangle` 세 클래스를 전부 찾아가서 메서드를 하나씩 추가해야 한다. 도형 종류가 지금은 세 개뿐이지만 다섯 개, 열 개로 늘어난다면 이 반복 작업은 그만큼 커진다. 게다가 `Circle`이라는 클래스 하나에 넓이 계산, 화면 출력, XML 직렬화, 경계 상자 계산처럼 서로 아무 관련 없는 책임이 계속 쌓인다. 이 클래스는 "도형을 표현한다"는 원래 역할과는 점점 멀어진 채, 온갖 연산의 잡동사니 창고가 되어 간다.

더 곤란한 경우도 있다. 만약 이 도형 클래스들이 팀에서 만든 것이 아니라 외부 라이브러리에서 가져온 것이라면 어떨까? 소스 코드를 아예 수정할 수 없으니 `Print()`나 `ToXml()` 같은 메서드를 직접 추가할 방법이 없다. 그렇다고 매번 `if (shape is Circle) ... else if (shape is Rectangle) ...` 하는 타입 검사 코드를 여기저기 흩어 놓는 것도 2장에서 다룬 개방-폐쇄 원칙을 정면으로 어기는 방식이다.

정리하면, 이 문제의 핵심은 "도형이라는 안정적인 데이터 구조는 그대로 두고, 그 위에서 수행할 연산만 계속 늘어나는" 상황인데, 연산을 추가할 때마다 데이터 구조 쪽 클래스를 매번 건드려야 한다는 것이다.

## 패턴 설명

비지터 패턴은 "데이터 구조(도형)"와 "그 데이터에 대한 연산(넓이 계산, 출력, 직렬화)"을 완전히 분리해서 각자 다른 클래스 계층에 둔다. 연산 하나가 곧 하나의 방문자(Visitor) 클래스가 된다.

구성 요소는 다음과 같다.

- **Element**: 방문을 받는 쪽. 여기서는 도형(`Circle`, `Rectangle`, `Triangle`)이다. 각 Element는 `Accept(IVisitor visitor)`라는 메서드 하나만 가진다.
- **IVisitor**: 연산을 담을 인터페이스. Element의 구체 타입 하나당 `VisitXxx(Xxx element)` 형태의 메서드를 하나씩 선언한다.
- **ConcreteVisitor**: 실제 연산 로직을 담은 클래스. 넓이 계산이면 `AreaVisitor`, 화면 출력이면 `PrintVisitor`처럼 연산 하나가 클래스 하나에 대응한다.

핵심 아이디어는 각 Element가 자신을 인자로 받은 `Accept` 메서드 안에서, 자기 자신을 방문자에게 다시 넘겨준다는 점이다.

```csharp
// Circle.Accept 내부
public void Accept(IShapeVisitor visitor) => visitor.VisitCircle(this);
```

이렇게 하면 도형 클래스는 "나를 방문하려는 손님(visitor)에게 나 자신을 보여준다"는 역할만 하고, 실제로 무슨 일을 할지는 전혀 알지도 못하고 신경 쓰지도 않는다. 연산의 구체적인 내용은 오직 `IShapeVisitor`를 구현하는 클래스 안에만 존재한다. 새로운 연산이 필요해지면 `IShapeVisitor`를 구현하는 새 클래스를 하나 추가하면 그만이고, `Circle`이나 `Rectangle`은 단 한 줄도 손댈 필요가 없다.

### 더블 디스패치(Double Dispatch)란 무엇인가

C#의 메서드 호출은 보통 "런타임에 결정되는 실제 타입 하나"에 의해서만 어떤 코드가 실행될지가 정해진다. 가상 메서드 호출이 대표적인 예로, 변수의 선언 타입이 무엇이든 실제로 담긴 객체의 타입에 따라 오버라이드된 메서드가 실행된다. 이것을 "싱글 디스패치"라고 부른다.

그런데 `shape.Accept(visitor)` 호출은 `shape`의 실제 타입과 `visitor`의 실제 타입, 두 객체의 타입 조합에 따라 최종적으로 실행되는 코드가 달라져야 한다. 예를 들어 "Circle을 AreaVisitor로 방문한다"와 "Circle을 PrintVisitor로 방문한다"는 서로 다른 코드가 실행되어야 하고, "Rectangle을 AreaVisitor로 방문한다"도 또 다른 코드다. 비지터 패턴은 이것을 두 번의 디스패치로 나누어 해결한다.

1. **첫 번째 디스패치**: `shape.Accept(visitor)` 호출은 가상 메서드 호출이므로, `shape`의 실제 타입(Circle인지 Rectangle인지)에 따라 알맞은 `Accept` 구현으로 런타임에 연결된다.
2. **두 번째 디스패치**: 예를 들어 `Circle.Accept` 내부에서는 `this`가 이미 `Circle` 타입으로 확정되어 있다. 그 안에서 `visitor.VisitCircle(this)`를 호출하면, `visitor`의 실제 타입(AreaVisitor인지 PrintVisitor인지)에 따라 그 클래스가 구현한 `VisitCircle`이 실행된다.

두 단계를 거치고 나면 결과적으로 "Circle × AreaVisitor", "Rectangle × PrintVisitor"처럼 두 객체의 타입 조합에 따라 정확히 알맞은 코드가 실행된다. C#의 메서드 오버로딩 자체는 컴파일 시점에 정적으로 결정되기 때문에, 클라이언트 코드에서 `visitor.Visit(shape)`처럼 한 번만 호출해서는 이런 효과를 얻을 수 없다. `Accept`라는 한 단계를 Element 쪽에 끼워 넣어야, `this`의 타입이 컴파일 시점에 구체적으로 고정된 지점에서 정확한 오버로드가 선택된다.

## C# 예제 코드

먼저 Element가 구현할 인터페이스와, 방문자가 구현할 인터페이스를 정의한다.

```csharp
// Element: 방문을 받는 도형들이 공통으로 구현하는 인터페이스
public interface IShape
{
    void Accept(IShapeVisitor visitor);
}

// Visitor: 도형 종류마다 하나씩의 Visit 메서드를 선언한다
public interface IShapeVisitor
{
    void VisitCircle(Circle circle);
    void VisitRectangle(Rectangle rectangle);
    void VisitTriangle(Triangle triangle);
}
```

세 가지 도형 클래스는 자신의 데이터만 가지고 있으며, `Accept`는 오직 자기 자신을 방문자에게 넘겨주는 한 줄로 끝난다.

```csharp
// ConcreteElement: 원
public class Circle : IShape
{
    public double Radius { get; }

    public Circle(double radius)
    {
        Radius = radius;
    }

    // 두 번째 디스패치: this가 이미 Circle로 고정되어 있으므로 VisitCircle 오버로드가 선택된다
    public void Accept(IShapeVisitor visitor) => visitor.VisitCircle(this);
}

// ConcreteElement: 사각형
public class Rectangle : IShape
{
    public double Width { get; }
    public double Height { get; }

    public Rectangle(double width, double height)
    {
        Width = width;
        Height = height;
    }

    public void Accept(IShapeVisitor visitor) => visitor.VisitRectangle(this);
}

// ConcreteElement: 삼각형
public class Triangle : IShape
{
    public double Base { get; }
    public double Height { get; }

    public Triangle(double @base, double height)
    {
        Base = @base;
        Height = height;
    }

    public void Accept(IShapeVisitor visitor) => visitor.VisitTriangle(this);
}
```

첫 번째 연산인 넓이 계산은 `AreaVisitor`에 담는다. 도형 클래스에는 넓이 계산 코드가 전혀 없다는 점에 주목하라.

```csharp
// ConcreteVisitor: 넓이 계산 연산을 담당
public class AreaVisitor : IShapeVisitor
{
    public double TotalArea { get; private set; }

    public void VisitCircle(Circle circle)
    {
        TotalArea += Math.PI * circle.Radius * circle.Radius;
    }

    public void VisitRectangle(Rectangle rectangle)
    {
        TotalArea += rectangle.Width * rectangle.Height;
    }

    public void VisitTriangle(Triangle triangle)
    {
        TotalArea += triangle.Base * triangle.Height / 2.0;
    }
}
```

두 번째 연산인 화면 출력은 `PrintVisitor`라는 완전히 별개의 클래스에 담는다. 도형 클래스는 이 연산이 새로 생겼다는 사실조차 알지 못한다.

```csharp
// ConcreteVisitor: 화면 출력 연산을 담당
public class PrintVisitor : IShapeVisitor
{
    public void VisitCircle(Circle circle)
    {
        Console.WriteLine($"[원] 반지름 = {circle.Radius}");
    }

    public void VisitRectangle(Rectangle rectangle)
    {
        Console.WriteLine($"[사각형] {rectangle.Width} x {rectangle.Height}");
    }

    public void VisitTriangle(Triangle triangle)
    {
        Console.WriteLine($"[삼각형] 밑변 = {triangle.Base}, 높이 = {triangle.Height}");
    }
}
```

사용하는 쪽에서는 도형 목록을 순회하며 원하는 방문자를 넘겨주기만 하면 된다.

```csharp
public class Program
{
    public static void Main()
    {
        var shapes = new List<IShape>
        {
            new Circle(5),
            new Rectangle(4, 6),
            new Triangle(3, 8)
        };

        // 출력 연산: 도형들에게 PrintVisitor를 보낸다
        var printVisitor = new PrintVisitor();
        foreach (var shape in shapes)
        {
            shape.Accept(printVisitor); // ① 첫 번째 디스패치(shape의 실제 타입) ② 두 번째 디스패치(visitor의 실제 타입)
        }

        // 넓이 계산 연산: 같은 도형들에게 이번엔 AreaVisitor를 보낸다
        var areaVisitor = new AreaVisitor();
        foreach (var shape in shapes)
        {
            shape.Accept(areaVisitor);
        }
        Console.WriteLine($"전체 넓이 합계: {areaVisitor.TotalArea:F2}");
    }
}
```

이후 "XML로 내보내라"는 요구사항이 들어와도, `XmlExportVisitor`라는 클래스 하나만 새로 추가하면 된다. `Circle`, `Rectangle`, `Triangle`은 이 책 전체에서 단 한 번, 최초에 `Accept` 메서드를 넣을 때만 수정되고 그 이후로는 전혀 바뀌지 않는다.

## 언제 사용하는가

- 클래스 계층 구조(Element 쪽)는 상당히 안정적이어서 새로운 타입이 자주 추가되지 않는데, 그 계층에 대해 수행할 연산(Visitor 쪽)은 앞으로도 계속 늘어날 것으로 예상될 때
- 연산의 로직이 여러 Element 타입에 걸쳐 흩어지는 것을 원하지 않고, 연산 하나를 클래스 하나에 온전히 모아두고 싶을 때
- Element 클래스의 소스 코드를 직접 수정할 수 없거나(외부 라이브러리 등), 수정하고 싶지 않은데 새로운 연산을 추가해야 할 때
- 10장 컴포지트와 함께 쓰이는 경우가 특히 많다. 트리 구조의 각 노드(Leaf든 Composite든)에 `Accept`를 추가해 두면, 하나의 Visitor로 트리 전체를 순회하면서 노드 종류에 맞는 처리를 할 수 있다. 예를 들어 컴포지트로 구성된 도형 그룹이 있다면, Composite 노드의 `Accept`는 자신의 모든 자식에게 `Accept`를 다시 호출해 주는 역할을 하고, 실제 연산은 여전히 Visitor 쪽에 모여 있다.

다만 비지터 패턴에는 뚜렷한 대가가 따른다. 문제 상황에서는 "연산이 늘어날 때 도형 클래스를 건드리지 않는다"는 점이 장점이었지만, 반대로 **도형 타입이 늘어나는 경우**를 생각해 보면 정반대의 상황이 벌어진다. 만약 `Pentagon`(오각형)이라는 새 도형이 추가된다면, `IShapeVisitor` 인터페이스에 `VisitPentagon` 메서드를 추가해야 하고, 그러면 이미 만들어져 있던 `AreaVisitor`, `PrintVisitor`뿐 아니라 앞으로 만들어질 모든 Visitor 구현체가 이 메서드를 구현하도록 전부 수정해야 한다. 즉 비지터 패턴은 "연산 축"에서는 2장에서 다룬 개방-폐쇄 원칙을 훌륭하게 지키지만, "타입 축"에서는 오히려 개방-폐쇄 원칙과 정면으로 충돌한다. 이 패턴을 도입하기 전에는 "이 계층에 타입이 늘어날 일이 많은가, 연산이 늘어날 일이 많은가"를 먼저 따져보아야 한다.

## 요약

비지터 패턴은 클래스 계층 구조(Element)와 그 위에서 수행할 연산(Visitor)을 서로 다른 클래스 계층으로 완전히 분리한다. Element는 `Accept(IVisitor visitor)` 메서드 하나만으로 자기 자신을 방문자에게 넘겨주고, 실제 연산 로직은 각 Visitor 구현체 안에 모두 모여 있다. `Accept` 호출(첫 번째 디스패치)과 그 안에서 이루어지는 `VisitXxx(this)` 호출(두 번째 디스패치)이 이어지면서, Element의 실제 타입과 Visitor의 실제 타입 조합에 맞는 코드가 실행되는데 이를 더블 디스패치라고 부른다. 이 구조 덕분에 새로운 연산을 추가할 때는 기존 Element 클래스를 전혀 건드리지 않아도 되지만, 반대로 새로운 Element 타입을 추가할 때는 모든 Visitor 구현체를 찾아가서 수정해야 한다는 대가가 따른다.

## 연습문제

1. 본문의 도형 예제에 `XmlExportVisitor`를 새로 추가해 보라. 각 도형을 `<circle radius="5" />`, `<rectangle width="4" height="6" />` 형태의 문자열로 출력하면 된다. 기존의 `Circle`, `Rectangle`, `Triangle` 클래스를 몇 줄이나 수정해야 하는가?
2. 본문의 도형 계층에 `Pentagon`(오각형)이라는 새 Element를 추가한다고 하자. `IShapeVisitor`와 `AreaVisitor`, `PrintVisitor`를 각각 어떻게 수정해야 하는지 정리해 보고, 이 작업이 왜 "개방-폐쇄 원칙을 어기는 것처럼 느껴지는지" 설명하라.
3. `shape.Accept(visitor)` 대신 클라이언트 코드에서 `visitor.Visit(shape)`처럼 `IShape`를 매개변수로 받는 메서드 하나만 호출하는 방식으로는 왜 더블 디스패치 효과를 얻을 수 없는지, C#의 오버로드 결정 규칙을 근거로 설명하라.
4. 10장에서 다룬 `IOrgUnit`(Employee/Department) 계층에 `IOrgUnitVisitor`를 도입한다면, `Department.Accept` 메서드는 어떤 일을 해야 하는지 코드로 스케치해 보라. (힌트: 자신의 각 자식에게 `Accept`를 다시 호출해야 한다.)
5. 만약 도형 종류는 거의 고정되어 있고 앞으로도 새로운 연산만 자주 추가될 것이 확실하다면, 비지터 패턴 대신 각 도형 클래스에 메서드를 직접 추가하는 원래 방식을 그대로 유지하는 것이 더 나을 수도 있다. 어떤 조건에서 그런 판단이 합리적일지 논하라.

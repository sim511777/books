## 문제 상황

사내 지출 결의 시스템을 만든다고 생각해 보자. 직원이 지출 결의서를 올리면 금액에 따라 승인권자가 달라진다.

- 500만 원 이하: 팀장이 승인
- 2,000만 원 이하: 부서장이 승인
- 2,000만 원 초과: 대표이사가 승인

처음에는 요구사항이 단순했기 때문에 개발자는 다음과 같이 짜고 끝냈다.

```csharp
public void Approve(ExpenseRequest request)
{
    if (request.Amount <= 5_000_000)
    {
        TeamLead.Approve(request);
    }
    else if (request.Amount <= 20_000_000)
    {
        DepartmentHead.Approve(request);
    }
    else
    {
        Ceo.Approve(request);
    }
}
```

그런데 회사가 커지면서 규칙이 계속 늘어난다. "해외 출장비는 금액과 무관하게 인사팀장 결재를 한 번 더 받아야 한다", "500만 원 이하라도 팀장이 휴가 중이면 부서장이 대신 승인한다", "특정 프로젝트 코드가 붙은 지출은 프로젝트 매니저가 우선 검토한다" 같은 예외가 하나씩 붙는다. 그 결과 `Approve` 메서드는 `if/else`가 중첩된 거대한 블록이 되고, 규칙 하나를 추가하거나 순서를 바꿀 때마다 이 메서드 전체를 다시 읽고 고쳐야 한다. 승인 라인이 조직 개편에 따라 자주 바뀌는 회사라면, 이 메서드는 매달 손을 대야 하는 코드가 되어 버린다.

더 큰 문제는 이 로직이 한 곳에 다 뭉쳐 있다는 점이다. 팀장 승인 로직과 부서장 승인 로직, 대표 승인 로직이 서로 분리되어 있지 않으니 팀장 승인 로직만 따로 테스트하기도, 승인 순서를 임시로 바꿔 보기도 어렵다. 필요한 것은 "각 승인권자가 자신이 처리할 수 있는 요청인지 스스로 판단하고, 처리할 수 없으면 다음 승인권자에게 넘기는" 구조다.

## 패턴 설명

체인 오브 리스판서빌리티는 요청을 처리할 수 있는 후보 객체들을 사슬(chain) 형태로 연결해 두고, 요청이 이 사슬을 따라 순서대로 전달되게 만드는 패턴이다. 사슬을 이루는 각 객체를 핸들러(Handler)라고 부르는데, 핸들러는 두 가지 일만 안다.

1. 이 요청을 내가 처리할 수 있는가?
2. 처리할 수 없다면(또는 처리한 뒤에도 다음 단계로 넘겨야 한다면) 사슬의 다음 핸들러에게 넘긴다.

핵심은 요청을 보내는 쪽(클라이언트)이 "누가 처리할지"를 전혀 몰라도 된다는 것이다. 클라이언트는 그저 사슬의 첫 번째 핸들러에게 요청을 던질 뿐이고, 실제로 누가 처리하는지는 핸들러들 사이에서 알아서 결정된다. 승인 라인 예제로 보면, 클라이언트(지출 결의서를 올리는 직원)는 팀장에게 결의서를 제출할 뿐이고, 팀장이 처리 가능하면 처리하고 아니면 부서장에게, 부서장도 안 되면 대표에게 자동으로 넘어간다.

이렇게 구조를 잡으면 승인 규칙이 바뀌어도 각 핸들러 클래스 하나만 고치면 되고, 승인 라인의 순서를 바꾸는 것도 사슬을 재구성하는 것으로 끝난다. 새로운 승인 단계(예: 프로젝트 매니저 사전 검토)를 추가하고 싶으면 새 핸들러 클래스를 하나 만들어 사슬 중간에 끼워 넣으면 된다. 기존 핸들러 코드는 손댈 필요가 없다. 이는 2장에서 다룬 개방-폐쇄 원칙(OCP)을 그대로 실현하는 방식이다.

체인은 반드시 "요청을 정확히 한 명만 처리한다"는 규칙을 강제하지는 않는다. 사슬의 각 핸들러가 요청을 처리한 뒤에도 다음 핸들러에게 넘길 수도 있고(예: 팀장 승인 후에도 감사 로그를 남기는 핸들러가 이어서 실행), 아무도 처리하지 못한 채 사슬 끝까지 도달할 수도 있다(이 경우를 대비해 기본 처리자를 마지막에 두는 것이 안전하다).

아래는 지출 결의서 승인 예제를 사슬 구조로 나타낸 것이다.

```text
                  체인 오브 리스판서빌리티 구조

  +-----------+  요청   +----------------+  처리 불가 시 전달  +----------------+  처리 불가 시 전달  +--------------+
  |클라이언트   | -----> | TeamLeadHandler | -----------------> | DepartmentHead | -----------------> |  CeoHandler   |
  |(지출 결의서 |        |  500만원 이하    |                     |   2000만원 이하  |                    |  한도 없음     |
  | 제출)      |        |  처리 가능?      |                     |   처리 가능?     |                    |  항상 처리     |
  +-----------+        +----------------+                     +----------------+                    +--------------+
                               |                                       |                                     |
                               v                                       v                                     v
                        여기서 처리되면                            여기서 처리되면                        마지막 처리자
                        사슬 진행 중단                             사슬 진행 중단                        (항상 처리)
```

## C# 예제 코드

먼저 요청 객체와 승인 결과를 담는 클래스를 정의한다.

```csharp
// 지출 결의 요청
public class ExpenseRequest
{
    public string Requester { get; }
    public decimal Amount { get; }
    public string Purpose { get; }

    public ExpenseRequest(string requester, decimal amount, string purpose)
    {
        Requester = requester;
        Amount = amount;
        Purpose = purpose;
    }
}
```

다음으로 사슬을 구성하는 추상 핸들러를 만든다. `SetNext`는 다음 핸들러를 지정하고 체이닝이 가능하도록 자기 자신을 반환하며, `Handle`은 처리 가능 여부를 판단한 뒤 다음 핸들러로 넘기는 공통 로직을 담는다.

```csharp
public abstract class ApprovalHandler
{
    private ApprovalHandler _next;

    // 다음 처리자를 지정하고, 체이닝을 위해 다음 처리자를 반환한다
    public ApprovalHandler SetNext(ApprovalHandler next)
    {
        _next = next;
        return next;
    }

    public void Handle(ExpenseRequest request)
    {
        if (CanApprove(request))
        {
            Approve(request);
        }
        else if (_next != null)
        {
            _next.Handle(request);
        }
        else
        {
            Console.WriteLine($"[미처리] {request.Requester}의 {request.Amount:N0}원 결의서를 승인할 수 있는 결재자가 없습니다.");
        }
    }

    protected abstract bool CanApprove(ExpenseRequest request);
    protected abstract void Approve(ExpenseRequest request);
}
```

이제 구체적인 승인권자 세 명을 각각 클래스로 만든다. 각 클래스는 자신의 승인 한도만 알고 있으면 된다.

```csharp
public class TeamLeadHandler : ApprovalHandler
{
    private const decimal Limit = 5_000_000m;

    protected override bool CanApprove(ExpenseRequest request) => request.Amount <= Limit;

    protected override void Approve(ExpenseRequest request)
    {
        Console.WriteLine($"[팀장 승인] {request.Requester} - {request.Amount:N0}원 ({request.Purpose})");
    }
}

public class DepartmentHeadHandler : ApprovalHandler
{
    private const decimal Limit = 20_000_000m;

    protected override bool CanApprove(ExpenseRequest request) => request.Amount <= Limit;

    protected override void Approve(ExpenseRequest request)
    {
        Console.WriteLine($"[부서장 승인] {request.Requester} - {request.Amount:N0}원 ({request.Purpose})");
    }
}

public class CeoHandler : ApprovalHandler
{
    // 대표이사는 한도 없이 모든 요청을 처리한다
    protected override bool CanApprove(ExpenseRequest request) => true;

    protected override void Approve(ExpenseRequest request)
    {
        Console.WriteLine($"[대표 승인] {request.Requester} - {request.Amount:N0}원 ({request.Purpose})");
    }
}
```

사슬을 구성하고 사용하는 코드는 다음과 같다.

```csharp
var teamLead = new TeamLeadHandler();
var departmentHead = new DepartmentHeadHandler();
var ceo = new CeoHandler();

// 팀장 -> 부서장 -> 대표 순으로 사슬을 구성한다
teamLead.SetNext(departmentHead).SetNext(ceo);

teamLead.Handle(new ExpenseRequest("김도윤", 3_000_000m, "팀 워크숍 비용"));
teamLead.Handle(new ExpenseRequest("이서연", 15_000_000m, "신규 장비 구매"));
teamLead.Handle(new ExpenseRequest("박지훈", 50_000_000m, "해외 지사 설립 비용"));
```

실행 결과는 각 요청이 처리 가능한 첫 번째 승인권자에게서 멈추는 것을 보여준다. 만약 "해외 출장비는 인사팀장 결재를 추가로 받는다"는 규칙이 생기면, `HrLeadHandler`라는 핸들러를 하나 새로 만들어 `Purpose`에 "출장"이 포함된 경우 처리 후에도 `_next`를 호출해 다음 단계로 넘기도록 만들고, 사슬 맨 앞에 끼워 넣으면 된다. 기존 세 클래스는 전혀 건드리지 않는다.

## 언제 사용하는가

체인 오브 리스판서빌리티는 다음과 같은 상황에 적합하다.

- 요청을 처리할 수 있는 후보가 여러 단계로 존재하고, 실제로 누가 처리할지가 요청의 조건(금액, 종류, 상태 등)에 따라 달라질 때. 위 승인 라인 예제가 대표적이다.
- 처리 순서나 처리 단계의 구성이 자주 바뀔 것으로 예상될 때. 새 단계를 끼워 넣거나 순서를 바꾸는 일이 기존 코드를 고치지 않고 사슬 구성만 바꾸는 일로 끝난다.
- 요청을 보내는 쪽이 실제 처리자를 몰라도 되게 만들고 싶을 때(발신자와 수신자의 결합도 낮추기).

실무에서 흔히 보는 예로는 ASP.NET Core의 미들웨어 파이프라인이 있다. 각 미들웨어는 요청을 처리하거나 다음 미들웨어로 넘기는데, 이 구조 자체가 체인 오브 리스판서빌리티의 응용이다. 윈도우 UI 프레임워크의 이벤트 버블링(자식 컨트롤이 처리하지 못한 이벤트가 부모로 전파되는 방식)도 같은 아이디어다. 로그 필터링에서 "디버그 레벨은 콘솔 핸들러가, 에러 레벨은 파일과 알림 핸들러가 모두 처리한다"처럼 여러 핸들러가 조건에 따라 개입하는 로깅 프레임워크의 구조도 이 패턴과 닮아 있다.

주의할 점도 있다. 사슬이 길어지면 요청이 정확히 어디서 처리됐는지 추적하기 어려워질 수 있고, 사슬 구성을 잘못하면 아무도 요청을 처리하지 못한 채 끝까지 흘러갈 수 있다. 따라서 사슬 끝에는 "처리되지 않은 요청"을 명확히 로그로 남기거나 예외를 던지는 기본 처리자를 두는 것이 안전하다. 처리자를 선택하는 조건 판단 자체가 복잡하다면, 22장에서 다루는 상태 패턴이나 23장의 전략 패턴과 결합해 각 핸들러의 판단 로직을 별도 객체로 분리하는 것도 고려할 수 있다.

## .NET BCL에서 이 패턴 찾아보기

체인 오브 리스판서빌리티를 가장 실감 나게 볼 수 있는 곳은 엄밀히는 BCL 자체가 아니라 ASP.NET Core 프레임워크의 미들웨어 파이프라인이지만, .NET 생태계에서 이 패턴을 설명할 때 가장 널리 인용되는 예이므로 함께 살펴볼 가치가 있다. `IApplicationBuilder.Use(...)`로 미들웨어를 등록하면, 들어오는 각 HTTP 요청은 등록된 순서대로 미들웨어를 하나씩 거쳐 간다. 각 미들웨어는 요청을 직접 처리하고 끝낼 수도 있고, 다음 미들웨어에게 넘겨줄 수도 있다.

```csharp
var app = builder.Build();

// 요청 로깅: 처리 후 반드시 다음 미들웨어로 넘긴다
app.Use(async (context, next) =>
{
    Console.WriteLine($"요청 시작: {context.Request.Path}");
    await next(); // 사슬의 다음 미들웨어로 넘긴다
    Console.WriteLine($"요청 종료: {context.Request.Path}");
});

// 인증 확인: 조건에 따라 여기서 처리를 끝낼 수도, 넘길 수도 있다
app.Use(async (context, next) =>
{
    if (!context.Request.Headers.ContainsKey("Authorization"))
    {
        context.Response.StatusCode = 401;
        return; // next()를 호출하지 않으면 사슬이 여기서 멈춘다
    }

    await next();
});

app.Run(async context =>
{
    await context.Response.WriteAsync("Hello, World!");
});
```

이 구조는 15장에서 만든 승인 체인과 정확히 같은 아이디어를 담고 있다. 각 미들웨어(핸들러)는 "이 요청을 내가 처리하고 끝낼지, 아니면 `next()`를 호출해 다음 단계로 넘길지"를 스스로 결정한다. 인증 미들웨어가 401을 반환하고 `next()`를 호출하지 않으면 사슬이 거기서 종료되는 것은, 본문의 `CanApprove`가 `false`를 반환해 `_next.Handle(request)`로 넘어가는 것과 반대로, 처리자가 "여기서 끝내겠다"고 결정하는 경우에 해당한다. 요청을 보내는 클라이언트(브라우저)는 어떤 미들웨어가 실제로 응답을 만들어내는지 전혀 알 필요가 없고, 새 미들웨어를 추가하거나 순서를 바꾸는 일도 파이프라인 구성 코드 한 줄을 바꾸는 것으로 끝난다는 점까지 승인 체인 예제와 그대로 일치한다.

## 요약

체인 오브 리스판서빌리티는 요청 처리 후보들을 사슬로 연결하고, 요청이 사슬을 따라 흐르며 처리 가능한 지점에서 멈추도록 만드는 패턴이다. 이 구조를 쓰면 거대한 `if/else` 블록 대신 각 처리 단계를 독립된 클래스로 분리할 수 있고, 처리 순서나 구성을 런타임에 유연하게 바꿀 수 있다. 발신자는 사슬의 첫 번째 핸들러만 알면 되므로 발신자와 수신자 사이의 결합도도 낮아진다. 다만 사슬이 지나치게 길어지면 디버깅이 어려워지고, 요청이 아무에게도 처리되지 않고 끝날 수 있다는 점은 항상 대비해야 한다.

## 연습문제

1. 본문의 승인 라인에 "해외 출장비는 금액과 무관하게 인사팀장의 결재를 추가로 받아야 한다"는 규칙을 추가하려면 어떤 핸들러를 새로 만들고 사슬의 어느 위치에 끼워 넣어야 할지 설계해 보라.
2. 헬프데스크 티켓 시스템에서 "1단계 상담원 → 2단계 기술지원 → 3단계 개발팀"으로 이어지는 처리 사슬을 체인 오브 리스판서빌리티로 구현해 보라. 각 단계가 처리할 수 없는 조건은 무엇으로 정의할 수 있는가?
3. 체인 오브 리스판서빌리티와 12장에서 다룬 퍼사드 패턴은 둘 다 클라이언트가 내부 구조를 몰라도 되게 해준다는 점에서 비슷해 보인다. 두 패턴의 목적이 근본적으로 어떻게 다른지 설명해 보라.

## 들어가며

주니어 개발자 시절을 떠올려 보면, 코드를 "돌아가게" 만드는 것과 "잘 만드는" 것 사이에는 상당한 거리가 있었을 것입니다. 처음 작성한 프로그램은 요구사항을 만족시키긴 했지만, 몇 주 뒤 요구사항이 바뀌면 코드 전체를 뜯어고쳐야 했던 경험이 누구에게나 있습니다. 이런 경험을 수백, 수천 번 반복한 선배 개발자들은 어느 순간 깨닫습니다. "이 문제, 어디서 본 적 있는데?"

디자인 패턴은 바로 이 깨달음을 체계화한 결과물입니다. 서로 다른 회사, 다른 도메인, 다른 프로그래밍 언어에서 일하는 개발자들이 놀랍도록 비슷한 구조적 문제에 부딪히고, 놀랍도록 비슷한 형태의 해법으로 그 문제를 풀어냈다는 사실이 반복적으로 확인되면서, 그 해법들에 이름이 붙고 정리되기 시작했습니다.

이번 장에서는 디자인 패턴이 정확히 무엇을 의미하는지, 왜 이런 개념이 만들어졌는지, 그리고 이 책을 어떤 방식으로 읽어 나가면 좋을지 살펴봅니다.

## 디자인 패턴의 정의

디자인 패턴(Design Pattern)이란, **특정 컨텍스트에서 반복적으로 발생하는 설계 문제에 대해, 여러 상황에 재사용할 수 있는 형태로 정리된 해결책의 템플릿**입니다.

이 정의에서 몇 가지 단어를 곱씹어 볼 필요가 있습니다.

- **반복적으로 발생하는 문제**: 패턴은 단 한 번 일어나는 특수한 상황을 위한 것이 아닙니다. "객체 생성을 서브클래스에 위임하고 싶다", "객체 하나만 존재하도록 강제하고 싶다", "인터페이스가 서로 맞지 않는 두 컴포넌트를 연결하고 싶다" 처럼, 도메인이 달라도 형태만 바뀌어 계속 등장하는 문제들이 패턴의 대상이 됩니다.
- **해결책의 템플릿**: 패턴은 복사해서 붙여넣을 수 있는 완성된 코드가 아닙니다. 클래스와 객체들이 서로 관계를 맺는 "구조"와 "역할 분담"에 대한 이름이자 설계도입니다. 실제 구현은 언어, 프레임워크, 프로젝트 상황에 맞게 매번 다시 작성해야 합니다.
- **검증된**: 패턴은 누군가가 머릿속에서 상상해 낸 이론이 아니라, 실제 소프트웨어에서 반복적으로 관찰되고 효과가 있음이 확인된 해법입니다.

정리하면, 디자인 패턴을 안다는 것은 "이런 상황에서는 이런 식으로 역할을 나누면 문제가 잘 풀린다"라는 경험적 지식을 미리 습득해 두는 것과 같습니다. 마치 요리에서 "볶음 요리는 센 불에서 짧게"라는 원칙을 알고 있으면 새로운 재료로 요리할 때도 그 원칙을 응용할 수 있는 것처럼, 패턴을 알고 있으면 처음 보는 문제도 "어? 이건 그 패턴 구조랑 비슷한데" 하고 빠르게 접근할 수 있습니다.

## 패턴이라는 개념은 어디서 왔는가

디자인 패턴이라는 아이디어 자체는 소프트웨어 분야에서 처음 나온 것이 아닙니다. 원래는 건축가 크리스토퍼 알렉산더(Christopher Alexander)가 도시와 건물을 설계할 때 반복되는 좋은 구조들을 "패턴 언어"라는 이름으로 정리한 데서 출발했습니다. "채광이 좋은 방을 만들려면 이런 구조가 반복적으로 나타난다"는 식의 관찰을 소프트웨어 설계에도 적용할 수 있다는 아이디어가 1990년대 초반 객체지향 커뮤니티에서 퍼져나갔습니다.

이 흐름 속에서 1994년, 에리히 감마(Erich Gamma), 리처드 헬름(Richard Helm), 랄프 존슨(Ralph Johnson), 존 블리시디스(John Vlissides) 네 명의 저자가 객체지향 설계에서 반복적으로 나타나는 23가지 설계 문제와 해법을 정리한 책을 출간했습니다. 저자가 네 명이었기 때문에 이들은 "Gang of Four", 흔히 줄여서 **GoF**라는 별칭으로 불리게 되었고, 이 책에서 정리한 패턴들을 "GoF 패턴"이라 부르는 관용어가 지금까지도 널리 쓰이고 있습니다. 이 책에서 다루는 3장부터 25장까지의 패턴들 역시 바로 이 GoF의 분류 체계를 따르고 있습니다.

여기서 짚어 둘 점은, 이 책은 GoF의 원서나 그 이후 나온 여러 해설서를 번역하거나 각색한 것이 아니라는 사실입니다. 패턴이라는 개념과 각 패턴의 이름, 의도는 이미 업계에 정착된 공통 자산이지만, 그것을 설명하는 방식과 예제는 필자가 직접 구성한 것입니다. 같은 패턴이라도 설명하는 사람에 따라 비유와 예제가 달라질 수 있으며, 이는 오히려 패턴을 다각도로 이해하는 데 도움이 됩니다.

## 세 가지 분류: 생성, 구조, 행동

GoF는 23가지 패턴을 목적에 따라 세 가지 범주로 나누었습니다. 이 책의 목차도 이 분류를 그대로 따릅니다.

### 생성 패턴 (Creational Patterns)

객체를 **어떻게 생성할 것인가**에 대한 패턴입니다. `new` 키워드로 객체를 직접 만드는 대신, 생성 과정을 캡슐화하거나 유연하게 만들어서 "어떤 클래스의 인스턴스를 만들지"를 나중에 결정할 수 있게 하거나, 생성 로직을 재사용 가능한 형태로 분리합니다. 이 책의 3장(싱글턴)부터 7장(프로토타입)까지가 여기에 속합니다.

### 구조 패턴 (Structural Patterns)

클래스와 객체를 **어떻게 조합하여 더 큰 구조를 만들 것인가**에 대한 패턴입니다. 서로 인터페이스가 다른 컴포넌트를 이어 붙이거나, 복잡한 하위 시스템을 단순한 인터페이스로 감싸거나, 객체를 트리 구조로 구성하는 등의 문제를 다룹니다. 8장(어댑터)부터 14장(프록시)까지가 여기에 속합니다.

### 행동 패턴 (Behavioral Patterns)

객체들이 **어떻게 협력하고 책임을 분담할 것인가**에 대한 패턴입니다. 요청을 여러 객체에 걸쳐 처리하거나, 알고리즘을 캡슐화해서 교체 가능하게 만들거나, 객체 간의 상태 변화를 통지하는 등의 문제를 다룹니다. 15장(체인 오브 리스판서빌리티)부터 25장(비지터)까지가 여기에 속합니다.

이 세 가지 분류를 미리 알아두면, 새로운 패턴을 만났을 때 "이건 객체를 만드는 문제인가, 구조를 짜는 문제인가, 아니면 협력 방식의 문제인가"를 먼저 따져보는 습관이 생깁니다. 이것만으로도 패턴을 훨씬 빠르게 이해할 수 있습니다.

## 패턴을 배우면 무엇이 좋아지는가

### 공통 어휘를 갖게 된다

"이 부분은 옵저버 패턴으로 처리했어요"라는 한마디로 수십 줄의 구조 설명을 대신할 수 있습니다. 패턴 이름은 팀 내에서, 나아가 업계 전체에서 통용되는 압축된 설계 언어입니다. 코드 리뷰나 설계 논의에서 "그거 팩토리 메서드로 뽑아내면 되지 않을까요?"라는 대화가 자연스럽게 오갈 수 있다면, 서로 긴 설명 없이도 설계 의도를 빠르게 공유할 수 있습니다.

### 검증된 해법을 재사용할 수 있다

패턴은 이미 여러 상황에서 통했던 구조입니다. 처음부터 설계를 고민하는 대신, "이 상황은 전략 패턴이 맞겠다"라고 판단하고 그 구조를 적용하면, 시행착오를 줄이고 알려진 함정들을 피해갈 수 있습니다.

### 유지보수성과 확장성이 좋아진다

대부분의 패턴은 결국 "변하는 부분과 변하지 않는 부분을 분리한다"는 공통된 목표를 가지고 있습니다. 이렇게 분리해두면 요구사항이 바뀌었을 때 코드 전체를 건드리지 않고 변하는 부분만 교체하거나 확장할 수 있습니다. 이는 2장에서 다룰 개방-폐쇄 원칙과도 직결되는 이야기입니다.

## 패턴 남용의 함정

패턴은 강력한 도구이지만, 도구가 강력할수록 잘못 쓰였을 때의 부작용도 큽니다. 디자인 패턴을 배우고 나면 흔히 겪는 함정이 하나 있습니다. 바로 **모든 문제에 패턴을 끼워 맞추려는 유혹**입니다.

간단한 예를 들어보겠습니다. 클래스 하나로 충분히 해결되는 작은 기능을 굳이 추상 팩토리와 전략 패턴, 데코레이터를 조합해서 만들면 어떻게 될까요? 코드를 읽는 사람은 실제 로직을 이해하기 전에 대여섯 개의 인터페이스와 클래스 사이를 오가며 "이게 왜 이렇게 복잡하게 짜여 있지?"라는 의문부터 갖게 됩니다. 패턴은 복잡성을 관리하기 위한 도구인데, 필요 없는 곳에 적용하면 오히려 복잡성을 만들어내는 원인이 되어버립니다.

좋은 설계자는 패턴을 "알고 있는 것"과 "적용하는 것"을 구분합니다. 이 책의 각 패턴 챕터마다 등장하는 "언제 사용하는가" 섹션은 바로 이 판단 기준을 다루기 위한 것입니다. 패턴을 배울 때는 항상 "이 패턴이 해결하는 문제가 지금 내 코드에 실제로 존재하는가?"를 함께 물어야 합니다. 문제가 존재하지 않는데 패턴을 먼저 들이대는 것은, 못도 없는데 망치부터 휘두르는 것과 다르지 않습니다.

## 이 책에서 사용하는 C# 관례

이 책의 모든 예제 코드는 C#으로 작성됩니다. 패턴 자체는 언어에 종속되지 않는 개념이지만, 구체적인 코드를 보여주기 위해서는 일관된 관례가 필요합니다. 이 책 전체에서 다음 규칙을 따릅니다.

- **인터페이스**는 `IShape`, `IObserver`처럼 이름 앞에 `I`를 붙입니다. 이는 C# 커뮤니티에서 널리 쓰이는 관례입니다.
- **클래스, 메서드, 속성(프로퍼티)**의 이름은 `PascalCase`로 씁니다. 예: `OrderService`, `CalculateTotal()`, `TotalPrice`.
- **지역 변수와 매개변수**는 `camelCase`로 씁니다. 예: `orderCount`, `customerName`.
- **private 필드**는 밑줄과 함께 `camelCase`로 씁니다. 예: `_orderCount`.
- 접근 제한자는 명시적으로 표기합니다. 특별한 이유가 없다면 필드는 `private`, 다른 클래스에 노출할 API는 `public`으로 선언하고, 그 중간이 필요할 때 `protected`나 `internal`을 사용합니다.
- 주석은 한국어로 작성하며, `//` 한 줄 주석을 기본으로 사용합니다.

다음은 이 관례를 반영한 아주 간단한 예시입니다.

```csharp
// 결제 수단을 표현하는 인터페이스
public interface IPaymentMethod
{
    // 금액을 결제하고 성공 여부를 반환한다
    bool Pay(decimal amount);
}

// 신용카드 결제를 구현한 클래스
public class CreditCardPayment : IPaymentMethod
{
    private readonly string _cardNumber;

    public CreditCardPayment(string cardNumber)
    {
        _cardNumber = cardNumber;
    }

    public bool Pay(decimal amount)
    {
        // 실제로는 카드사 API를 호출하는 로직이 들어간다
        Console.WriteLine($"{_cardNumber} 카드로 {amount:C} 결제 완료");
        return true;
    }
}
```

이 짧은 코드에도 이 책 전체에서 반복될 관례들이 모두 담겨 있습니다. 인터페이스는 `IPaymentMethod`, 클래스와 메서드는 `PascalCase`, private 필드는 `_cardNumber`, 매개변드는 `camelCase`로 되어 있습니다. 앞으로 등장하는 모든 예제 코드도 이 규칙을 그대로 따릅니다.

## 이 책을 읽는 방법

이 책은 크게 세 부분으로 구성됩니다.

1장과 2장은 준비 단계입니다. 패턴이라는 개념 자체와, 패턴들이 공통적으로 지향하는 객체지향 설계 원칙(SOLID)을 먼저 정리합니다. 패턴을 하나씩 외우기 전에 "왜 이런 구조가 필요한가"에 대한 감을 잡는 것이 목표입니다.

3장부터 25장까지는 23가지 GoF 패턴을 생성, 구조, 행동 순서로 다룹니다. 각 챕터는 동일한 구조를 따릅니다.

- **문제 상황**: 패턴이 없을 때 실제로 어떤 코드가 만들어지고, 그 코드가 왜 문제가 되는지를 먼저 보여줍니다.
- **패턴 설명**: 그 패턴의 의도와 구조를 설명합니다.
- **C# 예제 코드**: 실제로 동작하는 코드를 통해 패턴을 구현하는 방법을 보여줍니다.
- **언제 사용하는가**: 장단점과 실전에서의 활용 사례, 비슷한 다른 패턴과의 차이를 정리합니다.
- **요약**과 **연습문제**로 각 장을 마무리합니다.

이 책을 읽을 때는 패턴의 이름과 구조를 외우려 하기보다, "문제 상황" 절의 나쁜 예제 코드를 먼저 자기 손으로 이해해 보는 것을 추천합니다. 문제를 충분히 느낀 다음에 해법을 보면, 그 해법이 왜 그런 형태를 띠는지가 훨씬 명확하게 다가옵니다. 그리고 각 장의 연습문제는 단순히 패턴을 그대로 베끼는 것이 아니라, 여러분이 겪었거나 겪을 법한 상황에 패턴을 적용해보도록 설계되어 있으니 직접 코드를 작성해 보시길 권합니다.

부록에서는 여러 패턴 중 어떤 것을 선택해야 할지 판단하는 가이드와, 이 책의 다이어그램에서 사용하는 UML 표기법을 정리해 두었습니다. 패턴이 헷갈릴 때마다 참고 자료로 활용하시면 됩니다.

그럼 다음 장에서, 패턴들이 공통적으로 딛고 서 있는 기반인 객체지향 설계 원칙부터 다시 살펴보겠습니다.

## 요약

- 디자인 패턴은 반복적으로 발생하는 설계 문제에 대해 검증된 해결책을 구조화한 템플릿이다. 구체적인 코드가 아니라 역할과 관계에 대한 설계도다.
- "Gang of Four(GoF)"는 1994년 네 명의 저자가 23가지 객체지향 설계 패턴을 정리해 소개한 데서 유래한 용어이며, 이 책의 패턴 분류도 이를 따른다.
- 패턴은 생성(어떻게 만드는가), 구조(어떻게 조합하는가), 행동(어떻게 협력하는가) 세 가지로 분류된다.
- 패턴을 알면 공통 어휘를 얻고, 검증된 해법을 재사용하고, 유지보수성을 높일 수 있지만, 필요 없는 곳에 남용하면 불필요한 복잡도를 만들어낸다.
- 이 책은 인터페이스에 `I` 접두사, PascalCase, camelCase, `_camelCase` 필드 등 C# 커뮤니티의 관례를 일관되게 사용한다.

## 연습문제

1. 여러분이 최근에 작성했거나 읽었던 코드 중에서, "이런 문제는 전에도 본 적 있는데"라고 느꼈던 반복적인 구조적 문제가 있었는지 떠올려 보세요. 그 문제를 한두 문단으로 설명해 보세요.
2. 디자인 패턴을 "복사해서 붙여넣을 수 있는 코드"가 아니라 "설계 템플릿"이라고 부르는 이유를 자신의 언어로 설명해 보세요.
3. 생성, 구조, 행동이라는 세 가지 분류 중, 여러분이 지금까지 프로젝트에서 가장 자주 마주쳤을 것 같은 유형은 무엇이라고 생각하나요? 그 이유는 무엇인가요?
4. 패턴을 남용해서 오히려 코드가 복잡해진 경험(직접 겪었거나 들어본 사례)이 있다면 설명해 보세요. 없다면, 어떤 상황에서 패턴 남용이 발생할 수 있을지 가상의 예를 만들어 보세요.
5. 이 책의 C# 코드 관례(인터페이스에 `I` 접두사, private 필드에 `_` 접두사 등)가 익숙한지, 혹은 여러분이 평소 쓰던 관례와 다른 점이 있는지 비교해 보세요.

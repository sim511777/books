## 문제 상황

사내 인사 시스템을 만들고 있다고 해보자. 직원 명단을 관리하는 `EmployeeRoster` 클래스가 있는데, 처음에는 내부적으로 배열을 썼다가 팀이 커지면서 `List<Employee>`로 바꾸고, 나중에는 부서별로 트리 구조를 도입해서 조직도까지 표현하게 됐다.

문제는 이 클래스를 사용하는 다른 코드들이다. 처음 배열이었을 때는 `for (int i = 0; i < roster.Count; i++)`처럼 인덱스로 접근하는 코드가 여기저기 퍼졌다. 내부 구조를 `List`로 바꿨을 때는 다행히 인덱스 접근이 그대로 동작했지만, 트리 구조로 바꾸는 순간 기존 순회 코드는 전부 망가진다. 순회하는 쪽 코드가 컬렉션의 내부 구현 방식(배열인지, 리스트인지, 트리인지)을 알고 있었기 때문이다.

또 다른 요구도 있다. 화면에는 "재직 중인 직원만" 보여줘야 하는 목록도 있고, "특정 부서에 속한 직원만" 보여줘야 하는 목록도 있다. 매번 `EmployeeRoster`에 `GetActiveEmployees()`, `GetEmployeesByDepartment()` 같은 메서드를 추가하고 그 안에서 조건에 맞는 직원을 골라 새 리스트를 만들어 반환하는 방식은, 조건이 늘어날수록 컬렉션 클래스가 점점 비대해지고 필터링 로직과 저장 로직이 뒤섞이게 만든다.

컬렉션을 사용하는 쪽에서는 내부 구조를 몰라도 되고, 컬렉션을 만드는 쪽에서는 다양한 순회 방식(전체, 필터링된 일부, 특정 순서 등)을 유연하게 제공할 수 있는 방법이 필요하다.

## 패턴 설명

이터레이터 패턴은 컬렉션의 내부 표현 방식을 노출하지 않으면서, 그 원소들을 순차적으로 접근할 수 있는 방법을 제공하는 패턴이다. 핵심은 "순회하는 방법"을 컬렉션 자체가 아니라 별도의 이터레이터 객체에 위임하는 것이다.

일반적으로 두 가지 역할이 등장한다.

- 컬렉션(Aggregate) 역할: 원소들을 담고 있고, 이터레이터를 만들어 반환하는 책임을 가진다.
- 이터레이터(Iterator) 역할: "다음 원소가 있는가"(`MoveNext`)와 "현재 원소가 무엇인가"(`Current`)를 알려주는 최소한의 인터페이스를 제공한다.

순회하는 코드는 컬렉션이 배열인지, 리스트인지, 트리인지 전혀 몰라도 되고, 오직 이터레이터가 제공하는 `MoveNext`와 `Current`만 알면 된다. 컬렉션 내부 구조가 나중에 바뀌더라도, 이터레이터 인터페이스가 그대로 유지되면 순회하는 쪽 코드는 손댈 필요가 없다.

여기서 흥미로운 사실이 있다. C#을 쓰고 있다면 이 패턴을 이미 매일 쓰고 있다. `foreach` 문 자체가 이터레이터 패턴을 언어 차원에서 지원하기 위한 문법이다. `foreach`가 동작하려면 대상 객체가 `IEnumerable`(또는 `IEnumerable<T>`)을 구현해서 `GetEnumerator()`를 제공해야 하고, 그 메서드가 반환하는 객체는 `IEnumerator`(또는 `IEnumerator<T>`)를 구현해서 `MoveNext()`와 `Current`를 제공해야 한다. 이 두 인터페이스가 바로 위에서 말한 컬렉션 역할과 이터레이터 역할에 그대로 대응한다.

더 나아가 C#의 `yield return` 문법은 이터레이터 역할을 구현하는 클래스를 손으로 작성하는 수고를 덜어준다. `yield return`을 쓰면 컴파일러가 뒤에서 상태를 기억하는 이터레이터 클래스를 자동으로 만들어주기 때문에, 개발자는 "어떤 순서로 원소를 내보낼 것인가"에만 집중할 수 있다.

## C# 예제 코드

앞서 이야기한 "재직 중인 직원만 순회하는 컬렉션" 요구를 `yield return`으로 구현해보자.

```csharp
public class Employee
{
    public string Name { get; }
    public string Department { get; }
    public bool IsActive { get; }

    public Employee(string name, string department, bool isActive)
    {
        Name = name;
        Department = department;
        IsActive = isActive;
    }
}

// 내부적으로 List<Employee>를 쓰지만, 사용하는 쪽은 그 사실을 몰라도 된다
public class EmployeeRoster : IEnumerable<Employee>
{
    private readonly List<Employee> _employees = new();

    public void Add(Employee employee)
    {
        _employees.Add(employee);
    }

    // 전체 직원을 순회하는 기본 이터레이터
    public IEnumerator<Employee> GetEnumerator()
    {
        foreach (var employee in _employees)
        {
            yield return employee;
        }
    }

    System.Collections.IEnumerator System.Collections.IEnumerable.GetEnumerator()
    {
        return GetEnumerator();
    }

    // 재직 중인 직원만 걸러서 순회하는 별도의 이터레이터
    public IEnumerable<Employee> GetActiveEmployees()
    {
        foreach (var employee in _employees)
        {
            if (employee.IsActive)
            {
                // 조건을 만족하는 원소만 하나씩 내보낸다
                yield return employee;
            }
        }
    }

    // 특정 부서 직원만 걸러서 순회하는 이터레이터
    public IEnumerable<Employee> GetEmployeesByDepartment(string department)
    {
        foreach (var employee in _employees)
        {
            if (employee.Department == department)
            {
                yield return employee;
            }
        }
    }
}
```

사용하는 쪽 코드는 `EmployeeRoster`가 내부적으로 무엇을 쓰든 신경 쓸 필요가 없다.

```csharp
public class Program
{
    public static void Main()
    {
        var roster = new EmployeeRoster();
        roster.Add(new Employee("김서연", "개발팀", true));
        roster.Add(new Employee("이도윤", "영업팀", false));
        roster.Add(new Employee("박지우", "개발팀", true));

        // foreach는 내부적으로 GetEnumerator()와 MoveNext()를 사용한다
        foreach (var employee in roster)
        {
            System.Console.WriteLine($"전체: {employee.Name}");
        }

        foreach (var employee in roster.GetActiveEmployees())
        {
            System.Console.WriteLine($"재직 중: {employee.Name}");
        }

        foreach (var employee in roster.GetEmployeesByDepartment("개발팀"))
        {
            System.Console.WriteLine($"개발팀: {employee.Name}");
        }
    }
}
```

`GetActiveEmployees()`나 `GetEmployeesByDepartment()`는 새 리스트를 미리 만들어서 반환하는 것이 아니다. `yield return`으로 작성된 메서드는 호출 즉시 실행되지 않고, `foreach`가 실제로 원소를 하나씩 요청할 때마다 필요한 만큼만 실행되는 지연 평가(lazy evaluation) 방식으로 동작한다. 이 덕분에 원소가 아주 많은 컬렉션에서도 불필요한 메모리 사용을 피할 수 있다.

만약 조직도처럼 트리 구조를 순회해야 한다면 같은 방식을 재귀적으로 적용할 수 있다. 10장에서 다룬 컴포지트 패턴으로 구성한 부서-직원 트리가 있다면, 각 노드에서 자신의 자식들을 순회하며 `yield return`으로 하나씩 내보내고, 자식이 다시 자신의 하위 노드를 순회하도록 재귀 호출을 걸어주는 식으로 전체 트리를 평평하게 순회하는 이터레이터를 만들 수 있다. 트리를 구성하는 로직(컴포지트)과 트리를 순회하는 로직(이터레이터)이 서로 다른 책임이라는 점을 이 조합에서 다시 확인할 수 있다.

## 언제 사용하는가

- 컬렉션의 내부 구조(배열, 리스트, 트리, 해시 기반 구조 등)를 감추고, 순회 방법만 일관되게 노출하고 싶을 때
- 같은 컬렉션에 대해 여러 가지 순회 방식(전체 순회, 조건에 맞는 부분만 순회, 역순 순회 등)을 제공하고 싶을 때
- 트리나 그래프처럼 순회 자체가 복잡한 구조를 다루면서, 그 복잡함을 순회하는 쪽 코드로부터 숨기고 싶을 때

C#에서는 대부분의 경우 직접 `IEnumerator`를 구현할 필요 없이 `yield return`을 활용하는 것으로 충분하다. 커스텀 컬렉션을 만들 때 `IEnumerable<T>`를 구현해두면 `foreach`, LINQ 메서드 등 언어와 표준 라이브러리의 다양한 기능을 그대로 활용할 수 있다는 점도 큰 이점이다.

## .NET BCL에서 이 패턴 찾아보기

이터레이터 패턴은 GoF의 23가지 패턴 중에서도 특이한 위치에 있다. 대부분의 패턴은 BCL 어딘가에서 "이 클래스가 그 패턴을 구현한 사례다"라고 짚어낼 수 있는 정도지만, 이터레이터는 아예 C# 언어 문법 자체에 흡수되어 버렸다. 이번 장 본문에서 이미 다룬 내용이지만, 이 사실이야말로 이터레이터 패턴이 얼마나 널리, 얼마나 근본적으로 받아들여졌는지를 보여주는 가장 확실한 증거이므로 다시 한번 짚어볼 가치가 있다.

`foreach (var x in collection) { ... }` 문은 컴파일 시점에 다음과 같은 코드로 그대로 풀어써진다.

```csharp
// foreach가 컴파일러에 의해 실제로 변환되는 형태
IEnumerator<int> enumerator = collection.GetEnumerator();
try
{
    while (enumerator.MoveNext())
    {
        int x = enumerator.Current;
        // 루프 본문
    }
}
finally
{
    enumerator.Dispose();
}
```

즉 `foreach`는 컬렉션(Aggregate) 역할을 하는 `IEnumerable<T>`에서 `GetEnumerator()`를 호출하고, 이터레이터 역할을 하는 `IEnumerator<T>`의 `MoveNext()`와 `Current`를 반복 호출하는 코드를 개발자 대신 작성해주는 문법 설탕(syntactic sugar)일 뿐이다.

여기서 한 단계 더 들어가면 `yield return`이 있다. 개발자가 `MoveNext()`와 `Current`를 갖춘 이터레이터 클래스를 직접 작성하려면 "지금까지 어디까지 진행했는지"를 필드로 기억해야 하는데, 이 상태 관리 코드는 손으로 쓰기 번거롭고 실수하기도 쉽다. `yield return`을 쓰면 컴파일러가 이런 상태 머신 클래스를 자동으로 생성해서 `IEnumerator<T>`를 대신 구현해준다. 개발자는 "무엇을 내보낼지"만 `yield return`으로 표현하면 되고, "어디까지 왔는지 기억하는 일"은 컴파일러가 만든 숨은 클래스가 대신 떠맡는다. 결국 이터레이터 패턴의 두 축인 컬렉션 역할과 이터레이터 역할이, 각각 `IEnumerable<T>`/`foreach`와 `IEnumerator<T>`/`yield return`이라는 언어 기능으로 정확히 대응되어 있는 셈이다.

## 요약

이터레이터 패턴은 컬렉션의 내부 구조를 노출하지 않으면서 원소를 순서대로 접근하는 방법을 별도의 객체로 분리하는 패턴이다. 컬렉션은 이터레이터를 만들어주는 책임만 지고, 실제 순회는 이터레이터가 담당하기 때문에 컬렉션의 내부 구현이 바뀌어도 순회하는 쪽 코드는 영향을 받지 않는다. C#에서는 `IEnumerable`/`IEnumerator`와 `foreach` 문이 이 패턴을 언어 차원에서 지원하며, `yield return`을 사용하면 상태를 관리하는 이터레이터 클래스를 직접 작성하지 않고도 지연 평가 방식의 순회 로직을 간결하게 만들 수 있다. 10장 컴포지트로 구성한 트리 구조를 순회할 때도 같은 방식을 재귀적으로 적용할 수 있다.

## 연습문제

1. 본문의 `EmployeeRoster`에 `GetEmployeesSortedByName()`을 추가해서, 이름 순으로 정렬된 순서로 직원을 내보내는 이터레이터를 `yield return`으로 구현해보자.
2. `IEnumerable<T>`를 구현하지 않고 `MoveNext()`, `Current`를 갖는 이터레이터 클래스를 직접 작성해서 `GetActiveEmployees()`와 동일하게 동작하도록 만들어보고, `yield return` 버전과 코드량을 비교해보자.
3. 10장에서 다룬 컴포지트 구조(부서-직원 트리)를 하나 만들고, 트리 전체를 평평하게 순회하는 재귀적인 이터레이터를 `yield return`으로 구현해보자.
4. 본문의 `GetActiveEmployees()`가 지연 평가된다는 점을 확인하기 위해, `yield return` 직전에 `Console.WriteLine`을 추가하고 `foreach`에서 `break`를 걸었을 때 몇 번이나 출력되는지 관찰해보자.
5. 같은 컬렉션을 두 개의 `foreach` 문으로 동시에 순회하면 서로 영향을 주지 않는 이유를, `GetEnumerator()`가 매번 새로운 이터레이터 인스턴스를 반환한다는 사실과 연결지어 설명해보자.

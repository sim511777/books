## 문제 상황

온라인 쇼핑몰의 주문 시스템을 만들고 있다고 해보자. 주문이 완료되면 배송비를 계산해야 하는데, 배송 방식에는 일반 배송, 당일 배송, 해외 배송 세 가지가 있다. 각 방식마다 요금을 매기는 규칙이 전혀 다르다. 일반 배송은 무게에 비례해서 요금을 매기고, 당일 배송은 거리와 시간대에 따라 할증이 붙고, 해외 배송은 국가별 관세 정보까지 계산에 끌어와야 한다.

가장 손쉬운 방법은 `OrderProcessor` 클래스 안에 `if`나 `switch`로 분기하는 것이다.

```csharp
public class OrderProcessor
{
    public decimal CalculateShippingFee(Order order, string shippingType)
    {
        if (shippingType == "일반")
        {
            return order.WeightInKg * 500;
        }
        else if (shippingType == "당일")
        {
            decimal baseFee = order.WeightInKg * 800;
            if (order.IsPeakHour) baseFee *= 1.3m;
            return baseFee + order.DistanceInKm * 200;
        }
        else if (shippingType == "해외")
        {
            decimal baseFee = order.WeightInKg * 3000;
            decimal customs = CustomsTable.GetRate(order.CountryCode) * order.DeclaredValue;
            return baseFee + customs;
        }
        else
        {
            throw new ArgumentException("알 수 없는 배송 방식입니다.");
        }
    }
}
```

당장은 문제없이 동작한다. 하지만 배송 방식을 하나 더 추가한다고 생각해 보자. "픽업 배송"이나 "새벽 배송" 같은 방식이 추가될 때마다 이 `if-else` 블록에 새 가지를 덧붙여야 한다. `OrderProcessor`는 배송비 계산과는 무관한 주문 처리, 결제, 재고 확인 같은 책임도 함께 지고 있을 텐데, 배송 규칙이 바뀔 때마다 이 거대한 클래스를 다시 열어서 컴파일하고 테스트해야 한다. 이는 2장에서 다룬 개방-폐쇄 원칙(OCP)을 정면으로 위반하는 구조다. 확장을 하려면 반드시 기존 코드를 수정해야 하기 때문이다.

더 큰 문제는 테스트다. "당일 배송 요금 계산이 맞는지" 확인하려면 `OrderProcessor` 전체를 인스턴스화하고 문자열로 배송 방식을 지정해야 한다. 배송 요금 계산 로직만 따로 떼어 단위 테스트를 하기가 어렵다. 여러 규칙이 한 메서드 안에 뒤섞여 있으니 하나를 수정하다가 다른 하나를 깨뜨릴 위험도 커진다.

## 패턴 설명

전략(Strategy) 패턴은 "같은 목적을 달성하는 여러 알고리즘을 각각 별도의 클래스로 캡슐화하고, 이들을 인터페이스로 묶어서 런타임에 교체 가능하게 만드는" 패턴이다. 클라이언트 코드는 구체적인 알고리즘이 무엇인지 알 필요 없이, 인터페이스가 정의한 계약에만 의존한다.

핵심 구성 요소는 다음과 같다.

- **전략 인터페이스(Strategy)**: 알고리즘이 수행할 작업의 시그니처를 정의한다. 예제에서는 배송비를 계산하는 메서드 하나를 선언한다.
- **구체 전략(Concrete Strategy)**: 인터페이스를 구현하는 각각의 알고리즘. 일반 배송, 당일 배송, 해외 배송이 각각 하나의 클래스가 된다.
- **컨텍스트(Context)**: 전략 객체를 보유하고, 실제 작업이 필요할 때 그 전략에게 위임하는 클래스. 예제에서는 `OrderProcessor`가 이 역할을 맡는다.

이 구조에서 새로운 배송 방식을 추가하려면 `IShippingStrategy`를 구현하는 새 클래스 하나만 작성하면 된다. `OrderProcessor`는 손댈 필요가 없다. 알고리즘을 선택하는 책임은 컨텍스트를 사용하는 쪽(또는 조립을 담당하는 코드)으로 옮겨지고, 컨텍스트는 오직 "지금 주어진 전략을 실행한다"는 것만 알면 된다.

전략 패턴은 컴포지션을 이용해 행동을 교체한다는 점에서, 상속으로 행동 일부를 바꾸는 24장의 템플릿 메서드 패턴과 대조된다. 이 차이는 이 장의 뒷부분에서 다시 살펴본다.

아래는 전략 패턴의 구조를 나타낸 것이다.

```
IShippingStrategy (interface)
    + CalculateFee(Order order): decimal
        ↑ 구현
    ┌───────────────┬───────────────┬───────────────┐
StandardShipping  ExpressShipping  InternationalShipping
    Strategy          Strategy          Strategy

OrderProcessor (Context)
    - _shippingStrategy: IShippingStrategy
    + CalculateShippingFee(order): decimal → _shippingStrategy.CalculateFee(order)
```

## C# 예제 코드

먼저 전략 인터페이스를 정의한다.

```csharp
// 배송비 계산 알고리즘의 공통 인터페이스
public interface IShippingStrategy
{
    decimal CalculateFee(Order order);
}
```

각 배송 방식을 구체 전략 클래스로 구현한다.

```csharp
// 일반 배송: 무게에 비례한 요금
public class StandardShippingStrategy : IShippingStrategy
{
    private const decimal RatePerKg = 500m;

    public decimal CalculateFee(Order order)
    {
        return order.WeightInKg * RatePerKg;
    }
}

// 당일 배송: 무게 요금 + 성수기 할증 + 거리 요금
public class ExpressShippingStrategy : IShippingStrategy
{
    private const decimal RatePerKg = 800m;
    private const decimal RatePerKm = 200m;
    private const decimal PeakHourMultiplier = 1.3m;

    public decimal CalculateFee(Order order)
    {
        decimal baseFee = order.WeightInKg * RatePerKg;
        if (order.IsPeakHour)
        {
            baseFee *= PeakHourMultiplier;
        }
        return baseFee + order.DistanceInKm * RatePerKm;
    }
}

// 해외 배송: 무게 요금 + 국가별 관세
public class InternationalShippingStrategy : IShippingStrategy
{
    private const decimal RatePerKg = 3000m;

    public decimal CalculateFee(Order order)
    {
        decimal baseFee = order.WeightInKg * RatePerKg;
        decimal customs = CustomsTable.GetRate(order.CountryCode) * order.DeclaredValue;
        return baseFee + customs;
    }
}
```

컨텍스트인 `OrderProcessor`는 전략을 생성자로 주입받아 보관하고, 필요할 때 위임만 한다.

```csharp
public class OrderProcessor
{
    private IShippingStrategy _shippingStrategy;

    public OrderProcessor(IShippingStrategy shippingStrategy)
    {
        _shippingStrategy = shippingStrategy;
    }

    // 런타임에 배송 방식을 교체할 수 있도록 세터도 열어 둔다
    public void SetShippingStrategy(IShippingStrategy shippingStrategy)
    {
        _shippingStrategy = shippingStrategy;
    }

    public decimal CalculateShippingFee(Order order)
    {
        return _shippingStrategy.CalculateFee(order);
    }
}
```

사용하는 쪽 코드는 다음과 같이 원하는 전략을 골라 주입하면 된다.

```csharp
var order = new Order { WeightInKg = 2.5m, DistanceInKm = 12, IsPeakHour = true };

var processor = new OrderProcessor(new ExpressShippingStrategy());
decimal fee = processor.CalculateShippingFee(order);
Console.WriteLine($"당일 배송비: {fee:N0}원");

// 고객이 배송 방식을 바꾸면 전략만 교체한다
processor.SetShippingStrategy(new StandardShippingStrategy());
decimal standardFee = processor.CalculateShippingFee(order);
Console.WriteLine($"일반 배송비: {standardFee:N0}원");
```

여기서 "새벽 배송" 전략을 추가한다고 해도 `OrderProcessor`는 한 줄도 수정할 필요가 없다. `IShippingStrategy`를 구현하는 `DawnShippingStrategy` 클래스를 하나 추가하고, 그것을 주입해 주는 것으로 끝난다.

### 델리게이트를 이용한 경량 구현

C#은 함수를 일급 값으로 다룰 수 있기 때문에, 전략이 상태 없이 단순한 계산 로직 하나로만 이루어져 있다면 인터페이스와 클래스 여러 개를 만드는 대신 `Func<Order, decimal>` 델리게이트로 대체할 수 있다.

```csharp
public class OrderProcessor
{
    private Func<Order, decimal> _feeCalculator;

    public OrderProcessor(Func<Order, decimal> feeCalculator)
    {
        _feeCalculator = feeCalculator;
    }

    public decimal CalculateShippingFee(Order order) => _feeCalculator(order);
}

// 사용 예: 클래스를 만들지 않고 람다식으로 바로 전략을 전달
var processor = new OrderProcessor(order => order.WeightInKg * 500m);
```

이 방식은 전략에 별도의 상태나 재사용 가능한 이름이 필요 없을 때 코드량을 크게 줄여 준다. 반대로 전략이 여러 필드를 갖거나, 팀 내에서 명확한 타입 이름으로 문서화할 필요가 있거나, DI 컨테이너로 생명주기를 관리해야 한다면 인터페이스 기반 구현이 여전히 더 적합하다.

## 언제 사용하는가

- 같은 작업을 수행하는 방법이 여러 가지이고, 그 방법이 향후 늘어나거나 자주 바뀔 것으로 예상될 때
- 알고리즘 선택 로직이 거대한 조건문으로 흩어져 있어서 유지보수가 어려울 때
- 알고리즘 각각을 독립적으로 테스트하고 싶을 때 (전략 클래스 하나만 놓고 단위 테스트를 작성할 수 있다)
- 실행 중에 알고리즘을 교체해야 할 때 (예: 사용자가 배송 방식을 바꾸거나, 설정 값에 따라 계산 방식이 달라질 때)

반대로 알고리즘이 단 하나뿐이고 앞으로도 늘어날 가능성이 거의 없다면, 전략 패턴을 미리 도입하는 것은 불필요한 추상화가 될 수 있다. 이런 경우는 조건문 하나로 충분하다.

## 22장 상태 패턴과의 차이

전략 패턴은 22장에서 다룬 상태(State) 패턴과 클래스 구조가 거의 동일하다. 둘 다 인터페이스를 정의하고, 그 인터페이스를 구현하는 여러 클래스를 컨텍스트가 들고 있다가 위임한다는 점에서 코드만 보면 구분하기 어려울 정도다. 그러나 의도와 사용 방식은 분명히 다르다.

| 구분 | 전략(Strategy) | 상태(State) |
|---|---|---|
| 목적 | 같은 문제를 푸는 여러 "방법" 중 하나를 선택 | 객체가 처한 "상태"에 따라 행동이 달라짐 |
| 교체 시점 | 대개 클라이언트(사용하는 쪽)가 명시적으로 선택 | 상태 객체 스스로 다음 상태로 전이하는 경우가 많음 |
| 전략/상태 간 관계 | 서로 독립적이고 대등함 (일반 배송이 당일 배송을 몰라도 됨) | 서로 연관되어 있고 전이 규칙을 알아야 함 (주문이 "결제완료" 상태에서 "배송중" 상태로 갈 수 있음을 상태 객체가 알아야 함) |
| 컨텍스트의 역할 | 전략을 그냥 사용만 함 | 상태 전이를 조율하거나 상태 객체가 스스로 전이시킴 |
| 클라이언트의 인식 | 클라이언트가 어떤 전략인지 알고 선택함 | 클라이언트는 보통 상태 전이를 알지 못하며, 객체가 알아서 상태를 바꿈 |

즉 전략 패턴은 "이 문제를 어떤 방식으로 풀 것인가"에 대한 답이고, 상태 패턴은 "지금 이 객체가 어떤 국면에 있는가"에 대한 답이다. 배송비 계산 예제에서 배송 방식은 주문이 생성되는 시점에 고객이 선택하는 것이므로 전략에 해당한다. 만약 주문이 "결제대기 → 결제완료 → 배송중 → 배송완료"처럼 시간에 따라 국면이 바뀌고, 각 국면에서 취소 가능 여부나 알림 방식이 달라진다면 그것은 상태 패턴의 영역이다.

## 요약

전략 패턴은 여러 알고리즘을 인터페이스 뒤로 캡슐화하여 컨텍스트와 알고리즘을 분리한다. 새로운 알고리즘을 추가할 때 기존 코드를 수정하지 않아도 되므로 개방-폐쇄 원칙을 지킬 수 있고, 각 알고리즘을 독립적으로 테스트할 수 있다. C#에서는 상태가 거의 없는 단순한 전략이라면 인터페이스 대신 델리게이트(`Func`, `Action`)로 가볍게 표현할 수도 있다. 구조가 비슷한 상태 패턴과는 목적이 다르다는 점(방법의 선택 대 국면에 따른 행동 변화)을 기억해 두면 두 패턴을 헷갈리지 않을 수 있다.

## 연습문제

1. 결제 방식(신용카드, 계좌이체, 간편결제)마다 수수료를 다르게 계산해야 하는 `PaymentProcessor`를 전략 패턴으로 설계해 보라. 인터페이스와 최소 두 개의 구체 전략 클래스를 작성하라.
2. 본문의 배송비 계산 예제에 "픽업 배송"(요금 무료, 단 특정 매장만 가능) 전략을 추가해 보라. `OrderProcessor`를 수정해야 하는 부분이 있는지 확인하라.
3. 전략 패턴을 인터페이스로 구현한 코드와 델리게이트(`Func<Order, decimal>`)로 구현한 코드를 비교했을 때, 각각이 유리한 상황을 두 가지씩 들어 보라.
4. 상태 패턴과 전략 패턴은 구조가 비슷하지만 의도가 다르다. 여러분이 다뤄본(또는 상상한) 도메인에서 "이건 전략이다"와 "이건 상태다"를 구분해야 하는 사례를 하나씩 만들어 설명하라.
5. `OrderProcessor`가 여러 배송 전략 중 최저가 전략을 자동으로 골라주는 기능을 추가하려면 어떻게 설계하면 좋을지 논하라. (힌트: 전략 목록을 순회하며 비교하는 별도의 컨텍스트나 헬퍼가 필요할 수 있다.)

## 문제 상황

간단한 마크다운 노트 앱을 만들고 있다. 사용자가 글을 쓰다가 실수로 문단을 지우거나 엉뚱한 내용을 덮어썼을 때, `Ctrl+Z`를 누르면 바로 이전 상태로 되돌아가야 한다.

`NoteDocument` 클래스는 본문 텍스트뿐 아니라 커서 위치, 현재 글자 크기 같은 여러 상태를 내부에 들고 있다.

```csharp
public class NoteDocument
{
    private string _content = "";
    private int _cursorPosition;
    private int _fontSize = 14;

    public void Type(string text) { /* _content, _cursorPosition 갱신 */ }
    public void ChangeFontSize(int size) { _fontSize = size; }
}
```

실행취소를 구현하려면 "실행취소 관리자(Undo Manager)"가 어떤 시점의 상태를 기억해두고, 필요할 때 그 상태로 되돌려야 한다. 가장 쉬운 방법은 `NoteDocument`에 `GetContent()`, `SetContent()`, `GetCursorPosition()`, `SetCursorPosition()`, `GetFontSize()`, `SetFontSize()`처럼 내부 필드마다 getter/setter를 전부 열어주고, 관리자가 이 값들을 직접 읽고 저장해두는 것이다.

```csharp
public class NaiveUndoManager
{
    // 문서의 내부 상태를 낱개로 풀어서 보관한다
    private string _savedContent;
    private int _savedCursorPosition;
    private int _savedFontSize;

    public void Backup(NoteDocument doc)
    {
        _savedContent = doc.GetContent();
        _savedCursorPosition = doc.GetCursorPosition();
        _savedFontSize = doc.GetFontSize();
    }

    public void Undo(NoteDocument doc)
    {
        doc.SetContent(_savedContent);
        doc.SetCursorPosition(_savedCursorPosition);
        doc.SetFontSize(_savedFontSize);
    }
}
```

이 방식에는 두 가지 문제가 있다. 첫째, `NoteDocument`의 내부 상태를 확인하고 조작할 수 있는 setter가 전부 공개되어 있어서, 실행취소와 아무 상관 없는 다른 코드도 `SetContent`를 마음대로 호출해 문서 내용을 임의로 바꿀 수 있다. 캡슐화가 사실상 사라진 것이다. 둘째, 나중에 "글자 색상"이라는 상태를 하나 추가하면, `NoteDocument`에 getter/setter를 추가하는 것은 물론 `NaiveUndoManager`의 `Backup`과 `Undo`도 함께 고쳐야 한다. 실행취소 관리자가 문서의 내부 구조를 속속들이 알고 있어야만 동작하는 구조이기 때문이다.

원하는 것은 이렇다. 실행취소 관리자는 "어떤 시점의 상태를 저장해두었다가 나중에 그대로 복원한다"는 역할만 하고, 그 상태가 실제로 어떤 필드로 이루어져 있는지는 전혀 몰라야 한다.

## 패턴 설명

메멘토 패턴은 객체의 상태를 세 가지 역할로 나누어 다룬다.

- **Originator(생성자 객체)**: 자기 상태를 스스로 스냅샷(Memento)으로 만들어 내보내고, 나중에 그 스냅샷을 받아서 자기 상태를 그대로 복원한다. 위 예제의 `NoteDocument`가 여기에 해당한다.
- **Memento(기념물)**: 어느 한 시점의 상태를 담은 스냅샷. Originator만 그 내용을 꺼내볼 수 있고, 외부에서는 속을 들여다볼 수 없는 "봉인된 캡슐"이어야 한다.
- **Caretaker(관리자)**: Memento를 보관하는 책임만 진다. 몇 개를 보관할지, 언제 꺼내서 Originator에게 돌려줄지는 결정하지만, Memento 안에 무엇이 들어 있는지는 절대 열어보지 않는다.

핵심은 Memento의 내용을 Originator 자신만 읽고 쓸 수 있게 만드는 것이다. C#에서는 Memento를 Originator의 **private 중첩 클래스**로 선언하면 이것이 자연스럽게 강제된다. 중첩 클래스의 private 멤버는 바깥 클래스(Originator)에서는 접근할 수 있지만, 그 외의 어떤 코드에서도 접근할 수 없다. Caretaker는 `IMemento`처럼 아무 멤버도 없는 마커 인터페이스 타입으로만 Memento를 다루므로, 손에 쥐고는 있지만 속을 들여다볼 방법이 없다.

## C# 예제 코드

```csharp
// Caretaker가 다루는 타입. 아무 멤버도 노출하지 않는 "봉인된 캡슐" 역할만 한다.
public interface IMemento
{
}

// Originator: 자기 상태를 스스로 스냅샷으로 만들고, 스스로 복원한다.
public class NoteDocument
{
    private string _content = "";
    private int _cursorPosition;
    private int _fontSize = 14;

    public void Type(string text)
    {
        _content += text;
        _cursorPosition = _content.Length;
        Console.WriteLine($"[입력] 현재 내용: \"{_content}\"");
    }

    public void ChangeFontSize(int size)
    {
        _fontSize = size;
        Console.WriteLine($"[글자 크기 변경] {size}pt");
    }

    // 현재 상태를 스냅샷으로 떠서 반환한다. 반환 타입은 아무 멤버 없는 IMemento뿐이다.
    public IMemento Save()
    {
        return new NoteMemento(_content, _cursorPosition, _fontSize);
    }

    // 전달받은 스냅샷으로 자기 상태를 되돌린다. 반드시 자기 자신이 만든 스냅샷만 받는다.
    public void Restore(IMemento memento)
    {
        // Originator이므로 private 중첩 클래스인 NoteMemento의 내부에 접근할 수 있다.
        var snapshot = (NoteMemento)memento;
        _content = snapshot.Content;
        _cursorPosition = snapshot.CursorPosition;
        _fontSize = snapshot.FontSize;
        Console.WriteLine($"[복원] 내용: \"{_content}\", 글자 크기: {_fontSize}pt");
    }

    // Memento의 실제 구현. private 중첩 클래스이므로 NoteDocument 밖에서는
    // 이 클래스의 이름조차 알 수 없고, 필드에도 접근할 수 없다.
    private class NoteMemento : IMemento
    {
        public string Content { get; }
        public int CursorPosition { get; }
        public int FontSize { get; }

        public NoteMemento(string content, int cursorPosition, int fontSize)
        {
            Content = content;
            CursorPosition = cursorPosition;
            FontSize = fontSize;
        }
    }
}

// Caretaker: Memento를 쌓아두고 꺼내주는 역할만 한다. 내용은 전혀 모른다.
public class UndoManager
{
    private readonly Stack<IMemento> _history = new Stack<IMemento>();

    // 변경을 가하기 전에 현재 상태를 저장해둔다
    public void Backup(NoteDocument document)
    {
        _history.Push(document.Save());
    }

    public void Undo(NoteDocument document)
    {
        if (_history.Count == 0)
        {
            Console.WriteLine("[실행취소] 더 되돌릴 상태가 없습니다.");
            return;
        }
        var memento = _history.Pop();
        document.Restore(memento);
    }
}

public class NoteAppDemo
{
    public static void Main()
    {
        var document = new NoteDocument();
        var undoManager = new UndoManager();

        undoManager.Backup(document); // 빈 문서 상태 저장
        document.Type("오늘 할 일:\n");

        undoManager.Backup(document); // 한 문장 입력 후 상태 저장
        document.Type("1. 디자인 패턴 원고 작성\n");

        undoManager.Backup(document); // 글자 크기 변경 전 상태 저장
        document.ChangeFontSize(18);

        Console.WriteLine("\n--- 실행취소 1회 ---");
        undoManager.Undo(document); // 글자 크기 변경 취소

        Console.WriteLine("\n--- 실행취소 1회 더 ---");
        undoManager.Undo(document); // 두 번째 입력 취소
    }
}
```

`UndoManager`는 `IMemento` 타입의 스택만 다룰 뿐, 그 안에 문자열이 몇 개 들어있는지, 필드 이름이 무엇인지 전혀 알지 못한다. 나중에 `NoteDocument`에 "글자 색상"이라는 상태가 추가되어도 바뀌는 코드는 `NoteMemento`와 `Save`, `Restore` 뿐이며, `UndoManager`는 한 글자도 수정할 필요가 없다. 캡슐화가 그대로 유지되는 것이다.

## 커맨드 패턴과 함께 사용하기

16장에서 다룬 커맨드 패턴은 실행(`Execute`)뿐 아니라 취소(`Undo`)까지 하나의 명령 객체 안에 담는다. 그런데 "취소"를 구현하는 방법에는 두 갈래가 있다. 하나는 각 명령이 "반대로 되돌리는 논리"를 직접 구현하는 방법이고(예: `InsertTextCommand`의 반대는 `DeleteTextCommand`), 다른 하나는 명령을 실행하기 직전에 대상 객체의 메멘토를 떠두고, 취소할 때 그 메멘토로 복원해버리는 방법이다.

```csharp
// 메멘토를 활용해 취소를 구현하는 커맨드
public class ChangeFontSizeCommand : ICommand
{
    private readonly NoteDocument _document;
    private readonly int _newSize;
    private IMemento _mementoBeforeExecute; // 실행 전 상태를 여기 담아둔다

    public ChangeFontSizeCommand(NoteDocument document, int newSize)
    {
        _document = document;
        _newSize = newSize;
    }

    public void Execute()
    {
        _mementoBeforeExecute = _document.Save(); // 실행 직전 상태를 스냅샷으로 저장
        _document.ChangeFontSize(_newSize);
    }

    public void Undo()
    {
        _document.Restore(_mementoBeforeExecute); // 저장해둔 스냅샷으로 되돌린다
    }
}
```

이렇게 하면 명령 클래스마다 "되돌리는 논리"를 따로 작성할 필요가 없다. "실행 전 상태를 기억했다가 그대로 복원한다"는 동작은 어떤 변경에도 똑같이 적용되기 때문이다. 다만 메멘토를 매번 뜨는 방식은 상태 전체를 복사하므로, 상태가 아주 크거나 변경이 매우 잦은 경우에는 메모리 사용량을 함께 고려해야 한다.

## 언제 사용하는가

메멘토 패턴은 다음과 같은 상황에 적합하다.

- 실행취소·재실행 기능처럼, 객체를 이전 상태로 되돌려야 하는데 그 객체의 내부 구조를 외부에 노출하고 싶지 않을 때.
- 저장/불러오기처럼 "현재 상태를 통째로 떠서 나중에 그대로 복원"해야 하는데, 그 상태를 관리하는 코드(Caretaker)가 상태의 세부 내용을 알 필요는 없을 때.
- 여러 시점의 상태를 스택이나 리스트로 쌓아두고, 사용자가 원하는 시점으로 이동해야 할 때. 그림 편집 프로그램의 여러 단계 실행취소, 게임의 체크포인트 저장이 대표적인 예다.

반대로 객체의 상태가 아주 크고 변경이 매우 빈번하다면, 스냅샷을 매번 통째로 뜨는 방식은 메모리를 많이 소모한다. 이런 경우에는 상태 전체가 아니라 "변경된 부분(diff)"만 기록하는 방식을 고려해야 하며, 이는 메멘토 패턴의 기본 형태를 넘어서는 최적화의 영역이다.

## .NET BCL에서 이 패턴 찾아보기

.NET BCL 안에서 메멘토 패턴을 실제로 구현한 사례를 찾는다면 `System.ComponentModel.IEditableObject` 인터페이스가 정확히 들어맞는다. 이 인터페이스는 `BeginEdit()`, `EndEdit()`, `CancelEdit()`이라는 세 메서드로 구성되는데, 각각의 역할이 이번 장에서 설명한 메멘토 패턴의 흐름과 정확히 대응한다. `BeginEdit()`은 편집을 시작하기 전에 현재 상태를 스냅샷으로 떠두고, `EndEdit()`은 편집한 내용을 그대로 확정하며(스냅샷은 버려진다), `CancelEdit()`은 사용자가 편집을 취소했을 때 떠두었던 스냅샷으로 상태를 되돌린다.

```csharp
using System.ComponentModel;

// DataGridView 같은 데이터 바인딩 컨트롤이 인식하는 실제 메멘토 패턴 구현체
public class Customer : IEditableObject
{
    public string Name { get; set; }
    public string Email { get; set; }

    private Customer _backup; // 편집 시작 시점의 상태를 담아두는 스냅샷
    private bool _isEditing;

    public void BeginEdit()
    {
        if (_isEditing) return;
        // 현재 상태를 스냅샷으로 떠둔다
        _backup = new Customer { Name = Name, Email = Email };
        _isEditing = true;
    }

    public void CancelEdit()
    {
        if (!_isEditing) return;
        // 떠두었던 스냅샷으로 되돌린다
        Name = _backup.Name;
        Email = _backup.Email;
        _isEditing = false;
    }

    public void EndEdit()
    {
        // 변경 사항을 확정하고 스냅샷은 폐기한다
        _backup = null;
        _isEditing = false;
    }
}
```

`DataGridView`처럼 데이터 바인딩을 지원하는 컨트롤은 사용자가 셀 편집을 시작하는 순간 바인딩된 객체의 `BeginEdit()`을 자동으로 호출하고, 사용자가 값을 확정하면(다른 행으로 이동하거나 Enter를 누르면) `EndEdit()`을, `Esc` 키를 눌러 편집을 취소하면 `CancelEdit()`을 호출한다. 그 결과 사용자가 그리드에서 값을 수정하다가 취소 키를 누르면 화면과 바인딩된 객체 모두 원래 값으로 되돌아가는데, 이 복원 과정에서 `Customer` 클래스는 자신의 상태를 스스로 저장하고 스스로 복원할 뿐, 외부의 어떤 코드도 `_backup` 필드에 직접 접근하지 않는다. 이는 20장 본문에서 정의한 "객체의 캡슐화를 깨지 않고 이전 상태로 되돌린다"는 메멘토 패턴의 정의와 정확히 일치하는, BCL에서 찾을 수 있는 가장 명확한 사례다.

## 요약

- 메멘토 패턴은 객체(Originator)가 자기 상태의 스냅샷(Memento)을 스스로 만들고 복원하게 하여, 캡슐화를 깨지 않으면서 이전 상태로 되돌리는 방법을 제공한다.
- Memento는 Originator만 내용을 읽고 쓸 수 있는 봉인된 캡슐이어야 하며, C#에서는 private 중첩 클래스와 아무 멤버도 없는 마커 인터페이스로 이를 구현할 수 있다.
- Caretaker는 Memento를 보관하고 꺼내주는 역할만 하고, 그 안의 내용은 절대 들여다보지 않는다.
- 16장 커맨드 패턴의 `Undo` 구현에 메멘토를 결합하면, 명령마다 되돌리는 논리를 따로 작성하지 않고도 "실행 전 상태로 복원한다"는 동작을 일관되게 적용할 수 있다.

## 연습문제

1. 이번 장의 `NoteDocument`에 "글자 색상(`_fontColor`)"이라는 상태를 추가해 보라. `NoteMemento`, `Save`, `Restore`를 어떻게 고쳐야 하며, `UndoManager`는 수정이 필요한가?
2. `UndoManager`에 재실행(Redo) 기능을 추가하려면 어떤 자료구조가 추가로 필요한가? `Undo`를 호출했을 때 Redo용으로 무엇을 저장해두어야 하는지 설계해 보라.
3. `IMemento`가 아무 멤버도 없는 마커 인터페이스인데, 만약 실수로 `Content` 프로퍼티를 `IMemento`에 노출시켜 버렸다면 캡슐화 관점에서 어떤 문제가 생기는지 설명해 보라.
4. 그림 그리기 앱에서 도형 100개가 캔버스에 있는 상태를 매번 통째로 스냅샷으로 뜬다면 실행취소 한 번마다 메모리 사용량이 급격히 늘어날 수 있다. 이 문제를 완화할 수 있는 방법을 한 가지 이상 제안해 보라.
5. 메멘토 패턴과 7장 프로토타입은 둘 다 객체의 상태를 복제하는 개념을 다룬다. 두 패턴의 목적이 어떻게 다른지 설명해 보라.

## 문제 상황

지역 대기질 정보를 제공하는 서비스를 만든다고 해보자. 도시 곳곳에 설치된 미세먼지 측정소는 5분마다 PM2.5 농도를 갱신한다. 이 값이 바뀌면 여러 화면에 반영되어야 한다.

- 버스 정류장에 설치된 **전자 게시판**은 현재 농도와 "좋음/보통/나쁨" 등급을 표시한다.
- 시민들이 설치한 **모바일 앱**은 농도가 "나쁨" 이상으로 올라가면 푸시 알림을 보낸다.
- 지하철 역사의 **환기 제어 시스템**은 농도에 따라 송풍량을 자동으로 조절한다.

맨 처음 만든 버전은 각 화면이 스스로 측정소에 값을 물어보는 방식이었다.

```csharp
public class ElectronicBillboard
{
    private readonly AirQualityStation _station;

    public ElectronicBillboard(AirQualityStation station) => _station = station;

    public void Poll()
    {
        int pm25 = _station.CurrentPm25; // 값이 바뀌었는지 모르니 매번 다시 읽는다
        Console.WriteLine($"[게시판] 현재 PM2.5: {pm25}");
    }
}
```

이 방식은 `ElectronicBillboard`, `MobileAlertService`, `VentilationController` 각각이 별도의 타이머를 돌리면서 몇 초마다 `_station.CurrentPm25`를 확인한다. 값이 실제로 바뀐 적이 없어도 계속 확인 작업이 일어나므로 자원이 낭비되고, 반대로 값이 갱신된 순간과 화면이 확인하는 순간 사이에 시차가 생겨 알림이 늦어질 수도 있다.

그래서 폴링을 없애고, 측정소가 값이 바뀔 때마다 각 화면의 메서드를 직접 호출하도록 바꿔보았다.

```csharp
public class AirQualityStation
{
    private readonly ElectronicBillboard _billboard;
    private readonly MobileAlertService _mobileAlert;
    private readonly VentilationController _ventilation;

    public AirQualityStation(ElectronicBillboard billboard, MobileAlertService mobileAlert, VentilationController ventilation)
    {
        _billboard = billboard;
        _mobileAlert = mobileAlert;
        _ventilation = ventilation;
    }

    public void UpdatePm25(int pm25)
    {
        // 값이 바뀔 때마다 알아야 하는 대상을 하나하나 직접 호출한다
        _billboard.OnPm25Changed(pm25);
        _mobileAlert.OnPm25Changed(pm25);
        _ventilation.OnPm25Changed(pm25);
    }
}
```

폴링 문제는 사라졌지만 새로운 문제가 생겼다. `AirQualityStation`이 `ElectronicBillboard`, `MobileAlertService`, `VentilationController`라는 구체 클래스를 전부 알고 있어야 한다. 이후 "공공 데이터 포털에 값을 실시간으로 전송하는 기능"이 추가되면 `AirQualityStation`의 생성자와 `UpdatePm25` 메서드를 또 고쳐야 한다. 측정소 하나가 여러 측정소로 늘어나는 상황이라면 이 코드가 측정소마다 반복된다. 통지를 받아야 하는 대상이 늘어날 때마다 통지를 보내는 쪽의 코드를 계속 건드려야 하는 것이 문제의 핵심이다.

## 패턴 설명

옵저버 패턴은 어떤 객체(**Subject**)의 상태가 바뀌었을 때, 그 변화에 관심 있는 여러 객체(**Observer**)에게 자동으로 알리는 구조를 만든다. Subject는 자신을 구독하는 Observer들의 목록만 관리할 뿐, 그 목록에 어떤 구체적인 클래스가 들어있는지는 알지 못한다. 목록에는 공통 인터페이스만 존재한다.

핵심 구성 요소는 다음과 같다.

- **ISubject**: Observer를 등록(`Attach`)하고 해제(`Detach`)하고, 상태가 바뀌면 등록된 모두에게 통지(`Notify`)하는 역할을 정의하는 인터페이스.
- **IObserver**: 통지를 받았을 때 수행할 동작을 정의하는 인터페이스. Subject는 이 인터페이스만 알면 된다.
- **ConcreteSubject**: 실제 상태를 가지고 있고, 상태가 바뀔 때마다 `Notify`를 호출하는 클래스.
- **ConcreteObserver**: `IObserver`를 구현해서 통지를 받으면 자신이 할 일을 하는 클래스.

앞의 예제에서 문제였던 "Subject가 구체 클래스를 직접 알아야 한다"는 점이 여기서 해결된다. `AirQualityStation`은 `List<IObserver>`만 관리하고, 새로운 화면이 추가되어도 그 화면이 `IObserver`를 구현해서 `Attach`로 등록하기만 하면 된다. `AirQualityStation`의 코드는 전혀 바뀌지 않는다.

구조를 그림으로 나타내면 다음과 같다.

```text
  +----------------------------+          +--------------------------------+
  |   <<interface>>            |          |       <<interface>>            |
  |   IAirQualitySubject       |          |     IAirQualityObserver        |
  |   + Attach / Detach        |          |   + OnPm25Changed(pm25)        |
  +----------------------------+          +--------------------------------+
              ^                                  ^          ^          ^
              : (구현)                            :          :          :
              :                          통지(1)  :  통지(2)  :  통지(3)  :
  +----------------------------+  ------------>+----------------+       :
  |     AirQualityStation      |               |ElectronicBillboard|     :
  |  - _observers: List<IObserver>|            |+OnPm25Changed()  |     :
  |  - _pm25                    |             |  농도/등급 표시    |     :
  |  + UpdatePm25(value)        |  ------------>+----------------+       :
  |  (값이 바뀌면 Notify 호출)     |               |MobileAlertService|     :
  +----------------------------+               |+OnPm25Changed()  |     :
                                                |  기준치 초과 시     |     :
                                                |  푸시 알림         |     :
                                                +----------------+       :
                                    ------------>+----------------------+
                                                 |VentilationController |
                                                 |+OnPm25Changed()       |
                                                 |  송풍 단계 자동 조절    |
                                                 +----------------------+

  그림 설명
  AirQualityStation은 등록된 IAirQualityObserver 목록만 알고 있으며, 값이 바뀌면
  Notify를 통해 목록의 모든 대상에게 동시에 통지한다. 새 화면이 추가되어도
  Station 코드는 바뀌지 않는다.
```

## C# 예제 코드

### (1) 인터페이스를 직접 정의하는 고전적인 구현

```csharp
// 통지를 받는 쪽이 구현할 인터페이스
public interface IAirQualityObserver
{
    void OnPm25Changed(int pm25);
}

// 통지를 보내는 쪽이 구현할 인터페이스
public interface IAirQualitySubject
{
    void Attach(IAirQualityObserver observer);
    void Detach(IAirQualityObserver observer);
}

public class AirQualityStation : IAirQualitySubject
{
    private readonly List<IAirQualityObserver> _observers = new();
    private int _pm25;

    public void Attach(IAirQualityObserver observer) => _observers.Add(observer);

    public void Detach(IAirQualityObserver observer) => _observers.Remove(observer);

    public void UpdatePm25(int pm25)
    {
        if (_pm25 == pm25) return; // 값이 실제로 바뀌었을 때만 통지한다

        _pm25 = pm25;
        Notify();
    }

    private void Notify()
    {
        foreach (var observer in _observers)
        {
            observer.OnPm25Changed(_pm25);
        }
    }
}

public class ElectronicBillboard : IAirQualityObserver
{
    public void OnPm25Changed(int pm25)
    {
        string grade = pm25 <= 15 ? "좋음" : pm25 <= 35 ? "보통" : "나쁨";
        Console.WriteLine($"[전자게시판] PM2.5 {pm25} ({grade})");
    }
}

public class MobileAlertService : IAirQualityObserver
{
    public void OnPm25Changed(int pm25)
    {
        if (pm25 > 35)
        {
            Console.WriteLine($"[모바일 푸시] 미세먼지 나쁨! 현재 {pm25}. 마스크를 착용하세요.");
        }
    }
}

public class VentilationController : IAirQualityObserver
{
    public void OnPm25Changed(int pm25)
    {
        int fanLevel = pm25 > 35 ? 3 : pm25 > 15 ? 2 : 1;
        Console.WriteLine($"[환기 시스템] 송풍 단계를 {fanLevel}단으로 조정");
    }
}
```

사용하는 코드는 이렇다.

```csharp
var station = new AirQualityStation();
station.Attach(new ElectronicBillboard());
station.Attach(new MobileAlertService());
station.Attach(new VentilationController());

station.UpdatePm25(12);
Console.WriteLine("---");
station.UpdatePm25(48);
```

새로운 화면, 이를테면 공공 데이터 포털 전송 기능이 필요해지면 `IAirQualityObserver`를 구현하는 클래스 하나를 추가하고 `Attach`로 등록하면 끝난다. `AirQualityStation` 클래스의 소스는 한 줄도 건드릴 필요가 없다.

### (2) C#의 event/delegate로 표현한 같은 구조

C#은 옵저버 패턴에 해당하는 기능을 언어 차원에서 `event`와 `delegate`로 이미 제공한다. `IAirQualityObserver`라는 인터페이스를 따로 만들지 않고, Subject가 이벤트를 하나 선언하면 그 자체로 "구독자 목록을 관리하고 통지한다"는 의미가 된다.

```csharp
public class AirQualityChangedEventArgs : EventArgs
{
    public int Pm25 { get; }
    public AirQualityChangedEventArgs(int pm25) => Pm25 = pm25;
}

public class AirQualityStation
{
    // 이 이벤트 자체가 Attach/Detach/Notify 역할을 모두 담당한다
    public event EventHandler<AirQualityChangedEventArgs> Pm25Changed;

    private int _pm25;

    public void UpdatePm25(int pm25)
    {
        if (_pm25 == pm25) return;

        _pm25 = pm25;
        Pm25Changed?.Invoke(this, new AirQualityChangedEventArgs(pm25)); // 구독자 전체에게 통지
    }
}
```

구독하는 쪽은 별도의 클래스나 인터페이스 구현 없이 메서드나 람다를 이벤트에 등록(`+=`)하기만 하면 된다.

```csharp
var station = new AirQualityStation();

station.Pm25Changed += (sender, e) =>
{
    string grade = e.Pm25 <= 15 ? "좋음" : e.Pm25 <= 35 ? "보통" : "나쁨";
    Console.WriteLine($"[전자게시판] PM2.5 {e.Pm25} ({grade})");
};

station.Pm25Changed += (sender, e) =>
{
    if (e.Pm25 > 35)
        Console.WriteLine($"[모바일 푸시] 미세먼지 나쁨! 현재 {e.Pm25}.");
};

// 구독 해제도 가능하다
EventHandler<AirQualityChangedEventArgs> ventilationHandler = (sender, e) =>
{
    int fanLevel = e.Pm25 > 35 ? 3 : e.Pm25 > 15 ? 2 : 1;
    Console.WriteLine($"[환기 시스템] 송풍 단계를 {fanLevel}단으로 조정");
};
station.Pm25Changed += ventilationHandler;

station.UpdatePm25(48);
station.Pm25Changed -= ventilationHandler; // 환기 시스템만 구독 해제
```

두 구현은 본질적으로 같은 일을 한다. `IAirQualityObserver`를 직접 만든 버전은 통지 시점에 실행되어야 하는 절차가 여러 단계이거나(예: 로깅, 재시도, 우선순위 정렬) Observer가 여러 메서드를 가진 넓은 인터페이스일 때 의미가 분명해진다. 반면 `event`/`delegate` 버전은 알려야 할 것이 "값이 바뀌었다"는 사실 하나뿐일 때 훨씬 간결하며, 실무 C# 코드에서는 이 방식이 더 흔하게 쓰인다. UI 프레임워크의 버튼 클릭 이벤트, `INotifyPropertyChanged`의 `PropertyChanged` 이벤트도 모두 옵저버 패턴을 언어 문법으로 구현한 사례다.

## 19장 중재자와 함께 쓰이는 경우

19장에서 다루는 중재자 패턴은 여러 객체가 서로 직접 참조하지 않고 중재자를 통해서만 상호작용하게 만든다. 옵저버는 흔히 그 중재자 내부의 통신 수단으로 쓰인다. 예를 들어 여러 대의 측정소를 총괄하는 `AirQualityMediator`를 둔다면, 이 중재자가 각 측정소의 `Pm25Changed` 이벤트를 구독하고, 구역 평균이 기준치를 넘으면 다시 자신의 이벤트로 상위 시스템에 통지하는 식으로 두 패턴이 겹겹이 쓰일 수 있다. 즉 옵저버는 "누가 변화를 알게 되는가"를 다루고, 중재자는 "그 변화를 알게 된 다음 누구와 누구 사이의 상호작용을 어떻게 조율할 것인가"를 다룬다.

## 언제 사용하는가

- 한 객체의 상태 변화를 몇 개인지 미리 알 수 없는 다수의 객체에게 알려야 할 때. 통지 대상이 실행 중에 늘어나거나 줄어들 수 있어야 한다.
- Subject가 Observer의 구체적인 타입을 알아서는 안 될 때. 서로 다른 모듈이나 계층에 속한 코드를 느슨하게 연결하고 싶을 때 특히 유용하다.
- UI 요소가 데이터 모델의 변화를 반영해야 하는 MVVM/MVC 계열 아키텍처. `INotifyPropertyChanged`가 대표적인 예다.
- 반대로, 통지받는 쪽이 통지받은 순서에 의존하거나 통지 도중 구독자 목록이 계속 바뀌는 상황이라면 주의가 필요하다. 통지 순서를 보장하려면 리스트 대신 우선순위를 가진 구조가 필요할 수 있고, 통지 중 `Attach`/`Detach`가 일어나면 열거 중 컬렉션이 변경되는 오류가 날 수 있으므로 목록을 복사해서 순회하는 방어적 코드가 필요할 때가 많다.

## .NET BCL에서 이 패턴 찾아보기

이번 장 앞부분에서 C#의 `event`/`delegate`가 옵저버 패턴을 언어 차원에서 지원하는 장치라는 점을 살펴보았다. .NET BCL에는 이와 별도로, 옵저버 패턴을 인터페이스 쌍으로 정식 표현한 것이 있다. 바로 `System.IObservable<T>`와 `System.IObserver<T>`다.

`IObservable<T>`는 `Subscribe(IObserver<T> observer)` 메서드 하나만 정의한다. 이 메서드를 통해 Observer를 등록하는데, 앞서 만든 `IAirQualitySubject.Attach`와 정확히 같은 역할이다. `IObserver<T>`는 통지를 받을 때 호출되는 세 메서드 `OnNext`, `OnError`, `OnCompleted`를 정의한다. `OnPm25Changed` 하나만 있던 앞의 예제보다 더 세분화되어, 값이 갱신될 때(`OnNext`), 오류가 발생했을 때(`OnError`), 더 이상 값이 오지 않을 때(`OnCompleted`)를 구분해서 처리할 수 있다.

```csharp
public class Pm25Observable : IObservable<int>
{
    private readonly List<IObserver<int>> _observers = new();

    public IDisposable Subscribe(IObserver<int> observer)
    {
        _observers.Add(observer);
        return new Unsubscriber(_observers, observer);
    }

    public void Publish(int pm25)
    {
        foreach (var observer in _observers)
        {
            observer.OnNext(pm25); // 값이 갱신되었음을 통지
        }
    }

    public void Complete()
    {
        foreach (var observer in _observers)
        {
            observer.OnCompleted(); // 더 이상 통지가 없음을 알림
        }
    }

    private class Unsubscriber : IDisposable
    {
        private readonly List<IObserver<int>> _observers;
        private readonly IObserver<int> _observer;

        public Unsubscriber(List<IObserver<int>> observers, IObserver<int> observer)
        {
            _observers = observers;
            _observer = observer;
        }

        public void Dispose() => _observers.Remove(_observer);
    }
}
```

`Subscribe`가 `IDisposable`을 반환해서 `Dispose()` 호출만으로 구독을 해제할 수 있다는 점도 눈여겨볼 만하다. 앞서 `event`에서는 `-=` 연산자로 구독을 해제했지만, 여기서는 `IDisposable` 패턴을 재사용한다.

`IObservable<T>`/`IObserver<T>` 쌍은 Reactive Extensions(System.Reactive) 라이브러리 전체의 기반이기도 하다. Rx는 이 두 인터페이스 위에 `Where`, `Select`, `Throttle` 같은 연산자를 쌓아 올려, 비동기 이벤트 스트림을 LINQ 스타일로 조합할 수 있게 해준다. 즉 BCL이 옵저버 패턴의 최소 계약만 정의해 두고, 그 위에 더 풍부한 기능을 쌓아 올릴 수 있는 확장점을 열어 둔 것이다.

## 요약

- 옵저버 패턴은 Subject가 Observer 목록을 관리하고, 상태가 바뀔 때 그 목록 전체에 통지하는 구조다.
- 폴링 방식은 자원을 낭비하고 지연이 생기며, 하드코딩된 직접 호출 방식은 Subject가 구체 클래스에 의존하게 만들어 새 통지 대상이 늘어날 때마다 Subject 코드를 고쳐야 한다. 옵저버 패턴은 이 두 문제를 모두 없앤다.
- `IObserver`/`ISubject`를 직접 정의하는 고전적 구현과 C#의 `event`/`delegate`는 같은 개념을 표현하는 두 가지 방법이다. 알림 내용이 단순하면 `event`가 더 간결하다.
- 19장의 중재자 패턴은 옵저버를 내부 통신 수단으로 함께 사용하는 경우가 많다.

## 연습문제

1. 이번 장의 `AirQualityStation`에 "PM10 농도"라는 별도의 값이 추가되고, 이 값이 바뀔 때도 통지가 필요해졌다. `event`/`delegate` 버전에서 이를 어떻게 확장하는 것이 좋을지 설계해 보라. 이벤트를 하나 더 추가하는 방법과, `AirQualityChangedEventArgs`에 필드를 추가하는 방법 중 어느 쪽이 더 나은 선택인지 근거를 들어 설명하라.
2. 고전적 구현에서 `Notify` 메서드가 `_observers` 리스트를 순회하는 도중, 어느 Observer의 `OnPm25Changed`가 `station.Detach(this)`를 호출한다면 어떤 문제가 발생할 수 있는가? 이를 안전하게 처리하려면 코드를 어떻게 바꿔야 하는가?
3. 옵저버 패턴에서 Observer를 등록만 해두고 더는 사용하지 않는데 `Detach`를 호출하지 않으면 어떤 문제가 생기는가? 이 문제를 흔히 어떤 용어로 부르는지 조사해 보라.
4. `IAirQualityObserver`에 `OnPm25Changed` 외에 `OnStationOffline()`이라는 메서드가 추가로 필요해졌다고 하자. 이 상황에서는 `event`/`delegate` 방식과 인터페이스 기반 방식 중 어느 쪽이 더 적합한가? 이유를 설명하라.
5. 이번 장에서 만든 `MobileAlertService`는 PM2.5가 35를 넘을 때만 알림을 보낸다. 사용자마다 알림을 받고 싶은 기준값이 다르다고 할 때, 기존 구조를 크게 바꾸지 않고 이 요구를 반영하려면 어떻게 설계하면 좋을지 제안해 보라.

## 문제 상황

사내 통계팀에서 쓰는 월간 실적 보고서 생성 클래스를 만든다고 가정해 봅시다. 보고서는 제목과 기간은 항상 필요하지만, 그 외에 요약 섹션을 넣을지, 차트를 넣을지, 필터를 적용할지, 워터마크를 찍을지, 출력 형식을 PDF로 할지 엑셀로 할지 등 선택적인 옵션이 아주 많습니다. 처음에는 생성자 하나로 이 모든 걸 처리하려고 시도하게 됩니다.

```csharp
// 문제가 되는 코드: 매개변수가 계속 늘어나는 생성자
public class Report
{
    public Report(string title, DateTime periodStart, DateTime periodEnd,
                   bool includeSummary, bool includeChart, string chartType,
                   bool applyFilter, string filterExpression, bool watermark,
                   string watermarkText, string format, bool includeAppendix)
    {
        // ... 12개나 되는 매개변수를 순서에 맞춰 채워야 한다
    }
}
```

이런 생성자를 호출하는 코드는 다음과 같은 모습이 됩니다.

```csharp
// 호출하는 쪽: 이게 무엇을 의미하는지 코드만 보고는 알기 어렵다
var report = new Report(
    "8월 실적 보고서", new DateTime(2026, 8, 1), new DateTime(2026, 8, 31),
    true, true, "bar", false, null, true, "내부용", "pdf", false);
```

이렇게 생성자에 매개변수가 계단식으로 계속 늘어나는 상황을 흔히 "텔레스코핑 생성자(telescoping constructor)" 문제라고 부릅니다. 매개변수가 늘어날 때마다 오버로드를 하나씩 추가하는 경우도 있지만, 그래도 문제는 그대로입니다.

- `true, true, "bar", false, null, ...`처럼 각 값이 무엇을 의미하는지 호출 코드만 봐서는 알 수 없습니다.
- `bool` 매개변수가 여러 개 연달아 있으면 순서를 헷갈리기 쉽고, 컴파일러는 이 실수를 잡아주지 못합니다.
- 옵션 조합에 따라 유효성 검증이 필요한 경우(예: `includeChart`가 `true`인데 `chartType`이 비어 있는 경우) 이를 생성자 안에서 처리하기가 지저분해집니다.
- 선택적 매개변수가 새로 추가될 때마다 기존 생성자를 계속 수정하거나 오버로드를 늘려야 합니다.

## 패턴 설명

빌더 패턴은 복잡한 객체를 한 번의 생성자 호출로 완성하지 않고, 여러 단계에 걸쳐 하나씩 조립한 뒤 마지막에 완성된 객체를 얻어내는 패턴입니다.

핵심 구성 요소는 다음과 같습니다.

- **제품(Product)**: 최종적으로 만들어지는 복잡한 객체. 이번 예제에서는 `Report`
- **빌더(Builder)**: 제품을 조립하는 단계별 메서드를 제공하는 클래스. 이번 예제에서는 `ReportBuilder`
- **`Build()` 메서드**: 지금까지 설정된 값으로 최종 제품을 만들어 반환. 이 시점에 유효성 검증을 수행하기 좋음

빌더의 각 메서드는 보통 자기 자신(`this`)을 반환해서 메서드를 계속 이어 붙일 수 있도록 만듭니다. 이런 스타일을 플루언트 인터페이스(fluent interface)라고 부르는데, 문장을 읽듯이 코드를 이어서 쓸 수 있다는 뜻입니다.

```
ReportBuilder
    .Create("8월 실적 보고서", 기간)
    .WithSummary()
    .WithChart("bar")
    .WithWatermark("내부용")
    .Build()
```

이렇게 하면 호출하는 쪽 코드가 각 옵션의 이름을 그대로 드러내므로 무엇을 설정하는지 한눈에 읽힙니다. 또한 `Build()` 호출 시점에 "차트를 넣기로 했으면 차트 종류가 반드시 지정되어야 한다"처럼 옵션 간의 관계를 검증할 수 있는 자연스러운 지점이 생깁니다.

## C# 예제 코드

먼저 완성된 제품인 `Report`를 정의합니다. 이 클래스는 한 번 만들어지면 값이 바뀌지 않는 불변 객체로 설계합니다.

```csharp
// 완성된 제품: 생성 후에는 값이 바뀌지 않는 불변 객체
public class Report
{
    public string Title { get; }
    public DateTime PeriodStart { get; }
    public DateTime PeriodEnd { get; }
    public bool IncludeSummary { get; }
    public string? ChartType { get; }
    public string? WatermarkText { get; }
    public string Format { get; }

    // 생성자는 내부에서만 호출되며, 빌더를 통해서만 접근한다
    internal Report(string title, DateTime periodStart, DateTime periodEnd,
                     bool includeSummary, string? chartType,
                     string? watermarkText, string format)
    {
        Title = title;
        PeriodStart = periodStart;
        PeriodEnd = periodEnd;
        IncludeSummary = includeSummary;
        ChartType = chartType;
        WatermarkText = watermarkText;
        Format = format;
    }

    public void Print()
    {
        Console.WriteLine($"[{Format.ToUpper()}] {Title} ({PeriodStart:yyyy-MM-dd} ~ {PeriodEnd:yyyy-MM-dd})");
        if (IncludeSummary) Console.WriteLine("- 요약 섹션 포함");
        if (ChartType != null) Console.WriteLine($"- 차트 포함: {ChartType}");
        if (WatermarkText != null) Console.WriteLine($"- 워터마크: {WatermarkText}");
    }
}
```

다음으로 이 제품을 단계적으로 조립하는 `ReportBuilder`를 작성합니다.

```csharp
// 빌더: 옵션을 하나씩 쌓아가며 조립한다
public class ReportBuilder
{
    private readonly string _title;
    private readonly DateTime _periodStart;
    private readonly DateTime _periodEnd;
    private bool _includeSummary;
    private string? _chartType;
    private string? _watermarkText;
    private string _format = "pdf"; // 기본값

    private ReportBuilder(string title, DateTime periodStart, DateTime periodEnd)
    {
        _title = title;
        _periodStart = periodStart;
        _periodEnd = periodEnd;
    }

    // 필수 값은 정적 팩토리 메서드에서 받아 빌더를 시작한다
    public static ReportBuilder Create(string title, DateTime periodStart, DateTime periodEnd)
    {
        if (periodEnd < periodStart)
            throw new ArgumentException("종료일이 시작일보다 앞설 수 없습니다.");
        return new ReportBuilder(title, periodStart, periodEnd);
    }

    public ReportBuilder WithSummary()
    {
        _includeSummary = true;
        return this;
    }

    public ReportBuilder WithChart(string chartType)
    {
        _chartType = chartType;
        return this;
    }

    public ReportBuilder WithWatermark(string text)
    {
        _watermarkText = text;
        return this;
    }

    public ReportBuilder AsExcel()
    {
        _format = "xlsx";
        return this;
    }

    public Report Build()
    {
        // 옵션 간 관계에 대한 유효성 검증을 마지막에 한 번에 수행한다
        if (_chartType == "bar" && (_periodEnd - _periodStart).Days < 7)
            throw new InvalidOperationException("막대 차트는 최소 7일 이상의 기간에서만 지원됩니다.");

        return new Report(_title, _periodStart, _periodEnd,
                           _includeSummary, _chartType, _watermarkText, _format);
    }
}
```

호출하는 쪽 코드는 다음처럼 각 옵션의 의미가 그대로 드러나는 형태가 됩니다.

```csharp
var report = ReportBuilder
    .Create("8월 실적 보고서", new DateTime(2026, 8, 1), new DateTime(2026, 8, 31))
    .WithSummary()
    .WithChart("bar")
    .WithWatermark("내부용")
    .Build();

report.Print();
// [PDF] 8월 실적 보고서 (2026-08-01 ~ 2026-08-31)
// - 요약 섹션 포함
// - 차트 포함: bar
// - 워터마크: 내부용
```

이제 옵션이 하나 더 필요해지면 `ReportBuilder`에 메서드 하나(`WithAppendix()` 등)만 추가하면 되고, 기존 호출 코드나 생성자를 손댈 필요가 없습니다. 그리고 `Build()` 시점에 옵션 간의 관계(막대 차트는 7일 이상 기간에서만 지원 등)를 검증할 수 있다는 점도 텔레스코핑 생성자로는 얻기 어려운 이점입니다.

## C#의 객체 초기화 구문과 빌더 패턴의 차이

C#은 `new Foo { A = 1, B = 2 }` 형태의 객체 초기화 구문(object initializer)을 기본으로 제공합니다. 언뜻 보면 이것도 빌더 패턴과 비슷하게 "옵션을 하나씩 지정한다"는 느낌을 줍니다. 그렇다면 매번 빌더 클래스를 따로 만들 필요가 있을까요?

객체 초기화 구문은 다음과 같은 상황에서는 빌더 패턴을 대체할 수 없습니다.

- **불변 객체를 만들어야 할 때**: 객체 초기화 구문은 대상 속성에 `set`(또는 `init`) 접근자가 있어야 동작합니다. `Report`처럼 생성 후 절대 값이 바뀌지 않아야 하는 클래스라면, 속성을 모두 `get`만 있는 형태로 두고 싶은데 객체 초기화 구문으로는 이런 값을 채울 수 없습니다. C# 9의 `init` 접근자를 쓰면 일부 해결되지만, `Build()` 시점의 복잡한 검증까지는 대신해주지 못합니다.
- **속성 간 관계를 검증해야 할 때**: `new Report { ChartType = "bar", PeriodStart = ..., PeriodEnd = ... }`처럼 속성을 하나씩 채우는 동안에는 "차트가 bar일 때는 기간이 7일 이상이어야 한다"는 규칙을 강제할 시점이 없습니다. 모든 속성이 다 채워진 뒤에야 검증할 수 있는데, 객체 초기화 구문에는 "다 채워졌다"는 시점 자체가 없습니다. 반면 빌더는 `Build()`라는 명시적인 완료 시점이 있어서 그때 한 번에 검증할 수 있습니다.
- **여러 단계를 거쳐 조건부로 조립해야 할 때**: 예를 들어 사용자 권한에 따라 `WithWatermark()`를 호출할지 안 할지가 로직에 따라 갈리는 경우, 객체 초기화 구문의 단일 식(expression) 안에서는 이런 조건부 조립을 자연스럽게 표현하기 어렵습니다. 빌더는 메서드 호출을 조건문 사이에 자유롭게 끼워 넣을 수 있습니다.
- **필수 값과 선택 값을 구분해야 할 때**: 객체 초기화 구문은 어떤 속성을 반드시 채워야 하는지 강제하지 못합니다(모두 생략 가능). 위 예제의 `ReportBuilder.Create(...)`처럼 필수 값은 정적 메서드의 매개변수로 강제하고, 나머지는 선택적인 메서드 체이닝으로 남겨두는 방식은 객체 초기화 구문만으로는 구현할 수 없습니다.

반대로, 단순히 속성 몇 개를 채우는 것으로 끝나는 데이터 전달용 객체(DTO)나 설정 값 묶음이라면 객체 초기화 구문으로 충분하며, 굳이 빌더 클래스를 따로 만드는 것은 과한 설계입니다. 빌더 패턴은 "생성 과정 자체에 규칙과 검증이 필요하거나, 결과물이 불변이어야 하는" 상황에서 진짜 가치를 발휘합니다.

## 언제 사용하는가

- 생성자에 필요한 매개변수가 많고, 그중 상당수가 선택적일 때
- 생성 과정에서 값들 사이의 관계를 검증해야 할 때(하나를 설정하면 다른 것도 같이 설정되어야 하는 경우 등)
- 최종 객체는 불변으로 유지하고 싶지만, 조립 과정은 여러 단계로 나누고 싶을 때
- 같은 조립 절차로 서로 다른 결과물을 만들어야 할 때(예: 같은 단계를 거쳐 PDF 보고서와 엑셀 보고서를 모두 만드는 경우)

## 요약

빌더 패턴은 매개변수가 많고 복잡한 객체를, 한 번의 생성자 호출 대신 여러 단계의 메서드 호출로 나누어 조립하는 패턴입니다. 각 메서드가 자기 자신을 반환하는 플루언트 인터페이스 스타일을 쓰면 호출 코드가 각 옵션의 의미를 그대로 드러내면서 읽기 쉬워지고, `Build()`라는 명시적인 완료 시점을 두어 옵션 간의 관계를 한 번에 검증할 수 있습니다. C#의 객체 초기화 구문이 간단한 데이터 채움에는 충분하지만, 불변 객체를 만들어야 하거나 생성 과정에 검증 로직이 필요한 경우에는 빌더 패턴이 여전히 필요합니다.

## 연습문제

1. `ReportBuilder`에 `WithAppendix(string content)` 메서드를 추가하고, `Report`와 `Build()`도 함께 수정해 보세요. 기존 호출 코드가 수정 없이 계속 동작하는지 확인하세요.
2. 객체 초기화 구문(`new Report { ... }`)만으로 이번 장의 `Report` 클래스를 초기화하려고 하면 어떤 문제가 생기는지 직접 코드를 작성해서 확인해 보세요.
3. 커스텀 샌드위치 주문 시스템을 빌더 패턴으로 설계해 보세요. 빵 종류(필수), 토핑 목록(선택, 여러 개 가능), 소스(선택), 매운맛 여부(선택)를 조립할 수 있어야 하며, 토핑이 5개를 넘으면 `Build()`에서 예외가 발생하도록 만들어 보세요.
4. 이번 장의 `ReportBuilder`처럼 정적 팩토리 메서드로 필수 값을 강제하는 방식과, 생성자를 `public`으로 열어두고 모든 값을 메서드 체이닝으로 설정하게 하는 방식의 장단점을 비교해 보세요.
5. 3장에서 다룬 싱글턴 패턴과 이번 장의 빌더 패턴을 함께 쓸 수 있는 상황이 있을지 생각해 보세요. 예를 들어 애플리케이션 전체에서 공유하는 `ReportBuilder` 팩토리가 필요한 경우를 가정하고 설계해 보세요.

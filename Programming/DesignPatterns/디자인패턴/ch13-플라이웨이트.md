## 문제 상황

지도 서비스를 만드는 팀을 상상해 보자. 이 서비스는 전국의 매장 정보를 지도 위에 아이콘으로 표시한다. 카페, 편의점, 병원, 약국 등 업종별로 아이콘 모양과 색상이 정해져 있고, 사용자가 지도를 확대하면 한 화면에 수만 개의 매장 마커가 동시에 나타난다.

처음에는 단순하게 설계했다. `StoreMarker`라는 클래스를 만들고, 매장 하나마다 인스턴스를 하나씩 생성했다.

```csharp
public class StoreMarker
{
    public string Category { get; set; }      // 업종
    public byte[] IconImage { get; set; }      // 아이콘 이미지 원본 데이터
    public string ColorHex { get; set; }       // 업종별 색상
    public double Latitude { get; set; }       // 위도
    public double Longitude { get; set; }      // 경도
    public bool IsSelected { get; set; }       // 선택 상태

    public void Draw()
    {
        // IconImage를 ColorHex로 칠해서 (Latitude, Longitude) 위치에 그린다
    }
}
```

전국 매장이 20만 개라면 `StoreMarker` 인스턴스도 20만 개가 만들어진다. 문제는 `IconImage`다. 카페 아이콘 이미지 데이터는 카페 매장이 몇 개든 완전히 동일한데, 매장마다 이 이미지 데이터를 통째로 복사해서 들고 있다. 업종이 15가지뿐이라도, 15종류의 이미지 데이터가 20만 번 중복 저장되는 셈이다. 지도를 확대·축소할 때마다 메모리 사용량이 치솟고, 가비지 컬렉션이 자주 일어나 화면이 끊기기 시작했다.

곰곰이 살펴보면 매장마다 실제로 달라야 하는 값은 위도, 경도, 선택 상태뿐이다. 아이콘 이미지와 색상은 업종이 같으면 완전히 같은 값을 반복해서 들고 있을 뿐이다. 이렇게 "많은 객체가 공통으로 가지는, 변하지 않는 데이터"와 "객체마다 달라지는 데이터"를 구분하지 못하면 불필요한 메모리 낭비가 생긴다.

## 패턴 설명

플라이웨이트 패턴은 객체의 상태를 두 가지로 나누는 데서 시작한다.

- **내재적 상태(intrinsic state)**: 여러 객체가 공유할 수 있는, 변하지 않는 데이터. 위 예에서는 업종별 아이콘 이미지와 색상이다.
- **외재적 상태(extrinsic state)**: 객체마다 달라지는 데이터. 위 예에서는 위도, 경도, 선택 상태다.

내재적 상태만 담은 작고 가벼운 객체를 **플라이웨이트(Flyweight)**라고 부른다. "flyweight"는 원래 권투에서 가장 가벼운 체급을 뜻하는 말로, 이 패턴에서도 "가능한 한 가볍게 만든 공유 객체"라는 의미로 쓰인다. 같은 업종의 매장은 모두 같은 플라이웨이트 인스턴스 하나를 참조하고, 외재적 상태는 클라이언트(여기서는 지도를 그리는 코드)가 따로 관리해서 그림을 그릴 때 플라이웨이트에 매개변수로 넘겨준다.

플라이웨이트 인스턴스를 직접 `new`로 만들면 중복 생성을 막을 수 없으므로, 보통 **플라이웨이트 팩토리**를 둔다. 팩토리는 내부에 캐시(딕셔너리 등)를 가지고, 같은 키로 요청이 들어오면 이미 만들어둔 인스턴스를 돌려주고, 처음 보는 키라면 새로 만들어 캐시에 저장한 뒤 돌려준다. 클라이언트는 팩토리에게 "카페 아이콘 하나 주세요"라고 요청할 뿐, 그것이 새로 만들어진 것인지 재사용된 것인지는 신경 쓰지 않는다.

정리하면 구조는 세 부분으로 이루어진다.

- `IIconFlyweight`: 플라이웨이트가 구현할 인터페이스. 외재적 상태를 매개변수로 받는 메서드를 정의한다.
- `StoreIcon`: 내재적 상태(이미지, 색상)만 가지는 구체적인 플라이웨이트 클래스.
- `StoreIconFactory`: 업종을 키로 삼아 `StoreIcon` 인스턴스를 캐시하고 재사용하는 팩토리.

## C# 예제 코드

```csharp
// 플라이웨이트가 구현할 인터페이스
// Draw 메서드는 외재적 상태(위치, 선택 여부)를 매개변수로 받는다
public interface IIconFlyweight
{
    void Draw(double latitude, double longitude, bool isSelected);
}

// 내재적 상태만 가지는 구체적인 플라이웨이트
// 같은 업종이면 이미지와 색상이 완전히 같으므로 하나만 만들어 공유한다
public class StoreIcon : IIconFlyweight
{
    private readonly string _category;
    private readonly byte[] _iconImage;
    private readonly string _colorHex;

    public StoreIcon(string category, byte[] iconImage, string colorHex)
    {
        _category = category;
        _iconImage = iconImage;
        _colorHex = colorHex;
        Console.WriteLine($"[생성] '{_category}' 업종 아이콘을 새로 만들었습니다.");
    }

    public void Draw(double latitude, double longitude, bool isSelected)
    {
        // 실제로는 _iconImage를 _colorHex로 칠해서 (latitude, longitude)에 렌더링한다
        var mark = isSelected ? "★" : " ";
        Console.WriteLine($"{mark} [{_category}] 위치({latitude:F4}, {longitude:F4})에 그림");
    }
}

// 업종별로 하나씩만 StoreIcon을 만들어 캐시하고 재사용하는 팩토리
public class StoreIconFactory
{
    private readonly Dictionary<string, IIconFlyweight> _cache = new();

    public IIconFlyweight GetIcon(string category)
    {
        if (!_cache.TryGetValue(category, out var icon))
        {
            // 캐시에 없을 때만 실제로 이미지 데이터를 불러와 새로 생성한다
            byte[] image = LoadIconImageFromDisk(category);
            string color = ResolveCategoryColor(category);
            icon = new StoreIcon(category, image, color);
            _cache[category] = icon;
        }
        return icon;
    }

    public int CachedIconCount => _cache.Count;

    private byte[] LoadIconImageFromDisk(string category) => new byte[1024]; // 예시용 더미 데이터
    private string ResolveCategoryColor(string category) => category switch
    {
        "카페" => "#6F4E37",
        "편의점" => "#0072CE",
        "병원" => "#E53935",
        _ => "#888888"
    };
}

// 지도 위의 매장 하나를 나타내는 클래스. 외재적 상태만 직접 들고,
// 내재적 상태(아이콘)는 팩토리에서 공유 인스턴스를 받아 사용한다
public class StoreMarker
{
    private readonly IIconFlyweight _icon;
    public double Latitude { get; }
    public double Longitude { get; }
    public bool IsSelected { get; set; }

    public StoreMarker(IIconFlyweight icon, double latitude, double longitude)
    {
        _icon = icon;
        Latitude = latitude;
        Longitude = longitude;
    }

    public void Draw() => _icon.Draw(Latitude, Longitude, IsSelected);
}

public class MapRenderer
{
    public static void Main()
    {
        var factory = new StoreIconFactory();
        var markers = new List<StoreMarker>();

        // 매장 20만 개를 흉내 내되, 예제에서는 6개만 생성한다
        var sampleData = new[]
        {
            ("카페", 37.5651, 126.9895),
            ("카페", 37.5700, 126.9820),
            ("편의점", 37.5600, 126.9900),
            ("편의점", 37.5550, 126.9990),
            ("병원", 37.5680, 126.9850),
            ("카페", 37.5720, 126.9770),
        };

        foreach (var (category, lat, lng) in sampleData)
        {
            var icon = factory.GetIcon(category);   // 같은 업종은 같은 인스턴스를 반환받는다
            markers.Add(new StoreMarker(icon, lat, lng));
        }

        foreach (var marker in markers)
            marker.Draw();

        // 매장은 6개지만 실제로 생성된 아이콘(플라이웨이트)은 업종 수인 3개뿐이다
        Console.WriteLine($"생성된 아이콘 개수: {factory.CachedIconCount}");
    }
}
```

이 예제에서 매장 마커는 6개지만 `StoreIcon`은 카페, 편의점, 병원 세 종류만 생성된다. 매장 수가 20만 개로 늘어나도 아이콘 인스턴스는 업종 수만큼(수십 개 이내)만 존재하므로, 이미지 데이터가 중복으로 메모리를 차지하지 않는다.

## 언제 사용하는가

플라이웨이트는 다음 조건이 함께 성립할 때 효과가 크다.

- 같은 종류의 객체를 아주 많이(수만~수백만 개) 만들어야 한다.
- 그 객체들 중 상당 부분의 데이터가 서로 동일하다(공유 가능한 내재적 상태가 존재한다).
- 객체별로 달라지는 데이터(외재적 상태)는 클라이언트가 별도로 관리할 수 있다.

텍스트 에디터에서 글자마다 폰트·크기·굵기 정보를 객체로 표현할 때, 게임에서 지형에 흩어진 같은 모양의 나무나 파티클을 수천 개 그릴 때, 그리고 위 예제처럼 지도에 대량의 아이콘을 표시할 때 이 패턴이 자주 쓰인다.

다만 요즘 하드웨어에서는 메모리가 예전보다 훨씬 여유롭고, .NET 런타임의 가비지 컬렉터도 많이 개선되었다는 점을 감안해야 한다. 객체 수가 수백~수천 개 수준이라면 플라이웨이트로 얻는 이득보다, 상태를 내재적/외재적으로 억지로 분리하면서 코드가 복잡해지는 비용이 더 클 수 있다. 실제로 메모리 프로파일링을 해서 "동일한 데이터의 중복 저장"이 눈에 보이는 문제로 확인된 뒤에 적용하는 것이 안전하다. 성급하게 모든 클래스를 플라이웨이트로 쪼개는 것은 과도한 최적화(premature optimization)가 되기 쉽다.

또한 3장 싱글턴과 헷갈릴 수 있는데, 싱글턴은 "인스턴스가 전역에서 딱 하나만 존재해야 한다"는 제약이고, 플라이웨이트는 "키가 같으면 같은 인스턴스를 재사용한다"는 것이라 키의 종류만큼(위 예제라면 업종 수만큼) 여러 인스턴스가 존재할 수 있다는 차이가 있다.

## 요약

- 플라이웨이트 패턴은 객체의 상태를 공유 가능한 내재적 상태와 객체별로 다른 외재적 상태로 나누고, 내재적 상태만 담은 가벼운 객체를 재사용해 메모리 사용량을 줄인다.
- 플라이웨이트 팩토리가 캐시를 관리하며, 같은 키로 요청이 오면 기존 인스턴스를 돌려주고 없으면 새로 만든다.
- 외재적 상태는 클라이언트가 직접 들고 있다가 플라이웨이트의 메서드를 호출할 때 매개변수로 전달한다.
- 대량의 유사 객체를 만들어야 하고 데이터 중복이 실제로 메모리 문제를 일으킬 때 적용하며, 객체 수가 많지 않다면 굳이 적용할 필요는 없다.

## 연습문제

1. 온라인 게임에서 수천 개의 몬스터 캐릭터를 화면에 표시해야 한다. 몬스터는 종족(오크, 고블린, 드래곤 등)에 따라 3D 모델과 애니메이션 데이터가 정해지고, 개체마다 위치·체력·레벨이 다르다. 이 상황에 플라이웨이트를 적용한다면 내재적 상태와 외재적 상태를 각각 어떻게 나눌지 설계해 보라.
2. 위 1번 설계를 바탕으로 `MonsterFactory` 클래스를 C#으로 작성하고, 같은 종족을 여러 번 요청했을 때 인스턴스가 재사용되는지 확인하는 코드를 작성하라.
3. 이번 장의 `StoreIconFactory`에서 캐시가 무한히 커지지 않도록, 오랫동안 사용되지 않은 아이콘을 제거하는 기능을 추가하려면 어떤 점을 고려해야 하는가? (힌트: 참조하는 `StoreMarker`가 아직 남아있는데 아이콘을 지워버리면 어떤 문제가 생기는가?)
4. 플라이웨이트 패턴을 적용하기 전과 후, 매장 20만 개 상황에서 메모리 사용량이 어떻게 달라질지 대략적으로 추정해 보라. 아이콘 이미지 데이터가 평균 50KB이고 업종이 20가지라고 가정한다.
5. 플라이웨이트 패턴이 오히려 손해가 되는 상황을 하나 만들어 설명해 보라. 예를 들어 객체마다 내재적 상태로 취급할 데이터가 실제로는 거의 다 다른 경우를 생각해 보라.

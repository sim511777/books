## 문제 상황

쇼핑몰 백엔드를 개발하고 있다고 가정해 보자. 처음에는 국내 결제사인 "KPay"의 SDK만 연동했다. `KPay` 클래스는 `Charge(int amountWon)`이라는 메서드로 원화 결제를 처리하고, 성공하면 `true`, 실패하면 `false`를 반환한다. 주문 처리 코드는 이 메서드 하나만 호출하면 되도록 깔끔하게 작성되어 있었다.

그런데 해외 진출을 준비하면서 해외 결제 게이트웨이인 "GlobalGateway"를 추가로 연동해야 한다. 문제는 이 라이브러리가 전혀 다른 방식으로 동작한다는 점이다. 금액은 원 단위가 아니라 센트(cent) 단위 정수로 받고, 통화는 "KRW" 대신 ISO 4217 코드("USD", "EUR" 등)를 요구하며, 성공 여부도 `bool`이 아니라 `GatewayResult` 라는 열거형(`Success`, `Declined`, `NetworkError`)으로 돌려준다. 게다가 메서드 이름조차 `Charge`가 아니라 `Submit`이다.

주문 처리 코드는 이미 "결제 수단이 무엇이든 `Pay(금액, 통화)`를 호출하면 성공/실패를 알려준다"는 가정 위에서 짜여 있다. 이 가정을 깨고 결제 수단마다 `if (paymentType == "KPay") { ... } else if (paymentType == "GlobalGateway") { ... }` 식으로 분기 처리를 흩뿌리면, 결제 수단이 하나 더 늘어날 때마다 주문 처리 코드 전체를 다시 손봐야 하는 구조가 된다. 더 심각한 것은 `GlobalGateway`가 외부에서 받아온 SDK라서 소스 코드를 수정할 수 없다는 점이다. 클래스 내부를 고칠 수 없는데, 인터페이스는 우리가 원하는 형태로 통일해야 한다.

## 패턴 설명

**어댑터(Adapter) 패턴**은 서로 호환되지 않는 인터페이스를 가진 클래스를, 클라이언트가 기대하는 인터페이스로 변환해 주는 구조 패턴이다. 전원 콘센트에 꽂는 여행용 플러그 어댑터를 떠올리면 이해가 쉽다. 220V 콘센트 모양은 바꿀 수 없지만(레거시 코드), 어댑터를 하나 끼우면 110V용 플러그(클라이언트가 원하는 모양)로도 문제없이 전기를 쓸 수 있다.

어댑터 패턴의 참여자는 다음과 같다.

- **Target**: 클라이언트가 기대하는 인터페이스. 이 장의 예제에서는 `IPaymentProcessor`가 된다.
- **Adaptee**: 이미 존재하지만 Target과 인터페이스가 다른 클래스. 여기서는 `GlobalGateway`다. 수정할 수 없는 외부 라이브러리인 경우가 많다.
- **Adapter**: Target 인터페이스를 구현하면서, 내부적으로는 Adaptee의 인스턴스를 들고 있다가 호출을 Adaptee의 방식으로 변환해서 위임하는 클래스.
- **Client**: Target 인터페이스만 알고 사용하는 코드. 주문 처리 코드가 여기에 해당한다.

어댑터를 구현하는 방법은 크게 두 가지다. 클래스 어댑터는 다중 상속을 이용해 Adaptee를 상속하면서 Target을 구현하는데, C#은 클래스의 다중 상속을 지원하지 않으므로 이 방식은 쓸 수 없다. 대신 C#에서는 **객체 어댑터**, 즉 어댑터가 Adaptee의 인스턴스를 필드로 갖고(합성, composition) 호출을 위임하는 방식을 사용한다. 이 방식은 오히려 더 유연하다. Adaptee가 봉인된(sealed) 클래스여도 상관없고, 런타임에 다른 Adaptee 인스턴스로 교체하기도 쉽다.

아래 다이어그램은 어댑터가 `GlobalGateway`(Adaptee)를 감싸서 `IPaymentProcessor`(Target) 인터페이스로 노출하는 구조를 보여준다.

```text
   어댑터가 Adaptee를 감싸 Target 인터페이스로 노출한다
   Client는 IPaymentProcessor만 알고, Adapter 내부에서
   GlobalGateway의 형식으로 변환해 호출한다

   +----------+  사용   +--------------------------+
   |  Client  | ------> |     <<interface>>         |
   +----------+         |     IPaymentProcessor     |
                         | + Pay(amount, currency)   |
                         +--------------------------+
                                     ^
                                     : 구현(implements)
                                     :
                         +--------------------------+       합성(has-a)      +----------------------+
                         |   GlobalGatewayAdapter    | --------------------> |   GlobalGateway       |
                         | + Pay(amount, currency)   |     <>----------      | (기존 레거시 클래스)     |
                         | - _adaptee: GlobalGateway |                       | + Charge(cents, isoCode)|
                         +--------------------------+                       +----------------------+
```

## C# 예제 코드

먼저 클라이언트가 기대하는 공통 인터페이스와, 이미 잘 동작하고 있는 국내 결제 클래스를 정의한다.

```csharp
// Target: 클라이언트가 기대하는 통일된 인터페이스
public interface IPaymentProcessor
{
    bool Pay(decimal amount, string currencyCode);
}

// 기존에 잘 동작하던 국내 결제 클래스 (이미 IPaymentProcessor와 형태가 같다)
public class KPayProcessor : IPaymentProcessor
{
    public bool Pay(decimal amount, string currencyCode)
    {
        Console.WriteLine($"KPay로 {amount} {currencyCode} 결제를 시도합니다.");
        // 실제로는 KPay SDK 호출 로직이 들어간다
        return true;
    }
}
```

문제는 해외 게이트웨이인 `GlobalGateway`다. 이 클래스는 우리가 수정할 수 없는 외부 라이브러리라고 가정한다.

```csharp
// Adaptee: 인터페이스가 맞지 않는 기존(외부) 클래스, 수정 불가
public enum GatewayResult
{
    Success,
    Declined,
    NetworkError
}

public class GlobalGateway
{
    // 금액은 센트 단위 정수, 통화는 ISO 코드, 반환값은 열거형
    public GatewayResult Submit(long amountInCents, string isoCurrencyCode)
    {
        Console.WriteLine($"GlobalGateway로 {amountInCents} {isoCurrencyCode}(센트) 결제를 제출합니다.");
        // 실제로는 해외 게이트웨이 SDK 호출 로직이 들어간다
        return GatewayResult.Success;
    }
}
```

이제 `GlobalGateway`를 감싸서 `IPaymentProcessor`로 노출하는 객체 어댑터를 작성한다.

```csharp
// Adapter: Adaptee를 합성으로 보관하고, Target 인터페이스로 변환해 위임한다
public class GlobalGatewayAdapter : IPaymentProcessor
{
    private readonly GlobalGateway _adaptee;

    public GlobalGatewayAdapter(GlobalGateway adaptee)
    {
        _adaptee = adaptee;
    }

    public bool Pay(decimal amount, string currencyCode)
    {
        // 1. 금액 단위 변환: 원 단위 decimal -> 센트 단위 long
        long amountInCents = (long)(amount * 100);

        // 2. 통화 코드는 이미 ISO 형식을 쓰기로 통일했다고 가정
        GatewayResult result = _adaptee.Submit(amountInCents, currencyCode);

        // 3. 반환 타입 변환: GatewayResult -> bool
        return result == GatewayResult.Success;
    }
}
```

클라이언트인 주문 처리 코드는 `IPaymentProcessor`만 알고 있으면 된다. 어떤 결제 수단이 실제로 뒤에서 동작하는지는 신경 쓰지 않는다.

```csharp
public class OrderService
{
    public void Checkout(IPaymentProcessor processor, decimal amount, string currency)
    {
        bool succeeded = processor.Pay(amount, currency);
        Console.WriteLine(succeeded ? "결제 성공" : "결제 실패");
    }
}
```

```csharp
var orderService = new OrderService();

// 국내 결제 - 원래부터 인터페이스가 맞았다
IPaymentProcessor domestic = new KPayProcessor();
orderService.Checkout(domestic, 15000m, "KRW");

// 해외 결제 - 어댑터를 통해 같은 인터페이스로 사용한다
IPaymentProcessor overseas = new GlobalGatewayAdapter(new GlobalGateway());
orderService.Checkout(overseas, 49.99m, "USD");
```

`OrderService.Checkout` 메서드는 단 한 줄도 바뀌지 않았다. `GlobalGatewayAdapter`가 단위 변환과 반환값 변환을 전담하기 때문에, 결제 수단이 하나 더 추가되더라도 그에 맞는 어댑터 클래스만 새로 작성하면 된다. 분기문이 늘어나는 대신 클래스가 늘어나는 것이며, 이는 개방-폐쇄 원칙(2장에서 다룬 객체지향 설계 원칙 중 하나)을 지키는 방향이다.

## 언제 사용하는가

- 이미 만들어진 클래스를 그대로 쓰고 싶은데, 그 인터페이스가 지금 코드에서 요구하는 인터페이스와 다를 때
- 소스 코드를 수정할 수 없는 외부 라이브러리나 레거시 모듈을 새 코드베이스에 편입시켜야 할 때
- 여러 개의 서로 다른 라이브러리를, 클라이언트 입장에서는 하나의 통일된 인터페이스로 다루고 싶을 때(이 장의 결제 시스템 예제처럼)
- 클래스 계층 구조를 건드리지 않고 기존 클래스에 새로운 인터페이스를 "입히고" 싶을 때

어댑터와 자주 혼동되는 패턴이 12장에서 다룰 **퍼사드(Facade)**다. 둘 다 무언가를 감싸는 래퍼(wrapper)라는 점은 비슷하지만 목적이 다르다. 어댑터는 **이미 정해진 Target 인터페이스에 맞추기 위해 형태를 변환**하는 것이 목적이고, 대개 감싸는 대상은 하나(또는 소수)다. 퍼사드는 **여러 개의 복잡한 하위 시스템 호출을 단순한 창구 하나로 묶어 사용하기 쉽게** 만드는 것이 목적이며, 새로운 인터페이스를 발명해서 제공한다. 즉 어댑터는 "형태를 바꿔서 맞추기", 퍼사드는 "복잡함을 감춰서 단순화하기"에 가깝다. 12장에서 이 차이를 다시 자세히 다룬다.

## .NET BCL에서 이 패턴 찾아보기

.NET BCL에서 이름 그대로 어댑터 패턴을 구현한 예가 `System.Data.Common.DbDataAdapter`(그리고 그 기반 인터페이스인 `IDataAdapter`)다. 데이터베이스에서 데이터를 읽어오는 방식(예: `SqlDataReader`가 행 단위로 순차 접근하는 형태)과, 애플리케이션이 데이터를 다루고 싶어 하는 방식(메모리에 올려놓고 자유롭게 탐색·수정할 수 있는 `DataSet`/`DataTable`) 사이에는 이 장의 `KPay`와 `GlobalGateway`만큼이나 큰 인터페이스 차이가 있다.

```csharp
// DbDataAdapter(SqlDataAdapter): DB 데이터를 DataSet 형태로 변환해 준다
using (var connection = new SqlConnection(connectionString))
{
    var adapter = new SqlDataAdapter("SELECT * FROM Reports", connection);

    var dataSet = new DataSet();
    adapter.Fill(dataSet); // DB 결과를 DataSet/DataTable 형태로 채워 넣는다

    DataTable table = dataSet.Tables[0];
    foreach (DataRow row in table.Rows)
    {
        Console.WriteLine(row["Title"]);
    }
}
```

이 구조를 이 장의 참여자 개념에 대응해 보면, Adaptee는 데이터베이스가 노출하는 원시 접근 방식(순방향 전용 리더)이고, Target은 애플리케이션이 기대하는 `DataSet`/`DataTable` 형태이며, `SqlDataAdapter`(= `DbDataAdapter`의 구체 구현)가 그 사이를 이어주는 어댑터 역할을 한다. `Fill()` 메서드가 바로 이 변환을 수행하는 지점으로, 이 장의 `GlobalGatewayAdapter.Pay()`가 `Submit()` 호출 결과를 `bool`로 변환해 돌려주던 것과 같은 위치에 있다.

물론 `DbDataAdapter`는 이 장에서 다룬 최소한의 객체 어댑터보다 기능이 훨씬 많다(`Fill()` 외에도 `Update()`로 반대 방향 동기화까지 지원한다). 하지만 핵심 아이디어는 정확히 같다. "서로 다른 인터페이스를 가진 두 진영을, 클라이언트가 기대하는 하나의 인터페이스로 맞춰준다"는 어댑터의 정의를 `DbDataAdapter`라는 이름 자체가 이미 말해주고 있다.

## 요약

어댑터 패턴은 서로 다른 인터페이스를 가진 클래스들을 연결해서, 클라이언트가 하나의 통일된 인터페이스로 다룰 수 있게 해 주는 구조 패턴이다. C#에서는 다중 상속이 불가능하므로 합성을 이용한 객체 어댑터가 표준적인 구현 방식이며, 어댑터는 Target 인터페이스를 구현하는 동시에 Adaptee 인스턴스를 필드로 보관하면서 호출과 데이터 형식을 변환해 위임한다. 이 장의 결제 시스템 예제처럼, 어댑터를 도입하면 새로운 외부 시스템이 추가되어도 클라이언트 코드는 전혀 수정하지 않고 어댑터 클래스만 추가하면 된다.

## 연습문제

1. C#에서 클래스 어댑터(상속 기반) 대신 객체 어댑터(합성 기반)를 표준적으로 사용하는 이유를 언어적 특성과 연결해서 설명하라.
2. `KPayProcessor`가 원래부터 `IPaymentProcessor`와 형태가 같았던 것은 우연이라고 볼 수 있다. 만약 `KPay` 클래스도 전혀 다른 형태(`bool DoCharge(int won)`)였다면, 이를 위한 어댑터 클래스를 직접 작성하라.
3. 세 번째 결제 수단으로 `RegionalWallet`이라는 클래스가 추가되었다고 하자. 이 클래스는 `Task<bool> ChargeAsync(decimal amount, string currency)`처럼 비동기 메서드만 제공한다. 동기 메서드인 `IPaymentProcessor.Pay`와 연결하는 어댑터를 만들 때 어떤 점을 주의해야 하는지 서술하라.
4. 어댑터 패턴과 12장에서 예고한 퍼사드 패턴의 차이를, "감싸는 대상의 개수"와 "제공하는 인터페이스의 성격" 두 관점에서 비교하여 설명하라.
5. `GlobalGatewayAdapter`의 `Pay` 메서드에서 금액을 센트로 변환할 때 부동소수점 오차나 반올림 문제가 생길 수 있는 경우를 생각해 보고, 이를 방지하기 위한 코드 개선 방법을 제시하라.

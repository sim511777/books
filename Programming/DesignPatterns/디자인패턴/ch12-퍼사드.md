## 문제 상황

거실에 홈시어터를 갖춘 집을 상상해 보자. 영화 한 편을 보려면 실제로는 여러 기기를 순서대로 조작해야 한다.

```csharp
// 영화를 보기 위해 클라이언트가 직접 해야 하는 일
var amplifier = new Amplifier();
var projector = new Projector();
var streamer = new StreamingPlayer();
var screen = new MotorizedScreen();
var lights = new SmartLights();

lights.DimTo(20);
screen.Down();
projector.PowerOn();
projector.SetInputSource("HDMI1");
amplifier.PowerOn();
amplifier.SetVolume(15);
amplifier.SetInputSource("STREAMER");
streamer.PowerOn();
streamer.Play("영화 제목");
```

이 코드가 한 번은 동작하겠지만, 문제는 영화를 보고 싶어 하는 모든 클라이언트 코드가 이 순서를 정확히 알고 있어야 한다는 점이다. 조명을 어둡게 하기 전에 스크린을 내려야 하는지, 앰프의 입력 소스를 스트리머로 설정하는 시점이 앰프 전원을 켠 다음인지 전인지, 프로젝터의 입력 소스 문자열이 정확히 `"HDMI1"`인지 `"HDMI-1"`인지 같은 세부 사항까지 클라이언트가 알아야 한다.

기기가 다섯 개뿐인데도 벌써 복잡한데, 여기에 사운드바 모드나 스마트 스피커, 자동 커튼까지 추가된다면 어떨까. 영화를 끝내고 정리할 때도 마찬가지로 반대 순서의 절차가 필요하고, 이 절차는 영화를 보는 코드가 있는 모든 곳에 중복해서 나타나게 된다. 게다가 프로젝터를 다른 제조사 제품으로 바꾸면서 API가 바뀌면, 이 절차를 사용하는 모든 클라이언트 코드를 찾아서 고쳐야 한다.

## 패턴 설명

퍼사드 패턴은 여러 하위 시스템 클래스들이 복잡하게 얽혀 있을 때, 그 앞에 **단순한 통합 인터페이스 하나**를 세워서 클라이언트가 하위 시스템의 세부 사항을 몰라도 되게 만드는 패턴이다.

퍼사드 자신은 새로운 기능을 만들어내지 않는다. 대신 이미 존재하는 하위 시스템 클래스들을 알고 있고, "영화 보기"처럼 클라이언트가 실제로 원하는 작업 단위에 맞춰 하위 시스템 호출들을 올바른 순서로 대신 실행해 준다. 클라이언트는 개별 기기 클래스들을 직접 참조할 필요 없이 퍼사드가 제공하는 몇 개의 메서드만 알면 된다.

중요한 점은 퍼사드가 하위 시스템 클래스들을 감추거나 대체하는 것이 아니라는 것이다. 하위 시스템 클래스들은 여전히 각자의 상세한 인터페이스를 그대로 유지하며, 세밀한 제어가 필요한 고급 사용자는 여전히 개별 클래스에 직접 접근할 수 있다. 퍼사드는 단지 "가장 흔한 사용 패턴"을 위한 지름길을 하나 추가하는 것뿐이다.

## C# 예제 코드

먼저 하위 시스템 클래스들은 그대로 둔다. 이들은 각자 자신의 역할에 충실한 세부 인터페이스를 갖고 있다.

```csharp
public class Amplifier
{
    public void PowerOn() => Console.WriteLine("앰프 전원 켜짐");
    public void SetVolume(int level) => Console.WriteLine($"앰프 볼륨 {level}로 설정");
    public void SetInputSource(string source) => Console.WriteLine($"앰프 입력을 {source}로 전환");
    public void PowerOff() => Console.WriteLine("앰프 전원 꺼짐");
}

public class Projector
{
    public void PowerOn() => Console.WriteLine("프로젝터 전원 켜짐");
    public void SetInputSource(string source) => Console.WriteLine($"프로젝터 입력을 {source}로 전환");
    public void PowerOff() => Console.WriteLine("프로젝터 전원 꺼짐");
}

public class StreamingPlayer
{
    public void PowerOn() => Console.WriteLine("스트리밍 플레이어 전원 켜짐");
    public void Play(string title) => Console.WriteLine($"'{title}' 재생 시작");
    public void Stop() => Console.WriteLine("재생 정지");
    public void PowerOff() => Console.WriteLine("스트리밍 플레이어 전원 꺼짐");
}

public class MotorizedScreen
{
    public void Down() => Console.WriteLine("스크린 내려감");
    public void Up() => Console.WriteLine("스크린 올라감");
}

public class SmartLights
{
    public void DimTo(int percent) => Console.WriteLine($"조명 밝기 {percent}%로 조절");
    public void FullBright() => Console.WriteLine("조명 100%로 복귀");
}
```

이제 이 다섯 개 클래스 앞에 퍼사드를 세운다.

```csharp
// 퍼사드: 클라이언트가 알아야 할 창구를 하나로 줄인다
public class HomeTheaterFacade
{
    private readonly Amplifier _amplifier;
    private readonly Projector _projector;
    private readonly StreamingPlayer _streamer;
    private readonly MotorizedScreen _screen;
    private readonly SmartLights _lights;

    public HomeTheaterFacade(
        Amplifier amplifier,
        Projector projector,
        StreamingPlayer streamer,
        MotorizedScreen screen,
        SmartLights lights)
    {
        _amplifier = amplifier;
        _projector = projector;
        _streamer = streamer;
        _screen = screen;
        _lights = lights;
    }

    // 하위 시스템 여러 개를 올바른 순서로 조합해서 "영화 보기"라는 하나의 작업으로 제공
    public void WatchMovie(string title)
    {
        _lights.DimTo(20);
        _screen.Down();
        _projector.PowerOn();
        _projector.SetInputSource("HDMI1");
        _amplifier.PowerOn();
        _amplifier.SetInputSource("STREAMER");
        _amplifier.SetVolume(15);
        _streamer.PowerOn();
        _streamer.Play(title);
    }

    public void EndMovie()
    {
        _streamer.Stop();
        _streamer.PowerOff();
        _amplifier.PowerOff();
        _projector.PowerOff();
        _screen.Up();
        _lights.FullBright();
    }
}
```

클라이언트 코드는 다음과 같이 극단적으로 단순해진다.

```csharp
public class Program
{
    public static void Main()
    {
        var homeTheater = new HomeTheaterFacade(
            new Amplifier(), new Projector(), new StreamingPlayer(),
            new MotorizedScreen(), new SmartLights());

        homeTheater.WatchMovie("인터스텔라");
        // ... 영화 시청 ...
        homeTheater.EndMovie();
    }
}
```

프로젝터를 다른 제조사 제품으로 바꾸거나 입력 소스 문자열 규칙이 바뀌더라도, 수정할 곳은 `HomeTheaterFacade` 내부 한 곳뿐이다. 그 사실을 몰라도 되는 클라이언트 코드는 전혀 손댈 필요가 없다.

## 8장 어댑터와의 차이

8장에서 다룬 어댑터 패턴과 퍼사드 패턴은 둘 다 "무언가를 감싼다"는 점에서 구조가 비슷해 보이지만, 감싸는 목적과 감싸는 대상의 개수가 다르다.

| 비교 항목 | 어댑터(Adapter) | 퍼사드(Facade) |
|---|---|---|
| 감싸는 대상 | 보통 하나의 기존 클래스 | 여러 개의 하위 시스템 클래스 |
| 목적 | 클라이언트가 기대하는 인터페이스와 기존 클래스의 인터페이스가 서로 달라서 호환이 안 될 때, 그 간극을 메운다 | 여러 클래스의 인터페이스가 각각은 정상이지만 조합해서 쓰기에는 너무 복잡할 때, 사용을 단순화한다 |
| 인터페이스 변경 여부 | 기존 인터페이스를 클라이언트가 원하는 형태로 "번역"한다 | 기존 인터페이스들을 그대로 둔 채 그 위에 더 단순한 새 인터페이스를 "추가"한다 |
| 기존 인터페이스 접근 | 어댑터를 거치는 것이 유일한 방법인 경우가 많다 | 퍼사드를 거치지 않고 하위 시스템에 직접 접근하는 것도 여전히 가능하다 |
| 도입 시점 | 이미 있는 클래스와 새로 요구되는 인터페이스가 맞지 않을 때 사후에 도입 | 시스템이 복잡해지기 시작할 때 사용성을 위해 선제적으로 도입 |

간단히 말하면, 어댑터는 "이 인터페이스가 안 맞으니 바꿔서 쓰자"의 문제를 풀고, 퍼사드는 "이 인터페이스들이 너무 많고 복잡하니 단순화해서 쓰자"의 문제를 푼다.

## 언제 사용하는가

- 여러 하위 시스템 클래스를 정해진 순서와 조합으로 다뤄야 하는 코드가 여러 곳에서 중복될 때
- 하위 시스템의 내부 구조와 API를 클라이언트 코드로부터 감추어 결합도를 낮추고 싶을 때
- 라이브러리나 프레임워크를 도입하면서, 그 라이브러리의 세부 클래스를 팀 전체가 직접 다루지 않고 팀에서 정의한 좁은 진입점만 쓰게 하고 싶을 때
- 레거시 시스템을 점진적으로 교체하는 과정에서, 새 코드가 레거시의 복잡한 내부 구조에 직접 의존하지 않도록 경계를 세우고 싶을 때

## 요약

- 여러 하위 시스템을 직접 다뤄야 하는 클라이언트 코드는 호출 순서와 세부 API를 모두 알아야 해서 복잡해지고 중복되기 쉽다.
- 퍼사드 패턴은 하위 시스템 클래스들 앞에 단순한 통합 인터페이스를 두어, 흔히 쓰이는 작업 단위를 하나의 메서드 호출로 제공한다.
- 퍼사드는 하위 시스템을 대체하지 않으며, 필요하면 하위 시스템에 직접 접근하는 길도 그대로 열려 있다.
- 어댑터는 서로 맞지 않는 인터페이스 하나를 번역하는 데 초점을 두고, 퍼사드는 여러 인터페이스의 복잡함을 단순화하는 데 초점을 둔다.

## 연습문제

1. `HomeTheaterFacade`에 "음악 감상(ListenToMusic)" 모드를 추가해 보라. 프로젝터와 스크린은 사용하지 않고 앰프와 스트리머만 사용해야 한다.
2. 퍼사드가 내부적으로 갖고 있는 하위 시스템 객체들을 클라이언트가 생성자 주입이 아니라 퍼사드 내부에서 직접 `new`로 생성하게 바꾼다면 어떤 장단점이 생기는지 논의해 보라.
3. 위 예제에서 `Projector`의 `SetInputSource` 시그니처가 문자열 대신 열거형(enum)을 받도록 바뀌었다고 가정하자. 이 변경으로 인해 수정이 필요한 파일이 얼마나 되는지, 퍼사드가 없었다면 어떻게 달라졌을지 비교해 보라.
4. 퍼사드 패턴과 8장의 어댑터 패턴을 함께 사용할 수 있는 상황을 하나 생각해 보라. 예를 들어 서로 다른 제조사의 프로젝터 API를 어댑터로 통일한 다음, 그 위에 퍼사드를 씌우는 설계를 스케치해 보라.
5. `HomeTheaterFacade`를 사용하는 코드와 사용하지 않는 코드(기존의 개별 기기 조작 코드)가 같은 프로젝트에 공존할 때 생길 수 있는 문제점을 생각해 보라.

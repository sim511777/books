## 문제 상황

쇼핑몰 백엔드를 담당하고 있다고 가정해 보자. 마케팅팀은 시즌마다 새로운 할인 규칙을 만들어낸다.

- "장바구니 금액이 10000원을 초과하면 5% 할인"
- "회원등급이 VIP이고 금액이 30000원 이상이면 10% 할인"
- "특정 요일에는 회원등급과 무관하게 3% 할인"

처음에는 `if`문 몇 개로 충분했다. 하지만 규칙이 늘어날수록 조건은 점점 복잡하게 얽히고, 마케팅팀이 규칙을 바꾸고 싶다고 할 때마다 코드를 고치고 다시 빌드해서 배포해야 하는 상황이 반복된다. 배포 없이 규칙을 바꾸고 싶다는 요구가 나오면서, 할인 조건을 다음과 같은 문자열로 저장해두고 실행 시점에 해석하고 싶다는 아이디어가 나온다.

```
금액 > 10000 AND 회원등급 == VIP
```

이 문자열을 파싱해서 실제 주문 데이터에 대해 참/거짓을 판정하려면 무엇이 필요할까? 단순히 `Split`으로 자르고 `switch`로 분기하는 임시방편 코드는 조건이 두세 개만 추가돼도 순식간에 손대기 어려운 스파게티가 된다. 이럴 때 문법 규칙 자체를 객체로 표현하는 인터프리터 패턴을 고려할 수 있다.

## 패턴 설명

인터프리터 패턴은 특정 언어의 문법(grammar)을 클래스 구조로 표현하고, 그 구조를 이용해 문장을 해석(interpret)하는 방법을 정의하는 패턴이다. 핵심 아이디어는 두 가지다.

1. 문법의 각 규칙을 클래스로 만든다. 더 이상 나눌 수 없는 최종 단위(터미널 표현식)와, 다른 표현식들을 조합하는 규칙(비터미널 표현식)을 구분한다.
2. 이 클래스들을 조합해 트리를 만들고, 트리의 루트에서 `Interpret()` 같은 메서드를 호출하면 각 노드가 재귀적으로 자신을 해석한 뒤 결과를 조합해 위로 전달한다.

앞의 할인 규칙 예로 돌아가 보면, `AND`는 두 개의 하위 조건을 묶는 비터미널 표현식이고, `금액 > 10000`이나 `회원등급 == VIP`는 더 이상 분해되지 않는 터미널 표현식이다. 이런 조건들을 나타내는 공통 인터페이스를 하나 정의하고, 각 조건 종류마다 그 인터페이스를 구현하는 클래스를 만든 다음, 실제 규칙을 트리 형태로 조합해두면 새로운 주문이 들어올 때마다 트리를 순회하며 결과를 계산할 수 있다.

여기서 중요한 것은, 이 패턴이 "문자열을 파싱하는 방법"을 알려주는 것이 아니라 "이미 파싱된(또는 직접 구성한) 표현식 트리를 어떻게 평가할 것인가"에 대한 구조를 제시한다는 점이다. 문자열을 토큰으로 나누고 트리로 만드는 과정(파싱)은 별도의 문제이며, 실무에서는 보통 별도의 파서를 두거나 아예 트리를 코드로 직접 구성한다.

## C# 예제 코드

할인 규칙 같은 복잡한 문법을 처음부터 구현하면 파서 코드가 대부분을 차지해버려 패턴의 핵심이 가려진다. 그래서 여기서는 패턴의 골격만 보이도록 숫자와 `+`, `-` 연산만 다루는 아주 단순한 산술 표현식 트리로 예제를 좁혀본다. 실제 트리는 코드에서 직접 조합하며, 파서는 다루지 않는다.

```csharp
// 모든 표현식이 구현해야 하는 공통 인터페이스
public interface IExpression
{
    int Evaluate();
}

// 터미널 표현식: 더 이상 쪼갤 수 없는 숫자 하나
public class NumberExpression : IExpression
{
    private readonly int _value;

    public NumberExpression(int value)
    {
        _value = value;
    }

    public int Evaluate()
    {
        return _value;
    }
}

// 비터미널 표현식: 두 표현식을 더한다
public class AddExpression : IExpression
{
    private readonly IExpression _left;
    private readonly IExpression _right;

    public AddExpression(IExpression left, IExpression right)
    {
        _left = left;
        _right = right;
    }

    public int Evaluate()
    {
        // 좌우 하위 표현식을 각자 해석한 뒤 결과를 더한다
        return _left.Evaluate() + _right.Evaluate();
    }
}

// 비터미널 표현식: 두 표현식을 뺀다
public class SubtractExpression : IExpression
{
    private readonly IExpression _left;
    private readonly IExpression _right;

    public SubtractExpression(IExpression left, IExpression right)
    {
        _left = left;
        _right = right;
    }

    public int Evaluate()
    {
        return _left.Evaluate() - _right.Evaluate();
    }
}
```

이제 "10 + 20 - 5"에 해당하는 트리를 코드로 직접 구성하고 해석해보자.

```csharp
public class Program
{
    public static void Main()
    {
        // (10 + 20) - 5 트리를 직접 조합한다
        IExpression expression = new SubtractExpression(
            new AddExpression(
                new NumberExpression(10),
                new NumberExpression(20)),
            new NumberExpression(5));

        int result = expression.Evaluate();
        System.Console.WriteLine($"결과: {result}"); // 결과: 25
    }
}
```

앞서 예로 들었던 할인 규칙도 같은 골격으로 확장할 수 있다. `IExpression`을 `bool Interpret(Order order)`로 바꾸고, `AddExpression` 대신 `AndExpression`, `GreaterThanExpression`, `EqualsExpression` 같은 클래스를 만들면 "금액 > 10000 AND 회원등급 == VIP"에 대응하는 트리를 그대로 구성할 수 있다. 다만 문자열을 이 트리로 자동 변환하는 파서를 직접 만드는 순간, 문제가 처음 생각보다 훨씬 커진다는 점을 미리 알아두는 것이 좋다.

## 언제 사용하는가

- 반복적으로 해석해야 하는 간단한 문법이 있고, 그 문법이 자주 바뀌지 않을 때
- 문법의 각 규칙이 비교적 단순해서 클래스 하나로 표현할 수 있을 때
- 표현식을 트리로 표현하는 것 자체가 자연스러운 도메인일 때(수식 계산, 간단한 검색 조건, 규칙 엔진 등)

반대로 문법이 복잡해지거나 성능이 중요하다면 직접 인터프리터를 구현하는 것보다 다른 선택이 낫다. 정규식으로 충분한 경우도 많고, C#에는 NCalc, DynamicExpresso 같은 수식 평가 라이브러리가 있으며, 더 복잡한 로직이 필요하면 Roslyn 스크립팅 API나 Lua 같은 임베디드 스크립팅 엔진을 붙이는 편이 유지보수 면에서 훨씬 유리하다. 실무에서 인터프리터 패턴을 "직접" 구현하는 사례는 GoF 패턴 중에서도 상대적으로 드문데, 이는 파싱과 평가라는 두 가지 어려운 문제를 스스로 떠안기보다 이미 검증된 도구를 재사용하는 쪽이 대체로 더 합리적이기 때문이다.

한 가지 더 눈여겨볼 점은, 인터프리터 패턴의 트리 구조가 10장에서 다룬 컴포지트 패턴과 매우 닮아 있다는 것이다. 실제로 인터프리터는 컴포지트 구조에 "해석한다"는 특정 목적의 연산(`Interpret`, `Evaluate`)을 얹은 특수한 활용이라고 볼 수 있다. 컴포지트가 부분-전체 계층 구조를 다루는 범용 틀을 제공한다면, 인터프리터는 그 틀을 문법 해석이라는 구체적인 문제에 적용한 사례에 가깝다.

## 요약

인터프리터 패턴은 간단한 언어의 문법 규칙을 클래스로 표현하고, 그 클래스들을 트리로 조합해 재귀적으로 해석하는 구조를 제공한다. 각 노드는 자신이 담당하는 규칙만 알면 되고, 전체 해석 결과는 트리를 따라 하위에서 상위로 조합된다. 다만 실제 문자열을 트리로 바꾸는 파싱 작업은 패턴의 범위 밖이며, 문법이 복잡해질수록 직접 구현보다는 기존 파서 라이브러리나 스크립팅 엔진을 활용하는 것이 현실적인 선택이 된다. 트리 구조 자체는 10장 컴포지트와 본질적으로 같은 모양을 하고 있다는 점도 함께 기억해두자.

## 연습문제

1. 위 예제의 `IExpression`에 곱하기(`MultiplyExpression`)와 나누기(`DivideExpression`)를 추가하고, "(3 + 4) * 2"에 해당하는 트리를 직접 구성해 결과를 확인해보자.
2. 본문에서 언급한 할인 규칙 "금액 > 10000 AND 회원등급 == VIP"를 표현할 수 있도록 `bool Interpret(Order order)`를 갖는 인터페이스와 `GreaterThanExpression`, `EqualsExpression`, `AndExpression` 클래스를 설계하고, 트리를 직접 코드로 구성해 몇 가지 주문 데이터로 검증해보자.
3. `OrExpression`과 `NotExpression`을 추가해서 조건식을 더 풍부하게 표현할 수 있도록 확장해보자. 이때 클래스 수가 늘어날수록 트리를 사람이 직접 구성하는 코드가 어떻게 복잡해지는지 관찰해보자.
4. 문제 2에서 만든 표현식 트리와 10장 컴포지트 패턴의 트리 구조를 비교해보고, 두 패턴이 구조적으로 어떤 부분에서 같고 어떤 부분에서 다른지 정리해보자.
5. 간단한 수식 문자열(예: "10 + 20 - 5")을 토큰으로 나누고 위 예제의 `IExpression` 트리로 변환하는 아주 단순한 파서를 직접 작성해보고, 이 과정에서 코드량이 얼마나 늘어나는지 체감해보자.

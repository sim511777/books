## 문제 상황

데이터 수집 배치 프로그램을 만들고 있다고 하자. 매일 새벽 여러 외부 시스템에서 파일을 받아와 내용을 읽고 데이터베이스에 적재해야 하는데, 파일 형식이 CSV, JSON, XML로 제각각이다. 그런데 세 형식을 다루는 절차를 자세히 들여다보면 큰 흐름은 똑같다.

1. 파일을 연다.
2. 파일 내용을 읽어들인다.
3. 형식에 맞게 파싱해서 레코드 목록으로 만든다.
4. 파일을 닫는다.
5. 파싱 결과를 로그에 남긴다.

처음에는 이 흐름을 각 형식별로 별도의 클래스에 통째로 복사해서 작성하기 쉽다.

```csharp
public class CsvImporter
{
    public List<Record> Import(string path)
    {
        var stream = File.OpenRead(path);
        Console.WriteLine($"[열기] {path}");

        var content = new StreamReader(stream).ReadToEnd();
        Console.WriteLine("[읽기] 완료");

        var records = ParseCsv(content); // CSV 전용 파싱

        stream.Close();
        Console.WriteLine("[닫기] 완료");
        Console.WriteLine($"[결과] {records.Count}건 파싱됨");
        return records;
    }

    private List<Record> ParseCsv(string content) { /* CSV 파싱 로직 */ return new List<Record>(); }
}

public class JsonImporter
{
    public List<Record> Import(string path)
    {
        var stream = File.OpenRead(path);
        Console.WriteLine($"[열기] {path}");

        var content = new StreamReader(stream).ReadToEnd();
        Console.WriteLine("[읽기] 완료");

        var records = ParseJson(content); // JSON 전용 파싱

        stream.Close();
        Console.WriteLine("[닫기] 완료");
        Console.WriteLine($"[결과] {records.Count}건 파싱됨");
        return records;
    }

    private List<Record> ParseJson(string content) { /* JSON 파싱 로직 */ return new List<Record>(); }
}
```

`XmlImporter`까지 추가하면 똑같은 "열기-읽기-닫기-로그" 코드가 세 벌 존재하게 된다. 문제는 명확하다. 만약 "파일을 열 때 인코딩을 UTF-8로 명시해야 한다"거나 "로그 형식을 바꿔야 한다"는 요구사항이 생기면 `CsvImporter`, `JsonImporter`, `XmlImporter` 세 클래스를 전부 찾아 고쳐야 한다. 형식이 다섯, 열 개로 늘어나면 이 중복은 그만큼 배가된다. 게다가 그중 한 클래스에서만 "닫기"를 빠뜨리는 실수를 하더라도 컴파일러는 잡아내지 못한다. 절차 자체를 강제하는 장치가 코드 어디에도 없기 때문이다.

## 패턴 설명

템플릿 메서드(Template Method) 패턴은 "알고리즘의 뼈대(순서)는 상위 클래스가 고정하고, 그 뼈대를 이루는 개별 단계 중 형식마다 달라지는 부분만 하위 클래스가 채워 넣도록" 하는 패턴이다. 상위 클래스에 정의된 템플릿 메서드는 `sealed`이거나 최소한 재정의를 의도하지 않은 일반 메서드로 두고, 그 안에서 호출하는 각 단계를 `abstract`나 `virtual` 메서드로 선언한다. 하위 클래스는 전체 순서를 알 필요도 없고 바꿀 권한도 없다. 자신이 맡은 단계만 구현하면 된다.

구성 요소는 다음과 같다.

- **추상 클래스(AbstractClass)**: 템플릿 메서드를 정의하고, 그 안에서 호출할 단계들을 추상 메서드(하위 클래스가 반드시 구현) 또는 훅 메서드(하위 클래스가 선택적으로 재정의)로 선언한다.
- **구체 클래스(ConcreteClass)**: 추상 메서드를 구현하여 자신만의 세부 동작을 채운다.

이 패턴에서 제어의 흐름은 "상위 클래스가 하위 클래스를 호출한다"는 점에 주목할 필요가 있다. 흔히 상속을 사용할 때는 하위 클래스가 상위 클래스의 메서드를 호출하는 방향을 떠올리기 쉬운데, 템플릿 메서드는 반대다. 이를 할리우드 원칙(Hollywood Principle, "Don't call us, we'll call you")이라 부르기도 한다. 상위 클래스가 절차의 지휘자이고, 하위 클래스는 지휘자가 부를 때만 응답하는 배우인 셈이다.

## C# 예제 코드

먼저 파일 임포트 절차를 추상 클래스에 템플릿 메서드로 고정한다.

```csharp
public abstract class FileImporter
{
    // 템플릿 메서드: 절차의 순서를 이 메서드 하나가 결정한다.
    // 하위 클래스가 순서를 바꿀 수 없도록 sealed로 봉인한다.
    public sealed List<Record> Import(string path)
    {
        var stream = OpenFile(path);
        string content = ReadContent(stream);
        List<Record> records = Parse(content); // 형식마다 달라지는 단계
        CloseFile(stream);

        LogResult(records); // 훅 메서드: 기본 동작이 있으므로 재정의는 선택
        return records;
    }

    // 공통 단계는 상위 클래스가 그대로 구현해 중복을 없앤다.
    private Stream OpenFile(string path)
    {
        Console.WriteLine($"[열기] {path}");
        return File.OpenRead(path);
    }

    private string ReadContent(Stream stream)
    {
        string content = new StreamReader(stream).ReadToEnd();
        Console.WriteLine("[읽기] 완료");
        return content;
    }

    private void CloseFile(Stream stream)
    {
        stream.Close();
        Console.WriteLine("[닫기] 완료");
    }

    // 형식마다 반드시 달라야 하는 단계는 추상 메서드로 위임한다.
    protected abstract List<Record> Parse(string content);

    // 훅 메서드: 기본 구현을 제공하되 필요하면 하위 클래스가 재정의할 수 있다.
    protected virtual void LogResult(List<Record> records)
    {
        Console.WriteLine($"[결과] {records.Count}건 파싱됨");
    }
}
```

각 파일 형식은 `Parse` 단계만 구현하면 된다.

```csharp
public class CsvFileImporter : FileImporter
{
    protected override List<Record> Parse(string content)
    {
        var records = new List<Record>();
        foreach (var line in content.Split('\n'))
        {
            if (string.IsNullOrWhiteSpace(line)) continue;
            var fields = line.Split(',');
            records.Add(new Record(fields));
        }
        return records;
    }
}

public class JsonFileImporter : FileImporter
{
    protected override List<Record> Parse(string content)
    {
        // 실제로는 JSON 역직렬화 라이브러리를 사용한다
        return JsonToRecords(content);
    }

    private List<Record> JsonToRecords(string content)
    {
        // JSON 파싱 로직 (예시로 생략)
        return new List<Record>();
    }
}

public class XmlFileImporter : FileImporter
{
    protected override List<Record> Parse(string content)
    {
        // 실제로는 XML 파서를 사용한다
        return XmlToRecords(content);
    }

    private List<Record> XmlToRecords(string content)
    {
        return new List<Record>();
    }

    // 훅 메서드를 재정의해 XML만의 추가 로그를 남기는 예
    protected override void LogResult(List<Record> records)
    {
        base.LogResult(records);
        Console.WriteLine("[XML 전용] 네임스페이스 검증 완료");
    }
}
```

사용하는 쪽에서는 구체 클래스만 바꿔 끼우면 되고, 절차 자체를 신경 쓸 필요가 없다.

```csharp
FileImporter importer = new CsvFileImporter();
List<Record> records = importer.Import("orders.csv");
```

이제 "파일을 열 때 인코딩을 지정한다"는 요구사항이 생기면 `FileImporter.OpenFile` 한 곳만 고치면 모든 하위 클래스에 자동으로 반영된다. 새로운 형식(예: YAML)이 추가되어도 `Parse`만 구현한 새 클래스를 하나 만들면 된다. `Import` 메서드가 `sealed`로 봉인되어 있으므로, 누군가 실수로 "닫기" 단계를 빼먹은 채 전체 절차를 재정의하는 사고도 원천적으로 방지된다.

## 23장 전략 패턴과의 차이

템플릿 메서드와 전략은 둘 다 "알고리즘의 일부를 바꿔 끼운다"는 목표를 공유하지만, 그 방법이 근본적으로 다르다.

| 구분 | 템플릿 메서드 | 전략 |
|---|---|---|
| 변경 메커니즘 | 상속 (하위 클래스가 추상 메서드를 구현) | 컴포지션 (별도의 전략 객체를 주입) |
| 바꿀 수 있는 범위 | 알고리즘의 일부 단계만 | 알고리즘 전체를 통째로 |
| 관계 형성 시점 | 컴파일 타임 (클래스 상속 관계로 고정) | 런타임 (객체를 주입하거나 교체) |
| 절차의 소유자 | 상위 클래스가 전체 순서를 쥐고 있음 | 컨텍스트는 전략에게 통째로 위임, 순서를 몰라도 됨 |
| 유연성 | 상속 계층이 고정되어 있어 유연성이 낮음 | 인터페이스만 맞으면 어떤 구현으로도 교체 가능해 유연성이 높음 |
| 적합한 상황 | 절차의 큰 틀은 반드시 지켜야 하고, 몇 단계만 다양화하면 될 때 | 절차 전체가 알고리즘마다 완전히 달라질 때 |

23장의 배송비 계산 예제를 다시 떠올려 보자. 만약 "일반/당일/해외 배송" 각각이 요금 계산 공식 자체가 완전히 다르고 서로 공유할 절차가 거의 없다면 전략 패턴이 맞다. 반대로 이번 장의 파일 임포트 예제처럼 "열기→읽기→파싱→닫기"라는 절차 자체는 누가 보아도 동일하고 딱 한 단계(파싱)만 형식별로 다르다면, 굳이 전체를 인터페이스로 쪼개 컴포지션하기보다는 템플릿 메서드로 공통 절차를 상위 클래스에 고정하는 것이 중복을 줄이는 더 직접적인 방법이다.

다만 상속에 기반한다는 점은 템플릿 메서드의 한계이기도 하다. 하위 클래스는 컴파일 시점에 하나의 부모에 묶이므로, 런타임에 파싱 방식을 바꾸고 싶다면(예: 같은 임포터 객체가 상황에 따라 CSV 파싱과 TSV 파싱을 오가야 한다면) 템플릿 메서드로는 표현하기 어렵다. 이런 요구가 생긴다면 `Parse` 단계 자체를 전략 객체(`IParsingStrategy`)로 바꾸는 것을 고려할 수 있다. 실제로 두 패턴을 섞어서, 템플릿 메서드로 절차를 고정하고 그중 일부 단계는 전략으로 위임하는 구성도 흔히 쓰인다.

## 언제 사용하는가

- 여러 클래스가 동일한 순서의 절차를 따르지만, 그 중 한두 단계만 다르게 동작해야 할 때
- 절차의 순서 자체를 하위 클래스가 함부로 바꾸지 못하도록 강제하고 싶을 때
- 공통된 준비/마무리 작업(로깅, 리소스 열기/닫기, 예외 처리 등)을 여러 클래스에 중복해서 작성하고 있을 때
- 프레임워크나 라이브러리를 설계하면서, 사용자가 특정 확장 지점(훅 메서드)만 구현하도록 유도하고 싶을 때 (예: ASP.NET의 여러 생명주기 메서드들)

반대로 알고리즘 단계 사이의 의존 관계가 거의 없거나, 런타임에 유연하게 알고리즘을 교체해야 한다면 전략 패턴 쪽이 더 적합할 수 있다.

## 요약

템플릿 메서드 패턴은 여러 클래스가 공유하는 처리 절차를 상위 클래스의 템플릿 메서드로 고정하고, 형식마다 달라지는 세부 단계만 추상 메서드로 하위 클래스에 위임한다. 이를 통해 절차 중복을 없애고, 절차의 순서가 깨질 위험을 구조적으로 방지할 수 있다. 필요에 따라 기본 동작을 제공하는 훅 메서드를 두어 하위 클래스가 선택적으로 세부 동작을 조정하게 할 수도 있다. 상속으로 알고리즘의 일부만 바꾸는 템플릿 메서드와, 컴포지션으로 알고리즘 전체를 바꾸는 23장의 전략 패턴은 겉보기에 비슷한 목표를 갖지만 변경의 범위와 시점이 다르다는 점을 구분해서 기억해 두자.

## 연습문제

1. 본문의 `FileImporter`에 "YAML" 형식을 지원하는 `YamlFileImporter`를 추가해 보라. `Parse`만 구현하면 되는지 확인하라.
2. `LogResult`를 훅 메서드로 만든 이유를 설명하고, 만약 이것도 추상 메서드였다면 어떤 불편함이 생겼을지 서술하라.
3. 템플릿 메서드의 `Import`를 `sealed`로 봉인하지 않았다면 어떤 문제가 발생할 수 있는지, 구체적인 오용 시나리오를 하나 들어 설명하라.
4. 어떤 게임에서 "몬스터의 턴 처리"가 "상태이상 확인 → 행동 선택 → 행동 실행 → 쿨다운 갱신"이라는 동일한 절차를 따르지만 몬스터 종류마다 "행동 선택" 로직만 다르다고 하자. 이를 템플릿 메서드 패턴으로 설계해 보라.
5. 3번 문제의 시나리오에서, 만약 몬스터의 "행동 선택" 로직을 게임 중에 아이템 효과로 즉시 바꿔야 하는 요구가 추가된다면 템플릿 메서드만으로 충분한지, 전략 패턴을 일부 도입해야 하는지 논하라.

## 문제 상황

애플리케이션 어디서나 같은 설정값을 참조해야 하는 경우를 생각해보자. 서버 주소, 타임아웃 값, API 키 같은 값들을 담고 있는 `AppSettings` 클래스가 있고, 여러 모듈이 이 클래스를 각자 `new` 해서 사용한다고 하자.

```csharp
public class AppSettings
{
    private readonly Dictionary<string, string> _values;

    // 생성자에서 매번 파일을 읽어온다.
    public AppSettings()
    {
        _values = LoadFromFile("app.config");
        Console.WriteLine("설정 파일을 다시 읽었습니다.");
    }

    public string Get(string key) => _values.TryGetValue(key, out var value) ? value : string.Empty;

    private static Dictionary<string, string> LoadFromFile(string path)
    {
        // 실제로는 파일 입출력을 수행하지만 예제에서는 값을 고정한다.
        return new Dictionary<string, string>
        {
            ["ServerUrl"] = "https://api.example.com",
            ["Timeout"] = "30"
        };
    }
}

public class OrderService
{
    private readonly AppSettings _settings = new AppSettings();

    public void PlaceOrder()
    {
        var url = _settings.Get("ServerUrl");
        Console.WriteLine($"{url} 로 주문을 전송합니다.");
    }
}

public class PaymentService
{
    private readonly AppSettings _settings = new AppSettings();

    public void Pay()
    {
        var timeout = _settings.Get("Timeout");
        Console.WriteLine($"{timeout}초 타임아웃으로 결제를 시도합니다.");
    }
}
```

`OrderService`와 `PaymentService`는 각자 `AppSettings`를 하나씩 만든다. 겉으로는 문제없이 동작하는 것처럼 보이지만, 실제로는 다음과 같은 골칫거리가 숨어 있다.

- 설정 파일을 읽는 비용이 큰 작업(네트워크 조회, 암호화된 값 복호화 등)이라면 인스턴스를 만들 때마다 그 비용을 반복해서 지불한다.
- 런타임 중 설정값이 바뀌어 다시 읽어들여야 한다면, 이미 만들어진 여러 `AppSettings` 인스턴스 중 어느 것을 갱신해야 하는지 알 수 없다. 결국 `OrderService`가 보는 값과 `PaymentService`가 보는 값이 서로 달라질 수 있다.
- 로그 파일에 기록하는 `Logger` 같은 클래스라면 더 심각하다. 인스턴스마다 파일 핸들을 따로 열면 파일 잠금 충돌이 나거나, 로그 줄 순서가 뒤섞일 수 있다.

핵심은 "이 클래스는 애플리케이션 전체에서 정확히 하나만 존재해야 한다"는 제약이 코드 어디에도 강제되어 있지 않다는 점이다. 개발자의 습관에 의존할 뿐이다.

## 패턴 설명

싱글턴 패턴은 클래스의 인스턴스가 오직 하나만 만들어지도록 강제하고, 그 인스턴스에 접근할 수 있는 전역 진입점을 제공한다. 방법은 간단하다.

1. 생성자를 `private`으로 막아서 외부에서 `new`를 호출할 수 없게 한다.
2. 클래스 내부에 자기 자신의 인스턴스를 담는 `static` 필드를 둔다.
3. 그 필드에 접근할 수 있는 `static` 속성(또는 메서드)을 공개 API로 제공한다.

이렇게 하면 애플리케이션의 어느 코드에서 접근하더라도 항상 같은 객체를 참조하게 되고, "인스턴스가 여러 개 생겨서 상태가 어긋나는" 문제 자체가 애초에 발생하지 않는다.

다만 구현 방식에 따라 함정이 있다. 가장 단순하게 "속성을 호출할 때 인스턴스가 없으면 만든다"는 방식으로 구현하면, 여러 스레드가 동시에 처음 접근할 경우 두 개 이상의 인스턴스가 생성될 수 있다. 그래서 C#에서는 언어와 런타임이 제공하는 기능을 활용해 스레드 안전성을 자연스럽게 확보하는 방식을 선호한다.

## C# 예제 코드

가장 기본적인 형태는 정적 필드를 선언과 동시에 초기화하는 방식이다. .NET 런타임은 타입의 정적 필드를 그 타입이 처음 사용되기 전, 단 한 번만 초기화하도록 보장하므로 별도의 잠금 코드 없이도 스레드 안전하다.

```csharp
public sealed class AppSettings
{
    // 정적 필드 초기화는 CLR이 스레드 안전하게, 단 한 번만 수행한다.
    private static readonly AppSettings _instance = new AppSettings();

    private readonly Dictionary<string, string> _values;

    // private 생성자로 외부에서의 인스턴스 생성을 막는다.
    private AppSettings()
    {
        _values = LoadFromFile("app.config");
        Console.WriteLine("설정 파일을 읽었습니다.");
    }

    public static AppSettings Instance => _instance;

    public string Get(string key) => _values.TryGetValue(key, out var value) ? value : string.Empty;

    private static Dictionary<string, string> LoadFromFile(string path)
    {
        return new Dictionary<string, string>
        {
            ["ServerUrl"] = "https://api.example.com",
            ["Timeout"] = "30"
        };
    }
}
```

이 방식의 단점은 `AppSettings` 타입이 프로그램에서 처음 참조되는 시점에 무조건 인스턴스가 만들어진다는 점이다. 생성 비용이 크고, 실제로 그 기능을 쓰지 않을 수도 있는 상황이라면 낭비다. 이때는 `Lazy<T>`를 사용해 "처음 실제로 필요할 때"까지 생성을 미루면서도 스레드 안전성을 유지할 수 있다.

```csharp
public sealed class Logger
{
    // Lazy<T>는 기본적으로 스레드 안전한 지연 초기화를 보장한다.
    private static readonly Lazy<Logger> _lazyInstance = new Lazy<Logger>(() =>
    {
        Console.WriteLine("Logger 인스턴스를 처음으로 생성합니다.");
        return new Logger();
    });

    public static Logger Instance => _lazyInstance.Value;

    private Logger() { }

    public void Write(string message)
    {
        Console.WriteLine($"[LOG {DateTime.Now:HH:mm:ss}] {message}");
    }
}
```

`Lazy<T>`의 생성자에 넘긴 팩토리 델리게이트는 `.Value`가 처음 호출되는 순간에만 실행되며, 여러 스레드가 동시에 접근해도 내부적으로 한 번만 실행되도록 동기화된다. 필요하다면 `LazyThreadSafetyMode`를 지정해 동기화 정책을 세밀하게 조절할 수도 있다.

사용하는 쪽 코드는 다음과 같다.

```csharp
public class Program
{
    public static void Main()
    {
        var url = AppSettings.Instance.Get("ServerUrl");
        Logger.Instance.Write($"{url} 에 연결을 시도합니다.");

        // 어디서 호출하든 항상 같은 인스턴스를 참조한다.
        var isSameInstance = ReferenceEquals(AppSettings.Instance, AppSettings.Instance);
        Console.WriteLine($"같은 인스턴스인가? {isSameInstance}");
    }
}
```

## 언제 사용하는가

싱글턴은 "애플리케이션 전역에서 상태나 자원을 하나로 통일해서 관리해야 하는가"라는 질문에 답을 준다. 로그 기록기, 설정 관리자, 캐시 저장소, 커넥션 풀처럼 여러 곳에서 동시에 여러 인스턴스를 만드는 것이 오히려 해로운 경우에 어울린다.

장점은 명확하다. 인스턴스가 하나임을 보장하므로 자원 낭비와 상태 불일치를 막고, 전역에서 손쉽게 접근할 수 있다.

하지만 단점도 그만큼 크다.

- **전역 상태**: 싱글턴은 사실상 전역 변수다. 어떤 코드가 그 상태를 바꿨는지 추적하기 어렵고, 클래스 사이의 숨은 결합이 생긴다.
- **테스트 어려움**: `AppSettings.Instance`처럼 정적 접근을 코드 곳곳에 박아 놓으면, 테스트에서 가짜(Mock) 설정으로 바꿔 끼우기가 매우 어렵다. 테스트 하나가 인스턴스 상태를 바꾸면 다른 테스트에 영향을 줄 수도 있다.
- **숨겨진 의존성**: 메서드 시그니처만 봐서는 그 메서드가 `Logger.Instance`에 의존한다는 사실을 알 수 없다. 의존성이 코드 속에 숨어버린다.

이런 이유로 실무에서는 GoF 싱글턴 패턴을 직접 구현하는 대신, 2장에서 다룬 의존성 역전 원칙을 따라 인터페이스에 의존하고, 의존성 주입(DI) 컨테이너가 해당 타입을 "싱글턴 수명(singleton lifetime)"으로 등록해 관리하도록 위임하는 방식을 훨씬 더 많이 사용한다.

```csharp
public interface IAppSettings
{
    string Get(string key);
}

// DI 컨테이너 등록 예시(ASP.NET Core 기준)
// services.AddSingleton<IAppSettings, AppSettings>();

public class OrderService
{
    private readonly IAppSettings _settings;

    // 인스턴스를 직접 만들지 않고 외부에서 주입받는다.
    public OrderService(IAppSettings settings)
    {
        _settings = settings;
    }

    public void PlaceOrder()
    {
        Console.WriteLine($"{_settings.Get("ServerUrl")} 로 주문을 전송합니다.");
    }
}
```

이 방식에서는 "인스턴스가 하나뿐"이라는 제약이 클래스 자신이 아니라 DI 컨테이너의 설정으로 옮겨간다. 그래서 테스트할 때는 얼마든지 가짜 `IAppSettings`를 주입할 수 있고, 실제 운영 환경에서는 컨테이너가 하나의 인스턴스를 공유해 준다. 클래스 자체는 자신이 몇 개나 존재하는지 전혀 몰라도 되므로 훨씬 유연하다.

## .NET BCL에서 이 패턴 찾아보기

사실 .NET BCL 안에는 GoF 싱글턴 패턴을 그대로 구현한 뚜렷한 대표 클래스가 마땅치 않다. `private` 생성자와 `static` 접근 지점으로 인스턴스 하나만 강제하는 클래스를 BCL 공개 API에서 찾기는 어렵다. 대신 스레드 안전한 지연 초기화가 필요할 때 실무에서 가장 흔히 손이 가는 도구가 `System.Lazy<T>`이며, 이는 이번 장에서 다룬 `Lazy<T>` 기반 싱글턴 구현과 정확히 같은 메커니즘을 제공한다.

`Lazy<T>`는 값을 즉시 만들지 않고, `Value` 프로퍼티에 처음 접근하는 순간에만 팩토리 델리게이트를 실행한다. 여러 스레드가 동시에 `Value`에 접근해도 기본적으로는 내부적으로 동기화되어 정확히 한 번만 생성되도록 보장한다. 이 성질 덕분에 `Lazy<T>`를 `static readonly` 필드로 감싸두면, 앞서 살펴본 `Logger` 예제처럼 "처음 필요할 때 딱 한 번, 스레드 안전하게" 만들어지는 싱글턴을 손쉽게 구현할 수 있다.

```csharp
public sealed class ConnectionPoolManager
{
    // LazyThreadSafetyMode.ExecutionAndPublication:
    // 팩토리 델리게이트가 여러 스레드에서 동시에 실행되지 않도록 보장하는 기본 모드다.
    private static readonly Lazy<ConnectionPoolManager> _lazyInstance =
        new Lazy<ConnectionPoolManager>(
            () => new ConnectionPoolManager(),
            LazyThreadSafetyMode.ExecutionAndPublication);

    public static ConnectionPoolManager Instance => _lazyInstance.Value;

    private ConnectionPoolManager()
    {
        Console.WriteLine("커넥션 풀을 초기화합니다.");
    }

    public void Acquire() => Console.WriteLine("커넥션을 하나 대여합니다.");
}
```

`LazyThreadSafetyMode` 열거형을 통해 초기화 동작을 세밀하게 제어할 수 있다는 점도 눈여겨볼 만하다. `ExecutionAndPublication`은 기본값으로, 팩토리 델리게이트 자체가 동시에 여러 번 실행되는 것까지 막아준다. 반면 `PublicationOnly`는 여러 스레드가 각자 값을 만들도록 허용하되 그중 먼저 완료된 하나만 채택하고, `None`은 아무런 동기화도 하지 않는다. 즉 `Lazy<T>`는 "인스턴스를 하나로 강제한다"는 싱글턴의 목적 자체보다는 "지연 초기화를 안전하게 한다"는 데 초점이 맞춰진 범용 도구지만, 정적 필드와 결합하면 이번 장에서 다룬 싱글턴 구현의 실질적인 표준 도구 역할을 한다.

## 요약

싱글턴 패턴은 private 생성자와 static 접근 지점으로 인스턴스를 하나로 강제하는 가장 단순한 생성 패턴이다. C#에서는 정적 필드 초기화나 `Lazy<T>`를 이용해 별도의 잠금 코드 없이도 스레드 안전한 구현을 손쉽게 얻을 수 있다. 그러나 전역 상태와 숨은 의존성이라는 대가를 치러야 하므로, 정말로 필요한 경우가 아니라면 직접 구현하기보다는 DI 컨테이너의 싱글턴 수명 관리 기능으로 같은 효과를 얻는 쪽을 우선적으로 고려해야 한다.

## 연습문제

1. `private` 생성자가 없는 상태에서 `static` 인스턴스 필드만 두면 어떤 문제가 생기는지 설명해보라.
2. "속성 접근 시점에 인스턴스가 없으면 생성한다"는 방식(지연 생성)을 잠금 없이 구현했을 때, 멀티스레드 환경에서 어떤 문제가 발생할 수 있는지 설명하고 코드로 보여라.
3. `Lazy<T>`를 사용한 `Logger` 클래스에 `Dispose` 로직이 필요하다고 가정하자. 어떻게 안전하게 자원을 해제할 수 있을지 논의해보라.
4. 싱글턴으로 구현된 `AppSettings`를 사용하는 기존 코드를 DI 방식(`IAppSettings` 인터페이스 + 생성자 주입)으로 리팩터링해보라.
5. 싱글턴 패턴이 테스트를 어렵게 만드는 구체적인 시나리오를 하나 만들어보고, 그 시나리오에서 DI로 전환하면 무엇이 달라지는지 비교해보라.

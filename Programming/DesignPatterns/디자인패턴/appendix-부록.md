이 부록은 앞선 25개 장에서 다룬 내용을 실전에서 빠르게 다시 찾아볼 수 있도록 세 가지 표와 하나의 안내로 정리한 것이다. 패턴 이름이 잘 기억나지 않을 때, 클래스 다이어그램의 화살표 모양이 헷갈릴 때, 혹은 여기서 더 깊이 공부하고 싶을 때 펼쳐보기 좋은 참고 자료로 구성했다.

## 패턴 선택 가이드

아래 표는 "지금 겪고 있는 상황"에서 "어떤 패턴을 검토해 볼 만한지"를 매핑한 것이다. 실제 설계에서는 하나의 상황에 여러 패턴이 동시에 후보로 떠오르는 경우가 많으므로, 이 표는 정답을 알려주는 규칙이 아니라 "이 방향을 한번 살펴보라"는 이정표로 활용하는 것이 좋다.

| 겪고 있는 상황 | 검토할 패턴 |
|---|---|
| 애플리케이션 전체에서 단 하나만 존재해야 하고, 어디서든 같은 인스턴스에 접근해야 하는 대상이 있다 | 3장 싱글턴 |
| 어떤 구체 클래스를 생성할지가 서브클래스마다 달라져야 하는데, 생성 로직을 한곳에 정리하고 싶다 | 4장 팩토리 메서드 |
| 서로 어울리는 제품군(예: 플랫폼별 UI 컴포넌트 세트)을 통째로 교체할 수 있어야 한다 | 5장 추상 팩토리 |
| 생성자 인자가 너무 많거나, 선택적 옵션이 늘어나면서 오버로드 생성자가 계속 늘어난다 | 6장 빌더 |
| 객체를 새로 만드는 비용이나 초기화 과정이 복잡해서, 기존 인스턴스를 복제하는 편이 더 효율적이다 | 7장 프로토타입 |
| 이미 만들어진 클래스의 인터페이스가 내가 필요한 인터페이스와 맞지 않아 그대로 쓸 수 없다 | 8장 어댑터 |
| 클래스에 서로 독립적으로 변화하는 두 개의 축이 있어서, 상속만으로 다루면 조합이 기하급수적으로 늘어난다 | 9장 브리지 |
| 개별 객체와 그 객체들의 묶음(트리 구조)을 클라이언트가 구분 없이 똑같은 방식으로 다뤄야 한다 | 10장 컴포지트 |
| 상속으로 기능을 조합하려니 클래스 수가 폭발한다. 여러 기능을 런타임에 자유롭게 겹쳐 씌우고 싶다 | 11장 데코레이터 |
| 여러 하위 시스템을 정해진 순서로 호출해야 하는 복잡한 절차를, 단순한 진입점 하나로 감추고 싶다 | 12장 퍼사드 |
| 비슷한 속성을 가진 객체가 대량으로 생성되어 메모리 사용량이 급격히 늘어난다 | 13장 플라이웨이트 |
| 실제 객체에 접근하기 전에 접근 제어, 지연 생성, 로깅 같은 부가 처리를 끼워 넣고 싶다 | 14장 프록시 |
| 요청을 처리할 수 있는 후보가 여럿이고, 실제로 누가 처리할지는 실행 중에야 정해진다 | 15장 체인 오브 리스판서빌리티 |
| 실행할 동작을 객체로 캡슐화해서 큐에 쌓아두거나, 취소(undo)하거나, 나중에 실행하고 싶다 | 16장 커맨드 |
| 자주 반복되는 간단한 문법(수식, 검색 조건, 규칙 등)을 직접 해석해서 처리해야 한다 | 17장 인터프리터 |
| 컬렉션의 내부 구조를 감춘 채, 원소를 순차적으로 접근하는 방법을 통일하고 싶다 | 18장 이터레이터 |
| 여러 객체가 서로 직접 참조하며 복잡하게 얽혀 있어서, 하나를 바꾸면 나머지도 줄줄이 영향을 받는다 | 19장 중재자 |
| 객체를 이전 상태로 되돌리는(undo) 기능이 필요한데, 그 객체의 캡슐화는 깨고 싶지 않다 | 20장 메멘토 |
| 한 객체의 상태 변화를, 누가 구독하고 있는지 몰라도 여러 대상에게 알려야 한다 | 21장 옵저버 |
| 객체의 행동이 상태에 따라 달라지는데, 그 상태를 구분하는 if-else나 switch 문이 계속 늘어난다 | 22장 상태 |
| 여러 알고리즘 중 하나를 런타임에 선택하거나 갈아 끼워야 한다 | 23장 전략 |
| 여러 클래스가 거의 같은 순서의 알고리즘을 따르지만, 일부 단계만 서로 다르게 구현해야 한다 | 24장 템플릿 메서드 |
| 안정된 클래스 계층 구조에 새로운 연산을 계속 추가해야 하는데, 매번 각 클래스를 건드리고 싶지 않다 | 25장 비지터 |

## 생성·구조·행동 패턴 전체 요약표

각 패턴이 무엇을 의도하는지 한 줄로 정리했다. 패턴 이름만 보고 의도가 잘 떠오르지 않을 때 훑어보기 좋다.

### 생성 패턴

| 패턴 | 의도 |
|---|---|
| 3장 싱글턴 | 클래스의 인스턴스가 오직 하나만 존재하도록 보장하고, 어디서든 그 인스턴스에 접근할 수 있게 한다 |
| 4장 팩토리 메서드 | 객체 생성을 서브클래스에 위임하여, 정확히 어떤 클래스를 만들지는 서브클래스가 결정하게 한다 |
| 5장 추상 팩토리 | 서로 관련된 여러 제품 객체를 구체 클래스를 지정하지 않고 하나의 인터페이스로 생성한다 |
| 6장 빌더 | 복잡한 객체를 단계별로 조립하여 생성하고, 같은 조립 과정으로도 서로 다른 결과물을 만들어낼 수 있게 한다 |
| 7장 프로토타입 | 클래스로부터 새로 생성하는 대신, 기존 인스턴스를 복제하여 객체를 만든다 |

### 구조 패턴

| 패턴 | 의도 |
|---|---|
| 8장 어댑터 | 호환되지 않는 인터페이스를 가진 클래스를 감싸서, 클라이언트가 기대하는 인터페이스로 맞춰준다 |
| 9장 브리지 | 추상화와 구현을 분리하여, 두 축이 서로 독립적으로 확장될 수 있게 한다 |
| 10장 컴포지트 | 개별 객체와 그 객체들의 묶음을 같은 인터페이스로 다루어, 클라이언트가 둘을 구분하지 않게 한다 |
| 11장 데코레이터 | 객체에 새로운 책임을 상속 없이 동적으로 덧씌워 추가한다 |
| 12장 퍼사드 | 여러 하위 시스템의 복잡한 인터페이스를 하나의 단순한 진입점으로 감싼다 |
| 13장 플라이웨이트 | 여러 객체가 공유할 수 있는 데이터를 분리해 공유시켜 메모리 사용량을 줄인다 |
| 14장 프록시 | 실제 객체에 대한 접근을 대리 객체가 통제하여, 접근 제어나 지연 생성 같은 처리를 끼워 넣는다 |

### 행동 패턴

| 패턴 | 의도 |
|---|---|
| 15장 체인 오브 리스판서빌리티 | 요청을 처리할 수 있는 후보 객체들을 사슬로 연결하고, 그중 하나가 처리할 때까지 요청을 넘긴다 |
| 16장 커맨드 | 실행할 요청을 객체로 캡슐화하여, 큐에 저장하거나 취소하거나 나중에 실행할 수 있게 한다 |
| 17장 인터프리터 | 특정 문법을 클래스 구조로 표현하고, 그 구조를 순회하며 문장을 해석·실행한다 |
| 18장 이터레이터 | 컬렉션의 내부 표현을 드러내지 않고, 원소들을 순차적으로 접근하는 방법을 제공한다 |
| 19장 중재자 | 객체들이 서로 직접 참조하지 않고 중재자를 통해서만 상호작용하게 하여 결합도를 낮춘다 |
| 20장 메멘토 | 객체의 캡슐화를 깨지 않으면서 이전 상태를 저장해 두었다가 나중에 복원할 수 있게 한다 |
| 21장 옵저버 | 한 객체의 상태 변화를 그 객체를 구독하는 여러 객체에게 자동으로 알린다 |
| 22장 상태 | 객체의 행동을 상태별 클래스로 나누어, 상태가 바뀌면 행동도 함께 바뀌게 한다 |
| 23장 전략 | 알고리즘을 별도의 클래스로 캡슐화하여, 런타임에 알고리즘을 서로 바꿔 끼울 수 있게 한다 |
| 24장 템플릿 메서드 | 알고리즘의 전체 골격은 부모 클래스가 정의하고, 일부 단계는 서브클래스가 구현하도록 한다 |
| 25장 비지터 | 클래스 계층 구조를 건드리지 않고, 그 계층에 대해 수행할 새로운 연산을 별도의 클래스로 추가한다 |

## UML 클래스 다이어그램 표기법 정리

이 책의 각 장에 실린 SVG 다이어그램들은 모두 아래의 표기 규칙을 따른다. 클래스는 사각형 상자로, 인터페이스는 상자 위에 `<<interface>>`를 붙여 표시했다. 클래스 사이의 관계는 선의 종류(실선/점선)와 끝 모양(삼각형/다이아몬드/화살표)의 조합으로 구분한다.

| 관계 | 선 모양 | 끝 모양 | 의미 | 이 책에서의 예 |
|---|---|---|---|---|
| 상속 (Inheritance) | 실선 | 속이 빈(흰색) 삼각형, 부모 쪽을 향함 | "~는 ~의 한 종류다"(is-a). 자식 클래스가 부모 클래스를 확장한다 | 9장 브리지의 Circle → Shape |
| 구현 (Realization) | 점선 | 속이 빈 삼각형, 인터페이스 쪽을 향함 | 클래스가 인터페이스가 정한 계약(메서드 시그니처)을 실제로 구현한다 | 14장 프록시의 DocumentProxy ⇢ IDocumentLoader |
| 합성 (Composition) | 실선 | 속이 채워진(검은색) 다이아몬드, 전체 쪽에 위치 | 전체-부분 관계이면서 전체가 부분의 생명주기를 온전히 소유한다. 전체가 사라지면 부분도 함께 사라진다 | 10장 컴포지트의 Department가 자식 목록(`_children`)을 직접 소유하는 관계 |
| 집합 (Aggregation) | 실선 | 속이 빈 다이아몬드, 전체 쪽에 위치 | 전체-부분 관계이지만 부분이 전체와 독립적인 생명주기를 가진다. 전체가 사라져도 부분은 남을 수 있다 | 여러 프로젝트에 동시에 소속될 수 있는 팀원처럼, 하나의 부분이 여러 전체에 걸쳐 재사용되는 관계 |
| 의존 (Dependency) | 점선 | 속이 열린 화살표 | 한 클래스가 다른 클래스를(매개변수, 지역 변수, 반환값 등으로) 일시적으로 사용한다. 필드로 계속 들고 있지는 않는다 | 2장 의존성 역전 다이어그램에서 고수준 모듈이 인터페이스를 향해 그리는 화살표 |
| 연관/참조 (Association) | 실선 | 속이 열린 화살표 또는 화살표 없음 | 한 객체가 다른 객체를 필드 등으로 계속 참조하며 협력한다. 소유(합성/집합)까지는 아닌 일반적인 참조 관계 | 9장 브리지에서 Shape가 IRenderer를 필드로 참조하는 "다리" 관계 |

몇 가지 실전 팁을 덧붙인다.

- 화살표의 방향은 항상 "누가 누구를 알고 있는가"를 가리킨다. 상속·구현 화살표는 자식/구현체에서 부모/인터페이스 쪽을 향하고, 의존·연관 화살표는 사용하는 쪽에서 사용되는 쪽을 향한다.
- 합성과 집합을 구분하는 기준은 다이아몬드가 채워져 있는지가 아니라 "생명주기를 누가 책임지는가"다. 실무에서는 이 둘을 엄격히 구분하지 않고 뭉뚱그려 표시하는 경우도 많으므로, 다이어그램을 읽을 때는 채워진 다이아몬드를 "강한 소유", 빈 다이아몬드를 "약한 소유"로 이해하면 충분하다.
- 의존과 연관을 구분하는 기준은 "관계가 메서드 호출 한 번으로 끝나는가, 필드로 계속 유지되는가"이다. 이 책의 다이어그램에서는 필드로 유지되는 관계(예: Bridge의 `_renderer`)는 실선으로, 매개변수로만 짧게 등장하는 관계는 점선으로 구분해서 그렸다.

## 참고할 만한 자료 유형 안내

디자인 패턴은 한 권의 책으로 끝나는 지식이 아니라, 실제 코드를 읽고 쓰면서 계속 다듬어 가는 감각에 가깝다. 이 책을 다 읽은 뒤에는 아래와 같은 유형의 자료를 통해 이해를 계속 넓혀 가기를 권한다.

- **공식 문서**: 사용하는 언어나 프레임워크의 공식 문서는 특정 패턴이 라이브러리 설계에 어떻게 실제로 반영되어 있는지를 보여주는 가장 정확한 자료다. 예를 들어 .NET의 이벤트/델리게이트 문서를 읽으면 21장 옵저버 패턴이 언어 차원의 기능으로 어떻게 흡수되어 있는지 확인할 수 있고, `IEnumerable`/`IEnumerator` 관련 문서는 18장 이터레이터 패턴이 컬렉션 API 전체에 얼마나 깊이 배어 있는지를 보여준다.
- **오픈소스 코드 저장소**: 실제로 널리 쓰이는 오픈소스 프로젝트의 소스 코드를 직접 읽어보는 것은 패턴을 "교과서적인 예제"가 아니라 "실전에서 변형된 형태"로 만나는 가장 좋은 방법이다. 웹 프레임워크의 미들웨어 파이프라인에서 15장 체인 오브 리스판서빌리티의 변형을, 의존성 주입 컨테이너에서 5장 추상 팩토리의 흔적을 찾아보는 식으로 접근하면 좋다.
- **커뮤니티(기술 블로그, 컨퍼런스 발표, Q&A 사이트)**: 다른 개발자들이 같은 패턴을 두고 어떤 트레이드오프를 고민했는지, 어떤 상황에서 오히려 패턴을 걷어냈는지에 대한 실전 경험담은 책에서는 다루기 어려운 맥락을 채워준다. 특히 "이 패턴을 썼다가 후회한 이유"류의 회고는 패턴의 단점을 균형 있게 이해하는 데 도움이 된다.
- **직접 해보는 리팩토링 연습과 코드 리뷰**: 가장 확실한 학습 방법은 여러분이 이미 가지고 있는 코드, 혹은 동료의 코드를 놓고 "여기에 어떤 패턴을 적용하면 더 나아질까, 혹은 적용하지 않는 편이 더 나을까"를 직접 판단해 보는 것이다. 패턴은 정답을 맞히는 퀴즈가 아니라 설계 대안을 비교하는 도구이므로, 실제 코드에 적용해 보고 그 결과를 동료와 함께 리뷰하는 과정에서 비로소 체화된다.

패턴 이름을 아는 것과 패턴을 적재적소에 쓰는 것 사이에는 꽤 큰 간극이 있다. 이 책이 그 간극을 좁혀 가는 첫걸음이 되었기를 바란다.

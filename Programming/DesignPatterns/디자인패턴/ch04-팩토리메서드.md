## 문제 상황

주문이 완료되면 이메일, SMS, 푸시 알림 중 하나로 사용자에게 알려주는 기능을 만든다고 해보자. 처음에는 간단하게 조건문 하나로 해결한다.

```csharp
public class NotificationService
{
    public void Send(string type, string recipient, string message)
    {
        if (type == "Email")
        {
            var smtpClient = new SmtpClient();
            smtpClient.Connect();
            smtpClient.SendMail(recipient, message);
        }
        else if (type == "SMS")
        {
            var smsGateway = new SmsGateway();
            smsGateway.Authenticate();
            smsGateway.SendMessage(recipient, message);
        }
        else if (type == "Push")
        {
            var pushService = new PushNotificationService();
            pushService.Connect();
            pushService.Push(recipient, message);
        }
        else
        {
            throw new NotSupportedException($"지원하지 않는 알림 종류입니다: {type}");
        }
    }
}
```

처음 한동안은 이 코드로 충분하다. 그런데 기획팀이 "카카오톡 알림도 추가해 달라"고 요청한다. 개발자는 `Send` 메서드에 `else if`를 하나 더 추가한다. 얼마 뒤 "VIP 고객에게는 알림을 두 종류 동시에 보내달라"는 요청이 들어오고, 그다음엔 "테스트 환경에서는 실제로 보내지 말고 콘솔에 출력만 해달라"는 요청이 들어온다. `Send` 메서드는 점점 길어지고, 분기마다 서로 다른 초기화 로직(`Connect`, `Authenticate` 등)이 뒤섞여 가독성이 떨어진다.

더 큰 문제는 이 메서드를 건드리지 않고는 새 알림 종류를 추가할 방법이 없다는 점이다. 새로운 요구사항이 들어올 때마다 이미 잘 동작하던 기존 코드를 다시 열어서 수정해야 하고, 그 과정에서 기존 분기를 건드려 실수할 위험도 커진다. 이것은 2장에서 살펴본 개방-폐쇄 원칙(OCP) — "확장에는 열려 있고 수정에는 닫혀 있어야 한다" — 을 정면으로 위반하는 상황이다. 또한 이 클래스를 테스트하려면 이메일 서버, SMS 게이트웨이 등 모든 분기의 실제 의존성을 다 준비해야 해서 단위 테스트도 점점 어려워진다.

## 패턴 설명

문제의 근원은 "무엇을 만들지 결정하는 로직"과 "그것을 사용하는 로직"이 한 메서드 안에 뭉쳐 있다는 것이다. 팩토리 메서드 패턴은 이 둘을 분리한다. 객체 생성을 위한 별도의 메서드(팩토리 메서드)를 정의해두고, 실제로 어떤 구체 클래스를 만들지는 서브클래스가 결정하도록 위임한다.

구조는 크게 네 가지 역할로 나뉜다.

- **Product**: 만들어질 객체가 구현해야 하는 공통 인터페이스.
- **ConcreteProduct**: Product를 구현한 구체적인 클래스들.
- **Creator**: 팩토리 메서드를 선언하는 (보통 추상) 클래스. 팩토리 메서드가 만들어낸 Product를 사용하는 공통 흐름도 여기에 둘 수 있다.
- **ConcreteCreator**: 팩토리 메서드를 재정의해서 특정 ConcreteProduct를 반환하는 클래스.

핵심은 Creator의 공통 로직이 `CreateNotification()`처럼 아직 구체 타입이 정해지지 않은 메서드를 호출한다는 점이다. 실제로 어떤 타입이 만들어질지는 그 메서드를 재정의하는 서브클래스에 가서야 결정된다. 그래서 새로운 종류를 추가하고 싶으면 기존 Creator나 다른 ConcreteCreator를 전혀 건드리지 않고, 새 ConcreteCreator와 ConcreteProduct 한 쌍만 추가하면 된다.

아래 그림은 Creator/ConcreteCreator와 Product/ConcreteProduct 사이의 관계를 보여준다.

```text
  +----------------------------+           <<interface>>
  |  NotificationSender        |         +------------------------+
  |  (Creator, abstract)       |         |     INotification      |
  +----------------------------+         +------------------------+
  | + Notify(수신자, 메시지)     |-- 생성(creates) -->| + Send(수신자, 메시지) |
  | + CreateNotification()     |         +------------------------+
  |   : INotification (팩토리   |                ^              ^
  |   메서드, 서브클래스가 재정의) |                :              :
  +----------------------------+                :  구현(dashed)  :
        ^              ^                        :              :
        : (상속)        : (상속)         +----------------+  +----------------+
        :              :                | EmailNotification |  | SmsNotification |
  +----------------+  +----------------+ | (ConcreteProduct) |  | (ConcreteProduct)|
  |EmailNotification|  |SmsNotification | +----------------+  +----------------+
  |Sender           |  |Sender          |         ^                    ^
  |(ConcreteCreator)|  |(ConcreteCreator)|         |  생성               |  생성
  |CreateNotification()|CreateNotification()|------+                    |
  +----------------+  +----------------+-----------------------------------+

  구조 설명
  - Creator는 공통 흐름(Notify)과 팩토리 메서드(CreateNotification)를 정의한다.
  - ConcreteCreator는 팩토리 메서드를 재정의해 특정 ConcreteProduct를 생성한다.
  - 클라이언트는 Creator와 INotification(Product)에만 의존하므로,
    새로운 알림 종류를 추가할 때 기존 코드를 수정할 필요가 없다.
```

## C# 예제 코드

먼저 Product 역할을 하는 인터페이스와 구체 클래스들을 정의한다.

```csharp
// Product: 모든 알림이 구현해야 하는 공통 인터페이스
public interface INotification
{
    void Send(string recipient, string message);
}

// ConcreteProduct
public class EmailNotification : INotification
{
    public void Send(string recipient, string message)
    {
        Console.WriteLine($"[이메일] {recipient} 에게 전송: {message}");
    }
}

public class SmsNotification : INotification
{
    public void Send(string recipient, string message)
    {
        Console.WriteLine($"[SMS] {recipient} 에게 전송: {message}");
    }
}

public class PushNotification : INotification
{
    public void Send(string recipient, string message)
    {
        Console.WriteLine($"[푸시] {recipient} 에게 전송: {message}");
    }
}
```

다음으로 Creator를 정의한다. 공통 흐름(`Notify`)은 여기서 한 번만 작성하고, 실제로 어떤 알림 객체를 만드는지는 팩토리 메서드 `CreateNotification`에 위임한다.

```csharp
// Creator: 팩토리 메서드를 선언하는 추상 클래스
public abstract class NotificationSender
{
    // 팩토리 메서드 - 서브클래스가 재정의해서 구체적인 Product를 생성한다.
    protected abstract INotification CreateNotification();

    // 공통 흐름은 한 곳에서 관리하고, 생성 책임만 서브클래스에 넘긴다.
    public void Notify(string recipient, string message)
    {
        var notification = CreateNotification();
        Console.WriteLine("알림 발송을 준비합니다...");
        notification.Send(recipient, message);
        Console.WriteLine("발송 이력을 기록합니다.");
    }
}
```

각 알림 종류마다 ConcreteCreator를 하나씩 만든다.

```csharp
// ConcreteCreator
public class EmailNotificationSender : NotificationSender
{
    protected override INotification CreateNotification() => new EmailNotification();
}

public class SmsNotificationSender : NotificationSender
{
    protected override INotification CreateNotification() => new SmsNotification();
}

public class PushNotificationSender : NotificationSender
{
    protected override INotification CreateNotification() => new PushNotification();
}
```

이제 "카카오톡 알림"을 추가해달라는 요청이 들어와도, 기존 클래스는 손댈 필요가 없다.

```csharp
public class KakaoNotification : INotification
{
    public void Send(string recipient, string message)
    {
        Console.WriteLine($"[카카오톡] {recipient} 에게 전송: {message}");
    }
}

public class KakaoNotificationSender : NotificationSender
{
    protected override INotification CreateNotification() => new KakaoNotification();
}
```

사용하는 쪽 코드는 구체 클래스가 아니라 `NotificationSender`와 `INotification`이라는 추상화에만 의존한다.

```csharp
public class Program
{
    public static void Main()
    {
        var senders = new List<NotificationSender>
        {
            new EmailNotificationSender(),
            new SmsNotificationSender(),
            new PushNotificationSender(),
            new KakaoNotificationSender()
        };

        foreach (var sender in senders)
        {
            sender.Notify("user@example.com", "결제가 완료되었습니다.");
            Console.WriteLine();
        }
    }
}
```

`Program` 클래스는 새로운 알림 종류가 추가되어도 전혀 수정할 필요가 없다. `senders` 목록에 `new KakaoNotificationSender()`를 추가하는 것으로 끝난다.

## 언제 사용하는가

팩토리 메서드 패턴은 "어떤 구체 클래스를 만들지"가 조건에 따라 달라지고, 그 조건이 앞으로도 계속 늘어날 가능성이 있을 때 특히 유용하다. 클라이언트 코드는 Product 인터페이스와 Creator 추상 클래스에만 의존하므로, 개방-폐쇄 원칙을 지키면서 새로운 종류를 계속 추가할 수 있다. 각 ConcreteCreator가 독립적인 클래스이므로 단위 테스트도 개별적으로 하기 쉬워진다.

다만 대가도 있다. 알림 종류 하나를 추가할 때마다 ConcreteProduct와 ConcreteCreator라는 클래스 한 쌍이 계속 늘어난다. 종류가 두세 개뿐이고 앞으로도 거의 바뀌지 않을 거라 확신한다면, 이런 클래스 계층 구조를 만드는 것이 오히려 과한 설계일 수 있다. 그럴 때는 차라리 간단한 딕셔너리 기반 매핑(문자열 키에 생성 델리게이트를 등록하는 방식) 정도로 충분한 경우도 많다.

5장에서 다루는 추상 팩토리 패턴과 자주 혼동되는데, 둘의 차이는 명확하다. 팩토리 메서드는 상속을 이용해 "하나의 제품"을 만드는 방법을 서브클래스에 위임하는 패턴이다. 반면 추상 팩토리는 서로 관련된 "제품군 전체"(예: 알림 발송기, 알림 템플릿, 알림 로거를 한 세트로)를 만들어내는 팩토리 객체를 조합(composition)으로 교체하는 패턴이다. 즉 팩토리 메서드가 한 단계 더 확장되어 여러 팩토리 메서드를 하나의 인터페이스로 묶으면 추상 팩토리에 가까워진다고 볼 수 있다. 이 관계는 5장에서 같은 알림 시나리오를 확장하며 자세히 다룬다.

## .NET BCL에서 이 패턴 찾아보기

팩토리 메서드 패턴은 사실 BCL 곳곳에 이미 녹아 있다. 가장 널리 쓰이는 예는 `IEnumerable<T>.GetEnumerator()`다. `foreach`가 컬렉션을 순회할 때마다 호출하는 이 메서드는, 호출하는 쪽이 실제로 어떤 이터레이터 구현체가 반환되는지 전혀 몰라도 되게 만들어준다. `List<T>`, `Dictionary<TKey, TValue>`, `LINQ` 쿼리 결과 등은 각자 내부적으로 완전히 다른 이터레이터 타입을 반환하지만, 클라이언트 코드는 오직 `IEnumerator<T>` 인터페이스에만 의존한다. 이는 이번 장의 `CreateNotification()`이 `INotification`이라는 추상 타입만 노출하고 구체 타입 결정은 서브클래스(또는 이 경우 내부 구현)에 맡기는 것과 정확히 같은 구조다.

```csharp
// 호출하는 쪽은 반환되는 이터레이터의 구체 타입을 전혀 알 필요가 없다.
IEnumerable<int> numbers = new List<int> { 1, 2, 3 };

// GetEnumerator()가 팩토리 메서드 역할을 한다.
IEnumerator<int> enumerator = numbers.GetEnumerator();

while (enumerator.MoveNext())
{
    Console.WriteLine(enumerator.Current);
}

// LINQ의 Where()가 반환하는 시퀀스 역시 내부적으로 다른 이터레이터 구현체를 사용하지만,
// 클라이언트는 여전히 IEnumerable<int>/IEnumerator<int>에만 의존한다.
IEnumerable<int> evenNumbers = numbers.Where(n => n % 2 == 0);
IEnumerator<int> evenEnumerator = evenNumbers.GetEnumerator();
```

또 다른 실제 예는 `System.Data.Common.DbProviderFactory` 클래스가 제공하는 `CreateConnection()`, `CreateCommand()` 같은 `CreateXxx()` 메서드들이다. 이들은 이름 그대로 팩토리 메서드의 전형적인 형태를 띠고 있어서, 호출하는 쪽은 실제로 `SqlConnection`이 만들어지는지 다른 공급자의 커넥션 구현체가 만들어지는지 신경 쓸 필요가 없다. 다만 `DbProviderFactory` 자체는 하나의 팩토리가 `DbConnection`, `DbCommand`, `DbParameter` 등 서로 관련된 제품군 전체를 함께 만들어낸다는 점에서, 팩토리 메서드보다는 5장에서 다룰 추상 팩토리 패턴과 더 밀접하게 연결된다. 이 클래스는 5장에서 다시 자세히 살펴본다.

## 요약

팩토리 메서드 패턴은 객체 생성 로직을 조건문으로 흩어놓지 않고, Creator의 팩토리 메서드를 통해 서브클래스에 위임함으로써 개방-폐쇄 원칙을 지킬 수 있게 해준다. 새로운 제품 종류가 추가될 때 기존 코드를 수정하지 않고 새 ConcreteProduct/ConcreteCreator 쌍만 추가하면 되므로, 확장 가능성이 높은 생성 로직에 적합하다. 다만 제품 종류가 적고 변화가 거의 없는 경우에는 오히려 불필요한 클래스 계층을 만드는 결과가 될 수 있으므로, 상황에 맞게 판단해야 한다.

## 연습문제

1. 이 장의 "문제 상황"에 나온 `if/else` 기반 `NotificationService`에 새로운 알림 종류(예: 슬랙 알림)를 추가하려면 몇 곳을 수정해야 하는지 나열해보라. 팩토리 메서드로 바꾼 뒤에는 몇 곳을 수정해야 하는지 비교해보라.
2. `NotificationSender.Notify` 메서드에 "발송 실패 시 재시도" 로직을 추가하고 싶다. 이 로직을 Creator와 ConcreteCreator 중 어디에 두는 것이 적절한지 설명해보라.
3. 팩토리 메서드의 반환 타입을 인터페이스(`INotification`)가 아니라 구체 클래스로 선언하면 어떤 문제가 생기는지 설명해보라.
4. VIP 고객에게는 이메일과 SMS를 동시에 보내야 한다는 요구사항이 생겼다. 기존 클래스 구조를 최대한 재사용하면서 이 요구사항을 반영하는 방법을 설계해보라.
5. 팩토리 메서드 패턴과 5장에서 다룰 추상 팩토리 패턴의 차이를 자신의 언어로 한 문단 이내로 설명해보라.

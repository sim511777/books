## 문제 상황

간단한 텍스트 편집기를 만들고 있다고 해 보자. 사용자는 툴바 버튼이나 메뉴, 키보드 단축키로 "텍스트 삽입", "텍스트 삭제", "선택 영역 바꾸기" 같은 동작을 실행한다. 가장 손쉬운 구현은 버튼 클릭 이벤트 핸들러에서 편집기 내부 메서드를 바로 호출하는 방식이다.

```csharp
insertButton.Click += (s, e) => editor.InsertText(cursorPosition, "Hello");
deleteButton.Click += (s, e) => editor.DeleteText(start, length);
```

당장은 동작한다. 문제는 "실행 취소(Undo)"와 "다시 실행(Redo)"을 요구받는 순간 터진다. 버튼 핸들러는 `editor.InsertText`를 호출하는 순간 그 동작이 무엇이었는지, 되돌리려면 무엇을 해야 하는지에 대한 정보를 전혀 남기지 않는다. 편집기 클래스 안에 "마지막에 삽입한 텍스트의 위치와 길이" 같은 상태를 따로 기록해서 되돌리는 코드를 추가할 수도 있겠지만, 동작의 종류(삽입, 삭제, 서식 변경, 붙여넣기...)가 늘어날수록 이 되돌리기 로직도 각 동작마다 따로 얽혀서 편집기 클래스 자체가 거대해진다.

매크로 기능("이 세 가지 동작을 순서대로 실행하는 버튼 하나 만들기")이나 작업 큐("네트워크가 느릴 때는 동작을 큐에 쌓아 두고 순서대로 처리하기"), 실행 로그("사용자가 방금 무엇을 했는지 기록해서 나중에 재현하기") 같은 요구도 마찬가지다. 호출자가 편집기의 메서드를 직접 호출하는 구조에서는 "실행될 동작"을 변수에 담아 두거나, 줄을 세우거나, 기록해 둘 방법이 없다. 실행될 동작 자체를 데이터처럼 다룰 수 있는 형태로 만들어야 이런 요구를 자연스럽게 풀 수 있다.

## 패턴 설명

커맨드 패턴은 "실행할 요청"을 하나의 객체로 캡슐화한다. 이 객체는 보통 `Execute`(실행)와 `Undo`(되돌리기) 두 메서드를 가진 공통 인터페이스, 예를 들어 `ICommand`를 구현한다. 이렇게 하면 "무엇을 어떻게 실행할지"를 알고 있는 코드(리시버, Receiver)와 "언제 실행을 요청할지"를 아는 코드(인보커, Invoker)가 서로를 몰라도 되게 분리된다.

편집기 예제에 대응시켜 보면 다음과 같은 역할 구분이 생긴다.

- **Receiver(수신자)**: 실제 텍스트 조작 로직을 갖고 있는 `TextDocument` 클래스. "몇 번째 위치에 이런 텍스트를 넣어라" 같은 구체적인 작업을 실제로 수행한다.
- **Command(명령)**: `InsertTextCommand`, `DeleteTextCommand`처럼 "무엇을, 어디에" 실행할지 정보를 담고 `Execute`/`Undo`를 구현하는 객체. `Undo`는 `Execute`가 한 일을 정확히 반대로 되돌리는 로직을 담는다.
- **Invoker(호출자)**: 버튼, 메뉴, 매크로 실행기 등 "지금 이 명령을 실행해라"라고 지시만 하는 쪽. 명령이 구체적으로 무엇을 하는지는 알 필요가 없다.

명령을 객체로 만들어 두면 이 객체를 스택에 쌓아 Undo/Redo를 구현하거나, 큐에 넣어 순서대로 처리하거나, 여러 개를 묶어 매크로 명령으로 만드는 일이 모두 자연스러워진다. 명령이 "실행된 사실과 되돌리는 방법"까지 함께 들고 있기 때문이다. 이는 6장에서 다룬 빌더 패턴이 "객체를 어떻게 조립할지"를 캡슐화하는 것과 비슷한 방향으로, 커맨드 패턴은 "무엇을 실행할지"를 캡슐화한다고 볼 수 있다.

## C# 예제 코드

먼저 실제 작업을 수행하는 리시버, `TextDocument`를 정의한다.

```csharp
// 리시버: 실제 텍스트 조작을 담당한다
public class TextDocument
{
    private readonly StringBuilder _content = new StringBuilder();

    public string Content => _content.ToString();

    public void Insert(int position, string text)
    {
        _content.Insert(position, text);
    }

    public void Delete(int position, int length)
    {
        _content.Remove(position, length);
    }
}
```

명령 인터페이스와, 삽입/삭제 명령을 각각 구현한다. 각 명령은 되돌리기에 필요한 정보(어디에 무엇을 넣었는지, 어디서 무엇을 지웠는지)를 스스로 기억해 두어야 한다.

```csharp
public interface ICommand
{
    void Execute();
    void Undo();
}

// 텍스트 삽입 명령
public class InsertTextCommand : ICommand
{
    private readonly TextDocument _document;
    private readonly int _position;
    private readonly string _text;

    public InsertTextCommand(TextDocument document, int position, string text)
    {
        _document = document;
        _position = position;
        _text = text;
    }

    public void Execute()
    {
        _document.Insert(_position, _text);
    }

    public void Undo()
    {
        // 삽입한 만큼 다시 지우면 원상복구가 된다
        _document.Delete(_position, _text.Length);
    }
}

// 텍스트 삭제 명령
public class DeleteTextCommand : ICommand
{
    private readonly TextDocument _document;
    private readonly int _position;
    private readonly int _length;
    private string _deletedText; // 되돌리기 위해 지운 내용을 기억해 둔다

    public DeleteTextCommand(TextDocument document, int position, int length)
    {
        _document = document;
        _position = position;
        _length = length;
    }

    public void Execute()
    {
        _deletedText = _document.Content.Substring(_position, _length);
        _document.Delete(_position, _length);
    }

    public void Undo()
    {
        // 지웠던 내용을 그대로 다시 삽입한다
        _document.Insert(_position, _deletedText);
    }
}
```

여러 명령을 하나로 묶어 매크로처럼 실행하고 싶다면, `ICommand`를 구현하면서 내부에 명령 목록을 갖는 복합 명령을 만들 수 있다.

```csharp
// 여러 명령을 순서대로 실행/되돌리는 매크로 명령
public class MacroCommand : ICommand
{
    private readonly List<ICommand> _commands;

    public MacroCommand(IEnumerable<ICommand> commands)
    {
        _commands = commands.ToList();
    }

    public void Execute()
    {
        foreach (var command in _commands)
        {
            command.Execute();
        }
    }

    public void Undo()
    {
        // 실행한 순서와 반대로 되돌려야 한다
        for (int i = _commands.Count - 1; i >= 0; i--)
        {
            _commands[i].Undo();
        }
    }
}
```

이제 Undo 스택과 Redo 스택, 그리고 명령을 순서대로 처리하는 큐를 함께 관리하는 인보커, `EditorHistory`를 만든다.

```csharp
// 인보커: 명령의 실행/되돌리기/재실행을 관리한다
public class EditorHistory
{
    private readonly Stack<ICommand> _undoStack = new Stack<ICommand>();
    private readonly Stack<ICommand> _redoStack = new Stack<ICommand>();

    public void Execute(ICommand command)
    {
        command.Execute();
        _undoStack.Push(command);
        _redoStack.Clear(); // 새 명령을 실행하면 재실행 기록은 무효화된다
    }

    public void Undo()
    {
        if (_undoStack.Count == 0) return;

        var command = _undoStack.Pop();
        command.Undo();
        _redoStack.Push(command);
    }

    public void Redo()
    {
        if (_redoStack.Count == 0) return;

        var command = _redoStack.Pop();
        command.Execute();
        _undoStack.Push(command);
    }
}
```

전체를 사용하는 코드는 다음과 같다.

```csharp
var document = new TextDocument();
var history = new EditorHistory();

history.Execute(new InsertTextCommand(document, 0, "Hello, "));
history.Execute(new InsertTextCommand(document, 7, "World!"));
Console.WriteLine(document.Content); // Hello, World!

history.Undo();
Console.WriteLine(document.Content); // Hello,

history.Redo();
Console.WriteLine(document.Content); // Hello, World!

// 여러 명령을 매크로로 묶어 한 번에 실행/되돌리기
var macro = new MacroCommand(new ICommand[]
{
    new InsertTextCommand(document, document.Content.Length, " 좋은 아침입니다."),
    new DeleteTextCommand(document, 0, 7)
});
history.Execute(macro);
Console.WriteLine(document.Content);

history.Undo(); // 매크로 전체가 한 번에 되돌아간다
Console.WriteLine(document.Content);
```

인보커인 `EditorHistory`는 `InsertTextCommand`나 `DeleteTextCommand`가 내부적으로 무엇을 하는지 전혀 모른다. `ICommand`라는 인터페이스만 알고 있을 뿐이다. 덕분에 새로운 명령(예: `ReplaceTextCommand`, `ChangeFontCommand`)을 추가해도 `EditorHistory`는 코드를 한 줄도 고칠 필요가 없다.

명령을 즉시 실행하지 않고 큐에 쌓아 두었다가 순서대로 처리하고 싶다면, `Queue<ICommand>`에 명령을 쌓아 두고 별도의 처리 루프에서 `Dequeue` 후 `Execute`를 호출하는 방식으로 쉽게 확장할 수 있다. 명령이 이미 독립된 객체이기 때문에 "지금 실행"과 "나중에 실행"을 가르는 것은 그 객체를 어느 자료구조에 넣어 두느냐의 차이일 뿐이다.

## 언제 사용하는가

커맨드 패턴은 다음과 같은 상황에서 특히 유용하다.

- **실행 취소/다시 실행이 필요할 때**: 명령이 자기 자신을 되돌리는 방법을 알고 있으므로, Undo/Redo 스택을 명령 객체 리스트로 아주 단순하게 구현할 수 있다.
- **동작을 큐에 쌓아 처리해야 할 때**: 네트워크 요청, 배치 작업, 인쇄 작업처럼 "지금 요청됐지만 나중에 순서대로 처리해야 하는" 작업을 명령 객체로 만들어 큐에 넣으면 된다.
- **매크로나 복합 동작을 만들어야 할 때**: 여러 명령을 하나의 명령처럼 묶는 `MacroCommand`로 "저장 후 인쇄", "선택 영역 삭제 후 붙여넣기" 같은 복합 동작을 손쉽게 구성할 수 있다.
- **호출자와 실행자를 분리해야 할 때**: 리모컨의 버튼처럼, 버튼을 누르는 로직(Invoker)과 버튼이 눌렸을 때 실제로 일어나는 일(Receiver)을 분리하고 싶을 때. 같은 버튼에 나중에 다른 명령을 연결하는 것도 쉬워진다.
- **로깅이나 재현(replay)이 필요할 때**: 실행된 명령의 목록을 그대로 로그로 남겨 두면, 나중에 같은 명령들을 순서대로 다시 실행해 시스템 상태를 재현할 수 있다.

주의할 점은, 모든 동작을 커맨드 객체로 만들면 클래스 수가 급격히 늘어난다는 것이다. 되돌릴 필요가 없고 단순한 동작까지 굳이 `ICommand`로 감쌀 필요는 없다. 또한 `Undo`가 정확히 동작하려면 각 명령이 "되돌리기에 필요한 상태"를 실행 시점에 충실히 기록해 두어야 한다. 위 예제의 `DeleteTextCommand`가 지운 텍스트를 `_deletedText`에 저장해 두는 것처럼, 되돌리기 로직은 실행 로직과 짝을 맞춰 항상 함께 설계해야 한다. 커맨드 패턴은 15장의 체인 오브 리스판서빌리티와 함께 쓰이는 경우도 많은데, 예를 들어 명령을 큐에서 꺼내 처리할 때 "이 명령을 처리할 수 있는 핸들러를 사슬로 찾아가는" 구조를 결합할 수 있다.

## 요약

커맨드 패턴은 실행할 요청을 `Execute`/`Undo`를 가진 독립된 객체로 캡슐화하여, 요청을 보내는 호출자(Invoker)와 요청을 실제로 처리하는 수신자(Receiver)를 분리하는 패턴이다. 명령이 하나의 객체가 되면 이를 스택에 쌓아 Undo/Redo를 구현하거나, 큐에 넣어 순서대로 처리하거나, 여러 개를 묶어 매크로로 만드는 일이 모두 자연스러워진다. 다만 모든 동작을 명령 객체로 만들면 클래스 수가 늘어나므로, 실행 취소나 큐잉, 매크로 같은 요구가 실제로 있는 동작에 한해 적용하는 것이 합리적이다.

## 연습문제

1. 본문의 `TextDocument`에 "선택 영역의 서식을 바꾸는" 기능을 추가하고, 이를 되돌릴 수 있는 `ChangeFormatCommand`를 설계해 보라. 되돌리기 위해 어떤 상태를 실행 시점에 기억해 두어야 하는가?
2. `EditorHistory`의 `Execute` 메서드는 새 명령이 실행되면 `_redoStack`을 비운다. 이렇게 하지 않으면 어떤 문제가 생기는지 구체적인 시나리오로 설명해 보라.
3. 명령을 즉시 실행하지 않고 `Queue<ICommand>`에 쌓아 두었다가 별도의 스레드나 루프에서 순서대로 처리하는 "작업 큐" 구조를 코드로 구현해 보라.
4. 커맨드 패턴과 21장에서 다룰 옵저버 패턴은 둘 다 "발신자와 수신자를 분리한다"는 목표를 공유한다. 두 패턴이 이 목표를 달성하는 방식이 근본적으로 어떻게 다른지 설명해 보라.
5. 리모컨 애플리케이션을 가정하고, 버튼 하나에 연결된 명령을 실행 중에 다른 명령으로 교체할 수 있는 구조를 커맨드 패턴으로 설계해 보라. 버튼(Invoker)의 코드는 명령이 바뀌어도 수정할 필요가 없어야 한다.

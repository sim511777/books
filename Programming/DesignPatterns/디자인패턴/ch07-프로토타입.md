## 문제 상황

온라인 RPG 게임을 만들고 있다고 가정해 보자. 몬스터 하나를 생성하려면 이름, 종족, 레벨, 스탯(체력·공격력·방어력), 보유 스킬 목록, 드롭 아이템 테이블, AI 행동 패턴까지 십여 개의 값을 설정해야 한다. 게다가 스킬 목록은 `List<Skill>`이고 각 `Skill` 객체는 발동 조건과 애니메이션 정보를 담은 또 다른 객체를 참조한다. 즉 몬스터 하나를 "제대로" 만들려면 꽤 깊은 객체 그래프를 구성해야 한다.

기획팀에서 "오크 전사" 몬스터를 이미 완성해 놓았는데, 이제 "오크 전사(엘리트)"를 추가해야 한다고 하자. 차이는 체력이 1.5배, 공격력이 1.2배, 그리고 스킬 하나가 추가되는 것뿐이다. 그런데도 매번 `new Monster(...)`를 호출하며 생성자에 십여 개의 인자를 다시 채워 넣거나, 6장에서 다룬 빌더를 통해 처음부터 조립 과정을 다시 밟아야 한다면 비효율적이다. 이미 완성된 "오크 전사" 인스턴스가 메모리에 존재하는데, 그것을 거의 그대로 복사한 뒤 몇 가지 값만 바꾸는 것이 훨씬 자연스럽지 않을까?

문서 편집기를 만들 때도 비슷한 문제가 생긴다. 사용자가 공들여 만든 "표준 계약서 템플릿"을 기반으로 "2026년판 계약서"를 만들고 싶어 한다. 템플릿 객체 안에는 문단 스타일, 표, 머릿글/꼬릿글 설정이 촘촘히 들어 있는데, 이걸 처음부터 다시 코드로 조립하는 것은 배보다 배꼽이 더 크다. 필요한 것은 "이미 존재하는 객체를 복제해서 새 객체를 얻는" 방법이다.

## 패턴 설명

**프로토타입(Prototype) 패턴**은 새 객체를 클래스로부터 새로 생성하는 대신, 이미 존재하는 객체(프로토타입)를 **복제(clone)**해서 생성하는 패턴이다. 복제할 객체는 스스로 자신을 복제하는 방법을 알고 있어야 하므로, 보통 `Clone()`이라는 메서드를 인터페이스에 정의해 두고 각 클래스가 자기 자신의 복제 로직을 구현하도록 한다.

핵심 참여자는 세 가지다.

- **IPrototype**: 복제 메서드(`Clone()`)를 선언하는 인터페이스.
- **ConcretePrototype**: `IPrototype`을 구현하며, 자기 자신을 복제하는 구체적인 방법을 알고 있는 클래스. 몬스터, 문서 템플릿 등이 여기에 해당한다.
- **Client**: 새 객체가 필요할 때 `new`를 호출하지 않고, 기존 프로토타입 객체의 `Clone()`을 호출한다.

이 패턴의 가장 중요한 함정은 **얕은 복제(shallow copy)**와 **깊은 복제(deep copy)**의 차이를 정확히 이해하지 못하는 데서 발생한다. 얕은 복제는 객체의 필드 값을 그대로 복사하는데, 필드가 참조 타입(클래스, 리스트, 배열 등)이라면 그 참조 자체만 복사되어 원본과 복제본이 **같은 내부 객체를 공유**하게 된다. 복제본의 스킬 목록에 스킬을 추가했는데 원본의 스킬 목록도 함께 바뀌어 버리는 버그가 바로 이 문제다. 깊은 복제는 참조 타입 필드까지 재귀적으로 새로 복제하여, 원본과 복제본이 완전히 독립된 객체 그래프를 갖도록 한다.

C#에는 `System.ICloneable` 인터페이스가 기본으로 제공되지만, `Clone()`의 반환형이 `object`이고 얕은 복제와 깊은 복제 중 무엇을 구현했는지를 계약으로 보장하지 않는다는 단점이 있다. 그래서 실무에서는 `ICloneable`을 그대로 쓰기보다, 제네릭하고 의도가 분명한 자체 인터페이스(`IPrototype<T>` 같은)를 정의하는 경우가 많다. 이 장의 예제도 그 방식을 따른다.

## C# 예제 코드

먼저 얕은 복제와 깊은 복제의 차이를 명확히 보여주기 위해, 참조 타입 필드(스킬 목록)를 가진 몬스터 클래스를 만들어 보자.

```csharp
// 몬스터가 보유한 스킬 정보
public class Skill
{
    public string Name { get; set; }
    public int Cooldown { get; set; }

    public Skill(string name, int cooldown)
    {
        Name = name;
        Cooldown = cooldown;
    }

    // 스킬 자체도 값이 바뀔 수 있으므로 복제 시 새 인스턴스로 만든다
    public Skill DeepClone()
    {
        return new Skill(Name, Cooldown);
    }
}

// 복제 계약을 명확히 표현하는 자체 인터페이스
public interface IPrototype<T>
{
    T Clone();
}

public class Monster : IPrototype<Monster>
{
    public string Name { get; set; }
    public int Level { get; set; }
    public int Health { get; set; }
    public int Attack { get; set; }
    public List<Skill> Skills { get; set; } = new List<Skill>();

    // 얕은 복제: 참조 타입 필드는 참조만 복사된다
    public Monster ShallowClone()
    {
        return new Monster
        {
            Name = Name,
            Level = Level,
            Health = Health,
            Attack = Attack,
            Skills = Skills // 주의: 같은 리스트 인스턴스를 공유하게 된다
        };
    }

    // 깊은 복제: 리스트와 그 내부 요소까지 새로 만든다
    public Monster Clone()
    {
        var cloned = new Monster
        {
            Name = Name,
            Level = Level,
            Health = Health,
            Attack = Attack,
            Skills = new List<Skill>()
        };

        foreach (var skill in Skills)
        {
            cloned.Skills.Add(skill.DeepClone());
        }

        return cloned;
    }
}
```

얕은 복제와 깊은 복제의 차이는 실제로 실행해 보면 바로 드러난다.

```csharp
var orcWarrior = new Monster
{
    Name = "오크 전사",
    Level = 10,
    Health = 500,
    Attack = 80
};
orcWarrior.Skills.Add(new Skill("도끼 휘두르기", 3));

// 얕은 복제 - 스킬 리스트를 공유한다
var shallowCopy = orcWarrior.ShallowClone();
shallowCopy.Skills.Add(new Skill("분노", 10));
Console.WriteLine(orcWarrior.Skills.Count); // 2 - 원본까지 오염됨!

// 깊은 복제 - 스킬 리스트가 독립적이다
var eliteOrc = orcWarrior.Clone();
eliteOrc.Name = "오크 전사(엘리트)";
eliteOrc.Health = (int)(orcWarrior.Health * 1.5);
eliteOrc.Attack = (int)(orcWarrior.Attack * 1.2);
eliteOrc.Skills.Add(new Skill("광폭화", 15));
Console.WriteLine(orcWarrior.Skills.Count); // 1 - 원본은 그대로다
```

`ShallowClone()`에서 `eliteOrc`가 스킬을 추가하면 원본인 `orcWarrior`의 스킬 목록까지 바뀌어 버린다. 두 몬스터가 리스트 인스턴스를 공유하고 있기 때문이다. 반면 `Clone()`으로 만든 `eliteOrc`는 완전히 독립된 스킬 리스트를 가지므로 안전하게 값을 바꿀 수 있다. 실무에서는 값 타입(문자열, 숫자, 열거형)만 가진 단순한 클래스라면 얕은 복제로도 충분하지만, 리스트나 다른 클래스 인스턴스를 참조하는 필드가 있다면 반드시 깊은 복제를 고려해야 한다.

몬스터를 미리 등록해 두고 이름으로 꺼내 복제하는 저장소(레지스트리)를 두면 더 편리하다.

```csharp
public class MonsterRegistry
{
    private readonly Dictionary<string, Monster> _prototypes = new();

    public void Register(string key, Monster prototype)
    {
        _prototypes[key] = prototype;
    }

    public Monster Create(string key)
    {
        if (!_prototypes.TryGetValue(key, out var prototype))
            throw new ArgumentException($"등록되지 않은 프로토타입: {key}");

        return prototype.Clone(); // 항상 깊은 복제본을 반환한다
    }
}
```

```csharp
var registry = new MonsterRegistry();
registry.Register("orc_warrior", orcWarrior);

var newOrc1 = registry.Create("orc_warrior");
var newOrc2 = registry.Create("orc_warrior");
// newOrc1과 newOrc2는 서로 완전히 독립된 객체다
```

이렇게 하면 클라이언트 코드는 몬스터를 만들 때 생성자의 세부 인자를 전혀 알 필요가 없다. "orc_warrior" 라는 키만 알면 완성된 몬스터를 얻는다.

## 언제 사용하는가

- 객체를 초기 상태로 만드는 과정이 복잡하거나 비용이 크고(예: 파일 로딩, DB 조회 등을 거쳐 완성된 객체), 비슷한 객체를 반복해서 만들어야 할 때
- 클래스를 몰라도(구체 타입을 몰라도) 객체를 복제해서 새 인스턴스를 얻고 싶을 때 — 클라이언트는 `IPrototype`만 알면 된다
- 런타임에 결정된 객체 상태를 기준으로 변형본을 여러 개 만들어야 할 때(게임의 몬스터 변형, 문서의 버전 관리 등)
- 서브클래스를 늘리지 않고도 객체의 "종류"를 늘리고 싶을 때 — 새 프로토타입 인스턴스를 등록하는 것만으로 새로운 변형이 추가된다

6장에서 다룬 **빌더(Builder)** 패턴과 자주 비교된다. 빌더는 부품을 하나씩 조립해서 **처음부터** 객체를 완성하는 데 초점이 있고, 프로토타입은 **이미 완성된 객체를 복제**해서 약간의 수정만 가하는 데 초점이 있다. 오히려 두 패턴은 함께 쓰이기도 한다. 빌더로 정교하게 만든 "기본형" 객체 몇 가지를 프로토타입으로 등록해 두고, 이후에는 매번 복제해서 재사용하는 방식이다. 즉 초기 구축은 빌더가, 대량 생산과 변형은 프로토타입이 담당하는 조합이다.

## 요약

프로토타입 패턴은 객체 생성 비용이 크거나 구성이 복잡할 때, 기존 인스턴스를 복제해서 새 인스턴스를 만드는 생성 패턴이다. C#에서는 `Clone()` 메서드를 직접 정의하는 방식이 표준 `ICloneable`보다 의도를 명확히 드러낸다. 복제를 구현할 때는 참조 타입 필드를 그대로 복사하는 얕은 복제와, 참조 타입 필드까지 재귀적으로 새로 만드는 깊은 복제를 구분해야 하며, 둘을 혼동하면 원본과 복제본이 상태를 공유하는 버그로 이어진다. 프로토타입은 처음부터 조립하는 빌더와 대조되는, "복제를 통한 생성"이라는 또 하나의 생성 전략을 제공한다.

## 연습문제

1. `ICloneable.Clone()`이 반환형을 `object`로 선언하고 있는 것이 왜 실무에서 불편함을 초래할 수 있는지 설명하라. 이 장에서 `IPrototype<T>`를 자체적으로 정의한 이유와 연결해서 답하라.
2. 문서 템플릿 클래스 `DocumentTemplate`가 `Header`, `Footer`(둘 다 참조 타입), `PageCount`(값 타입) 필드를 가지고 있다고 하자. 얕은 복제만 구현했을 때 어떤 버그가 발생할 수 있는지 구체적인 시나리오로 서술하라.
3. `Monster` 클래스에 `Dictionary<string, int> DropTable`(아이템 이름과 드롭률)이라는 필드를 추가한다고 하면, `Clone()` 메서드를 어떻게 수정해야 깊은 복제가 유지되는지 코드로 작성하라.
4. 프로토타입 패턴과 빌더 패턴을 함께 사용하는 예시를 하나 설계해 보라. 어떤 부분을 빌더로 만들고, 어떤 부분을 프로토타입으로 복제할 것인지 근거를 들어 설명하라.
5. `MonsterRegistry`에 몬스터를 등록할 때 원본 객체를 그대로 저장하는 대신 복제본을 저장하도록 바꾼다면 어떤 이점이 있을지 생각해 보라.

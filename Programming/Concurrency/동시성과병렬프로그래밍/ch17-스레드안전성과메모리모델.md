지금까지 이 책은 `lock`, `Monitor`, `SemaphoreSlim`, `ConcurrentDictionary<TKey, TValue>` 같은 구체적인 도구를 중심으로 여러 스레드가 공유 데이터를 안전하게 다루는 방법을 살펴봤습니다. 이 장에서는 한 걸음 더 내려가서, 왜 애초에 그런 도구들이 필요한지를 CPU와 컴파일러 수준에서 이해해봅니다. 그리고 지금까지 배운 "락으로 막는" 접근 외에, 원자적 연산과 불변성이라는 두 가지 다른 전략도 함께 정리합니다.

이 장을 마치고 나면 스레드 안전성을 확보하는 세 가지 근본적인 전략, 즉 **동기화(락)**, **원자적 연산**, **불변성**을 상황에 맞게 골라 쓸 수 있게 됩니다.

## 왜 값이 "보이지 않는" 일이 생기는가

한 스레드가 어떤 변수에 값을 써도, 다른 스레드가 그 값을 즉시 보게 된다는 보장은 사실 당연한 것이 아닙니다. 이유는 두 군데에 있습니다.

첫째, **컴파일러와 JIT 컴파일러의 최적화**입니다. 컴파일러는 프로그램의 겉으로 드러나는 동작(단일 스레드 관점에서의 결과)만 보존하면 되기 때문에, 반복문 안에서 매번 메모리를 다시 읽지 않고 레지스터에 값을 캐싱해서 재사용하도록 코드를 바꿀 수 있습니다. 단일 스레드에서는 이 최적화가 결과에 아무 영향을 주지 않지만, 다른 스레드가 그 변수를 바꿔주기를 기다리는 코드라면 이야기가 달라집니다. 레지스터에 캐싱된 값만 계속 확인하고 있다면 실제 메모리가 바뀌어도 영원히 눈치채지 못할 수 있습니다.

둘째, **CPU 캐시와 명령어 재배치**입니다. 현대 CPU는 각 코어마다 별도의 캐시를 두고 있고, 코어 하나가 메모리에 값을 쓰더라도 그 값이 다른 코어의 캐시나 메인 메모리에 즉시 반영된다는 보장이 없습니다. 또한 CPU와 컴파일러는 프로그램의 최종 결과가 같다면 명령어의 실행 순서를 바꿀 수 있는 재량을 갖고 있습니다. 코드에 A를 실행한 다음 B를 실행하도록 적어놓아도, 실제로는 B가 먼저 실행될 수 있다는 뜻입니다. 단일 스레드 안에서는 이런 재배치가 절대 관찰되지 않지만, 여러 스레드가 같은 데이터를 공유하는 순간 재배치의 흔적이 겉으로 드러날 수 있습니다.

이런 문제들을 다루기 위해 .NET은 **메모리 모델**이라는 규칙 집합을 정의합니다. 메모리 모델은 "어떤 스레드가 쓴 값을 다른 스레드가 언제 볼 수 있는지", "명령어 재배치가 어디까지 허용되는지"를 규정합니다. 이 장에서 다루는 `volatile`, `Interlocked`, 메모리 배리어는 모두 이 메모리 모델 위에서 "특정 값만큼은 확실하게 최신 상태로 보이도록" 보장해주는 도구들입니다.

## volatile 키워드

`volatile` 키워드를 필드에 붙이면, 컴파일러와 CPU에게 "이 필드는 여러 스레드가 접근할 수 있으니 레지스터에 캐싱하지 말고, 읽고 쓰는 순서를 함부로 재배치하지 말라"고 지시하는 효과를 냅니다. 구체적으로는 다음 두 가지를 보장합니다.

- **읽기(read)**: `volatile` 필드를 읽을 때는 항상 메인 메모리(또는 그에 준하는 최신 상태)에서 값을 가져옵니다. 이전에 캐싱해둔 값을 재사용하지 않습니다.
- **쓰기(write)**: `volatile` 필드에 값을 쓰면 그 즉시 다른 스레드에서도 관찰할 수 있는 시점에 메모리에 반영됩니다.

가장 전형적인 사용 예는 백그라운드에서 반복적으로 작업을 수행하는 루프를 다른 스레드에서 멈추도록 신호를 보내는 플래그입니다.

```csharp
public class BackgroundWorker
{
    // 여러 스레드가 읽고 쓰므로 volatile로 선언한다
    private volatile bool _shouldStop;

    public void Run()
    {
        while (!_shouldStop)
        {
            DoUnitOfWork();
        }

        Console.WriteLine("작업 루프를 종료합니다.");
    }

    public void RequestStop()
    {
        _shouldStop = true;
    }

    private void DoUnitOfWork()
    {
        // 실제 작업 내용
    }
}
```

만약 `_shouldStop`이 `volatile`이 아니었다면, 최적화 컴파일러는 `while (!_shouldStop)` 검사를 "한 번만 메모리에서 읽고 그 결과를 계속 재사용해도 되는 검사"로 착각할 여지가 있습니다. 그렇게 되면 `RequestStop()`을 다른 스레드에서 아무리 호출해도 루프를 도는 스레드는 그 변경을 영원히 보지 못하고 무한 루프에 빠질 수 있습니다. `volatile`을 붙이면 매 반복마다 실제 메모리 값을 확인하도록 강제되므로 이런 문제가 사라집니다.

다만 `volatile`에는 분명한 한계가 있습니다. `volatile`은 **하나의 읽기 또는 하나의 쓰기가 항상 최신 값을 보장한다**는 뜻이지, **여러 단계로 이루어진 연산 전체를 원자적으로 만들어주지는 않습니다.** 예를 들어 다음 코드는 여전히 안전하지 않습니다.

```csharp
private volatile int _counter;

public void Increment()
{
    _counter++; // 위험: 읽기 -> 더하기 -> 쓰기, 세 단계가 원자적이지 않다
}
```

`_counter++`은 실제로는 "현재 값을 읽고, 1을 더하고, 그 결과를 다시 쓰는" 세 단계로 이루어집니다. `volatile`은 각 단계에서 최신 값을 읽고 즉시 반영한다는 것만 보장할 뿐, 세 단계 사이에 다른 스레드가 끼어들지 못하게 막아주지는 않습니다. 두 스레드가 동시에 `Increment()`를 호출하면 3장에서 다룬 경쟁 상태가 그대로 재현되어 증가분 하나가 사라질 수 있습니다. 즉 `volatile`은 "가시성(visibility)" 문제를 해결하는 도구이지, "원자성(atomicity)" 문제를 해결하는 도구가 아닙니다. 단순 증가/감소처럼 읽기-수정-쓰기가 필요한 연산에는 다음 절에서 다루는 `Interlocked`나 `lock`이 필요합니다.

> **참고**: `Volatile.Read(ref field)`와 `Volatile.Write(ref field, value)` 정적 메서드도 `volatile` 필드와 동일한 가시성 보장을 제공합니다. 필드 선언에 `volatile` 키워드를 붙일 수 없는 상황(예: 참조로 전달된 지역 변수)에서 같은 효과가 필요할 때 사용합니다.

## Interlocked 클래스: 가벼운 원자적 연산

`System.Threading.Interlocked` 클래스는 정수나 참조 값에 대해 "읽고, 계산하고, 쓰는" 일련의 과정을 CPU가 지원하는 단일 원자적 명령어로 처리해주는 정적 메서드 모음입니다. 락을 잡을 필요 없이 아주 짧고 단순한 연산 하나만 원자적으로 보호하면 되는 경우에 사용합니다.

### Increment, Decrement, Add

```csharp
public class RequestCounter
{
    private int _count;

    public void RecordRequest()
    {
        Interlocked.Increment(ref _count);
    }

    public void RecordCompletion()
    {
        Interlocked.Decrement(ref _count);
    }

    public int Current => Interlocked.CompareExchange(ref _count, 0, 0); // 현재 값을 안전하게 읽기
}
```

`Interlocked.Increment(ref _count)`는 `_count`를 읽고 1을 더한 뒤 다시 쓰는 과정을 하나의 원자적 단계로 실행합니다. 두 스레드가 동시에 호출해도 두 번의 증가가 모두 정확히 반영되며, 앞서 살펴본 `_counter++`의 경쟁 상태 문제가 사라집니다. `Interlocked.Add(ref location, value)`를 사용하면 1이 아닌 임의의 값을 원자적으로 더할 수도 있습니다.

### CompareExchange

`Interlocked.CompareExchange(ref location, newValue, comparand)`는 "`location`의 현재 값이 `comparand`와 같을 때만 `newValue`로 교체하고, 교체 직전의 원래 값을 반환한다"는 동작을 원자적으로 수행합니다. 이른바 CAS(Compare-And-Swap) 연산으로, 락을 전혀 사용하지 않고도 조건부 갱신을 안전하게 구현할 수 있는 강력한 도구입니다.

```csharp
public class LockFreeMaxTracker
{
    private int _max;

    public void Observe(int value)
    {
        int initial;
        do
        {
            initial = _max;
            if (value <= initial)
            {
                return; // 이미 더 큰 값이 기록되어 있으면 할 일이 없다
            }
        }
        // _max가 여전히 initial이면 value로 교체하고, 교체 성공 여부를 반환값으로 확인한다
        while (Interlocked.CompareExchange(ref _max, value, initial) != initial);
    }

    public int Max => _max;
}
```

이 패턴은 "값을 읽고 -> 새 값을 계산하고 -> 그 사이에 아무도 값을 바꾸지 않았을 때만 반영하고, 바뀌었다면 처음부터 다시 시도한다"는 재시도 루프입니다. `lock`을 쓰지 않고도 여러 스레드가 안전하게 최댓값을 갱신할 수 있습니다. 다만 경합이 아주 심한 상황에서는 재시도가 계속 실패해 반복될 수 있으므로, 연산 자체가 짧고 저렴할 때 적합한 기법입니다.

### lock보다 가벼운 대안이 되는 경우

`lock`(내부적으로는 `Monitor.Enter`/`Monitor.Exit`)은 스레드가 잠금을 얻지 못하면 대기 큐에 들어가고, 상황에 따라 커널 수준의 대기 상태로 전환될 수 있는 범용 동기화 메커니즘입니다. 반면 `Interlocked`는 CPU가 하드웨어 차원에서 지원하는 단일 명령어(예: x86/x64의 `LOCK` 접두사가 붙은 명령어)를 사용하므로 커널 모드 전환이나 대기 큐 관리 같은 부가 비용이 없습니다.

따라서 다음과 같은 조건을 모두 만족할 때는 `lock` 대신 `Interlocked`를 사용하는 것이 유리합니다.

- 보호해야 할 연산이 단일 필드에 대한 증가/감소, 교환, 조건부 교체처럼 매우 단순한 경우
- 여러 필드를 함께 일관된 상태로 유지해야 하는 것이 아니라, 딱 하나의 값만 원자적으로 다루면 되는 경우
- 통계 카운터, 참조 교체, 플래그 갱신처럼 호출 빈도가 매우 높아 락의 오버헤드가 누적되어 병목이 될 수 있는 경우

반대로 "여러 필드를 동시에 일관되게 갱신해야 한다"거나 "조건을 검사하고 나서 여러 줄에 걸쳐 상태를 바꿔야 한다"면 `Interlocked`만으로는 부족하고 `lock`이 필요합니다. `Interlocked`는 어디까지나 단일 값에 대한 원자성만 제공한다는 점을 기억해야 합니다.

## 메모리 배리어라는 개념

앞서 "CPU와 컴파일러가 명령어의 실행 순서를 재배치할 수 있다"고 설명했습니다. **메모리 배리어(memory barrier)**는 이런 재배치에 울타리를 치는 지점입니다. 메모리 배리어를 지나는 코드는 그 앞뒤로 명령어가 넘나들며 재배치되지 않도록 보장받습니다.

`lock`, `Interlocked`의 각 메서드, `volatile` 필드에 대한 읽기/쓰기는 모두 내부적으로 이런 메모리 배리어 역할을 겸하고 있습니다. 즉 이 장에서 다룬 도구들을 사용하면 "값이 최신으로 보인다"는 결과뿐 아니라 "이 지점을 기준으로 앞뒤 코드의 순서가 뒤섞이지 않는다"는 효과까지 함께 얻게 됩니다. .NET은 `Thread.MemoryBarrier()`라는 메서드로 이를 명시적으로 호출할 수도 있게 해두었지만, 실무 코드에서 이 메서드를 직접 호출하는 일은 거의 없습니다. 대부분의 경우 `lock`이나 `Interlocked`, `volatile`을 올바르게 사용하는 것만으로 필요한 메모리 배리어가 자동으로 확보되기 때문입니다.

이 절의 요점은 딱 하나입니다. **동시성 버그의 상당수는 "코드에 적힌 순서대로 메모리에 값이 반영될 것"이라는 무의식적인 가정에서 비롯됩니다.** 그 가정이 항상 성립하지는 않는다는 사실을 이해하고 있으면, 왜 공유 데이터를 다룰 때 반드시 검증된 동기화 도구를 거쳐야 하는지 훨씬 명확하게 납득할 수 있습니다.

## 불변 객체를 이용한 스레드 안전성

지금까지 살펴본 락과 원자적 연산은 모두 "데이터가 바뀔 수 있다"는 전제 위에서, 그 변경을 안전하게 조율하는 방법이었습니다. 하지만 더 근본적인 접근이 하나 더 있습니다. **애초에 공유되는 데이터를 변경 불가능하게 만들면, 여러 스레드가 동시에 읽어도 경쟁 상태 자체가 발생할 수 없습니다.** 값이 절대 바뀌지 않는다면 "읽는 도중에 다른 스레드가 값을 바꿔서 일관성이 깨지는" 상황이 원천적으로 성립하지 않기 때문입니다.

C#은 `record`와 `init` 접근자를 통해 불변 객체를 매우 간결하게 표현할 수 있습니다.

```csharp
public record OrderSnapshot
{
    public string OrderId { get; init; } = string.Empty;
    public decimal TotalAmount { get; init; }
    public OrderStatus Status { get; init; }
}

public enum OrderStatus
{
    Pending,
    Shipped,
    Delivered
}
```

`init` 접근자로 선언된 속성은 객체를 생성하는 시점(생성자 호출 또는 객체 초기화 구문)에서만 값을 설정할 수 있고, 그 이후에는 절대 변경할 수 없습니다. 여러 스레드가 같은 `OrderSnapshot` 인스턴스에 대한 참조를 나눠 갖고 있더라도, 그 인스턴스의 속성값을 읽는 동작은 항상 안전합니다. 어떤 스레드도 그 값을 바꿀 방법이 없기 때문입니다.

상태가 바뀌어야 하는 상황이라면, 기존 인스턴스를 변경하는 대신 변경된 내용을 반영한 **새로운 인스턴스**를 만들어서 교체합니다. `record`가 제공하는 `with` 표현식을 사용하면 이 작업을 간결하게 표현할 수 있습니다.

```csharp
public class OrderStatusPublisher
{
    // 참조 자체를 교체하는 것은 원자적이므로 volatile로 최신 참조를 읽도록 보장한다
    private volatile OrderSnapshot _current;

    public OrderStatusPublisher(OrderSnapshot initial)
    {
        _current = initial;
    }

    public OrderSnapshot Current => _current;

    public void MarkShipped()
    {
        OrderSnapshot updated = _current with { Status = OrderStatus.Shipped };
        _current = updated; // 기존 스냅샷은 그대로 두고, 새 스냅샷으로 참조만 교체한다
    }
}
```

`_current with { Status = OrderStatus.Shipped }`는 기존 `OrderSnapshot`의 다른 모든 속성값은 그대로 복사하면서 `Status`만 바꾼 새 인스턴스를 만들어냅니다. 이때 어떤 스레드가 `Current`를 통해 읽어가는 값은 항상 어느 한 시점에 완전히 만들어져 있던 `OrderSnapshot` 인스턴스이지, 절반만 갱신된 값을 읽을 위험이 없습니다. 참조 필드 자체를 원자적으로 교체하는 부분(`_current = updated`)만 가시성을 신경 써주면 되므로 `volatile`을 붙이는 것으로 충분하고, 별도의 `lock`은 필요 없습니다.

이 전략은 특히 "값을 자주 읽지만 갱신은 상대적으로 드문" 상황, 예를 들어 설정 정보나 캐시된 스냅샷, 여러 스레드가 참조하는 상태 객체 등에 잘 들어맞습니다. 반면 여러 스레드가 매우 빈번하게 갱신을 시도하는 상황에서는 매번 새 인스턴스를 할당하는 비용이 부담이 될 수 있으므로, 이런 경우에는 `lock`이나 `Interlocked`, 혹은 14장에서 다룬 동시성 컬렉션이 더 적합할 수 있습니다.

## 스레드 안전성을 확보하는 세 가지 전략

이 장과 앞선 여러 장에서 다룬 내용을 종합하면, 공유 데이터를 스레드 안전하게 만드는 방법은 결국 다음 세 가지 전략으로 압축됩니다.

| 전략 | 핵심 아이디어 | 대표 도구 | 적합한 상황 |
|---|---|---|---|
| 동기화(락) | 한 번에 하나의 스레드만 임계 구역에 들어가도록 강제한다 | `lock`, `Monitor`, `SemaphoreSlim` | 여러 필드를 함께 일관되게 갱신해야 하는 복잡한 로직 |
| 원자적 연산 | CPU가 지원하는 단일 명령어로 읽기-수정-쓰기를 쪼갤 수 없게 만든다 | `Interlocked` | 카운터, 플래그, 단일 참조 교체처럼 극도로 단순한 연산 |
| 불변성 | 데이터를 아예 바꿀 수 없게 만들어 동기화 자체를 불필요하게 만든다 | `record`, `init`, `with` 표현식 | 갱신보다 읽기가 훨씬 잦은 공유 상태, 값 자체를 통째로 교체하는 모델 |

세 전략은 서로 배타적이지 않고 함께 쓰이는 경우가 많습니다. 예를 들어 앞의 `OrderStatusPublisher` 예제는 불변성과 원자적 연산(참조 교체의 가시성 확보)을 함께 사용하고 있습니다. 실무에서 좋은 설계는 대개 "가능하면 불변성으로 문제 자체를 없애고, 단순한 값 하나만 남았다면 원자적 연산으로 처리하고, 그래도 남는 복잡한 상호작용에만 락을 사용한다"는 순서로 접근합니다. 락은 강력하지만 범위를 넓게 잡을수록 동시성을 갉아먹기 때문에, 세 전략 중 더 가벼운 것으로 대체할 수 있는지 항상 먼저 검토할 가치가 있습니다.

## 요약

- .NET의 메모리 모델은 컴파일러/CPU의 최적화와 캐싱으로 인해 한 스레드가 쓴 값이 다른 스레드에 언제 보이는지, 명령어 순서가 어디까지 재배치될 수 있는지를 규정합니다.
- `volatile`은 필드에 대한 읽기/쓰기가 항상 최신 메모리 값을 반영하도록 보장하는 가시성 도구이지만, 읽기-수정-쓰기로 이루어진 복합 연산의 원자성까지 보장하지는 않습니다.
- `Interlocked.Increment`/`Decrement`/`Add`/`CompareExchange`는 단일 값에 대한 연산을 CPU의 원자적 명령어로 처리해, 커널 모드 전환 없이 `lock`보다 가벼운 동기화를 제공합니다. 조건이 검사와 함께 여러 필드를 다뤄야 한다면 `Interlocked`만으로는 부족합니다.
- 메모리 배리어는 명령어 재배치에 울타리를 치는 지점이며, `lock`/`Interlocked`/`volatile`을 올바르게 쓰면 필요한 배리어가 대부분 자동으로 확보됩니다.
- `record`와 `init` 접근자로 불변 객체를 만들면 데이터 자체가 바뀌지 않으므로 동기화가 필요 없어집니다. 상태 변경은 `with` 표현식으로 새 인스턴스를 만들고 참조를 교체하는 방식으로 처리합니다.
- 스레드 안전성은 동기화(락), 원자적 연산, 불변성이라는 세 가지 전략으로 확보할 수 있으며, 가벼운 전략으로 대체할 수 있는지 먼저 검토하는 습관이 더 확장성 있는 동시성 코드로 이어집니다.

## 연습문제

1. `volatile bool _shouldStop` 플래그 예제에서, `volatile`을 제거하면 어떤 상황에서 어떤 문제가 발생할 수 있는지 컴파일러 최적화 관점에서 설명하세요.
2. `_counter++`가 `volatile int` 필드에 대해서도 여전히 안전하지 않은 이유를 "가시성"과 "원자성"이라는 두 개념을 구분하여 설명하세요.
3. `Interlocked.CompareExchange`를 이용해, 어떤 정수 필드의 값을 "현재 값이 짝수일 때만 2를 곱하는" 연산을 락 없이 원자적으로 구현해보세요.
4. 여러 스레드가 자주 읽고 가끔씩만 갱신하는 설정 객체가 있다고 할 때, 이를 `record`와 `init`, `with` 표현식으로 불변하게 설계하는 것과 `lock`으로 가변 객체를 보호하는 것을 비교하여 각각의 장단점을 서술하세요.
5. 동기화(락), 원자적 연산, 불변성 세 가지 전략 중 두 가지 이상을 함께 사용해야 하는 상황을 하나 떠올려보고, 왜 하나의 전략만으로는 충분하지 않은지 설명하세요.

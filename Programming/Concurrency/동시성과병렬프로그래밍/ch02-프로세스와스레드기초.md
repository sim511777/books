# 2장. 프로세스와 스레드 기초

[◀ 이전: 1장. 동시성과 병렬성이란 무엇인가](ch01-동시성과병렬성이란무엇인가.md) | [📖 목차](00-목차.md) | [다음: 3장. 스레드 동기화 기초 ▶](ch03-스레드동기화기초.md)


1장에서 동시성과 병렬성의 개념을 살펴보았다면, 이 장에서는 그것을 실제로 구현하는 가장 기본적인 단위인 **스레드**를 다룹니다. .NET에서 제공하는 `Task`나 `async`/`await` 같은 고수준 도구들도 결국 내부적으로는 운영체제 스레드 위에서 동작합니다. 따라서 스레드가 무엇이고 어떻게 만들고 다루는지를 먼저 몸에 익혀두면, 이후 장에서 배울 추상화들이 왜 그런 식으로 설계되었는지 훨씬 잘 이해할 수 있습니다.

## 프로세스와 스레드의 관계

**프로세스(Process)**는 실행 중인 프로그램의 인스턴스입니다. 운영체제는 프로세스를 실행할 때 그 프로세스만을 위한 독립된 메모리 공간(주소 공간)을 할당합니다. 메모장을 두 개 띄우면 두 개의 별도 프로세스가 실행되고, 한 프로세스의 메모리는 다른 프로세스가 직접 들여다볼 수 없습니다. 프로세스끼리 데이터를 주고받으려면 파일, 파이프, 소켓, 공유 메모리 같은 별도의 프로세스 간 통신(IPC) 수단이 필요합니다.

**스레드(Thread)**는 하나의 프로세스 안에서 실제로 코드를 실행하는 흐름의 단위입니다. 하나의 프로세스는 하나 이상의 스레드를 가질 수 있으며, **같은 프로세스에 속한 스레드들은 그 프로세스의 메모리 공간(힙, 정적 필드 등)을 서로 공유**합니다. 반면 각 스레드는 자신만의 호출 스택(call stack)과 레지스터 상태, 그리고 프로그램 카운터(현재 실행 중인 명령의 위치)를 독립적으로 가집니다.

이 차이는 매우 중요한 결과를 낳습니다. 프로세스 간에는 메모리가 격리되어 있어 한 프로세스의 오류가 다른 프로세스에 직접 영향을 주기 어렵지만, 같은 프로세스 안의 스레드들은 메모리를 공유하기 때문에 한 스레드가 실수로 공유 데이터를 잘못 건드리면 다른 스레드가 그 여파를 고스란히 받습니다. 이것이 바로 스레드 동기화가 필요한 근본적인 이유이며, 3장부터 본격적으로 다룰 주제입니다.

.NET 애플리케이션이 시작되면 운영체제는 해당 프로세스를 위한 **메인 스레드** 하나를 자동으로 만들어 `Main` 메서드를 실행합니다. 개발자가 별도로 스레드를 만들지 않는 한, 콘솔 애플리케이션의 모든 코드는 이 메인 스레드 하나에서 순차적으로 실행됩니다.

```csharp
using System;
using System.Threading;

Console.WriteLine($"메인 스레드 ID: {Environment.CurrentManagedThreadId}");
Console.WriteLine($"프로세스 ID: {Environment.ProcessId}");
```

## Thread 클래스로 스레드 생성하기

.NET에서 운영체제 스레드를 직접 다루는 API는 `System.Threading.Thread` 클래스입니다. 새 스레드를 만들려면 그 스레드가 실행할 코드를 나타내는 델리게이트를 `Thread` 생성자에 전달합니다.

```csharp
using System;
using System.Threading;

Thread worker = new Thread(PrintNumbers);
worker.Start();   // 새 스레드에서 PrintNumbers 실행 시작
worker.Join();    // worker 스레드가 끝날 때까지 현재 스레드를 대기시킴

Console.WriteLine("작업이 모두 끝났습니다.");

static void PrintNumbers()
{
    for (int i = 1; i <= 5; i++)
    {
        Console.WriteLine($"[{Environment.CurrentManagedThreadId}] 숫자: {i}");
    }
}
```

`new Thread(...)`는 스레드 객체를 생성할 뿐, 이 시점에는 아직 실제 운영체제 스레드가 만들어지지 않습니다. `Start()` 메서드를 호출해야 비로소 새 스레드가 시작되고 지정한 메서드가 그 스레드 위에서 실행됩니다. `Join()`은 호출한 스레드(위 예제에서는 메인 스레드)를 멈추고, 대상 스레드(`worker`)가 실행을 마칠 때까지 기다립니다. `Join()`을 호출하지 않으면 메인 스레드가 `worker` 스레드보다 먼저 끝나버릴 수도 있고, 콘솔 애플리케이션이라면 메인 스레드가 종료되는 순간 프로세스 전체가 끝나면서 `worker`가 작업을 채 마치기 전에 프로그램이 종료될 수 있습니다.

`Join()`에는 최대 대기 시간을 지정하는 오버로드도 있습니다.

```csharp
bool finished = worker.Join(TimeSpan.FromSeconds(3));
if (!finished)
{
    Console.WriteLine("3초 안에 끝나지 않았습니다.");
}
```

## 스레드에 매개변수 전달하기

`Thread` 생성자는 매개변수가 없는 `ThreadStart` 델리게이트뿐 아니라, `object?` 타입의 매개변수 하나를 받는 `ParameterizedThreadStart` 델리게이트도 지원합니다.

```csharp
using System;
using System.Threading;

Thread worker = new Thread(PrintMessage);
worker.Start("안녕하세요, 스레드!");
worker.Join();

static void PrintMessage(object? state)
{
    string message = (string)state!;
    Console.WriteLine($"[{Environment.CurrentManagedThreadId}] {message}");
}
```

`ParameterizedThreadStart`는 매개변수 타입이 `object?`로 고정되어 있어 사용할 때마다 캐스팅이 필요하고 타입 안전성이 떨어집니다. C#의 람다식과 클로저(closure)를 이용하면 이런 제약 없이 원하는 타입의 값을 자연스럽게 캡처해서 넘길 수 있습니다.

```csharp
using System;
using System.Threading;

void RunWorker(int workerId, string taskName)
{
    // 람다가 workerId와 taskName을 캡처한다
    Thread worker = new Thread(() =>
    {
        Console.WriteLine($"[{Environment.CurrentManagedThreadId}] 작업자 {workerId}가 '{taskName}'을(를) 시작합니다.");
    });
    worker.Start();
    worker.Join();
}

RunWorker(1, "데이터 정리");
```

다만 람다로 변수를 캡처할 때는 반복문 안에서 반복 변수를 그대로 캡처하지 않도록 주의해야 합니다. C# 5 이후로 `foreach`의 반복 변수는 매 반복마다 새로 선언되므로 아래 코드는 의도한 대로 동작하지만, 이 동작을 당연하게 여기기보다는 캡처되는 변수가 무엇인지 항상 의식하는 습관을 들이는 편이 안전합니다. 클로저와 관련된 미묘한 함정은 9장과 10장에서 `async`/`await`와 함께 다시 다룹니다.

```csharp
foreach (int id in new[] { 1, 2, 3 })
{
    Thread t = new Thread(() => Console.WriteLine($"작업자 {id} 실행"));
    t.Start();
}
```

## 스레드의 생명주기

스레드는 대략 다음과 같은 상태를 거칩니다.

1. **생성(Unstarted)**: `new Thread(...)`로 객체는 만들어졌지만 아직 `Start()`를 호출하지 않은 상태입니다.
2. **실행 가능/실행 중(Running)**: `Start()` 호출 이후 운영체제 스케줄러에 의해 CPU 시간을 배정받아 코드가 실제로 실행되는 상태입니다.
3. **대기/차단(WaitSleepJoin)**: `Thread.Sleep()`으로 스스로 잠들었거나, `Join()`으로 다른 스레드를 기다리거나, 잠금(lock)을 획득하지 못해 블로킹된 상태입니다. 이 상태에서는 CPU 시간을 소비하지 않습니다.
4. **종료(Stopped)**: 스레드에 전달된 메서드가 정상적으로 반환되었거나 처리되지 않은 예외로 인해 종료된 상태입니다. 한 번 종료된 스레드는 다시 시작할 수 없습니다.

`Thread.Sleep()`은 현재 스레드를 지정한 시간 동안 실행 가능 상태에서 대기 상태로 전환시켜, 그 시간 동안 스케줄러가 다른 스레드에 CPU를 배정할 수 있게 합니다.

```csharp
using System;
using System.Threading;

Console.WriteLine("작업 시작");
Thread.Sleep(TimeSpan.FromSeconds(2));   // 2초 동안 현재 스레드를 대기 상태로 전환
Console.WriteLine("2초 후 재개");

Thread.Sleep(0);   // 같은 우선순위의 다른 스레드에게 실행 기회를 양보
```

`Thread.Sleep()`은 지정한 시간이 **최소한 그만큼은** 지나야 깨어난다는 것을 보장할 뿐, 정확히 그 시각에 깨어난다고 보장하지는 않습니다. 운영체제 스케줄러의 상황에 따라 실제로는 더 오래 잠들어 있을 수 있습니다. 또한 `Thread.Sleep()`을 호출하는 동안에는 스레드가 완전히 블로킹되어 다른 어떤 작업도 할 수 없다는 점에 유의해야 합니다. 이는 곧 배울 `Task.Delay()`와 대비되는 특징으로, `Task.Delay()`는 스레드를 점유하지 않고도 시간 지연을 표현할 수 있습니다. 이 차이는 9장에서 자세히 설명합니다.

다음 예제는 스레드의 생명주기를 `ThreadState` 속성으로 관찰해봅니다.

```csharp
using System;
using System.Threading;

Thread worker = new Thread(() =>
{
    Thread.Sleep(500);
});

Console.WriteLine($"시작 전: {worker.ThreadState}");
worker.Start();
Thread.Sleep(100);
Console.WriteLine($"실행 중: {worker.ThreadState}");
worker.Join();
Console.WriteLine($"종료 후: {worker.ThreadState}");
```

## 포그라운드 스레드와 백그라운드 스레드

`Thread` 객체는 `IsBackground`라는 속성을 가지고 있으며, 기본값은 `false`입니다. 즉 `new Thread(...)`로 만든 스레드는 기본적으로 **포그라운드 스레드**입니다.

- **포그라운드 스레드**: 이 스레드가 실행을 마치기 전까지는 프로세스가 종료되지 않습니다. 메인 스레드가 먼저 끝나더라도, 살아있는 포그라운드 스레드가 하나라도 있으면 프로세스는 계속 유지됩니다.
- **백그라운드 스레드**: `IsBackground = true`로 설정한 스레드입니다. 프로세스 안에 남아있는 스레드가 모두 백그라운드 스레드뿐이라면(즉 포그라운드 스레드가 하나도 없다면), 그 시점에 프로세스는 즉시 종료되며 백그라운드 스레드들은 실행 중이던 작업을 채 마치지 못하고 강제로 중단됩니다.

```csharp
using System;
using System.Threading;

Thread background = new Thread(() =>
{
    for (int i = 0; i < 10; i++)
    {
        Thread.Sleep(500);
        Console.WriteLine($"백그라운드 작업 진행 중: {i}");
    }
});
background.IsBackground = true;
background.Start();

Console.WriteLine("메인 스레드는 곧바로 종료됩니다.");
// Join()을 호출하지 않으므로 메인 스레드가 끝나는 즉시
// background 스레드도 남은 작업을 마치지 못한 채 함께 종료된다.
```

만약 위 코드에서 `background.IsBackground = true;` 줄을 지운다면, `background`는 포그라운드 스레드가 되어 10번의 반복을 모두 마칠 때까지 프로세스가 종료되지 않고 기다리게 됩니다.

일반적으로 애플리케이션의 핵심 기능을 담당하며 반드시 끝까지 실행되어야 하는 작업은 포그라운드 스레드로, 로그 기록이나 캐시 정리처럼 프로세스가 종료될 때 함께 사라져도 무방한 보조 작업은 백그라운드 스레드로 두는 것이 자연스럽습니다. 참고로 이후 장에서 배울 `ThreadPool`의 작업자 스레드와 `Task`는 기본적으로 백그라운드 스레드 위에서 실행됩니다.

## 스레드를 직접 만드는 비용, 그리고 더 나은 대안

지금까지 살펴본 `Thread` 클래스는 스레드의 동작 원리를 이해하기에 좋은 출발점이지만, 실무 코드에서 매번 `new Thread(...)`로 스레드를 직접 만드는 것은 대부분의 경우 권장되지 않습니다. 그 이유는 비용에 있습니다.

운영체제 스레드를 하나 생성하는 데는 적지 않은 비용이 듭니다. 스레드마다 기본적으로 별도의 호출 스택 메모리(기본값이 보통 1MB 내외)가 할당되어야 하고, 커널 차원에서 스레드를 관리하기 위한 자료구조도 함께 생성됩니다. 게다가 여러 스레드가 하나의 CPU 코어를 나눠 쓰는 상황에서는 운영체제가 실행할 스레드를 바꿀 때마다 문맥 전환이 일어나는데, 이 과정에서 레지스터와 캐시 상태를 저장하고 복원하는 오버헤드가 발생합니다. 짧게 끝나는 작업 수백, 수천 개를 처리해야 하는 상황에서 매번 새 스레드를 만들고 없애기를 반복한다면, 정작 실제로 하려던 작업보다 스레드를 만들고 정리하는 데 드는 비용이 더 커지는 역전 현상이 벌어질 수 있습니다.

이 문제를 해결하기 위해 .NET은 스레드를 미리 만들어두고 여러 작업에 재사용하는 `ThreadPool`이라는 메커니즘을 제공합니다. 스레드를 매번 새로 만드는 대신, 이미 만들어져 대기하고 있는 스레드에 작업을 맡기고 끝나면 그 스레드를 다시 풀에 반납하는 방식입니다. 그리고 `System.Threading.Tasks.Task`는 이 `ThreadPool` 위에 구축된 더 높은 수준의 추상화로, 작업의 결과값이나 예외를 다루고 여러 작업을 조합하는 기능까지 함께 제공합니다.

결론적으로 실무에서 "여러 작업을 동시에 처리하고 싶다"는 요구가 있을 때, 대부분의 경우 정답은 `Thread`를 직접 다루는 것이 아니라 `ThreadPool`이나 `Task`를 사용하는 것입니다. `Thread`를 직접 쓰는 것이 여전히 적합한 경우는 스레드의 우선순위나 스택 크기를 세밀하게 제어해야 하거나, 애플리케이션 생애 전체에 걸쳐 계속 살아있어야 하는 전용 작업 스레드를 만드는 것처럼 비교적 드문 상황에 한정됩니다. `ThreadPool`의 동작 원리는 6장에서, `Task`와 TPL(Task Parallel Library)의 기초는 7장에서 자세히 다룹니다.

## 요약

- 프로세스는 독립된 메모리 공간을 가지는 실행 단위이고, 스레드는 프로세스 안에서 실제로 코드를 실행하는 흐름의 단위입니다. 같은 프로세스에 속한 스레드들은 메모리를 공유합니다.
- `System.Threading.Thread`로 스레드를 생성할 수 있으며, `Start()`로 실행을 시작하고 `Join()`으로 다른 스레드가 끝날 때까지 대기할 수 있습니다.
- `ParameterizedThreadStart`나 람다식의 클로저를 이용해 스레드에 매개변수를 전달할 수 있습니다.
- 스레드는 생성, 실행, 대기, 종료의 생명주기를 거치며, `Thread.Sleep()`은 현재 스레드를 지정한 시간 동안 블로킹시킵니다.
- `IsBackground` 속성으로 포그라운드/백그라운드 스레드를 구분합니다. 포그라운드 스레드가 모두 종료되어야 프로세스가 끝나며, 백그라운드 스레드만 남으면 프로세스는 그 즉시 종료됩니다.
- 스레드를 직접 생성하는 데는 메모리 할당과 문맥 전환이라는 적지 않은 비용이 따릅니다. 실무에서는 대부분 6장의 `ThreadPool`이나 7장의 `Task`를 사용하는 편이 더 효율적입니다.

## 연습문제

1. 프로세스와 스레드의 차이를 메모리 관점에서 설명하세요. 같은 프로세스 안의 스레드들이 메모리를 공유한다는 사실이 왜 동기화 문제로 이어지는지 서술하세요.
2. `Thread` 생성자에 매개변수를 전달하는 두 가지 방법(`ParameterizedThreadStart`, 람다식 클로저)을 각각 코드로 작성하고 장단점을 비교하세요.
3. `Join()`을 호출하지 않은 채 메인 스레드가 먼저 종료되면 어떤 일이 벌어지는지, 그 스레드가 포그라운드인지 백그라운드인지에 따라 어떻게 달라지는지 설명하세요.
4. `Thread.Sleep(1000)`을 호출했을 때 "정확히 1000밀리초 후에 깨어난다"고 보장할 수 없는 이유를 설명하세요.
5. 짧게 끝나는 작업 1000개를 처리해야 하는 상황에서 매번 `new Thread(...)`로 새 스레드를 만드는 방식이 왜 비효율적인지 설명하고, 대안이 될 수 있는 .NET 기능의 이름을 제시하세요.

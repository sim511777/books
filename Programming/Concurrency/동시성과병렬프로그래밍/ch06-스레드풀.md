## 6.1 스레드를 매번 새로 만드는 것의 문제

2장에서 `Thread` 객체를 생성해 새 스레드를 시작하는 방법을 배웠다. 그런데 실제 애플리케이션에서는 짧고 간단한 작업 하나를 처리하기 위해 스레드를 새로 만드는 일이 생각보다 비효율적이다. 그 이유를 다시 짚어보자.

- **운영체제 자원 소비**: 새 스레드를 만들면 운영체제는 커널 객체, 스레드 컨텍스트, 그리고 기본적으로 1MB에 달하는 스택 메모리를 할당한다. 이 작업 자체가 마이크로초 단위가 아니라 그보다 훨씬 무거운 시스템 콜을 필요로 한다.
- **컨텍스트 스위칭 비용**: 스레드 수가 많아질수록 운영체제 스케줄러가 어떤 스레드를 실행할지 결정하고 전환하는 데 드는 비용도 함께 늘어난다.
- **수명 관리의 번거로움**: 스레드가 작업을 마치면 소멸시켜야 하는데, 매번 생성과 소멸을 반복하면 그 비용이 고스란히 누적된다.

만약 초당 수천 건의 짧은 요청을 처리해야 하는 웹 서버가 요청 하나마다 새 스레드를 만들고 없앤다면, 실제 요청 처리보다 스레드를 만들고 정리하는 데 더 많은 시간을 쓰게 될 수도 있다. 이 문제의 해법은 간단하다. 스레드를 매번 새로 만들고 버리는 대신, 미리 만들어둔 스레드 묶음을 재사용하는 것이다. 이것이 바로 스레드 풀(thread pool)의 핵심 아이디어다.

.NET은 `System.Threading.ThreadPool` 클래스를 통해 프로세스 전역에서 공유되는 스레드 풀을 기본 제공한다. 스레드 풀은 필요할 때 스레드를 미리 만들어 대기시켜 놓고, 작업이 들어오면 노는 스레드에게 그 작업을 맡긴다. 작업이 끝난 스레드는 소멸되지 않고 풀로 돌아가 다음 작업을 기다린다. 이렇게 하면 스레드 생성·소멸 비용을 요청 하나하나가 아니라 스레드 풀의 수명 전체에 걸쳐 분산시킬 수 있다.

## 6.2 ThreadPool.QueueUserWorkItem으로 작업 위임하기

스레드 풀에 작업을 맡기는 가장 기본적인 방법은 `ThreadPool.QueueUserWorkItem()`이다. 이 메서드는 실행할 델리게이트를 작업 큐에 넣어두고 즉시 반환하며, 실제 실행은 풀에 있는 스레드가 여유가 생기는 대로 처리한다.

```csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        Console.WriteLine($"메인 스레드 ID: {Environment.CurrentManagedThreadId}");

        for (int i = 0; i < 5; i++)
        {
            int taskId = i;
            ThreadPool.QueueUserWorkItem(_ =>
            {
                Console.WriteLine(
                    $"작업 {taskId} 실행 중, 스레드 ID: {Environment.CurrentManagedThreadId}");
                Thread.Sleep(500);
            });
        }

        Console.WriteLine("모든 작업을 큐에 넣었습니다.");
        Thread.Sleep(2000); // 풀 스레드들이 작업을 마칠 시간을 확보(데모 목적)
    }
}
```

실행해보면 다섯 개의 작업이 매번 새 스레드가 아니라, 풀에 있는 소수의 스레드에 의해 나누어 처리되는 것을 확인할 수 있다. 작업량이 늘어나도 스레드 생성 비용이 늘어나는 대신, 이미 존재하는 스레드가 순차적으로(또는 스레드 수가 충분하면 병렬로) 작업을 처리한다.

`QueueUserWorkItem`은 몇 가지 오버로드를 제공한다.

```csharp
// 상태 객체 없이 실행
ThreadPool.QueueUserWorkItem(WaitCallback callback);

// 상태 객체를 전달하여 클로저 할당을 피할 수 있는 오버로드
ThreadPool.QueueUserWorkItem(WaitCallback callback, object state);

// .NET Core 3.0 이상: 제네릭 상태와 executionContext 흐름 여부를 지정
ThreadPool.QueueUserWorkItem<TState>(Action<TState> callback, TState state, bool preferLocal);
```

두 번째와 세 번째 오버로드는 클로저를 통해 변수를 캡처하는 대신 상태를 인자로 직접 전달하므로, 반복문 안에서 대량의 작업을 큐에 넣을 때 클로저 할당으로 인한 가비지를 줄이는 데 도움이 된다.

```csharp
for (int i = 0; i < 5; i++)
{
    ThreadPool.QueueUserWorkItem(state =>
    {
        int taskId = (int)state!;
        Console.WriteLine($"작업 {taskId} 실행, 스레드 ID: {Environment.CurrentManagedThreadId}");
    }, i);
}
```

### 6.2.1 QueueUserWorkItem의 한계

`ThreadPool.QueueUserWorkItem()`은 간단하지만 실무 코드에서 마주치는 몇 가지 요구를 채워주지 못한다.

- **반환값이 없다**: `WaitCallback`은 `void`를 반환하는 델리게이트이므로, 작업의 결과를 돌려받을 표준화된 방법이 없다. 결과를 얻으려면 공유 변수와 별도의 동기화를 직접 구현해야 한다.
- **완료 시점을 알 수 없다**: 큐에 넣은 작업이 언제 끝났는지 통지받을 방법이 기본적으로 없다. 5장에서 배운 `CountdownEvent`나 `ManualResetEvent`를 직접 조합해야 한다.
- **예외 처리가 어렵다**: 콜백 안에서 예외가 발생하면 그 예외를 호출한 쪽에서 잡을 방법이 없고, 처리되지 않은 예외는 프로세스를 종료시킬 수 있다.
- **작업 간 연결(체이닝)이 없다**: "이 작업이 끝나면 이어서 저 작업을 실행하라"는 흐름을 표현할 표준 방법이 없다.
- **취소가 지원되지 않는다**: 이미 큐에 들어간 작업을 취소하는 API가 없다.

다음 예제는 이런 한계를 몸소 체감하기 위해 `QueueUserWorkItem`만으로 "여러 작업의 결과를 모두 모아 합산하기"를 구현해본 것이다.

```csharp
using System;
using System.Linq;
using System.Threading;

class Program
{
    static void Main()
    {
        const int workerCount = 4;
        var results = new int[workerCount];
        using var countdown = new CountdownEvent(workerCount);

        for (int i = 0; i < workerCount; i++)
        {
            int index = i;
            ThreadPool.QueueUserWorkItem(_ =>
            {
                try
                {
                    results[index] = (index + 1) * 100; // 실제로는 어떤 계산을 수행한다고 가정
                }
                finally
                {
                    countdown.Signal();
                }
            });
        }

        countdown.Wait();
        Console.WriteLine($"합계: {results.Sum()}");
    }
}
```

결과값을 모으기 위해 5장의 `CountdownEvent`까지 동원해야 했다. 이런 코드를 매번 손으로 작성하는 것은 번거로울 뿐 아니라 실수하기도 쉽다. 7장에서 배울 `Task<TResult>`는 바로 이런 문제(반환값, 완료 통지, 예외 전파, 체이닝, 취소)를 모두 표준화된 방식으로 해결해준다. 지금은 "스레드 풀에 작업을 맡긴다"는 개념 자체와, `ThreadPool`이 그 바탕이 된다는 사실을 이해하는 데 집중하자.

## 6.3 스레드 풀의 스레드 개수 관리

### 6.3.1 최소/최대 스레드 수

스레드 풀은 작업량에 따라 스레드 수를 동적으로 늘리거나 줄인다. 이 동작을 이해하려면 두 가지 값을 알아야 한다.

- **최소 스레드 수(minimum threads)**: 스레드 풀이 요청이 몰릴 때 별도의 지연 없이 즉시 만들어내는(스레드 생성 속도를 늦추지 않는) 스레드 수의 하한선이다. 부하가 갑자기 증가해도 이 수까지는 스레드 풀이 곧바로 새 스레드를 투입한다.
- **최대 스레드 수(maximum threads)**: 스레드 풀이 동시에 유지할 수 있는 스레드 수의 상한선이다. 대기 중인 작업이 아무리 많아도 이 수를 넘는 스레드는 만들어지지 않는다.

현재 설정값은 `GetMinThreads`/`GetMaxThreads`로, 변경은 `SetMinThreads`/`SetMaxThreads`로 할 수 있다. 스레드 풀은 워커 스레드(worker thread)와 I/O 완료 포트 스레드(completion port thread, 주로 비동기 I/O 작업에 사용됨)를 구분해서 관리하므로, 두 API 모두 두 종류의 스레드 수를 함께 반환하거나 받는다.

```csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        ThreadPool.GetMinThreads(out int minWorker, out int minIoc);
        ThreadPool.GetMaxThreads(out int maxWorker, out int maxIoc);
        ThreadPool.GetAvailableThreads(out int availWorker, out int availIoc);

        Console.WriteLine($"최소 워커 스레드: {minWorker}, 최소 IO 스레드: {minIoc}");
        Console.WriteLine($"최대 워커 스레드: {maxWorker}, 최대 IO 스레드: {maxIoc}");
        Console.WriteLine($"현재 사용 가능한 워커 스레드: {availWorker}, IO 스레드: {availIoc}");

        // 최소 워커 스레드 수를 늘려본다.
        bool changed = ThreadPool.SetMinThreads(16, minIoc);
        Console.WriteLine($"최소 스레드 수 변경 성공 여부: {changed}");
    }
}
```

`GetAvailableThreads`가 반환하는 값은 "현재 풀에 존재하는 스레드 수"가 아니라 "최대치까지 추가로 만들 수 있는 여유분"이라는 점에 유의하자. 즉 `최대 스레드 수 - 현재 사용 중인 스레드 수`에 가까운 의미다.

### 6.3.2 최소 스레드 수를 조정해야 하는 이유

.NET의 스레드 풀은 부하가 갑자기 늘어나도 스레드를 무제한으로 즉시 투입하지 않는다. 최소 스레드 수를 넘어서면, 스레드 풀은 이미 대기 중인 작업이 잘 처리되고 있는지 잠시 지켜본 뒤(대략 초 단위 간격으로) 필요하다고 판단될 때만 서서히 스레드를 추가하는 "스레드 주입(thread injection)" 알고리즘을 사용한다. 이는 순간적인 부하 폭증 때문에 수백 개의 스레드가 한꺼번에 생성되어 시스템이 오히려 느려지는 것을 막기 위한 안전장치다.

문제는 짧은 시간에 동시성 높은 요청이 몰리는 상황에서, 이 점진적인 증가 속도가 오히려 응답 지연을 일으킬 수 있다는 점이다. 예를 들어 웹 애플리케이션이 시작 직후 트래픽이 갑자기 몰리는 경우, 스레드 풀이 필요한 만큼 스레드를 다 늘리기까지 몇 초의 지연이 발생할 수 있다. 이런 상황이 예상된다면 애플리케이션 시작 시점에 `SetMinThreads()`로 최소 스레드 수를 미리 높여두어, 스레드 주입 알고리즘의 점진적 증가를 기다리지 않고 즉시 더 많은 스레드를 확보하도록 유도할 수 있다.

다만 이 값을 무작정 높게 잡는 것은 권장되지 않는다. 스레드 수가 늘어나는 만큼 메모리 사용량과 컨텍스트 스위칭 비용도 함께 늘어나기 때문이다. 최소 스레드 수 조정은 실제 부하 테스트를 통해 병목을 확인한 뒤, 근거를 가지고 신중하게 적용해야 하는 최적화다.

### 6.3.3 스레드 기아(starvation)

스레드 풀의 스레드 수에는 상한이 있으므로, 풀에 있는 모든 스레드가 동시에 오래 걸리는 작업(특히 블로킹 작업)에 묶여 있으면 새로 들어온 작업은 기존 작업이 끝나 스레드가 반환될 때까지 큐에서 마냥 대기해야 한다. 이런 상태를 스레드 기아(thread starvation)라고 부른다.

스레드 기아는 특히 다음과 같은 안티패턴에서 자주 발생한다.

- 스레드 풀 작업 안에서 `Thread.Sleep()`이나 동기 I/O처럼 스레드를 오래 점유하는 블로킹 호출을 남발하는 경우
- 비동기로 처리할 수 있는 I/O 작업을 굳이 `.Result`나 `.Wait()`로 동기적으로 기다려, 풀 스레드를 쓸데없이 붙잡아 두는 경우
- 작업 하나가 내부에서 또 다른 스레드 풀 작업의 완료를 동기적으로 기다리는, 서로 물고 물리는 의존관계를 만드는 경우

스레드 기아가 발생하면 CPU는 한가한데도 애플리케이션의 응답 속도는 계속 느려지는 모순적인 상황이 벌어진다. 겉으로는 "스레드가 부족해서 그런가?" 싶어 `SetMinThreads()`로 임시방편을 쓸 수도 있지만, 근본적인 해법은 블로킹 작업을 줄이고 비동기 I/O를 제대로 활용하는 것이다. 이 주제는 9장과 10장에서 `async`/`await`를 다루면서 "왜 블로킹 대신 비동기를 써야 하는가"라는 관점으로 다시 자세히 살펴본다.

## 6.4 ThreadPool 대신 Task를 쓰는 이유

지금까지 살펴본 것처럼 `ThreadPool.QueueUserWorkItem()`은 "스레드를 재사용해서 작업을 실행한다"는 문제는 잘 해결하지만, 그 자체로는 상당히 저수준의 API다. 결과값, 완료 통지, 예외 전파, 취소, 작업 체이닝 같은 실전에서 거의 필수적인 기능들을 직접 구현해야 한다.

7장부터 다룰 `Task`와 TPL(Task Parallel Library)은 바로 이런 필요를 채우기 위해 설계되었다. 그리고 중요한 사실은, `Task`가 `ThreadPool`을 대체하는 완전히 새로운 실행 메커니즘이 아니라는 점이다. 기본 설정에서 `Task.Run()`으로 시작한 작업은 내부적으로 바로 이 장에서 다룬 스레드 풀 위에서 실행된다. 즉 `Task`는 `ThreadPool`을 갈아엎은 것이 아니라, 그 위에 한 겹을 더 쌓아 다음과 같은 것들을 얻어낸 것이다.

- `Task<TResult>`를 통한 표준화된 결과 반환
- `ContinueWith`, `await` 등을 통한 작업 완료 후 처리(체이닝)
- `AggregateException`을 통한 예외의 안전한 전파
- `CancellationToken`과 결합한 취소 지원(11장)
- 여러 작업의 완료를 기다리는 `Task.WhenAll`, `Task.WaitAll` 같은 조합 API(8장)

앞서 6.2절에서 `CountdownEvent`까지 동원해가며 작업 결과를 모았던 예제를 떠올려보자. 같은 문제를 `Task`로 표현하면 다음과 같이 훨씬 간결해진다. (문법의 세부 사항은 7장에서 차근차근 다룰 것이므로, 지금은 코드가 얼마나 짧아지는지만 눈여겨보자.)

```csharp
using System;
using System.Linq;
using System.Threading.Tasks;

class Program
{
    static async Task Main()
    {
        var tasks = Enumerable.Range(0, 4)
            .Select(i => Task.Run(() => (i + 1) * 100))
            .ToArray();

        int[] results = await Task.WhenAll(tasks);
        Console.WriteLine($"합계: {results.Sum()}");
    }
}
```

`CountdownEvent`도, 결과를 담을 배열도, `try`/`finally`도 필요 없다. `Task.Run`이 결과를 캡슐화하고, `Task.WhenAll`이 완료를 기다리며, 작업 중 예외가 발생하면 `await` 지점에서 자연스럽게 다시 던져진다.

그렇다고 해서 `ThreadPool.QueueUserWorkItem()`이 쓸모없어진 것은 아니다. 아주 가벼운 fire-and-forget 작업을 결과나 완료 통지 없이 그저 스레드 풀에 던져 넣기만 하면 되는 극히 단순한 경우라면, `Task`가 제공하는 부가 기능들의 아주 미세한 오버헤드조차 아끼고 싶을 때 여전히 선택지가 될 수 있다. 하지만 이런 경우는 실무에서 흔치 않으며, 대부분의 상황에서는 `Task`가 제공하는 안전성과 표현력이 그 작은 비용을 상쇄하고도 남는다. 이후 이 책에서 동시성 코드를 작성할 때는 특별한 이유가 없는 한 `ThreadPool`을 직접 다루기보다 `Task`를 기본으로 사용할 것이다.

## 요약

- 스레드를 매번 새로 만드는 것은 커널 자원 할당과 컨텍스트 스위칭 측면에서 비용이 크다. 스레드 풀은 미리 만들어둔 스레드를 재사용해 이 비용을 줄인다.
- `ThreadPool.QueueUserWorkItem()`은 델리게이트를 스레드 풀의 작업 큐에 넣고 즉시 반환하며, 풀에 있는 스레드가 여유가 생기는 대로 이를 실행한다.
- `QueueUserWorkItem`만으로는 결과 반환, 완료 통지, 예외 전파, 취소, 작업 체이닝을 표준화된 방식으로 처리하기 어렵다.
- `ThreadPool.GetMinThreads`/`SetMinThreads`, `GetMaxThreads`/`SetMaxThreads`로 스레드 풀의 최소·최대 스레드 수를 조회하고 조정할 수 있으며, 갑작스러운 부하 폭증 시 최소 스레드 수를 높여 스레드 주입 지연을 줄일 수 있다.
- 풀의 모든 스레드가 블로킹 작업에 묶여 새 작업이 대기하는 상태를 스레드 기아라고 하며, 근본적인 해법은 블로킹 호출을 줄이고 비동기 I/O를 활용하는 것이다.
- `Task`는 기본적으로 `ThreadPool` 위에서 동작하면서 결과 반환, 완료 통지, 예외 전파, 취소, 조합 등 실전에 필요한 기능을 갖춘 상위 계층이다. 대부분의 경우 `ThreadPool`을 직접 다루기보다 7장부터 배울 `Task`를 사용하는 것이 더 나은 선택이다.

## 연습문제

1. 스레드를 매번 새로 생성하는 방식과 스레드 풀을 사용하는 방식의 비용 차이를 2장에서 배운 스레드 생성 비용과 연결지어 설명하라.
2. `ThreadPool.QueueUserWorkItem()`으로 10개의 작업을 큐에 넣고, 각 작업이 실행되는 스레드의 `Environment.CurrentManagedThreadId`를 출력해 몇 개의 스레드가 재사용되는지 관찰하는 프로그램을 작성하라.
3. `ThreadPool.QueueUserWorkItem()`만 사용해 5개의 작업 결과(각각 정수)를 모아 평균을 계산하는 프로그램을 작성하고, 이 과정에서 어떤 추가적인 동기화 도구가 필요했는지 설명하라.
4. 스레드 기아가 발생하는 전형적인 코드 패턴을 하나 제시하고, 왜 CPU 사용률은 낮은데 응답 속도가 느려지는 현상이 나타나는지 설명하라.
5. `SetMinThreads()`로 최소 스레드 수를 높이는 것이 만능 해결책이 아닌 이유를 설명하고, 어떤 상황에서 이 조정이 정당화될 수 있는지 논하라.

# 11장. 취소와 진행률 보고

## 이 장에서 다루는 것

지금까지 우리는 `Task`를 만들고(7장), 여러 `Task`를 조합해서 예외를 처리하고(8장), `async`/`await`로 비동기 코드를 동기 코드처럼 자연스럽게 작성하는 방법(9장, 10장)을 살펴봤습니다. 그런데 실제 애플리케이션에서는 "작업을 시작했으니 끝까지 기다린다"만으로는 부족한 경우가 많습니다.

- 사용자가 "취소" 버튼을 눌렀다면, 진행 중인 다운로드나 계산을 중간에 멈출 수 있어야 합니다.
- 서버 API를 호출하는데 5초가 지나도 응답이 없다면, 무한정 기다리지 않고 타임아웃 처리를 해야 합니다.
- 오래 걸리는 작업이라면, 사용자에게 "지금 몇 %쯤 진행됐는지" 알려줘야 합니다.

이 장에서는 .NET이 이 두 가지 문제—**취소**와 **진행률 보고**—를 위해 제공하는 표준 메커니즘인 `CancellationToken`과 `IProgress<T>`를 다룹니다. 두 메커니즘 모두 특정 API에 종속되지 않고 `Task`, `async`/`await`, `Parallel`, PLINQ 등 이 책에서 다루는 거의 모든 동시성 도구에서 공통으로 사용되는 범용 인터페이스라는 점이 중요합니다.

## 취소는 왜 "협력적"이어야 하는가

스레드를 다뤄본 사람이라면 한 번쯤 "실행 중인 스레드를 강제로 죽이는 방법은 없을까?"라는 생각을 해봤을 것입니다. .NET에도 과거 `Thread.Abort()`라는 메서드가 존재했지만, 이는 스레드를 임의의 시점에서 강제로 중단시켜 락을 잡은 채로 멈추거나, 객체를 일관성 없는 상태로 남기는 등 심각한 문제를 일으켰습니다. 그래서 `Thread.Abort()`는 사실상 사용이 금지된 API가 되었고, .NET Core 이후로는 아예 예외를 던지는 것으로 동작이 바뀌었습니다.

.NET이 채택한 대안은 **협력적 취소(cooperative cancellation)** 모델입니다. 핵심 아이디어는 단순합니다.

> 취소를 요청하는 쪽은 "취소해 달라"는 신호만 보낼 뿐, 작업을 강제로 멈추지 않는다. 실제로 작업을 멈추는 것은 작업을 수행하는 코드 자신이며, 그 코드는 스스로 신호를 주기적으로 확인해서 신호가 켜져 있으면 스스로 중단한다.

즉 취소는 "당하는" 것이 아니라 "받아들이는" 것입니다. 작업 로직이 신호를 전혀 확인하지 않는다면, 아무리 취소를 요청해도 작업은 끝까지 실행됩니다. 이 모델은 언뜻 불편해 보일 수 있지만, 락을 잡은 도중에 중단되거나 절반만 쓰인 파일이 남는 것 같은 문제를 원천적으로 방지해줍니다. 취소는 항상 코드 안전한 지점(safe point)에서만 일어나기 때문입니다.

이 신호를 표현하는 것이 바로 `CancellationTokenSource`와 `CancellationToken`입니다.

## CancellationTokenSource와 CancellationToken

역할이 나뉘어 있다는 점이 이 API의 핵심입니다.

- `CancellationTokenSource`: 취소 신호를 **발생시키는** 쪽이 가지는 객체. `Cancel()` 메서드를 호출해서 신호를 켤 수 있습니다.
- `CancellationToken`: 취소 신호를 **받아서 확인하는** 쪽에 전달되는 값 타입(구조체). 신호를 켤 수는 없고, 오직 "취소가 요청되었는지" 읽기만 할 수 있습니다.

이렇게 나눠놓은 이유는 명확합니다. 작업을 실행하는 코드에는 `CancellationToken`만 넘겨줘서, 그 코드가 실수로든 의도적으로든 취소를 요청하는 주체가 되지 못하게 막는 것입니다. 취소를 발생시킬 권한은 오직 `CancellationTokenSource`를 쥔 쪽—보통은 작업을 시작한 호출자—에게만 있습니다.

```csharp
using CancellationTokenSource cts = new CancellationTokenSource();
CancellationToken token = cts.Token;

// token은 작업을 수행하는 메서드에 전달
DoWorkAsync(token);

// 어느 시점에 사용자가 취소를 요청하면
cts.Cancel();
```

`CancellationTokenSource`는 `IDisposable`을 구현하므로, 더 이상 필요 없어지면 반드시 `Dispose()`를 호출해 내부 리소스를(특히 타이머 관련 핸들) 정리해야 합니다. `using` 선언을 쓰는 것이 가장 안전합니다.

### IsCancellationRequested와 ThrowIfCancellationRequested

작업 쪽 코드에서 취소 신호를 확인하는 방법은 두 가지입니다.

**1. `IsCancellationRequested` 속성을 읽고 직접 판단하기**

```csharp
void ProcessItems(IReadOnlyList<int> items, CancellationToken token)
{
    foreach (int item in items)
    {
        if (token.IsCancellationRequested)
        {
            Console.WriteLine("취소 요청을 확인, 작업을 정리하고 종료합니다.");
            return; // 또는 필요한 정리 작업 후 반환
        }

        Process(item);
    }
}
```

이 방식은 취소가 요청됐을 때 예외 없이 조용히 빠져나가고 싶을 때 유용합니다.

**2. `ThrowIfCancellationRequested()`로 예외를 던지기**

```csharp
void ProcessItems(IReadOnlyList<int> items, CancellationToken token)
{
    foreach (int item in items)
    {
        token.ThrowIfCancellationRequested();
        Process(item);
    }
}
```

`ThrowIfCancellationRequested()`는 `IsCancellationRequested`가 `true`이면 `OperationCanceledException`(정확히는 `Task` 계열 API와 잘 맞물리도록 토큰 정보를 담은 하위 예외)을 던집니다. `Task` 기반 코드에서는 이 예외를 던지는 방식이 사실상 표준 관례입니다. `Task`가 이 예외를 감지하면 `Faulted` 상태가 아니라 `Canceled` 상태로 전이시켜주기 때문에, 호출자 입장에서 "실패한 것"과 "취소된 것"을 명확히 구분할 수 있습니다. 8장에서 다룬 `Task.Status`와 `AggregateException` 처리 로직도 이 구분을 전제로 동작합니다.

일반적으로는 반복문 안에서, I/O 대기 직전에, 혹은 비용이 큰 단계로 넘어가기 직전에 이런 확인 지점을 두는 것이 좋습니다. 확인 지점이 너무 뜸하면 취소 요청 후에도 한참 뒤에야 실제로 멈추고, 너무 잦으면 오버헤드가 늘어납니다.

## 취소 가능한 비동기 작업 만들기

다운로드나 대량 데이터 처리를 흉내 낸 예제로 살펴보겠습니다. 아래 `DownloadSimulationAsync`는 100개의 "청크"를 순차적으로 내려받는 것을 시뮬레이션하며, 매 청크마다 취소 여부를 확인합니다.

```csharp
async Task DownloadSimulationAsync(CancellationToken token)
{
    const int totalChunks = 100;

    for (int i = 1; i <= totalChunks; i++)
    {
        // 취소 요청이 있었다면 여기서 예외를 던지고 즉시 빠져나간다.
        token.ThrowIfCancellationRequested();

        // 청크 하나를 내려받는 데 걸리는 시간을 흉내낸다.
        // Task.Delay에 토큰을 넘기면 대기 중에도 취소에 즉시 반응한다.
        await Task.Delay(50, token);

        Console.WriteLine($"청크 {i}/{totalChunks} 다운로드 완료");
    }

    Console.WriteLine("다운로드 완료!");
}
```

여기서 `Task.Delay(50, token)`처럼 `token`을 넘긴 부분이 중요합니다. `Task.Delay`, `Task.WhenAny`, 스트림의 `ReadAsync` 등 취소를 지원하는 대부분의 비동기 API는 `CancellationToken`을 받는 오버로드를 제공합니다. 이 오버로드에 토큰을 넘기면, 굳이 반복문에서 직접 확인하지 않아도 대기 도중에 취소가 요청되는 즉시 `OperationCanceledException`을 던지며 빠져나옵니다. 즉 "확인 지점"을 코드 곳곳에 직접 심는 것과, "취소 인식 API"에 토큰을 전달하는 것은 서로 보완적인 취소 확인 수단입니다.

호출하는 쪽에서는 이렇게 사용합니다.

```csharp
using CancellationTokenSource cts = new CancellationTokenSource();

Task downloadTask = DownloadSimulationAsync(cts.Token);

// 예: 사용자가 300ms 뒤에 취소 버튼을 눌렀다고 가정
await Task.Delay(300);
cts.Cancel();

try
{
    await downloadTask;
}
catch (OperationCanceledException)
{
    Console.WriteLine("다운로드가 취소되었습니다.");
}
```

`Cancel()`을 호출한다고 해서 `downloadTask`가 그 즉시 끝나는 것은 아닙니다. 다음 확인 지점(`ThrowIfCancellationRequested()` 또는 `Task.Delay`의 대기)에 도달해야 비로소 예외가 발생하고 `Task`가 `Canceled` 상태가 됩니다. 이것이 바로 협력적 취소의 자연스러운 특성입니다.

> **주의** `await`한 `Task`가 취소되면 `await` 지점에서 `OperationCanceledException`이 다시 던져집니다. 이 예외를 `try`/`catch`로 잡지 않으면 예외가 그대로 호출 스택을 타고 전파되므로, 취소를 정상적인 흐름의 일부로 처리하려면 반드시 `OperationCanceledException`(또는 그 하위 타입인 `TaskCanceledException`)을 잡아줘야 합니다.

## CancelAfter로 타임아웃 걸기

"사용자가 명시적으로 취소 버튼을 누른다"는 시나리오 외에, "일정 시간이 지나도 끝나지 않으면 자동으로 취소한다"는 타임아웃 시나리오도 매우 흔합니다. `CancellationTokenSource`는 이를 위한 `CancelAfter()` 메서드를 제공합니다.

```csharp
using CancellationTokenSource cts = new CancellationTokenSource();
cts.CancelAfter(TimeSpan.FromSeconds(3)); // 3초 후 자동으로 Cancel() 호출

try
{
    await DownloadSimulationAsync(cts.Token);
}
catch (OperationCanceledException)
{
    Console.WriteLine("3초 안에 작업이 끝나지 않아 취소되었습니다.");
}
```

생성자에서 곧바로 타임아웃을 지정할 수도 있습니다.

```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
```

`CancelAfter()`는 이미 시작된 타이머를 다시 설정할 수도 있어서, "마지막 활동으로부터 3초"처럼 활동이 있을 때마다 타임아웃을 리셋하는 패턴에도 사용할 수 있습니다.

실무에서는 사용자 취소와 타임아웃을 동시에 지원해야 하는 경우가 많은데, 이때 유용한 것이 `CancellationTokenSource.CreateLinkedTokenSource()`입니다. 이 메서드는 여러 개의 토큰을 하나로 묶어서, 그중 어느 하나라도 취소되면 함께 취소되는 새로운 토큰 소스를 만들어줍니다.

```csharp
async Task DownloadWithTimeoutAsync(CancellationToken userToken)
{
    using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
    using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(userToken, timeoutCts.Token);

    await DownloadSimulationAsync(linkedCts.Token);
}
```

이렇게 하면 사용자가 취소 버튼을 눌러도, 5초가 지나도 동일하게 `linkedCts.Token`을 통해 취소가 전파됩니다. `HttpClient` 같은 실제 I/O API를 사용할 때 이 패턴이 특히 자주 등장합니다.

## IProgress&lt;T&gt;와 Progress&lt;T&gt;로 진행률 보고하기

취소가 "밖에서 안으로" 보내는 신호라면, 진행률 보고는 정반대로 "안에서 밖으로" 보내는 신호입니다. 오래 걸리는 작업이 지금 얼마나 진행됐는지를 호출자(흔히 UI)에게 알려주는 것입니다.

언뜻 보면 그냥 콜백 델리게이트나 이벤트를 하나 넘기면 될 것 같지만, 여기에는 10장에서 다룬 문제가 그대로 다시 나타납니다. 작업은 보통 스레드 풀 스레드나 별도의 백그라운드 스레드에서 실행되는데, 진행률을 UI 컨트롤에 반영하려면 그 갱신이 반드시 UI 스레드에서 일어나야 한다는 제약이 있습니다. 백그라운드 스레드에서 직접 UI 컨트롤을 건드리면 WPF나 WinForms에서는 예외가 발생하거나 정의되지 않은 동작이 일어납니다.

이 문제를 표준화해서 풀어주는 것이 `IProgress<T>` 인터페이스와 그 기본 구현체인 `Progress<T>`입니다.

```csharp
public interface IProgress<in T>
{
    void Report(T value);
}
```

인터페이스 자체는 매우 단순합니다. 진짜 마법은 `Progress<T>` 클래스의 구현에 있습니다.

> `Progress<T>`는 **생성되는 시점**의 `SynchronizationContext`를 캡처해두었다가, `Report()`가 어느 스레드에서 호출되든 캡처해둔 컨텍스트를 통해 콜백을 실행합니다.

10장에서 살펴봤듯이 WPF나 WinForms 애플리케이션의 UI 스레드에서는 `SynchronizationContext.Current`가 해당 UI 프레임워크의 컨텍스트로 설정되어 있습니다. 따라서 UI 스레드에서 `new Progress<T>(callback)`을 생성하면, 이후 어떤 백그라운드 스레드에서 `Report()`를 호출하더라도 `callback`은 항상 원래의 UI 스레드로 다시 마샬링되어 실행됩니다. 개발자가 `Dispatcher.Invoke`나 `Control.Invoke`를 직접 호출할 필요가 없어지는 것입니다. (콘솔 앱처럼 `SynchronizationContext`가 없는 환경에서는 스레드 풀 스레드에서 콜백이 실행됩니다.)

### 사용 패턴

`IProgress<T>`를 사용하는 코드는 보통 진행률 정보를 표현하는 타입을 하나 정의하는 것으로 시작합니다.

```csharp
readonly record struct DownloadProgress(int CompletedChunks, int TotalChunks)
{
    public double Percentage => (double)CompletedChunks / TotalChunks * 100;
}
```

작업 메서드는 `IProgress<T>`를 매개변수로 받아 진행 상황이 바뀔 때마다 `Report()`를 호출합니다.

```csharp
async Task DownloadWithProgressAsync(
    IProgress<DownloadProgress>? progress,
    CancellationToken token)
{
    const int totalChunks = 100;

    for (int i = 1; i <= totalChunks; i++)
    {
        token.ThrowIfCancellationRequested();

        await Task.Delay(50, token);

        progress?.Report(new DownloadProgress(i, totalChunks));
    }
}
```

호출하는 쪽(예: UI 스레드)에서는 `Progress<T>`를 생성하고 콜백에서 안전하게 UI를 갱신합니다.

```csharp
// 이 코드가 UI 스레드에서 실행 중이라고 가정
var progress = new Progress<DownloadProgress>(p =>
{
    // Progress<T>가 SynchronizationContext를 통해 마샬링해주므로
    // 이 콜백은 항상 UI 스레드에서 실행된다. 직접 Dispatcher.Invoke를
    // 호출할 필요가 없다.
    progressBar.Value = p.Percentage;
    statusLabel.Text = $"{p.CompletedChunks}/{p.TotalChunks} 완료";
});

using var cts = new CancellationTokenSource();

try
{
    await DownloadWithProgressAsync(progress, cts.Token);
}
catch (OperationCanceledException)
{
    statusLabel.Text = "취소됨";
}
```

콘솔 애플리케이션에서도 동일한 패턴을 그대로 사용할 수 있습니다. 이 경우 `SynchronizationContext.Current`가 `null`이므로 `Report()` 콜백은 스레드 풀 스레드에서 실행되지만, 콘솔에 진행률을 출력하는 정도라면 스레드 안전성 문제가 크지 않습니다.

```csharp
var progress = new Progress<DownloadProgress>(p =>
    Console.WriteLine($"진행률: {p.Percentage:F1}%"));

await DownloadWithProgressAsync(progress, CancellationToken.None);
```

### IProgress&lt;T&gt;를 직접 구현해야 할 때

`Progress<T>`는 대부분의 경우 충분하지만, `SynchronizationContext`를 거치지 않고 특정 스레드로 직접 마샬링하고 싶거나, 진행률 보고를 배치로 모았다가 한 번에 처리하고 싶은 등 특수한 요구사항이 있다면 `IProgress<T>`를 직접 구현할 수도 있습니다. 다만 일반적인 UI 갱신 시나리오에서는 `Progress<T>`가 이미 필요한 마샬링을 해주므로 별도 구현이 필요한 경우는 드뭅니다.

### 왜 콜백을 직접 넘기지 않고 IProgress&lt;T&gt;를 쓰는가

`Action<T>` 델리게이트를 직접 넘기는 것과 비교했을 때 `IProgress<T>`가 갖는 실질적인 이점은 두 가지입니다.

1. **스레드 마샬링이 인터페이스 계약의 일부로 명시된다.** `IProgress<T>.Report()`를 구현하는 쪽이 스레드 전환 책임을 지도록 관례화되어 있어서, 호출하는 작업 메서드는 "내가 지금 어느 스레드에서 실행되고 있는지" 신경 쓸 필요가 없습니다.
2. **테스트와 대체 구현이 쉬워진다.** 인터페이스이므로 테스트 코드에서는 진행률을 리스트에 기록하는 가짜 구현체로 손쉽게 대체할 수 있습니다.

이 두 가지 특성 덕분에 `IProgress<T>`는 `Task` 기반 비동기 API 전반에서(예를 들어 `HttpClient`의 일부 확장 메서드나 파일 복사 유틸리티 등) 진행률 보고의 사실상 표준 인터페이스로 자리 잡았습니다.

## 취소와 진행률을 함께 사용하기

실전 코드에서는 취소와 진행률 보고가 한 메서드 안에 함께 등장하는 경우가 대부분입니다.

```csharp
async Task ProcessLargeFileAsync(
    string path,
    IProgress<double>? progress,
    CancellationToken token)
{
    string[] lines = await File.ReadAllLinesAsync(path, token);
    int total = lines.Length;

    for (int i = 0; i < total; i++)
    {
        token.ThrowIfCancellationRequested();

        await ProcessLineAsync(lines[i], token);

        progress?.Report((i + 1) / (double)total * 100);
    }
}
```

이 메서드는 두 매개변수 모두 `null` 허용(진행률) 또는 `CancellationToken.None`(취소 없음)으로 호출될 수 있도록 설계되어 있어서, 호출자가 두 기능을 선택적으로 사용할 수 있습니다. 이는 .NET BCL이 비동기 API를 설계할 때 흔히 따르는 관례이기도 합니다.

이 장에서 다룬 `CancellationToken`은 다음 장의 `Parallel` 클래스에서도 그대로 사용됩니다. `ParallelOptions.CancellationToken`을 설정하면 병렬 반복문 전체를 협력적으로 중단시킬 수 있으며, 13장의 PLINQ에서도 `WithCancellation()`이라는 형태로 동일한 개념이 이어집니다.

## 요약

- .NET의 취소는 강제 종료가 아니라 **협력적 취소** 모델을 따릅니다. 취소를 요청하는 쪽은 신호만 보내고, 실제로 멈추는 것은 작업 코드 자신이 신호를 확인해서 스스로 결정합니다.
- `CancellationTokenSource`는 신호를 발생시키는 쪽(`Cancel()`)이, `CancellationToken`은 신호를 확인하는 쪽(`IsCancellationRequested`, `ThrowIfCancellationRequested()`)이 사용합니다.
- `ThrowIfCancellationRequested()`는 `OperationCanceledException`을 던지며, `Task` 기반 코드에서는 이 예외가 `Task`를 `Faulted`가 아닌 `Canceled` 상태로 만들어줍니다.
- `Task.Delay` 등 취소를 인식하는 API에 토큰을 넘기면, 대기 중에도 취소 요청에 즉시 반응할 수 있습니다.
- `CancelAfter()`로 타임아웃 취소를 설정할 수 있고, `CreateLinkedTokenSource()`로 사용자 취소와 타임아웃 취소를 하나의 토큰으로 묶을 수 있습니다.
- `IProgress<T>`는 진행률 보고를 위한 표준 인터페이스이며, 기본 구현체 `Progress<T>`는 생성 시점의 `SynchronizationContext`를 캡처해서 `Report()` 콜백이 항상 원래 스레드(대개 UI 스레드)에서 안전하게 실행되도록 마샬링해줍니다.

## 연습문제

1. 협력적 취소 모델에서 `Cancel()`을 호출한 즉시 작업이 멈추지 않는 이유를 설명하고, 취소 반응 속도를 높이려면 코드를 어떻게 작성해야 하는지 서술하세요.
2. `IsCancellationRequested`를 직접 확인하는 방식과 `ThrowIfCancellationRequested()`를 사용하는 방식의 차이를 설명하고, 각각 어떤 상황에 더 적합한지 예를 들어 설명하세요.
3. 사용자가 취소 버튼을 누르거나 10초가 지나면 자동으로 취소되는 다운로드 메서드를 `CreateLinkedTokenSource()`를 사용해 작성하세요.
4. `Progress<T>`가 `SynchronizationContext`를 캡처하는 시점은 언제인지, 그리고 만약 `Progress<T>` 객체를 백그라운드 스레드에서 생성한다면 어떤 문제가 발생할 수 있는지 설명하세요.
5. 1부터 N까지의 숫자를 순차적으로 처리하면서, 처리할 때마다 진행률(백분율)을 보고하고 `CancellationToken`으로 중간에 취소할 수 있는 비동기 메서드를 작성하세요. 콘솔 앱에서 이 메서드를 호출하고 3초 뒤 자동으로 취소되도록 구성해보세요.

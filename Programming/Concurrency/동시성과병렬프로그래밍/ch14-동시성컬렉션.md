## 들어가며: 일반 컬렉션은 왜 위험한가

3장에서 우리는 여러 스레드가 공유 자원을 동시에 읽고 쓸 때 발생하는 경쟁 조건(race condition)을 살펴봤습니다. `List<T>`나 `Dictionary<TKey, TValue>` 같은 BCL의 기본 컬렉션들은 이 문제에서 전혀 안전하지 않습니다. 두 스레드가 동시에 `list.Add()`를 호출하면 다음과 같은 일이 벌어질 수 있습니다.

```csharp
var list = new List<int>();

// 여러 스레드가 동시에 실행하면...
Parallel.For(0, 100_000, i =>
{
    list.Add(i); // 스레드 안전하지 않다!
});

Console.WriteLine(list.Count); // 100000이 아닐 수도, 예외가 날 수도 있다
```

`List<T>.Add()`는 내부적으로 "배열 용량 확인 → 필요하면 더 큰 배열로 교체 → 요소 대입 → 개수 증가"라는 여러 단계로 이루어져 있습니다. 이 단계들 사이에 다른 스레드가 끼어들면 요소가 유실되거나, `IndexOutOfRangeException`이 발생하거나, 심하면 내부 배열이 손상되어 이후 모든 접근이 불안정해질 수 있습니다. `Dictionary<TKey, TValue>`는 더 심각합니다. 내부적으로 해시 버킷과 연결 리스트 구조를 사용하기 때문에, 동시 쓰기가 겹치면 무한 루프에 빠지거나 데이터 구조 자체가 순환 참조를 갖게 되는 등 예측 불가능한 손상이 발생할 수 있습니다.

이 문제를 해결하는 전통적인 방법은 4장에서 배운 `lock`으로 컬렉션 접근을 감싸는 것입니다.

```csharp
var list = new List<int>();
var gate = new object();

Parallel.For(0, 100_000, i =>
{
    lock (gate)
    {
        list.Add(i);
    }
});
```

이 방식은 정확하지만, 모든 접근이 하나의 잠금을 두고 경쟁하기 때문에 병렬성이 크게 제한됩니다. 사실상 리스트에 대한 모든 연산이 순차적으로 직렬화되는 셈입니다.

`System.Collections.Concurrent` 네임스페이스는 이런 수작업 잠금 없이도 여러 스레드가 안전하게 접근할 수 있도록 내부적으로 세밀하게 동기화된 컬렉션들을 제공합니다. 이 컬렉션들은 단순히 모든 메서드에 `lock`을 씌운 것이 아니라, 락-프리(lock-free) 알고리즘이나 버킷 단위의 세분화된 잠금(fine-grained locking)을 사용해 `lock` 하나로 전체를 감싸는 것보다 훨씬 높은 처리량을 냅니다. 이번 장에서는 이 동시성 컬렉션들을 하나씩 살펴봅니다.

## ConcurrentDictionary&lt;TKey, TValue&gt;

`ConcurrentDictionary<TKey, TValue>`는 `Dictionary<TKey, TValue>`에 대응하는 스레드 안전한 컬렉션입니다. 내부적으로 키 공간을 여러 버킷으로 나누고 버킷 단위로 잠금을 걸기 때문에, 서로 다른 버킷에 속한 키를 다루는 스레드들은 서로를 기다리지 않고 동시에 진행할 수 있습니다.

가장 큰 특징은 "확인 후 실행(check-then-act)" 패턴을 원자적으로 수행하는 메서드들을 제공한다는 점입니다. 일반 `Dictionary<TKey, TValue>`로 다음과 같은 코드를 작성하면 경쟁 조건이 생깁니다.

```csharp
// 경쟁 조건이 있는 코드
if (!dict.ContainsKey(key))
{
    dict[key] = ComputeValue(key); // 이 사이에 다른 스레드가 끼어들 수 있다
}
```

`ContainsKey`로 확인한 시점과 `dict[key] = ...`로 대입하는 시점 사이에 다른 스레드가 같은 키를 먼저 추가해버리면 예상과 다른 동작이 발생합니다. `ConcurrentDictionary<TKey, TValue>`는 이런 확인-후-실행 패턴을 단일 원자적 연산으로 제공합니다.

### TryAdd / TryUpdate / TryRemove / TryGetValue

```csharp
var dict = new ConcurrentDictionary<string, int>();

bool added = dict.TryAdd("apple", 1);      // 키가 없으면 추가하고 true
bool addedAgain = dict.TryAdd("apple", 2); // 이미 있으므로 false, 값은 그대로 1

bool updated = dict.TryUpdate("apple", newValue: 10, comparisonValue: 1);
// 현재 값이 comparisonValue(1)와 같을 때만 newValue(10)로 교체. 성공하면 true

bool removed = dict.TryRemove("apple", out int removedValue);

if (dict.TryGetValue("apple", out int value))
{
    Console.WriteLine(value);
}
```

`TryUpdate`는 "지금 값이 내가 알던 값과 같을 때만 바꿔라"라는 조건부 갱신(compare-and-swap 방식)을 제공합니다. 다른 스레드가 그 사이 값을 바꿔놨다면 `TryUpdate`는 실패(`false`)를 반환하므로, 실패 시 재시도할지 여부를 호출 측에서 결정할 수 있습니다.

### GetOrAdd

캐시 패턴에서 가장 자주 쓰이는 메서드입니다. "키가 있으면 그 값을 반환하고, 없으면 계산해서 추가한 뒤 그 값을 반환"하는 동작을 원자적으로 수행합니다.

```csharp
var cache = new ConcurrentDictionary<int, string>();

string result = cache.GetOrAdd(42, key => ExpensiveComputation(key));
```

주의할 점이 있습니다. `GetOrAdd`에 전달한 팩토리 델리게이트(`key => ExpensiveComputation(key)`)는 **여러 스레드가 동시에 같은 키로 경합할 경우 두 번 이상 호출될 수 있습니다.** `ConcurrentDictionary<TKey, TValue>`는 최종적으로 딕셔너리에 저장되는 값이 단 하나임은 보장하지만, 그 값을 만들어내는 팩토리 함수 자체의 중복 호출까지 막아주지는 않습니다.

```csharp
// 여러 스레드가 동시에 GetOrAdd(1, ...)을 호출하면
// ExpensiveComputation(1)이 두 번 이상 실행될 수 있다 (결과는 하나만 저장됨)
var cache = new ConcurrentDictionary<int, ExpensiveObject>();
var obj = cache.GetOrAdd(1, key =>
{
    Console.WriteLine($"계산 중: {key}"); // 경합 시 여러 번 출력될 수 있다
    return new ExpensiveObject(key);
});
```

팩토리 호출 자체가 반드시 한 번만 일어나야 한다면(예: 비용이 매우 크거나 부수 효과가 있는 초기화), `Lazy<T>`를 값으로 저장하는 패턴을 함께 고려해야 합니다.

```csharp
var cache = new ConcurrentDictionary<int, Lazy<ExpensiveObject>>();

Lazy<ExpensiveObject> lazy = cache.GetOrAdd(1,
    key => new Lazy<ExpensiveObject>(() => new ExpensiveObject(key)));

ExpensiveObject obj = lazy.Value; // Lazy<T> 자체가 단 한 번의 초기화를 보장
```

### AddOrUpdate

키가 없으면 추가하고, 있으면 기존 값을 바탕으로 갱신합니다.

```csharp
var counters = new ConcurrentDictionary<string, int>();

// 없으면 1로 추가, 있으면 기존 값 + 1
counters.AddOrUpdate("hits", addValue: 1, updateValueFactory: (key, oldValue) => oldValue + 1);
```

`GetOrAdd`와 마찬가지로 `updateValueFactory`(그리고 팩토리 오버로드를 쓴다면 `addValueFactory`도)는 경합 상황에서 여러 번 호출될 수 있으므로, 이 델리게이트 내부에서는 부수 효과 없는 순수 계산만 수행하는 것이 안전합니다.

### 스냅샷 시맨틱

`Count`, `Keys`, `Values`, 그리고 `foreach` 순회는 호출 시점의 **스냅샷에 가까운 뷰**를 제공합니다. 정확히는 열거 도중 다른 스레드가 컬렉션을 수정해도 `Dictionary<TKey, TValue>`처럼 `InvalidOperationException`이 발생하지는 않지만, 그 열거 결과가 특정 시점의 정확한 상태와 100% 일치한다는 보장도 하지 않습니다. 열거 도중 반영되거나 반영되지 않은 변경 사항이 섞여 나타날 수 있다는 뜻입니다. 정확한 원자적 스냅샷이 필요하다면 별도의 동기화가 필요합니다.

## ConcurrentQueue&lt;T&gt;, ConcurrentStack&lt;T&gt;, ConcurrentBag&lt;T&gt;

세 컬렉션 모두 `IProducerConsumerCollection<T>` 인터페이스를 구현하며, 순서 정책과 최적화 대상이 서로 다릅니다.

### ConcurrentQueue&lt;T&gt; - FIFO

먼저 들어간 항목이 먼저 나오는 큐입니다. 내부적으로 락-프리 알고리즘으로 구현되어 있어 `lock`으로 보호한 `Queue<T>`보다 경합 상황에서 훨씬 효율적입니다.

```csharp
var queue = new ConcurrentQueue<int>();

queue.Enqueue(1);
queue.Enqueue(2);

if (queue.TryDequeue(out int item))
{
    Console.WriteLine(item); // 1
}

if (queue.TryPeek(out int peeked))
{
    Console.WriteLine(peeked); // 다음에 나올 항목을 제거 없이 확인
}
```

일반 `Queue<T>`와 달리 `Dequeue()`나 `Peek()`이 예외를 던지는 대신 `TryDequeue`/`TryPeek`처럼 `bool`을 반환하는 시도(Try) 패턴을 사용합니다. 큐가 비어 있다는 것은 여러 스레드가 동시에 접근하는 환경에서는 예외적 상황이 아니라 정상적으로 자주 발생하는 상태이기 때문입니다.

작업 순서가 중요한 생산자-소비자 시나리오, 예를 들어 로그를 기록된 순서대로 처리해야 하는 경우에 적합합니다.

### ConcurrentStack&lt;T&gt; - LIFO

나중에 들어간 항목이 먼저 나오는 스택입니다.

```csharp
var stack = new ConcurrentStack<int>();

stack.Push(1);
stack.Push(2);

if (stack.TryPop(out int item))
{
    Console.WriteLine(item); // 2
}

stack.PushRange(new[] { 3, 4, 5 }); // 여러 항목을 한 번에 원자적으로 push
```

`PushRange`/`TryPopRange`처럼 여러 항목을 한 번에 처리하는 벌크(bulk) 메서드도 제공하는데, 개별 호출을 여러 번 반복하는 것보다 동기화 비용을 줄일 수 있습니다. 가장 최근에 추가된 항목을 우선적으로 처리해야 하는 경우, 예를 들어 되돌리기(undo) 스택이나 깊이 우선 탐색 기반의 작업 분배에 적합합니다.

### ConcurrentBag&lt;T&gt; - 순서 없는 저장

`ConcurrentBag<T>`는 항목의 순서를 전혀 보장하지 않는 대신, 각 스레드가 자신만의 로컬 저장 공간을 갖도록 최적화되어 있습니다. 어떤 스레드가 `Add()`한 항목은 우선적으로 그 스레드의 로컬 저장소에 쌓이고, 같은 스레드가 `TryTake()`를 호출하면 다른 스레드와 경합할 필요 없이 자신의 로컬 저장소에서 먼저 꺼내갑니다. 로컬 저장소가 비어 있을 때만 다른 스레드의 저장소를 훔쳐오는(work-stealing) 방식으로 항목을 가져옵니다.

```csharp
var bag = new ConcurrentBag<int>();

Parallel.For(0, 1000, i =>
{
    bag.Add(i);
});

while (bag.TryTake(out int item))
{
    Process(item);
}
```

이 설계 덕분에 **같은 스레드가 항목을 추가하고 나중에 같은 스레드(혹은 소수의 스레드)가 그 항목을 다시 꺼내가는 패턴**에서 `ConcurrentBag<T>`는 `ConcurrentQueue<T>`나 `ConcurrentStack<T>`보다 훨씬 뛰어난 성능을 냅니다. 반대로, 순서가 필요하거나, 항목을 추가하는 스레드와 꺼내가는 스레드가 완전히 분리되어 있는 전형적인 생산자-소비자 패턴에서는 `ConcurrentBag<T>`의 장점이 사라지고 오히려 `ConcurrentQueue<T>`보다 불리할 수 있습니다. 순서가 의미 없는 작업 항목들을 여러 워커가 나눠서 처리하고 결과를 다시 같은 워커가 거둬들이는 시나리오에 가장 잘 맞습니다.

### 세 컬렉션 비교

| 컬렉션 | 순서 | 최적화 대상 | 대표 용도 |
|---|---|---|---|
| `ConcurrentQueue<T>` | FIFO | 일반적인 생산자-소비자 | 순서대로 처리해야 하는 작업 큐, 로그 버퍼 |
| `ConcurrentStack<T>` | LIFO | 일반적인 생산자-소비자 | 되돌리기 스택, 최신 항목 우선 처리 |
| `ConcurrentBag<T>` | 없음 | 스레드-로컬 추가/제거 | 순서 무관 작업 풀, 동일 스레드의 add-then-take 패턴 |

## BlockingCollection&lt;T&gt;

지금까지 본 `ConcurrentQueue<T>` 등은 항목이 없을 때 `TryDequeue`가 즉시 `false`를 반환할 뿐, 스레드를 대기시키지는 않습니다. 소비자가 "항목이 생길 때까지 기다렸다가 처리"하는 전형적인 생산자-소비자 패턴을 구현하려면 폴링(polling) 루프를 직접 짜야 하는데, 이는 CPU를 낭비하거나 반응 속도가 떨어지는 코드로 이어지기 쉽습니다.

`BlockingCollection<T>`는 바로 이 문제를 해결하기 위한 래퍼(wrapper) 컬렉션입니다. 내부적으로 `IProducerConsumerCollection<T>`(기본값은 `ConcurrentQueue<T>`)를 감싸면서, 항목이 없을 때 소비자를 실제로 블로킹(대기)시키고, 항목이 추가되면 대기 중인 소비자를 깨워주는 기능을 추가합니다.

```csharp
var collection = new BlockingCollection<int>();

// 생산자
var producer = Task.Run(() =>
{
    for (int i = 0; i < 10; i++)
    {
        collection.Add(i);
        Console.WriteLine($"생산: {i}");
    }
    collection.CompleteAdding(); // 더 이상 추가할 항목이 없음을 알림
});

// 소비자
var consumer = Task.Run(() =>
{
    foreach (int item in collection.GetConsumingEnumerable())
    {
        // 항목이 없으면 여기서 블로킹되어 대기하다가,
        // 새 항목이 들어오면 자동으로 깨어나 처리한다
        Console.WriteLine($"소비: {item}");
    }
    // CompleteAdding()이 호출되고 남은 항목을 모두 소비하면 루프가 자연스럽게 종료된다
});

await Task.WhenAll(producer, consumer);
```

### 핵심 메서드

- `Add(T item)`: 항목을 추가합니다. `BoundedCapacity`(용량 제한)가 설정되어 있고 컬렉션이 가득 찼다면, 공간이 생길 때까지 호출한 스레드를 블로킹합니다.
- `Take()`: 항목을 꺼냅니다. 컬렉션이 비어 있으면 새 항목이 추가되거나 `CompleteAdding()`이 호출될 때까지 블로킹합니다. 비어 있는 상태에서 `CompleteAdding()`이 이미 호출되었다면 `InvalidOperationException`을 던집니다.
- `TryAdd`/`TryTake`: 블로킹 대신 제한 시간(timeout)이나 즉시 반환을 선택할 수 있는 버전입니다.
- `CompleteAdding()`: "이제 더 이상 항목이 추가되지 않는다"는 신호를 보냅니다. 이후 `Add()`를 호출하면 `InvalidOperationException`이 발생합니다.
- `GetConsumingEnumerable()`: `foreach`로 순회할 수 있는 열거자를 반환합니다. 항목이 없으면 블로킹하며 대기하고, `CompleteAdding()`이 호출되고 남은 모든 항목을 소진하면 열거가 자연스럽게 종료됩니다. 별도의 종료 플래그를 두지 않아도 `foreach` 루프가 스스로 끝나는 것이 큰 장점입니다.
- `IsAddingCompleted`: `CompleteAdding()`이 호출되었는지 여부.
- `IsCompleted`: `CompleteAdding()`이 호출되었고 컬렉션도 완전히 비었는지 여부.

### 용량 제한과 배압(backpressure)

생산자가 소비자보다 훨씬 빠르게 항목을 만들어내면 컬렉션이 무한정 커지면서 메모리를 과도하게 소비할 수 있습니다. `BoundedCapacity`를 지정하면 컬렉션이 가득 찼을 때 `Add()`가 소비자가 항목을 꺼내갈 때까지 생산자를 블로킹시켜, 생산 속도를 소비 속도에 맞추는 배압 효과를 자연스럽게 얻을 수 있습니다.

```csharp
var collection = new BlockingCollection<int>(boundedCapacity: 100);
```

### 여러 생산자와 여러 소비자

`BlockingCollection<T>`는 다수의 생산자와 다수의 소비자가 동시에 접근하는 상황에서도 안전합니다. 다만 여러 생산자가 있는 경우 `CompleteAdding()`은 **모든 생산자가 작업을 끝낸 뒤** 단 한 번 호출해야 합니다. 일반적으로는 `Task.WhenAll`로 모든 생산자 태스크가 끝난 뒤 `CompleteAdding()`을 호출하는 방식을 사용합니다.

```csharp
var collection = new BlockingCollection<int>(boundedCapacity: 50);

var producers = Enumerable.Range(0, 3).Select(id => Task.Run(() =>
{
    for (int i = 0; i < 20; i++)
    {
        collection.Add(id * 100 + i);
    }
})).ToArray();

var consumers = Enumerable.Range(0, 2).Select(_ => Task.Run(() =>
{
    foreach (var item in collection.GetConsumingEnumerable())
    {
        Process(item);
    }
})).ToArray();

await Task.WhenAll(producers);
collection.CompleteAdding(); // 모든 생산자가 끝난 뒤 한 번만 호출

await Task.WhenAll(consumers);
```

### 다른 컬렉션과 조합하기

`BlockingCollection<T>`의 생성자는 내부에서 사용할 `IProducerConsumerCollection<T>` 구현체를 지정할 수 있습니다. 기본값은 `ConcurrentQueue<T>`(FIFO)지만, LIFO 순서가 필요하면 `ConcurrentStack<T>`를, 순서가 무관하다면 `ConcurrentBag<T>`를 넘겨서 블로킹 동작과 원하는 순서 정책을 조합할 수 있습니다.

```csharp
var lifoBlockingCollection = new BlockingCollection<int>(new ConcurrentStack<int>());
```

### 16장을 향한 예고

`BlockingCollection<T>`는 .NET에서 오랫동안 생산자-소비자 패턴의 표준적인 선택지였습니다. 하지만 근본적으로 **동기(synchronous) API** 위에 설계되어 있어서, `Take()`나 `GetConsumingEnumerable()`로 대기하는 스레드는 항목이 들어올 때까지 스레드 풀 스레드를 점유한 채 블로킹됩니다. 9~11장에서 다룬 `async`/`await` 기반 비동기 코드와 자연스럽게 어우러지지 않는다는 한계가 있습니다.

16장에서 다룰 `System.Threading.Channels`의 `Channel<T>`는 같은 생산자-소비자 문제를 `await WriteAsync()`, `await ReadAsync()`처럼 완전히 비동기적인 API로 제공하여, 대기 중에도 스레드를 점유하지 않는다는 점에서 `BlockingCollection<T>`와 대비됩니다. 두 컬렉션 모두 생산자-소비자 패턴을 위한 도구라는 목적은 같지만, `BlockingCollection<T>`는 동기 코드 기반 워커 스레드 모델에, `Channel<T>`는 비동기 코드 기반 모델에 적합하다는 차이를 16장에서 자세히 비교합니다.

## 선택 기준표

| 상황 | 권장 컬렉션 |
|---|---|
| 키-값 쌍을 여러 스레드가 읽고 쓰며, 캐시나 카운터처럼 원자적 조회/갱신이 필요 | `ConcurrentDictionary<TKey, TValue>` |
| 여러 스레드가 작업 항목을 순서대로(FIFO) 큐에 넣고 꺼내야 함 | `ConcurrentQueue<T>` |
| 나중에 들어온 항목을 먼저 처리해야 함(LIFO) | `ConcurrentStack<T>` |
| 순서가 무관하고, 같은 스레드가 넣고 빼는 패턴이 많음 | `ConcurrentBag<T>` |
| 소비자가 항목이 생길 때까지 대기해야 하는 동기 생산자-소비자 패턴 | `BlockingCollection<T>` |
| 생산 속도를 소비 속도에 맞춰 제한(배압)해야 함 | `BlockingCollection<T>` (`BoundedCapacity` 지정) |
| `async`/`await` 기반의 비동기 생산자-소비자 패턴 | `Channel<T>` (16장) |
| 읽기가 압도적으로 많고 쓰기가 드묾 | 읽기 전용 스냅샷을 만들어 공유하거나, `ReaderWriterLockSlim`(4장)으로 보호한 일반 컬렉션 검토 |
| 단일 스레드에서만 접근함이 확실함 | 굳이 동시성 컬렉션을 쓸 필요 없음. `List<T>`, `Dictionary<TKey, TValue>` 등 일반 컬렉션이 더 빠르다 |

마지막 항목이 특히 중요합니다. 동시성 컬렉션은 내부 동기화 메커니즘 때문에 일반 컬렉션보다 오버헤드가 있습니다. 실제로 여러 스레드가 동시에 접근하지 않는 상황이라면 일반 컬렉션을 사용하는 것이 더 빠르고 단순합니다. "혹시 모르니까"라는 이유로 모든 컬렉션을 동시성 컬렉션으로 바꾸는 것은 불필요한 성능 저하로 이어질 수 있습니다.

## 요약

- `List<T>`, `Dictionary<TKey, TValue>` 등 BCL의 기본 컬렉션은 스레드 안전하지 않으며, 여러 스레드가 동시에 접근하면 3장에서 다룬 경쟁 조건으로 인해 데이터 유실, 예외, 심지어 내부 구조 손상까지 발생할 수 있다.
- `ConcurrentDictionary<TKey, TValue>`는 `TryAdd`, `TryUpdate`, `TryRemove`, `GetOrAdd`, `AddOrUpdate` 등 확인-후-실행 패턴을 원자적으로 수행하는 메서드를 제공한다. 단, `GetOrAdd`/`AddOrUpdate`의 팩토리 델리게이트는 경합 시 중복 호출될 수 있다는 점에 유의해야 한다.
- `ConcurrentQueue<T>`(FIFO), `ConcurrentStack<T>`(LIFO), `ConcurrentBag<T>`(순서 없음, 스레드-로컬 최적화)는 각각 다른 순서 정책과 성능 특성을 가지며, 작업 패턴에 맞게 선택해야 한다.
- `BlockingCollection<T>`는 항목이 없을 때 소비자를 블로킹하고, 항목이 추가되면 깨우는 동기 생산자-소비자 컬렉션이다. `Add()`/`Take()`, `GetConsumingEnumerable()`, `CompleteAdding()`으로 생산자-소비자 흐름 종료까지 자연스럽게 처리할 수 있다.
- `BlockingCollection<T>`는 동기 API 기반이라 대기 중에도 스레드를 점유한다는 한계가 있으며, 완전히 비동기적인 생산자-소비자 패턴이 필요하다면 16장에서 다룰 `Channel<T>`가 대안이 된다.
- 동시성 컬렉션은 내부 동기화 비용이 있으므로, 실제로 여러 스레드가 동시 접근하지 않는 상황에서는 일반 컬렉션을 사용하는 것이 더 효율적이다.

## 연습문제

1. 여러 스레드가 동시에 `Dictionary<string, int>`에 값을 추가하는 코드를 작성해 `InvalidOperationException` 또는 데이터 손상이 발생하는 것을 재현해 보고, 이를 `ConcurrentDictionary<string, int>`로 교체해 문제를 해결하세요.
2. `ConcurrentDictionary<TKey, TValue>.GetOrAdd`의 팩토리 델리게이트가 경합 상황에서 여러 번 호출될 수 있음을 보여주는 예제를 작성하고, `Lazy<T>`를 이용해 정확히 한 번만 호출되도록 수정하세요.
3. `ConcurrentQueue<T>`와 `ConcurrentBag<T>`에 각각 100만 개의 항목을 추가한 뒤 같은 스레드에서 모두 꺼내는 벤치마크를 작성해 성능 차이를 비교하고, 그 차이가 나는 이유를 설명해 보세요.
4. `BlockingCollection<T>`를 사용해 생산자 3개, 소비자 2개로 구성된 파이프라인을 구현하고, `BoundedCapacity`를 설정했을 때와 설정하지 않았을 때 메모리 사용량과 처리 흐름이 어떻게 달라지는지 관찰하세요.
5. 이번 장의 선택 기준표를 참고하여, 여러분이 최근에 작성했던(또는 익숙한) 코드에서 일반 컬렉션을 동시성 컬렉션으로 바꿔야 할 지점이 있는지, 혹은 반대로 불필요하게 동시성 컬렉션을 사용하고 있는 지점이 있는지 점검해 보세요.

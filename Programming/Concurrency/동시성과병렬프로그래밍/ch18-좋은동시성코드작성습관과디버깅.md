# 18장. 좋은 동시성 코드 작성 습관과 디버깅

[◀ 이전: 17장. 스레드 안전성과 메모리 모델](ch17-스레드안전성과메모리모델.md) | [📖 목차](00-목차.md) | [다음: 부록 ▶](appendix-부록.md)


이 책의 마지막 본문 장입니다. 지금까지 스레드, Task, async/await, 병렬 프로그래밍, 동시성 컬렉션, Channel, 그리고 방금 17장에서 살펴본 메모리 모델까지 .NET이 제공하는 동시성 도구를 층위별로 살펴봤습니다. 도구를 아는 것과 그 도구로 신뢰할 수 있는 코드를 쓰는 것은 다른 문제입니다. 이 장에서는 실무에서 반복적으로 마주치는 안티패턴을 정리하고, 데드락과 경쟁 상태를 디버깅하는 접근법, 그리고 동시성 코드의 성능을 해치는 흔한 실수를 짚어봅니다. 마지막으로 이 책 전체를 관통하는 핵심 개념을 되짚어보고, 앞으로 더 공부할 만한 방향을 제안하며 마무리합니다.

## 흔한 안티패턴 정리

### async void

9장에서 다뤘듯, `async` 메서드의 반환 타입으로는 `Task`, `Task<TResult>`, `ValueTask<TResult>`, 그리고 이벤트 처리기를 위한 `async void`를 사용할 수 있습니다. 문제는 `async void` 메서드 안에서 예외가 발생했을 때입니다. `Task`를 반환하는 `async` 메서드는 예외를 반환된 `Task` 객체 안에 담아두므로, 호출자가 `await`하거나 `Task.Exception`을 확인하는 시점에 예외를 관찰할 수 있습니다. 반면 `async void` 메서드는 결과를 담을 `Task`가 없으므로, 예외가 발생하면 그 즉시 메서드를 호출한 `SynchronizationContext`로 직접 던져집니다. 이렇게 던져진 예외는 어디에서도 `catch`로 잡을 수 없고, 결국 처리되지 않은 예외로 취급되어 대부분의 경우 프로세스 자체를 종료시킵니다.

```csharp
// 위험: 예외가 발생하면 호출자가 이를 catch할 방법이 없다
private async void Button_Click(object sender, EventArgs e)
{
    await Task.Delay(1000);
    throw new InvalidOperationException("처리 중 오류 발생");
}
```

`async void`가 정당화되는 유일한 상황은 UI 프레임워크의 이벤트 처리기처럼 반환 타입을 프레임워크가 강제하는 경우뿐입니다. 그 경우에도 메서드 본문 전체를 `try`/`catch`로 감싸 예외가 밖으로 새어나가지 않도록 방어하는 것이 안전합니다. 그 외의 모든 경우, 즉 직접 호출하는 메서드나 라이브러리로 노출하는 API라면 예외 없이 `async Task`를 사용해야 합니다.

### .Result와 .Wait() 남용

10장에서 살펴본 데드락 함정도 실무에서 여전히 가장 흔하게 재발하는 실수 중 하나입니다. `Task<TResult>.Result`나 `Task.Wait()`는 비동기 작업이 끝날 때까지 현재 스레드를 동기적으로 블로킹합니다. UI 애플리케이션이나 ASP.NET(Classic) 환경처럼 `SynchronizationContext`가 하나의 스레드로 계속 작업을 이어붙이는 구조에서는, 그 스레드에서 `.Result`를 호출하는 순간 다음과 같은 순환이 만들어질 수 있습니다.

- 원래 스레드가 `.Result`를 호출하며 블로킹된다.
- `await`로 넘어간 비동기 작업이 완료된 뒤, 이어질 코드를 원래의 `SynchronizationContext`(즉 원래 스레드)로 되돌리려 한다.
- 원래 스레드는 이미 `.Result`에서 멈춰 있으므로 이어질 코드를 실행할 수 없다.
- 결과적으로 아무도 진행하지 못하는 데드락이 발생한다.

```csharp
// 위험: UI 스레드나 ASP.NET Classic 요청 스레드에서 호출하면 데드락 가능성이 있다
public void LoadData()
{
    string data = FetchDataAsync().Result;
    Display(data);
}
```

해법은 두 가지로 요약됩니다. 가능하다면 호출 체인 전체를 `async`/`await`로 끝까지 이어가서 애초에 블로킹 호출 자체를 만들지 않는 것이 최선입니다. 라이브러리 코드처럼 블로킹이 불가피한 극히 예외적인 상황이라면 `ConfigureAwait(false)`로 원래 컨텍스트로 돌아가지 않도록 지정해 순환 자체를 끊을 수 있지만, 이는 근본적인 해결책이라기보다 임시방편에 가깝다는 점을 10장에서 강조했습니다. 콘솔 애플리케이션처럼 `SynchronizationContext`가 없는 환경에서는 이 데드락이 재현되지 않기 때문에, 로컬에서는 멀쩡히 동작하던 코드가 IIS에 배포한 뒤에야 멈춰버리는 경우가 드물지 않습니다.

### 과도한 락 사용으로 인한 병목

락은 데이터를 안전하게 지켜주지만 공짜가 아닙니다. 임계 구역이 필요 이상으로 넓거나, 서로 무관한 데이터를 굳이 같은 락 하나로 묶어서 보호하면, 실제로는 동시에 실행해도 안전한 코드들이 순서를 기다리며 줄을 서게 됩니다. 이런 코드는 컴파일도 되고 겉보기에 정확하게 동작하지만, 코어를 여러 개 갖춘 서버에서도 사실상 한 번에 한 스레드씩만 일하는 것과 다름없는 상태가 됩니다.

```csharp
// 병목이 되기 쉬운 예: 서로 무관한 두 컬렉션에 대한 접근을 하나의 락으로 묶었다
private readonly object _lock = new();
private readonly List<Order> _orders = new();
private readonly List<AuditLogEntry> _auditLog = new();

public void RecordOrder(Order order)
{
    lock (_lock)
    {
        _orders.Add(order);
        // 감사 로그 기록은 주문 목록과 무관하지만 같은 락을 공유하고 있다
        _auditLog.Add(new AuditLogEntry(order.Id, DateTimeOffset.UtcNow));
    }
}

public IReadOnlyList<Order> GetOrders()
{
    lock (_lock)
    {
        return _orders.ToList();
    }
}
```

`_orders`를 읽는 요청과 `_auditLog`에 기록하는 요청이 서로 다른 데이터를 다루는데도 같은 락을 두고 경쟁하게 됩니다. 이런 병목은 뒤에서 다시 다룰 "동기화 범위 최소화"와 "세밀한 락" 원칙으로 완화할 수 있습니다.

## 데드락 디버깅하기

데드락은 재현되는 순간에는 명확하지만, 왜 멈췄는지 코드만 봐서는 한눈에 드러나지 않는 경우가 많습니다. Visual Studio는 이런 상황을 진단하기 위한 전용 도구를 제공합니다.

프로그램이 멈춘 것처럼 보일 때 디버거로 프로세스에 중단점을 걸거나 일시 중지시키면, **스레드(Threads) 창**에서 현재 실행 중이거나 대기 중인 모든 스레드의 목록과 각 스레드가 멈춰 있는 위치(콜 스택의 맨 위 프레임)를 확인할 수 있습니다. 여러 스레드가 각각 `Monitor.Enter`나 `SemaphoreSlim.Wait` 같은 대기 메서드 안에서 멈춰 있다면, 그 스레드들이 서로 어떤 자원을 기다리고 있는지가 데드락을 의심해볼 첫 번째 단서가 됩니다.

**병렬 스택(Parallel Stacks) 창**은 여기서 한 걸음 더 나아가, 여러 스레드의 콜 스택을 하나의 그래프로 시각화해서 보여줍니다. 같은 메서드에서 멈춰 있는 스레드들은 하나의 노드로 묶여 표시되고, 스레드 사이의 호출 관계를 화살표로 연결해서 보여주기 때문에 "스레드 A가 실행하는 메서드와 스레드 B가 실행하는 메서드가 서로 어떤 자원을 통해 얽혀 있는지"를 텍스트로 된 스레드 목록보다 훨씬 직관적으로 파악할 수 있습니다. Task 기반 코드를 디버깅할 때는 이 창의 Tasks 보기를 사용하면, 어떤 `Task`가 아직 완료되지 않은 채 다른 `Task`의 완료를 기다리고 있는지도 함께 확인할 수 있습니다.

이런 도구들을 활용해 데드락을 진단하는 절차는 대략 다음과 같은 흐름을 따릅니다.

1. 프로그램이 멈춘 상태에서 디버거로 일시 중지하고 스레드 창을 연다.
2. 어떤 스레드들이 실제로 진행하지 못하고 대기 메서드 안에 머물러 있는지 확인한다.
3. 병렬 스택 창에서 각 스레드의 콜 스택을 살펴보고, 어떤 락이나 세마포어, 어떤 `Task`의 완료를 기다리고 있는지 프레임을 따라 확인한다.
4. 서로 다른 두 스레드가 상대방이 쥐고 있는 자원을 각각 기다리고 있는 순환 구조가 보이면, 그것이 데드락의 원인이다.

이 과정을 개념 수준에서 익혀두면, 운영 환경에서 수집한 덤프 파일을 분석할 때도 같은 사고방식을 그대로 적용할 수 있습니다. 결국 데드락 디버깅의 핵심은 "멈춰 있는 각 스레드가 무엇을 기다리고 있는지"를 하나씩 추적해서 순환 고리를 찾아내는 일입니다.

## 경쟁 상태는 왜 재현하기 어려운가

경쟁 상태는 데드락과 다른 종류의 어려움을 안고 있습니다. 데드락은 한 번 발생하면 프로그램이 완전히 멈추기 때문에 최소한 "문제가 있다"는 사실은 명확하게 드러납니다. 반면 경쟁 상태는 스레드 스케줄링의 미묘한 타이밍에 의존하기 때문에, 대부분의 실행에서는 아무 문제 없이 지나가다가 아주 드문 순서로 명령어가 인터리빙될 때만 겉으로 드러납니다. 개발자의 컴퓨터에서 수백 번을 실행해도 재현되지 않던 버그가 운영 서버에서, 그것도 부하가 몰리는 특정 시간대에만 나타나는 경우가 드물지 않은 이유입니다. 디버거로 한 줄씩 실행하며 확인하려는 순간 그 자체가 타이밍을 바꿔버려서 버그가 사라지는, 1장에서 언급한 "하이젠버그" 현상도 같은 맥락입니다.

이런 특성 때문에 경쟁 상태는 발생한 뒤에 로그와 재현 시도만으로 잡아내려 하기보다, 애초에 코드 리뷰 단계에서 의심스러운 패턴을 걸러내는 습관이 훨씬 비용 효율적입니다. 코드를 리뷰할 때 다음과 같은 질문을 스스로에게 던져보는 것이 도움이 됩니다.

- 이 필드나 컬렉션은 둘 이상의 스레드(또는 둘 이상의 Task, 콜백)에서 접근할 가능성이 있는가?
- 그 접근 중 하나라도 값을 변경하는 쓰기 연산인가, 아니면 전부 읽기 전용인가?
- 읽기와 쓰기가 섞여 있다면, 그 접근은 `lock`이나 동시성 컬렉션, `Interlocked`, 혹은 17장에서 다룬 불변성 중 어떤 방식으로 보호되고 있는가?
- "지금 당장은 이 메서드가 한 스레드에서만 호출된다"는 가정에 기대고 있는 코드는 아닌가? 그 가정이 나중에 깨질 가능성은 없는가?

이 네 가지 질문에 답할 수 없는 공유 상태를 발견했다면, 그것이 경쟁 상태의 후보지입니다. 리뷰어의 역할은 버그를 직접 재현해 증명하는 것이 아니라, "이 접근은 안전한가?"라는 질문을 코드에 남겨두는 것만으로도 충분한 가치가 있습니다.

## 성능 고려사항: 동기화 범위와 락의 세밀도

### 동기화 범위 최소화

`lock` 블록 안에 들어가는 코드가 많아질수록, 그 락을 다른 스레드가 기다리는 시간도 함께 늘어납니다. 임계 구역 안에는 실제로 공유 상태를 다루는 최소한의 코드만 남기고, 네트워크 호출이나 파일 I/O, 로깅처럼 시간이 걸리거나 락과 무관한 작업은 임계 구역 밖으로 빼내는 것이 기본 원칙입니다.

```csharp
// 개선 전: 락을 잡은 채로 오래 걸리는 로깅까지 수행한다
lock (_lock)
{
    _orders.Add(order);
    _logger.LogInformation("주문 {OrderId} 추가됨", order.Id); // 락 안에 있을 필요가 없다
}

// 개선 후: 공유 상태를 다루는 부분만 락으로 보호한다
lock (_lock)
{
    _orders.Add(order);
}
_logger.LogInformation("주문 {OrderId} 추가됨", order.Id);
```

### 세밀한 락(fine-grained)과 굵은 락(coarse-grained)의 트레이드오프

락의 범위를 데이터 단위로 얼마나 잘게 나누는지도 중요한 설계 결정입니다. 앞서 안티패턴에서 본 것처럼 서로 무관한 데이터를 하나의 락으로 묶는 굵은 락(coarse-grained lock)은 구현이 단순하고 데드락 위험도 낮지만, 스레드 간 경쟁이 심해질수록 병렬로 처리할 수 있었던 작업까지 순차적으로 밀어내는 병목이 됩니다.

```csharp
// 세밀한 락: 주문과 감사 로그를 각각 다른 락으로 보호한다
private readonly object _ordersLock = new();
private readonly object _auditLogLock = new();

public void RecordOrder(Order order)
{
    lock (_ordersLock)
    {
        _orders.Add(order);
    }

    lock (_auditLogLock)
    {
        _auditLog.Add(new AuditLogEntry(order.Id, DateTimeOffset.UtcNow));
    }
}
```

락을 데이터별로 잘게 나누면 서로 무관한 작업들이 동시에 진행될 수 있어 처리량이 늘어나지만, 대가도 따릅니다. 락의 개수가 늘어날수록 코드가 복잡해지고, 한 연산이 여러 락을 동시에 필요로 하는 상황이 생기면 락을 획득하는 순서가 스레드마다 어긋나면서 4장에서 다룬 것과 같은 종류의 데드락 위험이 새로 생겨날 수 있습니다. 또한 락 하나하나를 획득하고 해제하는 데도 미세한 비용이 들기 때문에, 경쟁이 거의 없는 상황에서는 오히려 굵은 락 하나가 세밀한 락 여러 개보다 단순하고 빠를 수도 있습니다.

정답은 하나로 정해져 있지 않습니다. 실무에서는 다음과 같은 순서로 접근하는 것이 안전합니다. 먼저 이해하기 쉬운 굵은 락으로 정확성을 확보하고, 성능 측정(프로파일링) 결과 실제로 그 락이 병목으로 드러났을 때만 데이터 접근 패턴을 분석해서 잠금을 세분화합니다. 측정 없이 미리 잘게 쪼개면 복잡성만 늘어나고 실제 이득은 없는 경우가 많습니다. 그리고 14장에서 다룬 `ConcurrentDictionary<TKey, TValue>` 같은 동시성 컬렉션은 내부적으로 이미 세밀한 락 또는 락-프리 기법으로 구현되어 있으므로, 직접 락을 설계하기 전에 이런 기존 도구로 문제를 해결할 수 없는지부터 검토하는 것이 좋습니다.

## 이 책을 되돌아보며

여기까지 오면서 이 책은 저수준 도구에서 고수준 추상화로 층을 쌓아 올리는 순서를 따랐습니다. 2장의 `Thread`에서 출발해 3장과 4장의 동기화 프리미티브, 5장의 이벤트 기반 신호, 6장의 `ThreadPool`을 거쳐, 7장부터 11장까지 `Task`와 async/await를 중심으로 한 현대적인 비동기 프로그래밍 모델을 다뤘습니다. 이어서 12장과 13장의 `Parallel`/PLINQ로 데이터 병렬성을, 14장에서 16장까지 동시성 컬렉션과 비동기 스트림, Channel로 여러 스레드나 비동기 흐름 사이에서 데이터를 안전하게 주고받는 방법을 살펴봤고, 17장에서 그 밑바탕에 깔린 메모리 모델까지 확인했습니다.

이 여정 전체를 지탱하는 두 기둥을 꼽자면 다음과 같습니다.

**3장의 경쟁 상태**는 이 책이 다루는 거의 모든 문제의 출발점입니다. 여러 스레드가 같은 데이터를 동시에 건드릴 수 있다는 사실 자체가 락, `Interlocked`, 불변성, 동시성 컬렉션 등 이 책에서 소개한 모든 도구가 존재하는 이유입니다. 도구의 이름과 API는 장마다 달랐지만, 그 밑에 깔린 질문은 항상 "이 공유 데이터에 대한 접근이 안전하게 조율되고 있는가"였습니다.

**9장과 10장의 async/await**는 오늘날 .NET 애플리케이션에서 작성하는 동시성 코드의 대다수가 실제로 거쳐 가는 관문입니다. `Task`가 무엇을 표현하는지, `await`가 컴파일러 수준에서 어떻게 상태 기계로 변환되는지, `SynchronizationContext`가 이어지는 코드를 어느 스레드로 되돌려 보내는지를 정확히 이해하지 못하면, 이 장에서 다시 짚은 `async void`나 `.Result` 데드락 같은 실수를 반복하게 됩니다. 반대로 이 두 장의 내용을 확실히 익혀두면 11장의 취소, 15장의 비동기 스트림, 16장의 Channel처럼 그 위에 쌓인 개념들이 자연스럽게 이어져 보입니다.

이 두 장을 중심에 두고 나머지 장들을 되돌아보면, 이 책의 구성 전체가 "경쟁 상태를 어떻게 막을 것인가"와 "블로킹 없이 어떻게 기다릴 것인가"라는 두 질문에 대한 답을 층층이 쌓아 올린 것이었음을 알 수 있습니다.

## 더 공부할 방향

이 책은 .NET 동시성 프로그래밍의 핵심을 다뤘지만, 그 너머에는 더 깊이 파고들 만한 주제가 여전히 많이 남아 있습니다.

**TPL Dataflow**. `System.Threading.Tasks.Dataflow` 네임스페이스는 `BufferBlock<T>`, `TransformBlock<TInput, TOutput>`, `ActionBlock<T>` 같은 블록을 파이프라인 형태로 연결해 데이터 처리 흐름을 선언적으로 구성할 수 있게 해주는 라이브러리입니다. 16장에서 다룬 Channel이 생산자-소비자 관계를 저수준으로 표현하는 도구였다면, TPL Dataflow는 여러 단계로 이어지는 파이프라인과 병렬도 조절, 배치 처리 같은 패턴을 더 높은 추상화 수준에서 다룰 수 있게 해줍니다.

**분산 시스템에서의 동시성**. 이 책은 단일 프로세스 안에서 여러 스레드나 Task가 메모리를 공유하는 상황을 전제로 했습니다. 여러 대의 서버나 컨테이너에 걸쳐 상태를 공유해야 하는 분산 시스템에서는 이야기가 훨씬 복잡해집니다. 분산 락, 합의 알고리즘, 최종적 일관성(eventual consistency)처럼 네트워크 지연과 부분 장애를 전제로 한 새로운 개념들을 다뤄야 합니다.

**락-프리(lock-free) 자료구조**. 17장에서 `Interlocked.CompareExchange`를 이용한 아주 단순한 락-프리 패턴을 살펴봤습니다. 락-프리 스택이나 큐처럼 더 복잡한 자료구조를 직접 설계하려면 ABA 문제, 메모리 재사용 시점 관리 같은 훨씬 미묘한 주제까지 이해해야 합니다. .NET의 동시성 컬렉션 소스 코드를 직접 읽어보는 것도 이런 기법을 배우는 좋은 출발점이 됩니다.

이 밖에도 액터 모델(Actor model), 리액티브 프로그래밍(Reactive Extensions), 하드웨어 트랜잭셔널 메모리처럼 동시성을 다루는 또 다른 패러다임들도 있습니다. 이 책에서 다진 기초, 특히 경쟁 상태를 알아보는 눈과 async/await의 동작 원리에 대한 이해는 어떤 새로운 도구나 패러다임을 만나더라도 그대로 유효한 자산이 될 것입니다.

## 요약

- `async void`는 예외를 호출자가 잡을 수 없는 방식으로 던지므로, UI 이벤트 처리기처럼 반환 타입이 강제되는 경우가 아니라면 사용하지 않아야 합니다.
- `.Result`/`.Wait()`는 `SynchronizationContext`가 있는 환경에서 이어지는 코드가 돌아갈 스레드를 원래 스레드가 막고 있는 순환을 만들어 데드락을 유발할 수 있습니다. 호출 체인을 끝까지 `async`/`await`로 잇는 것이 근본적인 해법입니다.
- 서로 무관한 데이터를 하나의 락으로 묶거나 임계 구역을 필요 이상으로 넓게 잡으면, 병렬로 처리될 수 있었던 작업들이 줄지어 대기하는 병목이 됩니다.
- Visual Studio의 스레드 창과 병렬 스택 창은 각 스레드가 멈춰 있는 지점과 서로 기다리는 관계를 시각적으로 보여주어 데드락의 순환 고리를 찾는 데 도움을 줍니다.
- 경쟁 상태는 타이밍에 의존하기 때문에 재현하기 어렵고, 발생한 뒤 잡아내려 하기보다 코드 리뷰에서 공유 상태 접근을 의심하는 습관이 더 효과적입니다.
- 동기화 범위는 필요한 최소 범위로 줄이는 것이 기본이며, 락의 세밀도는 정확성을 먼저 확보한 뒤 측정 결과에 따라 조정하는 것이 안전합니다.
- 이 책 전체는 3장의 경쟁 상태와 9~10장의 async/await를 두 축으로 삼아 저수준 도구에서 고수준 추상화로 쌓아 올린 구성이며, TPL Dataflow, 분산 동시성, 락-프리 자료구조가 앞으로 더 살펴볼 만한 방향입니다.

## 연습문제

1. 자신이 작성했거나 접해본 코드에서 `async void`가 사용된 사례를 찾아보고, 그것이 이벤트 처리기처럼 정당한 사용인지 아니면 `async Task`로 바꿔야 하는 경우인지 판단해보세요.
2. `.Result`로 인한 데드락이 콘솔 애플리케이션에서는 재현되지 않고 UI 애플리케이션이나 ASP.NET(Classic) 환경에서만 재현되는 이유를 `SynchronizationContext` 관점에서 설명하세요.
3. 서로 무관한 두 개의 컬렉션을 하나의 락으로 보호하고 있는 코드를 예로 들고, 이를 세밀한 락으로 분리했을 때 새로 주의해야 할 데드락 위험은 무엇인지 서술하세요.
4. 병렬 스택 창이 일반 스레드 창보다 데드락 진단에 유리한 점은 무엇인지 설명하세요.
5. 이 책의 18개 장 중에서 자신의 실무나 학습에 가장 크게 도움이 된 장을 하나 꼽고, 그 이유와 함께 앞으로 더 깊이 공부하고 싶은 주제(TPL Dataflow, 분산 시스템 동시성, 락-프리 자료구조 등)를 정해보세요.

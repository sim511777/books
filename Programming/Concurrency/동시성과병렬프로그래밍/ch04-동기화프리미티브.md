[◀ 이전: 3장. 스레드 동기화 기초](ch03-스레드동기화기초.md) | [📖 목차](00-목차.md) | [다음: 5장. 이벤트 기반 동기화 ▶](ch05-이벤트기반동기화.md)


3장에서는 `lock` 키워드와 그 근간이 되는 `Monitor` 클래스를 이용해 임계 영역을 보호하는 방법을 배웠다. 하지만 `lock`/`Monitor`는 만능이 아니다. 예를 들어 프로세스 경계를 넘어서 동기화해야 하거나, "한 번에 하나"가 아니라 "한 번에 N개까지"의 접근을 허용해야 하거나, 읽기 작업이 압도적으로 많은 상황에서 읽기끼리는 서로 막지 않도록 하고 싶을 때는 `lock`만으로 충분하지 않다. 이 장에서는 이러한 상황에 맞춰 설계된 세 가지 동기화 도구인 `Mutex`, `Semaphore`/`SemaphoreSlim`, `ReaderWriterLockSlim`을 살펴본다.

## 4.1 Mutex: 프로세스 경계를 넘나드는 잠금

### 4.1.1 lock과 Mutex의 근본적인 차이

`System.Threading.Mutex`(Mutual Exclusion의 줄임말)는 `lock`과 마찬가지로 한 번에 하나의 스레드만 보호된 영역에 진입시키는 상호 배제 도구다. 기능적으로만 보면 `lock`과 크게 다르지 않아 보이지만, 결정적인 차이가 하나 있다.

- `lock`(`Monitor`)은 **같은 프로세스 안에서만** 유효하다. CLR이 관리하는 객체의 동기화 정보를 기반으로 동작하기 때문에, 다른 프로세스에서 실행 중인 코드는 애초에 그 객체에 접근할 수조차 없다.
- `Mutex`는 운영체제 커널이 관리하는 동기화 객체이기 때문에, **이름을 지정하면 서로 다른 프로세스에 속한 스레드들 사이에서도 상호 배제를 보장**할 수 있다.

즉, `Mutex`는 "이 컴퓨터에서 이 애플리케이션의 인스턴스가 동시에 두 개 이상 실행되지 않도록 막는다"거나 "여러 프로세스가 같은 파일에 순서대로만 접근하게 한다"와 같이, 스레드가 아니라 **프로세스 단위**의 동기화가 필요할 때 사용하는 도구다. 반대로 프로세스 내부의 여러 스레드만 동기화하면 되는 대부분의 경우에는, 커널 객체를 사용하는 `Mutex`보다 훨씬 가벼운 `lock`을 사용하는 것이 성능 면에서 유리하다.

### 4.1.2 로컬 Mutex 사용법

이름 없는(local) `Mutex`는 `lock`과 비슷하게 사용할 수 있다.

```csharp
using System;
using System.Threading;

class Program
{
    private static readonly Mutex _mutex = new Mutex();
    private static int _sharedValue = 0;

    static void Worker(int id)
    {
        for (int i = 0; i < 100000; i++)
        {
            _mutex.WaitOne(); // 잠금 획득 (획득할 때까지 대기)
            try
            {
                _sharedValue++;
            }
            finally
            {
                _mutex.ReleaseMutex(); // 반드시 해제
            }
        }
        Console.WriteLine($"Worker {id} 종료");
    }

    static void Main()
    {
        Thread t1 = new Thread(() => Worker(1));
        Thread t2 = new Thread(() => Worker(2));
        t1.Start();
        t2.Start();
        t1.Join();
        t2.Join();

        Console.WriteLine($"최종 값: {_sharedValue}"); // 200,000
    }
}
```

`Mutex`는 `WaitOne()`으로 잠금을 획득하고 `ReleaseMutex()`로 해제한다. `lock`이나 `Monitor`와 마찬가지로, 예외가 발생해도 잠금이 반드시 풀리도록 `try/finally` 패턴을 사용해야 한다. 다른 스레드가 이미 잠금을 보유하고 있다면 `WaitOne()`은 그 스레드가 `ReleaseMutex()`를 호출할 때까지 블로킹된다.

### 4.1.3 이름 있는 Mutex로 프로세스 간 동기화하기

`Mutex`의 진가는 이름을 지정했을 때 드러난다. 같은 이름의 `Mutex`를 생성하면, 운영체제가 그 이름으로 하나의 동기화 객체를 식별하여 서로 다른 프로세스에서도 동일한 잠금을 공유하게 된다. 대표적인 활용 예는 "애플리케이션 중복 실행 방지"다.

```csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        // 이 이름의 뮤텍스가 이미 시스템에 존재하는지 확인하면서 생성한다.
        using Mutex singleInstanceMutex = new Mutex(
            initiallyOwned: true,
            name: "Global\\MyCompany.MyApp.SingleInstance",
            createdNew: out bool isNewInstance);

        if (!isNewInstance)
        {
            Console.WriteLine("이미 프로그램이 실행 중입니다. 종료합니다.");
            return;
        }

        Console.WriteLine("프로그램을 시작합니다. 아무 키나 누르면 종료합니다.");
        Console.ReadKey();

        singleInstanceMutex.ReleaseMutex();
    }
}
```

여기서 `createdNew`로 넘긴 `out bool` 값은, 이 이름을 가진 뮤텍스가 시스템에 이미 존재했는지(`false`) 아니면 이번 호출로 새로 만들어졌는지(`true`)를 알려준다. 같은 프로그램을 두 번째로 실행하면 첫 번째 인스턴스가 이미 만들어 둔 이름의 뮤텍스가 존재하므로 `isNewInstance`가 `false`가 되어, 두 번째 인스턴스는 스스로 종료한다. 이름 앞의 `Global\\` 접두사는 하나의 운영체제 세션(터미널 서비스의 여러 세션 등)을 넘어 시스템 전체에서 이름을 공유하겠다는 의미다.

`Mutex`는 이렇게 커널 객체를 통해 프로세스 경계를 넘나드는 대신, `lock`보다 무거운 자원(커널 전환 비용)을 사용한다. 따라서 단순히 한 프로세스 안의 여러 스레드만 동기화하면 되는 상황이라면 `Mutex`를 선택할 이유가 없다.

## 4.2 Semaphore와 SemaphoreSlim: 동시 접근 개수 제한하기

`lock`과 `Mutex`는 "한 번에 하나의 스레드만" 허용하는 도구다. 하지만 실무에서는 "한 번에 최대 N개까지는 동시에 허용하고 싶다"는 요구가 자주 등장한다. 예를 들어 외부 API 호출을 동시에 최대 5개까지만 허용하고 싶다거나, 커넥션 풀에서 동시에 사용 가능한 커넥션 수를 제한하고 싶은 경우다. 이럴 때 사용하는 것이 카운팅 세마포어(counting semaphore)다.

### 4.2.1 세마포어의 기본 개념

세마포어는 내부적으로 "허용 가능한 남은 슬롯 수(count)"를 가지고 있다. 스레드가 세마포어에 진입을 시도하면 카운트를 하나 줄이고, 카운트가 0보다 크면 즉시 진입할 수 있다. 카운트가 이미 0이면 다른 스레드가 슬롯을 반환할 때까지 대기한다. 작업을 마친 스레드는 슬롯을 반환하여 카운트를 다시 하나 늘려준다.

.NET에는 두 가지 구현이 있다.

- **`System.Threading.Semaphore`**: `Mutex`처럼 운영체제 커널 객체를 기반으로 하며, 이름을 지정하면 프로세스 간에도 공유할 수 있다.
- **`System.Threading.SemaphoreSlim`**: 순수하게 관리되는(managed) 코드로 구현되어 있어 프로세스 내부에서 사용할 때 `Semaphore`보다 훨씬 가볍고 빠르다. 또한 `async`/`await`와 함께 사용할 수 있는 `WaitAsync()` 메서드를 제공한다. 프로세스 간 공유가 필요하지 않다면 대부분의 경우 `SemaphoreSlim`을 사용하는 것이 좋다.

### 4.2.2 SemaphoreSlim으로 동시 접근 제한하기: 커넥션 풀 예제

제한된 개수의 자원(예: 데이터베이스 커넥션)에 동시에 접근할 수 있는 스레드 수를 제한하는 상황을 예로 들어보자.

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

class ConnectionPoolSimulator
{
    // 동시에 최대 3개의 "커넥션"만 사용할 수 있다고 가정한다.
    private static readonly SemaphoreSlim _semaphore = new SemaphoreSlim(initialCount: 3, maxCount: 3);

    static async Task UseConnectionAsync(int requestId)
    {
        Console.WriteLine($"요청 {requestId}: 커넥션 대기 중...");

        await _semaphore.WaitAsync(); // 슬롯이 없으면 비동기적으로 대기
        try
        {
            Console.WriteLine($"요청 {requestId}: 커넥션 획득, 작업 시작 (남은 슬롯 {_semaphore.CurrentCount})");
            await Task.Delay(1000); // 실제로는 DB 쿼리 등 자원을 사용하는 작업
            Console.WriteLine($"요청 {requestId}: 작업 완료");
        }
        finally
        {
            _semaphore.Release(); // 사용이 끝난 슬롯을 반환
        }
    }

    static async Task Main()
    {
        Task[] tasks = new Task[10];
        for (int i = 0; i < 10; i++)
        {
            int requestId = i;
            tasks[i] = UseConnectionAsync(requestId);
        }

        await Task.WhenAll(tasks);
        Console.WriteLine("모든 요청 처리 완료");
    }
}
```

이 예제에서는 10개의 요청이 동시에 들어오지만, `SemaphoreSlim`의 최대 카운트가 3이므로 실제로 동시에 작업을 수행하는 요청은 항상 3개 이하로 유지된다. 나머지 요청들은 `WaitAsync()`에서 대기하다가, 앞선 요청이 `Release()`를 호출해 슬롯을 반환하는 순간 하나씩 깨어나 작업을 시작한다. 이렇게 하면 제한된 자원(여기서는 가상의 커넥션)에 한꺼번에 너무 많은 요청이 몰려 시스템이 과부하되는 것을 막을 수 있다.

`WaitOne()`/`Release()`(동기 버전, `Semaphore`와 `SemaphoreSlim` 모두 제공)와 `WaitAsync()`/`Release()`(비동기 버전, `SemaphoreSlim`만 제공)의 사용법은 거의 동일하다. 스레드를 블로킹해도 무방한 코드에서는 `Wait()`/`WaitOne()`을, `async` 메서드 안에서 스레드를 점유하지 않고 대기하고 싶다면 `WaitAsync()`를 사용하면 된다. 비동기 대기에 대해서는 9장과 10장에서 더 자세히 다룬다.

`SemaphoreSlim` 생성자의 `initialCount`는 시작 시점에 사용 가능한 슬롯 수, `maxCount`는 `Release()`를 통해 늘어날 수 있는 최대 슬롯 수를 의미한다. 대부분의 경우 두 값을 동일하게 지정한다. `Release()`를 필요 이상으로(즉, `maxCount`를 초과하도록) 호출하면 `SemaphoreFullException`이 발생하므로, `Wait`/`WaitAsync` 호출과 `Release` 호출의 쌍을 정확히 맞춰야 한다. 이 역시 `try/finally`(또는 `try` 블록에서 `WaitAsync`를 호출하기 전에 시작해, 획득 성공 이후의 코드만 `try`로 감싸는 패턴)로 관리하는 것이 안전하다.

### 4.2.3 이진 세마포어와 lock의 관계

`maxCount`를 1로 지정한 세마포어(이진 세마포어)는 `lock`과 비슷하게 한 번에 하나의 스레드만 허용한다. 하지만 결정적인 차이가 있다. `lock`(`Monitor`)은 잠금을 획득한 바로 그 스레드만 해제할 수 있는 **소유권(ownership)** 개념을 가지고 있지만, 세마포어에는 소유권 개념이 없다. 즉, 스레드 A가 획득한 세마포어 슬롯을 스레드 B가 `Release()`로 반환하는 것이 허용된다. 이 특성 때문에 세마포어는 "한 스레드가 신호를 기다리고 다른 스레드가 그 신호를 보내주는" 형태의 생산자-소비자 패턴에도 활용할 수 있다(이런 신호 기반 동기화는 5장에서 더 자세히 다룬다).

## 4.3 ReaderWriterLockSlim: 읽기와 쓰기를 구분하는 락

`lock`의 한 가지 한계는, 읽기 작업이든 쓰기 작업이든 구분 없이 무조건 하나의 스레드만 진입시킨다는 점이다. 하지만 많은 실전 상황에서 공유 데이터에 대한 접근은 쓰기보다 읽기가 압도적으로 많다. 예를 들어 설정 정보를 담은 캐시는 초기화 이후 거의 대부분 조회만 일어나고, 갱신은 드물게만 일어난다. 이런 상황에서 읽기 스레드끼리도 서로를 막아버리는 `lock`을 사용하면 불필요한 병목이 생긴다.

`System.Threading.ReaderWriterLockSlim`은 이 문제를 해결하기 위해 접근을 두 종류로 구분한다.

- **읽기 락(Read Lock)**: 여러 스레드가 동시에 읽기 락을 보유할 수 있다. 즉, 읽기끼리는 서로 막지 않는다.
- **쓰기 락(Write Lock)**: 오직 한 스레드만 쓰기 락을 보유할 수 있으며, 쓰기 락을 보유한 동안에는 다른 어떤 스레드도(읽기든 쓰기든) 진입할 수 없다.

즉, "여러 명이 동시에 읽는 것은 허용하되, 누군가 쓰는 동안에는 아무도 읽거나 쓸 수 없다"는 규칙이다. 이렇게 하면 읽기 작업들 사이의 불필요한 직렬화를 없애면서도 데이터 일관성은 그대로 유지할 수 있다.

### 4.3.1 사용 예제: 읽기가 빈번한 캐시

```csharp
using System;
using System.Collections.Generic;
using System.Threading;

class ConfigurationCache
{
    private readonly ReaderWriterLockSlim _rwLock = new ReaderWriterLockSlim();
    private readonly Dictionary<string, string> _settings = new Dictionary<string, string>();

    public string? GetSetting(string key)
    {
        _rwLock.EnterReadLock();
        try
        {
            return _settings.TryGetValue(key, out string? value) ? value : null;
        }
        finally
        {
            _rwLock.ExitReadLock();
        }
    }

    public void UpdateSetting(string key, string value)
    {
        _rwLock.EnterWriteLock();
        try
        {
            _settings[key] = value;
        }
        finally
        {
            _rwLock.ExitWriteLock();
        }
    }
}
```

`GetSetting`을 호출하는 스레드들은 서로 다른 스레드가 동시에 `GetSetting`을 호출해도 서로 막지 않고 병렬로 진행할 수 있다. 반면 `UpdateSetting`이 호출되어 쓰기 락을 획득하면, 그 순간 진행 중이던 다른 모든 읽기/쓰기 요청은 대기하게 되고, 쓰기가 끝난 뒤에야 다시 진행된다. 만약 이 클래스를 일반 `lock`으로 구현했다면, 100개의 스레드가 동시에 `GetSetting`만 호출하는 상황에서도 스레드들이 한 줄로 순서를 기다려야 했겠지만, `ReaderWriterLockSlim`을 사용하면 그 100개의 읽기 요청이 모두 동시에 처리될 수 있다.

### 4.3.2 업그레이드 가능한 락: EnterUpgradeableReadLock

"값이 있는지 확인하고, 없으면 새로 계산해서 캐시에 넣는다"처럼 읽기로 시작해서 조건에 따라 쓰기로 전환해야 하는 경우가 자주 있다. 이럴 때 읽기 락을 쓰기 락으로 직접 승격시키려 하면 데드락 위험이 있으므로, `ReaderWriterLockSlim`은 별도의 **업그레이드 가능한 읽기 락(upgradeable read lock)**을 제공한다.

```csharp
public string GetOrAdd(string key, Func<string> valueFactory)
{
    _rwLock.EnterUpgradeableReadLock();
    try
    {
        if (_settings.TryGetValue(key, out string? existing))
        {
            return existing;
        }

        _rwLock.EnterWriteLock();
        try
        {
            string newValue = valueFactory();
            _settings[key] = newValue;
            return newValue;
        }
        finally
        {
            _rwLock.ExitWriteLock();
        }
    }
    finally
    {
        _rwLock.ExitUpgradeableReadLock();
    }
}
```

업그레이드 가능한 읽기 락은 일반 읽기 락과 마찬가지로 다른 일반 읽기 락들과 공존할 수 있지만, **한 번에 하나의 스레드만 업그레이드 가능한 읽기 락을 보유**할 수 있다는 점이 다르다. 이 덕분에 이 락을 보유한 스레드가 안전하게 쓰기 락으로 전환(승격)할 수 있다. 만약 두 스레드가 동시에 일반 읽기 락을 쓰기 락으로 바꾸려 하면 서로가 서로를 기다리는 데드락이 생기지만, 업그레이드 가능한 읽기 락은 애초에 한 스레드만 가질 수 있으므로 이런 충돌이 원천적으로 차단된다.

### 4.3.3 언제 lock보다 효율적인가

`ReaderWriterLockSlim`이 항상 `lock`보다 빠른 것은 아니다. `ReaderWriterLockSlim`은 읽기/쓰기 상태를 관리하기 위해 `Monitor` 기반의 단순한 `lock`보다 더 많은 내부 상태를 유지하고 더 복잡한 로직을 수행하므로, 락을 획득/해제하는 단일 연산 자체의 오버헤드는 `lock`보다 크다.

`ReaderWriterLockSlim`이 이득을 보는 조건은 다음과 같다.

- **읽기 작업의 빈도가 쓰기 작업보다 훨씬 높다.**
- **임계 영역 안에서 수행하는 작업(읽기 자체)이 락 획득/해제 오버헤드에 비해 충분히 무겁다.** 아주 짧은 읽기 작업이라면 여러 스레드가 병렬로 읽어서 얻는 이득보다 `ReaderWriterLockSlim`의 관리 오버헤드가 더 클 수도 있다.
- **동시에 읽기를 수행하려는 스레드 수가 많다.** 읽기 스레드가 하나뿐이라면 어차피 병렬성을 얻을 수 없으므로 굳이 `ReaderWriterLockSlim`을 쓸 이유가 없다.

즉, "읽기 위주 + 읽기 동시성 확보로 얻는 이득이 관리 비용보다 큰 경우"에 한해 `lock`보다 우수한 처리량을 낼 수 있다. 반대로 쓰기가 잦거나 임계 영역이 아주 짧다면 단순한 `lock`이 오히려 더 나은 선택일 수 있으므로, 실제 적용 전에는 워크로드를 프로파일링해 보는 것이 바람직하다.

## 4.4 동기화 도구 선택 가이드

지금까지 살펴본 `lock`(`Monitor`), `Mutex`, `Semaphore`/`SemaphoreSlim`, `ReaderWriterLockSlim`은 각각 서로 다른 상황을 위해 설계되었다. 다음 표로 각 도구의 특징과 선택 기준을 정리한다.

| 도구 | 동시 진입 허용 개수 | 프로세스 간 공유 | 비동기 대기 지원 | 주요 사용 상황 |
|---|---|---|---|---|
| `lock` / `Monitor` | 1 | 불가능 | 지원 안 함 | 한 프로세스 내에서 단순한 상호 배제가 필요할 때. 가장 가볍고 기본이 되는 선택지 |
| `Mutex` | 1 | **가능** (이름 지정 시) | 지원 안 함 | 여러 프로세스에 걸친 동기화(예: 애플리케이션 중복 실행 방지, 여러 프로세스 간 자원 공유) |
| `Semaphore` | N (지정 가능) | **가능** (이름 지정 시) | 지원 안 함 | 프로세스 간에도 동시 접근 개수를 N개로 제한해야 할 때 |
| `SemaphoreSlim` | N (지정 가능) | 불가능(로컬 전용) | **지원함** (`WaitAsync`) | 한 프로세스 내에서 동시 접근 개수를 N개로 제한할 때(커넥션 풀, API 호출 제한 등). 대부분의 경우 `Semaphore`보다 이 쪽을 우선 고려 |
| `ReaderWriterLockSlim` | 읽기는 N, 쓰기는 1 | 불가능 | 지원 안 함 | 읽기가 쓰기보다 훨씬 빈번한 공유 데이터(캐시, 설정 등)를 보호할 때 |

선택 과정을 간단한 질문들로 정리하면 다음과 같다.

1. **프로세스 경계를 넘어야 하는가?** 그렇다면 `Mutex`(단일 진입) 또는 이름이 지정된 `Semaphore`(N개 진입)를 사용한다. 그렇지 않다면 아래로 진행한다.
2. **동시에 여러 스레드의 진입을 허용해야 하는가(N > 1)?** 그렇다면 `SemaphoreSlim`을 사용한다. 하나만 허용하면 된다면 아래로 진행한다.
3. **보호 대상 데이터에 대한 접근이 읽기 위주이고, 읽기 동시성을 높였을 때 이득이 뚜렷한가?** 그렇다면 `ReaderWriterLockSlim`을 고려한다. 그렇지 않다면(단순한 상호 배제로 충분하다면) `lock`을 사용한다.

실무에서는 대부분의 상황이 "같은 프로세스 안에서, 하나의 스레드만 임계 영역에 들어가면 되는" 경우이므로 `lock`이 기본값이 되어야 한다. `Mutex`, `Semaphore`류, `ReaderWriterLockSlim`은 각각의 필요조건(프로세스 간 공유, 동시 접근 개수 제한, 읽기 위주의 워크로드)이 명확할 때 선택하는 특화된 도구라고 이해하면 된다. 다음 장에서는 이러한 상호 배제 도구들과는 다른 방향의 동기화, 즉 스레드 간에 "신호를 주고받는" 이벤트 기반 동기화 도구들을 살펴본다.

## 요약

- `Mutex`는 `lock`과 같은 상호 배제를 제공하지만 운영체제 커널 객체를 사용하므로 이름을 지정하면 **프로세스 경계를 넘어** 동기화할 수 있다. 대신 `lock`보다 무겁기 때문에, 프로세스 내부 동기화만 필요하다면 `lock`을 사용하는 것이 낫다.
- `Semaphore`와 `SemaphoreSlim`은 동시에 접근 가능한 스레드 수를 N개로 제한하는 카운팅 세마포어다. `SemaphoreSlim`은 관리 코드로 구현되어 로컬 전용으로는 더 가볍고, `WaitAsync()`로 비동기 대기까지 지원하므로 프로세스 간 공유가 필요 없다면 우선적으로 고려한다.
- `ReaderWriterLockSlim`은 읽기 락(다중 진입 허용)과 쓰기 락(단일 진입, 배타적)을 구분하여, 읽기가 압도적으로 많은 워크로드에서 `lock`보다 높은 처리량을 낼 수 있다. 읽기에서 쓰기로 안전하게 전환하려면 `EnterUpgradeableReadLock`을 사용한다.
- 도구 선택은 "프로세스 경계를 넘어야 하는가", "동시 진입 개수가 1보다 큰가", "읽기 위주 워크로드인가"라는 질문들로 좁혀나갈 수 있으며, 특별한 요구가 없다면 가장 가벼운 `lock`이 기본 선택지다.

## 연습문제

1. `Mutex`와 `lock`이 내부적으로 어떤 종류의 객체(커널 객체 대 CLR 관리 객체)를 사용하는지 비교하고, 이 차이가 왜 성능과 프로세스 간 공유 가능 여부에 영향을 주는지 설명하라.
2. 이름 있는 `Mutex`를 사용해 "동시에 이 프로그램의 인스턴스가 하나만 실행되도록" 하는 콘솔 프로그램을 작성하고, 같은 프로그램을 두 번 실행해서 두 번째 실행이 즉시 종료되는 것을 확인하라.
3. `SemaphoreSlim(initialCount: 2, maxCount: 2)`를 사용하여 동시에 최대 2개의 작업만 허용하는 다운로드 시뮬레이터를 작성하고, 5개의 작업을 동시에 요청했을 때 실제로 2개씩 순차적으로 처리되는지 로그로 확인하라.
4. `ReaderWriterLockSlim`을 사용하는 캐시 클래스에서, 일반 `EnterReadLock`을 보유한 스레드가 조건에 따라 `EnterWriteLock`으로 직접 전환을 시도하면 어떤 문제가 발생할 수 있는지 설명하고, `EnterUpgradeableReadLock`이 이 문제를 어떻게 해결하는지 서술하라.
5. 읽기 작업이 극히 짧고(단순 필드 반환) 쓰기 작업도 자주 발생하는 상황에서 `ReaderWriterLockSlim`이 오히려 `lock`보다 느릴 수 있는 이유를 본문의 내용을 근거로 설명하라.

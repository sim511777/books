# 15장. 비동기 스트림

[◀ 이전: 14장. 동시성 컬렉션](ch14-동시성컬렉션.md) | [📖 목차](00-목차.md) | [다음: 16장. Channel과 생산자-소비자 패턴 ▶](ch16-Channel과생산자소비자패턴.md)


지금까지 살펴본 비동기 프로그래밍은 대부분 "값 하나를 비동기로 기다린다"는 형태였습니다. `Task<T>`를 `await`하면 결과 값 하나가 도착하고, 그것으로 끝입니다. 하지만 실무에서는 값이 하나가 아니라 여러 개가 시간을 두고 순차적으로 도착하는 상황이 자주 있습니다. 대용량 데이터를 페이지 단위로 가져오는 API, 센서에서 계속 밀려오는 측정값, 파일을 한 줄씩 읽으면서 각 줄마다 네트워크 조회가 필요한 경우 등이 그렇습니다.

이런 상황을 억지로 `Task<List<T>>` 하나로 처리하려 하면, 모든 데이터가 다 모일 때까지 기다렸다가 한꺼번에 반환해야 합니다. 데이터가 크면 메모리를 많이 소비하고, 첫 번째 항목이 이미 도착했는데도 사용자는 마지막 항목이 도착할 때까지 아무것도 볼 수 없습니다. 이 장에서 다루는 `IAsyncEnumerable<T>`는 바로 이 문제, 즉 "값을 비동기로 기다리면서, 동시에 여러 개를 순차적으로 흘려보내는" 상황을 위한 도구입니다.

## IAsyncEnumerable&lt;T&gt;란 무엇인가

C#을 사용해봤다면 `IEnumerable<T>`와 `foreach`에는 이미 익숙할 것입니다. `IEnumerable<T>`는 "값을 하나씩 꺼낼 수 있는 시퀀스"를 나타내는 인터페이스이고, 그 값을 꺼내는 동작(`MoveNext()`와 `Current`)은 철저히 동기적입니다. 즉 다음 값을 꺼내는 순간 호출 스레드는 그 값이 준비될 때까지 블로킹됩니다.

`IAsyncEnumerable<T>`는 이 개념을 비동기 세계로 그대로 옮긴 것입니다. "값을 하나씩 꺼낼 수 있는데, 각 값을 꺼내는 동작 자체가 비동기로 이루어지는 시퀀스"입니다. 다음 값이 아직 준비되지 않았다면, 동기 버전처럼 스레드를 블로킹하는 대신 9장에서 배운 `await`의 원리 그대로 스레드를 반납하고, 값이 준비되면 이어서 실행을 재개합니다.

두 인터페이스를 나란히 놓고 비교하면 이 대응 관계가 분명해집니다.

```csharp
// 동기 버전: 값을 꺼내는 동작(MoveNext)이 스레드를 블로킹할 수 있다
public interface IEnumerable<out T>
{
    IEnumerator<T> GetEnumerator();
}

public interface IEnumerator<out T> : IDisposable
{
    bool MoveNext();
    T Current { get; }
}

// 비동기 버전: 값을 꺼내는 동작 자체가 Task로 표현되어 await할 수 있다
public interface IAsyncEnumerable<out T>
{
    IAsyncEnumerator<T> GetAsyncEnumerator(CancellationToken cancellationToken = default);
}

public interface IAsyncEnumerator<out T> : IAsyncDisposable
{
    ValueTask<bool> MoveNextAsync();
    T Current { get; }
}
```

`MoveNext()`가 `bool`을 즉시 반환하는 대신 `MoveNextAsync()`가 `ValueTask<bool>`을 반환한다는 점, 그리고 자원 정리도 `IDisposable` 대신 `IAsyncDisposable`을 사용한다는 점만 다릅니다. `ValueTask<bool>`을 쓰는 이유는 스트림에서 다음 값이 이미 버퍼에 준비되어 있는 경우가 많아서, 매번 `Task<bool>`을 새로 힙에 할당하는 비용을 줄이기 위함입니다. `ValueTask`의 세부 동작은 8장에서 다룬 내용을 참고하면 됩니다.

## async 이터레이터 메서드로 비동기 스트림 생성하기

`IAsyncEnumerable<T>`를 직접 구현하는 클래스를 손으로 작성할 수도 있지만, 실무에서는 거의 항상 컴파일러가 대신 만들어주는 방식을 사용합니다. 이미 두 가지를 알고 있다면 이 방식은 자연스럽게 이해됩니다.

첫째, 일반 이터레이터 메서드입니다. 반환 타입이 `IEnumerable<T>`인 메서드 안에서 `yield return`을 사용하면, 컴파일러가 상태 기계를 만들어 `MoveNext()`가 호출될 때마다 다음 `yield return` 지점까지 실행하고 멈추는 코드를 생성해줍니다.

둘째, 9장에서 다룬 `async`/`await`입니다. `async` 메서드 안에서 `await`를 사용하면 컴파일러가 또 다른 형태의 상태 기계를 만들어, 비동기 작업이 완료될 때까지 실행을 중단했다가 재개하는 코드를 생성해줍니다.

`async IAsyncEnumerable<T>` 메서드는 이 두 가지를 그대로 합쳐 놓은 것입니다. 메서드 앞에 `async` 키워드를 붙이고 반환 타입을 `IAsyncEnumerable<T>`로 선언하면, 메서드 본문 안에서 `yield return`으로 값을 하나씩 내보내면서 동시에 `await`로 비동기 작업을 기다릴 수 있습니다.

```csharp
async IAsyncEnumerable<int> CountUpAsync(int count, int delayMs)
{
    for (int i = 1; i <= count; i++)
    {
        await Task.Delay(delayMs); // 비동기로 대기 - 9장의 async/await와 동일한 원리
        yield return i;            // 값을 하나 내보냄 - 일반 이터레이터의 yield return과 동일한 원리
    }
}
```

이 메서드를 호출하면 즉시 반복이 시작되는 것이 아니라, `IAsyncEnumerable<int>` 객체 하나가 반환됩니다(일반 이터레이터 메서드가 `IEnumerable<T>`를 즉시 반환하고 실제 실행은 나중에 이루어지는 것과 완전히 같은 지연 실행 방식입니다). 실제 코드가 실행되는 시점은 소비하는 쪽에서 이 시퀀스를 순회하기 시작할 때입니다.

여기서 반환 타입에 `Task<IAsyncEnumerable<T>>`가 아니라 `IAsyncEnumerable<T>`를 그대로 쓴다는 점을 눈여겨봐야 합니다. `async` 메서드인데도 `Task`나 `Task<T>`를 반환하지 않는 특수한 경우로, 컴파일러가 `yield return`의 존재를 보고 이 메서드를 "값을 여러 개 비동기로 내보내는 상태 기계"로 다르게 컴파일하기 때문입니다.

## await foreach로 비동기 스트림 소비하기

`IAsyncEnumerable<T>`를 순회할 때는 일반 `foreach` 대신 `await foreach`를 사용합니다.

```csharp
async Task RunAsync()
{
    await foreach (int number in CountUpAsync(count: 5, delayMs: 500))
    {
        Console.WriteLine($"받은 값: {number}");
    }

    Console.WriteLine("모든 값을 다 받았습니다.");
}
```

`await foreach`는 내부적으로 매 반복마다 `MoveNextAsync()`를 호출하고 그 결과를 `await`합니다. 겉보기에는 평범한 `foreach`처럼 한 줄씩 읽히지만, 실제로는 다음 값이 아직 준비되지 않았을 때마다 그 지점에서 실행이 중단되고 스레드가 반납됩니다. 위 예제를 실행하면 "받은 값: 1"이 출력된 뒤 곧바로 2, 3, 4, 5가 이어지는 것이 아니라, 각 값 사이에 500밀리초의 간격을 두고 하나씩 출력됩니다. 그동안 호출 스레드는 블로킹되지 않고 다른 작업을 처리할 수 있습니다.

`await foreach`를 사용하는 메서드 자신도 `async` 메서드여야 합니다(그 안에서 `await`가 일어나므로 당연한 요구 사항입니다). 또한 `foreach`와 마찬가지로 `break`로 중간에 순회를 멈출 수 있으며, 이 경우 내부적으로 `IAsyncDisposable.DisposeAsync()`가 호출되어 자원이 정리됩니다.

## CancellationToken 전달하기 - WithCancellation

11장에서 다룬 취소 패턴은 비동기 스트림에도 그대로 적용할 수 있습니다. `async IAsyncEnumerable<T>` 메서드는 매개변수에 `[EnumeratorCancellation]` 특성을 붙인 `CancellationToken`을 받도록 작성하는 것이 관례입니다.

```csharp
using System.Runtime.CompilerServices;

async IAsyncEnumerable<int> CountUpAsync(
    int count,
    int delayMs,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    for (int i = 1; i <= count; i++)
    {
        cancellationToken.ThrowIfCancellationRequested();
        await Task.Delay(delayMs, cancellationToken);
        yield return i;
    }
}
```

`[EnumeratorCancellation]` 특성이 필요한 이유는 다소 미묘합니다. 이 메서드는 컴파일러에 의해 상태 기계로 변환되는데, 메서드가 처음 호출되는 시점(즉 `GetAsyncEnumerator`가 호출되기 전)에는 아직 실제 반복이 시작되지 않은 상태입니다. 소비하는 쪽에서 뒤에 설명할 `WithCancellation()`으로 토큰을 전달하면, 런타임이 이 특성이 붙은 매개변수를 찾아 그 자리에 실제 토큰 값을 채워 넣어줍니다. 특성을 붙이지 않으면 메서드 호출 시점에 지정한 기본값(위 예제에서는 `default`)이 그대로 사용되어, 나중에 전달한 취소 토큰이 무시되는 문제가 생길 수 있습니다.

소비하는 쪽에서 취소 토큰을 전달할 때는 `WithCancellation()` 확장 메서드를 사용합니다.

```csharp
async Task RunWithCancellationAsync()
{
    using var cts = new CancellationTokenSource();
    cts.CancelAfter(TimeSpan.FromSeconds(2));

    try
    {
        await foreach (int number in CountUpAsync(count: 10, delayMs: 500)
                           .WithCancellation(cts.Token))
        {
            Console.WriteLine($"받은 값: {number}");
        }
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine("스트림 순회가 취소되었습니다.");
    }
}
```

`WithCancellation()`은 `IAsyncEnumerable<T>`가 아니라 `ConfiguredCancelableAsyncEnumerable<T>`라는 래퍼 구조체를 반환하며, `await foreach`는 이 래퍼도 그대로 순회할 수 있습니다. 이 구조는 8장과 10장에서 다룬 `ConfigureAwait()`가 `Task`를 감싸는 방식과 비슷한 패턴입니다. 실제로 `WithCancellation()` 뒤에 `.ConfigureAwait(false)`를 체이닝해서 컨텍스트 캡처 여부까지 함께 제어할 수도 있습니다.

```csharp
await foreach (int number in CountUpAsync(count: 10, delayMs: 500)
                   .WithCancellation(cts.Token)
                   .ConfigureAwait(false))
{
    // ...
}
```

## 실전 예제 - 페이지 단위 API를 비동기 스트림으로 감싸기

실무에서 비동기 스트림이 가장 빛을 발하는 상황 중 하나는 페이지네이션(pagination) API를 다룰 때입니다. 서버가 한 번에 모든 데이터를 주지 않고 "다음 페이지 토큰"과 함께 일부 데이터만 돌려주는 방식은 REST API에서 흔히 볼 수 있습니다. 이런 API를 호출할 때마다 페이지 하나씩 기다렸다가, 도착하는 즉시 그 페이지의 항목들을 처리할 수 있다면 전체 데이터를 기다릴 필요 없이 훨씬 빨리 첫 결과를 사용자에게 보여줄 수 있습니다.

먼저 페이지 단위로 데이터를 흉내 내어 가져오는 가상의 API를 만들어봅니다.

```csharp
public record Order(int Id, string CustomerName, decimal Amount);

public record OrderPage(IReadOnlyList<Order> Items, string? NextPageToken);

public class FakeOrderApiClient
{
    private readonly Random _random = new();

    // 실제 서버 호출을 흉내 낸다: 페이지 토큰을 받아 그다음 페이지를 돌려준다
    public async Task<OrderPage> FetchPageAsync(
        string? pageToken,
        CancellationToken cancellationToken)
    {
        // 네트워크 지연 흉내
        await Task.Delay(TimeSpan.FromMilliseconds(300), cancellationToken);

        int pageIndex = pageToken is null ? 0 : int.Parse(pageToken);
        const int pageSize = 3;
        const int totalPages = 4;

        var items = new List<Order>();
        for (int i = 0; i < pageSize; i++)
        {
            int orderId = pageIndex * pageSize + i + 1;
            items.Add(new Order(orderId, $"고객{orderId}", _random.Next(1000, 50000)));
        }

        string? nextToken = pageIndex + 1 < totalPages ? (pageIndex + 1).ToString() : null;
        return new OrderPage(items, nextToken);
    }
}
```

이제 이 API를 감싸서, 페이지가 도착할 때마다 그 안의 주문 항목들을 하나씩 흘려보내는 비동기 스트림을 작성합니다. 소비하는 쪽은 페이지라는 개념을 전혀 알 필요 없이 `Order` 하나하나를 순차적으로 받기만 하면 됩니다.

```csharp
async IAsyncEnumerable<Order> FetchAllOrdersAsync(
    FakeOrderApiClient client,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    string? pageToken = null;

    do
    {
        OrderPage page = await client.FetchPageAsync(pageToken, cancellationToken);

        foreach (Order order in page.Items)
        {
            yield return order;
        }

        pageToken = page.NextPageToken;
    }
    while (pageToken is not null);
}
```

이 메서드 하나 안에 `await`(페이지를 비동기로 가져오는 부분)와 `yield return`(가져온 페이지의 항목들을 하나씩 내보내는 부분)이 자연스럽게 섞여 있습니다. 이것이 바로 이 장 서두에서 말한 "일반 이터레이터와 async/await의 결합"이 실제 코드로 나타난 모습입니다.

소비하는 쪽 코드는 페이지 구조를 신경 쓰지 않고 마치 하나의 긴 시퀀스를 순회하듯 작성할 수 있습니다.

```csharp
async Task ProcessAllOrdersAsync(CancellationToken cancellationToken)
{
    var client = new FakeOrderApiClient();
    decimal total = 0;
    int count = 0;

    await foreach (Order order in FetchAllOrdersAsync(client, cancellationToken)
                       .WithCancellation(cancellationToken))
    {
        Console.WriteLine($"[페이지 도착] 주문 #{order.Id} - {order.CustomerName} - {order.Amount:C}");
        total += order.Amount;
        count++;
    }

    Console.WriteLine($"총 {count}건, 합계 {total:C}");
}
```

이 코드를 실행하면 네 번의 페이지 호출이 순차적으로 일어나면서, 각 페이지가 도착하는 즉시 그 안의 세 건씩 주문이 콘솔에 출력됩니다. 만약 전체 주문 목록을 `Task<List<Order>>`로 한꺼번에 반환하는 방식으로 작성했다면, 네 번째 페이지까지 전부 도착할 때까지 화면에는 아무것도 나타나지 않았을 것입니다. 데이터 양이 수십, 수백 페이지에 달하는 경우라면 이 차이는 응답성과 메모리 사용량 양쪽에서 실질적인 이득으로 이어집니다.

`CancellationToken`을 전달했기 때문에, 예를 들어 사용자가 화면을 벗어나거나 요청을 취소하면 다음 페이지를 가져오기 전 또는 `Task.Delay` 도중에 즉시 순회를 중단하고 `OperationCanceledException`을 던지도록 만들 수도 있습니다. 취소된 이후의 페이지 호출은 아예 발생하지 않으므로 불필요한 네트워크 요청도 함께 줄어듭니다.

## LINQ 스타일로 비동기 스트림 다루기

`System.Linq.Async` 같은 확장 라이브러리를 쓰지 않더라도, 표준 라이브러리만으로 간단한 필터링 정도는 직접 async 이터레이터로 구현할 수 있습니다.

```csharp
async IAsyncEnumerable<Order> WhereAsync(
    this IAsyncEnumerable<Order> source,
    Func<Order, bool> predicate,
    [EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    await foreach (Order order in source.WithCancellation(cancellationToken))
    {
        if (predicate(order))
        {
            yield return order;
        }
    }
}
```

```csharp
await foreach (Order highValueOrder in FetchAllOrdersAsync(client, cancellationToken)
                   .WhereAsync(o => o.Amount >= 10000, cancellationToken))
{
    Console.WriteLine($"고액 주문: {highValueOrder}");
}
```

이런 방식으로 비동기 스트림을 조합하면, 데이터 전체를 메모리에 올리지 않고도 필터링이나 변환 같은 파이프라인을 구성할 수 있습니다. 다만 본격적으로 다양한 LINQ 연산자(`Select`, `Take`, `SelectMany` 등)를 비동기 스트림에 적용하고 싶다면 커뮤니티에서 널리 쓰이는 `System.Linq.Async` NuGet 패키지를 도입하는 것이 일반적입니다.

## 요약

- `IAsyncEnumerable<T>`는 `IEnumerable<T>`를 비동기 세계로 옮긴 것으로, 값을 하나씩 꺼내는 동작(`MoveNextAsync()`)이 `ValueTask<bool>`을 통해 비동기로 이루어지는 시퀀스입니다.
- `async IAsyncEnumerable<T>` 메서드 안에서는 일반 이터레이터의 `yield return`과 9장에서 배운 `await`를 함께 사용할 수 있습니다. 컴파일러가 두 상태 기계의 성격을 결합해 처리해줍니다.
- 소비하는 쪽에서는 `await foreach`로 비동기 스트림을 순회하며, 다음 값이 준비되지 않은 구간에서는 스레드를 블로킹하지 않고 반납합니다.
- 취소를 지원하려면 생산 메서드의 `CancellationToken` 매개변수에 `[EnumeratorCancellation]` 특성을 붙이고, 소비하는 쪽에서는 `WithCancellation()`으로 토큰을 전달합니다.
- 페이지 단위 API처럼 데이터가 여러 번에 걸쳐 도착하는 상황을 비동기 스트림으로 감싸면, 전체 데이터를 기다리지 않고 도착하는 즉시 처리할 수 있어 응답성과 메모리 효율이 개선됩니다.

## 연습문제

1. `IEnumerable<T>`/`IEnumerator<T>`와 `IAsyncEnumerable<T>`/`IAsyncEnumerator<T>`의 메서드 시그니처를 나란히 비교하고, 각 차이가 왜 필요한지 설명하세요.
2. 1초 간격으로 1부터 N까지의 정수를 내보내는 `async IAsyncEnumerable<int>` 메서드를 작성하고, `await foreach`로 소비하면서 각 값이 도착한 시각을 함께 출력해보세요.
3. 위 문제의 메서드에 `[EnumeratorCancellation]` 토큰을 추가하고, 3초 후 자동으로 취소되는 `CancellationTokenSource`를 사용해 중간에 순회가 멈추는 것을 확인해보세요.
4. 이 장의 `FetchAllOrdersAsync` 예제를 변형해, 한 페이지를 가져오는 도중 예외가 발생하면 이미 처리한 주문 건수와 함께 예외를 다시 던지도록 수정해보세요.
5. `IAsyncEnumerable<T>`를 사용하는 방식과, 전체 데이터를 `Task<List<T>>`로 한 번에 반환한 뒤 `foreach`로 순회하는 방식을 비교했을 때, 각각이 유리한 상황을 두 가지씩 들어보세요.

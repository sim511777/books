## 5.1 들어가며: 신호를 주고받는 동기화

3장과 4장에서 살펴본 `lock`, `Monitor`, `Mutex`, `Semaphore` 같은 도구들은 공통적으로 "동시에 접근하면 안 되는 자원을 어떻게 보호할 것인가"라는 질문에 답하는 도구였다. 이들은 상호 배제(mutual exclusion)에 초점을 맞춘다.

그런데 스레드를 다루다 보면 성격이 조금 다른 문제와 자주 마주치게 된다. 바로 "어떤 일이 일어날 때까지 기다렸다가, 그 일이 일어나면 움직여라"는 문제다. 예를 들어 다음과 같은 상황들이다.

- 백그라운드에서 초기화 작업이 끝날 때까지 다른 스레드들이 기다려야 한다.
- 여러 작업 스레드가 각자 맡은 일을 끝낼 때까지 메인 스레드가 기다려야 한다.
- 여러 스레드가 특정 단계를 모두 통과할 때까지 서로를 기다렸다가, 다 함께 다음 단계로 넘어가야 한다.
- 큐에 새 항목이 들어올 때까지 소비자 스레드가 잠들어 있다가, 항목이 들어오면 즉시 깨어나야 한다.

이런 문제는 자원을 잠그는 것으로는 해결되지 않는다. 필요한 것은 "아직 준비되지 않음"과 "준비됨"이라는 두 가지 상태를 스레드들 사이에서 공유하고, 상태가 바뀌는 순간 대기 중인 스레드를 깨워주는 메커니즘이다. .NET은 이런 용도로 `ManualResetEvent`(및 슬림 버전), `AutoResetEvent`, `CountdownEvent`, `Barrier`라는 네 가지 이벤트 기반 동기화 도구를 제공한다.

이 도구들은 모두 내부적으로 "신호(signal) 상태"라는 개념을 공유한다. 신호 상태가 켜져 있으면(signaled) 대기 중인 스레드가 깨어나 진행할 수 있고, 꺼져 있으면(non-signaled, 또는 unsignaled) 대기 중인 스레드는 계속 잠들어 있다. 각 도구의 차이는 이 신호 상태를 누가, 언제, 어떻게 바꾸느냐, 그리고 신호를 받은 스레드가 몇 개나 통과하느냐에 있다.

> 이 장에서 다루는 클래스들은 대부분 `System.Threading` 네임스페이스에 있으며, `WaitHandle`을 상속하거나(`ManualResetEvent`, `AutoResetEvent`) 그와 별개로 독자적인 대기 로직을 구현한다(`ManualResetEventSlim`, `CountdownEvent`, `Barrier`). 4장에서 다룬 `Mutex`, `Semaphore`도 `WaitHandle`의 하위 클래스라는 점에서 이번 장의 도구들과 한 가족이다.

## 5.2 ManualResetEvent와 ManualResetEventSlim

### 5.2.1 기본 동작: 문을 열어두는 신호

`ManualResetEvent`는 이름 그대로 "수동으로(manual) 상태를 재설정(reset)해야 하는 이벤트"다. 동작 방식을 문에 비유하면 이해하기 쉽다.

- 신호 상태가 아닐 때(non-signaled): 문이 닫혀 있다. 이 문 앞에서 `Wait`를 호출한 모든 스레드는 문이 열릴 때까지 잠들어 대기한다.
- 신호 상태일 때(signaled): 문이 열려 있다. 대기 중이던 스레드는 물론이고, 앞으로 `Wait`를 호출하는 스레드도 즉시 통과한다.

중요한 특징은 한 번 열린 문은 누군가 다시 닫기 전까지 계속 열려 있다는 것이다. `AutoResetEvent`와 가장 크게 다른 점이 바로 이 부분인데, 뒤에서 바로 비교해보겠다.

`ManualResetEvent`는 생성자에서 초기 신호 상태를 지정하고, `Set()`으로 문을 열고, `Reset()`으로 문을 다시 닫는다. 대기하는 쪽은 `WaitOne()`을 호출한다.

```csharp
using System;
using System.Threading;

class Program
{
    // 초기 상태를 false(non-signaled)로 생성: 문이 닫혀 있는 상태로 시작
    static ManualResetEvent _ready = new ManualResetEvent(false);

    static void Main()
    {
        for (int i = 0; i < 3; i++)
        {
            int workerId = i;
            new Thread(() => Worker(workerId)).Start();
        }

        Console.WriteLine("초기화 작업을 진행합니다...");
        Thread.Sleep(1500); // 초기화 작업을 흉내 낸다.

        Console.WriteLine("초기화 완료! 대기 중인 모든 워커를 깨웁니다.");
        _ready.Set(); // 문을 연다. 대기 중인 스레드 전부가 통과한다.

        Console.ReadLine();
    }

    static void Worker(int id)
    {
        Console.WriteLine($"워커 {id}: 초기화 완료를 기다립니다.");
        _ready.WaitOne(); // 문이 열릴 때까지 대기
        Console.WriteLine($"워커 {id}: 신호를 받고 작업을 시작합니다.");
    }
}
```

이 예제에서 세 워커 스레드는 모두 `_ready.WaitOne()`에서 잠들어 있다가, 메인 스레드가 `Set()`을 호출하는 순간 동시에 깨어나 작업을 시작한다. `ManualResetEvent`가 "여러 스레드를 한꺼번에 깨우는" 용도에 적합한 이유가 여기에 있다.

만약 초기화를 다시 수행해야 한다면 `_ready.Reset()`을 호출해 문을 다시 닫을 수 있다. 이후 `WaitOne()`을 호출하는 스레드는 다시 대기 상태에 들어간다.

### 5.2.2 ManualResetEventSlim: 경량화된 버전

`ManualResetEvent`는 커널 객체를 기반으로 동작하는 `WaitHandle`이다. 이는 프로세스 간 동기화도 가능하게 해주지만, 그만큼 생성과 대기 비용이 비교적 크다는 뜻이기도 하다. 대부분의 경우처럼 동기화가 한 프로세스 안에서만 이루어진다면, .NET 4.0부터 추가된 `ManualResetEventSlim`을 쓰는 편이 낫다.

`ManualResetEventSlim`은 짧은 시간 동안은 스핀 대기(spin wait)를 수행하다가, 대기 시간이 길어지면 커널 수준의 대기로 전환하는 하이브리드 전략을 사용한다. 신호가 아주 짧은 시간 안에 켜질 것으로 예상되는 상황에서는 스레드를 실제로 잠재우고 깨우는 컨텍스트 스위칭 비용을 아낄 수 있어 `ManualResetEvent`보다 성능이 좋다.

사용법은 거의 동일하지만 대기 메서드 이름이 `Wait()`이다.

```csharp
using System;
using System.Threading;

class Program
{
    static ManualResetEventSlim _ready = new ManualResetEventSlim(false);

    static void Main()
    {
        for (int i = 0; i < 3; i++)
        {
            int workerId = i;
            new Thread(() => Worker(workerId)).Start();
        }

        Thread.Sleep(500);
        Console.WriteLine("신호를 보냅니다.");
        _ready.Set();

        Console.ReadLine();
    }

    static void Worker(int id)
    {
        _ready.Wait(); // 짧으면 스핀, 길어지면 커널 대기로 전환
        Console.WriteLine($"워커 {id}: 시작합니다.");
    }
}
```

`ManualResetEventSlim`은 내부적으로 `SpinWait` 구조체를 활용하며, 생성자에서 스핀 횟수를 지정할 수도 있다(`new ManualResetEventSlim(false, spinCount: 100)`). 다만 `WaitHandle`을 상속하지 않으므로 `WaitHandle.WaitAny` 같은 메서드에는 직접 쓸 수 없고, 필요하다면 `WaitHandle` 속성을 통해 내부 핸들을 얻어야 한다. 특별히 프로세스 간 동기화나 여러 핸들을 한꺼번에 기다리는 API가 필요한 것이 아니라면, 새 코드에서는 `ManualResetEventSlim`을 기본으로 선택하자.

## 5.3 AutoResetEvent: 한 명만 통과시키는 회전문

### 5.3.1 ManualResetEvent와의 결정적 차이

`AutoResetEvent`는 `ManualResetEvent`와 API 모양은 비슷하지만 동작 철학이 다르다. 문이 아니라 회전문(turnstile)을 떠올려보자. 회전문은 한 사람이 지나가면 자동으로 다시 잠긴다.

`AutoResetEvent`도 마찬가지다. `Set()`을 호출하면 대기 중이던 스레드 중 정확히 하나만 깨어나 통과하고, 그 즉시 신호 상태는 자동으로 다시 non-signaled로 바뀐다. 별도로 `Reset()`을 호출할 필요가 없다(호출할 수는 있지만, 이미 대기 중인 스레드가 없다면 굳이 필요하지 않다).

두 클래스의 차이를 표로 정리하면 다음과 같다.

| 구분 | ManualResetEvent | AutoResetEvent |
|---|---|---|
| `Set()` 호출 시 | 신호 상태가 유지된다. 대기 중인 모든 스레드와 이후 도착하는 스레드가 통과한다. | 대기 중인 스레드 하나만 통과시키고 즉시 non-signaled로 되돌아간다. |
| `Reset()` 필요 여부 | 다음 대기를 위해 명시적으로 호출해야 한다. | 자동으로 처리되므로 보통 필요 없다. |
| 적합한 용도 | 여러 스레드를 동시에 깨우기, 상태 플래그 전파 | 스레드 간 작업을 순서대로 하나씩 넘기기 |

### 5.3.2 예제: 두 스레드가 순서를 주고받기

`AutoResetEvent`가 진가를 발휘하는 상황은 두 스레드가 핑퐁을 치듯 순서를 주고받아야 할 때다. 신호를 받은 딱 한 스레드만 진행하고, 그 스레드가 다시 상대방에게 신호를 보내는 구조를 만들 수 있다.

```csharp
using System;
using System.Threading;

class Program
{
    static AutoResetEvent _pingEvent = new AutoResetEvent(true); // 먼저 시작할 쪽을 signaled로
    static AutoResetEvent _pongEvent = new AutoResetEvent(false);
    static volatile bool _stop = false;

    static void Main()
    {
        var ping = new Thread(Ping);
        var pong = new Thread(Pong);
        ping.Start();
        pong.Start();

        Thread.Sleep(2000);
        _stop = true;

        ping.Join();
        pong.Join();
    }

    static void Ping()
    {
        while (!_stop)
        {
            _pingEvent.WaitOne();   // 내 차례를 기다린다.
            Console.WriteLine("Ping");
            Thread.Sleep(200);
            _pongEvent.Set();       // 상대방 차례로 넘긴다.
        }
    }

    static void Pong()
    {
        while (!_stop)
        {
            _pongEvent.WaitOne();
            Console.WriteLine("Pong");
            Thread.Sleep(200);
            _pingEvent.Set();
        }
    }
}
```

이처럼 두 개의 `AutoResetEvent`를 짝지어 사용하면 정확히 한 스레드씩 번갈아 실행되는 흐름을 만들 수 있다. 만약 여기서 `ManualResetEvent`를 썼다면 `Set()` 이후 문이 계속 열려 있어 Ping과 Pong이 통제 없이 마구 겹쳐 실행되었을 것이다. "한 번에 딱 하나만 깨운다"는 `AutoResetEvent`의 성질이 순번을 지키는 데 핵심적인 역할을 한다.

`AutoResetEvent`에도 슬림 버전은 따로 제공되지 않는다. 이는 자동 재설정 기능이 세마포어의 카운트가 1인 경우와 매우 비슷하기 때문인데, 실제로 가벼운 대안이 필요하다면 4장에서 다룬 `SemaphoreSlim(1, 1)`을 고려할 수 있다. 다만 `SemaphoreSlim`은 세마포어를 "해제(release)"하는 것이지 "신호를 보낸다"는 의미론과는 미묘하게 다르므로, 상호 배제가 목적이라면 `SemaphoreSlim`이나 `lock`을, 신호 전달이 목적이라면 `AutoResetEvent`를 쓰는 것이 코드의 의도를 더 명확하게 드러낸다.

## 5.4 CountdownEvent: 여러 작업이 모두 끝나기를 기다리기

### 5.4.1 등장 배경

`ManualResetEvent`나 `AutoResetEvent`는 "신호가 켜졌는가 꺼졌는가"라는 이진 상태만 다룬다. 그런데 실무에서는 "N개의 작업이 모두 끝났는가"를 확인해야 하는 경우가 훨씬 흔하다. 여러 워커 스레드에 작업을 나눠 주고, 전부 끝나면 결과를 취합하는 패턴이 대표적이다.

이 문제를 `ManualResetEvent` 하나로 해결하려면 "마지막으로 끝난 스레드가 Set()을 호출해야 한다"는 로직을 직접 만들어야 하는데, 이를 위해서는 결국 남은 작업 수를 세는 카운터와 그 카운터를 보호하는 별도의 동기화가 또 필요해진다. `CountdownEvent`는 이 패턴을 통째로 캡슐화한 도구다.

### 5.4.2 기본 사용법

`CountdownEvent`는 생성할 때 카운트를 지정하고, 작업이 끝날 때마다 `Signal()`을 호출해 카운트를 하나씩 줄인다. 카운트가 0이 되는 순간 신호 상태가 되어, `Wait()`으로 대기하던 스레드가 깨어난다.

```csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        const int workerCount = 5;
        using var countdown = new CountdownEvent(workerCount);

        for (int i = 0; i < workerCount; i++)
        {
            int workerId = i;
            new Thread(() => DoWork(workerId, countdown)).Start();
        }

        Console.WriteLine("모든 워커가 끝나기를 기다립니다...");
        countdown.Wait(); // 카운트가 0이 될 때까지 대기
        Console.WriteLine("모든 워커가 완료되었습니다. 다음 단계로 진행합니다.");
    }

    static void DoWork(int id, CountdownEvent countdown)
    {
        try
        {
            Thread.Sleep(new Random(id).Next(500, 2000)); // 작업 시간 흉내
            Console.WriteLine($"워커 {id}: 작업 완료");
        }
        finally
        {
            countdown.Signal(); // 카운트를 1 감소시킨다.
        }
    }
}
```

`Signal()`을 `try`/`finally` 안에서 호출한 점에 주목하자. 작업 도중 예외가 발생하더라도 카운트는 반드시 감소시켜야 한다. 그렇지 않으면 메인 스레드는 영원히 `Wait()`에서 깨어나지 못하고 멈춰버린다. 이는 `CountdownEvent`뿐 아니라 이 장에서 다루는 모든 카운트 기반 동기화 도구에 공통으로 적용되는 원칙이다.

`CountdownEvent`는 `IDisposable`을 구현하므로 `using`으로 감싸 자원을 정리하는 것이 좋다. 또한 `AddCount()`를 사용하면 실행 도중에도 카운트를 늘릴 수 있어, 처음에는 몇 개인지 몰랐던 작업을 동적으로 추가하는 상황에도 대응할 수 있다. 다만 이미 카운트가 0에 도달해 신호 상태가 된 이후에는 `AddCount()`가 예외를 던지므로, 동적으로 카운트를 조작할 때는 타이밍에 주의해야 한다.

### 5.4.3 CountdownEvent vs Thread.Join

"여러 스레드가 끝나기를 기다린다"는 목적만 놓고 보면 각 `Thread` 객체에 대해 `Join()`을 순서대로 호출해도 같은 효과를 낼 수 있다. 그렇다면 `CountdownEvent`는 언제 진가를 발휘할까.

- 스레드가 아니라 `ThreadPool`의 작업 항목이나 `Task`처럼 `Join()`을 직접 호출할 수 없는 작업 단위를 기다려야 할 때
- 몇 개의 작업이 끝나야 하는지 실행 도중 동적으로 바뀌는 경우(`AddCount()` 활용)
- 작업이 끝나는 순서와 무관하게, "몇 개가 끝났는가"라는 숫자 자체가 중요한 로직일 때

7장에서 다룰 `Task.WaitAll()`은 사실 `CountdownEvent`와 유사한 문제를 Task 수준에서 더 편리하게 해결해주는 상위 호환 도구다. 저수준 스레드를 직접 다루는 경우가 아니라면 `Task.WaitAll()`을 사용하는 편이 대개 더 간결하다는 점을 기억해두자.

## 5.5 Barrier: 라운드 경계를 맞추는 동기화

### 5.5.1 CountdownEvent와 무엇이 다른가

`CountdownEvent`는 한 번 카운트가 0이 되면 그걸로 끝이다. 그런데 여러 스레드가 반복적으로 "각자의 단계를 마치고, 모두가 그 단계를 마칠 때까지 기다렸다가, 다 함께 다음 단계로 넘어간다"를 여러 라운드에 걸쳐 되풀이해야 하는 경우가 있다. 예를 들어 다음과 같은 시뮬레이션이 대표적이다.

- 여러 스레드가 각각 격자(grid)의 일부를 계산하는 물리 시뮬레이션에서, 다음 스텝을 계산하려면 모든 스레드가 이전 스텝 계산을 끝냈어야 한다.
- 여러 참가자가 동시에 라운드를 진행하는 게임이나 경매 로직에서, 모든 참가자의 입력이 모여야 다음 라운드가 시작된다.

이런 "매 라운드마다 모두를 기다렸다가 함께 출발하는" 패턴을 위해 `Barrier` 클래스가 제공된다. `CountdownEvent`가 일회용이라면, `Barrier`는 카운트가 다 차면 자동으로 리셋되어 다음 라운드에도 재사용할 수 있는 재사용 가능한 카운트다운이라고 이해하면 된다.

### 5.5.2 기본 사용법

`Barrier`는 참가할 스레드 수를 생성자에 지정한다. 각 스레드는 자신의 작업 단계를 마칠 때마다 `SignalAndWait()`을 호출하는데, 이 메서드는 이름대로 "나는 이 라운드를 마쳤다고 신호를 보내고(Signal), 다른 모든 참가자가 신호를 보낼 때까지 대기한다(Wait)"를 한 번에 수행한다. 참가자 전원이 `SignalAndWait()`을 호출하면 배리어가 열리고, 모든 스레드가 동시에 풀려나 다음 라운드로 진행한다.

```csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        const int participantCount = 3;

        // 각 라운드가 끝날 때마다 실행할 후처리 콜백을 지정할 수 있다(선택 사항).
        using var barrier = new Barrier(participantCount,
            b => Console.WriteLine($"--- {b.CurrentPhaseNumber + 1}라운드 시작 전, 모두 도착함 ---"));

        for (int i = 0; i < participantCount; i++)
        {
            int workerId = i;
            new Thread(() => RunRounds(workerId, barrier)).Start();
        }
    }

    static void RunRounds(int id, Barrier barrier)
    {
        for (int round = 1; round <= 3; round++)
        {
            Thread.Sleep(new Random(id * 100 + round).Next(200, 1000));
            Console.WriteLine($"워커 {id}: {round}라운드 작업 완료, 다른 워커를 기다립니다.");

            barrier.SignalAndWait(); // 모두 도착할 때까지 대기 후 함께 진행

            Console.WriteLine($"워커 {id}: {round}라운드를 마치고 다음 라운드로 진행합니다.");
        }
    }
}
```

이 예제에서 세 워커는 저마다 다른 속도로 라운드 작업을 수행하지만, 가장 늦게 도착한 워커가 `SignalAndWait()`을 호출하는 순간까지는 아무도 다음 라운드로 넘어가지 못한다. `Barrier` 생성자에 넘긴 콜백(`postPhaseAction`)은 매 라운드가 마무리될 때 정확히 한 번, 참가자 스레드 중 하나에 의해 실행되므로 라운드 사이의 공통 후처리 로직을 넣기에 알맞다.

### 5.5.3 참가자 수를 동적으로 조절하기

`Barrier`는 `AddParticipant()`와 `RemoveParticipant()`로 실행 도중 참가자 수를 조절할 수 있다. 작업 도중 새로운 워커가 합류하거나, 일부 워커가 조기에 작업을 끝내고 빠지는 시나리오에 대응할 수 있다. 다만 현재 라운드가 진행 중인 상태에서 참가자 수를 바꾸면 예외가 발생할 수 있으므로, 보통은 라운드와 라운드 사이, 즉 `SignalAndWait()` 호출 직후처럼 모두가 동기화된 시점에 호출하는 것이 안전하다.

`CountdownEvent`와 마찬가지로 `Barrier`도 `IDisposable`을 구현하므로 다 쓴 뒤에는 정리해주어야 한다.

## 5.6 어떤 도구를, 언제 쓸 것인가

지금까지 살펴본 네 가지 도구는 겉보기엔 비슷해 보여도 각자 뚜렷하게 다른 문제를 겨냥하고 있다. 실전에서 선택 기준을 정리하면 다음과 같다.

| 도구 | 핵심 동작 | 적합한 시나리오 |
|---|---|---|
| `ManualResetEvent(Slim)` | 신호가 켜지면 계속 열려 있음, 여러 스레드를 동시에 깨움 | 초기화 완료 알림, "준비됨" 같은 상태 플래그를 여러 소비자에게 전파 |
| `AutoResetEvent` | 신호를 받은 스레드 하나만 통과하고 자동으로 다시 잠김 | 스레드 간 작업을 한 명씩 순서대로 넘기는 핑퐁 패턴, 단일 소비자 깨우기 |
| `CountdownEvent` | N개의 완료 신호를 모아 0이 되면 대기자를 깨움(일회성) | 여러 워커의 작업이 모두 끝나기를 한 번 기다렸다가 결과를 취합 |
| `Barrier` | N개의 참가자가 매 라운드 신호를 보내면 함께 다음 라운드로 진행(재사용 가능) | 여러 스레드가 반복되는 단계(phase)를 서로 맞춰가며 진행하는 시뮬레이션 |

한 가지 더 짚어둘 점이 있다. 이 장에서 다룬 도구들은 모두 저수준 스레드를 직접 다룰 때 유용하지만, 실무에서 새로 작성하는 코드라면 7장 이후에서 다룰 `Task` 기반 API(`Task.WhenAll`, `Task.WaitAll` 등)나 11장의 `CancellationToken`, 16장의 `Channel`이 같은 문제를 더 안전하고 간결하게 해결해주는 경우가 많다. 다만 이런 상위 수준 도구들도 내부적으로는 결국 이번 장에서 배운 신호 기반 동기화 개념 위에서 동작하므로, 그 동작 원리를 이해해두면 나중에 미묘한 동시성 버그를 진단할 때 큰 도움이 된다.

## 요약

- 이벤트 기반 동기화 도구는 "자원 보호"가 아니라 "특정 조건이 될 때까지 기다렸다가 깨어나기"라는 문제를 해결한다.
- `ManualResetEvent`/`ManualResetEventSlim`은 `Set()`을 호출하면 신호 상태가 계속 유지되어, 대기 중인 모든 스레드와 이후 도착하는 스레드까지 통과시킨다. 다시 잠그려면 `Reset()`을 명시적으로 호출해야 한다. 프로세스 내부 동기화라면 스핀 대기를 활용하는 `ManualResetEventSlim`이 대개 더 효율적이다.
- `AutoResetEvent`는 `Set()`을 호출해도 대기 중인 스레드 하나만 통과시키고 즉시 스스로 다시 잠긴다. 스레드 간 작업을 순서대로 하나씩 넘기는 핑퐁 패턴에 적합하다.
- `CountdownEvent`는 지정한 개수만큼 `Signal()`이 호출되어 카운트가 0이 되면 대기자를 깨우는 일회성 도구로, 여러 워커의 작업 완료를 기다렸다가 결과를 취합할 때 유용하다. 카운트 감소는 예외 상황에서도 누락되지 않도록 `finally`에서 처리해야 한다.
- `Barrier`는 여러 참가자가 매 라운드 `SignalAndWait()`을 호출해 서로를 기다렸다가 함께 다음 라운드로 넘어가는, 재사용 가능한 동기화 도구다. 라운드 경계를 맞춰야 하는 반복 시뮬레이션에 적합하다.
- 대부분의 경우 저수준 이벤트 객체보다 `Task` 기반 API가 더 안전하고 간결한 대안이 되지만, 그 내부 동작을 이해하려면 이번 장의 개념이 기반이 된다.

## 연습문제

1. `ManualResetEvent`와 `AutoResetEvent`의 차이를 `Set()` 호출 이후의 동작을 기준으로 설명하고, 각각에 어울리는 실전 시나리오를 하나씩 제시하라.
2. `ManualResetEventSlim`이 `ManualResetEvent`보다 유리한 상황과 불리한 상황(예: 대기 시간이 매우 길 것으로 예상되는 경우)을 각각 설명하라.
3. 4개의 워커 스레드가 각자 1부터 1000까지의 합을 계산하고, 모든 워커가 끝나면 메인 스레드가 네 결과를 합산해 출력하는 프로그램을 `CountdownEvent`를 사용해 작성하라.
4. `Barrier`를 사용해 3개의 스레드가 5라운드에 걸쳐 각자 임의의 지연 후 "라운드 N 완료"를 출력하고, 매 라운드가 끝날 때마다 "라운드 N 종료"라는 메시지를 한 번씩만 출력하도록 프로그램을 작성하라.
5. `CountdownEvent`의 `Signal()` 호출을 `try`/`finally`로 감싸지 않았을 때 발생할 수 있는 문제를 예를 들어 설명하고, 이런 문제를 예방하기 위한 코딩 습관을 제안하라.

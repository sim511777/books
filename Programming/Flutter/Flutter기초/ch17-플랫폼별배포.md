# 17장. 플랫폼별 배포

## 들어가며

지금까지는 주로 `flutter run`으로 개발용 기기나 에뮬레이터에서 앱을 실행하며 기능을 하나씩 만들어왔다. 하지만 앱을 만드는 목적은 결국 다른 사람이 실제로 설치해서 쓸 수 있는 결과물을 내놓는 데 있다. Flutter가 1장에서 내세운 핵심 가치, 즉 "하나의 코드베이스로 여러 플랫폼을 감당한다"는 약속이 실제로 지켜지는지 확인하는 순간이 바로 배포 단계다. 이 장에서는 같은 Flutter 프로젝트를 Android, iOS, 웹, 데스크톱(Windows, macOS, Linux)용으로 각각 빌드하는 방법과, 각 플랫폼이 요구하는 최소한의 준비 사항을 살펴본다.

미리 밝혀둘 것이 있다. 이 장은 "빌드"까지를 다룬다. 즉 배포 가능한 실행 파일이나 패키지를 만들어내는 과정에 집중하며, Google Play와 App Store에 실제로 앱을 등록하고 심사를 통과시키는 절차는 이 책의 범위 밖이다. 그 부분은 각 스토어의 정책과 심사 기준이 수시로 바뀌는 영역이라, 책 한 권으로 다루기보다는 공식 문서를 그때그때 확인하는 편이 안전하다. 다만 무엇이 필요한지 개념 수준에서는 짚고 넘어간다.

## 빌드 명령의 공통 구조

Flutter는 플랫폼마다 `flutter build <플랫폼>` 형태의 명령을 제공한다. 어떤 플랫폼을 대상으로 하든 명령의 골격은 같고, 뒤에 붙는 플랫폼 이름과 옵션만 달라진다. 프로젝트 루트에서 다음과 같이 실행 가능한 빌드 대상 목록을 확인할 수 있다.

```bash
flutter build --help
```

빌드하기 전에는 항상 `flutter doctor`로 개발 환경이 정상인지 점검하는 습관을 들이는 것이 좋다. 특히 iOS나 Android처럼 별도의 네이티브 SDK가 필요한 플랫폼은, SDK 경로나 라이선스 동의가 누락되어 있으면 빌드 단계에서 바로 오류가 나기 때문이다.

```bash
flutter doctor -v
```

## Android 빌드

Android용 빌드 산출물은 크게 두 가지 형태로 나뉜다. 하나는 APK(Android Package), 다른 하나는 AAB(Android App Bundle)다.

```bash
flutter build apk
```

이 명령은 `build/app/outputs/flutter-apk/app-release.apk` 경로에 릴리스 빌드 APK를 생성한다. APK는 기기에 직접 설치하거나 Google Play가 아닌 경로로 배포할 때 적합하다. 반면 Google Play에 정식으로 등록할 계획이라면 AAB 형식을 권장한다.

```bash
flutter build appbundle
```

AAB는 APK와 달리 기기별 최적화를 Google Play가 대신 처리해주는 번들 형식으로, Play 스토어가 요구하는 표준 업로드 형식이다.

기기 아키텍처별로 크기를 줄인 APK가 필요하다면 다음처럼 분할 빌드도 가능하다.

```bash
flutter build apk --split-per-abi
```

### Android 배포 준비: 서명 키

Android는 배포용 빌드에 반드시 서명(signing)이 필요하다. 개발 중에는 Flutter가 디버그용 서명 키를 자동으로 사용하지만, 실제 배포용 릴리스 빌드는 개발자가 직접 만든 서명 키로 서명해야 한다. 서명 키는 다음과 같은 명령으로 생성한다.

```bash
keytool -genkey -v -keystore ~/upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

이렇게 만든 키스토어 파일의 경로와 비밀번호는 프로젝트의 `android/key.properties` 파일에 기록하고, `android/app/build.gradle`에서 이 정보를 읽어 릴리스 빌드에 적용하도록 설정한다. 이 서명 키는 앱을 한 번 배포한 이후에는 계속 같은 키를 사용해야 업데이트 배포가 가능하므로, 안전한 곳에 백업해두는 것이 중요하다.

## iOS 빌드

```bash
flutter build ios
```

여기서 반드시 정직하게 짚고 넘어가야 할 제약이 있다. **iOS용 빌드는 macOS에서만 가능하다.** Xcode 자체가 macOS 전용 도구이고, Flutter의 iOS 빌드 과정은 내부적으로 Xcode 툴체인을 호출하기 때문에, Windows나 Linux에서는 `flutter build ios`를 실행할 수 없다. 이 책의 실습 환경이 Windows라면, iOS 빌드와 배포는 실제 macOS 환경(또는 클라우드 macOS 빌드 서비스)에서 별도로 진행해야 한다는 점을 알아두자.

또한 iOS 빌드는 APK처럼 명령 한 줄로 끝나지 않는다. 다음과 같은 추가 준비가 필요하다.

- **Apple Developer 계정**: iOS 기기에 앱을 설치하거나 App Store에 배포하려면 유료 Apple Developer Program 가입이 필요하다.
- **서명 인증서(Signing Certificate)**: 앱이 신뢰할 수 있는 개발자가 만들었음을 증명하는 인증서로, Apple Developer 계정을 통해 발급받는다.
- **프로비저닝 프로파일(Provisioning Profile)**: 어떤 앱이, 어떤 기기에서, 어떤 인증서로 실행될 수 있는지를 정의하는 파일이다. 개발용과 배포용 프로파일이 별도로 존재한다.
- **Xcode 설정**: 프로젝트를 Xcode로 열어 Bundle Identifier, 서명 팀(Team), 배포 대상 iOS 버전 등을 설정해야 한다.

`flutter build ios`로 만들어진 결과물은 그 자체로 배포 가능한 최종 파일이 아니라, Xcode에서 아카이브(Archive)하고 서명하는 후속 과정을 거쳐야 App Store Connect에 업로드할 수 있는 형태(.ipa)가 된다. 이 서명과 아카이브 절차는 Xcode의 그래픽 인터페이스를 통해 진행하는 것이 일반적이다.

## 웹 빌드

```bash
flutter build web
```

이 명령은 `build/web` 디렉터리에 HTML, JavaScript(또는 WebAssembly), CSS, 정적 자산으로 구성된 웹 애플리케이션을 생성한다. 웹 빌드의 장점은 배포 준비가 가장 단순하다는 점이다. Android의 서명 키나 iOS의 인증서 같은 별도의 서명 절차가 필요 없다. `build/web` 폴더의 내용을 그대로 정적 파일 호스팅 서비스(예를 들면 Firebase Hosting, GitHub Pages, 일반 웹 서버 등)에 업로드하기만 하면 배포가 끝난다.

```bash
flutter build web --release --base-href /myapp/
```

`--base-href` 옵션은 앱이 웹사이트의 하위 경로(예: `example.com/myapp/`)에 배포될 때, 앱 내부의 리소스 경로를 올바르게 잡아주기 위해 사용한다. 루트 경로에 배포한다면 기본값을 그대로 사용해도 된다.

## 데스크톱 빌드

Flutter는 Windows, macOS, Linux 데스크톱 애플리케이션도 같은 코드베이스로 빌드할 수 있다.

```bash
flutter build windows
flutter build macos
flutter build linux
```

여기서 중요한 원칙은 각 명령을 **해당 운영체제 위에서** 실행해야 한다는 것이다. `flutter build windows`는 Windows에서, `flutter build macos`는 macOS에서, `flutter build linux`는 Linux에서 실행해야 한다. 이는 iOS와 같은 이유다. 각 플랫폼용 실행 파일은 그 플랫폼의 네이티브 툴체인(Windows는 Visual Studio의 C++ 빌드 도구, macOS는 Xcode, Linux는 GTK 개발 라이브러리 등)을 거쳐 만들어지기 때문에, 크로스 컴파일이 기본적으로 지원되지 않는다.

빌드 결과물은 각각 다음과 같은 위치에 생성된다.

- Windows: `build/windows/x64/runner/Release/`
- macOS: `build/macos/Build/Products/Release/`
- Linux: `build/linux/x64/release/bundle/`

데스크톱 앱은 모바일 스토어 같은 강제적인 심사 절차 없이, 생성된 실행 파일과 관련 리소스를 그대로 압축해서 배포하거나, 각 플랫폼의 패키징 형식(Windows의 MSIX, macOS의 .dmg 또는 App Store, Linux의 Snap이나 Flatpak 등)으로 감싸서 배포할 수 있다. 이런 패키징 형식까지 자세히 다루는 것은 이 책의 범위를 넘어서므로, 실행 파일을 만드는 단계까지만 짚고 넘어간다.

## 모바일 스토어 배포는 범위 밖

Android용 AAB나 iOS용 .ipa 파일을 손에 넣었다고 해서 곧바로 사용자에게 앱이 전달되는 것은 아니다. Google Play와 App Store는 각각 다음과 같은 별도의 절차를 요구한다.

- **Google Play Console**을 통한 앱 등록, 스토어 등록정보(설명, 스크린샷, 개인정보처리방침 등) 작성, 콘텐츠 등급 설문, 단계적 출시 설정
- **App Store Connect**를 통한 앱 등록, 심사 지침(App Review Guidelines) 준수 여부 검토, 사람이 직접 확인하는 심사 과정

이 절차들은 각 스토어의 정책에 따라 계속 바뀌고, 요구 서류나 심사 기준도 앱의 카테고리와 사용하는 권한에 따라 달라진다. 이 책에서는 "빌드된 결과물을 스토어에 올리려면 이런 별도의 심사·정책 절차가 기다리고 있다"는 사실만 짚고, 구체적인 등록 화면이나 심사 팁까지는 다루지 않는다. 실제로 스토어에 앱을 출시할 때는 각 스토어의 최신 공식 가이드를 확인하는 것이 가장 정확하다.

## 하나의 코드베이스, 여섯 개의 플랫폼

이 장을 마무리하며 1장에서 던졌던 질문으로 돌아가보자. "iOS용과 Android용을 따로 만들어야 한다면 어떨까"라는 물음에서 출발한 Flutter는, 지금까지 이 책에서 작성해온 단 하나의 Dart 코드베이스를 가지고 Android, iOS, 웹, Windows, macOS, Linux까지 총 여섯 개 플랫폼용 결과물을 만들어낼 수 있음을 이 장에서 직접 확인했다. 물론 플랫폼마다 서명 키, 인증서, 네이티브 툴체인처럼 그 플랫폼 고유의 준비 과정은 피할 수 없다. 하지만 화면을 그리는 위젯 코드, 상태 관리 로직, 네트워크 통신 코드는 단 한 줄도 고치지 않고 그대로 재사용된다. 이것이 1장에서 말한 "하나의 코드베이스"라는 약속이 빌드와 배포 단계까지 이어지는 방식이며, Flutter가 다른 크로스플랫폼 기술과 구분되는 실질적인 이유다.

## 요약

- `flutter build apk`와 `flutter build appbundle`은 Android용 빌드를 생성하며, Google Play에는 AAB 형식이 권장된다. 배포용 빌드에는 개발자가 직접 만든 서명 키가 필요하다.
- `flutter build ios`는 iOS용 빌드를 생성하지만 macOS에서만 실행할 수 있으며, Apple Developer 계정, 서명 인증서, 프로비저닝 프로파일이 필요하고 최종 배포 전 Xcode에서 아카이브·서명 과정을 거쳐야 한다.
- `flutter build web`은 별도의 서명 절차 없이 정적 파일 형태의 웹 애플리케이션을 생성하며, 정적 호스팅 서비스에 업로드하는 것만으로 배포할 수 있다.
- `flutter build windows`, `flutter build macos`, `flutter build linux`는 각각 해당 운영체제 위에서만 실행 가능하며, 그 플랫폼의 네이티브 툴체인을 필요로 한다.
- Google Play와 App Store에 앱을 정식 등록하려면 각 스토어의 별도 심사·정책 절차를 거쳐야 하며, 이 책은 그 세부 절차는 다루지 않는다.
- Flutter의 핵심 가치는 하나의 Dart 코드베이스로 여섯 개 플랫폼용 결과물을 만들어낼 수 있다는 데 있으며, 플랫폼별 준비 과정이 필요할 뿐 UI와 로직 코드는 재사용된다.

## 연습문제

1. `flutter build apk`와 `flutter build appbundle`의 차이를 설명하고, 각각 어떤 배포 상황에 적합한지 서술하라.
2. iOS 빌드가 Windows나 Linux에서는 불가능한 이유를 Xcode와의 관계를 들어 설명하라.
3. 웹 빌드가 Android나 iOS 빌드에 비해 배포 준비 과정이 단순한 이유는 무엇인가?
4. 데스크톱 빌드(Windows, macOS, Linux)를 각각 해당 운영체제에서만 실행해야 하는 이유를 설명하라.
5. 이 장에서 다루지 않은 "모바일 스토어 심사 절차"에는 어떤 종류의 작업들이 포함될지 추측해보고, 왜 이 책의 범위를 벗어난다고 판단했는지 자신의 말로 정리해보라.

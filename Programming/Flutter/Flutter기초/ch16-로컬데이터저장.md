## 들어가며

15장에서는 앱이 서버와 통신해서 데이터를 주고받는 방법을 배웠다. 하지만 모든 데이터를 매번 서버에서 새로 받아올 필요는 없다. 사용자가 마지막으로 선택한 다크 모드 여부, 로그인 상태, 즐겨찾기 목록, 할 일 목록처럼 기기 안에 계속 남아 있어야 하는 데이터도 많다. 앱을 껐다가 다시 켰을 때도 이런 데이터가 사라지지 않으려면, 인터넷 연결과 무관하게 기기 자체에 데이터를 저장하는 방법이 필요하다. 이를 로컬 데이터 저장(local persistence)이라고 부른다.

Flutter 생태계에는 로컬 저장을 위한 패키지가 여러 가지 있지만, 이 장에서는 가장 널리 쓰이는 두 가지, 즉 간단한 값 저장에 쓰이는 `shared_preferences`와 구조화된 대량의 데이터에 쓰이는 `sqflite`를 다룬다. 두 패키지가 어떤 상황에 적합한지 이해하고 나면, 18장의 할 일 관리 프로젝트에서 어떤 방식으로 데이터를 영속화할지 자연스럽게 판단할 수 있게 될 것이다.

## shared_preferences: 간단한 키-값 저장

### 언제 쓰는가

`shared_preferences`는 이름 그대로 키(key)와 값(value) 한 쌍으로 이루어진 간단한 데이터를 저장하는 패키지다. 내부적으로는 Android에서는 `SharedPreferences`, iOS에서는 `UserDefaults`라는 각 플랫폼의 기본 저장소를 그대로 활용하며, Flutter는 이를 공통된 Dart API로 감싸서 제공한다.

이 패키지가 어울리는 데이터는 다음과 같은 것들이다.

- 사용자가 다크 모드를 켰는지 여부(`true`/`false`)
- 로그인 여부, 혹은 마지막으로 로그인한 사용자의 아이디
- 온보딩 화면을 이미 봤는지 여부
- 글자 크기, 알림 on/off 같은 간단한 설정값

즉 값 하나하나가 독립적이고, 개수가 몇 개 되지 않으며, 복잡한 검색이나 정렬이 필요 없는 데이터에 적합하다.

### pubspec.yaml에 추가하기

`http` 패키지와 마찬가지로 `pubspec.yaml`의 `dependencies`에 추가한다.

```yaml
dependencies:
  flutter:
    sdk: flutter
  shared_preferences: ^2.2.0
```

### 값 저장하고 불러오기

`shared_preferences`를 사용하려면 먼저 `SharedPreferences.getInstance()`를 호출해 인스턴스를 얻어야 한다. 이 호출 자체가 비동기 작업이기 때문에 `Future<SharedPreferences>`를 반환한다.

```dart
import 'package:shared_preferences/shared_preferences.dart';

Future<void> saveSettings() async {
  final prefs = await SharedPreferences.getInstance();

  await prefs.setBool('isDarkMode', true);
  await prefs.setString('username', '홍길동');
  await prefs.setInt('fontSize', 16);
}
```

값을 저장할 때는 자료형에 맞는 메서드를 사용한다. `setBool`, `setString`, `setInt`, `setDouble`, `setStringList`처럼 자료형별로 이름이 나뉘어 있는데, 이는 각 플랫폼의 저장소가 타입이 있는 값을 다루기 때문이다. 값을 저장한 뒤에는 다시 읽어올 수 있다.

```dart
Future<void> loadSettings() async {
  final prefs = await SharedPreferences.getInstance();

  final isDarkMode = prefs.getBool('isDarkMode') ?? false;
  final username = prefs.getString('username') ?? '손님';
  final fontSize = prefs.getInt('fontSize') ?? 14;

  print('다크 모드: $isDarkMode, 사용자: $username, 글자 크기: $fontSize');
}
```

`getBool`, `getString` 같은 조회 메서드는 해당 키에 저장된 값이 없으면 `null`을 반환한다. 그래서 `??` 연산자로 기본값을 지정해두는 습관이 중요하다. 앱을 처음 설치해서 아직 아무 설정도 저장한 적 없는 사용자라면, 이 기본값이 곧 앱의 초기 상태가 된다.

### 실전 예제: 로그인 상태 유지하기

`shared_preferences`가 실제로 자주 쓰이는 예로, 로그인 여부를 저장해서 앱을 재시작해도 로그인 화면을 다시 보여주지 않는 코드를 살펴보자.

```dart
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

class AuthStorage {
  static const _keyIsLoggedIn = 'isLoggedIn';

  static Future<void> setLoggedIn(bool value) async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.setBool(_keyIsLoggedIn, value);
  }

  static Future<bool> isLoggedIn() async {
    final prefs = await SharedPreferences.getInstance();
    return prefs.getBool(_keyIsLoggedIn) ?? false;
  }
}
```

이렇게 저장/조회 로직을 별도의 클래스로 감싸두면, 키 이름을 문자열로 여기저기 흩어 적지 않아도 되고, 나중에 저장 방식을 바꾸더라도 이 클래스 안쪽만 수정하면 된다는 장점이 있다. 앱을 시작할 때는 14장에서 배운 `FutureBuilder`로 `AuthStorage.isLoggedIn()`의 결과를 확인해서, 로그인이 되어 있으면 홈 화면으로, 아니면 로그인 화면으로 분기할 수 있다.

```dart
class AppRoot extends StatelessWidget {
  const AppRoot({super.key});

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<bool>(
      future: AuthStorage.isLoggedIn(),
      builder: (context, snapshot) {
        if (snapshot.connectionState == ConnectionState.waiting) {
          return const Center(child: CircularProgressIndicator());
        }
        final loggedIn = snapshot.data ?? false;
        return loggedIn ? const HomeScreen() : const LoginScreen();
      },
    );
  }
}
```

## sqflite: 구조화된 대량의 데이터

### 언제 shared_preferences로는 부족한가

`shared_preferences`는 값 몇 개를 저장하는 데는 편리하지만, 다음과 같은 상황에서는 한계가 뚜렷하다.

- 할 일 목록처럼 **같은 구조를 가진 레코드가 여러 개** 있고, 그 개수가 계속 늘어나는 경우
- 특정 조건에 맞는 항목만 골라내거나(예: "완료되지 않은 할 일만"), 정렬하거나, 개수를 세는 등 **검색·조회 로직**이 필요한 경우
- 여러 종류의 데이터가 서로 연관되어 있는 경우(예: 할 일과 카테고리)

이런 데이터를 억지로 `shared_preferences`에 저장하려면, 리스트 전체를 JSON 문자열로 직렬화해서 하나의 키에 통째로 넣고, 읽어올 때마다 전체를 다시 파싱해야 한다. 항목이 몇 개 안 될 때는 그럭저럭 버틸 수 있지만, 데이터가 많아질수록 비효율적이고 관리하기도 어려워진다. 이럴 때 필요한 것이 실제 데이터베이스, 즉 `sqflite`다.

`sqflite`는 SQLite라는, 모바일 기기에 내장되어 널리 쓰이는 경량 관계형 데이터베이스를 Flutter에서 다룰 수 있게 해주는 pub.dev의 표준 패키지다. 테이블(table)이라는 형태로 데이터를 구조화해서 저장하고, SQL이라는 질의 언어로 원하는 데이터만 정확히 골라올 수 있다.

### 기본 흐름 (개념 수준)

`sqflite`를 프로젝트에서 쓰려면 마찬가지로 `pubspec.yaml`에 의존성을 추가한다.

```yaml
dependencies:
  flutter:
    sdk: flutter
  sqflite: ^2.3.0
  path: ^1.9.0
```

`path` 패키지는 데이터베이스 파일을 기기의 어느 경로에 저장할지 지정하는 데 함께 쓰인다. 전체적인 사용 흐름은 다음 네 단계로 요약할 수 있다.

**1단계: 데이터베이스 열기 및 테이블 생성.** 앱이 처음 실행될 때 데이터베이스 파일을 열고(없으면 새로 생성하고), 그 안에 어떤 열(column)로 구성된 테이블을 만들지 정의한다. 예를 들어 할 일 목록이라면 `id`, `title`, `isDone` 같은 열을 가진 `todos` 테이블을 만든다.

```dart
// 개념을 보여주기 위한 흐름 예시 (세부 문법은 sqflite 공식 문서를 참고)
final db = await openDatabase(
  path,
  version: 1,
  onCreate: (db, version) {
    return db.execute(
      'CREATE TABLE todos(id INTEGER PRIMARY KEY, title TEXT, isDone INTEGER)',
    );
  },
);
```

**2단계: 데이터 삽입.** 새 레코드를 추가할 때는 `insert` 메서드에 테이블 이름과 삽입할 값을 `Map` 형태로 넘긴다.

```dart
await db.insert(
  'todos',
  {'title': '장보기', 'isDone': 0},
);
```

**3단계: 데이터 조회.** `query` 메서드로 테이블에서 데이터를 읽어온다. 결과는 `List<Map<String, dynamic>>` 형태로 돌아오는데, 이는 앞서 15장에서 JSON을 파싱했을 때 얻었던 구조와 매우 비슷하다. 그래서 이 결과 역시 `factory Todo.fromJson(...)`과 같은 방식의 팩토리 생성자로 모델 클래스로 변환하는 것이 일반적이다.

```dart
final List<Map<String, dynamic>> rows = await db.query('todos');
final todos = rows.map((row) => Todo.fromJson(row)).toList();
```

**4단계: 데이터 수정 및 삭제.** `update`와 `delete` 메서드로 특정 조건에 맞는 레코드를 수정하거나 지운다.

```dart
await db.update(
  'todos',
  {'isDone': 1},
  where: 'id = ?',
  whereArgs: [1],
);

await db.delete(
  'todos',
  where: 'id = ?',
  whereArgs: [1],
);
```

이 책은 SQL 문법 자체를 깊이 다루는 책이 아니므로, `CREATE TABLE`이나 `WHERE` 절의 세부 문법까지 파고들지는 않는다. 지금 단계에서 기억해둘 것은 "테이블을 만들고, 행을 넣고, 조건에 맞게 조회·수정·삭제한다"는 관계형 데이터베이스의 기본 흐름과, `sqflite`의 조회 결과가 `Map` 리스트로 돌아온다는 점, 그리고 이를 모델 클래스로 변환해서 다루는 패턴이 15장의 JSON 처리 패턴과 본질적으로 같다는 사실이다.

## 선택 기준: shared_preferences vs sqflite

두 패키지 중 무엇을 선택할지는 저장하려는 데이터의 성격에 따라 결정된다. 다음 기준으로 판단해보면 대부분의 경우에 답이 명확해진다.

| 기준 | shared_preferences | sqflite |
|---|---|---|
| 데이터 형태 | 독립적인 값 하나하나 (설정값 등) | 같은 구조를 반복하는 레코드 여러 개 |
| 데이터 양 | 적음 (수십 개 이하의 키) | 많을 수 있음 (수백~수만 건) |
| 조회 방식 | 키로 값 하나를 바로 꺼냄 | 조건 검색, 정렬, 집계 등이 필요 |
| 데이터 간 관계 | 없음 | 있을 수 있음 (예: 할 일과 카테고리) |
| 대표 예시 | 다크 모드 여부, 로그인 상태, 마지막 접속 시각 | 할 일 목록, 메모 목록, 주문 내역 |

간단히 정리하면, **"이 앱을 어떻게 쓸지에 대한 설정값 몇 개"라면 `shared_preferences`**, **"사용자가 계속 추가·삭제·수정하는 목록형 데이터"라면 `sqflite`**를 선택한다고 기억해두면 실무에서도 크게 틀리지 않는다.

## 18장 예고: 할 일 관리 앱의 데이터 저장

이 책의 마지막 장인 18장에서는 지금까지 배운 내용을 총동원해 할 일 관리 앱을 처음부터 끝까지 만들어본다. 할 일 목록은 정확히 이 장에서 설명한 "같은 구조의 레코드가 여러 개 반복되는 데이터"에 해당하므로, 그 프로젝트에서는 `sqflite`를 사용해 할 일 항목들을 기기에 영속적으로 저장하는 방법을 실제로 구현하게 된다. 앱을 완전히 종료했다가 다시 열어도 추가했던 할 일과 완료 표시가 그대로 남아 있는 것을 직접 확인하면서, 이 장에서 배운 개념이 실전 프로젝트에서 어떻게 이어지는지 확인해보자.

## 요약

- `shared_preferences`는 Android의 `SharedPreferences`와 iOS의 `UserDefaults`를 감싼 키-값 저장 패키지로, `SharedPreferences.getInstance()`로 인스턴스를 얻은 뒤 `setBool`/`getBool`, `setString`/`getString` 등으로 값을 읽고 쓴다.
- `shared_preferences`는 설정값, 로그인 여부처럼 개수가 적고 독립적인 값을 저장하는 데 적합하다.
- `sqflite`는 SQLite 기반의 관계형 데이터베이스 패키지로, 테이블을 만들고(`CREATE TABLE`) 행을 삽입·조회·수정·삭제하는 흐름으로 동작하며, 조회 결과는 `Map` 리스트 형태로 반환된다.
- `sqflite`는 할 일 목록처럼 같은 구조의 레코드가 여러 개 반복되고, 조건 검색이나 정렬이 필요한 데이터에 적합하다.
- 저장하려는 데이터가 "설정값 몇 개"인지 "반복되는 목록형 데이터"인지를 기준으로 두 패키지 중 하나를 선택하면 된다.
- 18장의 할 일 관리 앱 프로젝트에서는 `sqflite`를 사용해 할 일 데이터를 기기에 영속적으로 저장하는 실습을 진행한다.

## 연습문제

1. `shared_preferences`와 `sqflite`가 각각 어떤 종류의 데이터를 저장하는 데 적합한지, 이 장에서 제시한 판단 기준을 근거로 설명해보라.
2. `SharedPreferences.getInstance()`가 `Future`를 반환하는 이유를 14장에서 배운 비동기 개념과 연결지어 설명해보라.
3. 앱의 "글자 크기 설정(정수)"과 "즐겨찾기한 게시물 목록(여러 건의 레코드)"을 각각 저장한다고 할 때, 어떤 패키지를 사용할지 선택하고 그 이유를 서술해보라.
4. 이 장의 `AuthStorage` 클래스처럼, 저장/조회 로직을 별도 클래스로 감싸두는 것이 왜 유지보수에 유리한지 설명해보라.
5. `sqflite`의 조회 결과가 `List<Map<String, dynamic>>` 형태로 반환된다는 점이, 15장에서 다룬 `jsonDecode`의 결과와 어떻게 비슷한지 비교해보고, 두 경우 모두 모델 클래스로 변환하는 것이 왜 권장되는지 설명해보라.

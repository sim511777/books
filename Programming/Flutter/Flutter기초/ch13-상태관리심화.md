6장에서는 `setState`를 이용해 위젯의 상태를 바꾸고 화면을 다시 그리는 방법을 배웠습니다. 버튼을 누르면 숫자가 올라가는 카운터, 체크박스를 누르면 목록 항목이 완료 표시로 바뀌는 화면처럼 상태와 그 상태를 사용하는 위젯이 가깝게 붙어 있을 때는 `setState`만으로 충분했습니다. 하지만 앱이 커지고 위젯 트리가 깊어지면 이야기가 달라집니다. 이 장에서는 `setState` 하나만으로는 감당하기 어려워지는 상황을 짚어보고, 이를 해결하기 위해 Flutter가 코어 프레임워크 차원에서 제공하는 `InheritedWidget`과, 실무에서 널리 쓰이는 상태 관리 패키지 `provider`의 핵심 개념을 소개합니다.

## setState의 한계: prop drilling 문제

먼저 구체적인 예를 하나 살펴보겠습니다. 사용자가 선택한 테마 색상을 앱 전체에서 공유해야 하는 상황을 가정해봅시다. 이 색상 값은 최상위 화면에서 관리되지만, 실제로 이 값을 사용하는 위젯은 트리 깊숙한 곳에 있는 버튼이나 아이콘일 수 있습니다.

```dart
class HomeScreen extends StatefulWidget {
  const HomeScreen({super.key});

  @override
  State<HomeScreen> createState() => _HomeScreenState();
}

class _HomeScreenState extends State<HomeScreen> {
  Color _accentColor = Colors.blue;

  void _changeColor(Color color) {
    setState(() {
      _accentColor = color;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('설정')),
      body: SettingsPanel(
        accentColor: _accentColor,
        onColorChanged: _changeColor,
      ),
    );
  }
}
```

`SettingsPanel`은 다시 `SettingsSection`에게, `SettingsSection`은 `ColorPickerTile`에게, `ColorPickerTile`은 마지막으로 `ColorSwatchButton`에게 `accentColor`와 `onColorChanged`를 전달해야 합니다.

```dart
class SettingsPanel extends StatelessWidget {
  final Color accentColor;
  final ValueChanged<Color> onColorChanged;

  const SettingsPanel({
    super.key,
    required this.accentColor,
    required this.onColorChanged,
  });

  @override
  Widget build(BuildContext context) {
    return SettingsSection(
      accentColor: accentColor,
      onColorChanged: onColorChanged,
    );
  }
}

class SettingsSection extends StatelessWidget {
  final Color accentColor;
  final ValueChanged<Color> onColorChanged;

  const SettingsSection({
    super.key,
    required this.accentColor,
    required this.onColorChanged,
  });

  @override
  Widget build(BuildContext context) {
    return ColorPickerTile(
      accentColor: accentColor,
      onColorChanged: onColorChanged,
    );
  }
}

class ColorPickerTile extends StatelessWidget {
  final Color accentColor;
  final ValueChanged<Color> onColorChanged;

  const ColorPickerTile({
    super.key,
    required this.accentColor,
    required this.onColorChanged,
  });

  @override
  Widget build(BuildContext context) {
    return ColorSwatchButton(
      color: accentColor,
      onTap: () => onColorChanged(Colors.orange),
    );
  }
}
```

정작 `accentColor`를 값 그대로 사용하는 것은 `ColorSwatchButton`뿐인데, `SettingsPanel`과 `SettingsSection`은 그저 값을 다음 자식에게 넘겨주는 역할만 하고 있습니다. 이렇게 실제로는 필요 없는 중간 위젯들이 하위 위젯에 데이터를 전달하기 위한 통로 역할만 하게 되는 현상을 흔히 **prop drilling**(속성 뚫고 내려가기)이라고 부릅니다.

prop drilling은 코드가 동작하지 않는 것은 아니지만 몇 가지 실질적인 문제를 만듭니다.

- 중간 위젯들이 자신과 무관한 매개변수를 계속 받아서 전달해야 하므로 생성자가 지저분해집니다.
- 트리 구조가 조금만 바뀌어도(중간에 위젯을 하나 더 끼워 넣는 등) 관련된 모든 위젯의 매개변수를 함께 고쳐야 합니다.
- 값을 사용하는 위젯과 값을 소유한 위젯이 코드상 멀리 떨어져 있어 어디서 상태가 바뀌는지 추적하기 어려워집니다.

트리가 3~4단계 정도면 참을 만하지만, 실제 앱에서는 화면 하나에 위젯이 열 단계 넘게 중첩되는 일이 흔합니다. 이런 상황에서 값이 필요한 위젯마다 트리를 거슬러 올라가 값을 넘겨받는 대신, 트리 아래 어디에서든 필요한 위젯이 직접 값을 "꺼내 쓸" 수 있다면 훨씬 편할 것입니다. 이것이 바로 `InheritedWidget`이 해결하는 문제입니다.

## InheritedWidget: 트리를 거슬러 올라가지 않고 값에 접근하기

`InheritedWidget`은 Flutter 프레임워크가 기본으로 제공하는 위젯 클래스로, 위젯 트리의 상위에 데이터를 "게시"해 두면 그 아래에 있는 모든 자손 위젯이 부모 체인을 몰라도 `BuildContext`를 통해 그 데이터에 접근할 수 있게 해줍니다. 사실 `Theme.of(context)`나 `MediaQuery.of(context)`처럼 지금까지 사용해온 여러 `of(context)` 형태의 API들이 내부적으로 `InheritedWidget`을 기반으로 동작합니다.

원리를 이해하기 위해 앞서 살펴본 색상 공유 예제를 `InheritedWidget`으로 직접 구현해보겠습니다.

```dart
class AccentColorProvider extends InheritedWidget {
  final Color accentColor;
  final ValueChanged<Color> onColorChanged;

  const AccentColorProvider({
    super.key,
    required this.accentColor,
    required this.onColorChanged,
    required super.child,
  });

  static AccentColorProvider of(BuildContext context) {
    final result =
        context.dependOnInheritedWidgetOfExactType<AccentColorProvider>();
    assert(result != null, 'AccentColorProvider가 트리에 없습니다.');
    return result!;
  }

  @override
  bool updateShouldNotify(AccentColorProvider oldWidget) {
    return accentColor != oldWidget.accentColor;
  }
}
```

몇 가지 핵심 요소를 짚어보겠습니다.

- `AccentColorProvider`는 내려보내고 싶은 데이터(`accentColor`, `onColorChanged`)를 필드로 가지고 있고, 자신의 하위 트리가 될 `child`를 감싸는 형태로 만들어집니다.
- `of(BuildContext context)`라는 정적 메서드를 관례적으로 만들어 둡니다. 내부에서 `context.dependOnInheritedWidgetOfExactType<T>()`를 호출하면, 현재 `context`에서 트리를 거슬러 올라가며 가장 가까운 `AccentColorProvider`를 찾아 반환합니다. 이 메서드를 호출한 위젯은 해당 `InheritedWidget`의 값이 바뀔 때 자동으로 다시 빌드되도록 등록됩니다.
- `updateShouldNotify`는 `InheritedWidget`이 갱신될 때(즉 부모가 새 `AccentColorProvider` 인스턴스를 만들 때) 이를 구독 중인 자손 위젯들에게 다시 빌드하라고 알려야 하는지를 결정합니다. 값이 실제로 바뀌었을 때만 `true`를 반환해 불필요한 리빌드를 막습니다.

이제 최상위 위젯은 상태를 들고 있다가 값이 바뀔 때마다 `AccentColorProvider`로 하위 트리를 다시 감싸주기만 하면 됩니다.

```dart
class HomeScreen extends StatefulWidget {
  const HomeScreen({super.key});

  @override
  State<HomeScreen> createState() => _HomeScreenState();
}

class _HomeScreenState extends State<HomeScreen> {
  Color _accentColor = Colors.blue;

  void _changeColor(Color color) {
    setState(() {
      _accentColor = color;
    });
  }

  @override
  Widget build(BuildContext context) {
    return AccentColorProvider(
      accentColor: _accentColor,
      onColorChanged: _changeColor,
      child: Scaffold(
        appBar: AppBar(title: const Text('설정')),
        body: const SettingsPanel(),
      ),
    );
  }
}
```

이제 `SettingsPanel`과 `SettingsSection`은 더 이상 `accentColor`나 `onColorChanged`를 매개변수로 받을 필요가 없습니다. 실제로 값을 사용하는 `ColorSwatchButton`만 `AccentColorProvider.of(context)`를 호출해 직접 값을 꺼내 쓰면 됩니다.

```dart
class ColorSwatchButton extends StatelessWidget {
  const ColorSwatchButton({super.key});

  @override
  Widget build(BuildContext context) {
    final provider = AccentColorProvider.of(context);

    return GestureDetector(
      onTap: () => provider.onColorChanged(Colors.orange),
      child: Container(
        width: 40,
        height: 40,
        color: provider.accentColor,
      ),
    );
  }
}
```

중간에 있던 `SettingsPanel`, `SettingsSection`, `ColorPickerTile`은 이제 색상과 무관한, 오직 자신의 레이아웃 책임만 지는 깔끔한 위젯으로 되돌아갔습니다. prop drilling이 사라진 것입니다.

## 실무에서는 provider 패키지를 사용한다

`InheritedWidget`은 원리를 이해하기에는 좋지만, 직접 사용하기에는 다소 번거롭습니다. `updateShouldNotify`를 매번 직접 구현해야 하고, 상태가 바뀔 때마다 상위 `StatefulWidget`에서 새 `InheritedWidget` 인스턴스로 트리를 다시 감싸주는 코드를 반복해서 작성해야 합니다. 상태의 종류가 여러 개로 늘어나면 이런 보일러플레이트는 금방 부담스러워집니다.

그래서 Flutter 커뮤니티에서는 `InheritedWidget`을 기반으로 좀 더 사용하기 쉬운 형태로 다듬은 상태 관리 패키지들을 많이 만들어왔고, 그중 가장 널리 쓰이는 것이 pub.dev에 공개된 `provider` 패키지입니다. `provider`는 Flutter 팀이 공식적으로 예제와 문서에서 자주 언급할 만큼 사실상 표준처럼 자리 잡았습니다. 여기서는 실제 사용법을 상세히 다루기보다, 핵심 개념 네 가지가 서로 어떤 역할을 하는지 큰 그림을 잡는 데 집중하겠습니다.

### ChangeNotifier: 변경을 알릴 수 있는 모델

`ChangeNotifier`는 Dart의 `foundation` 라이브러리에 포함된 클래스로, 자신의 상태가 바뀌었음을 리스너들에게 알리는 기능을 캡슐화하고 있습니다. 상태를 담는 모델 클래스가 이 클래스를 상속하면, 값이 바뀔 때 `notifyListeners()`를 호출해 "나를 지켜보고 있는 위젯들아, 다시 그려라"라고 알릴 수 있습니다.

```dart
class AccentColorModel extends ChangeNotifier {
  Color _accentColor = Colors.blue;

  Color get accentColor => _accentColor;

  void changeColor(Color color) {
    _accentColor = color;
    notifyListeners();
  }
}
```

앞서 `InheritedWidget` 예제와 비교하면, 상태와 그 상태를 바꾸는 로직이 한곳에 모여 있어 훨씬 정돈된 모습입니다.

### ChangeNotifierProvider: 위젯 트리에 상태 공급하기

`ChangeNotifierProvider`는 `ChangeNotifier` 인스턴스를 위젯 트리에 공급하는 역할을 합니다. `InheritedWidget`에서 상위 `StatefulWidget`이 하던 역할을 대신해준다고 볼 수 있습니다.

```dart
void main() {
  runApp(
    ChangeNotifierProvider(
      create: (context) => AccentColorModel(),
      child: const MyApp(),
    ),
  );
}
```

이렇게 트리 상단에 한 번 배치해두면, `MyApp` 아래 어떤 위젯에서도 `AccentColorModel`에 접근할 수 있습니다.

### context.watch와 context.read: 값을 읽는 두 가지 방법

`provider`는 위젯이 상태를 읽는 방법을 두 가지로 구분합니다.

- `context.watch<T>()`는 `T` 타입의 상태를 구독합니다. 이 상태가 `notifyListeners()`로 변경을 알릴 때마다 이 메서드를 호출한 위젯이 자동으로 다시 빌드됩니다. 화면에 값을 표시해야 해서 변경을 계속 반영해야 하는 `build` 메서드 안에서 사용합니다.
- `context.read<T>()`는 상태를 딱 한 번만 읽어옵니다. 값이 바뀌어도 이 메서드를 호출한 위젯을 다시 빌드하지 않습니다. 버튼의 `onPressed` 콜백처럼 상태를 변경하는 메서드만 호출하면 되고 값 자체를 화면에 그릴 필요는 없는 경우에 사용합니다.

```dart
class ColorSwatchButton extends StatelessWidget {
  const ColorSwatchButton({super.key});

  @override
  Widget build(BuildContext context) {
    // build 메서드 안에서 값을 표시하므로 watch를 사용해 변경을 구독한다.
    final accentColor = context.watch<AccentColorModel>().accentColor;

    return GestureDetector(
      // 콜백 안에서는 값을 바꾸는 메서드만 호출하므로 read로 충분하다.
      onTap: () => context.read<AccentColorModel>().changeColor(Colors.orange),
      child: Container(
        width: 40,
        height: 40,
        color: accentColor,
      ),
    );
  }
}
```

`build` 메서드 안에서도 `context.read<T>()`를 쓸 수는 있지만, 그렇게 하면 상태가 바뀌어도 위젯이 갱신되지 않아 화면이 최신 값을 반영하지 못하는 버그로 이어지기 쉽습니다. 반대로 콜백 안에서 `context.watch<T>()`를 쓰는 것은 허용되지 않습니다. 화면을 그리며 값을 표시할 때는 `watch`, 이벤트에 반응해 상태를 변경할 때는 `read`라는 원칙을 기억해두면 헷갈리지 않습니다.

이 네 가지 요소를 합쳐서 보면, `provider`는 결국 "`ChangeNotifier`로 상태와 변경 알림 로직을 한곳에 모으고, `ChangeNotifierProvider`로 트리에 공급하며, 위젯은 `watch`나 `read`로 필요한 방식에 맞게 값을 꺼내 쓴다"는 흐름으로 요약할 수 있습니다. 이 구조 덕분에 상태를 소유하는 위젯과 상태를 사용하는 위젯 사이의 거리가 아무리 멀어도 중간 위젯들을 오염시키지 않고 데이터를 전달할 수 있습니다.

## 이 책에서의 선택: 여전히 setState 중심으로

여기까지 읽고 나면 "그럼 앞으로는 항상 provider를 써야 하는 걸까?" 하는 의문이 들 수 있습니다. 하지만 이 책의 나머지 장, 특히 18장의 실전 프로젝트에서는 학습의 편의를 위해 계속 `setState` 중심으로 코드를 작성합니다. 여기에는 몇 가지 이유가 있습니다.

- `setState`는 Flutter 코어에 내장된 가장 기본적인 메커니즘이라 별도의 패키지 설치나 개념 학습 없이 바로 이해할 수 있습니다.
- 예제 규모의 앱에서는 위젯 트리가 그리 깊지 않아 prop drilling이 심각한 문제로 번지지 않습니다.
- 상태 관리는 그 자체로 큰 주제이며, `provider` 외에도 `Riverpod`, `Bloc` 등 다양한 접근 방식이 존재합니다. 입문서에서 이들을 모두 다루기보다, 문제의 본질(트리 깊숙이 데이터를 전달하는 어려움)과 Flutter가 이를 해결하는 근본 원리(`InheritedWidget`)를 이해하는 데 집중하는 편이 실용적입니다.

다만 실무에서 앱을 만들다 보면 화면 수가 늘어나고, 여러 화면이 같은 데이터를 공유해야 하며, 상태를 바꾸는 로직이 여기저기 흩어지기 시작하는 시점이 반드시 옵니다. 그 시점이 바로 `setState`를 넘어 `provider` 같은 상태 관리 패키지를 도입할 때입니다. 지금 배운 `ChangeNotifier`, `ChangeNotifierProvider`, `context.watch`, `context.read`라는 네 가지 개념은 그때 가서 `provider`의 공식 문서를 펼쳤을 때 낯설지 않게 코드를 읽어나갈 수 있는 밑거름이 되어 줄 것입니다.

## 요약

- 여러 단계의 부모-자식 위젯을 거쳐 값을 전달해야 하는 번거로움을 prop drilling이라고 하며, `setState`만으로 상태를 관리할 때 위젯 트리가 깊어지면 이 문제가 두드러집니다.
- `InheritedWidget`은 위젯 트리 상위에 데이터를 게시해, 트리를 거슬러 올라가지 않고도 하위 어디서든 `context.dependOnInheritedWidgetOfExactType<T>()`로 값에 접근할 수 있게 하는 Flutter 코어 메커니즘입니다. `Theme.of(context)` 같은 기존 API들도 내부적으로 이 메커니즘을 사용합니다.
- `updateShouldNotify`는 `InheritedWidget`의 값이 바뀌었을 때 이를 구독한 위젯들을 다시 빌드할지 결정합니다.
- 실무에서는 `InheritedWidget`을 직접 다루기보다, 이를 기반으로 만들어진 `provider` 패키지를 널리 사용합니다. `ChangeNotifier`는 변경을 알릴 수 있는 상태 모델을, `ChangeNotifierProvider`는 그 모델을 위젯 트리에 공급하는 역할을 합니다.
- `context.watch<T>()`는 값이 바뀔 때마다 위젯을 다시 빌드하도록 구독하며 주로 `build` 메서드 안에서 사용하고, `context.read<T>()`는 값을 한 번만 읽고 다시 빌드하지 않으며 주로 이벤트 콜백 안에서 상태를 변경할 때 사용합니다.
- 이 책의 나머지 장과 18장의 실전 프로젝트는 학습 목적상 `setState` 중심으로 진행하지만, 앱이 커지면 `provider` 같은 상태 관리 패키지 도입을 고려하는 것이 실무에서의 자연스러운 다음 단계입니다.

## 연습문제

1. prop drilling이 무엇인지 설명하고, 이것이 왜 코드 유지보수를 어렵게 만드는지 두 가지 이상의 이유를 들어 서술하세요.
2. `InheritedWidget`을 상속해 `LocaleProvider`라는 클래스를 만들어보세요. 현재 언어 코드(`String locale`, 예: `'ko'`, `'en'`)를 필드로 가지고, 관례에 따라 정적 메서드 `of(BuildContext context)`를 제공해야 합니다.
3. `updateShouldNotify` 메서드가 하는 역할은 무엇이며, 만약 이 메서드가 항상 `false`를 반환하도록 잘못 구현하면 어떤 문제가 발생할지 설명하세요.
4. `ChangeNotifier`를 상속하는 `CartModel` 클래스를 작성하세요. 장바구니에 담긴 상품 개수를 나타내는 `itemCount` getter와, 상품을 추가하며 `notifyListeners()`를 호출하는 `addItem()` 메서드를 포함해야 합니다.
5. `context.watch<T>()`와 `context.read<T>()`의 차이를 설명하고, 각각을 어떤 상황에서 사용해야 하는지 구체적인 예를 들어 서술하세요.

지금까지 만든 예제는 전부 창(window) 하나로 완결되는 프로그램이었습니다. `slint::include_modules!()`로 가져온 컴포넌트를 `::new()`로 하나 만들고, `run()`을 한 번 호출하면 프로그램의 화면 이야기는 끝이었습니다. 하지만 실제로 만드는 데스크톱 애플리케이션은 그렇게 단순하지만은 않습니다. 채팅 프로그램이라면 대화 목록을 보여주는 메인 창과 별도로 새 메시지를 알려 주는 작은 알림 창이 뜰 수 있고, 사용자의 접속 상태를 바꾸는 작은 드롭다운 메뉴가 버튼 옆에 잠깐 나타났다 사라지기도 합니다. 이번 장에서는 이런 상황을 다루는 두 가지 도구, 즉 서로 독립된 여러 개의 `Window`를 Rust 쪽에서 관리하는 방법과, 부모 창 위에 가볍게 떠 있는 `PopupWindow`를 살펴봅니다. 예제로는 채팅 애플리케이션을 하나 만들어 가면서, 창을 여러 개 인스턴스화하는 법, 창끼리 데이터를 공유하는 법, 창을 닫는 시점을 코드로 제어하는 법을 차례로 익히겠습니다.

## 화면 전환과 진짜 다중 창은 다르다

먼저 짚어야 할 구분이 있습니다. "화면이 여러 개 필요하다"는 요구가 항상 "창이 여러 개 필요하다"는 뜻은 아닙니다. 하나의 `Window` 안에 여러 화면을 담아 두고, 정수 상태값 하나로 어떤 화면을 보여줄지 전환하는 방식도 충분히 유효한 설계입니다. 이 경우 사용자에게는 언제나 창이 하나만 보이고, 그 안의 내용만 바뀝니다.

반면 이번 장에서 다루는 것은 운영체제가 실제로 별도의 창으로 인식하는, 각자 독립된 제목표시줄과 위치·크기를 가진 진짜 다중 창입니다. 메인 창은 그대로 둔 채 알림 창만 닫고 싶다거나, 두 창을 화면의 다른 위치에 나란히 띄워 두고 싶은 경우에는 화면 전환만으로는 해결되지 않고, 창 자체를 여러 개 두어야 합니다.

## 서로 중첩되지 않는 최상위 Window 여러 개 선언하기

여러 창을 만드는 첫걸음은 `.slint` 파일 안에 `Window`를 상속하는 컴포넌트를 필요한 개수만큼 선언하는 것입니다. 이때 중요한 점은 한 컴포넌트를 다른 컴포넌트의 자식으로 중첩시키지 않고, 서로 나란한 최상위 컴포넌트로 둔다는 것입니다.

```slint
// chat-app.slint
import { Button } from "std-widgets.slint";

export component ChatWindow inherits Window {
    title: "채팅";
    width: 360px;
    height: 220px;

    callback open-notification();

    VerticalLayout {
        padding: 20px;
        spacing: 12px;

        Text {
            text: "채팅 목록 창입니다.";
            font-size: 18px;
        }

        Button {
            text: "알림 창 열기";
            clicked => { open-notification(); }
        }
    }
}

export component NotifyWindow inherits Window {
    title: "새 메시지 알림";
    width: 280px;
    height: 140px;

    callback dismiss();

    VerticalLayout {
        padding: 16px;
        spacing: 10px;

        Text { text: "새 메시지가 도착했습니다."; }

        Button {
            text: "확인";
            clicked => { dismiss(); }
        }
    }
}
```

`ChatWindow`와 `NotifyWindow`는 둘 다 `Window`를 상속하지만 어느 한쪽이 다른 쪽 안에 들어가 있지 않습니다. 같은 파일 안에 나란히 선언된 독립된 최상위 컴포넌트입니다. Slint 컴파일러는 `export`가 붙은 최상위 컴포넌트마다 별도의 Rust 구조체를 생성하므로, 이 둘은 Rust 쪽에서 각각 `ChatWindow`, `NotifyWindow`라는 이름의 타입으로 나타납니다.

`ChatWindow`에는 `open-notification`이라는 콜백만 선언해 두고 본문을 비워 두었습니다. "알림 창을 실제로 화면에 띄우는 동작"은 `ChatWindow` 하나만으로는 할 수 없는, 다른 창의 존재를 알고 있는 Rust 코드에서만 가능한 일이기 때문입니다.

## Rust에서 각 창 인스턴스를 만들고 화면에 띄우기

`build.rs`에서 `slint_build::compile("chat-app.slint")`로 위 파일을 컴파일했다고 가정하면, `main.rs`에서는 `slint::include_modules!()`로 생성된 코드를 가져와 각 창을 인스턴스화합니다.

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;
    let notify_window = NotifyWindow::new()?;

    let notify_weak = notify_window.as_weak();
    chat_window.on_open_notification(move || {
        if let Some(notify_window) = notify_weak.upgrade() {
            notify_window.show().unwrap();
        }
    });

    chat_window.run()
}
```

`ChatWindow::new()`와 `NotifyWindow::new()`는 각각 `Result<Self, slint::PlatformError>`를 반환합니다. `?` 연산자로 풀어내면 두 창은 서로 완전히 독립된 `ComponentHandle` 값이 됩니다. `chat_window.on_open_notification(...)`으로 `open-notification` 콜백에 클로저를 연결하고, 그 클로저 안에서 `notify_window.show()`를 호출해 버튼 클릭이 다른 창을 띄우는 동작으로 이어지게 만들었습니다.

여기서 `notify_window`를 클로저 안에 직접 옮기지 않고 `as_weak()`로 약한 참조를 얻어 `upgrade()`로 다시 강한 참조를 얻는 방식을 썼습니다. 다음 절에서 이 방식이 왜 필요한지 자세히 살펴보겠습니다.

`chat_window.run()`은 `show()`, `run_event_loop()`, `hide()`를 순서대로 호출해 주는 편의 함수입니다. `run()`이 이벤트 루프를 시작한 뒤에도, 클로저 안에서 `notify_window.show()`를 호출하는 것처럼 다른 창을 추가로 화면에 띄우는 동작은 자연스럽게 처리됩니다. 이벤트 루프는 애플리케이션 전체에 하나만 존재하며 특정 창에 종속되지 않기 때문입니다.

두 창을 프로그램 시작과 동시에 함께 띄우고 싶다면, 어느 한쪽에서 `run()`을 호출하는 대신 각각 `show()`를 호출한 뒤 자유 함수 `slint::run_event_loop()`로 이벤트 루프를 직접 시작할 수도 있습니다.

```rust
fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;
    let notify_window = NotifyWindow::new()?;

    let notify_weak = notify_window.as_weak();
    chat_window.on_open_notification(move || {
        if let Some(notify_window) = notify_weak.upgrade() {
            notify_window.show().unwrap();
        }
    });

    chat_window.show()?;
    notify_window.show()?;
    slint::run_event_loop()
}
```

`slint::run_event_loop()`는 이미 `show()`로 화면에 띄워 둔 모든 창을 대상으로 이벤트를 처리합니다. 이 함수는 화면에 보이는 창이 하나도 남지 않을 때까지, 혹은 코드에서 명시적으로 `slint::quit_event_loop()`를 호출할 때까지 반환하지 않습니다.

## 약한 참조로 창 사이의 순환 소유를 피하기

앞의 예제에서 `notify_window.as_weak()`를 쓴 이유를 짚고 넘어가겠습니다. `ComponentHandle`은 내부적으로 강한 참조 카운트를 가진 값입니다. 만약 `notify_window`라는 값 자체를 클로저 안으로 옮겨 버리면, 그 클로저는 `chat_window`가 소유한 콜백 저장소 안에 들어가므로 `notify_window`의 강한 참조 하나가 `chat_window` 안에 갇히게 됩니다. 방향이 하나뿐이라면 이것만으로는 큰 문제가 없지만, `notify_window`도 `chat_window`를 다시 참조해야 하는 상황이라면 이야기가 달라집니다.

`NotifyWindow`의 "확인" 버튼을 누르면 `ChatWindow`의 읽지 않은 메시지 수를 0으로 되돌리는 기능을 추가해 보겠습니다.

```slint
export component ChatWindow inherits Window {
    title: "채팅";
    width: 360px;
    height: 220px;

    in-out property <int> unread-count: 0;
    callback open-notification();
    callback clear-unread();
    clear-unread => { unread-count = 0; }

    VerticalLayout {
        padding: 20px;
        spacing: 12px;

        Text { text: "읽지 않은 메시지: " + unread-count; }

        Button {
            text: "알림 창 열기";
            clicked => { open-notification(); }
        }
    }
}
```

이제 `NotifyWindow`의 `dismiss` 콜백이 눌렸을 때 `ChatWindow`의 `clear-unread`를 호출해야 하므로, 두 창이 서로를 참조하는 양방향 구조가 됩니다. 이럴 때 양쪽 모두 강한 참조 대신 약한 참조를 잡아 두면 순환 소유를 피할 수 있습니다.

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;
    let notify_window = NotifyWindow::new()?;

    chat_window.set_unread_count(3);

    let notify_weak_for_open = notify_window.as_weak();
    chat_window.on_open_notification(move || {
        if let Some(notify_window) = notify_weak_for_open.upgrade() {
            notify_window.show().unwrap();
        }
    });

    let chat_weak_for_dismiss = chat_window.as_weak();
    let notify_weak_for_dismiss = notify_window.as_weak();
    notify_window.on_dismiss(move || {
        if let Some(chat_window) = chat_weak_for_dismiss.upgrade() {
            chat_window.invoke_clear_unread();
        }
        if let Some(notify_window) = notify_weak_for_dismiss.upgrade() {
            notify_window.hide().unwrap();
        }
    });

    chat_window.run()
}
```

`chat_window.set_unread_count(3)`처럼 `in-out property`로 선언한 프로퍼티는 Rust 쪽에서 `set_<프로퍼티명>`, `get_<프로퍼티명>`으로 읽고 쓸 수 있습니다. `clear-unread`처럼 `.slint` 안에서 직접 구현을 채운 콜백은 Rust에서 `invoke_<콜백명>()`으로 호출할 수 있는데, 이는 UI에서 버튼을 눌러 호출하는 것과 완전히 동일하게 동작합니다.

만약 `notify_window` 값 자체를 두 콜백 클로저 양쪽에 강한 참조로 옮겨 넣었다면, `chat_window`의 콜백 저장소가 `notify_window`의 강한 참조를 쥐고 있는 동시에 `notify_window`의 콜백 저장소도 `chat_window`의 강한 참조를 쥐게 되어, 두 창이 서로를 붙잡고 놓아주지 않는 구조가 됩니다. `as_weak()`로 얻은 `Weak<T>`는 참조 카운트에 영향을 주지 않으므로, 이런 순환을 만들지 않으면서도 필요할 때 `upgrade()`로 안전하게 접근할 수 있습니다. 콜백 클로저 안에서 다른 창(혹은 자기 자신)을 참조해야 할 때는 이렇게 약한 참조를 기본값으로 삼는 것이 안전한 습관입니다.

## 창을 닫는 시점 제어하기: on_close_requested

사용자가 창의 X 버튼을 누르면 기본적으로 그 창은 화면에서 사라집니다. 정확히는 `hide()`가 호출된 것과 같은 상태가 되며, 창을 나타내던 `ComponentHandle` 자체가 즉시 파괴되는 것은 아닙니다. `NotifyWindow`처럼 부수적인 창이 이렇게 닫히는 것은 자연스럽지만, `ChatWindow`처럼 프로그램의 마지막 창이 닫히는 순간에는 `run_event_loop()`가 반환되면서 프로그램 전체가 종료됩니다. 즉 화면에 보이는 창이 하나도 남지 않게 되는 순간이 곧 이벤트 루프의 종료 시점입니다.

이 기본 동작을 그대로 받아들이지 않고, "정말 닫아도 되는지" 코드로 판단하고 싶을 때는 `ComponentHandle::window()`가 돌려주는 `Window` 값의 `on_close_requested`를 사용합니다.

```rust
use slint::CloseRequestResponse;

let chat_weak = chat_window.as_weak();
chat_window.window().on_close_requested(move || {
    let chat_window = chat_weak.unwrap();
    if chat_window.get_unread_count() > 0 {
        chat_window.invoke_open_notification();
        CloseRequestResponse::KeepWindowShown
    } else {
        CloseRequestResponse::HideWindow
    }
});
```

`on_close_requested`에 등록한 클로저는 사용자가 창을 닫으려고 시도할 때마다 호출되며, `CloseRequestResponse::HideWindow`나 `CloseRequestResponse::KeepWindowShown` 중 하나를 반환해야 합니다. `HideWindow`를 반환하면 원래대로 창이 닫히고, `KeepWindowShown`을 반환하면 닫기 요청이 무시되고 창이 그대로 유지됩니다. 위 예제는 읽지 않은 메시지가 남아 있으면 알림 창을 다시 띄우면서 닫기를 취소하고, 없으면 정상적으로 닫히게 만듭니다.

이 클로저는 `chat_window` 자기 자신의 `Window`에 등록하는 것이므로, `chat_window` 값 자체를 클로저 안에 강하게 옮기면 `chat_window`가 자기 자신을 소유하는 순환이 생겨 버립니다. 그래서 여기서도 `as_weak()`로 얻은 약한 참조를 클로저 안에서 `unwrap()`(같은 스레드에서 여전히 살아 있는 자기 자신을 되찾는 것이므로 안전합니다)하는 방식을 씁니다.

## 창 사이에서 데이터 공유하기 (1): Global 싱글톤의 함정

여러 창을 다루다 보면 "두 창이 같은 정보를 보여줘야 하는데, 굳이 콜백을 일일이 연결하지 않고 12장에서 배운 Global 싱글톤을 공유하면 되지 않을까?"라는 생각이 자연스럽게 듭니다. 사용자 프로필 이름을 두 창이 함께 표시하는 예로 확인해 보겠습니다.

```slint
export global UserProfile {
    in-out property <string> display-name: "손님";
}

export component ChatWindow inherits Window {
    title: "채팅";
    width: 320px;
    height: 160px;

    Text { text: "안녕하세요, " + UserProfile.display-name; }
}

export component ProfileWindow inherits Window {
    title: "프로필 편집";
    width: 260px;
    height: 140px;

    callback name-changed(string);
}
```

여기서 반드시 기억해야 할 함정이 있습니다. `ChatWindow::new()`와 `ProfileWindow::new()`는 서로 독립된 컴포넌트 트리를 만드는 별개의 호출입니다. 두 컴포넌트가 `.slint` 코드상으로 같은 이름의 `UserProfile`을 참조하고 있더라도, 각 `new()` 호출은 그 Global의 **자기만의 인스턴스**를 만듭니다. `profile_window` 쪽 `UserProfile.display-name`을 바꿔도 `chat_window`가 보고 있는 `UserProfile` 인스턴스는 자동으로 갱신되지 않습니다.

따라서 창 사이에 Global 데이터를 공유하려면 Rust 코드가 양쪽의 Global 인스턴스를 명시적으로 동기화해 주어야 합니다.

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;
    let profile_window = ProfileWindow::new()?;

    let chat_weak = chat_window.as_weak();
    let profile_weak = profile_window.as_weak();
    profile_window.on_name_changed(move |new_name| {
        if let Some(chat_window) = chat_weak.upgrade() {
            chat_window.global::<UserProfile>().set_display_name(new_name.clone());
        }
        if let Some(profile_window) = profile_weak.upgrade() {
            profile_window.global::<UserProfile>().set_display_name(new_name);
        }
    });

    chat_window.show()?;
    profile_window.show()?;
    slint::run_event_loop()
}
```

`global::<UserProfile>()`은 해당 창이 가진 `UserProfile` 인스턴스에 접근하는 통로입니다. `name-changed` 콜백 하나가 눌릴 때마다 두 창의 `UserProfile`을 모두 `set_display_name`으로 갱신해 주는 것이 이 함정을 피하는 방법입니다. 창이 늘어날수록 이런 동기화 코드도 함께 늘어나므로, 실제 프로젝트에서는 "값이 바뀌면 관리 중인 모든 창의 Global을 갱신한다"는 로직을 한 함수로 모아 두고 새 창을 추가할 때마다 그 목록에 등록하는 편이 유지보수에 유리합니다.

## 창 사이에서 데이터 공유하기 (2): Rc<RefCell<>>로 단일 진실 공급원 만들기

Global을 창마다 일일이 동기화하는 대신, 진짜 상태는 Rust 쪽에 단 하나만 두고 각 창의 Global은 그 상태를 화면에 비추는 거울로만 쓰는 방법도 있습니다. 공유할 상태를 `Rc<RefCell<T>>`로 감싸 두면, 여러 클로저가 이 값을 함께 참조하면서도 러스트의 소유권 규칙을 지킬 수 있습니다.

```rust
use std::cell::RefCell;
use std::rc::Rc;

slint::include_modules!();

#[derive(Default)]
struct AppState {
    display_name: String,
}

fn sync_windows(state: &AppState, chat_window: &ChatWindow, profile_window: &ProfileWindow) {
    let name: slint::SharedString = state.display_name.as_str().into();
    chat_window.global::<UserProfile>().set_display_name(name.clone());
    profile_window.global::<UserProfile>().set_display_name(name);
}

fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;
    let profile_window = ProfileWindow::new()?;

    let state = Rc::new(RefCell::new(AppState {
        display_name: "손님".to_string(),
    }));

    sync_windows(&state.borrow(), &chat_window, &profile_window);

    let state_for_callback = state.clone();
    let chat_weak = chat_window.as_weak();
    let profile_weak = profile_window.as_weak();
    profile_window.on_name_changed(move |new_name| {
        state_for_callback.borrow_mut().display_name = new_name.to_string();

        if let (Some(chat_window), Some(profile_window)) =
            (chat_weak.upgrade(), profile_weak.upgrade())
        {
            sync_windows(&state_for_callback.borrow(), &chat_window, &profile_window);
        }
    });

    chat_window.show()?;
    profile_window.show()?;
    slint::run_event_loop()
}
```

`AppState`는 순수한 Rust 구조체로, Slint와는 아무 관계가 없습니다. `Rc<RefCell<AppState>>`를 클로저마다 `.clone()`해서 넘겨주면, 각 클로저는 같은 힙 데이터를 함께 참조하게 됩니다. `sync_windows` 함수는 이 상태를 읽어서 두 창의 `UserProfile` Global에 그대로 밀어 넣는 역할만 합니다. 창이 몇 개로 늘어나든 `sync_windows` 함수의 인자와 본문만 늘리면 되므로, 동기화 로직이 콜백마다 흩어지지 않고 한 곳에 모입니다.

이 방식은 공유할 데이터가 단순한 문자열 하나를 넘어, 나중에 파일에 저장하거나 네트워크로 보내야 하는 등 Slint 프로퍼티만으로 표현하기 애매한 로직을 포함하게 될 때 특히 유리합니다. Global 동기화는 "화면에 보여줄 값 몇 개를 창끼리 맞추는" 가벼운 경우에, `Rc<RefCell<>>` 패턴은 "여러 창이 참조하는 진짜 애플리케이션 상태를 Rust 쪽에서 관리하는" 무거운 경우에 각각 어울립니다.

## PopupWindow: 부모 창 위에 뜨는 가벼운 오버레이

지금까지 다룬 것은 각자 독립된 제목표시줄을 가진 진짜 별도의 창이었습니다. 하지만 상태 표시줄 옆에 나타나는 작은 드롭다운 메뉴처럼, 부모 창에 붙어서 짧게 나타났다 사라지는 UI 조각에는 이런 무거운 창이 어울리지 않습니다. Slint는 이런 용도로 `PopupWindow`라는 전용 엘리먼트를 제공합니다.

`PopupWindow`는 이름에 "Window"가 들어 있지만 앞서 다룬 `Window` 상속 컴포넌트와는 성격이 다릅니다. 별도의 데스크톱 창이 아니라 **부모 창의 좌표계 위에 떠 있는 오버레이**이며, Rust 쪽에 별도의 타입이 생성되지도 않습니다. 팝업을 열고 닫는 모든 제어는 그 팝업이 선언된 `.slint` 컴포넌트 안에서 이루어집니다.

```slint
import { Button } from "std-widgets.slint";

export component ChatWindow inherits Window {
    title: "채팅";
    width: 320px;
    height: 220px;

    callback status-selected(string);
    in-out property <string> current-status: "온라인";

    status-menu := PopupWindow {
        x: 16px;
        y: 46px;
        width: 120px;
        height: 96px;
        close-policy: PopupClosePolicy.close-on-click-outside;

        Rectangle {
            background: white;
            border-width: 1px;
            border-color: #cccccc;

            VerticalLayout {
                for label in ["온라인", "자리비움", "오프라인"]: TouchArea {
                    clicked => {
                        current-status = label;
                        status-selected(label);
                        status-menu.close();
                    }

                    Text {
                        text: label;
                        color: parent.has-hover ? #2266cc : #222222;
                    }
                }
            }
        }
    }

    VerticalLayout {
        padding: 20px;
        spacing: 12px;

        TouchArea {
            height: 26px;
            clicked => { status-menu.show(); }

            Text {
                text: "상태: " + current-status + (status-menu.is-open ? " ▲" : " ▼");
            }
        }
    }
}
```

`status-menu := PopupWindow { ... }`처럼 `:=` 문법으로 이름(id)을 붙여 두면 같은 컴포넌트 안 다른 곳에서 이 이름으로 팝업을 제어할 수 있습니다. `PopupWindow`는 기본적으로 보이지 않는 상태로 시작하고, `status-menu.show()`를 호출해야 나타납니다. `x`와 `y`는 부모 창(`ChatWindow`)의 왼쪽 위 모서리를 기준으로 한 상대 좌표입니다.

`close-policy` 프로퍼티는 팝업이 자동으로 닫히는 조건을 결정합니다. `PopupClosePolicy.close-on-click`(기본값, 팝업 안팎 어디를 클릭해도 닫힘), `PopupClosePolicy.close-on-click-outside`(팝업 바깥을 클릭했을 때만 닫힘), `PopupClosePolicy.no-auto-close`(자동으로 닫히지 않고 `.close()` 호출로만 닫힘) 세 가지 중 고를 수 있습니다. 위 예제에서는 `close-on-click-outside`를 골랐는데, 항목 자체를 클릭했을 때 팝업이 먼저 저절로 닫혀 버리면 `status-selected(label)`을 호출하는 순서가 꼬일 수 있기 때문입니다. 대신 각 항목의 `TouchArea`가 클릭되면 `current-status`를 갱신하고, `status-selected` 콜백으로 부모에 알린 뒤, `status-menu.close()`를 명시적으로 호출해 닫습니다.

`status-menu.is-open`은 팝업이 현재 열려 있는지를 나타내는 읽기 전용 불리언 프로퍼티입니다. 위 예제에서는 이 값을 이용해 상태 텍스트 옆의 화살표 방향(`▲`/`▼`)을 팝업이 열려 있는지에 따라 바꾸었습니다.

## 팝업의 선택 결과를 Rust로 전달하기

`status-selected` 콜백은 다른 콜백과 똑같이 Rust에서 `on_status_selected(...)`로 구독할 수 있습니다.

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let chat_window = ChatWindow::new()?;

    chat_window.on_status_selected(|label| {
        println!("상태가 '{label}'(으)로 바뀌었습니다.");
    });

    chat_window.run()
}
```

정리하면, `PopupWindow`를 다루는 흐름은 이번 장에서 배운 것들의 조합입니다. `TouchArea`나 `Button`의 `clicked`에서 `.show()`를 호출해 팝업을 열고, 팝업 안의 인터랙션에서 `.close()`를 호출해 닫으며, 팝업 안에서 일어난 선택 결과는 콜백을 통해 부모 컴포넌트, 필요하다면 Rust 코드까지 전달합니다. `PopupWindow` 자체는 Rust 쪽에 어떤 타입도 만들지 않는다는 점에서, 각각 독립된 `ComponentHandle`을 갖는 `Window` 파생 창들과는 근본적으로 다른 도구라는 사실을 기억해 두면 좋습니다.

## 요약

- 진짜 독립된 OS 창이 여러 개 필요할 때는 서로 중첩되지 않은 별도의 `component ... inherits Window`를 선언하고, Rust에서 각각 `::new()?`로 인스턴스화합니다.
- 한 창에서 `run()`을 호출하면 이벤트 루프가 시작되고, 그 안에서 다른 창의 `show()`를 호출해도 정상적으로 처리됩니다. 여러 창을 동시에 띄우고 싶다면 각각 `show()`한 뒤 `slint::run_event_loop()`를 호출하는 방식도 쓸 수 있습니다.
- 콜백 클로저 안에서 다른 창이나 자기 자신을 참조할 때는 `as_weak()`/`upgrade()`로 약한 참조를 쓰는 것이 기본입니다. 강한 참조를 그대로 옮기면 창들이 서로를(혹은 자기 자신을) 붙잡는 순환 소유가 생길 수 있습니다.
- `ComponentHandle::window().on_close_requested(...)`로 닫기 요청을 가로채, `CloseRequestResponse::HideWindow`나 `KeepWindowShown`을 반환해 닫기를 허용하거나 취소할 수 있습니다. 화면에 보이는 창이 하나도 남지 않으면 이벤트 루프가 종료됩니다.
- 같은 이름의 Global 싱글톤이라도 `::new()` 호출마다 독립된 인스턴스가 생성됩니다. 여러 창의 Global을 맞추려면 Rust 코드가 각 창의 `global::<T>()`를 명시적으로 동기화해야 합니다. 공유 상태가 더 복잡해지면 `Rc<RefCell<T>>`에 진짜 상태를 두고, 필요할 때마다 각 창의 Global로 값을 밀어 넣는 패턴이 유지보수에 유리합니다.
- `PopupWindow`는 별도의 데스크톱 창이 아니라 부모 창 좌표 위에 뜨는 오버레이로, Rust 쪽에 별도 타입을 만들지 않습니다. `close-policy`로 자동 닫힘 동작을, `is-open`으로 열림 상태를 확인하며 `.show()`/`.close()`로 열고 닫습니다.

## 연습문제

1. `ChatWindow`와 `ProfileWindow`라는 두 개의 독립된 `Window` 파생 컴포넌트를 선언하고, `ChatWindow`의 버튼을 클릭하면 `ProfileWindow`가 열리도록 Rust 코드를 작성해 보세요. 두 창의 `ComponentHandle`을 서로의 콜백에서 참조할 때는 `as_weak()`를 사용해 보세요.
2. 두 창을 동시에 화면에 띄운 채 시작하는 프로그램을, `run()` 한 번으로 구현하는 방식과 `show()` + `slint::run_event_loop()` 조합으로 구현하는 방식 두 가지로 각각 작성해 보세요.
3. 같은 이름의 Global을 두 창이 참조하도록 만든 뒤, 한쪽 창에서 값을 바꿨을 때 다른 쪽 창에는 자동으로 반영되지 않는다는 사실을 직접 확인해 보세요. 그런 다음 `global::<T>()`를 이용한 동기화 코드를 추가해 두 창의 값이 일치하도록 고쳐 보세요.
4. 3번 문제를 `Rc<RefCell<AppState>>` 패턴으로 다시 구현하고, 세 번째 창을 추가해 세 창 모두가 같은 상태를 공유하도록 확장해 보세요.
5. `ChatWindow`에 `on_close_requested`를 등록해, 읽지 않은 메시지가 남아 있으면 닫기를 취소하고 그렇지 않으면 정상적으로 닫히도록 구현해 보세요. 그 다음 상태 선택 `PopupWindow`의 `close-policy`를 세 가지 값(`close-on-click`, `close-on-click-outside`, `no-auto-close`) 각각으로 바꿔가며 동작 차이를 관찰해 보세요.

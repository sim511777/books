지금까지 살펴본 예제는 화면에 놓일 엘리먼트의 개수가 미리 정해져 있었습니다. 버튼 하나, 입력창 하나, 텍스트 하나처럼 `.slint` 파일을 작성하는 시점에 이미 몇 개의 엘리먼트가 필요한지 알고 있었다는 뜻입니다. 그런데 실제로 만들게 될 애플리케이션 중 상당수는 그렇지 않습니다. 할 일 관리 앱은 사용자가 몇 개의 할 일을 등록할지 미리 알 수 없고, 채팅 앱은 대화가 길어질수록 메시지 개수가 계속 늘어납니다. 이렇게 "개수를 미리 알 수 없고 실행 중에 늘거나 줄어드는 목록"을 화면에 표시하는 방법이 이번 장의 주제입니다. 이 패턴은 18장에서 만들 할 일 관리 프로젝트의 뼈대이기도 하므로, 여기서 원리를 확실히 잡아 두면 그때 훨씬 수월해집니다.

## 프로퍼티만으로 목록을 표현하기 어려운 이유

5장에서 다룬 프로퍼티는 `int`, `bool`, `string`처럼 값 하나를 담는 상자였습니다. 항목이 딱 두세 개뿐이라면 `property <string> item-0`, `item-1`, `item-2`를 따로 선언하고 `Text` 엘리먼트를 그만큼 나열하는 방식으로 버틸 수 있을지도 모릅니다. 하지만 항목이 열 개, 백 개가 될 수도 있고, 무엇보다 실행 중에 사용자가 항목을 추가하거나 지울 수 있어야 한다면 이런 방식은 애초에 성립하지 않습니다. `.slint` 파일은 컴파일 시점에 고정되므로, "지금 몇 개의 `Text`를 그릴지"를 실행 중에 결정할 방법이 프로퍼티만으로는 없기 때문입니다.

Slint는 이 문제를 **모델(model)**이라는 별도의 개념으로 풀어냅니다. 모델은 같은 종류의 값을 여러 개 담을 수 있는 컬렉션이며, `.slint` 언어에는 모델의 항목 수만큼 엘리먼트를 자동으로 반복해서 그려 주는 `for` 구문이 마련되어 있습니다.

## `for` 구문으로 배열 프로퍼티 반복하기

가장 단순한 모델은 문자열을 대괄호로 감싼 배열 리터럴입니다.

```slint
export component TagList inherits Window {
    width: 240px;
    height: 180px;

    property <[string]> tags: ["rust", "slint", "gui"];

    VerticalLayout {
        padding: 12px;
        spacing: 4px;

        for tag in tags : Text {
            text: "# " + tag;
            font-size: 16px;
        }
    }
}
```

`property <[string]> tags`처럼 타입 이름을 대괄호로 감싸면 "그 타입의 값을 여러 개 담는 모델" 타입이 됩니다. 핵심은 `for 항목이름 in 모델 : 엘리먼트 { ... }` 구문입니다. `tags`에 담긴 항목 수만큼 `Text` 엘리먼트가 만들어지고, 각 `Text` 안에서는 `tag`라는 이름으로 그 반복 차례의 값을 참조할 수 있습니다. 지금은 항목이 세 개이므로 `Text`도 세 개가 만들어지는 셈입니다.

각 항목의 순서(인덱스)가 필요할 때는 대괄호를 하나 더 붙여 인덱스 변수를 함께 받을 수 있습니다.

```slint
for tag[index] in tags : Text {
    text: index + ": " + tag;
}
```

`index`에는 0부터 시작하는 정수가 담깁니다. 짝수/홀수 번째 항목의 배경을 다르게 칠하거나, 목록에 번호를 매기거나, 뒤에서 볼 것처럼 특정 항목을 지우는 콜백에 "몇 번째 항목인지"를 함께 넘길 때 이 인덱스가 요긴하게 쓰입니다.

## 구조체를 항목으로 갖는 모델

문자열 하나만 담긴 목록보다는, 여러 필드를 함께 가진 데이터를 나열해야 하는 경우가 실무에서는 훨씬 흔합니다. 할 일 목록이라면 "할 일 내용"과 "완료 여부"를 한 항목 안에 함께 담아야 합니다. 이럴 때는 구조체(`struct`)를 정의하고, 그 구조체의 모델을 선언합니다.

```slint
export struct TodoItem {
    text: string,
    done: bool,
}

export component TodoWindow inherits Window {
    width: 320px;
    height: 260px;

    property <[TodoItem]> todos: [
        { text: "Rust 문법 복습하기", done: true },
        { text: "모델 예제 작성하기", done: false },
        { text: "연습문제 풀어보기", done: false },
    ];

    VerticalLayout {
        padding: 12px;
        spacing: 6px;

        for todo in todos : Rectangle {
            height: 28px;
            background: todo.done ? #eafaf1 : #fdf2e9;

            Text {
                text: todo.done ? "[완료] " + todo.text : "[진행중] " + todo.text;
                color: todo.done ? #27ae60 : #d35400;
            }
        }
    }
}
```

`struct TodoItem { text: string, done: bool, }`으로 필드 두 개짜리 구조체를 정의하고, `property <[TodoItem]> todos`로 이 구조체의 모델을 선언했습니다. `for todo in todos` 안에서는 `todo.text`, `todo.done`처럼 점(`.`) 표기법으로 필드에 접근합니다. 항목이 문자열 대신 구조체라는 점만 다를 뿐, `for` 구문 자체의 사용법은 앞서 본 문자열 모델과 완전히 같습니다.

지금까지는 `.slint` 파일 안에서 모델을 리터럴로 직접 선언했습니다. 화면에 고정된 안내 문구를 나열하는 정도라면 이것으로 충분하지만, 실제 애플리케이션에서는 목록의 내용이 Rust 쪽 로직(파일에서 읽은 데이터, 사용자가 입력한 값, 서버 응답 등)에 따라 결정되는 경우가 대부분입니다. 이제 Rust에서 모델을 만들어 UI에 건네는 방법을 살펴보겠습니다.

## Rust에서 모델 다루기: `VecModel`과 `ModelRc`

Slint는 `.slint`의 배열 타입을 Rust 쪽에서 다루기 위한 공통 인터페이스로 `Model` 트레이트를 정의합니다. `.slint`에서 `property <[TodoItem]> todos;`처럼 선언된 모델 타입 프로퍼티는, 빌드 시점에 생성되는 Rust 코드에서 `slint::ModelRc<TodoItem>` 타입의 getter·setter로 대응됩니다. `ModelRc<T>`는 `Model` 트레이트를 구현하는 어떤 타입이든 감쌀 수 있는, 참조 카운트 기반의 공유 포인터라고 생각하면 됩니다.

직접 `Model` 트레이트를 구현하는 경우는 드물고, 대부분은 Slint가 기본으로 제공하는 `slint::VecModel<T>`를 사용합니다. `VecModel<T>`는 내부적으로 `Vec<T>`를 감싸고 있으면서, 항목을 추가·삭제할 때마다 그 변화를 UI에 알려 주는 기능까지 갖춘 타입입니다.

먼저 `.slint` 쪽을 라이브러리 형태로 다시 정리해 보겠습니다. `export`를 붙여 Rust 쪽에서 접근할 수 있게 하고, `todos` 프로퍼티에는 6장에서 다룬 방향성(`in`)을 붙였습니다.

```slint
export struct TodoItem {
    text: string,
    done: bool,
}

export component TodoWindow inherits Window {
    width: 320px;
    height: 260px;
    title: "할 일 목록";

    in property <[TodoItem]> todos;

    VerticalLayout {
        padding: 12px;
        spacing: 6px;

        for todo in todos : Text {
            text: todo.done ? "[완료] " + todo.text : "[진행중] " + todo.text;
        }
    }
}
```

`export struct TodoItem`은 빌드 과정에서 같은 이름의 필드를 가진 Rust 구조체로 변환됩니다. 문자열 필드는 `slint::SharedString`으로, `bool` 필드는 그대로 `bool`로 대응되며, 생성된 구조체에는 `Default`, `Clone`, `Debug`, `PartialEq`가 함께 구현됩니다. Rust 쪽에서 이 구조체를 값으로 만들 때는 다음과 같은 모양이 됩니다.

```rust
slint::include_modules!();

use slint::{ModelRc, VecModel};
use std::rc::Rc;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let ui = TodoWindow::new()?;

    let initial_todos: Rc<VecModel<TodoItem>> = Rc::new(VecModel::from(vec![
        TodoItem { text: "Rust 문법 복습하기".into(), done: true },
        TodoItem { text: "모델 예제 작성하기".into(), done: false },
        TodoItem { text: "연습문제 풀어보기".into(), done: false },
    ]));

    ui.set_todos(ModelRc::from(initial_todos));

    ui.run()?;
    Ok(())
}
```

`VecModel::from(vec![...])`으로 초기 항목을 담은 모델을 만들고, `Rc::new(...)`로 감쌌습니다. `ui.set_todos(...)`에는 `ModelRc<TodoItem>` 타입의 값이 필요한데, `Rc<VecModel<TodoItem>>`을 그대로 넘길 수는 없으므로 `ModelRc::from(...)`으로 한 번 변환해 줍니다. `.slint`의 `todos` 프로퍼티가 `in`으로 선언되어 있으므로, Rust 쪽에서는 `set_todos`라는 이름의 setter만 생성되고 `get_todos`는 만들어지지 않습니다. 이는 8장에서 익힌 프로퍼티 이름 변환 규칙(케밥 케이스는 밑줄로, `set_` 접두사)과 방향성 규칙을 그대로 따른 결과입니다.

모델을 한 번 만들어 화면에 보여 주기만 하고 이후 내용을 바꿀 계획이 없다면, 굳이 `Rc`를 손에 쥐고 있을 필요 없이 `ModelRc::new(...)`로 한 번에 넘겨도 됩니다.

```rust
ui.set_todos(ModelRc::new(VecModel::from(vec![
    TodoItem { text: "읽기 전용 항목".into(), done: false },
])));
```

`ModelRc::new`는 `Model` 트레이트를 구현하는 값을 받아 내부에서 참조 카운트로 감싸 `ModelRc`를 만들어 줍니다. 다만 이 방식은 모델을 만든 그 자리에서 소유권이 `ModelRc` 안으로 넘어가 버리므로, 이후 Rust 코드에서 항목을 추가하거나 지우려면 앞서처럼 `Rc<VecModel<T>>`를 별도의 변수로 계속 들고 있다가 `ModelRc::from`으로 변환해 전달하는 방식을 써야 합니다. 다음 절에서 다룰 "항목을 실행 중에 바꾸는" 시나리오에서는 후자가 기본형이 됩니다.

## 모델이 바뀌면 화면도 자동으로 갱신되는 원리

목록 UI에서 가장 자주 마주치는 요구사항은 "실행 중에 항목이 추가되거나 삭제되면 화면이 곧바로 그 변화를 반영해야 한다"는 것입니다. 여기서 반드시 지켜야 할 원칙이 하나 있습니다. **`VecModel`이 제공하는 메서드를 통해서 항목을 바꿔야만, 그 변경이 화면에 자동으로 반영됩니다.**

```rust
let todos: Rc<VecModel<TodoItem>> = Rc::new(VecModel::from(vec![
    TodoItem { text: "첫 번째 할 일".into(), done: false },
]));
ui.set_todos(ModelRc::from(todos.clone()));

// 이후 어디에서든 todos를 통해 항목을 추가할 수 있다
todos.push(TodoItem { text: "두 번째 할 일".into(), done: false });
```

`todos.push(...)`처럼 모델 자신의 메서드를 호출해 항목을 추가하면, `VecModel`은 내부에 가지고 있는 `ModelNotify`라는 알림 채널을 통해 "이 위치에 행이 하나 늘었다"는 사실을 통지합니다. `for` 구문으로 만들어진 반복 렌더링 로직은 이 통지를 구독하고 있다가, 알림을 받으면 늘어난 부분만 다시 계산해서 새 엘리먼트를 그려 넣습니다. 목록 전체를 처음부터 다시 그리는 것이 아니라 바뀐 부분만 갱신하기 때문에 효율적입니다.

`VecModel`은 이 밖에도 다음과 같은 메서드를 제공하며, 모두 같은 방식으로 변경 사항을 화면에 통지합니다.

- `push(value)` : 맨 뒤에 항목 추가
- `insert(index, value)` : 지정한 위치에 항목 삽입
- `remove(index)` : 지정한 위치의 항목을 제거하고 그 값을 반환
- `set_row_data(index, value)` : 지정한 위치의 항목 내용을 통째로 교체
- `clear()` : 모든 항목 제거

반대로, `VecModel`을 거치지 않고 원본 데이터를 어딘가에 따로 복사해 두었다가 그 복사본만 바꾸는 방식은 화면에 아무런 영향을 주지 않습니다. `VecModel`의 필드는 공개되어 있지 않으므로, 애초에 내부 `Vec`을 직접 꺼내 조작하는 길은 막혀 있습니다. "모델을 바꾸는 유일한 방법은 모델 자신의 메서드를 호출하는 것"이라는 규칙을 기억해 두면 충분합니다.

> 직접 커스텀 모델 타입을 만들어야 하는 고급 상황(예: 데이터베이스 조회 결과를 즉석에서 모델처럼 보여 주고 싶을 때)에는 `Model` 트레이트를 손수 구현하면서 `ModelNotify`를 직접 다루게 됩니다. 이 경우 `row_added`, `row_removed`, `row_changed` 같은 메서드를 상황에 맞게 호출해 알림을 보내야 합니다. 다만 대부분의 애플리케이션에서는 `VecModel`만으로 충분하며, `ModelNotify`를 직접 건드릴 일은 거의 없습니다.

## 실전 예제: 입력창과 버튼으로 항목 추가·삭제하기

이제 9장에서 다룬 `LineEdit`, `Button`과 이번 장의 모델을 결합해 보겠습니다. 입력창에 내용을 쓰고 버튼을 누르면 목록에 새 항목이 추가되고, 각 항목 옆의 "삭제" 버튼을 누르면 그 항목이 사라지는 예제입니다. 먼저 `.slint` 파일입니다.

```slint
import { Button, LineEdit } from "std-widgets.slint";

export struct TodoItem {
    text: string,
    done: bool,
}

export component TodoWindow inherits Window {
    width: 380px;
    height: 320px;
    title: "할 일 목록";

    in property <[TodoItem]> todos;
    in-out property <string> new-todo-text: "";
    callback add-todo-clicked();
    callback remove-todo-clicked(int);

    VerticalLayout {
        padding: 12px;
        spacing: 8px;

        HorizontalLayout {
            spacing: 8px;

            LineEdit {
                text <=> new-todo-text;
                placeholder-text: "할 일을 입력하세요";
            }

            Button {
                text: "추가";
                clicked => { add-todo-clicked(); }
            }
        }

        for todo[i] in todos : HorizontalLayout {
            spacing: 8px;

            Text {
                text: todo.text;
                vertical-alignment: center;
            }

            Button {
                text: "삭제";
                clicked => { remove-todo-clicked(i); }
            }
        }
    }
}
```

`new-todo-text`는 `in-out`으로 선언해 `LineEdit`의 `text`와 양방향 바인딩(`<=>`)으로 묶었습니다. `add-todo-clicked` 콜백은 인자가 없지만, `remove-todo-clicked`는 `int` 하나를 받도록 선언해 `for todo[i] in todos` 반복문에서 얻은 인덱스 `i`를 그대로 넘겨받을 수 있게 했습니다. 두 콜백의 실제 처리는 모두 Rust 쪽에서 담당합니다.

```rust
slint::include_modules!();

use slint::{ModelRc, VecModel};
use std::rc::Rc;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let ui = TodoWindow::new()?;

    let todos: Rc<VecModel<TodoItem>> = Rc::new(VecModel::from(Vec::<TodoItem>::new()));
    ui.set_todos(ModelRc::from(todos.clone()));

    {
        let ui_weak = ui.as_weak();
        let todos = todos.clone();
        ui.on_add_todo_clicked(move || {
            let ui = ui_weak.unwrap();
            let text = ui.get_new_todo_text();
            if !text.is_empty() {
                todos.push(TodoItem { text, done: false });
                ui.set_new_todo_text("".into());
            }
        });
    }

    {
        let todos = todos.clone();
        ui.on_remove_todo_clicked(move |index| {
            todos.remove(index as usize);
        });
    }

    ui.run()?;
    Ok(())
}
```

`ui.on_add_todo_clicked(...)`와 `ui.on_remove_todo_clicked(...)`는 `.slint`에서 선언한 콜백을 처리할 Rust 클로저를 등록합니다(콜백 등록 문법 자체는 6장과 7장에서 다룬 내용과 동일합니다). 콜백 이름의 대시(`-`)가 밑줄(`_`)로 바뀌고 앞에 `on_`이 붙는 규칙도 프로퍼티 접근자와 같은 패턴입니다.

`add-todo-clicked` 핸들러 안에서는 `ui.get_new_todo_text()`로 입력창의 내용을 읽고, 비어 있지 않다면 `todos.push(...)`로 새 항목을 모델에 추가한 뒤 `ui.set_new_todo_text("".into())`로 입력창을 비웁니다. `remove-todo-clicked` 핸들러는 `.slint`에서 넘어온 인덱스를 그대로 `todos.remove(...)`에 넘겨 해당 항목을 제거합니다. 두 경우 모두 `VecModel`의 메서드를 통해 항목을 바꾸었으므로, 화면의 목록이 곧바로 갱신됩니다.

두 클로저 모두 `todos.clone()`으로 `Rc`를 복제해 캡처하고 있다는 점을 눈여겨보세요. `Rc`를 복제하는 것은 참조 카운트만 늘리는 가벼운 연산이며, 이렇게 해야 클로저가 살아 있는 동안 같은 모델 인스턴스를 계속 공유할 수 있습니다. 반면 `ui`는 `ui.as_weak()`로 얻은 약한 참조(`Weak`)로 캡처했습니다. 클로저가 `ui`를 강하게 붙잡고 있으면 "창이 클로저를 들고 있고, 클로저가 다시 창을 들고 있는" 순환 참조가 생길 수 있는데, `as_weak()`로 얻은 핸들은 `.unwrap()`을 호출하는 시점에만 원래 창에 접근하고 참조 카운트를 늘리지 않으므로 이런 문제를 피할 수 있습니다.

## 요약

- 개수가 미리 정해지지 않았거나 실행 중에 늘고 줄어드는 목록에는 프로퍼티 대신 **모델(model)**을 사용합니다. `.slint`에서는 `property <[타입]> 이름;`처럼 타입을 대괄호로 감싸 모델 타입을 선언합니다.
- `for 항목 in 모델 : 엘리먼트 { ... }` 구문으로 모델의 각 항목마다 엘리먼트를 반복 생성합니다. `for 항목[인덱스] in 모델`처럼 쓰면 인덱스도 함께 받을 수 있습니다.
- 항목 하나가 여러 필드를 가져야 한다면 `struct`로 구조체를 정의하고 그 구조체의 모델(`[구조체이름]`)을 사용합니다. Rust 쪽에는 필드 이름이 그대로 대응되는 구조체가 생성됩니다.
- Rust에서는 `Rc::new(VecModel::from(vec![...]))`로 모델을 만들고 `ModelRc::from(rc.clone())`으로 감싸 생성된 컴포넌트의 `set_모델이름(...)`에 전달합니다. 이후 값을 바꿀 계획이 없다면 `ModelRc::new(...)`로 한 번에 넘길 수도 있습니다.
- 항목을 추가·삭제·수정할 때는 반드시 `VecModel`의 메서드(`push`, `insert`, `remove`, `set_row_data` 등)를 통해야 합니다. 이 메서드들은 내부의 `ModelNotify`를 통해 변경 사실을 알리고, Slint 런타임은 이 알림을 받아 바뀐 부분만 다시 그립니다.
- 콜백 안에서 모델을 계속 사용하려면 `Rc`를 복제해 캡처하고, 컴포넌트 핸들은 순환 참조를 피하기 위해 `as_weak()`로 얻은 약한 참조를 캡처하는 것이 일반적인 패턴입니다.

## 연습문제

1. `property <[int]> scores;` 형태의 정수 모델을 선언하고, `for` 구문과 인덱스를 함께 사용해 "1번째: 90"처럼 순번과 값을 함께 표시하는 목록을 만들어 보세요.
2. `Person` 구조체(`name: string`, `age: int`)를 정의하고, 이 구조체의 모델을 Rust에서 `VecModel`로 만들어 이름과 나이를 나열하는 목록 UI를 완성해 보세요.
3. 이번 장의 할 일 목록 예제에 9장에서 다룬 `CheckBox`를 각 항목마다 추가하고, 체크박스를 토글하면 해당 항목의 `done` 값이 바뀌도록 만들어 보세요. (힌트: `for` 반복문에서 받은 인덱스를 콜백에 함께 넘기고, Rust 쪽에서 `todos.row_data(index)`로 현재 값을 읽은 뒤 `todos.set_row_data(index, 새값)`을 호출합니다.)
4. `todos.clear()`를 호출해 목록 전체를 한 번에 비우는 "전체 삭제" 버튼을 추가해 보세요.
5. `ModelRc::new(...)`로 모델을 넘긴 경우와, `Rc<VecModel<T>>`를 별도로 보관했다가 `ModelRc::from(...)`으로 넘긴 경우의 차이를 코드로 비교해 보고, 실행 중에 항목을 추가해야 하는 상황에서는 왜 후자를 선택해야 하는지 설명해 보세요.

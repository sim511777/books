지금까지 만든 화면은 모두 사용자가 버튼을 누르거나 값을 입력하는 것 같은 "즉각적인 이벤트"에 반응해 왔습니다. 하지만 실제 애플리케이션에는 그렇지 않은 요구사항도 많습니다. 시계처럼 아무 입력 없이도 화면이 계속 갱신되어야 하는 경우, 파일을 내려받거나 대용량 데이터를 계산하는 동안 화면이 멈추지 않고 진행 상황을 보여줘야 하는 경우가 대표적입니다. 이번 장에서는 Slint 애플리케이션에서 시간의 흐름과 백그라운드 작업을 다루는 두 가지 도구, `slint::Timer`와 `slint::invoke_from_event_loop`를 배웁니다.

## 15.1 Slint의 스레드 모델: 왜 UI는 한 스레드에서만 다뤄야 하는가

본격적인 예제에 들어가기 전에 반드시 이해해야 할 제약이 하나 있습니다. `slint::include_modules!()`로 생성되는 `AppWindow` 같은 컴포넌트 구조체는 내부적으로 참조 카운팅 방식의 상태(주로 `Rc` 기반)를 들고 있어서, 여러 스레드가 동시에 안전하게 접근할 수 있도록 설계되어 있지 않습니다. 즉 이 구조체들은 `Send`도 `Sync`도 아니며, `ui.run()`을 호출한 스레드—흔히 "UI 스레드" 또는 "이벤트 루프 스레드"라고 부릅니다—안에서만 생성하고 다뤄야 합니다.

```rust
// 컴파일되지 않는 예시입니다. AppWindow는 Send가 아니므로
// 다른 스레드로 옮겨서 프로퍼티를 조작할 수 없습니다.
//
// let ui = AppWindow::new()?;
// std::thread::spawn(move || {
//     ui.set_counter(42); // 오류: `AppWindow`가 스레드 경계를 넘을 수 없습니다.
// });
```

이 제약은 불편해 보이지만 사실 대부분의 GUI 툴킷이 같은 원칙을 따릅니다. 화면을 그리는 코드와 이벤트를 처리하는 코드가 여러 스레드에서 동시에 실행되면 경쟁 상태(race condition)가 발생하기 쉽고, 디버깅도 극도로 어려워지기 때문입니다. 대신 Slint는 "시간이 지나면 UI 스레드 안에서 코드를 실행해 달라"고 예약하는 방법(`Timer`)과, "지금 다른 스레드에 있지만 이 코드만큼은 UI 스레드로 넘겨서 실행해 달라"고 요청하는 방법(`invoke_from_event_loop`)을 API로 제공합니다. 이번 장에서 다루는 내용은 결국 이 두 가지 방법을 안전하게 조합하는 법입니다.

## 15.2 `slint::Timer`와 `TimerMode`로 주기적인 작업 예약하기

`slint::Timer`는 UI 스레드의 이벤트 루프에 "일정 시간마다(또는 한 번만) 이 클로저를 실행해 달라"고 등록하는 타입입니다. 실행 방식은 `slint::TimerMode` 열거형으로 지정합니다.

- `TimerMode::Repeated`: 지정한 간격마다 반복해서 콜백을 실행합니다.
- `TimerMode::SingleShot`: 지정한 시간이 지난 뒤 딱 한 번만 콜백을 실행합니다.

`Timer`는 다음과 같은 메서드를 제공합니다.

- `Timer::default()`: 아직 아무 것도 예약되지 않은 타이머를 만듭니다.
- `timer.start(mode, interval, callback)`: 타이머를 지정한 모드와 간격으로 시작합니다.
- `timer.stop()`: 타이머를 멈춥니다.
- `timer.restart()`: 이미 설정된 모드·간격을 그대로 유지한 채 처음부터 다시 시작합니다.
- `timer.running()`: 타이머가 현재 동작 중인지 확인합니다.

간단한 스톱워치 예제로 확인해 보겠습니다. 버튼을 누르면 1초마다 경과 시간이 늘어나는 화면입니다.

```slint
// ui/stopwatch.slint
import { VerticalBox, HorizontalBox, Button } from "std-widgets.slint";

export component AppWindow inherits Window {
    in property <string> elapsed-text: "00:00";
    in property <bool> running: false;
    callback toggle-clicked();

    VerticalBox {
        padding: 24px;
        spacing: 16px;
        alignment: center;

        Text {
            text: elapsed-text;
            font-size: 40px;
            horizontal-alignment: center;
        }

        Button {
            text: running ? "정지" : "시작";
            clicked => { toggle-clicked(); }
        }
    }
}
```

```rust
// src/main.rs
use slint::{ComponentHandle, Timer, TimerMode};
use std::cell::Cell;
use std::rc::Rc;
use std::time::Duration;

slint::include_modules!();

fn format_mmss(total_seconds: i32) -> String {
    let minutes = total_seconds / 60;
    let seconds = total_seconds % 60;
    format!("{minutes:02}:{seconds:02}")
}

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    // 타이머 자체를 콜백 안에서 멈추려면, 콜백보다 먼저 타이머를 참조할 수
    // 있어야 합니다. Rc로 감싸서 클로저 안에서도 같은 타이머를 가리키게 합니다.
    let timer = Rc::new(Timer::default());
    let elapsed = Rc::new(Cell::new(0));

    let ui_weak = ui.as_weak();
    let timer_for_tick = timer.clone();
    let elapsed_for_tick = elapsed.clone();

    ui.on_toggle_clicked(move || {
        let Some(ui) = ui_weak.upgrade() else { return };

        if ui.get_running() {
            timer_for_tick.stop();
            ui.set_running(false);
            return;
        }

        ui.set_running(true);
        let ui_weak_tick = ui_weak.clone();
        let elapsed_tick = elapsed_for_tick.clone();
        timer_for_tick.start(TimerMode::Repeated, Duration::from_secs(1), move || {
            let Some(ui) = ui_weak_tick.upgrade() else { return };
            let next = elapsed_tick.get() + 1;
            elapsed_tick.set(next);
            ui.set_elapsed_text(format_mmss(next).into());
        });
    });

    ui.run()
}
```

여기서 `Rc<Timer>`로 감싼 이유를 짚어 둘 필요가 있습니다. `timer.stop()`을 호출하려면 버튼 클릭 콜백 안에서 같은 타이머 인스턴스를 다시 참조할 수 있어야 하는데, 클로저는 캡처한 값의 소유권을 가져가 버리므로 별도의 참조 카운팅 없이 "같은 타이머"를 여러 클로저에서 공유하기가 번거롭습니다. `Rc::clone`으로 참조를 복제해 두면 시작 콜백과 반복 콜백이 모두 같은 타이머를 가리키면서도 각자 독립적으로 소유권을 가질 수 있습니다. 경과 시간을 담은 `Cell<i32>`도 같은 이유로 `Rc`에 담았습니다.

## 15.3 `Timer::single_shot`으로 지연 실행하기

매번 시작·정지를 관리할 필요 없이 "일정 시간 뒤에 딱 한 번" 실행하면 되는 경우에는 정적 메서드인 `Timer::single_shot`을 쓰는 편이 훨씬 간단합니다. 예를 들어 저장 완료 메시지를 3초 뒤에 자동으로 숨기는 토스트 알림을 만들어 보겠습니다.

```slint
import { VerticalBox, Button } from "std-widgets.slint";

export component AppWindow inherits Window {
    in property <bool> message-visible: false;
    callback save-clicked();

    VerticalBox {
        padding: 24px;
        spacing: 16px;

        Button {
            text: "저장";
            clicked => { save-clicked(); }
        }

        Text {
            text: "저장되었습니다";
            color: #2e7d32;
            opacity: message-visible ? 1.0 : 0.0;
            animate opacity { duration: 200ms; }
        }
    }
}
```

```rust
use slint::{ComponentHandle, Timer};
use std::time::Duration;

slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    let ui_weak = ui.as_weak();
    ui.on_save_clicked(move || {
        let Some(ui) = ui_weak.upgrade() else { return };
        ui.set_message_visible(true);

        let ui_weak_hide = ui_weak.clone();
        Timer::single_shot(Duration::from_secs(3), move || {
            if let Some(ui) = ui_weak_hide.upgrade() {
                ui.set_message_visible(false);
            }
        });
    });

    ui.run()
}
```

`single_shot`은 타이머 핸들을 반환하지 않습니다. "한 번 실행되고 나면 알아서 사라지는" 용도로 설계되어 있어서, 시작 후에 취소할 필요가 없는 지연 작업에 적합합니다. 반대로 실행 도중에 취소하거나 반복해야 하는 작업이라면 15.2절처럼 `Timer` 인스턴스를 직접 만들어 관리해야 합니다.

## 15.4 반복 타이머로 진행률 표시줄 만들기

이번에는 `TimerMode::Repeated`를 이용해 진행률이 0에서 100까지 자동으로 채워지는 진행률 표시줄을 만들어 보겠습니다. 목표값에 도달하면 타이머 스스로 멈추도록 콜백 안에서 `timer.stop()`을 호출합니다.

```slint
import { VerticalBox, Button } from "std-widgets.slint";

export component AppWindow inherits Window {
    in property <int> progress: 0;
    callback start-clicked();

    VerticalBox {
        padding: 24px;
        spacing: 12px;

        Text {
            text: progress + "%";
            horizontal-alignment: center;
        }

        Rectangle {
            height: 18px;
            background: #3a3a3a;
            border-radius: 4px;

            Rectangle {
                x: 0;
                y: 0;
                height: parent.height;
                width: parent.width * progress / 100;
                background: #4caf50;
                border-radius: 4px;
                animate width { duration: 100ms; }
            }
        }

        Button {
            text: "시작";
            clicked => { start-clicked(); }
        }
    }
}
```

```rust
use slint::{ComponentHandle, Timer, TimerMode};
use std::rc::Rc;
use std::time::Duration;

slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    let timer = Rc::new(Timer::default());
    let ui_weak = ui.as_weak();
    let timer_outer = timer.clone();

    ui.on_start_clicked(move || {
        let Some(ui) = ui_weak.upgrade() else { return };
        ui.set_progress(0);

        let ui_weak_tick = ui_weak.clone();
        let timer_inner = timer_outer.clone();
        timer_outer.start(TimerMode::Repeated, Duration::from_millis(100), move || {
            let Some(ui) = ui_weak_tick.upgrade() else { return };
            let next = ui.get_progress() + 2;
            if next >= 100 {
                ui.set_progress(100);
                timer_inner.stop();
            } else {
                ui.set_progress(next);
            }
        });
    });

    ui.run()
}
```

`.slint` 쪽에서는 표준 위젯의 진행률 표시줄 대신 `Rectangle`을 중첩해 직접 그렸습니다. 바깥쪽 사각형은 배경 트랙 역할을, 안쪽 사각형은 `progress` 값에 비례해 너비가 늘어나는 채움 막대 역할을 합니다. `width: parent.width * progress / 100;`처럼 길이(`length`)와 정수를 곱하고 나누는 연산은 Slint 언어에서 그대로 지원되므로, 표준 위젯에 없는 모양의 진행률 표시줄도 어렵지 않게 직접 구성할 수 있습니다.

## 15.5 `slint::invoke_from_event_loop`와 `Weak`: 다른 스레드에서 UI 안전하게 건드리기

`Timer`는 어디까지나 "UI 스레드 자신이" 시간이 지난 뒤 스스로 실행하는 도구입니다. 하지만 파일 다운로드, 데이터베이스 조회, 무거운 계산처럼 시간이 오래 걸리는 작업은 UI 스레드에서 직접 실행하면 그동안 화면이 완전히 멈춰 버립니다. 이런 작업은 `std::thread::spawn`으로 별도 스레드에 맡기고, 결과가 나오면 그 결과를 UI 스레드로 안전하게 전달해야 합니다. 이때 쓰는 함수가 `slint::invoke_from_event_loop`입니다.

```rust
pub fn invoke_from_event_loop(
    func: impl FnOnce() + Send + 'static,
) -> Result<(), slint::EventLoopError>
```

이 함수는 어느 스레드에서 호출하든 상관없이, 넘겨준 클로저를 UI 이벤트 루프가 다음으로 한가해지는 시점에 UI 스레드 안에서 실행하도록 예약합니다. 즉 "지금 당장 실행"이 아니라 "UI 스레드 차례가 되면 실행"이라는 점에서 `Timer`와 비슷하지만, 실행 시점을 시간이 아니라 다른 스레드의 요청으로 트리거한다는 점이 다릅니다.

다른 스레드에서 UI 컴포넌트를 참조하려면 `AppWindow` 자체가 아니라 `slint::Weak<AppWindow>`를 사용해야 합니다. `ui.as_weak()`로 얻는 이 약한 참조는 `Send`를 구현하고 있어 스레드 경계를 넘어 이동할 수 있도록 설계되어 있습니다. 다만 `weak.upgrade()`를 호출해 실제 `AppWindow`로 되돌리는 작업은 반드시 UI 스레드 안에서, 즉 `invoke_from_event_loop`에 넘긴 클로저 내부에서 수행해야 합니다. 창이 이미 닫혀 있으면 `upgrade()`는 `None`을 반환하므로, 다음과 같이 `if let Some(ui) = weak.upgrade() { ... }` 패턴으로 항상 방어적으로 처리합니다.

```rust
use slint::ComponentHandle;

fn notify_ui_from_worker_thread(ui_weak: slint::Weak<AppWindow>, message: String) {
    // 이 함수는 워커 스레드에서 호출된다고 가정합니다.
    let result = slint::invoke_from_event_loop(move || {
        if let Some(ui) = ui_weak.upgrade() {
            ui.set_status_text(message.into());
        }
    });

    if let Err(err) = result {
        eprintln!("UI 스레드에 작업을 예약하지 못했습니다: {err}");
    }
}
```

정리하면 스레드 간 통신의 기본 패턴은 항상 다음과 같은 순서를 따릅니다.

1. UI 스레드에서 `let ui_weak = ui.as_weak();`로 약한 참조를 얻는다.
2. `ui_weak`를 `std::thread::spawn`의 클로저로 옮긴다(`move`).
3. 워커 스레드는 시간이 걸리는 작업을 수행하되, UI를 직접 건드리지 않는다.
4. UI에 반영할 시점마다 `slint::invoke_from_event_loop`를 호출하고, 그 안에서만 `ui_weak.upgrade()`로 실제 컴포넌트를 얻어 프로퍼티를 설정한다.

## 15.6 종합 예제: 백그라운드 계산과 진행 상황을 UI에 반영하기

지금까지 배운 내용을 하나로 모아, 버튼을 누르면 별도 스레드에서 소수(prime number) 개수를 세고, 진행률과 최종 결과를 UI에 반영하는 예제를 만들어 보겠습니다. 계산이 진행되는 동안에는 버튼을 비활성화해 중복 실행을 막습니다.

```slint
// ui/prime_counter.slint
import { VerticalBox, Button } from "std-widgets.slint";

export component AppWindow inherits Window {
    in property <int> progress: 0;
    in property <bool> busy: false;
    in property <string> result-text: "";
    callback compute-clicked();

    VerticalBox {
        padding: 24px;
        spacing: 12px;

        Text {
            text: "1부터 2,000,000 사이의 소수 개수 세기";
            font-size: 16px;
        }

        Rectangle {
            height: 18px;
            background: #3a3a3a;
            border-radius: 4px;

            Rectangle {
                x: 0;
                y: 0;
                height: parent.height;
                width: parent.width * progress / 100;
                background: #2196f3;
                border-radius: 4px;
            }
        }

        Text {
            text: result-text;
        }

        Button {
            text: busy ? "계산 중..." : "계산 시작";
            enabled: !busy;
            clicked => { compute-clicked(); }
        }
    }
}
```

```rust
// src/main.rs
use slint::ComponentHandle;
use std::thread;

slint::include_modules!();

fn is_prime(n: u64) -> bool {
    if n < 2 {
        return false;
    }
    let mut divisor = 2u64;
    while divisor * divisor <= n {
        if n % divisor == 0 {
            return false;
        }
        divisor += 1;
    }
    true
}

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    let ui_weak = ui.as_weak();
    ui.on_compute_clicked(move || {
        let Some(ui) = ui_weak.upgrade() else { return };
        if ui.get_busy() {
            // 이미 계산 중이면 새로 시작하지 않습니다.
            return;
        }

        ui.set_busy(true);
        ui.set_progress(0);
        ui.set_result_text("".into());

        let ui_weak_worker = ui_weak.clone();
        thread::spawn(move || {
            const LIMIT: u64 = 2_000_000;
            let mut count: u64 = 0;
            let mut last_reported_percent = -1i32;

            for n in 2..LIMIT {
                if is_prime(n) {
                    count += 1;
                }

                let percent = ((n * 100) / LIMIT) as i32;
                if percent != last_reported_percent {
                    last_reported_percent = percent;
                    let ui_weak_progress = ui_weak_worker.clone();
                    let _ = slint::invoke_from_event_loop(move || {
                        if let Some(ui) = ui_weak_progress.upgrade() {
                            ui.set_progress(percent);
                        }
                    });
                }
            }

            let ui_weak_done = ui_weak_worker.clone();
            let _ = slint::invoke_from_event_loop(move || {
                if let Some(ui) = ui_weak_done.upgrade() {
                    ui.set_progress(100);
                    ui.set_result_text(format!("소수 개수: {count}개").into());
                    ui.set_busy(false);
                }
            });
        });
    });

    ui.run()
}
```

이 예제에서 눈여겨볼 부분은 워커 스레드가 `ui`나 `AppWindow`를 단 한 번도 직접 들고 있지 않다는 점입니다. 워커 스레드가 가진 것은 오직 `slint::Weak<AppWindow>`의 복제본뿐이며, 실제 프로퍼티 접근은 전부 `invoke_from_event_loop`에 넘긴 클로저 안, 즉 UI 스레드 안에서만 일어납니다. 진행률을 매 반복마다 보고하지 않고 퍼센트 값이 실제로 바뀔 때만 `invoke_from_event_loop`를 호출하도록 한 것도 중요한 실무 팁입니다. 200만 번 반복할 때마다 이벤트 루프에 클로저를 예약하면 UI 스레드가 오히려 그 처리에 치여 버벅거릴 수 있으므로, 화면에 실제로 보여줄 변화가 있을 때만 통신 비용을 지불하는 편이 훨씬 효율적입니다.

## 15.7 async 런타임과의 연동에 대하여

`tokio`나 `async-std` 같은 비동기 런타임을 이미 사용하고 있는 프로젝트라면, `std::thread::spawn` 대신 그 런타임의 태스크로 작업을 실행하고 싶을 수 있습니다. Slint는 이런 시나리오를 위해 `slint::spawn_local` 같은 API로 Rust의 퓨처(future)를 이벤트 루프와 연동하는 기능도 제공합니다. 다만 이 연동 방식은 사용하는 비동기 런타임과 Slint 버전, 활성화한 카고 기능(feature)에 따라 세부 사항이 달라지고, 이 책이 목표로 하는 "Rust API로 Slint를 다루는 기초"의 범위를 넘어서므로 자세한 구현은 다루지 않습니다. 지금 단계에서 기억해 둘 점은 두 가지입니다.

- 굳이 별도의 비동기 런타임 없이도, 이번 장에서 배운 `std::thread::spawn` + `invoke_from_event_loop` 조합만으로 "무거운 작업을 백그라운드에서 돌리고 결과를 UI에 반영하는" 대부분의 요구는 충분히 해결할 수 있습니다.
- 이미 `tokio` 기반으로 작성된 네트워크·파일 I/O 코드를 Slint UI와 통합해야 하는 상황이라면, 공식 문서에서 해당 버전의 비동기 연동 API를 확인하는 것이 가장 정확합니다. API 이름과 세부 동작이 버전마다 조정되어 온 영역이기 때문입니다.

## 요약

- Slint가 생성하는 UI 컴포넌트는 `Send`/`Sync`가 아니므로, `ui.run()`을 호출한 UI 스레드 안에서만 프로퍼티를 읽고 써야 합니다.
- `slint::Timer`는 `TimerMode::Repeated`(반복)와 `TimerMode::SingleShot`(단발성) 두 모드로 UI 스레드 위에서 예약 실행을 수행합니다. `start`/`stop`/`restart`/`running`으로 상태를 제어합니다.
- `Timer::single_shot(duration, callback)`은 핸들 관리 없이 "한 번만, 지연 실행"하면 되는 경우에 적합한 정적 메서드입니다.
- `ui.as_weak()`로 얻는 `slint::Weak<T>`는 `Send`를 구현하고 있어 다른 스레드로 옮길 수 있으며, 실제 컴포넌트로 되돌리는 `upgrade()`는 반드시 UI 스레드 안에서 호출해야 합니다.
- `slint::invoke_from_event_loop(closure)`는 어느 스레드에서 호출하든 그 클로저를 UI 스레드에서 실행하도록 예약합니다. `std::thread::spawn`으로 백그라운드 작업을 수행하고, 진행 상황이나 결과가 바뀔 때만 이 함수로 UI에 반영하는 것이 표준적인 패턴입니다.
- `tokio` 등 비동기 런타임과의 정밀한 연동(`slint::spawn_local` 등)은 버전에 따라 세부가 달라지므로 이 책의 범위 밖으로 두고, 필요할 때 공식 문서를 참고하도록 안내합니다.

## 연습문제

1. 15.2절의 스톱워치 예제에 "초기화" 버튼을 추가해, 타이머가 정지된 상태에서만 경과 시간을 0으로 되돌리도록 만들어 보세요.
2. 15.3절의 토스트 알림 예제에서, 사용자가 메시지가 사라지기 전에 저장 버튼을 다시 누르면 이전 타이머가 UI를 잘못된 시점에 숨기지 않도록 동작을 개선해 보세요. (힌트: 매번 새로운 `single_shot`을 거는 대신, 몇 번째 요청인지 구분할 방법이 필요합니다.)
3. 15.4절의 진행률 표시줄 예제에서 `TimerMode::Repeated` 대신 `TimerMode::SingleShot`을 재귀적으로 거는 방식으로 바꿔서 동일한 동작을 구현해 보고, 두 방식의 장단점을 비교해 보세요.
4. 15.6절의 소수 세기 예제를 응용해, 계산 도중 "취소" 버튼을 눌러 워커 스레드에 중단 신호를 보내는 기능을 추가해 보세요. (힌트: `std::sync::atomic::AtomicBool`을 `Arc`로 감싸 워커 스레드와 공유하면, UI 스레드는 그 값을 `true`로 바꾸기만 하면 됩니다.)
5. `invoke_from_event_loop`를 UI 스레드가 아닌 스레드에서 남용해 아주 짧은 간격으로 수백 번 호출하면 어떤 문제가 생길 수 있을지 설명하고, 15.6절 예제가 이 문제를 어떻게 피하고 있는지 코드에서 근거를 찾아보세요.

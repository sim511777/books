# 5장. 프로퍼티와 바인딩

`.slint` 파일 안에서 프로퍼티가 어떻게 동작하는지는 이미 어느 정도 감을 잡았을 것입니다. 이번 장에서는 그 프로퍼티가 **Rust 코드와 어떻게 연결되는지**에 집중합니다. Slint 컴파일러는 `.slint` 파일을 빌드할 때 각 프로퍼티에 대응하는 Rust 메서드를 자동으로 만들어 주는데, 이 메서드들의 규칙을 정확히 알아야 UI와 Rust 로직을 자연스럽게 오갈 수 있습니다.

## 5.0 이 장에서 사용할 프로젝트 구조

이번 장의 예제는 아래와 같은 구조를 가진 Cargo 프로젝트를 전제로 합니다.

```
bmi-app/
├── Cargo.toml
├── build.rs
├── ui/
│   └── app-window.slint
└── src/
    └── main.rs
```

`Cargo.toml`에는 런타임 크레이트 `slint`와, 빌드 스크립트에서 `.slint` 파일을 컴파일하는 데 쓰는 `slint-build`를 각각 등록합니다.

```toml
[package]
name = "bmi-app"
version = "0.1.0"
edition = "2021"

[dependencies]
slint = "1.8"

[build-dependencies]
slint-build = "1.8"
```

`build.rs`는 `.slint` 파일을 찾아 Rust 코드로 변환하도록 지시하는 역할만 합니다.

```rust
fn main() {
    slint_build::compile("ui/app-window.slint").unwrap();
}
```

`cargo build`를 실행하면 `slint-build`가 `ui/app-window.slint`를 읽어서, 그 안에 선언된 컴포넌트에 대응하는 Rust 구조체와 메서드들을 생성합니다. 이 장의 핵심은 바로 이 "자동 생성되는 메서드"가 프로퍼티의 방향 키워드(`in`, `out`, `in-out`)에 따라 어떻게 달라지는지를 이해하는 것입니다.

## 5.1 프로퍼티 접근 제한자: in, out, in-out

Slint 프로퍼티는 기본적으로 **private**입니다. 즉 방향 키워드 없이 `property <type> name: value;`라고만 선언하면, 그 프로퍼티는 선언된 컴포넌트 내부의 바인딩 식에서만 참조할 수 있습니다. 이 컴포넌트를 사용하는 부모 `.slint` 코드도, Rust 코드도 이 값을 직접 읽거나 쓸 수 없습니다.

이 기본 동작을 바꾸는 것이 `in`, `out`, `in-out` 키워드입니다.

```slint
export component AppWindow inherits Window {
    // 바깥에서 값을 넣어주는 입력 프로퍼티
    in property <string> title: "체질량지수 계산기";

    // 바깥에서 읽고 쓸 수 있는 양방향 프로퍼티
    in-out property <float> height-cm: 170.0;
    in-out property <float> weight-kg: 65.0;

    // 컴포넌트 내부에서 계산해서 바깥으로 결과만 알려주는 출력 프로퍼티
    out property <bool> is-underweight: weight-kg / ((height-cm / 100) * (height-cm / 100)) < 18.5;

    // 방향 키워드가 없는 프로퍼티: 이 컴포넌트 내부에서만 사용
    property <color> accent-color: #2b6cb0;

    Text {
        text: title;
        color: accent-color;
    }
}
```

세 키워드의 의미는 다음과 같이 정리할 수 있습니다.

- `in property`: 이 컴포넌트를 사용하는 쪽(부모 `.slint` 코드, 또는 이 컴포넌트가 최상위 컴포넌트라면 Rust 코드)에서 값을 채워주는 프로퍼티입니다. 컴포넌트 내부에서도 다른 바인딩 식에서 읽을 수 있지만, "누가 값을 정하는가"의 책임은 바깥쪽에 있습니다.
- `out property`: 컴포넌트 내부의 바인딩 식으로 계산되어 바깥으로 결과를 알려주는 프로퍼티입니다. 바깥에서는 값을 읽을 수만 있고, 대입할 수는 없습니다.
- `in-out property`: 양쪽 모두에서 읽고 쓸 수 있는 프로퍼티입니다. 위 예제의 `height-cm`, `weight-kg`처럼 바깥에서 초기값을 설정하고, 이후에도 계속 값을 바꿀 필요가 있는 경우에 씁니다.

이 방향 키워드는 단순한 문서화 장치가 아닙니다. 잠시 후 5.3절에서 보겠지만, Rust 쪽에서 어떤 메서드가 만들어지는지가 바로 이 키워드에 의해 결정됩니다.

## 5.2 바인딩은 표현식이며, 값이 바뀌면 자동으로 재계산된다

위 예제의 `is-underweight`처럼, 바인딩 자리에는 다른 프로퍼티를 참조하는 임의의 산술식·비교식을 쓸 수 있습니다. 이 값은 "그 순간 한 번 계산해서 저장"되는 것이 아니라 "항상 이 식과 같아야 한다"는 선언입니다. `height-cm`이나 `weight-kg`가 바뀌면, Slint 런타임은 `is-underweight`가 이 두 프로퍼티에 의존한다는 것을 이미 컴파일 시점에 파악해 두었으므로, 별도의 코드 없이 자동으로 `is-underweight`를 다시 계산합니다.

이 특징이 왜 중요한지는 Rust와 나란히 놓고 보면 분명해집니다.

```rust
// 만약 Slint가 이런 식으로 동작했다면 (실제로는 이렇게 동작하지 않습니다)
let mut height_cm = 170.0_f32;
let mut weight_kg = 65.0_f32;
let mut is_underweight = weight_kg / (height_cm / 100.0).powi(2) < 18.5;

height_cm = 180.0;
// is_underweight는 여전히 이전 값이다.
// 최신 상태를 반영하려면 아래 줄을 잊지 않고 다시 실행해야 한다.
is_underweight = weight_kg / (height_cm / 100.0).powi(2) < 18.5;
```

Rust의 지역 변수는 대입한 순간의 값을 그대로 들고 있을 뿐, 다른 변수가 바뀌었다고 저절로 갱신되지 않습니다. 반면 `.slint` 쪽의 `is-underweight`는 `height-cm`이나 `weight-kg` 중 무엇이 바뀌든 상관없이 항상 최신 결과를 유지합니다. Rust 코드에서 `set_height_cm()`을 호출해 값을 바꾸기만 하면, `is-underweight`를 다시 계산하라고 명령할 필요 없이 다음번 `get_is_underweight()` 호출에서 곧바로 갱신된 값을 받게 됩니다.

## 5.3 컴파일 시 생성되는 접근자: get_x / set_x

`slint-build`는 최상위(export된) 컴포넌트의 `in`, `out`, `in-out` 프로퍼티마다 Rust 메서드를 생성합니다. 이때 프로퍼티 이름의 하이픈(`-`)은 Rust 관례에 맞춰 밑줄(`_`)로 바뀝니다. 예를 들어 `height-cm`은 Rust 쪽에서 `height_cm`이 됩니다.

생성되는 메서드는 프로퍼티의 방향에 따라 다릅니다.

| `.slint` 선언 | 생성되는 Rust 메서드 |
|---|---|
| `in property <T> x` | `get_x(&self) -> T`, `set_x(&self, value: T)` |
| `out property <T> x` | `get_x(&self) -> T` (setter 없음) |
| `in-out property <T> x` | `get_x(&self) -> T`, `set_x(&self, value: T)` |
| 방향 키워드 없음 | Rust 쪽에 아무 메서드도 생성되지 않음 |

`out property`에는 setter가 만들어지지 않습니다. 이 값은 오직 `.slint` 안의 바인딩 식으로만 결정되어야 하므로, Rust 코드가 실수로 값을 덮어써서 바인딩과 어긋나는 상태를 만들 수 없도록 컴파일러가 원천적으로 막아 놓은 것입니다.

이제 앞서 만든 `AppWindow`를 Rust에서 실제로 조작해 보겠습니다. `slint::include_modules!()` 매크로는 `build.rs`가 생성해 둔 Rust 코드를 현재 파일에 그대로 포함시켜, `.slint`에서 `export`한 컴포넌트를 동일한 이름의 Rust 구조체로 사용할 수 있게 해줍니다.

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    // in-out 프로퍼티는 읽고 쓰기가 모두 가능하다.
    println!("초기 키: {}", ui.get_height_cm());
    ui.set_height_cm(180.0);
    ui.set_weight_kg(70.0);

    // out 프로퍼티는 읽기만 가능하다. set_is_underweight() 같은 메서드는 존재하지 않는다.
    println!("저체중 여부: {}", ui.get_is_underweight());

    ui.run()
}
```

`ui.set_height_cm(180.0)`을 호출하는 순간, `.slint` 쪽의 `height-cm` 프로퍼티 값이 바뀌고, 이를 참조하던 `is-underweight`도 즉시 재계산됩니다. 그 직후에 호출한 `ui.get_is_underweight()`는 이미 갱신된 최신 값을 돌려줍니다. Rust 코드는 "언제 무엇을 다시 계산할지"를 전혀 신경 쓰지 않아도 되고, 화면에 표시되는 값과 `get_x()`로 읽는 값은 항상 일치합니다.

## 5.4 문자열 프로퍼티와 SharedString

`.slint`의 `string` 타입은 Rust의 `std::string::String`이 아니라 `slint::SharedString`에 대응합니다. `SharedString`은 내부적으로 참조 카운트를 사용해 값을 공유하는 문자열 타입으로, Slint 런타임이 화면을 다시 그릴 때마다 문자열을 값 그대로 복사하지 않고 저렴하게 공유할 수 있도록 설계되어 있습니다. `String`과는 다른 타입이므로, Rust의 `String`을 `.slint` 프로퍼티에 넣거나 반대로 꺼내려면 명시적인 변환이 필요합니다.

```slint
export component AppWindow inherits Window {
    in-out property <string> user-name: "";
    out property <string> greeting: "안녕하세요, " + user-name + "님!";
}
```

```rust
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    // Rust String -> SharedString
    let input: String = "슈아".to_string();
    ui.set_user_name(input.into());
    // 또는 명시적으로: ui.set_user_name(slint::SharedString::from(input.as_str()));

    // SharedString -> Rust String
    let greeting: slint::SharedString = ui.get_greeting();
    let greeting_owned: String = greeting.to_string();
    println!("{greeting_owned}");

    ui.run()
}
```

`String`에서 `SharedString`으로는 `.into()`(내부적으로 `From<String>` 구현을 사용) 또는 `SharedString::from(&str)`로 변환합니다. 반대로 `SharedString`에서 `String`을 얻으려면 `.to_string()`을 호출하거나, 소유권 이동 없이 잠깐 문자열 슬라이스만 필요하다면 `.as_str()`을 사용합니다. `SharedString`은 `Deref<Target = str>`을 구현하고 있어서, `println!("{shared}")`처럼 `&str`을 기대하는 대부분의 자리에 그대로 넘길 수 있습니다.

## 5.5 종합 예제: 여러 프로퍼티가 서로 의존하는 BMI 계산기

지금까지 다룬 내용을 하나로 묶어, 키와 몸무게를 입력받아 체질량지수(BMI)와 그 판정 결과를 함께 보여주는 예제를 완성해 보겠습니다.

```slint
// ui/app-window.slint
export component AppWindow inherits Window {
    width: 280px;
    height: 160px;

    in-out property <float> height-cm: 170.0;
    in-out property <float> weight-kg: 65.0;

    out property <float> bmi: weight-kg / ((height-cm / 100) * (height-cm / 100));
    out property <string> category: bmi < 18.5
        ? "저체중"
        : bmi < 25.0
            ? "정상"
            : "과체중";
    out property <string> summary: "BMI " + round(bmi * 10) / 10 + " (" + category + ")";

    VerticalLayout {
        padding: 16px;
        spacing: 8px;
        Text { text: "키: " + height-cm + "cm, 몸무게: " + weight-kg + "kg"; }
        Text { text: summary; font-weight: 700; }
    }
}
```

`bmi`는 `height-cm`과 `weight-kg` 두 프로퍼티에 의존하고, `category`는 다시 `bmi`에 의존하며, `summary`는 `bmi`와 `category` 모두에 의존합니다. 이런 사슬 구조는 3단계까지 이어지지만, 어디에도 "무엇을 먼저 계산하라"는 순서는 적혀 있지 않습니다.

```rust
// src/main.rs
slint::include_modules!();

fn main() -> Result<(), slint::PlatformError> {
    let ui = AppWindow::new()?;

    println!("--- 초기 상태 ---");
    println!("{}", ui.get_summary());

    // height-cm 하나만 바꿔도 bmi, category, summary가 연쇄적으로 재계산된다.
    ui.set_height_cm(158.0);
    println!("--- 키를 158cm로 변경 ---");
    println!("{}", ui.get_summary());

    ui.set_weight_kg(48.0);
    println!("--- 몸무게를 48kg으로 변경 ---");
    println!("{}", ui.get_summary());

    ui.run()
}
```

`set_height_cm`, `set_weight_kg`는 `in-out`으로 선언했기 때문에 존재하지만, `bmi`, `category`, `summary`는 `out`으로 선언했으므로 `get_x()`만 존재하고 `set_x()`는 아예 생성되지 않습니다. Rust 코드가 실수로 `ui.set_bmi(999.0)` 같은 코드를 작성하면, 그런 메서드 자체가 없으므로 컴파일 단계에서 바로 에러가 납니다. 방향 키워드가 "계산된 값과 입력값을 헷갈리지 않도록" Rust 코드 수준에서도 지켜주는 셈입니다.

## 요약

- Slint 프로퍼티의 기본 가시성은 private입니다. `in`, `out`, `in-out` 키워드로 컴포넌트 바깥(부모 `.slint` 코드나 Rust 코드)과 값을 주고받을 방향을 명시적으로 정합니다.
- 바인딩은 "이 값은 항상 이 식과 같다"는 선언이며, 참조하는 프로퍼티가 바뀌면 의존하는 프로퍼티들이 자동으로, 올바른 순서로 재계산됩니다.
- `slint-build`는 최상위 컴포넌트의 `in`/`out`/`in-out` 프로퍼티마다 Rust 접근자 메서드를 생성합니다. `in`과 `in-out`은 `get_x`/`set_x`를 모두 생성하고, `out`은 `get_x`만 생성합니다. 프로퍼티 이름의 하이픈은 밑줄로 바뀝니다.
- `.slint`의 `string` 타입은 Rust의 `slint::SharedString`에 대응합니다. `String`에서는 `.into()`나 `SharedString::from()`으로, `SharedString`에서는 `.to_string()`이나 `.as_str()`로 서로 변환합니다.
- 여러 프로퍼티가 사슬처럼 서로를 참조하더라도, Rust 코드는 맨 앞의 입력 프로퍼티만 `set_x()`로 바꿔주면 되고 나머지 갱신은 Slint 런타임이 책임집니다.

## 연습문제

1. `in property`로 선언된 프로퍼티와 `out property`로 선언된 프로퍼티에 대해 `slint-build`가 각각 어떤 Rust 메서드를 생성하는지, 그리고 왜 그렇게 설계되었는지 설명해보세요.
2. 이번 장의 `AppWindow`에 `in-out property <string> unit: "cm";`을 추가해서, `unit` 값이 `"cm"`이 아니라 `"in"`(인치)일 때는 `height-cm`을 인치로 환산해 보여주는 `out property <string> height-display`를 작성해보세요. 이 프로퍼티는 몇 개의 프로퍼티에 의존하나요?
3. Rust의 `String`과 Slint의 `SharedString`이 서로 다른 타입인 이유를 설명하고, 한 문자열 값을 Rust와 `.slint` 양쪽에서 계속 주고받아야 하는 상황에서 어떤 점을 주의해야 하는지 서술해보세요.
4. 방향 키워드 없이 선언한 프로퍼티(private)를 Rust 코드에서 `ui.get_x()`로 읽으려고 하면 어떤 일이 벌어지는지 예상해보고, 실제로 그런 코드를 작성해서 확인해보세요.
5. 이번 장의 BMI 계산기 예제에서, `weight-kg`를 계속 100kg씩 늘려가며 `ui.get_category()`가 어떤 시점에 `"과체중"`으로 바뀌는지 Rust 쪽 반복문으로 확인하는 프로그램을 작성해보세요.

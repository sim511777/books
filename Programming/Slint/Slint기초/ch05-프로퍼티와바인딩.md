# 5장. 프로퍼티와 바인딩

[◀ 이전: 4장. 레이아웃 시스템](ch04-레이아웃시스템.md) | [📖 목차](00-목차.md) | [다음: 6장. 콜백과 이벤트 처리 ▶](ch06-콜백과이벤트처리.md)


3장에서는 `property <type> name: value;` 문법으로 컴포넌트에 값을 담는 방법을 살펴봤습니다. 그때는 프로퍼티를 "변수 비슷한 것" 정도로 소개하고 넘어갔지만, 사실 프로퍼티는 Slint 언어 전체를 관통하는 핵심 개념입니다. 이번 장에서는 프로퍼티가 왜 변수와 다른지, 그리고 그 차이가 왜 GUI 프로그래밍을 훨씬 편하게 만들어주는지 제대로 짚어보겠습니다.

## 5.1 값을 대입하는 것과 관계를 선언하는 것

먼저 익숙한 C++ 코드를 하나 떠올려 봅시다.

```cpp
int count = 0;
std::string label = "카운트: " + std::to_string(count);

count = 5;
// label은 여전히 "카운트: 0" 이다.
// label을 갱신하려면 다시 대입해야 한다.
label = "카운트: " + std::to_string(count);
```

C++의 `=`는 "그 순간의 값을 계산해서 한 번 저장하라"는 명령입니다. `count`가 바뀌어도 `label`은 저절로 따라오지 않습니다. 개발자가 직접 "이 값이 바뀌었으니 저 값도 다시 계산해야 한다"는 것을 기억하고, 갱신 코드를 어딘가에 심어둬야 합니다. 화면에 표시되는 값이 열 개, 백 개로 늘어나면 이 "누가 무엇에 의존하는가"를 사람이 손으로 추적하는 일 자체가 버그의 온상이 됩니다.

Slint의 프로퍼티는 다릅니다. 같은 상황을 Slint로 적어보겠습니다.

```slint
export component Counter {
    property <int> count: 0;
    property <string> label: "카운트: " + count;

    Text {
        text: label;
    }
}
```

`label`에 적은 `"카운트: " + count`는 "지금 이 값으로 계산해서 저장하라"는 명령이 아니라 **"label은 항상 이 식의 결과와 같아야 한다"는 선언**입니다. 이것을 **바인딩(binding)**이라고 부릅니다. `count`가 0에서 5로 바뀌는 순간, Slint 런타임은 `label`이 `count`를 참조하고 있다는 것을 알고 있으므로 `label`을 자동으로 다시 계산합니다. 화면의 `Text`는 그 갱신된 `label`을 그대로 보여줍니다. 개발자가 "label도 갱신해줘"라고 따로 말할 필요가 없습니다.

이것이 Slint를 **선언적(declarative)** 언어라고 부르는 이유입니다. 우리는 절차(어떤 순서로 무엇을 갱신할지)를 적는 게 아니라, 프로퍼티 사이의 **관계**를 적습니다. 그 관계를 실제로 유지하는 일은 런타임이 맡습니다.

## 5.2 바인딩은 식(expression)이다

바인딩 자리에는 리터럴 값뿐 아니라 임의의 식을 쓸 수 있습니다. 다른 프로퍼티를 참조하거나, 연산자를 조합하거나, 조건식(삼항 연산자)을 넣는 것도 모두 가능합니다.

```slint
export component PriceTag {
    property <int> quantity: 1;
    property <float> unit-price: 1200;

    property <float> subtotal: quantity * unit-price;
    property <bool> is-bulk: quantity >= 10;
    property <float> discount-rate: is-bulk ? 0.1 : 0.0;
    property <float> total: subtotal * (1 - discount-rate);

    Text {
        text: "합계: " + total;
    }
}
```

여기서 `quantity`를 바꾸면 `subtotal`, `is-bulk`, `discount-rate`, `total`이 순서대로 다시 계산되어 결국 화면의 `Text`까지 갱신됩니다. 이 프로퍼티들은 서로 사슬처럼 얽혀 있는데, 우리는 그 어디에서도 "누가 먼저 계산되어야 한다"는 순서를 명시하지 않았습니다.

## 5.3 계산 순서는 누가 책임지는가

명령형 코드였다면 `quantity`가 바뀔 때 `subtotal` → `is-bulk` → `discount-rate` → `total` 순서로 재계산 함수를 호출하는 코드를 직접 짜야 했을 것입니다. 만약 새로운 프로퍼티를 하나 추가하면서 이 순서를 하나라도 놓치면, 화면에는 이전 값이 남아있는 미묘한 버그가 생깁니다.

Slint는 컴파일 시점에 각 프로퍼티의 바인딩 식을 분석해서 "이 프로퍼티는 저 프로퍼티에 의존한다"는 **의존성 그래프**를 스스로 구성합니다. 어떤 프로퍼티의 값이 바뀌면, 그 프로퍼티에 의존하는 프로퍼티들만 정확한 순서로 다시 계산됩니다. 심지어 아무도 화면에서 참조하지 않는 프로퍼티라면 굳이 재계산조차 하지 않습니다(필요할 때 계산하는 지연 평가). 개발자는 그래프를 관리할 필요 없이 "이 값은 이런 식으로 정의된다"는 사실만 기록하면 됩니다.

이 특징은 4장에서 다룬 레이아웃 시스템과도 맞닿아 있습니다. `width`나 `height` 같은 레이아웃 관련 프로퍼티 역시 내부적으로는 다른 프로퍼티(부모의 크기, 자식들의 최소/선호 크기 등)에 의존하는 바인딩으로 표현되며, 창 크기가 바뀔 때마다 이 관계식들이 자동으로 다시 풀립니다.

## 5.4 컴포넌트 안의 프로퍼티, 컴포넌트 밖에서 오는 프로퍼티

지금까지 본 예제의 프로퍼티는 전부 컴포넌트 내부에서 정의하고, 내부에서만 값을 계산했습니다. 하지만 실전에서는 "이 값은 이 컴포넌트를 사용하는 쪽(부모 컴포넌트나 C++ 코드)에서 정해줘야 한다"는 프로퍼티가 반드시 생깁니다. 예를 들어 재사용 가능한 카드 컴포넌트를 만든다면, 카드에 표시할 제목은 카드를 사용하는 쪽에서 지정하는 것이 자연스럽습니다.

Slint는 프로퍼티 앞에 방향을 나타내는 키워드를 붙여서 이런 "누가 값을 채워주는가"를 명시적으로 구분합니다.

```slint
export component Card {
    in property <string> title;
    in property <string> description;
    out property <bool> is-empty: title == "" && description == "";

    Rectangle {
        background: #f5f5f5;
        border-radius: 8px;

        VerticalLayout {
            padding: 12px;
            Text { text: title; font-weight: 700; }
            Text { text: description; }
        }
    }
}
```

- `in property`: 컴포넌트 바깥(사용하는 쪽)에서 값을 넣어주는 **입력 프로퍼티**입니다. 컴포넌트 내부에서는 이 값을 읽어서 쓸 수는 있지만, 바깥에서 넣어준 값이 우선이라고 생각하면 됩니다.
- `out property`: 컴포넌트 내부에서 계산해서 바깥으로 **결과를 알려주는** 프로퍼티입니다. `Card`를 사용하는 부모 컴포넌트나 C++ 코드는 `is-empty` 값을 읽을 수 있지만 직접 대입할 수는 없습니다.
- `in-out property`: 양쪽 모두에서 읽고 쓸 수 있는, 말 그대로 양방향 프로퍼티입니다. 3장과 지금까지의 예제에서 아무 키워드 없이 쓴 `property <int> count: 0;`처럼 방향을 지정하지 않은 프로퍼티는 기본적으로 `in-out`으로 취급되어, 컴포넌트 내부는 물론 바깥에서도 자유롭게 값을 읽고 쓸 수 있습니다.

정리하면, 방향 키워드는 "이 프로퍼티의 값이 어느 쪽 책임인가"를 코드 자체에 문서화하는 역할을 합니다. 재사용을 염두에 두지 않은 실험용 컴포넌트라면 방향 키워드 없이 편하게 써도 되지만, 다른 컴포넌트나 C++ 코드와 데이터를 주고받아야 하는 프로퍼티라면 `in`, `out`, `in-out`을 명시해서 의도를 분명히 하는 것이 좋은 습관입니다. C++ 코드에서 이 프로퍼티들을 실제로 읽고 쓰는 방법은 8장 "C++에서 프로퍼티 제어하기"에서 자세히 다룹니다.

## 5.5 정리해보는 예제: 온도 변환기

지금까지 배운 내용을 하나의 예제로 묶어보겠습니다.

```slint
export component TemperatureConverter {
    in-out property <float> celsius: 0;
    out property <float> fahrenheit: celsius * 9 / 5 + 32;
    out property <string> summary: "섭씨 " + celsius + "도는 화씨 " + fahrenheit + "도입니다.";

    VerticalLayout {
        spacing: 8px;
        Text { text: summary; }
    }
}
```

`celsius`는 바깥에서도 바꿀 수 있는 `in-out` 프로퍼티이고, `fahrenheit`와 `summary`는 `celsius`로부터 계산되는 `out` 프로퍼티입니다. `celsius`가 바뀌면 `fahrenheit`가 재계산되고, `fahrenheit`가 바뀌면 그것을 참조하는 `summary`까지 연쇄적으로 재계산됩니다. 우리는 그 순서를 어디에도 적지 않았지만, 화면은 언제나 최신 상태를 보여줍니다.

## 요약

- Slint의 프로퍼티 바인딩은 "그 순간의 값을 저장"하는 명령형 대입이 아니라, "이 값은 항상 이 식과 같다"는 선언입니다.
- 바인딩 식에는 다른 프로퍼티를 참조하는 임의의 표현식(산술 연산, 비교, 삼항 연산자 등)을 쓸 수 있습니다.
- 참조된 프로퍼티가 바뀌면 그 값을 참조하는 프로퍼티들이 자동으로, 올바른 순서로 다시 계산됩니다. 개발자가 의존성 그래프나 갱신 순서를 직접 관리할 필요가 없습니다.
- `in property`는 바깥에서 값을 채워주는 입력 프로퍼티, `out property`는 내부에서 계산해 바깥에 알려주는 출력 프로퍼티, `in-out property`는 양방향 프로퍼티입니다. 방향 키워드 없이 선언한 프로퍼티는 기본적으로 `in-out`으로 동작합니다.
- 컴포넌트가 재사용될수록, 그리고 C++ 코드와 값을 주고받을수록 방향 키워드로 책임 소재를 분명히 하는 것이 중요해집니다.

## 연습문제

1. `property <int> a: 3; property <int> b: a * 2; property <int> c: a + b;`라는 세 프로퍼티가 있을 때, `a`의 값을 10으로 바꾸면 `b`와 `c`는 각각 얼마가 되는지 계산해보세요. 그리고 왜 별도의 갱신 코드 없이 이 값이 맞아떨어지는지 설명해보세요.
2. 사각형의 가로(`width-cm`)와 세로(`height-cm`) 길이(센티미터 단위)를 입력받아 넓이(`area`)와 "정사각형 여부(`is-square`)"를 계산해 보여주는 `RectangleInfo` 컴포넌트를 작성하세요. 어떤 프로퍼티를 `in`으로, 어떤 프로퍼티를 `out`으로 선언해야 할지 근거와 함께 정하세요.
3. `in property`로 선언된 프로퍼티를 컴포넌트 내부에서 다른 프로퍼티의 바인딩 식에 사용하는 것이 가능한 이유를 설명해보세요. (힌트: 읽기와 쓰기 권한을 구분해서 생각해보세요.)
4. 이번 장의 "온도 변환기" 예제를 확장해서, 켈빈(`kelvin`) 온도까지 함께 계산해 보여주도록 프로퍼티를 추가해보세요. 새로 추가한 프로퍼티는 몇 단계의 연쇄 바인딩을 거쳐 계산되나요?
5. 명령형 언어(C++, Python 등)로 여러 값이 서로 의존하는 계산을 구현할 때 겪을 수 있는 문제점을 두 가지 이상 들고, Slint의 선언적 바인딩이 그 문제를 어떻게 해결하는지 비교해서 설명해보세요.

# 15장. 타이머와 비동기 작업 연동

[◀ 이전: 14장. 커스텀 스타일링과 테마](ch14-커스텀스타일링과테마.md) | [📖 목차](00-목차.md) | [다음: 16장. 이미지와 커스텀 렌더링 ▶](ch16-이미지와커스텀렌더링.md)


지금까지 다룬 예제들은 대부분 사용자의 클릭이나 입력에 반응해서 프로퍼티를 바꾸는 방식이었습니다. 하지만 실제 애플리케이션에는 "누가 누르지 않아도 스스로 움직이는" 화면이 자주 필요합니다. 시계는 매초 스스로 갱신되어야 하고, 대시보드는 일정 주기로 서버 데이터를 다시 불러와야 하며, 파일을 저장하거나 네트워크 요청을 보내는 동안에는 화면이 멈추지 않고 진행률을 계속 보여줘야 합니다. 이번 장에서는 Slint 애플리케이션에서 "시간이 흐르면서 벌어지는 일"을 다루는 두 가지 도구를 살펴봅니다. 정해진 주기로 반복되는 작업을 위한 `slint::Timer`, 그리고 오래 걸리는 작업을 별도 스레드에 맡기고 그 결과를 안전하게 화면에 반영하는 `slint::invoke_from_event_loop()`입니다.

## 15.1 slint::Timer로 반복 작업 실행하기

Slint의 이벤트 루프는 사용자 입력뿐 아니라 시간 기반 이벤트도 처리할 수 있습니다. `slint::Timer`는 이 이벤트 루프에 등록되어, 지정한 시간이 지날 때마다(또는 지정한 시간이 지난 후 단 한 번) 콜백을 실행해주는 객체입니다. 중요한 점은 이 콜백이 별도의 스레드가 아니라 **UI 이벤트 루프가 도는 바로 그 스레드**에서 실행된다는 것입니다. 즉 타이머 콜백 안에서는 UI 프로퍼티를 곧바로, 아무 걱정 없이 읽고 쓸 수 있습니다.

간단한 디지털 시계 예제로 살펴보겠습니다. 먼저 Slint 쪽에서는 시간을 문자열로 받아 보여주는 프로퍼티만 준비합니다.

```slint
export component ClockWindow inherits Window {
    in property <string> current-time: "00:00:00";

    width: 200px;
    height: 100px;

    Text {
        text: current-time;
        font-size: 32px;
        horizontal-alignment: center;
        vertical-alignment: center;
    }
}
```

C++ 쪽에서는 창을 띄운 뒤 반복 타이머를 하나 시작해서, 매초 `current-time` 프로퍼티를 새 값으로 갱신합니다.

```cpp
#include "clock-window.h"
#include <chrono>
#include <ctime>
#include <sstream>
#include <iomanip>

std::string format_now()
{
    auto t = std::time(nullptr);
    std::tm tm{};
    localtime_s(&tm, &t);
    std::ostringstream oss;
    oss << std::put_time(&tm, "%H:%M:%S");
    return oss.str();
}

int main()
{
    auto window = ClockWindow::create();

    slint::Timer clock_timer;
    clock_timer.start(
        slint::TimerMode::Repeated,
        std::chrono::seconds(1),
        [weak = window->as_weak()] {
            if (auto w = weak.lock()) {
                w->set_current_time(format_now());
            }
        });

    window->run();
}
```

`slint::Timer::start()`에는 세 가지를 전달합니다. 한 번만 실행할지 반복할지를 정하는 `slint::TimerMode`(`Repeated` 또는 `SingleShot`), 실행 주기를 나타내는 `std::chrono` 기간, 그리고 실제로 실행할 콜백입니다. 지연 후 딱 한 번만 실행하고 싶다면 `TimerMode::SingleShot`을 쓰면 됩니다. 예를 들어 "3초 후에 안내 문구를 자동으로 숨기는" 동작도 같은 방식으로 만들 수 있습니다.

콜백 안에서 `window->as_weak()`으로 얻은 약한 참조(weak handle)를 캡처하고, 실행 시점에 `.lock()`으로 다시 살아있는지 확인한 뒤 사용하는 패턴을 눈여겨보세요. 창이 이미 닫히고 파괴된 뒤에도 타이머 콜백이 남아 있는 상황을 안전하게 방지하기 위한 관용구이며, 7장에서 다룬 C++ ↔ Slint 연동 코드에서도 같은 이유로 강한 참조 대신 약한 참조를 즐겨 씁니다.

## 15.2 UI는 오직 UI 스레드에서만 안전하다

타이머는 여러 GUI 프레임워크가 공통으로 겪는 더 근본적인 규칙 위에 서 있습니다. **UI 요소는 UI 스레드(이벤트 루프가 도는 스레드)에서만 안전하게 다룰 수 있다**는 규칙입니다. Slint도 예외가 아닙니다. `slint::Timer`의 콜백이 UI 프로퍼티를 마음껏 건드려도 되는 이유는, 그 콜백 자체가 UI 이벤트 루프 안에서 호출되기 때문이지 타이머라는 것이 특별히 스레드 안전하기 때문이 아닙니다.

문제는 시계처럼 짧고 가벼운 작업이 아니라, 네트워크 요청이나 대용량 파일 읽기처럼 **완료까지 시간이 걸리는 작업**을 다뤄야 할 때 생깁니다. 이런 작업을 UI 스레드에서 그대로 실행하면 응답이 올 때까지 이벤트 루프가 멈추고, 창은 그 사이 완전히 얼어붙습니다. 그래서 실무에서는 이런 작업을 `std::thread`로 띄운 별도의 작업 스레드에서 처리합니다. 그런데 그 작업 스레드가 결과를 얻은 다음, 곧바로 `window->set_progress(100)`처럼 UI 프로퍼티를 건드리면 어떻게 될까요? UI 스레드가 아닌 곳에서 UI 요소를 직접 건드리는 셈이 되어, 정의되지 않은 동작이나 크래시로 이어질 수 있습니다.

이 문제는 Slint만의 특수한 사정이 아닙니다. UI 프레임워크는 대개 화면 갱신을 위한 내부 자료구조를 스레드 안전하게 설계하지 않는데, 이는 매번 잠금을 거는 비용을 치르지 않기 위한 의도적인 설계입니다. 대신 "다른 스레드의 작업 결과를 UI 스레드로 안전하게 넘기는" 전용 통로를 하나씩 제공합니다. 이 저장소의 "C#으로 배우는 동시성과 병렬 프로그래밍" 책에서 `SynchronizationContext`나 WPF/Avalonia의 `Dispatcher`를 통해 백그라운드 스레드의 결과를 UI 스레드로 마샬링(marshaling)하던 것을 다뤘다면, 지금부터 살펴볼 `slint::invoke_from_event_loop()`는 정확히 같은 역할을 하는 Slint의 통로라고 생각하면 됩니다. 프레임워크마다 이름은 다르지만 "UI를 건드리는 코드는 반드시 UI 스레드로 되돌려서 실행한다"는 원칙은 동일합니다.

## 15.3 slint::invoke_from_event_loop()로 안전하게 되돌아오기

`slint::invoke_from_event_loop()`는 어떤 스레드에서 호출하더라도, 전달한 콜백을 Slint의 UI 이벤트 루프 스레드에서 실행하도록 예약해주는 함수입니다. 백그라운드 스레드가 할 일을 마친 뒤 UI를 갱신하고 싶을 때는, 그 갱신 코드를 직접 실행하지 말고 이 함수에 람다로 넘기면 됩니다.

파일을 읽는 등 시간이 걸리는 작업을 흉내 낸 예제를 보겠습니다. Slint 쪽에는 진행 상태와 결과를 담을 프로퍼티, 그리고 작업을 시작시키는 콜백을 준비합니다.

```slint
export component LoaderWindow inherits Window {
    in property <bool> is-loading: false;
    in property <string> result-text: "";
    callback start-loading();

    VerticalLayout {
        padding: 16px;
        spacing: 8px;

        Text {
            text: is-loading ? "불러오는 중..." : result-text;
        }

        Button {
            text: "새로고침";
            enabled: !is-loading;
            clicked => { start-loading(); }
        }
    }
}
```

C++ 쪽에서는 버튼 클릭에 반응해 `std::thread`를 하나 띄우고, 그 스레드 안에서 오래 걸리는 작업(여기서는 흉내만 낸 지연)을 수행한 뒤, 결과를 `invoke_from_event_loop()`로 UI 스레드에 되돌려 반영합니다.

```cpp
#include "loader-window.h"
#include <thread>
#include <chrono>

int main()
{
    auto window = LoaderWindow::create();

    window->on_start_loading([weak = window->as_weak()] {
        auto w = weak.lock();
        if (!w) return;

        w->set_is_loading(true);

        // 오래 걸리는 작업은 반드시 별도 스레드에서 실행한다.
        // UI 스레드에서 직접 돌리면 창이 응답을 멈춘다.
        std::thread([weak] {
            std::this_thread::sleep_for(std::chrono::seconds(2));
            std::string fetched = "최신 데이터를 불러왔습니다.";

            // 작업 스레드는 UI 요소를 직접 건드리지 않는다.
            // 대신 UI 스레드에서 실행될 람다를 이벤트 루프에 넘긴다.
            slint::invoke_from_event_loop([weak, fetched] {
                if (auto w = weak.lock()) {
                    w->set_result_text(fetched);
                    w->set_is_loading(false);
                }
            });
        }).detach();
    });

    window->run();
}
```

이 코드에서 스레드 경계가 어디인지 분명히 짚어봅시다. `on_start_loading` 콜백 자체는 UI 스레드에서 실행되므로 `set_is_loading(true)`를 바로 호출해도 안전합니다. 그다음 만든 `std::thread`의 람다는 UI 스레드가 아닌 새 작업 스레드에서 실행되므로, 그 안에서는 `w->set_...` 같은 UI 프로퍼티 접근을 절대로 직접 하지 않습니다. 오직 `slint::invoke_from_event_loop()`에 넘긴 가장 안쪽 람다만 UI 스레드로 다시 옮겨져서 실행되며, 그 안에서 비로소 `set_result_text`와 `set_is_loading(false)`를 호출합니다.

여기서도 `weak = window->as_weak()`를 작업 스레드까지 그대로 들고 다니는 것을 볼 수 있습니다. 작업이 2초씩 걸리는 동안 사용자가 창을 닫아버릴 수도 있기 때문에, `invoke_from_event_loop()` 안에서도 `.lock()`으로 창이 아직 살아있는지 확인한 뒤에만 프로퍼티를 건드립니다.

## 15.4 타이머와 백그라운드 스레드 조합하기

실전에서는 15.1의 타이머와 15.3의 스레드 마샬링이 함께 쓰이는 경우가 많습니다. 예를 들어 "30초마다 서버에서 최신 상태를 자동으로 가져오는" 자동 새로고침 기능을 생각해봅시다. 타이머 자체는 UI 스레드에서 반복 실행되지만, 타이머 콜백 안에서 직접 네트워크 요청을 보내면 그 요청이 끝날 때까지 UI 스레드가 멈춰버립니다. 그래서 타이머 콜백이 하는 일은 "새 작업 스레드를 하나 띄우는 것"뿐이고, 실제 네트워크 작업과 그 결과 반영은 15.3과 똑같은 구조를 따릅니다.

```cpp
slint::Timer refresh_timer;
refresh_timer.start(
    slint::TimerMode::Repeated,
    std::chrono::seconds(30),
    [weak = window->as_weak()] {
        std::thread([weak] {
            std::string latest = fetch_from_server(); // 시간이 걸리는 작업

            slint::invoke_from_event_loop([weak, latest] {
                if (auto w = weak.lock()) {
                    w->set_result_text(latest);
                }
            });
        }).detach();
    });
```

이렇게 "타이머는 언제 시작할지를 UI 스레드에서 결정하고, 실제 무거운 작업은 별도 스레드가 처리하고, 그 결과는 `invoke_from_event_loop()`로 다시 UI 스레드에 되돌린다"는 세 단계 구조를 기억해두면, 자동 새로고침이든 진행률 표시든 대부분의 비동기 시나리오를 같은 패턴으로 풀어낼 수 있습니다.

## 요약

- `slint::Timer`는 UI 이벤트 루프 안에서 일정 주기로(`TimerMode::Repeated`) 또는 지연 후 한 번(`TimerMode::SingleShot`) 콜백을 실행합니다. 타이머 콜백은 UI 스레드에서 실행되므로 그 안에서 UI 프로퍼티를 직접 읽고 써도 안전합니다.
- Slint를 포함한 대부분의 GUI 프레임워크는 UI 요소를 UI 스레드에서만 안전하게 다룰 수 있다는 공통 규칙을 갖고 있습니다. 네트워크 요청이나 파일 I/O처럼 오래 걸리는 작업은 `std::thread` 등 별도 스레드에서 처리해야 UI가 멈추지 않습니다.
- 작업 스레드에서 UI 프로퍼티를 직접 건드리면 안 됩니다. 대신 `slint::invoke_from_event_loop()`에 UI를 갱신하는 람다를 넘기면, 그 람다가 UI 스레드로 안전하게 옮겨져 실행됩니다.
- 이는 "C#으로 배우는 동시성과 병렬 프로그래밍" 책에서 다룬 `SynchronizationContext`/`Dispatcher`를 통한 UI 스레드 마샬링과 본질적으로 같은 문제이자 같은 해법입니다. 프레임워크마다 API 이름은 다르지만, 원칙은 "UI를 건드리는 코드는 반드시 UI 스레드로 되돌려서 실행한다"로 동일합니다.
- 창이 이미 닫혔을 수도 있는 지연 실행 콜백에서는 `as_weak()`으로 얻은 약한 참조를 캡처하고, 실행 시점에 `.lock()`으로 대상이 아직 살아있는지 확인한 뒤에 프로퍼티를 건드리는 것이 안전한 관용구입니다.
- 자동 새로고침처럼 주기적으로 무거운 작업을 반복해야 할 때는 타이머(언제 시작할지 결정)와 작업 스레드(무거운 일 처리)와 `invoke_from_event_loop()`(결과 반영)를 조합해서 씁니다.

## 연습문제

1. `slint::Timer`의 콜백이 UI 프로퍼티를 직접 건드려도 안전한 이유를 한 문장으로 설명해보세요. 그리고 `std::thread`로 만든 작업 스레드의 콜백은 왜 그렇게 할 수 없는지도 함께 설명해보세요.
2. 15.1의 디지털 시계 예제를 수정해서, 처음 켰을 때는 시:분:초를 보여주다가 5분이 지나면 자동으로 멈추도록(`TimerMode::SingleShot` 타이머를 추가로 활용해서) 만들어보세요.
3. 15.3의 `LoaderWindow` 예제에서 만약 `invoke_from_event_loop()`를 쓰지 않고 작업 스레드 안에서 `w->set_result_text(...)`를 곧바로 호출하면 어떤 문제가 생길 수 있는지 서술해보세요.
4. `as_weak()`과 `.lock()` 패턴을 쓰지 않고 `window`를 원시 포인터나 참조로 그대로 작업 스레드 람다에 캡처했다면 어떤 상황에서 문제가 생길 수 있는지 예를 들어 설명해보세요.
5. 15.4의 자동 새로고침 예제를 확장해서, 서버 요청이 실패했을 때 오류 메시지를 보여주는 프로퍼티를 추가해보세요. 오류 메시지 역시 작업 스레드에서 곧바로 설정하면 안 되는 이유를 함께 적어보세요.

# 11장. 리스트와 모델(Model)

[◀ 이전: 10장. 상태(states)와 애니메이션](ch10-상태와애니메이션.md) | [📖 목차](00-목차.md) | [다음: 12장. 전역 싱글톤(Global) ▶](ch12-전역싱글톤.md)


지금까지 다룬 예제들은 대부분 화면에 고정된 개수의 엘리먼트를 배치하는 것이었습니다. 하지만 실제 애플리케이션에서는 "몇 개가 될지 미리 알 수 없는" 데이터를 화면에 나열해야 하는 경우가 훨씬 흔합니다. 할 일 목록 앱이라면 사용자가 추가한 할 일의 개수만큼 항목이 늘어나야 하고, 채팅 앱이라면 대화가 이어질수록 메시지 목록이 계속 길어져야 합니다. 이런 "목록형 UI"를 다루는 것이 이번 장의 주제입니다. 18장에서 만들어 볼 실전 프로젝트에서도 이런 목록 패턴이 뼈대를 이루게 되므로, 이번 장에서 확실히 익혀 두면 이후 훨씬 수월해집니다.

## 왜 프로퍼티만으로는 부족한가

5장에서 배운 프로퍼티는 `string`, `int`, `bool`처럼 값 하나를 담는 그릇이었습니다. 그런데 할 일 목록처럼 "여러 개의 항목"을 표현하려면 어떻게 해야 할까요? 항목이 정확히 3개뿐이라면 `property <string> item1`, `item2`, `item3`을 각각 선언하고 `Text` 세 개를 나란히 배치하면 될지도 모릅니다. 하지만 항목이 몇 개가 될지 실행 전에는 알 수 없고, 사용자가 실행 중에 항목을 추가하거나 삭제할 수 있어야 한다면 이 방식은 곧바로 한계에 부딪힙니다.

Slint는 이 문제를 **모델(model)**이라는 개념으로 해결합니다. 모델은 "같은 종류의 값이 여러 개 나열된 것"을 표현하는 데이터 구조이며, `.slint` 언어에는 모델의 각 항목마다 UI 엘리먼트를 하나씩 반복해서 그려 주는 전용 문법이 마련되어 있습니다.

## `for` 문법: 모델의 각 항목을 엘리먼트로 반복하기

가장 단순한 형태의 모델은 문자열 배열입니다. 대괄호(`[]`)로 감싼 리스트 형태로 값을 나열하면 그 자체로 모델이 됩니다.

```slint
component SimpleList inherits Window {
    width: 240px;
    height: 200px;

    property <[string]> fruits: ["사과", "바나나", "포도"];

    VerticalLayout {
        for fruit in fruits : Text {
            text: fruit;
            font-size: 16px;
        }
    }
}
```

`property <[string]> fruits`처럼 타입 이름을 대괄호로 감싸면 "그 타입의 값을 여러 개 담는 모델" 타입이 됩니다. 그리고 `for 항목이름 in 모델 : 엘리먼트 { ... }` 구문이 이번 장의 핵심입니다. 이 구문은 `fruits` 모델의 각 항목마다 `Text` 엘리먼트를 하나씩 만들어 내며, 엘리먼트 안에서는 `fruit`라는 이름으로 현재 반복 중인 항목의 값을 참조할 수 있습니다. 모델에 항목이 3개 있으므로 `Text`도 3개가 만들어지는 셈입니다. 4장에서 배운 `VerticalLayout`으로 감싸 두었기 때문에 이 3개의 `Text`가 세로로 가지런히 배치됩니다.

`for` 반복문 안에서 각 항목의 인덱스(순번)가 필요할 때는 다음처럼 대괄호를 하나 더 붙여 인덱스 변수를 함께 받을 수 있습니다.

```slint
component IndexedList inherits Window {
    width: 240px;
    height: 200px;

    property <[string]> fruits: ["사과", "바나나", "포도"];

    VerticalLayout {
        for fruit[index] in fruits : Text {
            text: index + ". " + fruit;
            font-size: 16px;
        }
    }
}
```

`for fruit[index] in fruits`처럼 쓰면 `index`에는 0부터 시작하는 정수 인덱스가 담기고, `fruit`에는 여전히 해당 항목의 값이 담깁니다. 목록에 번호를 매기거나, 짝수/홀수 번째 항목의 배경색을 다르게 칠하는 등의 처리를 할 때 이 인덱스가 유용하게 쓰입니다.

## 구조체 항목으로 이루어진 모델

실무에서 다루는 목록은 문자열 하나만 있는 경우보다, 여러 필드를 가진 데이터인 경우가 훨씬 많습니다. 할 일 목록이라면 "할 일 내용"과 "완료 여부"를 함께 가져야 합니다. 이때는 3장에서 익힌 프로퍼티 타입 문법을 확장해, 구조체(struct)를 정의하고 그 구조체의 모델을 만들면 됩니다.

```slint
struct TodoItem {
    text: string,
    done: bool,
}

component TodoList inherits Window {
    width: 320px;
    height: 240px;

    property <[TodoItem]> todos: [
        { text: "Slint 문법 익히기", done: true },
        { text: "모델 예제 작성하기", done: false },
        { text: "연습문제 풀기", done: false },
    ];

    VerticalLayout {
        for todo in todos : Rectangle {
            height: 32px;

            Text {
                text: todo.done ? "[완료] " + todo.text : "[진행중] " + todo.text;
                color: todo.done ? #7f8c8d : #2c3e50;
            }
        }
    }
}
```

`struct TodoItem { text: string, done: bool, }`으로 필드 두 개를 가진 구조체를 정의하고, `property <[TodoItem]> todos`로 이 구조체의 모델을 선언했습니다. `for todo in todos` 반복문 안에서는 `todo.text`, `todo.done`처럼 점(`.`) 표기법으로 각 필드에 접근합니다. 항목 하나하나가 단순한 문자열이 아니라 여러 정보를 함께 담은 구조체라는 점만 다를 뿐, `for` 구문 자체의 사용법은 앞서 본 문자열 모델과 동일합니다.

지금까지의 예제는 `.slint` 파일 안에서 모델을 직접 리터럴로 선언했습니다. 정적인 목록이라면 이것으로 충분하지만, 실제 애플리케이션에서는 목록의 내용이 C++ 쪽 로직(파일에서 읽어온 데이터, 서버에서 받아온 데이터, 사용자가 추가한 항목 등)에 따라 결정되는 경우가 대부분입니다. 이제 C++에서 모델을 만들어 UI에 전달하는 방법을 살펴보겠습니다.

## C++에서 모델 제공하기: `VectorModel`

7장과 8장에서 살펴본 것처럼, `.slint` 파일에 선언한 프로퍼티는 빌드 시점에 생성되는 C++ 클래스에 대응하는 getter·setter 메서드를 만들어 냅니다. 모델 타입의 프로퍼티도 마찬가지입니다. 다만 모델은 단순한 값이 아니라 "항목이 늘어나거나 줄어들 수 있는 컬렉션"이므로, C++에서는 이를 표현하기 위한 전용 클래스인 `slint::VectorModel<T>`를 사용합니다.

앞서 본 `TodoItem` 구조체를 예로 들어 보겠습니다. `.slint` 쪽 선언은 다음과 같습니다.

```slint
export struct TodoItem {
    text: string,
    done: bool,
}

export component TodoList inherits Window {
    width: 320px;
    height: 280px;

    in property <[TodoItem]> todos;

    VerticalLayout {
        for todo in todos : Rectangle {
            height: 32px;

            Text {
                text: todo.done ? "[완료] " + todo.text : "[진행중] " + todo.text;
            }
        }
    }
}
```

구조체와 컴포넌트 앞에 `export`를 붙여 C++ 쪽에서 접근할 수 있게 했고, `todos` 프로퍼티에는 `in` 방향성을 붙였습니다(방향성 프로퍼티에 대해서는 8장에서 이미 다루었습니다). 이렇게 하면 빌드 도구가 `TodoItem`에 대응하는 C++ 구조체와, `TodoList` 컴포넌트에 대응하는 클래스를 생성하는데, 이 클래스에는 `todos` 모델을 설정할 수 있는 setter가 함께 만들어집니다.

C++ 쪽에서 모델을 만들어 전달하는 코드는 다음과 같은 모양이 됩니다.

```cpp
#include "app-window.h"
#include <slint.h>

int main() {
    auto ui = TodoList::create();

    auto model = std::make_shared<slint::VectorModel<TodoItem>>(
        std::vector<TodoItem>{
            TodoItem{ .text = "Slint 문법 익히기", .done = true },
            TodoItem{ .text = "모델 예제 작성하기", .done = false },
            TodoItem{ .text = "연습문제 풀기", .done = false },
        }
    );

    ui->set_todos(model);

    ui->run();
}
```

`std::make_shared<slint::VectorModel<TodoItem>>(std::vector<TodoItem>{...})`로 초기 항목들을 담은 `VectorModel`을 만들고, 생성된 클래스의 `set_todos(model)`를 호출해 이 모델을 UI에 연결합니다. `.slint`에서 `todos` 프로퍼티였던 것이 C++에서는 `set_todos` / `todos()`라는 이름의 메서드로 대응되는데, 이는 8장에서 배운 프로퍼티 이름 변환 규칙(케밥 케이스는 밑줄로, `setter`는 `set_` 접두사)과 정확히 같은 패턴입니다. 모델은 `std::shared_ptr`로 다루어진다는 점도 기억해 둘 필요가 있습니다. UI는 이 포인터를 통해 모델을 참조하므로, C++ 쪽에서 같은 `shared_ptr`를 계속 들고 있으면 나중에 모델의 내용을 바꿀 수도 있습니다. 바로 다음 절에서 다룰 내용입니다.

## 모델이 바뀌면 UI도 자동으로 갱신되어야 한다

목록 UI를 다룰 때 가장 흔히 마주치는 요구사항은 "실행 중에 항목을 추가하거나 삭제했을 때 화면이 그 변화를 즉시 반영해야 한다"는 것입니다. 여기서 반드시 기억해야 할 원칙이 하나 있습니다. **`VectorModel`이 제공하는 메서드를 통해 항목을 추가·삭제·수정해야, 그 변경이 UI에 자동으로 반영됩니다.** 모델을 감싸고 있는 `std::vector`를 밖에서 직접 꺼내 조작하거나, 매번 새 모델을 만들어 다시 `set_todos`를 호출하는 방식은 번거롭고 비효율적입니다.

이를 위해서는 모델을 가리키는 `shared_ptr`를 어딘가에 계속 보관해 두어야 합니다. `main()` 함수의 지역 변수로 두면 콜백 핸들러 안에서 이 변수를 캡처해 재사용할 수 있습니다.

```cpp
int main() {
    auto ui = TodoList::create();

    auto model = std::make_shared<slint::VectorModel<TodoItem>>(
        std::vector<TodoItem>{
            TodoItem{ .text = "Slint 문법 익히기", .done = true },
        }
    );
    ui->set_todos(model);

    // model을 계속 붙잡고 있으므로, 이후 언제든 항목을 추가할 수 있다
    model->push_back(TodoItem{ .text = "새로 추가된 항목", .done = false });

    ui->run();
}
```

`model->push_back(...)`처럼 모델 자체의 메서드를 호출해 항목을 추가하면, `VectorModel`이 내부적으로 "항목이 추가되었다"는 사실을 UI 쪽에 통지합니다. 그러면 Slint 런타임이 이 통지를 받아 `for` 반복문으로 만들어진 엘리먼트 목록을 자동으로 다시 계산하고, 새로 추가된 항목에 대응하는 엘리먼트를 화면에 그려 넣습니다. `VectorModel`은 이 밖에도 `erase(인덱스)`로 특정 위치의 항목을 지우거나, `set_row_data(인덱스, 값)`으로 특정 위치의 항목 내용을 바꾸는 메서드를 제공하는데, 이들 모두 같은 원리로 동작합니다. 즉 항목을 바꾸는 방법이 다를 뿐, "모델 자신의 메서드를 통해 변경한다"는 규칙은 동일합니다.

## Button과 결합하기: 버튼을 눌러 목록에 항목 추가하기

이제 9장에서 배운 `Button`, `LineEdit`과 이번 장의 모델을 결합해, "입력창에 텍스트를 쓰고 버튼을 누르면 할 일 목록에 새 항목이 추가되는" 예제를 만들어 보겠습니다. 먼저 `.slint` 쪽입니다.

```slint
import { Button, LineEdit } from "std-widgets.slint";

export struct TodoItem {
    text: string,
    done: bool,
}

export component TodoList inherits Window {
    width: 360px;
    height: 320px;
    title: "할 일 목록";

    in property <[TodoItem]> todos;
    in-out property <string> new-todo-text: "";
    callback add-todo-clicked();

    VerticalLayout {
        padding: 12px;
        spacing: 8px;

        HorizontalLayout {
            spacing: 8px;

            LineEdit {
                text <=> new-todo-text;
                placeholder-text: "할 일을 입력하세요";
            }

            Button {
                text: "추가";
                clicked => { add-todo-clicked(); }
            }
        }

        for todo in todos : Text {
            text: todo.done ? "[완료] " + todo.text : "[진행중] " + todo.text;
        }
    }
}
```

`new-todo-text`는 `in-out` 프로퍼티로 선언해 `LineEdit`의 `text`와 양방향 바인딩(`<=>`, 6장에서 다룬 문법입니다)으로 묶었습니다. `Button`을 클릭하면 `add-todo-clicked()` 콜백이 발생하는데, 이 콜백을 실제로 처리해 목록에 항목을 추가하는 일은 C++ 쪽에서 담당합니다.

```cpp
#include "app-window.h"
#include <slint.h>

int main() {
    auto ui = TodoList::create();

    auto model = std::make_shared<slint::VectorModel<TodoItem>>(
        std::vector<TodoItem>{}
    );
    ui->set_todos(model);

    ui->on_add_todo_clicked([ui = slint::ComponentWeakHandle(ui), model] {
        if (auto locked_ui = ui.lock()) {
            auto text = (*locked_ui)->get_new_todo_text();
            if (!text.empty()) {
                model->push_back(TodoItem{ .text = text, .done = false });
                (*locked_ui)->set_new_todo_text("");
            }
        }
    });

    ui->run();
}
```

`ui->on_add_todo_clicked(...)`로 `.slint`에서 발생한 `add-todo-clicked` 콜백을 처리하는 C++ 람다를 등록합니다(콜백 연결의 세부 문법은 7장과 6장에서 다룬 내용을 그대로 따릅니다). 이 람다 안에서는 `get_new_todo_text()`로 입력창에 사용자가 입력한 값을 읽어 오고, 값이 비어 있지 않다면 `model->push_back(...)`으로 새 `TodoItem`을 모델에 추가합니다. 앞서 설명한 원칙대로, 모델 자신의 `push_back` 메서드를 사용했기 때문에 화면의 목록도 함께 갱신됩니다. 마지막으로 `set_new_todo_text("")`로 입력창을 비워, 사용자가 다음 할 일을 이어서 입력할 수 있게 했습니다.

여기서 람다가 `model`을 값으로 캡처하고 있다는 점도 눈여겨볼 만합니다. `model`은 `shared_ptr`이므로 값으로 캡처해도 복사 비용이 크지 않고, 참조 카운트가 늘어나 콜백이 살아 있는 동안 모델 객체가 안전하게 유지됩니다. `ui`는 `ComponentWeakHandle`로 캡처했는데, 이는 콜백이 창(그리고 창을 감싸는 `ui` 핸들)보다 더 오래 살아남는 순환 참조를 피하기 위한 관례입니다.

## 요약

- 여러 개의 항목을 화면에 나열해야 할 때는 프로퍼티 대신 **모델(model)**을 사용합니다. `.slint`에서는 `property <[타입]> 이름;`처럼 타입을 대괄호로 감싸 모델 타입을 선언합니다.
- `for 항목 in 모델 : 엘리먼트 { ... }` 문법으로 모델의 각 항목마다 엘리먼트를 하나씩 반복 생성합니다. `for 항목[인덱스] in 모델`처럼 쓰면 인덱스도 함께 받을 수 있습니다.
- 항목 하나에 여러 필드가 필요할 때는 `struct`로 구조체를 정의하고, 그 구조체의 모델(`[구조체이름]`)을 사용합니다. `for` 반복문 안에서는 점(`.`) 표기법으로 필드에 접근합니다.
- C++에서는 `std::make_shared<slint::VectorModel<T>>(std::vector<T>{...})`로 모델을 만들고, 생성된 클래스의 `set_모델이름(model)` setter로 UI에 전달합니다.
- 항목을 추가·삭제·수정할 때는 반드시 모델 자신의 메서드(`push_back`, `erase`, `set_row_data` 등)를 통해야 UI가 자동으로 갱신됩니다. 이를 위해 모델을 가리키는 `shared_ptr`를 콜백 등에서 재사용할 수 있도록 계속 보관해 두어야 합니다.
- `Button`의 `clicked` 콜백과 모델의 변경 메서드를 결합하면, "버튼을 누르면 목록에 새 항목이 추가되는" 동적인 UI를 만들 수 있습니다.

## 연습문제

1. `int` 타입의 모델(`property <[int]> scores;`)을 선언하고, `for` 구문으로 각 점수를 `Text`로 나열해 보세요. 인덱스를 함께 사용해 "1번째: 90"처럼 순번을 붙여 표시해 보세요.
2. `Person` 구조체(`name: string`, `age: int`)를 정의하고, 이 구조체의 모델을 `for` 구문으로 반복해 이름과 나이를 함께 표시하는 목록을 만들어 보세요.
3. 이번 장의 할 일 목록 예제를 확장하여, 각 항목 옆에 9장에서 다룬 `CheckBox`를 추가하고, 체크박스를 토글하면 해당 항목의 `done` 값이 바뀌도록 만들어 보세요. (힌트: `for` 반복문에 인덱스를 함께 받아, C++ 쪽에서 `model->set_row_data(인덱스, 새값)`을 호출하는 콜백을 연결합니다.)
4. C++ 쪽에서 `model->erase(인덱스)`를 사용해, 특정 위치의 할 일 항목을 삭제하는 "삭제" 버튼을 각 항목마다 추가해 보세요.
5. 모델을 `shared_ptr`로 보관하지 않고 콜백 안에서 매번 새로 만들어 `set_todos`를 다시 호출하는 방식과, 이번 장에서 소개한 `push_back` 방식의 차이를 코드로 비교해 보고 어떤 방식이 더 바람직한지 설명해 보세요.

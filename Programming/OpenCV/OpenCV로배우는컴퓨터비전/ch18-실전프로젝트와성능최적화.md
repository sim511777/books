## 18.1 실전 프로젝트: 스마트폰으로 찍은 문서를 정면으로 펴기

스마트폰 스캐너 앱들이 흔히 하는 일을 그대로 재현해보자. 비스듬한 각도에서 찍은 문서 사진 한 장을 입력받아, 문서의 네 꼭짓점을 찾아내고, 그 사각형을 정면에서 본 것처럼 펴서 출력하는 프로그램이다. 이 작업은 지금까지 배운 기법들을 다음과 같은 순서로 연결한 것에 불과하다.

| 단계 | 사용 기법 | 관련 장 |
|---|---|---|
| 1. 이미지 읽기 | `cv2.imread` | 4장 |
| 2. 그레이스케일 변환 | `cv2.cvtColor` | 5장 |
| 3. 노이즈 완화 | `cv2.GaussianBlur` | 9장 |
| 4. 경계 검출 | `cv2.Canny` | 12장 |
| 5. 윤곽선 검출 | `cv2.findContours` | 13장 |
| 6. 사각형 근사 | `cv2.approxPolyDP` | 13장 |
| 7. 원근 변환으로 펴기 | `cv2.getPerspectiveTransform` + `cv2.warpPerspective` | 8장 |

한 걸음씩 뜯어보면, 이 파이프라인의 핵심 논리는 이렇다. 먼저 엣지 검출로 문서와 배경의 경계선을 도드라지게 만든다. 그 경계선들로부터 윤곽선을 뽑아내고, 그중 가장 넓은 면적을 차지하면서 꼭짓점이 정확히 4개인 다각형을 "문서의 테두리"로 간주한다. 마지막으로 그 4개의 꼭짓점을 목표 사각형(가로세로가 딱 맞는 반듯한 직사각형)의 네 꼭짓점으로 매핑하는 원근 변환 행렬을 구해, 이미지 전체를 그 변환으로 다시 그리면 기울어져 찍힌 문서가 정면 스캔본처럼 펴진다.

```python
import cv2
import numpy as np


def order_points(pts):
    """4개의 점을 top-left, top-right, bottom-right, bottom-left 순서로 정렬한다."""
    pts = pts.reshape(4, 2).astype(np.float32)
    s = pts.sum(axis=1)                     # x+y가 가장 작으면 top-left, 가장 크면 bottom-right
    diff = np.diff(pts, axis=1).flatten()   # x-y가 가장 작으면 top-right, 가장 크면 bottom-left

    ordered = np.zeros((4, 2), dtype=np.float32)
    ordered[0] = pts[np.argmin(s)]
    ordered[2] = pts[np.argmax(s)]
    ordered[1] = pts[np.argmin(diff)]
    ordered[3] = pts[np.argmax(diff)]
    return ordered


def find_document_corners(img):
    """Canny + findContours + approxPolyDP로 문서의 네 꼭짓점을 자동으로 찾는다.
    찾지 못하면 None을 반환한다."""
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
    blurred = cv2.GaussianBlur(gray, (5, 5), 0)
    edges = cv2.Canny(blurred, 75, 200)

    contours, _ = cv2.findContours(edges, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)
    contours = sorted(contours, key=cv2.contourArea, reverse=True)

    for c in contours[:5]:  # 면적이 큰 상위 5개만 검사해 불필요한 연산을 줄인다.
        peri = cv2.arcLength(c, True)
        approx = cv2.approxPolyDP(c, 0.02 * peri, True)
        if len(approx) == 4:
            return approx.reshape(4, 2).astype(np.float32)

    return None


def warp_to_rectangle(img, corners):
    """4개의 꼭짓점(corners)을 기준으로 원근 변환을 적용해 정면 사각형으로 편다."""
    tl, tr, br, bl = order_points(corners)

    width = int(max(np.linalg.norm(br - bl), np.linalg.norm(tr - tl)))
    height = int(max(np.linalg.norm(tr - br), np.linalg.norm(tl - bl)))

    dst = np.array(
        [[0, 0], [width - 1, 0], [width - 1, height - 1], [0, height - 1]],
        dtype=np.float32,
    )
    src = np.array([tl, tr, br, bl], dtype=np.float32)

    M = cv2.getPerspectiveTransform(src, dst)
    return cv2.warpPerspective(img, M, (width, height))
```

이 세 함수만으로도 이상적인 조건(배경과 문서의 대비가 뚜렷하고, 문서 네 변이 모두 화면 안에 들어와 있는 경우)에서는 문서 스캐너가 잘 동작한다. 하지만 실제로 스마트폰으로 찍은 사진은 항상 이렇게 협조적이지 않다. 배경이 문서와 비슷한 색이거나, 그림자가 문서 위에 걸쳐 있거나, 문서 모서리가 사진 프레임 밖으로 살짝 벗어나 있으면 `approxPolyDP`가 정확히 4개의 점을 내놓지 못하는 경우가 흔하다.

## 18.2 자동 검출이 실패할 때: 마우스 클릭 폴백

`find_document_corners`가 `None`을 반환한다는 것은 "자동으로는 문서 경계를 찾지 못했다"는 뜻이다. 이때 프로그램을 그냥 종료시키는 대신, 6장에서 다룬 마우스 콜백을 재사용해 사용자가 직접 네 꼭짓점을 클릭해서 지정하도록 하면 훨씬 견고한 프로그램이 된다. 이런 "자동 처리가 실패하면 사람이 개입해 보정한다"는 패턴은 실전 컴퓨터 비전 파이프라인에서 매우 흔하게 쓰인다.

구현 방식은 6장에서 배운 `cv2.setMouseCallback`과 동일하다. 창을 하나 띄우고, 사용자가 왼쪽 마우스 버튼을 클릭할 때마다 그 좌표를 리스트에 쌓다가, 4개가 모두 채워지면 창을 닫고 그 좌표들을 돌려준다.

```python
import cv2
import numpy as np

_manual_points = []


def _on_mouse_click(event, x, y, flags, param):
    if event == cv2.EVENT_LBUTTONDOWN and len(_manual_points) < 4:
        _manual_points.append((x, y))
        print(f"점 {len(_manual_points)}번 지정: ({x}, {y})")


def get_manual_corners(img):
    """사용자가 마우스로 네 모서리를 순서대로(좌상->우상->우하->좌하) 클릭하게 하고
    그 좌표를 (4, 2) 배열로 반환한다. Esc를 누르면 취소한다."""
    global _manual_points
    _manual_points = []

    window_name = "Click 4 corners: TL -> TR -> BR -> BL (Esc to cancel)"
    cv2.namedWindow(window_name)
    cv2.setMouseCallback(window_name, _on_mouse_click)

    while True:
        display = img.copy()
        for i, p in enumerate(_manual_points):
            cv2.circle(display, p, 6, (0, 0, 255), -1)
            cv2.putText(
                display, str(i + 1), (p[0] + 8, p[1]),
                cv2.FONT_HERSHEY_SIMPLEX, 0.7, (0, 0, 255), 2,
            )
        # 이미 지정된 점들을 순서대로 잇는 선을 그려 진행 상황을 눈으로 확인한다.
        if len(_manual_points) >= 2:
            cv2.polylines(display, [np.array(_manual_points)], False, (0, 255, 255), 1)

        cv2.imshow(window_name, display)
        key = cv2.waitKey(20) & 0xFF

        if len(_manual_points) == 4:
            break
        if key == 27:  # Esc: 사용자가 취소
            break

    cv2.destroyWindow(window_name)

    if len(_manual_points) != 4:
        raise RuntimeError("4개의 점을 모두 지정하지 않아 스캔을 취소했습니다.")

    return np.array(_manual_points, dtype=np.float32)
```

이제 `scan_document` 함수는 자동 검출을 먼저 시도하고, 실패했을 때만 수동 지정으로 넘어가는 구조로 완성된다.

```python
def scan_document(path):
    img = cv2.imread(path)
    if img is None:
        raise FileNotFoundError(f"이미지를 열 수 없습니다: {path}")

    corners = find_document_corners(img)

    if corners is None:
        print("자동으로 문서의 네 모서리를 찾지 못했습니다. 수동으로 지정해 주세요.")
        corners = get_manual_corners(img)
    else:
        print("문서의 네 모서리를 자동으로 찾았습니다.")

    return warp_to_rectangle(img, corners)


if __name__ == "__main__":
    scanned = scan_document("document.jpg")
    cv2.imshow("Scanned", scanned)
    cv2.waitKey(0)
    cv2.destroyAllWindows()
```

이 구조의 핵심은 "자동 알고리즘이 실패할 수 있다는 사실을 프로그램이 스스로 인지하고, 실패 시 대안 경로를 제공한다"는 것이다. `find_document_corners`가 4개의 점을 찾지 못하면 예외를 던지는 대신 `None`을 반환하도록 설계했기 때문에, 호출하는 쪽에서 실패를 자연스럽게 분기 처리할 수 있다. 또한 `order_points`와 `warp_to_rectangle`은 좌표의 출처(자동 검출이든 수동 클릭이든)를 신경 쓰지 않고 동일하게 동작하므로, 두 경로가 하나의 함수로 자연스럽게 합쳐진다.

## 18.3 성능이라는 두 번째 문제

문서 스캐너가 정확하게 동작하는 것을 확인했다면, 이제 "얼마나 빠르게 동작하는가"를 살펴볼 차례다. `cv2.Canny`, `cv2.findContours`, `cv2.warpPerspective` 같은 OpenCV 함수들은 내부적으로 최적화된 C/C++ 코드로 구현되어 있어 그 자체는 매우 빠르다. 문제는 이런 함수들 "사이"에서 우리가 직접 작성하는 Python 코드다. Python은 인터프리터 언어이기 때문에, 함수 호출 하나하나에 오버헤드가 있고, 특히 픽셀 단위로 반복문을 도는 코드는 같은 연산을 OpenCV/NumPy 함수로 처리하는 것보다 수십~수백 배 느려질 수 있다.

### NumPy 벡터화 vs 순수 `for` 루프: 실측 비교

이미지의 밝기를 50만큼 올리는 간단한 연산을 예로 들어보자. 이 연산은 원리상 "모든 픽셀 값에 50을 더하고, 255를 넘으면 255로 자른다(클리핑)"는 단순한 산술이다. 이를 순수 Python 삼중 `for` 루프로 구현한 버전과, NumPy 벡터화 연산으로 구현한 버전을 `time` 모듈로 직접 측정해 비교해보자.

```python
import cv2
import numpy as np
import time

img = cv2.imread("photo.jpg")
if img is None:
    raise FileNotFoundError("photo.jpg를 찾을 수 없습니다.")

h, w, c = img.shape
print(f"이미지 크기: {w} x {h}, 채널: {c}, 총 픽셀 값 개수: {h * w * c:,}")

# ------------------------------------------------------------------
# 방식 1: 픽셀 단위로 순회하는 순수 Python 삼중 루프
# ------------------------------------------------------------------
src = img.astype(np.int16)  # 오버플로를 피하려고 더 넓은 정수형으로 복사
slow = src.copy()

start = time.perf_counter()
for y in range(h):
    for x in range(w):
        for ch in range(c):
            value = slow[y, x, ch] + 50
            slow[y, x, ch] = 255 if value > 255 else value
loop_time = time.perf_counter() - start
print(f"[루프 방식]      {loop_time:.4f}초")

# ------------------------------------------------------------------
# 방식 2: NumPy 벡터화 연산 (7장에서 다룬 클리핑과 동일한 원리)
# ------------------------------------------------------------------
start = time.perf_counter()
fast = np.clip(src + 50, 0, 255)
vector_time = time.perf_counter() - start
print(f"[벡터화 방식]    {vector_time:.6f}초")

print(f"두 결과가 동일한가? {np.array_equal(slow, fast)}")
print(f"속도 차이: 약 {loop_time / vector_time:.1f}배")
```

두 방식은 완전히 동일한 결과(`np.array_equal`이 `True`)를 만들어내지만, 실행 시간은 극적으로 차이가 난다. 저자의 환경에서 1920×1080 크기의 사진으로 측정했을 때, 순수 Python 루프는 픽셀 값 약 600만 개를 하나씩 순회하느라 수 초가 걸린 반면, `np.clip` 벡터화 연산은 같은 작업을 수 밀리초 안에 끝냈다. 정확한 배율은 하드웨어와 이미지 크기에 따라 달라지지만, **수십 배에서 수백 배 차이가 나는 것은 드문 일이 아니다.**

이 차이가 나는 이유는 다음과 같다.

- **인터프리터 오버헤드**: 순수 Python 루프는 반복마다 인덱싱, 타입 검사, 바이트코드 해석 등 부가 작업을 거친다. 픽셀 수만큼 이 오버헤드가 누적된다.
- **컴파일된 C 반복문**: `np.clip(src + 50, 0, 255)` 같은 NumPy 연산은 내부적으로 미리 컴파일된 C 코드가 배열 전체를 한 번에 순회하며, 이 반복문에는 Python 인터프리터가 개입하지 않는다.
- **메모리 접근 패턴과 SIMD**: NumPy는 연속된 메모리 블록을 효율적으로 순회하고, CPU의 벡터 연산(SIMD) 명령을 활용할 수 있어 같은 반복이라도 훨씬 적은 CPU 사이클로 끝낸다.

Python으로 OpenCV를 쓸 때 지켜야 할 원칙은 단순하다. **"픽셀 단위 반복문을 직접 작성해야 하는 순간이 오면, 먼저 NumPy나 OpenCV 함수로 대체할 방법이 있는지부터 찾아본다."** 7장에서 다룬 산술 연산, 9장의 필터링, 10장의 임계처리 모두 내부적으로 이런 벡터화(또는 그 이상의 최적화)가 적용된 함수들이므로, 가능하면 직접 루프를 짜기보다 이런 함수들을 조합하는 방향으로 설계하는 것이 좋다.

## 18.4 여러 프로세스로 나눠 처리하기: `multiprocessing`

벡터화로 단일 이미지 하나의 처리 속도를 끌어올렸다면, 그다음 단계는 "여러 이미지를 동시에" 처리하는 것이다. 폴더 안에 수백 장의 이미지가 있고 이들을 모두 리사이즈해야 하는 배치 작업을 생각해보자. Python의 표준 라이브러리 `multiprocessing`을 사용하면 이런 작업을 여러 프로세스에 나눠 병렬로 실행할 수 있다.

Python에는 GIL(Global Interpreter Lock)이라는 제약이 있어, 순수 Python 코드는 여러 스레드를 만들어도 동시에 한 스레드만 인터프리터를 실행할 수 있다. `threading` 모듈로는 이 제약 때문에 CPU 연산이 많은 작업의 속도를 온전히 끌어올리기 어렵다. 반면 `multiprocessing`은 완전히 별도의 파이썬 프로세스를 여러 개 띄우기 때문에, 각 프로세스가 독립적인 GIL을 가지고 실제로 여러 CPU 코어에서 동시에 실행된다.

```python
import os
import time
import cv2
from multiprocessing import Pool


def resize_one(args):
    """하나의 이미지를 읽어 리사이즈하고 저장한다. Pool.map에 넘길 함수는
    인자를 하나만 받아야 하므로 튜플로 묶어서 전달한다."""
    src_path, dst_path, size = args
    img = cv2.imread(src_path)
    if img is None:
        return f"[실패] 읽을 수 없음: {src_path}"

    resized = cv2.resize(img, size, interpolation=cv2.INTER_AREA)
    cv2.imwrite(dst_path, resized)
    return f"[완료] {os.path.basename(dst_path)}"


def batch_resize(src_dir, dst_dir, size=(800, 600), workers=4):
    os.makedirs(dst_dir, exist_ok=True)

    filenames = [
        f for f in os.listdir(src_dir)
        if f.lower().endswith((".jpg", ".jpeg", ".png", ".bmp"))
    ]
    tasks = [
        (os.path.join(src_dir, name), os.path.join(dst_dir, name), size)
        for name in filenames
    ]

    if not tasks:
        print("처리할 이미지가 없습니다.")
        return

    start = time.perf_counter()
    with Pool(processes=workers) as pool:
        results = pool.map(resize_one, tasks)
    elapsed = time.perf_counter() - start

    for r in results:
        print(r)
    print(f"\n총 {len(tasks)}개 이미지 처리, {workers}개 프로세스, {elapsed:.2f}초 소요")


# Windows에서는 멀티프로세싱이 자식 프로세스에서 이 스크립트를 다시 임포트하므로,
# 프로세스 생성 코드는 반드시 이 가드 안에 있어야 한다. 이 가드가 없으면
# 프로세스가 무한히 재귀적으로 생성되거나 RuntimeError가 발생할 수 있다.
if __name__ == "__main__":
    batch_resize("input_images", "output_images", size=(800, 600), workers=4)
```

`if __name__ == "__main__":` 가드는 특히 Windows 환경에서 필수적이다. Windows는 `fork` 대신 `spawn` 방식으로 자식 프로세스를 만드는데, 이 과정에서 스크립트 파일 자체를 다시 임포트한다. 만약 `Pool(...)`을 호출하는 코드가 이 가드 밖에 있다면, 자식 프로세스가 스크립트를 재실행할 때마다 또 새로운 `Pool`을 만들려고 시도해 오류가 나거나 무한히 프로세스를 늘리는 문제가 생긴다.

병렬화의 효과를 직접 체감해보려면, 단일 프로세스(`workers=1`)로 실행했을 때와 여러 프로세스(`workers=4` 등)로 실행했을 때의 시간을 함께 측정해 비교해보면 된다.

```python
if __name__ == "__main__":
    for n_workers in (1, 2, 4, 8):
        start = time.perf_counter()
        batch_resize("input_images", "output_images", size=(800, 600), workers=n_workers)
        print(f"workers={n_workers}: 총 {time.perf_counter() - start:.2f}초\n")
```

여기서 주의할 점이 있다. 프로세스 개수를 늘린다고 항상 그에 비례해 빨라지는 것은 아니다. 늘어나는 프로세스 수는 실제 CPU 코어 수를 넘는 순간부터 이득이 줄어들고, 각 이미지의 읽기/쓰기 같은 디스크 입출력(I/O) 비중이 크다면 CPU 병렬화의 효과가 상대적으로 희석된다. 또한 프로세스를 새로 띄우는 것 자체에도 약간의 오버헤드가 있으므로, 처리할 이미지 수가 매우 적을 때는 오히려 단일 프로세스가 더 빠를 수도 있다. 실제 작업량과 하드웨어에 맞춰 워커 개수를 실험적으로 정하는 것이 좋다.

> 참고로 `cv2.resize`, `cv2.GaussianBlur`처럼 무거운 연산을 수행하는 OpenCV 함수 중 다수는 내부적으로 GIL을 잠시 해제하고 실행되도록 구현되어 있다. 즉 OpenCV 연산 자체는 `threading`으로도 어느 정도 병렬성을 얻을 수 있는 경우가 있지만, 파일 읽기/쓰기나 순수 Python 로직이 섞인 배치 작업 전체를 안정적으로 병렬화하려면 `multiprocessing`이 더 예측 가능하고 확실한 선택이다.

### OpenCV 내부의 병렬성: `cv2.setNumThreads`

지금까지 살펴본 `multiprocessing`은 우리가 작성한 Python 코드를 여러 프로세스로 나누는 방법이었다. 이와는 별개로, OpenCV 라이브러리 자체도 `GaussianBlur`, `resize`처럼 무거운 함수 내부에서 여러 스레드를 사용해 연산을 자동으로 병렬화하고 있다. 이 내부 스레드 수는 다음 함수로 확인하고 조정할 수 있다.

```python
import cv2

print("현재 OpenCV가 내부적으로 사용하는 스레드 수:", cv2.getNumThreads())

# 스레드를 하나로 제한하면 OpenCV 함수 하나의 실행은 느려지지만,
# multiprocessing으로 여러 프로세스를 동시에 띄울 때 프로세스끼리
# CPU를 두고 경쟁하는 것을 막을 수 있어 전체 처리량이 오히려 좋아지는 경우가 있다.
cv2.setNumThreads(1)
```

`multiprocessing.Pool`로 여러 워커 프로세스를 띄우면서 각 프로세스 안의 OpenCV 함수도 동시에 여러 스레드를 쓰게 두면, 실제 CPU 코어 수보다 훨씬 많은 스레드가 서로 자원을 다투게 되어 오히려 전체 속도가 떨어지는 경우가 있다. 이런 상황이 의심되면 배치 작업을 시작하기 전에 각 워커에서 `cv2.setNumThreads(1)`을 호출해 OpenCV 내부 병렬성을 끄고, 병렬화는 `multiprocessing` 쪽에만 맡기는 방식을 실험해볼 만하다. 반대로 워커 프로세스 수를 적게 유지하면서 각 프로세스가 OpenCV 내부 스레드를 충분히 활용하게 두는 조합이 더 나은 경우도 있으므로, 두 축(프로세스 수 × OpenCV 스레드 수)을 함께 실험해보는 것이 정확한 결론에 도달하는 길이다.

OpenCV가 내부적으로 SIMD·병렬화 최적화를 사용하는지 여부는 `cv2.useOptimized()`로 확인할 수 있고, 디버깅 목적으로 이 최적화를 끄고 성능을 비교해보고 싶다면 `cv2.setUseOptimized(False)`로 끌 수도 있다(일반적인 사용에서는 항상 켜진 상태로 두는 것이 좋다).

## 18.5 더 가속하려면: Numba와 Cython

`multiprocessing`으로 여러 이미지를 동시에 처리하는 것과, 벡터화로 이미지 하나를 빠르게 처리하는 것을 결합해도 여전히 순수 Python 루프로만 표현해야 하는 복잡한 픽셀별 로직이 남는 경우가 있다. 이런 경우 실무에서는 흔히 다음 두 가지 도구를 추가로 검토한다.

- **Numba**: `@numba.jit` 데코레이터를 함수에 붙이는 것만으로 그 함수를 실행 시점에 기계어로 컴파일해주는 라이브러리다. 코드를 거의 그대로 유지하면서 순수 Python 루프를 크게 가속할 수 있어 진입 장벽이 낮다.
- **Cython**: Python과 유사한 문법에 타입 선언을 추가해 C 코드로 변환·컴파일하는 언어 및 컴파일러다. 성능은 Numba보다도 더 세밀하게 끌어올릴 수 있지만, 별도의 빌드 과정이 필요해 진입 장벽이 상대적으로 높다.

두 도구 모두 "NumPy 벡터화로도 표현하기 어려운 픽셀별 순차 로직"을 가속해야 할 때 고려할 만한 다음 단계이며, 이 책에서 다루는 범위를 넘어서므로 이름과 용도만 기억해두자.

## 18.6 성능 정리: Python에서 OpenCV를 빠르게 쓰는 세 가지 층위

지금까지 살펴본 성능 최적화 방법들을 계층적으로 정리하면 다음과 같다.

| 층위 | 방법 | 언제 쓰는가 |
|---|---|---|
| 1. 알고리즘/함수 선택 | OpenCV·NumPy가 제공하는 벡터화 함수를 최대한 활용 | 항상 최우선으로 검토 |
| 2. 단일 이미지 내부 가속 | 픽셀 루프가 꼭 필요하면 Numba/Cython 검토 | 벡터화로 표현할 수 없는 순차 로직이 남을 때 |
| 3. 여러 이미지 간 병렬화 | `multiprocessing`으로 여러 프로세스에 작업 분산 | 처리할 이미지·영상이 다수이고 독립적으로 처리 가능할 때 |

세 층위는 서로 배타적이지 않고 함께 적용할 수 있다. 예를 들어 각 이미지를 벡터화된 연산으로 빠르게 처리하는 함수를 만들고, 그 함수를 다시 `multiprocessing.Pool`로 여러 이미지에 병렬 적용하는 방식이 실무에서 흔히 쓰는 조합이다.

## 18.7 메모리 관리: Python에서는 무엇을 신경 써야 할까

Python에서 OpenCV의 이미지(NumPy 배열)는 참조 카운팅과 가비지 컬렉터(GC)에 의해 자동으로 회수된다. 개발자가 명시적으로 메모리를 해제할 일은 거의 없다. 다만 대량의 고해상도 이미지를 순차적으로 처리하는 프로그램에서는 다음과 같은 점을 의식하면 도움이 된다.

- **불필요하게 오래 참조를 들고 있지 않기**: 리스트나 딕셔너리에 대용량 이미지를 계속 누적해서 담아두면, 그 컨테이너가 살아있는 동안 GC가 이미지를 회수하지 못한다. 처리가 끝난 이미지는 변수 스코프를 벗어나게 하거나 `del` 문으로 참조를 명시적으로 끊어주는 것이 좋다.
- **뷰(view)와 복사(copy)의 구분**: 18.1~18.2절에서 본 것처럼 슬라이싱은 새 메모리를 할당하지 않고 원본을 참조하는 뷰를 만든다. 원본과 독립된 데이터가 필요할 때만 `.copy()`를 호출하고, 그렇지 않은 곳에서는 불필요한 복사를 피하는 것이 메모리와 속도 모두에 유리하다.
- **`multiprocessing` 사용 시 메모리 중복**: 여러 프로세스를 띄우면 각 프로세스가 독립된 메모리 공간을 가지므로, 큰 데이터를 여러 워커에 그대로 전달하면 그만큼 메모리 사용량이 곱절로 늘어날 수 있다. 이미지 배치 처리처럼 각 워커가 파일 경로만 받아 자신이 직접 읽어들이는 방식(18.4절 예제처럼)이 메모리 중복을 최소화하는 데 유리하다.

## 18.9 앞으로 더 공부할 방향

이 책은 OpenCV의 전통적인 이미지 처리 기법을 중심으로 다뤘지만, 컴퓨터 비전 분야는 이보다 훨씬 넓다. 다음 방향들을 이어서 살펴보면 좋다.

- **딥러닝 기반 객체 검출/세그멘테이션**: YOLO, SSD, Mask R-CNN 계열의 모델들은 17장에서 다룬 `cv2.dnn` 모듈이나, `ultralytics` 같은 Python 패키지, ONNX Runtime, TensorRT 등 전용 런타임을 통해 실제 서비스에 적용할 수 있다. 객체의 위치뿐 아니라 픽셀 단위로 영역을 구분하는 세그멘테이션까지 다루는 모델도 많다.
- **GPU 가속**: OpenCV는 CUDA 지원 빌드를 통해 `cv2.cuda` 네임스페이스의 함수들로 NVIDIA GPU에서 연산을 가속할 수 있고, `cv2.UMat`을 활용한 OpenCL 기반 투명 가속(Transparent API)도 지원한다. 대량의 이미지나 고해상도 비디오를 실시간으로 처리해야 한다면 이 방향을 검토할 만하다.
- **실시간 트래킹 알고리즘**: 이 책의 16장에서는 프레임 간 배경 제거를 다뤘지만, 특정 객체를 프레임마다 계속 추적하는 것은 별도의 문제다. `cv2.TrackerCSRT_create()`, `cv2.TrackerKCF_create()` 같은 OpenCV 내장 트래커부터, 딥러닝 기반 검출과 결합한 DeepSORT 같은 다중 객체 추적 기법까지 다양한 선택지가 있다.
- **모델 서빙과 배포**: 학습된 모델을 실제 서비스에 연결하려면 Flask/FastAPI 같은 웹 프레임워크로 추론 API를 감싸거나, 엣지 디바이스에 최적화된 형태(ONNX, TensorRT, OpenVINO 등)로 변환하는 과정이 필요하다. 이 책에서 다룬 전처리·후처리 감각은 이런 배포 단계에서도 그대로 유용하다.

이 책에서 다진 기초—이미지가 배열이라는 감각, 각 처리 단계가 무엇을 입력받고 무엇을 내놓는지에 대한 이해, 자동화가 실패하는 지점을 예상하고 대비하는 습관, 그리고 "느리면 벡터화를, 그래도 부족하면 병렬화를 먼저 검토한다"는 성능 원칙—은 이런 더 발전된 주제들을 공부할 때도 그대로 밑바탕이 되어줄 것이다.

- Python에서는 픽셀 단위 `for` 루프 대신 NumPy 벡터화 연산을 쓰는 것이 성능에 결정적이며, `time` 모듈로 직접 측정해보면 같은 연산이라도 수십~수백 배의 실행 시간 차이가 날 수 있다.
- 여러 이미지를 독립적으로 처리해야 하는 배치 작업은 `multiprocessing.Pool`로 여러 프로세스에 나눠 병렬 처리할 수 있으며, Windows에서는 `if __name__ == "__main__":` 가드가 필수적이다.
- NumPy 벡터화와 `multiprocessing`으로도 부족하면 Numba나 Cython으로 순수 Python 루프 자체를 컴파일해 가속하는 다음 단계가 있다.
- 이미지(NumPy 배열)는 Python의 가비지 컬렉션으로 자동 관리되지만, 불필요한 참조를 오래 들고 있지 않는 것, 뷰와 복사를 구분하는 것, 멀티프로세싱 시 메모리 중복을 의식하는 것이 대량 이미지 처리에서 중요하다.
- 딥러닝 기반 검출/세그멘테이션, GPU 가속, 실시간 트래킹, 모델 서빙은 이 책의 범위를 넘어서는 다음 학습 주제로 이어진다.

## 연습문제

1. 문서 스캐너 예제에서 `cv2.Canny`의 두 임계값(75, 200)을 다른 값으로 바꿔보고, 문서 경계 검출이 실패하는 조명 조건이나 배경을 찾아 원인을 분석해 보라. 자동 검출이 실패했을 때 18.2절의 마우스 클릭 폴백이 정상적으로 동작하는지도 함께 확인해 보라.
2. 18.2절의 `get_manual_corners`에서 사용자가 네 점을 반드시 좌상단부터 순서대로 클릭하지 않고 임의의 순서로 클릭해도, `order_points` 함수가 여전히 올바르게 top-left/top-right/bottom-right/bottom-left로 정렬해내는지 테스트해 보라.
3. 18.3절의 밝기 조정 예제를 참고하여, 이번에는 대비(contrast)를 조정하는 곱셈 연산(`pixel * 1.5`)에 대해서도 순수 `for` 루프와 NumPy 벡터화 버전의 실행 시간을 각각 측정하고 비교해 보라.
4. 18.4절의 `batch_resize`를 workers=1, 2, 4, 8로 각각 실행해 총 처리 시간을 측정하고, 자신의 컴퓨터의 CPU 코어 수와 비교했을 때 어느 지점부터 병렬화의 이득이 줄어드는지 분석해 보라.
5. `numba`를 설치한 뒤 `@numba.jit(nopython=True)` 데코레이터를 밝기 조정 루프 함수에 붙여보고, 순수 Python 루프·Numba 가속 루프·NumPy 벡터화, 이렇게 세 가지 방식의 실행 시간을 함께 비교해 보라.

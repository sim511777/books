# 16장. 다양한 렌더링 백엔드

[◀ 이전: 15장. 플롯과 데이터 시각화(ImPlot)](ch15-플롯과데이터시각화.md) | [📖 목차](00-목차.md) | [다음: 17장. 성능 최적화와 디버깅 ▶](ch17-성능최적화와디버깅.md)


2장에서 우리는 GLFW로 창을 열고 OpenGL3로 그림을 그리는 조합을 선택해 개발 환경을 꾸렸습니다. 그 이후로 이 책의 모든 예제는 이 조합 위에서 동작해 왔습니다. 그런데 실무에서는 항상 GLFW와 OpenGL을 쓸 수 있는 것은 아닙니다. 윈도우 전용 애플리케이션을 Win32 API로 직접 만들 수도 있고, 크로스 플랫폼 게임에 SDL2를 쓸 수도 있으며, 성능이 중요한 프로젝트라면 DirectX 12나 Vulkan 같은 저수준 그래픽 API를 이미 쓰고 있을 수도 있습니다. 이번 장에서는 Dear ImGui가 이런 다양한 환경에 맞춰 어떻게 유연하게 조합될 수 있는지 살펴봅니다.

## 16.1 백엔드는 왜 두 개로 나뉘어 있는가

2장의 초기화 코드를 다시 떠올려 보겠습니다.

```cpp
ImGui::CreateContext();
ImGui_ImplGlfw_InitForOpenGL(window, true);
ImGui_ImplOpenGL3_Init("#version 130");
```

여기서 `ImGui_ImplGlfw_*`와 `ImGui_ImplOpenGL3_*`, 이름이 다른 두 종류의 함수가 호출되고 있다는 점에 주목해 봅시다. 이것은 우연이 아니라 Dear ImGui의 설계 원칙을 그대로 드러내는 부분입니다. Dear ImGui는 GUI를 그리기 위해 필요한 일을 크게 두 가지로 나눕니다.

- **플랫폼 백엔드(platform backend)**: 운영체제 창, 마우스와 키보드 입력, 클립보드, 프레임 시간처럼 "운영체제 및 창 시스템과 대화하는" 부분을 담당합니다. `imgui_impl_glfw`가 이 역할을 맡고 있습니다.
- **렌더러 백엔드(renderer backend)**: Dear ImGui가 만들어 낸 정점과 인덱스 데이터를 실제 GPU 명령으로 변환해 화면에 그리는 부분을 담당합니다. `imgui_impl_opengl3`이 이 역할을 맡고 있습니다.

Dear ImGui 코어 자체는 창이 어떻게 열리는지도, 그림이 어떤 그래픽 API로 그려지는지도 전혀 알지 못합니다. 코어가 하는 일은 오직 위젯의 상태를 계산하고, 그 결과를 `ImDrawList`라는 그리기 명령 목록(정점 좌표, 색상, 텍스처, 인덱스)으로 만들어 내는 것뿐입니다. 이 목록을 실제 픽셀로 바꾸는 일은 렌더러 백엔드가, 입력을 모아 Dear ImGui에 전달하는 일은 플랫폼 백엔드가 나누어 맡습니다. 11장에서 `ImDrawList`를 직접 다뤄 보았다면, 이 구조가 어색하지 않게 느껴질 것입니다. 결국 위젯이든 우리가 직접 그린 도형이든 최종적으로는 같은 그리기 명령 목록에 쌓이고, 같은 렌더러 백엔드를 통해 화면에 도달합니다.

이렇게 역할이 분리되어 있기 때문에, 플랫폼 백엔드와 렌더러 백엔드는 서로 독립적으로 교체할 수 있습니다. "어떤 창 시스템을 쓰는가"와 "어떤 그래픽 API로 그리는가"는 원칙적으로 아무 상관이 없는 두 가지 선택지이기 때문입니다.

## 16.2 플랫폼 백엔드의 종류

Dear ImGui 저장소의 `backends/` 폴더에는 여러 플랫폼 백엔드가 함께 배포됩니다. 지금까지 사용해 온 `imgui_impl_glfw` 외에 대표적인 것들을 소개합니다.

- **SDL2** (`imgui_impl_sdl2`): SDL2는 GLFW와 마찬가지로 크로스 플랫폼 창/입력 라이브러리입니다. 이미 SDL2로 창과 게임 루프를 관리하고 있는 프로젝트라면, GLFW를 새로 도입하는 대신 이 백엔드를 사용해 자연스럽게 통합할 수 있습니다. SDL을 이용한 게임이나 미디어 플레이어에 디버그 UI를 얹을 때 흔히 선택됩니다.
- **Win32 네이티브** (`imgui_impl_win32`): 크로스 플랫폼 라이브러리를 거치지 않고 윈도우 API(`CreateWindowEx`, 메시지 루프 등)를 직접 사용하는 애플리케이션을 위한 백엔드입니다. 이미 Win32 기반의 윈도우 프로시저를 갖춘 기존 데스크톱 프로그램에 Dear ImGui를 얹고 싶을 때, 별도의 창 라이브러리를 추가하지 않고도 연동할 수 있습니다.

두 백엔드 모두 이름과 함수 시그니처가 GLFW 백엔드와 유사한 패턴을 따릅니다. 예를 들어 `ImGui_ImplGlfw_InitForOpenGL()`에 대응하는 함수가 SDL2에는 `ImGui_ImplSDL2_InitForOpenGL()`, Win32에는 `ImGui_ImplWin32_Init()`이라는 이름으로 존재합니다. 매 프레임 `ImGui_ImplGlfw_NewFrame()`을 호출했던 자리에도 마찬가지로 `ImGui_ImplSDL2_NewFrame()`, `ImGui_ImplWin32_NewFrame()`을 호출하면 됩니다. 즉 백엔드의 이름만 바뀔 뿐, 2장에서 익힌 "초기화 한 번, 매 프레임 NewFrame 호출"이라는 흐름 자체는 그대로 유지됩니다.

## 16.3 렌더러 백엔드의 종류

렌더러 백엔드 쪽도 마찬가지로 여러 선택지가 있습니다. 우리가 써 온 `imgui_impl_opengl3` 외에 대표적인 것들입니다.

- **DirectX 11 / 12** (`imgui_impl_dx11` / `imgui_impl_dx12`): 윈도우 게임이나 툴에서 흔히 쓰이는 마이크로소프트의 그래픽 API입니다. DX11 백엔드는 비교적 단순한 API 위에서 동작하고, DX12 백엔드는 커맨드 리스트와 디스크립터 힙처럼 저수준 개념을 직접 다루어야 하는 대신 더 세밀한 제어와 성능을 제공합니다.
- **Vulkan** (`imgui_impl_vulkan`): 여러 플랫폼에서 동작하는 저수준 그래픽 API입니다. DX12와 마찬가지로 렌더 패스, 파이프라인, 디스크립터 셋 같은 개념을 애플리케이션이 직접 관리해야 하므로, 초기화 코드가 OpenGL3 백엔드보다 다소 길고 명시적입니다.

렌더러 백엔드가 달라져도 우리가 매 프레임 작성하는 위젯 코드, 즉 `ImGui::Begin()`, `ImGui::Button()`, `ImGui::SliderFloat()` 같은 호출들은 단 한 줄도 바뀌지 않습니다. 바뀌는 부분은 오직 초기화 시점의 `ImGui_Impl*_Init()` 호출과, 렌더링 단계의 `ImGui_Impl*_NewFrame()` / `ImGui_Impl*_RenderDrawData()` 호출뿐입니다. 이것이 백엔드 분리 구조가 주는 가장 실질적인 이점입니다. 4장부터 15장까지 배운 모든 위젯과 패턴은 어떤 렌더러를 쓰든 그대로 재사용됩니다.

## 16.4 플랫폼과 렌더러는 자유롭게 조합된다

가장 중요한 지점은 플랫폼 백엔드와 렌더러 백엔드가 서로 독립적인 축이라는 것입니다. 다음과 같은 조합이 모두 가능합니다.

| 플랫폼 백엔드 | 렌더러 백엔드 | 예시 상황 |
|---|---|---|
| GLFW | OpenGL3 | 이 책에서 사용한 조합, 크로스 플랫폼 데스크톱 도구 |
| GLFW | Vulkan | 크로스 플랫폼을 유지하면서 저수준 API 성능이 필요한 경우 |
| Win32 | DirectX 11 | 윈도우 전용 데스크톱 애플리케이션 |
| SDL2 | DirectX 12 | SDL로 창/입력을 관리하면서 최신 그래픽 API를 쓰는 윈도우 게임 |

예를 들어 Win32 창 위에 DirectX 11로 그리고 싶다면, 초기화 코드는 다음과 같은 형태가 됩니다. 2장에서 작성했던 GLFW + OpenGL3 초기화 코드와 나란히 비교해 보면 구조가 거의 동일하다는 것을 알 수 있습니다.

```cpp
// GLFW + OpenGL3 (2장에서 사용한 조합)
ImGui::CreateContext();
ImGui_ImplGlfw_InitForOpenGL(window, true);
ImGui_ImplOpenGL3_Init("#version 130");

// ...

// Win32 + DirectX 11 (동일한 구조, 백엔드만 교체)
ImGui::CreateContext();
ImGui_ImplWin32_Init(hwnd);
ImGui_ImplDX11_Init(g_pd3dDevice, g_pd3dDeviceContext);
```

매 프레임 반복되는 루프 안에서도 마찬가지로 대응 관계가 유지됩니다.

```cpp
// GLFW + OpenGL3
ImGui_ImplOpenGL3_NewFrame();
ImGui_ImplGlfw_NewFrame();
ImGui::NewFrame();
// ... 위젯 코드 (변경 없음) ...
ImGui::Render();
ImGui_ImplOpenGL3_RenderDrawData(ImGui::GetDrawData());

// Win32 + DirectX 11
ImGui_ImplDX11_NewFrame();
ImGui_ImplWin32_NewFrame();
ImGui::NewFrame();
// ... 위젯 코드 (변경 없음) ...
ImGui::Render();
ImGui_ImplDX11_RenderDrawData(ImGui::GetDrawData());
```

플랫폼 백엔드 함수와 렌더러 백엔드 함수의 이름만 바뀌었을 뿐, 호출 순서와 역할 분담은 완전히 동일합니다. 이것이 "이름 짓는 패턴이 백엔드마다 비슷하다"는 말의 실질적인 의미입니다. 어떤 조합을 고르더라도 초기화, 프레임 시작, 위젯 작성, 렌더링이라는 네 단계 구조 자체는 흔들리지 않습니다. 새로운 백엔드로 옮겨갈 때 익혀야 할 것은 사실상 `Init`, `NewFrame`, `RenderDrawData`, 그리고 종료 시의 `Shutdown` 함수 이름뿐입니다.

이렇게 조합이 자유로운 이유는 결국 16.1절에서 설명한 역할 분리 덕분입니다. 플랫폼 백엔드는 입력을 모아 `ImGuiIO`에 채워 넣는 일만 하고, 렌더러 백엔드는 `ImGui::GetDrawData()`가 반환하는 그리기 명령을 소비하는 일만 합니다. 두 백엔드는 서로의 존재를 몰라도 되고, Dear ImGui 코어를 매개로만 간접적으로 연결되어 있습니다.

## 16.5 자체 렌더러를 가진 게임 엔진에 통합하기

지금까지 소개한 백엔드들은 모두 공식 저장소에서 바로 가져다 쓸 수 있는 기성품입니다. 하지만 이미 자체적인 렌더링 파이프라인을 갖춘 게임 엔진이나 애플리케이션 프레임워크에 Dear ImGui를 넣고 싶다면 이야기가 조금 달라집니다. 이런 경우 두 가지 선택지가 있습니다.

첫째, 엔진이 내부적으로 표준 그래픽 API(DirectX, Vulkan, OpenGL 등)를 사용하고 있고 그 API에 직접 접근할 수 있다면, 앞서 소개한 공식 렌더러 백엔드를 그대로 가져와 엔진의 렌더링 루프 어딘가에 `RenderDrawData()` 호출 한 번을 끼워 넣는 정도로 통합이 끝나는 경우가 많습니다.

둘째, 엔진이 자체적인 커스텀 렌더링 추상화 계층을 가지고 있어서 표준 백엔드를 그대로 꽂을 수 없다면, `ImGui::GetDrawData()`가 반환하는 `ImDrawData` 구조체(정점 버퍼, 인덱스 버퍼, 텍스처 정보, 클리핑 사각형 등)를 직접 읽어서 엔진의 렌더링 API 호출로 변환하는 통합 코드를 손수 작성해야 합니다. 11장에서 살펴본 `ImDrawList`의 정점·인덱스 구조를 이해하고 있다면, 이 작업은 기존 백엔드 소스 코드(예를 들어 `imgui_impl_opengl3.cpp`)를 참고 삼아 비교적 수월하게 진행할 수 있습니다. 실제로 상용 게임 엔진들이 Dear ImGui를 에디터나 디버그 UI로 채택할 때 흔히 이런 방식의 자체 통합 레이어를 작성합니다.

## 요약

- Dear ImGui는 플랫폼 백엔드(입력·창 관리)와 렌더러 백엔드(GPU 렌더링)를 분리된 두 계층으로 설계했으며, 이 책은 GLFW + OpenGL3 조합을 사용해 왔습니다.
- 대표적인 플랫폼 백엔드로 SDL2(`imgui_impl_sdl2`), Win32 네이티브(`imgui_impl_win32`)가 있으며, GLFW 백엔드와 유사한 `Init` / `NewFrame` 함수 이름 패턴을 공유합니다.
- 대표적인 렌더러 백엔드로 DirectX 11/12(`imgui_impl_dx11`/`imgui_impl_dx12`), Vulkan(`imgui_impl_vulkan`)이 있으며, 모두 `Init` / `NewFrame` / `RenderDrawData` 구조를 공유합니다.
- 플랫폼 백엔드와 렌더러 백엔드는 서로 독립적으로 조합할 수 있습니다(Win32 + DirectX11, GLFW + Vulkan 등). 위젯 코드는 어떤 조합을 쓰든 변경할 필요가 없습니다.
- 자체 렌더러를 가진 게임 엔진에 통합할 때는 표준 백엔드를 그대로 붙이거나, `ImDrawData`를 직접 읽어 엔진의 렌더링 API로 변환하는 통합 코드를 작성해야 합니다.

## 연습문제

1. 플랫폼 백엔드와 렌더러 백엔드가 각각 어떤 책임을 지는지, `ImGuiIO`와 `ImDrawData`를 예로 들어 설명해 보세요.
2. `imgui_impl_sdl2`와 `imgui_impl_win32`는 각각 어떤 상황에서 선택하는 것이 자연스러운지 비교해 보세요.
3. GLFW + OpenGL3 조합을 GLFW + Vulkan 조합으로 바꾼다면, 2장의 초기화 코드에서 구체적으로 어떤 두 함수 호출이 바뀌어야 하는지 적어 보세요.
4. 자체 렌더링 파이프라인을 가진 가상의 게임 엔진에 Dear ImGui를 통합해야 한다고 가정하고, `ImDrawData`에서 어떤 정보를 읽어 엔진의 드로우 콜로 변환해야 할지 목록을 만들어 보세요.
5. 11장에서 다룬 `ImDrawList`의 구조 지식이 16.5절의 자체 통합 작업에 왜 도움이 되는지 설명해 보세요.

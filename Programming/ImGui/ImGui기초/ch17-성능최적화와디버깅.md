# 17장. 성능 최적화와 디버깅

[◀ 이전: 16장. 다양한 렌더링 백엔드](ch16-다양한렌더링백엔드.md) | [📖 목차](00-목차.md) | [다음: 18장. 실전 프로젝트: 설정 에디터 만들기 ▶](ch18-실전프로젝트설정에디터.md)


지금까지 여러 장에 걸쳐 다양한 위젯과 기법을 익혔습니다. 이쯤에서 한 가지 의문이 들 법합니다. "매 프레임마다 UI 코드를 처음부터 다시 실행한다"는 즉시 모드의 방식이 과연 성능에 부담을 주지는 않을까 하는 것입니다. 이번 장에서는 이 질문에 답하기 위해 ImGui가 내장하고 있는 두 가지 진단 도구, 즉 데모 창과 메트릭 창을 살펴보고, 실전에서 정말로 주의해야 할 성능 포인트가 무엇인지 짚어봅니다. 그리고 초보자가 가장 자주 걸려 넘어지는 세 가지 실수도 함께 정리합니다.

## ImGui 데모 창: 최고의 참고서

Dear ImGui를 내려받으면 라이브러리 소스와 함께 `imgui_demo.cpp`라는 파일이 딸려 옵니다. 이 파일 하나를 호출하는 것만으로 ImGui가 제공하는 거의 모든 위젯과 기능을 한 화면에서 확인할 수 있는 데모 창이 열립니다.

```cpp
ImGui::ShowDemoWindow();
```

이 한 줄을 메인 루프 안에 넣기만 하면 됩니다. 열리는 창에는 기본 위젯, 레이아웃, 팝업, 도킹, 플롯, 커스텀 렌더링에 이르기까지 이 책에서 다룬(그리고 아직 다루지 않은) 거의 모든 기능이 실제로 동작하는 예제와 함께 나열되어 있습니다. 각 섹션은 접이식 헤더로 구분되어 있어서 필요한 부분만 펼쳐서 확인할 수 있습니다.

이 데모 창을 단순히 "구경하는 용도"로만 여기지 않는 것이 중요합니다. **`imgui_demo.cpp`의 소스 코드 자체가 각 위젯을 어떻게 호출해야 하는지 보여주는 가장 정확하고 최신 상태의 예제 모음**입니다. 새로운 위젯을 배우고 싶을 때, 또는 이 책에서 설명한 API가 실제로 어떤 매개변수 조합으로 쓰이는지 확인하고 싶을 때는 언제든 이 파일을 열어 관련 섹션을 검색해보는 습관을 들이는 것을 권합니다. 공식 문서보다도 오히려 더 실전적인 경우가 많은데, 함수 시그니처가 버전마다 조금씩 바뀌어도 데모 코드는 항상 그 버전에 맞게 관리되기 때문입니다.

```cpp
// 개발 빌드에서는 디버그 메뉴 등에 데모 창 토글을 심어두는 것이 일반적입니다.
static bool show_demo = false;

if (ImGui::BeginMainMenuBar())
{
    if (ImGui::BeginMenu("도움말"))
    {
        ImGui::MenuItem("ImGui 데모", nullptr, &show_demo);
        ImGui::EndMenu();
    }
    ImGui::EndMainMenuBar();
}

if (show_demo)
    ImGui::ShowDemoWindow(&show_demo);
```

`ShowDemoWindow()`는 `bool*`을 인자로 받아, 창 닫기 버튼을 눌렀을 때 그 변수를 `false`로 바꿔줍니다. 이는 5장에서 배운 "닫기 가능한 창" 패턴과 정확히 같습니다.

## 메트릭/디버거 창: 지금 무슨 일이 일어나고 있는가

`ImGui::ShowDemoWindow()`가 "무엇을 만들 수 있는가"를 보여준다면, `ImGui::ShowMetricsWindow()`는 "지금 내 애플리케이션 안에서 실제로 무슨 일이 벌어지고 있는가"를 보여주는 진단 도구입니다.

```cpp
ImGui::ShowMetricsWindow();
```

메트릭 창을 열면 다음과 같은 정보를 실시간으로 확인할 수 있습니다.

- **렌더링 통계**: 이번 프레임에 생성된 정점(vertex) 수, 인덱스 수, 드로우 콜(draw call) 수. 위젯이 늘어날수록 이 수치가 어떻게 증가하는지 눈으로 확인할 수 있습니다.
- **창 목록**: 현재 존재하는 모든 ImGui 창의 목록과 각 창의 크기, 위치, 상태(보이는지, 접혀 있는지 등)를 트리 형태로 볼 수 있습니다. 항목을 클릭하면 해당 창의 경계가 화면에 노란색 사각형으로 강조 표시되어, "이 사각형이 도대체 어느 창이지?"라는 의문을 바로 해결해줍니다.
- **활성 위젯 정보**: 현재 마우스에 의해 호버(hover)되고 있는 위젯, 활성화(active)되어 입력을 받고 있는 위젯, 포커스를 가진 위젯이 각각 무엇인지, 그리고 그 위젯의 ID가 무엇인지 표시됩니다. ID 충돌 같은 문제를 추적할 때 특히 유용합니다.
- **입력/도킹 상태**: 마우스 좌표, 키보드 입력 상태, 도킹 노드 구조 등 프레임워크 내부 상태 전반을 들여다볼 수 있습니다.

이 창은 "위젯이 원하는 곳에 그려지지 않는다", "클릭이 먹히지 않는다", "레이아웃이 이상하게 겹친다" 같은 문제를 디버깅할 때 첫 번째로 열어봐야 할 도구입니다. 특히 창 목록에서 항목에 마우스를 올렸을 때 화면에 나타나는 강조 사각형은, 여러 창이 겹쳐 있는 복잡한 레이아웃에서 "지금 이 부분을 그리고 있는 게 어느 창인지" 파악하는 데 매우 효과적입니다.

```cpp
static bool show_metrics = false;

if (ImGui::BeginMenu("도움말"))
{
    ImGui::MenuItem("메트릭/디버거", nullptr, &show_metrics);
    ImGui::EndMenu();
}

if (show_metrics)
    ImGui::ShowMetricsWindow(&show_metrics);
```

데모 창과 메트릭 창 모두 개발 빌드에서만 켜두고 배포 빌드에서는 아예 호출하지 않도록 전처리기 매크로(`#ifdef _DEBUG` 등)로 감싸두는 것이 일반적인 관례입니다.

## 즉시 모드는 정말 느릴까

"매 프레임마다 모든 UI 코드를 다시 실행한다"는 말을 처음 들으면 직관적으로 비효율적으로 느껴지기 쉽습니다. 하지만 실제로는 그렇지 않은 경우가 대부분입니다. 그 이유를 짚어보겠습니다.

**위젯 함수 자체는 매우 가볍게 설계되어 있습니다.** `ImGui::Button()`이나 `ImGui::Text()` 같은 함수가 하는 일은 텍스트 크기를 계산하고, 클릭 판정을 위한 사각형 영역을 확인하고, 정점 몇 개를 드로우 리스트에 추가하는 정도입니다. 객체를 새로 생성(`new`)하거나 힙 할당을 빈번하게 일으키는 무거운 작업이 아닙니다. ImGui 내부는 대부분의 상태를 스택 기반의 배열이나 재사용 가능한 버퍼에 담아 처리하도록 설계되어 있어서, 프레임마다 수백 개의 위젯을 호출해도 대개는 1밀리초 남짓의 시간 안에 처리됩니다. "즉시 모드 = 느림"이라는 등식은 성립하지 않습니다.

**진짜 위험한 것은 위젯 함수가 아니라, 그 위젯을 그리기 위해 UI 코드 안에 직접 박아 넣은 무거운 연산입니다.** 다음 코드를 봅시다.

```cpp
// 이렇게 쓰면 안 됩니다: 매 프레임 파일을 다시 읽고 다시 정렬합니다.
void DrawFileList()
{
    std::vector<std::string> files = ReadDirectoryFromDisk("assets/");
    std::sort(files.begin(), files.end());

    for (const auto& f : files)
        ImGui::Text("%s", f.c_str());
}
```

이 함수는 위젯을 그리는 것과 무관한 "파일 시스템 조회"와 "정렬"이라는 무거운 연산을 매 프레임 반복합니다. 프레임이 초당 60번, 많게는 수백 번 호출되는 렌더 루프 안에서 디스크 I/O나 O(n log n) 정렬을 매번 실행하면, 정작 느린 것은 ImGui가 아니라 이 코드입니다. 올바른 접근은 "데이터가 실제로 바뀌었을 때만" 무거운 연산을 수행하고, 그 결과를 캐싱해 두었다가 UI 코드는 그 캐시를 읽기만 하는 것입니다.

```cpp
// 개선: 파일 목록은 필요할 때만(폴더 변경, 새로고침 버튼 클릭 등) 갱신한다.
std::vector<std::string> cached_files;
bool files_dirty = true;

void RefreshFileListIfNeeded()
{
    if (!files_dirty)
        return;

    cached_files = ReadDirectoryFromDisk("assets/");
    std::sort(cached_files.begin(), cached_files.end());
    files_dirty = false;
}

void DrawFileList()
{
    RefreshFileListIfNeeded();

    for (const auto& f : cached_files)
        ImGui::Text("%s", f.c_str());
}
```

이 원칙은 정렬이나 파일 읽기뿐 아니라, 네트워크 요청, 이미지 디코딩, 복잡한 문자열 포매팅처럼 "결과가 자주 바뀌지 않는 무거운 계산" 전반에 똑같이 적용됩니다. 즉시 모드가 요구하는 것은 "매 프레임 UI *함수 호출*을 반복하라"는 것이지 "매 프레임 모든 *데이터 처리*를 반복하라"는 것이 아니라는 점을 구분하는 것이 성능 문제를 피하는 핵심입니다.

물론 항목 수가 극단적으로 많아지는 경우(수만 개의 테이블 행 등)에는 화면에 보이는 부분만 그리는 클리핑 기법이 별도로 필요한데, 이는 8장에서 다룬 테이블의 `ImGuiListClipper`가 담당하는 영역입니다.

## 프레임레이트 확인하기

지금 애플리케이션이 초당 몇 프레임으로 동작하고 있는지는 `ImGui::GetIO()`가 반환하는 `ImGuiIO` 구조체의 `Framerate` 필드로 확인할 수 있습니다.

```cpp
ImGuiIO& io = ImGui::GetIO();
ImGui::Text("애플리케이션 평균 %.3f ms/프레임 (%.1f FPS)",
            1000.0f / io.Framerate, io.Framerate);
```

`io.Framerate`는 매 프레임의 순간 값이 아니라 최근 여러 프레임의 이동 평균이기 때문에, 순간적인 프레임 드롭보다는 전반적인 추세를 파악하기에 적합합니다. 이 한 줄을 디버그 오버레이나 메인 창 한구석에 상시 표시해 두면, 위젯을 추가하거나 로직을 변경할 때마다 성능에 미치는 영향을 즉시 체감할 수 있어서 실전에서 매우 유용합니다. 참고로 `ShowMetricsWindow()`를 열면 이 값과 함께 앞서 설명한 정점/드로우 콜 수치도 나란히 볼 수 있으므로, 둘을 같이 관찰하는 습관을 들이면 좋습니다.

## 자주 겪는 실수 세 가지

ImGui를 배우는 과정에서 거의 모든 사람이 한 번쯤 겪는 실수들을 정리합니다. 미리 알아두면 디버깅 시간을 크게 아낄 수 있습니다.

### 1. InputText의 버퍼 크기 부족

`ImGui::InputText()`는 사용자가 입력한 문자열을 저장할 고정 크기 버퍼를 요구합니다.

```cpp
char name_buf[16] = "";
ImGui::InputText("이름", name_buf, sizeof(name_buf));
```

이 버퍼는 `char[16]`처럼 컴파일 타임에 크기가 고정된 배열이어야 하며, ImGui는 사용자가 이 크기를 넘어서는 문자를 입력하지 못하도록 자체적으로 막아줍니다(버퍼 오버플로우 자체는 방지됩니다). 하지만 버퍼가 너무 작으면 사용자가 원하는 만큼 입력하지 못하고 글자가 잘리는 매우 답답한 사용성 문제가 생깁니다. 특히 한글처럼 UTF-8에서 한 글자가 3바이트를 차지하는 문자를 다루는 입력 필드라면, 겉보기의 "글자 수"보다 훨씬 넉넉하게 바이트 크기를 잡아야 합니다. 이름이나 파일 경로처럼 길이를 예측하기 어려운 입력에는 256바이트 이상을 기본값으로 잡거나, `std::string`과 콜백을 연동하는 `ImGuiInputTextFlags_CallbackResize` 플래그를 사용해 버퍼를 동적으로 늘리는 방법도 고려할 만합니다.

### 2. ID 충돌로 인한 위젯 상태 꼬임

3장에서 다룬 것처럼, ImGui는 라벨 문자열을 바탕으로 위젯의 내부 ID를 만듭니다. 같은 창, 같은 계층 안에서 똑같은 라벨을 가진 위젯을 두 개 이상 그리면 두 위젯이 같은 ID를 공유하게 되어, 하나를 조작했더니 다른 하나까지 같이 바뀌거나, 포커스가 엉뚱한 곳으로 튀거나, 텍스트 입력 커서 위치가 이상해지는 등의 증상이 나타납니다. 7장에서 살펴본 것처럼 반복문 안에서 위젯을 그릴 때 특히 자주 발생하며, `##숨김접미사`나 `ImGui::PushID()` / `PopID()`로 해결합니다. 위젯이 이상하게 동작하는데 로직상 원인을 찾을 수 없다면, 가장 먼저 "혹시 라벨이 겹치지는 않았는가"를 의심하고 메트릭 창에서 활성 위젯의 ID를 확인해 보는 것이 좋습니다.

### 3. Begin/End 짝을 맞추지 않아 발생하는 크래시

`ImGui::Begin()`을 호출했다면 그 창의 내용을 다 그린 뒤 반드시 `ImGui::End()`를 호출해야 합니다. 여기서 중요한 것은, **`Begin()`이 `false`를 반환하더라도(창이 접혀 있거나 화면 밖에 있어서 보이지 않는 경우) `End()`는 반드시 호출해야 한다**는 점입니다. 이는 3장과 7장에서 다룬 `TreeNode()` / `TreePop()`의 규칙과는 정반대이므로 헷갈리기 쉽습니다.

```cpp
// 잘못된 예: Begin이 false를 반환하면 End를 건너뛰어 버린다.
if (ImGui::Begin("설정"))
{
    ImGui::Text("내용");
    ImGui::End();   // if 블록 안에 있어서 Begin이 false면 호출되지 않는다!
}

// 올바른 예: Begin의 반환값과 무관하게 End는 항상 호출한다.
if (ImGui::Begin("설정"))
{
    ImGui::Text("내용");
}
ImGui::End();
```

`TreeNode()`/`TreePop()`은 "펼쳐졌을 때만 짝을 맞추는" 규칙이지만, `Begin()`/`End()`, 그리고 이후 장에서 다룰 `BeginChild()`/`EndChild()`, `BeginTable()`/`EndTable()` 같은 함수들은 "호출 결과와 무관하게 항상 짝을 맞추는" 규칙을 따릅니다. 이 규칙을 어기면 내부 스택이 어긋나면서 다음 창을 그릴 때 어설션에 걸리거나 최악의 경우 크래시로 이어질 수 있습니다. 함수마다 규칙이 다르다는 점이 처음에는 헷갈릴 수 있으니, 새로운 `Begin`/`End` 계열 함수를 처음 사용할 때는 데모 창의 해당 예제에서 어떤 패턴을 쓰는지 확인하는 습관을 들이는 것이 안전합니다.

## 요약

- `ImGui::ShowDemoWindow()`는 ImGui의 거의 모든 기능을 실제 동작 예제로 보여주는 내장 데모 창이며, 그 소스 파일인 `imgui_demo.cpp`는 최신 API 사용법을 확인할 수 있는 가장 신뢰할 수 있는 참고 자료입니다.
- `ImGui::ShowMetricsWindow()`는 정점/드로우 콜 수, 창 목록, 호버·활성·포커스 위젯 정보 등 내부 상태를 실시간으로 보여주는 디버깅 도구로, 레이아웃 문제나 ID 충돌을 추적할 때 가장 먼저 열어봐야 할 창입니다.
- 즉시 모드에서 위젯 함수 자체는 매우 가볍게 설계되어 있어 매 프레임 호출해도 부담이 크지 않지만, 파일 읽기나 정렬처럼 무거운 연산을 UI 코드 안에 직접 넣으면 그 연산이 매 프레임 반복되어 성능 문제를 일으킬 수 있습니다. 이런 연산은 결과를 캐싱해두고 필요할 때만 갱신해야 합니다.
- `ImGui::GetIO().Framerate`로 현재 애플리케이션의 평균 프레임레이트를 확인할 수 있습니다.
- 자주 겪는 실수로는 `InputText`의 버퍼 크기 부족, 반복문에서의 ID 충돌로 인한 위젯 상태 꼬임, `Begin()`의 반환값과 무관하게 `End()`를 항상 호출하지 않아 발생하는 크래시가 있습니다.

## 연습문제

1. 여러분의 프로젝트에 도움말 메뉴를 만들고, 그 안에 데모 창과 메트릭 창을 여닫는 체크박스 메뉴 항목을 각각 추가해보세요.
2. 메트릭 창을 열어둔 채로 위젯을 하나씩 추가해가면서 드로우 콜 수와 정점 수가 어떻게 늘어나는지 관찰해보세요.
3. 반복문 안에서 정렬 연산을 매 프레임 실행하는 코드를 하나 작성한 뒤, "데이터가 바뀌었을 때만" 정렬하도록 더티 플래그(dirty flag)를 이용해 개선해보세요.
4. `char buf[8]`처럼 일부러 작은 버퍼로 `InputText`를 만들어보고, 긴 문자열을 입력했을 때 어떤 제약이 생기는지 확인해보세요.
5. `Begin()`이 `false`를 반환하는 상황(예: 창을 접었을 때)을 의도적으로 만든 뒤, `End()` 호출을 `if` 블록 안에 잘못 넣었을 때와 블록 밖에 올바르게 두었을 때의 차이를 메트릭 창의 창 목록으로 비교해보세요.

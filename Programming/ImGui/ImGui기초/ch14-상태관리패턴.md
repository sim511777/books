# 14장. 상태 관리 패턴

[◀ 이전: 13장. 입력 처리](ch13-입력처리.md) | [📖 목차](00-목차.md) | [다음: 15장. 플롯과 데이터 시각화(ImPlot) ▶](ch15-플롯과데이터시각화.md)


1장에서 ImGui를 "즉시 모드(immediate mode)" GUI 라이브러리라고 소개하면서, 이 라이브러리는 버튼이나 체크박스가 어떤 상태였는지를 스스로 기억하지 않는다고 이야기했다. 3장에서는 그 원칙을 조금 더 구체적으로 파고들어, `ImGui::Checkbox("동작", &enabled)`처럼 위젯 함수에 애플리케이션의 변수 주소를 직접 넘겨주는 방식이 왜 ImGui API 전반에 걸쳐 반복되는지를 살펴봤다. 이번 장에서는 그 원칙을 실제 애플리케이션 규모의 코드 구조로 확장한다. 위젯 하나짜리 예제에서는 전역 변수 몇 개로도 충분하지만, 창이 여러 개고 패널이 여러 개인 진짜 애플리케이션에서는 "이 상태를 누가 소유하고, 어떤 함수가 그 상태를 읽고 쓰는가"를 설계하는 일이 코드 품질을 가르는 분기점이 된다.

## 원칙 재확인: ImGui는 데이터를 소유하지 않는다

즉시 모드 GUI의 핵심은 매 프레임 UI를 처음부터 다시 그린다는 데 있다. `ImGui::SliderFloat("볼륨", &volume, 0.0f, 1.0f)`이라는 호출은 매 프레임 새로 실행되고, 그때마다 `volume` 변수의 현재 값을 읽어서 슬라이더를 그리고, 사용자가 드래그하면 같은 프레임 안에서 `volume`에 새 값을 곧바로 써넣는다. ImGui 내부 어디에도 "이 슬라이더의 현재 값"이라는 상태는 저장되어 있지 않다. 저장되어 있는 건 오직 우리가 넘겨준 `volume` 변수뿐이다.

이 원칙이 갖는 함의는 생각보다 크다. 리테인드 모드(retained mode) GUI 프레임워크라면 "슬라이더 위젯 객체"를 만들고 그 객체가 자신의 값을 들고 있다가, 값이 바뀌면 이벤트나 콜백을 통해 애플리케이션에 알려주는 구조가 일반적이다. 반면 ImGui에는 그런 위젯 객체가 존재하지 않는다. 위젯은 함수 호출이 시작되고 끝나는 그 짧은 순간에만 "존재"했다가 사라진다. 따라서 애플리케이션 데이터를 어딘가에 보관하고, 그 보관 위치를 UI 그리기 코드에 정확히 연결해주는 책임은 전적으로 우리 몫이다.

이 장에서 다루는 모든 패턴은 결국 하나의 질문에 대한 답이다. **여러 개의 창과 함수에 걸쳐 존재해야 하는 이 데이터를, 어디에 두고 어떻게 전달할 것인가?**

## 상태를 하나의 구조체로 묶기

작은 프로그램이라면 상태 몇 개를 지역 변수나 전역 변수로 흩어놓아도 큰 문제가 없다. 하지만 창이 서너 개만 넘어가도 "이 값은 어디서 선언됐더라"를 찾아 헤매게 되고, 함수 시그니처에 `bool&`, `float&`, `int&`를 대여섯 개씩 나열하는 코드가 만들어진다. 이런 상황을 정리하는 가장 실용적인 방법은 애플리케이션이 공유해야 할 상태를 하나의 구조체로 묶는 것이다.

```cpp
struct AppState
{
    // 창 표시 여부
    bool show_demo_window = false;
    bool show_settings_panel = true;
    bool show_log_window = true;

    // 설정 값
    float volume = 0.5f;
    int quality_level = 2;
    bool vsync_enabled = true;
    ImVec4 accent_color = ImVec4(0.26f, 0.59f, 0.98f, 1.0f);

    // 로그 패널이 참조하는 데이터
    std::vector<std::string> log_lines;

    // 문서/파일 관련 상태
    std::string current_file_path;
    bool document_dirty = false;
};
```

이 구조체 하나가 애플리케이션의 "진실의 원천(single source of truth)" 역할을 한다. 어떤 값이 필요하면 이 구조체 정의만 보면 되고, 초기값도 한곳에서 관리된다. 멤버 초기화 구문(`= false`, `= 0.5f` 등)을 활용하면 생성자를 따로 작성하지 않아도 안전한 기본값을 보장할 수 있다.

## UI 함수에 상태를 참조로 전달하기

`AppState`를 만들었다면, 이제 각 패널을 그리는 함수는 이 구조체의 참조를 받아서 필요한 멤버를 읽고 쓴다. 값이 아니라 **참조**로 받는 것이 중요하다. 값으로 복사해서 받으면 함수 안에서 아무리 값을 바꿔도 원본에는 반영되지 않아, 매 프레임 사용자의 입력이 사라지는 버그가 생긴다.

```cpp
void DrawSettingsPanel(AppState& state)
{
    ImGui::Begin("설정", &state.show_settings_panel);

    ImGui::SliderFloat("볼륨", &state.volume, 0.0f, 1.0f);
    ImGui::SliderInt("품질 레벨", &state.quality_level, 0, 4);
    ImGui::Checkbox("수직 동기화", &state.vsync_enabled);
    ImGui::ColorEdit3("강조 색상", (float*)&state.accent_color);

    ImGui::End();
}

void DrawLogWindow(AppState& state)
{
    ImGui::Begin("로그", &state.show_log_window);
    for (const auto& line : state.log_lines)
        ImGui::TextUnformatted(line.c_str());
    ImGui::End();
}

void DrawMainMenuBar(AppState& state)
{
    if (ImGui::BeginMainMenuBar())
    {
        if (ImGui::BeginMenu("보기"))
        {
            ImGui::MenuItem("설정", nullptr, &state.show_settings_panel);
            ImGui::MenuItem("로그", nullptr, &state.show_log_window);
            ImGui::MenuItem("데모 창", nullptr, &state.show_demo_window);
            ImGui::EndMenu();
        }
        ImGui::EndMainMenuBar();
    }
}
```

메인 루프는 이 함수들을 한데 모아 호출하기만 하면 된다. 각 함수가 무엇을 읽고 쓰는지는 함수 시그니처의 `AppState&` 하나로 명확하게 드러나고, 새로운 패널을 추가할 때도 `DrawXxxPanel(AppState&)` 형태의 함수 하나만 더 만들면 되므로 구조가 선형적으로 확장된다.

```cpp
void RenderFrame(AppState& state)
{
    DrawMainMenuBar(state);

    if (state.show_settings_panel)
        DrawSettingsPanel(state);
    if (state.show_log_window)
        DrawLogWindow(state);
    if (state.show_demo_window)
        ImGui::ShowDemoWindow(&state.show_demo_window);
}

// 메인 루프 안에서
while (!glfwWindowShouldClose(window))
{
    glfwPollEvents();
    ImGui_ImplOpenGL3_NewFrame();
    ImGui_ImplGlfw_NewFrame();
    ImGui::NewFrame();

    RenderFrame(appState);   // appState는 루프 바깥에서 한 번 선언된 객체

    ImGui::Render();
    // ... 렌더링 백엔드 호출 ...
}
```

이 방식의 장점은 **UI를 그리는 코드**(`DrawSettingsPanel` 안의 ImGui 호출들)와 **상태 자체**(`AppState`의 정의)가 서로 다른 곳에 분리되어 있으면서도, 참조 하나로 명확하게 연결된다는 점이다. 상태 구조체는 UI 계층과 무관하게 파일 저장, 네트워크 동기화, 실행 취소 스택 같은 다른 시스템에서도 재사용할 수 있는 순수한 데이터 덩어리로 남는다. 5장에서 다룬 창 배치나 8장의 테이블처럼 UI 구조가 복잡해질수록, 이렇게 데이터와 그리기 코드를 분리해두는 습관의 가치는 커진다.

여러 패널이 서로 다른 소스 파일에 나뉘어 있는 큰 프로젝트라면, `AppState`는 공용 헤더에 정의하고 각 `DrawXxxPanel` 함수는 각자의 `.cpp` 파일에 구현하는 식으로 물리적으로도 분리할 수 있다. 이때도 함수는 여전히 `AppState&` 하나만 받으면 되므로, 헤더 의존성이 최소화된다.

## 정적 지역 변수로 함수 지역 상태 가두기

모든 상태가 `AppState`에 들어갈 필요는 없다. 오히려 여러 창에 걸쳐 공유될 필요가 없는 상태까지 전부 전역 구조체에 몰아넣으면, 구조체가 비대해지고 "이 필드는 대체 어느 패널에서만 쓰이는 거지"를 파악하기 어려워진다. 특정 UI 함수 하나에서만 필요한 상태라면, 그 함수의 정적 지역 변수(`static`)로 선언해서 함수 스코프 안에 완전히 가둬버리는 편이 훨씬 깔끔하다.

```cpp
void DrawSearchBox()
{
    static char search_buffer[128] = "";
    static bool case_sensitive = false;
    static std::vector<std::string> results;

    if (ImGui::InputText("검색", search_buffer, sizeof(search_buffer)))
    {
        results = PerformSearch(search_buffer, case_sensitive);
    }
    ImGui::SameLine();
    ImGui::Checkbox("대소문자 구분", &case_sensitive);

    for (const auto& r : results)
        ImGui::BulletText("%s", r.c_str());
}
```

`static` 지역 변수는 함수가 처음 호출될 때 딱 한 번만 초기화되고, 이후 호출부터는 이전 프레임에 저장된 값을 그대로 유지한다. 이는 마치 함수 자신만을 위한 작은 `AppState`를 함수 내부에 숨겨두는 것과 같은 효과를 낸다. `search_buffer`나 `results` 같은 값은 애플리케이션의 다른 어떤 부분도 알 필요가 없는, 오직 검색창 UI 하나만을 위한 부속품이므로 전역 상태로 승격시킬 이유가 없다.

이 패턴을 언제 쓰고 언제 `AppState`로 옮겨야 하는지 판단하는 기준은 간단하다. **그 상태를 다른 함수나 다른 창에서도 읽거나 써야 하는 순간이 오면 `AppState`로 옮기고, 그 함수 하나의 생애주기 안에서만 의미가 있다면 `static` 지역 변수로 남겨둔다.** 예를 들어 위 검색 결과를 메뉴바의 다른 항목에서도 참조해야 하는 요구사항이 생긴다면, 그때 `results`를 `AppState`의 멤버로 승격시키면 된다. 처음부터 모든 상태를 전역화하기보다, 필요해질 때 범위를 넓혀가는 편이 코드를 훨씬 오래 건강하게 유지한다.

단, `static` 지역 변수를 쓸 때 한 가지 주의할 점이 있다. 같은 `DrawSearchBox()` 함수를 한 프레임에 여러 번(예를 들어 탭이 여러 개 열려서 각 탭마다 검색창이 필요한 경우) 호출하면, 모든 호출이 **같은** 정적 변수를 공유하게 되어 탭마다 독립된 검색 상태를 가질 수 없다. 이런 경우라면 `static` 대신 각 탭의 데이터 구조 안에 검색 상태를 담아 인자로 넘겨주는 방식으로 바꿔야 한다. 즉, `static` 지역 변수는 "이 함수가 프로그램 전체에서 딱 하나만 존재하는 UI를 그린다"는 전제가 성립할 때 가장 안전하다.

## 값이 바뀌었는지 감지하기: 위젯의 반환값

즉시 모드에서 "이전 프레임과 비교해서 값이 바뀌었는가"를 아는 방법은 생각보다 단순하다. 별도로 이전 값을 저장해뒀다가 매 프레임 비교할 필요가 없다. ImGui의 값 편집 위젯은 거의 예외 없이 **"이번 프레임에 이 위젯을 통해 값이 변경되었는가"**를 `bool` 반환값으로 알려주도록 설계되어 있다.

```cpp
static float volume = 0.5f;
if (ImGui::SliderFloat("볼륨", &volume, 0.0f, 1.0f))
{
    // 이 블록은 슬라이더가 실제로 값을 바꾼 바로 그 프레임에만 실행된다
    ApplyVolumeToAudioEngine(volume);
}
```

`ImGui::SliderFloat()`는 값을 바꾸지 않은 프레임에는 `false`를 반환하고, 사용자가 드래그해서 값이 바뀐 프레임에는 `true`를 반환한다. `Checkbox()`, `InputText()`, `ColorEdit4()`, `Combo()` 등 값을 편집하는 위젯 대부분이 이 관례를 따른다. 이 반환값 하나로 "값이 바뀔 때만 실행해야 하는 부수 효과(side effect)"를 정확히 그 프레임에만 실행할 수 있다.

```cpp
struct AppState
{
    int quality_level = 2;
    bool document_dirty = false;
};

void DrawSettingsPanel(AppState& state)
{
    ImGui::Begin("설정");

    if (ImGui::SliderInt("품질 레벨", &state.quality_level, 0, 4))
    {
        state.document_dirty = true;   // 값이 바뀐 프레임에만 "수정됨" 플래그를 세운다
    }

    if (state.document_dirty)
        ImGui::TextColored(ImVec4(1, 0.6f, 0.2f, 1), "저장되지 않은 변경 사항이 있습니다");

    ImGui::End();
}
```

이 패턴은 13장에서 다룬 `IsItemDeactivatedAfterEdit()`과 짝을 이루는 경우가 많다. 위젯의 반환값은 "값이 변경된 매 프레임마다" `true`가 되므로 실시간 반응(오디오 미리듣기, 3D 뷰 즉시 갱신 등)에 적합하고, `IsItemDeactivatedAfterEdit()`은 "편집이 끝난 단 한 번의 프레임"에만 반응하므로 파일 저장이나 서버 전송처럼 비용이 큰 작업에 적합하다. 두 가지를 함께 쓰면 "값이 바뀔 때마다 화면은 즉시 갱신하되, 실제 커밋(저장)은 사용자가 손을 뗐을 때 한 번만 수행"하는 흔한 요구사항을 자연스럽게 구현할 수 있다.

```cpp
if (ImGui::SliderFloat("밝기", &state.brightness, 0.0f, 2.0f))
{
    UpdatePreview(state.brightness);        // 매 프레임, 값이 바뀔 때마다
}
if (ImGui::IsItemDeactivatedAfterEdit())
{
    SaveSettingToDisk("brightness", state.brightness);   // 손을 뗀 순간 딱 한 번
}
```

여러 위젯의 변경 여부를 한데 모아 "이 패널에서 뭔가 하나라도 바뀌었는가"를 판단하고 싶을 때는 `|=` 연산자로 반환값을 누적하는 관용구를 쓴다.

```cpp
bool DrawTransformEditor(Transform& t)
{
    bool changed = false;
    changed |= ImGui::DragFloat3("위치", &t.position.x, 0.1f);
    changed |= ImGui::DragFloat3("회전", &t.rotation.x, 1.0f);
    changed |= ImGui::DragFloat3("크기", &t.scale.x, 0.01f);
    return changed;
}

// 호출부
if (DrawTransformEditor(selectedObject.transform))
{
    MarkSceneDirty();
}
```

여기서 `changed = ImGui::DragFloat3(...)`가 아니라 `changed |= ImGui::DragFloat3(...)`를 쓰는 이유에 주목할 필요가 있다. 대입(`=`)을 쓰면 마지막 위젯의 반환값만 `changed`에 남고, 그 앞의 위젯들이 값을 바꿨다는 사실은 덮어써져 사라진다. `|=`는 한 번이라도 `true`가 나오면 이후 결과와 무관하게 `changed`를 계속 `true`로 유지하므로, "이 그룹의 위젯 중 하나라도 바뀌었는가"라는 질문에 정확히 답한다. 이렇게 함수 자체가 `bool`을 반환하도록 만들면, `DrawTransformEditor()`처럼 여러 위젯을 감싼 함수도 마치 하나의 위젯처럼 "변경 여부"를 상위 호출자에게 그대로 전달할 수 있다.

## 종합 예제: 여러 패널을 가진 작은 애플리케이션

지금까지 다룬 네 가지 패턴, 즉 상태 구조체, 참조 전달, 정적 지역 변수, 변경 감지를 한데 모으면 다음과 같은 구조가 된다.

```cpp
struct AppState
{
    bool show_settings = true;
    bool show_stats = true;
    float volume = 0.5f;
    bool document_dirty = false;
    std::string status_message;
};

void DrawSettingsPanel(AppState& state)
{
    if (!state.show_settings) return;
    ImGui::Begin("설정", &state.show_settings);

    if (ImGui::SliderFloat("볼륨", &state.volume, 0.0f, 1.0f))
        state.document_dirty = true;

    if (ImGui::IsItemDeactivatedAfterEdit())
        state.status_message = "볼륨 설정이 저장되었습니다";

    ImGui::End();
}

void DrawStatsPanel(AppState& state)
{
    if (!state.show_stats) return;

    // 이 창 안에서만 쓰이는 이동 평균 계산용 상태는 static으로 가둔다
    static float frameTimes[120] = {};
    static int frameIndex = 0;
    frameTimes[frameIndex] = ImGui::GetIO().DeltaTime * 1000.0f;
    frameIndex = (frameIndex + 1) % IM_ARRAYSIZE(frameTimes);

    ImGui::Begin("통계", &state.show_stats);
    ImGui::PlotLines("프레임 시간(ms)", frameTimes, IM_ARRAYSIZE(frameTimes));
    ImGui::Text("%s", state.status_message.c_str());
    ImGui::End();
}

void RenderFrame(AppState& state)
{
    DrawSettingsPanel(state);
    DrawStatsPanel(state);
}
```

`AppState`는 설정 값, 창 표시 여부, 상태 메시지처럼 패널 간에 공유되거나 프로그램 전체 수명 동안 유지되어야 하는 데이터만 담고 있다. 반면 프레임 시간 그래프를 위한 원형 버퍼(`frameTimes`)는 `DrawStatsPanel()` 함수 밖으로 나갈 이유가 전혀 없는 구현 세부사항이므로 `static`으로 그 함수 안에 가둬뒀다. 이렇게 "공유해야 할 상태"와 "지역적인 구현 세부사항"을 구분해서 배치하는 것이, 규모가 커져도 무너지지 않는 ImGui 애플리케이션 구조의 핵심이다.

## 요약

- ImGui는 위젯의 값을 스스로 저장하지 않는다. 모든 상태는 애플리케이션이 소유하며, ImGui는 매 프레임 그 상태를 읽고 사용자 입력이 있으면 다시 그 자리에 써넣을 뿐이다.
- 여러 창과 패널에 걸쳐 공유해야 하는 상태는 `AppState`와 같은 하나의 구조체로 묶어서 관리하면, 데이터의 소재가 명확해지고 함수 시그니처가 단순해진다.
- UI를 그리는 함수는 `void DrawXxxPanel(AppState& state)`처럼 상태 구조체의 참조를 받아, UI 코드와 데이터를 깔끔하게 분리한다.
- 특정 함수 안에서만 의미 있는 지역적인 상태는 `static` 지역 변수로 그 함수 스코프에 가둬서, 전역 상태를 불필요하게 어지럽히지 않는다. 단, 같은 함수가 한 프레임에 여러 번 호출되는 경우에는 상태가 공유되어버리는 함정을 주의해야 한다.
- 값 편집 위젯의 반환값은 "이번 프레임에 값이 바뀌었는가"를 알려준다. 이 반환값을 조건문으로 활용하거나 `|=`로 누적하면, 별도의 이전 값 비교 없이도 변경 감지 로직을 자연스럽게 작성할 수 있다.

## 연습문제

1. `show_demo_window`, `show_about_dialog`, `theme_index`(0: 라이트, 1: 다크, 2: 클래식) 세 개의 필드를 가진 `AppState`를 정의하고, 메인 메뉴바에서 이 값들을 토글/변경하는 `DrawMainMenuBar(AppState&)` 함수를 작성해 보라. 12장에서 다룬 스타일 함수를 활용해 `theme_index`가 바뀌면 실제로 테마가 전환되도록 연결해 보라.
2. 이번 장의 `DrawTransformEditor()` 예제를 참고하여, `struct Light { ImVec4 color; float intensity; }`를 편집하는 `bool DrawLightEditor(Light& light)` 함수를 작성하고, 값이 하나라도 바뀌면 `true`를 반환하도록 구현해 보라.
3. 검색창 예제(`DrawSearchBox()`)를 여러 탭에서 각각 독립적으로 사용할 수 있도록, `static` 지역 변수 대신 탭별 데이터 구조체와 참조 전달 방식으로 리팩터링해 보라.
4. `AppState`에 `int autosave_interval_seconds`와 `float time_since_last_save`를 추가하고, `document_dirty`가 `true`인 상태로 지정된 시간이 지나면 자동 저장을 수행한 뒤 `document_dirty`를 `false`로 되돌리는 로직을 `RenderFrame()`에 추가해 보라.
5. 슬라이더의 반환값(매 프레임 변경 감지)과 `IsItemDeactivatedAfterEdit()`(편집 완료 감지)을 함께 사용하는 예제를 하나 더 만들어 보라. 예를 들어 색상 편집기에서 드래그 중에는 미리보기 사각형의 색만 바꾸고, 편집이 끝난 순간에만 "색상 팔레트에 최근 사용 색상으로 추가"하는 로직을 구현해 보라.

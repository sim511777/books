1장에서는 C#/.NET이 장비 제어 소프트웨어 개발 플랫폼으로서 갖는 위치와 전체 아키텍처를 조망했고, 2장에서는 그 아키텍처를 떠받치는 비동기·멀티스레딩 기반을 다졌다. 이제 실제로 "장비와 대화"하는 코드를 작성할 차례다. 아무리 우아한 상태 머신과 반응형 UI를 설계해도, 결국 그 아래에는 시리얼 케이블 너머의 컨트롤러, 이더넷으로 연결된 PLC, 벤더가 제공한 네이티브 DLL, 혹은 EtherCAT 슬레이브 드라이브와 바이트 단위로 정확하게 주고받는 통신 계층이 있어야 한다. 이 계층에서 발생하는 버그는 대개 재현이 어렵고, 현장에서만 터지며, 디버거를 붙이면 사라지는 특성을 가진다. 따라서 3장은 "일단 동작하는 코드"가 아니라 "현장에서 24시간 무중단으로 버티는 코드"를 기준으로 설명한다.

이 장에서는 장비 제어 소프트웨어가 마주치는 대표적인 네 가지 통신 경로를 다룬다. 시리얼 통신(RS-232C/422/485), TCP/IP 및 Modbus-TCP, C/C++ 네이티브 DLL과의 P/Invoke 연동, 그리고 EtherCAT/CANopen 같은 산업용 필드버스다. 각 절은 단순히 API 사용법을 나열하지 않고, 왜 그런 설계가 필요한지, 무엇이 실무에서 문제를 일으키는지를 함께 짚는다. 5장에서 본격적으로 다룰 상태 머신(FSM) 개념도 이 장의 프로토콜 파서 예제에서 미리 응용해 본다.

## 3.1 System.IO.Ports를 활용한 시리얼 통신(RS-232C / RS-422 / RS-485)

시리얼 통신은 산업 현장에서 여전히 가장 널리 쓰이는 통신 방식 중 하나다. 온도 컨트롤러, 바코드 리더, 구형 모션 컨트롤러, 저가형 센서 모듈 대부분이 RS-232C나 RS-485 인터페이스를 제공한다. .NET은 `System.IO.Ports.SerialPort` 클래스로 시리얼 포트를 추상화하지만, 이 클래스를 "그냥 열고 읽으면 되는" 단순한 것으로 취급하면 반드시 현장에서 문제가 생긴다.

### 3.1.1 SerialPort 클래스 기본 사용법

`SerialPort`는 COM 포트를 열고 바이트를 주고받는 가장 기본적인 API다.

```csharp
using System;
using System.IO.Ports;

public class TemperatureControllerLink : IDisposable
{
    private readonly SerialPort _port;

    public TemperatureControllerLink(string portName)
    {
        _port = new SerialPort(portName)
        {
            BaudRate = 9600,
            Parity = Parity.None,
            DataBits = 8,
            StopBits = StopBits.One,
            Handshake = Handshake.None,   // 하드웨어 흐름 제어(RTS/CTS) 미사용 시
            ReadTimeout = 500,             // 동기 Read 호출의 최대 대기 시간(ms)
            WriteTimeout = 500,
            Encoding = System.Text.Encoding.ASCII,
            NewLine = "\r\n"
        };
    }

    public void Open()
    {
        if (!_port.IsOpen)
        {
            _port.Open();
        }
    }

    public void Dispose()
    {
        if (_port.IsOpen)
        {
            _port.Close();
        }
        _port.Dispose();
    }
}
```

`BaudRate`, `Parity`, `DataBits`, `StopBits` 네 가지는 반드시 장비 매뉴얼과 정확히 일치해야 한다. 이 값이 하나라도 다르면 포트는 예외 없이 열리지만, 수신되는 데이터는 전부 깨진 바이트로 나타난다("Garbage data"). 실무에서 신규 장비를 붙일 때 통신이 전혀 안 되는 문제의 8~90%는 이 네 파라미터 불일치이므로, 가장 먼저 의심해야 할 지점이다.

`Handshake` 속성도 주의가 필요하다. `Handshake.None`이 기본값처럼 취급되지만, 일부 장비는 RTS/CTS 하드웨어 흐름 제어를 요구한다. 이 경우 `Handshake.RequestToSend`로 설정하지 않으면 송신 자체가 무시되거나 버퍼가 넘칠 수 있다.

### 3.1.2 DataReceived 이벤트 vs 폴링 방식 수신

`SerialPort`는 데이터가 도착하면 발생하는 `DataReceived` 이벤트를 제공한다.

```csharp
_port.DataReceived += Port_DataReceived;

private void Port_DataReceived(object sender, SerialDataReceivedEventArgs e)
{
    var port = (SerialPort)sender;
    int bytesToRead = port.BytesToRead;
    if (bytesToRead == 0) return;

    byte[] buffer = new byte[bytesToRead];
    int read = port.Read(buffer, 0, bytesToRead);
    // 수신 버퍼를 프레임 파서로 전달 (3.1.4절 참조)
    OnBytesReceived(buffer.AsSpan(0, read));
}
```

간단해 보이지만, `DataReceived` 이벤트에는 실무에서 자주 발목을 잡는 특성이 몇 가지 있다.

첫째, 이 이벤트는 .NET의 스레드 풀 스레드에서 호출된다. 즉 UI 스레드가 아니다. 이벤트 핸들러 안에서 WPF 컨트롤을 직접 갱신하면 `InvalidOperationException`("호출 스레드가 이 개체에 액세스할 수 없습니다")이 발생한다. 2장에서 다룬 `Dispatcher.Invoke`나 `SynchronizationContext`를 통해 UI 스레드로 마샬링해야 한다.

둘째, Windows에서 `SerialPort.DataReceived` 이벤트는 드라이버 구현에 따라 이벤트가 누락되거나 늦게 발생하는 알려진 이슈가 있다(특히 USB-Serial 변환 칩셋에서 두드러진다). 짧은 시간에 여러 번 데이터가 도착하면 이벤트가 한 번만 발생하고 이후 발생하지 않는 사례가 보고되어 왔다. 이 때문에 실무에서는 이벤트 기반 수신 대신, 2장에서 다룬 전용 백그라운드 스레드로 `Read`를 블로킹 호출하며 폴링하는 방식을 선호하는 경우가 많다.

```csharp
public class PollingSerialReceiver
{
    private readonly SerialPort _port;
    private readonly Thread _rxThread;
    private readonly CancellationTokenSource _cts = new();
    private readonly Action<byte[], int> _onDataReceived;

    public PollingSerialReceiver(SerialPort port, Action<byte[], int> onDataReceived)
    {
        _port = port;
        _onDataReceived = onDataReceived;
        _rxThread = new Thread(ReceiveLoop)
        {
            IsBackground = true,
            Name = "SerialRx",
            Priority = ThreadPriority.AboveNormal
        };
    }

    public void Start() => _rxThread.Start();

    public void Stop()
    {
        _cts.Cancel();
        _rxThread.Join(1000);
    }

    private void ReceiveLoop()
    {
        var buffer = new byte[256];
        while (!_cts.IsCancellationRequested)
        {
            try
            {
                int n = _port.Read(buffer, 0, buffer.Length); // ReadTimeout 만료 시 TimeoutException
                if (n > 0)
                {
                    _onDataReceived(buffer, n);
                }
            }
            catch (TimeoutException)
            {
                // 정상적인 타임아웃. 루프를 계속 돌며 취소 요청을 확인한다.
            }
            catch (IOException)
            {
                // 케이블 분리 등 물리적 단절. 재연결 로직으로 위임한다.
                break;
            }
        }
    }
}
```

이 방식은 전용 스레드 하나를 계속 점유한다는 비용이 있지만, 수신 타이밍을 애플리케이션이 완전히 통제할 수 있고 이벤트 유실 문제에서 자유롭다는 장점이 있다. 현장에 여러 대의 시리얼 장비를 연결하는 경우, 장비마다 하나씩 수신 스레드를 두고 2장에서 소개한 `BlockingCollection<T>`나 `Channel<T>`로 파싱 결과를 상위 소비자에게 넘기는 구조가 널리 쓰인다.

### 3.1.3 RS-232C, RS-422/RS-485의 물리적 차이와 소프트웨어 설계

`SerialPort` 클래스 자체는 RS-232C든 RS-422/485든 동일한 API로 다룬다(실제 전기적 신호 변환은 USB-RS485 컨버터 등 하드웨어가 담당한다). 하지만 소프트웨어 설계자가 반드시 이해해야 할 물리 계층 차이가 있다.

- **RS-232C**: 1:1 포인트-투-포인트 통신이다. 하나의 COM 포트는 하나의 장치와만 연결된다. 케이블 길이는 짧게(보통 15m 이내) 권장되며, 노이즈에 상대적으로 취약하다. 소프트웨어 관점에서는 "포트 하나 = 장치 하나"로 단순하게 모델링할 수 있다.
- **RS-422**: 차동 신호를 사용해 노이즈에 강하고 장거리(최대 1.2km 수준) 전송이 가능하다. 보통 1:N(마스터 1대, 슬레이브 여러 대) 구성이 가능하지만 실무에서는 RS-485가 더 일반적으로 쓰인다.
- **RS-485**: 반이중(half-duplex) 멀티드롭 버스다. 하나의 물리적 버스에 여러 장치가 병렬로 연결되고, 모든 장치가 같은 선을 공유한다.

RS-485를 다룰 때 소프트웨어 설계에서 가장 중요한 차이는 **주소 기반 프로토콜이 필수**라는 점이다. RS-232C처럼 "포트를 열면 상대방이 하나뿐"인 것이 아니라, 버스에 여러 장치가 물려 있으므로 모든 요청 프레임에 대상 장치의 주소(슬레이브 ID)를 포함해야 하고, 응답도 어느 장치가 보낸 것인지 주소로 식별해야 한다. 또한 반이중 특성상 한 장치가 송신하는 동안에는 다른 장치가 송신하면 안 되므로, 마스터가 요청을 보내고 응답을 받을 때까지 다음 요청을 보내지 않는 **폴링(polling) 방식의 순차 통신**이 사실상 강제된다.

```csharp
public class Rs485PollingScheduler
{
    private readonly SerialPort _port;
    private readonly byte[] _slaveAddresses;

    public Rs485PollingScheduler(SerialPort port, byte[] slaveAddresses)
    {
        _port = port;
        _slaveAddresses = slaveAddresses;
    }

    // 버스에 연결된 슬레이브를 순차적으로 폴링한다.
    // 반이중 버스에서는 절대 동시에 여러 요청을 내보내면 안 된다.
    public async Task PollAllAsync(CancellationToken token)
    {
        foreach (byte address in _slaveAddresses)
        {
            token.ThrowIfCancellationRequested();
            byte[] request = BuildReadRequest(address);
            _port.Write(request, 0, request.Length);

            byte[] response = await ReadResponseAsync(address, token);
            ProcessResponse(address, response);
        }
    }

    private byte[] BuildReadRequest(byte slaveAddress)
    {
        // 프로토콜별 요청 프레임 생성 (3.1.4절의 프레이밍 규칙 적용)
        throw new NotImplementedException();
    }

    private Task<byte[]> ReadResponseAsync(byte expectedAddress, CancellationToken token)
        => throw new NotImplementedException();

    private void ProcessResponse(byte address, byte[] response) { }
}
```

일부 USB-RS485 컨버터는 자동 방향 전환(auto direction control)을 지원하지만, 그렇지 않은 하드웨어를 사용할 경우 송신 직전 RTS 신호로 드라이버 인에이블을 켜고, 송신 완료 후 꺼야 한다. 이때 `SerialPort.Write`가 즉시 반환되더라도 실제 UART 하드웨어의 전송 완료 시점과는 다를 수 있으므로, RTS를 너무 일찍 내리면 마지막 바이트가 잘리는 문제가 발생할 수 있다. 이런 저수준 타이밍 문제는 가능하면 RTS 자동 전환을 지원하는 컨버터를 채택해 소프트웨어 복잡도를 낮추는 것이 실무적으로 바람직하다.

### 3.1.4 실전 프로토콜 파싱 패턴: 상태 머신 기반 프레임 파서

시리얼(그리고 TCP) 통신에서 가장 많은 버그를 만드는 지점은 "프레임 경계"를 잘못 처리하는 것이다. `DataReceived` 이벤트나 폴링 스레드가 한 번에 넘겨주는 바이트 배열은 프로토콜상의 한 프레임과 절대 일치한다는 보장이 없다. OS 버퍼링, USB 패킷 분할, 드라이버 스케줄링 등의 영향으로 다음과 같은 상황이 모두 발생할 수 있다.

- 프레임 하나가 여러 번의 수신 콜백에 걸쳐 조각나서 도착한다.
- 여러 프레임이 한 번의 수신 콜백에 뭉쳐서 도착한다.
- 노이즈로 인해 프레임 중간에 쓰레기 바이트가 섞여 들어온다.

이 문제를 안전하게 해결하는 정석적인 방법이 **상태 머신 기반 파서**다. 5장에서 장비의 동작 시퀀스를 상태 머신으로 설계하는 방법을 본격적으로 다루는데, 그 개념(상태, 전이 조건, 액션)을 여기서 통신 프레임 파싱이라는 훨씬 작은 스코프에 미리 적용해 본다.

다음은 `[STX][LEN][PAYLOAD...][CHECKSUM][ETX]` 형태의 전형적인 프레임 구조를 바이트 스트림에서 분리하는 파서 예제다.

```csharp
public enum FrameParseState
{
    WaitingForStx,
    ReadingLength,
    ReadingPayload,
    ReadingChecksum,
    WaitingForEtx
}

public class FrameParser
{
    private const byte Stx = 0x02;
    private const byte Etx = 0x03;

    private FrameParseState _state = FrameParseState.WaitingForStx;
    private byte _expectedLength;
    private readonly List<byte> _payload = new();
    private byte _receivedChecksum;

    public event Action<byte[]>? FrameReceived;
    public event Action<string>? FrameError;

    /// <summary>
    /// 수신된 바이트 조각(단편이든 여러 프레임이 뭉친 것이든)을 한 바이트씩
    /// 상태 머신에 흘려 넣는다. 부분 수신과 프레임 경계 깨짐에 안전하다.
    /// </summary>
    public void Feed(ReadOnlySpan<byte> chunk)
    {
        foreach (byte b in chunk)
        {
            ProcessByte(b);
        }
    }

    private void ProcessByte(byte b)
    {
        switch (_state)
        {
            case FrameParseState.WaitingForStx:
                if (b == Stx)
                {
                    _payload.Clear();
                    _state = FrameParseState.ReadingLength;
                }
                // STX가 아니면 프레임 시작 전 노이즈로 간주하고 버린다.
                break;

            case FrameParseState.ReadingLength:
                _expectedLength = b;
                if (_expectedLength == 0)
                {
                    // 길이 0은 비정상 프레임으로 간주하고 리셋한다.
                    Reset("길이 필드가 0입니다.");
                    return;
                }
                _state = FrameParseState.ReadingPayload;
                break;

            case FrameParseState.ReadingPayload:
                _payload.Add(b);
                if (_payload.Count >= _expectedLength)
                {
                    _state = FrameParseState.ReadingChecksum;
                }
                break;

            case FrameParseState.ReadingChecksum:
                _receivedChecksum = b;
                _state = FrameParseState.WaitingForEtx;
                break;

            case FrameParseState.WaitingForEtx:
                if (b == Etx)
                {
                    byte calculated = CalculateChecksum(_payload);
                    if (calculated == _receivedChecksum)
                    {
                        FrameReceived?.Invoke(_payload.ToArray());
                    }
                    else
                    {
                        FrameError?.Invoke(
                            $"체크섬 불일치: 수신={_receivedChecksum:X2}, 계산={calculated:X2}");
                    }
                }
                else
                {
                    FrameError?.Invoke("ETX 위치에서 예기치 않은 바이트를 수신했습니다.");
                }
                Reset(null);
                break;
        }
    }

    private void Reset(string? reason)
    {
        if (reason != null)
        {
            FrameError?.Invoke(reason);
        }
        _state = FrameParseState.WaitingForStx;
        _payload.Clear();
    }

    private static byte CalculateChecksum(List<byte> payload)
    {
        byte sum = 0;
        foreach (byte b in payload) sum ^= b; // XOR 체크섬 예시. 실제 프로토콜에 맞춰 교체
        return sum;
    }
}
```

이 파서의 핵심은 **바이트 하나하나를 상태 머신에 독립적으로 흘려 넣는다**는 점이다. 이렇게 하면 수신 콜백이 얼마나 잘게 쪼개져서 호출되든, 혹은 얼마나 많은 데이터를 한 번에 넘기든 파서 내부 상태(`_state`, `_payload`, `_expectedLength`)가 그 경계를 흡수한다. `ReadingLength` 상태에서 콜백이 끊기더라도 다음 콜백이 왔을 때 그 이전 상태를 그대로 이어받아 처리하므로, "프레임이 반토막 났다"는 문제 자체가 발생하지 않는다.

수신 스레드(3.1.2절)와 이 파서를 연결하면 다음과 같은 구조가 된다.

```csharp
var parser = new FrameParser();
parser.FrameReceived += payload => messageQueue.Add(payload); // 상위 계층으로 전달
parser.FrameError += reason => logger.Warn($"프레임 파싱 오류: {reason}");

var receiver = new PollingSerialReceiver(port, (buffer, length) =>
{
    parser.Feed(buffer.AsSpan(0, length));
});
receiver.Start();
```

체크섬 불일치나 예기치 않은 바이트를 만났을 때 예외를 던지는 대신 `FrameError` 이벤트로 로깅만 하고 상태를 리셋하는 설계에 주목하자. 통신 계층에서 예외를 던지면 수신 스레드 전체가 죽어버릴 위험이 있다. 노이즈로 인한 오류는 통신 채널의 일상적인 현상이므로, "에러를 기록하고 다음 프레임을 기다린다"는 복원력 있는 설계가 장비 제어 소프트웨어에는 필수적이다.

## 3.2 TcpClient / Socket 기반 TCP/IP 및 Modbus-TCP 구현

이더넷 기반 장비(PLC, 스마트 카메라, 파워 서플라이, 산업용 게이트웨이 등)와의 통신은 대부분 TCP/IP 위에서 이루어진다. .NET은 두 가지 수준의 API를 제공한다.

### 3.2.1 TcpClient와 Socket의 선택 기준

`System.Net.Sockets.TcpClient`는 `Socket`을 감싼 고수준 래퍼로, `NetworkStream`을 통해 스트림 기반으로 데이터를 주고받을 수 있게 해준다. 대부분의 장비 제어 통신(특히 Modbus-TCP처럼 단일 TCP 연결로 요청-응답을 주고받는 프로토콜)에는 `TcpClient`만으로 충분하다.

```csharp
using var client = new TcpClient();
await client.ConnectAsync("192.168.0.10", 502);
using NetworkStream stream = client.GetStream();
```

반면 `System.Net.Sockets.Socket` 클래스를 직접 사용하는 경우는 다음과 같은 세밀한 제어가 필요할 때다.

- `SocketOptionName.ReceiveTimeout`, `SendTimeout`, `KeepAlive`, `NoDelay`(Nagle 알고리즘 비활성화) 등 소켓 옵션을 세밀하게 조정해야 할 때. 특히 실시간성이 중요한 장비 제어에서는 `Socket.NoDelay = true`로 설정해 작은 패킷이 지연 없이 즉시 전송되도록 하는 경우가 많다.
- UDP 브로드캐스트/멀티캐스트처럼 `TcpClient`가 지원하지 않는 통신 방식이 필요할 때(`SocketType.Dgram`, `ProtocolType.Udp`).
- 다수의 연결을 `SocketAsyncEventArgs` 기반으로 매우 낮은 오버헤드로 처리해야 하는 서버(예: 여러 대의 장비를 동시에 수용하는 상위 게이트웨이)를 만들 때.

일반적인 장비 클라이언트 통신에서는 `TcpClient` + `NetworkStream`으로 시작하고, 성능 프로파일링(9장 참조) 결과 소켓 옵션 조정이 필요하다고 판단될 때 `client.Client`(내부 `Socket` 인스턴스에 접근하는 프로퍼티)를 통해 옵션을 조정하는 절충안이 실무적으로 무난하다.

```csharp
client.Client.NoDelay = true;
client.Client.ReceiveTimeout = 3000;
client.Client.SendTimeout = 3000;
client.Client.SetSocketOption(SocketOptionLevel.Socket, SocketOptionName.KeepAlive, true);
```

### 3.2.2 비동기 송수신과 2장 async/await 패턴의 재사용

`NetworkStream`은 `Stream`을 상속하므로 2장에서 다룬 `ReadAsync`/`WriteAsync` 패턴을 그대로 적용할 수 있다.

```csharp
public class ModbusTcpClient : IAsyncDisposable
{
    private TcpClient? _client;
    private NetworkStream? _stream;
    private readonly SemaphoreSlim _sendLock = new(1, 1); // 동시에 하나의 요청만 진행

    public async Task ConnectAsync(string host, int port, CancellationToken token)
    {
        _client = new TcpClient();
        await _client.ConnectAsync(host, port, token);
        _stream = _client.GetStream();
    }

    public async Task<byte[]> SendAndReceiveAsync(byte[] request, int expectedResponseLength,
        CancellationToken token)
    {
        if (_stream is null) throw new InvalidOperationException("연결되지 않았습니다.");

        await _sendLock.WaitAsync(token);
        try
        {
            await _stream.WriteAsync(request, token);

            var response = new byte[expectedResponseLength];
            int totalRead = 0;
            while (totalRead < expectedResponseLength)
            {
                int n = await _stream.ReadAsync(
                    response.AsMemory(totalRead, expectedResponseLength - totalRead), token);
                if (n == 0)
                {
                    // 원격 측이 연결을 정상 종료(graceful close)했다는 의미
                    throw new IOException("원격 장비가 연결을 종료했습니다.");
                }
                totalRead += n;
            }
            return response;
        }
        finally
        {
            _sendLock.Release();
        }
    }

    public async ValueTask DisposeAsync()
    {
        _stream?.Dispose();
        _client?.Dispose();
        await Task.CompletedTask;
    }
}
```

여기서 두 가지가 중요하다. 첫째, `ReadAsync`는 요청한 바이트 수를 전부 채워서 반환한다는 보장이 없다(TCP는 스트림 지향이지 메시지 지향이 아니다). 그래서 목표 길이만큼 채워질 때까지 반복해서 읽는 루프가 필요하다. 둘째, `SemaphoreSlim`으로 송수신 구간에 락을 걸어 동시에 여러 요청이 뒤섞이지 않도록 했다. Modbus-TCP처럼 요청-응답이 1:1로 짝지어지는 프로토콜에서 여러 스레드가 동시에 `SendAndReceiveAsync`를 호출하면 응답이 엉뚱한 요청과 매칭되는 심각한 버그로 이어지므로, 이 직렬화는 선택이 아니라 필수다.

### 3.2.3 Modbus-TCP 프로토콜 직접 구현

Modbus-TCP는 산업 현장에서 사실상의 표준으로 자리 잡은 프로토콜이다. 원리를 이해하기 위해 NuGet 라이브러리 없이 프레임을 직접 구성해 본다(실무에서는 오픈소스 [NModbus](https://github.com/NModbus/NModbus) 같은 라이브러리를 사용해 반복 구현을 줄이는 경우가 많지만, 프로토콜의 바이트 레벨 구조를 이해하고 있어야 라이브러리가 감춘 동작을 디버깅할 수 있다).

Modbus-TCP 프레임은 **MBAP 헤더(7바이트) + PDU(Protocol Data Unit)**로 구성된다.

| 필드 | 크기 | 설명 |
|---|---|---|
| Transaction Identifier | 2바이트 | 요청-응답을 짝짓는 식별자. 클라이언트가 임의로 부여하고 서버가 그대로 반사한다 |
| Protocol Identifier | 2바이트 | Modbus 프로토콜은 항상 0x0000 |
| Length | 2바이트 | 이후 필드(Unit ID + PDU)의 바이트 수 |
| Unit Identifier | 1바이트 | 대상 슬레이브 ID (시리얼 Modbus의 잔재. TCP에서는 대개 0xFF 또는 게이트웨이가 사용) |
| Function Code | 1바이트 | 예: 0x03(Read Holding Registers), 0x06(Write Single Register), 0x10(Write Multiple Registers) |
| Data | 가변 | 기능 코드에 따른 파라미터 |

Holding Register를 읽는 요청(Function Code 0x03)을 직접 구성하는 예제다.

```csharp
public static class ModbusFrameBuilder
{
    /// <summary>
    /// Function Code 0x03 (Read Holding Registers) 요청 프레임을 생성한다.
    /// </summary>
    public static byte[] BuildReadHoldingRegistersRequest(
        ushort transactionId, byte unitId, ushort startAddress, ushort quantity)
    {
        var frame = new byte[12];

        // MBAP 헤더
        WriteBigEndian(frame, 0, transactionId);   // Transaction ID
        WriteBigEndian(frame, 2, 0x0000);           // Protocol ID (항상 0)
        WriteBigEndian(frame, 4, 0x0006);           // Length: Unit ID(1) + PDU(5)
        frame[6] = unitId;                          // Unit ID

        // PDU
        frame[7] = 0x03;                             // Function Code
        WriteBigEndian(frame, 8, startAddress);      // 시작 레지스터 주소
        WriteBigEndian(frame, 10, quantity);         // 읽을 레지스터 개수

        return frame;
    }

    /// <summary>
    /// Function Code 0x06 (Write Single Register) 요청 프레임을 생성한다.
    /// </summary>
    public static byte[] BuildWriteSingleRegisterRequest(
        ushort transactionId, byte unitId, ushort registerAddress, ushort value)
    {
        var frame = new byte[12];
        WriteBigEndian(frame, 0, transactionId);
        WriteBigEndian(frame, 2, 0x0000);
        WriteBigEndian(frame, 4, 0x0006);
        frame[6] = unitId;

        frame[7] = 0x06;
        WriteBigEndian(frame, 8, registerAddress);
        WriteBigEndian(frame, 10, value);

        return frame;
    }

    private static void WriteBigEndian(byte[] buffer, int offset, ushort value)
    {
        // Modbus는 빅 엔디안(네트워크 바이트 순서)을 사용한다.
        buffer[offset] = (byte)(value >> 8);
        buffer[offset + 1] = (byte)(value & 0xFF);
    }
}
```

응답 프레임을 파싱하는 쪽도 마찬가지로 바이트 오프셋 기준으로 직접 해석한다.

```csharp
public static class ModbusFrameParser
{
    /// <summary>
    /// Read Holding Registers 응답 프레임에서 레지스터 값 배열을 추출한다.
    /// </summary>
    public static ushort[] ParseReadHoldingRegistersResponse(byte[] response)
    {
        // response[7] = Function Code, response[8] = Byte Count
        byte functionCode = response[7];
        if ((functionCode & 0x80) != 0)
        {
            // 최상위 비트가 설정되어 있으면 예외 응답(Exception Response)
            byte exceptionCode = response[8];
            throw new ModbusException(functionCode, exceptionCode);
        }

        byte byteCount = response[8];
        int registerCount = byteCount / 2;
        var registers = new ushort[registerCount];

        for (int i = 0; i < registerCount; i++)
        {
            int offset = 9 + i * 2;
            registers[i] = (ushort)((response[offset] << 8) | response[offset + 1]);
        }
        return registers;
    }
}

public class ModbusException : Exception
{
    public byte FunctionCode { get; }
    public byte ExceptionCode { get; }

    public ModbusException(byte functionCode, byte exceptionCode)
        : base($"Modbus 예외 응답: FunctionCode=0x{functionCode:X2}, ExceptionCode=0x{exceptionCode:X2}")
    {
        FunctionCode = functionCode;
        ExceptionCode = exceptionCode;
    }
}
```

이 두 클래스를 3.2.2절의 `ModbusTcpClient`와 결합하면, 온도 컨트롤러 등 실제 장비의 레지스터를 폴링하는 코드는 다음처럼 작성된다.

```csharp
ushort transactionId = 0;
byte[] request = ModbusFrameBuilder.BuildReadHoldingRegistersRequest(
    transactionId: ++transactionId, unitId: 1, startAddress: 0x0000, quantity: 2);

// 응답 길이: MBAP(7) + FunctionCode(1) + ByteCount(1) + 데이터(quantity*2)
int expectedLength = 9 + 2 * 2;
byte[] response = await modbusClient.SendAndReceiveAsync(request, expectedLength, cts.Token);
ushort[] registers = ModbusFrameParser.ParseReadHoldingRegistersResponse(response);
```

응답에서 `response[0..2]`(Transaction ID)가 요청 시 보냈던 값과 일치하는지 검증하는 코드도 실무에서는 추가하는 것이 안전하다. 다중 요청이 겹칠 가능성이 있는 구조라면 이 검증이 데이터 오정합을 조기에 잡아내는 마지막 방어선이 된다.

### 3.2.4 연결 끊김 감지와 자동 재연결

네트워크 장비는 케이블 분리, 스위치 재부팅, 장비 자체의 리셋 등으로 언제든 연결이 끊길 수 있다. TCP는 특성상 상대방이 갑자기 사라져도(예: 케이블을 물리적으로 뽑음) 애플리케이션이 그 사실을 바로 알기 어렵다. `Write`가 몇 번은 성공한 것처럼 보이다가 한참 후에야 `SocketException`이 발생하는 경우도 흔하다. 따라서 명시적인 감시와 재연결 전략이 필요하다.

```csharp
public class ReconnectingModbusClient
{
    private readonly string _host;
    private readonly int _port;
    private ModbusTcpClient _inner = new();
    private volatile bool _isConnected;

    public ReconnectingModbusClient(string host, int port)
    {
        _host = host;
        _port = port;
    }

    public async Task RunAsync(CancellationToken token)
    {
        while (!token.IsCancellationRequested)
        {
            if (!_isConnected)
            {
                await TryConnectWithBackoffAsync(token);
                continue;
            }

            try
            {
                // 주기적인 통신 사이클 (폴링 등)
                await DoCommunicationCycleAsync(token);
            }
            catch (IOException)
            {
                _isConnected = false; // 다음 루프에서 재연결 시도
            }
            catch (SocketException)
            {
                _isConnected = false;
            }
        }
    }

    private async Task TryConnectWithBackoffAsync(CancellationToken token)
    {
        int attempt = 0;
        while (!token.IsCancellationRequested && !_isConnected)
        {
            try
            {
                _inner = new ModbusTcpClient();
                await _inner.ConnectAsync(_host, _port, token);
                _isConnected = true;
                attempt = 0;
            }
            catch (SocketException)
            {
                attempt++;
                // 지수 백오프: 1s, 2s, 4s ... 최대 30초로 상한
                int delaySeconds = Math.Min(30, (int)Math.Pow(2, attempt));
                await Task.Delay(TimeSpan.FromSeconds(delaySeconds), token);
            }
        }
    }

    private async Task DoCommunicationCycleAsync(CancellationToken token)
    {
        // 3.2.3절의 Modbus 요청/응답을 여기서 수행
        await Task.CompletedTask;
    }
}
```

지수 백오프(exponential backoff)를 적용하는 이유는, 장비가 재부팅 중이거나 네트워크 설정 작업 중일 때 재연결을 초 단위로 무한정 재시도하면 로그가 폭발하고 CPU 자원을 낭비하기 때문이다. 재연결 시도 간격을 점진적으로 늘리되 상한을 두는 것이 실무적으로 안정적이다. 또한 `_isConnected` 상태를 HMI에 실시간으로 노출해(6장에서 다루는 MVVM 바인딩을 통해) 운영자가 "장비와 통신 두절" 상태를 즉시 인지할 수 있게 하는 것이 장비 제어 소프트웨어의 기본 요구사항이다.

## 3.3 C/C++ DLL 연동(P/Invoke, DllImport, Unmanaged Memory 관리)

### 3.3.1 P/Invoke가 필요한 이유

시리얼과 이더넷은 표준화된 통신 매체이므로 .NET 클래스 라이브러리가 직접 지원한다. 하지만 DIO(디지털 입출력) 보드, 모션 컨트롤러 보드, 프레임그래버, 일부 센서 인터페이스 카드는 보드 제조사가 오직 C/C++로 작성된 네이티브 DLL(때로는 32비트 전용)만 제공하는 경우가 여전히 매우 흔하다. .NET용 관리(managed) 래퍼를 제공하는 벤더도 있지만, 그렇지 않은 경우 애플리케이션 개발자가 직접 P/Invoke(Platform Invoke)로 네이티브 DLL을 호출하는 코드를 작성해야 한다.

### 3.3.2 DllImport 선언과 CallingConvention

`[DllImport]` 특성(attribute)은 네이티브 함수의 시그니처를 C#에 선언하는 방법이다.

```csharp
using System.Runtime.InteropServices;

public static class DioBoardApi
{
    // StdCall: Win32 API 및 대다수 Windows용 벤더 DLL의 기본 호출 규약
    [DllImport("DioBoard.dll", CallingConvention = CallingConvention.StdCall)]
    public static extern int DIO_BoardOpen(int boardNumber);

    [DllImport("DioBoard.dll", CallingConvention = CallingConvention.StdCall)]
    public static extern int DIO_BoardClose(int boardHandle);

    [DllImport("DioBoard.dll", CallingConvention = CallingConvention.StdCall)]
    public static extern int DIO_WriteBit(int boardHandle, int channel, [MarshalAs(UnmanagedType.Bool)] bool value);

    [DllImport("DioBoard.dll", CallingConvention = CallingConvention.StdCall)]
    [return: MarshalAs(UnmanagedType.Bool)]
    public static extern bool DIO_ReadBit(int boardHandle, int channel);
}
```

`CallingConvention`은 함수 호출 시 인자를 스택에 쌓는 순서와, 호출 후 스택을 정리하는 주체(호출자 vs 피호출자)를 정의한다. 대표적으로 두 가지를 구분해야 한다.

- **`CallingConvention.StdCall`**: 표준 Win32 API 호출 규약. 대부분의 Windows용 벤더 DLL(모션 보드, DIO 보드 SDK 등)이 이 규약을 사용한다.
- **`CallingConvention.Cdecl`**: C/C++에서 컴파일러가 기본으로 사용하는 규약. 호출자가 스택 정리를 담당하며, 가변 인자 함수(`printf` 계열)를 지원하기 위해 필요하다. 일부 오픈소스 C 라이브러리(예: SOEM)나 리눅스 계열에서 이식된 라이브러리가 이 규약을 쓴다.

**이 값을 잘못 지정하면 매우 위험하다.** 실제 DLL이 `Cdecl`로 컴파일되어 있는데 C# 쪽에서 `StdCall`로(혹은 그 반대로) 선언하면, 함수 호출 자체는 실행되지만 호출 후 스택 포인터가 어긋난다. 인자 개수가 적은 함수에서는 운 좋게 눈에 띄는 증상 없이 넘어가기도 하지만, 인자가 여러 개인 함수에서는 스택이 손상되어 반환 주소가 깨지고, 결국 호출과 전혀 무관한 시점에 `AccessViolationException`이나 애플리케이션이 즉시 크래시되는 형태로 나타난다. 이런 크래시는 스택 오염이 발생한 지점과 실제로 죽는 지점이 다르기 때문에 원인 추적이 극히 어렵다. DLL 벤더가 제공하는 C/C++ 헤더 파일(`.h`)이나 매뉴얼에서 함수 선언 규약을 반드시 확인해야 하며, 명시되어 있지 않다면 Windows용 SDK는 `StdCall`을 우선 시도하는 것이 경험적으로 안전하다.

### 3.3.3 데이터 타입 매핑

C의 기본 타입은 C#의 대응 타입으로 비교적 직관적으로 매핑되지만, 정확한 크기와 시맨틱을 알고 있어야 한다.

| C/C++ 타입 | C# 타입 | 비고 |
|---|---|---|
| `int` | `int` | 둘 다 32비트로 동일 |
| `long` (Windows) | `int` | Windows에서 C의 `long`은 32비트다(LLP64) |
| `float` | `float` | 32비트 부동소수점, 동일 |
| `double` | `double` | 64비트 부동소수점, 동일 |
| `char*` (문자열) | `string` 또는 `IntPtr` | 인코딩(ANSI/Unicode)에 따라 `MarshalAs` 지정 필요 |
| `void*`, 구조체 포인터 | `IntPtr` | 3.3.4절 참조 |
| `BOOL` (Win32) | `int` 또는 `bool`(`MarshalAs(UnmanagedType.Bool)`) | Win32 `BOOL`은 4바이트 정수 기반 |
| `struct` | `[StructLayout(LayoutKind.Sequential)]` struct | 멤버 순서와 정렬이 C 구조체와 정확히 일치해야 함 |

구조체 매핑 예제를 보자. 모션 보드 SDK가 다음과 같은 C 구조체를 사용한다고 가정한다.

```c
// C/C++ 헤더 (벤더 제공)
typedef struct {
    int   AxisNo;
    float TargetVelocity;
    float Acceleration;
    float Deceleration;
    int   UseSCurve;
} MOTION_PROFILE;
```

이를 C#으로 매핑하면 다음과 같다.

```csharp
[StructLayout(LayoutKind.Sequential)]
public struct MotionProfile
{
    public int AxisNo;
    public float TargetVelocity;
    public float Acceleration;
    public float Deceleration;
    public int UseSCurve; // C의 int를 bool 대용으로 사용하는 SDK가 많다 (0/1)
}

[DllImport("MotionBoard.dll", CallingConvention = CallingConvention.StdCall)]
public static extern int MOT_SetProfile(int axisHandle, ref MotionProfile profile);
```

`[StructLayout(LayoutKind.Sequential)]`는 .NET 런타임이 구조체 멤버를 선언한 순서 그대로, C 컴파일러가 하는 것과 동일한 정렬(alignment) 규칙으로 메모리에 배치하도록 강제한다. 이 특성을 빠뜨리면 .NET이 임의로 멤버 순서를 재배치할 수 있어(성능 최적화 목적), 네이티브 DLL이 기대하는 메모리 레이아웃과 어긋나 완전히 잘못된 값을 읽고 쓰게 된다. 값 타입 구조체는 `ref`로 전달하면 되므로, 이 경우 `MOT_SetProfile` 호출부는 별도의 메모리 관리 없이 자연스럽게 작성할 수 있다.

```csharp
var profile = new MotionProfile
{
    AxisNo = 0,
    TargetVelocity = 100.0f,
    Acceleration = 500.0f,
    Deceleration = 500.0f,
    UseSCurve = 1
};
int result = DioBoardApi_MOT_SetProfile(axisHandle, ref profile);
```

### 3.3.4 Unmanaged 메모리 관리

C 함수가 `void*` 포인터로 가변 크기 버퍼를 요구하거나, 구조체 배열을 통째로 넘겨야 하는 경우에는 .NET 가비지 컬렉터가 관리하지 않는 **비관리(unmanaged) 메모리**를 직접 할당해야 한다. `System.Runtime.InteropServices.Marshal` 클래스가 이를 위한 API를 제공한다.

```csharp
[DllImport("VisionBoard.dll", CallingConvention = CallingConvention.StdCall)]
public static extern int VIS_GetFrameBuffer(int cameraHandle, IntPtr bufferPtr, int bufferSize);

public byte[] CaptureFrame(int cameraHandle, int frameSizeBytes)
{
    IntPtr unmanagedBuffer = Marshal.AllocHGlobal(frameSizeBytes);
    try
    {
        int result = VIS_GetFrameBuffer(cameraHandle, unmanagedBuffer, frameSizeBytes);
        if (result != 0)
        {
            throw new InvalidOperationException($"프레임 취득 실패: 에러 코드 {result}");
        }

        byte[] managedBuffer = new byte[frameSizeBytes];
        Marshal.Copy(unmanagedBuffer, managedBuffer, 0, frameSizeBytes);
        return managedBuffer;
    }
    finally
    {
        // 예외가 발생하더라도 반드시 해제되어야 한다.
        Marshal.FreeHGlobal(unmanagedBuffer);
    }
}
```

구조체를 비관리 메모리에 마샬링해야 하는 경우(예: 구조체 포인터를 요구하는 함수)에는 `Marshal.StructureToPtr`와 `Marshal.PtrToStructure`를 사용한다.

```csharp
[DllImport("MotionBoard.dll", CallingConvention = CallingConvention.StdCall)]
public static extern int MOT_GetStatusEx(int axisHandle, IntPtr statusPtr);

[StructLayout(LayoutKind.Sequential)]
public struct AxisStatus
{
    public int IsMoving;
    public int IsInPosition;
    public float CurrentPosition;
    public float CurrentVelocity;
    public int ErrorCode;
}

public AxisStatus GetAxisStatus(int axisHandle)
{
    int size = Marshal.SizeOf<AxisStatus>();
    IntPtr ptr = Marshal.AllocHGlobal(size);
    try
    {
        // 초기값을 넘겨야 하는 API라면 StructureToPtr로 먼저 채운다.
        Marshal.StructureToPtr(default(AxisStatus), ptr, false);

        int result = MOT_GetStatusEx(axisHandle, ptr);
        if (result != 0)
        {
            throw new InvalidOperationException($"상태 조회 실패: 에러 코드 {result}");
        }

        // 네이티브 DLL이 채워 넣은 비관리 메모리를 관리 구조체로 복사한다.
        return Marshal.PtrToStructure<AxisStatus>(ptr);
    }
    finally
    {
        Marshal.FreeHGlobal(ptr);
    }
}
```

**여기서 절대 타협해서는 안 되는 원칙이 `try/finally`로 해제를 보장하는 것이다.** `Marshal.AllocHGlobal`로 할당한 메모리는 가비지 컬렉터의 관리 범위 밖에 있으므로, `Marshal.FreeHGlobal`을 호출하지 않으면 프로세스가 종료될 때까지 절대 회수되지 않는다. 네이티브 함수 호출 중 예외가 발생하는 상황(장비 통신 오류, 잘못된 핸들 등)은 장비 제어 소프트웨어에서 드물지 않게 일어나므로, `try` 블록 없이 "성공 경로"만 가정하고 해제 코드를 작성하면 24시간 연속 가동되는 설비에서 서서히 메모리를 잠식하는 누수로 이어진다. 이런 누수는 하루이틀은 증상이 없다가 며칠에서 몇 주 뒤 메모리 부족으로 설비가 응답 불능 상태에 빠지는 형태로 나타나므로 재현과 원인 추적이 매우 어렵다. 이 문제는 9장에서 프로파일러로 비관리 메모리 누수를 탐지하는 방법과 함께 다시 다룬다.

가능하다면 `try/finally`를 캡슐화한 `SafeHandle` 파생 클래스나, `IDisposable`을 구현한 래퍼로 비관리 리소스를 감싸서 `using` 문으로 관리하는 편이 실수를 구조적으로 방지하는 더 견고한 방법이다.

```csharp
public sealed class UnmanagedBuffer : IDisposable
{
    public IntPtr Pointer { get; }
    public int Size { get; }
    private bool _disposed;

    public UnmanagedBuffer(int size)
    {
        Size = size;
        Pointer = Marshal.AllocHGlobal(size);
    }

    public void Dispose()
    {
        if (!_disposed)
        {
            Marshal.FreeHGlobal(Pointer);
            _disposed = true;
        }
    }
}

// 사용 예
using var buffer = new UnmanagedBuffer(frameSizeBytes);
VIS_GetFrameBuffer(cameraHandle, buffer.Pointer, buffer.Size);
```

### 3.3.5 x86 전용 레거시 DLL을 다뤄야 할 때

일부 오래된 보드 SDK는 32비트(x86) 전용 DLL만 제공한다. 이런 DLL을 64비트(x64)로 빌드된 .NET 프로세스에서 `[DllImport]`로 로드하려고 하면 `BadImageFormatException`이 발생한다. 32비트 DLL은 32비트 프로세스에서만, 64비트 DLL은 64비트 프로세스에서만 로드할 수 있기 때문이다.

해결책은 프로젝트의 빌드 플랫폼 대상을 `AnyCPU`가 아니라 명시적으로 `x86`으로 지정하는 것이다.

```xml
<PropertyGroup>
  <PlatformTarget>x86</PlatformTarget>
</PropertyGroup>
```

이는 사소해 보이지만 실무에서 자주 걸려 넘어지는 지점이다. 개발 PC는 64비트 Windows를 사용하지만, 애플리케이션 자체가 32비트 프로세스로 실행되도록 강제해야 32비트 DLL을 문제없이 로드할 수 있다. 만약 애플리케이션이 여러 개의 하드웨어 모듈과 통신하는데 그중 일부는 x64 DLL, 일부는 x86 DLL만 제공한다면(레거시 장비와 신형 장비가 혼재하는 현장에서 드물지 않게 발생한다), 하나의 프로세스 안에서 비트 수가 다른 두 DLL을 동시에 로드하는 것은 불가능하므로, 별도의 프로세스로 분리하고 IPC(명명된 파이프, 로컬 소켓 등)로 통신을 중계하는 아키텍처까지 고려해야 할 수 있다. 이런 프로세스 분리 설계는 1장에서 다룬 시스템 아키텍처 결정과 맞닿아 있는 문제이므로, 하드웨어 조사 단계에서 각 DLL의 비트 수를 미리 파악해 두는 것이 프로젝트 후반의 큰 재작업을 예방한다.

## 3.4 산업용 필드버스(EtherCAT, CANopen) 및 C# SDK 연동 라이브러리 구성

### 3.4.1 EtherCAT의 개념

EtherCAT(Ethernet for Control Automation Technology)은 표준 이더넷 물리 계층 위에서 동작하는 실시간 산업용 필드버스다. 일반적인 이더넷 네트워크가 스위치를 통해 각 노드와 개별적으로 통신하는 것과 달리, EtherCAT은 **데이지체인(daisy-chain)** 방식으로 슬레이브들을 순서대로 연결한다. 마스터가 하나의 사이클릭 프레임을 네트워크에 내보내면, 이 프레임은 첫 번째 슬레이브를 거쳐 다음 슬레이브로, 그 다음 슬레이브로 순차적으로 흘러가면서 각 슬레이브가 "지나가는 프레임 안의 자기 몫의 데이터 영역"을 읽고 쓴다("on the fly" 처리). 마지막 슬레이브까지 도달한 프레임은 다시 같은 경로를 되짚어 마스터로 돌아온다.

이 구조가 저지연 실시간 통신에 유리한 이유는, 슬레이브 각각이 프레임을 수신해서 소프트웨어 스택으로 올리고 응답을 다시 만들어 내보내는 전통적인 "수신-처리-송신" 과정을 거치지 않고, 슬레이브의 전용 하드웨어(ESC, EtherCAT Slave Controller)가 프레임이 지나가는 동안 하드�웨어 수준에서 즉시 데이터를 읽고 쓰기 때문이다. 처리 지연이 슬레이브 개수에 비례해 누적되지 않고 나노초 단위로 매우 작기 때문에, 수백 개의 슬레이브가 연결되어 있어도 마이크로초 단위의 사이클 타임을 유지할 수 있다. 이런 특성 때문에 EtherCAT은 다축 모션 제어처럼 모든 축이 정확히 동기화되어야 하는 응용에서 널리 채택된다.

### 3.4.2 C# 애플리케이션이 EtherCAT 마스터에 접근하는 현실적인 구조

여기서 정직하게 짚어야 할 부분이 있다. EtherCAT처럼 마이크로초 단위의 사이클 타임을 요구하는 실시간 통신은, 일반적인 Windows의 선점형 스케줄러와 .NET 가비지 컬렉터를 가진 관리 실행 환경에서 직접 구현하기에 근본적으로 부적합하다. GC 일시정지(pause)나 OS 스케줄링 지연이 수 밀리초 단위로 발생할 수 있는데, 이는 EtherCAT이 요구하는 사이클 타임을 훨씬 초과한다. 그래서 실무에서 EtherCAT 마스터 스택은 대개 다음 두 가지 방식 중 하나로 구성된다.

1. **실시간 커널이나 전용 하드웨어에서 마스터를 구동**: EtherCAT 마스터 소프트웨어(사이클릭 프레임 송수신, 슬레이브 상태 관리)는 실시간 확장이 적용된 리눅스 커널이나 전용 산업용 컨트롤러 하드웨어에서 별도의 프로세스/펌웨어로 동작한다. C# 애플리케이션(HMI, 상위 감시/제어 로직)은 이 실시간 마스터와 **IPC(공유 메모리, 명명된 파이프, 로컬 소켓 등)**를 통해 프로세스 데이터(현재 위치, 상태 워드 등)를 주기적으로 교환하는 역할을 맡는다. 즉 C#은 "실시간 제어 루프 자체"가 아니라, 그 실시간 루프가 만들어 내는 데이터를 표시하고 상위 명령을 내리는 감시·제어(supervisory) 계층으로 위치한다.
2. **벤더가 제공하는 관리형(managed) 래퍼 라이브러리 사용**: 대표적인 실제 사례가 Beckhoff의 **TwinCAT.Ads** NuGet 패키지다. Beckhoff의 TwinCAT 런타임이 실시간 EtherCAT 마스터와 PLC 실행 환경을 담당하고, C# 애플리케이션은 ADS(Automation Device Specification) 프로토콜을 통해 TwinCAT 런타임의 변수를 읽고 쓰는 관리형 API(`TwinCAT.Ads` 패키지가 제공하는 `AdsClient` 등)를 사용한다. 이 경우 개발자는 EtherCAT 프레임 자체를 다룰 필요 없이, TwinCAT이 노출하는 심볼(PLC 변수)에 접근하는 훨씬 상위 수준의 API로 작업하게 된다.

오픈소스 진영에는 **SOEM(Simple Open EtherCAT Master)**이라는, C 언어로 작성된 경량 EtherCAT 마스터 스택이 실제로 존재한다. SOEM은 실시간 커널 없이도 일반 운영체제 위에서 EtherCAT 마스터 기능(슬레이브 스캔, 상태 전이, 사이클릭 프로세스 데이터 교환)을 구현할 수 있게 해주는 프로젝트로, 완전한 하드웨어 수준의 실시간성을 요구하지 않는 응용이나 프로토타이핑에서 채택되는 사례가 있다. C#에서 SOEM을 사용하려면 SOEM이 C 라이브러리이므로, 이 장 3.3절에서 다룬 P/Invoke 패턴 그대로 `[DllImport]`를 통해 SOEM이 제공하는 함수(예: 네트워크 어댑터 초기화, 슬레이브 설정, 프로세스 데이터 교환 함수)를 감싸는 래퍼를 직접 작성해야 한다. 이때도 `CallingConvention.Cdecl`(SOEM은 C 표준 규약으로 컴파일되는 경우가 일반적이다) 지정과, 프로세스 데이터 교환에 쓰이는 버퍼의 비관리 메모리 관리(3.3.4절)가 그대로 적용된다.

어떤 방식을 택하든 공통적으로 기억해야 할 설계 원칙은, **C#/.NET 애플리케이션이 EtherCAT의 실시간 사이클 자체를 직접 구동하려 들지 말고, 실시간성이 보장되는 별도의 계층(실시간 커널 프로세스, 벤더 런타임)이 그 역할을 맡도록 아키텍처를 분리**하는 것이다. C#은 그 위에서 감시, 파라미터 설정, 알람 처리, HMI 표시라는, 밀리초~수십 밀리초 수준의 응답성으로 충분한 역할을 담당한다.

### 3.4.3 CANopen의 개념: NMT, PDO, SDO

CANopen은 CAN(Controller Area Network) 물리 계층 위에 정의된 애플리케이션 계층 프로토콜로, 모터 드라이브, 센서, 인코더 등 다양한 산업 장치에서 널리 쓰인다. CANopen을 이해하려면 세 가지 통신 객체의 역할을 구분해야 한다.

- **NMT(Network Management)**: 네트워크에 연결된 노드(장치)들의 상태(Pre-Operational, Operational, Stopped 등)를 마스터가 제어하는 서비스다. 노드를 Operational 상태로 전환시켜야 비로소 PDO를 통한 실제 프로세스 데이터 교환이 시작된다.
- **PDO(Process Data Object)**: 실시간성이 중요한 주기적 데이터(모터의 현재 위치, 목표 속도, 디지털 입력 상태 등)를 오버헤드 없이 빠르게 주고받기 위한 통신 객체다. 사전에 어떤 데이터가 PDO에 매핑될지 구성해 두면, 이후에는 최소한의 CAN 프레임(식별자 + 최대 8바이트 데이터)만으로 데이터를 주기적으로 교환할 수 있다.
- **SDO(Service Data Object)**: 장치의 파라미터(가속도 설정값, 제어 모드, 제조사 고유 설정 등)를 읽고 쓰는 데 사용되는 통신 객체다. 오브젝트 딕셔너리(Object Dictionary)라는 인덱스/서브인덱스 체계로 각 파라미터에 접근하며, PDO에 비해 오버헤드는 크지만 확인 응답(acknowledgement)이 있어 신뢰성이 필요한 설정 변경에 적합하다.

정리하면 PDO는 "빠르지만 가벼운 주기적 데이터 교환", SDO는 "느리지만 확실한 파라미터 설정"이라는 상호 보완적인 역할을 한다. 장비 제어 소프트웨어를 설계할 때는 운전 중 지속적으로 갱신해야 하는 값(속도, 위치 피드백)은 PDO로 매핑하고, 초기화 시점이나 레시피 변경 시(7장에서 다룰 레시피 관리와 연결된다) 한 번씩 설정하면 되는 값은 SDO로 처리하는 것이 정석이다.

C#에서 CANopen을 직접 다루려면, 먼저 물리적인 CAN 인터페이스 카드(USB-CAN 어댑터 등)에 접근할 수 있어야 한다. 실무에서는 자체적으로 CAN 프레임 송수신 드라이버를 밑바닥부터 구현하기보다, **Peak-System의 PCAN-Basic**이나 **Kvaser의 CANlib**처럼 검증된 벤더 SDK를 사용하는 것이 일반적이다. 이들 SDK는 대부분 C/C++ 네이티브 DLL을 기본으로 제공하면서, 동시에 .NET에서 바로 사용할 수 있는 C# 래퍼(관리 어셈블리 또는 P/Invoke 선언이 포함된 헬퍼 클래스)를 함께 배포하는 경우가 많다. 이 경우 개발자는 벤더가 제공하는 C# 래퍼를 이용해 CAN 프레임을 송수신하고, 그 위에 CANopen의 NMT/PDO/SDO 프로토콜 로직(오브젝트 딕셔너리 인덱스 매핑, PDO 매핑 설정 등)을 애플리케이션 계층에서 직접 구현하는 구조가 된다.

### 3.4.4 결론: 필드버스 연동도 결국 P/Invoke 패턴의 재사용

이 절에서 살펴본 EtherCAT과 CANopen 연동은 겉보기에는 시리얼이나 TCP 통신과 전혀 다른 세계처럼 보이지만, 실제로 C# 코드를 작성하는 시점에서는 근본적으로 같은 접근으로 귀결된다. 벤더가 순수 C# 관리 라이브러리(TwinCAT.Ads처럼)를 제공하는 행운의 경우가 아니라면, 결국은

1. 네이티브 DLL(SOEM, PCAN-Basic, CANlib 등)의 함수를 `[DllImport]`로 선언하고,
2. `CallingConvention`을 정확히 맞추고,
3. C 구조체를 `[StructLayout(LayoutKind.Sequential)]`로 매핑하고,
4. 필요하다면 `Marshal.AllocHGlobal`/`FreeHGlobal`로 비관리 메모리를 관리하는,

3.3절에서 다룬 패턴을 그대로 다시 사용하게 된다. 즉 이 장에서 시리얼, TCP, P/Invoke, 필드버스라는 네 개의 절로 나누어 설명했지만, 실무 엔지니어의 관점에서는 "표준 .NET 클래스가 지원하는 통신"(시리얼, TCP)과 "네이티브 DLL을 P/Invoke로 감싸야 하는 통신"(DIO/모션 보드, EtherCAT, CANopen)이라는 두 개의 큰 범주로 요약할 수 있다. 뒤쪽 범주에 속하는 어떤 필드버스나 벤더 SDK를 만나더라도, 3.3절에서 다진 P/Invoke 기본기와 비관리 메모리 관리 원칙만 확실히 체화하고 있다면 새로운 하드웨어 연동은 "낯선 문제"가 아니라 "이미 아는 패턴의 변주"로 접근할 수 있다.

## 요약

- `SerialPort` 클래스는 `BaudRate`/`Parity`/`DataBits`/`StopBits`가 장비와 정확히 일치해야 정상 동작하며, `DataReceived` 이벤트는 스레드 마샬링 문제와 일부 드라이버의 이벤트 누락 이슈 때문에 실무에서는 전용 폴링 스레드로 대체하는 경우가 많다.
- RS-485는 멀티드롭 반이중 버스이므로 장치 주소 기반 프로토콜과 순차 폴링 스케줄러 설계가 필수적이며, 바이트 스트림에서 프레임 경계를 안전하게 분리하려면 상태 머신 기반 파서가 정석적인 해법이다(5장 FSM 개념의 선행 응용).
- `TcpClient`/`NetworkStream`의 `ReadAsync`/`WriteAsync`는 2장의 async/await 패턴을 그대로 재사용할 수 있으며, Modbus-TCP는 MBAP 헤더와 PDU를 바이트 배열로 직접 구성/파싱함으로써 원리를 이해할 수 있다(실무에서는 NModbus 같은 오픈소스 라이브러리도 활용 가능). 네트워크 연결 끊김에는 지수 백오프 기반 자동 재연결 로직이 필요하다.
- P/Invoke는 보드 제조사가 C/C++ 네이티브 DLL만 제공하는 상황에서 필수적인 기술이다. `CallingConvention`을 잘못 지정하면 스택 손상으로 원인 추적이 어려운 크래시가 발생하며, 비관리 메모리는 `Marshal.AllocHGlobal`/`FreeHGlobal`을 `try/finally`로 감싸 반드시 해제해야 한다(9장 메모리 누수 진단과 연결).
- EtherCAT은 데이지체인 구조와 하드웨어 수준의 on-the-fly 처리로 저지연 실시간 통신을 실현하지만, C# 애플리케이션은 대개 실시간 마스터 계층(실시간 커널 프로세스나 TwinCAT.Ads 같은 벤더 런타임)과 IPC로 통신하는 감시·제어 계층으로 위치한다. CANopen의 NMT/PDO/SDO 개념과 PCAN-Basic/CANlib 같은 벤더 SDK 활용도 결국 P/Invoke 패턴의 연장선이다.

## 연습문제

1. RS-485 멀티드롭 버스에 온도 컨트롤러 4대가 연결되어 있다. `SerialPort` 하나로 4대를 순차 폴링하는 `Rs485PollingScheduler`를 완성하고, 하나의 슬레이브가 응답하지 않을 때(타임아웃) 나머지 슬레이브 폴링에 영향을 주지 않도록 예외 처리를 추가해 보라.
2. 3.1.4절의 `FrameParser`를 확장하여, `[STX][ADDR][LEN][PAYLOAD...][CHECKSUM][ETX]` 형태로 장치 주소 필드가 추가된 프레임을 파싱하도록 상태를 하나 더 추가하라. 잘못된 주소를 가진 프레임은 무시하고 파서 상태를 리셋하도록 구현하라.
3. Modbus-TCP의 Function Code 0x10(Write Multiple Registers) 요청 프레임을 생성하는 `BuildWriteMultipleRegistersRequest` 메서드를 작성하라. Byte Count 필드와 Length 필드를 올바르게 계산하는 데 유의하라.
4. 벤더가 제공하는 모션 보드 SDK에 `int MOT_GetPositionArray(int boardHandle, float* positions, int axisCount)`라는 C 함수가 있다고 가정한다. 이 함수를 P/Invoke로 선언하고, `Marshal.AllocHGlobal`로 `float` 배열을 위한 비관리 메모리를 할당한 뒤 `Marshal.Copy`로 관리 배열에 옮기는 코드를 `try/finally`로 안전하게 작성하라.
5. EtherCAT 마스터가 실시간 커널 프로세스에서 동작하고, C# HMI 애플리케이션이 명명된 파이프(Named Pipe)로 100ms 주기 프로세스 데이터를 수신하는 아키텍처를 가정하자. 이 구조에서 파이프 연결이 끊겼을 때 HMI가 취해야 할 방어적 동작(마지막 유효 값 표시 여부, 알람 발생 시점 등)을 설계해 보고, 3.2.4절의 재연결 패턴을 어떻게 응용할 수 있을지 서술하라.

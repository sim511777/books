지금까지 1장에서 레이어드 아키텍처의 큰 그림을 그리고, 2장에서 비동기·멀티스레딩 기반을 다지고, 3장과 4장에서 통신과 모션/IO라는 하드웨어 접점을 구현하고, 5장에서 이 모든 것을 상태 머신으로 조율하고, 6장과 7장에서 HMI와 데이터 관리로 사람과 시스템을 연결하고, 8장에서 상위 시스템과 비전 장비까지 엮었습니다. 설계도는 완성됐지만, 실제로 공장 바닥에 설치되어 24시간 돌아가는 장비 제어 소프트웨어가 되려면 넘어야 할 마지막 관문이 남아 있습니다. 하드웨어 없이도 개발과 테스트가 가능해야 하고, 장시간 무중단 운전 중에도 메모리가 조금씩 새지 않아야 하며, 초당 수백 번씩 오가는 통신 패킷이 가비지 컬렉터를 몰아붙이지 않아야 하고, 마지막으로 고객사 현장에 설치된 뒤 무언가 잘못됐을 때 개발자가 그 자리에 없어도 원인을 추적할 수 있어야 합니다. 이 장에서는 이 네 가지 주제를 순서대로 다루며, 책의 마지막에서 9개 장 전체가 어떻게 하나의 시스템으로 통합되는지도 함께 되짚어봅니다.

## 가상 장비 시뮬레이터(Virtual Hardware Emulator) 구축

### 왜 하드웨어 없이 개발해야 하는가

실무에서 장비 제어 소프트웨어 프로젝트는 대개 하드웨어와 소프트웨어가 동시에 진행됩니다. 모터 스테이지, 카메라, PLC, 각종 센서가 실제로 조립되어 배선까지 끝나는 시점은 흔히 프로젝트 후반부입니다. 그런데 소프트웨어 개발자가 하드웨어가 완성될 때까지 손을 놓고 기다린다면 일정은 절대 맞출 수 없습니다. 게다가 하드웨어가 준비된 이후에도 몇 가지 현실적인 문제가 남습니다.

- **하드웨어는 한 대뿐인데 개발자는 여럿입니다.** 3장의 통신 계층을 작업하는 사람과 6장의 HMI 화면을 작업하는 사람이 동시에 같은 모터 스테이지를 붙잡고 테스트할 수는 없습니다.
- **CI 파이프라인에는 모터가 없습니다.** 9장에서 다룰 자동화 테스트를 빌드 서버에서 매번 돌리려면, 실제 축을 움직이지 않고도 상태 머신과 시퀀스 로직을 검증할 방법이 필요합니다.
- **알람이나 타임아웃처럼 실제 장비에서는 재현하기 어려운 예외 상황**을 의도적으로 발생시켜 5장의 FSM이 올바르게 Alarm 상태로 전이하는지 검증해야 합니다. 진짜 모터를 고의로 고장 낼 수는 없는 노릇입니다.

이 문제를 해결하는 열쇠는 이미 1장에서 마련해 두었습니다. 하드웨어 추상화 계층(HAL)을 P/Invoke 구현체에 직접 의존하지 않고 인터페이스로 분리해 둔 덕분에, 그 인터페이스를 구현하는 **가상의 시뮬레이터 구현체**를 하나 더 만들어 끼워 넣기만 하면 됩니다. 상위의 시퀀스 로직, FSM, HMI 코드는 자신이 실제 보드와 통신하는지 시뮬레이터와 통신하는지 전혀 알 필요가 없습니다.

### HAL 인터페이스를 재사용해 시뮬레이터로 교체하기

4장에서 정의했던 모션 컨트롤러 인터페이스를 다시 가져와 보겠습니다.

```csharp
public interface IMotionController
{
    bool IsConnected { get; }
    double GetCurrentPosition(int axis);
    Task MoveAbsoluteAsync(int axis, double targetPositionMm, MotionProfile profile, CancellationToken ct);
    Task HomeAsync(int axis, CancellationToken ct);
    event EventHandler<AxisAlarmEventArgs> AlarmRaised;
}
```

실제 보드용 구현체 `PciMotionController`는 3장에서 다룬 방식대로 벤더 DLL을 `[DllImport]`로 호출합니다. 이제 같은 인터페이스를 구현하는 시뮬레이터를 추가합니다.

```csharp
public sealed class VirtualMotionController : IMotionController, IDisposable
{
    private readonly ConcurrentDictionary<int, double> _positions = new();
    private readonly ConcurrentDictionary<int, double> _targets = new();
    private readonly Random _random = Random.Shared;
    private readonly PeriodicTimer _tickTimer;
    private readonly Task _simulationLoop;
    private readonly CancellationTokenSource _cts = new();

    public bool IsConnected { get; private set; } = true;

    public event EventHandler<AxisAlarmEventArgs>? AlarmRaised;

    public VirtualMotionController()
    {
        // 10ms 주기로 위치를 갱신한다. 실제 서보 드라이브의 위치 피드백 주기를 흉내낸다.
        _tickTimer = new PeriodicTimer(TimeSpan.FromMilliseconds(10));
        _simulationLoop = Task.Run(() => RunSimulationLoopAsync(_cts.Token));
    }

    public double GetCurrentPosition(int axis) => _positions.GetValueOrDefault(axis, 0.0);

    public Task HomeAsync(int axis, CancellationToken ct)
    {
        _positions[axis] = 0.0;
        return Task.CompletedTask;
    }

    public Task MoveAbsoluteAsync(int axis, double targetPositionMm, MotionProfile profile, CancellationToken ct)
    {
        // 실제 이동은 별도 시뮬레이션 루프에서 시간에 따라 진행된다.
        _targets[axis] = targetPositionMm;
        return Task.CompletedTask;
    }

    private async Task RunSimulationLoopAsync(CancellationToken ct)
    {
        try
        {
            while (await _tickTimer.WaitForNextTickAsync(ct))
            {
                foreach (var axis in _targets.Keys)
                {
                    AdvancePosition(axis);
                }

                // 평균 5분에 한 번꼴로 무작위 알람을 발생시켜 예외 경로를 테스트할 수 있게 한다.
                if (_random.NextDouble() < 0.0000067)
                {
                    RaiseRandomAlarm();
                }
            }
        }
        catch (OperationCanceledException)
        {
            // 정상 종료 경로
        }
    }

    private void AdvancePosition(int axis)
    {
        double current = _positions.GetValueOrDefault(axis, 0.0);
        double target = _targets[axis];
        if (Math.Abs(target - current) < 0.001)
        {
            return;
        }

        // 4장에서 구현한 사다리꼴 속도 프로파일 계산기를 그대로 재사용한다.
        double elapsedSec = 0.010;
        double nextPosition = TrapezoidalProfileCalculator.ComputeNextPosition(
            current, target,
            maxVelocityMmPerSec: 200.0,
            accelerationMmPerSec2: 1000.0,
            elapsedSec: elapsedSec);

        _positions[axis] = nextPosition;
    }

    private void RaiseRandomAlarm()
    {
        int axis = _targets.Keys.FirstOrDefault();
        AlarmRaised?.Invoke(this, new AxisAlarmEventArgs(axis, AlarmCode.ServoFollowingError,
            "시뮬레이션: 서보 추종 오차 초과"));
    }

    public void Dispose()
    {
        _cts.Cancel();
        _tickTimer.Dispose();
        try { _simulationLoop.Wait(TimeSpan.FromSeconds(1)); } catch { /* 종료 대기 중 예외는 무시 */ }
        _cts.Dispose();
    }
}
```

`TrapezoidalProfileCalculator.ComputeNextPosition`은 4장에서 실제 모션 프로파일을 계산하기 위해 만들었던 순수 함수를 그대로 재사용한 것입니다. 시뮬레이터가 "얼마나 그럴듯하게" 움직이는지가 이 재사용 덕분에 실제 장비의 가감속 거동과 거의 동일해집니다. 개발자가 HMI에서 그래프로 위치를 모니터링해도 실제 모터가 움직이는 것과 구분하기 어려울 정도입니다.

### DI 컨테이너 설정 한 줄로 전환하기

2장에서 구성한 DI 컨테이너에 실제 구현체 대신 시뮬레이터를 등록하는 것은 설정 값 하나를 바꾸는 문제로 단순화됩니다.

```csharp
public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddMotionSubsystem(
        this IServiceCollection services, IConfiguration configuration)
    {
        bool useSimulator = configuration.GetValue<bool>("Hardware:UseSimulator");

        if (useSimulator)
        {
            services.AddSingleton<IMotionController, VirtualMotionController>();
            services.AddSingleton<IIoDevice, VirtualIoDevice>();
        }
        else
        {
            services.AddSingleton<IMotionController, PciMotionController>();
            services.AddSingleton<IIoDevice, PciIoDevice>();
        }

        return services;
    }
}
```

`appsettings.json`에는 다음과 같이 플래그만 두면 됩니다.

```json
{
  "Hardware": {
    "UseSimulator": true
  }
}
```

개발 PC에서는 `UseSimulator: true`로 두고 노트북만으로 5장의 시퀀스 로직과 6장의 HMI 화면을 통째로 검증하다가, 실제 장비에 설치할 때는 이 값을 `false`로 바꾸는 것만으로 `PciMotionController`가 주입됩니다. 상위 계층인 FSM이나 ViewModel은 재컴파일은 물론 코드 수정조차 필요 없습니다. 이것이 인터페이스로 계층을 분리해 둔 설계가 마지막에 돌려주는 가장 큰 배당금입니다.

CI 서버에서 자동화 테스트를 돌릴 때도 마찬가지입니다. 테스트 프로젝트에서는 `UseSimulator`를 강제로 `true`로 고정한 테스트 전용 `ServiceProvider`를 구성해, 실제 하드웨어가 전혀 없는 빌드 에이전트에서도 시퀀스 전이 로직과 알람 처리 로직을 매 커밋마다 회귀 테스트할 수 있습니다.

```csharp
[Fact]
public async Task ServoFollowingError_알람_발생시_FSM은_Alarm_상태로_전이한다()
{
    var services = new ServiceCollection();
    services.AddSingleton<IMotionController, VirtualMotionController>();
    services.AddSingleton<EquipmentStateMachine>();
    using var provider = services.BuildServiceProvider();

    var fsm = provider.GetRequiredService<EquipmentStateMachine>();
    var motion = provider.GetRequiredService<IMotionController>();

    var alarmTcs = new TaskCompletionSource();
    fsm.StateChanged += (_, e) =>
    {
        if (e.NewState == EquipmentState.Alarm) alarmTcs.TrySetResult();
    };

    // 시뮬레이터의 알람 이벤트를 직접 발생시켜 실제 하드웨어 없이 예외 경로를 검증한다.
    ((VirtualMotionController)motion).RaiseAlarmForTest(AlarmCode.ServoFollowingError);

    var completed = await Task.WhenAny(alarmTcs.Task, Task.Delay(TimeSpan.FromSeconds(2)));
    Assert.Same(alarmTcs.Task, completed);
}
```

이렇게 시뮬레이터에 테스트 전용 트리거 메서드(`RaiseAlarmForTest`)를 하나 추가해 두면, 무작위 확률에 의존하지 않고도 원하는 시점에 원하는 알람을 결정론적으로 재현할 수 있어 자동화 테스트의 안정성이 크게 올라갑니다.

## GC 튜닝 및 메모리 누수 방지

### 세대별 GC와 장비 제어에 미치는 영향 다시 보기

.NET의 가비지 컬렉터는 객체를 수명에 따라 세대(generation)로 나누어 관리합니다. 새로 할당된 객체는 Gen0에 들어가고, Gen0 수집에서 살아남으면 Gen1로, Gen1 수집에서도 살아남으면 Gen2로 승격됩니다. Gen0 수집은 매우 자주 일어나지만 대상 영역이 작아 보통 1밀리초 미만으로 끝나는 반면, Gen2 수집(풀 GC)은 힙 전체를 훑어야 하므로 수십 밀리초 이상 걸릴 수 있고, 이 시간 동안 관리되는 스레드는 모두 멈춥니다(Stop-the-World).

1장에서 예고했듯, 이 일시정지(pause)는 일반적인 업무용 애플리케이션에서는 사용자가 체감하지 못할 정도로 짧지만, 장비 제어 소프트웨어에서는 이야기가 다릅니다. 모션 명령을 주기적으로 내보내는 제어 루프가 GC로 인해 20~30ms 멈추면, 그 사이 서보 드라이브는 마지막으로 받은 명령을 그대로 유지하다가 추종 오차(following error) 알람을 일으킬 수 있고, 통신 계층에서는 상대 장비가 보낸 응답의 타임아웃이 발생할 수 있습니다. GC 자체를 없앨 수는 없지만, 언제 어떻게 일어나는지를 통제해 그 영향을 최소화하는 것이 이 절의 목표입니다.

### GCSettings.LatencyMode로 완전 블로킹 GC 빈도 줄이기

`System.Runtime.GCSettings.LatencyMode`를 `GCLatencyMode.SustainedLowLatency`로 설정하면, 런타임은 애플리케이션이 지연 시간에 민감하다고 판단하고 Gen2에 대한 블로킹(비동시) 전체 수집을 가능한 한 피하려고 시도합니다. 대신 백그라운드에서 동시(concurrent) 방식으로 Gen2를 수집해, 애플리케이션 스레드를 완전히 멈추지 않고도 메모리를 회수합니다.

```csharp
public static class Program
{
    public static void Main(string[] args)
    {
        // 장비 제어 애플리케이션 시작 시 가장 먼저 설정한다.
        GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency;

        var host = BuildHost(args);
        host.Run();
    }
}
```

다만 이 설정에는 명확한 한계가 있습니다.

- **메모리 압박이 심해지면 무력화됩니다.** 시스템 전체의 가용 메모리가 부족해지면, 런타임은 `SustainedLowLatency` 설정을 무시하고서라도 블로킹 풀 GC를 강제로 수행합니다. 즉 이 설정은 "충분한 메모리가 있다는 전제 하에" 지연 시간을 줄여주는 것이지, 메모리 관리를 소홀히 해도 되는 면죄부가 아닙니다.
- **메모리 사용량이 늘어납니다.** 동시 수집을 위해 런타임이 더 많은 힙 공간을 확보해 두므로, 같은 작업 부하에서도 워킹 셋(working set)이 커집니다. 임베디드급 산업용 PC처럼 메모리가 제한적인 환경에서는 이 트레이드오프를 반드시 검증해야 합니다.
- **아주 짧고 결정적인 구간에는 부족합니다.** 예를 들어 비전 트리거와 모션 동기화처럼 수 밀리초 단위의 확정적 타이밍이 필요한 극히 짧은 구간이라면, `GC.TryStartNoGCRegion`으로 그 구간 동안 GC 자체를 아예 억제하는 방법을 함께 검토할 수 있습니다.

```csharp
public void ExecuteCriticalMotionWindow(Action criticalWork)
{
    // 이 구간에서는 최대 4MB까지 할당해도 GC가 개입하지 않도록 요청한다.
    bool noGcStarted = GC.TryStartNoGCRegion(totalSize: 4 * 1024 * 1024, disallowFullBlockingGC: true);
    try
    {
        criticalWork();
    }
    finally
    {
        if (noGcStarted)
        {
            GC.EndNoGCRegion();
        }
    }
}
```

`GC.TryStartNoGCRegion`은 지정한 크기만큼 미리 메모리를 확보해 두고, 그 구간 안에서는 GC가 끼어들지 않도록 시도합니다. `disallowFullBlockingGC: true`를 지정하면 예산을 초과하더라도 블로킹 GC로 전환하는 대신 `InvalidOperationException`을 던지도록 강제할 수 있어, "이 구간에서 GC가 몰래 끼어들었는지"를 눈치채지 못한 채 넘어가는 상황을 방지합니다. 다만 이 API는 짧고 예측 가능한 임계 구간에만 국한해서 써야 합니다. 구간이 길어지거나 할당량을 예측하기 어려우면 예산을 초과해 오히려 예외 처리 로직이 복잡해집니다.

### Server GC와 Workstation GC 중 무엇을 선택할 것인가

.NET은 두 가지 GC 모드를 제공합니다. `csproj`나 `runtimeconfig.json`을 통해 다음과 같이 설정합니다.

```xml
<PropertyGroup>
  <ServerGarbageCollection>false</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

이 설정은 빌드 시 `bin` 폴더에 함께 생성되는 `*.runtimeconfig.json`에 다음과 같이 반영됩니다.

```json
{
  "runtimeOptions": {
    "configProperties": {
      "System.GC.Server": false,
      "System.GC.Concurrent": true
    }
  }
}
```

Server GC는 CPU 코어 수만큼 힙을 나누어 각 코어가 병렬로 수집하도록 설계되어 있어, ASP.NET Core 같이 초당 수천 건의 요청을 처리하며 처리량(throughput)이 최우선인 서버 환경에 적합합니다. 하지만 코어마다 별도의 힙과 스레드를 유지하기 때문에 메모리 기본 사용량이 크고, 수집이 시작되면 상대적으로 더 긴 일시정지가 발생하는 경향이 있습니다.

반면 Workstation GC는 애플리케이션 스레드와 같은 우선순위로 동작하며 반응성(responsiveness)에 최적화되어 있고, `Concurrent GC`(백그라운드 GC라고도 부릅니다)를 함께 켜면 Gen2 수집의 상당 부분을 별도 스레드에서 애플리케이션을 멈추지 않고 수행합니다. 장비 제어 소프트웨어는 대개 한 대의 산업용 PC에서 단일 프로세스로 실행되고, 수천 개의 동시 요청을 처리하는 것이 아니라 소수의 축과 IO를 낮은 지연 시간으로 제어하는 것이 목표이므로, **일반적으로 Workstation GC + Concurrent 조합이 응답성 측면에서 더 유리합니다.** 이는 6장에서 다룬 WPF 애플리케이션이 기본적으로 Workstation GC를 사용하는 것과도 방향이 일치합니다. 코어가 아주 많은 서버급 산업용 PC에 여러 장비를 동시에 제어하는 소프트웨어를 올리는 특수한 경우라면 Server GC를 프로파일링을 통해 검토해볼 수는 있지만, 이는 예외적인 상황이지 기본 선택은 아닙니다.

### 메모리 누수의 흔한 원인과 진단

GC가 아무리 잘 튜닝되어 있어도, 애플리케이션 코드가 더 이상 필요 없는 객체를 계속 참조하고 있다면 GC는 그 객체를 회수할 수 없습니다. 이것이 관리되는 언어에서도 "메모리 누수"가 발생하는 근본 원인입니다. 장비 제어 소프트웨어처럼 몇 주, 몇 달씩 재시작 없이 돌아가는 프로그램에서는 하루 몇 킬로바이트씩만 새는 누수도 결국 메모리 부족으로 인한 예기치 않은 정지로 이어집니다.

**원인 1: 이벤트 구독 후 해제하지 않음**

가장 흔하고 가장 발견하기 어려운 누수입니다. C#의 이벤트 구독(`+=`)은 내부적으로 구독자(이 예제에서는 델리게이트가 감싸는 대상 객체)에 대한 강한 참조를 발행자(publisher) 쪽에 남깁니다. 장수명 객체가 단명 객체의 이벤트를 구독하면서 구독 해제(`-=`)를 하지 않으면, 발행자가 살아 있는 한 GC는 구독자를 회수하지 못합니다.

```csharp
// 문제: MainViewModel(장수명)이 AxisViewModel(단명)의 이벤트를 구독한다
public class MainViewModel
{
    private readonly List<AxisViewModel> _axisViewModels = new();

    public void AddAxis(AxisViewModel axisVm)
    {
        axisVm.PositionChanged += OnAxisPositionChanged; // 구독만 하고
        _axisViewModels.Add(axisVm);
    }

    public void RemoveAxis(AxisViewModel axisVm)
    {
        _axisViewModels.Remove(axisVm);
        // -= 를 빠뜨리면 axisVm은 여전히 OnAxisPositionChanged의 대상으로 남아,
        // MainViewModel의 델리게이트 필드가 axisVm을 계속 붙잡고 있게 된다.
    }

    private void OnAxisPositionChanged(object? sender, PositionChangedEventArgs e) { }
}
```

이 시나리오가 특히 위험한 이유는 방향이 직관과 반대이기 때문입니다. `MainViewModel`이 `AxisViewModel`을 참조하는 것은 자연스러워 보이지만, 실제로는 `AxisViewModel.PositionChanged`라는 이벤트 필드 안에 `MainViewModel.OnAxisPositionChanged`를 가리키는 델리게이트가 저장되면서, **`AxisViewModel`(발행자)이 `MainViewModel`(구독자)을 참조하는 것이 아니라, 이벤트 구독 관계 자체가 항상 발행자 → 구독자 방향의 참조를 만든다**는 점을 놓치기 쉽습니다. `RemoveAxis`를 호출해 리스트에서는 지웠지만, `axisVm` 객체가 살아있는 다른 코드(예: 6장의 화면 트리, 혹은 이 예제처럼 여전히 참조를 들고 있는 다른 컬렉션)에 남아 있다면, `axisVm`은 `MainViewModel`을 계속 구독한 채로 남아 두 객체 모두 회수되지 않습니다. 특히 이 예제처럼 짧은 주기로 축을 교체하며 표시하는 화면에서는 교체할 때마다 이전 `AxisViewModel`이 누적되어 메모리 사용량이 시간이 지날수록 계단식으로 증가하는 패턴을 보입니다.

해결책은 구독한 쪽에서 명시적으로 해제하는 것입니다. `IDisposable`을 구현해 해제 시점을 명확히 하는 것이 가장 안전합니다.

```csharp
public class MainViewModel
{
    private readonly List<AxisViewModel> _axisViewModels = new();

    public void RemoveAxis(AxisViewModel axisVm)
    {
        axisVm.PositionChanged -= OnAxisPositionChanged; // 반드시 짝을 맞춘다
        _axisViewModels.Remove(axisVm);
    }

    private void OnAxisPositionChanged(object? sender, PositionChangedEventArgs e) { }
}
```

이벤트 해제를 코드 곳곳에서 빠뜨리지 않고 관리하기 어렵다면, `WeakEventManager`를 사용해 구독 자체를 약한 참조로 만드는 방법도 있습니다. WPF는 `System.Windows.WeakEventManager<TEventSource, TEventArgs>`를 기본 제공하며, 이를 사용하면 구독자가 다른 이유로 이미 회수 대상이 된 경우 이벤트 구독 관계가 그 회수를 막지 않습니다.

```csharp
WeakEventManager<AxisViewModel, PositionChangedEventArgs>.AddHandler(
    axisVm, nameof(AxisViewModel.PositionChanged), OnAxisPositionChanged);
```

진단 측면에서는, 의심되는 화면을 반복해서 열고 닫은 뒤 `GC.Collect()`와 `GC.GetTotalMemory(forceFullCollection: true)`를 이용해 메모리 사용량이 반복 횟수에 비례해 계속 늘어나는지 확인하는 간단한 회귀 테스트를 작성해 둘 수 있습니다.

```csharp
[Fact]
public void AxisViewModel_반복_생성후_해제하면_메모리가_증가하지_않는다()
{
    var mainVm = new MainViewModel();

    long Snapshot()
    {
        GC.Collect();
        GC.WaitForPendingFinalizers();
        GC.Collect();
        return GC.GetTotalMemory(forceFullCollection: true);
    }

    Snapshot(); // 워밍업

    long before = Snapshot();
    for (int i = 0; i < 1000; i++)
    {
        var axisVm = new AxisViewModel(axisNumber: i % 4);
        mainVm.AddAxis(axisVm);
        mainVm.RemoveAxis(axisVm);
    }
    long after = Snapshot();

    // 약간의 오차는 허용하되, 1000개의 AxisViewModel이 통째로 살아남는 수준이면 실패해야 한다
    Assert.True(after - before < 200_000, $"메모리 증가량이 비정상적으로 큽니다: {after - before} bytes");
}
```

**원인 2: Timer/Thread를 제대로 정리하지 않음**

`System.Threading.Timer`나 `System.Timers.Timer`는 내부적으로 콜백을 실행하기 위해 대상 객체에 대한 참조를 유지합니다. `Dispose()`를 호출하지 않고 타이머를 담고 있던 객체를 그냥 놓아버리면, 타이머는 계속 살아서 콜백을 실행하며 그 콜백이 참조하는 객체 그래프 전체를 회수되지 못하게 붙잡습니다.

```csharp
// 문제: Dispose를 구현하지 않아 타이머가 계속 살아있는다
public class HeartbeatMonitor
{
    private readonly Timer _timer;

    public HeartbeatMonitor(ICommDriver driver)
    {
        _timer = new Timer(_ => CheckHeartbeat(driver), null, 0, 1000);
    }

    private void CheckHeartbeat(ICommDriver driver) { /* ... */ }
}
```

```csharp
// 해결: IDisposable을 구현해 타이머를 명시적으로 해제한다
public class HeartbeatMonitor : IDisposable
{
    private readonly Timer _timer;
    private bool _disposed;

    public HeartbeatMonitor(ICommDriver driver)
    {
        _timer = new Timer(_ => CheckHeartbeat(driver), null, 0, 1000);
    }

    private void CheckHeartbeat(ICommDriver driver) { /* ... */ }

    public void Dispose()
    {
        if (_disposed) return;
        _disposed = true;
        _timer.Dispose();
    }
}
```

2장에서 다룬 것처럼 직접 `Thread`를 생성해 무한 루프를 도는 백그라운드 작업도 마찬가지입니다. `CancellationToken`으로 종료 신호를 보낼 방법이 없는 스레드는, 그 스레드가 참조하는 모든 객체와 함께 프로세스가 끝날 때까지 살아있게 됩니다. 스레드나 `Task.Run`으로 시작한 장기 실행 루프에는 반드시 `CancellationTokenSource`를 짝지어 두고, 컨테이너 객체의 `Dispose()`에서 취소와 종료 대기를 수행해야 합니다.

**원인 3: static 컬렉션에 계속 항목을 추가만 함**

7장에서 다룬 알람 이력이나 트레이스 로그처럼 시간에 따라 계속 쌓이는 데이터를 `static` 컬렉션에 무심코 담아두면, 애플리케이션 수명 전체 동안 그 컬렉션은 절대 줄어들지 않습니다.

```csharp
// 문제: static 컬렉션은 애플리케이션이 종료될 때까지 절대 GC 대상이 되지 않는다
public static class DiagnosticLog
{
    public static readonly List<string> Entries = new();

    public static void Append(string message)
    {
        Entries.Add($"{DateTime.Now:O} {message}");
        // 제거 로직이 없다. 장비가 몇 주간 가동되면 이 리스트는 수백만 항목으로 자란다.
    }
}
```

`static` 필드가 참조하는 객체는 GC의 루트(root) 중 하나로 취급되어, 그 안의 항목들은 애플리케이션이 종료되기 전까지는 절대로 회수되지 않습니다. 진단은 비교적 쉽습니다. 장시간 실행 후 메모리 사용량이 꾸준히 우상향한다면 `static`으로 선언된 컬렉션 필드부터 의심해야 합니다. 해결책은 두 가지 방향으로 나뉩니다. 진단용 로그처럼 최근 데이터만 필요하다면 크기 상한을 둔 원형 버퍼(circular buffer)로 바꾸고, 7장에서 다룬 것처럼 영구 보관이 필요한 데이터라면 메모리에 무한정 쌓아두지 말고 주기적으로 데이터베이스나 파일로 플러시한 뒤 메모리에서는 비워야 합니다.

```csharp
// 해결: 크기 상한을 둔 링 버퍼로 교체한다
public static class DiagnosticLog
{
    private const int MaxEntries = 5000;
    private static readonly object _lock = new();
    private static readonly Queue<string> _entries = new(MaxEntries);

    public static void Append(string message)
    {
        lock (_lock)
        {
            if (_entries.Count >= MaxEntries)
            {
                _entries.Dequeue();
            }
            _entries.Enqueue($"{DateTime.Now:O} {message}");
        }
    }

    public static IReadOnlyList<string> Snapshot()
    {
        lock (_lock)
        {
            return _entries.ToArray();
        }
    }
}
```

## Memory/Span을 활용한 고성능 바이트 패킷 파싱 최적화

### 배열 슬라이싱이 만드는 GC 압박

3장에서 통신 프로토콜을 파싱할 때, 수신한 `byte[]` 버퍼에서 헤더와 페이로드를 분리하기 위해 `Array` 조각을 잘라내는 방식을 사용했다면 다음과 비슷한 코드였을 것입니다.

```csharp
// 문제: 호출할 때마다 새 배열을 힙에 할당한다
public ParsedPacket ParsePacket(byte[] buffer)
{
    byte[] header = buffer.Take(8).ToArray();      // 새 배열 할당
    byte[] payload = buffer.Skip(8).ToArray();     // 새 배열 할당

    ushort commandId = BitConverter.ToUInt16(header, 0);
    int length = BitConverter.ToInt32(header, 2);

    return new ParsedPacket(commandId, length, payload);
}
```

이 코드는 기능적으로는 올바르게 동작하지만, 패킷 하나를 파싱할 때마다 최소 두 개의 새 배열을 Gen0 힙에 할당합니다. 통신 속도가 초당 수십~수백 건 수준이라면 눈에 띄지 않을 수 있지만, 고속 IO 스캔이나 비전 데이터 스트리밍처럼 초당 수천 건의 패킷을 처리해야 하는 구간에서는 이 할당들이 쌓여 Gen0 수집을 훨씬 더 자주 유발합니다. Gen0 수집 자체는 짧지만, 앞서 다룬 것처럼 그 잦은 중단조차 실시간성이 중요한 제어 루프에는 누적된 지터(jitter)로 작용합니다. 즉 2절에서 다룬 GC 튜닝만으로는 근본적인 처방이 되지 못하며, 애초에 할당 자체를 줄이는 것이 더 근본적인 해법입니다.

### Span&lt;T&gt;와 Memory&lt;T&gt;

`Span<T>`(그리고 읽기 전용 버전인 `ReadOnlySpan<T>`)는 배열이나 스택 메모리의 연속된 구간을 힙 할당 없이 참조할 수 있게 해주는 타입입니다. `buffer.AsSpan(0, 8)`은 새 배열을 만들지 않고, 기존 `buffer` 배열의 0번부터 8바이트를 "가리키는" 뷰(view)만 만듭니다.

```csharp
// 개선: 배열을 복사하지 않고 기존 버퍼를 그대로 가리키는 뷰만 만든다
public ParsedPacketHeader ParseHeader(ReadOnlySpan<byte> buffer)
{
    ReadOnlySpan<byte> header = buffer.Slice(0, 8); // 할당 없음, 그저 포인터 + 길이 쌍
    ushort commandId = BinaryPrimitives.ReadUInt16BigEndian(header.Slice(0, 2));
    int length = BinaryPrimitives.ReadInt32BigEndian(header.Slice(2, 4));

    return new ParsedPacketHeader(commandId, length);
}
```

`Span<T>`는 `ref struct`로 선언되어 있어 항상 스택에만 존재할 수 있습니다. 이 제약 덕분에 컴파일러는 `Span<T>`가 가리키는 메모리보다 더 오래 살아남는 일이 없도록(즉 힙에 저장된 뒤 원본 배열이 회수된 후에도 참조가 남는 등의 문제가 없도록) 강력하게 보장할 수 있지만, 대신 클래스의 필드로 저장할 수 없고 `async` 메서드 안에서 `await` 경계를 넘나들며 사용할 수도 없습니다. `async` 메서드는 `await`할 때마다 컴파일러가 상태 기계를 힙에 만들어 필요한 지역 변수를 그 안에 담아두는데, `Span<T>`는 힙에 존재할 수 없으므로 이 변환 자체가 불가능하기 때문입니다.

수신 루프처럼 `await socket.ReceiveAsync(...)`을 거쳐야 하는 코드에서 버퍼를 다뤄야 한다면 `Memory<T>`(그리고 `ReadOnlyMemory<T>`)를 사용합니다. `Memory<T>`는 일반 구조체(struct)이므로 힙에 저장할 수 있고 필드로 보관하거나 `async` 메서드를 넘나들며 전달할 수 있습니다. 실제로 파싱 로직을 실행하는 순간에만 `Memory<T>.Span`으로 `Span<T>`를 얻어 짧게 사용하는 것이 일반적인 패턴입니다.

```csharp
public class PacketReceiver
{
    private readonly Socket _socket;
    private Memory<byte> _receiveBuffer; // 필드로 보관 가능 (Span은 불가능)

    public PacketReceiver(Socket socket, Memory<byte> buffer)
    {
        _socket = socket;
        _receiveBuffer = buffer;
    }

    public async Task<ParsedPacketHeader> ReceiveAndParseAsync(CancellationToken ct)
    {
        int received = await _socket.ReceiveAsync(_receiveBuffer, SocketFlags.None, ct);

        // await 경계를 넘어온 뒤, 실제 파싱 순간에만 Span으로 변환해 사용한다.
        ReadOnlySpan<byte> data = _receiveBuffer.Span.Slice(0, received);
        return ParseHeader(data);
    }
}
```

### BinaryPrimitives로 엔디안을 명시적으로 다루기

3장에서 다룬 것처럼 장비 제어 통신 프로토콜은 벤더에 따라 빅 엔디안과 리틀 엔디안이 뒤섞여 있는 경우가 많습니다. `System.Buffers.Binary.BinaryPrimitives`는 `Span<byte>`를 대상으로 바이트 순서를 명시적으로 지정해 읽고 쓸 수 있는 정적 메서드를 제공하며, 배열을 할당하지 않고 동작하므로 `Span<T>`와 함께 쓰기에 이상적입니다.

```csharp
public readonly struct PacketHeader
{
    public const int Size = 12;

    public ushort CommandId { get; init; }
    public int PayloadLength { get; init; }
    public uint SequenceNumber { get; init; }

    public static PacketHeader Parse(ReadOnlySpan<byte> span)
    {
        if (span.Length < Size)
        {
            throw new ArgumentException("헤더 파싱에 필요한 최소 길이를 만족하지 않습니다.", nameof(span));
        }

        return new PacketHeader
        {
            // 장비가 빅 엔디안(네트워크 바이트 순서)으로 통신하는 경우
            CommandId = BinaryPrimitives.ReadUInt16BigEndian(span.Slice(0, 2)),
            PayloadLength = BinaryPrimitives.ReadInt32BigEndian(span.Slice(2, 4)),
            SequenceNumber = BinaryPrimitives.ReadUInt32BigEndian(span.Slice(6, 4)),
        };
    }

    public void WriteTo(Span<byte> destination)
    {
        BinaryPrimitives.WriteUInt16BigEndian(destination.Slice(0, 2), CommandId);
        BinaryPrimitives.WriteInt32BigEndian(destination.Slice(2, 4), PayloadLength);
        BinaryPrimitives.WriteUInt32BigEndian(destination.Slice(6, 4), SequenceNumber);
    }
}
```

`BitConverter`와 달리 `BinaryPrimitives`는 `ReadUInt16BigEndian`/`ReadUInt16LittleEndian`처럼 메서드 이름 자체에 바이트 순서가 드러나므로, 코드를 읽는 사람이 실행 중인 CPU 아키텍처의 기본 엔디안이 무엇인지 신경 쓸 필요 없이 프로토콜 스펙에 적힌 바이트 순서를 그대로 코드에 옮길 수 있습니다. 이는 리틀 엔디안 환경에서 개발하다가 빅 엔디안 프로토콜을 다루는 벤더 장비를 만났을 때 흔히 발생하는 바이트 순서 버그를 원천적으로 차단해줍니다.

### ArrayPool&lt;byte&gt;.Shared로 버퍼 재사용하기

`Span<T>`와 `Memory<T>`가 이미 존재하는 배열을 다시 자르는 비용을 없애준다면, `System.Buffers.ArrayPool<T>`는 애초에 그 배열 자체를 새로 할당하는 비용을 없애줍니다. 수신 루프처럼 반복적으로 임시 버퍼가 필요한 상황에서, 매번 `new byte[4096]`으로 새 배열을 만드는 대신 풀에서 배열을 빌려 쓰고 반납하는 패턴을 사용합니다.

```csharp
public async Task ReceiveLoopAsync(Socket socket, IPacketHandler handler, CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        byte[] buffer = ArrayPool<byte>.Shared.Rent(minimumLength: 4096);
        try
        {
            int received = await socket.ReceiveAsync(buffer.AsMemory(0, 4096), SocketFlags.None, ct);
            if (received == 0)
            {
                break; // 연결 종료
            }

            handler.HandlePacket(buffer.AsSpan(0, received));
        }
        finally
        {
            // 반드시 반납한다. 반납하지 않으면 풀의 이점이 사라지고 일반 GC 대상 객체와 다를 바 없어진다.
            ArrayPool<byte>.Shared.Return(buffer, clearArray: true);
        }
    }
}
```

`ArrayPool<byte>.Shared.Rent`가 반환하는 배열의 길이는 요청한 `minimumLength`보다 클 수 있다는 점에 주의해야 합니다. 풀은 2의 거듭제곱 단위로 관리되는 내부 버킷에서 배열을 꺼내주기 때문에, 실제로 사용할 길이는 항상 `AsSpan(0, received)`처럼 명시적으로 잘라서 사용해야 합니다. 또한 `Return`에 `clearArray: true`를 지정하면 반납 시 배열 내용을 0으로 초기화하는데, 이전 통신 내용이 다음 대여자에게 그대로 노출되면 곤란한 보안 민감 데이터를 다뤘다면 반드시 켜야 하지만, 그 초기화 비용 자체는 성능에 영향을 주므로 일반적인 제어 패킷처럼 민감하지 않은 데이터라면 `false`로 두어 불필요한 초기화 비용을 아낄 수 있습니다.

`try`/`finally`로 반납을 보장하는 것이 이 패턴의 핵심입니다. 예외가 발생해 `Return`이 호출되지 않으면 그 배열은 조용히 풀에서 사라지고, 결국 일반적인 `new byte[]`와 다를 바 없이 GC에 의존하게 되어 풀을 쓰는 의미가 없어집니다. 이 세 가지 도구, 즉 `Span<T>`/`Memory<T>`로 불필요한 복사를 없애고, `BinaryPrimitives`로 파싱 로직을 명확하고 할당 없이 작성하고, `ArrayPool<T>`로 버퍼 자체의 재할당을 줄이는 조합은 2절에서 다룬 GC 튜닝과 상호 보완적입니다. GC 설정은 "GC가 일어날 때의 영향"을 줄이는 것이고, 이번 절의 기법들은 애초에 "GC가 일어날 빈도" 자체를 줄이는 것입니다.

## 현장 셋업(Site Commissioning) 및 예외 복구 디버깅 노하우

### 현장 셋업이란 무엇인가

현장 셋업(Site Commissioning)은 개발실에서 완성한 장비를 실제 고객 공장으로 옮겨 설치하고 처음 가동해 정상 양산 가능 상태로 인수인계하는 단계를 말합니다. 개발실에서는 문제없이 몇 주씩 잘 돌아가던 소프트웨어가 현장에만 가면 낯선 문제를 일으키는 경우가 드물지 않은데, 여기에는 몇 가지 전형적인 이유가 있습니다.

- **전기적 노이즈로 인한 통신 오류.** 현장의 다른 대전력 설비(모터 인버터, 용접기 등)에서 발생하는 전자기 간섭이 3장에서 다룬 시리얼이나 이더넷 통신 케이블에 노이즈를 유발해, 개발실에서는 전혀 보지 못했던 CRC 오류나 타임아웃이 간헐적으로 발생할 수 있습니다. 접지와 실드 케이블 시공이 원인인 경우가 많지만, 소프트웨어 쪽에서도 재시도 로직과 오류 카운트 로깅이 충실해야 원인 파악에 걸리는 시간을 줄일 수 있습니다.
- **실제 기구物 공차로 인한 티칭 재조정.** 4장에서 다룬 위치 좌표나 오프셋 값은 개발실의 지그(jig)를 기준으로 잡혀 있지만, 실제 양산 라인에 설치된 기구물은 조립 공차, 설치 수평도, 지그 개체 차이 등으로 미세하게 다릅니다. 현장에서는 반드시 원점 복귀와 주요 좌표를 다시 티칭(teaching)해야 하며, 이 과정을 코드 재배포 없이 설정 파일이나 레시피(7장)만 바꿔서 반영할 수 있도록 설계해 두었는지가 셋업 소요 시간을 좌우합니다.
- **현장 네트워크 환경 차이.** 8장에서 다룬 상위 시스템(MES/SECS-GEM 호스트) 연동은 개발실에서는 격리된 테스트 네트워크로 검증하지만, 실제 공장 네트워크는 방화벽 정책, 고정 IP 대역, 다른 장비와의 IP 충돌, VLAN 구성 등이 완전히 다를 수 있습니다. 연결 문자열이나 포트 번호를 코드에 하드코딩하지 않고 설정 파일로 분리해 두는 원칙은 이런 상황에서 큰 차이를 만듭니다.

### 원격 디버깅과 로그 수집 전략

현장에 개발 환경을 통째로 들고 갈 수 없는 상황은 흔합니다. 원격지 고객사 공장은 보안 정책상 외부 네트워크 접속 자체가 막혀 있는 경우도 많고, 설령 원격 데스크톱이 가능하더라도 디버거를 붙여 한 줄씩 실행하며 원인을 찾는 방식은 현실적이지 않습니다. 결국 문제가 발생했을 때 "그 순간에 무슨 일이 있었는지"를 로그만으로 완전히 재구성할 수 있어야 합니다. 7장에서 구축한 로깅 시스템을 현장 대응이라는 관점에서 다시 설계 원칙으로 정리하면 다음과 같습니다.

- **시퀀스 실행마다 상관관계 ID(Correlation ID)를 부여합니다.** 한 번의 웨이퍼/기판 처리 시퀀스에 고유 ID를 매기고, 그 시퀀스 동안 발생하는 모든 로그(모션 명령, 통신 송수신, 알람, IO 상태 변화)에 이 ID를 함께 기록하면, 나중에 문제가 된 특정 처리 건 하나만 필터링해서 시간 순서대로 훑어볼 수 있습니다.

```csharp
using (LogContext.PushProperty("SequenceId", sequenceId))
{
    _logger.LogInformation("웨이퍼 로드 시퀀스 시작: 슬롯 {SlotNumber}", slotNumber);
    await _motionController.MoveAbsoluteAsync(axis: 1, targetPositionMm, profile, ct);
    _logger.LogInformation("웨이퍼 로드 시퀀스 완료");
}
```

- **통신 원본 프레임을 오류 발생 시점 전후로 남깁니다.** 파싱된 결과만 로그로 남기면 "왜 파싱이 실패했는지"를 재구성할 수 없습니다. 3장에서 다룬 통신 드라이버에 오류 발생 시 최근 송수신한 원본 바이트를 16진수로 덤프하는 링 버퍼를 두면, CRC 오류나 프로토콜 위반이 발생했을 때 그 직전 몇 개의 프레임을 그대로 로그에 남길 수 있습니다.

```csharp
private readonly RingBuffer<byte[]> _recentFrames = new(capacity: 20);

private void OnFrameReceived(byte[] frame)
{
    _recentFrames.Add(frame);
}

private void OnCommunicationError(Exception ex)
{
    string dump = string.Join(" | ", _recentFrames.Select(f => Convert.ToHexString(f)));
    _logger.LogError(ex, "통신 오류 발생. 최근 프레임: {RecentFrames}", dump);
}
```

- **로그 레벨을 재배포 없이 원격으로 조정할 수 있어야 합니다.** 평소에는 `Information` 레벨로 조용히 돌아가다가, 현장에서 문제가 재현되기 시작하면 `Debug`나 `Trace` 레벨로 즉시 전환해 더 상세한 정보를 수집할 수 있어야 합니다. `Microsoft.Extensions.Logging`의 `LoggingLevelSwitch`(Serilog 사용 시)나 `IOptionsMonitor<LoggerFilterOptions>`를 활용해, 설정 파일을 원격 접속으로 수정하는 것만으로 애플리케이션 재시작 없이 로그 레벨이 바뀌도록 구성해 두면 현장에서 재현이 드문 문제를 만났을 때 결정적인 도움이 됩니다.
- **로그를 로컬 파일과 함께 압축 아카이브로 순환(rotate)합니다.** 현장에서 며칠씩 로그를 쌓다가 결국 네트워크가 되는 시점에 압축된 로그 묶음 하나만 전달받으면 원격 분석이 가능합니다. 파일 크기나 일 단위로 로그 파일을 순환시키고 오래된 파일은 압축해 보관하는 정책은 7장에서 다룬 데이터 관리 원칙과 동일한 맥락입니다.

### 전역 예외 처리와 안전한 정지 상태로의 전환

아무리 방어적으로 코드를 작성해도 예상치 못한 예외는 발생합니다. 문제는 그 예외가 애플리케이션을 아무 대응 없이 죽여버리느냐, 아니면 안전하게 정지한 뒤 사람에게 알리느냐입니다. .NET은 처리되지 않은 예외를 마지막으로 붙잡을 수 있는 전역 훅을 제공합니다.

```csharp
public static class Program
{
    public static void Main(string[] args)
    {
        AppDomain.CurrentDomain.UnhandledException += OnAppDomainUnhandledException;
        TaskScheduler.UnobservedTaskException += OnUnobservedTaskException;

        var app = new App();
        app.DispatcherUnhandledException += OnDispatcherUnhandledException;
        app.Run();
    }

    private static void OnAppDomainUnhandledException(object sender, UnhandledExceptionEventArgs e)
    {
        var ex = e.ExceptionObject as Exception;
        Log.Fatal(ex, "처리되지 않은 예외로 프로세스가 종료됩니다. IsTerminating={IsTerminating}", e.IsTerminating);

        // 이 시점에서는 프로세스 종료를 막을 수 없다. 남은 시간 동안 할 수 있는 최선은
        // 5장의 FSM에 안전 정지를 시도하고 로그를 디스크로 강제 플러시하는 것뿐이다.
        TryEmergencyStop();
        Log.CloseAndFlush();
    }

    private static void OnDispatcherUnhandledException(object sender, DispatcherUnhandledExceptionEventArgs e)
    {
        Log.Error(e.Exception, "UI 스레드에서 처리되지 않은 예외가 발생했습니다.");

        // 5장에서 정의한 Alarm 상태로 강제 전이시켜 장비를 안전한 정지 상태로 만든다.
        EquipmentStateMachineHost.Instance.RequestEmergencyAlarm(e.Exception);

        // 사용자에게 상황을 알린다. 예외를 조용히 삼키고 아무 일 없었다는 듯 계속 진행하지 않는다.
        MessageBox.Show(
            $"예상치 못한 오류가 발생하여 장비를 안전 정지 상태로 전환했습니다.\n{e.Exception.Message}",
            "시스템 오류", MessageBoxButton.OK, MessageBoxImage.Error);

        // UI 스레드가 계속 살아있을 수 있도록 처리했음을 표시한다.
        // 단, 이는 오직 안전 정지 전환과 로깅이 끝난 뒤에만 해야 하는 예외적인 조치다.
        e.Handled = true;
    }

    private static void OnUnobservedTaskException(object sender, UnobservedTaskExceptionEventArgs e)
    {
        Log.Error(e.Exception, "관찰되지 않은 Task 예외가 발생했습니다.");
        e.SetObserved(); // 파이널라이저 스레드에서 프로세스를 종료시키지 않도록 관찰 처리한다.
    }

    private static void TryEmergencyStop()
    {
        try
        {
            EquipmentStateMachineHost.Instance.RequestEmergencyAlarm(reason: "UnhandledException");
        }
        catch
        {
            // 비상 정지 시도 자체에서 예외가 나더라도 로그 플러시는 반드시 진행되어야 한다.
        }
    }
}
```

몇 가지 원칙을 짚어볼 필요가 있습니다. `AppDomain.CurrentDomain.UnhandledException`은 프로세스 종료를 막지 못합니다. .NET에서 스레드 풀 스레드나 일반 스레드에서 처리되지 않은 예외가 발생하면 프로세스는 결국 종료되며, 이 이벤트 핸들러는 "종료되기 직전 마지막으로 무언가를 기록하고 정리할 기회"를 줄 뿐입니다. 반면 WPF의 `Application.DispatcherUnhandledException`은 UI 스레드에서 발생한 예외에 한해 `e.Handled = true`로 지정하면 애플리케이션을 계속 실행시킬 수 있는 유일한 훅입니다.

가장 중요한 원칙은 **예외를 절대 조용히 삼키지 않는 것**입니다. `catch (Exception) { }`처럼 아무 조치 없이 예외를 무시하는 코드는, 당장은 프로그램이 죽지 않아 안전해 보이지만 실제로는 장비가 어떤 비정상 상태에 놓였는지 아무도 모른 채로 다음 동작을 계속 시도하게 만듭니다. 모션 시퀀스 도중 예외가 발생했다면, 그 즉시 5장에서 설계한 FSM을 Alarm 상태로 강제 전이시켜 더 이상의 모션 명령이 나가지 않도록 막고, 6장의 HMI 화면에 명확한 오류 메시지를 띄우고, 7장의 로깅 시스템으로 스택 트레이스 전체를 남긴 뒤에야 비로소 "예외를 처리했다"고 말할 수 있습니다. 예외를 잡아서 처리한다는 것은 원래 상태로 되돌리는 것이 아니라, 안전하게 정의된 정지 상태로 전환하는 것을 의미합니다.

### 이 책을 되돌아보며

여기까지 오면서 이 책은 아래쪽 하드웨어 접점에서 위쪽 사람과 조직의 접점으로 층을 쌓아 올리는 순서를 따랐습니다. 1장에서 그린 레이어드 아키텍처가 뼈대였고, 2장의 비동기·멀티스레딩 기반 위에 3장의 통신 계층과 4장의 모션/IO 계층이 하드웨어와의 접점을 담당했습니다. 5장의 상태 머신은 이 접점들을 순서와 규칙에 맞게 조율하는 두뇌 역할을 했고, 6장의 HMI는 그 두뇌가 하는 일을 사람이 보고 개입할 수 있게 열어주는 창이었습니다. 7장의 알람과 레시피, 데이터 관리는 시스템이 무엇을 했고 무엇을 해야 하는지 기억하게 해주었고, 8장의 상위 시스템·비전 연동은 장비 한 대를 공장 전체의 생산 흐름과 다른 지능형 장비들과 엮어냈습니다. 그리고 이번 9장은 이 모든 층이 실험실 수준의 코드가 아니라 실제 현장에서 몇 달, 몇 년씩 버텨내는 소프트웨어가 되도록 마감하는 역할을 했습니다.

이 여정 전체를 지탱하는 하나의 축을 꼽자면 **인터페이스를 통한 관심사의 분리**입니다. 1장에서 HAL을 인터페이스로 분리해 둔 덕분에 이번 장에서 하드웨어 없이도 개발할 수 있는 시뮬레이터를 끼워 넣을 수 있었고, 5장에서 시퀀스 로직을 상태 머신으로 캡슐화해 둔 덕분에 6장의 HMI는 "무엇을 보여줄지"에만 집중할 수 있었으며, 7장에서 데이터 계층을 분리해 둔 덕분에 8장의 상위 시스템 연동이 나머지 코드를 건드리지 않고 얹힐 수 있었습니다. 장비 제어 소프트웨어는 하드웨어, 실시간성, 사람의 개입, 조직 시스템이라는 서로 다른 성격의 요구가 한곳에서 만나는 특수한 영역이지만, 그 복잡성을 다루는 방법은 결국 일반적인 소프트웨어 공학 원칙, 즉 계층을 나누고 각 계층이 인터페이스로만 소통하게 만드는 원칙과 다르지 않다는 것이 이 책 전체가 전하고자 한 메시지입니다.

### 더 공부할 방향

이 책은 C#/.NET으로 장비 제어 소프트웨어를 개발하는 데 필요한 핵심을 다뤘지만, 그 너머에는 더 깊이 파고들 만한 주제가 여전히 많이 남아 있습니다.

**SEMI 표준 심화.** 8장에서 SECS/GEM의 기본을 다뤘지만, 반도체·디스플레이 장비 분야로 더 들어가면 E40(프로세스 잡 관리), E90(기판 추적), E94(제어 잡 관리), E116(장비 성능 추적) 등 SEMI 표준 스펙이 정의하는 더 정교한 상태 모델과 이벤트 체계가 있습니다. 실제 양산 팹에 납품하는 장비라면 이런 표준을 깊이 이해하는 것이 곧 호환성과 직결됩니다.

**실시간 OS 및 RTX 연동.** 이 책에서 다룬 .NET 환경은 범용 Windows 운영체제 위에서 동작하는 소프트 리얼타임(soft real-time) 수준의 응답성을 제공합니다. 마이크로초 단위의 확정적 타이밍이 요구되는 초정밀 모션 제어라면, IntervalZero의 RTX나 TwinCAT과 같은 실시간 확장 커널 위에서 저수준 제어 루프를 돌리고, .NET 애플리케이션은 그 위에서 상위 조율과 UI만 담당하는 하이브리드 구조를 검토하게 됩니다.

**산업용 엣지 컴퓨팅.** 장비 한 대의 제어를 넘어, 여러 장비에서 나오는 데이터를 엣지에서 실시간으로 집계·분석하고 OPC UA로 상위 시스템이나 클라우드와 표준화된 방식으로 주고받는 아키텍처가 스마트 팩토리의 흐름 속에서 점점 더 중요해지고 있습니다. 컨테이너 기반으로 산업용 PC에 소프트웨어를 배포하고 원격으로 업데이트하는 운영 체계까지 고려한다면, 이 책에서 다진 기초 위에 DevOps와 엣지 오케스트레이션이라는 새로운 층을 쌓아야 합니다.

이 책에서 익힌 계층화된 사고방식, 즉 하드웨어를 인터페이스 뒤에 감추고, 상태를 명시적인 기계로 관리하고, 예외를 안전한 정지 상태로 전환하는 습관은 앞으로 어떤 표준이나 실시간 플랫폼, 엣지 아키텍처를 만나더라도 그대로 유효한 자산이 될 것입니다.

## 요약

- HAL을 인터페이스로 분리해 두면 실제 P/Invoke 구현체 대신 가상 시뮬레이터 구현체를 DI 컨테이너 설정 하나로 교체할 수 있고, 4장의 속도 프로파일 계산을 재사용해 실제 모터와 유사하게 동작하는 시뮬레이터로 하드웨어 없이 개발·CI 테스트·예외 상황 재현이 가능해집니다.
- `GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency`는 블로킹 Gen2 수집 빈도를 줄여주지만 메모리 압박 시에는 무력화되며, 짧고 확정적인 구간에는 `GC.TryStartNoGCRegion`을 함께 검토할 수 있습니다. 장비 제어 소프트웨어는 대개 Workstation GC + Concurrent 조합이 처리량보다 응답성에 유리합니다.
- 메모리 누수의 흔한 원인은 이벤트 구독 후 미해제(`+=`만 하고 `-=` 누락), Timer/Thread 미정리, 무한정 자라는 static 컬렉션이며, 각각 명시적 구독 해제 또는 약한 이벤트, `IDisposable` 패턴, 크기 상한이 있는 버퍼로 해결합니다.
- `Span<T>`/`ReadOnlySpan<T>`는 힙 할당 없이 배열의 일부를 참조하지만 `ref struct`라 필드나 `async` 메서드에 저장할 수 없고, `Memory<T>`는 구조체이므로 필드 저장과 `await` 경계를 넘나드는 전달이 가능합니다. `BinaryPrimitives`로 엔디안을 명시하고 `ArrayPool<byte>.Shared`로 버퍼를 재사용하면 패킷 파싱의 GC 압박을 크게 줄일 수 있습니다.
- 현장 셋업에서는 전기적 노이즈로 인한 통신 오류, 기구物 공차로 인한 재티칭, 현장 네트워크 환경 차이라는 특유의 문제를 마주하며, 상관관계 ID와 통신 원본 프레임 덤프를 포함한 로깅 설계가 원격 문제 진단의 핵심입니다.
- `AppDomain.CurrentDomain.UnhandledException`, `TaskScheduler.UnobservedTaskException`, WPF의 `Application.DispatcherUnhandledException`으로 전역 예외를 붙잡되, 예외를 조용히 삼키지 말고 5장의 Alarm 상태로 전환한 뒤 사용자에게 명확히 알리는 것이 원칙입니다.
- 이 책 전체는 인터페이스를 통한 관심사의 분리를 축으로, 1장의 레이어드 아키텍처부터 9장의 최적화·테스트까지 하드웨어 접점에서 사람·조직의 접점으로 층을 쌓아 올린 구성이며, SEMI 표준 심화, 실시간 OS 연동, 산업용 엣지 컴퓨팅이 앞으로 더 살펴볼 만한 방향입니다.

## 연습문제

1. `IMotionController` 인터페이스를 구현하는 `VirtualMotionController`에 랜덤 알람 발생 대신, 특정 시점에 정확히 원하는 알람을 발생시키는 테스트 전용 메서드를 추가하고, 이를 이용해 5장에서 만든 FSM이 Alarm 상태로 전이하는지 검증하는 단위 테스트를 작성해보세요.
2. `GCSettings.LatencyMode = GCLatencyMode.SustainedLowLatency`를 설정해도 블로킹 GC가 완전히 사라지지 않는 이유를 설명하고, 이 설정만으로 충분하지 않은 상황에서 함께 고려할 수 있는 방법을 서술하세요.
3. 장수명 객체가 단명 객체의 이벤트를 구독하면서 해제하지 않아 메모리 누수가 발생하는 코드를 예로 들고, `IDisposable` 패턴과 `WeakEventManager` 두 가지 해결책의 장단점을 비교하세요.
4. 3장에서 작성했던 패킷 파싱 코드를 `Array.Slice`(또는 `Take`/`Skip`) 방식에서 `Span<T>`와 `BinaryPrimitives` 기반으로 리팩터링하고, `ArrayPool<byte>.Shared`로 수신 버퍼를 재사용하도록 개선해보세요.
5. 현장 셋업 중 발생한 통신 오류를 원격으로 진단해야 하는 상황을 가정하고, 어떤 정보(상관관계 ID, 원본 프레임 덤프, 로그 레벨 등)를 어떤 형태로 남겨두어야 개발실에서 재현 없이 원인을 찾을 수 있을지 로깅 설계안을 작성해보세요.

## 17.1 배포란 무엇인가

지금까지는 Qt Creator나 명령행에서 직접 빌드하고 실행하는 개발 환경을 전제로 예제를 다뤘습니다. 하지만 실제로 프로그램을 사용자에게 전달하려면 개발 PC가 아닌 다른 컴퓨터, 즉 Qt SDK가 설치되어 있지 않은 환경에서도 실행 파일이 정상적으로 동작해야 합니다. 이 과정을 **배포(deployment)**라고 부릅니다.

Qt 애플리케이션은 기본적으로 여러 개의 공유 라이브러리(Windows의 DLL, Linux의 `.so`, macOS의 `.dylib`)에 의존합니다. 예를 들어 `QtWidgets`를 사용하는 간단한 프로그램이라도 최소한 다음과 같은 요소가 실행 시점에 필요합니다.

- Qt 코어/GUI/위젯 라이브러리 본체 (`Qt6Core.dll`, `Qt6Gui.dll`, `Qt6Widgets.dll` 등)
- 플랫폼 통합 플러그인(`platforms/` 폴더의 `qwindows.dll`, `libqxcb.so` 등) — 이것이 없으면 애플리케이션이 아예 창을 띄우지 못합니다.
- 이미지 포맷 플러그인(`imageformats/` 폴더) — PNG 외의 형식(JPEG, ICO 등)을 다룰 때 필요합니다.
- 스타일 플러그인, 각종 코덱/드라이버 플러그인 등 사용한 기능에 따라 추가되는 항목들
- C++ 런타임 라이브러리(MSVC의 재배포 가능 패키지, MinGW의 `libgcc`/`libstdc++` 등)

개발 PC에서는 Qt SDK가 이미 설치되어 있고 개발 도구가 경로를 알아서 맞춰주기 때문에 이런 의존성이 눈에 띄지 않습니다. 하지만 사용자의 컴퓨터에는 이런 파일들이 전혀 없을 수 있으므로, 배포 패키지에는 실행 파일뿐 아니라 이러한 의존 요소를 함께 담아야 합니다. 이 장에서는 이를 자동화해주는 플랫폼별 도구와, 배포 전에 반드시 확인해야 할 설정을 다룹니다.

> **범위 안내**: 이 장은 실행 파일을 "다른 컴퓨터에서 실행 가능한 상태로 묶는 것"까지를 다룹니다. 설치 프로그램(인스톨러) 제작 도구의 세부 사용법이나 Microsoft Store, Mac App Store 같은 앱 스토어 심사 절차, 코드 서명 인증서 발급 절차는 이 책의 범위를 벗어나므로 다루지 않습니다. 필요하다면 각 플랫폼의 공식 배포 가이드를 별도로 참고하시기 바랍니다.

## 17.2 정적 링크와 동적 링크

Qt 라이브러리를 애플리케이션과 결합하는 방식은 크게 두 가지입니다.

- **동적 링크(shared/dynamic build)**: Qt 라이브러리가 별도의 공유 라이브러리 파일로 존재하고, 실행 파일은 실행 시점에 이를 로드합니다. Qt Online Installer로 설치하는 사전 빌드 배포판은 기본적으로 이 방식입니다.
- **정적 링크(static build)**: Qt 라이브러리 코드가 실행 파일 안에 통째로 포함됩니다. 이렇게 만들려면 Qt 소스 코드를 직접 정적 구성으로 빌드해야 하며, 사전 빌드된 표준 배포판만으로는 불가능합니다.

두 방식의 장단점을 정리하면 다음과 같습니다.

| 항목 | 동적 링크 | 정적 링크 |
|---|---|---|
| 배포 파일 구성 | 실행 파일 + 여러 DLL/공유 라이브러리 + 플러그인 폴더 | 실행 파일 하나(플러그인은 별도로 필요할 수 있음) |
| 실행 파일 용량 | 작음 | 큼 (Qt 코드가 모두 포함됨) |
| 여러 프로그램 간 공유 | 같은 Qt 버전을 쓰는 여러 앱이 라이브러리를 공유 가능 | 각 실행 파일마다 중복 포함 |
| 빌드 준비 | 표준 Qt 설치본으로 바로 가능 | Qt를 정적 옵션으로 직접 빌드해야 함(시간이 오래 걸림) |
| 라이선스 고려사항 | LGPL 조건(동적 링크, 라이브러리 교체 가능성 보장)을 상대적으로 쉽게 충족 | LGPL 하에서는 조건 충족이 까다로워지며, 상용 라이선스가 필요한 경우가 많음 |
| 배포 실수 위험 | 파일 누락(플러그인, DLL) 가능성 있음 | 누락 위험이 적음(실행 파일 자체에 포함) |

실무에서는 특별한 이유가 없는 한 **동적 링크 배포**가 기본 선택지입니다. Qt Online Installer가 제공하는 사전 빌드 라이브러리를 그대로 사용할 수 있고, 뒤에서 설명할 `windeployqt`, `macdeployqt` 같은 도구도 동적 링크 배포를 자동화하는 데 초점이 맞춰져 있기 때문입니다. 정적 링크는 실행 파일 하나로 배포하고 싶은 특수한 상황(예: 휴대용 유틸리티)이나 라이선스 정책상 Qt 소스를 직접 빌드해서 쓰는 상황에서 고려합니다.

## 17.3 CMake 릴리스 빌드 설정

배포용 실행 파일은 디버그 빌드가 아니라 **릴리스 빌드**로 만들어야 합니다. 디버그 빌드는 최적화가 꺼져 있고 디버그 심볼이 포함되어 있어 실행 속도가 느리고 파일 크기도 큽니다. CMake를 사용하는 프로젝트에서는 `CMAKE_BUILD_TYPE` 변수로 빌드 구성을 지정합니다.

```cmake
cmake_minimum_required(VERSION 3.16)
project(NotepadApp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTORCC ON)
set(CMAKE_AUTOUIC ON)

# 별도로 지정하지 않았다면 기본값을 Release로 설정
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Build type" FORCE)
endif()

find_package(Qt6 REQUIRED COMPONENTS Widgets)

add_executable(NotepadApp
    main.cpp
    mainwindow.cpp
    mainwindow.h
)

target_link_libraries(NotepadApp PRIVATE Qt6::Widgets)
```

`CMAKE_BUILD_TYPE`은 단일 구성(single-config) 제너레이터인 Makefile이나 Ninja를 사용할 때 적용되는 변수입니다. 명령행에서 직접 지정할 수도 있습니다.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Visual Studio나 `Ninja Multi-Config`처럼 하나의 빌드 트리에서 여러 구성을 함께 관리하는 **다중 구성(multi-config) 제너레이터**를 사용할 때는 `CMAKE_BUILD_TYPE` 대신 빌드 시점에 구성을 선택합니다.

```bash
cmake -S . -B build -G "Visual Studio 17 2022"
cmake --build build --config Release
```

릴리스 빌드는 컴파일러 최적화 옵션(`-O2` 등)이 활성화되고 `Q_ASSERT` 같은 디버그 전용 매크로의 동작이 달라지므로, 배포 전에는 반드시 릴리스 구성으로 한 번 더 빌드하고 동작을 검증하는 것이 좋습니다.

## 17.4 Windows 배포: windeployqt

`windeployqt`는 Qt 설치 경로의 `bin` 폴더에 포함되어 있는 배포 보조 도구입니다. 완성된 실행 파일(`.exe`)을 분석하여 그 실행 파일이 어떤 Qt 라이브러리와 플러그인을 사용하는지 자동으로 추적하고, 필요한 파일들을 실행 파일과 같은 폴더에 복사해줍니다.

기본적인 사용법은 다음과 같습니다.

```bash
windeployqt --release path\to\build\NotepadApp.exe
```

주요 옵션은 다음과 같습니다.

- `--release` / `--debug`: 릴리스용 또는 디버그용 라이브러리를 복사하도록 지정합니다.
- `--no-translations`: Qt 자체의 번역 파일(`.qm`)을 복사하지 않습니다.
- `--dir <경로>`: 결과물을 실행 파일이 아닌 다른 폴더에 모읍니다.
- `--compiler-runtime`: MSVC 컴파일러 런타임 재배포 파일까지 함께 복사하도록 시도합니다.

명령을 실행하면 실행 파일 옆에 다음과 비슷한 구조가 만들어집니다.

```
NotepadApp.exe
Qt6Core.dll
Qt6Gui.dll
Qt6Widgets.dll
platforms/
    qwindows.dll
imageformats/
    qjpeg.dll
    qico.dll
styles/
    qwindowsvistastyle.dll
```

이 폴더 전체(하위 폴더 포함)를 사용자에게 그대로 전달하면, Qt가 설치되어 있지 않은 Windows 컴퓨터에서도 실행 파일을 바로 실행할 수 있습니다. `windeployqt`는 빌드 스크립트나 CMake의 사용자 정의 명령(custom command)에 연결하여 빌드 직후 자동으로 실행되도록 구성하는 경우도 많습니다.

```cmake
add_custom_command(TARGET NotepadApp POST_BUILD
    COMMAND "$<TARGET_FILE:Qt6::windeployqt>" "$<TARGET_FILE:NotepadApp>"
    COMMENT "Running windeployqt on the built executable"
)
```

## 17.5 Linux 배포: linuxdeployqt와 AppImage

Linux는 배포판(Ubuntu, Fedora, Arch 등)마다 시스템 라이브러리 버전과 패키지 관리 방식이 크게 다르기 때문에, 하나의 바이너리를 모든 배포판에서 동일하게 실행하기가 Windows나 macOS보다 까다롭습니다. 이 문제를 해결하기 위해 커뮤니티에서 널리 쓰이는 접근 방식이 **AppImage**이며, 이를 만들 때 흔히 사용하는 도구가 **linuxdeployqt**입니다.

- **linuxdeployqt**: 실행 파일이 의존하는 Qt 라이브러리와 플러그인, 그 외 공유 라이브러리를 분석하여 `AppDir`이라는 특정 구조의 디렉터리 안에 모아주는 서드파티 도구입니다. `windeployqt`의 Linux/AppImage 버전이라고 이해하면 됩니다.
- **AppImage**: 애플리케이션 실행에 필요한 모든 것(실행 파일, 라이브러리, 아이콘, 데스크톱 통합 정보)을 하나의 파일로 묶는 배포 포맷입니다. 사용자는 설치 과정 없이 실행 권한만 부여하고 그 파일을 바로 실행할 수 있습니다.

일반적인 작업 흐름은 다음과 같습니다.

1. 릴리스 빌드로 실행 파일을 만듭니다.
2. `AppDir` 구조(`AppDir/usr/bin/`, `AppDir/usr/share/applications/*.desktop`, 아이콘 파일 등)를 준비합니다.
3. `linuxdeployqt`를 실행하여 필요한 라이브러리와 Qt 플러그인을 `AppDir` 안에 모읍니다.
4. AppImage 생성 도구로 `AppDir`을 하나의 `.AppImage` 파일로 패키징합니다.

`.desktop` 파일은 애플리케이션 이름, 실행 명령, 아이콘, 카테고리 등을 기술하는 텍스트 파일로, 데스크톱 환경의 애플리케이션 메뉴에 프로그램을 등록하는 데 사용됩니다. 이 책에서는 AppImage 제작의 세부 명령어까지는 다루지 않지만, "Linux에서는 배포판 간 라이브러리 차이를 흡수하기 위해 이런 방식이 쓰인다"는 개념을 알아두면 충분합니다. 물론 배포판의 패키지 관리자에 맞춰 `.deb`, `.rpm` 패키지로 만드는 전통적인 방식도 여전히 널리 쓰입니다.

## 17.6 macOS 배포: macdeployqt

macOS 애플리케이션은 보통 `.app`이라는 확장자를 가진 **번들(bundle)** 형태로 배포됩니다. `.app`은 사실 여러 파일이 정해진 규칙에 따라 모여 있는 디렉터리이며, Finder에서는 하나의 실행 파일처럼 보입니다. 내부 구조는 대략 다음과 같습니다.

```
NotepadApp.app/
    Contents/
        Info.plist
        MacOS/
            NotepadApp        (실제 실행 파일)
        Frameworks/           (Qt 프레임워크가 위치)
        PlugIns/
            platforms/
            imageformats/
        Resources/
```

`macdeployqt`는 Qt가 공식적으로 제공하는 배포 도구로, 이미 만들어진 `.app` 번들을 대상으로 실행하면 해당 번들이 필요로 하는 Qt 프레임워크를 `Contents/Frameworks/` 폴더로 복사하고, 실행 파일 안의 라이브러리 참조 경로를 번들 내부 상대 경로로 재작성하며, 필요한 플러그인을 `Contents/PlugIns/`로 복사해줍니다.

```bash
macdeployqt NotepadApp.app
```

이렇게 처리된 `.app` 번들은 Qt가 설치되지 않은 다른 Mac에서도 그대로 실행할 수 있습니다. `macdeployqt`는 `-dmg` 옵션을 통해 배포용 디스크 이미지(`.dmg`)를 함께 만들어주는 기능도 제공합니다. 다만 macOS에서 배포판을 다른 사용자와 공유하려면 코드 서명(code signing)과 공증(notarization) 절차가 별도로 필요한 경우가 많은데, 이는 Apple 개발자 계정 및 인증서 관리와 관련된 주제이므로 이 책에서는 다루지 않습니다.

## 17.7 배포 시 흔히 겪는 문제

배포 파일을 준비하고 다른 컴퓨터에서 테스트할 때 자주 마주치는 문제들을 정리하면 다음과 같습니다.

- **플랫폼 플러그인 누락**: `platforms/` 폴더(및 그 안의 `qwindows.dll`, `libqxcb.so`, `libqcocoa.dylib` 등)를 빠뜨리면 애플리케이션이 창을 하나도 띄우지 못하고 즉시 종료됩니다. Windows에서는 "this application failed to start because no Qt platform plugin could be initialized" 같은 오류 메시지가 대표적인 증상입니다. 배포 시 가장 흔하게 빠뜨리는 폴더이므로 최우선으로 확인해야 합니다.
- **이미지 포맷 플러그인 누락**: `imageformats/` 폴더를 빠뜨리면 PNG 이외의 형식(JPEG, ICO, GIF 등)을 다루는 `QImage`/`QPixmap` 로드가 조용히 실패할 수 있습니다. 아이콘이나 스플래시 이미지가 갑자기 표시되지 않는다면 이 폴더를 의심해야 합니다.
- **DLL/공유 라이브러리 누락**: Qt 모듈을 추가로 사용했는데(예: `QtNetwork`, `QtSql`) 해당 라이브러리를 배포 파일에 포함하지 않은 경우입니다. `windeployqt`나 `macdeployqt`를 실행 파일에 대해 실행하면 대부분 자동으로 해결되지만, 실행 파일을 다시 빌드한 뒤 배포 도구를 재실행하지 않으면 이전 버전 그대로 남아 있을 수 있습니다.
- **컴파일러 런타임 누락**: MSVC로 빌드한 경우 Visual C++ 재배포 가능 패키지가 대상 컴퓨터에 없으면 실행 자체가 거부될 수 있습니다.
- **상대 경로 문제**: 애플리케이션이 리소스 파일이나 설정 파일을 상대 경로로 찾도록 작성했다면, 사용자가 실행 파일을 다른 위치로 옮겼을 때 경로를 찾지 못할 수 있습니다. `QCoreApplication::applicationDirPath()`를 기준으로 경로를 구성하면 실행 파일 위치가 바뀌어도 안정적으로 동작합니다.
- **플러그인 경로를 직접 제어해야 하는 경우**: 표준 배포 구조를 벗어나 플러그인을 다른 폴더에 두고 싶다면, 애플리케이션 시작 시 `QCoreApplication::addLibraryPath()`로 추가 경로를 등록할 수 있습니다.

```cpp
#include <QApplication>
#include <QCoreApplication>
#include <QDir>

int main(int argc, char *argv[])
{
    QApplication app(argc, argv);

    // 실행 파일 위치를 기준으로 plugins 폴더를 라이브러리 경로에 추가
    const QString pluginDir =
        QDir(QCoreApplication::applicationDirPath()).filePath("plugins");
    QCoreApplication::addLibraryPath(pluginDir);

    // ... 이후 MainWindow 생성 및 실행 ...

    return app.exec();
}
```

배포 전에 확인할 사항을 체크리스트로 정리하면 다음과 같습니다.

1. 릴리스 구성으로 새로 빌드했는가?
2. 배포 도구(`windeployqt`/`linuxdeployqt`/`macdeployqt`)를 최신 실행 파일에 대해 다시 실행했는가?
3. `platforms/`, `imageformats/` 등 플러그인 폴더가 배포 파일에 포함되어 있는가?
4. Qt SDK가 전혀 설치되지 않은 "깨끗한" 컴퓨터(또는 가상 머신)에서 실제로 실행해 보았는가?
5. 애플리케이션이 사용하는 파일 경로가 실행 파일 위치에 상대적으로 올바르게 계산되는가?

## 요약

- 배포는 실행 파일과 함께 필요한 Qt 라이브러리, 플러그인을 Qt가 설치되지 않은 환경에서도 실행 가능한 형태로 묶는 작업입니다.
- 동적 링크는 배포 파일 구성이 복잡해지는 대신 라이브러리 공유와 LGPL 조건 충족이 쉽고, 정적 링크는 배포가 단순해지는 대신 Qt를 직접 정적으로 빌드해야 하고 라이선스 고려사항이 늘어납니다. 실무에서는 동적 링크가 기본 선택지입니다.
- CMake에서는 `CMAKE_BUILD_TYPE=Release`(단일 구성 제너레이터) 또는 `cmake --build . --config Release`(다중 구성 제너레이터)로 릴리스 빌드를 만듭니다.
- Windows는 `windeployqt`, macOS는 `macdeployqt`라는 Qt 공식 도구가 필요한 라이브러리와 플러그인을 자동으로 모아주며, Linux에서는 `linuxdeployqt`와 AppImage 포맷이 배포판 간 라이브러리 차이 문제를 완화하는 데 널리 쓰입니다.
- 배포 실패의 대부분은 `platforms/`, `imageformats/` 같은 플러그인 폴더 누락이나 새로 추가한 Qt 모듈의 라이브러리 누락에서 발생하므로, 배포 도구를 최신 빌드에 다시 실행하고 깨끗한 환경에서 실행 테스트를 하는 습관이 중요합니다.
- 설치 프로그램 제작, 코드 서명, 앱 스토어 심사 등은 이 장의 범위를 벗어나며 필요 시 별도로 학습해야 합니다.

## 연습문제

1. 동적 링크 배포와 정적 링크 배포의 차이를 배포 파일 구성, 실행 파일 용량, 라이선스 관점에서 각각 설명하시오.
2. `CMAKE_BUILD_TYPE=Release`가 단일 구성 제너레이터(Makefile, Ninja)에서는 잘 동작하지만 Visual Studio 제너레이터에서는 별도의 처리가 필요한 이유를 설명하시오.
3. `windeployqt`, `linuxdeployqt`, `macdeployqt`의 공통적인 역할과 각 도구가 대상으로 하는 배포 산출물(실행 파일 폴더, AppDir, `.app` 번들)의 차이를 비교하시오.
4. 배포한 프로그램을 다른 컴퓨터에서 실행했더니 "no Qt platform plugin could be initialized" 오류가 발생했다. 원인으로 가장 가능성이 높은 것은 무엇이며 어떻게 해결해야 하는지 서술하시오.
5. 애플리케이션이 실행 파일 위치와 무관하게 항상 올바른 경로에서 설정 파일을 찾도록 하려면 어떤 API를 사용해야 하는지, 그 이유와 함께 설명하시오.

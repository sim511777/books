## 15.1 QtNetwork 모듈과 비동기 네트워크 프로그래밍

지금까지는 애플리케이션 내부의 데이터, 즉 파일이나 메모리에 있는 정보를 다루는 방법을 익혔습니다. 그러나 실제 데스크톱 애플리케이션은 인터넷 너머의 서버와 통신하는 경우가 매우 많습니다. 클라우드에 저장된 데이터를 내려받거나, REST API 서버에 로그인 요청을 보내거나, 사내 장비와 TCP로 직접 통신하는 등의 작업이 대표적입니다. Qt는 이러한 네트워크 통신을 위해 `QtNetwork`라는 별도 모듈을 제공합니다.

QtNetwork를 사용하려면 프로젝트 설정에 이 모듈을 추가해야 합니다.

- qmake(`.pro` 파일)를 사용한다면 다음 줄을 추가합니다.

```
QT += network
```

- CMake를 사용한다면 다음과 같이 작성합니다.

```cmake
find_package(Qt6 REQUIRED COMPONENTS Network)
target_link_libraries(myapp PRIVATE Qt6::Network)
```

QtNetwork가 제공하는 기능은 크게 두 갈래로 나눌 수 있습니다.

1. **고수준 HTTP 통신**: `QNetworkAccessManager`를 사용해 HTTP/HTTPS 프로토콜로 REST API 등과 통신합니다. 웹 서버와 JSON, XML 등의 데이터를 주고받는 대부분의 작업은 이 방식으로 처리합니다.
2. **저수준 소켓 통신**: `QTcpSocket`, `QTcpServer`, `QUdpSocket` 등을 사용해 TCP/UDP 프로토콜을 직접 다룹니다. 자체 프로토콜을 설계해야 하거나, HTTP가 아닌 다른 방식으로 통신하는 장비와 연결할 때 사용합니다.

두 방식 모두 공통적으로 **비동기(asynchronous) 모델**을 따른다는 점이 중요합니다. 네트워크 통신은 응답이 언제 도착할지 예측할 수 없고, 때로는 몇 초씩 걸리기도 합니다. 만약 요청을 보내고 응답이 올 때까지 코드가 그 자리에서 멈춰 기다린다면(블로킹, blocking), 그동안 GUI 스레드는 이벤트 루프를 처리하지 못해 화면이 멈춘 것처럼 보이게 됩니다. 14장에서 살펴본 것처럼 시간이 오래 걸리는 작업은 UI 스레드를 막지 않아야 하는데, Qt의 네트워크 클래스들은 애초에 논블로킹(non-blocking) 소켓 위에서 동작하도록 설계되어 있어서, 별도의 `QThread`를 만들지 않아도 자연스럽게 UI 스레드를 막지 않습니다. 요청을 보낸 뒤에는 즉시 제어권이 돌아오고, 응답이 도착하면 시그널이 발생해 우리가 등록한 슬롯이 호출되는 방식입니다.

## 15.2 QNetworkAccessManager로 HTTP GET 요청 보내기

HTTP 통신의 중심에는 `QNetworkAccessManager` 클래스가 있습니다. 이 클래스는 하나의 애플리케이션에서 보통 하나의 인스턴스만 만들어 재사용하며, 연결 유지(keep-alive), 쿠키, 인증 등을 내부적으로 관리해 줍니다.

기본적인 사용 흐름은 다음과 같습니다.

1. `QNetworkRequest` 객체를 만들어 요청할 URL과 헤더를 설정합니다.
2. `QNetworkAccessManager::get()`(또는 `post()`, `put()` 등)을 호출하면 요청이 비동기로 전송되고, 그 결과를 나타내는 `QNetworkReply` 객체가 즉시 반환됩니다.
3. `QNetworkReply`의 `finished` 시그널에 슬롯을 연결해 두면, 응답이 도착했을 때(성공이든 실패든) 이 슬롯이 호출됩니다.
4. 슬롯 안에서 `reply->error()`로 오류 여부를 확인하고, 문제가 없다면 `reply->readAll()`로 응답 본문을 읽습니다.
5. 다 쓴 `QNetworkReply`는 `deleteLater()`로 해제합니다.

다음은 버튼을 눌렀을 때 GET 요청을 보내고 응답 텍스트를 라벨에 표시하는 간단한 예제입니다.

```cpp
// networkclientwindow.h
#pragma once

#include <QWidget>
#include <QNetworkAccessManager>
#include <QNetworkReply>

class QLabel;
class QPushButton;

class NetworkClientWindow : public QWidget
{
    Q_OBJECT

public:
    explicit NetworkClientWindow(QWidget *parent = nullptr);

private slots:
    void onFetchButtonClicked();
    void onReplyFinished(QNetworkReply *reply);

private:
    QNetworkAccessManager *m_manager;
    QLabel *m_resultLabel;
    QPushButton *m_fetchButton;
};
```

```cpp
// networkclientwindow.cpp
#include "networkclientwindow.h"

#include <QLabel>
#include <QPushButton>
#include <QVBoxLayout>
#include <QNetworkRequest>
#include <QUrl>

NetworkClientWindow::NetworkClientWindow(QWidget *parent)
    : QWidget(parent)
    , m_manager(new QNetworkAccessManager(this))
{
    m_resultLabel = new QLabel(tr("아직 요청하지 않았습니다."), this);
    m_resultLabel->setWordWrap(true);

    m_fetchButton = new QPushButton(tr("서버에서 가져오기"), this);

    auto *layout = new QVBoxLayout(this);
    layout->addWidget(m_resultLabel);
    layout->addWidget(m_fetchButton);

    connect(m_fetchButton, &QPushButton::clicked,
            this, &NetworkClientWindow::onFetchButtonClicked);

    // QNetworkAccessManager는 요청이 끝날 때마다 finished(QNetworkReply*) 시그널을
    // 한 번 발생시킵니다. 요청을 여러 곳에서 보내더라도 이 시그널 하나로 처리할 수 있습니다.
    connect(m_manager, &QNetworkAccessManager::finished,
            this, &NetworkClientWindow::onReplyFinished);
}

void NetworkClientWindow::onFetchButtonClicked()
{
    m_resultLabel->setText(tr("요청 중..."));
    m_fetchButton->setEnabled(false);

    // 예시로 사용하는 가상의 API 주소입니다. 실제 프로젝트에서는
    // 사용하려는 서비스의 실제 엔드포인트로 바꿔야 합니다.
    QNetworkRequest request(QUrl("https://api.example.com/v1/status"));
    request.setHeader(QNetworkRequest::UserAgentHeader, QByteArray("QtBookClient/1.0"));

    // get()을 호출하는 즉시 함수가 반환됩니다. 응답을 기다리며 멈추지 않습니다.
    m_manager->get(request);
}

void NetworkClientWindow::onReplyFinished(QNetworkReply *reply)
{
    m_fetchButton->setEnabled(true);

    if (reply->error() != QNetworkReply::NoError) {
        m_resultLabel->setText(tr("오류 발생: %1").arg(reply->errorString()));
        reply->deleteLater();
        return;
    }

    const QByteArray responseBody = reply->readAll();
    m_resultLabel->setText(QString::fromUtf8(responseBody));

    // QNetworkReply는 부모가 QNetworkAccessManager가 아니므로
    // 사용이 끝나면 반드시 직접 해제해 주어야 메모리 누수를 막을 수 있습니다.
    reply->deleteLater();
}
```

이 예제에서는 `QNetworkAccessManager::finished(QNetworkReply*)` 시그널 하나로 모든 요청의 완료를 감지했습니다. 요청 종류가 다양해지면 어떤 요청에 대한 응답인지 구분해야 하는데, 이때는 `reply->request().url()`로 원래 요청 정보를 확인하거나, `get()`이 반환한 `QNetworkReply*` 각각에 대해 개별적으로 `finished` 시그널을 연결하는 방식을 사용할 수 있습니다.

```cpp
// 요청별로 개별 QNetworkReply에 직접 연결하는 방식
QNetworkReply *reply = m_manager->get(request);
connect(reply, &QNetworkReply::finished, this, [this, reply]() {
    if (reply->error() == QNetworkReply::NoError) {
        // ... 응답 처리 ...
    }
    reply->deleteLater();
});
```

> **참고**: `QNetworkReply`는 오류가 발생했을 때 `errorOccurred(QNetworkReply::NetworkError)` 시그널도 함께 발생시킵니다(Qt 5.15 이상). 과거에는 이름이 겹치는 `error(QNetworkReply::NetworkError)` 시그널을 사용했지만 지금은 사용이 권장되지 않는(deprecated) 상태이므로, 새 코드에서는 `errorOccurred`를 사용하는 것이 좋습니다. 다만 대부분의 경우 `finished` 슬롯 안에서 `reply->error()`로 확인하는 것만으로 충분합니다.

## 15.3 JSON API 호출 예제 (12장 연계)

실무에서 가장 흔한 패턴은 REST API 서버에 요청을 보내고 JSON 형식의 응답을 받아 처리하는 것입니다. 12장에서 다룬 `QJsonDocument`, `QJsonObject`, `QJsonArray`를 그대로 활용하면 됩니다. 이번에는 JSON 본문을 담아 POST 요청을 보내고, 역시 JSON으로 응답을 받는 예제를 만들어 보겠습니다.

```cpp
// apiclient.h
#pragma once

#include <QObject>
#include <QNetworkAccessManager>
#include <QNetworkReply>

class ApiClient : public QObject
{
    Q_OBJECT

public:
    explicit ApiClient(QObject *parent = nullptr);

    // 로그인 요청을 보낸다. 결과는 loginSucceeded/loginFailed 시그널로 알려준다.
    void login(const QString &userId, const QString &password);

signals:
    void loginSucceeded(const QString &displayName, const QString &token);
    void loginFailed(const QString &reason);

private:
    QNetworkAccessManager *m_manager;
};
```

```cpp
// apiclient.cpp
#include "apiclient.h"

#include <QNetworkRequest>
#include <QJsonDocument>
#include <QJsonObject>
#include <QUrl>

ApiClient::ApiClient(QObject *parent)
    : QObject(parent)
    , m_manager(new QNetworkAccessManager(this))
{
}

void ApiClient::login(const QString &userId, const QString &password)
{
    // 1. 12장에서 배운 방식으로 요청 본문을 JSON으로 구성한다.
    QJsonObject payload;
    payload["userId"] = userId;
    payload["password"] = password;

    const QByteArray body = QJsonDocument(payload).toJson(QJsonDocument::Compact);

    // 2. 요청 헤더와 URL을 준비한다.
    QNetworkRequest request(QUrl("https://api.example.com/v1/login"));
    request.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");

    // 3. POST 요청을 비동기로 전송한다.
    QNetworkReply *reply = m_manager->post(request, body);

    connect(reply, &QNetworkReply::finished, this, [this, reply]() {
        reply->deleteLater();

        if (reply->error() != QNetworkReply::NoError) {
            emit loginFailed(reply->errorString());
            return;
        }

        const QByteArray responseBody = reply->readAll();
        const QJsonDocument doc = QJsonDocument::fromJson(responseBody);

        if (!doc.isObject()) {
            emit loginFailed(tr("서버 응답 형식이 올바르지 않습니다."));
            return;
        }

        const QJsonObject obj = doc.object();
        const bool success = obj.value("success").toBool(false);

        if (!success) {
            const QString message = obj.value("message").toString(tr("알 수 없는 오류"));
            emit loginFailed(message);
            return;
        }

        const QString displayName = obj.value("displayName").toString();
        const QString token = obj.value("token").toString();
        emit loginSucceeded(displayName, token);
    });
}
```

이렇게 `ApiClient`를 별도 클래스로 분리해 두면, UI 코드는 네트워크 세부사항을 몰라도 됩니다. UI 쪽에서는 다음과 같이 시그널만 연결하면 됩니다.

```cpp
auto *client = new ApiClient(this);

connect(client, &ApiClient::loginSucceeded, this, [this](const QString &name, const QString &token) {
    statusBar()->showMessage(tr("%1님, 환영합니다.").arg(name));
    // token은 이후 요청의 인증 헤더 등에 사용할 수 있다.
});

connect(client, &ApiClient::loginFailed, this, [this](const QString &reason) {
    QMessageBox::warning(this, tr("로그인 실패"), reason);
});

client->login(userIdEdit->text(), passwordEdit->text());
```

이 구조는 UI와 네트워크 로직을 분리하는 전형적인 방법으로, 나중에 API가 바뀌거나 테스트 코드를 작성할 때도 유리합니다.

## 15.4 QTcpSocket과 QTcpServer로 TCP 통신하기

REST API처럼 HTTP 위에서 동작하는 통신이 아니라, 직접 설계한 프로토콜로 두 프로그램이 통신해야 하는 경우도 있습니다. 예를 들어 사내에서 만든 계측 장비와 통신하거나, 같은 네트워크 안의 두 프로그램이 실시간으로 짧은 메시지를 주고받아야 하는 상황입니다. 이럴 때는 `QTcpSocket`과 `QTcpServer`로 TCP 소켓을 직접 다룹니다.

여기서는 가장 단순한 예제인 **에코(echo) 서버/클라이언트**를 만들어 봅니다. 에코 서버는 클라이언트가 보낸 데이터를 그대로 되돌려 보내는 서버입니다.

### 15.4.1 에코 서버

```cpp
// echoserver.h
#pragma once

#include <QObject>
#include <QTcpServer>

class EchoServer : public QObject
{
    Q_OBJECT

public:
    explicit EchoServer(QObject *parent = nullptr);

    bool start(quint16 port);

private slots:
    void onNewConnection();

private:
    QTcpServer *m_server;
};
```

```cpp
// echoserver.cpp
#include "echoserver.h"

#include <QTcpSocket>
#include <QDebug>

EchoServer::EchoServer(QObject *parent)
    : QObject(parent)
    , m_server(new QTcpServer(this))
{
    connect(m_server, &QTcpServer::newConnection,
            this, &EchoServer::onNewConnection);
}

bool EchoServer::start(quint16 port)
{
    // QHostAddress::Any는 모든 네트워크 인터페이스에서 연결을 받아들인다.
    if (!m_server->listen(QHostAddress::Any, port)) {
        qWarning() << "서버 시작 실패:" << m_server->errorString();
        return false;
    }
    qInfo() << "에코 서버가 포트" << port << "에서 대기 중입니다.";
    return true;
}

void EchoServer::onNewConnection()
{
    while (m_server->hasPendingConnections()) {
        QTcpSocket *client = m_server->nextPendingConnection();

        connect(client, &QTcpSocket::readyRead, this, [client]() {
            // 받은 데이터를 그대로 되돌려 보낸다.
            const QByteArray data = client->readAll();
            client->write(data);
        });

        connect(client, &QTcpSocket::disconnected, client, &QTcpSocket::deleteLater);
    }
}
```

한 대의 서버가 여러 클라이언트와 동시에 통신할 수 있는 이유는, `QTcpServer`가 연결이 들어올 때마다 `newConnection` 시그널만 발생시키고 실제 데이터 송수신은 각 연결에 대응하는 `QTcpSocket` 객체가 독립적으로 처리하기 때문입니다. 별도의 스레드를 만들지 않아도 이벤트 루프가 여러 소켓의 `readyRead` 시그널을 순서대로 처리해 줍니다. 다만 각 요청 처리에 시간이 오래 걸리는 무거운 연산이 섞여 있다면, 14장에서 다룬 `QThread` 기반 워커로 그 연산만 분리하는 것을 고려해야 합니다.

### 15.4.2 에코 클라이언트

```cpp
// echoclient.h
#pragma once

#include <QObject>
#include <QTcpSocket>

class EchoClient : public QObject
{
    Q_OBJECT

public:
    explicit EchoClient(QObject *parent = nullptr);

    void connectToServer(const QString &host, quint16 port);
    void sendMessage(const QString &message);

signals:
    void messageEchoed(const QString &message);
    void connectionFailed(const QString &reason);

private:
    QTcpSocket *m_socket;
};
```

```cpp
// echoclient.cpp
#include "echoclient.h"

EchoClient::EchoClient(QObject *parent)
    : QObject(parent)
    , m_socket(new QTcpSocket(this))
{
    connect(m_socket, &QTcpSocket::readyRead, this, [this]() {
        const QByteArray data = m_socket->readAll();
        emit messageEchoed(QString::fromUtf8(data));
    });

    connect(m_socket, &QTcpSocket::errorOccurred, this, [this](QAbstractSocket::SocketError) {
        emit connectionFailed(m_socket->errorString());
    });
}

void EchoClient::connectToServer(const QString &host, quint16 port)
{
    // connectToHost()는 비동기로 동작한다. 실제 연결 여부는
    // connected 시그널이나 errorOccurred 시그널로 확인해야 한다.
    m_socket->connectToHost(host, port);
}

void EchoClient::sendMessage(const QString &message)
{
    if (m_socket->state() != QAbstractSocket::ConnectedState) {
        emit connectionFailed(tr("서버에 연결되어 있지 않습니다."));
        return;
    }
    m_socket->write(message.toUtf8());
}
```

`connectToHost()`, `write()` 모두 즉시 반환되는 비동기 함수입니다. 연결이 실제로 맺어졌는지는 `connected` 시그널로, 데이터가 도착했는지는 `readyRead` 시그널로 알 수 있습니다. 콘솔 프로그램에서 학습용으로 `waitForConnected()`, `waitForReadyRead()`처럼 블로킹으로 동작하는 함수를 사용하는 예제를 종종 볼 수 있지만, 이런 함수는 호출한 스레드를 멈춰 세우기 때문에 **GUI 스레드에서는 사용을 피해야 합니다.**

## 15.5 네트워크 작업과 UI 스레드 (14장 연계)

14장에서 무거운 연산을 `QThread`로 분리해 UI가 멈추지 않도록 하는 방법을 배웠습니다. 네트워크 통신 역시 "오래 걸릴 수 있는 작업"이라는 점에서 비슷해 보이지만, 처리 방식에는 중요한 차이가 있습니다.

- `QNetworkAccessManager`, `QTcpSocket` 같은 클래스는 내부적으로 논블로킹 소켓과 이벤트 루프를 사용합니다. 요청을 보낸 뒤 바로 제어권이 돌아오고, 응답은 시그널로 통지됩니다. 따라서 **별도의 스레드 없이도** UI 스레드에서 직접 사용해도 화면이 멈추지 않습니다.
- 반대로 `waitForReadyRead()`처럼 이름에 `waitFor`가 붙은 함수들은 응답이 올 때까지 현재 스레드를 블로킹합니다. 콘솔 애플리케이션이나 워커 스레드 안에서는 코드를 단순하게 만들기 위해 종종 사용되지만, GUI 스레드에서 직접 호출하면 그 시간만큼 화면이 완전히 멈춥니다.
- 응답 이후에 처리해야 하는 작업 자체가 무거운 경우도 있습니다. 예를 들어 서버에서 내려받은 대용량 데이터를 파싱하고 복잡하게 가공해야 한다면, 네트워크 요청은 비동기로 처리하되 응답을 받은 뒤의 가공 작업만 14장에서 배운 워커 스레드에 맡기는 조합도 가능합니다.
- 레거시 C 라이브러리처럼 블로킹 API로만 통신을 제공하는 라이브러리를 어쩔 수 없이 사용해야 한다면, 그 호출 전체를 `QThread` 워커 안에 감싸서 UI 스레드와 분리하는 것이 유일한 방법입니다.

요청이 예상보다 오래 걸리는 상황에 대비해 타임아웃을 직접 구현하는 것도 실무에서 자주 필요합니다. `QNetworkReply`에는 자체 타임아웃 기능이 없으므로(Qt 버전에 따라 `QNetworkRequest::setTransferTimeout()`이 제공되기도 합니다), 다음처럼 `QTimer`와 `abort()`를 조합해 직접 구현할 수도 있습니다.

```cpp
QNetworkReply *reply = m_manager->get(request);

auto *timeoutTimer = new QTimer(this);
timeoutTimer->setSingleShot(true);
connect(timeoutTimer, &QTimer::timeout, reply, &QNetworkReply::abort);
timeoutTimer->start(5000); // 5초 안에 응답이 없으면 요청을 취소한다.

connect(reply, &QNetworkReply::finished, this, [reply, timeoutTimer]() {
    timeoutTimer->stop();
    timeoutTimer->deleteLater();
    // ... 응답 처리 ...
    reply->deleteLater();
});
```

## 요약

- QtNetwork 모듈은 고수준 HTTP 통신을 위한 `QNetworkAccessManager`/`QNetworkReply`와, 저수준 소켓 통신을 위한 `QTcpSocket`/`QTcpServer` 두 갈래를 제공합니다.
- `QNetworkAccessManager::get()`/`post()`는 즉시 반환되는 비동기 함수이며, 응답은 `QNetworkReply`의 `finished` 시그널로 통지됩니다. 응답 처리 후에는 `reply->deleteLater()`로 해제해야 합니다.
- 12장에서 배운 `QJsonDocument`/`QJsonObject`를 활용하면 REST API의 JSON 요청 본문 작성과 응답 파싱을 자연스럽게 처리할 수 있습니다.
- `QTcpServer`는 `newConnection` 시그널로 새 연결을 알리고, 각 연결은 `QTcpSocket`의 `readyRead` 시그널로 데이터 수신을 처리합니다. 에코 서버/클라이언트 예제로 기본 흐름을 살펴보았습니다.
- Qt의 네트워크 클래스는 논블로킹 소켓 기반이므로 대부분 별도 스레드 없이 UI 스레드에서 사용해도 안전합니다. 다만 `waitForXxx()` 같은 블로킹 함수는 GUI 스레드에서 피해야 하며, 정말 블로킹 API만 제공하는 라이브러리를 다룰 때는 14장의 `QThread` 워커 패턴을 함께 사용합니다.

## 연습문제

1. `QNetworkAccessManager::get()`을 호출한 직후 응답 데이터를 바로 사용할 수 없는 이유를 설명하고, 응답을 올바르게 처리하려면 어떤 시그널을 사용해야 하는지 서술하시오.
2. 15.3절의 `ApiClient::login()` 예제를 참고하여, 회원가입 요청(사용자 ID, 비밀번호, 이메일을 JSON으로 전송)을 보내는 `signup()` 메서드를 설계하시오. 성공/실패에 따라 어떤 시그널을 발생시킬지도 함께 설계하시오.
3. `QTcpServer`가 하나의 포트에서 여러 클라이언트의 연결을 동시에 처리할 수 있는 이유를 `newConnection` 시그널과 `QTcpSocket` 객체의 관계를 근거로 설명하시오.
4. `waitForConnected()`, `waitForReadyRead()`와 같은 블로킹 함수를 GUI 스레드에서 사용하면 안 되는 이유를 설명하고, 부득이하게 블로킹 API만 제공하는 라이브러리를 사용해야 한다면 어떻게 처리해야 하는지 14장의 내용과 연결지어 설명하시오.
5. 15.5절의 타임아웃 예제 코드에서 `timeoutTimer`가 이미 멈춰 있는데 나중에 `timeout` 시그널이 뒤늦게 발생하면 어떤 문제가 생길 수 있는지 생각해 보고, 이를 방지하려면 코드를 어떻게 수정하면 좋을지 서술하시오.
